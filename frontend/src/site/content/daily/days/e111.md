## Understand

### Loaded is not the same as correct

The load of Day 110 can finish with status `ok` and the table can still be wrong: pages were skipped by a paging bug, a cleaning rule dropped more rows than intended, an update was lost, a column was filled with the wrong value. The database accepted every row it was given, so constraints cannot detect rows it was never given. **Validation** is the step that compares the result with expectations, using evidence that does not come from the load code itself. It is the API counterpart of Day 95's CSV validation and Day 100's reconciliation, and it uses the same ideas on API data: counts, checksums, key checks and independent checks of values.

### Four families of checks

**Counts.** Rows in the table against the rows you expected. The expectation comes from the source: the API's own total (here 120), or the count of rows your run says it loaded plus the rows already there. A count can be exact (equality) or tolerant (within a window, for sources that change during the read); say which. Count per group is stronger than the total: orders per status per day catches two errors that cancel out in the total.

**Keys.** The primary key is unique and never null; the database enforces it, and a query confirms it for tables that lack the constraint (staging, copies). Foreign keys have parents (every `customer_id` exists in the customer table, when there is one). Keys form no unexpected gaps: ids that run 1 to 120 with 118 rows present point to two missing orders, which is a detectable pattern for sequential ids and not for others.

**Nulls and values.** Required columns have no NULLs, even when the constraints would allow them. Values are in range (`amount_cents >= 0`), in the accepted vocabulary (`status` is one of three words, `currency` one of two) and plausible (`created_at` not in the future, not before the system existed). Value checks count the rows that break each rule; the count should be zero or the failing rows should be accounted for in the reject table (Day 109).

**Agreement with the source.** Aggregates that the source can state independently: the sum of `amount_cents`, the number of orders per status, the earliest and latest `created_at`. And **sampling**: pick some records, fetch them again from the source (`GET /orders/{id}`), and compare every field with the table row. Sampling is the only check that tests values the aggregates would average out, and the only one that finds a column that was loaded into the wrong place.

### What sampling can and cannot prove

Take a **random sample** with a seeded generator, so that the check is repeatable and an engineer can run the same sample again. A sample finds **widespread** problems with high probability and **rare** problems with low probability. If 12 of 120 rows are wrong and you sample 10, the chance that the sample contains no bad row is `C(108, 10) / C(120, 10)`, about 33 percent, so a clean sample is weak evidence. A single wrong row among 120 is missed 92 percent of the time by a sample of 10. This is why sampling complements aggregates and counts and never replaces them: counts and sums are exhaustive over all rows but blind to compensating errors, samples see every field but only a few rows. Using both covers most failures.

### Severity and the report

Not every failed check should stop a pipeline. A **blocking** check (row count mismatch, duplicate keys, a null in a required column) means the table must not be used, so the run fails and nobody reads the data until a person decides. A **warning** check (freshness older than expected by a few hours, a sample mismatch rate below a threshold) lets the run finish with a visible note. The report prints one line per check (`PASS`, `FAIL` or `WARN`, a name, and the numbers behind it) and ends with an overall status. Writing the report as data (a list of check results) instead of print statements lets the load log of Day 110 store it and lets the scheduler read the overall verdict.

### Common misconception

Learners validate with the same code path that produced the data: they count the rows of the DataFrame they loaded and compare them with the rows of the table. That proves the insert worked and nothing about the extract. Take the expectation from the **source of truth** (the API total, the source's own sum), not from your own intermediate result.

### Why it matters

Silent errors in a table are found by the people who use it, usually weeks later, in a meeting. A validation report found by the pipeline the same night turns the same error into a ticket.

## Syntax and key functions

```sql-syntax
SELECT 'row count' AS check_name, count(*) = 120 AS ok FROM orders
UNION ALL SELECT 'unique keys', count(*) = count(DISTINCT order_id) FROM orders
UNION ALL SELECT 'no null status', count(*) FILTER (WHERE status IS NULL) = 0 FROM orders
UNION ALL SELECT 'amount in range', count(*) FILTER (WHERE amount_cents < 0) = 0 FROM orders;
```

```python
import random

rng = random.Random(7)
sample_ids = sorted(rng.sample(all_ids, 10))
mismatches = [i for i in sample_ids if table_row(i) != source_row(i)]
```

| Item | What it does or returns |
|---|---|
| `count(*) FILTER (WHERE cond)` | Count of rows meeting a condition (PostgreSQL). |
| `count(DISTINCT col)` | Number of distinct values; compare with `count(*)`. |
| `UNION ALL` of checks | One row per check, same columns. |
| `min(col)`, `max(col)` | Range check for dates and numbers. |
| `random.Random(7).sample(population, k)` | Repeatable sample without replacement. |
| `math.comb(n, k)` | Binomial coefficient for sample-size arithmetic. |
| `GET /orders/{id}` | Source record for a spot check. |

## Learn by example

### Example 1: Validation queries on PostgreSQL syntax (PGlite)

`loaded_orders` is built with `generate_series` to hold the 120 orders of the stand-in, then damaged the way real loads are: two orders (60 and 61) were never loaded and one row has a NULL currency. A single query returns every check as a row with the measured value, the expected value and a pass/fail flag. The browser database already holds Northwind's `orders`, so the table is named `loaded_orders`.

```sql run
CREATE TABLE loaded_orders (
    order_id integer PRIMARY KEY, customer_id integer, amount_cents integer,
    currency text, status text, created_at timestamptz);
INSERT INTO loaded_orders
SELECT i, i * 7 % 25 + 1, 1000 + i * 137 % 9000,
       CASE WHEN i % 4 = 0 THEN 'USD' ELSE 'EUR' END,
       (ARRAY['paid', 'paid', 'refunded', 'failed'])[i % 4 + 1],
       '2026-03-01T00:00:00Z'::timestamptz + ((i - 1) / 4) * interval '1 day'
         + (i * 7 % 24) * interval '1 hour' + (i * 13 % 60) * interval '1 minute'
FROM generate_series(1, 120) AS i;
DELETE FROM loaded_orders WHERE order_id IN (60, 61);
UPDATE loaded_orders SET currency = NULL WHERE order_id = 7;
SELECT check_name, value, expected, value = expected AS ok FROM (
    SELECT 1 AS k, 'row count' AS check_name, count(*) AS value, 120::bigint AS expected FROM loaded_orders
    UNION ALL SELECT 2, 'distinct keys', count(DISTINCT order_id), count(*) FROM loaded_orders
    UNION ALL SELECT 3, 'missing ids in 1..120', 120 - count(*), 0 FROM loaded_orders
    UNION ALL SELECT 4, 'null currency', count(*) FILTER (WHERE currency IS NULL), 0 FROM loaded_orders
    UNION ALL SELECT 5, 'unknown status', count(*) FILTER (WHERE status NOT IN ('paid', 'refunded', 'failed')), 0 FROM loaded_orders
    UNION ALL SELECT 6, 'negative amount', count(*) FILTER (WHERE amount_cents < 0), 0 FROM loaded_orders
    UNION ALL SELECT 7, 'latest day', (max(created_at AT TIME ZONE 'UTC'))::date - date '2026-03-01', 29 FROM loaded_orders
) t ORDER BY k;
```

```output
check_name | value | expected | ok
row count | 118 | 120 | false
distinct keys | 118 | 118 | true
missing ids in 1..120 | 2 | 0 | false
null currency | 1 | 0 | false
unknown status | 0 | 0 | true
negative amount | 0 | 0 | true
latest day | 29 | 29 | true
```

Three checks fail and point at the defects: the row count is 118 and the missing ids number 2 (the pattern for sequential keys), and one currency is NULL. The others pass.

### Example 2: Compare the table with the source's own figures (Python)

The expected figures come from the source side: the total and the sum computed from the source records, orders per status, and the first and last day. The table is `sqlite3`. A `report` function returns a list of `(status, name, detail)` results and the overall verdict. It runs on a correct load, then on a damaged one where one order's amount was changed (the count still matches but the sum and a group do not).

```python run
import sqlite3

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

source = ORDERS
expected = {
    "rows": len(source),
    "sum": sum(o["amount_cents"] for o in source),
    "by_status": {s: sum(1 for o in source if o["status"] == s) for s in ("failed", "paid", "refunded")},
    "first": min(o["created_at"] for o in source)[:10],
    "last": max(o["created_at"] for o in source)[:10],
}

def build(damage=False):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)")
    conn.executemany("INSERT INTO orders VALUES (:order_id, :customer_id, :amount_cents, :currency, :status, :created_at)", source)
    if damage:
        conn.execute("UPDATE orders SET amount_cents = amount_cents + 100, status = 'paid' WHERE order_id = 3")
    return conn

def report(conn):
    one = lambda sql: conn.execute(sql).fetchone()[0]
    by_status = dict(conn.execute("SELECT status, COUNT(*) FROM orders GROUP BY status ORDER BY status").fetchall())
    checks = [
        ("blocking", "row count", one("SELECT COUNT(*) FROM orders") == expected["rows"]),
        ("blocking", "sum of amount_cents", one("SELECT SUM(amount_cents) FROM orders") == expected["sum"]),
        ("blocking", "orders per status", by_status == expected["by_status"]),
        ("blocking", "unique keys", one("SELECT COUNT(DISTINCT order_id) FROM orders") == expected["rows"]),
        ("blocking", "no null required", one("SELECT COUNT(*) FROM orders WHERE currency IS NULL OR status IS NULL") == 0),
        ("warning", "date range", (one("SELECT MIN(substr(created_at, 1, 10)) FROM orders"), one("SELECT MAX(substr(created_at, 1, 10)) FROM orders")) == (expected["first"], expected["last"])),
    ]
    lines = [("PASS" if ok else "FAIL" if sev == "blocking" else "WARN") + " " + name for sev, name, ok in checks]
    verdict = "FAILED" if any(not ok for sev, _, ok in checks if sev == "blocking") else "OK"
    return lines, verdict

for damage in (False, True):
    lines, verdict = report(build(damage))
    print(verdict, [line for line in lines if not line.startswith("PASS")])
print(expected["rows"], expected["by_status"], expected["first"], expected["last"])
```

```output
OK []
FAILED ['FAIL sum of amount_cents', 'FAIL orders per status']
120 {'failed': 30, 'paid': 60, 'refunded': 30} 2026-03-01 2026-03-30
```

The damaged load has the right number of rows and the right keys, so those checks pass, and the sum and the per-status counts expose the change. That is why the report has several checks and not one.

### Example 3: Sampling, and how much a sample proves

The first part draws a seeded sample of 10 ids from the 120 and compares each table row with the source record, for a table in which order 17 has a wrong status. The sample may or may not contain order 17; the printed result says which. The second part computes, with `math.comb`, the probability that a random sample of 10 contains none of the bad rows, for 1, 12 and 40 bad rows.

```python run
import math
import random

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

source = {o["order_id"]: o for o in ORDERS}
table = {k: dict(v) for k, v in source.items()}
table[17]["status"] = "failed" if source[17]["status"] != "failed" else "paid"

rng = random.Random(7)
sample = sorted(rng.sample(sorted(source), 10))
mismatched = [i for i in sample if table[i] != source[i]]
print(sample)
print("mismatches:", mismatched, "order 17 in sample:", 17 in sample)

for bad in (1, 12, 40):
    miss = math.comb(120 - bad, 10) / math.comb(120, 10)
    print(bad, "bad rows: chance a sample of 10 misses all of them", round(miss, 2))
print("sample size for 5 bad rows missing less than 5%:", next(k for k in range(1, 121) if math.comb(115, k) / math.comb(120, k) < 0.05))
```

```output
[7, 10, 13, 20, 42, 47, 51, 69, 84, 106]
mismatches: [] order 17 in sample: False
1 bad rows: chance a sample of 10 misses all of them 0.92
12 bad rows: chance a sample of 10 misses all of them 0.33
40 bad rows: chance a sample of 10 misses all of them 0.01
sample size for 5 bad rows missing less than 5%: 54
```

This sample was clean and missed the bad order 17, which is the normal outcome: with one bad row in 120, ten sampled rows miss it 92 percent of the time. Aggregate checks (the sum and the per-status counts of Example 2) catch it every time, and samples catch what aggregates cannot.

### Example 4: Spot-check against the real source over HTTP

This local example loads 120 orders into `sqlite3`, corrupts the amount of order 40 in the table, and then spot-checks a seeded sample of ids by calling `GET /orders/{id}` on the local stand-in server with `requests`. It compares every field and lists mismatching ids and fields. The sample covers order 40 with this seed, which the first output line shows; with a seed that did not draw it, the same corrupted table would pass.

```python local
import random
import sqlite3

import json
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import parse_qs, urlparse

import requests

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

API_KEY = "demo-key-123"

def start_server(orders, rate_limit_every=0):
    state = {"requests": 0, "orders": {o["order_id"]: dict(o) for o in orders}}

    def route(method, parts, query, body):
        table = state["orders"]
        if parts == ["orders"] and method == "GET":
            rows = [table[k] for k in sorted(table)]
            if "cursor" in query:
                start = int(query["cursor"] or 0)
                size = int(query.get("limit", 25))
                nxt = start + size
                return 200, {"data": rows[start:nxt], "next_cursor": str(nxt) if nxt < len(rows) else None}
            if "offset" in query:
                start, size = int(query["offset"]), int(query.get("limit", 25))
                return 200, {"data": rows[start:start + size], "offset": start, "total": len(rows)}
            page, size = int(query.get("page", 1)), int(query.get("page_size", 20))
            if page < 1 or not 1 <= size <= 100:
                return 400, {"error": "bad paging parameters"}
            pages = -(-len(rows) // size)
            return 200, {"data": rows[(page - 1) * size:page * size], "page": page, "total_pages": pages}
        if parts == ["orders"] and method == "POST":
            if not body or "customer_id" not in body:
                return 422, {"error": "customer_id is required"}
            new_id = max(table) + 1
            table[new_id] = {"order_id": new_id, **body}
            return 201, table[new_id]
        if len(parts) == 2 and parts[0] == "orders" and parts[1].isdigit():
            key = int(parts[1])
            if key not in table:
                return 404, {"error": "order not found"}
            if method == "GET":
                return 200, table[key]
            if method == "PUT":
                table[key] = {"order_id": key, **body}
                return 200, table[key]
            if method == "DELETE":
                del table[key]
                return 204, None
        return 404, {"error": "no such route"}

    class Handler(BaseHTTPRequestHandler):
        def log_message(self, *args):
            pass

        def handle_request(self, method):
            state["requests"] += 1
            length = int(self.headers.get("Content-Length") or 0)
            body = json.loads(self.rfile.read(length)) if length else None
            if self.headers.get("X-Api-Key") != API_KEY:
                status, payload, extra = 401, {"error": "invalid api key"}, {}
            elif rate_limit_every and state["requests"] % rate_limit_every == 0:
                status, payload, extra = 429, {"error": "slow down"}, {"Retry-After": "2"}
            else:
                url = urlparse(self.path)
                query = {k: v[0] for k, v in parse_qs(url.query, keep_blank_values=True).items()}
                status, payload = route(method, url.path.strip("/").split("/"), query, body)
                extra = {}
            data = b"" if payload is None else json.dumps(payload).encode()
            self.send_response(status)
            self.send_header("Content-Type", "application/json")
            self.send_header("Content-Length", str(len(data)))
            for name, value in extra.items():
                self.send_header(name, value)
            self.end_headers()
            self.wfile.write(data)

        do_GET = lambda self: self.handle_request("GET")
        do_POST = lambda self: self.handle_request("POST")
        do_PUT = lambda self: self.handle_request("PUT")
        do_DELETE = lambda self: self.handle_request("DELETE")

    server = HTTPServer(("127.0.0.1", 0), Handler)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    return server, f"http://127.0.0.1:{server.server_port}", state

server, base, state = start_server(ORDERS)
try:
    conn = sqlite3.connect(":memory:")
    conn.row_factory = sqlite3.Row
    conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)")
    conn.executemany("INSERT INTO orders VALUES (:order_id, :customer_id, :amount_cents, :currency, :status, :created_at)", ORDERS)
    conn.execute("UPDATE orders SET amount_cents = amount_cents + 1 WHERE order_id = 40")

    ids = [row[0] for row in conn.execute("SELECT order_id FROM orders ORDER BY order_id")]
    sample = sorted(random.Random(2).sample(ids, 15))
    headers = {"X-Api-Key": API_KEY}
    problems = {}
    for order_id in sample:
        source = requests.get(f"{base}/orders/{order_id}", headers=headers, timeout=5).json()
        row = dict(conn.execute("SELECT * FROM orders WHERE order_id = ?", (order_id,)).fetchone())
        diff = sorted(k for k in source if source[k] != row.get(k))
        if diff:
            problems[order_id] = diff
    print(len(sample), 40 in sample)
    print(problems)
finally:
    server.shutdown()
    server.server_close()
```

```output
15 True
{40: ['amount_cents']}
```

## Real-world applications

- **Nightly sign-off.** The validation report is stored with the load log; the dashboard refresh waits for the overall verdict to be `OK`.
- **Provider disputes.** A per-status count that differs from the provider's own report is concrete evidence in a conversation about missing orders.
- **Regression checks after a code change.** Running the same checks and a seeded sample before and after a pipeline change shows whether the change altered any loaded values.
- **Data contracts.** The checks (null rules, vocabularies, ranges) document what the downstream analysts can rely on.

## Daily review

### Key takeaways

- A load that did not fail is not validated; take expectations from the source, not from your own intermediate data.
- Four families: counts, keys, nulls and values, agreement with the source.
- Per-group counts and sums catch errors that cancel in totals; samples catch value errors that aggregates average out.
- A sample is weak evidence for rare problems; compute what it can detect.
- Report each check with a severity; blocking failures fail the run.

### Common mistakes

- **Comparing the table with the DataFrame you loaded.** It proves the insert, not the extract. Compare with the source's totals.
- **Only checking the total count.** Compensating errors pass. Add a sum and per-group counts.
- **Unseeded samples.** The check cannot be repeated. Seed the generator.
- **Treating a clean sample as proof.** One bad row in 120 is missed most of the time. Use aggregates too.
- **Checks that cannot fail.** Run the report on a deliberately damaged table once.

### Revision notes

- Counts, keys, nulls and values, source agreement.
- SQL: `count(*) FILTER (WHERE ...)`, `count(DISTINCT ...)`, `UNION ALL` of checks.
- `random.Random(seed).sample`, `math.comb` for sample arithmetic.
- Severities: blocking vs warning; overall verdict.

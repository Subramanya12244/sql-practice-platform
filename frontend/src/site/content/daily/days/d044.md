## Objectives

- Add rows with `INSERT ... VALUES` (one or several rows) and `INSERT ... SELECT`.
- Change existing rows with `UPDATE ... SET ... WHERE`, including expressions that use the current value.
- Remove rows with `DELETE ... WHERE` and explain why the `WHERE` clause matters.
- Use `RETURNING` to see the rows an `INSERT`, `UPDATE` or `DELETE` touched, including generated values such as ids.
- Apply safe practice: preview with `SELECT`, verify afterwards, and read constraint errors.

## Understand

### Queries read, statements write

Every statement so far was a `SELECT`: it reads data and changes nothing. Three other statements change the contents of a table. They are called **DML**, data manipulation language. `INSERT` adds new rows, `UPDATE` changes values in existing rows, and `DELETE` removes rows. They write to the database, so a mistake is not harmless: an `UPDATE` without a condition rewrites every row of the table. In this course every statement you run in the browser is wrapped in a transaction that is rolled back at the end, so nothing you do here is saved and Northwind is safe. In a real database a **transaction** groups statements so that they all take effect together (`COMMIT`) or not at all (`ROLLBACK`); without one, each statement is committed as soon as it succeeds. The browser runner forbids the `BEGIN`, `COMMIT` and `ROLLBACK` keywords because it handles the transaction for you.

### INSERT

`INSERT INTO table (column_list) VALUES (value_list)` creates one row. Always name the columns. The values are matched to the columns by position, so the number and the order must agree. Columns you leave out receive their **default** value (set in the table definition, day 45) or NULL if there is no default. Columns that are `SERIAL` (such as `shipper_id`) generate the next number by themselves, so you normally leave them out and let the database choose the id. A column declared `NOT NULL` without a default must be supplied: leaving out `company_name` fails with "null value in column "company_name" ... violates not-null constraint". If the value list is shorter than the column list the error is "INSERT has more target columns than expressions".

To add several rows at once, write several value lists separated by commas: `VALUES (...), (...)`. One statement adding many rows is faster than many statements. To copy rows that already exist, replace `VALUES` with a query: `INSERT INTO table (columns) SELECT ... FROM ...`. The `SELECT` may transform, filter or join as much as it likes, as long as its columns match the target list.

### UPDATE

`UPDATE table SET column = expression [, column2 = expression2] WHERE condition` changes the rows that satisfy the condition. The right side of `SET` may use the current value: `unit_price = ROUND(unit_price * 1.10, 2)` raises the price by ten percent. Everything on the right is evaluated with the old values of the row, so `SET a = b, b = a` swaps two columns. The `WHERE` clause works exactly as in `SELECT` (day 33): it decides which rows change. **Without a `WHERE` clause every row is updated.** The same is true of `DELETE`.

### DELETE

`DELETE FROM table WHERE condition` removes the matching rows. Like `UPDATE`, it deletes everything if you forget `WHERE`. Deleting is also limited by relationships between tables: a row cannot be deleted while another table's foreign key points at it (day 31). `DELETE FROM customers WHERE customer_id = 'ALFKI'` fails with `update or delete on table "customers" violates foreign key constraint "orders_customer_id_fkey" on table "orders"`, because ALFKI still has orders. The database protects the consistency of the data; you must delete the child rows first, or design the constraint differently (day 45).

### RETURNING: see what you changed

In PostgreSQL, `INSERT`, `UPDATE` and `DELETE` can end with `RETURNING column_list`, which returns the affected rows as a result table, just like a `SELECT`. It shows the values after an insert or update and the removed values after a delete. It is the best way to learn the generated id of a new row without a second query, and to check that the statement touched the rows you expected. `RETURNING` is a PostgreSQL feature; other databases use different syntax (SQL Server uses `OUTPUT`), so check the documentation of the database you work with. The order of the returned rows is not guaranteed, so do not rely on it.

### Safe practice

1. **Preview with `SELECT`.** Write the `WHERE` first as a `SELECT` and look at the rows it picks, then change the keyword to `UPDATE` or `DELETE`.
2. **Check the count.** Compare the number of affected rows with what you expected.
3. **Use `RETURNING` or a trailing `SELECT`** to verify the result.
4. **Work in a transaction** on a real database and commit only after checking.
5. **Prefer a key in the `WHERE`** (`WHERE shipper_id = 3`) for single-row changes, so a typo cannot widen the change.

### Common misconception

Learners believe a `DELETE` or `UPDATE` always touches one row. It touches every row the condition matches, and every row if there is no condition, and it reports success either way. Another belief is that you can put any value in any column: constraints (NOT NULL, foreign keys, and others from day 45) reject changes that would break the rules.

### Why it matters

Analysts mostly read, but data engineers and analysts who maintain reference tables, fix bad values or load new data write every day. Knowing the three statements, `RETURNING` and the safety habits is what makes changes reviewable and reversible.

## Syntax and key functions

```sql-syntax
INSERT INTO table_name (column_1, column_2)
VALUES (value_1, value_2), (value_3, value_4)
RETURNING column_1, column_2;

INSERT INTO table_name (column_1, column_2)
SELECT expression_1, expression_2 FROM other_table WHERE condition
RETURNING *;

UPDATE table_name
SET column_1 = expression, column_2 = expression
WHERE condition
RETURNING column_1;

DELETE FROM table_name
WHERE condition
RETURNING *;
```

| Part | Meaning |
|---|---|
| `INSERT INTO t (cols) VALUES (...)` | New row; omitted columns get their default or NULL |
| `INSERT INTO t (cols) SELECT ...` | New rows copied or computed from a query |
| `SET col = expr` | New value; `expr` may use the old values of the row |
| `WHERE` | Which rows to change or delete; missing means all rows |
| `RETURNING cols` | The affected rows after the change (PostgreSQL) |

## Learn by example

In the browser every example below is rolled back, so the shippers, products and order lines you change reappear in their original state on the next run. Each statement ends by returning rows, as the runner requires.

### Example 1: Insert one row and read back its id

The column list names `company_name` and `phone`, and the values follow in the same order. `shipper_id` is generated, so it is not mentioned, and `RETURNING` shows the id the database chose. There are already three shippers, so the new one is number 4.

```sql run
INSERT INTO shippers (company_name, phone)
VALUES ('Northern Freight', '555-0101')
RETURNING shipper_id, company_name, phone;
```

```output
shipper_id | company_name | phone
4 | Northern Freight | 555-0101
```

### Example 2: Defaults for the columns you leave out

Only three columns are supplied for the new product. The id is generated, and the other columns take the defaults defined in the table: no stock and not discontinued. Columns without a default would have been NULL. Naming the columns makes the statement safe even if the table later gets more columns.

```sql run
INSERT INTO products (product_name, category_id, unit_price)
VALUES ('Test Tea', 1, 12.50)
RETURNING product_id, product_name, category_id, unit_price, units_in_stock, discontinued;
```

```output
product_id | product_name | category_id | unit_price | units_in_stock | discontinued
78 | Test Tea | 1 | 12.50 | 0 | false
```

### Example 3: Several rows, and INSERT with SELECT

Two rows are added by one statement with several value lists; the second leaves the phone as an explicit NULL. The `RETURNING` clause shows both new ids. This is the multi-row form. The same statement could copy existing rows by replacing `VALUES` with a `SELECT`, for example `INSERT INTO shippers (company_name, phone) SELECT company_name || ' (backup)', phone FROM shippers WHERE shipper_id <= 2`.

```sql run
INSERT INTO shippers (company_name, phone)
VALUES ('Northern Freight', '555-0101'),
       ('Coastal Haulage', NULL)
RETURNING shipper_id, company_name, phone;
```

```output
shipper_id | company_name | phone
4 | Northern Freight | 555-0101
5 | Coastal Haulage | NULL
```

### Example 4: UPDATE with an expression and a condition

Raise by ten percent the price of the products in category 8 that cost less than 10. `ROUND` keeps two decimals. The `WHERE` selects three products, and `RETURNING` shows their new prices (the old prices were 6.00, 9.65 and 9.50). Without the `WHERE`, all 77 prices would change.

```sql run
UPDATE products
SET unit_price = ROUND(unit_price * 1.10, 2)
WHERE category_id = 8 AND unit_price < 10
RETURNING product_id, product_name, unit_price;
```

```output
product_id | product_name | unit_price
13 | Konbu | 6.60
41 | Jack's New England Clam Chowder | 10.62
45 | Rogede sild | 10.45
```

### Example 5: Several columns in one UPDATE

`SET` takes a comma-separated list, so one statement changes two columns for the rows picked by the key list. This is a typical way to retire a product: mark it discontinued and zero its stock. The `WHERE` uses `IN` with the product keys so exactly the intended rows change.

```sql run
UPDATE products
SET discontinued = true, units_in_stock = 0
WHERE product_id IN (1, 2)
RETURNING product_id, product_name, discontinued, units_in_stock;
```

```output
product_id | product_name | discontinued | units_in_stock
1 | Chai | true | 0
2 | Chang | true | 0
```

### Example 6: DELETE, then verify with a SELECT

The delete removes the small order lines (quantity below 3) of order 10279, which are two of its lines. Because the runner needs the last statement to return rows, a `SELECT` follows. It counts the lines left in the whole table inside the same transaction: 250 lines minus the 2 deleted gives 248. After the run, the rollback restores the lines. Try this on `orders` instead and PostgreSQL would refuse, because lines still reference the order.

```sql run
DELETE FROM order_details
WHERE order_id = 10279 AND quantity < 3;

SELECT COUNT(*) AS lines_left FROM order_details;
```

```output
lines_left
248
```

## Real-world applications

**Loading and maintaining reference data.** New shippers, categories and products arrive as `INSERT` statements (examples 1 to 3). Bulk loads use multi-row `INSERT` or `INSERT ... SELECT` from a staging table.

**Corrections and business changes.** Price increases, status changes and bad-value fixes are `UPDATE ... WHERE` (examples 4 and 5). Reviewing the affected rows with `SELECT` first is standard change-control practice.

**Cleaning up.** Removing test rows, duplicates or expired records uses `DELETE` with a precise `WHERE` (example 6), and foreign keys prevent orphaning data.

**Audit and feedback.** `RETURNING` gives an application the generated id of a new row and gives an engineer a log of exactly which rows changed, without a second query.

## Daily review

### Key takeaways

- `INSERT` adds rows (name the columns), `UPDATE` changes values, `DELETE` removes rows.
- `UPDATE` and `DELETE` without `WHERE` affect every row.
- Omitted columns get defaults or NULL; `SERIAL` columns generate their own ids.
- `RETURNING` returns the affected rows; their order is not guaranteed.
- Constraints (NOT NULL, foreign keys) reject changes that break the rules.
- Preview with `SELECT`, check the count, verify afterwards.

### Common mistakes

- Running `UPDATE products SET unit_price = 0` and forgetting `WHERE`. Write the `WHERE` first and test it with `SELECT`.
- Listing the values in a different order than the columns, putting a price into the wrong column or hitting a type error.
- Leaving out a `NOT NULL` column: "null value in column ... violates not-null constraint".
- Providing fewer values than columns: "INSERT has more target columns than expressions".
- Deleting a parent row that is still referenced: "update or delete ... violates foreign key constraint". Delete or move the child rows first.
- Inserting `shipper_id` by hand and colliding with the sequence later. Let the database generate ids.
- Assuming `RETURNING` rows come in a useful order. Sort with a `SELECT` if the order matters.

### Revision notes

- `INSERT INTO t (cols) VALUES (...)`; `INSERT ... SELECT`.
- `UPDATE t SET c = expr WHERE cond`; `DELETE FROM t WHERE cond`; no `WHERE` means every row.
- `RETURNING` shows new ids and changed rows.
- Preview, count, verify.

## Understand

### What a relational database is

A **database** is an organised store of data that many programs can read and change safely at the same time. A **relational database** keeps that data in **tables**, and it lets you connect tables to each other through shared values. PostgreSQL, the system used in this course, is a relational database. SQL (Structured Query Language) is the language you use to ask it questions.

The best mental picture is a set of spreadsheets that follow strict rules. Each spreadsheet describes one kind of thing: customers, products, orders. Every row describes exactly one of those things, and every column holds exactly one fact about it. Unlike a spreadsheet, the database enforces the rules: a column has a fixed data type, some columns may not be empty, and some values must be unique.

### Tables, rows and columns

A **table** holds one kind of entity. In Northwind, a small trading company's sample database, the `customers` table holds one row per customer company. A **row** (also called a record) is one customer. A **column** (also called a field) is one fact, such as `city` or `country`. The list of columns with their types is called the table's **schema** or definition.

Each column has a **data type** that limits what it can store. `integer` stores whole numbers, `numeric` stores exact decimals such as prices, `character varying` (written `VARCHAR`) stores text up to a length, `date` stores a calendar day, and `boolean` stores true or false. Choosing a type is a promise: you cannot put the word "cheap" into a `numeric` column.

A column can also be **nullable**, which means a row may have no value there at all. That "no value" is called `NULL`. In this copy of Northwind every `phone`, `address` and `region` column is NULL. NULL is not zero and not an empty string; it means "unknown or not applicable". Day 35 is entirely about NULL, so for now just recognise that it exists.

### Keys: how rows are identified and linked

A **primary key** is a column (or group of columns) whose value identifies each row uniquely and is never NULL. `customers.customer_id` is the primary key of customers: no two customers share an ID. A primary key is how the rest of the database points at one specific row.

A **foreign key** is a column that stores the primary key value of a row in another table. In `orders`, the column `customer_id` holds a customer's ID, such as `ALFKI`. The database guarantees that every such value exists in `customers`, so you can never have an order for a customer that does not exist. This link is called a **relationship**.

Why not just put the customer's name and city on every order row? Because then a change of address would have to be fixed in hundreds of places, and typos would make the same customer appear under several spellings. Storing each fact once and pointing to it by key is the core idea of the relational model. Splitting data like this is called **normalisation**.

Relationships come in three shapes. **One-to-many** is the common one: one customer has many orders, and each order belongs to one customer. **Many-to-many** needs a middle table: an order can contain many products and a product can appear on many orders, so the table `order_details` has one row per order-and-product pair. Its primary key is the pair `(order_id, product_id)`, which is called a **composite key**. **One-to-one** is rare. A table can also point at itself: `employees.reports_to` holds the `employee_id` of a manager.

### The Northwind map

The database has eight tables. `customers`, `employees`, `suppliers`, `shippers` and `categories` describe things. `products` points at `suppliers` and `categories`. `orders` points at `customers`, `employees` and `shippers`. `order_details` connects `orders` and `products` and records the price and quantity of each line. You will combine these tables with joins starting on day 40. Today you only look at one table at a time.

### Reading a schema with SQL itself

PostgreSQL describes itself in tables. The standard schema `information_schema` contains views such as `tables`, `columns` and `key_column_usage`, which you query exactly like normal tables. This is how data analysts find their way around a database they have never seen. Our own tables live in the schema called `public`.

### How a query is thought about

A SQL query says what result you want, not how to compute it. `SELECT` names the columns you want, `FROM` names the table to read, and `LIMIT` stops after a number of rows. The database chooses the method. The result of any query is itself a table: columns with names, and rows.

### Common misconception

Beginners often think a table has a natural row order, as in a spreadsheet, so "the first 5 rows" has a fixed meaning. It does not. A table is a set of rows, and without an `ORDER BY` PostgreSQL may return them in any order. Today we add `ORDER BY` on the key column so that results are repeatable; day 34 explains sorting properly.

### Why it matters

Every later skill in this course depends on this picture. A join is only "match a foreign key to a primary key". A data-quality check often asks whether a column allows NULL. Reading the schema before writing a query is the habit that prevents most beginner mistakes.

## Syntax and key functions

The simplest query reads every column of a table. The star `*` means "all columns".

```sql-syntax
SELECT * FROM table_name;
```

Name the columns you want, separated by commas, and the database returns only those, in the order you wrote them.

```sql-syntax
SELECT column_1, column_2
FROM table_name;
```

`LIMIT` keeps only the first `n` rows of the result. Pair it with `ORDER BY` so that "first" is well defined.

```sql-syntax
SELECT column_1, column_2
FROM table_name
ORDER BY column_1
LIMIT n;
```

A first, minimal `WHERE` keeps only rows for which a condition is true. Day 33 covers it fully; here it is used only to look at one table in `information_schema`. Text values go in single quotes.

```sql-syntax
SELECT column_1
FROM table_name
WHERE column_2 = 'some text';
```

The schema views you will use today:

| View | One row per | Useful columns |
|---|---|---|
| `information_schema.tables` | table or view | `table_schema`, `table_name`, `table_type` |
| `information_schema.columns` | column of a table | `table_name`, `column_name`, `ordinal_position`, `data_type`, `is_nullable`, `character_maximum_length` |
| `information_schema.key_column_usage` | column that is part of a key | `table_name`, `column_name`, `constraint_name`, `position_in_unique_constraint` |

Reading the results: `ordinal_position` is the column's place in the table (1, 2, 3, ...). `is_nullable` is the text `YES` or `NO`. In `key_column_usage`, a constraint name ending in `_pkey` is a primary key and one ending in `_fkey` is a foreign key. `position_in_unique_constraint` is filled in only for foreign key columns.

## Learn by example

### Example 1: Look at a whole small table

Start by reading every column and row of a tiny table. `shippers` has three rows, so `SELECT *` is safe. The `ORDER BY` on the primary key keeps the order the same every time.

```sql run
SELECT *
FROM shippers
ORDER BY shipper_id;
```

```output
shipper_id | company_name | phone
1 | Speedy Express | (503) 555-9831
2 | United Package | (503) 555-3199
3 | Federal Shipping | (503) 555-9931
```

### Example 2: Choose columns and limit rows

Real tables are large, so you rarely want everything. Here we name three columns of `orders` and ask for five rows. Notice `customer_id` and `employee_id`: each is a foreign key, a pointer to a row in another table. The order with `order_id` 10248 belongs to the customer `ALFKI` and was taken by employee 1.

```sql run
SELECT order_id, customer_id, employee_id, order_date
FROM orders
ORDER BY order_id
LIMIT 5;
```

```output
order_id | customer_id | employee_id | order_date
10248 | ALFKI | 1 | 1996-01-01
10249 | ANATR | 2 | 1997-02-02
10250 | ANTON | 3 | 1998-03-03
10251 | AROUT | 4 | 1996-04-04
10252 | BERGS | 6 | 1997-05-05
```

### Example 3: List the tables in the database

`information_schema.tables` has one row per table. The condition `table_schema = 'public'` hides PostgreSQL's own internal tables and leaves ours. You can already see the eight entities of the Northwind model.

```sql run
SELECT table_name, table_type
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY table_name;
```

```output
table_name | table_type
categories | BASE TABLE
customers | BASE TABLE
employees | BASE TABLE
order_details | BASE TABLE
orders | BASE TABLE
products | BASE TABLE
shippers | BASE TABLE
suppliers | BASE TABLE
```

### Example 4: Read one table's definition

`information_schema.columns` describes columns. For `products`, read each column's type and whether it accepts NULL. Primary key columns and `NOT NULL` columns show `NO`. The price is `numeric` (exact decimals) and `discontinued` is a `boolean`. Ordering by `ordinal_position` shows the columns in the order the table was created.

```sql run
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'products'
ORDER BY ordinal_position;
```

```output
column_name | data_type | is_nullable
product_id | integer | NO
product_name | character varying | NO
supplier_id | integer | YES
category_id | integer | YES
quantity_per_unit | character varying | YES
unit_price | numeric | YES
units_in_stock | integer | YES
units_on_order | integer | YES
reorder_level | integer | YES
discontinued | boolean | YES
```

### Example 5: Find the keys of the composite table

`order_details` links orders and products. `key_column_usage` lists each column that takes part in a key. Both `order_id` and `product_id` appear twice: once in the composite primary key `order_details_pkey` and once as a foreign key to the table it references. That is exactly the many-to-many pattern from the theory section.

```sql run
SELECT column_name, constraint_name
FROM information_schema.key_column_usage
WHERE table_name = 'order_details'
ORDER BY constraint_name, column_name;
```

```output
column_name | constraint_name
order_id | order_details_order_id_fkey
order_id | order_details_pkey
product_id | order_details_pkey
product_id | order_details_product_id_fkey
```

### Example 6: Map every foreign key in the database

`position_in_unique_constraint` is only filled in for foreign key columns, so `IS NOT NULL` keeps exactly those. (`IS NOT NULL` is covered on day 35.) The result is the list of arrows in the Northwind diagram: for example `orders.customer_id` points at `customers`, and `employees.reports_to` points back at `employees` itself.

```sql run
SELECT table_name, column_name
FROM information_schema.key_column_usage
WHERE table_schema = 'public' AND position_in_unique_constraint IS NOT NULL
ORDER BY table_name, column_name;
```

```output
table_name | column_name
employees | reports_to
order_details | order_id
order_details | product_id
orders | customer_id
orders | employee_id
orders | ship_via
products | category_id
products | supplier_id
```

## Real-world applications

**Onboarding to an unfamiliar database.** A new analyst's first task is nearly always "find where the data lives". Querying `information_schema.tables` and `information_schema.columns`, as in examples 3 and 4, gives you a table list and column types without asking anyone, and works in any PostgreSQL database.

**Checking a data model before building a report.** To report "orders per customer" you must know that `orders.customer_id` is a foreign key to `customers`. Example 6 proves such links exist, which tells you which joins are safe once you reach day 40.

**Data-quality review.** The `is_nullable` flag from example 4 tells you which columns are allowed to be empty. A data engineer uses it to decide which columns need NULL handling in a pipeline, and which can be trusted to always have a value.

**Sampling a new table.** `SELECT ... ORDER BY key LIMIT 5`, as in example 2, is the standard way to peek at a table of millions of rows without pulling all of it, and it is what you will type most often on a first contact with new data.

## Daily review

### Key takeaways

- A relational database stores data in tables of rows and columns, and each column has a data type and may or may not allow NULL.
- A primary key identifies a row uniquely; a foreign key stores another table's primary key and creates a relationship.
- Many-to-many relationships use a middle table with a composite key, such as `order_details`.
- A table has no built-in row order. Add `ORDER BY` whenever the order matters, and combine it with `LIMIT` to sample.
- `information_schema` lets you query a database about its own tables, columns and keys.

### Common mistakes

- Expecting rows to come back in the same order without `ORDER BY`.
- Forgetting the single quotes around text in a condition: `table_name = products` looks for a column, while `'products'` is the text.
- Using double quotes for text. In PostgreSQL double quotes mark identifiers (column and table names), not values.
- Forgetting `table_schema = 'public'` and so mixing PostgreSQL's internal tables into your results.
- Reading a NULL as "0" or "empty text". It means there is no value.

### Revision notes

- Table = one entity type. Row = one entity. Column = one fact about it.
- PK: unique and never NULL. FK: copies a PK to point at another row.
- One-to-many: customers to orders. Many-to-many: orders and products through `order_details`. Self reference: `employees.reports_to`.
- `SELECT cols FROM table ORDER BY key LIMIT n` is the safe way to look at data.
- Schema views: `information_schema.tables`, `.columns`, `.key_column_usage`.

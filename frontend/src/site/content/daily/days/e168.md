## Objectives

- Plan a PySpark ETL job in four stages (extract, transform, load, check) and write each stage as a small, testable function.
- Reject invalid rows with a reason instead of dropping them silently, and keep the rejected rows for review.
- Deduplicate to the latest record per key and compute a daily aggregate, and verify the logic with a pandas and a SQL equivalent.
- Reconcile row counts so that every input row is accounted for: loaded, rejected or removed as a duplicate.
- Document the job in a short README with its inputs, outputs, checks and how to run it.

## Understand

### The project

You will build one complete batch job: it reads a CSV of order events, cleans and validates them, keeps the latest version of each order, computes revenue per day and writes the result as date-partitioned Parquet, then checks that nothing was lost. The job is written in PySpark, and because Spark and Java are not available in the browser, the same logic is implemented in pandas (extract, validate, deduplicate, aggregate) and the SQL window function is checked on the browser's PostgreSQL-compatible database. The PySpark code is shown in a plain block and is syntax-checked but not run. Every number printed in the lesson comes from the runnable equivalent. Day 167 explained the reader, writer and partitioned output, and earlier days taught the validation and idempotency ideas this project joins together.

### The four stages

1. **Extract.** Read the CSV with an explicit schema and in permissive mode, so that the job survives bad values and you can count them. Keep the raw text columns as well as the typed ones, so that a rejected row can be shown exactly as it arrived.
2. **Transform.** First validate: each row either passes every rule or is rejected with one reason (missing customer, invalid date, invalid amount, negative amount). Then standardise (strip spaces and lower-case the status), keep the latest record for each `order_id` by `updated_at` (an update after the first event, such as a refund, replaces it), and aggregate paid revenue per day.
3. **Load.** Write the daily result so that the job can be re-run: overwrite the partition for each date, never append. The rejected rows go to a separate location with their reason.
4. **Check.** After the load, assert the invariants: the input row count equals loaded plus rejected plus duplicates removed; the key is unique in the output; no negative revenue; revenue in the output equals revenue recomputed from the clean rows. A job without checks reports success even when it silently lost half of its input.

### Why reject instead of dropping

A filter such as `df.filter(amount > 0)` removes bad rows without a trace, and a month later nobody knows why the totals are lower than the source. A rejected-rows table with a reason column makes the loss visible and countable. The reconciliation equation then proves that rows left the main path only for a stated reason. If the reject rate suddenly jumps from 1 percent to 30 percent, the check should fail the run, because the source has probably changed.

### Idempotency and re-runs

The job takes its date range as an input and rewrites exactly those partitions. Running it twice with the same input gives the same output, and running it after a failure fixes the failed day without touching the others. Duplicate events inside one input are handled by the latest-record rule, not by hoping that the source is clean. These choices come from Days 124 to 127 and apply to Spark just as to the smaller tools.

### The README

A finished pipeline has a short README that answers the questions of the next person on call: what the job does, the input and output locations and formats, the schema, the rules and thresholds of the checks, how to run it for one day, what to do when a check fails and who owns it. Writing the README at the end of the project forces you to notice what is unclear in your own design.

### Why it matters, and the misconception

Most pipeline incidents are not crashes. They are quiet wrong results: rows lost in a filter, duplicates after a retry, a column that changed type. The misconception is that if the job finished without an error the data is right. The checks in this project are what turn "it ran" into "it is correct".

## Syntax and key functions

The PySpark version of the job (syntax-checked, not run here):

```python
from pyspark.sql import SparkSession, Window
from pyspark.sql import functions as F
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

spark = SparkSession.builder.appName("orders_etl").getOrCreate()
spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")

schema = StructType([
    StructField("order_id", StringType()), StructField("customer_id", StringType()),
    StructField("amount", StringType()), StructField("status", StringType()),
    StructField("order_date", StringType()), StructField("updated_at", StringType()),
])
raw = spark.read.csv("landing/orders/*.csv", header=True, schema=schema)

typed = (raw
    .withColumn("amount_n", F.col("amount").cast("double"))
    .withColumn("date_n", F.to_date("order_date", "yyyy-MM-dd"))
    .withColumn("ts", F.to_timestamp("updated_at", "yyyy-MM-dd HH:mm")))

reason = (F.when(F.col("customer_id").isNull() | (F.trim("customer_id") == ""), "missing customer")
           .when(F.col("date_n").isNull(), "bad date")
           .when(F.col("amount_n").isNull(), "bad amount")
           .when(F.col("amount_n") < 0, "negative amount"))
flagged = typed.withColumn("reason", reason)
rejected = flagged.filter(F.col("reason").isNotNull())
ok = flagged.filter(F.col("reason").isNull())

w = Window.partitionBy("order_id").orderBy(F.col("ts").desc())
latest = (ok.withColumn("status", F.lower(F.trim("status")))
            .withColumn("rn", F.row_number().over(w))
            .filter("rn = 1").drop("rn"))

daily = (latest.filter(F.col("status") == "paid")
               .groupBy("date_n").agg(F.round(F.sum("amount_n"), 2).alias("revenue")))

daily.repartition("date_n").write.mode("overwrite").partitionBy("date_n").parquet("curated/daily_revenue")
rejected.write.mode("overwrite").parquet("quarantine/orders")
```

| Piece | Pandas equivalent used in this lesson |
|---|---|
| `F.col("amount").cast("double")` | `pd.to_numeric(..., errors="coerce")` |
| `F.to_date(col, fmt)` | `pd.to_datetime(..., format=..., errors="coerce")` |
| `F.when(...).when(...)` | `Series.mask(condition, value)` applied in order |
| `row_number().over(w)` then `rn = 1` | `sort_values` then `drop_duplicates(keep="last")` |
| `groupBy(...).agg(F.sum(...))` | `groupby(...)[...].sum()` |
| `write.partitionBy(...)` | one group per date |

## Learn by example

### Example 1: Extract and validate

The data and the first two stages are implemented as small functions. The rows that fail a rule are kept with a reason. Note that a row can break several rules and receives the reason of the last rule that applies.

```python run
import io
import pandas as pd

TEXT = """order_id,customer_id,amount,status,order_date,updated_at
1001,C1,19.99,paid,2025-03-01,2025-03-01 09:00
1002,C2,45.00,paid,2025-03-01,2025-03-01 10:00
1002,C2,45.00,refunded,2025-03-01,2025-03-02 08:00
1003,C1,abc,paid,2025-03-02,2025-03-02 09:00
1004,,12.50,paid,2025-03-02,2025-03-02 09:30
1005,C3,30.00,PAID ,2025-03-02,2025-03-02 11:00
1006,C4,-5.00,paid,2025-03-03,2025-03-03 08:00
1007,C2,60.00,paid,2025-03-03,2025-03-03 09:00
1008,C5,25.00,paid,not-a-date,2025-03-03 10:00
1009,C1,15.00,failed,2025-03-03,2025-03-03 11:00
"""


def extract(text):
    raw = pd.read_csv(io.StringIO(text), dtype=str, keep_default_na=False)
    typed = raw.copy()
    typed["amount_n"] = pd.to_numeric(raw["amount"], errors="coerce")
    typed["date_n"] = pd.to_datetime(raw["order_date"], format="%Y-%m-%d", errors="coerce")
    typed["ts"] = pd.to_datetime(raw["updated_at"], format="%Y-%m-%d %H:%M", errors="coerce")
    return typed


def split_valid(typed):
    reason = pd.Series("", index=typed.index)
    reason = reason.mask(typed["customer_id"].str.strip() == "", "missing customer")
    reason = reason.mask(typed["date_n"].isna(), "bad date")
    reason = reason.mask(typed["amount_n"].isna(), "bad amount")
    reason = reason.mask(typed["amount_n"] < 0, "negative amount")
    rejected = typed[reason != ""].assign(reason=reason[reason != ""])
    return typed[reason == ""].copy(), rejected


def transform(ok):
    ok = ok.copy()
    ok["status"] = ok["status"].str.strip().str.lower()
    latest = ok.sort_values(["order_id", "ts"], kind="stable").drop_duplicates("order_id", keep="last")
    daily = latest[latest["status"] == "paid"].groupby("date_n")["amount_n"].sum().round(2)
    return latest, daily


def run_job(text):
    typed = extract(text)
    ok, rejected = split_valid(typed)
    latest, daily = transform(ok)
    counts = {"read": len(typed), "rejected": len(rejected), "duplicates": len(ok) - len(latest), "loaded": len(latest)}
    return {"latest": latest, "rejected": rejected, "daily": daily, "counts": counts}
typed = extract(TEXT)
ok, rejected = split_valid(typed)
print("rows read:", len(typed), "| valid:", len(ok), "| rejected:", len(rejected))
print(rejected[["order_id", "amount", "order_date", "reason"]].to_string(index=False))
```

```output
rows read: 10 | valid: 6 | rejected: 4
order_id amount order_date           reason
    1003    abc 2025-03-02       bad amount
    1004  12.50 2025-03-02 missing customer
    1006  -5.00 2025-03-03  negative amount
    1008  25.00 not-a-date         bad date
```

Four rows are rejected, each with the reason that explains it. Nothing disappeared without a trace, which is what makes the later reconciliation possible.

Now the SQL check of the window function on a table created in the block.

```sql run
DROP TABLE IF EXISTS ev;
CREATE TEMP TABLE ev (order_id int, status text, ts timestamp);
INSERT INTO ev VALUES (1002, 'paid', '2025-03-01 10:00'), (1002, 'refunded', '2025-03-02 08:00'), (1001, 'paid', '2025-03-01 09:00');
SELECT order_id, status
FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY ts DESC) AS rn FROM ev) t
WHERE rn = 1
ORDER BY order_id;
```

```output
order_id | status
1001 | paid
1002 | refunded
```

Both show order 1002 as refunded and order 1001 as paid. In Spark the same rule is the `Window` expression of the Syntax section.

### Example 4: The reconciliation check

The check function turns the invariants into a list of named results and a verdict. The first run uses the correct output. The second run drops a clean row to simulate a bug, and the check fails.

```python run

import pandas as pd

TEXT = """order_id,customer_id,amount,status,order_date,updated_at
1001,C1,19.99,paid,2025-03-01,2025-03-01 09:00
1002,C2,45.00,paid,2025-03-01,2025-03-01 10:00
1002,C2,45.00,refunded,2025-03-01,2025-03-02 08:00
1003,C1,abc,paid,2025-03-02,2025-03-02 09:00

1006,C4,-5.00,paid,2025-03-03,2025-03-03 08:00
1007,C2,60.00,paid,2025-03-03,2025-03-03 09:00
1008,C5,25.00,paid,not-a-date,2025-03-03 10:00

    return typed[reason == ""].copy(), rejected


def transform(ok):
    ok = ok.copy()
    ok["status"] = ok["status"].str.strip().str.lower()
    latest = ok.sort_values(["order_id", "ts"], kind="stable").drop_duplicates("order_id", keep="last")

    ok, rejected = split_valid(typed)
    latest, daily = transform(ok)

    return {"latest": latest, "rejected": rejected, "daily": daily, "counts": counts}
def checks(res):
    c = res["counts"]
    latest = res["latest"]
    return [
        ("rows reconcile", c["read"] == c["loaded"] + c["rejected"] + c["duplicates"]),
        ("order_id unique", bool(latest["order_id"].is_unique)),
        ("no negative revenue", bool((res["daily"] >= 0).all())),
        ("revenue matches clean rows", round(float(latest.loc[latest["status"] == "paid", "amount_n"].sum()), 2) == round(float(res["daily"].sum()), 2)),
    ]

res = run_job(TEXT)
print(res["counts"])
for name, passed in checks(res):
    print(("PASS " if passed else "FAIL ") + name)

res["latest"] = res["latest"].iloc[1:]
res["counts"]["loaded"] = len(res["latest"])
print("after losing a row:", [name for name, passed in checks(res) if not passed])
```

```output
{'read': 10, 'rejected': 4, 'duplicates': 1, 'loaded': 5}
PASS rows reconcile
PASS order_id unique
PASS no negative revenue
PASS revenue matches clean rows
after losing a row: ['rows reconcile', 'revenue matches clean rows']
```

The reconciliation equation (10 read = 5 loaded + 4 rejected + 1 duplicate) holds for the real run and fails for the damaged one. A job that raised an error on a failed check would stop before the bad result is published.

### Example 5: The job as a function, run twice

A re-runnable job returns the same result on the same input. The code runs the job twice and compares the results, then runs it on a second day's file whose partition replaces the first day's data only for its own date.

```python run

first = run_job(TEXT)
second = run_job(TEXT)
print("same daily result on re-run:", first["daily"].equals(second["daily"]))

store = {d.strftime("%Y-%m-%d"): float(v) for d, v in first["daily"].items()}
next_day = TEXT.split("\n")[0] + "\n1010,C6,80.00,paid,2025-03-04,2025-03-04 09:00\n1011,C1,20.00,paid,2025-03-02,2025-03-04 10:00\n"
```

```output
same daily result on re-run: True
{'2025-03-01': 19.99, '2025-03-02': 20.0, '2025-03-03': 60.0, '2025-03-04': 80.0}
```

The late event for 2025-03-02 rewrote that date's partition to its new total from this file alone, while 2025-03-01 and 2025-03-03 stayed untouched. The partition for 2025-03-02 now holds only the rows of the new file: that is the behaviour of overwriting a partition with new data, so the input of a re-run has to contain all the rows of the partition, or the job must read the existing data and merge. This is the trade-off to document in the README.

## Real-world applications

- **Daily curated tables**: the same extract, validate, transform, load and check structure runs as a nightly job in an orchestrator, with the reject table feeding a data-quality dashboard.
- **Incident response**: when a number looks wrong, the reconciliation counts show at once whether rows were rejected, duplicated or lost.
- **Onboarding**: the README lets a new engineer run a single day and read the check results without asking the author.
- **Refactoring to tests**: because each stage is a function, it can be tested with a ten-row input (Example 4 is already such a test).

## Daily review

### Key takeaways

- Structure a job as extract, validate and transform, load, check, each stage a function.
- Reject with a reason and keep the rejected rows; never filter silently.
- Keep the latest record per key and aggregate by the business rule (paid revenue).
- Reconcile counts: read = loaded + rejected + duplicates removed.
- Overwrite the partitions of the run's dates, and document what the input must contain.

### Common mistakes

- Filtering invalid rows with no record. The totals drift from the source and nobody knows why; write a reject table with a reason.
- Deduplicating with `dropDuplicates()` on all columns when the events differ by timestamp: both rows survive. Rank by the key and the update time.
- Using `append` for the daily output. A retry duplicates the data; overwrite the partitions.
- Checking only that the job ran. A job that loses rows still finishes; assert the reconciliation.
- Leaving the README for later. The assumptions (for example that the input holds all rows of a partition) are then lost.

### Revision notes

- Stages: extract, validate and transform, load, check.
- `row_number() over (partition by key order by ts desc)`, keep `rn = 1`.
- Reconciliation: `read = loaded + rejected + duplicates`.
- Idempotent load: overwrite partitions, with the input holding the partition's full data.

## Objectives

- Write a README for the capstone with the sections a reviewer looks for, and check it with a small linter.
- Produce an architecture diagram as text and a data dictionary generated from the real schema.
- Create a Git repository with a `.gitignore`, a clean commit history and no secrets or data files committed.
- Push to a remote and read the remote's history; use a local bare repository as the stand-in for GitHub.
- Explain what a reviewer sees first in a portfolio repository and what makes it trustworthy.

## Understand

### Documentation is part of the pipeline

The pipeline from Days 173 to 178 works on your computer. A reviewer, an interviewer or a colleague next year does not have your computer, so what they judge is the repository: can they understand what it does in a minute, run it in five, and trust it. **Documentation** is the written part of that answer, and **repository hygiene** is the part that stops the repository from lying: no secrets, no generated files, no half-finished history. Both are cheap compared with the work they make visible.

### The README

A **README** is the first file a visitor opens. For this project it has seven sections. **What it does**: two or three sentences, with the sources and the result. **Architecture**: the diagram of stages. **Data**: where it comes from and its shape (here generated by a seeded function, so anyone gets the same numbers). **How to run**: the exact commands, in order, that someone with a fresh checkout types. **Tests**: how to run them and what they cover. **Design decisions**: the reasons behind choices a reviewer might question: why quarantine and not drop, why a surrogate key with history, why a watermark. **Limitations**: what the project does not do, such as late-arriving orders, because honest limits build trust. Numbers in the README should be the numbers the pipeline prints (120 raw records, 114 clean, 6 quarantined, 91 fact rows), so a reader can check them.

### The architecture diagram

A diagram shows stages and the stores between them. Plain text is enough, and it has an advantage over an image: it lives in the README, diffs in Git and cannot go out of date silently because it is reviewed with the code. A good diagram shows the sources, the raw layer, the clean and quarantine outputs, the warehouse tables and the consumers, with the direction of data flow.

### A data dictionary from the schema

Column lists written by hand drift away from the schema. A small script can read the schema from the database (`PRAGMA table_info` in SQLite, `information_schema.columns` in PostgreSQL) and print the table of columns and types. What the script cannot know is the meaning of each column, so the descriptions stay hand-written and short.

### Git and repository hygiene

**Git** records snapshots called commits. A good history is a list of small commits with messages that say what changed in the imperative: "Add cleaning rules", "Add warehouse load". The command `git log --format=%s` prints just the messages, which is how a reviewer skims it. A **`.gitignore`** lists files Git must not track: environment files with keys (`.env`), local databases (`*.db`), caches (`__pycache__/`), virtual environments. The rule that matters most is **never commit a secret**. A key committed once stays in the history even after the file is deleted, and must then be revoked and replaced. A **remote** such as GitHub is a copy of the repository on a server; `git remote add origin <url>` names it, and `git push` sends the commits. GitHub itself is not available here, so the examples push to a local bare repository, which behaves like a remote for these commands.

### Common misconception

Learners treat the README as an afterthought and the history as private. A reviewer opens the README first, skims the commit messages second and the code third; a single commit called "final" with a database file and a key in it says more than the code does.

### Why it matters

For a portfolio, the repository is the product. A clear README, tests that pass, a clean history and an honest limitations section separate a project that can be trusted from one that only looks finished.

## Syntax and key functions

```bash
git init -b main
git add .gitignore README.md
git commit -m "Add README"
git log --format=%s
git remote add origin <url>
git push -u origin main
```

| Command | What it does |
|---|---|
| `git init -b main` | Creates a repository whose first branch is `main`. |
| `git add <paths>` | Stages files for the next commit. |
| `git commit -m "msg"` | Records the staged files as a commit. |
| `git status --short` | One line per changed or untracked file. |
| `git log --format=%s` | The commit messages, newest first. |
| `git check-ignore -v <path>` | Shows which `.gitignore` line ignores a path. |
| `git remote add origin <url>` | Names the remote repository. |
| `git push -u origin main` | Sends `main` and remembers it as the upstream branch. |
| `PRAGMA table_info(t)` | SQLite: one row per column with name and type. |

## Learn by example

### Example 1: A README checker

The linter reads a README and reports what is missing. It checks the seven sections by their `##` headings, leftover `TODO` text, at least one indented command and a pattern that looks like a leaked secret. The first text (built from a list of lines) is a finished README; the second is a draft with a missing section, a TODO and an API key pasted into the instructions.

```python run
import re

REQUIRED = ["What it does", "Architecture", "Data", "How to run", "Tests", "Design decisions", "Limitations"]
SECRET = re.compile(r"(api[_-]?key|secret|password|token)\s*[=:]\s*['\"]?[A-Za-z0-9_-]{6,}", re.IGNORECASE)

def lint_readme(text):
    """Problems found in a README: missing sections, leftover TODOs, a command block, a leaked secret."""
    headings = [line[3:].strip() for line in text.splitlines() if line.startswith("## ")]
    problems = [f"missing section: {name}" for name in REQUIRED if name not in headings]
    if "TODO" in text:
        problems.append("contains TODO")
    if not any(line.startswith("    ") and line.strip() for line in text.splitlines()):
        problems.append("no command shown")
    if SECRET.search(text):
        problems.append("possible secret")
    return problems

good = "\n".join([
    "# Orders pipeline",
    "",
    "## What it does",
    "Loads 120 generated orders and 20 customers into a star schema and serves analytical SQL.",
    "",
    "## Architecture",
    "API and CSV, raw tables, clean and quarantine, warehouse, analytics views.",
    "",
    "## Data",
    "Generated by a seeded function: 120 raw records, 114 clean, 6 quarantined, 91 fact rows.",
    "",
    "## How to run",
    "    python run_pipeline.py",
    "",
    "## Tests",
    "    python -m pytest -q",
    "",
    "## Design decisions",
    "Quarantine instead of drop; type 2 customer history; watermark with upsert.",
    "",
    "## Limitations",
    "Late-arriving orders are not reloaded.",
])
draft = "\n".join([
    "# Orders pipeline",
    "",
    "## What it does",
    "TODO describe",
    "",
    "## How to run",
    "Set API_KEY=abc123secret and run the script.",
])
print("good:", lint_readme(good))
for problem in lint_readme(draft):
    print("draft:", problem)
```

```output
good: []
draft: missing section: Architecture
draft: missing section: Data
draft: missing section: Tests
draft: missing section: Design decisions
draft: missing section: Limitations
draft: contains TODO
draft: no command shown
draft: possible secret
```

### Example 2: A data dictionary from the real schema

The tables are created by the warehouse code of Day 176, and `PRAGMA table_info` reads their columns back. The script prints a Markdown table for the fact table and the number of columns per table. Hand-written descriptions can then be added next to the generated names.

```python run
import sqlite3
from datetime import date, timedelta

DDL = """
CREATE TABLE dim_date (date_key INTEGER PRIMARY KEY, full_date TEXT, year INTEGER, month INTEGER);
CREATE TABLE dim_product (product_key INTEGER PRIMARY KEY AUTOINCREMENT, product_id TEXT UNIQUE, product_name TEXT, category TEXT);
CREATE TABLE dim_customer (customer_key INTEGER PRIMARY KEY AUTOINCREMENT, customer_id TEXT, customer_name TEXT, country TEXT,
                           valid_from TEXT, valid_to TEXT, is_current INTEGER);
CREATE TABLE fact_sales (sale_id INTEGER PRIMARY KEY, date_key INTEGER, customer_key INTEGER, product_key INTEGER,
                         quantity INTEGER, amount_cents INTEGER);
CREATE TABLE etl_state (name TEXT PRIMARY KEY, watermark TEXT);
"""

def init_warehouse():
    conn = sqlite3.connect(":memory:")
    conn.executescript(DDL)
    return conn

def load_dim_date(conn, start, end):
    days = (end - start).days + 1
    rows = [(int(d.strftime("%Y%m%d")), d.isoformat(), d.year, d.month) for d in (start + timedelta(days=i) for i in range(days))]
    with conn:
        conn.executemany("INSERT OR IGNORE INTO dim_date VALUES (?, ?, ?, ?)", rows)

def load_dim_product(conn, products):
    with conn:
        conn.executemany("""INSERT INTO dim_product (product_id, product_name, category) VALUES (?, ?, ?)
                            ON CONFLICT(product_id) DO UPDATE SET product_name = excluded.product_name, category = excluded.category""", products)

def load_dim_customer(conn, customers, as_of, first_from="2026-01-01"):
    """Type 2 history: a changed customer gets a new row; the old row is closed on `as_of`."""
    with conn:
        for cid, name, country in customers:
            cur = conn.execute("SELECT customer_key, customer_name, country FROM dim_customer WHERE customer_id = ? AND is_current = 1", (cid,)).fetchone()
            if cur is None:
                conn.execute("INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current) VALUES (?, ?, ?, ?, '9999-12-31', 1)",
                             (cid, name, country, first_from))
            elif (cur[1], cur[2]) != (name, country):
                conn.execute("UPDATE dim_customer SET valid_to = ?, is_current = 0 WHERE customer_key = ?", (as_of, cur[0]))
                conn.execute("INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current) VALUES (?, ?, ?, ?, '9999-12-31', 1)",
                             (cid, name, country, as_of))

def load_fact(conn, good):
    """Incremental: only paid orders newer than the watermark; upsert on sale_id; the watermark moves after the load."""
    row = conn.execute("SELECT watermark FROM etl_state WHERE name = 'fact_sales'").fetchone()
    mark = row[0] if row else ""
    new = [g for g in good if g["created_at"] > mark]
    facts = []
    for g in new:
        if g["status"] != "paid":
            continue
        day = g["created_at"][:10]
        ck = conn.execute("SELECT customer_key FROM dim_customer WHERE customer_id = ? AND valid_from <= ? AND ? < valid_to", (g["customer_id"], day, day)).fetchone()[0]
        pk = conn.execute("SELECT product_key FROM dim_product WHERE product_id = ?", (g["product_id"],)).fetchone()[0]
        facts.append((g["sale_id"], g["date_key"], ck, pk, g["quantity"], g["amount_cents"]))
    with conn:
        conn.executemany("""INSERT INTO fact_sales VALUES (?, ?, ?, ?, ?, ?)
                            ON CONFLICT(sale_id) DO UPDATE SET date_key = excluded.date_key, customer_key = excluded.customer_key,
                            product_key = excluded.product_key, quantity = excluded.quantity, amount_cents = excluded.amount_cents""", facts)
        if new:
            conn.execute("INSERT INTO etl_state VALUES ('fact_sales', ?) ON CONFLICT(name) DO UPDATE SET watermark = excluded.watermark",
                         (max(g["created_at"] for g in new),))
    return len(facts)

conn = init_warehouse()
print("| column | type | primary key |")
print("|---|---|---|")
for _, name, ctype, notnull, default, pk in conn.execute("PRAGMA table_info(fact_sales)"):
    print(f"| {name} | {ctype} | {'yes' if pk else ''} |")
for table in ("dim_customer", "dim_product", "dim_date", "fact_sales"):
    print(table, len(conn.execute(f"PRAGMA table_info({table})").fetchall()), "columns")
```

```output
| column | type | primary key |
|---|---|---|
| sale_id | INTEGER | yes |
| date_key | INTEGER |  |
| customer_key | INTEGER |  |
| product_key | INTEGER |  |
| quantity | INTEGER |  |
| amount_cents | INTEGER |  |
dim_customer 7 columns
dim_product 4 columns
dim_date 4 columns
fact_sales 6 columns
```

### Example 3: A repository with a clean history

The shell block creates a throwaway repository, writes a `.gitignore` and a short README, and makes three commits with imperative messages. `git status --short` is empty when everything is committed, and `git log --format=%s` prints the messages without the commit hashes, which differ on every machine.

```bash run
git init -q -b main orders-pipeline && cd orders-pipeline
printf '.env\n*.db\n__pycache__/\n' > .gitignore
git add .gitignore && git commit -q -m "Add gitignore"
printf '# Orders pipeline\n\n## What it does\nLoads generated orders into a star schema.\n' > README.md
git add README.md && git commit -q -m "Add README"
mkdir src && printf 'print("pipeline")\n' > src/run_pipeline.py
git add src && git commit -q -m "Add pipeline entry point"
echo "status:"; git status --short
echo "history:"; git log --format=%s
```

```output
status:
history:
Add pipeline entry point
Add README
Add gitignore
```

### Example 4: Keep secrets and data out

A `.env` file with a key and a local database file exist in the folder, but the `.gitignore` covers both. `git status --short` shows only the new source file, and `git check-ignore -v` names the rule that hides the key. Finally a search of the tracked files for key-like text finds nothing, which is the check to run before every push.

```bash run
git init -q -b main safe && cd safe
printf '.env\n*.db\n__pycache__/\n' > .gitignore
printf 'DATAFORGE_API_KEY=secret-key\n' > .env
printf 'x' > warehouse.db
printf 'import os\nkey = os.environ["DATAFORGE_API_KEY"]\n' > app.py
git add -A && git commit -q -m "Add app"
echo "tracked files:"; git ls-files
printf 'print(1)\n' > extra.py
echo "status:"; git status --short
echo "why .env is hidden:"; git check-ignore -v .env | cut -f1
echo "key-like text in tracked files:"; git grep -n -i "secret-key" || echo none
```

```output
tracked files:
.gitignore
app.py
status:
?? extra.py
why .env is hidden:
.gitignore:1:.env
key-like text in tracked files:
none
```

### Example 5: Push to a remote

GitHub is not available, so a local bare repository plays the remote. The commands are the ones you would use with GitHub: `git remote add origin <url>` and `git push -u origin main`. Afterwards the log of the remote shows the same messages as the local one. With GitHub the only difference is the URL, such as `https://github.com/your-name/orders-pipeline.git`, and a login.

```bash run
git init -q --bare remote.git
git init -q -b main work && cd work
printf '# Orders pipeline\n' > README.md
git add README.md && git commit -q -m "Add README"
printf 'print("pipeline")\n' > run_pipeline.py
git add run_pipeline.py && git commit -q -m "Add pipeline entry point"
git remote add origin ../remote.git
git push -q -u origin main
git remote -v
echo "remote history:"; git --git-dir=../remote.git log --format=%s main
```

```output
origin	../remote.git (fetch)
origin	../remote.git (push)
remote history:
Add pipeline entry point
Add README
```

## Real-world applications

- **Portfolio review.** Hiring managers open the README of Example 1 first; the linter is a quick way to make sure the sections and numbers are there.
- **Onboarding.** A data dictionary generated as in Example 2 stays correct when the schema changes, which saves the next engineer an afternoon.
- **Security hygiene.** The `.gitignore` and the search of Example 4 are the standard guard against pushing a key to a public repository.
- **Collaboration.** Small commits with clear messages (Example 3) make code review and `git bisect`-style debugging possible.

## Daily review

### Key takeaways

- A README answers what, how to run, how it is tested, why it is built this way and what it does not do.
- A text diagram and a generated data dictionary stay in the repository and stay accurate.
- Commit in small steps with imperative messages; `git log --format=%s` is how history is skimmed.
- `.gitignore` the environment file, databases and caches; never commit a secret, and revoke any that was committed.
- A remote receives commits with `git push`; GitHub differs from a local bare repository only in URL and login.

### Common mistakes

- Committing `.env` or a key in the README. Removing it later does not remove it from history; revoke the key.
- Adding `.gitignore` after the files were committed. Ignored files that are already tracked stay tracked; use `git rm --cached`.
- One huge commit named "final". Commit per stage.
- README numbers that the pipeline does not print, so nobody can verify them.
- Instructions that skip a step (installing packages, setting a variable), which only work on your machine.
- A README without limitations, which hides what a reviewer will find in five minutes anyway.

### Revision notes

- README sections: what it does, architecture, data, how to run, tests, design decisions, limitations.
- `git init -b main`, `git add`, `git commit -m`, `git status --short`, `git log --format=%s`.
- `.gitignore`: `.env`, `*.db`, `__pycache__/`.
- Remote: `git remote add origin <url>`, `git push -u origin main`.

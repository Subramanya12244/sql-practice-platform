## Objectives

- Write sargable predicates, conditions that let the database use an index, and rewrite non-sargable ones.
- Avoid `SELECT *` and name only the columns you need, including the benefit of index-only scans.
- Rewrite subqueries (`NOT IN` to `NOT EXISTS`, `IN` to a join) and explain why the answers can differ.
- Explain that the written order of joins and filters is not the execution order, and filter early where it reduces work.
- Measure a change with plans and row counts instead of guessing.

## Understand

### Optimise by measuring, not by superstition

A query is slow for a reason you can find: it reads too many rows, sorts too much, joins in a poor way, or returns more data than needed. The method has three steps. Measure the current behaviour with the plan (day 58). Change one thing. Measure again and check that the result is unchanged. A faster query that returns different rows is a bug. Most of the examples today change a query without changing its answer and compare plans or counts.

### Sargable predicates

**Sargable** (from "Search ARGument ABLE") describes a condition the engine can answer with an index. A B-tree index (day 57) is sorted by the raw column value, so it can answer "column equals a constant" or "column is between two constants". If you wrap the column in a function or an expression, the engine cannot use the sorted order of the raw values, and it must compute the expression for every row: it falls back to a `Seq Scan` with a `Filter`.

Non-sargable: `WHERE EXTRACT(YEAR FROM order_date) = 1997`, `WHERE lower(name) = 'ana'`, `WHERE price * 1.2 > 100`, `WHERE order_date + 30 > CURRENT_DATE`. Sargable rewrites move the computation to the constant side: `WHERE order_date >= DATE '1997-01-01' AND order_date < DATE '1998-01-01'`, `WHERE price > 100 / 1.2`. For case-insensitive search you can instead create an **expression index** on `lower(name)`, and then `lower(name) = 'ana'` is sargable. Also a leading wildcard, `LIKE '%market%'`, cannot use a plain B-tree index, while `LIKE 'Mar%'` can in some configurations. Use half-open date ranges (`>= start AND < next_start`) and not `BETWEEN` with an end-of-day time, so no rows are lost at the boundary.

### Avoid SELECT *

`SELECT *` returns every column, including wide text columns you do not use. That moves more data from the table to the client, uses more memory in sorts and hash tables, and is fragile: when a column is added or reordered, a downstream job may break. It also blocks an **index-only scan**: if an index contains every column the query needs, the database can answer from the index alone without visiting the table (Example 4). Listing just the needed columns makes that possible. Use `SELECT *` for quick exploration only.

### Rewriting subqueries

A subquery can often be written several ways. `NOT IN (SELECT ...)` has a trap: if the subquery returns any NULL, the whole condition becomes unknown and no rows come back (day 48). It is also usually planned as a hashed subplan, which the planner cannot turn into a join. `NOT EXISTS` has no NULL trap and is planned as an anti join (Example 5). `IN (SELECT ...)` and `EXISTS` become a semi join. A correlated subquery in the select list, which runs once per outer row, can often be replaced by a join to a pre-aggregated table. Modern planners do convert many forms for you, so check the plan before and after instead of assuming a rewrite helps. Rewrites to `NOT EXISTS` are about correctness first.

### Join and filter order

You write `FROM`, `JOIN` and `WHERE` in an order that makes sense to you. The planner is free to reorder inner joins and to apply each `WHERE` condition at the earliest possible place, usually at the scan of its table, before the join (Example 3). So moving a condition from `WHERE` into a subquery that "filters first" normally changes nothing for inner joins. Two cases do matter. For outer joins, a condition in `WHERE` on the nullable side turns the join into an inner join; in `ON` it keeps the preserved rows. And you do control the work when you aggregate: reducing rows with `GROUP BY` in a subquery before joining to another table can be much cheaper than joining the large table first and aggregating after, when the aggregate has few groups.

### Measuring changes

Compare plans: node types, the `Filter` and `Index Cond` lines, and with `EXPLAIN (ANALYZE ...)` the `actual rows` and `Rows Removed by Filter`. Rows removed shows wasted work: reading 100 rows and discarding 67 means the scan was not selective. Always verify the answer: compare `COUNT(*)` or a checksum such as `SUM` of a key column before and after the rewrite. Do not trust timing from a single run; caches and other load change timings, which is why this lesson prints plans and counts instead of times. On real data volumes, time with repeated runs.

### Common misconception

A frequent belief is that putting a condition in a different place, or writing a subquery instead of a join, "makes it faster" by itself. The planner usually decides based on cost, so such rewrites often produce identical plans. What does change plans: sargable conditions, the right indexes, fewer columns and fewer rows early. Another belief is that `NOT IN` and `NOT EXISTS` are interchangeable; they differ when NULL is present.

### Why it matters

On a table with millions of rows the difference between a function on the column and a plain range is the difference between scanning everything and reading a few pages. Optimisation is mostly about not doing unneeded work.

## Syntax and key functions

```sql-syntax
-- non-sargable           -- sargable rewrite
WHERE EXTRACT(YEAR FROM d) = 1997        WHERE d >= DATE '1997-01-01' AND d < DATE '1998-01-01'
WHERE lower(name) = 'ana'                 CREATE INDEX ON t (lower(name));  -- then same condition
WHERE price * 1.2 > 100                   WHERE price > 100 / 1.2
```

```sql-syntax
-- NOT IN to NOT EXISTS
SELECT ... FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.key = a.key);
```

| Technique | Effect |
|---|---|
| Compare the bare column with constants | Allows index use |
| Expression index `ON t (lower(col))` | Makes a function condition sargable |
| List needed columns | Less data, possible index-only scan |
| `NOT EXISTS` instead of `NOT IN` | NULL-safe, anti join plan |
| Half-open date range | Index-friendly and boundary-safe |
| `EXPLAIN (ANALYZE ...)` rows | Compare actual rows and rows removed |

## Learn by example

### Example 1: a function on the column blocks the index

We create an index on `order_date` and look for 1997 orders with `EXTRACT(YEAR FROM order_date) = 1997`. The index is on the raw date, so the condition cannot use it: the plan is a `Seq Scan` with the function in its `Filter`. Sequential scans are switched off for the demonstration (`SET LOCAL`, day 57) to show that even then the index is not usable; newer PostgreSQL versions print an extra `Disabled: true` line for that case.

```sql run
CREATE INDEX idx_orders_date ON orders (order_date);
SET LOCAL enable_seqscan = off;
EXPLAIN (COSTS OFF)
SELECT order_id FROM orders WHERE EXTRACT(YEAR FROM order_date) = 1997;
```

```output
QUERY PLAN
Seq Scan on orders
  Disabled: true
  Filter: (EXTRACT(year FROM order_date) = '1997'::numeric)
```

### Example 2: the sargable rewrite

The same question as a half-open date range. The condition now compares the bare column with two constants, and the plan uses the index through an `Index Cond`. The next example proves that the rewrite returns the same count.

```sql run
CREATE INDEX idx_orders_date ON orders (order_date);
SET LOCAL enable_seqscan = off;
EXPLAIN (COSTS OFF)
SELECT order_id
FROM orders
WHERE order_date >= DATE '1997-01-01' AND order_date < DATE '1998-01-01';
```

```output
QUERY PLAN
Index Scan using idx_orders_date on orders
  Index Cond: ((order_date >= '1997-01-01'::date) AND (order_date < '1998-01-01'::date))
```

### Example 3: prove that the rewrite keeps the answer

Both forms count the orders of 1997 and both return 33. Always run a check like this before trusting a rewrite: a faster query that returns other rows is wrong.

```sql run
SELECT (SELECT COUNT(*) FROM orders WHERE EXTRACT(YEAR FROM order_date) = 1997) AS with_function,
       (SELECT COUNT(*) FROM orders
        WHERE order_date >= DATE '1997-01-01' AND order_date < DATE '1998-01-01') AS with_range;
```

```output
with_function | with_range
33 | 33
```

### Example 4: naming columns allows an index-only scan

With a composite index on `(customer_id, order_date)`, a query that needs only those two columns can be answered from the index: the node is `Index Only Scan`. `SELECT *` on the same filter needs every column of the table, so it must use a plain `Index Scan` and visit the table (verified with the same setup). Index-only scans are an advantage of listing columns.

```sql run
CREATE INDEX idx_orders_customer_date ON orders (customer_id, order_date);
SET LOCAL enable_seqscan = off;
EXPLAIN (COSTS OFF)
SELECT customer_id, order_date FROM orders WHERE customer_id = 'ALFKI';
```

```output
QUERY PLAN
Index Only Scan using idx_orders_customer_date on orders
  Index Cond: (customer_id = 'ALFKI'::text)
```

### Example 5: NOT EXISTS is planned as an anti join

"Customers with no orders" written with `NOT EXISTS` becomes a `Hash Anti Join`, a join that keeps unmatched rows. The `NOT IN` version of the same question is planned as a `Seq Scan` with a hashed subplan in its filter and returns nothing at all if the subquery produces a NULL. Here `orders.customer_id` has no NULLs, so both give the same two customers, but only `NOT EXISTS` stays correct if that changes.

```sql run
EXPLAIN (COSTS OFF)
SELECT c.customer_id
FROM customers AS c
WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.customer_id);
```

```output
QUERY PLAN
Hash Anti Join
  Hash Cond: ((c.customer_id)::text = (o.customer_id)::text)
  ->  Seq Scan on customers c
  ->  Hash
        ->  Seq Scan on orders o
```

### Example 6: a filter written after the join is applied at the scan

The `WHERE` conditions come after the join in the text, but in the plan the `Filter` sits on the `Seq Scan` of `orders`, below the join: the planner filters first and then looks up the matching customers by primary key in a `Nested Loop`. You gain nothing by hand-moving such a filter into a subquery for an inner join.

```sql run
EXPLAIN (COSTS OFF)
SELECT o.order_id, c.company_name
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id
WHERE o.ship_country = 'Germany';
```

```output
QUERY PLAN
Nested Loop
  ->  Seq Scan on orders o
        Filter: ((ship_country)::text = 'Germany'::text)
  ->  Index Scan using customers_pkey on customers c
        Index Cond: ((customer_id)::text = (o.customer_id)::text)
```

## Real-world applications

**Date filters in reports.** Reports filtered by year, month or day often use `EXTRACT` or `date_trunc` on the column. Replacing them with half-open ranges (Examples 1 and 2) is the most common optimisation in analytics code and needs no schema change.

**Case-insensitive lookups.** Searching customers by `lower(email)` is non-sargable on a plain index. An expression index on `lower(email)` makes it fast without changing the application queries.

**Narrow queries for pipelines.** ETL jobs that select only the columns they need move less data and can use index-only scans (Example 4). It also protects the job when someone adds a column to the source table.

**Safe anti-joins.** "Customers who never ordered" (Example 5) written with `NOT EXISTS` is both NULL-safe and efficient, which is why it is the standard form for data-quality checks.

## Daily review

### Key takeaways

- Sargable conditions compare the bare column with constants; a function or expression on the column blocks a plain index.
- Fix non-sargable conditions by moving the computation to the constant, using half-open ranges, or creating an expression index.
- List only the columns you need; it reduces data and enables index-only scans.
- `NOT EXISTS` is NULL-safe and planned as an anti join; `NOT IN` is not NULL-safe.
- The planner reorders inner joins and pushes filters down; the written order does not decide the execution order.
- Measure with plans, actual rows and counts; verify that the answer did not change.

### Common mistakes

- Wrapping an indexed column in `EXTRACT`, `lower`, `CAST` or arithmetic in `WHERE`.
- Using `BETWEEN '1997-01-01' AND '1997-12-31'` on a timestamp column and losing the rows of the last day after midnight. Use `>= start AND < next_start`.
- Using `NOT IN (SELECT ...)` against a column that can be NULL and getting an empty result.
- Rewriting a query without checking that the row count is unchanged.
- Judging a query by a single timing.
- Putting a `WHERE` condition on the nullable side of a `LEFT JOIN` and turning it into an inner join.

### Revision notes

- Sargable: `col >= a AND col < b`. Not sargable: `f(col) = x`.
- Expression index: `CREATE INDEX ON t (lower(col))`.
- `NOT EXISTS` for anti joins. List columns, not `*`.
- Measure: plan, `actual rows`, `Rows Removed by Filter`, and an answer check.

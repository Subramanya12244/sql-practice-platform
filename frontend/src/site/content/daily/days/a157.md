## Objectives

- Connect to a database from Python, run a query, fetch the rows and close the connection, using the standard-library `sqlite3` module as a stand-in for PostgreSQL.
- Pass values to a query with parameters instead of building the SQL text, and explain what happens to the value when you do.
- Demonstrate SQL injection on a deliberately unsafe function, and fix it with a parameterised query and a whitelist for identifiers.
- Read a query result into a pandas DataFrame with `read_sql` and a `params` argument.
- Say where `sqlite3` differs from PostgreSQL with `psycopg` (placeholders, types, transactions, server) so the code can be moved.

## Understand

### Why analysts run SQL from Python

So far you wrote SQL in a query window and pandas in a notebook. Real analysis often needs both: SQL to select and aggregate the data inside the database, Python to model, chart, schedule and report. The bridge is a **database driver**, a library that sends SQL text to the database and returns the results as Python objects. Python defines a standard interface for drivers, called the **DB-API**, so that the code looks much the same for different databases: you create a **connection**, take a **cursor** from it, call `cursor.execute(sql, parameters)`, then fetch rows with `fetchone()`, `fetchmany(n)` or `fetchall()`. For PostgreSQL the usual driver is `psycopg` (the current version is psycopg 3); for SQLite, which is built into Python, it is the `sqlite3` module.

### The tool used in this lesson

A PostgreSQL server cannot run inside the lesson's browser sandbox or in the automated checks, so the runnable examples use `sqlite3` with an in-memory database. This is a different database engine and the differences matter, so keep this table in mind:

- **Placeholders.** `sqlite3` marks a parameter with `?` (positional) or `:name` (named). `psycopg` uses `%s` (positional) and `%(name)s` (named). The idea is identical; only the marker differs. A literal percent sign in a `psycopg` query must be written `%%`.
- **Types.** PostgreSQL enforces column types: putting `'abc'` into an integer column is an error. SQLite is loosely typed: a column has a type "affinity" but accepts a value of another type, and Example 4 shows it storing text in an `INTEGER` column. Code that works on SQLite can therefore hide type errors that PostgreSQL would raise.
- **Dates and many functions.** SQLite has no real date type (dates are text or numbers) and lacks PostgreSQL functions such as `date_trunc`. SQL that uses PostgreSQL features must be tested against PostgreSQL itself.
- **Transactions and connections.** Both start a transaction implicitly and need a `commit()` to save changes. `psycopg` can also be used as a context manager that commits at the end of the block (and closes the connection, in psycopg 3). `sqlite3` connections should be closed explicitly with `close()`.
- **Server and credentials.** PostgreSQL runs as a server that you reach with a host, port, database, user and password, which belong in environment variables or a secrets store, never in the code. SQLite is a local file or memory.

The browser Python and the checks use `sqlite3`, `pandas` and plain code. Code that needs a real PostgreSQL server is shown in untagged code blocks with the same logic proven on `sqlite3`.

### Parameterised queries

The most important habit of this lesson: **never build a query by pasting values into the SQL text**. Instead, write the SQL with placeholders and pass the values separately:

```python
cur.execute("SELECT * FROM orders WHERE customer = ? AND amount >= ?", (customer, minimum))
```

The driver (or the server) receives the statement and the values as separate things. The statement is parsed as SQL first, and the values are then bound as data, so a value can never change the structure of the statement, whatever characters it contains. This also removes quoting problems, such as a customer named O'Brien, and it lets the database reuse the plan for the statement.

### SQL injection

**SQL injection** happens when text supplied by a user ends up inside the SQL statement as code. If a function builds `"... WHERE customer = '" + name + "'"` and the name is `x' OR '1'='1`, the statement becomes `... WHERE customer = 'x' OR '1'='1'`, which is true for every row, and every order is returned. With a `UNION` the attacker can read another table, as Example 2 shows. In the worst cases injection allows deleting data or running commands. It is among the most common and most damaging security flaws, and the defence is simple and complete for values: parameters. Notes on what parameters do not cover: they bind **values only**, never identifiers such as a table or column name, or keywords such as `ASC` and `DESC`. When a program must choose a column or a sort direction dynamically, compare the input with a fixed list (a whitelist) and insert only the matching item from your own list.

### `read_sql` and the analyst's workflow

`pandas.read_sql_query(sql, connection, params=...)` runs a query and returns a DataFrame. It accepts the same placeholders as the driver and is the quickest way to move a result set into pandas. A good pattern is to let the database do the heavy work (filtering, joining, aggregating) and use pandas on the small result. With SQLAlchemy (a library that wraps drivers and gives one interface for many databases) you create an engine from a URL such as `sqlite://` for an in-memory database, or `postgresql+psycopg://user:password@host/dbname` for PostgreSQL, wrap the SQL in `text()` and use named parameters like `:name`. SQLAlchemy needs installing, so the example using it is shown as local-only.

### Common misconception

Many learners think that escaping or "cleaning" the string, for example by replacing quote characters, is as good as a parameter. It is not: escaping rules differ between databases and encodings, they are easy to get subtly wrong, and one forgotten code path is enough for an attack. The reliable defence is structural: the value never becomes part of the statement text. A second misconception is that internal tools do not need this. Data in your own database may come from a web form, a file upload or a partner system, and a tool written for analysts today often serves a wider group tomorrow.

## Syntax and key functions

```python
import sqlite3
conn = sqlite3.connect(":memory:")                 # connection
cur = conn.cursor()                                # cursor
cur.execute("SELECT ... WHERE x = ?", (value,))    # parameters as a tuple
rows = cur.fetchall()                              # list of tuples
conn.commit(); conn.close()
```

```python
# the same logic with psycopg 3 and PostgreSQL (needs a server, not run here)
import os
import psycopg

with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
    rows = conn.execute(
        "SELECT order_id, amount FROM orders WHERE customer = %s AND amount >= %s",
        (customer, minimum),
    ).fetchall()
```

| Function | Returns or does |
|---|---|
| `sqlite3.connect(path)` | A connection; `":memory:"` is a temporary database. |
| `conn.execute(sql, params)` | Runs one statement and returns a cursor. |
| `conn.executemany(sql, seq)` | Runs a statement once for each parameter set. |
| `cur.fetchone()` / `fetchall()` | One row or a list of all remaining rows (tuples). |
| `conn.row_factory = sqlite3.Row` | Rows that can be read by column name. |
| `pd.read_sql_query(sql, conn, params=...)` | A DataFrame from a query. |
| `conn.commit()` / `conn.close()` | Save changes / release the connection. |

## Learn by example

### Example 1: Connect, load, query with parameters

An in-memory database is created and filled with `executemany`, which sends one statement with several parameter sets. A query with two parameters returns the paid orders of one customer above a minimum amount. Rows can be read by column name with `sqlite3.Row`.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer TEXT, amount REAL, status TEXT)")
conn.executemany("INSERT INTO orders (customer, amount, status) VALUES (?, ?, ?)", [
    ("ana", 120.0, "paid"), ("ben", 35.5, "paid"), ("ana", 80.0, "refunded"),
    ("cy", 210.0, "paid"), ("ben", 15.0, "failed"), ("cy", 60.0, "paid"),
])
conn.execute("CREATE TABLE secrets (name TEXT, value TEXT)")
conn.execute("INSERT INTO secrets VALUES ('api_key', 'k-12345')")
conn.commit()
conn.row_factory = sqlite3.Row
rows = conn.execute(
    "SELECT order_id, amount FROM orders WHERE customer = ? AND status = ? AND amount >= ? ORDER BY order_id",
    ("ana", "paid", 100),
).fetchall()
print("rows:", len(rows))
for r in rows:
    print(r["order_id"], r["amount"])
total = conn.execute("SELECT customer, SUM(amount) FROM orders GROUP BY customer ORDER BY customer").fetchall()
print([tuple(t) for t in total])
conn.close()
```

```output
rows: 1
1 120.0
[('ana', 200.0), ('ben', 50.5), ('cy', 270.0)]
```

The three placeholders are filled from the tuple in order. The aggregate query shows that the database does the grouping and Python only receives three rows.

### Example 2: SQL injection, demonstrated

An unsafe function builds the statement with an f-string. A normal name works, but a crafted name returns every order, and another crafted name reads the `secrets` table through a `UNION`. The safe function uses a parameter and treats the same text as a customer name that does not exist.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer TEXT, amount REAL, status TEXT)")
conn.executemany("INSERT INTO orders (customer, amount, status) VALUES (?, ?, ?)", [
    ("ana", 120.0, "paid"), ("ben", 35.5, "paid"), ("ana", 80.0, "refunded"),
    ("cy", 210.0, "paid"), ("ben", 15.0, "failed"), ("cy", 60.0, "paid"),
])
conn.execute("CREATE TABLE secrets (name TEXT, value TEXT)")
conn.execute("INSERT INTO secrets VALUES ('api_key', 'k-12345')")
conn.commit()
def unsafe(name):
    sql = f"SELECT order_id, customer FROM orders WHERE customer = '{name}'"
    return conn.execute(sql).fetchall()

def safe(name):
    return conn.execute("SELECT order_id, customer FROM orders WHERE customer = ?", (name,)).fetchall()

print("normal:", len(unsafe("ana")))
print("injected OR:", len(unsafe("x' OR '1'='1")))
print("injected UNION:", unsafe("x' UNION SELECT 0, value FROM secrets --"))
print("safe, same text:", safe("x' OR '1'='1"))
try:
    conn.execute("SELECT 1; DROP TABLE orders")
except Exception as e:
    print("two statements:", type(e).__name__)
conn.close()
```

```output
normal: 2
injected OR: 6
injected UNION: [(0, 'k-12345')]
safe, same text: []
two statements: ProgrammingError
```

The unsafe function returned all six orders for the injected name and exposed the API key from another table. The safe function returned nothing, because the whole text was treated as one customer name. The last block shows that `sqlite3` refuses to run two statements in one call, which blocks some attacks but not the two shown above: do not rely on it.

### Example 3: `read_sql_query` with parameters

A parameterised query goes straight into a DataFrame. The pandas step then works on the small result: here a share of the paid revenue per customer.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer TEXT, amount REAL, status TEXT)")
conn.executemany("INSERT INTO orders (customer, amount, status) VALUES (?, ?, ?)", [
    ("ana", 120.0, "paid"), ("ben", 35.5, "paid"), ("ana", 80.0, "refunded"),
    ("cy", 210.0, "paid"), ("ben", 15.0, "failed"), ("cy", 60.0, "paid"),
])
conn.execute("CREATE TABLE secrets (name TEXT, value TEXT)")
conn.execute("INSERT INTO secrets VALUES ('api_key', 'k-12345')")
conn.commit()
import pandas as pd

df = pd.read_sql_query(
    "SELECT customer, SUM(amount) AS revenue, COUNT(*) AS orders FROM orders WHERE status = ? GROUP BY customer ORDER BY customer",
    conn, params=("paid",),
)
df["share_pct"] = (df["revenue"] / df["revenue"].sum() * 100).round(1)
print(df.to_string(index=False))
conn.close()
```

```output
customer  revenue  orders  share_pct
     ana    120.0       1       28.2
     ben     35.5       1        8.3
      cy    270.0       2       63.5
```

The filter and the aggregation ran in the database, and pandas only added a column. The `params` argument takes the same placeholder style as the driver (`?` for `sqlite3`, `%s` for `psycopg`).

### Example 4: Loose types, and identifiers that cannot be parameters

SQLite accepts text in an integer column, which PostgreSQL would reject. A parameter also cannot stand for a column name, so a whitelist chooses the sort column.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE t (a INTEGER, b TEXT)")
conn.execute("INSERT INTO t VALUES (?, ?)", ("not a number", "x"))
print(conn.execute("SELECT a, typeof(a) FROM t").fetchall())

conn.executemany("INSERT INTO t VALUES (?, ?)", [(3, "c"), (1, "a"), (2, "b")])
ALLOWED = {"a": "a", "b": "b"}

def sorted_rows(column):
    col = ALLOWED.get(column)
    if col is None:
        raise ValueError("column not allowed: " + column)
    return conn.execute(f"SELECT a, b FROM t WHERE typeof(a) = 'integer' ORDER BY {col}").fetchall()

print(sorted_rows("b"))
try:
    sorted_rows("a; DROP TABLE t")
except ValueError as e:
    print(e)
conn.close()
```

```output
[('not a number', 'text')]
[(1, 'a'), (2, 'b'), (3, 'c')]
column not allowed: a; DROP TABLE t
```

The first line shows `('not a number', 'text')`: the database did not complain. Only the whitelisted names reach the SQL text, because the f-string inserts the value that came from `ALLOWED`, never the user's string.

### Example 5: SQLAlchemy with named parameters

The same query through SQLAlchemy, with `text()` and a named parameter. This example needs `pip install sqlalchemy` and runs on your own computer; the browser shows it read-only with the verified output.

```python local
import pandas as pd
from sqlalchemy import create_engine, text

engine = create_engine("sqlite://")
with engine.begin() as conn:
    conn.execute(text("CREATE TABLE orders (customer TEXT, amount REAL, status TEXT)"))
    conn.execute(text("INSERT INTO orders VALUES (:c, :a, :s)"),
                 [{"c": "ana", "a": 120.0, "s": "paid"}, {"c": "ben", "a": 35.5, "s": "paid"}, {"c": "ana", "a": 80.0, "s": "refunded"}])

with engine.connect() as conn:
    df = pd.read_sql(text("SELECT customer, SUM(amount) AS revenue FROM orders WHERE status = :s GROUP BY customer ORDER BY customer"), conn, params={"s": "paid"})
print(df.to_string(index=False))
engine.dispose()
```

```output
customer  revenue
     ana    120.0
     ben     35.5
```

With a PostgreSQL server, only the URL changes (`postgresql+psycopg://user:password@host:5432/dbname`), and the SQL must be valid PostgreSQL.

### Example 6: PostgreSQL SQL on the browser database

SQL that uses PostgreSQL features cannot run on `sqlite3`, so it is shown on the PostgreSQL-compatible database of the browser. This is the query a script would send with `%s` placeholders; here the value is written into the text only because the browser runner has no parameters, and you would never do this with user input.

```sql run
SELECT date_trunc('quarter', o.order_date)::date AS quarter,
       COUNT(*) AS orders,
       COUNT(*) FILTER (WHERE o.shipped_date IS NULL) AS unshipped
FROM orders o
WHERE o.order_date >= DATE '1998-01-01'
GROUP BY 1
ORDER BY 1;
```

```output
quarter | orders | unshipped
1998-01-01 | 9 | 2
1998-04-01 | 8 | 1
1998-07-01 | 8 | 1
1998-10-01 | 8 | 1
```

`date_trunc` and `FILTER` are available in PostgreSQL, but `date_trunc` does not exist in SQLite (which has `strftime` instead), so the Python code of this query must be run against a real PostgreSQL connection.

## Real-world applications

- **Scheduled reports**: a script runs a parameterised query for the reporting month, loads the result with `read_sql`, formats it and sends it, as in Example 3.
- **Internal tools**: a dashboard with a customer search box passes the typed text as a parameter (Example 2's `safe` function), so a curious user cannot read other tables.
- **Prototyping against a copy**: analysts test a query logic on `sqlite3` or SQLAlchemy locally and then point the same code at PostgreSQL, changing the placeholder style or the URL and rechecking the SQL features.
- **Auditing code**: during a review, any f-string, `%` formatting or `+` inside an `execute` call is flagged as a possible injection.

## Daily review

### Key takeaways

- A DB-API workflow is connect, cursor, execute with parameters, fetch, commit if you wrote, close.
- Values go in parameters, never in the SQL text: placeholders are `?` or `:name` in `sqlite3` and `%s` or `%(name)s` in `psycopg`.
- Parameters bind values only; use a whitelist for column names and sort directions.
- `read_sql_query` with `params` loads a result into pandas; let the database do the heavy work.
- `sqlite3` is loosely typed and lacks PostgreSQL features; test PostgreSQL-specific SQL against PostgreSQL.

### Common mistakes

- Building SQL with an f-string or `+`. It works in testing and fails safely only until someone types a quote; use placeholders.
- Passing a single value as `("ana")` instead of `("ana",)`. The parentheses without a comma are just a string, and `sqlite3` raises `ProgrammingError: Incorrect number of bindings supplied`.
- Using `%s` placeholders with `sqlite3` or `?` with `psycopg`. The statement fails with a syntax or binding error; use the marker of the driver.
- Forgetting `commit()` after an insert. The rows exist inside the connection but disappear when it closes.
- Not closing the connection. Connections are limited resources; close them or use a context manager.

### Revision notes

- `cur.execute(sql, (a, b))`: parameters as a tuple; a one-element tuple needs a trailing comma.
- Placeholders: `?` / `:name` (sqlite3), `%s` / `%(name)s` (psycopg).
- Never format values into SQL; whitelist identifiers.
- `pd.read_sql_query(sql, conn, params=(...))`.

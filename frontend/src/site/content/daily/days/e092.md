## Objectives

- Choose PostgreSQL column types for loaded data, and explain why money belongs in `numeric` and not in a floating-point type.
- Decide between a natural key and a surrogate key, and declare primary, unique and foreign keys.
- Write `NOT NULL`, `CHECK`, `UNIQUE` and `DEFAULT` constraints, and predict which bad rows each one rejects (including the NULL trap in `CHECK`).
- Design a staging table that accepts raw text safely and records where each row came from.
- Promote staged rows into a typed target table with casts, sending bad rows to a reject table with a reason.

## Understand

### Design the destination before you load

A **target schema** is the set of tables, columns, types and rules that will receive your data. In a pipeline the data arrives from somewhere you do not control, such as a CSV export, and the target table is the one place you do control. Every guarantee you put into the schema is a guarantee that every later query and report can rely on without checking again. A column typed `date` can never contain the word "tomorrow"; a column typed `text` can contain anything, so each analyst must defend against anything. Designing the schema first is therefore cheaper than cleaning the table afterwards.

On Day 45 you met `CREATE TABLE`, types and constraints as SQL. This day applies them as a data engineer: you read a source file, decide what each column is, and write the table that makes bad data impossible to store. All the SQL below runs on PGlite, a real PostgreSQL engine compiled to run in the browser, so the types and errors are PostgreSQL's own.

### Choosing data types

Pick the narrowest type that represents every legal value exactly. For identifiers and counts use `integer` (4 bytes, up to 2,147,483,647) or `bigint` (8 bytes) when the value could pass two billion. For text use `text`; in PostgreSQL `varchar(n)` is not faster, it only adds a length limit, so use it only when the limit is a real rule. For true or false use `boolean`.

For money and any measured quantity that must add up exactly use `numeric(precision, scale)`: `numeric(12,2)` holds twelve digits in total, two after the decimal point. The floating-point types `real` and `double precision` store binary approximations, so `0.1` is stored as a nearby fraction, and sums drift by tiny amounts. They suit sensor readings, never invoices. For time use `date` for a calendar day, `timestamp` for a date and time with no zone, and `timestamptz` for an exact instant; `timestamptz` is stored in UTC and shown in the session's time zone, which is why event times are usually `timestamptz`.

A common mistake is to store a date as `text` "because it loaded without errors". It loads, and then sorting is alphabetical, date arithmetic fails and `05/01/2026` is ambiguous between 5 January and 1 May.

### Keys

A **primary key** is the column, or columns, that identifies one row. It is unique and never NULL, and PostgreSQL builds an index on it. A **natural key** comes from the data itself, such as an order number given by the source system. A **surrogate key** is a meaningless number your database generates. In PostgreSQL write `customer_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY`. Surrogate keys are stable when the source corrects a value, but they do not stop duplicates: if the source's natural key, such as an email address, is not also declared `UNIQUE`, the same customer can be loaded twice under two surrogate numbers. Keep the natural key as a unique **business key** next to the surrogate.

A **foreign key** says a column's value must exist in another table's key. `customer_id integer REFERENCES dim_customer(customer_id)` stops an order from naming a customer that does not exist.

### Constraints

A **constraint** is a rule the database enforces on every insert and update. `NOT NULL` rejects a missing value. `UNIQUE` rejects a repeated value. `CHECK (condition)` rejects a row when the condition is false. `DEFAULT value` fills a column when the insert leaves it out. Each failed rule raises an error with a standard five-character code called the SQLSTATE: `23502` not-null, `23505` unique, `23503` foreign key and `23514` check. Pipelines test these codes to decide what to do with a failed row.

Two details surprise beginners. A `CHECK` passes when its condition is **unknown**, so with `CHECK (amount >= 0)` a NULL amount is accepted, because `NULL >= 0` is NULL and not false. Add `NOT NULL` whenever missing must be illegal. And `UNIQUE` allows many NULLs, since two unknowns are not known to be equal.

### Staging tables

A **staging table** is a holding table where data lands before it is trusted. Its columns are all `text`, so any file can load into it without a type error, and the strict checking happens in SQL afterwards. It also carries **load metadata**: the row number in the file, the source file name and a `loaded_at` time, so that any bad value can be traced to its origin. A load then has three steps: land the raw rows in staging, validate them, and promote the valid rows into the typed target with casts. Rows that fail validation go to a **reject table** with a reason, so nothing is silently lost and the count staged always equals the count loaded plus the count rejected. Staging is usually emptied at the start of each run.

### Why validation in SQL has limits

A pattern test such as "four digits, a dash, two digits, a dash, two digits" accepts `2026-02-30`, which is not a real date. Casting it raises an error that stops the whole statement. Real calendar checks therefore happen where you can test one value at a time, in Python, or by casting only the rows already known to be well-formed.

### Common misconception

Many learners think constraints slow loading down for no gain and should be added "later, once the data is clean". Data that is not constrained does not become clean; it stays dirty and hides the problem. Constraints turn a silent data defect into an immediate, countable, traceable error.

### Why it matters

A well-chosen schema is the cheapest data-quality tool available: it prevents duplicates, orphan rows, negative amounts and unreadable dates at the moment of loading. The staging pattern also gives you a place to count and explain every row, which is how you can later prove that a load is complete.

## Syntax and key functions

A typed target table:

```sql-syntax
CREATE TABLE table_name (
  id        bigint PRIMARY KEY,
  key_col   integer GENERATED ALWAYS AS IDENTITY,
  amount    numeric(12,2) NOT NULL CHECK (amount >= 0),
  status    text NOT NULL DEFAULT 'new',
  other_id  integer REFERENCES other_table (other_id),
  UNIQUE (business_key)
);
```

`PRIMARY KEY` means unique and not null. `GENERATED ALWAYS AS IDENTITY` lets PostgreSQL number the column. `REFERENCES` declares a foreign key. A table-level `UNIQUE (a, b)` makes the pair unique.

Promote from staging:

```sql-syntax
INSERT INTO target (col1, col2)
SELECT col1::bigint, col2::numeric(12,2)
FROM stg
WHERE <rules that make the cast safe>;
```

| Item | Meaning |
|---|---|
| `integer`, `bigint` | Whole numbers, 4 and 8 bytes. |
| `numeric(p,s)` | Exact decimal with `p` digits, `s` after the point. |
| `double precision` | Binary floating point; approximate. |
| `text`, `varchar(n)` | Text without limit / with a length limit. |
| `date`, `timestamp`, `timestamptz` | A day / a date and time / an exact instant. |
| `boolean` | `true` or `false` (and NULL). |
| `value::type`, `CAST(value AS type)` | Convert a value; raises an error when it cannot. |
| `pg_typeof(x)` | The type of an expression, as text. |
| `col ~ 'regex'` | True when the text matches the regular expression. |
| `information_schema.columns` | Catalogue view listing each column's name, type and nullability. |
| `SQLSTATE` | The standard code of the last error, such as `23505`. |

## Learn by example

### Example 1: Why money is `numeric`

Summing `0.1` ten times is not exactly `1` in floating point, because `0.1` has no exact binary form. `numeric` stores decimal digits and gets exactly `1.0`. `pg_typeof` names the type that each literal gets.

```sql run
SELECT
  sum(0.1::double precision) = 1.0 AS float_sum_is_one,
  sum(0.1::numeric) = 1.0 AS numeric_sum_is_one,
  pg_typeof(sum(0.1::double precision)) AS float_type,
  pg_typeof(sum(0.1::numeric)) AS numeric_type
FROM generate_series(1, 10);
```

```output
float_sum_is_one | numeric_sum_is_one | float_type | numeric_type
false | true | double precision | numeric
```

### Example 2: A typed target with keys and constraints

This creates a customer dimension and an order fact table, loads two valid rows and reads the column catalogue back. `customer_id` is a surrogate key; `email` is the unique business key. The tables exist only inside this example, because the browser rolls back every run.

```sql run
CREATE TABLE dim_customer (
  customer_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text NOT NULL UNIQUE,
  full_name   text NOT NULL
);
CREATE TABLE fact_order (
  order_id    bigint PRIMARY KEY,
  customer_id integer NOT NULL REFERENCES dim_customer (customer_id),
  order_date  date NOT NULL,
  amount      numeric(12,2) NOT NULL CHECK (amount >= 0),
  status      text NOT NULL DEFAULT 'new' CHECK (status IN ('new', 'paid', 'shipped', 'cancelled'))
);
INSERT INTO dim_customer (email, full_name) VALUES ('ana@example.com', 'Ana Silva'), ('ben@example.com', 'Ben Okoye');
INSERT INTO fact_order (order_id, customer_id, order_date, amount) VALUES (1001, 1, '2026-01-05', 19.90), (1002, 2, '2026-01-06', 25);
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'fact_order'
ORDER BY ordinal_position;
```

```output
column_name | data_type | is_nullable | column_default
order_id | bigint | NO | NULL
customer_id | integer | NO | NULL
order_date | date | NO | NULL
amount | numeric | NO | NULL
status | text | NO | 'new'::text
```

### Example 3: Watching each constraint fire

A `DO` block is a small PL/pgSQL program that runs once. Each attempt is wrapped in its own `BEGIN ... EXCEPTION` block so that one failure does not stop the next, and the SQLSTATE of each failure is logged in a table that the final `SELECT` reads. The last attempt is a NULL balance: the `CHECK` accepts it, the trap described above.

```sql run
CREATE TABLE acct (id integer PRIMARY KEY, email text NOT NULL UNIQUE, balance numeric(8,2) CHECK (balance >= 0));
CREATE TABLE note (id integer PRIMARY KEY, acct_id integer REFERENCES acct (id));
INSERT INTO acct VALUES (1, 'a@x.com', 10);
CREATE TABLE attempt (n integer GENERATED ALWAYS AS IDENTITY, label text, sqlstate text);
DO $$
BEGIN
  BEGIN INSERT INTO acct VALUES (2, NULL, 5);
    INSERT INTO attempt (label, sqlstate) VALUES ('null email', 'ok');
  EXCEPTION WHEN OTHERS THEN INSERT INTO attempt (label, sqlstate) VALUES ('null email', SQLSTATE); END;
  BEGIN INSERT INTO acct VALUES (3, 'a@x.com', 5);
    INSERT INTO attempt (label, sqlstate) VALUES ('duplicate email', 'ok');
  EXCEPTION WHEN OTHERS THEN INSERT INTO attempt (label, sqlstate) VALUES ('duplicate email', SQLSTATE); END;
  BEGIN INSERT INTO acct VALUES (4, 'd@x.com', -1);
    INSERT INTO attempt (label, sqlstate) VALUES ('negative balance', 'ok');
  EXCEPTION WHEN OTHERS THEN INSERT INTO attempt (label, sqlstate) VALUES ('negative balance', SQLSTATE); END;
  BEGIN INSERT INTO note VALUES (1, 99);
    INSERT INTO attempt (label, sqlstate) VALUES ('unknown account', 'ok');
  EXCEPTION WHEN OTHERS THEN INSERT INTO attempt (label, sqlstate) VALUES ('unknown account', SQLSTATE); END;
  BEGIN INSERT INTO acct VALUES (5, 'e@x.com', NULL);
    INSERT INTO attempt (label, sqlstate) VALUES ('null balance', 'ok');
  EXCEPTION WHEN OTHERS THEN INSERT INTO attempt (label, sqlstate) VALUES ('null balance', SQLSTATE); END;
END $$;
SELECT label, sqlstate FROM attempt ORDER BY n;
```

```output
label | sqlstate
null email | 23502
duplicate email | 23505
negative balance | 23514
unknown account | 23503
null balance | ok
```

### Example 4: A staging table and shape checks

The staging table keeps every field as text and adds load metadata. The query tests the shape of each field with regular expressions and returns a boolean per rule; none of it can fail on dirty input because nothing is cast. `row_num` lets you point at the exact line of the file.

```sql run
CREATE TABLE stg_order (
  row_num integer, order_id text, customer_email text, order_date text, amount text, status text,
  source_file text DEFAULT 'orders_2026_01.csv', loaded_at timestamptz DEFAULT now()
);
INSERT INTO stg_order (row_num, order_id, customer_email, order_date, amount, status) VALUES
  (1, '1001', 'ana@example.com', '2026-01-05', '19.90', 'paid'),
  (2, '1002', 'ben@example.com', '2026-01-06', '25',    'paid'),
  (3, 'abc',  'cy@example.com',  '2026-01-07', '12.50', 'new'),
  (4, '1004', '',                '2026-01-08', '-4',    'shipped'),
  (5, '1005', 'dee@example.com', '2026-01-09', '8.00',  'pending'),
  (6, '1006', 'eli@example.com', '2026-01-09', '',      'paid'),
  (7, '1007', 'fay@example.com', '05/01/2026', '30.00', 'paid'),
  (8, '1008', 'gus@example.com', '2026-01-10', '7.5',   'paid');
SELECT row_num,
       order_id ~ '^[0-9]+$' AS id_ok,
       order_date ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$' AS date_ok,
       amount ~ '^[0-9]+(\.[0-9]{1,2})?$' AS amount_ok,
       source_file
FROM stg_order
ORDER BY row_num;
```

```output
row_num | id_ok | date_ok | amount_ok | source_file
1 | true | true | true | orders_2026_01.csv
2 | true | true | true | orders_2026_01.csv
3 | false | true | true | orders_2026_01.csv
4 | true | true | false | orders_2026_01.csv
5 | true | true | true | orders_2026_01.csv
6 | true | true | false | orders_2026_01.csv
7 | true | false | true | orders_2026_01.csv
8 | true | true | true | orders_2026_01.csv
```

### Example 5: Promote the valid rows and reject the rest

The reject table is filled first, with the first rule each row breaks. The target insert then takes only the rows that are not rejected, so the casts run on well-formed text only. The final query proves that staged equals loaded plus rejected: 3 loaded and 5 rejected make the 8 staged rows.

```sql run
CREATE TABLE stg_order (row_num integer, order_id text, customer_email text, order_date text, amount text, status text);
INSERT INTO stg_order VALUES
  (1, '1001', 'ana@example.com', '2026-01-05', '19.90', 'paid'),
  (2, '1002', 'ben@example.com', '2026-01-06', '25',    'paid'),
  (3, 'abc',  'cy@example.com',  '2026-01-07', '12.50', 'new'),
  (4, '1004', '',                '2026-01-08', '-4',    'shipped'),
  (5, '1005', 'dee@example.com', '2026-01-09', '8.00',  'pending'),
  (6, '1006', 'eli@example.com', '2026-01-09', '',      'paid'),
  (7, '1007', 'fay@example.com', '05/01/2026', '30.00', 'paid'),
  (8, '1008', 'gus@example.com', '2026-01-10', '7.5',   'paid');
CREATE TABLE fact_order (
  order_id bigint PRIMARY KEY, customer_email text NOT NULL, order_date date NOT NULL,
  amount numeric(12,2) NOT NULL CHECK (amount >= 0),
  status text NOT NULL CHECK (status IN ('new', 'paid', 'shipped', 'cancelled'))
);
CREATE TABLE reject_order (row_num integer, reason text);
INSERT INTO reject_order
SELECT row_num,
  CASE WHEN order_id !~ '^[0-9]+$' THEN 'bad order_id'
       WHEN customer_email = '' THEN 'missing email'
       WHEN order_date !~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$' THEN 'bad date'
       WHEN amount !~ '^[0-9]+(\.[0-9]{1,2})?$' THEN 'bad amount'
       WHEN status NOT IN ('new', 'paid', 'shipped', 'cancelled') THEN 'bad status'
  END
FROM stg_order
WHERE order_id !~ '^[0-9]+$' OR customer_email = '' OR order_date !~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'
   OR amount !~ '^[0-9]+(\.[0-9]{1,2})?$' OR status NOT IN ('new', 'paid', 'shipped', 'cancelled');
INSERT INTO fact_order
SELECT order_id::bigint, customer_email, order_date::date, amount::numeric(12,2), status
FROM stg_order
WHERE row_num NOT IN (SELECT row_num FROM reject_order);
SELECT 'loaded' AS outcome, count(*) AS rows FROM fact_order
UNION ALL
SELECT reason, count(*) FROM reject_order GROUP BY reason
ORDER BY outcome;
```

```output
outcome | rows
bad amount | 1
bad date | 1
bad order_id | 1
bad status | 1
loaded | 3
missing email | 1
```

### Example 6: From pandas dtypes to a `CREATE TABLE`

Python can draft the DDL from a DataFrame, but only as a starting point: a `float64` column is mapped to `double precision`, and design must override it where the meaning is money. The mapping below is a fixed dictionary, so no value from the data is ever pasted into the SQL. The text produced is plain PostgreSQL DDL that you would review and run on a server.

```python run
import pandas as pd

df = pd.DataFrame({
    "order_id": [1001, 1002],
    "customer_email": ["ana@example.com", "ben@example.com"],
    "order_date": pd.to_datetime(["2026-01-05", "2026-01-06"]),
    "amount": [19.90, 25.0],
    "paid": [True, False],
})
TYPE_MAP = {"int64": "bigint", "float64": "double precision", "object": "text", "bool": "boolean", "datetime64[ns]": "date"}
OVERRIDES = {"amount": "numeric(12,2)"}

def ddl(name, frame):
    lines = [f"  {col} {OVERRIDES.get(col, TYPE_MAP[str(dtype)])}" for col, dtype in frame.dtypes.items()]
    return f"CREATE TABLE {name} (\n" + ",\n".join(lines) + "\n);"

print(ddl("fact_order", df))
```

```output
CREATE TABLE fact_order (
  order_id bigint,
  customer_email text,
  order_date date,
  amount numeric(12,2),
  paid boolean
);
```

## Real-world applications

- **Landing a vendor file.** A partner sends a CSV whose dates, codes and amounts are inconsistent. A text staging table (Example 4) accepts it whatever it contains, and validation queries count the problems before anything reaches reporting tables.
- **Protecting finance reports.** A `numeric(12,2)` amount with `NOT NULL` and a `CHECK` (Examples 1 and 2) guarantees that revenue sums are exact and that no negative or missing amount can be stored, so a monthly total is the same every time it is recalculated.
- **Audit and re-processing.** A reject table with row numbers and reasons (Example 5) gives the data owner a list to correct and re-send, and lets you prove that every staged row is accounted for.
- **Handling failed loads in code.** Pipelines catch the SQLSTATE codes from Example 3 to decide whether a failure is a duplicate to skip, an orphan to park or a real fault to stop on.

## Daily review

### Key takeaways

- Design the target first: types, keys and constraints decide what bad data can be stored.
- Use `numeric(p,s)` for money, `date` or `timestamptz` for time, `text` for text, and `bigint` when a count could pass two billion.
- Keep a unique business key next to a surrogate key, or duplicates slip in under new numbers.
- `CHECK` accepts NULL and `UNIQUE` allows several NULLs; add `NOT NULL` when missing is illegal.
- Land raw data in an all-text staging table with load metadata, validate, promote with casts and send failures to a reject table with a reason.

### Common mistakes

- Typing a money column as `real` or `double precision`, so totals show values like `0.30000000000000004` or fail to match a source total by a cent. Use `numeric(12,2)`.
- Storing dates as text. Sorting is alphabetical, `ORDER BY` puts `10/01/2026` before `2/01/2026`, and date arithmetic needs a conversion every time. Cast to `date` on the way in.
- Assuming a `CHECK (x >= 0)` rejects NULL. It does not: the condition is unknown, and unknown passes.
- Loading straight into the typed table. One bad value raises `invalid input syntax for type integer: "abc"` and the whole statement, with every good row, is rolled back. Stage first.
- Relying on a surrogate key alone, so the same business record is loaded twice. Declare the business key `UNIQUE`.
- Validating a date only by its shape; `2026-02-30` passes the pattern and then fails the cast with `date/time field value out of range`.

### Revision notes

- `numeric(12,2)` exact, `double precision` approximate; `date` a day, `timestamptz` an instant.
- `id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY`; `business_key text NOT NULL UNIQUE`; `REFERENCES parent (key)`.
- SQLSTATE: `23502` not null, `23505` unique, `23503` foreign key, `23514` check.
- Staging (text plus `row_num`, `source_file`, `loaded_at`), then validate, promote with `::type`, reject with a reason; staged = loaded + rejected.

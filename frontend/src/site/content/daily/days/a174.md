## Objectives

- Apply the six quality rules in a cleaning function that reports the rows removed at every step.
- Standardise labels and drop orphan and duplicate rows without changing valid data.
- Validate the cleaned tables by re-running the rules and requiring zero violations.
- Reconcile rows and revenue between the raw and clean tables so that every difference has a named cause.

## Understand

### What this stage produces

Day 173 delivered raw tables that match the manifest. This stage produces cleaned tables plus two pieces of evidence: a log of how many rows each step removed, and a validation that the rules now hold. Cleaning without evidence is guesswork: a reader cannot tell whether you removed 5 rows or 500. The cleaning function in this capstone, `clean(t)`, takes the raw tables and returns the cleaned tables and a log dictionary. It never changes the raw tables: it works on copies, so the raw baseline stays available for comparison.

### Order of the cleaning steps

The order matters because the steps interact. First remove exact duplicate order rows, since a duplicated order inflates every later count. Second remove rows with a quantity of zero or less, because a negative quantity cannot be a sale. Third standardise customer labels (`" us "` becomes `US`) with `str.strip()` and `str.upper()`. Fourth drop orders whose customer is not in the customers table: they cannot be attributed to a country. Fifth, filter the returns to orders that still exist, and drop repeated returns for one order. Last, add the derived columns: the product's price, the line revenue and a `returned` flag. Each step records the row count after it runs, so the log reads like an audit trail.

### Remove or fix

Not every defect should be deleted. A label such as `us ` is fixable without losing information, so it is standardised. A negative quantity might be a data entry error or a refund recorded in the wrong table, and the cleaning cannot know which, so it is removed and counted, with the decision recorded in the README. A rule of thumb: fix when the correct value is certain, remove and report when it is not, and never invent values. Removing rows also changes totals, which is why a reconciliation is required.

### Validation is a separate step

Validation re-runs the rules from Day 172 on the cleaned tables. All six must report zero violations. This is independent evidence: it would catch a cleaning step that has a bug, such as a filter written backwards. Validation is also what you run every time the data is regenerated, so it doubles as a regression test and becomes a pytest test on Day 179.

### Reconciliation

Reconciliation shows that raw and clean tables differ only by the documented removals. Row reconciliation: raw rows equal clean rows plus rows removed at each step. Revenue reconciliation: raw revenue equals clean revenue plus the revenue of the removed rows at each step, with a difference of exactly zero. A non-zero difference means a row went missing or was changed without a log entry. A misconception is that reconciling is only for accountants: any analysis that reports a total benefits from knowing why it differs from the source system.

## Syntax and key functions

```python
o = o.drop_duplicates()                              # remove exact repeats, keep the first
o = o[o["quantity"] > 0]                             # keep valid rows
c["country"] = c["country"].str.strip().str.upper()  # standardise labels
o = o[o["customer_id"].isin(c["customer_id"])]       # drop orphans
```

| Function | Returns |
|---|---|
| `df.drop_duplicates(subset=None)` | DataFrame without repeated rows (first kept) |
| `s.str.strip()` and `s.str.upper()` | Text Series without surrounding spaces and in capitals |
| `s.isin(values)` | Boolean Series for membership |
| `df.merge(other, on=k, how="left")` | Rows of `df` with matching columns from `other` |
| `round(x, 2)` | Number rounded to 2 decimals |

## Learn by example

### Example 1: Clean with row accounting

The function applies the steps in order and records the row count after each one. The log is printed and checked: raw rows minus removals equals the final rows.

```python run
import numpy as np
import pandas as pd


def generate(seed=7):
    """Seeded online-store data with planted defects: 500 orders, 120 customers, 20 products."""
    rng = np.random.default_rng(seed)
    customers = pd.DataFrame({
        "customer_id": np.arange(1, 121),
        "country": rng.choice(["DE", "FR", "UK", "US"], 120, p=[0.3, 0.2, 0.2, 0.3]),
        "signup_date": pd.Timestamp("2024-07-01") + pd.to_timedelta(rng.integers(0, 180, 120), unit="D"),
    })
    customers.loc[rng.choice(120, 8, replace=False), "country"] = "us "
    products = pd.DataFrame({
        "product_id": np.arange(1, 21),
        "category": np.repeat(["home", "beauty", "sports", "electronics"], 5),
        "unit_price": (10 + rng.random(20) * 90).round(2),
    })
    campaigns = pd.DataFrame({
        "campaign_id": [0, 1, 2, 3],
        "channel": ["organic", "email", "paid_search", "social"],
        "spend": [0.0, 800.0, 2500.0, 1200.0],
    })
    n = 500
    orders = pd.DataFrame({
        "order_id": np.arange(1001, 1001 + n),
        "customer_id": rng.integers(1, 121, n),
        "product_id": rng.integers(1, 21, n),
        "order_date": pd.Timestamp("2025-01-01") + pd.to_timedelta(rng.integers(0, 180, n), unit="D"),
        "quantity": rng.integers(1, 5, n),
        "discount_pct": rng.choice([0, 10, 20], n, p=[0.6, 0.25, 0.15]),
        "campaign_id": rng.choice([0, 1, 2, 3], n, p=[0.4, 0.2, 0.25, 0.15]),
    })
    orders.loc[rng.choice(n, 5, replace=False), "quantity"] = -1
    orders.loc[rng.choice(n, 6, replace=False), "customer_id"] = 999
    orders = pd.concat([orders, orders.sample(10, random_state=1)], ignore_index=True)
    returned = rng.choice(np.arange(1001, 1001 + n), 60, replace=False)
    returns = pd.DataFrame({
        "order_id": np.concatenate([returned, [9001, 9002, 9003]]),
        "reason": rng.choice(["damaged", "wrong_item", "changed_mind"], 63, p=[0.3, 0.2, 0.5]),
    })
    return {"orders": orders, "customers": customers, "products": products, "campaigns": campaigns, "returns": returns}



def clean(t):
    """Apply the quality rules; return cleaned tables and a row-accounting log."""
    log = {}
    o = t["orders"]
    log["raw_orders"] = len(o)
    o = o.drop_duplicates()
    log["after_duplicates"] = len(o)
    o = o[o["quantity"] > 0]
    log["after_quantity"] = len(o)
    c = t["customers"].copy()
    c["country"] = c["country"].str.strip().str.upper()
    o = o[o["customer_id"].isin(c["customer_id"])]
    log["after_customers"] = len(o)
    r = t["returns"]
    log["raw_returns"] = len(r)
    r = r[r["order_id"].isin(o["order_id"])].drop_duplicates("order_id")
    log["clean_returns"] = len(r)
    p = t["products"]
    o = o.merge(p[["product_id", "unit_price"]], on="product_id", how="left")
    o["revenue"] = (o["quantity"] * o["unit_price"] * (1 - o["discount_pct"] / 100)).round(2)
    o["returned"] = o["order_id"].isin(r["order_id"])
    return {"orders": o.reset_index(drop=True), "customers": c, "products": p, "campaigns": t["campaigns"], "returns": r.reset_index(drop=True)}, log


t = generate()
clean_t, log = clean(t)
for k, v in log.items():
    print(f"{k}: {v}")
removed = log["raw_orders"] - log["after_customers"]
print("orders removed:", removed, "| clean orders:", len(clean_t["orders"]))
print("countries:", sorted(clean_t["customers"]["country"].unique()))
```

```output
raw_orders: 510
after_duplicates: 500
after_quantity: 495
after_customers: 489
raw_returns: 63
clean_returns: 59
orders removed: 21 | clean orders: 489
countries: ['DE', 'FR', 'UK', 'US']
```

### Example 3: Reconcile revenue

Revenue is computed for the raw rows and for the rows removed at each step. Raw revenue minus the removed revenue must equal clean revenue, with a difference of zero. Revenue is summed unrounded here: the `revenue` column in the cleaned table is rounded to cents per row, so its sum can differ from the unrounded total by a few cents. The first removal is duplicates, then non-positive quantities, then orphan customers.

## Real-world applications

- A data engineer adds a row-count log to every pipeline stage so that an alert fires when a step suddenly removes ten times more rows than usual, as Example 1's log makes visible.
- A finance analyst reconciles a dashboard total against the ledger by listing excluded rows with their amounts, the same method as Example 3.
- A data quality team runs the rule set from Example 2 nightly and publishes the violation counts as a trend, which turns cleaning into monitoring.
- An analyst documents each cleaning decision (remove or fix, and why) in the README so a reviewer can disagree with a specific rule instead of with the whole analysis.

## Daily review

### Key takeaways

- Clean in a fixed order, on copies, and log the rows after every step.
- Fix labels when the correct value is certain; remove and report when it is not.
- Validate by re-running the original rules: zero violations is the pass condition.
- Reconcile rows and revenue so every difference has a named cause.

### Common mistakes

- Removing orphans before duplicates and double counting the removals in the log. Follow one order and record the count after each step.
- Summing a per-row rounded column and expecting it to match an unrounded total to the cent: compare like with like, or allow a tolerance of a few cents.
- Using `drop_duplicates()` on a subset such as `customer_id`, which deletes valid orders. Duplicates of orders are whole-row repeats, or repeats of `order_id`.
- Standardising labels after filtering with `isin`, so valid rows are dropped for a trailing space. Standardise before filtering.
- Forgetting that the returns table depends on the cleaned orders: if an order is removed, its return becomes an orphan.

### Revision notes

- Raw to clean orders: 510, then 500 after duplicates, then 495 after quantity, then 489 after customers (see Example 1).
- Rules R1 to R6 all pass after cleaning; the `returned` flag marks orders with a return.
- Revenue reconciliation difference is 0.00 when every removal is accounted for.

## Understand

### DDL: defining the shape of data

Until today you used tables someone else created. **DDL**, data definition language, is the part of SQL that creates and changes the tables themselves, as opposed to DML (day 44), which changes the rows. The main statements are `CREATE TABLE`, `ALTER TABLE` and `DROP TABLE`. A table definition lists the columns, gives each a name and a **data type**, and attaches **constraints**: rules the database enforces on every insert and update. Good definitions are the cheapest data-quality tool there is, because a rule that the database enforces cannot be forgotten by an application or a tired analyst. In this course each statement runs in a transaction that is rolled back, so tables you create here vanish after the run; in a real database they persist.

### Data types

The type of a column decides which values it accepts, how much space it uses and which operations work. The types you will use most often in PostgreSQL are:

- `integer` (and `bigint` for very large counts, `smallint` for small ones): whole numbers.
- `numeric(p, s)`: exact decimals with `p` digits in total and `s` after the point. Use it for money. `numeric(10, 2)` stores up to 99999999.99 exactly.
- `real` and `double precision`: approximate floating point numbers, fast but subject to rounding noise (you met this with `order_details.discount`). Do not use them for money.
- `text` and `varchar(n)`: character data. `varchar(40)` rejects longer values; `text` has no limit. In PostgreSQL they perform the same, so `varchar(n)` is only worth it when the limit is a real business rule.
- `boolean`: true, false or NULL.
- `date`, `timestamp`, `timestamptz`, `interval`: dates and times (day 39).
- `serial`: an integer that fills itself from a sequence, which is how `shipper_id` gets its values.

Pick the narrowest type that matches the meaning: a date belongs in a `date` column, not in text, so that sorting and arithmetic work (day 39). You can convert a value with `CAST(x AS type)` or `x::type`, and a value that cannot be converted raises an error such as `invalid input syntax for type integer: "abc"`.

### Keys: PRIMARY KEY and FOREIGN KEY

A **primary key** identifies each row uniquely. It combines `NOT NULL` and `UNIQUE`: no duplicates and no missing values. Every table should have one. A **foreign key** says that a column must hold a value that exists in another table's key: `customer_id integer REFERENCES customers(customer_id)`. It is what makes joins reliable and what stopped you from deleting customer ALFKI on day 44. A foreign key column may be NULL unless you also declare it `NOT NULL`: NULL means "no related row".

### Other constraints

`NOT NULL` forbids missing values. `UNIQUE` forbids duplicates in a column (or a combination), but it allows several NULLs, because NULL is not equal to NULL. `CHECK (condition)` rejects rows for which the condition is false, for example `CHECK (credits > 0)`; a row whose condition is unknown (NULL) is accepted. `DEFAULT value` supplies the value when an insert omits the column. When a constraint is violated, the whole statement fails and no row of that statement is stored, with a message that names the constraint: `violates check constraint "course_credits_check"`, `duplicate key value violates unique constraint "course_pkey"`, `null value in column "title" ... violates not-null constraint`, or `violates foreign key constraint`. Reading these messages is how you find the broken rule.

### Creating tables from queries and changing them

`CREATE TABLE new_table AS SELECT ...` creates a table whose columns and rows come from a query. It copies the data and the column types but none of the constraints, so it is suited to snapshots and intermediate results rather than to tables that need keys. `ALTER TABLE name ADD COLUMN column type [DEFAULT value]` adds a column to an existing table; existing rows receive the default or NULL. Be careful with `DROP TABLE`: it deletes the table and all its rows.

### Common misconception

Learners think constraints are only documentation, or that the application will validate everything. Applications have bugs and other applications write to the same database, so the database is the last line of defence. Another misconception is that `UNIQUE` allows only one NULL; in PostgreSQL it allows any number.

### Why it matters

Analysts build staging tables, lookup tables and summaries all the time, and engineers design the schemas that the whole company queries. Choosing types and constraints well prevents the bad data that wrecks every report afterwards.

## Syntax and key functions

```sql-syntax
CREATE TABLE table_name (
  id         integer PRIMARY KEY,
  name       varchar(40) NOT NULL,
  email      text UNIQUE,
  score      integer NOT NULL DEFAULT 0 CHECK (score >= 0),
  parent_id  integer REFERENCES other_table(id)
);

CREATE TABLE summary_table AS
SELECT column_1, COUNT(*) AS n FROM source_table GROUP BY column_1;

ALTER TABLE table_name ADD COLUMN level text DEFAULT 'beginner';
```

| Part | What it enforces |
|---|---|
| `PRIMARY KEY` | Unique and not NULL; identifies the row |
| `REFERENCES t(col)` | Value must exist in `t.col` (or be NULL) |
| `NOT NULL` | The value may not be missing |
| `UNIQUE` | No duplicates; several NULLs are allowed |
| `CHECK (cond)` | Rows where `cond` is false are rejected |
| `DEFAULT v` | Value used when the column is omitted from an insert |
| `serial` | Integer filled automatically from a sequence |

| Type | Typical use | Watch out for |
|---|---|---|
| `integer`, `bigint` | Counts, ids | `integer` overflows above about 2.1 billion |
| `numeric(p, s)` | Money, exact decimals | Slower than `real`, but exact |
| `real`, `double precision` | Measurements | Rounding noise: cast to `numeric` before `ROUND` |
| `varchar(n)`, `text` | Names, codes | `varchar(n)` rejects longer text |
| `date`, `timestamp` | Calendar values | Never store dates as text |
| `boolean` | Flags | NULL is a third state |

## Learn by example

Each block creates its own tables, fills them and ends with a query, because the runner rolls everything back afterwards.

### Example 1: A first table with defaults

A table with an integer key, a bounded text column, a column with a default and a `CHECK`. The insert leaves out `credits` for two rows, which receive the default 3, and supplies it for the third. The final `SELECT` shows the stored rows.

```sql run
CREATE TABLE course (
  course_id integer PRIMARY KEY,
  title     varchar(40) NOT NULL,
  credits   integer NOT NULL DEFAULT 3 CHECK (credits > 0),
  code      text UNIQUE
);

INSERT INTO course (course_id, title, code)
VALUES (1, 'SQL', 'S1'), (2, 'Python', 'P1');
INSERT INTO course (course_id, title, credits, code)
VALUES (3, 'Statistics', 5, 'ST');

SELECT * FROM course ORDER BY course_id;
```

```output
course_id | title | credits | code
1 | SQL | 3 | S1
2 | Python | 3 | P1
3 | Statistics | 5 | ST
```

### Example 2: What the constraints reject

Run against the table of example 1, each of these statements fails and stores nothing. The messages are exactly what PostgreSQL reports. Read them as "which rule did I break?".

```text
INSERT INTO course (course_id, title, credits) VALUES (4, 'x', 0);
  ERROR: new row for relation "course" violates check constraint "course_credits_check"
INSERT INTO course (course_id, title, code) VALUES (1, 'dup', 'Z');
  ERROR: duplicate key value violates unique constraint "course_pkey"
INSERT INTO course (course_id, title, code) VALUES (9, 'dup', 'S1');
  ERROR: duplicate key value violates unique constraint "course_code_key"
INSERT INTO course (course_id, title) VALUES (9, NULL);
  ERROR: null value in column "title" of relation "course" violates not-null constraint
```

The one thing `UNIQUE` does allow is several NULLs. This block inserts two rows without a `code` and then counts them: both are accepted.

```sql run
CREATE TABLE course (
  course_id integer PRIMARY KEY,
  title     varchar(40) NOT NULL,
  code      text UNIQUE
);

INSERT INTO course (course_id, title, code)
VALUES (1, 'SQL', 'S1'), (2, 'Python', NULL), (3, 'Statistics', NULL);

SELECT COUNT(*) AS rows_without_code
FROM course
WHERE code IS NULL;
```

```output
rows_without_code
2
```

### Example 3: A foreign key links two tables

The child table `enrolment` references the parent `course`. An enrolment for a course that does not exist would fail with `violates foreign key constraint`. With valid data, the tables join as usual (day 40), and a left join shows the course nobody enrolled in.

```sql run
CREATE TABLE course (course_id integer PRIMARY KEY, title text NOT NULL);
CREATE TABLE enrolment (
  enrolment_id serial PRIMARY KEY,
  course_id    integer NOT NULL REFERENCES course (course_id),
  student      text NOT NULL
);

INSERT INTO course VALUES (1, 'SQL'), (2, 'Python'), (3, 'Statistics');
INSERT INTO enrolment (course_id, student)
VALUES (1, 'Ana'), (1, 'Ben'), (2, 'Ana');

SELECT c.title, COUNT(e.enrolment_id) AS students
FROM course c
LEFT JOIN enrolment e ON e.course_id = c.course_id
GROUP BY c.course_id, c.title
ORDER BY c.course_id;
```

```output
title | students
SQL | 2
Python | 1
Statistics | 0
```

### Example 4: Types in Northwind and the cost of floating point

`pg_typeof` returns the type of an expression. The first three columns show how Northwind stores prices exactly (`numeric`), the discount approximately (`real`) and the order date as a real date. The last two columns show why money needs `numeric`: with double precision, 0.1 + 0.2 is not exactly 0.3, while `numeric` is.

```sql run
SELECT pg_typeof(od.unit_price) AS price_type,
       pg_typeof(od.discount) AS discount_type,
       pg_typeof(o.order_date) AS date_type,
       0.1::double precision + 0.2::double precision AS float_sum,
       0.1::numeric + 0.2::numeric AS numeric_sum
FROM order_details od
JOIN orders o ON o.order_id = od.order_id
LIMIT 1;
```

```output
price_type | discount_type | date_type | float_sum | numeric_sum
numeric | real | date | 0.30000000000000004 | 0.3
```

### Example 5: CREATE TABLE AS SELECT

A summary table is created from a query and then used like any table. It keeps the data and types but not constraints. Here the per-customer order summary becomes a table, and we query the biggest customers from it. In a real warehouse this pattern is used for snapshots and intermediate results.

```sql run
CREATE TABLE customer_summary AS
SELECT customer_id, COUNT(*) AS orders, SUM(freight) AS total_freight
FROM orders
GROUP BY customer_id;

SELECT customer_id, orders, total_freight
FROM customer_summary
ORDER BY total_freight DESC, customer_id
LIMIT 5;
```

```output
customer_id | orders | total_freight
BLAUS | 2 | 336.20
BONAP | 3 | 298.49
BLONP | 2 | 287.16
ALFKI | 2 | 257.04
BERGS | 2 | 228.03
```

### Example 6: A realistic table with rules, added to Northwind

A `complaint` table stores support issues about orders. Foreign keys tie each complaint to an existing customer and, optionally, an order. `severity` is limited to 1 to 5 by a `CHECK`, and `opened` has a default. `ALTER TABLE` then adds a column, which existing rows fill with its default. The closing query joins the new table to Northwind's `customers` and `orders`, combining DDL, DML and joins.

```sql run
CREATE TABLE complaint (
  complaint_id serial PRIMARY KEY,
  customer_id  varchar(10) NOT NULL REFERENCES customers (customer_id),
  order_id     integer REFERENCES orders (order_id),
  severity     integer NOT NULL CHECK (severity BETWEEN 1 AND 5),
  note         text,
  opened       date NOT NULL DEFAULT DATE '1998-01-01'
);

INSERT INTO complaint (customer_id, order_id, severity, note)
VALUES ('ALFKI', 10248, 4, 'Order not shipped'),
       ('ANATR', 10249, 2, 'Late delivery'),
       ('FISSA', NULL, 1, 'General question');

ALTER TABLE complaint ADD COLUMN status text DEFAULT 'open';

SELECT cm.complaint_id, c.company_name, o.order_date, cm.severity, cm.opened, cm.status
FROM complaint cm
JOIN customers c ON c.customer_id = cm.customer_id
LEFT JOIN orders o ON o.order_id = cm.order_id
ORDER BY cm.complaint_id;
```

```output
complaint_id | company_name | order_date | severity | opened | status
1 | Alfreds Futterkiste | 1996-01-01 | 4 | 1998-01-01 | open
2 | Ana Trujillo Emparedados | 1997-02-02 | 2 | 1998-01-01 | open
3 | FISSA Fabrica Inter. Salchichas | NULL | 1 | 1998-01-01 | open
```

## Real-world applications

**Staging and reference tables.** Analysts create small tables for mappings, targets or imported lists (examples 1 and 3). Declaring keys and `NOT NULL` makes bad imports fail loudly instead of silently corrupting a report.

**Data quality at the source.** `CHECK`, `UNIQUE` and foreign keys (examples 1 to 3 and 6) stop impossible values: negative quantities, duplicate customers, orders for customers that do not exist. Many "data quality" tickets would never exist with the right constraints.

**Snapshots and intermediate results.** `CREATE TABLE AS SELECT` (example 5) freezes a query result for a report or a test, which engineers also use to speed up repeated joins.

**Choosing types for correctness.** Money in `numeric` and dates in `date` (example 4) is the difference between totals that reconcile to the cent and totals that are off by fractions.

## Daily review

### Key takeaways

- `CREATE TABLE` lists columns, types and constraints. The type decides what is accepted; the constraints enforce rules.
- Primary key = unique and not null. Foreign key = must exist in the parent table (or be NULL).
- `NOT NULL`, `UNIQUE` (allows several NULLs), `CHECK` and `DEFAULT` cover most business rules.
- Violations fail the whole statement and name the broken constraint.
- Use `numeric` for money, `date` for dates, `text` or `varchar(n)` for text; never store dates as text.
- `CREATE TABLE AS SELECT` copies data and types, not constraints; `ALTER TABLE ADD COLUMN` extends a table.

### Common mistakes

- Using `real` or `double precision` for money and getting totals like 0.30000000000000004. Use `numeric(p, s)`.
- Storing dates as text: sorting and date arithmetic then fail or give wrong answers.
- Forgetting `NOT NULL` on a required column and finding NULL keys later.
- Declaring a foreign key to a column that is not a primary key or unique: PostgreSQL reports that there is no unique constraint matching the referenced columns.
- Inserting a child row before its parent: "violates foreign key constraint". Insert the parent first.
- Assuming `UNIQUE` blocks multiple NULLs, or that `CHECK` rejects rows where the condition is NULL. It does not.
- Expecting `CREATE TABLE AS SELECT` to copy the primary key.

### Revision notes

- Types: `integer`, `numeric(p, s)`, `text`/`varchar(n)`, `boolean`, `date`, `serial`.
- Constraints: PRIMARY KEY, REFERENCES, NOT NULL, UNIQUE, CHECK, DEFAULT.
- Error text names the constraint: `*_pkey`, `*_key`, `*_check`, `*_fkey`.
- Parent rows before child rows; child rows before deleting a parent.

## Objectives

- Explain what NULL means and why it is neither zero nor an empty string.
- Predict the result of comparisons and of `AND`, `OR` and `NOT` when NULL is involved, using three-valued logic.
- Test for missing values with `IS NULL`, `IS NOT NULL` and `IS DISTINCT FROM`.
- Replace or create NULLs with `COALESCE` and `NULLIF`, including a safe way to avoid division by zero.
- Describe how `COUNT(*)`, `COUNT(column)`, `AVG` and `SUM` treat NULL, and why a `NOT IN` list containing NULL returns nothing.

## Understand

### What NULL is

`NULL` is the database's marker for "no value here". A value can be missing because it is unknown (the date has not been recorded), not applicable (a top manager has no manager), or not yet available (an order that has not shipped has no shipped date). NULL is not a number and not text. It is not zero, not an empty string `''` and not the word "null". A price of 0 is a known price; a NULL price means nobody knows it. Treating the two as the same produces wrong averages and wrong counts.

In this Northwind copy you have already met several NULLs. Every customer's `region`, `phone` and `address` is NULL. Fifteen orders have a NULL `shipped_date`, because they were never shipped. One order has a NULL `employee_id`. The employee Fuller has a NULL `reports_to`, because nobody is above them.

### Why comparisons with NULL are special

Think of NULL as "I do not know the value". Is an unknown value equal to 5? You cannot say. Is an unknown value equal to another unknown value? You cannot say that either. So SQL answers neither true nor false but **unknown**. That is why `NULL = NULL` is not true: its result is NULL. The same is true for `<>`, `<` and `>`: any comparison with NULL gives unknown.

SQL therefore has **three-valued logic**: every condition evaluates to TRUE, FALSE or UNKNOWN. The rule that matters most in practice is this: `WHERE` keeps a row only if its condition is TRUE. FALSE rows are discarded, and so are UNKNOWN rows. This is why `WHERE shipped_date = NULL` returns no rows at all, not even the unshipped ones. The correct test is the special predicate `IS NULL`, which always answers TRUE or FALSE, never UNKNOWN.

### AND, OR and NOT with unknown

The logical operators extend naturally. `FALSE AND UNKNOWN` is FALSE, because whatever the unknown value turns out to be, the whole is false. `TRUE OR UNKNOWN` is TRUE, for the same reason. But `TRUE AND UNKNOWN` is UNKNOWN, `FALSE OR UNKNOWN` is UNKNOWN, and `NOT UNKNOWN` is UNKNOWN. A condition is only as certain as its parts allow. Example 1 prints these results so that you can see them.

### Arithmetic and text with NULL

Any arithmetic with NULL gives NULL: `5 + NULL` is NULL. So does text concatenation with `||`: `'Berlin' || NULL` is NULL. One missing piece makes the whole label disappear. You saw this on day 32 when `shipped_date - order_date` came out as NULL for an unshipped order. The cure is to give the missing value a stand-in with `COALESCE`.

### COALESCE and NULLIF

`COALESCE(a, b, c, ...)` returns the first argument that is not NULL, and NULL if they all are. It is the standard way to show "n/a" or 0 instead of a gap, or to fall back from one column to another. All arguments must be of compatible types, so a date has to be cast to text before it can be replaced by a word.

`NULLIF(a, b)` does the opposite job: it returns NULL when `a` equals `b`, and `a` otherwise. Its classic use is to protect a division: `x / NULLIF(y, 0)` returns NULL instead of an error when `y` is zero, because dividing by NULL is just NULL. It is also used to turn "empty-string" placeholders into real NULLs during data cleaning.

### IS DISTINCT FROM

Sometimes you want a comparison that treats NULL like an ordinary value. `a IS DISTINCT FROM b` is TRUE when the two differ, where two NULLs count as equal and a NULL and a value count as different. It never returns UNKNOWN. `a IS NOT DISTINCT FROM b` is the null-safe equality. This is the clean way to say "everyone who does not report to employee 2, including people with no manager", which `reports_to <> 2` would get wrong.

### NULL in aggregate functions

An **aggregate function** collapses many rows into one value. Day 36 covers them fully; today you need just enough to see what NULL does. `COUNT(*)` counts rows, whatever they contain. `COUNT(column)` counts only rows where that column is not NULL. `AVG`, `SUM`, `MIN` and `MAX` ignore NULLs. This matters: the average of 4, NULL and 8 is 6 (the two known values), not 4 (which would treat NULL as 0). If every value is NULL, `SUM` and `AVG` return NULL, not 0, while `COUNT(column)` returns 0.

### NOT IN and NULL

`x IN (1, 2, NULL)` is true when `x` is 1 or 2, but otherwise unknown. `x NOT IN (1, 2, NULL)` is therefore never true: it is false when `x` is 1 or 2, and unknown for every other value. A single NULL in the list makes `NOT IN` return no rows. Beginners hit this when a list comes from a column that unexpectedly contains NULLs. On day 43 you will see the same trap with subqueries and how to avoid it.

### Common misconception

"NULL means empty or zero, so `column = ''` or `column = 0` finds the missing rows." It does not. Those compare against a real empty string or a real zero, which are different from NULL. The other widespread belief is that `column <> 'x'` returns "everything except x". It returns everything that is not NULL and not 'x'. Rows with NULL silently disappear, and your row counts for a condition and its opposite do not add up to the table size.

### Why it matters

Missing data is normal in real systems. Customer forms are incomplete, shipments are pending, optional fields stay blank. Almost every wrong report in practice comes from NULL handling: counts that silently exclude rows, averages that treat unknown as zero, filters that drop the very rows you were looking for, and joins in later days that produce NULLs on purpose.

## Syntax and key functions

Testing for NULL. These predicates never return unknown:

```sql-syntax
WHERE column IS NULL
WHERE column IS NOT NULL
WHERE column IS DISTINCT FROM value
WHERE column IS NOT DISTINCT FROM value
```

Replacing and creating NULLs:

```sql-syntax
COALESCE(value_1, value_2, ..., fallback)
NULLIF(value, value_that_means_missing)
```

| Expression | Result | Why |
|---|---|---|
| `NULL = NULL` | NULL (unknown) | Two unknowns cannot be said to be equal |
| `NULL IS NULL` | true | The dedicated NULL test |
| `5 + NULL` | NULL | Arithmetic with NULL is NULL |
| `'a' \|\| NULL` | NULL | Concatenation with NULL is NULL |
| `TRUE AND NULL` | NULL | Depends on the unknown part |
| `FALSE AND NULL` | false | Already false whatever the unknown is |
| `TRUE OR NULL` | true | Already true whatever the unknown is |
| `COALESCE(NULL, NULL, 'x')` | `x` | First non-NULL argument |
| `NULLIF(0, 0)` | NULL | Equal arguments give NULL |
| `NULLIF(5, 0)` | 5 | Different arguments return the first |
| `x / NULLIF(y, 0)` | NULL when y is 0 | No "division by zero" error |
| `3 NOT IN (1, 2, NULL)` | NULL | The NULL makes it unknown, never true |

Aggregates and NULL:

| Function | Treatment of NULL |
|---|---|
| `COUNT(*)` | Counts every row |
| `COUNT(column)` | Counts rows where the column is not NULL |
| `AVG(column)`, `SUM(column)` | Ignore NULL; return NULL if every value is NULL |
| `MIN(column)`, `MAX(column)` | Ignore NULL |

## Learn by example

### Example 1: Three-valued logic, printed

No table is needed; each column is one expression. A comparison with NULL gives NULL (shown as `NULL`), while `IS NULL` gives a real `true`. `TRUE AND NULL` is unknown, but `FALSE AND NULL` is false and `TRUE OR NULL` is true: they are decided without knowing the unknown part. `NOT` of an unknown is still unknown.

```sql run
SELECT 1 = NULL AS equals_null,
       NULL = NULL AS null_equals_null,
       NULL IS NULL AS is_null,
       TRUE AND NULL AS true_and_null,
       FALSE AND NULL AS false_and_null,
       TRUE OR NULL AS true_or_null,
       NOT CAST(NULL AS boolean) AS not_null;
```

```output
equals_null | null_equals_null | is_null | true_and_null | false_and_null | true_or_null | not_null
NULL | NULL | true | NULL | false | true | NULL
```

### Example 2: Find the missing values with IS NULL

Fifteen orders have no shipped date. `IS NULL` finds them. The tempting `WHERE shipped_date = NULL` is valid SQL but returns no rows at all, because the comparison is unknown for every row. `LIMIT 5` shows the first five of the fifteen.

```sql run
SELECT order_id, order_date, shipped_date
FROM orders
WHERE shipped_date IS NULL
ORDER BY order_id
LIMIT 5;
```

```output
order_id | order_date | shipped_date
10248 | 1996-01-01 | NULL
10255 | 1997-08-08 | NULL
10262 | 1998-03-15 | NULL
10269 | 1996-10-22 | NULL
10276 | 1997-05-01 | NULL
```

### Example 3: Null-safe comparison with IS DISTINCT FROM

We want every employee who does not report to employee 2. The plain test `reports_to <> 2` returns only three rows, because Fuller's NULL makes the comparison unknown and silently removes Fuller. `IS DISTINCT FROM` counts a NULL as different from 2, so Fuller is included as well: four rows.

```sql run
SELECT employee_id, last_name, reports_to
FROM employees
WHERE reports_to IS DISTINCT FROM 2
ORDER BY employee_id;
```

```output
employee_id | last_name | reports_to
2 | Fuller | NULL
6 | Suyama | 5
7 | King | 5
9 | Dodsworth | 5
```

### Example 4: COALESCE keeps a label alive

Joining text with `||` yields NULL as soon as one part is NULL, so `naive_label` is empty for every row (all regions are NULL). `COALESCE(region, 'no region')` supplies a stand-in for the missing region and the label survives.

```sql run
SELECT company_name,
       company_name || ' (' || region || ')' AS naive_label,
       company_name || ' (' || COALESCE(region, 'no region') || ')' AS safe_label
FROM customers
ORDER BY customer_id
LIMIT 4;
```

```output
company_name | naive_label | safe_label
Alfreds Futterkiste | NULL | Alfreds Futterkiste (no region)
Ana Trujillo Emparedados | NULL | Ana Trujillo Emparedados (no region)
Antonio Moreno Taquería | NULL | Antonio Moreno Taquería (no region)
Around the Horn | NULL | Around the Horn (no region)
```

### Example 5: NULLIF protects a division, COALESCE finishes the job

`units_on_order` is 0 for every product here, so `units_in_stock / units_on_order` would stop the whole query with the error `division by zero`. `NULLIF(units_on_order, 0)` turns the zero into NULL, so the division returns NULL instead of failing. Wrapping the whole expression in `COALESCE(..., 0)` then converts the NULL to 0 for display. Decide deliberately whether a missing ratio should show as NULL or as 0.

```sql run
SELECT product_id,
       units_in_stock,
       units_on_order,
       units_in_stock / NULLIF(units_on_order, 0) AS ratio,
       COALESCE(units_in_stock / NULLIF(units_on_order, 0), 0) AS ratio_or_zero
FROM products
ORDER BY product_id
LIMIT 4;
```

```output
product_id | units_in_stock | units_on_order | ratio | ratio_or_zero
1 | 21 | 0 | NULL | 0
2 | 22 | 0 | NULL | 0
3 | 23 | 0 | NULL | 0
4 | 24 | 0 | NULL | 0
```

### Example 6: NULL in aggregates

Of 100 orders, 85 have a shipped date. `COUNT(*)` counts all 100 rows, `COUNT(shipped_date)` only the 85 non-NULL ones, and their difference is the 15 unshipped orders. `COUNT(ship_region)` is 0 because the column is entirely NULL. `AVG(shipped_date - order_date)` averages only the shipped orders. The last column wrongly treats unshipped orders as 0 days, which drags the average down from 5.65 to 4.80. That difference is exactly the NULL-versus-zero mistake.

```sql run
SELECT COUNT(*) AS orders,
       COUNT(shipped_date) AS shipped,
       COUNT(*) - COUNT(shipped_date) AS not_shipped,
       COUNT(ship_region) AS with_region,
       ROUND(AVG(shipped_date - order_date), 2) AS avg_days_to_ship,
       ROUND(AVG(COALESCE(shipped_date - order_date, 0)), 2) AS avg_if_null_is_zero
FROM orders;
```

```output
orders | shipped | not_shipped | with_region | avg_days_to_ship | avg_if_null_is_zero
100 | 85 | 15 | 0 | 5.65 | 4.80
```

## Real-world applications

**Finding incomplete records.** Data-quality checks start with `WHERE column IS NULL` (example 2): orders with no shipped date, orders with no employee, customers with no phone. Counting them with `COUNT(*) - COUNT(column)`, as in example 6, gives a completeness percentage for any column.

**Reports that must not lose rows.** Labels, exports and dashboards often combine several columns. `COALESCE`, as in example 4, keeps a row visible with a clear fallback such as "no region" or "pending" instead of an empty cell. Choosing the fallback text is a business decision, not a technical one.

**Safe calculations.** Rates and ratios divide by counts that can be zero. `NULLIF` (example 5) prevents a failed pipeline run caused by one zero, and keeps "undefined" distinguishable from a real 0.

**Correct averages and KPIs.** Average delivery time, average order value and conversion rate must use only rows that have a value. Knowing that `AVG` skips NULLs, and that replacing NULL with 0 changes the answer (example 6), lets an analyst state exactly what a KPI measures.

## Daily review

### Key takeaways

- NULL means "no value": not zero, not an empty string.
- Any comparison with NULL is unknown. `WHERE` keeps only TRUE rows, so `= NULL` and `<> value` lose NULL rows.
- Use `IS NULL` and `IS NOT NULL` to test for NULL, and `IS DISTINCT FROM` for a null-safe comparison.
- `FALSE AND NULL` is false and `TRUE OR NULL` is true; most other combinations stay unknown.
- `COALESCE` replaces NULL with the first non-NULL argument; `NULLIF(a, b)` returns NULL when `a = b`, which prevents division by zero.
- `COUNT(*)` counts rows; `COUNT(col)` and `AVG`/`SUM`/`MIN`/`MAX` skip NULLs; a NULL inside a `NOT IN` list makes it return nothing.

### Common mistakes

- Writing `WHERE col = NULL` or `col <> NULL`; use `IS NULL` and `IS NOT NULL`.
- Treating NULL as 0 in an average and so changing the result.
- Concatenating with `||` when a column may be NULL, which makes the whole label NULL.
- Using `col <> 'x'` and expecting to see rows where `col` is NULL.
- Using `COUNT(column)` when you wanted the number of rows (`COUNT(*)`), or the other way round.
- Putting NULL into a `NOT IN` list and wondering why no rows come back.
- Using `COALESCE` with incompatible types, such as a date and the text `'pending'`, without a cast.

### Revision notes

- Three truth values: TRUE, FALSE, UNKNOWN. `WHERE` keeps only TRUE.
- Test: `IS [NOT] NULL`; null-safe: `IS [NOT] DISTINCT FROM`.
- `COALESCE(a, b)` fills gaps; `NULLIF(a, b)` creates NULL; `x / NULLIF(y, 0)` is safe division.
- `COUNT(*)` = all rows; `COUNT(col)` = non-NULL values; `AVG` ignores NULL.
- A NULL in a `NOT IN` list makes it unknown for every row.

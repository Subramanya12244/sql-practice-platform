## Understand

### One row per group

On day 36 an aggregate summarised the whole table into one row. Real questions usually ask for a summary for each something: orders per country, products per category, revenue per customer. `GROUP BY` does this. It sorts the rows that survive `WHERE` into **groups**, one group for each distinct value (or combination of values) of the columns you name, and then each aggregate is computed separately inside each group. The result has one row per group.

A useful picture is a pile of paper order slips. `GROUP BY ship_country` means you put all the slips for Germany in one stack, all for France in another, and so on. `COUNT(*)` then counts the slips in each stack, and `AVG(freight)` averages the freight on the slips in each stack. The stacks, not the individual slips, become the output rows.

### The rule for the select list

Once rows are grouped, each output row stands for a whole stack, so every column in `SELECT` must have one value per stack. There are only two kinds of expression that do: a column you listed in `GROUP BY` (all slips in a stack share its value) and an aggregate (it collapses the stack to one value). Anything else, such as `product_name` when you group by `category_id`, has many different values in one stack and PostgreSQL rejects the query with "column must appear in the GROUP BY clause or be used in an aggregate function". The fix is to add the column to `GROUP BY` or to wrap it in an aggregate such as `MAX` or `MIN`. Do not add columns to `GROUP BY` only to silence the error: each extra column splits the groups further and changes the meaning of the result.

### Several grouping columns

`GROUP BY ship_country, ship_via` makes one group for every distinct pair. Germany shipped by carrier 1 and Germany shipped by carrier 2 are different groups. The more columns you group by, the more and the smaller the groups. The order of columns in `GROUP BY` does not change the result, only which rows exist: it is the set of columns that matters.

### NULL forms its own group

`GROUP BY` treats all NULLs in a grouping column as equal, so they land in one group of their own, even though NULL never equals NULL in a `WHERE` comparison. In Northwind one order has no employee, and grouping orders by `employee_id` produces a group whose key is NULL. Remember that when you see a blank key in a report: it is not an error, it is the rows with missing data.

### WHERE filters rows, HAVING filters groups

Suppose you want only the countries with at least five orders. The count exists only after grouping, so `WHERE` cannot test it (day 36: aggregates are not allowed in `WHERE`). `HAVING` is the filter that runs after grouping and can use aggregates: `HAVING COUNT(*) >= 5`. A simple test for which to use: if the condition is about a single row (its date, its country, its price), use `WHERE`; if it is about the group as a whole (its count, its total, its average), use `HAVING`.

Both can appear in one query, and they do different jobs. `WHERE order_date >= '1997-01-01'` removes rows before they are counted. `HAVING COUNT(*) >= 5` removes finished groups afterwards. Filtering rows with `WHERE` whenever you can is also faster, because fewer rows reach the grouping step.

### The logical order of a query

You write `SELECT` first, but the database works in this order:

1. `FROM` finds the rows.
2. `WHERE` keeps the rows that pass.
3. `GROUP BY` builds the groups.
4. `HAVING` keeps the groups that pass.
5. `SELECT` computes the output columns, including aggregates and aliases.
6. `ORDER BY` sorts the result.
7. `LIMIT` trims it.

This order explains the rules you have met. `WHERE` cannot use an aggregate because grouping has not happened. `HAVING` should not rely on a `SELECT` alias because `SELECT` has not run yet (PostgreSQL requires you to repeat the expression). `ORDER BY` can use an alias, because it comes after `SELECT`.

### Common misconception

Learners often think `HAVING` is "WHERE for aggregates" and so use it for everything, for example `HAVING ship_country = 'Germany'`. That works but is the wrong tool: it filters after grouping and wastes work. Equally, they try `WHERE COUNT(*) > 5`, which fails. Keep the single test above in mind: rows or groups.

### Why it matters

Group-and-filter is the core of reporting: revenue per month, customers with repeat purchases, products that sell too slowly. Nearly every analyst interview includes a "find the groups with more than N" question.

## Syntax and key functions

The full shape of a grouped query. Each clause is optional except `SELECT`, but the order is fixed:

```sql-syntax
SELECT group_column, aggregate(expression) AS alias
FROM table_name
WHERE row_condition
GROUP BY group_column
HAVING group_condition
ORDER BY alias DESC
LIMIT n;
```

Grouping by two columns, and a `HAVING` that uses an aggregate:

```sql-syntax
GROUP BY column_a, column_b
HAVING COUNT(*) >= 5
HAVING SUM(quantity) > 100 AND MIN(unit_price) > 10
```

| Clause | Runs on | Can use aggregates | Typical use |
|---|---|---|---|
| `WHERE` | Individual rows, before grouping | No | Dates, countries, prices, flags |
| `GROUP BY` | Rows that passed `WHERE` | Not applicable | Names the grouping columns |
| `HAVING` | Groups, after grouping | Yes | Counts, totals and averages per group |
| `ORDER BY` | The finished result | Yes, and aliases | Sorting the summary |

## Learn by example

### Example 1: Orders per country

`GROUP BY ship_country` makes one stack of orders per country, and `COUNT(*)` counts each stack. `ORDER BY` sorts the summary (the largest first, ties by name so the order is stable) and `LIMIT` shows the top five. `ship_country` may appear in `SELECT` because it is a grouping column.

```sql run
SELECT ship_country, COUNT(*) AS orders
FROM orders
GROUP BY ship_country
ORDER BY orders DESC, ship_country
LIMIT 5;
```

```output
ship_country | orders
France | 13
Germany | 13
USA | 13
Brazil | 9
UK | 8
```

### Example 2: Several aggregates per group

One grouping and several aggregates. For each product category, the query counts the products, finds the cheapest and dearest price, and averages the price (rounded). Every group is a category, so there are eight rows.

```sql run
SELECT category_id,
       COUNT(*) AS products,
       MIN(unit_price) AS cheapest,
       MAX(unit_price) AS dearest,
       ROUND(AVG(unit_price), 2) AS avg_price
FROM products
GROUP BY category_id
ORDER BY category_id;
```

```output
category_id | products | cheapest | dearest | avg_price
1 | 12 | 4.50 | 263.50 | 37.98
2 | 12 | 10.00 | 43.90 | 23.06
3 | 13 | 9.20 | 81.00 | 25.16
4 | 10 | 2.50 | 55.00 | 28.73
5 | 7 | 7.00 | 38.00 | 20.25
6 | 6 | 7.45 | 123.79 | 54.01
7 | 5 | 10.00 | 53.00 | 32.37
8 | 12 | 6.00 | 62.50 | 20.68
```

### Example 3: NULL is a group

Grouping orders by `employee_id` gives one row per employee, plus a row with the key NULL for the order that has no employee. All NULLs are put into the same group. Notice that employee 6 has 22 orders, twice the others, a fact worth investigating in a real project.

```sql run
SELECT employee_id, COUNT(*) AS orders, SUM(freight) AS total_freight
FROM orders
GROUP BY employee_id
ORDER BY employee_id;
```

```output
employee_id | orders | total_freight
1 | 11 | 1072.69
2 | 11 | 990.19
3 | 11 | 1346.30
4 | 11 | 1057.96
6 | 22 | 1949.80
7 | 11 | 1387.37
8 | 11 | 697.82
9 | 11 | 1176.63
NULL | 1 | 172.85
```

### Example 4: Grouping by two columns

Every distinct pair of `ship_country` and `ship_via` is one group, so Germany appears once for carrier 1 and once for carrier 2. The groups are smaller than in example 1. The result is sorted by the count and then by both keys so that it is stable.

```sql run
SELECT ship_country, ship_via, COUNT(*) AS orders
FROM orders
GROUP BY ship_country, ship_via
ORDER BY orders DESC, ship_country, ship_via
LIMIT 6;
```

```output
ship_country | ship_via | orders
Brazil | 1 | 5
France | 2 | 5
Germany | 1 | 5
Germany | 2 | 5
USA | 2 | 5
USA | 3 | 5
```

### Example 5: WHERE and HAVING in one query

The two filters do different jobs. `WHERE` first keeps only orders placed in 1997, and the rows are then grouped by country. `HAVING COUNT(*) >= 4` then discards the countries with fewer than four orders in that year. Changing the `WHERE` changes which orders are counted; changing the `HAVING` changes which countries are listed.

```sql run
SELECT ship_country,
       COUNT(*) AS orders_1997,
       ROUND(AVG(freight), 2) AS avg_freight
FROM orders
WHERE order_date >= '1997-01-01' AND order_date < '1998-01-01'
GROUP BY ship_country
HAVING COUNT(*) >= 4
ORDER BY orders_1997 DESC, ship_country;
```

```output
ship_country | orders_1997 | avg_freight
France | 5 | 91.78
Germany | 5 | 81.66
USA | 5 | 113.77
UK | 4 | 61.92
```

### Example 6: Best-selling products by revenue

On `order_details`, group the lines by product, compute units and revenue, and keep only the products whose revenue is above 5000. The `HAVING` repeats the whole `SUM` expression because the alias `revenue` does not exist yet when `HAVING` runs. The discount is cast to `numeric` for exact money arithmetic (day 32).

```sql run
SELECT product_id,
       SUM(quantity) AS units,
       ROUND(SUM(unit_price * quantity * (1 - discount::numeric)), 2) AS revenue
FROM order_details
GROUP BY product_id
HAVING SUM(unit_price * quantity * (1 - discount::numeric)) > 5000
ORDER BY revenue DESC, product_id;
```

```output
product_id | units | revenue
38 | 72 | 17509.58
29 | 192 | 17437.79
20 | 72 | 5576.85
28 | 129 | 5497.08
```

## Real-world applications

**Sales reports by dimension.** Orders per country (example 1), revenue per product (example 6) and freight per employee (example 3) are all the same shape: pick a dimension, group by it, aggregate a measure. Swap the grouping column to get a new report.

**Finding the groups that matter.** `HAVING` turns a summary into a shortlist: countries with enough volume to justify a warehouse, products above a revenue threshold (example 6), customers with repeat purchases.

**Spotting data problems.** Group-by with `COUNT(*)` reveals oddities fast: the NULL-employee row in example 3 and the double count for employee 6 are the kind of finding data-quality reviews are made of. Grouping a key column and keeping `HAVING COUNT(*) > 1` finds duplicates.

**Period summaries.** Add a date filter with `WHERE` (example 5) and the same query becomes a monthly or yearly report. Day 39 shows how to group by month and year.

## Daily review

### Key takeaways

- `GROUP BY` builds one group per distinct combination of the grouping columns and the output has one row per group.
- Every selected column must be a grouping column or inside an aggregate.
- NULLs in a grouping column form one group.
- `WHERE` filters rows before grouping; `HAVING` filters groups after, and can use aggregates.
- Logical order: `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `ORDER BY`, `LIMIT`.
- `HAVING` cannot use a `SELECT` alias in PostgreSQL; `ORDER BY` can.

### Common mistakes

- Selecting a non-grouped column and getting "column must appear in the GROUP BY clause or be used in an aggregate function". Add it to `GROUP BY` if you want one row per value, or aggregate it.
- Writing `WHERE COUNT(*) > 5`. PostgreSQL raises "aggregate functions are not allowed in WHERE". Use `HAVING COUNT(*) > 5`.
- Putting a row condition in `HAVING` (`HAVING ship_country = 'Germany'`). It gives the right rows but does extra work; use `WHERE`.
- Using the alias in `HAVING` (`HAVING orders >= 5`), which fails with "column does not exist". Repeat the aggregate expression.
- Grouping by too many columns, for example adding `company_name` next to `customer_id`, and getting a different (usually larger) number of rows than expected.
- Forgetting `ORDER BY` and treating the output order of groups as meaningful. It is not guaranteed.

### Revision notes

- Stack the slips: one output row per stack.
- Row question: `WHERE`. Group question: `HAVING`.
- Execution order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.
- Select list: grouping columns and aggregates only.

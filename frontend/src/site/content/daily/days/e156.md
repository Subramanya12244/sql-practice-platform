## Objectives

- Lay out a Python pipeline project with a `src` folder, a package, tests and a `pyproject.toml`.
- Read a `pyproject.toml`: project metadata, dependencies, optional dependencies and entry points.
- Run a package with `python -m`, and expose a command through an entry point.
- Load environment-specific settings from a TOML file with `tomllib` and override them with environment variables, keeping secrets out of files.

## Understand

### From a script to a package

A pipeline starts as one script. It becomes a problem when a second person needs to run it, when a scheduler needs to call it from another folder, or when you want to test one function without running everything. The fix is a **package**: a folder with an `__init__.py` file whose modules other code can `import`. A package is installed or placed on Python's import path, so it works from any working directory, which a loose script that reads `config.toml` relative to where you stand does not.

A common project shape is the **src layout**:

```text
orders-pipeline/
  pyproject.toml
  config.toml
  src/
    pipeline/
      __init__.py
      __main__.py
      cli.py
      config.py
  tests/
    test_config.py
```

The code lives under `src/pipeline`, tests under `tests`, and the project description in `pyproject.toml`. The `src` folder prevents a quiet mistake: with code at the top level, tests import the local folder even when the package is not installed correctly, and a packaging error is only found on the server. With `src`, the import works only if the package is properly on the path.

### pyproject.toml

**TOML** is a simple configuration format: `key = value` lines, `[table]` headings and lists in brackets. Python 3.11 and later reads it with the standard `tomllib` module. `pyproject.toml` is the standard file that describes a Python project:

```text
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "orders-pipeline"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["pandas>=2.2,<3", "requests>=2.31"]

[project.optional-dependencies]
dev = ["pytest>=8"]

[project.scripts]
orders-load = "pipeline.cli:main"
```

`[build-system]` says which tool builds the package. `[project]` holds the name, version, the minimum Python and the runtime **dependencies**: packages the code needs, with **version specifiers** such as `>=2.2,<3` (a range) or `==2.2.2` (a pin). `[project.optional-dependencies]` groups extras, such as the tools needed only for development. `[project.scripts]` defines an **entry point**: after installation, a command `orders-load` exists that imports module `pipeline.cli` and calls its function `main`. The text `pipeline.cli:main` is `module:function`. These steps need a package index and are not run in this lesson; you install a project in development mode with `pip install -e .` inside a virtual environment.

### Running a package

`python -m pipeline` runs the module `pipeline.__main__`, with the package imported properly. `python -m pipeline.cli` runs one module. Use `-m` rather than `python src/pipeline/cli.py`: the file form puts the file's own folder on the path and breaks imports such as `from pipeline.config import ...`. A `__main__.py` usually contains `raise SystemExit(main())`, so the function's return value becomes the process exit code, as in Day 153.

Here is the trace of why the file form fails. Python builds its import path from the folder of the script you run, so `python src/pipeline/cli.py` puts `src/pipeline` on the path, not `src`. The line `from pipeline.config import load_config` then looks for a folder named `pipeline` inside `src/pipeline`, finds none, and raises `ModuleNotFoundError`. With `python -m pipeline.cli` and `src` on the path (installed, or `PYTHONPATH=src`), the name `pipeline` resolves to `src/pipeline`. The same rule explains why a pipeline that works in your editor can fail under a scheduler: the scheduler starts it from another folder with a different path.

### Environments and configuration

An **environment** means two things. A Python **virtual environment** is an isolated set of installed packages for one project, so two projects can use different versions of pandas. A **deployment environment** (dev, test, prod) is where the pipeline runs, and the settings differ: the database, the batch size, the log level. Keep settings out of the code. A file such as `config.toml` holds the non-secret defaults with a table per environment, the code selects one with an environment variable (here `PIPELINE_ENV`), and **secrets** such as passwords come only from environment variables or a secrets manager, never from a committed file. A common misconception is that adding the secrets file to the repository "just for now" is harmless; it stays in the history after deletion.

### Dependencies and reproducibility

A range such as `pandas>=2.2` lets a new release change behaviour between two deployments of the same code. Libraries keep ranges loose so they work with others; **applications** record exact versions of everything installed, for example with a constraints or lock file produced from a tested environment, and install from it. The symptom of ignoring this is a pipeline that passes on your laptop on Friday and fails on Monday after an upstream release. Specifiers without any version at all are the worst case, because any release is accepted.

### Why it matters

Orchestrators run your code on machines you do not control. A package with a clear entry point, pinned dependencies and configuration from the environment is the form that Airflow, containers and CI can all run the same way. The next phase builds Airflow on exactly this base.

## Syntax and key functions

```text
python -m package            # run package.__main__
python -m package.module     # run one module
pip install -e .             # editable install (needs an index; not run here)
```

```python
import tomllib

with open("config.toml", "rb") as handle:
    data = tomllib.load(handle)
data = tomllib.loads(text)
```

| Item | What it does |
|---|---|
| `tomllib.load(file)` | Reads TOML from a file opened in binary mode, returns a dict. |
| `tomllib.loads(text)` | Reads TOML from a string. |
| `os.environ.get("NAME", default)` | Reads an environment variable. |
| `[project.scripts]` | Maps a command name to `module:function`. |
| `dependencies` | Runtime packages and version specifiers. |
| `argparse` | Reads command-line options; `main(argv)` returns the exit code. |

## Learn by example

### Example 1: The project layout

The block creates the layout in a throwaway folder and lists the files with `find`.

```bash run
mkdir -p work/src/pipeline work/tests && cd work
touch src/pipeline/__init__.py tests/test_config.py
printf '[default]\nbatch_size = 100\ndb_url = "sqlite:///dev.db"\n\n[prod]\nbatch_size = 1000\ndb_url = "postgresql://prod-host/warehouse"\n' > config.toml
find . -type f | sort
```

```output
./config.toml
./src/pipeline/__init__.py
./tests/test_config.py
```

The package folder has `__init__.py`, the test lives apart from the code, and `config.toml` sits at the project root with a `[default]` table and a `[prod]` table that overrides two of its values.

### Example 2: Run the package with python -m

The package reads the configuration with `tomllib`, selects the environment from `PIPELINE_ENV` and lets `PIPELINE_DB_URL` override the database URL. `PYTHONPATH=src` stands in for installing the package.

```bash run
mkdir -p work/src/pipeline && cd work
touch src/pipeline/__init__.py
printf '[default]\nbatch_size = 100\ndb_url = "sqlite:///dev.db"\n\n[prod]\nbatch_size = 1000\ndb_url = "postgresql://prod-host/warehouse"\n' > config.toml
cat > src/pipeline/config.py <<'EOF'
import os
import tomllib


def load_config(path, env=None, environ=None):
    environ = os.environ if environ is None else environ
    env = env or environ.get("PIPELINE_ENV", "default")
    with open(path, "rb") as handle:
        data = tomllib.load(handle)
    cfg = {**data["default"], **data.get(env, {})}
    if "PIPELINE_DB_URL" in environ:
        cfg["db_url"] = environ["PIPELINE_DB_URL"]
    cfg["env"] = env
    return cfg
EOF
cat > src/pipeline/cli.py <<'EOF'
import argparse

from pipeline.config import load_config


def main(argv=None):
    parser = argparse.ArgumentParser(prog="pipeline")
    parser.add_argument("--config", default="config.toml")
    args = parser.parse_args(argv)
    cfg = load_config(args.config)
    print(f"env={cfg['env']} batch_size={cfg['batch_size']} db={cfg['db_url']}")
    return 0
EOF
cat > src/pipeline/__main__.py <<'EOF'
from pipeline.cli import main

raise SystemExit(main())
EOF
export PYTHONPATH=src PYTHONDONTWRITEBYTECODE=1
python -m pipeline
PIPELINE_ENV=prod python -m pipeline
PIPELINE_ENV=prod PIPELINE_DB_URL=postgresql://test-host/scratch python -m pipeline
python -m pipeline --config missing.toml 2>/dev/null || echo "exit=$?"
```

```output
env=default batch_size=100 db=sqlite:///dev.db
env=prod batch_size=1000 db=postgresql://prod-host/warehouse
env=prod batch_size=1000 db=postgresql://test-host/scratch
exit=1
```

With no variable the `default` table is used. `PIPELINE_ENV=prod` merges the `prod` table over the defaults, and `PIPELINE_DB_URL` overrides the URL last. The final run fails because the file does not exist: Python exits with 1 and the shell reports it. Exiting non-zero is what a scheduler needs to see.

### Example 3: Read a pyproject.toml and split an entry point

`tomllib` parses the text into dictionaries, so you can check the metadata with code. The entry point string is split into the module to import and the function to call.

```python run
import tomllib

text = """
[project]
name = "orders-pipeline"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["pandas>=2.2,<3", "requests>=2.31"]

[project.optional-dependencies]
dev = ["pytest>=8"]

[project.scripts]
orders-load = "pipeline.cli:main"
"""
project = tomllib.loads(text)["project"]
print(project["name"], project["version"])
print(len(project["dependencies"]), project["optional-dependencies"]["dev"])
for command, target in project["scripts"].items():
    module, function = target.split(":")
    print(command, "->", module, function)
```

```output
orders-pipeline 0.1.0
2 ['pytest>=8']
orders-load -> pipeline.cli main
```

The project has two runtime dependencies and one development extra. The command `orders-load` will import module `pipeline.cli` and call `main`.

### Example 4: Configuration by environment, with a required secret

The same merge as the shell example, but written as a function that takes the environment variables as a dictionary, so it can be tested without changing the real environment. A missing secret is an error, not a silent default.

```python run
import tomllib

TEXT = """
[default]
batch_size = 100
db_host = "localhost"

[prod]
batch_size = 1000
db_host = "warehouse.internal"
"""


def load(env, environ):
    data = tomllib.loads(TEXT)
    cfg = {**data["default"], **data.get(env, {})}
    if "DB_PASSWORD" not in environ:
        raise KeyError("DB_PASSWORD is not set")
    cfg["db_password_set"] = True
    return cfg


print(load("dev", {"DB_PASSWORD": "x"}))
print(load("prod", {"DB_PASSWORD": "x"}))
try:
    load("prod", {})
except KeyError as error:
    print("error:", error)
```

```output
{'batch_size': 100, 'db_host': 'localhost', 'db_password_set': True}
{'batch_size': 1000, 'db_host': 'warehouse.internal', 'db_password_set': True}
error: 'DB_PASSWORD is not set'
```

An unknown environment name (`dev`) falls back to the defaults because `data.get(env, {})` returns an empty table. The password is never part of the file, and the result records only that it was set; printing it would put it in the logs.

## Real-world applications

- A scheduler runs `orders-load` from the entry point with `PIPELINE_ENV=prod`, so the same package runs in test and production with different settings (Examples 2 and 3).
- A CI job reads `pyproject.toml` with `tomllib` to check that every dependency has a version specifier before merging (Example 3).
- An incident review finds that a rerun failed because `DB_PASSWORD` was missing and the loader raised an error immediately instead of connecting with an empty password (Example 4).

## Daily review

### Key takeaways

- A package under `src/` with a `pyproject.toml` runs the same way from any folder and in any scheduler.
- `[project.scripts]` maps a command to `module:function`.
- Use `python -m package` rather than running a file inside the package.
- Settings come from a file per environment plus environment variables; secrets only from the environment.

### Common mistakes

- Running `python src/pipeline/cli.py`. Symptom: `ModuleNotFoundError: No module named 'pipeline'`. Fix: `python -m pipeline.cli` with the package on the path or installed.
- Opening a TOML file in text mode. Symptom: `TypeError` from `tomllib.load`. Fix: open with `"rb"`.
- Committing a password in `config.toml`. Symptom: the secret is in the repository history. Fix: read it from an environment variable and rotate the leaked one.
- Leaving dependencies without versions. Symptom: a run that worked last week fails after an upstream release. Fix: pin the tested versions for deployment.

### Revision notes

- `tomllib.load(open(path, "rb"))`.
- `pipeline.cli:main` means module `pipeline.cli`, function `main`.
- Config layers: defaults, then environment table, then environment variables.

## Objectives

- Explain what source-to-target validation proves and what it cannot prove, and say where it sits after a load.
- Compare row counts and column sums between a source and a target, and account for rows the transform removes on purpose.
- Compute a stable row hash with `hashlib` and use it to find missing, extra and changed rows by key.
- Produce a column-level diff that names which column differs for which key.
- Combine the checks into one validation function that returns a readable report.

## Understand

### The question this day answers

Your pipeline from Days 120 to 127 extracts orders, cleans them and loads them into `orders_clean`. Every step ran without an error. That tells you the code did not crash; it does not tell you the data is right. **Source-to-target validation** is the habit of comparing what you read from the source with what now sits in the target, and stating in numbers whether they agree. The word "validation" here means a comparison between two datasets, unlike the rule checks of Days 132 to 135, which look at one dataset on its own. A rule check can say "no amount is negative". Only a comparison can say "an order that existed at the source is now missing".

Think of a removals company that counts boxes at the old house and again at the new one. Matching counts do not prove nothing broke inside a box, so they also check the heaviest crate by weight, and open a few boxes to compare contents. Source-to-target validation uses the same three layers, from cheap and coarse to expensive and precise.

### Layer 1: row counts

The cheapest check compares `COUNT(*)` on both sides. If the source has 8 rows and the target has 7, something dropped a row, and you must find out whether that was intended. The count is quick and catches the biggest failures: an extract that stopped after one page, a join that lost rows, a load that was never committed. It misses any bug that keeps the number of rows the same, such as one lost row cancelling out one duplicated row.

The important idea is **expected loss**. A transform may remove rows on purpose: it may drop `failed` orders or collapse duplicates. A valid comparison therefore never says "target count must equal source count". It says "target count must equal the source count after the documented rules are applied". The cleanest way to hold this is to write the rule once as a function and compute what the target should contain, then compare the real target with that expectation.

### Layer 2: sums and other aggregates

A **control total** is an aggregate computed on both sides: the sum of `amount_cents`, the number of distinct customers, the minimum and maximum `created_at`. Sums catch bugs that counts miss. A currency conversion applied twice, an amount parsed as dollars instead of cents, or a row whose amount became zero all leave the row count alone and change the sum. Compare sums on integers, which is why the pipeline stores `amount_cents`; sums of floats differ in the last digits and need a tolerance, which Day 137 covers. A sum still has a weakness: two errors in opposite directions can cancel, for example one amount 180 too high and another 180 too low.

### Layer 3: row hashes and column-level diffs

To compare content you need something per row. A **hash** is a fixed-size fingerprint computed from data: the same input always gives the same fingerprint, and a one-character change gives a completely different one. With `hashlib.sha256` you turn a row into text, encode it as bytes and take the hex digest. If the source row and the target row have equal hashes, you treat them as equal without comparing every column.

A hash is only useful when both sides build the text the same way. That is called a **canonical form**: the columns in a fixed order, a separator that cannot appear in the data, every value converted with the same rules (strip spaces, upper-case the currency, integers as plain digits). Two sides that format `12.50` and `12.5` differently report a false difference on every row. The same fingerprint idea shows up in the table-level check of PostgreSQL's `md5(string_agg(...))`, which you can use inside the database.

A hash tells you that a row differs, not how. When it differs, do a **column-level diff**: join source and target on the key and compare each column, producing a list such as "order 6, column amount_cents: source 2200, target 2020". This is the layer that makes a failure fixable, because it points at the transform step responsible. Run the expensive layer only on the keys the cheaper layer flagged, or on a sample, when the tables are large.

### Missing, extra and changed

Every key falls into one of four groups. **Missing** keys exist in the source only; **extra** keys exist in the target only; **changed** keys exist in both with different content; **matching** keys are identical. A full outer join on the key, with `IS DISTINCT FROM` for the content (it treats two NULLs as equal, unlike `<>`), sorts every row into one of these groups. In pandas, `merge(..., how="outer", indicator=True)` gives the same classification in a `_merge` column.

### Common misconception

Many learners believe that equal row counts mean the load is correct. Counts are the weakest check: a pipeline that overwrote half the rows with wrong amounts and lost nothing passes it. A second misconception is that a mismatch always means a bug. A mismatch you can explain by a documented rule is expected; a mismatch you cannot explain is the one to investigate. A third is hashing the wrong thing: if the target adds a `loaded_at` column and you hash it, every row differs. Hash only the business columns both sides share.

### Why it matters

Reports are built on the target. If a stakeholder finds that the revenue figure in the dashboard differs from the source system, trust drops and nobody can say when the difference began. A validation step that runs after every load turns that surprise into an alert on the day it happens, with the key and the column already identified.

## Syntax and key functions

Canonical row hash:

```python
import hashlib

def row_hash(row):
    text = "|".join(str(v) for v in row)          # fixed column order, fixed separator
    return hashlib.sha256(text.encode("utf-8")).hexdigest()
```

Outer join classification in pandas:

```python
merged = source.merge(target, on="order_id", how="outer", suffixes=("_src", "_tgt"), indicator=True)
merged["_merge"]   # "left_only" = missing, "right_only" = extra, "both" = in both
```

Outer join classification in PostgreSQL:

```sql-syntax
SELECT COALESCE(s.key, t.key) AS key,
       CASE WHEN t.key IS NULL THEN 'missing'
            WHEN s.key IS NULL THEN 'extra'
            ELSE 'changed' END AS problem
FROM source s FULL OUTER JOIN target t ON t.key = s.key
WHERE s.key IS NULL OR t.key IS NULL OR s.col IS DISTINCT FROM t.col;
```

| Item | What it does or returns |
|---|---|
| `COUNT(*)`, `SUM(col)` | Control totals computed on each side. |
| `hashlib.sha256(bytes).hexdigest()` | 64-character hex fingerprint of the bytes. |
| `str.encode("utf-8")` | Turns text into bytes, which hashing requires. |
| `df.merge(other, on, how="outer", indicator=True)` | Joins on the key and adds `_merge` with `left_only`, `right_only` or `both`. |
| `a IS DISTINCT FROM b` | True when values differ, treating two NULLs as equal. |
| `FULL OUTER JOIN` | Keeps unmatched rows from both tables. |
| `set(a) - set(b)` | Keys present in one collection but not the other. |

## Learn by example

All examples use the order pipeline's shape: a source list of orders, the documented rule "clean the currency to upper case and drop `failed` orders", and a target table that a faulty load produced. Order 7 was lost and order 6 arrived with its digits transposed.

### Example 1: Counts and sums, with the expected loss

The function `expected_target` is the documented rule written once. The report compares the source with the expectation first, which explains the one dropped row, and then compares the real target with the expectation. The count difference between source and target is 2, but only 1 of them is explained by the rule.

```python run
import sqlite3

source = [
    (1, 10, 1250, "usd", "paid", "2026-01-05"),
    (2, 11, 3400, "USD", "paid", "2026-01-05"),
    (3, 10, 999, "USD", "refunded", "2026-01-06"),
    (4, 12, 5000, "EUR", "paid", "2026-01-06"),
    (5, 13, 0, "USD", "failed", "2026-01-07"),
    (6, 11, 2200, "USD", "paid", "2026-01-07"),
    (7, 14, 7500, "USD", "paid", "2026-01-08"),
    (8, 12, 1800, "EUR", "paid", "2026-01-08"),
]

def expected_target(rows):
    return [(i, c, a, cur.upper(), s, d) for i, c, a, cur, s, d in rows if s != "failed"]

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, customer_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)")
faulty = [r for r in expected_target(source) if r[0] != 7]
faulty = [(6, 11, 2020) + r[3:] if r[0] == 6 else r for r in faulty]
conn.executemany("INSERT INTO orders_clean VALUES (?, ?, ?, ?, ?, ?)", faulty)

expected = expected_target(source)
tgt_count, tgt_sum = conn.execute("SELECT COUNT(*), SUM(amount_cents) FROM orders_clean").fetchone()
print("source rows:", len(source), "expected rows:", len(expected), "target rows:", tgt_count)
print("rows lost on purpose:", len(source) - len(expected))
print("rows lost by mistake:", len(expected) - tgt_count)
print("expected sum:", sum(r[2] for r in expected), "target sum:", tgt_sum)
```

```output
source rows: 8 expected rows: 7 target rows: 6
rows lost on purpose: 1
rows lost by mistake: 1
expected sum: 22149 target sum: 14469
```

The counts say one row is missing. The sums differ by 7,680 cents, which is more than the lost order 7 explains (7,500): the target also holds 180 cents less than it should, so something else changed an amount. Counts alone would have missed that.

### Example 2: Row hashes find missing, extra and changed keys

Each row becomes a canonical string, with the same columns in the same order on both sides. Hashes are stored by key, and set operations on the keys then classify the problems. The program prints only the keys and a hash length, never the hash itself, because a hash is long and meaningless to read.

```python run
import hashlib
import sqlite3

def row_hash(row):
    text = "|".join(str(v) for v in row[1:])
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

expected = {
    1: (1, 10, 1250, "USD", "paid"),
    2: (2, 11, 3400, "USD", "paid"),
    6: (6, 11, 2200, "USD", "paid"),
    7: (7, 14, 7500, "USD", "paid"),
}
target = {
    1: (1, 10, 1250, "USD", "paid"),
    2: (2, 11, 3400, "USD", "paid"),
    6: (6, 11, 2020, "USD", "paid"),
    9: (9, 15, 100, "USD", "paid"),
}
h_exp = {k: row_hash(v) for k, v in expected.items()}
h_tgt = {k: row_hash(v) for k, v in target.items()}

print("hash length:", len(h_exp[1]))
print("missing:", sorted(set(h_exp) - set(h_tgt)))
print("extra:", sorted(set(h_tgt) - set(h_exp)))
print("changed:", sorted(k for k in set(h_exp) & set(h_tgt) if h_exp[k] != h_tgt[k]))
print("same text, same hash:", row_hash((0, "a", 1)) == row_hash((9, "a", 1)))
print("12.5 vs 12.50 as text:", row_hash((0, "12.5")) == row_hash((0, "12.50")))
```

```output
hash length: 64
missing: [7]
extra: [9]
changed: [6]
same text, same hash: True
12.5 vs 12.50 as text: False
```

The last two lines show the canonical-form rule: the key is left out of the text on purpose, so identical business columns give identical hashes, and `"12.5"` and `"12.50"` count as different because the text differs. Fix that by formatting numbers the same way on both sides before hashing.

### Example 3: Column-level diff with pandas

For the keys the hash flagged, a pandas merge shows which column differs. The comparison loops over the shared columns, builds a mask of rows that differ, and collects one line per difference. `indicator=True` gives the missing and extra classification at the same time.

```python run
import pandas as pd

exp = pd.DataFrame({"order_id": [1, 2, 6, 7], "amount_cents": [1250, 3400, 2200, 7500], "currency": ["USD", "USD", "USD", "USD"]})
tgt = pd.DataFrame({"order_id": [1, 2, 6, 9], "amount_cents": [1250, 3400, 2020, 100], "currency": ["USD", "EUR", "USD", "USD"]})

m = exp.merge(tgt, on="order_id", how="outer", suffixes=("_exp", "_tgt"), indicator=True)
print(m["_merge"].value_counts().sort_index().to_dict())

both = m[m["_merge"] == "both"]
for col in ["amount_cents", "currency"]:
    bad = both[both[col + "_exp"] != both[col + "_tgt"]]
    for _, r in bad.iterrows():
        print(f"order {int(r['order_id'])} column {col}: expected {r[col + '_exp']} got {r[col + '_tgt']}")
```

```output
{'left_only': 1, 'right_only': 1, 'both': 3}
order 6 column amount_cents: expected 2200.0 got 2020.0
order 2 column currency: expected USD got EUR
```

Order 2 has the right amount but the wrong currency: a hash alone would have said "changed" without saying which column. Order 6's amount has two digits swapped, a typical manual or parsing slip.

### Example 4: The same classification in PostgreSQL

On PGlite the source and target are tables, and one full outer join does the classification, using `IS DISTINCT FROM` so that NULLs compare sensibly. Order 3 has a NULL status in the target while the source has `refunded`, which a plain `<>` would never flag, because comparing with NULL gives NULL.

```sql run
CREATE TABLE src (order_id int PRIMARY KEY, amount_cents int, status text);
CREATE TABLE tgt (order_id int PRIMARY KEY, amount_cents int, status text);
INSERT INTO src VALUES (1, 1250, 'paid'), (2, 3400, 'paid'), (3, 999, 'refunded'), (4, 5000, 'paid');
INSERT INTO tgt VALUES (1, 1250, 'paid'), (2, 3000, 'paid'), (3, 999, NULL), (5, 100, 'paid');

SELECT COALESCE(s.order_id, t.order_id) AS order_id,
       CASE WHEN t.order_id IS NULL THEN 'missing'
            WHEN s.order_id IS NULL THEN 'extra'
            ELSE 'changed' END AS problem
FROM src s
FULL OUTER JOIN tgt t ON t.order_id = s.order_id
WHERE s.order_id IS NULL OR t.order_id IS NULL
   OR s.amount_cents IS DISTINCT FROM t.amount_cents
   OR s.status IS DISTINCT FROM t.status
ORDER BY order_id
LIMIT 10;
```

```output
order_id | problem
2 | changed
3 | changed
4 | missing
5 | extra
```

### Example 5: One validation function with a report

The last example combines the layers. `validate` takes the expected rows and the target rows (dictionaries by key), runs counts, sums, hashes and the column diff, and returns a list of problem lines. An empty list means the load passed. Cheap checks run first; the column diff runs only for flagged keys.

```python run
import hashlib

COLS = ["customer_id", "amount_cents", "currency"]

def row_hash(row):
    return hashlib.sha256("|".join(str(row[c]) for c in COLS).encode("utf-8")).hexdigest()

def validate(expected, target):
    problems = []
    if len(expected) != len(target):
        problems.append(f"row count: expected {len(expected)}, got {len(target)}")
    s_exp = sum(r["amount_cents"] for r in expected.values())
    s_tgt = sum(r["amount_cents"] for r in target.values())
    if s_exp != s_tgt:
        problems.append(f"sum amount_cents: expected {s_exp}, got {s_tgt}")
    for k in sorted(set(expected) - set(target)):
        problems.append(f"missing key {k}")
    for k in sorted(set(target) - set(expected)):
        problems.append(f"extra key {k}")
    for k in sorted(set(expected) & set(target)):
        if row_hash(expected[k]) != row_hash(target[k]):
            for c in COLS:
                if expected[k][c] != target[k][c]:
                    problems.append(f"key {k} column {c}: expected {expected[k][c]}, got {target[k][c]}")
    return problems

good = {1: {"customer_id": 10, "amount_cents": 100, "currency": "USD"}, 2: {"customer_id": 11, "amount_cents": 250, "currency": "EUR"}}
bad = {1: {"customer_id": 10, "amount_cents": 100, "currency": "USD"}, 2: {"customer_id": 11, "amount_cents": 205, "currency": "EUR"}, 3: {"customer_id": 12, "amount_cents": 5, "currency": "USD"}}
print(validate(good, dict(good)))
for line in validate(good, bad):
    print(line)
```

```output
[]
row count: expected 2, got 3
sum amount_cents: expected 350, got 310
extra key 3
key 2 column amount_cents: expected 250, got 205
```

Here the sums differ because of both the changed amount and the extra row, and the report lists each cause on its own line, which is what an on-call engineer needs.

## Real-world applications

- **Post-load gate in an orders pipeline.** After the load of `orders_clean`, run counts, the revenue control total and a hash comparison against the expectation computed from the extracted rows. A failing gate stops downstream reports from refreshing and tells the team which keys are wrong.
- **Migration sign-off.** When data moves from one database to another, the migration is accepted only when per-table counts, sums and a hash per partition agree. A column-level diff on the failing partitions turns "it does not match" into a list of fixable rows.
- **Regression check after a code change.** Run the old and new version of a transform on the same extract and compare their outputs by key. Rows that changed are exactly the effect of the change, and reviewers can approve it against that list.
- **Audit evidence.** Finance teams ask for proof that a reporting table equals the ledger. A saved report with the control totals and the explained exceptions is that proof.

## Daily review

### Key takeaways

- Validate by comparing two datasets in layers: counts, control totals, row hashes, then a column-level diff.
- Compare the target with the source after the documented rules, never with the raw source.
- A hash needs a canonical form: same columns, order, separator and formatting on both sides.
- Classify keys as missing, extra, changed or matching. Use `IS DISTINCT FROM` for NULL-safe comparison in SQL.
- A hash says a row differs; a column diff says which column.

### Common mistakes

- **Requiring target count to equal source count.** The check then fails on every correct run that drops failed orders. Compute the expected rows from the rule and compare to that.
- **Hashing columns that exist only on one side** (`loaded_at`, surrogate ids). Every row then looks changed. Hash the shared business columns only.
- **Comparing with `<>` when NULLs exist.** `NULL <> 'x'` is NULL, so the row is silently skipped. Use `IS DISTINCT FROM`.
- **Trusting equal sums.** Offsetting errors cancel. Add counts and hashes.
- **Formatting differently before hashing.** `12.5` and `12.50` produce different hashes. Normalise on both sides.

### Revision notes

- Layers: `COUNT(*)`, `SUM`, hash by key, column diff.
- Four key groups: missing, extra, changed, matching.
- `hashlib.sha256(text.encode()).hexdigest()`; text = `"|".join(...)` over shared columns in fixed order.
- pandas: `merge(how="outer", indicator=True)`. SQL: `FULL OUTER JOIN` with `IS DISTINCT FROM`.

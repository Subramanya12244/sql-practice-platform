## Objectives

- Define a reporting view that joins the fact table to its dimensions once, so that analysts do not repeat the joins.
- Compute metrics (revenue, orders, average order value) by month, country and category with `GROUP BY`.
- Use window functions for month-over-month change, share of total and a rank within a group.
- Check a metric against an independent calculation, and write the same views and queries in PostgreSQL.
- Explain why a metric is defined once, in a view, and not rewritten in every query.

## Understand

### What the analytics layer is

Day 176 loaded the star schema. The **analytics layer** is the set of views and queries on top of it that answer business questions: how much did we sell each month, which countries and categories lead, who are the top customers. It is the part of the pipeline that people outside engineering see. Its quality is not about clever SQL, it is about **definitions**: every number must mean one thing, and the same question must give the same answer no matter who asks it.

### A view joins once

A star schema needs joins to be useful: the fact table has keys, the dimensions have the names. A **view** is a saved query that behaves like a table. The view `vw_sales` joins `fact_sales` to `dim_customer`, `dim_product` and `dim_date` and exposes readable columns: the sale, the date, the month, the customer's country at the time of the sale, the product category and the amount. Analysts then write `SELECT ... FROM vw_sales` and never have to remember how a surrogate key is joined, which is where mistakes like joining on the current customer row instead of the row used by the fact come from. A view stores no data, so it is always as fresh as the tables below it.

### Metrics are defined once

A **metric** is a named calculation: revenue is the sum of `amount_cents` over paid orders; orders is the count of distinct sales; average order value is revenue divided by orders. If each analyst writes their own query, one counts refunds and another does not, and two dashboards disagree. Defining a metric in one view and building reports on it removes that class of argument. The capstone keeps amounts as integer cents everywhere and converts to euros only for display, because dividing early produces rounding differences between reports.

### Aggregation by dimension

Metrics are sliced by dimension attributes: month from `dim_date`, country from `dim_customer`, category from `dim_product`. The pattern is always `SELECT <dimension columns>, <aggregates> FROM vw_sales GROUP BY <dimension columns> ORDER BY ...`. Because the fact grain is one paid order, `count(*)` is the number of orders and no `DISTINCT` is needed; if a join accidentally multiplied rows the count would be wrong, which is why the totals are checked.

### Window functions for comparisons

Aggregates collapse rows; **window functions** compute a value for each row from a related set of rows without collapsing them. `LAG(revenue) OVER (ORDER BY month)` gives the previous month's revenue on each row, so the change is `revenue - LAG(revenue)`. `SUM(revenue) OVER ()` gives the total on every row, so the share is `revenue / total`. `ROW_NUMBER() OVER (PARTITION BY country ORDER BY revenue DESC)` numbers rows inside each country, so rank 1 is the top customer per country. The first month has no previous month, so its change is NULL, which is correct and should not be replaced by zero.

### Checking a metric

A report is trusted when it reconciles. The sum of monthly revenue must equal the total of the fact table, which must equal the paid total of the clean data from Day 175. Recomputing a metric with a different method, for example in Python from the clean records, catches join mistakes that return plausible numbers.

### Common misconception

Learners think a view makes queries faster. A plain view is only a saved query and is run every time; its value is consistency and readability. Speed comes from indexes, summary tables or materialised views, which are beyond this project.

### Why it matters

Decisions are made on these numbers. A metric defined twice in two dashboards is a meeting about whose number is right.

## Syntax and key functions

A view over the star schema:

```sql-syntax
CREATE VIEW vw_sales AS
SELECT f.sale_id, d.full_date, d.year, d.month, c.country, p.category, f.quantity, f.amount_cents
FROM fact_sales f
JOIN dim_date d ON d.date_key = f.date_key
JOIN dim_customer c ON c.customer_key = f.customer_key
JOIN dim_product p ON p.product_key = f.product_key;
```

Window functions over a monthly summary:

```sql-syntax
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS change,
       round(100.0 * revenue / SUM(revenue) OVER (), 1) AS share_pct
FROM monthly ORDER BY month;
```

| Item | What it does or returns |
|---|---|
| `CREATE VIEW name AS SELECT ...` | Saves a query; reading the view runs it. |
| `LAG(x) OVER (ORDER BY m)` | The value of `x` on the previous row in order `m`; NULL on the first row. |
| `SUM(x) OVER ()` | The total over all rows, repeated on each row. |
| `ROW_NUMBER() OVER (PARTITION BY g ORDER BY x DESC)` | 1, 2, 3 ... inside each group `g`, largest first. |
| `round(x::numeric, n)` | PostgreSQL rounding; cast `real` or `double precision` to numeric first. |
| `sum(amount_cents) / count(*)` | Average order value in cents (integer division in `sqlite3` when both are integers). |

## Learn by example

### Example 1: The reporting view and monthly metrics

`build_full()` runs the pipeline of the earlier days (copied below) and returns the loaded warehouse. The view `vw_sales` joins the four tables; the monthly metrics then need only one table. Average order value is shown in cents, rounded to a whole number, and revenue is also shown in euros for display.

```python run
import random
from datetime import date, timedelta

COUNTRIES = ["DE", "FR", "IN", "US", "BR"]
CATEGORIES = ["tools", "books", "games"]

def generate(seed=7):
    """Seeded stand-in data: customers, products and 120 raw order records with planted defects."""
    rng = random.Random(seed)
    customers = [(f"C{n:03d}", f"Customer {n:02d}", COUNTRIES[n % 5]) for n in range(1, 21)]
    products = [(f"P{n:02d}", f"Product {n:02d}", CATEGORIES[n % 3]) for n in range(1, 9)]
    price = {pid: 500 * (i + 1) for i, (pid, _, _) in enumerate(products)}
    orders = []
    for n in range(1, 121):
        pid = products[rng.randrange(8)][0]
        qty = rng.randint(1, 4)
        day = date(2026, 1, 1) + timedelta(days=(n - 1) * 89 // 119)
        orders.append({
            "order_id": f"O{n:04d}", "customer_id": customers[rng.randrange(20)][0], "product_id": pid,
            "quantity": qty, "amount_cents": price[pid] * qty, "currency": "EUR",
            "status": rng.choices(["paid", "refunded", "failed"], weights=[8, 1, 1])[0],
            "created_at": f"{day}T{(n * 7) % 24:02d}:{(n * 13) % 60:02d}:00Z",
        })
    orders[29]["amount_cents"] = -1000
    orders[44]["customer_id"] = "C999"
    orders[59]["created_at"] = ""
    orders[74]["currency"] = "???"
    orders[104]["status"] = "pending"
    orders[119] = dict(orders[9])
    return customers, products, orders

from datetime import datetime

def first_problem(rec, seen, known):
    """The first rule a raw order breaks, or None. `seen` holds the order ids already processed."""
    if rec["order_id"] in seen:
        return "duplicate order_id"
    if not rec["created_at"]:
        return "missing created_at"
    try:
        datetime.strptime(rec["created_at"], "%Y-%m-%dT%H:%M:%SZ")
    except ValueError:
        return "bad created_at"
    if not isinstance(rec["amount_cents"], int) or rec["amount_cents"] <= 0:
        return "bad amount"
    if rec["customer_id"].strip().upper() not in known:
        return "unknown customer"
    if rec["currency"].strip().upper() != "EUR":
        return "bad currency"
    if rec["status"].strip().lower() not in ("paid", "refunded", "failed"):
        return "bad status"
    return None

def transform(rec):
    """Typed, normalised copy of a valid raw order."""
    return {"sale_id": int(rec["order_id"][1:]), "order_id": rec["order_id"],
            "customer_id": rec["customer_id"].strip().upper(), "product_id": rec["product_id"],
            "quantity": int(rec["quantity"]), "amount_cents": rec["amount_cents"],
            "status": rec["status"].strip().lower(), "created_at": rec["created_at"],
            "date_key": int(rec["created_at"][:10].replace("-", ""))}

def clean_orders(raw, known):
    good, quarantine, seen = [], [], set()
    for rec in raw:
        reason = first_problem(rec, seen, known)
        seen.add(rec["order_id"])
        if reason:
            quarantine.append({"order_id": rec["order_id"], "reason": reason, "payload": rec})
        else:
            good.append(transform(rec))
    return good, quarantine

import sqlite3
from datetime import date, timedelta

DDL = """
CREATE TABLE dim_date (date_key INTEGER PRIMARY KEY, full_date TEXT, year INTEGER, month INTEGER);
CREATE TABLE dim_product (product_key INTEGER PRIMARY KEY AUTOINCREMENT, product_id TEXT UNIQUE, product_name TEXT, category TEXT);
CREATE TABLE dim_customer (customer_key INTEGER PRIMARY KEY AUTOINCREMENT, customer_id TEXT, customer_name TEXT, country TEXT,
                           valid_from TEXT, valid_to TEXT, is_current INTEGER);
CREATE TABLE fact_sales (sale_id INTEGER PRIMARY KEY, date_key INTEGER, customer_key INTEGER, product_key INTEGER,
                         quantity INTEGER, amount_cents INTEGER);
CREATE TABLE etl_state (name TEXT PRIMARY KEY, watermark TEXT);
"""

def init_warehouse():
    conn = sqlite3.connect(":memory:")
    conn.executescript(DDL)
    return conn

def load_dim_date(conn, start, end):
    days = (end - start).days + 1
    rows = [(int(d.strftime("%Y%m%d")), d.isoformat(), d.year, d.month) for d in (start + timedelta(days=i) for i in range(days))]
    with conn:
        conn.executemany("INSERT OR IGNORE INTO dim_date VALUES (?, ?, ?, ?)", rows)

def load_dim_product(conn, products):
    with conn:
        conn.executemany("""INSERT INTO dim_product (product_id, product_name, category) VALUES (?, ?, ?)
                            ON CONFLICT(product_id) DO UPDATE SET product_name = excluded.product_name, category = excluded.category""", products)

def load_dim_customer(conn, customers, as_of, first_from="2026-01-01"):
    """Type 2 history: a changed customer gets a new row; the old row is closed on `as_of`."""
    with conn:
        for cid, name, country in customers:
            cur = conn.execute("SELECT customer_key, customer_name, country FROM dim_customer WHERE customer_id = ? AND is_current = 1", (cid,)).fetchone()
            if cur is None:
                conn.execute("INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current) VALUES (?, ?, ?, ?, '9999-12-31', 1)",
                             (cid, name, country, first_from))
            elif (cur[1], cur[2]) != (name, country):
                conn.execute("UPDATE dim_customer SET valid_to = ?, is_current = 0 WHERE customer_key = ?", (as_of, cur[0]))
                conn.execute("INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current) VALUES (?, ?, ?, ?, '9999-12-31', 1)",
                             (cid, name, country, as_of))

def load_fact(conn, good):
    """Incremental: only paid orders newer than the watermark; upsert on sale_id; the watermark moves after the load."""
    row = conn.execute("SELECT watermark FROM etl_state WHERE name = 'fact_sales'").fetchone()
    mark = row[0] if row else ""
    new = [g for g in good if g["created_at"] > mark]
    facts = []
    for g in new:
        if g["status"] != "paid":
            continue
        day = g["created_at"][:10]
        ck = conn.execute("SELECT customer_key FROM dim_customer WHERE customer_id = ? AND valid_from <= ? AND ? < valid_to", (g["customer_id"], day, day)).fetchone()[0]
        pk = conn.execute("SELECT product_key FROM dim_product WHERE product_id = ?", (g["product_id"],)).fetchone()[0]
        facts.append((g["sale_id"], g["date_key"], ck, pk, g["quantity"], g["amount_cents"]))
    with conn:
        conn.executemany("""INSERT INTO fact_sales VALUES (?, ?, ?, ?, ?, ?)
                            ON CONFLICT(sale_id) DO UPDATE SET date_key = excluded.date_key, customer_key = excluded.customer_key,
                            product_key = excluded.product_key, quantity = excluded.quantity, amount_cents = excluded.amount_cents""", facts)
        if new:
            conn.execute("INSERT INTO etl_state VALUES ('fact_sales', ?) ON CONFLICT(name) DO UPDATE SET watermark = excluded.watermark",
                         (max(g["created_at"] for g in new),))
    return len(facts)

def build_full():
    """The pipeline of Days 174 to 176 in one call: generate, clean, load the star schema."""
    customers, products, orders = generate()
    good, quarantine = clean_orders(orders, {c[0] for c in customers})
    conn = init_warehouse()
    load_dim_date(conn, date(2026, 1, 1), date(2026, 3, 31))
    load_dim_product(conn, products)
    load_dim_customer(conn, customers, "2026-01-01")
    load_fact(conn, good)
    return conn

conn = build_full()
conn.execute("""CREATE VIEW vw_sales AS
SELECT f.sale_id, d.full_date, d.year, d.month, c.country, p.category, f.quantity, f.amount_cents
FROM fact_sales f
JOIN dim_date d ON d.date_key = f.date_key
JOIN dim_customer c ON c.customer_key = f.customer_key
JOIN dim_product p ON p.product_key = f.product_key""")
conn.execute("""CREATE VIEW vw_monthly_revenue AS
SELECT year, month, SUM(amount_cents) AS revenue_cents, COUNT(*) AS orders, SUM(amount_cents) / COUNT(*) AS aov_cents
FROM vw_sales GROUP BY year, month""")
for year, month, cents, orders, aov in conn.execute("SELECT * FROM vw_monthly_revenue ORDER BY year, month"):
    print(year, month, "revenue", cents, f"({cents / 100:.2f} EUR)", "orders", orders, "aov", aov)
print("view rows equal fact rows:", conn.execute("SELECT COUNT(*) FROM vw_sales").fetchone()[0] == conn.execute("SELECT COUNT(*) FROM fact_sales").fetchone()[0])
```

```output
2026 1 revenue 221500 (2215.00 EUR) orders 36 aov 6152
2026 2 revenue 110000 (1100.00 EUR) orders 23 aov 4782
2026 3 revenue 192000 (1920.00 EUR) orders 32 aov 6000
view rows equal fact rows: True
```

### Example 3: Top customer in each country

`ROW_NUMBER() OVER (PARTITION BY country ORDER BY revenue DESC, customer_id)` numbers customers inside each country, with the id as a tie-breaker so the result is stable. Keeping rank 1 gives one row per country. The customer's country comes from the dimension row used by the sale, so history is respected.

### Example 4: The same layer in PostgreSQL

The tables below are small stand-ins with eight sales. The view, the window functions and the rounding work as in PostgreSQL 16 on PGlite. The share is computed with the numeric literal `100.0`, so the value is `numeric` and the two-argument `round` works; a `double precision` value would need a `::numeric` cast first. `NULL` appears for the first month's change.

```sql run
CREATE TABLE dim_date (date_key int PRIMARY KEY, full_date date, year int, month int);
CREATE TABLE dim_product (product_key int PRIMARY KEY, product_id text, category text);
CREATE TABLE fact_sales (sale_id int PRIMARY KEY, date_key int, product_key int, amount_cents int);
INSERT INTO dim_date VALUES (20260105, '2026-01-05', 2026, 1), (20260120, '2026-01-20', 2026, 1), (20260210, '2026-02-10', 2026, 2), (20260301, '2026-03-01', 2026, 3);
INSERT INTO dim_product VALUES (1, 'P01', 'books'), (2, 'P02', 'games');
INSERT INTO fact_sales VALUES (1, 20260105, 1, 1000), (2, 20260105, 2, 1500), (3, 20260120, 1, 500), (4, 20260210, 2, 3000),
                              (5, 20260210, 1, 1000), (6, 20260301, 2, 1500), (7, 20260301, 1, 2500), (8, 20260301, 2, 500);
CREATE VIEW vw_sales AS
SELECT f.sale_id, d.year, d.month, p.category, f.amount_cents
FROM fact_sales f JOIN dim_date d USING (date_key) JOIN dim_product p USING (product_key);
WITH monthly AS (SELECT month, sum(amount_cents) AS revenue, count(*) AS orders FROM vw_sales GROUP BY month)
SELECT month, revenue, orders,
       revenue - lag(revenue) OVER (ORDER BY month) AS change,
       round(100.0 * revenue / sum(revenue) OVER (), 1) AS share_pct
FROM monthly ORDER BY month;
```

## Daily review

### Key takeaways

- The analytics layer is views and queries over the star schema, built on one definition per metric.
- A view joins the dimensions once and hides the surrogate keys.
- Keep money in integer cents and convert for display only.
- `LAG`, `SUM() OVER ()` and `ROW_NUMBER() OVER (PARTITION BY ...)` compare rows without collapsing them.
- Check totals against an independent calculation; slices must add up to the total.

### Common mistakes

- Joining to the current customer row instead of the row the fact points to, so history is lost.
- Replacing the first month's NULL change with 0, which reports a change that did not happen.
- Rounding per row before summing, so slices no longer add to the total. Round only at the end.
- Ranking without a tie-breaker, so the winner changes between runs. Add a second `ORDER BY` column.
- Using `round(double_precision, 2)` in PostgreSQL without a `::numeric` cast, which is an error.
- Believing a view stores data or is faster than its query.

## Objectives

- Build an analysis as three small functions, query, transform and summarise, so that each step can be run, tested and reused on its own.
- Choose the grain of the SQL result so that the pandas step receives exactly the rows it needs, and check the grain with a simple assertion.
- Detect and fix a join that multiplies rows (fan-out) and silently inflates totals.
- Make an analysis reproducible: explicit parameters, a deterministic order, no hidden state, and a small run log that proves two runs agree.
- Combine a PostgreSQL query with a pandas follow-up step and say where each part of the work belongs.

## Understand

### One workflow, three verbs

On Day 157 you sent SQL from Python and on Day 158 you decided where each operation should run. This day puts both tools into one repeatable workflow. Almost every analysis in this course has the same three steps. **Query**: ask the database for the rows you need, already filtered, joined and aggregated to a useful size. **Transform**: reshape and enrich that small result in pandas, for example add a share of total, a month-on-month change or a pivot. **Summarise**: reduce the result to the table, numbers or file that a reader will see. Naming the steps matters because each one has a different job and a different kind of mistake. A query mistake gives wrong rows, a transform mistake gives wrong columns, and a summary mistake gives a wrong message.

A useful analogy is a kitchen line. The database is the prep station: it has the big sacks, the large knives and the cold storage, so it peels and chops (filters and aggregates). Pandas is the cooking station: it takes the prepared portions and combines them into the dish. Carrying whole sacks of potatoes to the cooking station is slow, and asking the prep station to plate the dish is awkward. The workflow from Day 158 follows: push heavy reduction down, do flexible shaping in Python.

### Choosing the grain

The **grain** of a table is what one row represents: one order, one customer per month, one country per month. The query step should return the grain that the next step needs and no finer. If the transform only needs revenue per country per month, query that grain with `GROUP BY`; returning every order and grouping later in pandas moves far more data for no benefit. The reverse mistake is also common: aggregating too early. If you may later want a share of each customer inside a country, the grain must still include the customer. Decide the grain by writing the final table on paper first, then ask which grain is the smallest one from which that table can be computed.

Once the grain is chosen, check it. A grain check is a one-line assertion, for example that there is exactly one row for each combination of month and country: `assert not df.duplicated(["month", "country"]).any()`. When the assertion fails, something upstream produced extra rows, and it is far cheaper to find that at the step where it happened.

### The fan-out trap

The most damaging silent error in combined SQL and pandas work is a **fan-out**: a join in which one row on the left matches several rows on the right, so the left row is repeated. If an order has two payment rows and you join orders to payments and then sum the order amount, the order is counted twice. Nothing fails; the totals are simply too high, often by a plausible amount. The symptom is that a total computed after the join does not equal the total computed from the table alone. The defences are the grain check above, a reconciliation of the total before and after a join (Day 162 builds this out into a full report), and aggregating the many-side table to the grain of the one-side table before joining.

### Reproducible analysis

An analysis is **reproducible** when someone else, or you next month, can run it from the start and get the same numbers, and when a difference can be explained. Four habits give you most of that. First, put every choice in explicit **parameters** (start date, end date, status filter) instead of editing numbers inside code or using today's date implicitly. Second, give every query a deterministic order, because `GROUP BY` without `ORDER BY` returns groups in no guaranteed order and the same code can print rows in a different order on another database. Third, avoid **hidden state**: functions that modify a global DataFrame in place give different results the second time they run, which is the classic "I ran the notebook cells in a different order" bug. A function that receives data and returns a new object is safe to call twice. Fourth, keep a small **run log**: the parameters, the number of rows and the total of the key measure. If two runs have the same log, they very likely agree; if they differ, the log tells you where to look.

### Why it matters, and the misconception

Reports are rerun: next week, with a new month, or by a colleague. A workflow made of named functions with parameters turns a one-off notebook into a tool. The misconception is that doing everything in pandas, or everything in SQL, is "simpler". One tool for everything is simple to explain but it often forces large downloads or unreadable SQL. The workflow in this lesson is simple in a different way: each step has a clear input and output that you can print and check.

## Syntax and key functions

```python
def extract(conn, start, end):
    sql = "SELECT ... WHERE order_date >= ? AND order_date < ? GROUP BY ... ORDER BY ..."
    return pd.read_sql_query(sql, conn, params=(start, end))

def transform(df):
    out = df.copy()              # never change the caller's DataFrame
    out["share_pct"] = ...
    return out

def summarise(df):
    return df.groupby("country", as_index=False).agg(revenue=("revenue", "sum"))
```

Each function takes its input and returns a new object. The same shape with `psycopg` on PostgreSQL (not run here, it needs a server) only changes the connection and the placeholder marker:

```python
import os
import pandas as pd
import psycopg

with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
    df = pd.read_sql_query(
        "SELECT date_trunc('month', order_date)::date AS month, SUM(amount) AS revenue "
        "FROM orders WHERE order_date >= %s AND order_date < %s GROUP BY 1 ORDER BY 1",
        conn, params=(start, end),
    )
```

| Function | Returns or does |
|---|---|
| `pd.read_sql_query(sql, conn, params=...)` | DataFrame from a parameterised query. |
| `df.copy()` | An independent copy, so a transform does not change its input. |
| `df.pivot_table(index, columns, values, aggfunc, fill_value)` | A wide table with one row per index value and one column per column value. |
| `df.pct_change(fill_method=None)` | Relative change from the previous row. |
| `df.duplicated(subset)` | Boolean Series marking repeated key combinations (grain check). |
| `df.groupby(key, as_index=False).agg(name=(col, func))` | Named aggregates with the key kept as a column. |
| `pd.testing.assert_frame_equal(a, b)` | Raises when two DataFrames differ; silent when equal. |

## Learn by example

All SQLite examples use the same small in-memory database built by `make_db()`: nine customers in three countries and 54 orders from January to June 2025, generated by a tiny fixed formula so the data is identical on every run. `sqlite3` stands in for PostgreSQL; the stand-in differs in placeholders (`?` instead of `%s`), types (SQLite is loosely typed) and date functions (here `substr` takes the month from a text date, where PostgreSQL would use `date_trunc`).

### Example 1: Query, transform, summarise

Three functions, each testable alone. The query returns revenue per month and country for paid orders in a half-open date range (`>= start` and `< end`, which never double counts the boundary day).

```python run
import sqlite3
import pandas as pd

def make_db():
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE customers (customer_id INTEGER PRIMARY KEY, name TEXT, country TEXT)")
    conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER, order_date TEXT, amount REAL, status TEXT)")
    countries = ["DE", "FR", "UK"]
    conn.executemany("INSERT INTO customers VALUES (?, ?, ?)", [(i, f"cust{i:02d}", countries[i % 3]) for i in range(1, 10)])
    rows, x = [], 7
    for k in range(1, 55):
        x = (x * 75 + 74) % 65537
        status = "refunded" if k % 11 == 0 else ("failed" if k % 13 == 0 else "paid")
        rows.append((k, x % 9 + 1, f"2025-{(x // 9) % 6 + 1:02d}-{(x // 54) % 28 + 1:02d}", float(20 + (x // 1512) % 180), status))
    conn.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?)", rows)
    conn.commit()
    return conn

def extract(conn, start, end):
    sql = """SELECT substr(o.order_date, 1, 7) AS month, c.country,
                    COUNT(*) AS orders, SUM(o.amount) AS revenue
             FROM orders o JOIN customers c ON c.customer_id = o.customer_id
             WHERE o.status = 'paid' AND o.order_date >= ? AND o.order_date < ?
             GROUP BY month, c.country ORDER BY month, c.country"""
    return pd.read_sql_query(sql, conn, params=(start, end))

def transform(df):
    out = df.copy()
    out["avg_order"] = (out["revenue"] / out["orders"]).round(2)
    return out

def summarise(df):
    s = df.groupby("country", as_index=False).agg(orders=("orders", "sum"), revenue=("revenue", "sum"))
    return s.sort_values("revenue", ascending=False, kind="stable")

conn = make_db()
raw = extract(conn, "2025-01-01", "2025-04-01")
print(raw.shape, "grain ok:", not raw.duplicated(["month", "country"]).any())
print(transform(raw).head(4).to_string(index=False))
print(summarise(transform(raw)).to_string(index=False))
conn.close()
```

```output
(8, 4) grain ok: True
  month country  orders  revenue  avg_order
2025-01      DE       4    165.0      41.25
2025-01      FR       2     53.0      26.50
2025-01      UK       3    125.0      41.67
2025-02      DE       4    138.0      34.50
country  orders  revenue
     UK       8    364.0
     FR       9    356.0
     DE       9    342.0
```

The query returned one row per month and country, and the grain check passed before any transformation. `transform` does not change `raw`, so `raw` can be reused for other views.

### Example 2: A pivot and a month-on-month change

Pandas is the right place for reshaping. `pivot_table` turns the long result (one row per month and country) into a wide table, and `pct_change` adds the monthly growth of the total. The first month has no previous month, so its growth is missing.

```python run
import sqlite3
import pandas as pd

def make_db():
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE customers (customer_id INTEGER PRIMARY KEY, name TEXT, country TEXT)")
    conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER, order_date TEXT, amount REAL, status TEXT)")
    countries = ["DE", "FR", "UK"]
    conn.executemany("INSERT INTO customers VALUES (?, ?, ?)", [(i, f"cust{i:02d}", countries[i % 3]) for i in range(1, 10)])
    rows, x = [], 7
    for k in range(1, 55):
        x = (x * 75 + 74) % 65537
        status = "refunded" if k % 11 == 0 else ("failed" if k % 13 == 0 else "paid")
        rows.append((k, x % 9 + 1, f"2025-{(x // 9) % 6 + 1:02d}-{(x // 54) % 28 + 1:02d}", float(20 + (x // 1512) % 180), status))
    conn.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?)", rows)
    conn.commit()
    return conn

conn = make_db()
long = pd.read_sql_query(
    """SELECT substr(o.order_date, 1, 7) AS month, c.country, SUM(o.amount) AS revenue
       FROM orders o JOIN customers c ON c.customer_id = o.customer_id
       WHERE o.status = 'paid' GROUP BY month, c.country ORDER BY month, c.country""", conn)
wide = long.pivot_table(index="month", columns="country", values="revenue", aggfunc="sum", fill_value=0)
wide["total"] = wide.sum(axis=1)
wide["mom_pct"] = (wide["total"].pct_change(fill_method=None) * 100).round(1)
print(wide.to_string())
conn.close()
```

```output
country     DE     FR     UK  total  mom_pct
month                                       
2025-01  165.0   53.0  125.0  343.0      NaN
2025-02  138.0  158.0    0.0  296.0    -13.7
2025-03   39.0  145.0  239.0  423.0     42.9
2025-04  225.0   22.0   79.0  326.0    -22.9
2025-05   90.0   51.0   46.0  187.0    -42.6
2025-06   83.0  119.0   85.0  287.0     53.5
```

The database did the aggregation to month and country (18 rows at most); pandas did the pivot and the growth, which would be awkward in plain SQL.

### Example 3: A fan-out, caught and fixed

A `payments` table holds one row per payment, and order 2 was paid in two instalments. Joining orders to payments repeats order 2, and summing `amount` after the join counts it twice. A reconciliation of the total with the single-table total reveals it; aggregating payments to one row per order before the join removes it.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, amount REAL)")
conn.execute("CREATE TABLE payments (order_id INTEGER, paid REAL)")
conn.executemany("INSERT INTO orders VALUES (?, ?)", [(1, 100.0), (2, 200.0), (3, 50.0)])
conn.executemany("INSERT INTO payments VALUES (?, ?)", [(1, 100.0), (2, 120.0), (2, 80.0), (3, 50.0)])

truth = conn.execute("SELECT SUM(amount) FROM orders").fetchone()[0]
fanned = conn.execute("SELECT SUM(o.amount) FROM orders o JOIN payments p ON p.order_id = o.order_id").fetchone()[0]
fixed = conn.execute("""SELECT SUM(o.amount) FROM orders o
                        JOIN (SELECT order_id, SUM(paid) AS paid FROM payments GROUP BY order_id) p
                          ON p.order_id = o.order_id""").fetchone()[0]
print("orders only:", truth)
print("after join:", fanned, "inflated" if fanned != truth else "ok")
print("after aggregating payments first:", fixed, "inflated" if fixed != truth else "ok")
conn.close()
```

```output
orders only: 350.0
after join: 550.0 inflated
after aggregating payments first: 350.0 ok
```

The rule of thumb: before summing a measure across a join, ask whether the other table is unique on the join key. When it is not, aggregate it first or sum a measure that belongs to the many side.

### Example 4: Hidden state and a run log

Two versions of a revenue adjustment. The first modifies a shared DataFrame in place, so running the "cell" twice compounds the change. The second returns a new DataFrame, so a second run gives the same answer. A run log built from parameters, row count and total lets two runs be compared, and `assert_frame_equal` proves the pure function repeatable.

```python run
import pandas as pd

base = pd.DataFrame({"month": ["2025-01", "2025-02", "2025-03"], "revenue": [100.0, 200.0, 300.0]})

def adjust_in_place(df, rate):
    df["revenue"] = df["revenue"] * (1 + rate)
    return df["revenue"].sum()

def adjust_pure(df, rate):
    out = df.copy()
    out["revenue"] = out["revenue"] * (1 + rate)
    return out

shared = base.copy()
print("in place, run 1:", round(adjust_in_place(shared, 0.1), 2))
print("in place, run 2:", round(adjust_in_place(shared, 0.1), 2))

first = adjust_pure(base, 0.1)
second = adjust_pure(base, 0.1)
pd.testing.assert_frame_equal(first, second)
log = {"rate": 0.1, "rows": len(first), "total": round(float(first["revenue"].sum()), 2)}
print("pure, both runs equal; log:", log)
print("input untouched:", base["revenue"].tolist())
```

```output
in place, run 1: 660.0
in place, run 2: 726.0
pure, both runs equal; log: {'rate': 0.1, 'rows': 3, 'total': 660.0}
input untouched: [100.0, 200.0, 300.0]
```

The in-place version gave 660.0 and then 726.0 for the same call. Reproducibility means the same inputs give the same output every time, and the cheapest way to get it is to treat DataFrames passed to a function as read-only.

### Example 5: The same workflow against PostgreSQL SQL

SQL that uses PostgreSQL features (`date_trunc`, CTEs, window functions) runs on the browser database, which behaves like PostgreSQL. The query step computes monthly order counts for 1997 and uses `LAG` for the previous month, the part of the work that is natural inside SQL; a script would then load it with `read_sql_query` and `%s` placeholders. Here the dates are written into the text because the browser runner has no parameters.

```sql run
WITH monthly AS (
  SELECT date_trunc('month', order_date)::date AS month, COUNT(*) AS orders
  FROM orders
  WHERE order_date >= DATE '1997-01-01' AND order_date < DATE '1998-01-01'
  GROUP BY 1
)
SELECT month, orders, LAG(orders) OVER (ORDER BY month) AS prev_orders
FROM monthly
ORDER BY month
LIMIT 5;
```

```output
month | orders | prev_orders
1997-02-01 | 9 | NULL
1997-05-01 | 8 | 9
1997-08-01 | 8 | 8
1997-11-01 | 8 | 8
```

The synthetic Northwind data has orders in only four months of 1997, so only those months appear, and the first row has no previous month (`NULL`). Whether `LAG` runs in SQL or `shift` runs in pandas is the Day 158 question: with a handful of rows it makes no difference, with a very large table the aggregation must stay in the database.

## Real-world applications

- **Monthly revenue pack**: `extract` queries one month by parameters, `transform` adds growth and shares, `summarise` produces the table in the management report (Examples 1 and 2). Next month only the parameters change.
- **Total checks after joins**: analysts compare the total before and after joining a dimension or a payments table to catch fan-outs before the numbers reach a dashboard (Example 3).
- **Handover to a colleague**: a function-based analysis with a run log can be rerun by someone else, who can compare their log with yours instead of arguing about whose numbers are right (Example 4).
- **Audit questions**: when a stakeholder asks why a figure changed, the parameters and the log show whether the data, the date range or the code changed.

## Daily review

### Key takeaways

- Split an analysis into query, transform and summarise functions with explicit inputs and outputs.
- Choose the smallest grain that still allows the final table, and assert it.
- A join to a table that is not unique on the key repeats rows and inflates sums; compare totals before and after.
- Reproducible means parameters, deterministic order, no in-place changes of shared data, and a run log.
- Let the database aggregate, let pandas reshape.

### Common mistakes

- Joining first and summing after, without checking uniqueness. The total is too high and no error appears; reconcile against the single-table total.
- Using `<=` with an end date on a timestamp column. Rows later on the end day are lost; use a half-open range `>= start AND < next_day`.
- Modifying a DataFrame inside a function without copying. The caller's data changes and a second run gives other numbers; use `df.copy()`.
- Relying on the order of `GROUP BY` results. The rows may come back in another order elsewhere; add `ORDER BY`.
- Pivoting with `pivot_table` and forgetting `fill_value`. Missing combinations appear as `NaN` and break later arithmetic.

### Revision notes

- Workflow: query (SQL, grain), transform (pandas, `copy()`), summarise (small table).
- Grain check: `df.duplicated(keys).any()` must be `False`.
- Fan-out: aggregate the many side first; compare totals.
- Run log: parameters, rows, total.
- Half-open ranges: `>= start AND < end`.

## Objectives

- Record run metrics (rows read, loaded, quarantined, duration, status) in a table for every run.
- Compute freshness (how old the newest data is) and compare it with a threshold.
- Express alert rules as data and evaluate them against a run, with severity and a clear message.
- Compare a run with its recent history to catch volume drops and slowdowns that a fixed threshold misses.

## Understand

### Why monitor

A pipeline that finishes without an error can still be wrong: the source sent half the usual rows, the load took five times longer, the last successful run was three days ago because the scheduler stopped. Nobody sees these problems in a log unless they look. **Monitoring** is the habit of measuring a pipeline continuously and telling a person when something needs attention. It has three parts: **metrics** (numbers recorded on every run), **checks** (comparisons of those numbers with expectations) and **alerts** (messages sent when a check fails). Day 129 gave you the events and counts; today turns them into numbers over time.

### Run metrics

A **run metric record** is one row per run in an `etl_runs` table: a run id, the day or window processed, start and finish times, rows read, loaded and quarantined, and a status (`ok`, `failed`). From it you derive the **duration** (finish minus start), the **quarantine rate** (quarantined divided by read) and the **throughput** (rows loaded per second). Recording the numbers in a table, not only in log text, lets you query trends with SQL and chart them as on Day 118. Store times as UTC and compute with plain numbers or timestamps in code; in the examples a fake clock of whole seconds keeps the output reproducible.

### Freshness

**Freshness** is how old the data in the target is. It is measured as `now - newest timestamp that is loaded`, for example the maximum `updated_at` in `orders_clean`, or the finish time of the last successful run. A table can be unfresh with no failing run: if the scheduler never started the job, nothing failed, yet the data is two days old. That is why freshness is measured from the data and the successful runs, not from error counts. A **freshness threshold** (a service level, such as "orders are never more than 26 hours old") turns the number into a check. The time passed in must be an argument, as with the injected clock of Day 129, so the check can be tested with a fixed `now`.

### Alert rules as data

An **alert rule** states a condition and what to do when it holds: a metric, a comparison, a threshold and a severity (`warning`, `critical`). Writing rules as a list of dictionaries, not as scattered `if` statements, makes them easy to read, change and test: the evaluator is one function that applies every rule to a metrics record and returns the messages of the rules that fired. Good alerts are **actionable**: the message names the pipeline, the metric, the value, the threshold and what to check. **Alert fatigue** is the real danger: rules that fire constantly are muted, and then the one that matters is missed. Fewer alerts with honest thresholds beat many that cry wolf. Page a person only for problems that need action now; send the rest to a daily summary.

### Comparing with history

A fixed threshold ("fewer than 50 rows is a problem") fails when the normal level changes, and it cannot tell that 60 rows is a collapse on a day that normally brings 1,000. A **relative check** compares the run with its own recent history: the median of the last N runs is a stable baseline, and a run that is below, say, 50 percent of the median is suspicious. Duration works the same way: a run three times longer than the median is a warning even though it succeeded. The median is better than the mean here because one bad run does not move it much. Seasonality matters: a pipeline that loads fewer orders on Sundays should compare Sundays with Sundays, which is why thresholds are honest only when you have looked at the history.

### What monitoring cannot do

Row counts do not prove that values are right; quality checks (Days 132 to 135) do that. Monitoring answers whether the pipeline ran, how much it moved, how long it took and how fresh the data is. A misconception is that a green dashboard means correct data; it means the pipeline behaved normally.

### Why it matters in data work

The first sign of a broken source is usually a number that looks slightly off. A metrics table with a few checks finds it the same morning, before an analyst finds it in a report a week later.

```sql-syntax
SELECT pipeline, finished_at, status
FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY pipeline ORDER BY finished_at DESC) AS rn FROM etl_runs) t
WHERE rn = 1;
```

| Item | What it does or returns |
|---|---|
| `duration = finished - started` | How long a run took. |
| `quarantine_rate = quarantined / read` | Share of rows set aside. |
| freshness | `now - newest loaded timestamp`, compared with a threshold. |
| alert rule | A metric, comparison, threshold and severity as a dictionary. |
| `statistics.median(values)` | The middle value; robust against one extreme run. |
| relative check | Run value divided by the median of recent runs. |
| severity | `warning` for a summary, `critical` for a page. |

## Learn by example

### Example 1: Metrics per run

Five runs are stored in an `etl_runs` table, and the derived metrics (duration, quarantine rate) are computed in SQL. Run 5 stands out: it read far fewer rows and took five times longer, and its status is still `ok`.

```python run
import sqlite3
RUNS = [
    {"run_id": 1, "day": "2025-03-01", "started": 1000, "finished": 1060, "read": 100, "loaded": 98, "quarantined": 2, "status": "ok"},
    {"run_id": 2, "day": "2025-03-02", "started": 1000, "finished": 1065, "read": 104, "loaded": 102, "quarantined": 2, "status": "ok"},
    {"run_id": 3, "day": "2025-03-03", "started": 1000, "finished": 1058, "read": 98, "loaded": 97, "quarantined": 1, "status": "ok"},
    {"run_id": 4, "day": "2025-03-04", "started": 1000, "finished": 1070, "read": 103, "loaded": 99, "quarantined": 4, "status": "ok"},
    {"run_id": 5, "day": "2025-03-05", "started": 1000, "finished": 1300, "read": 41, "loaded": 40, "quarantined": 1, "status": "ok"},
]

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE etl_runs (run_id INTEGER PRIMARY KEY, day TEXT, started INTEGER, finished INTEGER, read INTEGER, loaded INTEGER, quarantined INTEGER, status TEXT)")
conn.executemany("INSERT INTO etl_runs VALUES (:run_id, :day, :started, :finished, :read, :loaded, :quarantined, :status)", RUNS)
sql = """SELECT run_id, day, finished - started AS seconds, read, ROUND(100.0 * quarantined / read, 1) AS quarantine_pct, status
         FROM etl_runs ORDER BY run_id"""
for row in conn.execute(sql):
    print(row)
```

```output
(1, '2025-03-01', 60, 100, 2.0, 'ok')
(2, '2025-03-02', 65, 104, 1.9, 'ok')
(3, '2025-03-03', 58, 98, 1.0, 'ok')
(4, '2025-03-04', 70, 103, 3.9, 'ok')
(5, '2025-03-05', 300, 41, 2.4, 'ok')
```
### Example 2: Freshness with an injected clock

The newest loaded timestamp is compared with a fixed `now` passed as an argument. The function returns the age in hours and a status. A run that never happened looks just like this: no error, but a stale table.

```python run
from datetime import datetime

def freshness(newest, now, max_hours):
    age = (now - newest).total_seconds() / 3600
    return round(age, 1), "OK" if age <= max_hours else "STALE"

now = datetime(2025, 3, 5, 12, 0)
print(freshness(datetime(2025, 3, 5, 3, 30), now, 26))
print(freshness(datetime(2025, 3, 3, 23, 0), now, 26))
```

```output
(8.5, 'OK')
(37.0, 'STALE')
```
### Example 3: Alert rules as data

Three rules are plain dictionaries, and one function applies them to a metrics record. The message names the pipeline, the metric, the value and the threshold, so the person who receives it knows what to check. The record is run 4 and then a bad run.

```python run
import operator

OPS = {"<": operator.lt, ">": operator.gt, ">=": operator.ge}
RULES = [
    {"name": "quarantine_rate", "metric": "quarantine_rate", "op": ">", "threshold": 0.05, "severity": "critical"},
    {"name": "no_rows", "metric": "read", "op": "<", "threshold": 1, "severity": "critical"},
    {"name": "slow_run", "metric": "seconds", "op": ">", "threshold": 120, "severity": "warning"},
]

def evaluate(pipeline, metrics):
    return [f"[{r['severity']}] {pipeline}: {r['name']} {metrics[r['metric']]} {r['op']} {r['threshold']}"
            for r in RULES if OPS[r["op"]](metrics[r["metric"]], r["threshold"])]

print(evaluate("orders", {"read": 103, "quarantine_rate": 0.039, "seconds": 70}))
print(evaluate("orders", {"read": 41, "quarantine_rate": 0.24, "seconds": 300}))
```

```output
[]
['[critical] orders: quarantine_rate 0.24 > 0.05', '[warning] orders: slow_run 300 > 120']
```
### Example 4: Compare a run with its history

The volume and duration of the last run are divided by the median of the four runs before it. The ratio exposes the drop and the slowdown, although both runs finished with status `ok`. The thresholds are 0.5 and 3.0.

```python run
from statistics import median
RUNS = [
    {"run_id": 1, "day": "2025-03-01", "started": 1000, "finished": 1060, "read": 100, "loaded": 98, "quarantined": 2, "status": "ok"},
    {"run_id": 2, "day": "2025-03-02", "started": 1000, "finished": 1065, "read": 104, "loaded": 102, "quarantined": 2, "status": "ok"},
    {"run_id": 3, "day": "2025-03-03", "started": 1000, "finished": 1058, "read": 98, "loaded": 97, "quarantined": 1, "status": "ok"},
    {"run_id": 4, "day": "2025-03-04", "started": 1000, "finished": 1070, "read": 103, "loaded": 99, "quarantined": 4, "status": "ok"},
    {"run_id": 5, "day": "2025-03-05", "started": 1000, "finished": 1300, "read": 41, "loaded": 40, "quarantined": 1, "status": "ok"},
]

history, last = RUNS[:-1], RUNS[-1]
read_ratio = last["read"] / median(r["read"] for r in history)
duration_ratio = (last["finished"] - last["started"]) / median(r["finished"] - r["started"] for r in history)
print(f"read vs median: {read_ratio:.2f}", "ALERT" if read_ratio < 0.5 else "ok")
print(f"duration vs median: {duration_ratio:.2f}", "ALERT" if duration_ratio > 3.0 else "ok")
print("fixed threshold of 50 rows would say:", "ok" if last["read"] >= 50 else "alert")
```

```output
read vs median: 0.40 ALERT
duration vs median: 4.80 ALERT
fixed threshold of 50 rows would say: alert
```
### Example 5: Monitoring queries on PostgreSQL syntax (PGlite)

The `etl_runs` table holds runs of two pipelines. One query finds the latest run of each pipeline, another counts failures per pipeline among its last three runs. The timestamps are compared with a fixed `now`, and results are cast to text so the output is stable.

```sql run
CREATE TABLE etl_runs (pipeline text, run_id int, finished_at timestamp, status text);
INSERT INTO etl_runs VALUES ('orders', 1, '2025-03-03 03:00', 'ok'), ('orders', 2, '2025-03-04 03:00', 'failed'), ('orders', 3, '2025-03-05 03:00', 'ok'),
  ('customers', 1, '2025-03-03 02:00', 'ok'), ('customers', 2, '2025-03-04 02:00', 'failed'), ('customers', 3, '2025-03-04 14:00', 'failed');
SELECT pipeline, latest::text AS latest_run, last_status,
       ROUND(EXTRACT(EPOCH FROM (TIMESTAMP '2025-03-05 12:00' - latest)) / 3600) AS hours_old, failures_in_last_3
FROM (
  SELECT pipeline,
         MAX(finished_at) AS latest,
         MAX(status) FILTER (WHERE rn = 1) AS last_status,
         COUNT(*) FILTER (WHERE status = 'failed') AS failures_in_last_3
  FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY pipeline ORDER BY finished_at DESC) AS rn FROM etl_runs) r
  WHERE rn <= 3
  GROUP BY pipeline
) s
ORDER BY pipeline;
```

```output
pipeline | latest_run | last_status | hours_old | failures_in_last_3
customers | 2025-03-04 14:00:00 | failed | 22 | 2
orders | 2025-03-05 03:00:00 | ok | 9 | 1
```
## Real-world applications

- **Morning check.** A freshness query and the last run's metrics (Examples 1, 2 and 5) are the first thing an on-call engineer reads, before anyone asks why a report looks old.
- **Volume drops from the source.** A relative check (Example 4) detects the partner who sent half a file even though every step succeeded.
- **Paging policy.** Rules with severities (Example 3) page for a failed or empty run and put slow runs in a daily summary, which keeps the pager trustworthy.
- **Capacity planning.** Run durations over weeks show when a nightly job will outgrow its window, long before it overlaps with the next run.

## Daily review

### Key takeaways

- Record one metrics row per run: counts, duration, status; derive quarantine rate and throughput.
- Freshness is `now - newest loaded timestamp`; measure it from the data, because a job that never ran raises no error.
- Write alert rules as data with a severity and an actionable message.
- Compare with the median of recent runs, not only with fixed thresholds.
- Fewer, honest alerts beat many noisy ones; monitoring shows behaviour, not correctness.

### Common mistakes

- Alerting only on failed runs, so a job that never started or loaded nothing stays silent. Add freshness and volume checks.
- A fixed row-count threshold that is wrong when volumes change. Use a ratio to the recent median.
- Using the mean of the history, which one extreme run distorts. Use the median.
- Rules that fire daily until everyone mutes them. Tune thresholds from the history and send low severity to a summary.
- Reading the clock inside the check, so tests cannot reproduce it. Pass `now` in.
- Treating a green run as correct data; add quality checks.

### Revision notes

- `etl_runs`: run id, window, start, finish, read, loaded, quarantined, status.
- Duration, quarantine rate, freshness = now minus newest loaded timestamp.
- Rule = metric, op, threshold, severity; evaluate returns messages.
- Relative check = value / median of last N runs.

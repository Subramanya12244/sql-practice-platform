## Objectives

- Describe ETL (extract, transform, load) and ELT (extract, load, transform) and say where the transformation runs in each.
- Explain staging and the raw, clean and mart layers, and what each layer is for.
- Build the same small pipeline both ways and show that the results match.
- Choose between ETL and ELT for a given source, data volume and team skill set.

## Understand

### Three steps, two orders

Every batch pipeline does the same three jobs. **Extract** reads data from a source: an API, a file, another database. **Transform** changes it: fixes types, cleans text, removes duplicates, joins, aggregates. **Load** writes it into the target system, usually a database or warehouse. The two classic architectures differ only in the order and in where the transformation runs. In **ETL** the data is transformed *before* it reaches the target: a Python process (or a dedicated tool) reads the source, cleans it in memory, and writes only the finished rows. In **ELT** the data is loaded *first*, as it came, into the target, and the transformation then runs inside the target using its own engine, usually SQL. The abbreviations are just the order of the letters.

The pipeline for the rest of this phase is small on purpose: orders arrive as CSV text (some amounts like `$7.50` or `1,250.00`, a text amount `abc`, a status in capitals, order 3 sent twice as it changed), and the target is a table `orders_clean(order_id PRIMARY KEY, customer_id, amount_cents, currency, status, updated_at)`. The target here is `sqlite3` in memory, a stand-in for PostgreSQL (`sqlite3` is also an SQL engine, so it can run the "T" of ELT). Where PostgreSQL syntax differs (it has `DISTINCT ON`, `regexp_replace` and a `numeric` type) a `sql run` example shows it on PGlite.

### ETL in practice

ETL puts the logic in code: small Python functions such as `clean_amount`, `parse_ts` and `dedupe_latest`, which are easy to unit test and can call any library. The target receives only valid, final rows, which keeps it small and protects it from bad data. The costs are that the transformation runs on the machine that does the extraction (memory and CPU limits apply, so Day 115's pushdown arguments matter), that rows rejected before loading are gone unless you save them, and that changing a rule means re-extracting from the source, which may be slow, rate-limited or no longer available.

### ELT in practice

ELT loads the raw rows into a **staging** table with loose types (everything as text) and then runs SQL inside the database. The database engine is built for set-based work on large tables, the transformation logic lives next to the data, analysts who know SQL can read and change it, and the raw copy stays available. When a rule changes, you rerun the SQL on the stored raw data without calling the source again. The costs are that you need a database that scales, that raw data (including bad data and personal data) now sits in the target and needs access control, and that SQL is harder to unit test line by line than Python functions. Modern cloud warehouses made ELT the default because storage and compute there are cheap and elastic.

### Staging and layers

A **layer** is a stage of refinement, usually a schema or a set of tables. The common names are **raw** (or bronze): an untouched copy of what arrived, all text, with load metadata; **clean** (or staging/silver): typed, deduplicated and validated rows, one row per business key, which is `orders_clean` here; and **mart** (or gold): aggregates shaped for a report, such as daily revenue. Each layer is built only from the one before it. The rule that makes layers useful is that you never edit the raw layer: if clean is wrong you drop and rebuild it from raw, which is safe, repeatable and traceable.

### Choosing

Use ETL when the transformation needs code the database cannot run (custom parsing, calls to services), when sensitive data must be removed before it reaches the target, or when the target is small or expensive. Use ELT when the target has a capable SQL engine, volumes are large, requirements change often, or you want raw data kept for reprocessing. Most real systems are mixed: light cleaning in code at the edge, heavy modelling in SQL inside the warehouse. The misconception to drop is that one is "modern" and the other "old": the choice is about where the work is cheapest and safest.

### Why it matters in data work

The architecture decides how you test, how you recover from a mistake and what data you hold. If you can rebuild clean from raw, a wrong rule is a fix and a rerun. If you only kept the transformed rows, a wrong rule is a data loss.

## Syntax and key functions

An ELT transform in PostgreSQL syntax (shown as a template; the PGlite example below runs it):

```sql-syntax
CREATE TABLE orders_clean AS
SELECT DISTINCT ON (order_id)
       order_id::int, customer_id::int,
       round(NULLIF(regexp_replace(amount, '[^0-9.]', '', 'g'), '')::numeric * 100)::int AS amount_cents,
       upper(currency) AS currency, lower(trim(status)) AS status, updated_at
FROM stg_orders
WHERE NULLIF(regexp_replace(amount, '[^0-9.]', '', 'g'), '') IS NOT NULL
ORDER BY order_id, updated_at DESC;
```

| Item | What it does or returns |
|---|---|
| `csv.DictReader(io.StringIO(text))` | Reads CSV text as dictionaries, one per row, all values text. |
| `executemany(sql, rows)` | Loads many rows with one statement. |
| `INSERT INTO t SELECT ...` | Transforms inside the database: reads staging, writes clean. |
| `DISTINCT ON (key) ... ORDER BY key, ts DESC` | PostgreSQL: the first row per key in that order (the latest). |
| `ROW_NUMBER() OVER (...) = 1` | The portable way to keep the latest row per key. |
| `regexp_replace(text, pattern, '', 'g')` | PostgreSQL: removes every match of the pattern. |
| `round(x)::int` | Rounds a numeric and casts it to an integer. |

## Learn by example

### Example 1: ETL, transform in Python

The functions clean the rows in memory and only valid rows reach `orders_clean`. Rejected rows are returned, not lost: the pipeline keeps them for inspection.

```python run
import csv
import io
import sqlite3
from datetime import datetime, timezone

def extract(text):
    return list(csv.DictReader(io.StringIO(text)))

def clean_amount(text):
    """'$1,250.00' -> 125000 (cents); None when the text is not a number."""
    cleaned = text.replace("$", "").replace(",", "").strip()
    try:
        return round(float(cleaned) * 100)
    except ValueError:
        return None

def parse_ts(text):
    """ISO 8601 with Z -> normalised UTC text 'YYYY-MM-DDTHH:MM:SSZ'."""
    parsed = datetime.fromisoformat(text.replace("Z", "+00:00")).astimezone(timezone.utc)
    return parsed.strftime("%Y-%m-%dT%H:%M:%SZ")

def dedupe_latest(rows):
    latest = {}
    for row in rows:
        key = row["order_id"]
        if key not in latest or row["updated_at"] >= latest[key]["updated_at"]:
            latest[key] = row
    return [latest[key] for key in sorted(latest)]

def transform(raw_rows):
    good, rejected = [], []
    for r in raw_rows:
        cents = clean_amount(r["amount"])
        if cents is None:
            rejected.append((r["order_id"], "bad amount"))
            continue
        good.append({"order_id": int(r["order_id"]), "customer_id": int(r["customer_id"]), "amount_cents": cents,
                     "currency": r["currency"].upper(), "status": r["status"].strip().lower(),
                     "updated_at": parse_ts(r["updated_at"])})
    return dedupe_latest(good), rejected

def open_db():
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, currency TEXT, status TEXT, updated_at TEXT)""")
    return conn

def load(conn, rows):
    conn.executemany("INSERT INTO orders_clean VALUES (:order_id,:customer_id,:amount_cents,:currency,:status,:updated_at)", rows)

RAW = """order_id,customer_id,amount,currency,status,updated_at
1,10,19.90,EUR,paid,2025-03-01T10:00:00Z
2,11,"1,250.00",EUR,PAID,2025-03-01T11:30:00Z
3,10,40.00,EUR,paid,2025-03-02T09:00:00Z
3,10,45.00,EUR,refunded,2025-03-03T08:00:00Z
4,12,abc,USD,paid,2025-03-02T12:00:00Z
5,13,$7.50,USD,failed,2025-03-03T15:45:00Z
6,11,12.00,EUR,paid,2025-03-04T07:15:00Z
"""

raw_rows = extract(RAW)
good, rejected = transform(raw_rows)
conn = open_db()
load(conn, good)
print("read", len(raw_rows), "loaded", conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0], "rejected", rejected)
for row in conn.execute("SELECT order_id, amount_cents, status FROM orders_clean ORDER BY order_id"):
    print(row)
```

```output
read 7 loaded 5 rejected [('4', 'bad amount')]
(1, 1990, 'paid')
(2, 125000, 'paid')
(3, 4500, 'refunded')
(5, 750, 'failed')
(6, 1200, 'paid')
```
### Example 2: ELT, transform in SQL

The same CSV is loaded as text into a staging table without any change, and one `INSERT ... SELECT` does the cleaning in the database. `GLOB '[0-9]*'` is a rough numeric guard that rejects `abc`; real validation would be stricter. The result is compared with the ETL result.

```output
staging rows: 7 clean rows: 5
same as ETL: True
```
### Example 3: ELT on PostgreSQL syntax (PGlite)

The staging table holds raw text. `DISTINCT ON` keeps the latest row per order, `regexp_replace` removes `$` and thousands separators and `NULLIF(..., '')` turns the empty result of `abc` into NULL so that the row is filtered out. `numeric` is exact, and the amounts become integer cents.

```sql run
CREATE TABLE stg_orders (order_id text, customer_id text, amount text, currency text, status text, updated_at text);
INSERT INTO stg_orders VALUES ('1','10','19.90','EUR','paid','2025-03-01T10:00:00Z'), ('2','11','1,250.00','EUR','PAID','2025-03-01T11:30:00Z'),
  ('3','10','40.00','EUR','paid','2025-03-02T09:00:00Z'), ('3','10','45.00','EUR','refunded','2025-03-03T08:00:00Z'),
  ('4','12','abc','USD','paid','2025-03-02T12:00:00Z'), ('5','13','$7.50','USD','failed','2025-03-03T15:45:00Z'),
  ('6','11','12.00','EUR','paid','2025-03-04T07:15:00Z');
SELECT DISTINCT ON (order_id::int) order_id::int AS order_id,
       round(NULLIF(regexp_replace(amount, '[^0-9.]', '', 'g'), '')::numeric * 100)::int AS amount_cents,
       lower(trim(status)) AS status
FROM stg_orders
WHERE NULLIF(regexp_replace(amount, '[^0-9.]', '', 'g'), '') IS NOT NULL
ORDER BY order_id::int, updated_at DESC;
```

```output
order_id | amount_cents | status
1 | 1990 | paid
2 | 125000 | paid
3 | 4500 | refunded
5 | 750 | failed
6 | 1200 | paid
```

### Example 5: Rebuild clean from raw after a rule change

    if drop_failed:

    conn.execute("DROP TABLE orders_clean")

    return conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0]

print("old rule:", rebuild_clean(conn, False))

## Real-world applications

- **Warehouse loading.** Cloud data teams land raw extracts in a warehouse and model them in SQL layers (Examples 2 to 4), so analysts can change business rules without touching extraction code.
- **Sensitive data at the edge.** When a source contains personal data that must not reach the analytics database, ETL removes or masks it in code before loading, as in Example 1.
- **Rule changes and audits.** Keeping raw lets a team rebuild the clean layer after a rule change or an audit question (Example 5) without asking the source system to resend history.
- **API pipelines.** The orders API route used light ETL at the edge (parsing, types) and SQL after loading, which is the mixed design most teams end with.

## Daily review

### Key takeaways

- ETL transforms before loading; ELT loads raw data first and transforms inside the target.
- Layers (raw, clean, mart) are built in order, and raw is never edited.
- A rebuild of a derived layer from raw is the safe way to fix a rule.
- Choose by where the work is cheapest and safest, not by fashion; most systems mix both.

### Common mistakes

- Transforming in the loader and keeping no raw copy, so a wrong rule means asking the source again, if it still has the data. Keep raw.
- Loading raw data into a table with strict types and constraints, so the first bad row fails the whole load. Stage as text, validate afterwards.
- Casting text to a number without a guard: in SQLite `CAST('abc' AS REAL)` is 0.0 and quietly wrong, and in PostgreSQL `''::numeric` raises an error. Check first and send failures to a reject list.
- Editing the clean table by hand, which the next rebuild overwrites. Fix the rule, not the data.
- Calling any pipeline with SQL in it ELT: ELT means the raw data was loaded into the target before it was transformed.

### Revision notes

- ETL: transform in code, load results. ELT: load raw, transform in SQL.
- Layers: raw, clean (typed, deduplicated), mart (aggregates).
- Keep raw; rebuild derived layers; stage as text.
- Latest per key: `ROW_NUMBER() ... = 1` or PostgreSQL `DISTINCT ON`.

## Objectives

- Summarise a whole table or a filtered set of rows with `COUNT`, `SUM`, `AVG`, `MIN` and `MAX`.
- Explain the difference between `COUNT(*)`, `COUNT(column)` and `COUNT(DISTINCT column)`, and predict each result when the column contains NULL.
- Predict what each aggregate returns for an empty set of rows and for a column with NULLs.
- Use `ROUND` and a cast to `numeric` to produce stable, readable aggregate values.
- Combine `WHERE` with aggregates to answer one-number business questions such as total revenue for a year.

## Understand

### From many rows to one row

Until now every query returned one output row for each input row that survived `WHERE`. An **aggregate function** works differently: it reads many rows and returns a single value that summarises them. `COUNT` says how many rows there are, `SUM` adds a column up, `AVG` takes the mean, and `MIN` and `MAX` find the smallest and largest value. Think of a till at the end of the day. You do not want a list of every sale, you want the number of sales, the total takings and the biggest single sale. An aggregate query is that end-of-day summary.

A query that contains an aggregate and no `GROUP BY` treats the whole set of surviving rows as one group and produces exactly one row. This is why `SELECT product_name, COUNT(*) FROM products` is an error: one row cannot hold 77 product names next to a single count. Without a grouping clause, every column in the select list must be an aggregate (or a constant). Day 37 adds `GROUP BY`, which lets you produce one summary row per group instead of one for the whole table.

### Where aggregates sit in the order of work

The logical order is `FROM`, then `WHERE`, then the aggregate, then `SELECT`. `WHERE` runs first, so `SELECT SUM(freight) FROM orders WHERE order_date >= '1998-01-01'` adds up only the 1998 orders. You cannot write an aggregate inside `WHERE` (`WHERE freight > AVG(freight)` is an error), because the aggregate needs the finished set of rows and `WHERE` is the step that decides which rows those are. Day 37 explains the clause that filters on aggregate results, and day 43 shows the subquery that solves the "above average" question.

### The five core aggregates

`COUNT(*)` counts rows. `SUM(x)` adds the values of `x`; it works on numbers only. `AVG(x)` returns the mean of `x`; for integers and numerics it returns a `numeric` with many decimal places, so wrap it in `ROUND(AVG(x), 2)` for reports. `MIN(x)` and `MAX(x)` work on numbers, text and dates: the smallest and largest number, the first and last text in alphabetical order, the earliest and latest date. `MIN(order_date)` is the date of the first order and `MAX(order_date)` the date of the last.

### How aggregates treat NULL

This is the most important rule of the day, and it builds on day 35. **Every aggregate except `COUNT(*)` ignores NULL values.** `SUM`, `AVG`, `MIN`, `MAX` and `COUNT(column)` skip rows where the column is NULL as if those rows were not there. Two consequences follow.

First, `COUNT(*)` and `COUNT(column)` can differ. `COUNT(*)` counts rows no matter what they contain. `COUNT(shipped_date)` counts only the rows whose `shipped_date` is not NULL, which is a handy way to count "how many have a value". In Northwind, 100 orders exist and 85 have a ship date, so the two counts are 100 and 85.

Second, `AVG` is the sum of the non-NULL values divided by the number of non-NULL values. It is not the sum divided by the number of rows. The average of 1, 2 and NULL is 1.5, not 1. If a missing value really means zero, you must say so with `COALESCE(x, 0)` inside the aggregate; whether that is right depends on what the NULL means, and the two choices give different averages (example 4 shows this).

When there are no rows at all (for example `WHERE` removed every row) `COUNT` returns 0 but `SUM`, `AVG`, `MIN` and `MAX` return NULL, not 0. A report that must show 0 needs `COALESCE(SUM(x), 0)`.

### DISTINCT inside an aggregate

`COUNT(DISTINCT customer_id)` counts how many different customers appear, ignoring repeats and NULLs. The 100 orders belong to only 89 different customers, so `COUNT(customer_id)` is 100 and `COUNT(DISTINCT customer_id)` is 89. `DISTINCT` also works inside `SUM` and `AVG` (`SUM(DISTINCT x)` adds each distinct value once), but this is rarely what you want and is a common source of wrong totals. Do not confuse it with `SELECT DISTINCT` from day 34, which removes duplicate output rows; here `DISTINCT` acts on the values going into one aggregate.

### Common misconception

Many learners believe `COUNT(column)` and `COUNT(*)` are interchangeable and that `AVG` "counts NULL as zero". Neither is true. When a count looks too low or an average looks too high, check the column for NULLs.

### Why it matters

Almost every business metric is an aggregate: number of orders, total revenue, average basket, first and last activity. Getting NULL behaviour and the `DISTINCT` rules right is the difference between a dashboard figure that reconciles with finance and one that does not.

## Syntax and key functions

An aggregate query without grouping returns one row:

```sql-syntax
SELECT aggregate_1(expression), aggregate_2(expression)
FROM table_name
WHERE condition;
```

The `COUNT` forms and `DISTINCT` inside an aggregate:

```sql-syntax
COUNT(*)                 -- rows
COUNT(column)            -- rows where column is not NULL
COUNT(DISTINCT column)   -- different non-NULL values
```

Stable numeric output. `real` columns need a cast to `numeric` before `ROUND(value, digits)` works (day 32):

```sql-syntax
ROUND(SUM(unit_price * quantity * (1 - discount::numeric)), 2)
```

| Function | Returns | NULL handling |
|---|---|---|
| `COUNT(*)` | Number of rows | Counts every row |
| `COUNT(x)` | Number of rows where `x` is not NULL | Skips NULLs; 0 for no rows |
| `COUNT(DISTINCT x)` | Number of distinct non-NULL values | Skips NULLs |
| `SUM(x)` | Total of `x` | Skips NULLs; NULL for no rows |
| `AVG(x)` | Mean of the non-NULL values | Skips NULLs; NULL for no rows |
| `MIN(x)`, `MAX(x)` | Smallest and largest value (numbers, text, dates) | Skips NULLs; NULL for no rows |

## Learn by example

### Example 1: COUNT(*) against COUNT(column)

Three counts on the same table. `COUNT(*)` counts all 100 orders. `COUNT(shipped_date)` skips the orders without a ship date, and `COUNT(employee_id)` skips the single order with no employee (day 35). The unshipped orders are the ones with a NULL date, and the arithmetic matches: 100 - 85 = 15.

```sql run
SELECT COUNT(*) AS all_orders,
       COUNT(shipped_date) AS shipped,
       COUNT(employee_id) AS with_employee
FROM orders;
```

```output
all_orders | shipped | with_employee
100 | 85 | 99
```

### Example 2: The five aggregates together

One query can hold several aggregates, and they all read the same filtered rows. Here the whole `orders` table is summarised. `ROUND(..., 2)` keeps the average readable, and the `MIN` and `MAX` of a date column give the first and last order dates.

```sql run
SELECT COUNT(*) AS orders,
       SUM(freight) AS total_freight,
       ROUND(AVG(freight), 2) AS avg_freight,
       MIN(order_date) AS first_order,
       MAX(order_date) AS last_order
FROM orders;
```

```output
orders | total_freight | avg_freight | first_order | last_order
100 | 9851.61 | 98.52 | 1996-01-01 | 1998-12-28
```

### Example 3: Counting distinct values

`COUNT(customer_id)` counts orders, but `COUNT(DISTINCT customer_id)` counts the customers who placed them. The third column counts countries that orders were shipped to. Compare the first two numbers to see how much `DISTINCT` changes the answer.

```sql run
SELECT COUNT(customer_id) AS orders_with_customer,
       COUNT(DISTINCT customer_id) AS distinct_customers,
       COUNT(DISTINCT ship_country) AS ship_countries
FROM orders;
```

```output
orders_with_customer | distinct_customers | ship_countries
100 | 89 | 21
```

### Example 4: AVG ignores NULL

The expression `shipped_date - order_date` subtracts two dates and gives the number of days (day 39 covers date arithmetic properly). For unshipped orders it is NULL, so the first average uses 85 values. The second average replaces NULL with 0 first, so it divides by 100 and is lower. Neither is automatically right: the first answers "how long do shipped orders take", the second invents zero-day shipments for orders that have not shipped.

```sql run
SELECT COUNT(shipped_date - order_date) AS values_used,
       ROUND(AVG(shipped_date - order_date), 2) AS avg_days_shipped_only,
       ROUND(AVG(COALESCE(shipped_date - order_date, 0)), 2) AS avg_days_null_as_zero
FROM orders;
```

```output
values_used | avg_days_shipped_only | avg_days_null_as_zero
85 | 5.65 | 4.80
```

### Example 5: An empty set

`WHERE` removes every row, because no order is dated after 2000. `COUNT` still returns a number (0), but `SUM` and `MAX` have nothing to summarise and return NULL. `COALESCE` turns the NULL sum into 0 for a report.

```sql run
SELECT COUNT(*) AS orders,
       SUM(freight) AS total_freight,
       COALESCE(SUM(freight), 0) AS total_or_zero,
       MAX(order_date) AS latest
FROM orders
WHERE order_date > '2000-01-01';
```

```output
orders | total_freight | total_or_zero | latest
0 | NULL | 0 | NULL
```

### Example 6: A realistic revenue summary

Revenue of an order line is `unit_price * quantity * (1 - discount)`. The `discount` column is `real`, so it is cast to `numeric` before rounding to avoid floating point noise. There is no date on `order_details`, so this example summarises every line. It combines `COUNT`, `COUNT(DISTINCT ...)`, `SUM` and `ROUND` in one row: how many lines, how many different products and orders, the units sold and the revenue.

```sql run
SELECT COUNT(*) AS order_lines,
       COUNT(DISTINCT product_id) AS products_sold,
       COUNT(DISTINCT order_id) AS orders,
       SUM(quantity) AS units,
       ROUND(SUM(unit_price * quantity * (1 - discount::numeric)), 2) AS revenue
FROM order_details;
```

```output
order_lines | products_sold | orders | units | revenue
250 | 75 | 100 | 5080 | 138319.80
```

## Real-world applications

**Headline figures on a dashboard.** The orders, total and average columns of example 2 are the tiles at the top of a sales dashboard. The same query with a `WHERE` on dates gives the figure for any period.

**Data completeness checks.** Comparing `COUNT(*)` with `COUNT(column)`, as in example 1, shows how many values are missing. Analysts run this on every column of a new dataset before trusting it.

**Counting people, not events.** "How many customers bought something" is `COUNT(DISTINCT customer_id)` (example 3), while `COUNT(*)` counts orders. Mixing them up inflates customer numbers, one of the most common reporting errors.

**Revenue and unit totals for finance.** Example 6 shows the calculation finance teams reconcile: the sum of line values after discount, rounded to cents. The same shape works for margins and tax.

## Daily review

### Key takeaways

- An aggregate reads many rows and returns one value; without `GROUP BY` the whole result is one row.
- `COUNT(*)` counts rows; `COUNT(column)` counts non-NULL values; `COUNT(DISTINCT column)` counts different non-NULL values.
- `SUM`, `AVG`, `MIN` and `MAX` ignore NULL. `AVG` divides by the number of non-NULL values.
- On an empty set `COUNT` is 0 and the other aggregates are NULL.
- `WHERE` filters rows before the aggregate runs, and aggregates are not allowed inside `WHERE`.
- Cast `real` to `numeric` before `ROUND`, and round averages for display.

### Common mistakes

- Selecting a plain column next to an aggregate, for example `SELECT product_name, MAX(unit_price) FROM products`. PostgreSQL raises "column must appear in the GROUP BY clause or be used in an aggregate function". Add `GROUP BY` (day 37) or remove the column.
- Writing `WHERE freight > AVG(freight)`. PostgreSQL raises "aggregate functions are not allowed in WHERE". Compute the average in a subquery (day 43).
- Using `COUNT(column)` to count rows and getting a smaller number because of NULLs. Use `COUNT(*)`.
- Using `COUNT(*)` to count customers and getting the number of orders. Use `COUNT(DISTINCT customer_id)`.
- Assuming `AVG` treats NULL as 0. If zero is what you mean, write `AVG(COALESCE(x, 0))`.
- Calling `ROUND(AVG(discount), 2)` on a `real` column and getting an error that `round(real, integer)` does not exist. Cast with `::numeric` first.

### Revision notes

- `COUNT(*)` rows, `COUNT(x)` non-NULL, `COUNT(DISTINCT x)` distinct non-NULL.
- Every aggregate but `COUNT(*)` skips NULL; empty set gives 0 for `COUNT`, NULL for the rest.
- No `GROUP BY` means one output row and only aggregates in `SELECT`.
- Aggregates cannot appear in `WHERE`.

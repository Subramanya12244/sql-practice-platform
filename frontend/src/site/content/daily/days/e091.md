## Understand

### Why a connection is needed

PostgreSQL is a **server**: a program that runs on one machine, owns the data files and waits for requests. Your Python script is a **client**: another program, usually on a different machine, that sends requests. A **connection** is the open channel between the two. Opening one costs real time because the client must find the server by host name and port (PostgreSQL listens on port 5432 by default), prove who it is with a user name and password, and choose a database. Once it is open, the server creates a **session** for it, a private context that remembers settings and any transaction in progress. When you close the connection the session ends.

Up to now every database you used lived inside your own program, or inside the browser. A pipeline does not work that way. The data you load belongs to a shared server that other people and jobs also use, so you must open connections deliberately, use them briefly and close them.

### The standard Python database interface

Python defines one common shape for database drivers, called the **DB-API**. Whatever the database, the same four objects appear. A **driver** is the library that speaks the database's network protocol; `psycopg` is the driver for PostgreSQL and `sqlite3` is the driver for SQLite that ships with Python. A **connection** is the open channel. A **cursor** is the object you send SQL through and read results from; one connection can create many cursors. A **row** comes back as a tuple. The cycle is always the same: connect, create a cursor, `execute` a statement, `fetchone`, `fetchmany` or `fetchall` to read rows, `commit` to make changes permanent, and `close`.

Because every driver follows this shape, code that works with `sqlite3` teaches you the structure of code that works with `psycopg`. Two details differ and you must remember them. First, the **placeholder** style: `sqlite3` marks a value with `?` while `psycopg` uses `%s` (a literal percent sign is then written `%%`). Second, `sqlite3` is typed loosely and has no server, no user names and no network, so it cannot show you connection errors or PostgreSQL types. Treat it as a faithful model of the call sequence and nothing more.

### Parameters, never string building

A **parameterised query** keeps the SQL text and the values apart. You write the statement once with placeholders and pass the values separately: `cur.execute("SELECT * FROM city WHERE name = ?", (name,))`. The driver sends the values as data, so a value can never change what the statement means. If instead you join the text yourself with an f-string, a value such as `x' OR '1'='1` becomes part of the SQL and returns every row. This attack is called **SQL injection**, and it is also how innocent values such as the name `O'Brien` break a query. Only values can be parameters. Table and column names cannot, so a pipeline that chooses a table dynamically must check the name against a fixed list it controls.

### Transactions and connection handling

A **transaction** is a group of statements that succeed or fail together. A DB-API connection opens a transaction automatically at your first statement and keeps it open until you call `commit()`, which saves everything, or `rollback()`, which discards everything since the last commit. Forgetting `commit()` is the classic first bug: the script prints the right rows, ends, and the table is empty because the changes were rolled back when the connection closed.

A `with` block makes this safer. In `psycopg` (version 3) `with psycopg.connect(...) as conn:` commits when the block ends normally, rolls back when an exception escapes, and then closes the connection. The `sqlite3` stand-in differs: `with conn:` commits or rolls back but does **not** close, so closing needs `contextlib.closing`. A connection that is never closed is a **leak**, and a server accepts only a limited number of connections, so many leaks lock everyone out.

### SQLAlchemy engines

**SQLAlchemy** is a library that sits above drivers. Its central object is the **engine**, created with `create_engine(url)`. An engine is not one connection. It is a factory that holds a **connection pool**, a small set of open connections that are reused, so your code does not pay the opening cost each time. Creating the engine opens nothing; the first `engine.connect()` does. You run SQL with `conn.execute(text("... WHERE id = :id"), {"id": 7})`, where `text()` marks a string as SQL and `:id` is a named placeholder that SQLAlchemy translates into the driver's own style. `with engine.begin() as conn:` opens a transaction that commits on success and rolls back on error. `pandas.read_sql` and `DataFrame.to_sql` accept an engine, which is why engines appear in every pipeline.

The **URL** names everything the connection needs: `postgresql+psycopg://user:password@host:5432/database`. The part before `://` selects the dialect and driver. A plain libpq connection string, the format `psycopg` also accepts, looks like `postgresql://user:password@host:5432/database` or `host=... dbname=...`.

### Credentials stay out of the code

A password written in a script is copied into version control, into logs and onto every laptop that clones the project. The standard fix is to read secrets from **environment variables**, values the operating system gives to a process when it starts. In Python, `os.environ["PGPASSWORD"]` reads one and raises `KeyError` when it is missing, which is the correct behaviour: a pipeline should stop with a clear message rather than guess. PostgreSQL's own tools also read the variables `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER` and `PGPASSWORD`. Local `.env` files are fine if they are listed in `.gitignore`. When you print a connection string for debugging, hide the password first.

### Common misconception

Learners often believe `create_engine` connects to the database, so a typing mistake in the host should fail on that line. It does not: it only records settings. The error appears at the first query. Another frequent belief is that `with sqlite3.connect(...) as conn` closes the connection; it only controls the transaction.

### Why it matters

Every ingestion job begins with a connection and ends with a commit. Parameterised queries protect the warehouse from bad input, short transactions keep tables unlocked for other users, and environment variables let the same code run on a laptop, in a test and in production with different servers.

## Syntax and key functions

The DB-API sequence, shown with `psycopg` and a PostgreSQL server (not run in the browser, because there is no server):

```python
import os
import psycopg

with psycopg.connect(
    host=os.environ["PGHOST"],
    dbname=os.environ["PGDATABASE"],
    user=os.environ["PGUSER"],
    password=os.environ["PGPASSWORD"],
) as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT id, name FROM city WHERE country = %s", ("Norway",))
        rows = cur.fetchall()
```

`psycopg.connect` opens the connection; the outer `with` commits or rolls back and closes it. The values travel in the tuple and `%s` marks each place. `cur.fetchall()` returns a list of tuples.

The same call sequence on the `sqlite3` stand-in:

```python
import sqlite3
conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.execute("SELECT id, name FROM city WHERE country = ?", ("Norway",))
rows = cur.fetchall()
conn.commit()
conn.close()
```

The SQLAlchemy form, again for PostgreSQL:

```python
import os
from sqlalchemy import create_engine, text

engine = create_engine(os.environ["DATABASE_URL"])   # e.g. postgresql+psycopg://user:pw@host:5432/db
with engine.begin() as conn:
    result = conn.execute(text("SELECT id, name FROM city WHERE country = :c"), {"c": "Norway"})
    rows = result.fetchall()
```

| Name | What it does or returns |
|---|---|
| `connect(...)` | Opens a connection (`psycopg.connect` or `sqlite3.connect`). |
| `conn.cursor()` | Returns a cursor for sending SQL. |
| `cur.execute(sql, params)` | Runs one statement; `params` is a tuple (or a dict for named styles). |
| `cur.fetchone()`, `fetchmany(n)`, `fetchall()` | One tuple or `None`, a list of up to `n` tuples, or a list of all remaining tuples. |
| `cur.rowcount` | Rows changed by the last statement (`-1` when unknown, as after a `SELECT` in `sqlite3`). |
| `cur.description` | One entry per column; item `[0]` is the column name. |
| `conn.commit()`, `conn.rollback()` | Save or discard the open transaction. |
| `create_engine(url)` | Builds an engine and pool; opens nothing yet. |
| `text(sql)` | Marks a string as SQL with `:name` placeholders. |
| `engine.begin()` / `engine.connect()` | A transaction that commits on success / a connection that you commit yourself. |
| `make_url(url)` | Parses a URL without connecting; printing it hides the password. |

## Learn by example

### Example 1: Connect, execute, fetch, commit

This runs on `sqlite3` in memory. It follows the full DB-API cycle. `description` gives the column names, `rowcount` the rows inserted, and `fetchall` the result.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.execute("CREATE TABLE city (id INTEGER PRIMARY KEY, name TEXT, country TEXT)")
cur.execute("INSERT INTO city (name, country) VALUES (?, ?)", ("Oslo", "Norway"))
print("inserted:", cur.rowcount)
cur.execute("INSERT INTO city (name, country) VALUES (?, ?)", ("Bergen", "Norway"))
conn.commit()

cur.execute("SELECT id, name, country FROM city ORDER BY id")
print([c[0] for c in cur.description])
print(cur.fetchone())
print(cur.fetchall())
conn.close()
```

```output
inserted: 1
['id', 'name', 'country']
(1, 'Oslo', 'Norway')
[(2, 'Bergen', 'Norway')]
```

### Example 2: Why parameters matter

The unsafe query pastes the text into the SQL, so the attacker's quote closes the string and the condition `'1'='1'` is always true. The parameterised query treats the same text as a plain value and finds nothing. The unsafe version appears here only to show the failure.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE city (name TEXT, country TEXT)")
for row in [("Oslo", "Norway"), ("Lyon", "France"), ("Turin", "Italy")]:
    conn.execute("INSERT INTO city VALUES (?, ?)", row)

evil = "x' OR '1'='1"
unsafe = f"SELECT name FROM city WHERE name = '{evil}'"
print(unsafe)
print("unsafe rows:", len(conn.execute(unsafe).fetchall()))
print("safe rows:", len(conn.execute("SELECT name FROM city WHERE name = ?", (evil,)).fetchall()))

# a value with an apostrophe is harmless as a parameter
conn.execute("INSERT INTO city VALUES (?, ?)", ("O'Brien Town", "Ireland"))
print(conn.execute("SELECT name FROM city WHERE country = ?", ("Ireland",)).fetchone())
conn.close()
```

```output
SELECT name FROM city WHERE name = 'x' OR '1'='1'
unsafe rows: 3
safe rows: 0
("O'Brien Town",)
```

### Example 3: Transactions and the `with` block

A transaction ends in `commit` or `rollback`. In `sqlite3`, `with conn:` commits on success and rolls back when an exception leaves the block, then lets the exception continue. The `try` below catches it so the script goes on. `contextlib.closing` closes the connection at the end, which `with conn:` does not do.

```python run
import sqlite3
from contextlib import closing

with closing(sqlite3.connect(":memory:")) as conn:
    conn.execute("CREATE TABLE city (name TEXT PRIMARY KEY)")
    with conn:
        conn.execute("INSERT INTO city VALUES (?)", ("Oslo",))
    print("after first block:", conn.execute("SELECT COUNT(*) FROM city").fetchone()[0])

    try:
        with conn:
            conn.execute("INSERT INTO city VALUES (?)", ("Bergen",))
            conn.execute("INSERT INTO city VALUES (?)", ("Oslo",))   # duplicate key
    except sqlite3.IntegrityError as err:
        print("error:", err)
    print("after failed block:", conn.execute("SELECT COUNT(*) FROM city").fetchone()[0])

    conn.execute("INSERT INTO city VALUES (?)", ("Tromso",))
    conn.rollback()
    print("after rollback:", conn.execute("SELECT COUNT(*) FROM city").fetchone()[0])
```

```output
after first block: 1
error: UNIQUE constraint failed: city.name
after failed block: 1
after rollback: 1
```

### Example 4: Credentials from environment variables

A pipeline should build its connection settings from variables and fail clearly when one is missing. This function takes a dictionary so it can be tested; in a real job you would pass `os.environ`. The helper `mask` hides the password before anything is printed.

```python run
def build_url(env):
    needed = ["PGHOST", "PGDATABASE", "PGUSER", "PGPASSWORD"]
    missing = [name for name in needed if name not in env]
    if missing:
        raise KeyError("missing environment variables: " + ", ".join(missing))
    port = env.get("PGPORT", "5432")
    return f"postgresql+psycopg://{env['PGUSER']}:{env['PGPASSWORD']}@{env['PGHOST']}:{port}/{env['PGDATABASE']}"

def mask(url, password):
    return url.replace(password, "***")

env = {"PGHOST": "db.example.com", "PGDATABASE": "warehouse", "PGUSER": "etl", "PGPASSWORD": "s3cret"}
url = build_url(env)
print(mask(url, env["PGPASSWORD"]))

try:
    build_url({"PGHOST": "db.example.com"})
except KeyError as err:
    print(err.args[0])
```

```output
postgresql+psycopg://etl:***@db.example.com:5432/warehouse
missing environment variables: PGDATABASE, PGUSER, PGPASSWORD
```

### Example 5: A SQLAlchemy engine

This needs the `sqlalchemy` package, which the browser does not have, so it is a local example. The engine uses `sqlite://` (in-memory SQLite) as a stand-in for `postgresql+psycopg://`. `make_url` parses a PostgreSQL URL without connecting and without needing the driver, and printing it hides the password. `engine.begin()` commits on success. An in-memory SQLite database disappears with its connection, so SQLAlchemy reuses one connection for it; a PostgreSQL engine would pool several.

```python local
import pandas as pd
from sqlalchemy import create_engine, text
from sqlalchemy.engine import make_url

print(make_url("postgresql+psycopg://etl:s3cret@db.example.com:5432/warehouse"))

engine = create_engine("sqlite://")
with engine.begin() as conn:
    conn.execute(text("CREATE TABLE city (id INTEGER PRIMARY KEY, name TEXT, country TEXT)"))
    conn.execute(
        text("INSERT INTO city (name, country) VALUES (:name, :country)"),
        [{"name": "Oslo", "country": "Norway"}, {"name": "Bergen", "country": "Norway"}, {"name": "Lyon", "country": "France"}],
    )

with engine.connect() as conn:
    rows = conn.execute(text("SELECT name FROM city WHERE country = :c ORDER BY name"), {"c": "Norway"}).fetchall()
    print(rows)
    print(pd.read_sql(text("SELECT country, COUNT(*) AS n FROM city GROUP BY country ORDER BY country"), conn))
engine.dispose()
```

```output
postgresql+psycopg://etl:***@db.example.com:5432/warehouse
[('Bergen',), ('Oslo',)]
  country  n
0  France  1
1  Norway  2
```

### Example 6: What the server sees: `$1` parameters

On PostgreSQL, a parameterised query is sent as statement text with numbered slots (`$1`, `$2`) and the values separately. SQL's `PREPARE` shows the same idea directly. This runs on PGlite, a real PostgreSQL engine compiled for the browser. `psycopg` and SQLAlchemy do this work for you; here you see the server's side of it.

```sql run
CREATE TEMP TABLE city (name text, country text);
INSERT INTO city VALUES ('Oslo', 'Norway'), ('Bergen', 'Norway'), ('Lyon', 'France');
PREPARE by_country (text) AS
  SELECT name FROM city WHERE country = $1 ORDER BY name;
EXECUTE by_country('Norway');
```

```output
name
Bergen
Oslo
```

## Real-world applications

- **Pipeline entry points.** Every load script in this phase starts like Example 4 and Example 1: read settings from variables, connect, work inside a transaction and close. The same code runs against a test database and the production one by changing only the environment.
- **Safe dynamic filters.** A job that loads one customer file per run takes the file name or an identifier from a scheduler. Passing it as a parameter, as in Example 2, keeps a malformed value from damaging the load or deleting data.
- **Shared servers.** A warehouse accepts a limited number of connections. Short transactions (Example 3), closed connections and one pooled engine per process (Example 5) keep your job from blocking dashboards and colleagues.
- **Pandas into the database.** `read_sql` and `to_sql` need an engine or a connection. Writing a DataFrame to a table with `to_sql` uses exactly the engine from Example 5.

## Daily review

### Key takeaways

- A connection is an open session with a server; open it late, use it briefly and close it.
- The DB-API cycle is connect, cursor, execute, fetch, commit, close, and it is the same for every driver. Placeholders differ: `%s` for `psycopg`, `?` for `sqlite3`, `:name` for SQLAlchemy `text()`.
- Always pass values as parameters. Only values can be parameters, never table or column names.
- Changes are lost unless the transaction is committed; a `with` block commits or rolls back for you, and `sqlite3` still needs `closing` to close.
- `create_engine` opens nothing and manages a pool. Credentials come from environment variables and are masked before printing.

### Common mistakes

- Forgetting `conn.commit()`: the script runs without errors, but the table is empty afterwards. Commit, or use a `with` block.
- Using `%s` on `sqlite3` or `?` on `psycopg`. SQLite raises `sqlite3.OperationalError: near "%": syntax error`, and `psycopg` reports a syntax error at or near `?`.
- Passing a single value without a tuple: `execute(sql, ("Oslo"))` passes the string `"Oslo"`, which is read as four values and raises `ProgrammingError: Incorrect number of bindings supplied`. Write `("Oslo",)`.
- Building SQL with an f-string. It works in testing and returns every row (or an error on `O'Brien`) when the input is hostile or merely unusual.
- Putting a password in a script or committing a `.env` file. Move it to an environment variable and add the file to `.gitignore`.
- Expecting `create_engine` to raise on a wrong host. It raises on the first `connect` or `execute`.

### Revision notes

- `psycopg.connect(...)`, `conn.cursor()`, `cur.execute(sql, (v,))`, `fetchall()`, `commit()`, `close()`.
- `%s` (psycopg), `?` (sqlite3), `:name` with `text()` (SQLAlchemy), `$1` (what the server sees).
- `with psycopg.connect() as conn` commits or rolls back and closes; `with sqlite3 conn` does not close.
- `postgresql+psycopg://user:password@host:5432/database`; read secrets with `os.environ[...]`.

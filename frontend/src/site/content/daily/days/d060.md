## Understand

### Transactions and ACID

A **transaction** is a group of statements that the database treats as one unit of work. The classic case is a bank transfer: subtract 100 from account A and add 100 to account B. If the system fails between the two steps, money has vanished. A transaction guarantees that either both steps happen or neither does. The guarantees are summarised as **ACID**:

- **Atomicity**: all statements of the transaction take effect, or none do. A failure in the middle undoes the earlier steps.
- **Consistency**: a transaction moves the database from one valid state to another. Constraints (day 45) such as `CHECK (balance >= 0)` or foreign keys are enforced, and a transaction that violates one is rejected.
- **Isolation**: concurrent transactions do not see each other's half-finished work. PostgreSQL's default level, `READ COMMITTED`, shows a transaction only data that other transactions have committed.
- **Durability**: once `COMMIT` returns, the change survives a crash, because it is written to the write-ahead log on disk first.

### BEGIN, COMMIT and ROLLBACK

`BEGIN` starts a transaction. The statements that follow are tentative: only your session sees them. `COMMIT` makes them permanent and visible to others. `ROLLBACK` throws them all away. Without `BEGIN`, PostgreSQL runs every statement in its own automatic transaction, which is committed at once (autocommit). If a statement fails inside an explicit transaction, PostgreSQL marks the transaction as aborted and refuses further statements until you `ROLLBACK`. A `SAVEPOINT` marks a point inside a transaction to which you can roll back without abandoning the whole transaction.

The SQL runner in this course wraps every run in a transaction that it always rolls back, and it forbids `BEGIN`, `COMMIT` and `ROLLBACK`, so these three commands are shown in plain code blocks that are not executed. The Python example below demonstrates atomicity for real, with the standard library `sqlite3` database, in memory.

### Views

A **view** is a saved query with a name. `CREATE VIEW customer_revenue AS SELECT ...` stores the query text, and every time you `SELECT` from the view the database runs it against the current data. A view holds no data of its own. Use views to name a complicated query once, to give analysts a stable, simplified shape of the data, and to hide columns (for instance by exposing only some columns of a table). Changes to the underlying tables show up immediately in the view.

### Materialised views

A **materialised view** stores the result of the query as data on disk, like a table that remembers how it was produced. Reading it is as fast as reading a table, which is valuable when the query is expensive, but the stored result goes **stale** when the underlying tables change. `REFRESH MATERIALIZED VIEW name` runs the query again and replaces the stored result. Choose a plain view for always-current data and cheap queries, and a materialised view for heavy aggregations that can tolerate some delay, refreshed on a schedule. Examples 2 and 3 show a stale and a refreshed materialised view.

### Common misconception

People think a view makes a query faster, because a view looks like a table. A plain view only saves typing; the database still runs its query each time, and the planner treats it as part of the outer query. Only a materialised view stores results, at the price of staleness. Another misconception is that `ROLLBACK` can undo a committed transaction; once committed, only a new statement can reverse the change.

### Why it matters

Any workflow that changes several tables, such as loading orders, moving stock or posting payments, must be atomic or the data becomes inconsistent. And analytics teams rely on views and materialised views to publish stable, tested definitions of business metrics.

## Syntax and key functions

Transaction control. These statements are shown but not executed here, because the runner manages the transaction itself:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- make both changes permanent
-- or: ROLLBACK;   -- undo both changes
```

```sql
BEGIN;
SAVEPOINT before_risky_step;
-- ... a statement that might fail ...
ROLLBACK TO SAVEPOINT before_risky_step;   -- undo only back to the savepoint
COMMIT;
```

```sql-syntax
CREATE [OR REPLACE] VIEW view_name AS select_query;
DROP VIEW view_name;

CREATE MATERIALIZED VIEW view_name AS select_query;
REFRESH MATERIALIZED VIEW view_name;
DROP MATERIALIZED VIEW view_name;
```

| Item | Meaning |
|---|---|
| `BEGIN` / `COMMIT` / `ROLLBACK` | Start, make permanent, undo a transaction |
| `SAVEPOINT name` | Partial rollback point inside a transaction |
| ACID | Atomicity, Consistency, Isolation, Durability |
| View | Named query, always current, stores no data |
| Materialised view | Stored result, fast to read, stale until refreshed |
| `REFRESH MATERIALIZED VIEW` | Recompute the stored result |

## Learn by example

### Example 1: create a view and query it

Both statements run in one block: the view `customer_revenue` is created and then used like a table. It exists only inside this run, because the runner rolls the transaction back, so you can run the example again without a conflict. The view stores the query, not the numbers.

```sql run
CREATE VIEW customer_revenue AS
SELECT o.customer_id,
       ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 2) AS revenue
FROM orders AS o
JOIN order_details AS od ON od.order_id = o.order_id
GROUP BY o.customer_id;

SELECT customer_id, revenue
FROM customer_revenue
ORDER BY revenue DESC, customer_id
LIMIT 5;
```

```output
customer_id | revenue
FOLKO | 12905.32
GOURL | 9578.85
BOLID | 8095.04
ALFKI | 4703.69
BONAP | 4509.46
```

### Example 2: a materialised view goes stale

The materialised view stores the order count per country at creation time. We then move all German orders to another country name in the base table. The plain query on `orders` sees the change at once (0 German orders) but the materialised view still holds the old figure (13).

```sql run
CREATE MATERIALIZED VIEW orders_by_country AS
SELECT ship_country, COUNT(*) AS orders
FROM orders
GROUP BY ship_country;

UPDATE orders SET ship_country = 'Atlantis' WHERE ship_country = 'Germany';

SELECT (SELECT orders FROM orders_by_country WHERE ship_country = 'Germany') AS stored_in_view,
       (SELECT COUNT(*) FROM orders WHERE ship_country = 'Germany') AS live_in_table;
```

```output
stored_in_view | live_in_table
13 | 0
```

### Example 3: REFRESH brings it up to date

The same steps, plus `REFRESH MATERIALIZED VIEW`. Now the view has no row for Germany and it has a row for Atlantis with 13 orders. The result shows the country rows for the two names.

```sql run
CREATE MATERIALIZED VIEW orders_by_country AS
SELECT ship_country, COUNT(*) AS orders
FROM orders
GROUP BY ship_country;

UPDATE orders SET ship_country = 'Atlantis' WHERE ship_country = 'Germany';
REFRESH MATERIALIZED VIEW orders_by_country;

SELECT ship_country, orders
FROM orders_by_country
WHERE ship_country IN ('Germany', 'Atlantis')
ORDER BY ship_country;
```

```output
ship_country | orders
Atlantis | 13
```

### Example 4: a transaction that commits

The runner does not allow `COMMIT` or `ROLLBACK`, so we use SQLite from Python's standard library to show the behaviour. Differences from PostgreSQL: the placeholder is `?` and not `%s`, SQLite starts transactions implicitly, and column types are looser. The `with conn:` block commits when the block ends normally. Two accounts hold 100 and 50; moving 30 changes both rows together.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE accounts (id INTEGER PRIMARY KEY, owner TEXT, balance INTEGER CHECK (balance >= 0))")
conn.executemany("INSERT INTO accounts VALUES (?, ?, ?)", [(1, "Ada", 100), (2, "Grace", 50)])
conn.commit()

def balances():
    return conn.execute("SELECT owner, balance FROM accounts ORDER BY id").fetchall()

def transfer(src, dst, amount):
    with conn:  # COMMIT if the block finishes, ROLLBACK if it raises
        conn.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", (amount, src))
        cur = conn.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?", (amount, dst))
        if cur.rowcount == 0:
            raise LookupError("destination account does not exist")

transfer(1, 2, 30)
print("after transfer:", balances())
```

```output
after transfer: [('Ada', 70), ('Grace', 80)]
```

### Example 5: atomicity, a failed transfer is rolled back

The destination account 99 does not exist, so the second step finds no row and raises an error. The first step, the debit of 40, had already run, but leaving the `with conn:` block with an exception triggers a rollback: both accounts keep their old balances. Without the transaction, Ada would have lost 40 for nothing.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE accounts (id INTEGER PRIMARY KEY, owner TEXT, balance INTEGER CHECK (balance >= 0))")
conn.executemany("INSERT INTO accounts VALUES (?, ?, ?)", [(1, "Ada", 100), (2, "Grace", 50)])
conn.commit()

def transfer(src, dst, amount):
    with conn:
        conn.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", (amount, src))
        cur = conn.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?", (amount, dst))
        if cur.rowcount == 0:
            raise LookupError("destination account does not exist")

try:
    transfer(1, 99, 40)
except LookupError as error:
    print("failed:", error)
print("balances:", conn.execute("SELECT owner, balance FROM accounts ORDER BY id").fetchall())

try:
    transfer(1, 2, 500)   # the CHECK constraint (consistency) rejects a negative balance
except Exception as error:
    print("rejected:", type(error).__name__)
print("balances:", conn.execute("SELECT owner, balance FROM accounts ORDER BY id").fetchall())
```

```output
failed: destination account does not exist
balances: [('Ada', 100), ('Grace', 50)]
rejected: IntegrityError
balances: [('Ada', 100), ('Grace', 50)]
```

### Example 6: a view that combines ranking and a join

Views can contain window functions. This one ranks the products of each category by price, which is the pattern of day 50. Querying the view with a simple filter gives the top product per category without repeating the window code. The final query is the kind of reusable definition a team would store as a view.

```sql run
CREATE VIEW ranked_products AS
SELECT p.category_id, c.category_name, p.product_name, p.unit_price,
       ROW_NUMBER() OVER (PARTITION BY p.category_id ORDER BY p.unit_price DESC, p.product_id) AS price_rank
FROM products AS p
JOIN categories AS c ON c.category_id = p.category_id;

SELECT category_name, product_name, unit_price
FROM ranked_products
WHERE price_rank = 1
ORDER BY category_name;
```

## Real-world applications

**Money, stock and orders.** Example 5 is the pattern behind every system that moves value between rows: debit and credit, reserve and ship, order header and order lines. Wrapping them in one transaction prevents half-posted data.

**Data loads.** A pipeline that loads a day of data into several tables does it in one transaction, so a failure leaves yesterday's consistent state instead of a mix of two days.

**Stable business definitions.** Example 1 and Example 6 define a metric once. Dashboards, reports and analysts query the view and cannot disagree about what "revenue" means, and the definition can be changed in one place.

**Fast dashboards.** A materialised view (Examples 2 and 3) stores the result of an expensive aggregation. A nightly `REFRESH` gives dashboards instant reads, at the cost of data that is up to a day old.

## Daily review

### Key takeaways

- A transaction is all or nothing: ACID means atomicity, consistency, isolation and durability.
- `BEGIN` starts, `COMMIT` makes permanent, `ROLLBACK` undoes; without `BEGIN` every statement is its own transaction.
- A failed statement aborts a PostgreSQL transaction until you roll back; `SAVEPOINT` allows a partial rollback.
- A view is a saved query with always-current results and no stored data; a materialised view stores results and needs `REFRESH`.
- The checkpoint tests days 49 to 59; use the results to decide what to revisit.

### Common mistakes

- Forgetting `COMMIT`, so changes are visible only inside your session and are lost when it ends.
- Continuing after an error in a PostgreSQL transaction: the error is `current transaction is aborted, commands ignored until end of transaction block`. Issue `ROLLBACK`.
- Assuming a plain view stores data or makes queries faster.
- Reading a materialised view and forgetting that it may be stale; schedule `REFRESH` and show the refresh time.
- Doing a multi-step change without a transaction, which leaves half-applied data after a failure.
- Holding a transaction open for a long time, which blocks other work and delays clean-up.

### Revision notes

- ACID: all-or-nothing, valid state, isolated from others, safe after commit.
- Transaction: `BEGIN; ...; COMMIT;` or `ROLLBACK;`.
- View: `CREATE VIEW v AS ...`. Materialised: add `REFRESH MATERIALIZED VIEW v`.
- Checkpoint areas: windows, ranking, `LAG`, frames, `NTILE`, recursion, dedupe, cohorts, indexes, plans, rewrites.

## Objectives

- Explain what version control is and use `git init`, `git add` and `git commit` to record snapshots of a project.
- Inspect state and history with `git status --short`, `git diff`, `git log` and `git rev-list --count`.
- Create branches, switch between them and merge them, including resolving a merge conflict.
- Connect repositories with remotes: `git remote add`, `git push`, `git clone` and `git pull`, practised with a local bare repository.
- Describe the GitHub pull request workflow, and keep files out of the repository with `.gitignore`.

## Understand

### Why version control

Without version control, projects collect files such as `report_final.py`, `report_final2.py` and `report_really_final.py`. **Version control** is a system that records every change to a project, who made it and why, so you can compare versions, undo mistakes and let several people work on the same code. **Git** is the most widely used version control system. It runs on your own computer and stores the project's history in a hidden folder called `.git`. A folder together with its `.git` history is a **repository** (repo).

### Commits: snapshots with messages

A **commit** is a saved snapshot of all tracked files, with a message, an author, a time and a pointer to the previous commit. Commits form a chain, and each has a unique identifier called a **hash**, a 40-character code such as `3f2a9c...`; the first seven characters are usually enough to name one. Git does not save a commit automatically. Saving takes two steps through an intermediate place called the **staging area** (or index): `git add file` places the current version of a file in the staging area, deciding what will be in the next commit, and `git commit -m "message"` turns the staged files into a commit. The staging area lets you commit related changes together. A good message is a short sentence in the imperative: "Add currency column".

Files exist in one of these states: **untracked** (new, Git has never seen it), **modified** (changed since the last commit), **staged** (added, ready to commit) and **committed**. `git status` shows them; `git status --short` shows one line per file with codes such as `??` (untracked), ` M` (modified, not staged), `M ` (staged) and `A ` (new and staged). `git diff` shows unstaged changes line by line, `git diff --staged` shows staged ones, and `git log --format=%s` prints the commit messages, newest first. The first commit of a repository has no parent.

### Branches

A **branch** is a movable name that points to a commit. The default branch is usually called `main`. Creating a branch with `git switch -c feature` makes a new pointer at the current commit, and new commits then move only that pointer. Branches are cheap, so the usual habit is one branch per task: you can experiment without touching `main`. `git branch --list` shows the names, with `*` marking the current one, and `git switch name` changes branch (the files in the folder change to match). The commit you are on is called `HEAD`.

### Merging and conflicts

`git merge feature`, run while on `main`, brings the work of `feature` into `main`. If `main` has not moved since `feature` started, Git simply moves the `main` pointer forward, called a **fast-forward**. If both branches have new commits, Git creates a **merge commit** with two parents that combines both lines of work. When both branches changed the **same lines** of the same file, Git cannot decide which to keep and reports a **merge conflict**: it stops, marks the file with conflict markers, and waits for you. The markers look like this:

```text
<<<<<<< HEAD
the version on the current branch
=======
the version on the other branch
>>>>>>> feature
```

You edit the file to the text you want and delete the three marker lines, run `git add file`, and then `git commit` to finish the merge. Conflicts are normal, not errors: they mean two people changed the same place. Different files or different lines merge cleanly.

### Remotes, push and pull

A **remote** is another copy of the repository, usually on a server. `git remote add origin <location>` gives a remote the name `origin` (the usual name for the main one). `git push origin main` uploads your commits and `git pull` downloads and merges new commits from the remote. `git clone <location>` copies a whole repository, history included, and sets `origin` for you. A **bare repository** (`git init --bare`) has no working files, only history, which is what a server stores. Two local folders, with one bare repository acting as the remote between them, behave exactly like two people sharing a server, and this lesson uses that to practise without a network.

### GitHub and pull requests

**GitHub** is a website that hosts Git repositories and adds collaboration tools. It is not Git itself, and it cannot run inside this course's browser or tests, so this part is described rather than executed. The usual workflow is: you **fork** or clone the repository, create a branch, commit your work and push the branch to GitHub. On the website you open a **pull request** (PR): a request to merge your branch into `main`, showing the changes, a discussion thread and automatic checks such as tests. Teammates **review** it, you may push more commits to the branch, and when it is approved someone merges it. Typical commands before that:

```text
git switch -c add-currency-column
# edit files, then
git add .
git commit -m "Add currency column"
git push -u origin add-currency-column
# then open the pull request in the GitHub web page
```

### .gitignore

A file named `.gitignore` lists patterns of files Git must not track: one pattern per line, `*.log` for all log files, `.venv/` for a folder, `data/raw/` for a path. Ignore generated files, virtual environments (Day 22), caches and, above all, **secrets** such as passwords and API keys. Files that were already committed stay tracked; ignoring only affects untracked files.

### Common misconception

Learners think `git commit` uploads their work. It saves a snapshot only on your own computer. Sharing needs `git push`. Another one: committing a secret and then deleting it in the next commit removes it from the latest version but not from history, so a leaked password must be revoked, not just deleted.

### About this lesson's environment

Git runs in a terminal, which the browser cannot provide, so the `bash run` examples are shown read-only with output from a real run in a throwaway folder. Commit hashes change with every machine, so the examples print messages, counts and short status codes, never hashes. The graded exercises are pure-Python alternatives: parsing `git log --oneline` text, working with a commit graph and applying `.gitignore`-style patterns. GitHub itself is covered in text and in written exercises.

### Why it matters

Pipelines, SQL scripts and notebooks are code. Version control gives them history, safe experiments and review. Nearly every data team works in Git, and a pipeline that is not in a repository cannot be reproduced.

## Syntax and key functions

```text
git init -b main
git add file.py          # or: git add .
git commit -m "Message"
git status --short
git log --format=%s
git switch -c new-branch
git merge other-branch
git push -u origin main
git clone location folder
git pull
```

`init` creates a repository, `add` stages, `commit` saves, `status` and `log` inspect, `switch -c` creates and enters a branch, `merge` combines, `push` and `pull` exchange commits, `clone` copies.

| Command | What it does |
|---|---|
| `git init -b main` | Creates a repository with branch `main`. |
| `git add file` / `git add .` | Stages a file / everything changed. |
| `git commit -m "msg"` | Saves the staged changes as a commit. |
| `git status --short` | One line per changed file (`??`, ` M`, `M `, `A `). |
| `git diff`, `git diff --staged` | Unstaged / staged changes. |
| `git log --format=%s` | Commit messages, newest first. |
| `git rev-list --count HEAD` | Number of commits reachable from the current one. |
| `git branch --list`, `git switch name`, `git switch -c name` | List, change, create-and-change branch. |
| `git merge name` | Merge a branch into the current one. |
| `git remote add origin loc`, `git push`, `git pull`, `git clone` | Connect, upload, download, copy. |
| `.gitignore` | Patterns of files that are not tracked. |

## Learn by example

### Example 1: Init, commit and history

A repository is created, a file is added and committed twice. `git status --short` shows `??` for a new file and `A ` once it is staged. `git log --format=%s` prints messages only and `rev-list --count` counts commits, so no hash appears.

```bash run
git init -q -b main project
cd project
echo "id,amount" > sales.csv
git status --short
git add sales.csv
git status --short
git commit -q -m "Add sales file"
echo "1,120" >> sales.csv
git status --short
git commit -q -am "Add first row"
git log --format=%s
git rev-list --count HEAD
```

```output
?? sales.csv
A  sales.csv
 M sales.csv
Add first row
Add sales file
2
```

### Example 2: Seeing changes and ignoring files

`git diff --name-only` lists changed files, and `git diff` shows the lines. A `.gitignore` that lists `*.log` and `.venv/` makes Git ignore matching files, which disappear from the status. `git check-ignore` confirms which file matches a rule.

```bash run
git init -q -b main project
cd project
printf 'a\nb\n' > notes.txt
git add notes.txt
git commit -q -m "Add notes"
printf 'a\nB\n' > notes.txt
git diff --name-only
git diff | grep '^[+-][^+-]'
touch run.log
mkdir .venv && touch .venv/lib.py
git status --short
printf '*.log\n.venv/\n' > .gitignore
git status --short
git check-ignore run.log
```

```output
notes.txt
-b
+B
 M notes.txt
?? .venv/
?? run.log
 M notes.txt
?? .gitignore
run.log
```

### Example 3: Branches and a clean merge

A branch is created, committed on, and merged back. The first merge is a fast-forward because `main` did not move; the second branch diverges from `main`, so Git makes a merge commit. `git branch --list` marks the current branch with `*`, and the log shows the history.

```bash run
git init -q -b main project
cd project
echo "v1" > app.txt
git add app.txt
git commit -q -m "Start app"
git switch -q -c feature-a
echo "a" > a.txt
git add a.txt
git commit -q -m "Add feature A"
git switch -q main
git merge -q feature-a
git branch --list
git switch -q -c feature-b
echo "b" > b.txt
git add b.txt
git commit -q -m "Add feature B"
git switch -q main
echo "hotfix" > fix.txt
git add fix.txt
git commit -q -m "Hotfix on main"
git merge -q --no-edit feature-b
git log --format=%s --topo-order
ls
```

```output
  feature-a
* main
Merge branch 'feature-b'
Add feature B
Hotfix on main
Add feature A
Start app
a.txt
app.txt
b.txt
fix.txt
```

### Example 4: A merge conflict and its resolution

Both branches change the same line of `config.txt`. The merge stops with a conflict (the `|| true` keeps the script running), `git status --short` shows `UU` (unmerged on both sides), and the file contains markers. The fix is to write the final text, stage the file and commit.

```bash run
git init -q -b main project
cd project
echo "mode=slow" > config.txt
git add config.txt
git commit -q -m "Add config"
git switch -q -c fast
echo "mode=fast" > config.txt
git commit -q -am "Use fast mode"
git switch -q main
echo "mode=safe" > config.txt
git commit -q -am "Use safe mode"
git merge fast > /dev/null || true
git status --short
cat config.txt
echo "mode=safe-fast" > config.txt
git add config.txt
git commit -q --no-edit
git status --short
cat config.txt
git log --format=%s --topo-order
```

```output
UU config.txt
<<<<<<< HEAD
mode=safe
=======
mode=fast
>>>>>>> fast
mode=safe-fast
Merge branch 'fast'
Use fast mode
Use safe mode
Add config
```

### Example 5: A local bare repository as the remote

A bare repository stands in for GitHub. One clone pushes a commit, a second clone pulls it, adds its own commit and pushes back, and the first pulls again. Only messages and counts are printed. A real GitHub remote works the same with a web address in place of the folder path.

```bash run
git init -q --bare -b main remote.git
git clone -q remote.git ana 2> /dev/null
cd ana
git switch -q -c main 2> /dev/null || true
echo "id" > data.csv
git add data.csv
git commit -q -m "Ana adds data"
git push -q -u origin main 2> /dev/null
cd ..
git clone -q remote.git bo
cd bo
git log --format=%s
echo "id,amount" > data.csv
git commit -q -am "Bo adds a column"
git push -q origin main
cd ../ana
git pull -q --ff-only
git log --format=%s
git remote
git rev-list --count HEAD
```

```output
Ana adds data
Bo adds a column
Ana adds data
origin
2
```

### Example 6: A commit graph in Python

This pure-Python version works on the same ideas without Git: the log text is parsed, a commit graph with parent links is built, and the ancestors of a branch are collected to decide whether a merge would be a fast-forward. Because it runs in the browser, it is the graded alternative.

```python run
log = """c1 Start app
c2 Add feature A
c3 Hotfix on main
c4 Add feature B
c5 Merge feature B"""
parents = {"c1": [], "c2": ["c1"], "c3": ["c2"], "c4": ["c2"], "c5": ["c3", "c4"]}
branches = {"main": "c5", "feature-b": "c4", "feature-a": "c2"}

messages = {}
for line in log.splitlines():
    commit, message = line.split(" ", 1)
    messages[commit] = message

def ancestors(commit):
    seen = set()
    stack = [commit]
    while stack:
        current = stack.pop()
        if current not in seen:
            seen.add(current)
            stack.extend(parents[current])
    return seen

def is_fast_forward(into, other):
    return branches[into] in ancestors(branches[other])

print(sorted(messages[c] for c in ancestors(branches["main"])))
print(len(ancestors("c4")))
print(is_fast_forward("feature-a", "main"), is_fast_forward("main", "feature-a"))
print([c for c, p in parents.items() if len(p) > 1])
```

```output
['Add feature A', 'Add feature B', 'Hotfix on main', 'Merge feature B', 'Start app']
3
True False
['c5']
```

## Real-world applications

- **History and recovery.** When a pipeline change breaks results, `git log` and `git diff` show exactly what changed and when, and a commit can be reverted (Examples 1 and 2).
- **Parallel work without collisions.** Each person works on a branch and merges when ready, so unfinished work never blocks `main` (Example 3), and conflicts (Example 4) are resolved deliberately.
- **Review before release.** On GitHub, a pull request puts a change in front of teammates and automated tests before it reaches `main`; that is the gate for SQL scripts and DAGs.
- **Keeping the repository clean.** `.gitignore` keeps virtual environments, caches and secrets out of history (Example 2).

## Daily review

### Key takeaways

- A commit is a saved snapshot with a message; `git add` stages and `git commit` saves, only locally.
- `git status --short`, `git diff` and `git log --format=%s` show the state and history.
- A branch is a pointer to a commit; merges are fast-forward or create a merge commit; same-line edits cause a conflict you resolve by hand.
- Remotes share repositories: `push` uploads, `pull` downloads, `clone` copies; a bare repository works as a server.
- A pull request asks to merge a branch on GitHub and is reviewed first; `.gitignore` keeps files out of Git.

### Common mistakes

- Forgetting `git add` before `git commit`, so the commit is empty (`nothing added to commit`). Check `git status` first.
- Believing `commit` uploads work. Without `git push` nobody else sees it.
- Committing secrets, virtual environments or data dumps. Add them to `.gitignore` before the first commit, and revoke any leaked secret.
- Editing a conflicted file but leaving the `<<<<<<<` markers inside, which breaks the code. Remove all three marker lines and test.
- Working directly on `main` for risky changes. Create a branch.
- Using `git add .` blindly and staging generated or private files. Read `git status --short` first.
- Expecting `.gitignore` to remove a file that is already tracked. Untrack it with `git rm --cached file`.

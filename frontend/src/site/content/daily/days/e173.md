## Objectives

- Define the scope of the capstone pipeline as a short set of requirements that can each be checked with a number.
- Profile the generated orders and customers data and count the planted defects before writing any pipeline code.
- Write a source-to-target mapping from the API and CSV fields to the star schema `fact_sales`, `dim_customer`, `dim_product` and `dim_date`.
- Draw the architecture as text and split the build into the stages of Days 174 to 179.
- Turn each requirement into an acceptance check that the later days will run.

## Understand

### One project for eight days

Days 173 to 180 build one pipeline from an empty folder to a presented result. Each day builds exactly one stage and ends with checks on that stage's output, so nothing is trusted because "it ran". The project is an **event and orders pipeline**. A stand-in for an orders API emits paginated JSON orders, a CSV file lists customers, and the pipeline loads both incrementally into a star schema that analysts query with SQL. All data is generated in code by one seeded generator, so every number printed in these lessons is reproducible on your computer. No real database, scheduler or hosting service is needed: ingestion calls a stand-in function, the warehouse is `sqlite3` in Python and PostgreSQL on the browser database in SQL, orchestration is modelled in plain Python, and Git runs in a throwaway folder.

### Scoping: what is in, what is out

**Scoping** means writing down what the pipeline must do and, just as important, what it will not do, before building it. A pipeline without a scope grows in every direction: one more field, one more source, one more report. A useful scope has four parts. The **sources**: where the data comes from, in what shape, how large, and how it fails. The **requirements**: statements about the result, each phrased so that a number or a query can say yes or no. The **architecture**: the stages the data passes through and what is stored between them. The **plan**: the order of work, with a finish line for each step. In this capstone the facts are: 120 order records over 5 pages of 25, a customer CSV with 20 rows, a fact table that holds paid orders only, and a result that must reconcile.

### Requirements you can test

"Load the orders correctly" is not a requirement, because nobody can tell whether it holds. "Every raw order is either loaded or quarantined, so raw count equals loaded plus quarantined" is one: it is a subtraction. Good requirements name an input, an output and a number. They also cover the failure paths, because data engineering is mostly failure paths: what happens to a record with a negative amount, to a page that fails, to a run that is started twice. The requirements for this project are listed in Example 3, and each one reappears as an assertion on the day that builds the stage.

### Profile before you design

**Profiling** is counting what the data looks like: how many records, how many distinct keys, which statuses, which date range, how many rows break each rule. You profile first because the design depends on the answers. Duplicate order ids mean the loader must be idempotent. Unknown customers mean a quarantine is needed. A status outside the list means the validation cannot be a simple filter on `paid`. In Example 2 you will find six planted defects in 120 records, and those six numbers become the expected results of Day 175.

### The star schema is the target

The target is the warehouse sample used across the engineer path: `fact_sales(sale_id, date_key, customer_key, product_key, quantity, amount_cents)`, `dim_customer(customer_key, customer_id, customer_name, country, valid_from, valid_to, is_current)`, `dim_product(product_key, product_id, product_name, category)` and `dim_date(date_key, full_date, year, month)`. The **grain** of the fact table, which is what one row means, is one paid order. Writing the grain down early prevents the most common modelling error, a fact table whose rows mean different things.

### Common misconception

Learners start with the code because code feels like progress. The cost shows up on Day 176, when a missing key or an unclear grain forces a rewrite of Days 174 and 175. One hour of scoping removes more rework than it costs.

### Why it matters

A pipeline you can describe in one page, test with a dozen numbers and demonstrate in five minutes is a portfolio piece. A pipeline you can only describe as "it loads data" is not.

## Syntax and key functions

The generator used on every capstone day is a seeded function; the same call always returns the same data:

```python
customers, products, orders = generate()   # 20 customers, 8 products, 120 raw order dicts
```

A requirement written as data, so that a program can check it:

```python
requirement = {"id": "R1", "statement": "raw = loaded + quarantined", "check": lambda s: s["raw"] == s["loaded"] + s["quarantined"]}
```

| Item | What it does or returns |
|---|---|
| `generate(seed=7)` | Returns `(customers, products, orders)`; customers and products are tuples, orders are dicts. |
| `collections`-style counting with a dict | The standard way to profile: `counts[key] = counts.get(key, 0) + 1`. |
| Source-to-target mapping | A table of target column, source field and rule, one row per target column. |
| Grain | One sentence stating what a fact row represents. |
| Acceptance check | A requirement turned into a function that returns True or False. |

## Learn by example

### Example 1: Generate and profile the orders

The generator below is copied into every capstone day, so each day runs on its own. It builds 20 customers, 8 products and 120 order records with planted defects (explained in Example 2). The order record extends the Orders API stand-in (`order_id`, `customer_id`, `amount_cents`, `currency`, `status`, `created_at`) with `product_id` and `quantity`, because the star schema needs a product dimension and a quantity. The profile counts records, distinct ids, statuses and the date range.

```python run
import random
from datetime import date, timedelta

COUNTRIES = ["DE", "FR", "IN", "US", "BR"]
CATEGORIES = ["tools", "books", "games"]

def generate(seed=7):
    """Seeded stand-in data: customers, products and 120 raw order records with planted defects."""
    rng = random.Random(seed)
    customers = [(f"C{n:03d}", f"Customer {n:02d}", COUNTRIES[n % 5]) for n in range(1, 21)]
    products = [(f"P{n:02d}", f"Product {n:02d}", CATEGORIES[n % 3]) for n in range(1, 9)]
    price = {pid: 500 * (i + 1) for i, (pid, _, _) in enumerate(products)}
    orders = []
    for n in range(1, 121):
        pid = products[rng.randrange(8)][0]
        qty = rng.randint(1, 4)
        day = date(2026, 1, 1) + timedelta(days=(n - 1) * 89 // 119)
        orders.append({
            "order_id": f"O{n:04d}", "customer_id": customers[rng.randrange(20)][0], "product_id": pid,
            "quantity": qty, "amount_cents": price[pid] * qty, "currency": "EUR",
            "status": rng.choices(["paid", "refunded", "failed"], weights=[8, 1, 1])[0],
            "created_at": f"{day}T{(n * 7) % 24:02d}:{(n * 13) % 60:02d}:00Z",
        })
    orders[29]["amount_cents"] = -1000
    orders[44]["customer_id"] = "C999"
    orders[59]["created_at"] = ""
    orders[74]["currency"] = "???"
    orders[104]["status"] = "pending"
    orders[119] = dict(orders[9])
    return customers, products, orders

customers, products, orders = generate()
statuses = {}
for r in orders:
    statuses[r["status"]] = statuses.get(r["status"], 0) + 1
dates = sorted(r["created_at"][:10] for r in orders if r["created_at"])
print("customers:", len(customers), "products:", len(products))
print("records:", len(orders), "distinct order ids:", len({r["order_id"] for r in orders}))
print("statuses:", sorted(statuses.items()))
print("first day:", dates[0], "last day:", dates[-1])
print("pages of 25:", -(-len(orders) // 25))
```

```output
customers: 20 products: 8
records: 120 distinct order ids: 119
statuses: [('failed', 13), ('paid', 96), ('pending', 1), ('refunded', 10)]
first day: 2026-01-01 last day: 2026-03-30
pages of 25: 5
```

### Example 2: Count the planted defects

Each rule is a question with a yes or no answer per record. The loop counts the records that break each rule. The duplicate rule needs a set of ids already seen, because a duplicate is defined relative to an earlier record.

```python run
import random
from datetime import date, timedelta

COUNTRIES = ["DE", "FR", "IN", "US", "BR"]
CATEGORIES = ["tools", "books", "games"]

def generate(seed=7):
    """Seeded stand-in data: customers, products and 120 raw order records with planted defects."""
    rng = random.Random(seed)
    customers = [(f"C{n:03d}", f"Customer {n:02d}", COUNTRIES[n % 5]) for n in range(1, 21)]
    products = [(f"P{n:02d}", f"Product {n:02d}", CATEGORIES[n % 3]) for n in range(1, 9)]
    price = {pid: 500 * (i + 1) for i, (pid, _, _) in enumerate(products)}
    orders = []
    for n in range(1, 121):
        pid = products[rng.randrange(8)][0]
        qty = rng.randint(1, 4)
        day = date(2026, 1, 1) + timedelta(days=(n - 1) * 89 // 119)
        orders.append({
            "order_id": f"O{n:04d}", "customer_id": customers[rng.randrange(20)][0], "product_id": pid,
            "quantity": qty, "amount_cents": price[pid] * qty, "currency": "EUR",
            "status": rng.choices(["paid", "refunded", "failed"], weights=[8, 1, 1])[0],
            "created_at": f"{day}T{(n * 7) % 24:02d}:{(n * 13) % 60:02d}:00Z",
        })
    orders[29]["amount_cents"] = -1000
    orders[44]["customer_id"] = "C999"
    orders[59]["created_at"] = ""
    orders[74]["currency"] = "???"
    orders[104]["status"] = "pending"
    orders[119] = dict(orders[9])
    return customers, products, orders

customers, products, orders = generate()
known = {c[0] for c in customers}
seen, found = set(), {}
for r in orders:
    problems = []
    if r["order_id"] in seen:
        problems.append("duplicate order_id")
    seen.add(r["order_id"])
    if not r["created_at"]:
        problems.append("missing created_at")
    if r["amount_cents"] <= 0:
        problems.append("non-positive amount")
    if r["customer_id"] not in known:
        problems.append("unknown customer")
    if r["currency"] != "EUR":
        problems.append("bad currency")
    if r["status"] not in ("paid", "refunded", "failed"):
        problems.append("bad status")
    for p in problems:
        found[p] = found.get(p, 0) + 1
for name, n in sorted(found.items()):
    print(name, n)
print("records with a defect:", sum(found.values()))
```

```output
bad currency 1
bad status 1
duplicate order_id 1
missing created_at 1
non-positive amount 1
unknown customer 1
records with a defect: 6
```

### Example 3: Requirements as acceptance checks

Each requirement is a pair of an id and a function over a summary dictionary. The summary here is the one the finished pipeline should produce: 120 raw records, 6 quarantined, 114 clean, of which the paid ones go to the fact table. The expected numbers are computed from the generated data with the same rules as Example 2, so the requirements are checked against the data and not against numbers typed from memory.

```python run
import random
from datetime import date, timedelta

COUNTRIES = ["DE", "FR", "IN", "US", "BR"]
CATEGORIES = ["tools", "books", "games"]

def generate(seed=7):
    """Seeded stand-in data: customers, products and 120 raw order records with planted defects."""
    rng = random.Random(seed)
    customers = [(f"C{n:03d}", f"Customer {n:02d}", COUNTRIES[n % 5]) for n in range(1, 21)]
    products = [(f"P{n:02d}", f"Product {n:02d}", CATEGORIES[n % 3]) for n in range(1, 9)]
    price = {pid: 500 * (i + 1) for i, (pid, _, _) in enumerate(products)}
    orders = []
    for n in range(1, 121):
        pid = products[rng.randrange(8)][0]
        qty = rng.randint(1, 4)
        day = date(2026, 1, 1) + timedelta(days=(n - 1) * 89 // 119)
        orders.append({
            "order_id": f"O{n:04d}", "customer_id": customers[rng.randrange(20)][0], "product_id": pid,
            "quantity": qty, "amount_cents": price[pid] * qty, "currency": "EUR",
            "status": rng.choices(["paid", "refunded", "failed"], weights=[8, 1, 1])[0],
            "created_at": f"{day}T{(n * 7) % 24:02d}:{(n * 13) % 60:02d}:00Z",
        })
    orders[29]["amount_cents"] = -1000
    orders[44]["customer_id"] = "C999"
    orders[59]["created_at"] = ""
    orders[74]["currency"] = "???"
    orders[104]["status"] = "pending"
    orders[119] = dict(orders[9])
    return customers, products, orders

customers, products, orders = generate()
known = {c[0] for c in customers}
seen, clean = set(), []
for r in orders:
    ok = (r["order_id"] not in seen and r["created_at"] and r["amount_cents"] > 0 and r["customer_id"] in known
          and r["currency"] == "EUR" and r["status"] in ("paid", "refunded", "failed"))
    seen.add(r["order_id"])
    if ok:
        clean.append(r)
summary = {"raw": len(orders), "clean": len(clean), "quarantined": len(orders) - len(clean),
           "fact_rows": sum(1 for r in clean if r["status"] == "paid"),
           "fact_cents": sum(r["amount_cents"] for r in clean if r["status"] == "paid"), "rerun_added": 0}
requirements = [
    ("R1 every raw record is loaded or quarantined", lambda s: s["raw"] == s["clean"] + s["quarantined"]),
    ("R2 the fact table holds paid orders only", lambda s: s["fact_rows"] <= s["clean"]),
    ("R3 revenue is a positive whole number of cents", lambda s: isinstance(s["fact_cents"], int) and s["fact_cents"] > 0),
    ("R4 a second run adds no rows", lambda s: s["rerun_added"] == 0),
]
for name, check in requirements:
    print("PASS" if check(summary) else "FAIL", name)
print(summary)
```

```output
PASS R1 every raw record is loaded or quarantined
PASS R2 the fact table holds paid orders only
PASS R3 revenue is a positive whole number of cents
PASS R4 a second run adds no rows
{'raw': 120, 'clean': 114, 'quarantined': 6, 'fact_rows': 91, 'fact_cents': 523500, 'rerun_added': 0}
```

### Example 4: Source-to-target mapping and the plan

The mapping lists, for every column of the four target tables, the source field it comes from. A program can then verify that no target column was forgotten and that every source field is used or deliberately dropped. The plan maps each requirement group to a day. The architecture diagram is plain text.

```text
orders API (5 pages) --> ingest --> raw_orders ----+
customers.csv --------> ingest --> raw_customers --+--> clean + validate --> quarantine
                                                         |
                                                         v
                                   dim_date, dim_product, dim_customer, fact_sales (incremental)
                                                         |
                                                         v
                                            analytics views and metrics
```

```python run
mapping = {
    "fact_sales.sale_id": "order_id (digits)",
    "fact_sales.date_key": "created_at (YYYYMMDD)",
    "fact_sales.customer_key": "customer_id via dim_customer",
    "fact_sales.product_key": "product_id via dim_product",
    "fact_sales.quantity": "quantity",
    "fact_sales.amount_cents": "amount_cents",
    "dim_customer.customer_id": "customers.csv customer_id",
    "dim_customer.customer_name": "customers.csv customer_name",
    "dim_customer.country": "customers.csv country",
    "dim_product.product_id": "orders product_id",
    "dim_date.full_date": "generated calendar",
}
source_fields = ["order_id", "customer_id", "product_id", "quantity", "amount_cents", "currency", "status", "created_at"]
used = " ".join(mapping.values())
print("target columns mapped:", len(mapping))
print("source fields used:", [f for f in source_fields if f in used])
print("source fields only filtered on:", [f for f in source_fields if f not in used])
plan = [("Day 174", "ingestion"), ("Day 175", "cleaning and validation"), ("Day 176", "warehouse model and load"),
        ("Day 177", "analytics layer"), ("Day 178", "orchestration and tests"), ("Day 179", "documentation and GitHub")]
for day, stage in plan:
    print(day, stage)
```


## Real-world applications

- **Project kick-off documents.** Teams write a one-page scope with sources, requirements and a plan before sprint work starts; Example 3 is that page in executable form.
- **Data contracts.** The source-to-target mapping of Example 4 is the starting point of a contract between the team that owns the API and the team that loads it.
- **Estimating effort.** Profiling (Example 2) turns a vague "some bad data" into six rules and six counts, which is what a manager needs to size the cleaning work.
- **Reviews and handover.** A reviewer can read the requirements and check each one, instead of reading all the code.

## Daily review

### Key takeaways

- A capstone is built stage by stage; each stage has its own output and its own checks.
- Scope states sources, requirements, architecture and plan, and what is left out.
- A requirement is useful only when a number or a query can say yes or no.
- Profile the data before designing: the defects found decide the rules, the quarantine and the idempotency needs.
- Write the fact grain down: one paid order per row.

### Common mistakes

- Writing requirements like "clean data" that cannot fail. Rewrite them as a count comparison.
- Skipping profiling and finding duplicates after the load, when they already sit in the fact table.
- Mixing grains: loading refunded and paid orders into the same fact rows without a rule, so revenue is wrong.
- Planning only the happy path and leaving out bad rows, failed pages and re-runs.
- Forgetting what is out of scope, so the project never ends.

### Revision notes

- Sources: orders API (120 records, 5 pages), customers CSV (20 rows).
- Target: `fact_sales`, `dim_customer`, `dim_product`, `dim_date`; grain is one paid order.
- Six planted defects: duplicate id, missing timestamp, non-positive amount, unknown customer, bad currency, bad status.
- Requirement pattern: `raw == loaded + quarantined`.

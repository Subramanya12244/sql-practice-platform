## Objectives

- Write an analytical question set with a metric definition, the columns needed and an owner decision for each question.
- Inventory the project's data sources: rows, keys, relationships and the problems the raw data already shows.
- State quality rules and success criteria as checks that code can run, and measure the raw data against them.
- Produce a stage plan for Days 172 to 180 with a testable output at every stage.

## Understand

### The capstone in one paragraph

Days 172 to 180 build one project: an analytics study of an online store. The store sells 20 products in four categories to 120 customers in four countries. Over six months (January to June 2025) customers place orders, some orders are returned, and each order may be tied to a marketing campaign (email, paid search, social) or to none (organic). The data is generated in code by a seeded generator, so every learner gets the same 500 orders, and every number in the capstone can be checked. The raw data deliberately contains defects: duplicate order rows, negative quantities, orders for customers who do not exist, inconsistent country labels and returns for orders that are not in the orders table. Each day builds one stage of a real analytics project and ends with graded checks on the stage's output.

### Start from questions, not from data

A project that starts from the data produces charts nobody asked for. A project that starts from questions can be finished, because you know when a question is answered. A good question names a metric, a comparison and a decision. "How is revenue doing?" is weak. "Which marketing channel returns the most net revenue per unit of spend, so we can move budget?" is strong, because the metric (net revenue divided by spend), the comparison (across channels) and the decision (move budget) are all in it. The capstone has five questions: monthly net revenue and its trend, return on spend by campaign channel, return rate by product category, the share of customers who order more than once, and revenue by country. Each question is written with the columns it needs, which lets you check on Day 172 that the data can answer it at all.

### Metric definitions

Two analysts can both say "revenue" and report different numbers. Writing the definition once prevents that. The capstone defines line revenue as `quantity * unit_price * (1 - discount_pct / 100)` using the product's current price. Net revenue is line revenue of valid orders that were not returned. Return rate is returned orders divided by valid orders. Return on spend (ROAS) is net revenue of a channel divided by its spend. A definition also says what is excluded: an order that fails a quality rule is not valid, and is counted and reported, not silently dropped.

### Data sources, rules and success criteria

A source inventory lists each table with its row count, key column, and how it relates to others. A relationship is only trustworthy if the foreign keys match: an order whose `customer_id` is missing from `customers` cannot be assigned to a country. Quality rules turn this into checks: order ids are unique, quantities are positive, every order's customer exists, countries use four standard codes, every return refers to an existing order, and every order date falls in the study window. Success criteria say when the project is done: for example, zero rule violations remain after cleaning, every removed row is accounted for, and every figure in the final report can be reproduced by running one command.

### Common misconception

Learners often treat scoping as paperwork before the real work. The symptom shows up on Day 176: a question that needs a column nobody ingested, or a metric computed two ways in two places that disagree. Fifteen minutes of scoping on the first day removes that rework. Another misconception is that raw data can be trusted until it breaks. Measuring the raw data against written rules on the first day gives you a baseline: later you can show how many violations existed, and prove they are gone.

### The repository checklist

The final deliverable is a repository, not a notebook. It holds `README.md`, `requirements.txt`, `.gitignore`, `src/store.py` (generator and cleaning), `sql/` (analysis queries), `tests/test_store.py`, and `reports/` (figures and the written narrative). Generated data is not committed, because the generator recreates it.

## Syntax and key functions

The scoping artefacts are plain Python data structures, so they can be checked by code.

```python
questions = {"Q1": {"text": "...", "needs": {"orders": ["order_date", "quantity"]}}}
rules = {"R1": ("order_id unique", lambda t: int(t["orders"]["order_id"].duplicated().sum()))}
```

Each question lists the tables and columns it needs, and each rule is a name plus a function that returns the number of violating rows.

| Function | Returns |
|---|---|
| `df.duplicated()` | Boolean Series, True for repeats of an earlier row |
| `df["col"].is_unique` | True when no value repeats |
| `s.isin(other)` | Boolean Series: True where the value appears in `other` |
| `df.shape` | `(rows, columns)` |
| `set(a) <= set(b)` | True when every item of `a` is in `b` |

## Learn by example

### Example 1: Source inventory

The first step lists every table with rows, columns and the key. The orders table has more rows than distinct order ids, which already shows a defect.

```python run
import numpy as np
import pandas as pd


def generate(seed=7):
    """Seeded online-store data with planted defects: 500 orders, 120 customers, 20 products."""
    rng = np.random.default_rng(seed)
    customers = pd.DataFrame({
        "customer_id": np.arange(1, 121),
        "country": rng.choice(["DE", "FR", "UK", "US"], 120, p=[0.3, 0.2, 0.2, 0.3]),
        "signup_date": pd.Timestamp("2024-07-01") + pd.to_timedelta(rng.integers(0, 180, 120), unit="D"),
    })
    customers.loc[rng.choice(120, 8, replace=False), "country"] = "us "
    products = pd.DataFrame({
        "product_id": np.arange(1, 21),
        "category": np.repeat(["home", "beauty", "sports", "electronics"], 5),
        "unit_price": (10 + rng.random(20) * 90).round(2),
    })
    campaigns = pd.DataFrame({
        "campaign_id": [0, 1, 2, 3],
        "channel": ["organic", "email", "paid_search", "social"],
        "spend": [0.0, 800.0, 2500.0, 1200.0],
    })
    n = 500
    orders = pd.DataFrame({
        "order_id": np.arange(1001, 1001 + n),
        "customer_id": rng.integers(1, 121, n),
        "product_id": rng.integers(1, 21, n),
        "order_date": pd.Timestamp("2025-01-01") + pd.to_timedelta(rng.integers(0, 180, n), unit="D"),
        "quantity": rng.integers(1, 5, n),
        "discount_pct": rng.choice([0, 10, 20], n, p=[0.6, 0.25, 0.15]),
        "campaign_id": rng.choice([0, 1, 2, 3], n, p=[0.4, 0.2, 0.25, 0.15]),
    })
    orders.loc[rng.choice(n, 5, replace=False), "quantity"] = -1
    orders.loc[rng.choice(n, 6, replace=False), "customer_id"] = 999
    orders = pd.concat([orders, orders.sample(10, random_state=1)], ignore_index=True)
    returned = rng.choice(np.arange(1001, 1001 + n), 60, replace=False)
    returns = pd.DataFrame({
        "order_id": np.concatenate([returned, [9001, 9002, 9003]]),
        "reason": rng.choice(["damaged", "wrong_item", "changed_mind"], 63, p=[0.3, 0.2, 0.5]),
    })
    return {"orders": orders, "customers": customers, "products": products, "campaigns": campaigns, "returns": returns}


t = generate()
for name, df in t.items():
    key = df.columns[0]
    print(f"{name}: rows={len(df)} cols={df.shape[1]} key={key} unique_key={df[key].is_unique}")
o = t["orders"]
print("orders customer match:", int(o["customer_id"].isin(t["customers"]["customer_id"]).sum()), "of", len(o))
print("returns order match:", int(t["returns"]["order_id"].isin(o["order_id"]).sum()), "of", len(t["returns"]))
```

```output
orders: rows=510 cols=7 key=order_id unique_key=False
customers: rows=120 cols=3 key=customer_id unique_key=True
products: rows=20 cols=3 key=product_id unique_key=True
campaigns: rows=4 cols=3 key=campaign_id unique_key=True
returns: rows=63 cols=2 key=order_id unique_key=True
orders customer match: 504 of 510
returns order match: 60 of 63
```

### Example 3: Rules and plan

The rules are functions that count violations. Running them on the raw data gives the baseline, and the success criteria say what the cleaned data must show.

o, c, r = t["orders"], t["customers"], t["returns"]
rules = {
    "R1 order_id unique": int(o["order_id"].duplicated().sum()),
    "R2 quantity positive": int((o["quantity"] <= 0).sum()),
    "R3 customer exists": int((~o["customer_id"].isin(c["customer_id"])).sum()),
    "R4 country standard": int((~c["country"].isin(["DE", "FR", "UK", "US"])).sum()),

## Real-world applications

- An analytics team writes a one-page scoping note (question, metric, data, owner) before starting any request, which is the question set and metric definitions you wrote today.
- A data engineer runs a source inventory and rule baseline before building a pipeline, so the first data quality report shows how many violations exist in the source, as in Example 3.
- A consultant agrees success criteria with a client so that "done" means measurable checks, such as zero remaining rule violations and a reproducible report.
- A hiring manager reading a portfolio looks for exactly the repository checklist on this page: README, tests, a reproducible dataset and a written narrative.

## Daily review

### Key takeaways

- Questions name a metric, a comparison and a decision, and each one lists the columns it needs.
- Metric definitions are written once and include what is excluded.
- Quality rules are functions that count violations, so the raw data gets a baseline.
- Success criteria and a stage plan make "finished" testable.

### Common mistakes

- Writing vague questions such as "analyse sales". The fix is to add the metric, the comparison and the decision.
- Counting duplicated rows with `duplicated()` and forgetting that the first copy is not flagged: `duplicated()` marks the later copies, so the count equals the extra rows.
- Checking relationships on only one side. `customers` having 120 rows says nothing about whether every order's customer is among them: use `isin`.
- Hard-coding the numbers into the plan instead of computing them, so the plan goes stale when the data changes.

### Revision notes

- Five questions: monthly net revenue, return on spend, return rate by category, repeat customers, revenue by country.
- Six rules R1 to R6 with raw violation counts: duplicates, bad quantity, missing customer, country labels, orphan returns, date window.
- Net revenue is valid, not returned, line revenue: quantity times price times one minus the discount.

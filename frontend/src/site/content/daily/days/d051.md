## Objectives

- Read the previous or next row's value with `LAG` and `LEAD` inside an ordered window.
- Change the offset and supply a default value for rows that have no neighbour.
- Compute period-over-period change and percentage change.
- Use `PARTITION BY` so that the comparison never crosses from one entity into another.

## Understand

### Looking sideways in a window

Ranking functions (day 50) assign a position. `LAG` and `LEAD` do something different: for each row they fetch a value from another row in the same ordered window, and place it next to the current row. `LAG(x)` returns `x` from the row **before** the current one; `LEAD(x)` returns it from the row **after**. Before and after are defined by the `ORDER BY` inside `OVER`, so that clause is mandatory for any meaningful result.

An analogy: a list of daily temperatures printed in date order. `LAG(temp)` is the column you would write by copying the list one line down, so that each line also shows yesterday's temperature. `LEAD(temp)` copies it one line up and shows tomorrow's. With both next to the original, subtraction gives the day-to-day change.

### Offset and default

`LAG(x)` looks back one row. A second argument sets the offset: `LAG(x, 2)` looks two rows back. A third argument is a **default**: `LAG(x, 1, 0)` returns 0 instead of NULL when no such row exists. Without a default the first row of every partition has `NULL` for `LAG`, and the last row has `NULL` for `LEAD`, because there is nothing to read. Any arithmetic with NULL gives NULL, so the first change value is also NULL, which is usually honest: there is no earlier period to compare with.

Choose defaults carefully. A default of 0 can create a false change ("revenue jumped from 0 to 5217"), whereas NULL says "no earlier value". Use a default only when the business meaning is real, for example "stock level before the first record was 0".

### PARTITION BY keeps entities apart

If you compare orders and write `LAG(order_date) OVER (ORDER BY order_date)`, each order is compared with the previous order of anyone. To compare each customer's order with that customer's previous order, add `PARTITION BY customer_id`. The first order of each customer then has `NULL` as its previous date, because the window restarts for every partition. Forgetting the partition is the most common error: the query runs and the numbers look plausible but are wrong.

### Period-over-period change

With the previous value on the same row, the change is a subtraction: `revenue - LAG(revenue) OVER (ORDER BY month)`. The percentage change is `100.0 * (revenue - previous) / previous`. Guard against a zero previous value with `NULLIF(previous, 0)`, which returns NULL for a zero and avoids a division-by-zero error. Because window functions cannot be nested inside each other and are awkward to repeat, analysts normally compute `LAG` once in a CTE or subquery, then do the arithmetic in the next step.

### LAG looks at rows, not at calendar periods

`LAG` returns the previous **row**. If the data has no row for a period, the previous row is an earlier period than you might think. In this copy of Northwind orders exist only in 12 different months over three years, so the "previous month" row for April 1996 is January 1996 (Example 5). When real calendar adjacency matters, first build a complete list of periods (day 54 shows how to generate a series) and join the data to it. At minimum, compute the date difference and print it next to the change.

### Dates in PostgreSQL

Subtracting two `date` values gives an integer number of days: `'1996-01-05'::date - '1996-01-01'::date` is 4. This is how Examples 1 and 4 measure gaps between orders.

### Common misconception

Many people expect `LAG` to need a self-join or to look at the previous row of the table. It reads the previous row **of the window**, in the window's `ORDER BY`, after `WHERE` has filtered. If you filter out rows in `WHERE`, they cannot be the previous row. If two rows tie on the sort column, which one counts as previous is arbitrary unless you add a tie-breaker.

### Why it matters

Growth rates, time between events, session gaps, status changes and "did the value change from last time" checks all need the neighbour row. `LAG` and `LEAD` do it in one pass without a self-join.

## Syntax and key functions

```sql-syntax
LAG(expression [, offset [, default]]) OVER ([PARTITION BY group_column] ORDER BY sort_column)
LEAD(expression [, offset [, default]]) OVER ([PARTITION BY group_column] ORDER BY sort_column)
```

`expression` is the value to fetch. `offset` is how many rows back (`LAG`) or forward (`LEAD`), default 1. `default` is returned when that row does not exist, default NULL. `ORDER BY` defines the order; `PARTITION BY` restarts the window per group.

| Function | Returns |
|---|---|
| `LAG(x)` | `x` from the previous row in the window, NULL for the first row |
| `LAG(x, n)` | `x` from `n` rows back |
| `LAG(x, n, d)` | as above, but `d` instead of NULL when there is no such row |
| `LEAD(x)` | `x` from the next row, NULL for the last row |
| `LEAD(x, n, d)` | `x` from `n` rows ahead, `d` when missing |
| `NULLIF(a, b)` | NULL when `a = b`, else `a`; guards a division by zero |

## Learn by example

### Example 1: the previous order date

Order every order by date with `order_id` as a tie-breaker, and fetch the previous order's date. The first row has no previous row, so it shows NULL. Subtracting dates gives days between orders; two orders on the same day give 0.

```sql run
SELECT order_id, order_date,
       LAG(order_date) OVER (ORDER BY order_date, order_id) AS prev_date,
       order_date - LAG(order_date) OVER (ORDER BY order_date, order_id) AS days_since_prev
FROM orders
ORDER BY order_date, order_id
LIMIT 6;
```

```output
order_id | order_date | prev_date | days_since_prev
10248 | 1996-01-01 | NULL | NULL
10332 | 1996-01-01 | 1996-01-01 | 0
10308 | 1996-01-05 | 1996-01-01 | 4
10284 | 1996-01-09 | 1996-01-05 | 4
10260 | 1996-01-13 | 1996-01-09 | 4
10344 | 1996-01-13 | 1996-01-13 | 0
```

### Example 2: LEAD, the next row

`LEAD` reads forward. Here each product in category 1, in price order, is shown with the next more expensive price and the step to it. The dearest product, not shown because of the limit, would have NULL here.

```sql run
SELECT product_id, unit_price,
       LEAD(unit_price) OVER (ORDER BY unit_price, product_id) AS next_price,
       LEAD(unit_price) OVER (ORDER BY unit_price, product_id) - unit_price AS step_up
FROM products
WHERE category_id = 1
ORDER BY unit_price, product_id
LIMIT 6;
```

```output
product_id | unit_price | next_price | step_up
24 | 4.50 | 7.75 | 3.25
75 | 7.75 | 14.00 | 6.25
34 | 14.00 | 14.00 | 0.00
67 | 14.00 | 15.00 | 1.00
70 | 15.00 | 18.00 | 3.00
1 | 18.00 | 18.00 | 0.00
```

### Example 3: offset and default

`LAG(unit_price, 2, 0)` reaches two rows back and returns 0 instead of NULL when there is no such row. Compare it with the plain `LAG` in the next column. The first row has no previous row and the second has no row two back.

```sql run
SELECT product_id, unit_price,
       LAG(unit_price) OVER (ORDER BY product_id) AS prev_price,
       LAG(unit_price, 2, 0) OVER (ORDER BY product_id) AS two_back_or_zero
FROM products
ORDER BY product_id
LIMIT 4;
```

```output
product_id | unit_price | prev_price | two_back_or_zero
1 | 18.00 | NULL | 0
2 | 19.00 | 18.00 | 0
3 | 10.00 | 19.00 | 18.00
4 | 22.00 | 10.00 | 19.00
```

### Example 4: gaps per customer with PARTITION BY

Each customer's orders are compared only with that customer's own previous order. The first order of each customer has a NULL gap. Without `PARTITION BY customer_id` the ANTON row would be compared with an order from a different customer.

```sql run
SELECT customer_id, order_id, order_date,
       order_date - LAG(order_date) OVER (PARTITION BY customer_id ORDER BY order_date, order_id) AS days_since_prev
FROM orders
WHERE customer_id IN ('ALFKI', 'ANTON', 'BONAP')
ORDER BY customer_id, order_date, order_id;
```

```output
customer_id | order_id | order_date | days_since_prev
ALFKI | 10248 | 1996-01-01 | NULL
ALFKI | 10339 | 1997-08-08 | 585
ANTON | 10341 | 1996-10-10 | NULL
ANTON | 10250 | 1998-03-03 | 509
BONAP | 10347 | 1996-04-16 | NULL
BONAP | 10304 | 1998-09-01 | 868
BONAP | 10256 | 1998-09-09 | 8
```

### Example 5: change in monthly revenue

First a CTE builds revenue per month (the discount is included). Then `LAG` fetches the previous month's revenue. The percentage change uses `NULLIF` to protect against zero. Notice that the previous row of 1996-04-01 is 1996-01-01: the data has no orders in February or March, so "previous row" is not "previous month".

```sql run
WITH monthly AS (
  SELECT date_trunc('month', o.order_date)::date AS month,
         ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 2) AS revenue
  FROM orders AS o
  JOIN order_details AS od ON od.order_id = o.order_id
  GROUP BY 1
), with_prev AS (
  SELECT month, revenue, LAG(revenue) OVER (ORDER BY month) AS prev_revenue
  FROM monthly
)
SELECT month, revenue, prev_revenue,
       revenue - prev_revenue AS change,
       ROUND(100.0 * (revenue - prev_revenue) / NULLIF(prev_revenue, 0), 1) AS pct_change
FROM with_prev
ORDER BY month
LIMIT 6;
```

```output
month | revenue | prev_revenue | change | pct_change
1996-01-01 | 5217.41 | NULL | NULL | NULL
1996-04-01 | 18574.06 | 5217.41 | 13356.65 | 256.0
1996-07-01 | 19336.35 | 18574.06 | 762.29 | 4.1
1996-10-01 | 9197.44 | 19336.35 | -10138.91 | -52.4
1997-02-01 | 7450.80 | 9197.44 | -1746.64 | -19.0
1997-05-01 | 3460.08 | 7450.80 | -3990.72 | -53.6
```

### Example 6: find long gaps between a customer's orders

Combine `LAG` with a filter. The gap is calculated in a CTE, and the outer query keeps only gaps of more than 500 days. Both dates appear so that the reader can see the period that was silent. Filtering needs the CTE because a window function cannot be in `WHERE`.

```sql run
WITH gaps AS (
  SELECT customer_id, order_id, order_date,
         LAG(order_date) OVER (PARTITION BY customer_id ORDER BY order_date, order_id) AS prev_order_date
  FROM orders
)
SELECT customer_id, prev_order_date, order_date, order_date - prev_order_date AS gap_days
FROM gaps
WHERE order_date - prev_order_date > 500
ORDER BY gap_days DESC, customer_id
LIMIT 5;
```

```output
customer_id | prev_order_date | order_date | gap_days
BLAUS | 1996-01-13 | 1998-06-06 | 875
BONAP | 1996-04-16 | 1998-09-01 | 868
FOLKO | 1996-10-22 | 1998-12-24 | 793
AROUT | 1996-04-04 | 1997-11-11 | 586
BERGS | 1997-05-05 | 1998-12-12 | 586
```

## Real-world applications

**Growth reporting.** Example 5 is the core of month-over-month and year-over-year dashboards. Replace the month with a year and use `LAG(revenue, 1)` for the previous year, or `LAG(value, 12)` over a complete monthly series for the same month last year.

**Time between events.** Example 4 measures how long a customer was away. The same pattern finds the time between support tickets, sessions or machine readings, and flags long silences as churn signals (Example 6).

**Detecting a change of value.** Comparing a column with its `LAG` (for example a customer's status or a product's price) lists the rows where the value changed, which is the basis of slowly changing history tables.

**Look-ahead checks.** `LEAD` shows what happens next: the next price tier (Example 2), the next scheduled shipment, or the next event in a funnel.

## Daily review

### Key takeaways

- `LAG` reads a value from an earlier row and `LEAD` from a later row, according to the window's `ORDER BY`.
- `LAG(x, n, d)`: `n` rows back, with `d` replacing NULL when there is no such row.
- The first row of each partition has NULL for `LAG`, and the last has NULL for `LEAD`, unless a default is given.
- `PARTITION BY` restarts the window so comparisons stay inside one customer, product or account.
- Change is `x - LAG(x)`, percentage change divides by the previous value with `NULLIF` for safety.
- `LAG` means the previous row, not the previous calendar period.

### Common mistakes

- Forgetting `PARTITION BY`, so the first order of one customer is compared with the last order of another. The query runs without error and the numbers are wrong.
- Omitting `ORDER BY` in `OVER`: the window order is then undefined and the results are meaningless.
- Using a default of 0 for the first row and reporting a huge growth rate. Prefer NULL.
- Dividing by `LAG(x)` that is zero: `division by zero`. Use `NULLIF(LAG(x) OVER (...), 0)`.
- Filtering with `WHERE` before `LAG` when you wanted all rows as neighbours, which removes rows that should have been the previous row. Compute `LAG` first, filter after.
- Assuming one row per month when some months are missing; the change is then across a longer period.

### Revision notes

- `LAG(x, n, d) OVER (PARTITION BY g ORDER BY t)`; `LEAD` is the mirror image.
- Date minus date is an integer number of days in PostgreSQL.
- Compute the neighbour in a CTE, do the arithmetic and filtering outside.

## Objectives

- Combine two tables on a key with `pd.merge`, choosing `inner`, `left`, `right` or `outer` for the question being asked.
- Join on columns with different names (`left_on`, `right_on`) and handle clashing column names with `suffixes`.
- Prove that a merge did not multiply or lose rows by using `validate` and by comparing row counts.
- Use `indicator=True` to see which rows matched, and use it to find unmatched rows (an anti-join).

## Understand

### Why tables are combined

Data is rarely in one table. Orders hold a `customer_id`; the customer names, cities and segments live in a customers table. To report revenue by city you must bring the two together. This is the same operation as the SQL joins of Days 40 and 41, and pandas calls it a **merge**. A merge matches rows of two tables on one or more **key** columns: a row from the left table is paired with every row from the right table that has the same key value. The result is a wider table that holds columns from both.

A useful picture is two stacks of index cards. For every card in the left stack, you look for cards in the right stack carrying the same customer number, and staple each matching pair together. What you do with cards that find no partner is what distinguishes the join types.

### The four join types

`pd.merge(left, right, on="customer_id", how=...)` takes `how` as one of four values.

- `inner` keeps only keys present in both tables. Unmatched rows on either side vanish.
- `left` keeps every row of the left table. Where the right table has no match, its columns are filled with `NaN`.
- `right` is the mirror image: every row of the right table is kept.
- `outer` keeps every row from both tables, filling `NaN` on whichever side has no match.

The default is `inner`, which is the dangerous default for reporting. If you merge orders with customers using `inner` and some orders have an unknown customer, those orders silently disappear from your revenue. When one table is the "main" table of the report and the other only adds attributes, use `left` with the main table on the left, so no main row is lost. Choose `inner` only when you really want the overlap, and `outer` when you want to see everything from both sides, such as when comparing two lists.

### Keys with different names, and clashing columns

If the key is called `customer_id` in one table and `id` in the other, use `left_on="customer_id", right_on="id"`. Both key columns then appear in the result, and you drop the duplicate afterwards. When both tables have a non-key column of the same name, such as `name` or `created`, pandas keeps both and adds the suffixes `_x` and `_y`. These names say nothing, so pass `suffixes=("_order", "_customer")` to get readable ones. Renaming columns before the merge, which Day 73 covered, is another way.

### Row multiplication and validate

The most serious merge bug is invisible: a key that is **not unique** in a table multiplies rows. If the customers table accidentally has two rows for customer 7, every order of customer 7 matches both rows, and the merge produces two copies of each of those orders. The row count rises, and revenue totals are inflated, with no error. Day 40 called this row multiplication. In general, a key that appears `m` times on the left and `n` times on the right produces `m * n` rows for that key.

The defence is the `validate` argument. `validate="many_to_one"` states that the key must be unique in the right table, which is the usual relationship of orders (many) to customers (one). If the right table has duplicate keys, pandas raises a `MergeError` instead of producing the wrong table. The other values are `"one_to_one"`, `"one_to_many"` and `"many_to_many"`, the last of which is a declaration of intent and checks nothing. A second defence is to compare the row counts of the result with the left table after a left merge: if the counts differ, the right key was not unique.

### indicator: where each row came from

`indicator=True` adds a column named `_merge` with the value `left_only`, `right_only` or `both` for each result row. Combined with an `outer` merge, it shows exactly which keys exist in only one table. Filtering on `_merge == "left_only"` after a left merge returns the rows with no match, which is the **anti-join** of Day 41: customers who have never ordered, or orders with no customer record. The indicator is the quickest way to check a merge and a common step in data quality reports.

### Common misconception

Learners often think a merge pairs rows by their position, as if the tables were pasted side by side. A merge pairs by key value, and the row order of the inputs is irrelevant. Another belief is that `how="left"` guarantees the same number of rows as the left table. It guarantees that no left row is lost, but duplicates in the right key add rows. Only a unique right key keeps the count equal.

### Why it matters

Joins are where most silent errors in analytics appear. An inner join drops customers, a duplicated key doubles revenue, and a mismatch in key spelling (`"A-01"` against `"a-01"`) makes every row unmatched. Developing the habit of stating `how`, passing `validate`, and checking counts or `_merge` makes the result trustworthy.

## Syntax and key functions

```python nocheck
pd.merge(left, right, on="key", how="left")
pd.merge(left, right, left_on="a", right_on="b", how="inner", suffixes=("_l", "_r"))
pd.merge(left, right, on="key", how="outer", indicator=True)
pd.merge(left, right, on="key", how="left", validate="many_to_one")
left.merge(right, on="key")      # the same call as a method
```

`on` names a key column that exists in both tables, or a list of columns for a composite key. `how` selects the join type. `validate` raises `pandas.errors.MergeError` when the key relationship is not what you declared. `indicator=True` adds the `_merge` column.

| Option | Effect |
|---|---|
| `how="inner"` | only keys in both tables (default) |
| `how="left"` / `"right"` | all rows of one table, `NaN` where unmatched |
| `how="outer"` | all rows of both tables |
| `left_on`, `right_on` | key columns with different names |
| `suffixes=("_a", "_b")` | names for clashing non-key columns |
| `validate="many_to_one"` | error if right key is not unique |
| `indicator=True` | adds `_merge`: `left_only`, `right_only`, `both` |

## Learn by example

### Example 1: Inner against left

Customer 3 has no orders, and order 104 has a customer 9 that is not in the customers table.

```python run
import pandas as pd
customers = pd.DataFrame({"customer_id": [1, 2, 3], "name": ["Ada", "Bo", "Cy"]})
orders = pd.DataFrame({"order_id": [101, 102, 103, 104], "customer_id": [1, 1, 2, 9], "amount": [50, 20, 30, 70]})
inner = orders.merge(customers, on="customer_id", how="inner")
left = orders.merge(customers, on="customer_id", how="left")
print(inner.to_string(index=False))
print(left.to_string(index=False))
print(inner["amount"].sum(), left["amount"].sum())
```

```output
 order_id  customer_id  amount name
      101            1      50  Ada
      102            1      20  Ada
      103            2      30   Bo
 order_id  customer_id  amount name
      101            1      50  Ada
      102            1      20  Ada
      103            2      30   Bo
      104            9      70  NaN
100 170
```

The inner join lost order 104 and its 70 of revenue. The left join keeps it with `NaN` for the name.

### Example 2: All four join types with the indicator

The same tables are merged four ways, and the row counts are compared. Then `indicator` labels an outer merge.

```python run
import pandas as pd
customers = pd.DataFrame({"customer_id": [1, 2, 3], "name": ["Ada", "Bo", "Cy"]})
orders = pd.DataFrame({"order_id": [101, 102, 103, 104], "customer_id": [1, 1, 2, 9], "amount": [50, 20, 30, 70]})
for how in ["inner", "left", "right", "outer"]:
    print(how, len(orders.merge(customers, on="customer_id", how=how)))
both = orders.merge(customers, on="customer_id", how="outer", indicator=True)
print(both.sort_values(["customer_id", "order_id"])[["customer_id", "order_id", "_merge"]].to_string(index=False))
```

```output
inner 3
left 4
right 4
outer 5
 customer_id  order_id     _merge
           1     101.0       both
           1     102.0       both
           2     103.0       both
           3       NaN right_only
           9     104.0  left_only
```

Customer 3 is `right_only` (never ordered) and customer 9 is `left_only` (unknown customer).

### Example 3: Different key names and suffixes

The key is `cust` in one table and `id` in the other. Both tables have a `created` column, so suffixes keep them apart.

```python run
import pandas as pd
orders = pd.DataFrame({"order_id": [1, 2], "cust": [10, 20], "created": ["2024-01-05", "2024-02-10"]})
people = pd.DataFrame({"id": [10, 20], "name": ["Ada", "Bo"], "created": ["2023-06-01", "2023-09-15"]})
m = orders.merge(people, left_on="cust", right_on="id", suffixes=("_order", "_person")).drop(columns="id")
print(m.to_string(index=False))
```

```output
 order_id  cust created_order name created_person
        1    10    2024-01-05  Ada     2023-06-01
        2    20    2024-02-10   Bo     2023-09-15
```

Without `suffixes` the two date columns would be `created_x` and `created_y`.

### Example 4: Duplicate keys multiply rows, validate catches them

Customer 1 appears twice in the customers table. The merge doubles the orders of customer 1. With `validate` the same merge fails.

```python run
import pandas as pd
from pandas.errors import MergeError
customers = pd.DataFrame({"customer_id": [1, 1, 2], "name": ["Ada", "Ada (old)", "Bo"]})
orders = pd.DataFrame({"order_id": [101, 102, 103], "customer_id": [1, 2, 1], "amount": [50, 30, 20]})
m = orders.merge(customers, on="customer_id", how="left")
print(len(orders), len(m), m["amount"].sum(), orders["amount"].sum())
try:
    orders.merge(customers, on="customer_id", how="left", validate="many_to_one")
except MergeError:
    print("MergeError: customers.customer_id is not unique")
```

```output
3 5 170 100
MergeError: customers.customer_id is not unique
```

Three orders became five rows and revenue rose from 100 to 170. The `validate` check turns the silent bug into an error.

### Example 5: Anti-join and a reconciliation check

Find customers who never ordered, then verify that a safe left merge keeps the row count.

```python run
import pandas as pd
customers = pd.DataFrame({"customer_id": [1, 2, 3, 4], "name": ["Ada", "Bo", "Cy", "Di"]})
orders = pd.DataFrame({"order_id": [101, 102, 103], "customer_id": [1, 1, 3], "amount": [50, 20, 30]})
check = customers.merge(orders, on="customer_id", how="left", indicator=True)
never = check[check["_merge"] == "left_only"]["name"].tolist()
print("never ordered:", never)
safe = orders.merge(customers, on="customer_id", how="left", validate="many_to_one")
print(len(safe) == len(orders), safe["amount"].sum() == orders["amount"].sum())
```

```output
never ordered: ['Bo', 'Di']
True True
```

Customers 2 and 4 have no order rows, and Bo and Di appear only on the left. Here the second merge keeps the order count and total intact.

## Real-world applications

- **Enriching facts with attributes.** An analyst merges orders with customers and products using `left` so revenue by city or category has no missing order lines.
- **Finding gaps between systems.** A data engineer outer-merges the ids from a source system and a warehouse with `indicator=True` and counts `left_only` and `right_only` rows to reconcile them.
- **Guarding a pipeline.** A load step uses `validate="many_to_one"` on every lookup merge so a duplicated dimension row stops the job rather than doubling revenue.
- **Customers with no activity.** The anti-join in Example 5 builds the list for a re-engagement campaign.

## Daily review

### Key takeaways

- A merge pairs rows by key value; `how` decides what happens to rows without a partner.
- Default `inner` drops unmatched rows silently; use `left` with the main table on the left for enrichment.
- Non-unique keys multiply rows; state the expected relationship with `validate` and compare counts.
- `indicator=True` and `_merge` show where rows came from and give the anti-join.

### Common mistakes

- Using the default inner join and finding fewer rows or lower revenue than expected. Pass `how="left"` and check `len`.
- Totals that grow after a merge: the right key has duplicates. Use `validate="many_to_one"`, or `drop_duplicates` on the lookup table first.
- Columns `name_x` and `name_y` appear: both tables have the column. Pass `suffixes` or rename beforehand.
- Everything is unmatched because the key types differ (text `"1"` against number `1`) or spelling differs (`"A-01"` against `"a-01"`). Compare `dtypes` and clean the keys; a merge on mismatched types raises `ValueError: You are trying to merge on object and int64 columns`.

### Revision notes

- `inner` both, `left` all left, `right` all right, `outer` all.
- `validate="many_to_one"` guards the right key.
- `_merge`: `left_only`, `right_only`, `both`.
- Compare `len` before and after.

## Objectives

- Read every sheet of a workbook into a dictionary of DataFrames and describe how the sheets relate to each other.
- Split one wide, repeated sheet into separate tables for customers, products and orders, and say why each repeated group becomes its own table.
- Choose a key for each table (natural or surrogate), test that it is unique, and find rows that violate it.
- Detect orphan rows (a foreign key with no matching parent) and conflicting duplicates before they reach the database.
- Rebuild the original wide sheet from the new tables with joins, to prove that the split lost nothing.

## Understand

### Workbooks as informal databases

Teams use the sheets of a workbook like the tables of a small database: a `Customers` tab, a `Products` tab and an `Orders` tab, with a customer id typed into each order. Other teams use one huge flat sheet in which every order row repeats the customer name, email and city and the product name and price. Both shapes carry the same facts, but only one of them is safe to load into PostgreSQL. A **normalised** schema (Day 92) stores each fact once: one row per customer, one row per product, one row per order, and orders point at customers and products by key. Today you turn the workbook's shape into that schema in pandas, before any SQL runs.

### The reasons to split

Look at a flat sheet where `Ana Silva, ana@example.com, Lisbon` appears on forty order rows. If Ana moves to Porto, forty rows need changing, and any row you miss now contradicts the rest. If you compute "number of customers" with `COUNT(*)` you count orders instead. These are the classic **update**, **insert** and **delete anomalies**, and they all come from the same cause: the sheet mixes facts about different things. The test for a column group is a question: "does this value depend on the whole row, or only on one part of it?" The customer's city depends only on the customer, so it belongs in a customer table. The quantity depends on the order line, so it stays there.

### Keys and relationships

A **key** is a column, or a group of columns, whose value identifies one row. A **natural key** comes from the business: an email address, a product code. A **surrogate key** is an integer the pipeline invents, such as 1, 2, 3, that carries no meaning. Natural keys are readable but can change or be reused (people change email addresses); surrogate keys are stable but need a lookup. Many pipelines keep both: a surrogate `customer_key` as the primary key, and the natural `email` under a unique constraint.

A **relationship** says how two tables connect. Customers to orders is **one-to-many**: one customer has many orders, and each order has one customer. The "many" side stores the "one" side's key as a **foreign key**. Orders to products through order lines is many-to-many, which is why an order-lines table exists between them: it stores one row per product on an order, with the order's key and the product's key. A foreign key whose value has no row in the parent table is an **orphan**. Orphans are not harmless; they make joins drop rows silently.

### Splitting step by step

First, **choose the grain** of the flat sheet: what does one row mean? In an order-line sheet, one row is one product on one order. Second, for each entity, **select its columns and drop duplicate rows** (`df[["email", "name", "city"]].drop_duplicates()`). Third, **test the key**: after deduplication, the key column should still be unique. If `email` appears twice with two different names, the sheet contradicts itself, and you must decide a rule (the latest row wins, or the row is rejected to a review list) rather than hide it. Fourth, **assign surrogate keys** to the new tables, for instance with the row number or `pd.factorize`. Fifth, **replace the repeated columns in the fact table** with the key by merging the lookup back (`merge(customers, on="email")`) and dropping the descriptive columns. Sixth, **verify**: join the tables back together and compare with the original sheet. If the numbers differ, the split lost or duplicated something.

### Several sheets that already relate

When the workbook already has separate sheets, `pd.read_excel(path, sheet_name=None)` returns a dictionary from sheet name to DataFrame. The work is then checking the relationships the author only implied: the key columns are unique in the parent sheets, no key is empty, every foreign key in `Orders` exists in `Customers`, and types agree (a customer id read as an integer in one sheet and as text `"C001"` in another never matches). A check that lists the orphan values is worth more than one that prints `False`.

### Common misconception

Learners believe `drop_duplicates()` on the whole sheet normalises it. It only removes rows that are identical in every column. Two rows for the same customer that differ in a trailing space or in the city are not duplicates to pandas, and both survive. Always deduplicate on the key and inspect the rows that disagree.

### Why it matters

The shape of the target tables decides whether later questions are easy. With one row per customer, "how many customers bought in March" is a single `COUNT(DISTINCT ...)`. In the flat sheet it is a guessing exercise. The keys you choose here are what Day 99 turns into primary and foreign key constraints.

## Syntax and key functions

Splitting a flat sheet into a customer table and an order table:

```python
customers = (flat[["email", "name", "city"]]
             .drop_duplicates(subset="email", keep="last")
             .reset_index(drop=True))
customers["customer_key"] = customers.index + 1

orders = flat.merge(customers[["email", "customer_key"]], on="email", how="left")
orders = orders.drop(columns=["name", "city", "email"])
```

Reading all sheets and checking a relationship:

```python
book = pd.read_excel("sales.xlsx", sheet_name=None)       # dict of DataFrames
customers, orders = book["Customers"], book["Orders"]
orphans = orders[~orders["customer_id"].isin(customers["customer_id"])]
```

| Item | What it does or returns |
|---|---|
| `df.drop_duplicates(subset, keep)` | Rows with the first or last occurrence of each key. |
| `df.duplicated(subset, keep=False)` | Mask of every row involved in a duplicate. |
| `df.groupby(key)[col].nunique()` | How many different values each key has; above 1 is a conflict. |
| `df.merge(other, on, how, validate)` | Join; `validate="m:1"` raises if the right side repeats a key. |
| `Series.isin(values)` | Mask of values found in another column (orphan test with `~`). |
| `pd.factorize(s)` | Integer codes and the unique values, in order of appearance. |
| `Series.is_unique` | True when no value repeats. |
| `pd.read_excel(path, sheet_name=None)` | Dictionary of all sheets. |

## Learn by example

### Example 1: Three sheets and their implied relationships

A local example builds a three-sheet workbook (`Customers`, `Products`, `Orders`), reads all sheets at once and checks the relationships: key columns unique, foreign keys present. `openpyxl` is needed to write and read the file, so this runs locally; the checks themselves are plain pandas.

```python local
import os
import tempfile

import pandas as pd
from openpyxl import Workbook

with tempfile.TemporaryDirectory() as folder:
    path = os.path.join(folder, "sales.xlsx")
    wb = Workbook()
    ws = wb.active
    ws.title = "Customers"
    for row in [["customer_id", "name"], [1, "Ana"], [2, "Ben"]]:
        ws.append(row)
    ws = wb.create_sheet("Products")
    for row in [["product_id", "title", "price"], ["P1", "Pen", 2.5], ["P2", "Book", 12.0]]:
        ws.append(row)
    ws = wb.create_sheet("Orders")
    for row in [["order_id", "customer_id", "product_id", "qty"],
                [100, 1, "P1", 2], [101, 2, "P2", 1], [102, 3, "P1", 4]]:
        ws.append(row)
    wb.save(path)

    book = pd.read_excel(path, sheet_name=None)
    print({name: frame.shape for name, frame in book.items()})
    orders = book["Orders"]
    print(book["Customers"]["customer_id"].is_unique, book["Products"]["product_id"].is_unique)
    orphan_customers = orders[~orders["customer_id"].isin(book["Customers"]["customer_id"])]
    orphan_products = orders[~orders["product_id"].isin(book["Products"]["product_id"])]
    print(orphan_customers["order_id"].tolist(), orphan_products["order_id"].tolist())
```

```output
{'Customers': (2, 2), 'Products': (2, 3), 'Orders': (3, 4)}
True True
[102] []
```

Order 102 points at customer 3, who is in no sheet. A join between `Orders` and `Customers` would drop that order without a warning, so the check lists it first.

### Example 2: Split a flat sheet into three tables (browser-safe)

The flat sheet repeats customer and product columns on every order line. The code builds a customer table (one row per email) and a product table (one row per product code), assigns surrogate keys and replaces the descriptive columns in the order lines with those keys. `validate="m:1"` asks pandas to raise if a lookup table repeated a key.

```python run
import pandas as pd

flat = pd.DataFrame({
    "order_id": [1, 1, 2, 3, 3],
    "email": ["ana@x.com", "ana@x.com", "ben@x.com", "ana@x.com", "ana@x.com"],
    "name": ["Ana", "Ana", "Ben", "Ana", "Ana"],
    "city": ["Lisbon", "Lisbon", "Porto", "Lisbon", "Lisbon"],
    "code": ["P1", "P2", "P1", "P1", "P2"],
    "title": ["Pen", "Book", "Pen", "Pen", "Book"],
    "price": [2.5, 12.0, 2.5, 2.5, 12.0],
    "qty": [2, 1, 4, 1, 3],
})

customers = flat[["email", "name", "city"]].drop_duplicates(subset="email").reset_index(drop=True)
customers["customer_key"] = customers.index + 1
products = flat[["code", "title", "price"]].drop_duplicates(subset="code").reset_index(drop=True)
products["product_key"] = products.index + 1

lines = (flat[["order_id", "email", "code", "qty"]]
         .merge(customers[["email", "customer_key"]], on="email", how="left", validate="m:1")
         .merge(products[["code", "product_key"]], on="code", how="left", validate="m:1")
         [["order_id", "customer_key", "product_key", "qty"]])
print(len(flat), len(customers), len(products), len(lines))
print(lines)
```

```output
5 2 2 5
   order_id  customer_key  product_key  qty
0         1             1            1    2
1         1             1            2    1
2         2             2            1    4
3         3             1            1    1
4         3             1            2    3
```

Five order lines now reference two customers and two products. Customer data appears once.

### Example 3: Conflicting duplicates

The same email appears with two different names, and one product code has two prices. `drop_duplicates(subset=key)` would keep one silently. The code finds the keys with more than one distinct value, shows the rows that disagree and applies an explicit rule (the last row wins), reporting what it discarded.

```python run
import pandas as pd

flat = pd.DataFrame({
    "email": ["ana@x.com", "ben@x.com", "ana@x.com", "cy@x.com"],
    "name": ["Ana Silva", "Ben", "Ana S.", "Cy"],
    "order_id": [1, 2, 3, 4],
})

distinct = flat.groupby("email")["name"].nunique()
conflict_keys = distinct[distinct > 1].index.tolist()
print(conflict_keys)
print(flat[flat["email"].isin(conflict_keys)].sort_values("order_id")[["email", "name"]])

chosen = flat.drop_duplicates(subset="email", keep="last")
discarded = flat[~flat.index.isin(chosen.index)]
print(chosen.sort_values("email")[["email", "name"]].to_string(index=False))
print("discarded:", discarded["name"].tolist())
```

```output
['ana@x.com']
       email       name
0  ana@x.com  Ana Silva
2  ana@x.com     Ana S.
    email   name
ana@x.com Ana S.
ben@x.com    Ben
 cy@x.com     Cy
discarded: ['Ana Silva']
```

"Last row wins" is a decision about the business, not a technical fact. It is written in the code and reported, so the owner of the data can disagree with it.

### Example 4: Declare the schema and prove the split with a join

The tables are stored in an in-memory `sqlite3` database with primary keys and foreign key columns (the same ideas as PostgreSQL; the SQL type names differ slightly). Joining the three tables back together reproduces the original rows, which proves the split lost nothing. The comparison sorts both sides, because a join does not promise an order.

```python run
import sqlite3
import pandas as pd

flat = pd.DataFrame({
    "order_id": [1, 1, 2],
    "name": ["Ana", "Ana", "Ben"],
    "title": ["Pen", "Book", "Pen"],
    "qty": [2, 1, 4],
})
customers = pd.DataFrame({"customer_key": [1, 2], "name": ["Ana", "Ben"]})
products = pd.DataFrame({"product_key": [1, 2], "title": ["Pen", "Book"]})
lines = pd.DataFrame({"order_id": [1, 1, 2], "customer_key": [1, 1, 2], "product_key": [1, 2, 1], "qty": [2, 1, 4]})

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE customer (customer_key INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE product (product_key INTEGER PRIMARY KEY, title TEXT NOT NULL);
CREATE TABLE order_line (
    order_id INTEGER, customer_key INTEGER REFERENCES customer(customer_key),
    product_key INTEGER REFERENCES product(product_key), qty INTEGER,
    PRIMARY KEY (order_id, product_key));
""")
customers.to_sql("customer", conn, if_exists="append", index=False)
products.to_sql("product", conn, if_exists="append", index=False)
lines.to_sql("order_line", conn, if_exists="append", index=False)

back = pd.read_sql("""
SELECT l.order_id, c.name, p.title, l.qty
FROM order_line l JOIN customer c USING (customer_key) JOIN product p USING (product_key)
ORDER BY l.order_id, p.title""", conn)
want = flat.sort_values(["order_id", "title"]).reset_index(drop=True)
print(back.equals(want))
print(conn.execute("SELECT COUNT(*) FROM order_line").fetchone()[0])
```

```output
True
3
```

`to_sql` with `if_exists="append"` keeps the declared keys (Day 94: `replace` would drop them). The `True` confirms that the normalised tables and the joins carry the original information.

## Real-world applications

- **Order exports from a shop.** A weekly flat export repeats every customer on every line. Splitting gives a customer table that is updated once and an order-line table that only grows.
- **HR workbooks.** Employees, departments and assignments arrive as three tabs. Checking the implied relationships finds employees assigned to a department that has no row, before the foreign key rejects the load.
- **Conflicting master data.** Two regional teams enter the same product code with different prices. The conflict query lists them for a human decision instead of picking one at random.
- **Migration proofs.** After moving a legacy sheet into tables, the join-back comparison is the evidence for the sign-off.

## Daily review

### Key takeaways

- A flat sheet mixes facts about different things; a normalised design stores each fact once.
- Choose the grain, deduplicate each entity on its key and test that the key is unique.
- Natural keys are meaningful but can change; surrogate keys are stable integers.
- Check implied relationships: unique parents, no empty keys, no orphans.
- Prove the split by joining back and comparing.

### Common mistakes

- **`drop_duplicates()` on all columns.** Near-duplicates survive. Deduplicate on the key and list disagreements.
- **Keeping one conflicting row silently.** Report the keys with `nunique() > 1` and name the rule.
- **Key type mismatch.** `1` in one sheet and `"1"` in another never join and `merge` gives empty matches. Convert both to one type first.
- **A many-to-many merge.** Merging on a column that is not unique multiplies rows. Use `validate="m:1"`.
- **Orphans dropped by an inner join.** Counts shrink without error. Run the orphan check before joining.

### Revision notes

- Grain first, then entity tables, then keys, then facts with keys.
- `drop_duplicates(subset=key)`, `groupby(key)[col].nunique()`, `isin` for orphans, `merge(validate=...)`.
- Surrogate key: `index + 1` or `factorize`.
- Verify with a join-back comparison.

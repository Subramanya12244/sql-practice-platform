## Understand

### Why pipelines need to survive failure

A scheduled pipeline runs unattended, often at night, against systems that you do not control. Some failures are **transient**: a network timeout, a database that is briefly busy, a rate-limit response from an API (covered in the API days earlier on the engineering path). Retrying a few minutes later usually succeeds. Other failures are **deterministic**: a bug, a missing column, a wrong password. Retrying those wastes time and hides the problem. A well-designed pipeline retries the first kind automatically, fails fast and loudly on the second, and is safe to run again when a person decides to rerun it.

Airflow is the scheduler that runs a pipeline written as a **DAG**, a directed acyclic graph of tasks (Days 157 to 159). It cannot run in this course's tests or browser, so this lesson shows the Airflow code as text and checks every behaviour with a pure-Python model that you can run: tasks as functions, dependencies as a dictionary, a fake clock instead of real waiting.

### Retries

Each task can be given `retries`, the number of extra attempts after the first failure, so `retries=3` means up to four attempts in total. `retry_delay` is a `timedelta` that Airflow waits between attempts. With `retry_exponential_backoff=True` the wait grows with each attempt (the waits roughly double, with a small deterministic jitter added by Airflow), and `max_retry_delay` caps it. While a task is waiting for its next attempt its state is `up_for_retry`; after the last failed attempt it is `failed`. The tasks downstream of a failed task do not run; they get the state `upstream_failed`, unless a trigger rule says otherwise. Retries are usually set for the whole DAG in `default_args` and overridden for a task that needs more or fewer.

```python
from datetime import datetime, timedelta
from airflow.decorators import dag, task  # in Airflow 3: from airflow.sdk import dag, task

default_args = {
    "retries": 3,
    "retry_delay": timedelta(minutes=5),
    "retry_exponential_backoff": True,
    "max_retry_delay": timedelta(minutes=30),
}

@dag(schedule="@daily", start_date=datetime(2025, 1, 1), catchup=False, default_args=default_args)
def orders_daily():
    @task
    def extract(ds=None):
        return f"extracted {ds}"

    extract()

orders_daily()
```

Retrying only helps if the task can be run twice without harm. A task that sends an email or appends rows is changed by every attempt. That brings us to idempotence, below. Also set `execution_timeout` so that a hung task fails and is retried and does not block the pipeline forever.

### Logical date, data interval and catchup

A DAG with `schedule="@daily"` creates one **DAG run** per day. Each run has a **data interval**: the period of data it is responsible for, for example 2025-01-03 00:00 to 2025-01-04 00:00. The run starts when the interval has ended, so the run for 3 January starts just after midnight on 4 January. The start of the interval is the **logical date** of the run (named `execution_date` in older versions), and the template value `{{ ds }}` renders it as `2025-01-03`. A task that processes `{{ ds }}` rather than "today" does the same work whenever it runs, which is the point: you can run the January 3 run on 20 January and it still processes January 3.

`start_date` is the first interval. `catchup` decides what happens when the scheduler finds intervals that have not run yet (for example, a DAG that is switched on three weeks after its start date). With `catchup=True` Airflow creates a run for each missed interval; with `catchup=False` it creates a run only for the latest one. A **backfill** is the deliberate version of catchup: running a DAG for a chosen range of past dates, for example after a bug fix or when a new DAG needs history. In Airflow 2.x the command is `airflow dags backfill -s 2025-01-01 -e 2025-01-05 orders_daily`; Airflow 3 manages backfills through the UI, the API and `airflow backfill create`. Clearing the state of a task or run in the UI makes the scheduler run it again, which is the way to rerun a single failed day.

### Idempotent tasks

A task is **idempotent** if running it once or many times for the same logical date leaves the system in the same state. Retries, manual reruns, backfills that overlap an earlier run and a scheduler that starts a task twice all become safe. The usual techniques are to write to a partition that is determined by the logical date and replace it (delete the day's rows then insert, or overwrite the day's file), to use an upsert keyed on the natural key (`INSERT ... ON CONFLICT DO UPDATE` in PostgreSQL), and to avoid anything that depends on "now". The misconception to avoid is that idempotence is only a database detail. It is a property of the whole task, including files written, messages sent and counters incremented. The symptoms of its absence are duplicated rows after a retry and totals that grow every time someone clicks Clear.

### SLAs

In Airflow 2.x a task can have an `sla` (a `timedelta`): the time after the start of the DAG run by which the task should have finished. A task that finishes later, or has not finished, is recorded as an SLA miss and the DAG's `sla_miss_callback` is called. The task is not stopped: an SLA is a notification, not a timeout. The SLA mechanism was removed in Airflow 3.0 and replaced by newer deadline features, so check the documentation of the version you run. The idea transfers: define how late is too late, measure it, and tell someone.

### Why it matters

These settings are the difference between a pipeline that pages someone every week and one that quietly recovers. The common failure modes are retries on a non-idempotent task (duplicates), backfills with `catchup` surprises (hundreds of runs at once) and tasks that use the current date instead of the logical date (a rerun silently loads the wrong day).

## Syntax and key functions

```python
default_args = {"retries": 2, "retry_delay": timedelta(minutes=5)}
BashOperator(task_id="load", bash_command="load.sh {{ ds }}", retries=3, execution_timeout=timedelta(minutes=10))
```

| Setting | Meaning |
|---|---|
| `retries` | Extra attempts after the first failure (total attempts = retries + 1). |
| `retry_delay` | Wait between attempts (`timedelta`). |
| `retry_exponential_backoff`, `max_retry_delay` | Growing wait between attempts, capped. |
| `execution_timeout` | Maximum run time of one attempt; exceeding it fails the attempt. |
| `catchup` | Whether missed past intervals are run when the DAG is enabled. |
| `max_active_runs` | Maximum number of DAG runs in flight at once (limits a backfill). |
| `{{ ds }}`, `data_interval_start` | Template values for the logical date and interval start. |
| `sla`, `sla_miss_callback` | Airflow 2.x deadline notification (removed in Airflow 3). |

## Learn by example

### Example 1: A DAG as a dictionary, and a run order

A DAG is a mapping from each task to its upstream tasks. A valid run order puts every task after all of its upstream tasks.

```python run
def topo_order(deps):
    remaining = {t: set(u) for t, u in deps.items()}
    order = []
    while remaining:
        ready = sorted(t for t, u in remaining.items() if not u)
        if not ready:
            raise ValueError("cycle")
        t = ready[0]
        order.append(t)
        del remaining[t]
        for u in remaining.values():
            u.discard(t)
    return order

deps = {"extract": [], "clean": ["extract"], "load": ["clean"], "report": ["load"], "audit": ["load"]}
print(topo_order(deps))
try:
    topo_order({"a": ["b"], "b": ["a"]})
except ValueError as e:
    print("error:", e)
```

```output
['extract', 'clean', 'load', 'audit', 'report']
error: cycle
```

The order is `extract`, `clean`, `load`, `audit`, `report`: the two tasks that wait for `load` could run in either order, and the model picks alphabetical order so the output is stable. A graph with a cycle has no valid order, which is why Airflow refuses a DAG that contains one.

### Example 2: Retries with a fake clock

A flaky task fails twice before succeeding. The clock is a number that the model advances instead of sleeping.

```python run
def run_with_retries(fn, retries, delay, exponential=False, cap=None):
    clock = 0
    attempt = 0
    while True:
        attempt += 1
        try:
            return {"state": "success", "attempts": attempt, "waited": clock, "result": fn(attempt)}
        except RuntimeError:
            if attempt > retries:
                return {"state": "failed", "attempts": attempt, "waited": clock, "result": None}
            wait = delay * (2 ** (attempt - 1)) if exponential else delay
            if cap is not None:
                wait = min(wait, cap)
            clock += wait

def flaky(fail_times):
    def fn(attempt):
        if attempt <= fail_times:
            raise RuntimeError("timeout")
        return "ok"
    return fn

print(run_with_retries(flaky(2), retries=3, delay=300))
print(run_with_retries(flaky(2), retries=3, delay=300, exponential=True))
print(run_with_retries(flaky(2), retries=3, delay=300, exponential=True, cap=400))
print(run_with_retries(flaky(5), retries=3, delay=300))
```

```output
{'state': 'success', 'attempts': 3, 'waited': 600, 'result': 'ok'}
{'state': 'success', 'attempts': 3, 'waited': 900, 'result': 'ok'}
{'state': 'success', 'attempts': 3, 'waited': 700, 'result': 'ok'}
{'state': 'failed', 'attempts': 4, 'waited': 900, 'result': None}
```

With a fixed delay of 300 seconds, two failures cost 600 seconds of waiting and three attempts. With plain doubling the waits are 300 and 600, so 900 seconds; capped at 400 they are 300 and 400, so 700. When the task fails five times and only three retries are allowed, it makes four attempts, waits 900 seconds in total and ends `failed`. Airflow adds jitter to its own backoff, so real waits differ slightly; the model only shows the shape.

### Example 3: A failed task makes its downstream tasks `upstream_failed`

Run a whole DAG model with states.

```python run
def run_dag(deps, behaviour):
    states = {}
    order = []
    remaining = {t: set(u) for t, u in deps.items()}
    while remaining:
        t = sorted(x for x, u in remaining.items() if not u)[0]
        order.append(t)
        del remaining[t]
        for u in remaining.values():
            u.discard(t)
    for t in order:
        if any(states[u] != "success" for u in deps[t]):
            states[t] = "upstream_failed"
        else:
            states[t] = behaviour.get(t, "success")
    return states

deps = {"extract": [], "clean": ["extract"], "load": ["clean"], "report": ["load"], "audit": ["load"]}
print(run_dag(deps, {}))
print(run_dag(deps, {"clean": "failed"}))
```

```output
{'extract': 'success', 'clean': 'success', 'load': 'success', 'audit': 'success', 'report': 'success'}
{'extract': 'success', 'clean': 'failed', 'load': 'upstream_failed', 'audit': 'upstream_failed', 'report': 'upstream_failed'}
```

In the second run `clean` fails, so `load`, `audit` and `report` all report `upstream_failed` and never start: a failed task stops everything below it, and the task to fix is the one with the state `failed`.

### Example 4: Dates of a backfill

Generate the logical dates for a backfill and the data interval of each run.

```python run
from datetime import date, timedelta

def backfill_dates(start, end):
    days = (end - start).days
    return [start + timedelta(days=i) for i in range(days + 1)]

dates = backfill_dates(date(2025, 1, 29), date(2025, 2, 2))
for d in dates:
    print(d.isoformat(), "interval", d.isoformat(), "to", (d + timedelta(days=1)).isoformat())
print(len(dates))
print(len(backfill_dates(date(2025, 1, 1), date(2025, 3, 31))))
```

```output
2025-01-29 interval 2025-01-29 to 2025-01-30
2025-01-30 interval 2025-01-30 to 2025-01-31
2025-01-31 interval 2025-01-31 to 2025-02-01
2025-02-01 interval 2025-02-01 to 2025-02-02
2025-02-02 interval 2025-02-02 to 2025-02-03
5
90
```

Five daily runs cover 29 January to 2 February, each responsible for its own 24 hours, and a quarter of backfill (1 January to 31 March) is 90 runs. That number is why `max_active_runs` matters: without a limit, ninety runs of a heavy DAG could start together. This model treats the end date as included, as the Airflow 2.x command does; check how your version treats the end of a range before relying on it.

### Example 5: Idempotent and non-idempotent loads

Load two days of orders with append and with delete-then-insert, repeat the first day, and count the rows.

```python run
import sqlite3

source = {
    "2025-01-01": [(1, 120), (2, 80)],
    "2025-01-02": [(3, 200)],
}

def setup():
    db = sqlite3.connect(":memory:")
    db.execute("CREATE TABLE orders_daily (order_id INTEGER, amount INTEGER, load_date TEXT)")
    return db

def load_append(db, day):
    db.executemany("INSERT INTO orders_daily VALUES (?, ?, ?)", [(i, a, day) for i, a in source[day]])

def load_replace(db, day):
    db.execute("DELETE FROM orders_daily WHERE load_date = ?", (day,))
    load_append(db, day)

for name, loader in [("append", load_append), ("replace", load_replace)]:
    db = setup()
    for day in ["2025-01-01", "2025-01-02", "2025-01-01"]:
        loader(db, day)
    rows, total = db.execute("SELECT COUNT(*), SUM(amount) FROM orders_daily").fetchone()
    db.close()
    print(name, rows, total)
```

```output
append 5 600
replace 3 400
```

The days are loaded in the order 1 January, 2 January and then 1 January again, as a retry or an overlapping backfill would do. The append loader ends with 5 rows and a total of 600 because the first day is counted twice; the replace loader ends with 3 rows and a total of 400, the true figures. Replacing the partition of the logical date makes the repeated run harmless.

### Example 6: Detecting a missed SLA

Compare the finish time of each task with its SLA, measured from the start of the run, using seconds on a fake clock.

```python run
runs = [
    {"task": "extract", "finished": 120, "sla": 300},
    {"task": "load", "finished": 840, "sla": 600},
    {"task": "report", "finished": 1500, "sla": 1800},
]
misses = [r["task"] for r in runs if r["finished"] > r["sla"]]
print(misses)
for r in runs:
    print(r["task"], r["finished"] - r["sla"])
```

```output
['load']
extract -180
load 240
report -300
```

Only `load` misses: it finished 240 seconds after its deadline. The other tasks finished 180 and 300 seconds early (negative numbers). An SLA miss is a notification and does not stop the task; the callback would send the message.

## Real-world applications

- **Rate-limited API extraction.** Retries with exponential backoff and a cap absorb 429 responses without a human (Example 2).
- **Safe reruns after a fix.** After a bug is fixed, clearing the failed days re-runs them, and an idempotent load replaces the bad data instead of adding to it (Example 5).
- **Loading history for a new DAG.** A backfill over a quarter, limited by `max_active_runs`, fills a warehouse table (Example 4).
- **Operational reporting.** A deadline for the morning report, tracked as an SLA, lets the on-call engineer know before the business does (Example 6).

## Daily review

### Key takeaways

- `retries` are extra attempts; add `retry_delay`, backoff and a cap; retry only transient failures.
- A failed task leaves its downstream tasks `upstream_failed`.
- A run's logical date and data interval define the data it owns; use `{{ ds }}` and not "today".
- A backfill reruns a chosen date range; limit it with `max_active_runs`.
- Idempotent tasks replace a partition or upsert on a key, so reruns are safe.
- SLAs (Airflow 2.x) notify; they do not stop a task.

### Common mistakes

- Retrying a task that appends rows, so every retry duplicates the data. Replace the partition or upsert.
- Using `datetime.now()` in a task, so a rerun loads today's data instead of the logical date's.
- Enabling `catchup=True` on an old `start_date` and starting hundreds of runs at once.
- Retrying forever on a deterministic error, hiding a bug. Cap retries and alert after the last one.
- Expecting an SLA to cancel a slow task. Use `execution_timeout` for that.

### Revision notes

- Total attempts = retries + 1; states `up_for_retry`, `failed`, `upstream_failed`.
- Logical date = start of the data interval; run starts after the interval ends.
- `catchup`, backfill, `max_active_runs`, clear to rerun.
- Idempotent = replace partition, upsert, no dependence on now.

## Understand

### Two kinds of work on data

A **workload** is the pattern of queries a database is asked to answer. Two patterns dominate, and almost every design decision in data engineering follows from which one you are serving.

**OLTP** stands for online transaction processing. It runs the operational systems of a business: the shop that records an order, the bank that moves money, the app that updates a profile. OLTP queries are many, short and about single things: "insert this order", "change the status of order 7", "fetch the customer with id 4". Each touches a handful of rows, usually found through a primary key or an index, and each is a **transaction** (Day 91) that must be fast and must leave the data consistent. Thousands of users run them at once. The database holds the current state: when a customer changes address, the old address is overwritten.

**OLAP** stands for online analytical processing. It answers questions about the business as a whole: "revenue by country by month for two years", "which products were returned most often", "how did conversion change after the redesign". OLAP queries are few, long-running and about many things: they scan millions of rows but need only a few columns of them, group them and aggregate with `SUM`, `COUNT` and `AVG`. The data is mostly read, loaded in batches (Days 120 to 131), and history is kept because the questions are about change over time.

A useful comparison: OLTP is the till at a supermarket, OLAP is the head office report on last quarter's sales. You would not run the quarterly report on the till, and you would not ring up customers at head office.

| | OLTP | OLAP |
|---|---|---|
| Typical query | Fetch or change one order | Revenue by country and month |
| Rows touched | A few | Millions |
| Columns used | Most of the row | A few |
| Users | Thousands, concurrent | Few analysts and dashboards |
| Writes | Constant small inserts and updates | Periodic bulk loads |
| History | Current state | Full history |
| Design | Normalised: each fact stored once | Denormalised: wide tables built for aggregation |

### Why not one database for both?

A long analytical scan competes with transactions for CPU, disk and locks, and a slow report can make the checkout page slow. The schema is also different: the normalised tables that keep OLTP data consistent need many joins to answer an analytical question, which is slow and awkward. For these reasons companies copy data from the operational databases into a separate system built for analysis. That copy is the job of the ETL pipelines you have been building.

### Row stores and column stores

A **row store** keeps all the values of a row next to each other on disk: `(1, Ana, DE, ...)`, then `(2, Ben, FR, ...)`. To fetch or update order 7 the database reads one place and gets every column. PostgreSQL, MySQL and SQLite store tables this way, which is ideal for OLTP. The same layout is wasteful for analytics: to sum one column, the database must read every row in full, including the columns it does not need.

A **column store** keeps all the values of one column together: all the order dates, then all the countries, then all the amounts. A query that sums the amounts reads only the amount column and skips the rest. Values in one column have the same type and often repeat (a country has a few dozen distinct values), so they **compress** very well, which reduces the amount read again. The price is that reconstructing or updating a whole row touches many places, so column stores are slow for single-row writes. Parquet files and warehouse engines such as BigQuery, Redshift, Snowflake and ClickHouse are column-oriented. Do not confuse the storage layout with the SQL you write: the same `SELECT SUM(amount) ... GROUP BY country` runs on both.

### Warehouses and marts

A **data warehouse** is a database designed for OLAP that integrates data from several source systems (orders, payments, marketing) into one consistent, historical store. It is loaded by pipelines, read by analysts, dashboards and models, and rarely edited by hand. Its job is to give one agreed answer to a business question regardless of how many systems hold the raw facts.

A **data mart** is a smaller, subject-focused slice prepared for one team: a sales mart, a finance mart, a marketing mart. A mart can be a subset of the warehouse or built from it with a summary query. Marts are easier to understand and faster to query because they contain only the tables and columns the team needs, and they let each team have its own definitions of a few metrics while sharing the same underlying data. The usual flow is: source systems (OLTP) to a landing or staging area, then the warehouse, then marts, then reports.

```text
 OLTP sources        pipelines          warehouse (OLAP)        marts          consumers
 ---------------     -----------     ---------------------   -----------     -------------
 shop database  -->                                           sales mart  --> dashboards
 payments db    -->  extract,        integrated, historical    finance mart --> finance reports
 marketing api  -->  clean, load  -->  fact and dimension  -->  marketing   --> analysts, models
                                       tables
```

### Common misconception

Learners often say "OLAP is the opposite of OLTP and replaces it". They are partners, not rivals: OLTP creates the data, OLAP analyses a copy of it. Another belief is that "a warehouse is just a big database". A big PostgreSQL database with the shop's tables is still an OLTP schema; what makes a warehouse is the purpose (analytical reads), the integration of sources, the kept history and a schema designed for aggregations. A third misconception is that column stores are always better: for lookups and updates of single rows they are worse.

### Why it matters

An engineer who knows the workload picks the right tool and the right schema. A reporting query that scans the live orders table on the production database is a common cause of outages; a dashboard that joins eight normalised tables on every refresh is a common cause of slow reports. Separating the two workloads, and loading a purpose-built analytical store, removes both problems.

## Syntax and key functions

An OLTP-style statement (few rows, found by key) and an OLAP-style statement (many rows, grouped):

```sql-syntax
-- OLTP: one row by primary key, one row updated
SELECT * FROM purchase WHERE order_id = 3;
UPDATE purchase SET status = 'refunded' WHERE order_id = 3;

-- OLAP: scan, join, group, aggregate
SELECT c.country, date_trunc('month', o.order_date) AS month, SUM(i.qty * p.unit_price) AS revenue
FROM purchase o
JOIN customer c ON c.customer_id = o.customer_id
JOIN order_item i ON i.order_id = o.order_id
JOIN product p ON p.product_id = i.product_id
GROUP BY c.country, date_trunc('month', o.order_date);

-- Building a mart table from the source schema
CREATE TABLE mart_daily_sales AS SELECT ... GROUP BY ...;
```

| Item | What it does or returns |
|---|---|
| `WHERE pk = value` | Point lookup; uses the primary-key index, touches one row. |
| `GROUP BY` with `SUM`, `COUNT` | Aggregates many rows into few; the core OLAP pattern. |
| `date_trunc('month', d)` | Rounds a date down to the first day of its month. |
| `CREATE TABLE t AS SELECT ...` | Creates and fills a table from a query; the basic way to build a mart or summary. |
| Row store | Stores each row's values together; fast row access. |
| Column store | Stores each column together; fast scans of few columns, good compression. |
| Data mart | A subject-focused subset or summary prepared for one team. |

## Learn by example

The examples use a small shop schema: `customer`, `product`, `purchase` and `order_item`. Each SQL block creates its own tables, and a short `python run` example shows the layout difference between row and column stores.

### Example 1: An OLTP workload, small and by key

A point lookup and a one-row update touch a single row each, found by primary key. The update changes the current state and keeps no history, which is typical for OLTP. The final query shows the row after the change.

```sql run
CREATE TABLE customer (customer_id int PRIMARY KEY, name text NOT NULL, country text NOT NULL);
CREATE TABLE product (product_id int PRIMARY KEY, name text NOT NULL, category text NOT NULL, unit_price numeric(8,2) NOT NULL);
CREATE TABLE purchase (order_id int PRIMARY KEY, customer_id int NOT NULL REFERENCES customer, order_date date NOT NULL, status text NOT NULL);
CREATE TABLE order_item (order_id int REFERENCES purchase, line_no int, product_id int NOT NULL REFERENCES product, qty int NOT NULL, PRIMARY KEY (order_id, line_no));
INSERT INTO customer VALUES (1, 'Ana', 'DE'), (2, 'Ben', 'FR'), (3, 'Cy', 'DE'), (4, 'Di', 'US');
INSERT INTO product VALUES (1, 'Pen', 'office', 2.00), (2, 'Desk', 'furniture', 150.00), (3, 'Lamp', 'furniture', 40.00);
INSERT INTO purchase VALUES (1, 1, '2026-01-05', 'paid'), (2, 2, '2026-01-12', 'paid'), (3, 1, '2026-02-03', 'paid'), (4, 3, '2026-02-10', 'refunded'), (5, 4, '2026-02-14', 'paid'), (6, 2, '2026-03-01', 'paid');
INSERT INTO order_item VALUES (1, 1, 1, 10), (1, 2, 3, 1), (2, 1, 2, 1), (3, 1, 3, 2), (3, 2, 1, 5), (4, 1, 2, 1), (5, 1, 1, 20), (5, 2, 3, 1), (6, 1, 2, 2);
UPDATE purchase SET status = 'refunded' WHERE order_id = 3;
SELECT order_id, customer_id, status FROM purchase WHERE order_id = 3;
```

```output
order_id | customer_id | status
3 | 1 | refunded
```

The table now says `refunded` and the earlier value is gone. An analytical question such as "how many orders were refunded in February" is awkward on a table that overwrites state, which is one reason warehouses keep history.

### Example 2: An OLAP workload, wide and aggregated

This query reads every order line, joins to three tables and aggregates to a few result rows: revenue by country and month for paid orders. It touches many rows but uses only a few columns. On a large table this is the query that must not run on the production database.

```sql run
CREATE TABLE customer (customer_id int PRIMARY KEY, name text NOT NULL, country text NOT NULL);
CREATE TABLE product (product_id int PRIMARY KEY, name text NOT NULL, category text NOT NULL, unit_price numeric(8,2) NOT NULL);
CREATE TABLE purchase (order_id int PRIMARY KEY, customer_id int NOT NULL REFERENCES customer, order_date date NOT NULL, status text NOT NULL);
CREATE TABLE order_item (order_id int REFERENCES purchase, line_no int, product_id int NOT NULL REFERENCES product, qty int NOT NULL, PRIMARY KEY (order_id, line_no));
INSERT INTO customer VALUES (1, 'Ana', 'DE'), (2, 'Ben', 'FR'), (3, 'Cy', 'DE'), (4, 'Di', 'US');
INSERT INTO product VALUES (1, 'Pen', 'office', 2.00), (2, 'Desk', 'furniture', 150.00), (3, 'Lamp', 'furniture', 40.00);
INSERT INTO purchase VALUES (1, 1, '2026-01-05', 'paid'), (2, 2, '2026-01-12', 'paid'), (3, 1, '2026-02-03', 'paid'), (4, 3, '2026-02-10', 'refunded'), (5, 4, '2026-02-14', 'paid'), (6, 2, '2026-03-01', 'paid');
INSERT INTO order_item VALUES (1, 1, 1, 10), (1, 2, 3, 1), (2, 1, 2, 1), (3, 1, 3, 2), (3, 2, 1, 5), (4, 1, 2, 1), (5, 1, 1, 20), (5, 2, 3, 1), (6, 1, 2, 2);
SELECT c.country,
       to_char(date_trunc('month', o.order_date), 'YYYY-MM') AS month,
       SUM(i.qty * p.unit_price) AS revenue
FROM purchase o
JOIN customer c ON c.customer_id = o.customer_id
JOIN order_item i ON i.order_id = o.order_id
JOIN product p ON p.product_id = i.product_id
WHERE o.status = 'paid'
GROUP BY c.country, date_trunc('month', o.order_date)
ORDER BY c.country, month
LIMIT 10;
```

```output
country | month | revenue
DE | 2026-01 | 60.00
DE | 2026-02 | 90.00
FR | 2026-01 | 150.00
FR | 2026-03 | 300.00
US | 2026-02 | 80.00
```

Four tables and a join chain answer a simple business question. The normalised schema is excellent for recording orders consistently and awkward for analysing them, which is why analytical systems reshape the data into wide tables, as Example 4 shows.

### Example 3: Row layout against column layout

The same four orders are stored two ways: a list of rows and a dictionary of columns. A function counts how many stored values each layout must read to sum one column and to fetch one whole row. The counts, not timings, are the point: they show why a scan favours columns and a lookup favours rows.

```python run
rows = [
    {"order_id": 1, "customer": "Ana", "country": "DE", "amount": 30.0, "status": "paid"},
    {"order_id": 2, "customer": "Ben", "country": "FR", "amount": 150.0, "status": "paid"},
    {"order_id": 3, "customer": "Ana", "country": "DE", "amount": 90.0, "status": "paid"},
    {"order_id": 4, "customer": "Cy", "country": "DE", "amount": 150.0, "status": "refunded"},
]
columns = {k: [r[k] for r in rows] for k in rows[0]}

# Row store: reading a row's values means touching every cell in that row
cells_row_scan = sum(len(r) for r in rows)
# Column store: summing "amount" reads only that column
cells_col_scan = len(columns["amount"])
print("sum of amount:", sum(r["amount"] for r in rows), sum(columns["amount"]))
print("cells read to sum one column: row store", cells_row_scan, "column store", cells_col_scan)

# Fetching order 3 as a whole row
cells_row_fetch = len(rows[2])
cells_col_fetch = len(columns)
print("cells read to fetch one row: row store", cells_row_fetch, "column store", cells_col_fetch, "(one per column, in different places)")
print("distinct countries:", sorted(set(columns["country"])), "of", len(columns["country"]), "values")
```

```output
sum of amount: 420.0 420.0
cells read to sum one column: row store 20 column store 4
cells read to fetch one row: row store 5 column store 5 (one per column, in different places)
distinct countries: ['DE', 'FR'] of 4 values
```

Here the scan reads 5 times fewer cells in a column layout, and the ratio grows with the number of columns. The last line shows why columns compress: two distinct values stand for four entries, and in a real table millions of entries repeat a few dozen values.

### Example 4: The same answer from a normalised schema and a wide table

A warehouse often stores a pre-joined, wide table so that analysts avoid the join chain. `CREATE TABLE ... AS SELECT` builds `sales_wide` from the source tables once; the report then reads one table. The final query returns the same revenue by country as the four-table join, and the check compares both results with `EXCEPT`, so any difference would appear as rows.

```sql run
CREATE TABLE customer (customer_id int PRIMARY KEY, name text NOT NULL, country text NOT NULL);
CREATE TABLE product (product_id int PRIMARY KEY, name text NOT NULL, category text NOT NULL, unit_price numeric(8,2) NOT NULL);
CREATE TABLE purchase (order_id int PRIMARY KEY, customer_id int NOT NULL REFERENCES customer, order_date date NOT NULL, status text NOT NULL);
CREATE TABLE order_item (order_id int REFERENCES purchase, line_no int, product_id int NOT NULL REFERENCES product, qty int NOT NULL, PRIMARY KEY (order_id, line_no));
INSERT INTO customer VALUES (1, 'Ana', 'DE'), (2, 'Ben', 'FR'), (3, 'Cy', 'DE'), (4, 'Di', 'US');
INSERT INTO product VALUES (1, 'Pen', 'office', 2.00), (2, 'Desk', 'furniture', 150.00), (3, 'Lamp', 'furniture', 40.00);
INSERT INTO purchase VALUES (1, 1, '2026-01-05', 'paid'), (2, 2, '2026-01-12', 'paid'), (3, 1, '2026-02-03', 'paid'), (4, 3, '2026-02-10', 'refunded'), (5, 4, '2026-02-14', 'paid'), (6, 2, '2026-03-01', 'paid');
INSERT INTO order_item VALUES (1, 1, 1, 10), (1, 2, 3, 1), (2, 1, 2, 1), (3, 1, 3, 2), (3, 2, 1, 5), (4, 1, 2, 1), (5, 1, 1, 20), (5, 2, 3, 1), (6, 1, 2, 2);
CREATE TABLE sales_wide AS
SELECT o.order_id, o.order_date, o.status, c.country, p.category, i.qty, i.qty * p.unit_price AS revenue
FROM purchase o
JOIN customer c ON c.customer_id = o.customer_id
JOIN order_item i ON i.order_id = o.order_id
JOIN product p ON p.product_id = i.product_id;

SELECT country, SUM(revenue) AS revenue,
       (SELECT COUNT(*) FROM (
          SELECT c.country, SUM(i.qty * p.unit_price)
          FROM purchase o JOIN customer c ON c.customer_id = o.customer_id
          JOIN order_item i ON i.order_id = o.order_id JOIN product p ON p.product_id = i.product_id
          WHERE o.status = 'paid' GROUP BY c.country
          EXCEPT
          SELECT country, SUM(revenue) FROM sales_wide WHERE status = 'paid' GROUP BY country
       ) d) AS differences
FROM sales_wide
WHERE status = 'paid'
GROUP BY country
ORDER BY country
LIMIT 10;
```

```output
country | revenue | differences
DE | 150.00 | 0
FR | 450.00 | 0
US | 80.00 | 0
```

Zero differences: the wide table carries the same facts. The trade is storage and repeated values (the country is copied on every line) for much simpler queries, which is the OLAP trade-off.

### Example 5: A data mart for the sales team

A mart is a summary built for one audience. This block builds `mart_monthly_sales` from the source schema, one row per month and category with orders and revenue, and then queries it as the sales team would. The mart has two dimensions only and no joins in the query.

```sql run
CREATE TABLE customer (customer_id int PRIMARY KEY, name text NOT NULL, country text NOT NULL);
CREATE TABLE product (product_id int PRIMARY KEY, name text NOT NULL, category text NOT NULL, unit_price numeric(8,2) NOT NULL);
CREATE TABLE purchase (order_id int PRIMARY KEY, customer_id int NOT NULL REFERENCES customer, order_date date NOT NULL, status text NOT NULL);
CREATE TABLE order_item (order_id int REFERENCES purchase, line_no int, product_id int NOT NULL REFERENCES product, qty int NOT NULL, PRIMARY KEY (order_id, line_no));
INSERT INTO customer VALUES (1, 'Ana', 'DE'), (2, 'Ben', 'FR'), (3, 'Cy', 'DE'), (4, 'Di', 'US');
INSERT INTO product VALUES (1, 'Pen', 'office', 2.00), (2, 'Desk', 'furniture', 150.00), (3, 'Lamp', 'furniture', 40.00);
INSERT INTO purchase VALUES (1, 1, '2026-01-05', 'paid'), (2, 2, '2026-01-12', 'paid'), (3, 1, '2026-02-03', 'paid'), (4, 3, '2026-02-10', 'refunded'), (5, 4, '2026-02-14', 'paid'), (6, 2, '2026-03-01', 'paid');
INSERT INTO order_item VALUES (1, 1, 1, 10), (1, 2, 3, 1), (2, 1, 2, 1), (3, 1, 3, 2), (3, 2, 1, 5), (4, 1, 2, 1), (5, 1, 1, 20), (5, 2, 3, 1), (6, 1, 2, 2);
CREATE TABLE mart_monthly_sales AS
SELECT to_char(date_trunc('month', o.order_date), 'YYYY-MM') AS month,
       p.category,
       COUNT(DISTINCT o.order_id) AS orders,
       SUM(i.qty * p.unit_price) AS revenue
FROM purchase o
JOIN order_item i ON i.order_id = o.order_id
JOIN product p ON p.product_id = i.product_id
WHERE o.status = 'paid'
GROUP BY 1, 2;

SELECT month, category, orders, revenue
FROM mart_monthly_sales
ORDER BY month, category
LIMIT 10;
```

```output
month | category | orders | revenue
2026-01 | furniture | 2 | 190.00
2026-01 | office | 1 | 20.00
2026-02 | furniture | 2 | 120.00
2026-02 | office | 2 | 50.00
2026-03 | furniture | 1 | 300.00
```

The sales team queries a ready table with plain column names. The mart is rebuilt on every load, and its definition (only paid orders) is written once, which makes the metric consistent for everyone who uses it.

## Real-world applications

- **Keeping reports off the production database.** A nightly pipeline copies orders into a warehouse so that analysts' long queries never compete with checkouts.
- **Choosing a storage format.** Large analytical datasets are written as column-oriented files (Parquet) because most reports read a few columns of many rows.
- **Building team marts.** Finance, sales and marketing each get a mart with the metrics defined once, so "revenue" means the same thing in every dashboard.
- **Designing a load.** Knowing the source is OLTP (overwritten state) tells you to capture history yourself, with incremental loads and change capture (Days 125 and 127).

## Daily review

### Key takeaways

- OLTP: many small, concurrent transactions on current data, by key. OLAP: few large scans and aggregations over history.
- Row stores keep rows together (fast row access, updates); column stores keep columns together (fast scans of few columns, high compression).
- A warehouse integrates sources into a historical analytical store; a mart is a subject-focused slice or summary built for a team.
- Analytical queries on a normalised schema need many joins; analytical schemas are wide and denormalised.
- Pipelines move data from OLTP systems to the warehouse and on to marts.

### Common mistakes

- **Running heavy reports on the production OLTP database.** Checkouts slow down. Copy the data to an analytical store.
- **Calling any large database a warehouse.** Without integration, history and an analytical schema it is a big OLTP database.
- **Thinking column stores suit every workload.** Single-row updates are slow there; keep OLTP on a row store.
- **Overwriting state in the warehouse and losing history.** Keep dated rows or snapshots so trends can be analysed.
- **Confusing storage layout with SQL.** The same SQL runs on both; only the speed differs.

### Revision notes

- OLTP: transactions, key lookups, current state, normalised, row store.
- OLAP: aggregations, scans, history, denormalised, column store.
- Flow: sources, staging, warehouse, marts, reports.
- `CREATE TABLE ... AS SELECT` builds marts and wide tables.

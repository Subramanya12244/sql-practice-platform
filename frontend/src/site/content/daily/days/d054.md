## Objectives

- Write a recursive CTE with an anchor member, `UNION ALL` and a recursive member.
- Trace how the recursion runs round by round and why it stops.
- Walk a hierarchy such as an employee-manager tree, tracking depth and path.
- Generate number and date series, and fill gaps in a report with them.
- Protect a recursive query from running forever.

## Understand

### The problem: depth that is not known in advance

On day 42 a self join linked each employee to their manager, one level. Two levels need two joins, three levels three joins. But a real organisation, a folder tree or a bill of materials has unknown depth, and a query cannot contain an unknown number of joins. A **recursive CTE** (day 46 introduced ordinary CTEs) lets a query refer to itself, so the database repeats a step until there is nothing new to add.

### Anatomy of a recursive CTE

A recursive CTE has two parts joined by `UNION ALL`:

1. The **anchor member** is an ordinary query that runs once and produces the starting rows. For an organisation chart, it is the employee with no manager.
2. The **recursive member** is a query that reads from the CTE itself and produces the next rows from the previous ones. For an organisation chart, it is "employees whose manager is in the rows found in the previous round".

The keyword `RECURSIVE` follows `WITH`. Think of dominoes: the anchor member sets up the first domino and the recursive member says how each fallen domino knocks over the next ones.

### How the database runs it

PostgreSQL evaluates it in rounds. Round 0 runs the anchor and stores its rows. Round 1 runs the recursive member, where the CTE name stands for only the rows produced in the previous round (not the whole result so far), and adds the new rows. It repeats until a round produces no rows. The final result is the union of the anchor rows and all rounds. With the tree of Example 3, round 0 gives the vice president, round 1 gives the people reporting to the vice president, round 2 the people reporting to them, and round 3 finds nobody, so recursion ends.

### Termination

Recursion stops only when the recursive member returns no new rows. If it always returns something, the query never ends. The classic accident is `SELECT n + 1 FROM t` with no `WHERE n < 5`. There are three safeguards. A **stop condition** in the recursive member, such as `WHERE n < 5`, bounds a series. A **depth counter** such as `level + 1` with `WHERE level < 10` bounds a hierarchy. And in **graphs** that can contain cycles (A leads to B leads to C leads to A), keep the path of visited nodes and refuse to step onto a node already in the path (Example 6). Clean tree hierarchies, like an employee tree where nobody is their own ancestor, cannot loop, but data errors can create a loop, so a depth limit is a cheap protection.

### Carrying columns along: depth and path

Each round can add columns computed from the previous round: a `level` that increases by 1, and a `path` that appends each employee's name to the path of their manager. In Example 3 these show the shape of the tree. The column types of the anchor and the recursive member must match exactly. A common error is anchoring with a `varchar` column and appending to it in the recursive member, whose type no longer matches the anchor's. Cast the anchor value, for example `last_name::text`.

### UNION ALL versus UNION

`UNION ALL` keeps every row produced. `UNION` removes duplicates against all rows found so far, which can stop a loop in simple graphs, but it costs a comparison for every row and does not protect against growing paths. Prefer `UNION ALL` with an explicit guard.

### Series generation

Recursion can also create rows from nothing. The anchor is a start value and the recursive member adds a step until an end value: the numbers 1 to 5, a date every seven days, the first day of every month (Examples 1, 2 and 5). PostgreSQL also has a built-in `generate_series` function, which is simpler for plain series, but the recursive version works in other databases and shows how the mechanism works. A generated list of months can be joined with a `LEFT JOIN` to data, so that months with no rows show a zero instead of disappearing. That fixes the gap problem you saw with `LAG` on day 51.

### Common misconception

Recursion in SQL is not a loop that runs row by row in the order you imagine, and the recursive member does not see the whole result so far, only the previous round. The order of rows in the final output is not guaranteed; add `ORDER BY` for a stable display, using the path or level columns.

### Why it matters

Organisation charts, category trees, folder structures, bills of materials, network routes and calendars are all recursive structures. Without recursive CTEs, analysts either export the data and process it in another language or hard-code a fixed number of joins that breaks when the tree gets deeper.

## Syntax and key functions

```sql-syntax
WITH RECURSIVE cte_name (column_1, column_2) AS (
  anchor_query                -- runs once
  UNION ALL
  recursive_query             -- refers to cte_name; runs until no new rows
)
SELECT ... FROM cte_name;
```

The anchor query provides the first rows. The recursive query reads `cte_name`, adds a stop condition in its `WHERE`, and produces columns of exactly the same names and types as the anchor.

| Piece | Purpose |
|---|---|
| `WITH RECURSIVE` | Allows the CTE to refer to itself |
| Anchor member | Starting rows, evaluated once |
| `UNION ALL` | Joins the anchor to the recursive rows and keeps duplicates |
| Recursive member | Next rows from the previous round's rows |
| `WHERE level < n` or `WHERE n < limit` | Stop condition |
| `path \|\| value`, `NOT value = ANY(path)` | Build and check a visited path (text or array) |

## Learn by example

### Example 1: the numbers 1 to 5

The anchor produces 1. Each round adds 1 to the previous number. `WHERE n < 5` stops the recursion: in round 4 `n` is 5, the condition fails and no more rows are produced.

```sql run
WITH RECURSIVE counter (n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM counter WHERE n < 5
)
SELECT n FROM counter ORDER BY n;
```

```output
n
1
2
3
4
5
```

### Example 2: a date every seven days

Dates plus an integer add days. The same shape produces week starts, month ends or any regular calendar. The stop condition compares the date with the last date wanted.

```sql run
WITH RECURSIVE weeks (week_start) AS (
  SELECT DATE '1998-01-01'
  UNION ALL
  SELECT week_start + 7 FROM weeks WHERE week_start < DATE '1998-01-29'
)
SELECT week_start FROM weeks ORDER BY week_start;
```

```output
week_start
1998-01-01
1998-01-08
1998-01-15
1998-01-22
1998-01-29
```

### Example 3: the employee hierarchy

Anchor: the employee with `reports_to IS NULL`, level 1. Recursive part: join `employees` to the previous round on `reports_to = employee_id`, level plus 1, path extended. The cast `::text` gives the anchor's path column the right type. The result lists the whole tree sorted by path, so each manager appears before their team.

```sql run
WITH RECURSIVE org AS (
  SELECT employee_id, last_name, 1 AS level, last_name::text AS path
  FROM employees
  WHERE reports_to IS NULL
  UNION ALL
  SELECT e.employee_id, e.last_name, o.level + 1, o.path || ' > ' || e.last_name
  FROM employees AS e
  JOIN org AS o ON e.reports_to = o.employee_id
)
SELECT employee_id, last_name, level, path
FROM org
ORDER BY path;
```

```output
employee_id | last_name | level | path
2 | Fuller | 1 | Fuller
5 | Buchanan | 2 | Fuller > Buchanan
9 | Dodsworth | 3 | Fuller > Buchanan > Dodsworth
7 | King | 3 | Fuller > Buchanan > King
6 | Suyama | 3 | Fuller > Buchanan > Suyama
8 | Callahan | 2 | Fuller > Callahan
1 | Davolio | 2 | Fuller > Davolio
3 | Leverling | 2 | Fuller > Leverling
4 | Peacock | 2 | Fuller > Peacock
```

### Example 4: everyone below one manager

Start the anchor at employee 5 (Buchanan, the sales manager) and walk down. The result is Buchanan and the three people who report to Buchanan. Changing the anchor's `WHERE` is all it takes to start from a different subtree. Counting the rows gives the size of a team, including its head.

```sql run
WITH RECURSIVE team AS (
  SELECT employee_id, last_name, reports_to, 0 AS depth
  FROM employees
  WHERE employee_id = 5
  UNION ALL
  SELECT e.employee_id, e.last_name, e.reports_to, t.depth + 1
  FROM employees AS e
  JOIN team AS t ON e.reports_to = t.employee_id
)
SELECT employee_id, last_name, depth,
       COUNT(*) OVER () AS team_size
FROM team
ORDER BY depth, employee_id;
```

```output
employee_id | last_name | depth | team_size
5 | Buchanan | 0 | 4
6 | Suyama | 1 | 4
7 | King | 1 | 4
9 | Dodsworth | 1 | 4
```

### Example 5: fill the missing months

A generated month list joined to the data fixes the day 51 problem. February, March, May and June 1996 had no orders, and the `LEFT JOIN` shows them with count 0. `COUNT(o.order_id)` counts only matched rows, so unmatched months give 0 (`COUNT(*)` would wrongly give 1).

```sql run
WITH RECURSIVE months (month) AS (
  SELECT DATE '1996-01-01'
  UNION ALL
  SELECT (month + INTERVAL '1 month')::date FROM months WHERE month < DATE '1996-06-01'
)
SELECT m.month, COUNT(o.order_id) AS orders
FROM months AS m
LEFT JOIN orders AS o ON date_trunc('month', o.order_date) = m.month
GROUP BY m.month
ORDER BY m.month;
```

```output
month | orders
1996-01-01 | 9
1996-02-01 | 0
1996-03-01 | 0
1996-04-01 | 9
1996-05-01 | 0
1996-06-01 | 0
```

### Example 6: a graph with a cycle

A small route table has a loop: A to B to C to A, and C to D. The walk starts at A and records the path. `NOT e.dst = ANY(w.path)` refuses to enter a node already visited, so the cycle is cut and recursion ends. Without that condition this query would never stop. The `VALUES` list builds the edge table inline.

```sql run
WITH RECURSIVE edges (src, dst) AS (
  VALUES ('A', 'B'), ('B', 'C'), ('C', 'A'), ('C', 'D')
), walk (node, path) AS (
  SELECT 'A'::text, ARRAY['A']
  UNION ALL
  SELECT e.dst, w.path || e.dst
  FROM walk AS w
  JOIN edges AS e ON e.src = w.node
  WHERE NOT e.dst = ANY (w.path)
)
SELECT node, array_to_string(path, ' > ') AS route
FROM walk
ORDER BY cardinality(path), node;
```

```output
node | route
A | A
B | A > B
C | A > B > C
D | A > B > C > D
```

## Real-world applications

**Organisation and reporting lines.** Examples 3 and 4 list everyone below a manager, compute depth and build the reporting chain. The same query answers "who approves this expense" or "how many people sit under this vice president".

**Calendar and series tables.** Examples 2 and 5 generate dates. Reports that must show every week or month, even when there was no activity, join their data to such a series so that gaps appear as zeros.

**Bills of materials and category trees.** A product is made of parts that are themselves made of parts. A recursive CTE expands the structure to raw materials and can multiply quantities down the levels. Web shops use it for nested categories.

**Routes and dependencies.** Example 6 is the shape of "which nodes can be reached from here": network paths, pipeline task dependencies and workflow steps. The path check prevents the endless loop.

## Daily review

### Key takeaways

- A recursive CTE has an anchor member, `UNION ALL` and a recursive member that refers to the CTE name.
- The recursive member sees only the rows from the previous round; recursion ends when a round produces no rows.
- Always have a stop condition: a limit in a series, a depth limit, or a visited-path check for graphs.
- Anchor and recursive member must have the same columns and types; cast the anchor if needed.
- Track `level` and `path` columns to show the tree shape; use `ORDER BY` to display it.
- Joining a generated series to data with `LEFT JOIN` makes missing periods visible.

### Common mistakes

- No stop condition: the query runs until the server stops it or runs out of memory. Add `WHERE n < limit`.
- Type mismatch: `recursive query "org" column 3 has type character varying(50) in non-recursive term but type character varying overall`. Cast the anchor value, for example `last_name::text`.
- Forgetting `RECURSIVE`: the error is `relation "org" does not exist` because an ordinary CTE cannot see itself.
- Using `COUNT(*)` after the `LEFT JOIN` onto a generated calendar, which counts the empty month as 1. Count a column of the joined table.
- Relying on the output order without `ORDER BY`.
- Starting the anchor with the wrong rows, such as a manager column that is not NULL, and getting an empty result.

### Revision notes

- Shape: `WITH RECURSIVE t AS (anchor UNION ALL recursive WHERE stop) SELECT ...`.
- Rounds: anchor, then recursive member on the last round's rows, until nothing new.
- Guards: limit in `WHERE`, depth counter, path check.
- Series: anchor = start, step = `+ 1` or `+ 7` or `+ INTERVAL '1 month'`.

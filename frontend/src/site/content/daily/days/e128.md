## Objectives

- Explain partitions (one slice of data per day) and why a pipeline should be able to rebuild one partition on its own.
- Write a partition loader that is idempotent: rebuild one day without touching its neighbours.
- Build a backfill driver that walks a date range, logs each partition and resumes after a failure.
- Handle late data with a reprocessing window, and reprocess from raw after a rule change, checking the counts.

## Understand

### Late data and rule changes

Two events force a pipeline to look backwards. **Late data** is a record that reaches the source after the run that should have loaded it: an order stamped 2 March that only arrives on 5 March. A **rule change** is a correction to the logic: yesterday you learned that amounts in `€` were being rejected, and every day since the bug began is wrong. In both cases the fix is the same shape. You must **reprocess** past periods, and you must do it without breaking the days that were fine and without loading anything twice. A reprocessing job over a range of past dates is a **backfill**.

### Partitions

A **partition** is one self-contained slice of the data, normally one day. Treating the pipeline as a sequence of daily partitions is the key to safe backfills. Each partition has a clear definition (the half-open window `day <= t < day + 1`, as on Day 123), can be extracted by itself, and can be rebuilt by itself: delete exactly that day's rows from the target and insert the freshly computed rows, in one transaction. Other days are never touched, so rebuilding 2 March cannot damage 3 March. In PostgreSQL the same idea exists as **declarative partitioning**: a table declared `PARTITION BY RANGE (day)` is stored as child tables, one per range, and you can empty or replace one child (`TRUNCATE` on the child) without scanning the rest. Whether partitions are physical child tables or just a `day` column you filter on, the design rule is the same: **a run is parameterised by its partition**, `run_partition(day)`, not by "now".

### Idempotent partition rewrite

A partition rewrite is idempotent if running it twice for the same day leaves the same rows. The usual pattern is *delete the partition, insert the partition* inside one transaction. The alternative is an upsert by key (Day 126) with a guard, which also never duplicates but does not remove rows that disappeared from the source for that day; the delete-and-insert pattern does, which matters when a correction removes rows. Choose by asking whether the corrected source can lose rows for that day.

### Designing a backfill

A backfill driver is a loop over partitions with a few rules. It takes a **start and an end date** (half-open) and visits each day in order, which keeps logs readable and makes failures easy to locate. It **records progress** per partition (a `partition_log` table with the day and the rows loaded), so that after a crash a rerun skips the finished days instead of starting over, and a flag lets you force a redo. It **limits its pace**: a backfill over two years that fires all requests at once can exhaust an API's rate limit or overload the database, so it runs one partition at a time or with a small number of workers. It does not **overwrite newer data with older**, because other runs may be writing the recent partitions at the same time; the usual protection is to backfill only closed days, or to use the guarded upsert. And it **verifies**: after each partition it compares the loaded count with the source count, and at the end it compares the totals per day before and after, so that nobody discovers a mistake in a report.

### Late data windows

For late data the simplest policy is a **reprocessing window**: every daily run processes today's partition and also the last N days (for example three), rebuilding each. Rows that arrived late for those days are picked up automatically, because each rebuild reads the source again. This is the partition version of Day 125's lookback window, and it is safe for the same reason: the rewrite is idempotent. Data later than N days needs a manual backfill for that date, or a periodic full reload as a safety net. Choose N from how late data actually arrives: measure the lag between event time and arrival time in your source.

### Reprocessing from raw

Day 120 kept the raw layer for this moment. After a rule change, rebuild the affected partitions of `orders_clean` from `raw_orders` with the new rule, not from the source: the source may not hold the old days any more, may be rate-limited, or may have changed. The comparison "before and after totals per day" shows exactly which days the rule change affected, which is also what you tell the business.

### A common misconception

Backfills are not "just rerun the job for each old date". If the job reads "yesterday" from the clock, it cannot be pointed at 2 March; if its write is an append, rerunning doubles the data; if it keeps one watermark, it cannot jump back. These properties must be built in from the start: the date is a parameter, the write replaces the partition, and the watermark is a tool for the daily run and not a limit on backfills.

### Why it matters in data work

Data is late and rules are wrong more often than anyone plans for. A pipeline that can rebuild one day safely turns each of those events into a routine command instead of a crisis.

## Syntax and key functions

```python
def load_partition(conn, day, rows):
    with conn:
        conn.execute("DELETE FROM orders_clean WHERE day = ?", (day,))
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?, ?)", rows)
```

```sql-syntax
CREATE TABLE ev (event_id int, day date NOT NULL, cents int) PARTITION BY RANGE (day);
CREATE TABLE ev_2025_03_01 PARTITION OF ev FOR VALUES FROM ('2025-03-01') TO ('2025-03-02');
TRUNCATE ev_2025_03_01;
```

| Item | What it does or returns |
|---|---|
| partition | One day (or other range) of data that can be rebuilt on its own. |
| `DELETE ... WHERE day = ?` plus insert, one transaction | Idempotent rewrite of one partition. |
| `PARTITION BY RANGE (col)` | PostgreSQL declarative partitioning: child tables per range. |
| `FOR VALUES FROM (a) TO (b)` | The half-open range of one partition. |
| backfill driver | Loops over days; logs, skips finished days, verifies. |
| reprocessing window | Rebuild the last N partitions on every run. |
| `partition_log` | Table recording which partitions are done and how many rows. |

## Learn by example

### Example 1: Rebuild one partition

The table holds three days. The loader rewrites 2 March with corrected rows, twice, and the per-day counts show that the neighbours were not touched and that the second rewrite changed nothing.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, day TEXT, amount_cents INTEGER)")
conn.executemany("INSERT INTO orders_clean VALUES (?, ?, ?)", [(1, "2025-03-01", 100), (2, "2025-03-02", 200), (3, "2025-03-02", 300), (4, "2025-03-03", 400)])

def load_partition(conn, day, rows):
    with conn:
        conn.execute("DELETE FROM orders_clean WHERE day = ?", (day,))
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?, ?)", rows)

def per_day():
    return conn.execute("SELECT day, COUNT(*), SUM(amount_cents) FROM orders_clean GROUP BY day ORDER BY day").fetchall()

print("before:", per_day())
corrected = [(2, "2025-03-02", 250), (3, "2025-03-02", 300), (5, "2025-03-02", 150)]
load_partition(conn, "2025-03-02", corrected)
after_once = per_day()
load_partition(conn, "2025-03-02", corrected)
print("after :", after_once)
print("rerun changes nothing:", per_day() == after_once)
```

```output
before: [('2025-03-01', 1, 100), ('2025-03-02', 2, 500), ('2025-03-03', 1, 400)]
after : [('2025-03-01', 1, 100), ('2025-03-02', 3, 700), ('2025-03-03', 1, 400)]
rerun changes nothing: True
```
### Example 2: A backfill driver with a progress log

The driver walks a half-open date range, loads each day from `source_by_day`, and records the row count in `partition_log`. The second call skips the days already done, and a failing day stops the run so that the next call resumes from it.

```python run
import sqlite3
from datetime import date, timedelta

source_by_day = {"2025-03-01": [(1, 100)], "2025-03-02": [(2, 200), (3, 300)], "2025-03-03": None, "2025-03-04": [(4, 400)]}
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, day TEXT, amount_cents INTEGER)")
conn.execute("CREATE TABLE partition_log (day TEXT PRIMARY KEY, rows_loaded INTEGER)")

def run_day(day):
    rows = source_by_day[day]
    if rows is None:
        raise ConnectionError("source down for " + day)
    with conn:
        conn.execute("DELETE FROM orders_clean WHERE day = ?", (day,))
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?, ?)", [(i, day, c) for i, c in rows])
        conn.execute("INSERT OR REPLACE INTO partition_log VALUES (?, ?)", (day, len(rows)))

def backfill(start, end):
    done_days, current = [], start
    while current < end:
        day = current.isoformat()
        if conn.execute("SELECT 1 FROM partition_log WHERE day = ?", (day,)).fetchone():
            done_days.append(day + " skipped")
        else:
            try:
                run_day(day)
                done_days.append(day + " loaded")
            except ConnectionError as exc:
                done_days.append(day + " FAILED")
                break
        current += timedelta(days=1)
    return done_days

print(backfill(date(2025, 3, 1), date(2025, 3, 5)))
source_by_day["2025-03-03"] = [(5, 500)]
print(backfill(date(2025, 3, 1), date(2025, 3, 5)))
print(conn.execute("SELECT * FROM partition_log ORDER BY day").fetchall())
```

```output
['2025-03-01 loaded', '2025-03-02 loaded', '2025-03-03 FAILED']
['2025-03-01 skipped', '2025-03-02 skipped', '2025-03-03 loaded', '2025-03-04 loaded']
[('2025-03-01', 1), ('2025-03-02', 2), ('2025-03-03', 1), ('2025-03-04', 1)]
```
### Example 3: A reprocessing window for late data

Orders for 2 March are loaded by the 4 March run, and one more order for 2 March arrives late, before the 5 March run. A run that rebuilds only its own day never sees it. A run with a window of three days rebuilds 2 March to 5 March each time, so the late order is loaded and nothing is duplicated.

```python run
import sqlite3
from datetime import date, timedelta

source = {"2025-03-02": [(1, 100)], "2025-03-04": [(2, 200)], "2025-03-05": [(3, 300)]}

def run(conn, today, days_back):
    for n in range(days_back, -1, -1):
        day = (today - timedelta(days=n)).isoformat()
        with conn:
            conn.execute("DELETE FROM t WHERE day = ?", (day,))
            conn.executemany("INSERT INTO t VALUES (?, ?)", [(i, day) for i, _ in source.get(day, [])])

for name, back in [("no window", 0), ("3-day window", 3)]:
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE t (order_id INTEGER PRIMARY KEY, day TEXT)")
    run(conn, date(2025, 3, 4), back)          # the 4 March run
    source["2025-03-02"].append((9, 900))      # a late order for 2 March arrives
    run(conn, date(2025, 3, 5), back)          # the 5 March run
    print(name, conn.execute("SELECT day, COUNT(*) FROM t GROUP BY day ORDER BY day").fetchall())
    source["2025-03-02"].pop()
```

```output
no window [('2025-03-04', 1), ('2025-03-05', 1)]
3-day window [('2025-03-02', 2), ('2025-03-04', 1), ('2025-03-05', 1)]
```
### Example 4: Reprocess from raw after a rule change

The raw table keeps the original text. Version 1 of the amount rule rejected `€` amounts, version 2 accepts them. The partitions are rebuilt from raw with the new rule, and a before and after comparison per day shows which days changed.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE raw_orders (order_id INTEGER, day TEXT, amount TEXT)")
conn.executemany("INSERT INTO raw_orders VALUES (?, ?, ?)", [(1, "2025-03-01", "10.00"), (2, "2025-03-01", "€5.00"), (3, "2025-03-02", "7.50"), (4, "2025-03-03", "€2.00"), (5, "2025-03-03", "3.00")])
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, day TEXT, amount_cents INTEGER)")

def clean_v1(text):
    try:
        return round(float(text) * 100)
    except ValueError:
        return None

def clean_v2(text):
    return clean_v1(text.replace("€", ""))

def rebuild(day, clean):
    rows = [(i, d, clean(a)) for i, d, a in conn.execute("SELECT * FROM raw_orders WHERE day = ?", (day,)) if clean(a) is not None]
    with conn:
        conn.execute("DELETE FROM orders_clean WHERE day = ?", (day,))
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?, ?)", rows)

def totals():
    return dict(conn.execute("SELECT day, SUM(amount_cents) FROM orders_clean GROUP BY day"))

days = ["2025-03-01", "2025-03-02", "2025-03-03"]
for d in days:
    rebuild(d, clean_v1)
before = totals()
for d in days:
    rebuild(d, clean_v2)
after = totals()
print("before:", before)
print("after :", after)
print("days changed:", [d for d in days if before.get(d) != after.get(d)])
```

```output
before: {'2025-03-01': 1000, '2025-03-02': 750, '2025-03-03': 300}
after : {'2025-03-01': 1500, '2025-03-02': 750, '2025-03-03': 500}
days changed: ['2025-03-01', '2025-03-03']
```
### Example 5: Replace one partition in PostgreSQL (PGlite)

The table is partitioned by day. After the load, the partition for 1 March is emptied with `TRUNCATE` on the child table and refilled with a corrected row; the other partition is untouched. The query shows the rows and the sum per partition.

```sql run
CREATE TABLE ev (event_id int, day date NOT NULL, cents int) PARTITION BY RANGE (day);
CREATE TABLE ev_2025_03_01 PARTITION OF ev FOR VALUES FROM ('2025-03-01') TO ('2025-03-02');
CREATE TABLE ev_2025_03_02 PARTITION OF ev FOR VALUES FROM ('2025-03-02') TO ('2025-03-03');
INSERT INTO ev VALUES (1, '2025-03-01', 100), (2, '2025-03-01', 200), (3, '2025-03-02', 300);
TRUNCATE ev_2025_03_01;
INSERT INTO ev VALUES (9, '2025-03-01', 999);
SELECT tableoid::regclass::text AS part, count(*) AS n, sum(cents) AS cents FROM ev GROUP BY 1 ORDER BY 1;
```

```output
part | n | cents
ev_2025_03_01 | 1 | 999
ev_2025_03_02 | 1 | 300
```
## Real-world applications

- **Late events.** A mobile app delivers orders hours or days late; a reprocessing window of a few days (Example 3) loads them without anyone raising a ticket.
- **Fixing a bug in the cleaning rule.** After a rule change the engineer rebuilds the affected days from raw (Example 4) and reports which days and totals moved.
- **Initial history load.** A new pipeline starts with a backfill of two years of days, one partition at a time and resumable (Example 2), and then switches to the daily run.
- **Cheap replacement in large tables.** Partitioned tables (Example 5) let a team replace one day of a billion-row table without rewriting the rest.

## Daily review

### Key takeaways

- A backfill reprocesses a range of past partitions; late data and rule changes both need it.
- Parameterise the run by partition; rebuild a partition by deleting and inserting it in one transaction.
- A backfill driver walks half-open date ranges, logs each partition, skips finished ones, paces itself and verifies counts.
- A reprocessing window of N days picks up late data automatically; later data needs a manual backfill.
- After a rule change, rebuild from raw and compare totals per day before and after.

### Common mistakes

- A job that reads "yesterday" from the clock, so it cannot be pointed at an old date. Pass the day as a parameter.
- Appending when backfilling, which doubles the days that were already loaded. Rewrite the partition.
- Backfilling with one watermark so a run for an old day skips rows. Use the partition, not the watermark, for backfills.
- Starting all partitions at once against an API or database and hitting limits. Walk the days with a small pace.
- Changing a rule and rebuilding without a before and after comparison, so nobody knows what moved. Compare totals per day.

### Revision notes

- `run_partition(day)`: delete the day, insert the day, one transaction.
- Backfill: half-open range, `partition_log`, skip done, stop or resume on failure.
- Window: rebuild today and the last N days; N from the observed lag.
- Rule change: rebuild from raw, compare per-day totals.

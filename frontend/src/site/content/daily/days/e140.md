## Understand

### Why pipelines change through pull requests

A pipeline is code that other people and reports depend on. If you edit `transforms.py` directly on the copy that the scheduler runs, a typo reaches production at the next run, and nobody else saw the change. Teams therefore keep one trusted line of code, usually called `main`, and make every change on a separate line first. **Git** is the version-control program that stores the history of a project as a series of **commits**, each a saved snapshot with a message. **GitHub** is a website that hosts Git repositories and adds collaboration features: pull requests, reviews and automatic test runs. The two are different things: Git runs on your computer, GitHub is a service.

A **branch** is a named line of development inside a repository. `main` is the shared branch; you create a branch such as `fix/amount-parser`, commit on it, and `main` stays unchanged until you decide to merge. Branches are cheap: creating one copies nothing. A **merge** brings the commits of one branch into another. When both branches changed the same lines, Git cannot choose and reports a **merge conflict**; a person edits the file to the correct version and commits the result.

### The pull request cycle

A **pull request** (PR) is a proposal on GitHub: "merge branch `fix/amount-parser` into `main`". It shows the changes (the **diff**), the commit messages, a place for discussion and the status of automatic checks. The cycle has six steps.

1. Create a branch from the latest `main` with a short, descriptive name.
2. Make small commits with messages that say what changed in the imperative ("Strip currency symbol in clean_amount").
3. Push the branch and open a pull request.
4. Automatic checks run (the tests, from Day 138). A reviewer reads the diff and comments.
5. You fix what the review found and push more commits; the PR updates.
6. When the checks pass and a reviewer approves, the PR is merged into `main`.

### Writing a pull request description

Reviewers have little time. A good description answers four questions: what changed, why, how it was tested, and what the risk is. For a pipeline change add: which tables or columns are affected, whether a backfill or rerun is needed (Day 128), and how to roll back. "Fix stuff" gets a shallow review. "Strip the dollar sign in `clean_amount`; orders with a `$` prefix were loaded as null (14 rows on 2026-01-07). Added a parametrized test. No schema change; rerun of 2026-01-07 needed after merge" gets a useful one.

Keep each PR small and focused on one change. A 40-line change gets read; a 2,000-line change gets approved without reading.

### Reviewing a data pipeline change

Reviewing means reading the diff for problems the author is blind to. A checklist for pipelines:

- **Correctness:** does the logic do what the description says, including edge cases (nulls, empty input)?
- **Tests:** is there a test for the new behaviour, and for the bug that triggered the change?
- **Idempotency:** is a rerun safe (Day 94)? Does a changed key or `INSERT` create duplicates?
- **Data impact:** which tables, columns and downstream reports change? Is a backfill needed?
- **Secrets and configuration:** no passwords, keys or hard-coded paths in the diff.
- **Readability:** names, structure and comments that a stranger can follow.

A good review comment is specific and kind: it names the line, states the problem and, if possible, suggests a fix. Mark opinions as optional and blockers as required.

### Continuous integration with GitHub Actions

**Continuous integration** (CI) means that every change is automatically built and tested in a clean environment before it is merged. On GitHub this is done with **GitHub Actions**. A **workflow** is a YAML file stored in `.github/workflows/` in the repository. It states when to run (`on:`), and a set of **jobs**, each made of **steps** that run on a fresh machine (`runs-on:`). A step either uses a ready-made action (`uses:`) or runs a shell command (`run:`). The usual pipeline-test job checks out the code, installs Python, installs the requirements and runs `python -m pytest -q`. If any step exits with a non-zero status, the job fails and GitHub shows a red mark on the pull request.

The workflow cannot run in this course's browser, because it needs GitHub's runners. Everything it does you can do on your machine with the same commands, which is why the lesson also shows the Git commands locally and simulates the merge rules in Python.

### Branch protection

A repository administrator can protect `main`: require a pull request, require at least one approving review, require named status checks (for example the `test` job) to pass, and block direct pushes. With these rules the tests are not advice but a gate. The rules are configured in the repository settings on GitHub, not in a file in the code.

### Common misconception

Learners often think a pull request is only a way to ask permission. Its real value is the record: the discussion, the test result and the reason for the change stay attached to the code. A second misconception is that green checks mean the change is correct. They mean the tests passed; a missing test is invisible. A third is that Git and GitHub are the same program, so that pushing to GitHub is the same as committing: a commit is local until it is pushed.

### Why it matters

In data work a bad merge is rarely a crash; it is a quietly wrong number. The pull request cycle and CI are the cheapest place in the process to catch that, before any table is written.

## Syntax and key functions

Local Git commands:

```text
git init -b main                  # new repository whose first branch is main
git switch -c fix/amount-parser   # create a branch and switch to it
git add transforms.py             # stage a change
git commit -m "Strip currency symbol in clean_amount"
git branch --list                 # list local branches
git log --format=%s               # commit subjects, newest first
git diff --name-status main fix/amount-parser   # files that differ
git switch main && git merge fix/amount-parser  # bring the branch into main
```

A GitHub Actions workflow, saved as `.github/workflows/ci.yml` (shown, not run here):

```yaml
name: ci

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: python -m pytest -q
```

| Item | What it does |
|---|---|
| `git switch -c name` | Creates a branch and moves to it. |
| `git merge branch` | Merges a branch into the current one; stops with a conflict if both changed the same lines. |
| `git status --short` | Lists changed files; `UU` marks a file with an unresolved conflict. |
| `on: pull_request` | Runs the workflow when a pull request is opened or updated. |
| `jobs.<name>.steps` | Ordered steps; a failing step fails the job. |
| `uses: actions/checkout@v4` | Copies the repository into the runner. |
| `run: cmd` | Runs a shell command; non-zero exit status means failure. |
| Branch protection | Requires reviews and passing checks before merging into `main`. |

## Learn by example

The Git examples use `bash run` in a throwaway folder and print no commit hashes. The workflow file cannot run here, so Examples 4 and 5 simulate its rules in Python. The environment note explains how to try the real thing.

### Example 1: Branch, commit, compare and merge

A repository starts with a transform on `main`. A branch changes it and adds a test. `git diff --name-status` lists the files that differ between the branches, and `git log --format=%s` shows the subjects only. `--no-ff` records a merge commit even when the history is linear, which makes the pull request visible in the log.

```bash run
git init -q -b main
printf 'def clean_amount(raw):\n    return int(float(raw) * 100)\n' > transforms.py
git add transforms.py
git commit -q -m "Add clean_amount"
git switch -q -c fix/dollar-sign
printf 'def clean_amount(raw):\n    return int(float(str(raw).replace("$", "")) * 100)\n' > transforms.py
printf 'def test_dollar():\n    assert clean_amount("$5") == 500\n' > test_transforms.py
git add transforms.py test_transforms.py
git commit -q -m "Strip dollar sign in clean_amount"
git branch --list
git diff --name-status main fix/dollar-sign
git switch -q main
git merge -q --no-ff -m "Merge fix/dollar-sign" fix/dollar-sign
git log --format=%s
```

```output
* fix/dollar-sign
  main
A	test_transforms.py
M	transforms.py
Merge fix/dollar-sign
Add clean_amount
Strip dollar sign in clean_amount
```

The star marks the branch you are on. After the merge, `main` contains the branch's commit and the merge commit. The branch itself remains until you delete it.

### Example 2: A merge conflict

Two branches change the same line differently. Git cannot choose, stops the merge and marks the file `UU`. `git merge --abort` returns to the state before the merge. The `|| true` keeps the script going, because a conflicted merge exits non-zero.

```bash run
git init -q -b main
printf 'RATE = 1.00\n' > config.py
git add config.py
git commit -q -m "Add rate"
git switch -q -c feature/eur
printf 'RATE = 1.08\n' > config.py
git commit -q -am "EUR rate"
git switch -q main
printf 'RATE = 0.95\n' > config.py
git commit -q -am "Update rate"
git merge feature/eur > /dev/null 2>&1 || true
git status --short
git merge --abort
git status --short
echo "state restored"
```

```output
UU config.py
state restored
```

`UU config.py` means both sides modified the file. The fix is to edit the file to the correct line, `git add` it and commit; here the author would decide which rate is right, which is a question for a person, not for Git.

### Example 3: Merge rules as code

Branch protection is a set of rules. Writing them as a function makes them concrete: a pull request can merge only with enough approvals, passing required checks and no unresolved conflict, and nobody may have requested changes. The function returns the list of reasons that block the merge.

```python run
PROTECTION = {"approvals": 1, "required_checks": ["test"]}

def blockers(pr, rules=PROTECTION):
    reasons = []
    approvals = sum(1 for r in pr["reviews"] if r == "approve")
    if approvals < rules["approvals"]:
        reasons.append(f"needs {rules['approvals']} approval(s), has {approvals}")
    if "request_changes" in pr["reviews"]:
        reasons.append("changes requested")
    for check in rules["required_checks"]:
        if pr["checks"].get(check) != "pass":
            reasons.append(f"check {check}: {pr['checks'].get(check, 'missing')}")
    if pr["conflicts"]:
        reasons.append("merge conflict")
    return reasons

prs = {
    "fix-amount": {"reviews": ["approve"], "checks": {"test": "pass"}, "conflicts": False},
    "new-source": {"reviews": [], "checks": {"test": "fail"}, "conflicts": False},
    "rename-cols": {"reviews": ["approve", "request_changes"], "checks": {}, "conflicts": True},
}
for name, pr in prs.items():
    r = blockers(pr)
    print(name, "MERGE" if not r else "BLOCKED", "; ".join(r))
```

```output
fix-amount MERGE 
new-source BLOCKED needs 1 approval(s), has 0; check test: fail
rename-cols BLOCKED changes requested; check test: missing; merge conflict
```

A check that did not run counts as failing: `missing` blocks the merge, which is why requiring the `test` check is stronger than hoping someone runs it.

### Example 4: Simulating a CI job

A workflow job is an ordered list of steps that stops at the first failure. Each step here is a small function that returns an exit status, and `run_job` runs them in order and prints the same kind of result GitHub shows. The steps use the real pipeline tests of Day 138 as the model: install, test, and a final step that never runs because the tests failed.

```python run
def checkout():
    return 0

def install():
    return 0

def pytest_step():
    return 1  # one test fails

def upload_report():
    return 0

def run_job(name, steps):
    print(f"job {name}")
    for step in steps:
        code = step()
        print(f"  {step.__name__}: {'ok' if code == 0 else 'FAILED (exit ' + str(code) + ')'}")
        if code != 0:
            print(f"job {name}: failed, remaining steps skipped")
            return False
    print(f"job {name}: passed")
    return True

ok = run_job("test", [checkout, install, pytest_step, upload_report])
print("PR check:", "green" if ok else "red")
```

```output
job test
  checkout: ok
  install: ok
  pytest_step: FAILED (exit 1)
job test: failed, remaining steps skipped
PR check: red
```

The upload step never ran. A real workflow behaves the same way unless a step is told to run `if: always()`. The "red" check blocks a protected branch from merging.

### Example 5: A rough linter for the workflow file

The workflow is YAML, which the standard library cannot parse, so this check only scans the text for the lines a pipeline-test workflow needs: a trigger on pull requests, a checkout step and the pytest command. It is a sanity check, not a YAML parser, and it shows what a reviewer looks for in a workflow change.

```python run
workflow = """name: ci

on:
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - run: pip install -r requirements.txt
"""

REQUIRED = {
    "triggers on pull requests": "pull_request:",
    "checks out the code": "actions/checkout",
    "installs requirements": "pip install",
    "runs pytest": "pytest",
}
for label, needle in REQUIRED.items():
    print(("ok     " if needle in workflow else "MISSING") , label)
```

```output
ok      triggers on pull requests
ok      checks out the code
ok      installs requirements
MISSING runs pytest
```

The sample forgot the pytest step: a green workflow that never runs the tests is the failure the check looks for, and a reviewer should look for it too.

## Real-world applications

- **Reviewing a transform change.** A change to `clean_amount` arrives as a PR with the diff, a parametrized test and a note that 14 rows were affected. The reviewer checks the checklist, asks for a rerun plan and approves.
- **CI on a pipeline repository.** Each PR runs the unit tests and the integration test from Day 138 in a clean environment, so a missing dependency or a hard-coded local path is caught before merge.
- **Protecting the production branch.** Only `main` is scheduled in production, and `main` accepts only reviewed PRs with passing tests, so every production change has an author, a reviewer and a test result on record.
- **Incident follow-up.** After a bad load, the history shows which merged PR changed the rule and what the reviewer saw, which makes the fix and the postmortem quicker.

## Daily review

### Key takeaways

- Git keeps history on your computer; GitHub hosts repositories and adds pull requests, reviews and Actions.
- The cycle: branch, small commits, push, pull request, checks and review, merge.
- A PR description says what, why, how tested and the risk; a pipeline PR also says which data is affected and whether a rerun is needed.
- A workflow (`.github/workflows/*.yml`) runs steps on a fresh machine; a non-zero exit fails the job.
- Branch protection turns reviews and passing checks into required gates.

### Common mistakes

- **Committing on `main` directly.** Nobody reviews it and the tests do not gate it. Create a branch first.
- **Huge pull requests.** They get approved unread. Keep one change per PR.
- **Vague commit messages and PR titles ("fix").** The history becomes useless. Say what changed.
- **A workflow that installs but never runs the tests.** It is always green. Check the `run:` lines.
- **Resolving a conflict by choosing a side blindly.** The result may drop someone's change. Read both versions and test.
- **Committing secrets.** A key in the diff stays in the history. Keep credentials out of the repository.

### Revision notes

- Local: `git init -b main`, `git switch -c`, `git add`, `git commit -m`, `git merge`, `git status --short`.
- PR: branch, description (what, why, tested, risk), review, checks, merge.
- Workflow: `on`, `jobs`, `runs-on`, `steps` with `uses` and `run`.
- Protection: required review, required checks, no direct pushes.

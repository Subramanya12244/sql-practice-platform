## Understand

### What idempotent means

An operation is **idempotent** when doing it twice has the same effect as doing it once. Setting a light switch to "on" is idempotent; pressing a toggle button is not. A data load is idempotent when running the same job again on the same input leaves the table exactly as the first run did. This matters because pipelines are run again all the time: a scheduler retries after a timeout, an engineer reruns last night's file after a fix, and a crash halfway through leaves you unsure which rows made it. If every rerun appends the same rows again, each retry silently doubles the data, totals are wrong and nobody notices until a report is questioned.

A **plain insert is never idempotent**. Idempotency has to be designed into the load, in one of three ways that this day teaches: replace what the run owns, upsert by key, or make the whole run all-or-nothing and let a successful run be the only one that counts.

### Ways to write rows

**One statement per row** (`INSERT` called in a Python loop) is simple and slow, because each statement is a separate round trip to the server. `cursor.executemany(sql, rows)` takes one statement and a sequence of parameter tuples and runs it for each of them, which is much shorter to write and, with `psycopg`, sends the rows efficiently. **Batching** means sending a bounded group of rows, for example 1,000 at a time, rather than one row or the entire file: batches keep memory small and make progress visible.

`DataFrame.to_sql(name, connection, if_exists=..., index=False)` writes a whole DataFrame, creating the table when needed. `if_exists="fail"` (the default) raises an error when the table exists, `"append"` adds the rows, and `"replace"` **drops the table and creates it again**, which also removes your primary key, constraints and column types, because the new table is built from the DataFrame's dtypes. `to_sql` is convenient for small and medium loads and for staging; a table with designed constraints (Day 92) should be created first with your own `CREATE TABLE` and then filled with `if_exists="append"`.

**`COPY`** is PostgreSQL's bulk-loading command. `COPY target (a, b) FROM STDIN WITH (FORMAT csv)` opens a stream, and the client sends all the rows through it as one command, with far less overhead per row than separate inserts. In `psycopg` 3 you write `with cur.copy("COPY ... FROM STDIN") as copy:` and send rows with `copy.write_row(row)`. `COPY ... FROM 'path'` reads a file on the **server's** disk and needs special privileges, and the `psql` command `\copy` reads a file on the client machine. A `COPY` is one statement, so it is **all-or-nothing**: one malformed row aborts the command and loads none of the rows.

### Making a load repeatable

The first technique is **replace what the run owns**. If each run loads one day's file, tag every row with that day and begin the run with `DELETE FROM sale WHERE load_date = '2026-01-05'`, then insert the day's rows, all in one transaction. A rerun deletes its own earlier rows and inserts them again, so the result is the same. Emptying a staging table with `TRUNCATE` at the start of every run is the same idea for tables that only ever hold the current load.

The second technique is the **upsert**, a word made from update and insert: `INSERT ... ON CONFLICT (key) DO UPDATE SET ...`. If no row with that key exists the row is inserted; if one does, the existing row is updated. `DO NOTHING` skips rows whose key already exists. Both need a primary key or unique constraint on the conflict column, and both are available in PostgreSQL and in SQLite 3.24 or later. The special name `EXCLUDED` refers to the row you tried to insert. Adding `WHERE target.col IS DISTINCT FROM EXCLUDED.col` skips updates that would change nothing, so a rerun writes zero rows. One restriction to remember: a single `INSERT ... ON CONFLICT DO UPDATE` cannot contain the same key twice, and PostgreSQL stops with the error "cannot affect row a second time", so deduplicate the batch first.

### Transactions and batches

A **transaction** (Day 91) ends in a commit or a rollback. If you commit after every batch and the job fails on batch three, the table keeps batches one and two: a **partial load**, which is the worst state, because a rerun then meets duplicates or a table of unknown content. If the whole load runs inside one transaction, a failure rolls back everything and the table is as it was before the run. For files too large for one transaction, use per-batch commits only together with a repeatable technique, so that a rerun repairs the table. A transaction holds locks, so it should cover the load and nothing else.

### Common misconception

Many learners believe that a retry loop makes a load safe: "if it fails, run it again". A retry of a non-idempotent load is exactly what creates duplicates. A second belief is that `to_sql(if_exists="replace")` is a harmless way to make a load repeatable. It is repeatable, but it throws away the table's design every time.

### Why it matters

A load that can be run twice is a load you can retry, backfill and test without fear. Every orchestration tool you will use later assumes that tasks can be retried, and idempotency is what makes that assumption true.

## Syntax and key functions

Batched inserts with `psycopg` on PostgreSQL (placeholders are `%s`; not run here because there is no server):

```python
import psycopg

with psycopg.connect(dsn) as conn:                # commits at the end, rolls back on error
    with conn.cursor() as cur:
        cur.executemany(
            "INSERT INTO sale (id, amount) VALUES (%s, %s) "
            "ON CONFLICT (id) DO UPDATE SET amount = EXCLUDED.amount",
            rows,                                  # a list of (id, amount) tuples
        )
```

Bulk load with `COPY` through `psycopg`:

```python
with psycopg.connect(dsn) as conn:
    with conn.cursor() as cur:
        with cur.copy("COPY sale (id, amount) FROM STDIN") as copy:
            for row in rows:
                copy.write_row(row)
```

`DataFrame.to_sql` through a SQLAlchemy engine:

```python
df.to_sql("stg_sale", engine, if_exists="append", index=False, chunksize=1000)
```

Upsert and replace in SQL:

```sql-syntax
INSERT INTO target (key, col) VALUES (...)
ON CONFLICT (key) DO UPDATE SET col = EXCLUDED.col
WHERE target.col IS DISTINCT FROM EXCLUDED.col;

INSERT INTO target (key, col) VALUES (...) ON CONFLICT (key) DO NOTHING;

DELETE FROM target WHERE load_date = <this run's date>;
```

| Item | What it does or returns |
|---|---|
| `cur.executemany(sql, rows)` | Runs the statement once per parameter tuple; `rowcount` totals the changed rows in `sqlite3`. |
| `df.to_sql(name, con, if_exists, index, chunksize)` | Writes a DataFrame; returns the number of rows written when the driver reports it. |
| `if_exists="fail" / "append" / "replace"` | Error when the table exists / add rows / drop and recreate. |
| `COPY t (cols) FROM STDIN` | Bulk-loads a stream; all-or-nothing. |
| `COPY t FROM 'file'`, `COPY t TO 'file'` | Server-side file forms (PGlite uses its own virtual file system). |
| `ON CONFLICT (key) DO UPDATE / DO NOTHING` | Upsert or skip rows whose key exists. |
| `EXCLUDED` | The row proposed for insertion. |
| `RETURNING cols` | Returns the rows an insert or update wrote. |
| `with conn:` (sqlite3) | Commit on success, rollback on exception. |

## Learn by example

### Example 1: Batches with `executemany`

A generator produces 10 rows without building a list. `batches` cuts any iterable into lists of at most 4 rows, so memory holds one batch at a time. All batches run inside one `with conn:` block, so they commit together. In `sqlite3`, `rowcount` after `executemany` is the total number of rows written.

```python run
import sqlite3
from itertools import islice

def batches(rows, size):
    it = iter(rows)
    while True:
        batch = list(islice(it, size))
        if not batch:
            return
        yield batch

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE reading (id INTEGER PRIMARY KEY, sensor TEXT, value REAL)")
rows = ((i, f"s{i % 3}", i * 1.5) for i in range(1, 11))

loaded = 0
with conn:
    for number, batch in enumerate(batches(rows, 4), start=1):
        cur = conn.executemany("INSERT INTO reading VALUES (?, ?, ?)", batch)
        loaded += cur.rowcount
        print("batch", number, len(batch), cur.rowcount)
print(loaded, conn.execute("SELECT COUNT(*), SUM(value) FROM reading").fetchone())
```

```output
batch 1 4 4
batch 2 4 4
batch 3 2 2
10 (10, 82.5)
```

### Example 2: A rerun that duplicates, and two repeatable loads

The first table has no key, so running the same load twice stores every row twice. The second load replaces what its run owns: it deletes the rows with this run's `load_date` and inserts them again inside one transaction. The third is an upsert on the primary key. Both are run twice, and the second run of the upsert uses a corrected amount for id 2 to show that it updates the row in place.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
rows = [(1, 10.0), (2, 20.0), (3, 30.0)]

conn.execute("CREATE TABLE plain_sale (id INTEGER, amount REAL)")
for _ in range(2):
    conn.executemany("INSERT INTO plain_sale VALUES (?, ?)", rows)
print("plain insert twice:", conn.execute("SELECT COUNT(*) FROM plain_sale").fetchone()[0])

conn.execute("CREATE TABLE day_sale (id INTEGER, amount REAL, load_date TEXT)")
def load_day(conn, day, rows):
    with conn:
        conn.execute("DELETE FROM day_sale WHERE load_date = ?", (day,))
        conn.executemany("INSERT INTO day_sale VALUES (?, ?, ?)", [(i, a, day) for i, a in rows])
load_day(conn, "2026-01-05", rows)
load_day(conn, "2026-01-05", rows)
print("replace the day twice:", conn.execute("SELECT COUNT(*) FROM day_sale").fetchone()[0])

conn.execute("CREATE TABLE sale (id INTEGER PRIMARY KEY, amount REAL)")
upsert = "INSERT INTO sale VALUES (?, ?) ON CONFLICT (id) DO UPDATE SET amount = excluded.amount"
with conn:
    conn.executemany(upsert, rows)
with conn:
    conn.executemany(upsert, [(1, 10.0), (2, 25.0), (3, 30.0)])
print("upsert twice:", conn.execute("SELECT id, amount FROM sale ORDER BY id").fetchall())
```

```output
plain insert twice: 6
replace the day twice: 3
upsert twice: [(1, 10.0), (2, 25.0), (3, 30.0)]
```

### Example 3: One transaction or one per batch

Nine rows are loaded in batches of 3, and row 7 repeats the key `2`, so batch 3 fails. Committing per batch leaves batches 1 and 2 in the table, a partial load. One transaction around the whole load leaves the table empty, which is a clean state to rerun from.

```python run
import sqlite3

rows = [(1, "a"), (2, "b"), (3, "c"), (4, "d"), (5, "e"), (6, "f"), (2, "dup"), (8, "h"), (9, "i")]

def load(per_batch):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE t (id INTEGER PRIMARY KEY, v TEXT)")
    try:
        if per_batch:
            for start in range(0, len(rows), 3):
                with conn:
                    conn.executemany("INSERT INTO t VALUES (?, ?)", rows[start:start + 3])
        else:
            with conn:
                for start in range(0, len(rows), 3):
                    conn.executemany("INSERT INTO t VALUES (?, ?)", rows[start:start + 3])
    except sqlite3.IntegrityError as err:
        print("failed:", err)
    return conn.execute("SELECT COUNT(*) FROM t").fetchone()[0]

print("rows after per-batch commits:", load(True))
print("rows after one transaction:", load(False))
```

```output
failed: UNIQUE constraint failed: t.id
rows after per-batch commits: 6
failed: UNIQUE constraint failed: t.id
rows after one transaction: 0
```

### Example 4: `to_sql` and `if_exists`

`to_sql` accepts a plain `sqlite3` connection. The default `if_exists="fail"` refuses to touch an existing table, `"append"` adds rows (and so duplicates a rerun unless a key rejects the rows), and `"replace"` drops and recreates the table. The last lines show the table definition before and after a replace: the primary key disappears because the new table is built from DataFrame dtypes.

```python run
import sqlite3
import pandas as pd

df = pd.DataFrame({"id": [1, 2, 3], "name": ["Ana", "Ben", "Cy"], "amount": [10.5, 20.0, 7.25]})
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE sale (id INTEGER PRIMARY KEY, name TEXT, amount REAL)")

try:
    df.to_sql("sale", conn, index=False)
except ValueError as err:
    print("fail:", err)

df.to_sql("sale", conn, index=False, if_exists="append")
try:
    df.to_sql("sale", conn, index=False, if_exists="append")
except sqlite3.IntegrityError as err:
    print("second append:", err)
print(conn.execute("SELECT sql FROM sqlite_master WHERE name = 'sale'").fetchone()[0])

n = df.to_sql("sale", conn, index=False, if_exists="replace")
print("replace wrote", n)
print(conn.execute("SELECT sql FROM sqlite_master WHERE name = 'sale'").fetchone()[0].replace("\n", " "))
```

```output
fail: Table 'sale' already exists.
second append: UNIQUE constraint failed: sale.id
CREATE TABLE sale (id INTEGER PRIMARY KEY, name TEXT, amount REAL)
replace wrote 3
CREATE TABLE "sale" ( "id" INTEGER,   "name" TEXT,   "amount" REAL )
```

### Example 5: `COPY` on PGlite

PGlite cannot take a `FROM STDIN` stream through plain SQL, but it supports the file forms of `COPY` on its own virtual file system. The first part writes a table to a CSV file and loads it into a second table: the NULL amount is written as an empty unquoted field and read back as NULL, and the comma and the quote inside names are escaped by CSV quoting. The second part writes a file with one bad id and shows that `COPY` loads nothing at all, with SQLSTATE `22P02` (invalid text representation). On a real server the `FROM STDIN` form works the same way.

```sql run
CREATE TABLE src (id int, name text, amount numeric(8,2));
INSERT INTO src VALUES (1, 'Ana', 10.5), (2, 'O''Brien, Jr', NULL), (3, 'Cy "C"', 7);
COPY src TO '/tmp/src.csv' WITH (FORMAT csv, HEADER true);
CREATE TABLE dst (id int PRIMARY KEY, name text, amount numeric(8,2));
COPY dst FROM '/tmp/src.csv' WITH (FORMAT csv, HEADER true);

CREATE TABLE raw_text (id text, name text);
INSERT INTO raw_text VALUES ('1', 'Ana'), ('abc', 'Bad'), ('3', 'Cy');
COPY raw_text TO '/tmp/raw.csv' WITH (FORMAT csv);
CREATE TABLE dst2 (id int PRIMARY KEY, name text);
CREATE TABLE copy_log (state text);
DO $$
BEGIN
  BEGIN
    COPY dst2 FROM '/tmp/raw.csv' WITH (FORMAT csv);
  EXCEPTION WHEN OTHERS THEN INSERT INTO copy_log VALUES (SQLSTATE);
  END;
END $$;

SELECT (SELECT count(*) FROM dst) AS copied_rows,
       (SELECT amount IS NULL FROM dst WHERE id = 2) AS null_kept,
       (SELECT count(*) FROM dst2) AS rows_after_bad_copy,
       (SELECT state FROM copy_log) AS bad_copy_state;
```

```output
copied_rows | null_kept | rows_after_bad_copy | bad_copy_state
3 | true | 0 | 22P02
```

### Example 6: An upsert that writes zero rows on a rerun

A data-modifying `WITH` clause lets an insert report how many rows it wrote through `RETURNING`, and the count is logged. Day 1 loads two products. Day 2 corrects a price and adds a product. The corrected load is then run a second time: because of `WHERE product.price IS DISTINCT FROM EXCLUDED.price` it writes zero rows, which is what idempotent means in numbers. The last two columns show the final state of the tables, so they are the same on every line.

```sql run
CREATE TABLE product (sku text PRIMARY KEY, name text NOT NULL, price numeric(8,2) NOT NULL);
CREATE TABLE incoming (sku text, name text, price numeric(8,2));
CREATE TABLE run_log (run_no int, rows_written bigint);

INSERT INTO incoming VALUES ('A1', 'Pen', 1.50), ('B2', 'Ink', 4.00);
WITH w AS (
  INSERT INTO product SELECT * FROM incoming
  ON CONFLICT (sku) DO UPDATE SET name = EXCLUDED.name, price = EXCLUDED.price
  WHERE product.price IS DISTINCT FROM EXCLUDED.price OR product.name IS DISTINCT FROM EXCLUDED.name
  RETURNING sku)
INSERT INTO run_log SELECT 1, count(*) FROM w;

DELETE FROM incoming;
INSERT INTO incoming VALUES ('A1', 'Pen', 1.75), ('B2', 'Ink', 4.00), ('C3', 'Pad', 2.20);
WITH w AS (
  INSERT INTO product SELECT * FROM incoming
  ON CONFLICT (sku) DO UPDATE SET name = EXCLUDED.name, price = EXCLUDED.price
  WHERE product.price IS DISTINCT FROM EXCLUDED.price OR product.name IS DISTINCT FROM EXCLUDED.name
  RETURNING sku)
INSERT INTO run_log SELECT 2, count(*) FROM w;
WITH w AS (
  INSERT INTO product SELECT * FROM incoming
  ON CONFLICT (sku) DO UPDATE SET name = EXCLUDED.name, price = EXCLUDED.price
  WHERE product.price IS DISTINCT FROM EXCLUDED.price OR product.name IS DISTINCT FROM EXCLUDED.name
  RETURNING sku)
INSERT INTO run_log SELECT 3, count(*) FROM w;

SELECT l.run_no, l.rows_written, (SELECT count(*) FROM product) AS rows_in_product,
       (SELECT price FROM product WHERE sku = 'A1') AS a1_price
FROM run_log l ORDER BY l.run_no;
```

```output
run_no | rows_written | rows_in_product | a1_price
1 | 2 | 3 | 1.75
2 | 2 | 3 | 1.75
3 | 0 | 3 | 1.75
```

## Real-world applications

- **Retried and backfilled jobs.** A scheduler retries a failed daily load, and an engineer reloads a month after a fix. With replace-the-day (Example 2) or an upsert (Example 6) each rerun converges to the same table instead of doubling it.
- **Bulk loading.** A nightly file with millions of rows is written with `COPY`, which is one command and one transaction (Example 5), instead of millions of inserts.
- **Staging loads.** `to_sql` with `if_exists="replace"` or an emptied staging table (Example 4) is a quick way to land a DataFrame before the validated rows are promoted into a designed table.
- **Safe failure.** A load inside one transaction (Example 3) means that a crash leaves either the old state or the new state, so the on-call engineer never has to inspect a half-loaded table.

## Daily review

### Key takeaways

- Idempotent means a rerun leaves the same result; a plain insert is not idempotent.
- `executemany` runs one statement for many parameter tuples; batch large inputs, and pass `%s` placeholders to `psycopg`, `?` to `sqlite3`.
- `to_sql(if_exists="append")` duplicates on a rerun and `"replace"` drops the table and its design; create the table yourself and append.
- `COPY` is the bulk path and is all-or-nothing; `ON CONFLICT` upserts by key and `EXCLUDED` is the proposed row.
- Wrap a load in one transaction, or pair per-batch commits with a repeatable technique.

### Common mistakes

- Rerunning a plain `INSERT` load and doubling the rows. The symptom is totals that exactly double; fix it with delete-then-insert for the run's own rows, or an upsert.
- Using `to_sql(..., if_exists="replace")` on a table with keys and constraints, so the next load runs on a table that has none.
- `ON CONFLICT` without a unique key: PostgreSQL raises `there is no unique or exclusion constraint matching the ON CONFLICT specification`.
- Two rows with the same key in one `INSERT ... ON CONFLICT DO UPDATE`: `ON CONFLICT DO UPDATE command cannot affect row a second time`. Deduplicate the batch first.
- Committing after every batch, so a failure leaves a partial load.
- Calling `executemany` with a bare value instead of tuples, which raises a bindings error; pass a list of tuples.

### Revision notes

- `with conn:` commits or rolls back; `cur.executemany(sql, rows)`; `cur.copy("COPY t FROM STDIN")` with `copy.write_row(row)`.
- Repeatable: `DELETE` this run's rows then insert, or `INSERT ... ON CONFLICT (key) DO UPDATE SET ... = EXCLUDED....`.
- `if_exists`: `fail`, `append`, `replace` (drops constraints).
- A failed `COPY` loads zero rows.

## Objectives

- Move paths, table names, limits and credentials out of the code and into configuration.
- Read settings from environment variables with `os.environ`, with defaults and required values.
- Load config from JSON, `configparser` (INI) and TOML text, and merge per-environment settings over defaults.
- Keep secrets out of the code, out of logs and out of version control, and validate the config at startup.

## Understand

### What configuration is

Everything in a pipeline that can legitimately change without changing the logic is **configuration**: the source URL, the output table name, the batch size, the database host, the number of retries, the API key. Code is the same on your laptop, in the test environment and in production; the configuration is what differs. If values are hard-coded (`TABLE = "orders_clean"`, `host="db.internal"`) every change means editing code, and a mistake means a deploy; worse, the code that runs on your laptop may write to a production table because someone forgot to change one string. The rule is simple: **code says how, configuration says which and how much**.

### Environment variables

An **environment variable** is a named text value that the operating system gives to a process. In Python they appear in the dictionary-like `os.environ`. Reading one is `os.environ["ETL_DB_HOST"]`, which raises `KeyError` when the variable is missing, or `os.environ.get("ETL_DB_HOST", "localhost")`, which returns a default. All values are text, so numbers must be converted: `int(os.environ.get("ETL_BATCH_SIZE", "500"))`. Environment variables are the usual way to pass secrets and per-environment settings to a program, because the platform that runs the job (a scheduler, a container, a CI system) can set them without any file in the repository. In today's examples the code sets the variables itself (`os.environ["ETL_ENV"] = "dev"`) so the output is reproducible; in real life the platform sets them before the program starts.

### Config files

A **config file** holds structured settings, so you can keep many together and give them structure. Python's standard library reads three common formats. **JSON** (`json.loads(text)`) is universal but has no comments. **INI** files, read by `configparser`, have `[sections]` and `key = value` lines, and every value is text. **TOML**, read by `tomllib.loads(text)` (standard library from Python 3.11), has sections, comments and real types: strings, integers, booleans and lists. TOML is a good default for new projects. A config file belongs in the repository only if it holds no secrets; a file with a password is a leak waiting to happen.

### Per-environment settings and layering

Real pipelines run in at least two places, often called `dev` and `prod`. A tidy config has a `[default]` section with settings that are the same everywhere and one section per environment that overrides only what differs. Loading is then **layering**: start with the defaults, apply the section for the current environment, then apply environment variables, and let the highest layer win. The result is one plain dictionary the pipeline uses, so no other function reads files or the environment. This keeps the rest of the code simple and testable (Day 121): a test builds a config dictionary by hand.

### Secrets

A **secret** is a value that gives access: a password, an API key, a token. Four rules. Never write a secret in code or in a committed config file; Git history keeps it forever, even after deletion. Supply it through the environment or a secret manager (a service that stores secrets and hands them to authorised jobs). Never print or log it: a log line is stored, copied and searched by many people, so print a masked form (`****abcd`) or just that it is set. And give each environment its own secret, so a leak from dev cannot open production. The symptom of a mistake is serious: a key committed to a public repository can be picked up by automated scanners, and the only safe fix is to revoke it, so removing the line is not enough. A common misconception is that a `.env` file is "just config": it usually contains secrets and belongs in `.gitignore`.

### Validating at startup

A missing setting should fail at the start of the run, with a message that names every problem, not three hours in when the loader reaches the line that needs it. A `validate(config)` function checks that required keys are present and have the right type, and raises one error listing all problems. This turns a confusing `KeyError` deep in the code into a clear first line of the log.

### Where PostgreSQL fits

The connection string to PostgreSQL is the typical config-plus-secret value: host, port, database name and user are ordinary settings; the password is the secret. Code reads a single `DATABASE_URL` variable or builds the connection from settings plus `ETL_DB_PASSWORD`. The `psycopg` code is shown below as text only, since no server runs in this learning environment; the runnable examples use `sqlite3` in memory, whose location is just another setting.

## Syntax and key functions

```python
import os

host = os.environ.get("ETL_DB_HOST", "localhost")        # default
password = os.environ["ETL_DB_PASSWORD"]                 # required: KeyError when missing
batch_size = int(os.environ.get("ETL_BATCH_SIZE", "500"))  # text to int
```

```python
import os
import psycopg

# real connection: the password comes from the environment, never from the code
conn = psycopg.connect(
    host=os.environ["ETL_DB_HOST"], dbname="shop", user="etl",
    password=os.environ["ETL_DB_PASSWORD"],
)
```

```toml
[default]
table = "orders_clean"
batch_size = 500

[prod]
db_host = "db.internal"
batch_size = 5000
```

| Item | What it does or returns |
|---|---|
| `os.environ[key]` | The value, or `KeyError` if unset. |
| `os.environ.get(key, default)` | The value, or the default. |
| `json.loads(text)` | Parses JSON text to dicts, lists, numbers, strings. |
| `configparser.ConfigParser().read_string(text)` | Parses INI text; values are strings; `cp["section"]["key"]`. |
| `tomllib.loads(text)` | Parses TOML text with real types (Python 3.11+). |
| `{**defaults, **override}` | Merges dicts; later keys win. |
| `.gitignore` | List of files Git must never commit, such as `.env`. |

## Learn by example

### Example 1: Environment variables

The code sets two variables (a platform would do this) and reads them. A required variable raises `KeyError`, a default covers the optional one, and the text value is converted to an `int`.

```python run
import os

os.environ["ETL_ENV"] = "dev"
os.environ["ETL_BATCH_SIZE"] = "250"

print(os.environ["ETL_ENV"])
batch_size = int(os.environ.get("ETL_BATCH_SIZE", "500"))
print(batch_size, type(batch_size).__name__)
print(os.environ.get("ETL_TABLE", "orders_clean"))
try:
    os.environ["ETL_DB_PASSWORD_NOT_SET"]
except KeyError as exc:
    print("missing:", exc)
```

```output
dev
250 int
orders_clean
missing: 'ETL_DB_PASSWORD_NOT_SET'
```
### Example 2: Three file formats

The same settings in JSON, INI and TOML text. JSON and TOML give numbers back as numbers; INI gives text and `getint` converts. TOML also allows a comment and a list.

```python run
import configparser
import json
import tomllib

as_json = json.loads('{"table": "orders_clean", "batch_size": 500}')
ini = configparser.ConfigParser()
ini.read_string("[etl]\ntable = orders_clean\nbatch_size = 500\n")
as_toml = tomllib.loads('# pipeline settings\ntable = "orders_clean"\nbatch_size = 500\nstatuses = ["paid", "refunded"]\n')

print(as_json["batch_size"] + 1)
print(ini["etl"]["batch_size"] + "1", ini.getint("etl", "batch_size") + 1)
print(as_toml["batch_size"] + 1, as_toml["statuses"])
```

```output
501
5001 501
501 ['paid', 'refunded']
```
### Example 3: Layering defaults, environment and variables

The TOML text has defaults and one section per environment. The loader merges them in order: defaults, the environment's section, then any `ETL_` environment variable, which wins.

```python run
import os
import tomllib

TEXT = """
[default]
table = "orders_clean"
batch_size = 500
db_path = ":memory:"

[dev]
batch_size = 50

[prod]
db_path = "/data/orders.db"
batch_size = 5000
"""

def load_config(env, environ):
    data = tomllib.loads(TEXT)
    config = {**data["default"], **data.get(env, {})}
    if "ETL_BATCH_SIZE" in environ:
        config["batch_size"] = int(environ["ETL_BATCH_SIZE"])
    return config

print(load_config("dev", {}))
print(load_config("prod", {}))
print(load_config("prod", {"ETL_BATCH_SIZE": "100"})["batch_size"])
```

```output
{'table': 'orders_clean', 'batch_size': 50, 'db_path': ':memory:'}
{'table': 'orders_clean', 'batch_size': 5000, 'db_path': '/data/orders.db'}
100
```
### Example 4: Secrets stay out of the logs

A `Secret` wrapper prints as `***` in every repr and log line, while `.reveal()` gives the real value only where the connection is built. The mask function shows the last two characters at most. The connection string for the log is built without the password.

```python run
import os

class Secret:
    def __init__(self, value):
        self._value = value
    def reveal(self):
        return self._value
    def __repr__(self):
        return "Secret(***)"
    __str__ = __repr__

os.environ["ETL_DB_PASSWORD"] = "s3cr3t-value"
config = {"host": "db.internal", "user": "etl", "password": Secret(os.environ["ETL_DB_PASSWORD"])}
print(config)
print(f"password is {config['password']}")
print("postgresql://{user}@{host}/shop".format(**config))
print("revealed length:", len(config["password"].reveal()))
```

```output
{'host': 'db.internal', 'user': 'etl', 'password': Secret(***)}
password is Secret(***)
postgresql://etl@db.internal/shop
revealed length: 12
```
### Example 5: Validate at startup and run the pipeline from config

`validate` lists every problem at once. The pipeline then uses only the validated dictionary: the database location and the table name come from config, and the run prints the loaded count.

```python run
import sqlite3

class ConfigError(Exception):
    pass

REQUIRED = {"db_path": str, "table": str, "batch_size": int}

def validate(config):
    problems = []
    for key, kind in REQUIRED.items():
        if key not in config:
            problems.append(f"missing {key}")
        elif not isinstance(config[key], kind):
            problems.append(f"{key} must be {kind.__name__}")
    if problems:
        raise ConfigError("; ".join(problems))
    return config

try:
    validate({"db_path": ":memory:", "batch_size": "500"})
except ConfigError as exc:
    print("config error:", exc)

config = validate({"db_path": ":memory:", "table": "orders_clean", "batch_size": 2})
conn = sqlite3.connect(config["db_path"])
conn.execute(f"CREATE TABLE {config['table']} (order_id INTEGER PRIMARY KEY, amount_cents INTEGER)")
rows = [(1, 1990), (2, 125000), (3, 4500), (4, 750), (5, 1200)]
for start in range(0, len(rows), config["batch_size"]):
    conn.executemany(f"INSERT INTO {config['table']} VALUES (?, ?)", rows[start:start + config["batch_size"]])
print("loaded", conn.execute(f"SELECT COUNT(*) FROM {config['table']}").fetchone()[0], "rows into", config["table"])
```

```output
config error: missing table; batch_size must be int
loaded 5 rows into orders_clean
```
## Real-world applications

- **Dev and prod from the same code.** The layered config of Example 3 lets one code base use an in-memory database on a laptop and the real database in production, chosen only by `ETL_ENV`.
- **Credential hygiene.** Passwords arrive through the environment or a secret manager, and the `Secret` wrapper of Example 4 stops them reaching the logs even when someone prints the whole config.
- **Fast, clear failures.** Validating at startup (Example 5) turns a missing setting into a one-line message at the start of a nightly job, not a stack trace at 3 a.m.
- **Tuning without deploys.** The batch size or retry count can be changed in the scheduler's settings for one run, which is how operators react to a slow database.

## Daily review

### Key takeaways

- Code says how; configuration says which and how much.
- Environment variables are text; convert and give defaults; use `os.environ[key]` for required values.
- Layer defaults, the environment's section and overrides into one dictionary at startup.
- Secrets live in the environment or a secret manager, never in code, config files in the repository or logs.
- Validate the config at startup and name every problem.

### Common mistakes

- Committing a password or key. Deleting the line later does not remove it from history; revoke and replace the secret.
- Using `os.environ.get("ETL_BATCH_SIZE", 500)` and getting a string `"250"` from the environment but an int `500` from the default. Convert: `int(os.environ.get("ETL_BATCH_SIZE", "500"))`.
- Reading `os.environ` in many functions, so tests need patched environments. Read it once into a config dictionary.
- Printing the whole config in a debug line and leaking a password. Wrap secrets or mask them.
- Putting a `.env` file in Git. List it in `.gitignore` and commit a `.env.example` with fake values.

### Revision notes

- `os.environ["K"]` required; `.get("K", "default")` optional; everything is text.
- JSON, INI (`configparser`, all text) and TOML (`tomllib`, typed) all load from text.
- Layering: defaults, `[env]` section, environment variables; later wins.
- Secrets: environment, masked in logs, one per environment, never committed.

## Objectives

- Use a repeatable method for a SQL interview question: clarify, state the approach, write, test on edge cases, then discuss optimisation.
- Solve the recurring interview patterns on Northwind: anti-join, top-N per group, period-over-period change, grouped conditions with `HAVING`, and latest-record-per-key.
- Explain the traps that interviewers probe: NULL behaviour, ties, fan-out after a join, and non-sargable filters.
- Work inside a time box and say what you would do with more time.
- Explain a query's result in a sentence, as an interviewer expects after you write it.

## Understand

### What a SQL interview tests

A SQL interview question is rarely about obscure syntax. It tests four things at once: whether you understand the **data model** (which tables, what one row means), whether you can break a request into steps, whether you notice **edge cases** such as ties, NULLs and missing rows, and whether you can **communicate** while you work. A candidate who writes a correct query in silence often scores below one who states the approach, writes a slightly slower query and checks it. For a data engineering role the questions also lean toward data correctness: deduplication, latest record per key, idempotent loads, reconciliation between two tables and constraint design.

### A method that fits in a time box

Typical questions are given 10 to 20 minutes. Use the same five steps every time:

1. **Clarify** (one minute). Repeat the request in your words and ask about the grain and the ambiguous parts: "Revenue is price times quantity after discount, per order line? Should customers without orders appear? What should happen on ties?" Interviewers often leave exactly these parts open to see whether you ask.
2. **Plan** (one minute). Say the steps aloud: "Join orders to lines, aggregate to one row per customer, then rank." A plan you can state is a plan you can fix when it is wrong.
3. **Write** the simplest correct version first, in small pieces: a CTE for each step is easier to explain and to debug than one nested expression.
4. **Test** against a mental sample and the edge cases: a customer with no rows, two rows with the same value, a NULL in the filter column. Run the query if you can and check the row count against what you expect.
5. **Improve and discuss.** Mention readability, then performance: is the filter sargable, is a join multiplying rows, would an index on the join key help.

If you are stuck, say what you would do (for example "I would first check how many rows each customer has") and write a partial solution. A partial answer with the right structure scores better than a blank.

### The recurring patterns

- **Anti-join (rows with no match).** "Customers with no orders" or "products never sold". The safe forms are `LEFT JOIN ... WHERE right.key IS NULL` and `NOT EXISTS`. The trap is `NOT IN (subquery)`: if the subquery returns a single NULL, the whole comparison becomes unknown and no rows come back.
- **Top-N per group.** "The best product in each category". Use `ROW_NUMBER()` (exactly N rows per group, ties broken arbitrarily unless you add a tie-break to `ORDER BY`), `RANK()` (ties share a rank, so you may get more than N rows) or `DENSE_RANK()`. State which one you chose and why.
- **Period-over-period.** `LAG(value) OVER (ORDER BY period)` gives the previous row's value. Remember that it is the previous **row**, not the previous calendar period: if a period has no row, the comparison silently spans a gap. Protect the percentage with `NULLIF(previous, 0)`.
- **Grouped conditions.** `HAVING` filters groups after aggregation and `WHERE` filters rows before it. Conditional counts such as `COUNT(*) FILTER (WHERE shipped_date > required_date)` answer "how many of each kind" in one pass.
- **Latest record per key.** `ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC) = 1`, with a tie-break column so that the result is deterministic.
- **Running totals and moving averages.** `SUM(x) OVER (ORDER BY period)`, whose default frame with an `ORDER BY` runs from the start to the current row (with ties in the ordering column grouped together in `RANGE` mode).

### The traps interviewers set

**Fan-out.** Joining orders to order lines and then summing an order-level column (such as freight) repeats it once per line and inflates the total. Aggregate each side to the same grain before joining, or sum a column that lives at line level. **NULLs.** `NULL = NULL` is not true; comparisons with NULL are unknown; `COUNT(column)` skips NULLs while `COUNT(*)` does not; `NOT IN` with a NULL returns nothing. **Ties.** "Top 3" with ties can legitimately mean more than 3 rows. **Non-sargable filters.** `WHERE EXTRACT(year FROM order_date) = 1997` wraps the column in a function, so an index on `order_date` cannot be used; the range `order_date >= '1997-01-01' AND order_date < '1998-01-01'` returns the same rows and can use the index. **Integer division.** In PostgreSQL `3 / 2` is `1`; cast one side to numeric before dividing.

### Explaining results and trade-offs

After writing a query, give a one-sentence reading ("Two products were never ordered, so they are candidates for review") and one limitation ("revenue here ignores freight and returns"). For performance questions, talk in the right order: first correctness, then the amount of data scanned, then joins and indexes. Do not claim a plan you have not seen: say "I would check the execution plan with `EXPLAIN` to confirm that the index is used."

### Why it matters, and the misconception

These patterns are also the daily work of an engineer: finding orphan rows, deduplicating, computing deltas. The misconception is that speed of typing decides the interview. What decides it is a clear plan, correct handling of edge cases, and a calm explanation of the result.

## Syntax and key functions

```sql-syntax
-- anti-join
SELECT p.product_id FROM products p
LEFT JOIN order_details od ON od.product_id = p.product_id
WHERE od.product_id IS NULL;

-- top-1 per group with a deterministic tie-break
ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY revenue DESC, product_id)

-- previous period
LAG(revenue) OVER (ORDER BY quarter)
```

| Tool | Use |
|---|---|
| `LEFT JOIN ... IS NULL` / `NOT EXISTS` | Rows with no match. |
| `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()` | Ranking with different tie rules. |
| `LAG(x, n)` / `LEAD(x, n)` | Value from an earlier / later row. |
| `COUNT(*) FILTER (WHERE c)` | Conditional count in one pass. |
| `HAVING` | Filter after `GROUP BY`. |
| `NULLIF(a, 0)` | Avoids division by zero. |

## Learn by example

### Example 1: Products that were never ordered

Question: "Which products have never been sold?" The clarifying question is whether a product with an order line counts as sold even if the order was never shipped. Here it does. The anti-join keeps products with no matching line.

```sql run
SELECT p.product_id, p.product_name
FROM products p
LEFT JOIN order_details od ON od.product_id = p.product_id
WHERE od.product_id IS NULL
ORDER BY p.product_id;
```

```output
product_id | product_name
9 | Mishi Kobe Niku
17 | Alice Mutton
```

Two products come back. State the reading: "Two products have no sales in three years." The `NOT EXISTS` form returns the same rows and is often preferred because it cannot be broken by NULLs.

### Example 2: Top product per category

Question: "For each category, which product sold the most units?" The tie-break (`product_id`) makes the result deterministic. The plan is in two CTEs: units per product, then a rank within each category.

```sql run
WITH units AS (
  SELECT p.category_id, p.product_id, p.product_name, SUM(od.quantity) AS units
  FROM products p JOIN order_details od ON od.product_id = p.product_id
  GROUP BY p.category_id, p.product_id, p.product_name
), ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY units DESC, product_id) AS rn
  FROM units
)
SELECT c.category_name, r.product_name, r.units
FROM ranked r JOIN categories c ON c.category_id = r.category_id
WHERE r.rn = 1
ORDER BY c.category_name;
```

```output
category_name | product_name | units
Beverages | Lakkalikööri | 112
Condiments | Gula Malacca | 134
Confections | NuNuCa Nuß-Nougat-Creme | 100
Dairy Products | Mascarpone Fabioli | 138
Grains/Cereals | Tunnbröd | 72
Meat/Poultry | Thüringer Rostbratwurst | 192
Produce | Rössle Sauerkraut | 129
Seafood | Inlagd Sill | 162
```

Each of the eight categories appears once. If the interviewer asks "what if two products tie?", answer that `RANK()` would return both and `ROW_NUMBER()` with the tie-break returns one, and ask which the business wants.

### Example 3: Change against the previous quarter

Question: "Show quarterly revenue and the change from the previous quarter for 1998." The window runs over all quarters first and the filter is applied afterwards, so that the first quarter of 1998 still sees the last quarter of 1997. The series has no gaps, so `LAG` is the previous quarter.

```sql run
WITH q AS (
  SELECT date_trunc('quarter', o.order_date)::date AS quarter,
         SUM(od.unit_price * od.quantity * (1 - od.discount)) AS revenue
  FROM orders o JOIN order_details od ON od.order_id = o.order_id
  GROUP BY 1
), d AS (
  SELECT quarter, revenue, LAG(revenue) OVER (ORDER BY quarter) AS prev FROM q
)
SELECT quarter, ROUND(revenue::numeric, 0) AS revenue,
       ROUND(((revenue - prev) / NULLIF(prev, 0) * 100)::numeric, 1) AS change_pct
FROM d
WHERE quarter >= DATE '1998-01-01'
ORDER BY quarter;
```

```output
quarter | revenue | change_pct
1998-01-01 | 15449 | 36.2
1998-04-01 | 8687 | -43.8
1998-07-01 | 3323 | -61.7
1998-10-01 | 18477 | 456.0
```

Filtering inside the CTE before the window would have made the first row's change NULL. This is the most common mistake in this pattern.

### Example 4: HAVING and a conditional count

Question: "Which customers placed at least two orders, and how many of them shipped late?" `HAVING` filters customers after the counts exist, and `FILTER` counts the late ones in the same pass.

```sql run
SELECT customer_id,
       COUNT(*) AS orders,
       COUNT(*) FILTER (WHERE shipped_date > required_date) AS late_orders
FROM orders
GROUP BY customer_id
HAVING COUNT(*) >= 2
ORDER BY late_orders DESC, customer_id
LIMIT 5;
```

```output
customer_id | orders | late_orders
ANATR | 2 | 1
BERGS | 2 | 1
ALFKI | 2 | 0
ANTON | 2 | 0
AROUT | 2 | 0
```

The two customers with a late order come first. A not-yet-shipped order has a NULL `shipped_date`, so it is not counted as late, and the answer should mention it ("unshipped orders are not counted as late here").

### Example 5: A sargable filter

Question: "Count the orders of 1997 and make the filter index-friendly." Both queries return the same number. The first wraps the column in a function and the second compares the column with a range. Same result, different ability to use an index on the column; the lesson cannot show a plan, so state what you would check.

```sql run
SELECT 'function on column' AS version, COUNT(*) AS orders
FROM orders WHERE EXTRACT(year FROM order_date) = 1997
UNION ALL
SELECT 'range filter', COUNT(*)
FROM orders WHERE order_date >= DATE '1997-01-01' AND order_date < DATE '1998-01-01'
ORDER BY 1;
```

```output
version | orders
function on column | 33
range filter | 33
```

An interviewer expects: "The range form is sargable, so an index on `order_date` can be used. I would confirm with `EXPLAIN`." Nothing more should be claimed without the plan.

## Real-world applications

- **Data-quality checks**: the anti-join of Example 1 finds orphan and unused rows, and the same shape reconciles two tables.
- **Reporting queries**: period-over-period change with `LAG` (Example 3) is in almost every business dashboard.
- **Pipeline logic**: latest record per key (Day 168) and conditional counts are the core of deduplication and validation steps.
- **Code review**: spotting fan-out, `NOT IN` with NULLs and non-sargable filters is a routine review skill.

## Daily review

### Key takeaways

- Method: clarify, plan, write simply, test edge cases, then improve and discuss.
- Know the patterns: anti-join, top-N per group, `LAG`, `HAVING` with `FILTER`, latest per key.
- Watch for fan-out, NULLs, ties, non-sargable filters and integer division.
- Explain the result in a sentence and name one limitation.
- Claim performance only after seeing a plan.

### Common mistakes

- Starting to type without clarifying the grain. You solve the wrong problem; restate the question first.
- `NOT IN (subquery)` where the subquery can return NULL. No rows come back; use `NOT EXISTS` or a `LEFT JOIN`.
- Filtering inside the CTE before a `LAG`. The first row of the output loses its previous value; filter after the window.
- Summing an order-level column after a join to lines. The total is multiplied; aggregate at the right grain first.
- Saying "this is faster" without evidence. Say what you would measure.

### Revision notes

- `LEFT JOIN ... IS NULL`, `NOT EXISTS`; never `NOT IN` over a nullable column.
- `ROW_NUMBER` (one row, tie-break), `RANK` (ties share), `DENSE_RANK` (no gaps).
- Window first, filter afterwards.
- Sargable: compare the bare column with a range.

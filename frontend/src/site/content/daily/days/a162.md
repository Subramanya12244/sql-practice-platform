## Objectives

- Compare a source and a target on row counts and totals, and explain what each check can and cannot catch.
- Find the exact rows that differ with a key comparison: keys missing in the target, extra in the target, and duplicated.
- Compare values for the keys present on both sides, using a tolerance for decimal amounts.
- Locate a difference by comparing totals per group, and write the findings as a reconciliation report with a pass or fail status per check.
- Run the same comparison in SQL (`EXCEPT`, outer join) on the PostgreSQL-compatible database and in pandas on two tables read with `read_sql_query`.

## Understand

### What reconciliation is for

After a load (Day 161) the question is no longer "did the code run" but "is the target a faithful copy of the source". **Source-to-target validation** answers it by comparing what was supposed to arrive with what is in the table. **Reconciliation** is the same comparison written up as a report that says which checks passed, which failed, by how much, and which rows are involved. It matters because loads fail in quiet ways. A filter in the extract query is a day short. A type conversion truncates a decimal. A retry duplicates a batch. A test row is left in the target. A column is shifted by a header change. None of these produce an error, all of them produce wrong reports, and the people reading the reports find out weeks later.

### The ladder of checks

Think of the checks as a ladder, from cheap and coarse to expensive and exact. Each step catches problems the one below it misses.

**Row counts.** The number of rows in the source and the target. It is fast and catches lost batches and duplicated loads. It cannot catch a lost row balanced by an extra one: the count can agree while the contents differ.

**Totals.** The sum (and sometimes the minimum, maximum and the number of distinct values) of the important numeric columns. A total catches changed values and truncated decimals that counts miss. It can still be fooled when one error cancels another, for instance one amount too high by 9 and another too low by 9.

**Key comparison.** The set of keys on each side. The set difference tells you exactly which keys are **missing in the target** (in the source only), **extra in the target** (in the target only), and which keys are **duplicated**. This is the first check that names rows instead of counting them.

**Value comparison.** For the keys that exist on both sides, compare each column. This finds the row whose amount changed from 45.5 to 54.5 while the count, the keys and, in a lucky case, even the total looked fine. It is the most expensive step, so it is often run on a sample or on columns that matter.

**Group totals.** Totals per month, per status or per region. They are not another rung of exactness but a **locator**: when the grand totals differ, the group totals show where, so that you know whether the problem sits in one month or everywhere.

### Tolerances and expected differences

Two sides rarely agree to the last digit, and a perfect-match rule produces false alarms. Decimal values stored as floating-point numbers carry tiny binary errors (the sum of 0.1 and 0.2 is 0.30000000000000004), so compare amounts with a **tolerance**, such as a difference of at most 0.005 for two-decimal money, or round both sides to the same number of decimals first. Text can differ by invisible whitespace or case, which the cleaning step on Day 160 should remove before comparing.

Some differences are **expected**. The load may have rejected rows that failed validation and sent them to a reject list. The report should then not shout about them: it subtracts the known rejects from the missing keys and flags only the rest. The rule is that every difference is either explained by a named, counted reason or reported as a failure. "A few rows are always different" is how real problems get ignored.

### Where the comparison runs

When both tables live in the same database, compare them in SQL: `EXCEPT` returns the rows of one query that the other does not have, and a `FULL OUTER JOIN` on the key puts both sides next to each other, with `NULL` on the side that lacks the row. The data stays in the database and only the differences travel. When the source is a file or another system, load it into a DataFrame and compare in pandas: `merge(..., how="outer", indicator=True)` adds a column that says whether each key was found in the left side, the right side or both. In this lesson both are shown and give the same answer.

### What a good report contains

A reconciliation report is a small table with one row per check: the check name, the source value, the target value, the difference and a status (`OK` or `FAIL`). Below it, detail lists show the keys behind each failure, since "2 keys missing" is not actionable but "keys 1004 and 1010 missing" is. The report is produced by code on every load, stored with the load log, and when any check fails the job raises an error so that a person is told. A report that is only printed and never acted on is decoration.

### Why it matters, and the misconception

The misconception is that "the counts match, so the load is fine". Counts are the cheapest check and the weakest: the example of this lesson has equal counts, one missing row, one extra row and one changed amount at the same time. A second misconception is that a mismatch means the target is wrong: sometimes the source changed between the extract and the check, which is why the report records when each side was read.

## Syntax and key functions

```python
merged = src.merge(tgt, on="order_id", how="outer", suffixes=("_src", "_tgt"), indicator=True)
missing = merged.loc[merged["_merge"] == "left_only", "order_id"]      # in source only
extra   = merged.loc[merged["_merge"] == "right_only", "order_id"]     # in target only
both    = merged[merged["_merge"] == "both"]
```

```sql-syntax
SELECT <key>, <columns> FROM source
EXCEPT
SELECT <key>, <columns> FROM target;

SELECT COALESCE(s.<key>, t.<key>) AS key, s.<col> AS source_value, t.<col> AS target_value
FROM source s FULL OUTER JOIN target t ON t.<key> = s.<key>
WHERE s.<key> IS NULL OR t.<key> IS NULL OR s.<col> IS DISTINCT FROM t.<col>;
```

With PostgreSQL and `psycopg`, the same comparison reads the two tables (here from two databases) and compares them in pandas; this needs servers and is not run here:

```python
import os
import pandas as pd
import psycopg

with psycopg.connect(os.environ["SOURCE_DSN"]) as src_conn, psycopg.connect(os.environ["TARGET_DSN"]) as tgt_conn:
    src = pd.read_sql_query("SELECT order_id, amount_eur FROM orders ORDER BY order_id", src_conn)
    tgt = pd.read_sql_query("SELECT order_id, amount_eur FROM sales_orders ORDER BY order_id", tgt_conn)
```

| Function or clause | Returns or does |
|---|---|
| `a.merge(b, on=key, how="outer", indicator=True)` | Both sides side by side; `_merge` is `left_only`, `right_only` or `both`. |
| `df[key].duplicated()` | True for repeated keys; `df[key].duplicated(keep=False)` marks all copies. |
| `set(a) - set(b)` | Keys in `a` but not in `b`. |
| `(x - y).abs() > tol` | Boolean mask of values that differ by more than the tolerance. |
| `df.groupby(col)[measure].sum()` | Totals per group, to locate a difference. |
| `EXCEPT` | Rows of the first query that the second does not return. |
| `FULL OUTER JOIN ... IS DISTINCT FROM` | All keys of both sides; null-safe comparison of values. |

## Learn by example

The source and the target of the examples hold eight orders each. The target is the result of a flawed load: order 1004 is missing, a test order 1009 is extra, and the amount of order 1006 was typed as 54.5 instead of 45.5. The counts agree. `sqlite3` stands in for PostgreSQL where tables are needed; it differs from PostgreSQL in placeholders (`?` instead of `%s`), in loose types, and in lacking some SQL (older SQLite versions write the null-safe comparison `IS DISTINCT FROM` as `IS NOT`), so the SQL comparison is run on the PostgreSQL-compatible database in Example 5.

### Example 1: Counts and totals

Two checks in one small table. The counts are equal, the totals are not, and the difference shows that values or keys differ even though the counts look fine.

```python run
import pandas as pd

src = pd.DataFrame({"order_id": [1001, 1002, 1003, 1004, 1005, 1006, 1007, 1008],
                    "amount_eur": [1200.5, 310.0, 89.9, 50.0, 2050.0, 45.5, 99.0, 12.25]})
tgt = pd.DataFrame({"order_id": [1001, 1002, 1003, 1005, 1006, 1007, 1008, 1009],
                    "amount_eur": [1200.5, 310.0, 89.9, 2050.0, 54.5, 99.0, 12.25, 500.0]})

rows = [
    ("row count", len(src), len(tgt)),
    ("total amount", round(float(src["amount_eur"].sum()), 2), round(float(tgt["amount_eur"].sum()), 2)),
    ("distinct keys", int(src["order_id"].nunique()), int(tgt["order_id"].nunique())),
]
for check, s, t in rows:
    diff = round(t - s, 2)
    print(f"{check:14} {s:>9} {t:>9} {diff:>7} {'OK' if abs(diff) <= 0.005 else 'FAIL'}")
```

```output
row count              8         8       0 OK
total amount     3857.15   4316.15   459.0 FAIL
distinct keys          8         8       0 OK
```

The counts and the number of distinct keys agree, so a count-only check would pass. The total is 459.0 higher in the target, which proves something differs but not what.

### Example 2: The key comparison

An outer merge with `indicator=True` splits the keys into those only in the source, only in the target and in both, and a duplicate check on the target completes the picture.

```python run
import pandas as pd

src = pd.DataFrame({"order_id": [1001, 1002, 1003, 1004, 1005, 1006, 1007, 1008],
                    "amount_eur": [1200.5, 310.0, 89.9, 50.0, 2050.0, 45.5, 99.0, 12.25]})
tgt = pd.DataFrame({"order_id": [1001, 1002, 1003, 1005, 1006, 1007, 1008, 1009],
                    "amount_eur": [1200.5, 310.0, 89.9, 2050.0, 54.5, 99.0, 12.25, 500.0]})

merged = src.merge(tgt, on="order_id", how="outer", suffixes=("_src", "_tgt"), indicator=True)
print(merged["_merge"].value_counts().sort_index().to_dict())
print("missing in target:", merged.loc[merged["_merge"] == "left_only", "order_id"].tolist())
print("extra in target:", merged.loc[merged["_merge"] == "right_only", "order_id"].tolist())
print("duplicate keys in target:", tgt.loc[tgt["order_id"].duplicated(keep=False), "order_id"].tolist())
```

```output
{'left_only': 1, 'right_only': 1, 'both': 7}
missing in target: [1004]
extra in target: [1009]
duplicate keys in target: []
```

Now the report names rows: 1004 was lost and 1009 should not be there. The empty duplicate list is an answer too.

### Example 3: Values for the keys on both sides, with a tolerance

For the seven keys present on both sides, the amounts are compared with a tolerance of half a cent, so that floating-point noise does not raise false alarms while a real change does. The first lines show why the tolerance is needed.

```python run
import pandas as pd

print("0.1 + 0.2 == 0.3:", 0.1 + 0.2 == 0.3, "| within tolerance:", abs((0.1 + 0.2) - 0.3) <= 0.005)

src = pd.DataFrame({"order_id": [1001, 1002, 1003, 1004, 1005, 1006, 1007, 1008],
                    "amount_eur": [1200.5, 310.0, 89.9, 50.0, 2050.0, 45.5, 99.0, 12.25]})
tgt = pd.DataFrame({"order_id": [1001, 1002, 1003, 1005, 1006, 1007, 1008, 1009],
                    "amount_eur": [1200.5, 310.0, 89.9, 2050.0, 54.5, 99.0, 12.25, 500.0]})
both = src.merge(tgt, on="order_id", how="inner", suffixes=("_src", "_tgt"))
both["diff"] = (both["amount_eur_tgt"] - both["amount_eur_src"]).round(2)
changed = both[both["diff"].abs() > 0.005]
print("compared:", len(both), "changed:", len(changed))
print(changed.to_string(index=False))
```

```output
0.1 + 0.2 == 0.3: False | within tolerance: True
compared: 7 changed: 1
 order_id  amount_eur_src  amount_eur_tgt  diff
     1006            45.5            54.5   9.0
```

The single changed row is the one that no count or key check could have found. A difference divisible by 9 is the classic sign of two transposed digits: 455 and 545 differ by 90, and here 45.5 and 54.5 differ by 9.0.

### Example 4: Locate a difference with group totals

Totals per status for both sides: the failing group tells where to look. Here the extra test order and the changed amount are in `paid` orders and the lost order 1004 was a `refunded` one, so the statuses differ in different directions.

```python run
import pandas as pd

src = pd.DataFrame({"order_id": [1001, 1002, 1003, 1004, 1005, 1006, 1007, 1008],
                    "status": ["paid", "paid", "failed", "refunded", "paid", "paid", "failed", "paid"],
                    "amount_eur": [1200.5, 310.0, 89.9, 50.0, 2050.0, 45.5, 99.0, 12.25]})
tgt = pd.DataFrame({"order_id": [1001, 1002, 1003, 1005, 1006, 1007, 1008, 1009],
                    "status": ["paid", "paid", "failed", "paid", "paid", "failed", "paid", "paid"],
                    "amount_eur": [1200.5, 310.0, 89.9, 2050.0, 54.5, 99.0, 12.25, 500.0]})

a = src.groupby("status")["amount_eur"].agg(source_rows="count", source_total="sum")
b = tgt.groupby("status")["amount_eur"].agg(target_rows="count", target_total="sum")
by_status = a.join(b, how="outer").fillna(0)
by_status[["source_rows", "target_rows"]] = by_status[["source_rows", "target_rows"]].astype("int64")
by_status["difference"] = (by_status["target_total"] - by_status["source_total"]).round(2)
print(by_status.to_string())
```

```output
          source_rows  source_total  target_rows  target_total  difference
status                                                                    
failed              2        188.90            2        188.90         0.0
paid                5       3618.25            6       4127.25       509.0
refunded            1         50.00            0          0.00       -50.0
```

The refunded group lost 50.0 (order 1004), and the paid group gained 509.0 (the extra 500.0 and the 9.0 change). The `failed` group agrees. With `how="outer"`, a group that exists on one side only still appears.

### Example 5: The comparison in SQL

Two tables on the PostgreSQL-compatible database. `EXCEPT` in both directions finds the keys that differ, and a full outer join with `IS DISTINCT FROM` shows the missing, the extra and the changed rows in one result. The tables are created in the block with the same data as before.

```sql run
DROP TABLE IF EXISTS rc_source;
DROP TABLE IF EXISTS rc_target;
CREATE TABLE rc_source (order_id integer PRIMARY KEY, amount_eur numeric(12,2));
CREATE TABLE rc_target (order_id integer PRIMARY KEY, amount_eur numeric(12,2));
INSERT INTO rc_source VALUES (1001, 1200.50), (1002, 310), (1003, 89.90), (1004, 50), (1005, 2050), (1006, 45.50), (1007, 99), (1008, 12.25);
INSERT INTO rc_target VALUES (1001, 1200.50), (1002, 310), (1003, 89.90), (1005, 2050), (1006, 54.50), (1007, 99), (1008, 12.25), (1009, 500);
SELECT COALESCE(s.order_id, t.order_id) AS order_id,
       s.amount_eur AS source_amount,
       t.amount_eur AS target_amount,
       CASE WHEN t.order_id IS NULL THEN 'missing in target'
            WHEN s.order_id IS NULL THEN 'extra in target'
            ELSE 'changed' END AS problem
FROM rc_source s
FULL OUTER JOIN rc_target t ON t.order_id = s.order_id
WHERE s.order_id IS NULL OR t.order_id IS NULL OR s.amount_eur IS DISTINCT FROM t.amount_eur
ORDER BY 1;
```

```output
order_id | source_amount | target_amount | problem
1004 | 50.00 | NULL | missing in target
1006 | 45.50 | 54.50 | changed
1009 | NULL | 500.00 | extra in target
```

The query returns exactly the three problems and nothing for the five rows that agree. Because these tables use `numeric(12,2)`, comparing for equality is safe here; with floating-point columns you would compare with a tolerance as in Example 3.

### Example 6: A reconciliation report from two tables

The whole workflow: read the source and the target tables with `read_sql_query` (from `sqlite3` as a stand-in for two PostgreSQL connections), subtract the keys the loader rejected on purpose, run the checks and print a report with a final status. In a scheduled job the last line would raise an error to alert someone.

```python run
import sqlite3
import pandas as pd

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE source (order_id INTEGER, amount_eur REAL)")
conn.execute("CREATE TABLE target (order_id INTEGER, amount_eur REAL)")
conn.executemany("INSERT INTO source VALUES (?, ?)", [(1001, 1200.5), (1002, 310.0), (1003, 89.9), (1004, 50.0), (1005, 2050.0), (1006, 45.5), (1007, 99.0), (1008, 12.25)])
conn.executemany("INSERT INTO target VALUES (?, ?)", [(1001, 1200.5), (1002, 310.0), (1003, 89.9), (1005, 2050.0), (1006, 54.5), (1007, 99.0), (1008, 12.25), (1009, 500.0)])
src = pd.read_sql_query("SELECT order_id, amount_eur FROM source ORDER BY order_id", conn)
tgt = pd.read_sql_query("SELECT order_id, amount_eur FROM target ORDER BY order_id", conn)
conn.close()

rejected = {1004}                      # keys the loader rejected on purpose and logged

def reconcile(src, tgt, rejected, tol=0.005):
    m = src.merge(tgt, on="order_id", how="outer", suffixes=("_s", "_t"), indicator=True)
    missing = sorted(set(m.loc[m["_merge"] == "left_only", "order_id"]) - rejected)
    extra = sorted(m.loc[m["_merge"] == "right_only", "order_id"])
    both = m[m["_merge"] == "both"]
    changed = sorted(both.loc[(both["amount_eur_t"] - both["amount_eur_s"]).abs() > tol, "order_id"])
    dupes = sorted(tgt.loc[tgt["order_id"].duplicated(), "order_id"])
    checks = [
        ("keys missing in target (not rejected)", missing),
        ("keys extra in target", extra),
        ("amounts changed", changed),
        ("duplicate keys in target", dupes),
    ]
    return [(name, keys, "OK" if not keys else "FAIL") for name, keys in checks]

report = reconcile(src, tgt, rejected)
for name, keys, status in report:
    print(f"{status:4} {name}: {keys}")
print("overall:", "PASS" if all(s == "OK" for _, _, s in report) else "FAIL")
```

```output
OK   keys missing in target (not rejected): []
FAIL keys extra in target: [1009]
FAIL amounts changed: [1006]
OK   duplicate keys in target: []
overall: FAIL
```

Order 1004 is explained by the reject list and is not reported, while the other three problems remain. Every difference is either explained by a named reason or listed as a failure.

## Real-world applications

- **After every scheduled load**: the job runs the checks of Examples 1 and 2 and stops the pipeline when a key is missing, instead of letting a dashboard refresh on wrong data.
- **Migrating a table to a new platform**: group totals and a key comparison (Examples 4 and 5) show where the new warehouse differs from the old one and whether the cause is a filter, a type or a time zone.
- **Finance sign-off**: the report with source total, target total and difference is attached to the month-end close, and an explained reject list is part of it (Example 6).
- **Data-quality monitoring**: the share of rows with changed values is tracked over time, and a sudden jump points to a change in the source system.

## Daily review

### Key takeaways

- Compare in a ladder: counts, totals, keys, values; use group totals to locate a difference.
- Equal counts do not mean equal tables: a missing and an extra row cancel in the count.
- A key comparison names the rows: missing, extra and duplicated keys.
- Compare decimals with a tolerance (or exact `numeric` types), not with `==` on floats.
- Every difference must be explained by a counted reason, such as a reject list, or reported as a failure.
- Reports are produced by code on every load and fail the job when a check fails.

### Common mistakes

- Trusting equal row counts. A lost row and a test row cancel; always compare the keys.
- Comparing float amounts with `==`. Tiny binary errors cause false alarms; use `abs(diff) <= tolerance` or round both sides.
- Using an inner merge for the key comparison. It drops exactly the rows you are looking for; use `how="outer"` with `indicator=True`.
- Counting duplicates after a join. A join repeats rows (Day 159), so check `duplicated()` on each table before joining.
- Ignoring a known difference without recording it. Keep an explicit reject list so "expected" differences are counted, not waved away.

### Revision notes

- Checks: count, total, distinct keys, key sets, values per key, totals per group.
- `merge(how="outer", indicator=True)` gives `left_only`, `right_only`, `both`.
- `duplicated(keep=False)` shows all copies of a repeated key.
- Tolerance: `abs(target - source) <= 0.005` for two-decimal amounts.
- SQL: `EXCEPT` both ways, or `FULL OUTER JOIN ... WHERE ... IS DISTINCT FROM`.

## Objectives

- Read a traceback and name the exception type, the message and the line that caused it.
- Handle errors with `try`, `except`, `else` and `finally`, catching specific exception types.
- Raise exceptions with `raise` and define a custom exception class for your own error conditions.
- Configure the `logging` module with a handler, a format and a level, and write messages at the right severity.
- Decide when to catch an error, when to let it stop the program and when to log it.

## Understand

### What an exception is

When Python cannot carry out an instruction, it creates an **exception**: an object that describes the problem, and it stops normal execution. `int("abc")` raises `ValueError`, `[1][5]` raises `IndexError`, `{}["k"]` raises `KeyError`, `1 / 0` raises `ZeroDivisionError` and opening a missing file raises `FileNotFoundError`. Unless the exception is **handled**, it travels up through the calling functions and ends the program, printing a **traceback**: the list of calls that led to the error, with the exception type and message on the last line. Read a traceback from the bottom: the last line says what happened, and the line above it says where.

An exception is not a failure of Python; it is a signal that your code can respond to. Real data is messy, and handling the expected problems (a bad number, a missing file) is part of writing a pipeline.

### try and except

```python
try:
    value = int(text)
except ValueError:
    value = 0
```

The code in `try` runs normally. If it raises an exception of the named type, Python skips the rest of the `try` block and runs the matching `except` block. If nothing is raised, the `except` block is skipped. You can name several types in a tuple, `except (ValueError, TypeError):`, or write several `except` blocks. The exception object is available with `as`: `except ValueError as error:`, and `str(error)` is its message. Exception types form a hierarchy, and an `except` for a parent type also catches its children. `LookupError` covers `KeyError` and `IndexError`, and `Exception` covers nearly everything. Always name the most specific type you expect. A bare `except:` or `except Exception:` that does nothing hides real bugs, including typing mistakes in your own code.

### else and finally

`else` runs only when the `try` block raised nothing. It keeps the code that depends on success out of the `try`, so you catch errors from the risky line only. `finally` runs always: after success, after a handled error, and even when an unhandled error is on its way up. It is the place for clean-up such as closing a resource. The order of events is: `try`, then `except` if it failed or `else` if it did not, and then `finally`. (The `with` statement from Day 19 is the tidier tool for closing files; `finally` is the general mechanism.)

### Raising and custom exceptions

You signal your own problems with `raise`: `raise ValueError("price must be positive")`. Raising early, with a clear message, is better than letting bad data travel through a pipeline until something unrelated breaks. Inside an `except` block, a bare `raise` re-raises the same exception after you have logged it.

A **custom exception** is a class that inherits from `Exception`. It gives a problem its own name that callers can catch precisely:

```python
class InvalidRecord(Exception):
    pass
```

A class is a template for objects, which Day 24 explains in full. Here you only need the pattern: the name, and `(Exception)` in brackets. You can raise it with a message, `raise InvalidRecord("row 7: missing id")`, and catch it with `except InvalidRecord`.

### Logging

`print` is fine while learning, but programs that run unattended need **logging**: messages with a severity, a source and often a time, which can be sent to the screen, a file or a monitoring system and be switched on or off without editing the code. The standard `logging` module has five levels in rising order: `DEBUG` (details for developers), `INFO` (normal events), `WARNING` (something unexpected, work continues), `ERROR` (an operation failed) and `CRITICAL` (the program may not continue). A logger only emits messages at or above its configured level.

Three parts work together. A **logger** is the object you call, such as `logger.info("loaded %d rows", count)`; get one with `logging.getLogger(name)`. A **handler** decides where messages go, for example `StreamHandler` for the screen or `FileHandler` for a file. A **formatter** decides how a message looks, using placeholders like `%(asctime)s`, `%(levelname)s` and `%(message)s`. Pass values as arguments rather than building the string yourself (`"%s"` style), so formatting is skipped when the message is filtered out. Inside an `except` block, `logger.exception("...")` logs at ERROR level and includes the traceback.

In this lesson each example configures its own logger with a handler that writes to standard output and sets `propagate = False`, so the output is predictable. A simple script can call `logging.basicConfig(level=logging.INFO)` instead; by default it writes to standard error.

### Common misconception

Learners think a `try` block makes the code safe. It only gives you a place to respond. Wrapping a whole program in `except Exception: pass` makes errors invisible, not absent. Catch the narrow error you can actually handle, and let everything else stop the program with a traceback.

### Why it matters

Pipelines process thousands of records, and one bad record should not silently corrupt the output or needlessly kill the whole run. Specific handlers, clear custom errors and useful logs let a job skip or report what it should and fail loudly on what it should not.

## Syntax and key functions

Handling:

```python
try:
    risky()
except SpecificError as error:
    handle(error)
else:
    on_success()
finally:
    cleanup()
```

Only `try` and at least one `except` or `finally` are required. Raising and logging:

```python
raise ErrorType("message")

logger = logging.getLogger("etl")
logger.setLevel(logging.INFO)
handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(logging.Formatter("%(levelname)s %(message)s"))
logger.addHandler(handler)
logger.info("loaded %d rows", 40)
```

| Name | Meaning |
|---|---|
| `ValueError`, `TypeError` | Right type but bad value; wrong type. |
| `KeyError`, `IndexError` | Missing dictionary key; position out of range. |
| `FileNotFoundError`, `ZeroDivisionError` | Missing file; division by zero. |
| `raise X("msg")` | Raises an exception; a bare `raise` re-raises the current one. |
| `str(error)` | The message of a caught exception. |
| `logging.getLogger(name)` | The logger for that name (same object every time). |
| `logger.debug/info/warning/error/critical(msg, *args)` | Log at that level. |
| `logger.exception(msg)` | Log at ERROR with the current traceback (use inside `except`). |
| `StreamHandler(stream)`, `FileHandler(path)` | Where messages go. |
| `logging.Formatter(fmt)` | How a record is written. |

## Learn by example

### Example 1: The anatomy of an error

An unhandled error ends the program, so the failing call is shown in a `text` block with its traceback, and the code that follows catches the same error and prints details of the exception object.

```text
Traceback (most recent call last):
  File "demo.py", line 1, in <module>
    int("abc")
ValueError: invalid literal for int() with base 10: 'abc'
```

```python run
try:
    int("abc")
except ValueError as error:
    print(type(error).__name__)
    print(error)
```

```output
ValueError
invalid literal for int() with base 10: 'abc'
```

### Example 2: Specific handlers and else/finally

The function tries to convert and divide. Each failure type has its own handler, `else` runs only on success and `finally` runs every time, which the printed order shows.

```python run
def ratio(a, b):
    try:
        result = int(a) / int(b)
    except ValueError:
        print("not a number:", a, b)
        return None
    except ZeroDivisionError:
        print("cannot divide by zero")
        return None
    else:
        print("ok")
        return result
    finally:
        print("done", a, b)

print(ratio("10", "4"))
print(ratio("x", "4"))
print(ratio("10", "0"))
```

```output
ok
done 10 4
2.5
not a number: x 4
done x 4
None
cannot divide by zero
done 10 0
None
```

### Example 3: Raising and catching your own error

A custom exception names the problem. The validator raises it with a message for each bad record, and the loop catches it, counts it, and carries on with the rest of the records.

```python run
class InvalidRecord(Exception):
    pass

def validate(record):
    if "id" not in record:
        raise InvalidRecord("missing id")
    if record.get("amount", 0) <= 0:
        raise InvalidRecord(f"bad amount for id {record['id']}")
    return record

records = [{"id": 1, "amount": 5}, {"amount": 3}, {"id": 3, "amount": -1}, {"id": 4, "amount": 9}]
good = []
for record in records:
    try:
        good.append(validate(record))
    except InvalidRecord as error:
        print("skipped:", error)
print([r["id"] for r in good])
```

```output
skipped: missing id
skipped: bad amount for id 3
[1, 4]
```

### Example 4: Logging levels and format

The logger is set to INFO, so the DEBUG message is dropped and the other three appear. The formatter puts the level name first. Values are passed as arguments, not joined into the string.

```python run
import logging
import sys

logger = logging.getLogger("etl")
logger.setLevel(logging.INFO)
logger.propagate = False
handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(logging.Formatter("%(levelname)s | %(name)s | %(message)s"))
logger.addHandler(handler)

logger.debug("row detail, hidden at INFO level")
logger.info("loaded %d rows", 40)
logger.warning("%d rows had empty names", 3)
logger.error("could not reach %s", "orders.csv")
```

```output
INFO | etl | loaded 40 rows
WARNING | etl | 3 rows had empty names
ERROR | etl | could not reach orders.csv
```

### Example 5: Logging a caught error

`logger.exception` records the message and the traceback. To keep the output short and stable, this example logs the error with `logger.error` and the exception text, and then re-raises it with a bare `raise` so a caller can still handle it.

```python run
import logging
import sys

logger = logging.getLogger("load")
logger.setLevel(logging.INFO)
logger.propagate = False
handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(logging.Formatter("%(levelname)s: %(message)s"))
logger.addHandler(handler)

def load(value):
    try:
        return int(value)
    except ValueError as error:
        logger.error("cannot load %r (%s)", value, error)
        raise

try:
    load("12x")
except ValueError:
    logger.warning("falling back to 0")
print(load("12"))
```

```output
ERROR: cannot load '12x' (invalid literal for int() with base 10: '12x')
WARNING: falling back to 0
12
```

### Example 6: A resilient batch with a summary

Combining the pieces: each line is parsed, bad lines are logged as warnings and counted, and an INFO summary closes the run. The job continues past bad input but reports exactly what it skipped.

```python run
import logging
import sys

logger = logging.getLogger("batch")
logger.setLevel(logging.INFO)
logger.propagate = False
handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(logging.Formatter("%(levelname)s %(message)s"))
logger.addHandler(handler)

lines = ["10", "20", "abc", "", "5.5", "30"]
total, bad = 0, 0
for number, line in enumerate(lines, start=1):
    try:
        total += float(line)
    except ValueError:
        bad += 1
        logger.warning("line %d: cannot parse %r", number, line)
logger.info("sum=%.1f bad=%d of %d", total, bad, len(lines))
```

```output
WARNING line 3: cannot parse 'abc'
WARNING line 4: cannot parse ''
INFO sum=65.5 bad=2 of 6
```

## Real-world applications

- **Skipping bad records without stopping.** A loader validates every row (Example 3), skips and counts the rejects, and finishes the good ones, which is how real ingestion jobs behave.
- **Auditing unattended jobs.** A scheduled job writes timestamped INFO and WARNING lines to a file (Examples 4 and 6). When a number looks wrong the next morning, the log says what happened.
- **Failing loudly on real problems.** Catching only `FileNotFoundError` for an optional file, and letting every other error stop the job, prevents silently wrong results.
- **Cleaning up resources.** A `finally` block releases a database connection or removes a temporary file whether or not the load succeeded (Example 2).

## Daily review

### Key takeaways

- An exception is an object raised when Python cannot continue; unhandled, it ends the program with a traceback read from the bottom.
- Catch specific exception types; use `else` for success-only code and `finally` for clean-up that must always run.
- `raise` signals your own problems, and a custom exception class gives them a name.
- Logging has levels (DEBUG, INFO, WARNING, ERROR, CRITICAL), handlers (where) and formatters (how).
- Pass values as arguments to logging calls and keep `logger.exception` for use inside `except`.

### Common mistakes

- Writing `except:` or `except Exception: pass`, which hides typos and real bugs. Name the expected exception and do something useful.
- Putting too much code in `try`, so an unrelated bug is caught by accident. Keep `try` to the risky line and use `else`.
- Catching a parent type before its child, so the child handler never runs.
- Expecting an `INFO` message to appear when the level is `WARNING` (the default for the root logger). Set the level on the logger and handler.
- Adding a handler each time a function runs, so every message prints several times. Configure a logger once.
- Calling `logging.info` with an f-string and arguments mixed up, giving `TypeError: not all arguments converted`. Use `%s` placeholders or only an f-string.
- Forgetting that the root logger writes to standard error, so output appears in the wrong place. Give the handler `sys.stdout` when you need it there.

### Revision notes

- Order: `try`, then `except` (failure) or `else` (success), then `finally` (always).
- `except (ValueError, TypeError) as error:`; `str(error)` is the message.
- `class MyError(Exception): pass` and `raise MyError("text")`; bare `raise` re-raises.
- `logger = logging.getLogger("name")`, `setLevel`, `addHandler(StreamHandler(sys.stdout))`, `setFormatter`.
- Level order: DEBUG < INFO < WARNING < ERROR < CRITICAL.

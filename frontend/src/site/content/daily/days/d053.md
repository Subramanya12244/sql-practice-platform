## Objectives

- Split ordered rows into equal-sized groups with `NTILE` and read the result as quartiles or deciles.
- Fetch the first or last value of a window with `FIRST_VALUE` and `LAST_VALUE`, and avoid the default-frame trap of `LAST_VALUE`.
- Compute medians and other percentiles with `percentile_cont` and `percentile_disc`.
- Describe how a distribution is spread with buckets, medians and percentiles instead of only an average.

## Understand

### Why averages are not enough

An average hides the shape of the data. The 77 product prices in Northwind range from 2.50 to 263.50, and a few very expensive products pull the average up. The **median**, the middle value when the data is sorted, is not affected by extremes. **Distribution analysis** describes how values spread: where the middle is, how far the top is from the bottom, and which values belong to the top quarter. Three tools help: `NTILE` to cut the ordered rows into buckets, `FIRST_VALUE` and `LAST_VALUE` to compare each row with the edges of its group, and percentile functions to read exact cut points.

### NTILE: equal-sized buckets

`NTILE(n) OVER (ORDER BY x)` sorts the rows and deals them into `n` buckets numbered 1 to `n`, each with (almost) the same **number of rows**. `NTILE(4)` gives quartiles: bucket 1 holds the lowest quarter of rows, bucket 4 the highest. `NTILE(10)` gives deciles. If the row count does not divide evenly, the first buckets receive one extra row: 77 rows in 4 buckets are 20, 19, 19 and 19 (Example 1).

Two points matter. Buckets contain equal numbers of rows, not equal ranges of values, so the value range of bucket 4 can be enormous. And tied values can be split across two buckets, because `NTILE` only looks at row positions. Add a unique tie-breaker to the `ORDER BY` so that the split is repeatable. `PARTITION BY` creates the buckets separately in each group.

### FIRST_VALUE and LAST_VALUE

`FIRST_VALUE(x)` returns `x` from the first row of the window frame and `LAST_VALUE(x)` from the last row. Typical use: next to every product, show the cheapest product of its category, so the difference can be computed. Because they read from the **frame** (day 52), the frame matters.

The trap: with an `ORDER BY` and no frame clause, the default frame ends at the current row. So `LAST_VALUE(x) OVER (ORDER BY y)` returns the current row's own value (or that of its last peer), not the last row of the partition. The fix is an explicit frame: `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`. Example 4 shows both results. `FIRST_VALUE` does not suffer from this because the default frame always starts at the first row. PostgreSQL also has `NTH_VALUE(x, n)` for the n-th row; it follows the same frame rule.

### Percentiles: ordered-set aggregates

The k-th **percentile** is the value below which k percent of the data lie. The median is the 50th percentile. PostgreSQL computes percentiles with an **ordered-set aggregate**, which has a special syntax:

`percentile_cont(0.5) WITHIN GROUP (ORDER BY unit_price)`

The fraction goes in the first parentheses (0.5 for the median, 0.9 for the 90th percentile) and the sort expression goes after `WITHIN GROUP`. `percentile_cont` ("continuous") interpolates between neighbouring values when the exact position falls between two rows, so the median of an even number of values is the mean of the two middle ones. `percentile_disc` ("discrete") always returns an actual value from the data: the first one whose position reaches the fraction. Both are aggregates: with `GROUP BY` they return one row per group, and they ignore NULLs.

`percentile_cont` returns a floating-point number, so results such as `21.200000000000003` can appear. Cast to `numeric` and round for display: `ROUND(percentile_cont(0.5) WITHIN GROUP (ORDER BY x)::numeric, 2)`. For percentile functions on a `numeric` column the continuous version returns `double precision`.

### Combining the tools

Percentiles give the cut points, and `NTILE` labels each row with its bucket. They answer similar questions in different ways: `NTILE` says "this row is in the top quarter by position", `percentile_cont(0.75)` says "the 75th percentile value is 33.2". For customer segmentation by revenue, `NTILE` is usual because every customer needs a label. For reporting a threshold such as "the 90th percentile order value", the percentile function is the right one.

### Common misconception

People assume `NTILE(4)` makes four equal **ranges** of the value (such as 0 to 66, 66 to 132). It makes four equal **row counts**. Another misconception is that `LAST_VALUE` returns the last value of the group; with the default frame it does not. Finally, the mean and the median are different measures: if they differ greatly, the distribution is skewed.

### Why it matters

Segmenting customers into value tiers, flagging the top decile of slow deliveries, reporting a median instead of a misleading mean, and comparing every row with the best or worst in its group are standard analyst tasks. They rely on exactly these functions.

## Syntax and key functions

```sql-syntax
NTILE(n) OVER ([PARTITION BY g] ORDER BY x)
FIRST_VALUE(x) OVER (PARTITION BY g ORDER BY y [frame])
LAST_VALUE(x)  OVER (PARTITION BY g ORDER BY y ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)
percentile_cont(fraction) WITHIN GROUP (ORDER BY x)
percentile_disc(fraction) WITHIN GROUP (ORDER BY x)
```

| Function | Returns |
|---|---|
| `NTILE(n)` | Bucket number from 1 to `n`; bucket sizes differ by at most one row |
| `FIRST_VALUE(x)` | `x` of the first row in the frame |
| `LAST_VALUE(x)` | `x` of the last row in the frame (default frame ends at the current row) |
| `percentile_cont(f)` | Interpolated value at fraction `f` (0 to 1); double precision |
| `percentile_disc(f)` | An actual value from the data at fraction `f` |

## Learn by example

### Example 1: quartiles with NTILE

`NTILE(4)` assigns quartiles by price position. The outer query summarises each bucket: the first bucket has 20 rows because 77 does not divide by 4. The price ranges are very uneven because the buckets have equal counts, not equal value ranges.

```sql run
SELECT quartile, COUNT(*) AS products, MIN(unit_price) AS lowest, MAX(unit_price) AS highest
FROM (
  SELECT unit_price,
         NTILE(4) OVER (ORDER BY unit_price, product_id) AS quartile
  FROM products
) AS t
GROUP BY quartile
ORDER BY quartile;
```

```output
quartile | products | lowest | highest
1 | 20 | 2.50 | 13.25
2 | 19 | 14.00 | 19.50
3 | 19 | 20.00 | 33.25
4 | 19 | 34.00 | 263.50
```

### Example 2: uneven bucket sizes

Category 1 has 12 products. Five buckets of 12 rows cannot be equal: 12 = 3 + 3 + 2 + 2 + 2. The extra rows go to the first buckets.

```sql run
SELECT tile, COUNT(*) AS products
FROM (
  SELECT NTILE(5) OVER (ORDER BY product_id) AS tile
  FROM products
  WHERE category_id = 1
) AS t
GROUP BY tile
ORDER BY tile;
```

```output
tile | products
1 | 3
2 | 3
3 | 2
4 | 2
5 | 2
```

### Example 3: compare every row with the cheapest in its category

`FIRST_VALUE` with `ORDER BY unit_price, product_id` inside each category returns the lowest price (and name) of the group on every row. The default frame always begins at the first row, so no frame clause is needed.

```sql run
SELECT category_id, product_name, unit_price,
       FIRST_VALUE(product_name) OVER w AS cheapest_product,
       unit_price - FIRST_VALUE(unit_price) OVER w AS above_cheapest
FROM products
WHERE category_id IN (1, 2)
WINDOW w AS (PARTITION BY category_id ORDER BY unit_price, product_id)
ORDER BY category_id, unit_price, product_id
LIMIT 5;
```

```output
category_id | product_name | unit_price | cheapest_product | above_cheapest
1 | Guaraná Fantástica | 4.50 | Guaraná Fantástica | 0.00
1 | Rhönbräu Klosterbier | 7.75 | Guaraná Fantástica | 3.25
1 | Sasquatch Ale | 14.00 | Guaraná Fantástica | 9.50
1 | Laughing Lumberjack Lager | 14.00 | Guaraná Fantástica | 9.50
1 | Outback Lager | 15.00 | Guaraná Fantástica | 10.50
```

### Example 4: the LAST_VALUE default-frame trap

In category 8 the most expensive product is 62.50. `lv_default` uses the default frame, which ends at the current row, so it repeats the row's own price. `lv_full` has the full frame and shows 62.50 on every row.

```sql run
SELECT product_id, unit_price,
       LAST_VALUE(unit_price) OVER (PARTITION BY category_id ORDER BY unit_price, product_id) AS lv_default,
       LAST_VALUE(unit_price) OVER (PARTITION BY category_id ORDER BY unit_price, product_id
                                    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS lv_full
FROM products
WHERE category_id = 8
ORDER BY unit_price, product_id
LIMIT 5;
```

```output
product_id | unit_price | lv_default | lv_full
13 | 6.00 | 6.00 | 62.50
45 | 9.50 | 9.50 | 62.50
41 | 9.65 | 9.65 | 62.50
46 | 12.00 | 12.00 | 62.50
58 | 13.25 | 13.25 | 62.50
```

### Example 5: median, percentile and mean

`percentile_cont(0.5)` is the median. For category 3 the mean and median differ (25.16 against 16.25), a sign of skew. `percentile_disc(0.5)` returns an actual price from the data and so can differ from the continuous value. The casts and `ROUND` hide floating-point noise.

```sql run
SELECT category_id,
       ROUND(AVG(unit_price), 2) AS mean_price,
       ROUND(percentile_cont(0.5) WITHIN GROUP (ORDER BY unit_price)::numeric, 2) AS median_cont,
       percentile_disc(0.5) WITHIN GROUP (ORDER BY unit_price) AS median_disc,
       ROUND(percentile_cont(0.9) WITHIN GROUP (ORDER BY unit_price)::numeric, 2) AS p90
FROM products
WHERE category_id IN (1, 2, 3, 4)
GROUP BY category_id
ORDER BY category_id;
```

```output
category_id | mean_price | median_cont | median_disc | p90
1 | 37.98 | 18.00 | 18.00 | 43.30
2 | 23.06 | 21.20 | 21.05 | 38.85
3 | 25.16 | 16.25 | 16.25 | 48.22
4 | 28.73 | 33.00 | 32.00 | 39.70
```

### Example 6: customer value tiers

A realistic segmentation. A CTE computes each customer's revenue, `NTILE(4)` labels the customers by revenue (tier 1 is the highest because the sort is descending), and the final query summarises each tier: its size, its total revenue and its share of all revenue. Customers with no orders are not in the data of this query because it starts from orders.

```sql run
WITH revenue AS (
  SELECT o.customer_id,
         SUM(od.unit_price * od.quantity * (1 - od.discount)) AS revenue
  FROM orders AS o
  JOIN order_details AS od ON od.order_id = o.order_id
  GROUP BY o.customer_id
), tiers AS (
  SELECT customer_id, revenue,
         NTILE(4) OVER (ORDER BY revenue DESC, customer_id) AS tier
  FROM revenue
)
SELECT tier, COUNT(*) AS customers,
       ROUND(SUM(revenue)::numeric, 2) AS tier_revenue,
       ROUND((100 * SUM(revenue) / SUM(SUM(revenue)) OVER ())::numeric, 1) AS pct_of_revenue
FROM tiers
GROUP BY tier
ORDER BY tier;
```

```output
tier | customers | tier_revenue | pct_of_revenue
1 | 23 | 83493.11 | 60.4
2 | 22 | 32087.65 | 23.2
3 | 22 | 17803.28 | 12.9
4 | 22 | 4935.75 | 3.6
```

## Real-world applications

**Customer segmentation.** Example 6 labels customers into value tiers, the basis of "top 25 percent" campaigns and of the weighting of customer-success effort. The tier summary shows how concentrated revenue is.

**Reporting robust statistics.** Delivery times, order values and response times are skewed. Reporting the median and the 90th percentile (Example 5) is more honest than the mean, and service-level targets are often written as percentiles.

**Benchmarking inside groups.** `FIRST_VALUE` (Example 3) compares every row with the best or the base of its group: price against the cheapest product, salary against the department minimum, sales against the first month of a launch.

**Outlier screening.** Rows above the 90th or 99th percentile of their group are candidates for review, and `NTILE(100)` or `NTILE(10)` turns a continuous value into a label that dashboards can filter on.

## Daily review

### Key takeaways

- `NTILE(n)` creates `n` buckets with equal numbers of rows (sizes differ by at most one), not equal value ranges.
- `FIRST_VALUE` reads the first row of the frame; `LAST_VALUE` needs an explicit full frame to return the last row of the partition.
- `percentile_cont(f) WITHIN GROUP (ORDER BY x)` interpolates; `percentile_disc` returns an existing value; `f = 0.5` is the median.
- Percentile functions are aggregates (with `GROUP BY`), while `NTILE`, `FIRST_VALUE` and `LAST_VALUE` are window functions.
- Mean far from median means a skewed distribution.

### Common mistakes

- Using `LAST_VALUE` with the default frame and getting each row's own value. Add `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.
- Writing `percentile_cont(0.5) OVER (...)`. The syntax is `WITHIN GROUP (ORDER BY ...)`, and `OVER` is not accepted for it; PostgreSQL reports an error.
- Passing 50 instead of 0.5. The fraction must be between 0 and 1: `percentile value 50 is not between 0 and 1`.
- Expecting `NTILE` buckets to cover equal value ranges, or to keep tied values together.
- Forgetting the tie-breaker in the `NTILE` order, so tied rows land in different buckets from run to run.
- Showing raw `percentile_cont` output with float noise such as `21.200000000000003` instead of casting to `numeric` and rounding.

### Revision notes

- Quartiles: `NTILE(4) OVER (ORDER BY x, id)`.
- Median: `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)`.
- Last row of the group: full frame required.
- Equal row counts, not equal value ranges.

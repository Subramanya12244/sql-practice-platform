## Objectives

- Combine rows of two tables with `INNER JOIN ... ON`, matching a foreign key to a primary key.
- Use table aliases and qualified column names, and fix "column reference is ambiguous" errors.
- Predict how many rows a join returns from the relationship between the two tables (one-to-many, one-to-one).
- Explain why rows without a match disappear from an inner join.
- Spot row multiplication and the wrong totals it causes when you aggregate after a join.

## Understand

### Why tables are split, and how a join puts them back

In a well-designed database each fact is stored once. A customer's name lives in `customers`, and an order stores only the customer's key, `customer_id`, in `orders`. Day 31 called that column a **foreign key**: it points at the **primary key** of another table. This avoids repeating the company name on every order, but it means an order row alone cannot tell you the company name. A **join** reunites the data: it builds result rows by combining a row from one table with the row from another table that matches on a key.

Think of two card files. One holds order slips, each with a customer code. The other holds customer cards, each with a code and a name. To print "order and customer name" you take each slip, look up the card with the same code, and clip them together. The matching rule is the join condition.

### INNER JOIN ... ON

```sql-syntax
SELECT o.order_id, c.company_name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
```

reads as: take every row of `orders`, find the `customers` rows whose `customer_id` equals the order's `customer_id`, and output one combined row for each matching pair. `INNER` is optional: `JOIN` alone means `INNER JOIN`. The condition after `ON` is a normal predicate, but it describes how rows of the two tables relate, not which rows you want. Keep filters for `WHERE`. An inner join keeps a pair only when the `ON` condition is true.

The standard join key is the foreign key against the primary key it references: `orders.customer_id = customers.customer_id`, `products.category_id = categories.category_id`, `order_details.order_id = orders.order_id`. PostgreSQL also accepts `USING (customer_id)` when both tables use the same column name; this course writes `ON` because it works for every case.

### Aliases and qualified names

A **table alias** is a short name given to a table for the length of the query: `FROM orders o` lets you write `o.order_id` instead of `orders.order_id`. A **qualified name** (`o.order_id`) states which table a column comes from. Both tables here have a `customer_id` column; writing just `customer_id` is ambiguous and PostgreSQL stops with "column reference "customer_id" is ambiguous". Qualify every column in a join query, even when it is not strictly required, because it makes the query readable and keeps it working if someone later adds a same-named column. Once you alias a table, you must use the alias; the original name is no longer available in that query.

### How many rows come back

The number of result rows is the number of matching pairs. For the most common shape, a **one-to-many** relationship (one customer, many orders), each row on the "many" side matches at most one row on the "one" side. Joining `orders` (100 rows) to `customers` therefore returns 100 rows: one per order, each carrying its customer's columns. Joining `orders` to `order_details` returns 250 rows, because each order has several lines and the join returns one row per line: the order's columns are repeated on each of its lines. Joining a table to a one-to-one partner returns at most as many rows as the smaller table. The rule of thumb: the result has one row for every row of the "many" side that finds a match.

### Rows that do not match disappear

An inner join keeps only matched pairs. An order with a NULL `customer_id` or a customer who never ordered contributes no row, because there is no partner (and NULL never equals anything, day 35). In this Northwind order 10347 has no employee, so joining `orders` to `employees` returns 99 rows, not 100: the order is silently dropped. Customers FISSA and PARIS have no orders and would never appear in `customers JOIN orders`. This is the reason day 41 introduces outer joins, which keep unmatched rows. For now remember: when a count after a join is lower than expected, check for rows that lost their partner.

### Row multiplication: the aggregation trap

Because a one-to-many join repeats the "one" side's values on each of its many rows, aggregating those repeated values counts them several times. If order 10251 has four lines and freight 48.53, a join to `order_details` gives four rows each showing 48.53, and `SUM(o.freight)` over the join adds 48.53 four times. The real freight total of all orders is 9851.61 but, as example 5 shows, the same sum over `orders JOIN order_details` is 23554.40. Whenever you join and then aggregate, ask what one row of the joined result represents. If it is "one order line", aggregate line measures (quantity, line revenue) and do not sum order-level columns.

### Common misconception

Many beginners believe a join "adds columns" and so keeps the number of rows the same. A join can return fewer rows (unmatched rows dropped) or more rows (one row matches several). Always check the row count before and after.

### Why it matters

Almost every useful query needs more than one table: revenue by customer country, products by category, employees per order. Correct join keys and a clear idea of what each result row means are the difference between a trustworthy report and a double-counted one.

## Syntax and key functions

```sql-syntax
SELECT a.column, b.column
FROM table_a a
INNER JOIN table_b b ON a.key = b.key
WHERE row_condition;
```

`INNER JOIN` and `JOIN` are the same. The alias follows the table name, with or without `AS`. Combining a join with grouping:

```sql-syntax
SELECT b.label, COUNT(*) AS n
FROM table_a a
JOIN table_b b ON a.key = b.key
GROUP BY b.label;
```

| Part | Meaning |
|---|---|
| `table_a a` | Table with alias `a`; use `a.column` from then on |
| `ON a.key = b.key` | Pairs rows whose keys are equal; NULL keys never match |
| `JOIN` / `INNER JOIN` | Keep only matched pairs |
| `a.*` | All columns of table `a` only |
| `USING (key)` | Shorthand when both tables have a column of the same name |

| Relationship | Example in Northwind | Rows after the join |
|---|---|---|
| One-to-many | `customers` to `orders` | One per order that has a customer |
| One-to-many | `orders` to `order_details` | One per order line |
| Many-to-one | `products` to `categories` | One per product that has a category |

## Learn by example

### Example 1: Orders with their customer names

Each order is paired with the customer whose key matches. The aliases `o` and `c` keep the query short, and both columns are qualified. Only columns of the joined result can be selected, so the company name from `customers` now appears next to the order data.

```sql run
SELECT o.order_id, o.order_date, c.company_name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
ORDER BY o.order_id
LIMIT 4;
```

```output
order_id | order_date | company_name
10248 | 1996-01-01 | Alfreds Futterkiste
10249 | 1997-02-02 | Ana Trujillo Emparedados
10250 | 1998-03-03 | Antonio Moreno Taquería
10251 | 1996-04-04 | Around the Horn
```

### Example 2: Products with their category

The foreign key `products.category_id` matches the primary key `categories.category_id`. Every product has a category, so the join returns one row per product. Selecting columns from both tables is the whole point of a join.

```sql run
SELECT p.product_id, p.product_name, c.category_name, p.unit_price
FROM products p
JOIN categories c ON p.category_id = c.category_id
ORDER BY p.product_id
LIMIT 4;
```

```output
product_id | product_name | category_name | unit_price
1 | Chai | Beverages | 18.00
2 | Chang | Beverages | 19.00
3 | Aniseed Syrup | Condiments | 10.00
4 | Chef Anton's Cajun Seasoning | Condiments | 22.00
```

### Example 3: Counting rows after a join

`order_details` has 250 lines for 100 orders. After joining orders to their lines the result has one row per line: 250 rows. The distinct count shows that the 250 rows still belong to only 100 different orders, so the order columns are repeated several times.

```sql run
SELECT COUNT(*) AS joined_rows,
       COUNT(DISTINCT o.order_id) AS distinct_orders
FROM orders o
JOIN order_details od ON od.order_id = o.order_id;
```

```output
joined_rows | distinct_orders
250 | 100
```

### Example 4: A row that disappears

There are 100 orders but 99 rows come out of this join, because order 10347 has a NULL `employee_id` and so matches no employee. The second column proves that the order is the missing one. An inner join drops rows silently, with no error and no warning.

```sql run
SELECT COUNT(*) AS joined_orders,
       COUNT(*) FILTER (WHERE o.order_id = 10347) AS order_10347
FROM orders o
JOIN employees e ON o.employee_id = e.employee_id;
```

```output
joined_orders | order_10347
99 | 0
```

### Example 5: Row multiplication in action

Order 10251 has four lines, so its freight appears four times after the join. The query adds the freight column of the whole joined result and gives 23554.40, although the freight of all orders is really 9851.61 (day 36). The excess comes from repeating each order's freight on every one of its lines.

```sql run
SELECT SUM(o.freight) AS freight_over_join,
       COUNT(*) AS joined_rows,
       COUNT(DISTINCT o.order_id) AS orders
FROM orders o
JOIN order_details od ON od.order_id = o.order_id;
```

```output
freight_over_join | joined_rows | orders
23554.40 | 250 | 100
```

### Example 6: Join, group and aggregate correctly

Here the aggregates only use columns that belong to the joined rows' level of detail. One row of this join is one product, so `COUNT(*)` counts products and `AVG(p.unit_price)` averages product prices per category name. The result is the summary by category from day 37, now showing names instead of numbers.

```sql run
SELECT c.category_name,
       COUNT(*) AS products,
       ROUND(AVG(p.unit_price), 2) AS avg_price
FROM products p
JOIN categories c ON p.category_id = c.category_id
GROUP BY c.category_name
ORDER BY products DESC, c.category_name;
```

```output
category_name | products | avg_price
Confections | 13 | 25.16
Beverages | 12 | 37.98
Condiments | 12 | 23.06
Seafood | 12 | 20.68
Dairy Products | 10 | 28.73
Grains/Cereals | 7 | 20.25
Meat/Poultry | 6 | 54.01
Produce | 5 | 32.37
```

## Real-world applications

**Readable reports.** Raw fact tables contain codes (`customer_id`, `category_id`). Joining to the lookup tables, as in examples 1, 2 and 6, replaces codes with names so a report can be read by people.

**Line-level analysis.** Revenue questions need `order_details` (price and quantity) combined with `orders` (dates, customers). Example 3 shows the grain of that join: one row per order line.

**Data validation.** Comparing row counts before and after a join, as in example 4, finds orphan rows and missing keys, a routine check when loading data into a warehouse.

**Avoiding double counting.** Checking what one joined row represents (example 5) is the first step before computing revenue, freight or headcounts across tables, and a standard interview question.

## Daily review

### Key takeaways

- A join combines rows from two tables where the `ON` condition is true; the usual condition is foreign key equals primary key.
- `JOIN` means `INNER JOIN`. Unmatched rows, and rows with NULL keys, are dropped.
- Alias tables and qualify columns; an unqualified shared name is ambiguous.
- One-to-many joins repeat the "one" side on every "many" row. The result has one row per matched "many" row.
- Aggregating a repeated column after a join overcounts. Know the grain of your joined result.

### Common mistakes

- Selecting `customer_id` that exists in both tables without a prefix: "column reference "customer_id" is ambiguous". Write `o.customer_id`.
- Joining on the wrong columns (`o.order_id = c.customer_id`): the query runs but returns no rows or nonsense. Join foreign key to primary key.
- Forgetting the `ON` clause: PostgreSQL raises a syntax error at the next keyword. Day 42 shows the one case where you want every combination.
- Using the table name after giving it an alias: "invalid reference to FROM-clause entry for table". Use the alias.
- Summing an order-level column after joining to order lines and getting a total that is far too large.
- Expecting every order to survive the join when some keys are NULL, and then reporting 99 orders instead of 100.
- Putting filters in `ON` out of habit. For an inner join the result is the same as `WHERE`, but day 41 shows that it is not for outer joins, so keep filters in `WHERE`.

### Revision notes

- `FROM a JOIN b ON a.fk = b.pk`, alias both, qualify every column.
- Inner join drops unmatched rows; rows = matched pairs.
- Orders to details gives 250 rows; orders to employees gives 99.
- Before summing after a join, ask: what is one row now?

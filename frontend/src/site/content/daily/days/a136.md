## Objectives

- Explain why model size depends on columns and cardinality, and name the usual ways to shrink a model.
- Recognise slow DAX patterns and rewrite them into the preferred form.

- Audit a model, its measures and a report page with a checklist expressed as Python functions.

## Understand

### Why a model is fast or slow

A Power BI model in import mode is held in memory by an engine that stores each column separately and compresses it. This is a **column store**. It works well when a column has few distinct values, because repeated values compress into very little space, and works badly when almost every row has a different value. The number of distinct values in a column is its **cardinality**. A column with a cardinality of 12 (a product id in the sample model) is cheap; an order id, unique per row, is as expensive as a column can be, and a date-time down to the second is almost as bad. Memory use matters for the size of the file, the time to refresh and the time to answer a query. A model with ten million rows and a dozen unused high-cardinality columns will be slow for no benefit.

The levers that most reports need are few. **Remove what is not used**: every column that no visual, relationship or measure needs should be deleted in Power Query, not just hidden. **Reduce cardinality**: split a date-time into a date and (if needed) a separate time or hour, round numbers that do not need many decimals, and do not keep free text in the fact table. **Keep a star schema**: one narrow fact table with keys and numbers, and dimension tables with descriptions, as in the sample model (Day 127); wide flat tables repeat text in every row. **Prefer measures to calculated columns** for aggregations, because a calculated column is stored for every row (Day 129). **Be careful with bidirectional relationships**, which widen filter propagation and make queries slower and ambiguous. The auto date/time setting creates a hidden date table for every date column, and a model with its own date table (Day 128) should switch it off.

### DAX performance

A measure runs once per visual cell, often many times per page, so a small inefficiency is multiplied. Most real gains come from a short list of habits. Filter columns and not whole tables: `CALCULATE([Total Revenue], Products[category] = "Hardware")` is cheaper than `CALCULATE([Total Revenue], FILTER(Products, Products[category] = "Hardware"))`, because the second iterates the table row by row (Day 130). Use variables so that an expression is evaluated once (Day 132). Use `DIVIDE` and not an `IF` that tests the denominator and then divides. Avoid iterating a large fact table when a plain aggregation does the job: `SUM(Sales[Revenue])` on a stored column is faster than `SUMX(Sales, Sales[quantity] * Sales[unit_price])`, which has to compute each row, though the iterator is correct and sometimes the only choice. Do not nest iterators over large tables. A measure written clearly and correctly first and tuned only where measured is a better rule than guessing.

### Measuring with the Performance Analyzer

You should measure before changing anything. **Performance Analyzer** is a pane in Power BI Desktop (View, Performance analyzer). You start recording, interact with the page, and for each visual the pane lists how long it took, split into three parts: the time of the **DAX query** (the engine computing the data), the **visual display** (drawing it) and **other** (waiting for other visuals and overhead). The DAX query text can be copied out to run in other tools. The reading rule is simple: a large DAX query time points at the measure or the model, a large display time points at the visual (too many points or a heavy custom visual), and a large other time usually means too many visuals on the page. Fix the slowest visual first, and record again to prove that the change helped.

### Naming conventions and best practices

A **naming convention** is an agreement on how to name things so that a model reads the same way everywhere. A common set: measures use Title Case with spaces and no underscores, such as `Total Revenue` and `Revenue YTD`; tables use a plain business name; key columns and helper columns used only in the model are hidden from the report view; measures are kept in a dedicated folder or table, with a display folder per subject; columns have a description; and units are in the format, not the name. A convention is about the reader of the report as well as the author: people who build a report on the published model see only the names and will pick a measure called `Measure 3` at random. Documentation, a consistent format string and descriptions of measures belong to the same habit. Version the file and keep a short changelog.

### Why it matters

Performance and naming are the difference between a prototype and a model that can be shared. A report that takes ten seconds per click is abandoned, and one with a hundred poorly named fields is rebuilt by every new author. The usual misconception is that performance is a hardware or licence problem; most slow reports have an avoidable cause in the model or the formulas, and measurement shows which one.

## Syntax and key functions

There is no new syntax. The reference compares slow and preferred DAX forms and lists the tools of the day.

| Slow or risky form | Preferred form |
|---|---|
| `FILTER(Products, Products[category] = "Hardware")` as a filter | `Products[category] = "Hardware"` |
| `IF(den = 0, 0, num / den)` | `DIVIDE(num, den)` |
| The same expression written twice | `VAR x = ...` once, then `RETURN` |
| `SUMX(Sales, Sales[Revenue])` over a stored column | `SUM(Sales[Revenue])` |
| Date-time column to the second | Date column plus (if needed) an hour column |
| Calculated column that sums or averages | A measure |

```dax
-- two forms with the same result
Hardware Revenue = CALCULATE([Total Revenue], Products[category] = "Hardware")
Hardware Revenue Slow = CALCULATE([Total Revenue], FILTER(Products, Products[category] = "Hardware"))
```

## Learn by example

### Example 1: Cardinality decides the cost

Compute the distinct values per column of the `Sales` table. The columns with the highest ratio are the candidates for removal or splitting.

```python run
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
countries = ["UK", "Germany", "France", "Spain"]
cats = ["Hardware", "Software", "Services"]
customers = pd.DataFrame({
    "customer_id": range(1, 41),
    "customer_name": [f"Customer {i:02d}" for i in range(1, 41)],
    "country": [countries[i % 4] for i in range(40)],
    "segment": [["Retail", "Corporate"][(i // 4) % 2] for i in range(40)],
})
products = pd.DataFrame({
    "product_id": range(1, 13),
    "product_name": [f"Product {i:02d}" for i in range(1, 13)],
    "category": [cats[i % 3] for i in range(12)],
    "unit_cost": [float(10 + 5 * i) for i in range(12)],
})
n = 400
sales = pd.DataFrame({
    "order_id": range(1, n + 1),
    "order_date": pd.to_datetime("2025-01-01") + pd.to_timedelta(rng.integers(0, 365, n), unit="D"),
    "customer_id": rng.integers(1, 41, n),
    "product_id": rng.integers(1, 13, n),
    "quantity": rng.integers(1, 6, n),
})
sales["unit_price"] = (sales["product_id"].map(products.set_index("product_id")["unit_cost"]) * 1.5).round(2)
calendar = pd.DataFrame({"date": pd.date_range("2025-01-01", "2025-12-31")})
calendar["year"] = calendar["date"].dt.year
calendar["quarter"] = calendar["date"].dt.quarter
calendar["month_number"] = calendar["date"].dt.month
calendar["month_name"] = calendar["date"].dt.strftime("%B")
sales["revenue"] = sales["quantity"] * sales["unit_price"]
fact = (sales.merge(customers, on="customer_id").merge(products, on="product_id")
        .merge(calendar, left_on="order_date", right_on="date"))
cols = ["order_id", "order_date", "customer_id", "product_id", "quantity", "unit_price", "revenue"]
card = sales[cols].nunique()
table = pd.DataFrame({"distinct": card, "ratio": (card / len(sales)).round(3)})
print(table.to_string())
print([c for c in cols if card[c] / len(sales) > 0.5])
```

```output
             distinct  ratio
order_id          400  1.000
order_date        250  0.625
customer_id        40  0.100
product_id         12  0.030
quantity            5  0.012
unit_price         12  0.030
revenue            39  0.098
['order_id', 'order_date']
```

`order_id` is unique (400 distinct values in 400 rows, a ratio of 1.0) and `order_date` has 250. `product_id` has 12 values and `quantity` has 5, so those compress very well. The last line lists columns with a ratio above 0.5: `order_id` and `order_date`. The id may be needed as a key for distinct counts, the date is needed for the relationship, but if nothing used `order_id`, deleting it would be the biggest single saving.

### Example 2: Splitting a date-time lowers cardinality

If the source delivers a timestamp with the time, every row is distinct. Keeping the date and an hour column gives the same analysis with far fewer distinct values.

```python run
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
countries = ["UK", "Germany", "France", "Spain"]
cats = ["Hardware", "Software", "Services"]
customers = pd.DataFrame({
    "customer_id": range(1, 41),
    "customer_name": [f"Customer {i:02d}" for i in range(1, 41)],
    "country": [countries[i % 4] for i in range(40)],
    "segment": [["Retail", "Corporate"][(i // 4) % 2] for i in range(40)],
})
products = pd.DataFrame({
    "product_id": range(1, 13),
    "product_name": [f"Product {i:02d}" for i in range(1, 13)],
    "category": [cats[i % 3] for i in range(12)],
    "unit_cost": [float(10 + 5 * i) for i in range(12)],
})
n = 400
sales = pd.DataFrame({
    "order_id": range(1, n + 1),
    "order_date": pd.to_datetime("2025-01-01") + pd.to_timedelta(rng.integers(0, 365, n), unit="D"),
    "customer_id": rng.integers(1, 41, n),
    "product_id": rng.integers(1, 13, n),
    "quantity": rng.integers(1, 6, n),
})
sales["unit_price"] = (sales["product_id"].map(products.set_index("product_id")["unit_cost"]) * 1.5).round(2)
calendar = pd.DataFrame({"date": pd.date_range("2025-01-01", "2025-12-31")})
calendar["year"] = calendar["date"].dt.year
calendar["quarter"] = calendar["date"].dt.quarter
calendar["month_number"] = calendar["date"].dt.month
calendar["month_name"] = calendar["date"].dt.strftime("%B")
sales["revenue"] = sales["quantity"] * sales["unit_price"]
fact = (sales.merge(customers, on="customer_id").merge(products, on="product_id")
        .merge(calendar, left_on="order_date", right_on="date"))
seconds = rng.integers(0, 86400, len(sales))
stamp = sales["order_date"] + pd.to_timedelta(seconds, unit="s")
print(stamp.nunique(), stamp.dt.normalize().nunique(), stamp.dt.hour.nunique())
print(stamp.dt.normalize().nunique() + stamp.dt.hour.nunique())
```

```output
400 250 24
274
```

The timestamp column has 400 distinct values, one per row. Split into a date (250 distinct values) and an hour (24), the two columns hold 274 distinct values together, which compress much better and still support revenue by day and by hour. The split is done in Power Query before load.

### Example 3: A small DAX linter

A function that reads the text of measures and warns about the slow forms from the table above.

```python run
import re

rules = [
    (r"FILTER\(\s*(Sales|Products|Customers)\b", "FILTER over a whole table: use a column condition"),
    (r"\bIF\(\s*[\w\[\]\. ]+=\s*0", "IF test before dividing: use DIVIDE"),
    (r"\[\w[\w ]*\]\s*/\s*\[", "plain / between measures: use DIVIDE"),
]

measures = {
    "Hardware Revenue": 'CALCULATE([Total Revenue], Products[category] = "Hardware")',
    "Hardware Revenue Slow": 'CALCULATE([Total Revenue], FILTER(Products, Products[category] = "Hardware"))',
    "Margin": "[Total Profit] / [Total Revenue]",
    "AOV": "IF([Orders] = 0, 0, [Total Revenue] / [Orders])",
}
for name, text in measures.items():
    hits = [msg for pattern, msg in rules if re.search(pattern, text)]
    print(name + ":", "; ".join(hits) if hits else "ok")
```

```output
Hardware Revenue: ok
Hardware Revenue Slow: FILTER over a whole table: use a column condition
Margin: plain / between measures: use DIVIDE
AOV: IF test before dividing: use DIVIDE; plain / between measures: use DIVIDE
```

The first measure is clean. The second filters a whole table. `Margin` divides with `/`, which does not handle a zero or blank denominator cleanly. The last measure is flagged twice: for the `IF` test before dividing and for its plain `/`. A linter like this cannot judge performance; it only catches known patterns. It is a review aid and the Performance Analyzer remains the judge.

### Example 4: Reading a Performance Analyzer result

Three durations per visual, as the pane shows them. The numbers here are invented for the exercise.

```python run
import pandas as pd

log = pd.DataFrame({
    "visual": ["Revenue card", "Monthly trend", "Category bar", "Customer table", "Map"],
    "dax_ms": [12, 85, 40, 640, 95],
    "display_ms": [5, 30, 20, 150, 700],
    "other_ms": [8, 10, 12, 20, 15],
})
log["total_ms"] = log[["dax_ms", "display_ms", "other_ms"]].sum(axis=1)
print(log.sort_values("total_ms", ascending=False, kind="stable").to_string(index=False))
worst = log.loc[log["total_ms"].idxmax()]
slowest_part = worst[["dax_ms", "display_ms", "other_ms"]].astype(int).idxmax()
print(worst["visual"], int(worst["total_ms"]), slowest_part)
```

```output
        visual  dax_ms  display_ms  other_ms  total_ms
Customer table     640         150        20       810
           Map      95         700        15       810
 Monthly trend      85          30        10       125
  Category bar      40          20        12        72
  Revenue card      12           5         8        25
Customer table 810 dax_ms
```

The customer table takes 810 ms in total, mostly in its DAX query (640 ms), so the measure or the model behind it is the fix. The map has a similar total (810 ms) but its time is in drawing it (700 ms), so a better DAX measure would not help; reduce the number of points instead. The code picks the first maximum, the table, and reports its slowest part, `dax_ms`.

### Example 5: A naming convention check

Test names against the convention: measures in Title Case with spaces and no underscores, hidden helper columns allowed lower snake case.

```python run
import re

def check_measure(name):
    problems = []
    if "_" in name:
        problems.append("underscore")
    if name != name.strip() or "  " in name:
        problems.append("extra spaces")
    if not re.fullmatch(r"[A-Z][A-Za-z0-9%]*( [A-Z0-9%][A-Za-z0-9%]*)*", name):
        problems.append("not Title Case")
    return problems

for n in ["Total Revenue", "revenue_total", "Revenue YTD", "Measure 3", "Gross  Margin %", "total revenue"]:
    p = check_measure(n)
    print(f"{n!r}: {', '.join(p) if p else 'ok'}")
```

```output
'Total Revenue': ok
'revenue_total': underscore, not Title Case
'Revenue YTD': ok
'Measure 3': ok
'Gross  Margin %': extra spaces, not Title Case
'total revenue': not Title Case
```

`Total Revenue`, `Revenue YTD` and `Measure 3` pass the format rule; the convention does not make a name meaningful, so `Measure 3` still needs a person to rename it. `revenue_total` and `total revenue` fail, and the one with a double space is caught for spacing. Rules that a program can check are worth automating; meaning is checked in review.

## Real-world applications

- **Slimming a large model.** A cardinality table like Example 1 shows which columns to drop or split before a 50-million-row model is published (Examples 1 and 2).
- **Code review of measures.** A pull-request style review of measures, with a simple linter, keeps slow patterns out of a shared model (Example 3).
- **Slow report triage.** Performance Analyzer numbers tell whether to fix a measure, a visual or the page design (Example 4).
- **Self-service readiness.** A naming and description standard makes a published model usable by analysts who did not build it (Example 5).

## Daily review

### Key takeaways

- Model size and speed are driven by columns and their cardinality; remove unused columns and split date-times.
- Prefer a star schema, measures over calculated columns and single-direction relationships.
- Write DAX with column filters, variables and `DIVIDE`; use iterators when they are needed, not by default.
- Performance Analyzer gives DAX query, visual display and other time per visual; fix the biggest part of the slowest visual and measure again.
- A naming convention makes a model readable; automate what a function can check.

### Common mistakes

- Hiding columns instead of deleting them, so they still take memory.
- Wrapping a whole table in `FILTER` when a column condition would do.
- Tuning by guesswork without recording before and after.
- Putting 20 visuals on a page and blaming the measures for the slow load.
- Leaving default names such as `Measure 2` or `Column1` in a published model.

### Revision notes

- Cardinality: distinct values per column; ratio to row count.
- Shrink: delete unused, split date-time, star schema, measures not columns.
- Fast DAX: column filters, VAR, DIVIDE.
- Performance Analyzer: DAX query, visual display, other.
- Naming: Title Case measures, hidden keys, descriptions.

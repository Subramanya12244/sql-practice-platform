## Understand

### Why joins are the expensive step

In pandas a join looks up keys in memory on one machine. In Spark the two tables are spread over many partitions on many machines, so to match rows with the same key, those rows must meet on the same machine. Moving rows across the network is a **shuffle**, and it is the most expensive thing a Spark job does: data is serialised, written to disk, sent over the network, read and deserialised. Spark's join planning is largely about avoiding the shuffle of the big table. Spark and Java are not available in this course's tests or browser, so this lesson shows the PySpark code as text and uses plain-Python simulations to count exactly what a shuffle moves, and pandas and SQL to confirm that results do not depend on the strategy.

### Join strategies

Spark chooses a physical strategy for each join. The most common are these. A **broadcast hash join** sends a copy of the small table to every executor, which then joins it with its local part of the big table. The big table does not move at all. Spark uses it automatically when one side is smaller than `spark.sql.autoBroadcastJoinThreshold` (10 MB by default), and you can request it with `F.broadcast(small)` or the SQL hint `/*+ BROADCAST(small) */`. A **sort-merge join** is the default for two large tables with an equality condition: both sides are shuffled by the join key so equal keys land in the same partition, sorted, and merged. A **shuffled hash join** shuffles both sides and builds a hash table from the smaller side in each partition. A **broadcast nested loop join** and a **cartesian product** are used when there is no equality key (for example a range condition or a cross join) and can be very slow, because every row is compared with many others. You read the choice in `explain()`: `BroadcastHashJoin`, `SortMergeJoin`, `Exchange` for a shuffle and `BroadcastExchange` for a broadcast.

With **adaptive query execution (AQE)**, switched on by default in recent Spark versions, Spark can change its mind at run time, using the true sizes of the data after a shuffle: it can switch a sort-merge join to a broadcast join when one side turns out small, merge many tiny shuffle partitions into fewer, and split an oversized partition. The plan you see before running is then not always the plan that runs.

```python
from pyspark.sql import functions as F

joined = orders.join(customers, on="customer_id", how="left")          # Spark picks the strategy
hinted = orders.join(F.broadcast(customers), on="customer_id")          # force a broadcast hash join
joined.explain()
```

### Partitions and how data is spread

A DataFrame is a set of **partitions**, and one task processes one partition, so the number of partitions controls parallelism. After a shuffle, the number of partitions is `spark.sql.shuffle.partitions`, which is 200 by default. That is sensible for large data, but with a small table most of the 200 partitions are empty, and Spark spends time scheduling tasks that do nothing, which AQE reduces by coalescing them. Rows are assigned to a partition by hashing the key, so all rows with the same key go to the same partition. The simulations here use the CRC32 hash; Spark uses Murmur3, so the numbers of a real cluster differ but the reasoning does not.

You control partitioning with two methods. `repartition(n)` or `repartition(n, "col")` does a **full shuffle** into `n` partitions (by round-robin or by the hash of the column) and can increase or decrease the number. `coalesce(n)` only **reduces** the number of partitions by merging neighbours, without a full shuffle, which is cheaper but can leave partitions of unequal size. Use `repartition` to spread data evenly or to co-locate keys before a join or a write, and `coalesce` to cut the number of output files at the end of a job.

### Shuffle cost

A useful first estimate of shuffle cost is the number of records that must change partition. For a shuffle by key into N partitions, a record stays where it is only if the hash of its key happens to equal its current partition, which on average is one chance in N. So about (N - 1)/N of the rows move. In the simulation of this lesson 151 of 200 order rows and 15 of 20 customer rows move, 166 records in total, to join two tables on four partitions. A broadcast join of the 20 customers to the four partitions moves 80 customer copies and no orders. The saving is huge when one side is small and disappears when both are large, which is why the rule is to broadcast the small side and to filter and select columns before a join so that fewer and narrower rows are shuffled.

### Data skew

A shuffle by key puts all rows of one key on one partition. If one key is far more common than the others, one partition is much bigger than the rest. This is **skew**. The job finishes only when its slowest task finishes, so a single overloaded partition, with a task running for an hour while the others are done in a minute, delays everything, and may run out of memory. You detect skew by counting rows per key or per partition and comparing the largest with the average. Remedies: broadcast the other side if it is small (no shuffle, no skew); let AQE split skewed partitions in sort-merge joins (`spark.sql.adaptive.skewJoin.enabled`); or **salt** the key: add a random number from 0 to K-1 to the key of the big side and replicate each row of the small side K times with every salt value, so one hot key is spread over K partitions. Salting costs K copies of the small side and a little complexity, and it is only worth doing when skew is real.

### Why it matters

Most slow Spark jobs are slow because of a shuffle, a skewed key or too many or too few partitions. Being able to count what moves and to read the join strategy in `explain()` turns tuning from guessing into arithmetic. The misconception is that more executors always make a job faster: a skewed join waits for one task whatever the cluster size.

## Syntax and key functions

```python
orders.join(customers, "customer_id", "inner")          # how: inner, left, right, outer, left_semi, left_anti
orders.join(F.broadcast(customers), "customer_id")
orders.repartition(8, "customer_id")
orders.coalesce(2)
spark.conf.set("spark.sql.shuffle.partitions", "50")
```

| Item | What it does |
|---|---|
| `join(other, on, how)` | Join types `inner`, `left`, `right`, `outer` (full), `left_semi`, `left_anti`, `cross`. |
| `F.broadcast(df)`, `/*+ BROADCAST(t) */` | Hint to broadcast the small side. |
| `repartition(n)` / `repartition(n, col)` | Full shuffle into n partitions (hash of col). |
| `coalesce(n)` | Reduce partitions by merging neighbours, no full shuffle. |
| `spark.sql.shuffle.partitions` | Partitions after a shuffle (default 200). |
| `spark.sql.autoBroadcastJoinThreshold` | Size under which a side is broadcast (default 10 MB). |
| `spark.sql.adaptive.enabled`, `...skewJoin.enabled` | Adaptive execution and skew-join handling. |
| `explain()` | Shows `Exchange`, `BroadcastExchange`, `SortMergeJoin`, `BroadcastHashJoin`. |

## Learn by example

### Example 1: Join types and what they return

`orders.join(customers, "customer_id", how)` with `how` as `inner`, `left` and `left_anti` on small tables: the SQL equivalents run here.

```sql run
WITH orders(order_id, customer_id, amount) AS (
  VALUES (1, 10, 50), (2, 11, 30), (3, 12, 20), (4, 10, 70), (5, 99, 15)
), customers(customer_id, tier) AS (
  VALUES (10, 'gold'), (11, 'basic'), (12, 'basic'), (13, 'gold')
)
SELECT 'inner' AS how, COUNT(*) AS rows FROM orders o JOIN customers c USING (customer_id)
UNION ALL
SELECT 'left', COUNT(*) FROM orders o LEFT JOIN customers c USING (customer_id)
UNION ALL
SELECT 'full', COUNT(*) FROM orders o FULL JOIN customers c USING (customer_id)
UNION ALL
SELECT 'left_anti', COUNT(*) FROM orders o WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id)
ORDER BY 1
```

```output
how | rows
full | 6
inner | 4
left | 5
left_anti | 1
```

Four of the five orders find a customer (inner), all five are kept by the left join (order 5 has no customer 99 and gets nulls), the full join also keeps customer 13 who has no orders (6 rows), and the anti join returns the single order without a match. The strategy Spark uses to run these joins does not change these counts: it changes only the cost.

### Example 2: A shuffle join, counted

Place 200 orders and 20 customers on 4 partitions, shuffle both by `customer_id`, join inside each partition and check against a plain merge.

```python run
import zlib

COLS = ["order_id", "customer_id", "category", "amount"]
ROWS = [
    (1, "c1", "books", 20), (2, "c2", "books", 35), (3, "c1", "games", 60), (4, "c3", "games", 15),
    (5, "c2", "music", 10), (6, "c4", "books", 45), (7, "c3", "music", 30), (8, "c1", "books", 25),
    (9, "c4", "games", 80), (10, "c5", "music", 12), (11, "c2", "games", 70), (12, "c5", "books", 18),
]

def show(rows, cols, n=20):
    """Format rows the way DataFrame.show() prints them."""
    cells = [[str(v) for v in r] for r in rows[:n]]
    widths = [max(len(c), *(len(r[i]) for r in cells)) if cells else len(c) for i, c in enumerate(cols)]
    line = "+" + "+".join("-" * w for w in widths) + "+"
    out = [line, "|" + "|".join(c.rjust(w) for c, w in zip(cols, widths)) + "|", line]
    out += ["|" + "|".join(v.rjust(w) for v, w in zip(r, widths)) + "|" for r in cells]
    return "\n".join(out + [line])

def slices(rows, n):
    size = -(-len(rows) // n)
    return [rows[i * size:(i + 1) * size] for i in range(n)]

def target(key, n):
    return zlib.crc32(str(key).encode()) % n

import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
n = 200
keys = np.where(rng.random(n) < 0.5, 1, rng.integers(1, 21, n))
orders = pd.DataFrame({"order_id": np.arange(1, n + 1), "customer_id": keys, "amount": rng.integers(5, 100, n)})
customers = pd.DataFrame({"customer_id": np.arange(1, 21), "tier": np.where(np.arange(1, 21) % 3 == 0, "gold", "basic")})
N = 4

def split(df, parts):
    size = -(-len(df) // parts)
    return [df.iloc[i * size:(i + 1) * size] for i in range(parts)]

moved_o = sum(int(target(k, N) != i) for i, p in enumerate(split(orders, N)) for k in p["customer_id"])
moved_c = sum(int(target(k, N) != i) for i, p in enumerate(split(customers, N)) for k in p["customer_id"])
print(moved_o, moved_c, moved_o + moved_c)

joined = 0
for i in range(N):
    o = orders[orders["customer_id"].map(lambda k: target(k, N)) == i]
    c = customers[customers["customer_id"].map(lambda k: target(k, N)) == i]
    joined += len(o.merge(c, on="customer_id"))
print(joined, len(orders.merge(customers, on="customer_id")))
```

```output
151 15 166
200 200
```

151 of the 200 order rows and 15 of the 20 customer rows start on a partition other than the one their key hashes to, so 166 records are sent across the network. Joining inside each partition produces 200 rows, exactly the result of the plain merge: the shuffle does not change the answer, it only puts matching keys together.

### Example 3: Broadcasting the small side

Instead of shuffling both tables, copy the 20 customers to each of the 4 partitions.

```python run
import numpy as np

N = 4
size = -(-len(orders) // N)
parts = [orders.iloc[i * size:(i + 1) * size] for i in range(N)]

records_broadcast = len(customers) * N

print(records_broadcast, len(joined))
print(joined.groupby("tier")["amount"].sum().to_dict())
```

```output
80 200
{'basic': 8985, 'gold': 1682}
```

Broadcasting moves 20 x 4 = 80 customer copies and no order rows, against 166 records for the shuffle join, and the join result is the same 200 rows. The revenue by tier is 8,985 for basic and 1,682 for gold. A real broadcast sends one copy to each executor, not to each partition, so the true cost is lower still when an executor holds several partitions.

### Example 4: Detecting and fixing skew

Half of the orders belong to customer 1. Count the rows per partition after a shuffle, and then after salting the key.

```python run
import zlib

COLS = ["order_id", "customer_id", "category", "amount"]
ROWS = [
    (1, "c1", "books", 20), (2, "c2", "books", 35), (3, "c1", "games", 60), (4, "c3", "games", 15),
    (5, "c2", "music", 10), (6, "c4", "books", 45), (7, "c3", "music", 30), (8, "c1", "books", 25),
    (9, "c4", "games", 80), (10, "c5", "music", 12), (11, "c2", "games", 70), (12, "c5", "books", 18),
]

def show(rows, cols, n=20):
    """Format rows the way DataFrame.show() prints them."""
    cells = [[str(v) for v in r] for r in rows[:n]]
    widths = [max(len(c), *(len(r[i]) for r in cells)) if cells else len(c) for i, c in enumerate(cols)]
    line = "+" + "+".join("-" * w for w in widths) + "+"
    out = [line, "|" + "|".join(c.rjust(w) for c, w in zip(cols, widths)) + "|", line]
    out += ["|" + "|".join(v.rjust(w) for v, w in zip(r, widths)) + "|" for r in cells]
    return "\n".join(out + [line])

def slices(rows, n):
    size = -(-len(rows) // n)
    return [rows[i * size:(i + 1) * size] for i in range(n)]

def target(key, n):
    return zlib.crc32(str(key).encode()) % n

import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
n = 200
keys = np.where(rng.random(n) < 0.5, 1, rng.integers(1, 21, n))
N = 4
load = [0] * N
for k in keys:
    load[target(k, N)] += 1
print(load, round(max(load) / (n / N), 2))
print(int((keys == 1).sum()))

rng2 = np.random.default_rng(7)
_ = np.where(rng2.random(n) < 0.5, 1, rng2.integers(1, 21, n))
K = 4
salt = rng2.integers(0, K, n)
load2 = [0] * N
for k, s in zip(keys, salt):
    load2[target(f"{k}_{s}", N)] += 1
print(load2, round(max(load2) / (n / N), 2))
```

```output
[24, 26, 26, 124] 2.48
95
[75, 27, 67, 31] 1.5
```

After a plain shuffle by key the partitions hold 24, 26, 26 and 124 rows: the largest is 2.48 times the average of 50, because customer 1 alone has 95 orders, and that one task decides when the job ends. After salting the key with K = 4 the loads are 75, 27, 67 and 31, a ratio of 1.5. The balance is not perfect (a small number of partitions and a hash make it uneven), but the hot partition has gone from 124 rows to 75. The price is that the customer table must be replicated 4 times, once per salt value.

### Example 5: repartition, coalesce and 200 shuffle partitions

Compare the cost of reducing 4 partitions to 2 by `coalesce` and by `repartition`, and look at what 200 shuffle partitions mean for 20 keys.

```python run
import zlib

COLS = ["order_id", "customer_id", "category", "amount"]
ROWS = [
    (1, "c1", "books", 20), (2, "c2", "books", 35), (3, "c1", "games", 60), (4, "c3", "games", 15),
    (5, "c2", "music", 10), (6, "c4", "books", 45), (7, "c3", "music", 30), (8, "c1", "books", 25),
    (9, "c4", "games", 80), (10, "c5", "music", 12), (11, "c2", "games", 70), (12, "c5", "books", 18),
]

def show(rows, cols, n=20):
    """Format rows the way DataFrame.show() prints them."""
    cells = [[str(v) for v in r] for r in rows[:n]]
    widths = [max(len(c), *(len(r[i]) for r in cells)) if cells else len(c) for i, c in enumerate(cols)]
    line = "+" + "+".join("-" * w for w in widths) + "+"
    out = [line, "|" + "|".join(c.rjust(w) for c, w in zip(cols, widths)) + "|", line]
    out += ["|" + "|".join(v.rjust(w) for v, w in zip(r, widths)) + "|" for r in cells]
    return "\n".join(out + [line])

def slices(rows, n):
    size = -(-len(rows) // n)
    return [rows[i * size:(i + 1) * size] for i in range(n)]

def target(key, n):
    return zlib.crc32(str(key).encode()) % n

parts = [list(range(i * 5, i * 5 + 5)) for i in range(4)]
merged = [parts[0] + parts[1], parts[2] + parts[3]]
coalesce_moved = len(parts[1]) + len(parts[3])
repartition_moved = sum(1 for i, p in enumerate(parts) for k in p if target(k, 2) != i)
print([len(p) for p in merged], coalesce_moved, repartition_moved)

used = {target(k, 200) for k in range(1, 21)}
print(len(used), 200 - len(used))
```

```output
[10, 10] 10 17
19 181
```

`coalesce(2)` merges neighbours: partitions of 10 and 10 rows, and only the 10 rows of partitions 1 and 3 change place, with no hashing. `repartition(2)` hashes every row, so the number of rows that change partition (here 17) is larger and the data is spread by key, not by position. For 20 keys and 200 shuffle partitions at most 20 partitions can receive data: in this model 19 do (two keys hash to the same partition) and 181 are empty, which shows why the default of 200 is too many for small data (AQE would coalesce the empty ones).

## Real-world applications

- **Dimension joins.** Joining a large fact table to a small dimension is the standard case for a broadcast join (Examples 1 and 3).
- **Hot keys.** A default customer id, a null key or one very large account produces skew; detecting it from the key counts and salting or broadcasting fixes a job that "hangs at 99%" (Example 4).
- **Output file layout.** `coalesce` at the end of a job reduces the number of small output files without paying for a full shuffle (Example 5).
- **Tuning shuffle partitions.** Setting `spark.sql.shuffle.partitions` to match the data size avoids thousands of empty tasks (Example 5).

## Daily review

### Key takeaways

- A join of two big tables shuffles both by the key; a broadcast join copies the small table and moves nothing of the big one.
- Shuffle cost is the records that change partition, about (N - 1)/N of them for a hash shuffle.
- `repartition` does a full shuffle; `coalesce` only merges neighbouring partitions.
- Skew is one partition much larger than the average; fix it with broadcast, AQE skew handling or salting.
- Read `explain()` for `Exchange`, `BroadcastExchange` and the join type; AQE can change the plan at run time.

### Common mistakes

- Joining a big table with a small one without a broadcast and shuffling gigabytes for nothing.
- Joining before filtering and selecting, so more and wider rows are shuffled.
- Leaving 200 shuffle partitions on small data, or too few on huge data.
- Ignoring a hot key (null or default id) and waiting for one slow task.
- Using `repartition` to reduce the output file count, paying for a shuffle that `coalesce` avoids.

### Revision notes

- Strategies: broadcast hash, sort-merge, shuffled hash, nested loop, cartesian.
- `F.broadcast`, 10 MB default threshold, AQE.
- `repartition(n, col)` vs `coalesce(n)`; `spark.sql.shuffle.partitions` = 200.
- Skew: max load / mean load; salting costs K copies of the small side.

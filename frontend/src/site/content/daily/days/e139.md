## Objectives

- Compute quality metrics for a pipeline run (volume, null rate, duplicate rate, rejected share and freshness) as plain numbers.
- Compare metrics with warning and critical thresholds and explain how thresholds are chosen.
- Format an alert message that says what failed, by how much, and what to do, and send it through a replaceable notification function.
- Store metrics per run and query the history for a trend, so that a dashboard can show change over time.
- Reduce alert noise by alerting on state changes and sending a summary instead of one message per check.

## Understand

### From checks to a report

Days 132 to 137 gave you many checks: completeness, uniqueness, counts, sums and reconciliation. Each check gives a result such as "3 of 120 amounts are null". On their own these results are scattered across log lines. A **quality report** collects them after each run into one summary that anyone can read: which checks ran, the measured value of each, the allowed limit and the verdict. A report is also the evidence that the check ran at all; a silent pipeline cannot be told apart from one that never ran.

A **metric** is a number that describes the data or the run. Good starting metrics for the orders pipeline are:

- **Volume:** rows extracted, rows loaded and rows rejected.
- **Completeness:** the share of null values in a required column (null rate).
- **Uniqueness:** the share of rows with a repeated key (duplicate rate).
- **Validity:** the share of rows that fail a rule such as a negative amount.
- **Freshness:** the age of the newest record, `now - max(created_at)`, in hours.
- **Reconciliation:** the difference between source and target totals from Day 137.

Turn counts into **rates** (a share between 0 and 1) wherever the data grows. "30 null amounts" means little; "0.4 percent null" can be compared across a day with 500 rows and a day with 50,000.

### Thresholds and severity

A **threshold** is the value at which a metric is considered a problem. Most teams use two levels. A **warning** says "look at this when you can", and a **critical** says "stop and fix now, downstream data is unreliable". For example, a null rate above 1 percent warns and above 5 percent is critical. Some metrics fail in one direction only: null rate and duplicate rate are bad when high, row volume and freshness can be bad in either direction (zero rows loaded is critical; an unexpectedly large load is a warning).

Choose thresholds from evidence. Look at the metric over several past runs and set the warning above its normal range. A threshold that fires every day trains everyone to ignore it, and one set far above normal never fires. Write the threshold in code or configuration next to the check so that changes are reviewed, as with any other code (Day 140).

### Alerts: message and delivery

An **alert** is a message sent to a person or system when a check crosses a threshold. A useful alert answers five questions in the message itself: what pipeline and run, which metric, the measured value and the limit, how severe, and what to look at first. "Data quality failed" forces the reader to open logs; "CRITICAL orders_clean null_rate_amount 6.2% > 5.0% (run 2026-01-08): check the amount parser" does not.

Delivery (email, a chat channel, a paging service) is a separate concern from deciding that something is wrong. Write one function `notify(severity, text)` and call it from the check logic; in production it posts to a webhook, and in tests it appends to a list. That separation lets you test the alert logic without a network, which is the approach this day uses. The lesson never sends a real message.

### Avoiding alert fatigue

Alert fatigue is what happens when people receive so many alerts that they stop reading them. Three habits reduce it. **Alert on state changes:** send a message when a metric moves from OK to warning, from warning to critical, or recovers, and not on every run while it stays bad. **Group:** send one summary per run listing all failed checks rather than ten messages. **Route by severity:** warnings go to a channel read in working hours, criticals page the on-call person. An alert nobody acts on should be fixed (changing the check or the threshold) or deleted.

### History and dashboards

A single run's report says whether today is acceptable; the trend says whether it is getting worse. Store each run's metrics as rows: `(run_date, metric, value)`. A query over this table gives the latest value, the average of the last few runs and the change, and a **dashboard** is a picture of exactly such a query, usually a line per metric with the threshold drawn as a horizontal line. You do not need a dashboard tool to start: the query and a text table are the dashboard's data. Tools such as Metabase, Grafana or a BI tool can draw it later.

### Common misconception

Learners often think that more checks and lower thresholds mean better quality. Past a certain point they only mean more noise, and the one alert that mattered is lost among twenty. The goal is a small set of checks that each have an owner, a reason and a response. A second misconception is that a passing report proves the data is correct: it proves the checks you wrote passed, and a metric that is not measured cannot alert.

### Why it matters

Bad data that is found by the pipeline on the day it arrives costs a rerun. Bad data found by a stakeholder two weeks later costs trust and a backfill (Day 128). Reports and alerts are how that difference is created.

## Syntax and key functions

Metrics, thresholds and a verdict:

```python
null_rate = df["amount"].isna().mean()                 # share between 0 and 1
dup_rate = df["order_id"].duplicated().mean()
age_hours = (now - df["created_at"].max()) / pd.to_timedelta(1, unit="h")

THRESHOLDS = {"null_rate": (0.01, 0.05)}               # (warning, critical)
status = "CRITICAL" if value > crit else "WARN" if value > warn else "OK"
```

A trend query in PostgreSQL:

```sql-syntax
SELECT run_date, value,
       AVG(value) OVER (ORDER BY run_date ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING) AS previous_avg
FROM quality_run
WHERE metric = 'null_rate'
ORDER BY run_date;
```

| Item | What it does or returns |
|---|---|
| `Series.isna().mean()` | Share of nulls (True counts as 1). |
| `Series.duplicated().mean()` | Share of rows whose key already appeared. |
| `(now - ts) / pd.to_timedelta(1, unit="h")` | Age in hours as a number. |
| `f"{value:.1%}"` | Formats 0.062 as `6.2%`. |
| `notify(severity, text)` | Your delivery function (webhook, email); in tests a list append. |
| `AVG(x) OVER (... ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING)` | Average of the previous three runs. |
| `COUNT(*) FILTER (WHERE cond)` | Count of rows meeting a condition in one aggregate. |

## Learn by example

### Example 1: Metrics for one run

A small extract has a missing amount, a repeated order and an old newest record. The code computes the metrics and prints them as a small report. `now` is a fixed timestamp so that the output is stable; a real pipeline would use the current time.

```python run
import pandas as pd

df = pd.DataFrame({
    "order_id": [1, 2, 3, 3, 4, 5, 6, 7, 8, 9],
    "amount": [10.0, None, 25.0, 25.0, 40.0, None, 15.0, 30.0, 12.5, 8.0],
    "status": ["paid", "paid", "failed", "failed", "paid", "paid", "refunded", "paid", "paid", "paid"],
    "created_at": pd.to_datetime(["2026-01-08 01:00", "2026-01-08 02:00", "2026-01-08 03:00", "2026-01-08 03:00",
                                  "2026-01-08 04:00", "2026-01-08 05:00", "2026-01-08 06:00", "2026-01-08 07:00",
                                  "2026-01-08 08:00", "2026-01-08 09:00"]),
})
now = pd.Timestamp("2026-01-08 15:00")

metrics = {
    "rows": len(df),
    "null_rate_amount": float(df["amount"].isna().mean()),
    "duplicate_rate": float(df["order_id"].duplicated().mean()),
    "failed_share": float((df["status"] == "failed").mean()),
    "freshness_hours": float((now - df["created_at"].max()) / pd.to_timedelta(1, unit="h")),
}
for name, value in metrics.items():
    print(f"{name:18} {value:g}")
```

```output
rows               10
null_rate_amount   0.2
duplicate_rate     0.1
failed_share       0.2
freshness_hours    6
```

Rates are fractions: `0.2` means 20 percent. The newest record is six hours old, which only matters once a freshness threshold is defined.

### Example 2: Thresholds and severity

Each metric has a warning and a critical limit and a direction. `evaluate` returns a list of result tuples rather than printing, so other code can format or route them. Freshness uses limits of 4 and 12 hours.

```python run
metrics = {"rows": 10, "null_rate_amount": 0.2, "duplicate_rate": 0.1, "failed_share": 0.2, "freshness_hours": 6.0}

# metric: (warning, critical, direction); "high" is bad when the value is too large
THRESHOLDS = {
    "null_rate_amount": (0.01, 0.05, "high"),
    "duplicate_rate": (0.0, 0.02, "high"),
    "failed_share": (0.10, 0.30, "high"),
    "freshness_hours": (4, 12, "high"),
    "rows": (50, 1, "low"),
}

def evaluate(metrics, thresholds):
    results = []
    for name, (warn, crit, direction) in thresholds.items():
        value = metrics[name]
        if direction == "high":
            status = "CRITICAL" if value > crit else "WARN" if value > warn else "OK"
        else:
            status = "CRITICAL" if value < crit else "WARN" if value < warn else "OK"
        results.append((name, value, status))
    return results

for name, value, status in evaluate(metrics, THRESHOLDS):
    print(f"{status:8} {name} = {value:g}")
```

```output
CRITICAL null_rate_amount = 0.2
CRITICAL duplicate_rate = 0.1
WARN     failed_share = 0.2
WARN     freshness_hours = 6
WARN     rows = 10
```

For `rows` the direction is reversed: fewer than 50 rows is a warning and fewer than 1 row is critical. A direction flag keeps both kinds of metric in one table of limits.

### Example 3: Formatting and sending an alert

`format_alert` produces one message per failed check with the five answers an alert needs. `notify` is a stand-in for a webhook: it appends to a list so the test needs no network. The summary message groups everything for one run, and its first line carries the worst severity.

```python run
sent = []

def notify(severity, text):
    sent.append((severity, text))

HINTS = {"null_rate_amount": "check the amount parser", "freshness_hours": "check the extract schedule"}

def format_alert(pipeline, run_date, name, value, limit, status):
    shown = f"{value:.1%}" if "rate" in name else f"{value:g}"
    lim = f"{limit:.1%}" if "rate" in name else f"{limit:g}"
    return f"{status} {pipeline} {name} {shown} > {lim} (run {run_date}): {HINTS.get(name, 'see the run log')}"

failed = [("null_rate_amount", 0.2, 0.05, "CRITICAL"), ("freshness_hours", 6.0, 4, "WARN")]
lines = [format_alert("orders_clean", "2026-01-08", *f) for f in failed]
worst = "CRITICAL" if any(f[3] == "CRITICAL" for f in failed) else "WARN"
notify(worst, f"[{worst}] orders_clean: {len(failed)} checks failed\n" + "\n".join(lines))

for severity, text in sent:
    print(severity)
    print(text)
```

```output
CRITICAL
[CRITICAL] orders_clean: 2 checks failed
CRITICAL orders_clean null_rate_amount 20.0% > 5.0% (run 2026-01-08): check the amount parser
WARN orders_clean freshness_hours 6 > 4 (run 2026-01-08): check the extract schedule
```

The first line of the message (`[CRITICAL] orders_clean: 2 checks failed`) is enough for a phone notification; the details follow. Replacing `notify` with a function that posts to a webhook changes the delivery and nothing else.

### Example 4: Metric history and a trend in PostgreSQL

Each run stores its null rate. The window function averages the three previous runs and the final query flags runs that are more than double their recent average. The dashboard data is this query.

```sql run
CREATE TABLE quality_run (run_date date, metric text, value numeric(6,3));
INSERT INTO quality_run VALUES
  ('2026-01-01', 'null_rate', 0.010), ('2026-01-02', 'null_rate', 0.012), ('2026-01-03', 'null_rate', 0.008),
  ('2026-01-04', 'null_rate', 0.011), ('2026-01-05', 'null_rate', 0.030), ('2026-01-06', 'null_rate', 0.012),
  ('2026-01-01', 'dup_rate', 0.000), ('2026-01-02', 'dup_rate', 0.000), ('2026-01-03', 'dup_rate', 0.004);

WITH t AS (
  SELECT run_date, value,
         ROUND(AVG(value) OVER (ORDER BY run_date ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING), 4) AS previous_avg
  FROM quality_run
  WHERE metric = 'null_rate'
)
SELECT run_date, value, previous_avg,
       CASE WHEN previous_avg IS NOT NULL AND value > 2 * previous_avg THEN 'spike' ELSE 'normal' END AS trend
FROM t
ORDER BY run_date
LIMIT 10;
```

```output
run_date | value | previous_avg | trend
2026-01-01 | 0.010 | NULL | normal
2026-01-02 | 0.012 | 0.0100 | normal
2026-01-03 | 0.008 | 0.0110 | normal
2026-01-04 | 0.011 | 0.0100 | normal
2026-01-05 | 0.030 | 0.0103 | spike
2026-01-06 | 0.012 | 0.0163 | normal
```

The first run has no previous average, so it cannot be a spike. January 5 stands out against its recent average even though 3 percent might still be under a fixed critical limit, which is the value of a trend check next to a threshold.

### Example 5: Alert on state changes and send one summary

Keeping the previous status per metric lets the run send only changes: new problems, escalations and recoveries. A metric that stays in WARN produces no new message. The function returns the lines so the caller can pass them to `notify`.

```python run
ORDER = {"OK": 0, "WARN": 1, "CRITICAL": 2}

def changes(previous, current):
    lines = []
    for name in sorted(current):
        before, now = previous.get(name, "OK"), current[name]
        if before == now:
            continue
        if ORDER[now] > ORDER[before]:
            lines.append(f"{name}: {before} -> {now}")
        else:
            lines.append(f"{name}: recovered ({before} -> {now})")
    return lines

monday = {"null_rate": "OK", "dup_rate": "WARN", "freshness": "CRITICAL", "volume": "OK"}
tuesday = {"null_rate": "WARN", "dup_rate": "WARN", "freshness": "OK", "volume": "OK"}
wednesday = {"null_rate": "WARN", "dup_rate": "WARN", "freshness": "OK", "volume": "OK"}

for label, prev, cur in [("Tuesday", monday, tuesday), ("Wednesday", tuesday, wednesday)]:
    msgs = changes(prev, cur)
    print(label, "sends", len(msgs), "lines")
    for m in msgs:
        print("  ", m)
```

```output
Tuesday sends 2 lines
   freshness: recovered (CRITICAL -> OK)
   null_rate: OK -> WARN
Wednesday sends 0 lines
```

On Wednesday nothing changed, so nothing is sent, even though two metrics are still in WARN. The standing problems stay visible in the daily report, not in the alert channel.

## Real-world applications

- **Run summary at the end of an orders load.** The pipeline writes one row per metric to `quality_run`, evaluates thresholds and posts a single summary with the failed checks to the team channel.
- **Freshness monitoring.** A scheduled check compares the newest `created_at` with the current time. A stalled extract shows up as rising freshness hours, before any consumer notices the missing day.
- **Trend review in a weekly quality meeting.** The history query shows which metrics are drifting upward while still under their limits, so a fix can be planned instead of firefought.
- **On-call routing.** Criticals page the engineer on duty; warnings are collected into a morning digest, which keeps the pager meaningful.

## Daily review

### Key takeaways

- A quality report collects metrics, limits and verdicts for every run; it is also evidence that checks ran.
- Use rates for growing data, and two thresholds (warning and critical), with a direction per metric.
- An alert states the pipeline, metric, value, limit, severity and a first action.
- Keep delivery behind one `notify` function so the logic is testable without a network.
- Reduce noise: alert on state changes, group per run, route by severity. Store history to see trends.

### Common mistakes

- **Alerting on raw counts.** A count of 30 means different things on different days. Convert to a rate.
- **Thresholds that fire daily.** People ignore them. Set limits from past runs.
- **One message per failed check.** Ten messages bury the cause. Send one grouped summary.
- **Comparing with 0 for freshness or volume in the wrong direction.** Zero rows is bad; zero nulls is good. Store the direction with the threshold.
- **Alerting every run while a metric stays bad.** Alert on the change and show the standing state in the report.

### Revision notes

- Metrics: volume, null rate, duplicate rate, validity, freshness, reconciliation difference.
- Status: `OK` / `WARN` / `CRITICAL` from `(warn, crit, direction)`.
- Alert text: severity, pipeline, metric, value > limit, run, first action.
- History: `quality_run(run_date, metric, value)`; trend with a window average.

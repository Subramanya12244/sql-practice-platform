## Objectives

- Test whether related rows exist with `EXISTS`, and whether they do not exist with `NOT EXISTS`.
- Explain why `NOT IN` returns no rows when its list contains a NULL, and why `NOT EXISTS` does not have that problem.
- Write semi-joins and anti-joins three ways (`EXISTS`/`NOT EXISTS`, `IN`/`NOT IN`, `LEFT JOIN ... IS NULL`) and choose between them.
- Explain why `EXISTS` never repeats outer rows, unlike a join.
- Combine several `EXISTS` and `NOT EXISTS` conditions to describe a customer's history.

## Understand

### Existence as a question

Often you do not care about the values in a related table, only whether a matching row exists. "Customers who have placed an order." "Products nobody has bought." "Employees with no sales." Each is a yes-or-no question about the related rows. `EXISTS` asks it directly. `EXISTS (subquery)` is true when the subquery returns at least one row, and false when it returns none. It is almost always correlated (day 43): the subquery refers to the current outer row, so the answer is per row.

```sql-syntax
SELECT c.customer_id
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)
```

For each customer `c` the database asks: does at least one order exist with this customer's id? If yes, the customer is kept. The `SELECT 1` in the subquery is a convention: `EXISTS` ignores the columns and only checks whether any row comes back, so the select list does not matter (`SELECT *` or `SELECT NULL` would behave identically). Because the database can stop as soon as it finds one matching row, `EXISTS` is efficient even when a customer has thousands of orders.

### Semi-join and anti-join

A query that keeps the outer rows that have a match is called a **semi-join**: it behaves like a join, except that it never returns columns from the other table. A query that keeps the outer rows that have no match is an **anti-join**. `NOT EXISTS (subquery)` is true when the subquery returns no rows, so it is the anti-join: `WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)` returns the customers without orders (FISSA and PARIS). Day 41 wrote the same thing as `LEFT JOIN ... WHERE o.order_id IS NULL`, and day 47 as `EXCEPT`. Three spellings, one meaning.

### Semi-join compared with a join

If you want customers who have orders and write `customers JOIN orders`, a customer with three orders appears three times (day 40). `EXISTS` returns each customer at most once, because it tests the customer row, not the pairs. For the customers who have an order dated from 1998 on, a join returns 33 rows (BONAP has two such orders) while `EXISTS` returns the 32 customers. When the question is "which customers", `EXISTS` is safer than a join followed by `DISTINCT`.

### The NOT IN trap

`NOT IN` looks like the natural opposite of `IN` (day 43), but it has a serious trap with NULL. Think about how `x NOT IN (1, 2, NULL)` is evaluated: it means `x <> 1 AND x <> 2 AND x <> NULL`. The last comparison is never true; it is unknown (day 35). With `AND`, one unknown among trues makes the whole result unknown, and `WHERE` keeps only true rows. So if the list contains a single NULL, `NOT IN` returns **no rows at all**, for every value of x, with no error. In Northwind exactly this happens: order 10347 has a NULL `employee_id`, so
`SELECT ... FROM employees WHERE employee_id NOT IN (SELECT employee_id FROM orders)` returns nothing, although employee 5, Buchanan, has no orders. The query "works", looks plausible and gives an empty result that is wrong.

`NOT EXISTS` does not have this problem: it checks whether the correlated subquery returns any row, and a NULL value in the other table simply never matches `o.employee_id = e.employee_id`. Buchanan has no matching order, so he is returned. You can also repair `NOT IN` by filtering the NULLs out of the list (`WHERE employee_id IS NOT NULL` in the subquery), but then you rely on remembering it each time. The rule of thumb: **use `NOT EXISTS`** for "has no matching row", and use `NOT IN` only with a literal list or a column declared `NOT NULL`.

### IN, EXISTS and joins: which to choose?

For the positive case, `IN (subquery)`, `EXISTS` and a join with `DISTINCT` give the same rows, and PostgreSQL usually plans them identically, so choose the form that reads best. `EXISTS` is the most flexible, because the correlated subquery can contain any conditions and several tables. For the negative case, prefer `NOT EXISTS` or `LEFT JOIN ... IS NULL`; they are NULL-safe and the planner turns both into an efficient anti-join. Avoid `NOT IN` on columns that can be NULL.

### Combining conditions

`EXISTS` and `NOT EXISTS` are ordinary predicates, so they combine with `AND` and `OR` like any other condition. Customers who ordered in 1998 but not in 1996 is `EXISTS (... 1998 ...) AND NOT EXISTS (... 1996 ...)`: two separate questions about the same customer, each with its own correlated subquery.

### Common misconception

Learners believe `NOT IN` and `NOT EXISTS` are interchangeable. They agree only when the list has no NULLs. When NULLs are possible, `NOT IN` can silently return nothing. Another belief is that the select list of the `EXISTS` subquery must match something in the outer query; it does not, since only the existence of a row matters.

### Why it matters

"Who has not done X" questions (inactive customers, products without sales, employees without a manager) are among the most common in analysis, and a silent empty result from `NOT IN` is a classic bug. `EXISTS` is the readable and safe way to ask existence questions.

## Syntax and key functions

```sql-syntax
-- semi-join: keep rows that have a match
SELECT c.column
FROM outer_table c
WHERE EXISTS (SELECT 1 FROM inner_table i WHERE i.key = c.key AND i.other > value);

-- anti-join: keep rows that have no match
SELECT c.column
FROM outer_table c
WHERE NOT EXISTS (SELECT 1 FROM inner_table i WHERE i.key = c.key);

-- equivalent spellings of the anti-join
LEFT JOIN inner_table i ON i.key = c.key WHERE i.primary_key IS NULL
WHERE c.key NOT IN (SELECT key FROM inner_table WHERE key IS NOT NULL)
```

| Form | True when | NULL in the inner column |
|---|---|---|
| `EXISTS (subquery)` | The subquery returns at least one row | Never matches, harmless |
| `NOT EXISTS (subquery)` | The subquery returns no row | Never matches, harmless |
| `x IN (subquery)` | `x` equals some value of the list | NULL values are ignored |
| `x NOT IN (subquery)` | `x` differs from every value of the list | One NULL in the list makes the result empty |
| `LEFT JOIN ... WHERE i.pk IS NULL` | No matching row on the right | Harmless |

## Learn by example

### Example 1: Customers who ordered in 1998

For each customer the subquery looks for an order of that customer dated 1998 or later. The correlation `o.customer_id = c.customer_id` ties it to the current customer, and the extra condition narrows the orders considered. The first five matches are shown. `SELECT 1` is only a placeholder, because `EXISTS` checks for a row, not for a value.

```sql run
SELECT c.customer_id, c.company_name
FROM customers c
WHERE EXISTS (SELECT 1
              FROM orders o
              WHERE o.customer_id = c.customer_id
                AND o.order_date >= '1998-01-01')
ORDER BY c.customer_id
LIMIT 5;
```

```output
customer_id | company_name
ANATR | Ana Trujillo Emparedados
ANTON | Antonio Moreno Taquería
BERGS | Berglunds snabbköp
BLAUS | Blauer See Delikatessen
BOLID | Bólido Comidas preparadas
```

### Example 2: A semi-join does not repeat rows

The first number counts the rows of a join between customers and their 1998 orders: 33, because BONAP has two such orders and appears twice. The second counts the customers returned by `EXISTS`: 32, one per customer. If the question is "how many customers", the join count would be wrong.

```sql run
SELECT (SELECT COUNT(*)
        FROM customers c
        JOIN orders o ON o.customer_id = c.customer_id
        WHERE o.order_date >= '1998-01-01') AS join_rows,
       (SELECT COUNT(*)
        FROM customers c
        WHERE EXISTS (SELECT 1
                      FROM orders o
                      WHERE o.customer_id = c.customer_id
                        AND o.order_date >= '1998-01-01')) AS customers_with_1998_order;
```

```output
join_rows | customers_with_1998_order
33 | 32
```

### Example 3: NOT EXISTS, customers without orders

The anti-join: keep the customers for whom the subquery finds no order at all. It returns the same two customers as the `LEFT JOIN ... IS NULL` of day 41 and the `EXCEPT` of day 47. The orders table has no NULL customers, so even `NOT IN` would work here, but the habit of `NOT EXISTS` is safer.

```sql run
SELECT c.customer_id, c.company_name
FROM customers c
WHERE NOT EXISTS (SELECT 1
                  FROM orders o
                  WHERE o.customer_id = c.customer_id)
ORDER BY c.customer_id;
```

```output
customer_id | company_name
FISSA | FISSA Fabrica Inter. Salchichas
PARIS | Paris spécialités
```

### Example 4: The NOT IN trap

Employee 5 has no orders, so we expect Buchanan. But the subquery returns the list of `employee_id` values of all orders, and order 10347 has a NULL employee, so the list contains NULL. `employee_id NOT IN (..., NULL)` can never be true, and the result is empty: only the header line appears. There is no error and no warning.

```sql run
SELECT employee_id, last_name
FROM employees
WHERE employee_id NOT IN (SELECT employee_id FROM orders)
ORDER BY employee_id;
```

```output
employee_id | last_name
```

### Example 5: NOT EXISTS gives the right answer

The same question with `NOT EXISTS`. A NULL `employee_id` in `orders` never equals `e.employee_id`, so it does not interfere, and Buchanan is found. Compare this with example 4: the only change is the form of the test.

```sql run
SELECT e.employee_id, e.last_name
FROM employees e
WHERE NOT EXISTS (SELECT 1
                  FROM orders o
                  WHERE o.employee_id = e.employee_id)
ORDER BY e.employee_id;
```

```output
employee_id | last_name
5 | Buchanan
```

### Example 6: Several existence conditions together

Customers who have an order from 1998 on and no order in 1996: one `EXISTS` and one `NOT EXISTS`, joined with `AND`, each with its own correlated subquery. The conditions describe a customer's history, a common shape for "new in the period" or "won back" analyses. The first five of the matches are shown.

```sql run
SELECT c.customer_id, c.company_name
FROM customers c
WHERE EXISTS (SELECT 1
              FROM orders o
              WHERE o.customer_id = c.customer_id
                AND o.order_date >= '1998-01-01')
  AND NOT EXISTS (SELECT 1
                  FROM orders o
                  WHERE o.customer_id = c.customer_id
                    AND o.order_date >= '1996-01-01' AND o.order_date < '1997-01-01')
ORDER BY c.customer_id
LIMIT 5;
```

```output
customer_id | company_name
ANATR | Ana Trujillo Emparedados
BERGS | Berglunds snabbköp
BOLID | Bólido Comidas preparadas
CACTU | Cactus Comidas para llevar
COMMI | Comércio Mineiro
```

## Real-world applications

**Inactive customers and unsold products.** `NOT EXISTS` finds customers with no orders (example 3) or products with no sales, the lists marketing and purchasing ask for. It stays correct when columns contain NULLs.

**Audit and data quality.** Finding rows without a matching partner, such as orders without a customer or lines without a product, is an anti-join. Using `NOT EXISTS` avoids the silent empty result of example 4.

**Customer history and cohorts.** Conditions like "bought this year but not last year" or "bought product A and never product B" (example 6) combine `EXISTS` and `NOT EXISTS`, without joins that would multiply rows.

**Counting entities correctly.** When the question is "how many customers", a semi-join (example 2) avoids the double counting of a join.

## Daily review

### Key takeaways

- `EXISTS (subquery)` is true if the subquery returns a row; `NOT EXISTS` if it returns none. The select list does not matter.
- A semi-join keeps rows with a match and never repeats them; an anti-join keeps rows without a match.
- `NOT IN` returns nothing at all if the list contains a NULL. Use `NOT EXISTS`.
- Three anti-join spellings: `NOT EXISTS`, `LEFT JOIN ... IS NULL`, `EXCEPT`/`NOT IN` on NOT NULL data.
- `EXISTS` conditions combine with `AND`/`OR` like any predicate.

### Common mistakes

- Using `NOT IN (SELECT col FROM t)` where `col` can be NULL and getting an empty result. Use `NOT EXISTS`, or filter `IS NOT NULL` in the subquery.
- Forgetting the correlation in the subquery (`WHERE o.customer_id IS NOT NULL` only). The subquery then does not depend on the outer row, so `EXISTS` is true for all rows or none.
- Joining and counting rows when the question is about distinct entities, which overcounts.
- Believing `SELECT 1` matters. Any select list works.
- Writing `NOT EXISTS` with a join condition that uses the wrong columns, which returns every outer row.
- Testing a nullable column in the anti-join `LEFT JOIN ... WHERE i.some_nullable IS NULL` instead of the key (day 41).

### Revision notes

- `EXISTS`: at least one row; `NOT EXISTS`: no rows; correlated on the key.
- `x NOT IN (..., NULL)` is never true.
- Semi-join: no duplicates; join: duplicates.
- Safe anti-join: `NOT EXISTS`.

## Objectives

- Explain why dimension attributes change over time and what a report should say about the past when they do.
- Describe slowly changing dimension types 1 (overwrite), 2 (new row) and 3 (previous-value column), and say what each loses or keeps.
- Use `valid_from`, `valid_to` and `is_current` correctly, with one clear rule for the end of a validity period.
- Implement type 2 in PostgreSQL SQL (close the current row, insert the new version with a new surrogate key) and in Python on `sqlite3`.
- Look up the dimension row that was valid on a given date, and check that a type 2 load is idempotent.

## Understand

### Attributes change

Day 145 left an open question: what happens when a customer moves from Germany to Spain? The customer dimension holds the country, and the fact table holds sales made while the customer lived in Germany. Whatever the dimension does with the change decides what the report says. If the country is simply overwritten, last year's sales to that customer move to Spain in every report, and the past is rewritten. Dimension attributes change slowly compared with facts (a customer moves rarely, a product changes category occasionally), which is why this topic is called **slowly changing dimensions** (SCD). The design question is per attribute: should history matter?

### The types

**Type 1: overwrite.** The new value replaces the old one in the same row. Nothing else changes. It is the simplest and is right for corrections (a misspelt name) and for attributes where only the current value matters. Its cost is that history is lost: every fact now appears to have been made under the new value, and a report run last month cannot be reproduced.

**Type 2: add a row.** The old row is kept and closed, and a new row with the new values and a **new surrogate key** is inserted. Facts that were loaded earlier still point to the old key and therefore show the old value; facts loaded later point to the new key. This is full history, and it is why surrogate keys exist. Its cost is more rows, a more complex load, and the need to choose the right key when loading a fact.

**Type 3: add a column.** The row holds the current value and one previous value (`previous_country`). It keeps a little history without new rows, but only one step back, and all facts, old and new, join to the same row, so it answers questions like "compare under the old and the new classification" but not "what was true at the time of the sale".

Real dimensions mix the types per column: a customer's `customer_name` correction is type 1, the `country` is type 2.

### Type 2 in detail

A type 2 dimension carries three extra columns. `valid_from` is the date the version became true. `valid_to` is the date it stopped being true, or NULL while it is still current. `is_current` is a flag for the open row, redundant but convenient and fast to filter.

Choose one rule for the end of a period and use it everywhere. This lesson uses a **half-open interval**: a version is valid from `valid_from` **inclusive** to `valid_to` **exclusive**, and the closing date of an old row equals the starting date of the next, so the periods touch and never overlap or leave a gap. The row valid on date `d` satisfies `valid_from <= d AND (valid_to IS NULL OR d < valid_to)`. With this rule, exactly one row of a business key is valid on any date, which is the property to test. The first version of a row gets an early `valid_from` (here the start of the data); the current row has `valid_to IS NULL` and `is_current = true`, and each business key must have exactly one current row.

A type 2 load has two steps for each changed customer. First **close** the current row: `valid_to` becomes the change date and `is_current` becomes false. Second **insert** a new row with a fresh surrogate key, the new attribute values, `valid_from` equal to the change date, `valid_to` NULL and `is_current` true. A brand-new customer needs only the insert. A customer whose tracked attributes did not change needs nothing, which is what makes the load idempotent: running it twice must not create a second version. Compare attributes with `IS DISTINCT FROM` (Day 110), because a plain `<>` treats NULL as unknown and would miss a change from NULL.

### Choosing the key for a fact

When a new fact arrives, it must reference the dimension version that was valid at the time of the event. For facts that are loaded the same day, that is the current row. For late-arriving facts (Day 148) it is the row whose period contains the event date. The lookup is by business key and date, not by business key alone, because a business key now matches several rows.

### Common misconception

Learners believe that type 2 means "keep an audit table somewhere". It is part of the dimension and changes how joins work: the dimension has more rows than the business has customers, so counting customers needs `count(DISTINCT customer_id)` and not `count(*)`. Another misconception is that `is_current` alone is enough: it tells you the latest version, not the version that was valid last March.

### Why it matters

History decides whether last quarter's report can be reproduced next year and whether a regional sales target is judged against the region the customer belonged to at the time. The choice of type is a business decision that the engineer must ask for, per column.

## Syntax and key functions

```sql-syntax
-- type 2: close the current row, then insert the new version
UPDATE dim_customer d SET valid_to = DATE '2026-02-01', is_current = false
FROM changed c WHERE d.customer_id = c.customer_id AND d.is_current;

INSERT INTO dim_customer
SELECT (SELECT max(customer_key) FROM dim_customer) + row_number() OVER (ORDER BY customer_id),
       customer_id, customer_name, country, DATE '2026-02-01', NULL, true
FROM changed;

-- the version valid on a date
SELECT * FROM dim_customer
WHERE customer_id = 'C003' AND valid_from <= DATE '2026-01-20' AND (valid_to IS NULL OR DATE '2026-01-20' < valid_to);
```

| Item | Meaning |
|---|---|
| Type 1 | Overwrite; no history. |
| Type 2 | New row with new surrogate key; full history. |
| Type 3 | `previous_value` column; one step of history. |
| `valid_from` (inclusive), `valid_to` (exclusive, NULL if current) | Half-open validity period. |
| `is_current` | Flag for the open row. |
| `IS DISTINCT FROM` | Null-safe inequality for detecting changes. |
| `count(DISTINCT customer_id)` | Number of customers when the dimension has versions. |

### Example 1: Type 1 rewrites the past

Customer `C003` (key 3) was in Germany and moves to Spain. With a type 1 change the country is overwritten. Every sale of customer 3, including the ones made before the move, is now reported under Spain, and the German total drops.

```sql run

    valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
```

### Example 4: A type 2 load from a staging table

The staging table holds the latest customer data: `C003` has moved to Spain, `C005` is unchanged and `C013` is new. The load finds the changed and new rows with `IS DISTINCT FROM`, closes the current rows of the changed customers and inserts new versions with new surrogate keys. The result lists the versions of the affected customers. The unchanged customer gets no new row.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL,
    valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer,
    product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'),
    (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01', NULL, true FROM generate_series(1, 12) AS i;
INSERT INTO dim_product SELECT i, 'P' || lpad(i::text, 3, '0'), 'Product ' || i,
    (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
CREATE TABLE stg_customer (customer_id text, customer_name text, country text);
INSERT INTO stg_customer VALUES ('C003', 'Customer 03', 'ES'), ('C005', 'Customer 05', 'ES'), ('C013', 'Customer 13', 'FR');
CREATE TABLE changed AS
SELECT s.* FROM stg_customer s LEFT JOIN dim_customer d ON d.customer_id = s.customer_id AND d.is_current
WHERE d.customer_key IS NULL OR d.country IS DISTINCT FROM s.country OR d.customer_name IS DISTINCT FROM s.customer_name;
UPDATE dim_customer d SET valid_to = date '2026-02-01', is_current = false FROM changed c WHERE d.customer_id = c.customer_id AND d.is_current;
INSERT INTO dim_customer
SELECT (SELECT max(customer_key) FROM dim_customer) + row_number() OVER (ORDER BY customer_id),
       customer_id, customer_name, country, date '2026-02-01', NULL, true FROM changed;
SELECT customer_key, customer_id, country, valid_from, valid_to, is_current
FROM dim_customer WHERE customer_id IN ('C003', 'C005', 'C013') ORDER BY customer_id, valid_from;
```

```output
customer_key | customer_id | country | valid_from | valid_to | is_current
3 | C003 | DE | 2026-01-01 | 2026-02-01 | false
13 | C003 | ES | 2026-02-01 | NULL | true
5 | C005 | ES | 2026-01-01 | NULL | true
14 | C013 | FR | 2026-02-01 | NULL | true
```

### Example 5: The same load in Python, and a point-in-time lookup

The Python version runs on `sqlite3`: it closes and inserts versions for changed or new customers. Running it a second time with the same data changes nothing (idempotent). `country_on` returns the country that was valid on a date using the half-open rule.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("""CREATE TABLE dim_customer (customer_key INTEGER PRIMARY KEY, customer_id TEXT, country TEXT,
                valid_from TEXT, valid_to TEXT, is_current INTEGER)""")
conn.execute("INSERT INTO dim_customer VALUES (3, 'C003', 'DE', '2026-01-01', NULL, 1)")

def apply_scd2(conn, incoming, as_of):
    created = 0
    with conn:
        for customer_id, country in incoming:
            row = conn.execute("SELECT customer_key, country FROM dim_customer WHERE customer_id = ? AND is_current = 1", (customer_id,)).fetchone()
            if row and row[1] == country:
                continue
            if row:
                conn.execute("UPDATE dim_customer SET valid_to = ?, is_current = 0 WHERE customer_key = ?", (as_of, row[0]))
            next_key = conn.execute("SELECT COALESCE(MAX(customer_key), 0) + 1 FROM dim_customer").fetchone()[0]
            conn.execute("INSERT INTO dim_customer VALUES (?, ?, ?, ?, NULL, 1)", (next_key, customer_id, country, as_of))
            created += 1
    return created

def country_on(conn, customer_id, day):
    return conn.execute("SELECT country FROM dim_customer WHERE customer_id = ? AND valid_from <= ? AND (valid_to IS NULL OR ? < valid_to)",
                        (customer_id, day, day)).fetchone()[0]

data = [("C003", "ES"), ("C013", "FR")]
print(apply_scd2(conn, data, "2026-02-01"), apply_scd2(conn, data, "2026-02-01"))
print(conn.execute("SELECT customer_key, customer_id, country, valid_from, valid_to, is_current FROM dim_customer ORDER BY customer_key").fetchall())
print(country_on(conn, "C003", "2026-01-31"), country_on(conn, "C003", "2026-02-01"))
print(conn.execute("SELECT COUNT(*), COUNT(DISTINCT customer_id) FROM dim_customer").fetchone())
```

```output
2 0
[(3, 'C003', 'DE', '2026-01-01', '2026-02-01', 0), (4, 'C003', 'ES', '2026-02-01', None, 1), (5, 'C013', 'FR', '2026-02-01', None, 1)]
DE ES
(3, 2)
```

## Real-world applications

- **Regional sales reporting.** Customers move between sales regions; a type 2 country or region keeps each sale in the region that applied then.
- **Price and category history.** Product category changes are tracked so that last year's category report does not change when products are reclassified.
- **Corrections.** A misspelt customer name is a type 1 fix on the current row; it should not create history.
- **Audit and reproducibility.** A report can be re-run for any past date by joining on validity periods.

## Daily review

### Key takeaways

- The type is chosen per attribute: overwrite (1), new row (2), previous column (3).
- Type 2 closes the current row and inserts a new version with a new surrogate key.
- Use half-open periods: `valid_from <= d < valid_to`, `valid_to` NULL for the current row.
- Detect change with `IS DISTINCT FROM`; an unchanged row gets no new version, so reruns are safe.
- The dimension has more rows than customers; count with `COUNT(DISTINCT customer_id)`.

### Common mistakes

- **Overwriting a history-relevant attribute.** Past reports change silently. Ask which type each attribute needs.
- **Overlapping or gapped periods.** Two rows match one date, or none. Close with the next row's start date.
- **Comparing with `<>`.** A change from NULL is missed. Use `IS DISTINCT FROM`.
- **Loading a fact with the business key lookup only.** It matches several versions. Look up by key and date, or take the current row.
- **Counting customers with `count(*)`.** Versions inflate it. Use `COUNT(DISTINCT customer_id)`.

### Revision notes

- Type 1 overwrite, 2 new row, 3 previous column.
- `valid_from` inclusive, `valid_to` exclusive; one current row per key.
- Close, then insert; unchanged means no new row.
- Point-in-time: `valid_from <= d AND (valid_to IS NULL OR d < valid_to)`.

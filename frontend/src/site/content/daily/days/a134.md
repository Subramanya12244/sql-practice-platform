## Objectives

- Lay out a report page on a grid so that visuals are aligned, do not overlap and stay on the canvas.
- Use size, position and colour to give a page a clear visual hierarchy and reading order.
- Describe a Power BI theme file and check text and background colours against a contrast threshold.
- Plan a phone layout by stacking visuals in reading order.
- Check a page layout against a written checklist with a Python function.

## Understand

### The canvas and the grid

A report page in Power BI Desktop is a fixed **canvas**. The default size is 1280 by 720 pixels, a 16:9 shape that fits a screen or a slide. Every visual is a rectangle with a position (x and y from the top left corner) and a size (width and height). A **layout grid** is a set of invisible rules that decide the allowed positions: for example a grid of 40 pixel squares with a 40 pixel margin around the page. When every rectangle starts and ends on a grid line, edges line up, gaps are equal and the page looks calm without any other effort. Desktop helps with this: the View tab offers Show gridlines and Snap to grid, and the Format pane has exact x, y, width and height fields, so alignment can be set by number rather than by eye. The Format menu also has Align and Distribute commands.

Three alignment mistakes show up in nearly every first report. Visuals that overlap by a few pixels hide a border or a title. Visuals that are almost, but not quite, aligned look like an error rather than a choice. And visuals that hang over the page edge are cut off in some views and in print or PDF export. Each of these can be tested by a rule, which is how the exercises of this lesson work.

### Visual hierarchy and reading order

**Visual hierarchy** means the reader's eye is led through the page in a deliberate order: the main message first, then support, then detail. Four tools control it. **Position**: in left-to-right languages, readers start at the top left, so the headline number or the title belongs there. **Size**: the biggest visual is read as the most important, so the key trend should take the most area, and a minor table should not. **Contrast and colour**: one strong colour on one mark pulls the eye, and if five things are bright, none stands out. **Grouping**: related visuals placed together with equal spacing read as a unit, and a clear gap separates a different topic. A useful test is the five-second test: show the page for five seconds and ask what the person remembers. If the answer is not the page's main message, the hierarchy is wrong.

A page usually follows a simple pattern: a row of KPI cards on the top, a large trend or main comparison below, and supporting breakdowns or a table at the bottom or the side, with slicers in a consistent strip at the top or left (Day 133). Fewer visuals are almost always better: a common working limit is about six to eight per page, with more detail moved to drill-through pages.

### Themes

A **theme** is a set of colours and text defaults applied to the whole report, so that visuals are consistent without formatting each one. It is stored as a JSON file that Desktop imports from View, Themes, Browse for themes. A small theme has a name, a list of data colours that charts use in order, and a few named colours:

```json
{
  "name": "Course theme",
  "dataColors": ["#0B3D91", "#118DFF", "#F2C811", "#6B007B"],
  "background": "#FFFFFF",
  "foreground": "#333333",
  "tableAccent": "#0B3D91"
}
```

Themes keep colour meaning stable: if blue is Hardware on one page, it is Hardware on every page. They also hold the accessibility risk. Colour choices must keep enough **contrast** between text and its background. The Web Content Accessibility Guidelines (WCAG) define a **contrast ratio** from 1 (identical) to 21 (black on white) and ask for at least 4.5 for normal text. Light yellow text on white fails clearly; a mid grey (#777777) on white is just under the threshold. Do not rely on colour alone to carry meaning, since many readers cannot tell red from green: add labels, icons or position.

### Mobile layout

Power BI Desktop has a **phone layout** view (View, Mobile layout) where the author arranges a tall, narrow version of the same page. Visuals are dragged from a list of the page's visuals onto the phone canvas. Nothing is copied: the phone page shows the same visuals, so every measure and filter is shared, but only those placed in the phone layout are shown on the phone. The planning rule is to stack visuals in reading order, in one column, with the key cards first and large tables left out or replaced by a smaller chart. Because the page scrolls vertically on a phone, the length of the scroll is a design budget.

### Why it matters

Layout decides whether a correct report is used. A page that is crowded, misaligned or hard to read makes people distrust the numbers and ask for a spreadsheet instead. The misconception is that design is decoration added at the end. A layout rule that can be tested, such as no overlap, on the grid, the key card first, contrast of at least 4.5 and no more than eight visuals, is part of quality assurance in the same way as a reconciliation of totals.

## Syntax and key functions

There is no formula syntax here: layout is set in the Format pane (Position, Size) and in View, Themes. The reference lists the settings used on this day.

| Setting | Meaning |
|---|---|
| Page size | The canvas, default 1280 by 720 (16:9). |
| Show gridlines, Snap to grid | Visual aids that keep edges on grid lines. |
| Position and size (x, y, width, height) | Exact rectangle of one visual, in pixels. |
| Align, Distribute | Commands that line up selected visuals and equalise gaps. |
| Theme (JSON) | Data colours, background, foreground and defaults for the report. |
| Mobile layout | A separate phone arrangement of the same page's visuals. |

## Learn by example

### Example 1: A layout checker

A page is a list of rectangles. The checker applies the course rules: on the canvas, on the 40 pixel grid, no overlaps, at most eight visuals, and a card in the top left.

```python run
CANVAS_W, CANVAS_H, GRID = 1280, 720, 40

def overlaps(a, b):
    return (a["x"] < b["x"] + b["w"] and b["x"] < a["x"] + a["w"]
            and a["y"] < b["y"] + b["h"] and b["y"] < a["y"] + a["h"])

def check_layout(visuals):
    problems = []
    for v in visuals:
        if v["x"] < 0 or v["y"] < 0 or v["x"] + v["w"] > CANVAS_W or v["y"] + v["h"] > CANVAS_H:
            problems.append(f"{v['name']}: off canvas")
        if any(v[k] % GRID for k in ("x", "y", "w", "h")):
            problems.append(f"{v['name']}: not on grid")
    for i, a in enumerate(visuals):
        for b in visuals[i + 1:]:
            if overlaps(a, b):
                problems.append(f"{a['name']} overlaps {b['name']}")
    if len(visuals) > 8:
        problems.append("more than 8 visuals")
    first = min(visuals, key=lambda v: (v["y"], v["x"]))
    if first["type"] != "card":
        problems.append(f"top-left visual is a {first['type']}, not a card")
    return problems

bad = [
    {"name": "trend", "type": "line", "x": 30, "y": 20, "w": 800, "h": 400},
    {"name": "by_category", "type": "bar", "x": 800, "y": 20, "w": 440, "h": 400},
    {"name": "revenue_card", "type": "card", "x": 40, "y": 440, "w": 360, "h": 120},
    {"name": "detail", "type": "table", "x": 40, "y": 600, "w": 1240, "h": 200},
]
for p in check_layout(bad):
    print(p)
```

```output
trend: not on grid
by_category: not on grid
detail: off canvas
trend overlaps by_category
top-left visual is a line, not a card
```

The bad page has five problems: the trend starts at x = 30 and y = 20 and the bar chart at y = 20, so neither is on the 40 pixel grid; the trend overlaps the bar chart (it ends at x = 830 and the bar starts at 800); the table runs past the bottom edge (600 + 200 = 800 is more than 720); and the top-left visual is the trend rather than a card. The checker lists each one with the visual's name, so a reviewer knows what to move.

### Example 2: The fixed layout

Rearrange the same visuals on the grid: cards across the top, the trend large, the breakdown beside it.

```python run
CANVAS_W, CANVAS_H, GRID = 1280, 720, 40

def overlaps(a, b):
    return (a["x"] < b["x"] + b["w"] and b["x"] < a["x"] + a["w"]
            and a["y"] < b["y"] + b["h"] and b["y"] < a["y"] + a["h"])

def check_layout(visuals):
    problems = []
    for v in visuals:
        if v["x"] < 0 or v["y"] < 0 or v["x"] + v["w"] > CANVAS_W or v["y"] + v["h"] > CANVAS_H:
            problems.append(f"{v['name']}: off canvas")
        if any(v[k] % GRID for k in ("x", "y", "w", "h")):
            problems.append(f"{v['name']}: not on grid")
    for i, a in enumerate(visuals):
        for b in visuals[i + 1:]:
            if overlaps(a, b):
                problems.append(f"{a['name']} overlaps {b['name']}")
    if len(visuals) > 8:
        problems.append("more than 8 visuals")
    first = min(visuals, key=lambda v: (v["y"], v["x"]))
    if first["type"] != "card":
        problems.append(f"top-left visual is a {first['type']}, not a card")
    return problems

good = [
    {"name": "revenue_card", "type": "card", "x": 40, "y": 40, "w": 360, "h": 120},
    {"name": "orders_card", "type": "card", "x": 440, "y": 40, "w": 360, "h": 120},
    {"name": "aov_card", "type": "card", "x": 840, "y": 40, "w": 360, "h": 120},
    {"name": "trend", "type": "line", "x": 40, "y": 200, "w": 760, "h": 480},
    {"name": "by_category", "type": "bar", "x": 840, "y": 200, "w": 360, "h": 480},
]
print(check_layout(good))
total = CANVAS_W * CANVAS_H
for v in sorted(good, key=lambda v: -v["w"] * v["h"]):
    print(f"{v['name']}: {v['w'] * v['h'] / total:.1%}")
```

```output
[]
trend: 39.6%
by_category: 18.8%
revenue_card: 4.7%
orders_card: 4.7%
aov_card: 4.7%
```

The empty list means that every rule passes. The area shares show the hierarchy: the trend takes 39.6% of the canvas, the largest share, so it reads as the main message; the cards and the breakdown follow. If a small table took the largest share, the hierarchy would contradict the purpose.

### Example 3: A theme and its contrast

Compute the WCAG contrast ratio to test the colours in a theme.

```python run
def luminance(hex_colour):
    h = hex_colour.lstrip("#")
    parts = []
    for i in (0, 2, 4):
        c = int(h[i:i + 2], 16) / 255
        parts.append(c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4)
    return 0.2126 * parts[0] + 0.7152 * parts[1] + 0.0722 * parts[2]

def contrast(a, b):
    hi, lo = sorted([luminance(a), luminance(b)], reverse=True)
    return (hi + 0.05) / (lo + 0.05)

pairs = [("#000000", "#FFFFFF"), ("#777777", "#FFFFFF"), ("#0B3D91", "#FFFFFF"), ("#F2C811", "#FFFFFF"), ("#333333", "#F5F5F5")]
for fg, bg in pairs:
    ratio = contrast(fg, bg)
    print(fg, bg, round(ratio, 2), "pass" if ratio >= 4.5 else "fail")
```

```output
#000000 #FFFFFF 21.0 pass
#777777 #FFFFFF 4.48 fail
#0B3D91 #FFFFFF 10.04 pass
#F2C811 #FFFFFF 1.61 fail
#333333 #F5F5F5 11.59 pass
```

Black on white is 21. The mid grey #777777 reaches 4.48, just under 4.5, so it fails the normal-text threshold by a hair; a darker grey such as #333333 passes easily. The yellow #F2C811 reaches only 1.61 on white, so it fails as text and is weak even as a mark against a white background; a theme can use it for large marks on a darker panel and must use a dark colour for text.

### Example 4: Reading order and the phone layout

Stack the fixed layout's visuals in reading order (top to bottom, then left to right), with a fixed height per type, to plan the phone page.

```python run
good = [
    {"name": "revenue_card", "type": "card", "x": 40, "y": 40},
    {"name": "orders_card", "type": "card", "x": 440, "y": 40},
    {"name": "aov_card", "type": "card", "x": 840, "y": 40},
    {"name": "trend", "type": "line", "x": 40, "y": 200},
    {"name": "by_category", "type": "bar", "x": 840, "y": 200},
]
phone_height = {"card": 80, "line": 220, "bar": 220, "table": 260}

order = sorted(good, key=lambda v: (v["y"], v["x"]))
top = 0
for v in order:
    print(f"{top:>4} {v['name']} ({v['type']}, {phone_height[v['type']]})")
    top += phone_height[v["type"]]
print("scroll length", top)
```

```output
   0 revenue_card (card, 80)
  80 orders_card (card, 80)
 160 aov_card (card, 80)
 240 trend (line, 220)
 460 by_category (bar, 220)
scroll length 680
```

The phone page lists the cards first, then the trend, then the breakdown, in the same order the desktop page is read. The scroll length is 680 in these course units (they are not Power BI pixels; they only compare designs). Dropping the breakdown would shorten the scroll to 460. Which visuals to keep on the phone is an editorial choice.

## Real-world applications

- **Design review before release.** A checklist function like `check_layout` run on a page specification catches overlap and off-grid visuals before a stakeholder does (Examples 1 and 2).
- **Brand and accessibility compliance.** Contrast checks on a company theme show which brand colours may be used for text and which only for marks (Example 3).
- **Executive and field versions.** A desktop page for a meeting and a phone layout for managers on the road share the same model and measures (Example 4).
- **Template pages.** A team fixes one grid and one card row for every report so that dashboards from different analysts look alike.

## Daily review

### Key takeaways

- A page is a canvas of rectangles; a grid keeps edges aligned and gaps equal.
- Hierarchy comes from position, size, colour and grouping; the main message gets top-left and the largest area.
- A theme is JSON with data colours and defaults; check text contrast (4.5 or more for normal text).
- The phone layout reuses the page's visuals in a single column; keep only the essential ones.
- Layout rules that can be tested should be tested.

### Common mistakes

- Placing visuals by eye so that edges are one or two pixels off and overlaps hide borders. Use the position fields and snap to grid.
- Making every visual the same size and colour, so that nothing leads. Choose one primary visual.
- Using light data colours for text or small labels; check contrast and use dark text.
- Using red and green alone to show good and bad. Add a sign, an icon or a label.
- Assuming the phone layout happens automatically: a page without a phone layout shows the desktop page scaled down.

### Revision notes

- Canvas 1280 by 720; grid 40; margin 40.
- Hierarchy: position, size, colour, grouping; five-second test.
- Theme JSON: name, dataColors, background, foreground, tableAccent.
- Contrast ratio at least 4.5 for text; do not rely on colour alone.
- Phone layout: same visuals, one column, reading order.

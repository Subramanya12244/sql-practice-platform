## Understand

### From a response to a table

Day 163 ended with a Python list of records fetched from an API. A list of dictionaries is not yet analysis-ready: the amounts are in cents, the timestamps are text, some records have extra or missing fields, and the interesting data may sit inside nested objects. Today's route is **JSON, then DataFrame, then report**. Each step has a different risk. Parsing can fail on malformed text. Shaping can silently produce missing values or lose records. Reporting can state numbers that no one can trace back. The aim is to make each of these visible.

### JSON and its Python types

**JSON** (JavaScript Object Notation) is text with six building blocks: objects `{"a": 1}`, arrays `[1, 2]`, strings, numbers, `true`/`false` and `null`. `json.loads(text)` turns the text into Python objects: an object becomes a `dict`, an array a `list`, `true` and `false` become `True` and `False`, `null` becomes `None`, and numbers become `int` or `float`. With `requests`, `response.json()` does the same. There is **no date type in JSON**: a timestamp such as `"2025-01-05T10:15:00Z"` arrives as a plain string and must be converted. There is also no exact decimal type, which is why many APIs send money as integer **cents** (`amount_cents: 12050`) to avoid floating-point rounding. Keep the integer cents in the data and convert to euros only for display, or divide by 100 once, deliberately.

A common source of silent errors is that JSON records are not forced to have the same keys. One record may lack `currency`; another may have `"country": null`. Both end up as missing values in a DataFrame, and a calculation that includes them may quietly skip them. Check for required keys before analysing, and count the records that fail.

### Records to a DataFrame

When the records are flat (every value is a number, string or null), `pd.DataFrame(records)` or `pd.json_normalize(records)` builds the table: one row per record, one column per key, and a missing key becomes `NaN`. Then you type the columns, as on Day 160: integers for amounts, `pd.to_datetime(..., utc=True)` for timestamps (UTC is the usual API convention, marked by the `Z`), and a fixed list of expected values for statuses. An important rule: write the **schema check** as code (the set of required columns, and the allowed statuses) so that a change in the API shows up as an error at the top of the job and not as a strange number in a report.

### Nested data: objects and arrays

Real payloads nest. A **nested object** is a dictionary inside a record (`customer: {id, name, country}`). **Flattening** it gives one column for each inner key with a combined name; `pd.json_normalize(records, sep="_")` produces `customer_id`, `customer_name` and `customer_country`. A **nested array** is a list inside a record (`items: [{sku, qty, ...}, ...]`) and cannot become one cell sensibly because one order has several lines. The right move is a second table: one row per line item, with the order's id repeated so that the lines can be joined back. `pd.json_normalize(records, record_path="items", meta=["order_id"])` does exactly this: `record_path` names the array to unpack, and `meta` names the parent fields to carry onto each line. Two consequences matter. An order whose array is **empty** produces no line rows, so it vanishes from the line table; if you count orders from the lines you lose it. And the lines are a different **grain** from the orders (Day 159): adding order totals onto line rows and summing would count each order once per line, the fan-out from Day 159.

### Reconciling the pieces

Nested payloads often carry the same fact twice: an order total and the lines that should add up to it. Compare them. The sum of `qty * unit_price_cents` per order against `amount_cents` is a source-to-target check (Day 162) inside one response, and a mismatch is either a data problem or something you do not model, such as shipping or a discount. Either way you want to know the number of orders and the amount involved before it reaches a report.

### Reports that can be traced

A report from API data is a small set of aggregates with an explicit definition: revenue counts only `paid` orders, the refund rate is refunded orders divided by paid plus refunded, the day is the UTC date. Write the definitions next to the numbers. Also keep the **raw payload** (the JSON as received, saved to a file or a JSON column) alongside the cleaned table: when a figure is questioned you can re-derive it from what the API actually said, and when your parsing code has a bug you can fix and rerun without calling the API again (and without waiting for rate limits). In PostgreSQL the `jsonb` type stores a JSON document in a column, and `payload->>'status'` extracts a field as text, so analysis can start inside the database when the raw documents have already been loaded.

### Why it matters, and the misconception

An analyst who treats JSON as "like a CSV" loses data in three ways: nested arrays flattened to strings, records with missing keys turned into `NaN` and ignored, and amounts parsed as floats. The misconception is that `pd.DataFrame(records)` always gives a usable table. It gives a table; whether it is usable depends on the checks you add.

## Syntax and key functions

```python
import json
import pandas as pd

records = json.loads(text)["data"]
flat = pd.json_normalize(records, sep="_")                                   # nested objects become columns
lines = pd.json_normalize(records, record_path="items", meta=["order_id"])   # one row per array element
flat["created_at"] = pd.to_datetime(flat["created_at"], utc=True)
```

```sql-syntax
SELECT payload->>'status' AS status,
       (payload->>'amount_cents')::integer AS amount_cents
FROM <table_with_a_jsonb_column>;
```

| Function | Returns or does |
|---|---|
| `json.loads(text)` / `json.dumps(obj, sort_keys=True)` | Parse JSON text / write a Python object as JSON text. |
| `pd.DataFrame(records)` | Table from a list of flat dictionaries. |
| `pd.json_normalize(records, sep, record_path, meta)` | Flattened table; array unpacking with `record_path`; parent fields with `meta`. |
| `pd.to_datetime(s, utc=True)` | Timezone-aware datetimes from ISO text. |
| `df.dt.date`, `df.dt.strftime(fmt)` | Date part, or formatted text. |
| `df.groupby(key).agg(name=(col, func))` | Named aggregates. |
| `payload->>'key'`, `payload->'key'` | PostgreSQL: field as text / as jsonb. |

## Learn by example

All Python examples use canned JSON, the kind of payload an API call such as the one on Day 163 would return; no network is involved. The orders have `order_id`, `customer_id`, `amount_cents`, `currency`, `status` and `created_at`, as in the Orders API of Day 163.

### Example 1: JSON text to Python objects

A response body is text. `json.loads` converts it, and the Python types show what each JSON value became: `null` is `None`, numbers keep their kind, and the timestamp is still a string.

```python run
import json

text = '{"data": [{"order_id": 1001, "amount_cents": 12050, "discount": null, "paid": true, "created_at": "2025-01-05T10:15:00Z"}], "page": 1, "total_pages": 3}'
body = json.loads(text)
rec = body["data"][0]
print({k: type(v).__name__ for k, v in rec.items()})
print("discount is None:", rec["discount"] is None)
print("timestamp is a string:", isinstance(rec["created_at"], str))
print(json.dumps(rec, sort_keys=True))
try:
    json.loads('{"data": [1, 2,]}')
except json.JSONDecodeError as e:
    print("malformed JSON:", type(e).__name__)
```

```output
{'order_id': 'int', 'amount_cents': 'int', 'discount': 'NoneType', 'paid': 'bool', 'created_at': 'str'}
discount is None: True
timestamp is a string: True
{"amount_cents": 12050, "created_at": "2025-01-05T10:15:00Z", "discount": null, "order_id": 1001, "paid": true}
malformed JSON: JSONDecodeError
```

Malformed JSON raises `JSONDecodeError`, so a job should catch it and report the page that failed rather than die silently. `sort_keys=True` makes the written JSON stable between runs.

### Example 2: Flat records to a typed DataFrame with a schema check

Twelve order records become a DataFrame. A check lists missing required columns and unexpected statuses before any analysis. Amounts stay in cents, a euro column is added once, and timestamps become datetimes in UTC.

```python run
import pandas as pd

orders = [
    {"order_id": 1000 + i, "customer_id": 1 + (i * 7) % 5, "amount_cents": 1000 + (i * 137) % 9000,
     "currency": "EUR", "status": {3: "failed", 7: "refunded"}.get(i % 10, "paid"),
     "created_at": f"2025-01-{1 + i % 4:02d}T{8 + i % 6:02d}:30:00Z"}
    for i in range(12)
]
del orders[5]["currency"]                     # one record misses a field

REQUIRED = {"order_id", "customer_id", "amount_cents", "currency", "status", "created_at"}
ALLOWED = {"paid", "refunded", "failed"}

df = pd.json_normalize(orders)
print("missing columns:", sorted(REQUIRED - set(df.columns)))
print("records with a missing value:", int(df[sorted(REQUIRED)].isna().any(axis=1).sum()))
print("unexpected statuses:", sorted(set(df["status"]) - ALLOWED))

df["created_at"] = pd.to_datetime(df["created_at"], utc=True)
df["amount_eur"] = df["amount_cents"] / 100
print(df[["order_id", "amount_cents", "amount_eur", "status", "created_at"]].head(3).to_string(index=False))
print(df["created_at"].dt.tz, "| currency missing:", int(df["currency"].isna().sum()))
```

```output
missing columns: []
records with a missing value: 1
unexpected statuses: []
 order_id  amount_cents  amount_eur status                created_at
     1000          1000       10.00   paid 2025-01-01 08:30:00+00:00
     1001          1137       11.37   paid 2025-01-02 09:30:00+00:00
     1002          1274       12.74   paid 2025-01-03 10:30:00+00:00
UTC | currency missing: 1
```

The schema holds, but one record has no currency, and the `NaN` it created would be skipped by many calculations. The count makes it visible. Whether to drop, fill or reject such a record is a decision for the owner of the data, not for the parser.

### Example 3: Nested objects with `json_normalize`

The `customer` object in each record becomes three columns. A customer with `"country": null` gives a missing value, and the `items` array stays as a list in a single column, which the next example unpacks.

```python run
import pandas as pd

payload = {"data": [
    {"order_id": 1001, "created_at": "2025-01-05T10:15:00Z", "amount_cents": 7050,
     "customer": {"id": 7, "name": "Ana Silva", "country": "DE"},
     "items": [{"sku": "A1", "qty": 2, "unit_price_cents": 1500}, {"sku": "B2", "qty": 1, "unit_price_cents": 4050}]},
    {"order_id": 1002, "created_at": "2025-01-06T09:00:00Z", "amount_cents": 1500,
     "customer": {"id": 9, "name": "Ben Okafor", "country": None},
     "items": [{"sku": "A1", "qty": 1, "unit_price_cents": 1500}]},
    {"order_id": 1003, "created_at": "2025-01-06T11:45:00Z", "amount_cents": 0,
     "customer": {"id": 7, "name": "Ana Silva", "country": "DE"}, "items": []},
    {"order_id": 1004, "created_at": "2025-01-07T16:20:00Z", "amount_cents": 2999,
     "customer": {"id": 12, "name": "Cy Tran", "country": "FR"},
     "items": [{"sku": "C3", "qty": 3, "unit_price_cents": 999}]},
]}
orders = pd.json_normalize(payload["data"], sep="_")
print(sorted(orders.columns))
print(orders[["order_id", "customer_id", "customer_name", "customer_country"]].to_string(index=False))
print("items cell type:", type(orders.loc[0, "items"]).__name__)
```

```output
['amount_cents', 'created_at', 'customer_country', 'customer_id', 'customer_name', 'items', 'order_id']
 order_id  customer_id customer_name customer_country
     1001            7     Ana Silva               DE
     1002            9    Ben Okafor             None
     1003            7     Ana Silva               DE
     1004           12       Cy Tran               FR
items cell type: list
```

The names are joined with the separator, so `customer.name` became `customer_name`. The `items` column holds Python lists: it is not yet usable for analysis.

### Example 4: Unpack the array, then reconcile with the totals

`record_path="items"` produces one row per line item, and `meta` carries the order id onto every line. The line table has a different grain from the orders table. Summing the lines per order and comparing with `amount_cents` is a check inside the payload.

```python run
import pandas as pd

data = [
    {"order_id": 1001, "amount_cents": 7050, "items": [{"sku": "A1", "qty": 2, "unit_price_cents": 1500}, {"sku": "B2", "qty": 1, "unit_price_cents": 4050}]},
    {"order_id": 1002, "amount_cents": 1500, "items": [{"sku": "A1", "qty": 1, "unit_price_cents": 1500}]},
    {"order_id": 1003, "amount_cents": 0, "items": []},
    {"order_id": 1004, "amount_cents": 2999, "items": [{"sku": "C3", "qty": 3, "unit_price_cents": 999}]},
]
orders = pd.json_normalize(data).drop(columns="items")
lines = pd.json_normalize(data, record_path="items", meta=["order_id"])
print("orders:", len(orders), "| orders with lines:", lines["order_id"].nunique())

lines["line_cents"] = lines["qty"] * lines["unit_price_cents"]
by_order = lines.groupby("order_id", as_index=False).agg(lines_cents=("line_cents", "sum"))
check = orders.merge(by_order, on="order_id", how="left").fillna({"lines_cents": 0})
check["lines_cents"] = check["lines_cents"].astype("int64")
check["difference"] = check["amount_cents"] - check["lines_cents"]
print(check.to_string(index=False))
print("orders that do not match:", check.loc[check["difference"] != 0, "order_id"].tolist())
```

```output
orders: 4 | orders with lines: 3
order_id  amount_cents  lines_cents  difference
    1001          7050         7050           0
    1002          1500         1500           0
    1003             0            0           0
    1004          2999         2997           2
orders that do not match: [1004]
```

Order 1003 has no lines, so a left merge from the orders (and `fillna`) keeps it; counting orders from the line table would have lost it. Order 1004 is 2 cents off: three items at 9.99 give 29.97, the payload says 29.99. Whether that is shipping rounding or an error is a question for the provider, and the report now has a number to ask about.

### Example 5: A traceable report

From twelve flat orders the report computes revenue per day from paid orders only, the count of each status, the refund rate and the top customers by paid revenue. Definitions are printed beside the numbers.

```python run
import pandas as pd

orders = [
    {"order_id": 1000 + i, "customer_id": 1 + (i * 7) % 5, "amount_cents": 1000 + (i * 137) % 9000,
     "status": {3: "failed", 7: "refunded"}.get(i % 10, "paid"), "created_at": f"2025-01-{1 + i % 4:02d}T{8 + i % 6:02d}:30:00Z"}
    for i in range(12)
]
df = pd.json_normalize(orders)
df["created_at"] = pd.to_datetime(df["created_at"], utc=True)
df["day"] = df["created_at"].dt.strftime("%Y-%m-%d")
df["amount_eur"] = df["amount_cents"] / 100

paid = df[df["status"] == "paid"]
daily = paid.groupby("day", as_index=False).agg(orders=("order_id", "count"), revenue_eur=("amount_eur", "sum"))
counts = df["status"].value_counts().sort_index()
refund_rate = counts.get("refunded", 0) / (counts.get("paid", 0) + counts.get("refunded", 0))
top = paid.groupby("customer_id", as_index=False).agg(revenue_eur=("amount_eur", "sum")).sort_values(["revenue_eur", "customer_id"], ascending=[False, True], kind="stable").head(3)

print("Revenue = sum of paid orders, by UTC day")
print(daily.round(2).to_string(index=False))
print("Status counts:", counts.to_dict())
print(f"Refund rate = refunded / (paid + refunded) = {refund_rate:.1%}")
print("Top customers by paid revenue:")
print(top.round(2).to_string(index=False))
```

```output
Revenue = sum of paid orders, by UTC day
       day  orders  revenue_eur
2025-01-01       3        46.44
2025-01-02       3        50.55
2025-01-03       3        54.66
2025-01-04       1        25.07
Status counts: {'failed': 1, 'paid': 10, 'refunded': 1}
Refund rate = refunded / (paid + refunded) = 9.1%
Top customers by paid revenue:
 customer_id  revenue_eur
           3        54.66
           1        50.55
           4        37.81
```

Every number comes with its definition, so a reader can reproduce it. The status counts add up to the 12 records, a quick check that nothing was dropped.

### Example 6: JSON inside PostgreSQL

When the raw documents are loaded into a `jsonb` column, `->>` extracts a field as text and a cast gives it a type, so aggregation can run in the database. This block uses the PostgreSQL-compatible browser database; the table is created in the block.

```sql run
DROP TABLE IF EXISTS api_raw_orders;
CREATE TABLE api_raw_orders (id serial PRIMARY KEY, payload jsonb NOT NULL);
INSERT INTO api_raw_orders (payload) VALUES
  ('{"order_id": 1001, "status": "paid", "amount_cents": 12050, "customer": {"name": "Ana Silva"}}'),
  ('{"order_id": 1002, "status": "refunded", "amount_cents": 3000, "customer": {"name": "Ben Okafor"}}'),
  ('{"order_id": 1003, "status": "paid", "amount_cents": 4500, "customer": {"name": "Ana Silva"}}');
SELECT payload->'customer'->>'name' AS customer,
       COUNT(*) AS orders,
       SUM((payload->>'amount_cents')::integer) AS cents
FROM api_raw_orders
WHERE payload->>'status' = 'paid'
GROUP BY 1
ORDER BY 1;
```

```output
customer | orders | cents
Ana Silva | 2 | 16550
```

`->` returns a JSON value and `->>` returns text; chain them for nested fields and cast before doing arithmetic. Keeping the raw `jsonb` next to cleaned tables lets you fix a parsing mistake without calling the API again.

## Real-world applications

- **Payment or ad-platform reports**: pages of JSON are fetched (Day 163), flattened into an orders table, typed and summarised into daily revenue and refund-rate reports (Examples 2 and 5).
- **Nested e-commerce data**: orders with line items become two tables, orders and lines, and the totals check (Example 4) finds orders that disagree with their lines before finance does.
- **Schema drift detection**: the required-column and allowed-status checks of Example 2 stop a job when the provider renames a field or adds a status.
- **Raw storage for audit**: the raw payload is saved in a `jsonb` column and queried with `->>` (Example 6), so any published number can be re-derived.

## Daily review

### Key takeaways

- `json.loads` gives dicts, lists, `None` and numbers; JSON has no date type and no exact decimals, so convert timestamps and keep money in integer cents.
- `pd.json_normalize` flattens nested objects (`sep`) and unpacks arrays into a second table (`record_path`, `meta`).
- An empty array yields no rows; reconcile line sums with order totals and count orders from the order table.
- Check required columns, allowed values and missing counts in code before analysing.
- Write the definition beside every reported number, and keep the raw payload.
- In PostgreSQL, `payload->>'key'` with a cast reads a field from `jsonb`.

### Common mistakes

- Leaving `items` as a column of lists. Sums and group-bys on it fail or give nonsense; unpack it with `record_path`.
- Counting orders from the line table. Orders without lines disappear; count from the orders table and left-merge the line totals.
- Summing order totals after merging them onto line rows. Each order is counted once per line (fan-out); aggregate the lines first.
- Treating `NaN` as zero without looking. Missing fields hide as skipped values; count them and decide explicitly.
- Parsing timestamps without `utc=True`. Naive and aware times cannot be compared, and day boundaries shift; state the time zone.
- Using `float` division on cents and printing without rounding. Output such as `120.50000000000001` appears in reports; round when formatting.

### Revision notes

- `json.loads(text)["data"]` then `pd.json_normalize(records, sep="_")`.
- Arrays: `record_path="items"`, `meta=["order_id"]`; empty arrays give no rows.
- `pd.to_datetime(s, utc=True)`; money in cents, divide once.
- Schema check: required columns, allowed statuses, missing counts.
- PostgreSQL: `->` JSON, `->>` text, cast before arithmetic.

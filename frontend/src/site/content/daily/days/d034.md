## Objectives

- Sort results with `ORDER BY` on one or several columns, in ascending or descending direction, and by an alias or an expression.
- Add a tie-breaker column so that a sorted result is always in the same, fully determined order.
- Keep a number of rows with `LIMIT`, and page through a result with `OFFSET`.
- Remove duplicate rows with `DISTINCT`, on a single column and on a combination of columns.
- Predict where NULL values appear in a sorted result and control it with `NULLS FIRST` and `NULLS LAST`.

## Understand

### A result has no order unless you ask for one

On day 31 you learned that a table is an unordered set of rows. The same is true of a query result: unless the query contains `ORDER BY`, PostgreSQL may return the rows in any order, and the order can change between runs, after an update, or on a different server. Any query where the order matters, such as "the five most expensive products" or "page 2 of the customer list", must contain `ORDER BY`.

In the logical order of work, sorting is one of the last steps. The database finds rows (`FROM`), filters them (`WHERE`), computes the output columns (`SELECT`), removes duplicates (`DISTINCT`), sorts (`ORDER BY`) and finally cuts the result down (`LIMIT`/`OFFSET`). Because sorting happens after `SELECT`, `ORDER BY` can use the aliases you created in the select list, something `WHERE` cannot do.

### ORDER BY: direction and several columns

`ORDER BY column` sorts ascending (smallest first, A to Z, oldest date first). Add `DESC` for descending. You may sort by several columns separated by commas. The database sorts by the first one, and the later columns are used only to order rows that are tied on the earlier columns. So `ORDER BY country, city` lists countries alphabetically, and inside each country, cities alphabetically. Each column has its own direction: `ORDER BY unit_price DESC, product_name` means highest price first, and alphabetical by name among equal prices.

You can sort by any expression (`ORDER BY unit_price * units_in_stock DESC`), by an alias from the select list, or by the position of a select-list column (`ORDER BY 2`). Positions are fine for quick exploration but fragile in saved queries, because inserting a column silently changes the sort.

### Ties and deterministic results

If two rows have the same sort key, the database may order them either way, and it is not required to do so consistently. This causes real bugs: a "top 5" list can change from one run to the next, and paging can show the same row twice or skip one. The cure is a **tie-breaker**: end the `ORDER BY` with a column that is unique, usually the primary key, for example `ORDER BY unit_price DESC, product_id`. A sort that ends in a unique column is called **deterministic**. All the examples in this course end their sorts in a unique key for this reason.

A note on text: how text is ordered (upper and lower case, accented letters, punctuation) depends on the database's **collation**, a set of language rules. Two databases can order the same names slightly differently. When the order of text really matters, sort on a key as well, and do not assume that your local result matches another server's.

### LIMIT and OFFSET

`LIMIT n` keeps only the first `n` rows of the already sorted result. `OFFSET m` skips the first `m` rows before counting. Together they give simple paging: with a page size of 5, page 1 is `LIMIT 5 OFFSET 0`, page 2 is `LIMIT 5 OFFSET 5`, page 3 is `LIMIT 5 OFFSET 10`, and in general `OFFSET (page - 1) * size`. `LIMIT` without `ORDER BY` returns some rows, but not a meaningful "first" rows. `LIMIT` is PostgreSQL syntax shared by MySQL and SQLite; standard SQL spells it `FETCH FIRST n ROWS ONLY`, and SQL Server uses `TOP n`. Large offsets get slower, because the database still has to produce and throw away the skipped rows.

### DISTINCT: one copy of each row

`SELECT DISTINCT` removes duplicate rows from the result. A row is a duplicate when **every selected column** is equal to that of another row. So `SELECT DISTINCT country FROM customers` lists each country once, while `SELECT DISTINCT country, city` lists each country-and-city combination once. The columns you select define what "the same" means. `DISTINCT` is applied to the whole row, not to the first column; writing `DISTINCT(country), city` does not change that.

For `DISTINCT`, two NULLs count as the same value. So `SELECT DISTINCT employee_id FROM orders` returns one row with NULL for all the orders that have no employee, even though NULL is not equal to NULL in a `WHERE` comparison.

### Where do NULLs sort?

NULL is neither smaller nor larger than anything, but a sort has to put it somewhere. In PostgreSQL, NULL is treated as larger than every value. So in ascending order NULLs come last, and in descending order they come **first**. That second case surprises people: `ORDER BY shipped_date DESC` starts with the unshipped orders, not with the latest shipping date. You can override the default with `NULLS FIRST` or `NULLS LAST` after each column. Other databases choose differently (for example, SQL Server and MySQL treat NULL as smallest), so spell it out when you share queries between systems.

### Common misconception

Many beginners believe `LIMIT 5` returns "the best 5" or "the first 5 by ID". It returns whichever 5 rows happen to come first in the sorted result, and if there is no `ORDER BY`, in an arbitrary order. The sort, with a tie-breaker, defines "best". Another widespread belief is that `DISTINCT` applies to a single column; it always applies to the complete select list.

### Why it matters

Reports with "top 10", "latest 20" and "next page" all depend on sorting and limiting. Deduplicating lists of customers, countries or products is one of the most common clean-up steps in data work. And NULL-aware sorting prevents the classic mistake of a "latest shipment" report that is topped by blank rows.

## Syntax and key functions

The full order of the clauses you know so far:

```sql-syntax
SELECT [DISTINCT] expression_list
FROM table_name
[WHERE condition]
[ORDER BY expression [ASC | DESC] [NULLS FIRST | NULLS LAST], ...]
[LIMIT count]
[OFFSET skipped_rows];
```

A deterministic top-N query always ends its `ORDER BY` with a unique column:

```sql-syntax
SELECT column_list
FROM table_name
ORDER BY sort_column DESC, unique_id_column
LIMIT n;
```

| Clause | What it does | Example |
|---|---|---|
| `ORDER BY a` | Sort ascending by `a` (default `ASC`) | `ORDER BY order_date` |
| `ORDER BY a DESC` | Sort descending | `ORDER BY unit_price DESC` |
| `ORDER BY a, b DESC` | Sort by `a`; ties by `b` descending | `ORDER BY country, city DESC` |
| `ORDER BY alias` | Sort by a select-list alias | `ORDER BY stock_value DESC` |
| `ORDER BY 2` | Sort by the second selected column | `SELECT a, b ... ORDER BY 2` |
| `NULLS FIRST` / `NULLS LAST` | Place NULLs at the start or the end | `ORDER BY shipped_date DESC NULLS LAST` |
| `LIMIT n` | Keep at most `n` rows | `LIMIT 10` |
| `OFFSET m` | Skip the first `m` rows | `LIMIT 5 OFFSET 10` is page 3 of size 5 |
| `SELECT DISTINCT a, b` | One row per distinct combination of `a` and `b` | `SELECT DISTINCT country, city` |

## Learn by example

### Example 1: Sort descending by a calculated alias

The five most valuable stock holdings. The alias `stock_value` is defined in the select list and can be used in `ORDER BY`, because sorting happens after `SELECT`. `DESC` puts the largest first, and `product_name` breaks ties.

```sql run
SELECT product_name, unit_price * units_in_stock AS stock_value
FROM products
ORDER BY stock_value DESC, product_name
LIMIT 5;
```

```output
product_name | stock_value
Côte de Blaye | 15283.00
Thüringer Rostbratwurst | 6065.71
Raclette Courdavault | 4345.00
Tarte au sucre | 4042.60
Manjimup Dried Apples | 3763.00
```

### Example 2: Sort by several columns

Rows are ordered by country first, then by city inside each country, and finally by `customer_id`. Look at Argentina: all three customers share the same country and city, so only the third sort key decides their order. Without it, those three rows could swap places between runs.

```sql run
SELECT customer_id, country, city
FROM customers
ORDER BY country, city, customer_id
LIMIT 8;
```

```output
customer_id | country | city
CACTU | Argentina | Buenos Aires
OCEAN | Argentina | Buenos Aires
RANCH | Argentina | Buenos Aires
ERNSH | Austria | Graz
PICCO | Austria | Salzburg
MAISD | Belgium | Bruxelles
SUPRD | Belgium | Charleroi
GOURL | Brazil | Campinas
```

### Example 3: Page 2 with LIMIT and OFFSET

With five rows per page, page 2 skips the first five rows. Sorting by the primary key makes the pages stable: the same product never appears on two pages.

```sql run
SELECT product_id, product_name
FROM products
ORDER BY product_id
LIMIT 5 OFFSET 5;
```

```output
product_id | product_name
6 | Grandma's Boysenberry Spread
7 | Uncle Bob's Organic Dried Pears
8 | Northwoods Cranberry Sauce
9 | Mishi Kobe Niku
10 | Ikura
```

### Example 4: DISTINCT on one column, and a NULL

The orders table has 100 rows, but they were taken by only eight different employees. `DISTINCT` returns each `employee_id` once. Employee 5 took no orders, so it does not appear at all. The last row, `NULL`, stands for the order that has no employee recorded. NULL values are treated as equal by `DISTINCT`, so they collapse into one row, and in ascending order the NULL is sorted last.

```sql run
SELECT DISTINCT employee_id
FROM orders
ORDER BY employee_id;
```

```output
employee_id
1
2
3
4
6
7
8
9
NULL
```

### Example 5: DISTINCT on a combination of columns

With two columns, a row counts as a duplicate only if both values match another row. This lists each shipper that has carried goods to Germany or to France. Each of the three shippers appears once per country, so we get six rows even though many more orders exist.

```sql run
SELECT DISTINCT ship_via, ship_country
FROM orders
WHERE ship_country IN ('Germany', 'France')
ORDER BY ship_via, ship_country;
```

```output
ship_via | ship_country
1 | France
1 | Germany
2 | France
2 | Germany
3 | France
3 | Germany
```

### Example 6: NULLs and descending order

Fifteen of the 100 orders have no shipped date. In a descending sort PostgreSQL treats NULL as the largest value, so they would come first. `NULLS LAST` moves them to the end, so the latest real shipping dates are at the top. Without that clause, this query would begin with 15 rows of `NULL`.

```sql run
SELECT order_id, shipped_date
FROM orders
ORDER BY shipped_date DESC NULLS LAST, order_id
LIMIT 6;
```

```output
order_id | shipped_date
10307 | 1999-01-04
10331 | 1998-12-28
10271 | 1998-12-27
10295 | 1998-12-23
10319 | 1998-12-19
10259 | 1998-12-15
```

## Real-world applications

**Top-N and latest-N reports.** "Top 5 products by stock value" (example 1) and "latest 20 shipments" (example 6) are daily dashboard queries. Sorting with a unique tie-breaker and `LIMIT` makes such lists repeatable, so that the number a manager sees on Monday can be reproduced on Tuesday.

**Paging in applications.** A web page that lists customers or orders 20 at a time uses `LIMIT 20 OFFSET (page - 1) * 20`, as in example 3. Data engineers also use deterministic sorting when exporting a table in batches, so that no row is skipped or exported twice.

**Building lookup and filter lists.** The drop-down of countries in a report, or the list of distinct shippers per market (example 5), comes from `SELECT DISTINCT`. Analysts also use it for data profiling: how many different values does this column hold, and does it contain unexpected variants or NULLs, like the NULL employee in example 4?

**Finding open work.** In an operations view, unshipped orders (`shipped_date` is NULL) should be at the top of the list, while a history view wants them at the bottom. `NULLS FIRST` and `NULLS LAST` turn the same data into either view.

## Daily review

### Key takeaways

- Without `ORDER BY`, the order of rows is not defined. With `ORDER BY`, the first column decides, and later columns only break ties.
- `DESC` reverses a column's direction; each column has its own direction.
- End every important sort with a unique column so the result is deterministic.
- `LIMIT n` keeps `n` rows of the sorted result; `OFFSET m` skips `m` rows first; page `p` of size `s` has offset `(p - 1) * s`.
- `DISTINCT` removes duplicate rows over the whole select list, and treats NULLs as equal.
- In PostgreSQL NULL sorts as the largest value: last for `ASC`, first for `DESC`, unless you add `NULLS FIRST` or `NULLS LAST`.

### Common mistakes

- Using `LIMIT` without `ORDER BY` and treating the result as "the top rows".
- Sorting only by a non-unique column such as `unit_price` and getting a different order for ties between runs.
- Forgetting that descending order puts NULLs first.
- Expecting `DISTINCT` to apply only to the first column in the list.
- Writing `LIMIT` before `ORDER BY`; the order of clauses is fixed.
- Using `ORDER BY 2` in saved queries; a later change to the select list silently changes the sort.
- Using a very large `OFFSET` for deep paging, which is slow.

### Revision notes

- Clause order: `SELECT DISTINCT ... FROM ... WHERE ... ORDER BY ... LIMIT ... OFFSET`.
- `ORDER BY a DESC, b`: `a` high to low, ties by `b` low to high.
- Tie-breaker = a unique column at the end of the sort.
- NULLs: biggest value, so `ASC` ends with them and `DESC` starts with them; control with `NULLS FIRST/LAST`.
- `DISTINCT` looks at the complete row of selected columns.

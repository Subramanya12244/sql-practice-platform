## Understand

### What this stage produces

The analysis is finished; this stage makes it trustworthy and reusable. It produces three things: automated tests that fail when the numbers change unexpectedly, a README that tells a stranger what the project is and how to run it, and a Git history that shows how the project was built. Together they are the difference between a notebook that worked once on your machine and a project another person can run, check and trust.

### Tests for an analytics project

A test is a small function that asserts something that must be true. pytest finds functions named `test_*` in files named `test_*.py`, runs them and reports passes and failures. For this capstone, four kinds of test are worth writing. A reproducibility test: the same seed gives identical tables. A defect test: the raw data contains the planted defects (510 orders, 10 duplicates), which guards the generator. A rule test: after cleaning, every quality rule holds. A result test: the headline figure (net revenue 52630.99) is unchanged. A result test is a regression test, and a failure means either a bug or a deliberate change that you must review and record. Tests like these are what make a change to the cleaning code safe.

### Testing with tolerance

Floating-point sums can differ in the last digits between machines, so compare rounded numbers (`round(x, 2)`) or use `pytest.approx`. Never compare unrounded floats with `==`. A related misconception is that more tests are always better: a test that mirrors the code line by line only repeats its bugs. Prefer tests that state facts about the data and the rules.

### The README

A README is the first file a visitor reads. For the capstone it has five sections: the question (what the project answers), the data (what it is and how it is generated), how to run (the exact commands), results (the key findings and where the figures are) and decisions and limits (cleaning choices and caveats). The most important section is how to run, because it is the proof of reproducibility: create an environment, install the requirements, run the tests, run the pipeline. A README is checked like anything else: Example 2 verifies that each required section exists.

### Git workflow

A feature branch holds one piece of work away from `main`. You create the branch, commit on it, then merge it back with a merge commit that records that a branch existed. Commit messages are short sentences in the imperative: `Add cleaning tests`, `Fix country label cleaning`. Reading the history with `git log --format=%s` shows only the subjects, which is the story of the project. Do not commit generated data, caches or secrets; `.gitignore` handles that, as on Day 173.

### Publishing on GitHub

GitHub hosts a remote copy of the repository. Publishing means adding the remote with `git remote add origin <url>` and pushing with `git push -u origin main`. A pull request on GitHub is a request to merge a branch, with a description and a place for review. The browser cannot reach GitHub, so those commands are shown but not run. Before publishing, check: tests pass from a clean clone, the README's commands work in order, no data files or secrets are tracked, and the requirements file lists numpy and pandas.

## Syntax and key functions

```python
def test_name():
    assert condition, "message"
```

```bash
python -m pytest -q -p no:cacheprovider
git switch -c feature/add-tests
git merge --no-ff feature/add-tests -m "Merge feature/add-tests"
git log --format=%s
```

| Command or function | Meaning |
|---|---|
| `assert x == y` | Fails the test when false |
| `python -m pytest -q` | Runs tests quietly: dots, then the summary |
| `-p no:cacheprovider` | Do not write a `.pytest_cache` folder |
| `git switch -c name` | Create and switch to a new branch |
| `git merge --no-ff name` | Merge with a merge commit |
| `git log --format=%s` | One line per commit: the subject |
| `git push -u origin main` | Publish `main` to the remote (not run here) |

## Learn by example

### Example 1: Tests in a throwaway folder

The project module and its tests are written into a new folder and pytest runs them. Five tests cover reproducibility, the planted defects, row accounting, the quality rules and the headline revenue figure. The timing text is removed so the output is stable.

```bash run
mkdir store && cd store
cat > store.py <<'EOF'
import numpy as np
import pandas as pd


def generate(seed=7):
    """Seeded online-store data with planted defects: 500 orders, 120 customers, 20 products."""
    rng = np.random.default_rng(seed)
    customers = pd.DataFrame({
        "customer_id": np.arange(1, 121),
        "country": rng.choice(["DE", "FR", "UK", "US"], 120, p=[0.3, 0.2, 0.2, 0.3]),
        "signup_date": pd.Timestamp("2024-07-01") + pd.to_timedelta(rng.integers(0, 180, 120), unit="D"),
    })
    customers.loc[rng.choice(120, 8, replace=False), "country"] = "us "
    products = pd.DataFrame({
        "product_id": np.arange(1, 21),
        "category": np.repeat(["home", "beauty", "sports", "electronics"], 5),
        "unit_price": (10 + rng.random(20) * 90).round(2),
    })
    campaigns = pd.DataFrame({
        "campaign_id": [0, 1, 2, 3],
        "channel": ["organic", "email", "paid_search", "social"],
        "spend": [0.0, 800.0, 2500.0, 1200.0],
    })
    n = 500
    orders = pd.DataFrame({
        "order_id": np.arange(1001, 1001 + n),
        "customer_id": rng.integers(1, 121, n),
        "product_id": rng.integers(1, 21, n),
        "order_date": pd.Timestamp("2025-01-01") + pd.to_timedelta(rng.integers(0, 180, n), unit="D"),
        "quantity": rng.integers(1, 5, n),
        "discount_pct": rng.choice([0, 10, 20], n, p=[0.6, 0.25, 0.15]),
        "campaign_id": rng.choice([0, 1, 2, 3], n, p=[0.4, 0.2, 0.25, 0.15]),
    })
    orders.loc[rng.choice(n, 5, replace=False), "quantity"] = -1
    orders.loc[rng.choice(n, 6, replace=False), "customer_id"] = 999
    orders = pd.concat([orders, orders.sample(10, random_state=1)], ignore_index=True)
    returned = rng.choice(np.arange(1001, 1001 + n), 60, replace=False)
    returns = pd.DataFrame({
        "order_id": np.concatenate([returned, [9001, 9002, 9003]]),
        "reason": rng.choice(["damaged", "wrong_item", "changed_mind"], 63, p=[0.3, 0.2, 0.5]),
    })
    return {"orders": orders, "customers": customers, "products": products, "campaigns": campaigns, "returns": returns}


def clean(t):
    """Apply the quality rules; return cleaned tables and a row-accounting log."""
    log = {}
    o = t["orders"]
    log["raw_orders"] = len(o)
    o = o.drop_duplicates()
    log["after_duplicates"] = len(o)
    o = o[o["quantity"] > 0]
    log["after_quantity"] = len(o)
    c = t["customers"].copy()
    c["country"] = c["country"].str.strip().str.upper()
    o = o[o["customer_id"].isin(c["customer_id"])]
    log["after_customers"] = len(o)
    r = t["returns"]
    log["raw_returns"] = len(r)
    r = r[r["order_id"].isin(o["order_id"])].drop_duplicates("order_id")
    log["clean_returns"] = len(r)
    p = t["products"]
    o = o.merge(p[["product_id", "unit_price"]], on="product_id", how="left")
    o["revenue"] = (o["quantity"] * o["unit_price"] * (1 - o["discount_pct"] / 100)).round(2)
    o["returned"] = o["order_id"].isin(r["order_id"])
    return {"orders": o.reset_index(drop=True), "customers": c, "products": p, "campaigns": t["campaigns"], "returns": r.reset_index(drop=True)}, log
EOF
cat > test_store.py <<'EOF'
from store import generate, clean


def test_generate_is_reproducible():
    a, b = generate(7), generate(7)
    assert all(a[k].equals(b[k]) for k in a)


def test_raw_data_has_planted_defects():
    t = generate()
    assert len(t["orders"]) == 510
    assert t["orders"].duplicated().sum() == 10


def test_clean_row_accounting():
    _, log = clean(generate())
    assert (log["raw_orders"], log["after_duplicates"], log["after_quantity"], log["after_customers"]) == (510, 500, 495, 489)


def test_clean_passes_rules():
    ct, _ = clean(generate())
    o, c, r = ct["orders"], ct["customers"], ct["returns"]
    assert not o["order_id"].duplicated().any()
    assert (o["quantity"] > 0).all()
    assert o["customer_id"].isin(c["customer_id"]).all()
    assert set(c["country"]) <= {"DE", "FR", "UK", "US"}
    assert r["order_id"].isin(o["order_id"]).all()


def test_net_revenue_total():
    ct, _ = clean(generate())
    net = ct["orders"].loc[~ct["orders"]["returned"], "revenue"].sum()
    assert round(float(net), 2) == 52630.99
EOF
python -m pytest -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output
.....                                                                    [100%]
5 passed
```

### Example 2: Check the README with code

The README text is checked for the five required sections and for a run command. The function returns what is missing, so a weak README is caught the same way as a failing test.

```python run
REQUIRED = ["Question", "Data", "How to run", "Results", "Decisions and limits"]


def readme_problems(text):
    headings = [line[3:].strip() for line in text.splitlines() if line.startswith("## ")]
    problems = [f"missing section: {name}" for name in REQUIRED if name not in headings]
    if "python -m pytest" not in text:
        problems.append("no test command")
    return problems


good = "\n".join([
    "# Store analytics",
    "## Question", "Which channel returns most per unit of spend?",
    "## Data", "Seeded generator, 500 orders.",
    "## How to run", "pip install -r requirements.txt", "python -m pytest -q",
    "## Results", "Email 13.68.",
    "## Decisions and limits", "Negative quantities removed.",
])
weak = "\n".join(["# Store analytics", "## Question", "What sells?", "## Data", "CSV."])
print("good:", readme_problems(good))
print("weak:", readme_problems(weak))
```

```output
good: []
weak: ['missing section: How to run', 'missing section: Results', 'missing section: Decisions and limits', 'no test command']
```

## Real-world applications

- A data team keeps pytest tests that assert row counts and headline totals for each pipeline, so a change that silently shifts a number fails the build, as Example 1 does for the capstone.
- An open-source project requires a README with a how-to-run section and checks it in review, like Example 2's checker.
- A reviewer reads `git log --format=%s` on a pull request to follow the story of changes before opening the diff, as in Example 3.
- A hiring manager clones a candidate's portfolio repository, follows the README commands and judges the project by whether the tests pass.

## Daily review

### Key takeaways

- Tests state facts about the data and the rules; a result test guards the headline numbers.
- Compare rounded numbers, not raw floats.
- A README has the question, data, how to run, results, and decisions and limits.
- Use a feature branch, a clear message and a merge; publish only code, tests and documents.

### Common mistakes

- Comparing floating-point results with `==` unrounded: the test fails on another machine. Round or use `pytest.approx`.
- Naming a test file `store_test.txt` or a function `check_x`: pytest does not find it and reports no tests. Use `test_*.py` and `test_*`.
- Writing a README that describes the code but not how to run it. Add the exact commands in order.
- Committing `data/` or `.pytest_cache/`: add them to `.gitignore` before the first `git add`.

### Revision notes

- Capstone tests: reproducible, defects present, row accounting 510 / 500 / 495 / 489, rules pass, net revenue 52630.99.

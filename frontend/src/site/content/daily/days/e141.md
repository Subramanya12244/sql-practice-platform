## Objectives

- Assemble a small validation pipeline that extracts, cleans, loads, validates and reports on an order file.
- Account for every source row as loaded, rejected, excluded or removed as a duplicate.
- Validate the target against the expected rows with counts, sums, hashes and a column-level diff.
- Test the pipeline with a small harness, including a deliberate bug that the validation must catch.
- Produce a quality report with thresholds and alerts, and express the key checks in SQL.

## Understand

### What you build today

This is a project day. You combine the tools of Days 120 to 140 into one small pipeline that you can run, break on purpose and watch the checks catch. The input is a CSV text of eight orders with the problems real feeds have: a thousands separator and currency symbol (`"$1,250.50"`), lowercase currency codes, one unreadable amount, one missing customer, a failed order and a duplicated order whose second row is a later correction. The output is a SQLite table `orders_clean` and a printed quality report.

The pipeline has five stages. **Extract** reads the CSV text into rows. **Transform** cleans amounts into integer cents, upper-cases currencies, rejects rows that cannot be repaired, drops failed orders by documented rule and keeps the latest row for each duplicated key. **Load** writes the clean rows with `INSERT OR REPLACE`, so a rerun changes nothing (Day 94). **Validate** compares the target with what the transform said it should contain. **Report** prints counts, the validation result and a threshold verdict, and calls a `notify` function for anything that is not OK.

### Design decisions to keep

First, every source row must be accounted for. With 8 rows in, 4 loaded, 2 rejected, 1 excluded (failed) and 1 removed as a duplicate account for all of them: `4 + 2 + 1 + 1 = 8`. That equation is the cheapest and strongest check in the project, because a row that vanishes without a reason breaks it. Second, validation compares the target with the expected rows after the documented rules, never with the raw source (Day 136). Third, the transform returns a result object (clean rows, rejects, counts) instead of printing, so tests, the report and the loader can all use the same values. Fourth, the alert and its delivery are separate: the report calls `notify`, and in this project `notify` appends to a list.

### Steps

1. Read the transform and run it: confirm that the counts add up.
2. Run the whole pipeline with a clean load and read the report.
3. Run it again with the bug switch on (an amount is stored as 5700 instead of 7500). Read which line of the validation names the problem.
4. Run the tests (Day 138) and check that the bug-detection test would fail if the validation were missing.
5. Express the target checks as SQL: constraints and check queries (Day 135).
6. Do the independent exercises on new data and write your own thresholds.

### What good looks like

The clean run prints "validation: ok" and one warning, because 2 of 8 rows (25 percent) were rejected, which is above the 10 percent warning limit. That warning is correct: the feed really does have unreadable rows, and a human should look at the reject list. The buggy run prints the same warning plus one critical message naming the key, the column and both values. If your pipeline prints "ok" on the buggy run, your validation is not looking at the target, which is the most common mistake in this project: validating the data you meant to write instead of the data that is in the table.

## Syntax and key functions

The pipeline's interface:

```python
result = transform(RAW)            # {"source", "clean", "rejected", "excluded", "duplicates"}
load(conn, result["clean"])        # idempotent INSERT OR REPLACE
problems = validate(result, conn)  # list of strings, empty when the target is right
report("2026-01-08", result, problems, notify)
```

| Item | What it does or returns |
|---|---|
| `transform(text)` | Returns the clean rows and the counts needed to account for every source row. |
| `clean_amount(raw)` | Text such as `"$1,250.50"` to integer cents; raises `ValueError` for bad text. |
| `load(conn, clean, bug=False)` | Writes rows with `INSERT OR REPLACE`; `bug=True` damages one amount for the demonstration. |
| `validate(result, conn)` | Compares the table with the expected rows: accounting, count, sum, hashes, column diff. |
| `report(run_date, result, problems, notify)` | Prints the report and sends alerts. |
| `run_tests(globals())` | Runs functions named `test_*` and prints PASS or FAIL. |

## Learn by example

Each example is complete and self-contained. Examples 1 and 2 share the same pipeline code; the code is repeated so that each one runs on its own.

### Example 1: Extract and transform, with row accounting

The transform returns a result with the counts. The program prints the equation that accounts for every source row, and the reject list with the reason for each.

```python run
import csv, hashlib, io, sqlite3
from decimal import Decimal, InvalidOperation

RAW = """order_id,customer_id,amount,currency,status,updated_at
1,10,"$1,250.50",usd,paid,2026-01-05
2,11,34.00,USD,paid,2026-01-05
2,11,35.00,USD,paid,2026-01-06
3,10,abc,USD,paid,2026-01-06
4,12,50.00,EUR,failed,2026-01-06
5,,22.00,USD,paid,2026-01-07
6,13,18.75,eur,refunded,2026-01-07
7,14,75.00,USD,paid,2026-01-08
"""

def clean_amount(raw):
    text = str(raw).strip().replace("$", "").replace(",", "")
    try:
        return int(Decimal(text) * 100)
    except InvalidOperation:
        raise ValueError(f"bad amount: {raw!r}")

def transform(text):
    rows = list(csv.DictReader(io.StringIO(text)))
    rejected, excluded, candidates = [], 0, []
    for r in rows:
        try:
            amount = clean_amount(r["amount"])
        except ValueError:
            rejected.append((r["order_id"], "bad amount"))
            continue
        if not r["customer_id"]:
            rejected.append((r["order_id"], "missing customer"))
            continue
        if r["status"] == "failed":
            excluded += 1
            continue
        candidates.append({"order_id": int(r["order_id"]), "customer_id": int(r["customer_id"]), "amount_cents": amount,
                           "currency": r["currency"].upper(), "status": r["status"], "updated_at": r["updated_at"]})
    latest = {}
    for c in candidates:
        if c["order_id"] not in latest or c["updated_at"] > latest[c["order_id"]]["updated_at"]:
            latest[c["order_id"]] = c
    clean = [latest[k] for k in sorted(latest)]
    return {"source": len(rows), "clean": clean, "rejected": rejected, "excluded": excluded, "duplicates": len(candidates) - len(clean)}

def load(conn, clean, bug=False):
    conn.execute("CREATE TABLE IF NOT EXISTS orders_clean (order_id INTEGER PRIMARY KEY, customer_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT, updated_at TEXT)")
    with conn:
        for c in clean:
            amount = 5700 if bug and c["order_id"] == 7 else c["amount_cents"]
            conn.execute("INSERT OR REPLACE INTO orders_clean VALUES (?, ?, ?, ?, ?, ?)",
                         (c["order_id"], c["customer_id"], amount, c["currency"], c["status"], c["updated_at"]))

result = transform(RAW)
print("source:", result["source"])
print("clean ids:", [c["order_id"] for c in result["clean"]])
print("rejected:", result["rejected"])
print("excluded failed:", result["excluded"], "duplicates removed:", result["duplicates"])
print("accounted:", len(result["clean"]) + len(result["rejected"]) + result["excluded"] + result["duplicates"])
print("order 2 amount (latest correction):", [c["amount_cents"] for c in result["clean"] if c["order_id"] == 2][0])
```

```output
source: 8
clean ids: [1, 2, 6, 7]
rejected: [('3', 'bad amount'), ('5', 'missing customer')]
excluded failed: 1 duplicates removed: 1
accounted: 8
order 2 amount (latest correction): 3500
```

Order 2 appears twice; the later row (35.00) wins, so the target holds 3500 cents. The thousands separator in order 1 was handled by `clean_amount`.

### Example 2: The full run, a damaged run and the tests

The second block adds validation, the report and the harness. The same pipeline runs twice into two fresh databases: once correctly and once with `bug=True`. Four small tests follow; the last one asserts that the validation catches the bug.

```python run
import csv, hashlib, io, sqlite3
from decimal import Decimal, InvalidOperation

RAW = """order_id,customer_id,amount,currency,status,updated_at
1,10,"$1,250.50",usd,paid,2026-01-05
2,11,34.00,USD,paid,2026-01-05
2,11,35.00,USD,paid,2026-01-06
3,10,abc,USD,paid,2026-01-06
4,12,50.00,EUR,failed,2026-01-06
5,,22.00,USD,paid,2026-01-07
6,13,18.75,eur,refunded,2026-01-07
7,14,75.00,USD,paid,2026-01-08
"""

def clean_amount(raw):
    text = str(raw).strip().replace("$", "").replace(",", "")
    try:
        return int(Decimal(text) * 100)
    except InvalidOperation:
        raise ValueError(f"bad amount: {raw!r}")

def transform(text):
    rows = list(csv.DictReader(io.StringIO(text)))
    rejected, excluded, candidates = [], 0, []
    for r in rows:
        try:
            amount = clean_amount(r["amount"])
        except ValueError:
            rejected.append((r["order_id"], "bad amount"))
            continue
        if not r["customer_id"]:
            rejected.append((r["order_id"], "missing customer"))
            continue
        if r["status"] == "failed":
            excluded += 1
            continue
        candidates.append({"order_id": int(r["order_id"]), "customer_id": int(r["customer_id"]), "amount_cents": amount,
                           "currency": r["currency"].upper(), "status": r["status"], "updated_at": r["updated_at"]})
    latest = {}
    for c in candidates:
        if c["order_id"] not in latest or c["updated_at"] > latest[c["order_id"]]["updated_at"]:
            latest[c["order_id"]] = c
    clean = [latest[k] for k in sorted(latest)]
    return {"source": len(rows), "clean": clean, "rejected": rejected, "excluded": excluded, "duplicates": len(candidates) - len(clean)}

def load(conn, clean, bug=False):
    conn.execute("CREATE TABLE IF NOT EXISTS orders_clean (order_id INTEGER PRIMARY KEY, customer_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT, updated_at TEXT)")
    with conn:
        for c in clean:
            amount = 5700 if bug and c["order_id"] == 7 else c["amount_cents"]
            conn.execute("INSERT OR REPLACE INTO orders_clean VALUES (?, ?, ?, ?, ?, ?)",
                         (c["order_id"], c["customer_id"], amount, c["currency"], c["status"], c["updated_at"]))

COLS = ["customer_id", "amount_cents", "currency", "status", "updated_at"]

def row_hash(values):
    return hashlib.sha256("|".join(str(v) for v in values).encode("utf-8")).hexdigest()

def validate(result, conn):
    problems = []
    accounted = len(result["clean"]) + len(result["rejected"]) + result["excluded"] + result["duplicates"]
    if accounted != result["source"]:
        problems.append(f"row accounting: {accounted} accounted of {result['source']}")
    target = {r[0]: r[1:] for r in conn.execute("SELECT order_id, " + ", ".join(COLS) + " FROM orders_clean")}
    expected = {c["order_id"]: tuple(c[k] for k in COLS) for c in result["clean"]}
    if len(target) != len(expected):
        problems.append(f"count: expected {len(expected)} got {len(target)}")
    s_exp = sum(v[1] for v in expected.values())
    s_tgt = sum(v[1] for v in target.values())
    if s_exp != s_tgt:
        problems.append(f"sum amount_cents: expected {s_exp} got {s_tgt}")
    for k in sorted(set(expected) | set(target)):
        if k not in target:
            problems.append(f"missing key {k}")
        elif k not in expected:
            problems.append(f"extra key {k}")
        elif row_hash(expected[k]) != row_hash(target[k]):
            for name, a, b in zip(COLS, expected[k], target[k]):
                if a != b:
                    problems.append(f"key {k} column {name}: expected {a} got {b}")
    return problems

THRESHOLDS = {"reject_rate": (0.10, 0.30)}

def report(run_date, result, problems, notify):
    reject_rate = len(result["rejected"]) / result["source"]
    print(f"run {run_date}")
    print(f"source rows: {result['source']}")
    print(f"loaded {len(result['clean'])}, rejected {len(result['rejected'])}, excluded failed {result['excluded']}, duplicates removed {result['duplicates']}")
    print("validation:", "ok" if not problems else f"{len(problems)} problem(s)")
    for p in problems:
        print("  -", p)
    warn, crit = THRESHOLDS["reject_rate"]
    status = "CRITICAL" if reject_rate > crit else "WARN" if reject_rate > warn else "OK"
    print(f"reject_rate {reject_rate:.1%} {status}")
    if problems:
        notify("CRITICAL", f"orders_clean validation failed on {run_date}: {len(problems)} problem(s)")
    if status != "OK":
        notify(status, f"orders_clean reject_rate {reject_rate:.1%} > {(crit if status == 'CRITICAL' else warn):.1%} on {run_date}")
notified = []
def notify(severity, text):
    notified.append((severity, text))

def run(run_date, bug):
    conn = sqlite3.connect(":memory:")
    result = transform(RAW)
    load(conn, result["clean"], bug=bug)
    problems = validate(result, conn)
    report(run_date, result, problems, notify)
    conn.close()
    return problems

print("== clean run ==")
run("2026-01-08", bug=False)
print("== damaged run ==")
run("2026-01-09", bug=True)
print("== alerts ==")
for severity, text in notified:
    print(severity, text)

def test_clean_amount():
    assert clean_amount("$1,250.50") == 125050

def test_bad_amount_raises():
    try:
        clean_amount("abc")
    except ValueError:
        return
    raise AssertionError("did not raise")

def test_row_accounting():
    r = transform(RAW)
    assert len(r["clean"]) + len(r["rejected"]) + r["excluded"] + r["duplicates"] == r["source"]

def test_validation_catches_bug():
    assert run_quiet(bug=True) != []

def run_quiet(bug):
    conn = sqlite3.connect(":memory:")
    result = transform(RAW)
    load(conn, result["clean"], bug=bug)
    problems = validate(result, conn)
    conn.close()
    return problems

print("== tests ==")
for name in sorted(n for n in list(globals()) if n.startswith("test_")):
    globals()[name]()
    print("PASS", name)
```

```output
== clean run ==
run 2026-01-08
source rows: 8
loaded 4, rejected 2, excluded failed 1, duplicates removed 1
validation: ok
reject_rate 25.0% WARN
== damaged run ==
run 2026-01-09
source rows: 8
loaded 4, rejected 2, excluded failed 1, duplicates removed 1
validation: 2 problem(s)
  - sum amount_cents: expected 137925 got 136125
  - key 7 column amount_cents: expected 7500 got 5700
reject_rate 25.0% WARN
== alerts ==
WARN orders_clean reject_rate 25.0% > 10.0% on 2026-01-08
CRITICAL orders_clean validation failed on 2026-01-09: 2 problem(s)
WARN orders_clean reject_rate 25.0% > 10.0% on 2026-01-09
== tests ==
PASS test_bad_amount_raises
PASS test_clean_amount
PASS test_row_accounting
PASS test_validation_catches_bug
```

The damaged run has the same warning as the clean run, plus validation problems that name the changed key and column and the sum difference. Order 7 should hold 7500 and holds 5700, a difference of 1800 that the sum check also sees.

### Example 3: The same checks in PostgreSQL

On PGlite, constraints stop some problems at write time and check queries find the rest afterwards (Day 135). The table has a primary key and a `CHECK`; the last query is a single report that a pipeline could run on the target.

```sql run
CREATE TABLE orders_clean (
  order_id int PRIMARY KEY,
  customer_id int NOT NULL,
  amount_cents int NOT NULL CHECK (amount_cents >= 0),
  currency text NOT NULL CHECK (currency IN ('USD', 'EUR', 'GBP')),
  status text NOT NULL
);
INSERT INTO orders_clean VALUES
  (1, 10, 125050, 'USD', 'paid'),
  (2, 11, 3500, 'USD', 'paid'),
  (6, 13, 1875, 'EUR', 'refunded'),
  (7, 14, 7500, 'USD', 'paid');

SELECT COUNT(*) AS n,
       SUM(amount_cents) AS total_cents,
       COUNT(*) - COUNT(DISTINCT order_id) AS duplicate_keys,
       COUNT(*) FILTER (WHERE amount_cents <= 0) AS non_positive,
       COUNT(*) FILTER (WHERE status NOT IN ('paid', 'refunded')) AS odd_status
FROM orders_clean;
```

```output
n | total_cents | duplicate_keys | non_positive | odd_status
4 | 137925 | 0 | 0 | 0
```

Constraints make a class of errors impossible rather than detectable: a duplicate `order_id` or a negative amount is refused at insert. Check queries still matter for rules constraints cannot express, such as "the total must equal the source".

## Real-world applications

- **Daily orders load.** The same structure (transform with row accounting, idempotent load, validation against the expectation, report with thresholds) is a normal shape for any batch feed into a warehouse.
- **Onboarding a new source.** Writing the reject reasons and the row-accounting equation first tells you what the feed is really like before anyone builds on it.
- **Vendor file acceptance.** A supplier's file is loaded to a staging table and accepted only when the validation passes, with the reject list sent back to them.
- **Portfolio project.** A clean repository with the pipeline, the tests and a CI workflow (Day 140) shows the whole set of skills in one place.

## Daily review

### Key takeaways

- Account for every source row: loaded, rejected, excluded and duplicates must add up to the source count.
- Validate the table that exists, against the expected rows after documented rules.
- Return a result object from the transform so loader, validator, report and tests share it.
- A pipeline is not finished until a deliberate bug is caught by its own checks.
- Constraints prevent some errors; check queries and comparisons find the rest.

### Common mistakes

- **Validating the in-memory rows instead of the table.** The bug is introduced in the load and never seen. Read the target back.
- **Dropping rows with no reason recorded.** The accounting breaks and nobody knows why. Record each reject with a reason.
- **Comparing the target with the raw source.** Failed orders and duplicates make every run fail. Compare with the transformed expectation.
- **Hard-coding thresholds in the report text.** Keep them in one table so a reviewer sees changes.
- **Skipping the test that proves detection.** Without a damaged run you do not know the validation can fail.

### Revision notes

- Stages: extract, transform, load, validate, report.
- Accounting: `clean + rejected + excluded + duplicates = source`.
- Validation: count, sum, hash per key, column diff; compare target with expectation.
- Report: counts, validation verdict, threshold status, alert for anything not OK.
- Proof of detection: a damaged run must produce problems.

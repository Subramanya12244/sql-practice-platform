## Objectives

- Describe an HTTP request and response (method, URL, query parameters, headers, status code, JSON body) and read the status code families.
- Authenticate with an API key in a header and with a bearer token, and keep the secret in an environment variable instead of the code.
- Fetch every record of a paginated endpoint with page, offset and cursor pagination, and explain why offset pagination can repeat or skip rows.

## Understand

### An API is a conversation in a fixed format

Many of the numbers analysts need live in other companies' systems: a payment provider, a marketing platform, an internal service. They share the data through a **REST API**, a web service that you call over HTTP and that answers with structured data, almost always **JSON**. You do not need to learn a new tool for it: the call is a function call across the network, and the answer becomes a list of dictionaries that pandas can read (Day 164). What the lesson adds is the discipline around the call: proving who you are, getting all the pages, and surviving the limits the provider sets.

### HTTP basics

A call has a **request** and a **response**. The request has a **method** (`GET` reads data, `POST` creates, `PUT` and `PATCH` change, `DELETE` removes; analysts mostly use `GET`), a **URL** whose path names the resource (`/orders`), optional **query parameters** after a question mark (`?page=2&page_size=50`), **headers** that carry metadata such as the key, and sometimes a body. The response has a **status code**, headers and a body. The status code tells you first what happened: the **2xx** family means success (200 OK), **4xx** means the request was wrong (400 bad request, 401 not authenticated, 403 not allowed, 404 not found, 429 too many requests), and **5xx** means the server failed (500, 502, 503, 504). The split matters because the right reaction differs: a 4xx error (except 429) will fail again every time you repeat it, while a 5xx error or a 429 is often temporary.

In Python, the `requests` library makes the call: `requests.get(url, params={"page": 2}, headers={"X-Api-Key": key}, timeout=10)` returns a response with `.status_code`, `.headers` and `.json()`. Always set a `timeout`: without one a call to a stalled server can wait forever. The browser Python here cannot reach the network, so the browser examples call a **stand-in**, a small class with the same `get(path, params, headers)` method that returns canned JSON. The code you write around it is the code you would write around `requests.get`.

### Authentication and secrets

**Authentication** is how the server knows who is calling. The simplest form is an **API key**, a long random string you are given and send with every request, usually in a header (here `X-Api-Key`; the header name is defined by the provider). A **bearer token** is similar: you send `Authorization: Bearer <token>`, and tokens often expire and must be renewed. A missing or wrong credential gives **401**; a valid credential without permission for the resource gives **403**.

A key is a password for your account's data and usage quota. Never write it in code, notebooks or commits, because anything that is committed to a repository or shared in a notebook can be copied. Read it from an **environment variable** (`os.environ["ORDERS_API_KEY"]`), which the shell, the scheduler or the platform's secret store sets. Never print it; if you must log something, log a masked form. If a key leaks, revoke it at the provider and issue a new one.

### Pagination

A list endpoint never returns a million rows in one response. It returns one **page** and tells you how to ask for the next. There are three common designs, and the provider's documentation says which one is used.

**Page-based**: `?page=3&page_size=50`; the response says how many pages exist. **Offset-based**: `?offset=100&limit=50`; skip 100 rows and return 50. **Cursor-based**: the response contains an opaque `next_cursor` that you pass back (`?cursor=...`); when it is `null` or missing, you are done. Your loop must be driven by the response (the total pages, an empty page or a missing cursor), never by a count that you guessed.

Pagination has one trap. Page and offset numbers refer to positions in a list that can change while you read. If the endpoint lists newest first and five new orders arrive after you fetched page 1, page 2 now starts five rows earlier and **repeats five rows you already have**. With rows removed, rows are **skipped** instead. A cursor refers to a position in the data ("orders older than 1070") and does not shift. When a provider offers cursors, prefer them for long extractions; with pages and offsets, deduplicate by the key after fetching, and check the count.

### Rate limits and retries

Providers protect themselves with **rate limits**: a maximum number of requests per time window. When you exceed it, the server answers **429 Too Many Requests**, often with a **`Retry-After`** header that says how many seconds to wait (it may also be an HTTP date; the examples handle seconds). The right reaction is to wait that long and try again. When there is no header, or for a temporary 5xx error or a timeout, use **exponential backoff**: wait 1 second, then 2, then 4, then 8, doubling each time, up to a limit on the number of tries. Add **jitter**, a small random amount, so that many clients that failed together do not all retry in the same instant. Do not retry errors that cannot succeed (400, 401, 403, 404): retrying only wastes quota and delays the real error message. Retrying a `GET` is safe because it does not change anything; retrying a `POST` can create a record twice unless the API supports an idempotency key.

In tests, you should not wait for real seconds and should not get random numbers that differ from run to run. The examples use a **fake sleep** (a function that records the delay instead of waiting) and a **seeded** random generator, so the sequence of delays is the same every time.

### Why it matters, and the misconception

An extraction that stops at the first page silently loads only 50 of 120 orders, and nobody notices because a table of 50 rows looks plausible. An extraction that retries blindly on a 401 hammers a service with a wrong key. The common misconception is that an API call is "just a download". It is a negotiation with limits, and the code must check the status of each response and the number of rows it ended with.

```python
def fetch_all(get):
```

| Item | Meaning |
|---|---|
| `requests.get(url, params, headers, timeout)` | Sends a GET; returns a response object. |
| `resp.status_code`, `resp.headers`, `resp.json()` | Status, response headers (case-insensitive in `requests`), parsed JSON body. |
| `resp.raise_for_status()` | Raises `requests.HTTPError` for 4xx and 5xx. |
| `os.environ["NAME"]`, `os.environ.get("NAME")` | The secret: raises `KeyError` when unset, or returns `None`. |
| `Retry-After` | Seconds to wait (or a date) after a 429 or 503. |
| `page`, `page_size`; `offset`, `limit`; `cursor` / `next_cursor` | The three pagination styles. |
| backoff | `base * 2 ** attempt + jitter` seconds before the next try. |

## Learn by example

The stand-in `FakeAPI` serves the orders endpoint described above: 120 orders, newest first, fields `order_id`, `customer_id`, `amount_cents`, `currency`, `status` (`paid`, `refunded` or `failed`) and `created_at`, API key header `X-Api-Key` with the value `demo-key`, and a cap of 50 rows per page. With `limit_every=3` every third call returns a 429 with `Retry-After: 2`. Its `get` method has the same shape as `requests.get`, but it only reads Python lists: there is no network, no real key and no real server.

### Example 1: Anatomy of a call

One call with the key and page parameters, one without a key, and one to a path that does not exist. The status code tells the three outcomes apart before the body is even read.

```python run
class FakeResponse:
    def __init__(self, status_code, body=None, headers=None):
        self.status_code, self._body, self.headers = status_code, body, headers or {}

    def json(self):
        return self._body

    def raise_for_status(self):
        if self.status_code >= 400:
            raise RuntimeError(f"HTTP {self.status_code}")


class FakeAPI:
    """Stand-in for a web API: no network, canned JSON, same shape as requests.get."""

    def __init__(self, n=120, key="demo-key", limit_every=0):
        special = {3: "failed", 7: "refunded"}
        self.orders = [
            {"order_id": 1000 + i, "customer_id": 1 + (i * 7) % 25, "amount_cents": 1000 + (i * 137) % 9000,
             "currency": "EUR", "status": special.get(i % 10, "paid"), "created_at": f"2025-01-{1 + i % 28:02d}T10:00:00Z"}
            for i in range(n)
        ]
        self.key, self.limit_every, self.calls = key, limit_every, 0

    def add_orders(self, count):
        start = max(o["order_id"] for o in self.orders) + 1
        for i in range(count):
            self.orders.append({"order_id": start + i, "customer_id": 1, "amount_cents": 500, "currency": "EUR",
                                "status": "paid", "created_at": "2025-02-01T09:00:00Z"})

    def get(self, path, params=None, headers=None):
        params, headers = params or {}, headers or {}
        self.calls += 1
        if self.limit_every and self.calls % self.limit_every == 0:
            return FakeResponse(429, {"error": "rate limited"}, {"Retry-After": "2"})
        if headers.get("X-Api-Key") != self.key:
            return FakeResponse(401, {"error": "invalid or missing API key"})
        if path != "/orders":
            return FakeResponse(404, {"error": "not found"})
        newest_first = sorted(self.orders, key=lambda o: -o["order_id"])
        limit = min(int(params.get("page_size", params.get("limit", 50))), 50)
        if "cursor" in params:
            bound = 10 ** 9 if params["cursor"] == "start" else int(params["cursor"])
            rows = [o for o in newest_first if o["order_id"] < bound][:limit]
            return FakeResponse(200, {"data": rows, "next_cursor": str(rows[-1]["order_id"]) if len(rows) == limit else None})
        if "offset" in params:
            off = int(params["offset"])
            return FakeResponse(200, {"data": newest_first[off:off + limit], "offset": off, "limit": limit, "total": len(newest_first)})
        page = int(params.get("page", 1))
        total_pages = -(-len(newest_first) // limit)
        return FakeResponse(200, {"data": newest_first[(page - 1) * limit: page * limit], "page": page, "total_pages": total_pages})
api = FakeAPI()
key = {"X-Api-Key": "demo-key"}

r = api.get("/orders", params={"page": 1, "page_size": 3}, headers=key)
body = r.json()
print(r.status_code, sorted(body))
print("page", body["page"], "of", body["total_pages"])
print(body["data"][0])
print("no key:", api.get("/orders").status_code)
print("wrong path:", api.get("/customers", headers=key).status_code)
print("error body:", api.get("/orders").json())
```

```output
200 ['data', 'page', 'total_pages']
page 1 of 40
{'order_id': 1119, 'customer_id': 9, 'amount_cents': 8303, 'currency': 'EUR', 'status': 'paid', 'created_at': '2025-01-08T10:00:00Z'}
no key: 401
wrong path: 404
error body: {'error': 'invalid or missing API key'}
```

The 200 response has a `data` list and paging fields. The two failures are 4xx: the first is a problem with who you are (401), the second with what you asked for (404). Neither is worth retrying.

### Example 4: Offset and cursor pagination, and why cursors are steadier

The same endpoint is read by offset and by cursor. In the second part, five new orders arrive between the first and the second request. With offset pagination the second page repeats five rows; with a cursor nothing is repeated.

```python run
    rows, offset = [], 0
    while True:
        body = api.get("/orders", params={"offset": offset, "limit": 50}, headers=headers).json()
        rows += body["data"]
        offset += 50
        if interrupt and offset == 50:
            interrupt()
        if len(body["data"]) < 50:
            return rows

def by_cursor(api, interrupt=None):
    rows, cursor = [], "start"
    while cursor:
        body = api.get("/orders", params={"cursor": cursor, "limit": 50}, headers=headers).json()
        rows += body["data"]
        cursor = body["next_cursor"]
        if interrupt and len(rows) == 50:
            interrupt()
    return rows
```

### Example 5: A 429, `Retry-After` and backoff, without waiting

With `limit_every=3`, every third call is refused. The function waits `Retry-After` seconds when the header exists, and otherwise uses exponential backoff with jitter from a seeded generator. The `sleep` argument is replaced by a function that records delays, so the example runs instantly and prints the same delays every time. A 401 must not be retried.

```python run
        start = max(o["order_id"] for o in self.orders) + 1
        for i in range(count):
            self.orders.append({"order_id": start + i, "customer_id": 1, "amount_cents": 500, "currency": "EUR",
                                "status": "paid", "created_at": "2025-02-01T09:00:00Z"})

    def get(self, path, params=None, headers=None):
        params, headers = params or {}, headers or {}
        self.calls += 1
        if self.limit_every and self.calls % self.limit_every == 0:
            return FakeResponse(429, {"error": "rate limited"}, {"Retry-After": "2"})
        if headers.get("X-Api-Key") != self.key:
            return FakeResponse(401, {"error": "invalid or missing API key"})
        if path != "/orders":
            return FakeResponse(404, {"error": "not found"})
        newest_first = sorted(self.orders, key=lambda o: -o["order_id"])
        limit = min(int(params.get("page_size", params.get("limit", 50))), 50)
        if "cursor" in params:
            bound = 10 ** 9 if params["cursor"] == "start" else int(params["cursor"])
            rows = [o for o in newest_first if o["order_id"] < bound][:limit]
            return FakeResponse(200, {"data": rows, "next_cursor": str(rows[-1]["order_id"]) if len(rows) == limit else None})
        if "offset" in params:
            off = int(params["offset"])
            return FakeResponse(200, {"data": newest_first[off:off + limit], "offset": off, "limit": limit, "total": len(newest_first)})
        page = int(params.get("page", 1))
        total_pages = -(-len(newest_first) // limit)
        return FakeResponse(200, {"data": newest_first[(page - 1) * limit: page * limit], "page": page, "total_pages": total_pages})
import random

def get_with_retries(api, path, params, headers, sleep, rng, max_tries=5, base=1.0):
    for attempt in range(max_tries):
        resp = api.get(path, params=params, headers=headers)
        if resp.status_code < 400:
            return resp
        if resp.status_code == 429 or resp.status_code >= 500:
            retry_after = resp.headers.get("Retry-After")
            delay = float(retry_after) if retry_after else base * 2 ** attempt + rng.random() * 0.5
            sleep(delay)
            continue
        resp.raise_for_status()                  # 400, 401, 403, 404: retrying cannot help
    raise RuntimeError(f"gave up after {max_tries} tries")

delays = []
rng = random.Random(7)
api = FakeAPI(limit_every=3)
headers = {"X-Api-Key": "demo-key"}
rows = []
for page in (1, 2, 3, 4, 5):
    body = get_with_retries(api, "/orders", {"page": page, "page_size": 25}, headers, delays.append, rng).json()
    rows += body["data"]
print("rows:", len(rows), "calls:", api.calls, "waits:", delays)

bad = FakeAPI()
try:
    get_with_retries(bad, "/orders", {}, {"X-Api-Key": "wrong"}, delays.append, rng)
except RuntimeError as e:
    print("401 not retried:", e, "| calls:", bad.calls)

jitter = random.Random(7)
backoff = [round(1.0 * 2 ** n + jitter.random() * 0.5, 2) for n in range(4)]
print("backoff without Retry-After:", backoff)
```

```output
rows: 120 calls: 7 waits: [2.0, 2.0]
401 not retried: HTTP 401 | calls: 1
backoff without Retry-After: [1.16, 2.08, 4.33, 8.04]
```

Calls 3 and 6 were refused, so the function waited the 2 seconds the server asked for each time and the retries (calls 4 and 7) succeeded. The wrong key failed on the first call and raised immediately. The last line shows the shape of the backoff sequence: roughly 1, 2, 4, 8 seconds with a small random addition. Real jitter must differ between clients; the seed is only for reproducible lessons and tests.

### Example 6: The same loop against a local web server (local)

This example starts a throwaway HTTP server on `127.0.0.1` in a thread. It serves the orders endpoint with the same rules (key check, pages of at most 50, a 429 with `Retry-After: 0` on every third request) and the loop calls it with `requests`. It needs `pip install requests` and runs on your own computer; the browser shows it read-only with the verified output. It never touches a real remote service.

```python local
import json
import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qs, urlparse

import requests

ORDERS = [{"order_id": 1000 + i, "amount_cents": 1000 + (i * 137) % 9000, "status": "paid"} for i in range(120)]
ORDERS.sort(key=lambda o: -o["order_id"])
STATE = {"calls": 0, "limited": 0}

class Handler(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def _send(self, code, body, headers=None):
        raw = json.dumps(body).encode()
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(raw)))
        for k, v in (headers or {}).items():
            self.send_header(k, v)
        self.end_headers()
        self.wfile.write(raw)

    def do_GET(self):
        STATE["calls"] += 1
        if STATE["calls"] % 3 == 0:
            STATE["limited"] += 1
            return self._send(429, {"error": "slow down"}, {"Retry-After": "0"})
        if self.headers.get("X-Api-Key") != "demo-key":
            return self._send(401, {"error": "bad key"})
        query = parse_qs(urlparse(self.path).query)
        page, size = int(query.get("page", ["1"])[0]), min(int(query.get("page_size", ["50"])[0]), 50)
        total_pages = -(-len(ORDERS) // size)
        self._send(200, {"data": ORDERS[(page - 1) * size: page * size], "page": page, "total_pages": total_pages})

server = ThreadingHTTPServer(("127.0.0.1", 0), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()
base = f"http://127.0.0.1:{server.server_address[1]}"

def fetch_all(session):
    rows, page = [], 1
    while True:
        resp = session.get(base + "/orders", params={"page": page, "page_size": 50}, timeout=5)
        if resp.status_code == 429:
            continue                                   # Retry-After is 0 here, so retry at once
        resp.raise_for_status()
        body = resp.json()
        rows += body["data"]
        if page >= body["total_pages"]:
            return rows
        page += 1

with requests.Session() as session:
    session.headers["X-Api-Key"] = "demo-key"
    rows = fetch_all(session)
    print("rows:", len(rows), "unique:", len({r["order_id"] for r in rows}))
    print("429 responses seen:", STATE["limited"], "of", STATE["calls"], "calls")
    print("no key ->", requests.get(base + "/orders", timeout=5).status_code)

server.shutdown()
server.server_close()
```

```output
rows: 120 unique: 120
429 responses seen: 1 of 4 calls
no key -> 401
```

A `requests.Session` keeps the header on every call and reuses the connection. The loop retried the throttled calls at once because the server sent `Retry-After: 0`; against a real service you would wait the number of seconds in the header, as in Example 5. The last line shows a missing key: the server answered 401 because that was call number 5, which is not one of the throttled calls.

## Real-world applications

- **Pulling payments or marketing data**: a nightly job fetches every page of an endpoint (Example 3), checks the row count against the provider's total and loads the result (Days 164 and 165).
- **Staying inside provider quotas**: the retry function (Example 5) waits as long as the provider asks, so one analyst's extraction does not get the company's key blocked.
- **Keeping credentials out of repositories**: the key is read from the environment in the scheduler (Example 2), so the notebook can be shared without leaking access.
- **Long historical extractions**: cursor pagination (Example 4) avoids the duplicates and gaps that offset paging produces when a source is changing during a long run.

## Daily review

### Key takeaways

- A call is a method, a URL with query parameters, headers and a status code; 2xx succeeded, 4xx is your request, 5xx is the server's problem.
- API keys and tokens go in headers and live in environment variables, never in code or logs.
- Drive pagination from the response (total pages, empty page, missing cursor) and check the count and uniqueness afterwards.
- Offset and page numbers can repeat or skip rows while data changes; cursors are steadier, and deduplication is the fallback.
- Retry 429, 5xx and timeouts with `Retry-After` or exponential backoff plus jitter; never retry 400, 401, 403 or 404.
- Test with a stand-in, a fake sleep and a seeded random generator.

### Common mistakes

- Stopping after the first page. The table has 50 rows and looks fine; compare the row count with the provider's total.
- Writing the key in the notebook. It leaks when the notebook is shared or committed; read `os.environ` and rotate any key that was exposed.
- Calling `requests.get` without `timeout`. A stalled server blocks the job forever; always set one.
- Retrying a 401 or 404 in a loop. It never succeeds and burns quota; raise the error.
- Retrying immediately in a tight loop after a 429. The limit is hit again and some providers block the key; wait `Retry-After` or back off.
- Assuming `Retry-After` is always a number. It can also be a date; handle both when the provider documents it.

### Revision notes

- Status families: 2xx ok, 4xx caller error (429 is temporary), 5xx server error.
- Headers: `X-Api-Key: <key>` or `Authorization: Bearer <token>`.
- Pagination: page, offset or cursor; loop until the response says stop.
- Backoff: `base * 2 ** attempt + jitter`; honour `Retry-After`.
- Secrets: `os.environ["NAME"]`; mask before logging.

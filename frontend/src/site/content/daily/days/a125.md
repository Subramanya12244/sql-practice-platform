## Understand

### The Power Query Editor and Applied Steps

Power Query is the data preparation tool inside Power BI (it is the same engine as in Excel, which you met on Days 98 and 99). You open it with `Transform data`. On the left is the list of **queries**, one per table. For the selected query, the right-hand pane lists its **Applied Steps**: each action you take (promote headers, change a type, filter rows) is recorded as one named step, in order. Clicking an earlier step shows the data as it was at that point, and each step takes the previous step's output as its input. This record is what makes the work repeatable: when the source is refreshed, Power BI replays every step on the new data. Nothing is changed in the source file.

Every step is also written as text in the **M language**, which you can read in the formula bar or in the `Advanced Editor`. A query is a `let ... in` expression: each line inside `let` is a named step that refers to the previous one, and the name after `in` is the result.

### The common transformations

Most cleaning is a handful of transformations, found in the Home and Transform ribbons. **Remove duplicates** keeps the first of each identical row (`Table.Distinct`). **Filter rows** keeps rows that meet a condition (`Table.SelectRows`). **Change type** sets a column to text, whole number, decimal number or date (`Table.TransformColumnTypes`); setting types early prevents errors later. **Trim** and **Clean** and **Capitalize Each Word** fix text that looks the same to a human but differs to a computer, such as `"  customer 03 "` against `"Customer 03"`. **Add column** (custom column) creates a new column from a formula (`Table.AddColumn`), for example revenue as quantity times unit price. **Merge queries** joins two queries on a key, like a SQL join; you choose the join kind (left outer, inner, and so on) and then expand the columns you need. **Group by** aggregates rows (`Table.Group`), like `groupby` in pandas. Each of these steps has a pandas twin, and the pandas examples below print the row count after every step, because the row count is the most useful check: it tells you at once if a step removed or multiplied rows.

### Merges can multiply rows

A merge on a key that is not unique in the right-hand table duplicates the left-hand rows: if a customer appears twice in the dimension, every order from that customer appears twice after the merge, and revenue totals inflate. Power Query shows the merge result as a nested table column first, and you should check that the number of rows has not changed after you expand it. The reverse effect is a left merge where some keys have no match: those rows stay, with nulls in the new columns (inner would drop them). A one-to-many relationship in the model (Day 126) is usually a better way to combine a fact and a dimension than merging them into one wide table.

### Query dependencies and staging

Queries can refer to other queries. Choosing `Reference` on a query creates a new query that starts from the output of the first, so any change in the first flows into the second; `Duplicate` copies the steps instead, and the copy no longer follows the original. A common design is a **staging query** (for example `Sales_raw`, which only reads the file) followed by a clean query that references it, and the staging query has `Enable load` turned off so it is not loaded into the model as an extra table. The **Query Dependencies** view (View tab) draws these links as a diagram. Power BI refreshes a query only after the queries it depends on, so the refresh order is a **topological order** of the dependency graph: every query comes after everything it refers to. A circular reference (A refers to B, B refers to A) is an error.

### Parameters

A **parameter** is a named value that queries can use, created in `Manage parameters`: a date, a text, a number, with a current value. A query step refers to it by name, for example filtering `order_date` to dates on or after the parameter `StartDate`. Change the value once and every query using it follows, and in the Power BI Service a parameter value can be changed for a published dataset. Parameters replace hard-coded values scattered through steps, such as a year or a folder path that differs between a developer's computer and the server.

### Query folding

When the source is a database, Power Query may translate your steps into a single SQL query that the database runs, so only the result comes back. This is **query folding**. A folded filter sends `WHERE order_date >= '2025-07-01'` to the server and transfers only the matching rows; an unfolded one downloads every row and filters on your computer. Folding is why the same query can be fast on one source and slow on another. Steps such as filtering rows, removing columns, simple type changes and merges between tables on the same server usually fold; a step the source cannot express (for example a custom function or `Table.Buffer`) breaks the fold, and every later step then runs locally. Right-click a step and look at `View Native Query`: if it is greyed out, folding stopped at or before that step. Sources like CSV files cannot fold, as there is no server to translate to. As a rule, put the filtering and column-removal steps first, before anything that breaks folding.

### Why it matters

Clean, repeatable queries decide whether a report can be trusted and refreshed unattended. The common failures are a merge that multiplies rows, a type change that was never applied, and a filter that runs in the wrong place and takes minutes. Counting rows after each step catches the first two, and understanding folding explains the third.

## Syntax and key functions

M text for the cleaning pipeline of this lesson (a CSV source, with file path as an example):

```
let
    Source = Csv.Document(File.Contents("C:\PowerBI\sales_raw.csv"), [Delimiter=",", Columns=6, Encoding=65001, QuoteStyle=QuoteStyle.None]),
    Promoted = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
    Typed = Table.TransformColumnTypes(Promoted, {{"order_id", Int64.Type}, {"order_date", type date}, {"customer_id", Int64.Type}, {"product_id", Int64.Type}, {"quantity", Int64.Type}, {"unit_price", type number}}),
    Distinct = Table.Distinct(Typed),
    Positive = Table.SelectRows(Distinct, each [quantity] > 0),
    Recent = Table.SelectRows(Positive, each [order_date] >= StartDate),
    WithRevenue = Table.AddColumn(Recent, "revenue", each [quantity] * [unit_price], type number)
in
    WithRevenue
```

A parameter is itself a query. Its M text (shown in the Advanced Editor) has this form:

```
#date(2025, 7, 1) meta [IsParameterQuery = true, Type = "Date", IsParameterQueryRequired = true]
```

Merge and group:

```
Merged = Table.NestedJoin(WithRevenue, {"customer_id"}, Customers, {"customer_id"}, "Cust", JoinKind.LeftOuter),
Expanded = Table.ExpandTableColumn(Merged, "Cust", {"customer_name", "country"}),
Grouped = Table.Group(Expanded, {"country"}, {{"orders", each Table.RowCount(_), Int64.Type}, {"revenue", each List.Sum([revenue]), type number}})
```

| Power Query step | M function | pandas equivalent |
|---|---|---|
| Remove duplicates | `Table.Distinct` | `drop_duplicates()` |
| Filter rows | `Table.SelectRows` | boolean mask `df[df.col > 0]` |
| Change type | `Table.TransformColumnTypes` | `pd.to_datetime`, `astype` |
| Trim, Capitalize | `Text.Trim`, `Text.Proper` | `str.strip()`, `str.title()` |
| Add custom column | `Table.AddColumn` | `df.assign(...)` |
| Merge queries | `Table.NestedJoin` | `merge(how="left")` |
| Group by | `Table.Group` | `groupby().agg()` |
| Parameter | named query with `IsParameterQuery` | function argument |

## Learn by example

### Example 1: Applied Steps with a row count after each

The raw table has 406 rows: 400 orders, six exact duplicates, three impossible negative quantities and dates stored as text, the kind of problems found in a real export. The function applies the steps in order and records the row count after each, which is what you would see by clicking through the Applied Steps list.

```python run
import numpy as np
import pandas as pd


def make_model():
    rng = np.random.default_rng(7)
    customers = pd.DataFrame({
        "customer_id": np.arange(1, 41),
        "customer_name": [f"Customer {i:02d}" for i in range(1, 41)],
        "country": rng.choice(["UK", "Germany", "France", "Spain"], size=40),
        "segment": rng.choice(["Consumer", "Corporate", "Small Business"], size=40, p=[0.5, 0.3, 0.2]),
    })
    names = ["Desk", "Chair", "Bookcase", "Laptop", "Monitor", "Phone", "Notebook", "Pen Set", "Stapler", "Printer", "Lamp", "Cabinet"]
    categories = ["Furniture", "Furniture", "Furniture", "Technology", "Technology", "Technology",
                  "Office Supplies", "Office Supplies", "Office Supplies", "Technology", "Furniture", "Furniture"]
    products = pd.DataFrame({
        "product_id": np.arange(1, 13),
        "product_name": names,
        "category": categories,
        "unit_cost": rng.integers(5, 120, size=12),
    })
    sales = pd.DataFrame({
        "order_id": np.arange(1001, 1401),
        "order_date": pd.Timestamp("2025-01-01") + pd.to_timedelta(rng.integers(0, 365, 400), unit="D"),
        "customer_id": rng.integers(1, 41, 400),
        "product_id": rng.integers(1, 13, 400),
        "quantity": rng.integers(1, 8, 400),
    })
    cost = products.set_index("product_id")["unit_cost"]
    sales["unit_price"] = (cost[sales["product_id"]].to_numpy() * (1.3 + 0.5 * rng.random(400))).round(2)
    sales = sales.sort_values(["order_date", "order_id"]).reset_index(drop=True)
    dates = pd.date_range("2025-01-01", "2025-12-31", freq="D")
    calendar = pd.DataFrame({
        "date": dates,
        "year": dates.year,
        "quarter": dates.quarter,
        "month_number": dates.month,
        "month_name": dates.strftime("%B"),
    })
    return sales, customers, products, calendar

def messy_inputs():
    sales, customers, products, calendar = make_model()
    raw = sales.copy()
    raw["order_date"] = raw["order_date"].dt.strftime("%Y-%m-%d")
    raw.loc[[10, 50, 90], "quantity"] = -1
    raw = pd.concat([raw, raw.iloc[[3, 33, 133, 233, 283, 333]]], ignore_index=True)
    cust = customers.copy()
    cust.loc[[2, 12], "customer_name"] = ["  customer 03 ", "CUSTOMER 13"]
    return raw, cust, products
def clean_sales(raw, start=None):
    steps = [("Source", len(raw))]
    df = raw.drop_duplicates()
    steps.append(("Removed Duplicates", len(df)))
    df = df[df["quantity"] > 0]
    steps.append(("Filtered Rows: quantity > 0", len(df)))
    df = df.assign(order_date=pd.to_datetime(df["order_date"]))
    steps.append(("Changed Type: order_date", len(df)))
    if start is not None:
        df = df[df["order_date"] >= pd.Timestamp(start)]
        steps.append((f"Filtered Rows: order_date >= {start}", len(df)))
    df = df.assign(revenue=(df["quantity"] * df["unit_price"]).round(2))
    steps.append(("Added Custom: revenue", len(df)))
    return df.reset_index(drop=True), steps

raw, customers, products = messy_inputs()
clean, steps = clean_sales(raw)
for name, rows in steps:
    print(f"{name:32} {rows:>4} rows")
print("revenue total:", round(float(clean["revenue"].sum()), 2))
```

```output
Source                            406 rows
Removed Duplicates                400 rows
Filtered Rows: quantity > 0       397 rows
Changed Type: order_date          397 rows
Added Custom: revenue             397 rows
revenue total: 157068.17
```

### Example 4: Dependencies and refresh order

The queries of the model and what each refers to are written as a dictionary. A function lists the queries in a valid refresh order, with every query after the ones it depends on, and raises an error for a circular reference. `Sales_raw` is a staging query whose load is disabled.

```python run
def refresh_order(depends_on):
    done, order = set(), []
    remaining = dict(depends_on)
    while remaining:
        ready = sorted(q for q, deps in remaining.items() if all(d in done for d in deps))
        if not ready:
            raise ValueError("circular reference among: " + ", ".join(sorted(remaining)))
        for q in ready:
            order.append(q)
            done.add(q)
            del remaining[q]
    return order


queries = {
    "Sales_raw": [],
    "Customers": [],
    "Products": [],
    "Sales": ["Sales_raw"],
    "Sales_by_country": ["Sales", "Customers"],
}
print(refresh_order(queries))
queries["Customers"] = ["Sales_by_country"]
try:
    refresh_order(queries)
except ValueError as error:
    print(error)
```

```output
['Customers', 'Products', 'Sales_raw', 'Sales', 'Sales_by_country']
circular reference among: Customers, Sales_by_country
```

## Real-world applications

- **Repeatable monthly cleaning.** The cleaning steps from Example 1 are recorded once in Power Query and replayed on every refresh, replacing a manual spreadsheet routine.
- **Safe joins in data prep.** Checking the row count after a merge (Example 2) catches a duplicated customer before the finance report double counts revenue.
- **Pipeline design.** A staging query plus clean and summary queries (Example 4) keeps raw data separate from business logic and makes the dependency diagram readable for the next developer.
- **Environment switching.** A `StartDate` or server-name parameter (Example 5) lets a developer test on a small window and the production dataset run on the full range without editing steps.

## Daily review

### Key takeaways

- Applied Steps record every action in order, in M text, and are replayed on refresh.
- Check the row count after each step; merges can multiply rows and filters can remove too many.
- Staging queries with load disabled, plus `Reference`, keep raw and clean data separate.
- Refresh order is a topological order of the dependency graph; circular references are errors.
- Parameters replace hard-coded values; folding pushes work to the source, and some steps break it.

### Common mistakes

- Changing types after other steps. Symptom: errors in later steps or `Error` cells. Fix: set types early.
- Merging on a non-unique key. Symptom: more rows after the merge, inflated revenue. Fix: check key uniqueness and row counts, or use a model relationship instead.
- Using `Duplicate` when `Reference` is meant. Symptom: a fix to the first query does not reach the copy. Fix: reference the original query.
- A step that breaks folding placed early. Symptom: a slow refresh that downloads the whole table. Fix: filter and remove columns first, and check `View Native Query`.

### Revision notes

- `Table.Distinct`, `Table.SelectRows`, `Table.TransformColumnTypes`, `Table.AddColumn`, `Table.NestedJoin`, `Table.Group`.
- Row counts after each step; unmatched and multiplied rows on merges.
- Staging query, `Reference`, `Enable load` off, Query Dependencies view.
- Folding: filters and column removal usually fold; CSV sources never do.

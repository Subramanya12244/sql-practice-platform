## Objectives

- Turn the loaded `orders` table into three findings, each backed by one query whose result you can quote.
- Draw a bar chart and a line chart with Matplotlib from query results, and check the chart's data and labels with code.
- Write a short narrative that states each insight with its number, its caveat and the filter behind it.
- Assemble a handover note that tells the next engineer what was loaded, what was checked and what to rerun.

## Understand

### What this project day does

On Days 101 to 112 you pulled order records from the Orders API stand-in, loaded them into a PostgreSQL table `orders(order_id PRIMARY KEY, customer_id, amount_cents, currency, status, created_at)`, validated the load and wrote analytical SQL on it. Today finishes that route. The data is already in the table; the new job is to **communicate** what it says. A pipeline that nobody can read has delivered nothing, so the last step of an engineering project is a small, honest report: charts that show the finding, sentences that state it, and a handover that lets someone else run and trust the work.

No real API or PostgreSQL server exists in this learning environment. The API is the same kind of stand-in function you used before: `get_orders(page, page_size, api_key)` returns canned JSON in the shape `{"data": [...], "page": N, "total_pages": T}`. The database is `sqlite3` in memory, which runs the same SQL for everything used today (aggregation, window functions) and stands in for PostgreSQL. Where they differ it is said: PostgreSQL has a true `numeric` type and `timestamptz`, `sqlite3` stores the timestamps as text, which sorts correctly because the format is ISO 8601.

### From question to insight

An insight is a statement that a reader can act on, tied to a number. "Revenue by status" is a query, not an insight. "Refunds took 20 percent of order count and 16 percent of gross revenue in March, so the refund rate deserves a look" is an insight. Work in this order: start from a question (how much do we earn, and how much do we lose?), write the query that answers it, read the result, and only then decide whether a chart helps. Each query should do one job and keep its filter visible, because the most common error in reporting is a number whose definition nobody remembers. Revenue here means the sum of `amount_cents` for `status = 'paid'`, in cents, divided by 100 only when displayed.

### Choosing a chart

Pick the chart from the question. A **bar chart** compares a few categories (revenue by currency, orders by status). A **line chart** shows change over an ordered axis such as days. Avoid a pie chart for more than two or three slices and never truncate a bar axis, because bar length encodes the value and a cut axis exaggerates differences. Give every chart a title that states the subject and unit, labelled axes, and no decoration. Because charts are images, you cannot test them by eye in a pipeline, but you can test their ingredients: the title string, the axis labels, the number of bars and the numbers behind them. Today's `python local` example prints exactly those properties.

### Narrative and handover

A narrative has four parts for each insight: the claim, the number, the definition and the caveat. Generate the numbers in code and place them into the sentence with an f-string, so that the text can never disagree with the query. The handover is a short note for the engineer or analyst who takes over: where the data came from, how many rows were read, loaded and rejected, which checks passed, how to rerun, and what is known to be missing. It is the difference between a project and a script.

A common misconception is that the chart is the deliverable. The deliverable is the decision the reader can make after the chart; if you cannot say in one sentence what the chart should change, simplify it or drop it. Another is to chart everything the table contains; three clear findings beat ten charts that a reader must interpret alone.

## Syntax and key functions

The stages of today's project in code form:

```python
rows = fetch_all(get_orders, page_size=25)          # extract: loop pages 1..total_pages
conn.executemany("INSERT INTO orders VALUES (?,?,?,?,?,?)", tuples)   # load
findings = conn.execute("SELECT ... GROUP BY ...").fetchall()          # query
fig, ax = plt.subplots(); ax.bar(labels, values)                     # chart
print(f"{share:.1%} of orders were refunded")                          # narrative
```

| Item | What it does or returns |
|---|---|
| `conn.execute(sql).fetchall()` | Runs a query and returns a list of row tuples. |
| `SUM(x) OVER (ORDER BY d ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` | A moving window sum over the current row and the two before it. |
| `fig, ax = plt.subplots()` | Creates a figure and one set of axes. |
| `ax.bar(labels, values)` / `ax.plot(x, y)` | Draw a bar chart or a line chart. |
| `ax.set_title`, `ax.set_xlabel`, `ax.set_ylabel` | Set the title and axis labels; `ax.get_title()` reads them back. |
| `len(ax.patches)` | Number of bars drawn on the axes. |
| `f"{x:.1%}"` | Formats a fraction as a percentage with one decimal. |

## Learn by example

### Example 1: Extract and load

The loop asks for page 1 to learn `total_pages`, then reads the remaining pages, in the same way as on the earlier API days. The rows are loaded into an in-memory `sqlite3` table with the target schema. The count read from the table, not a counter in the loader, is what the report quotes.

```python run
import sqlite3
import math

def make_orders():
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    rows = []
    for i in range(1, 121):
        rows.append({
            "order_id": i,
            "customer_id": 1 + (i * 5) % 17,
            "amount_cents": 500 + (i * 37) % 89 * 50,
            "currency": "EUR" if i % 5 else "USD",
            "status": statuses[i % 6],
            "created_at": f"2025-03-{1 + (i * 13) % 28:02d}T{(i * 3) % 24:02d}:{(i * 11) % 60:02d}:00Z",
        })
    return rows

ORDERS = make_orders()

def get_orders(page, page_size, api_key):
    """Stand-in for GET /orders?page=N&page_size=P, header X-Api-Key."""
    if api_key != "demo-key":
        return {"error": "unauthorized"}
    total_pages = math.ceil(len(ORDERS) / page_size)
    start = (page - 1) * page_size
    return {"data": ORDERS[start:start + page_size], "page": page, "total_pages": total_pages}

def fetch_all(page_size):
    first = get_orders(1, page_size, "demo-key")
    rows = list(first["data"])
    for page in range(2, first["total_pages"] + 1):
        rows.extend(get_orders(page, page_size, "demo-key")["data"])
    return rows

rows = fetch_all(25)
conn = sqlite3.connect(":memory:")
conn.execute("""CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER,
    amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)""")
conn.executemany("INSERT INTO orders VALUES (?,?,?,?,?,?)",
    [(r["order_id"], r["customer_id"], r["amount_cents"], r["currency"], r["status"], r["created_at"]) for r in rows])
print("read", len(rows), "loaded", conn.execute("SELECT COUNT(*) FROM orders").fetchone()[0])
```

```output
read 120 loaded 120
```

### Example 3: A time series with a window

Daily paid revenue is noisy, so the insight is the trend: a moving sum over the current day and the two days before it. The window runs inside the query (the same `SUM ... OVER` form you used in PostgreSQL), and `substr(created_at, 1, 10)` takes the date part of the ISO text. Only the first six days are printed here.

```python run
import sqlite3
import math

def make_orders():
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    rows = []
    for i in range(1, 121):
        rows.append({
            "order_id": i,
            "customer_id": 1 + (i * 5) % 17,
            "amount_cents": 500 + (i * 37) % 89 * 50,
            "currency": "EUR" if i % 5 else "USD",
            "status": statuses[i % 6],
            "created_at": f"2025-03-{1 + (i * 13) % 28:02d}T{(i * 3) % 24:02d}:{(i * 11) % 60:02d}:00Z",
        })
    return rows

ORDERS = make_orders()

def get_orders(page, page_size, api_key):
    """Stand-in for GET /orders?page=N&page_size=P, header X-Api-Key."""
    if api_key != "demo-key":
        return {"error": "unauthorized"}
    total_pages = math.ceil(len(ORDERS) / page_size)
    start = (page - 1) * page_size
    return {"data": ORDERS[start:start + page_size], "page": page, "total_pages": total_pages}

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)")
conn.executemany("INSERT INTO orders VALUES (:order_id,:customer_id,:amount_cents,:currency,:status,:created_at)", ORDERS)
sql = """
WITH daily AS (
  SELECT substr(created_at, 1, 10) AS day, SUM(amount_cents) AS cents
  FROM orders WHERE status = 'paid' GROUP BY 1
)
SELECT day, cents, SUM(cents) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS moving3
FROM daily ORDER BY day LIMIT 6
"""
for row in conn.execute(sql):
    print(row)
```

```output
('2025-03-03', 11250, 28200)
('2025-03-04', 4300, 19800)
('2025-03-05', 14250, 29800)
('2025-03-06', 2200, 20750)
```

### Example 5: Narrative and handover

The sentences are built from the numbers, so text and query cannot drift apart. The handover collects the reconciliation, the checks that passed and the rerun instructions in one plain text note.

```python run
import sqlite3
import math

def make_orders():
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    rows = []
    for i in range(1, 121):
        rows.append({
            "order_id": i,
            "customer_id": 1 + (i * 5) % 17,
            "amount_cents": 500 + (i * 37) % 89 * 50,
            "currency": "EUR" if i % 5 else "USD",
            "status": statuses[i % 6],
            "created_at": f"2025-03-{1 + (i * 13) % 28:02d}T{(i * 3) % 24:02d}:{(i * 11) % 60:02d}:00Z",
        })
    return rows

ORDERS = make_orders()

def get_orders(page, page_size, api_key):
    """Stand-in for GET /orders?page=N&page_size=P, header X-Api-Key."""
    if api_key != "demo-key":
        return {"error": "unauthorized"}
    total_pages = math.ceil(len(ORDERS) / page_size)
    start = (page - 1) * page_size
    return {"data": ORDERS[start:start + page_size], "page": page, "total_pages": total_pages}

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)")
conn.executemany("INSERT INTO orders VALUES (:order_id,:customer_id,:amount_cents,:currency,:status,:created_at)", ORDERS)
total, refunded = conn.execute("SELECT COUNT(*), SUM(status = 'refunded') FROM orders").fetchone()
gross, refunded_cents = conn.execute("SELECT SUM(amount_cents), SUM(CASE WHEN status='refunded' THEN amount_cents END) FROM orders").fetchone()
print(f"Refunds were {refunded / total:.1%} of orders ({refunded} of {total}) and {refunded_cents / gross:.1%} of order value.")
print("Definition: all statuses counted; amounts are amount_cents summed, shown in currency units.")
print("Caveat: EUR and USD amounts are added without conversion.")
dup = conn.execute("SELECT COUNT(*) FROM (SELECT order_id FROM orders GROUP BY order_id HAVING COUNT(*) > 1)").fetchone()[0]
print("--- handover ---")
print("source: Orders API stand-in, 120 orders, 5 pages of 25")
print("loaded:", total, "rejected: 0", "duplicate ids:", dup)
print("rerun: fetch_all(25), load into orders, run insight queries")
```

## Real-world applications

- **Weekly business review.** The status, currency and trend queries become the fixed section of a weekly note; because the narrative is generated from the queries, the numbers are refreshed by rerunning the script rather than retyped.
- **Pipeline health reporting.** The same pattern (query, chart, sentence) reports load volumes and rejection counts to the team that owns the pipeline, as Example 5's handover does for one load.
- **Hand-off between engineers.** A handover note with row counts, checks and a rerun line lets a colleague take over the pipeline without reading the history.
- **Testing a chart.** Printing a chart's title, labels and data (Example 4) lets a CI job notice when a refactor silently drops a series or renames an axis.

## Daily review

### Key takeaways

- An insight is a claim with a number, a definition and a caveat; a query result alone is not one.
- Choose the chart from the question: bars compare categories, lines show change over an ordered axis.
- Test charts by their properties (title, labels, bar count, data), not by eye.
- Generate narrative sentences from query results so the text cannot disagree with the numbers.
- A handover states what was loaded, what was checked and how to rerun.

### Common mistakes

- Quoting revenue without saying which statuses are included; the same word then means different numbers to different readers. State the filter in the sentence.
- Adding amounts in different currencies as if they were one currency; the total looks fine and is meaningless. Group by currency or convert first.
- Starting a bar chart's axis above zero, which makes a small difference look large. Bars start at zero.
- Hand-typing numbers into the narrative; after the next load they are stale. Format them from the query result.
- Reporting the loader's counter as the loaded count instead of `SELECT COUNT(*)` on the table.

### Revision notes

- Question, query, result, then chart, then sentence, then handover.
- Revenue here is paid `amount_cents` summed; divide by 100 only for display.
- `ax.get_title()`, `len(ax.patches)` and the `get_ydata()` of a line check a chart without looking.
- Handover: source, read/loaded/rejected, checks, rerun, known gaps.

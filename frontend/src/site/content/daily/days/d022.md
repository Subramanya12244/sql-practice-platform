## Understand

### Modules: reusing code

A **module** is a Python file whose names (functions, classes, variables) other code can use. The `import` statement finds the file, runs it once, and gives you a module object. `import math` makes the name `math` available, and you reach inside with a dot: `math.sqrt(16)`. `from math import sqrt` copies one name into your code so you write `sqrt(16)`. `import statistics as stats` gives the module a shorter name. A third form, `from x import *`, copies every public name and is discouraged because you can no longer tell where a name came from, and it can silently replace your own names.

Python runs the module's top-level code only the first time it is imported in a program. Later imports reuse the stored module object. Imported modules are kept in `sys.modules`, a dictionary of modules loaded so far.

### The standard library

Python ships with a large **standard library**: modules available in every installation without installing anything. Already used in this course are `csv`, `json`, `logging`, `pathlib`, `io` and `sys`. Others you will use constantly: `math` (square roots, rounding up and down), `statistics` (mean and median), `random` (seeded random numbers), `collections` (`Counter`, `defaultdict`), `itertools`, `functools`, `os` and `datetime` (Day 23). Before writing a utility yourself, check whether the standard library already has it.

### Creating your own module and package

Save functions in `tools.py` and `import tools` in another file in the same folder. Python searches for modules in a list of folders, `sys.path`: first the folder of the running script, then installed locations. If Python raises `ModuleNotFoundError`, the file is not in one of those folders or its name is misspelled. Do not name your file after a standard module (a file called `random.py` hides the real `random`).

A **package** is a folder of modules that Python treats as one importable unit. It contains a file named `__init__.py`, which may be empty and runs when the package is imported. With a folder `shop/` holding `__init__.py` and `pricing.py`, you write `from shop import pricing` or `from shop.pricing import total`.

Every module has a built-in variable `__name__`. It equals the module's name when the module is imported, and the string `"__main__"` when the file is run directly. The common pattern `if __name__ == "__main__":` therefore guards code that should run only when the file is a script, not when it is imported for its functions.

### Third-party packages and pip

The **Python Package Index (PyPI)** hosts hundreds of thousands of packages written by others, such as `pandas`, `requests` and `pytest`. **pip** is the tool that downloads and installs them: `pip install requests`. Each package has a **version** like `2.31.0`. Packages depend on other packages, and different projects may need different versions of the same one. If everything is installed into one shared place, projects conflict: upgrading a library for project A breaks project B.

### Virtual environments

A **virtual environment** (venv) solves this. It is a folder that holds its own copy of the Python interpreter link and its own `site-packages` folder, so packages installed into it affect only that project. You create one with `python -m venv .venv`, then **activate** it so that `python` and `pip` in your shell refer to it: on macOS and Linux `source .venv/bin/activate`, on Windows `.venv\Scripts\activate`. While active, the shell prompt usually shows `(.venv)`. `deactivate` leaves it. You never copy a venv folder to another machine or into Git; you rebuild it from a list of requirements.

You can skip activation and call the environment's programs directly with a path, `.venv/bin/python` and `.venv/bin/pip`, which is how scripts and the examples here do it.

### requirements.txt

A **requirements file** is a text file with one requirement per line, such as `requests==2.31.0` (exactly that version), `pandas>=2.0` (at least) or just `pytest`. Lines starting with `#` are comments. `pip freeze > requirements.txt` records the exact versions installed in the active environment, and `pip install -r requirements.txt` installs everything on the list. This is how a teammate or a server recreates your environment. Pinning exact versions makes runs reproducible; leaving versions open means a later run may install something newer.

### Common misconception

Learners think a virtual environment is a copy of their project. It contains no project code, only an interpreter and installed packages, and the project lives beside it.

### About this lesson's environment

The DataForge browser runner cannot create a venv or run pip, because it has no operating system shell and no network. The `bash run` examples run in a throwaway folder on your computer's shell with no network, so they only show commands that work offline and print only stable facts (no versions or paths). Everything that needs the internet (installing from PyPI) is shown as text and, for practice, replaced with pure-Python versions of the same logic.

### Why it matters

Reproducible environments are the difference between "it works on my machine" and a pipeline that runs the same on a teammate's laptop and on a server. Clean modules and packages also keep a growing project readable.

## Syntax and key functions

Imports:

```python
import module
from module import name
import module as short
```

Create and use an environment (shell):

```text
python -m venv .venv
source .venv/bin/activate
pip install requests
pip freeze > requirements.txt
pip install -r requirements.txt
deactivate
```

The first line creates the folder `.venv`. After activation, `pip` installs into it. `freeze` writes the installed versions and `-r` reads the file back.

| Name | Meaning |
|---|---|
| `import x`, `from x import y`, `import x as z` | Three import forms. |
| `sys.path` | List of folders searched for modules. |
| `sys.modules` | Dictionary of modules already imported. |
| `__name__` | The module's name, or `"__main__"` when run as a script. |
| `__init__.py` | Marks a folder as a package. |
| `python -m venv DIR` | Creates a virtual environment. |
| `pip install NAME`, `pip list`, `pip freeze` | Install; list installed packages; list them as requirement lines. |
| `pip install -r FILE` | Install every requirement in the file. |
| `NAME==1.2`, `NAME>=1.2` | Exact version; minimum version. |

## Learn by example

### Example 1: Import forms and the standard library

Three import styles reach the same functions. `Counter` from `collections` counts items, and `statistics` computes a mean and median. A module is an object, and `sys.modules` shows it has been loaded.

```python run
import math
from math import sqrt
import statistics as stats
from collections import Counter
import sys

print(math.sqrt(16), sqrt(81), math.ceil(2.1), math.floor(2.9))
data = [4, 8, 6, 5, 3, 9]
print(stats.mean(data), stats.median(data))
print(Counter("banana").most_common(2))
print("math" in sys.modules)
```

```output
4.0 9.0 3 2
5.833333333333333 5.5
[('a', 3), ('n', 2)]
True
```

### Example 2: Your own module and `__name__`

The code writes a module file, imports it and calls its function. The module prints its own `__name__` on import, which is `pricing` and not `__main__`. The guard at the bottom would run only if the file were started directly. The working folder is added to `sys.path` so the import finds the new file. This example is tagged `python local` because the browser runner's checks do not allow importing a module that the program creates by name; the exercises use `importlib.import_module("pricing")`, which does the same work as `import pricing`.

```python local
import importlib
import os
import sys

with open("pricing.py", "w", encoding="utf-8") as f:
    f.write('''def with_tax(price, rate=0.2):
    return round(price * (1 + rate), 2)

print("module name:", __name__)

if __name__ == "__main__":
    print("running as a script")
''')

sys.path.insert(0, os.getcwd())
importlib.invalidate_caches()
import pricing
print(pricing.with_tax(50))
print(pricing.with_tax(50, 0.1))
import pricing as again
print(again is pricing)
```

```output
module name: pricing
60.0
55.0
True
```

### Example 3: A package

A folder with `__init__.py` becomes a package. The package's `__init__.py` imports a name from one of its modules so users can write `from shop import total`. The submodule is also reachable by its full dotted path.

```python local
import importlib
import os
import sys

os.makedirs("shop", exist_ok=True)
with open(os.path.join("shop", "pricing.py"), "w", encoding="utf-8") as f:
    f.write("def total(prices):\n    return sum(prices)\n")
with open(os.path.join("shop", "__init__.py"), "w", encoding="utf-8") as f:
    f.write("from shop.pricing import total\n")

sys.path.insert(0, os.getcwd())
importlib.invalidate_caches()
from shop import total
from shop.pricing import total as same
print(total([1.5, 2.5, 6]))
print(total is same)
import shop
print(sorted(name for name in dir(shop) if not name.startswith("_")))
```

```output
10.0
True
['pricing', 'total']
```

### Example 4: Create a virtual environment

This runs in a shell. It creates an environment, checks that the folder exists, asks the environment's own `python` whether it is inside a venv, and lists the packages it contains. A fresh venv holds only `pip`; version numbers are removed from the output so it stays stable.

```bash run
python -m venv env
test -d env/bin && echo "environment folder created"
env/bin/python -c "import sys; print('inside venv:', sys.prefix != sys.base_prefix)"
env/bin/pip list --disable-pip-version-check | awk 'NR > 2 { print $1 }'
```

```output
environment folder created
inside venv: True
pip
```

### Example 5: requirements.txt without a network

A requirements file is plain text. Here one is written by hand, then the shell shows its lines and counts them. Installing from it would need PyPI, so the install is shown with an empty requirements file, which works offline and installs nothing. A real project runs the same `pip install -r` command with a filled file.

```bash run
cat > requirements.txt <<'EOF'
# data stack
pandas>=2.0
requests==2.31.0
pytest
EOF
grep -v '^#' requirements.txt
grep -vc '^#' requirements.txt
python -m venv env
: > empty.txt
env/bin/pip install -r empty.txt --disable-pip-version-check > /dev/null && echo "install finished"
env/bin/pip freeze --disable-pip-version-check | wc -l | tr -d ' '
```

```output
pandas>=2.0
requests==2.31.0
pytest
3
install finished
0
```

### Example 6: Reading requirement lines in Python

This pure-Python version does what you would otherwise inspect by eye: it parses a requirements file into names, operators and versions, and checks the installed versions against the pins. It runs in the browser, so it is the graded alternative to a real pip session.

```python run
text = """# data stack
pandas>=2.0
requests==2.31.0
pytest
"""
installed = {"pandas": "2.2.1", "requests": "2.30.0", "pytest": "8.0.0"}

def parse(line):
    for op in ("==", ">="):
        if op in line:
            name, version = line.split(op)
            return name, op, version
    return line, "", ""

for line in text.splitlines():
    line = line.strip()
    if not line or line.startswith("#"):
        continue
    name, op, version = parse(line)
    have = installed[name]
    if op == "==":
        status = "ok" if have == version else f"wrong version (have {have})"
    else:
        status = "ok"
    print(f"{name:<9}{op:<3}{version:<7}{status}")
```

```output
pandas   >= 2.0    ok
requests == 2.31.0 wrong version (have 2.30.0)
pytest             ok
```

## Real-world applications

- **Reproducible projects.** A data project keeps its libraries in `requirements.txt` and its own venv. A new team member runs two commands (Example 5) and gets the same versions you have.
- **Shared helper code.** Cleaning functions used by several scripts live in one module or package (Examples 2 and 3), so a fix is made once.
- **Using the standard library first.** Counting, statistics, dates, JSON and file handling need no installation (Example 1), which keeps scheduled jobs light and easy to deploy.
- **Auditing dependencies.** Checking that installed versions match the pins (Example 6) is a small version of what continuous-integration jobs do before a pipeline is deployed.

## Daily review

### Key takeaways

- `import` runs a module once and gives you its names; the standard library is available everywhere.
- A module is a `.py` file and a package is a folder with `__init__.py`; `__name__ == "__main__"` is true only when the file is run directly.
- A virtual environment gives each project its own packages; create it with `python -m venv`, activate it, and never commit it.
- `pip install` adds packages to the active environment; `pip freeze > requirements.txt` and `pip install -r requirements.txt` recreate it.
- Pin versions (`==`) for reproducible runs.

### Common mistakes

- Installing packages with no environment active, so they go into the system Python and conflict with other projects. Create and activate a venv first.
- Naming your file after a module, such as `random.py` or `json.py`, which hides the real module and produces confusing errors like `AttributeError: module 'random' has no attribute 'choice'`.
- Getting `ModuleNotFoundError` because the package is not installed in the active environment, or because the file is in another folder. Check `which python` and `pip list`.
- Forgetting `__init__.py` in a package folder and wondering why imports behave differently across tools.
- Using `from x import *` and losing track of where names come from. Import the names you need.
- Putting the `venv` folder into Git or a zip. Share `requirements.txt` instead.
- Writing import and test code at the top level of a module without the `__name__` guard, so importing the module also runs it.

### Revision notes

- `import x`, `from x import y`, `import x as z`.
- Module: file. Package: folder with `__init__.py`. Guard: `if __name__ == "__main__":`.
- `python -m venv .venv`, then `source .venv/bin/activate` (Windows: `.venv\Scripts\activate`).
- `pip install name`, `pip freeze > requirements.txt`, `pip install -r requirements.txt`.
- `==` exact, `>=` minimum, `#` comment.

## Objectives

- Pass values to SQL with placeholders (`?`, `:name`, `%s`) instead of building query strings.
- Demonstrate SQL injection against a string-built query, and show that a placeholder blocks it.
- Load query results into a pandas DataFrame with `read_sql` and `params`.
- Control result types with `parse_dates`, `dtype` and nullable integers.
- Explain what a placeholder cannot do (table and column names) and the safe alternative.

## Understand

### Why values must not be pasted into SQL

A database program usually needs a value from outside: a customer id typed in a form, a status chosen on a dashboard, a date from a config file. The tempting way to use it is to glue it into the SQL text with an f-string: `f"SELECT * FROM orders WHERE status = '{status}'"`. That works for every well-behaved value and fails for the others. If the value contains an apostrophe (a name such as `O'Brien`), the quote closes the SQL string early and the query is a syntax error. If a person deliberately sends `x' OR '1'='1`, the quote closes the string, the extra text becomes part of the **query logic**, and the condition is now true for every row. This attack is called **SQL injection**: data is interpreted as code, because the code and the data were mixed in one string.

### What a placeholder does

A **placeholder** is a marker in the SQL text where a value will go, and the value is passed separately: `cursor.execute("SELECT * FROM orders WHERE status = ?", ("paid",))`. The driver sends the statement and the values through different channels (or escapes the value correctly for its own protocol), so the value is always treated as a single literal and never as SQL. The text `x' OR '1'='1` becomes a status that matches nothing. You get correctness (apostrophes just work) and safety in one move. The marker style depends on the driver: `sqlite3` uses `?` (positional) or `:name` (named); `psycopg` for PostgreSQL uses `%s` or `%(name)s`; SQLAlchemy's `text()` uses `:name`. The idea is identical. Never put quotes around a placeholder: the driver adds the quoting.

Because the learning environment has no PostgreSQL server, today's runnable code uses `sqlite3` in memory with `?` and `:name`. The psycopg and SQLAlchemy forms are shown as code and have the same shape; only the marker differs.

### What a placeholder cannot do

A placeholder stands for a **value**, not for SQL structure. You cannot write `SELECT * FROM ?` or `ORDER BY ?` with a table or column name: the driver would quote it as a string literal, and the query would sort by a constant. When a name must vary (the column to sort by, the table to load), do not paste user input. Compare it against an **allowlist**, a fixed set of permitted names written in your code, and raise an error otherwise. In psycopg you can also compose identifiers with its `sql.Identifier` helper, which quotes names correctly. A related trap: `IN (?)` takes one value; for a list you generate one marker per item (`",".join("?" * len(ids))`) and pass the list, still never the values themselves.

### read_sql and typed results

`pandas.read_sql(sql, connection, params=...)` runs a query and returns a DataFrame, so the result of a parameterised query goes straight into the pandas tools you know. It accepts the same placeholders and `params` as the driver. A database column is typed, but what arrives in pandas depends on the driver. SQLite stores dates as text, so a date column arrives as `object` strings until you ask for `parse_dates=["created_at"]`. A column with NULLs and integers arrives as `float64` with `NaN` (pandas integers cannot be missing), unless you ask for the nullable `Int64` through `dtype={"col": "Int64"}`. Checking the dtypes of a loaded frame is the first step in treating query results as typed data, because a silent `object` column breaks sorting, arithmetic and date logic later.

A common misconception is that escaping quotes by hand (`value.replace("'", "''")`) is just as safe. It is fragile: encodings, backslashes and database-specific rules cause bypasses, and one forgotten call reopens the hole. The second misconception is that injection needs a stacked `DROP TABLE`. Most real attacks only change a `WHERE` clause to read data they should not see, which is why the demonstration below uses a simple always-true condition.

### Why it matters in data work

Pipelines take values from files, configs and APIs, which are untrusted input in the same way as a web form. A watermark from a state table, a table name from a config and a customer name from a CSV all end up in SQL. Placeholders also make queries reusable: the same statement text with different values lets the database cache the plan and lets you write the query once and test it with many inputs.

## Syntax and key functions

```python
cur.execute("SELECT ... WHERE status = ? AND amount_cents >= ?", ("paid", 3000))   # sqlite3, positional
cur.execute("SELECT ... WHERE status = :s", {"s": "paid"})                          # sqlite3, named
df = pd.read_sql("SELECT ... WHERE status = ?", conn, params=("paid",))
```

The same query with psycopg (PostgreSQL) and SQLAlchemy, shown as code because no server runs here:

```python
import psycopg

with psycopg.connect("dbname=shop") as conn:
    rows = conn.execute("SELECT order_id FROM orders WHERE status = %s", ("paid",)).fetchall()
    named = conn.execute("SELECT order_id FROM orders WHERE status = %(s)s", {"s": "paid"}).fetchall()
```

```python
from sqlalchemy import create_engine, text

engine = create_engine("postgresql+psycopg://user:password@localhost/shop")
with engine.connect() as conn:
    rows = conn.execute(text("SELECT order_id FROM orders WHERE status = :s"), {"s": "paid"}).fetchall()
```

| Item | What it does or returns |
|---|---|
| `?` / `:name` (sqlite3) | Positional and named placeholders; values passed as a tuple or dict. |
| `%s` / `%(name)s` (psycopg) | The PostgreSQL driver's markers; also values in a tuple or dict. |
| `pd.read_sql(sql, conn, params=)` | Runs the query and returns a DataFrame. |
| `parse_dates=["col"]` | Converts text columns to datetimes. |
| `dtype={"col": "Int64"}` | Forces a column type; `Int64` keeps NULLs as `<NA>`. |
| `df.dtypes` | Shows what type each column arrived as. |
| allowlist | A fixed set of allowed names for identifiers, checked before building SQL. |

## Learn by example

### Example 1: The query that string-building breaks

A tiny `accounts` table holds names and a secret. The unsafe function builds the SQL with an f-string. A normal name works. A name with an apostrophe breaks the statement, and the always-true input returns every row, including accounts that were never asked for.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE accounts (name TEXT, secret TEXT)")
conn.executemany("INSERT INTO accounts VALUES (?, ?)", [("ada", "s1"), ("bob", "s2"), ("O'Brien", "s3")])

def find_unsafe(name):
    sql = f"SELECT name, secret FROM accounts WHERE name = '{name}'"
    return conn.execute(sql).fetchall()

print(find_unsafe("ada"))
try:
    find_unsafe("O'Brien")
except sqlite3.OperationalError as exc:
    print("error:", type(exc).__name__)
print(find_unsafe("x' OR '1'='1"))
```

```output
[('ada', 's1')]
error: OperationalError
[('ada', 's1'), ('bob', 's2'), ("O'Brien", 's3')]
```
### Example 2: The same lookup with placeholders

The only change is that the value moves out of the SQL text into the second argument. The apostrophe name now works, and the attack string is just a name that nobody has.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE accounts (name TEXT, secret TEXT)")
conn.executemany("INSERT INTO accounts VALUES (?, ?)", [("ada", "s1"), ("bob", "s2"), ("O'Brien", "s3")])

def find_safe(name):
    return conn.execute("SELECT name, secret FROM accounts WHERE name = ?", (name,)).fetchall()

print(find_safe("ada"))
print(find_safe("O'Brien"))
print(find_safe("x' OR '1'='1"))
print(conn.execute("SELECT name FROM accounts WHERE name = :n OR secret = :s ORDER BY name", {"n": "bob", "s": "s3"}).fetchall())
```

```output
[('ada', 's1')]
[("O'Brien", 's3')]
[]
[("O'Brien",), ('bob',)]
```
### Example 3: Names cannot be placeholders

A placeholder in `ORDER BY` is just a constant string, so the order does not change. The correct pattern checks the requested column against an allowlist before building the text.

```python run
import sqlite3
import math

def make_orders():
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    rows = []
    for i in range(1, 121):
        rows.append({
            "order_id": i,
            "customer_id": 1 + (i * 5) % 17,
            "amount_cents": 500 + (i * 37) % 89 * 50,
            "currency": "EUR" if i % 5 else "USD",
            "status": statuses[i % 6],
            "created_at": f"2025-03-{1 + (i * 13) % 28:02d}T{(i * 3) % 24:02d}:{(i * 11) % 60:02d}:00Z",
        })
    return rows

ORDERS = make_orders()

def get_orders(page, page_size, api_key):
    """Stand-in for GET /orders?page=N&page_size=P, header X-Api-Key."""
    if api_key != "demo-key":
        return {"error": "unauthorized"}
    total_pages = math.ceil(len(ORDERS) / page_size)
    start = (page - 1) * page_size
    return {"data": ORDERS[start:start + page_size], "page": page, "total_pages": total_pages}


def make_conn():
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)""")
    conn.executemany("INSERT INTO orders VALUES (:order_id,:customer_id,:amount_cents,:currency,:status,:created_at)", ORDERS)
    return conn

conn = make_conn()
rows_param = conn.execute("SELECT order_id, amount_cents FROM orders WHERE order_id <= 4 ORDER BY ?", ("amount_cents",)).fetchall()
print("placeholder order:", rows_param)

ALLOWED = {"order_id", "amount_cents"}

def top_orders(order_by, limit):
    if order_by not in ALLOWED:
        raise ValueError(f"cannot order by {order_by!r}")
    sql = f"SELECT order_id, amount_cents FROM orders WHERE order_id <= 4 ORDER BY {order_by} DESC LIMIT ?"
    return conn.execute(sql, (limit,)).fetchall()

print("allowlist order:", top_orders("amount_cents", 3))
try:
    top_orders("amount_cents; DROP TABLE orders", 3)
except ValueError as exc:
    print("rejected:", exc)
```

```output
placeholder order: [(1, 2350), (2, 4200), (3, 1600), (4, 3450)]
allowlist order: [(2, 4200), (4, 3450), (1, 2350)]
rejected: cannot order by 'amount_cents; DROP TABLE orders'
```
### Example 4: read_sql with params

`read_sql` takes the placeholders and `params` unchanged. Two parameters filter by status and by a minimum amount; the DataFrame is then ready for pandas work.

```python run
import sqlite3
import pandas as pd
import math

def make_orders():
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    rows = []
    for i in range(1, 121):
        rows.append({
            "order_id": i,
            "customer_id": 1 + (i * 5) % 17,
            "amount_cents": 500 + (i * 37) % 89 * 50,
            "currency": "EUR" if i % 5 else "USD",
            "status": statuses[i % 6],
            "created_at": f"2025-03-{1 + (i * 13) % 28:02d}T{(i * 3) % 24:02d}:{(i * 11) % 60:02d}:00Z",
        })
    return rows

ORDERS = make_orders()

def get_orders(page, page_size, api_key):
    """Stand-in for GET /orders?page=N&page_size=P, header X-Api-Key."""
    if api_key != "demo-key":
        return {"error": "unauthorized"}
    total_pages = math.ceil(len(ORDERS) / page_size)
    start = (page - 1) * page_size
    return {"data": ORDERS[start:start + page_size], "page": page, "total_pages": total_pages}


def make_conn():
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)""")
    conn.executemany("INSERT INTO orders VALUES (:order_id,:customer_id,:amount_cents,:currency,:status,:created_at)", ORDERS)
    return conn

conn = make_conn()
df = pd.read_sql(
    "SELECT order_id, customer_id, amount_cents, status FROM orders WHERE status = ? AND amount_cents >= ? ORDER BY order_id LIMIT 5",

print(len(df), "rows")
```

### Example 5: Typed results

Dates arrive as strings and a nullable integer arrives as a float until you ask. The first frame shows the defaults, the second repairs them with `parse_dates` and `dtype`.

```python run
import sqlite3
import pandas as pd

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE refunds (refund_id INTEGER, order_id INTEGER, refunded_at TEXT, reviewer_id INTEGER)")
conn.executemany("INSERT INTO refunds VALUES (?,?,?,?)", [(1, 10, "2025-03-04T10:00:00", 7), (2, 11, "2025-03-05T12:30:00", None), (3, 12, "2025-03-06T09:15:00", 7)])
sql = "SELECT * FROM refunds WHERE refund_id >= ? ORDER BY refund_id"
raw = pd.read_sql(sql, conn, params=(1,))
print({c: str(t) for c, t in raw.dtypes.items() if c in ("refunded_at", "reviewer_id")})
typed = pd.read_sql(sql, conn, params=(1,), parse_dates=["refunded_at"], dtype={"reviewer_id": "Int64"})
print({c: str(t) for c, t in typed.dtypes.items() if c in ("refunded_at", "reviewer_id")})
print(typed["reviewer_id"].tolist())
print(typed["refunded_at"].dt.day.tolist())
```

```output
{'refunded_at': 'object', 'reviewer_id': 'float64'}
{'refunded_at': 'datetime64[ns]', 'reviewer_id': 'Int64'}
[7, <NA>, 7]
[4, 5, 6]
```
## Real-world applications

- **Incremental extracts.** A pipeline reads its watermark from a state table and passes it as a parameter (`WHERE created_at > ?`), so the same statement serves every run and a corrupt value cannot rewrite the query.
- **Loading from files.** A CSV can contain names with apostrophes or text that looks like SQL; `executemany` with placeholders loads it as data, which Examples 1 and 2 show for a single row.
- **Report endpoints and notebooks.** A dashboard filter that picks a status or a date range is untrusted input; `read_sql` with `params` returns a typed DataFrame without exposing the database.
- **Config-driven pipelines.** A config may name the table or sort column; an allowlist (Example 3) is the control, because placeholders cannot carry names.

## Daily review

### Key takeaways

- Never build SQL by pasting values into strings; pass values separately with placeholders.
- A placeholder carries a value, never an identifier; use an allowlist for names.
- The marker depends on the driver (`?`, `:name`, `%s`) but the principle is the same.
- `read_sql(..., params=...)` returns a DataFrame; check `dtypes` and repair with `parse_dates` and `dtype`.
- Escaping by hand is fragile; placeholders are the reliable fix.

### Common mistakes

- Wrapping the placeholder in quotes (`'?'`), so the query compares to the literal text `?` and returns nothing. Write the bare marker.
- Passing a single value without a tuple: `execute(sql, ("paid"))` is a string, not a tuple, and the driver reports the wrong number of bindings. Write `("paid",)`.
- Trying `ORDER BY ?` or `FROM ?`; the query runs but orders by a constant or fails. Allowlist the name and format it into the text.
- Using an f-string "just for the number", which is still injection when the number comes from a string input. Cast to `int` or bind it.
- Leaving a date column as `object` text after `read_sql`, then sorting or subtracting dates incorrectly. Use `parse_dates`.

### Revision notes

- `execute(sql, (value,))`, `execute(sql, {"name": value})`, `read_sql(sql, conn, params=...)`.
- `?` and `:name` in sqlite3, `%s` in psycopg, `:name` in SQLAlchemy `text()`.
- Values bind, names allowlist.
- NULL ints arrive as float unless `dtype="Int64"`; dates arrive as text unless `parse_dates`.

## Understand

### Publishing: from Desktop to the Service

Power BI Desktop is where a model and a report are built, and it runs on Windows only. The **Power BI Service** is the cloud side, used in a web browser: it hosts reports, refreshes data and shares content. **Publishing** sends the file from Desktop to a **workspace** in the Service (Home, Publish). A workspace is a shared folder with its own members. Publishing creates two items: a **semantic model** (the tables, relationships and measures, also called a dataset in older material) and a **report** that uses it. Reports built later, in the browser or in another file, can connect to the same semantic model, so measures are defined once. This is why the explicit measure habit from Day 129 matters: one published model is read by many reports.

Publishing sends a copy. The file on the author's disk and the model in the Service are separate, so a change made in Desktop reaches readers only after the next publish. The data in the published model is the data as of the last refresh.

### Refresh

A model in **import mode** stores a copy of the data. It stays as it was loaded until a **refresh** reloads it from the sources, which runs the Power Query steps again. Refresh can be started manually or on a **schedule** set in the model's settings in the Service: choose days and times in a time zone. The number of allowed refreshes per day depends on the licence, so check the current limits for your plan. A scheduled refresh needs credentials for each source stored in the Service. A source that sits on a private network or a local file, such as an on-premises database, is reached through an **on-premises data gateway**, software installed on a machine inside the network that carries queries from the Service. If the gateway machine is off, the refresh fails.

A refresh can fail, for example from an expired password, a changed column name or a source that is unavailable. The model then keeps the old data and shows the failure in the refresh history, so a report can look normal while it is stale. A good habit is to show the last refresh time on the report, for example with a measure such as `Last Refresh = MAX(RefreshLog[loaded_at])` from a small table, and to check refresh history after any source change. A report with DirectQuery sends queries to the source on every interaction and needs no scheduled refresh, at the cost of speed and some DAX limits; this lesson works with import mode.

### Row-level security

**Row-level security (RLS)** restricts which rows of data a signed-in user can see. It is the only mechanism in this lesson that really restricts data; a hidden slicer or a page filter does not (Day 133). You define it in two steps. In Desktop, under Modeling, Manage roles, create a **role** and give each table a DAX filter that evaluates to true for the allowed rows. In the Service, add people or groups to the role in the semantic model's security settings.

A **static** role has a fixed condition:

```dax
[country] = "UK"
```

This is entered as a filter on the `Customers` table for the role `UK Sales`. Members see only UK customers. The filter propagates through the relationships, so `Sales` rows of other countries are no longer visible, and every measure, such as `[Total Revenue]`, returns UK-only values. Static roles need one role per group, which does not scale to many users. A **dynamic** role uses the identity of the viewer: the DAX function `USERPRINCIPALNAME()` returns the email-style sign-in name of the user. With a small `UserSecurity` table that lists an email and an allowed country, one role covers everybody:

```dax
[country] IN SELECTCOLUMNS(
    FILTER(UserSecurity, UserSecurity[email] = USERPRINCIPALNAME()),
    "c", UserSecurity[country]
)
```

The role is applied to `Customers`, and the table itself is not visible in reports. A user missing from `UserSecurity` sees no rows, which is the safe default. Two further facts matter. When a person belongs to **several roles**, the roles add up: the user sees the union of the rows allowed by each, not the intersection. And RLS in the Service applies to people who open the content as viewers; people with edit rights on the workspace are not restricted by the role, so the test is done with View as roles in Desktop or the "Test as role" option in the Service, and the audience should be viewers, not editors.

### Sharing

Content in a workspace is shared in three common ways. Add people to the workspace with a role (Admin, Member, Contributor or Viewer), which gives them access to everything in it according to the role. Share a single report with a link or by email, which gives that person access to the report. Publish an **app**, a packaged, read-only collection of the workspace's content for a wider audience, with a separate list of who can open it. Viewers of an app or report need the permissions on the underlying model as well when RLS is in use. In all cases the data permission is the point to check last: sharing a report with someone must never be the way a person gains access to rows that the data owner has not approved.

### Why it matters

A dashboard that is not refreshed, or shows another team's customers to the wrong person, is worse than no dashboard. Refresh and security are the part of reporting that decides whether the business can trust it, and the issues are usually found by testing as a user. The misconception is that hiding a column or a page secures the data. Only role definitions with RLS do that, and they need to be tested.

## Syntax and key functions

```dax
-- static role filter on Customers
[country] = "UK"
-- dynamic role filter on Customers
[country] IN SELECTCOLUMNS(FILTER(UserSecurity, UserSecurity[email] = USERPRINCIPALNAME()), "c", UserSecurity[country])
```

| Item | Meaning |
|---|---|
| Publish | Sends the semantic model and report from Desktop to a workspace. |
| Scheduled refresh | Reloads an import-mode model at set times, using stored credentials. |
| On-premises data gateway | Software that connects the Service to sources inside a private network. |
| Role | A named set of DAX table filters that restrict rows. |
| `USERPRINCIPALNAME()` | The sign-in name of the current user, for dynamic RLS. |
| View as / Test as role | Previews the report as a role or a user. |
| Workspace role, app | Ways to give access: to a workspace, or to read-only packaged content. |

## Learn by example

### Example 1: A static role as a filter

The role `UK Sales` filters `Customers[country] = "UK"`. The filter reaches `Sales` through the relationship, which in pandas means filtering customers first and then keeping their sales.

```python run
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
countries = ["UK", "Germany", "France", "Spain"]
cats = ["Hardware", "Software", "Services"]
customers = pd.DataFrame({
    "customer_id": range(1, 41),
    "customer_name": [f"Customer {i:02d}" for i in range(1, 41)],
    "country": [countries[i % 4] for i in range(40)],
    "segment": [["Retail", "Corporate"][(i // 4) % 2] for i in range(40)],
})
products = pd.DataFrame({
    "product_id": range(1, 13),
    "product_name": [f"Product {i:02d}" for i in range(1, 13)],
    "category": [cats[i % 3] for i in range(12)],
    "unit_cost": [float(10 + 5 * i) for i in range(12)],
})
n = 400
sales = pd.DataFrame({
    "order_id": range(1, n + 1),
    "order_date": pd.to_datetime("2025-01-01") + pd.to_timedelta(rng.integers(0, 365, n), unit="D"),
    "customer_id": rng.integers(1, 41, n),
    "product_id": rng.integers(1, 13, n),
    "quantity": rng.integers(1, 6, n),
})
sales["unit_price"] = (sales["product_id"].map(products.set_index("product_id")["unit_cost"]) * 1.5).round(2)
calendar = pd.DataFrame({"date": pd.date_range("2025-01-01", "2025-12-31")})
calendar["year"] = calendar["date"].dt.year
calendar["quarter"] = calendar["date"].dt.quarter
calendar["month_number"] = calendar["date"].dt.month
calendar["month_name"] = calendar["date"].dt.strftime("%B")
sales["revenue"] = sales["quantity"] * sales["unit_price"]
fact = (sales.merge(customers, on="customer_id").merge(products, on="product_id")
        .merge(calendar, left_on="order_date", right_on="date"))
def role_view(customers_filter):
    allowed = customers[customers_filter(customers)]["customer_id"]
    return sales[sales["customer_id"].isin(allowed)]

uk = role_view(lambda c: c["country"] == "UK")
print(len(uk), round(float(uk["revenue"].sum()), 2))
print(len(sales), round(float(sales["revenue"].sum()), 2))
```

```output
83 14047.5
400 67132.5
```

The UK role sees 83 orders worth 14,047.50 instead of 400 orders worth 67,132.50. The filter is applied to the dimension, as in DAX, and the fact table follows through the relationship; a Sales-only filter would have to repeat the condition.

user_security = pd.DataFrame({
    "email": ["ana@example.com", "ben@example.com", "ben@example.com", "cho@example.com"],
    "country": ["UK", "France", "Spain", "Germany"],
})

def view_for(email):
    countries = user_security.loc[user_security["email"] == email, "country"]
    allowed = customers[customers["country"].isin(countries)]["customer_id"]

for who in ["ana@example.com", "ben@example.com", "cho@example.com", "guest@example.com"]:

```output
ana@example.com 83 14047.5
ben@example.com 204 33637.5
cho@example.com 113 19447.5
guest@example.com 0 0.0
```

Ana sees UK only, Ben sees France and Spain together (33,637.50), Cho sees Germany, and the guest who is not in the table sees nothing: zero rows and zero revenue. One role covers four people because the rule reads the table, which is `USERPRINCIPALNAME()` plus a lookup.

### Example 3: Several roles are a union

A person in both `UK Sales` and `Germany Sales` sees both countries, not none.

```python run
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
countries = ["UK", "Germany", "France", "Spain"]
cats = ["Hardware", "Software", "Services"]
customers = pd.DataFrame({
    "customer_id": range(1, 41),
    "customer_name": [f"Customer {i:02d}" for i in range(1, 41)],
    "country": [countries[i % 4] for i in range(40)],
    "segment": [["Retail", "Corporate"][(i // 4) % 2] for i in range(40)],
})
products = pd.DataFrame({
    "product_id": range(1, 13),
    "product_name": [f"Product {i:02d}" for i in range(1, 13)],
    "category": [cats[i % 3] for i in range(12)],
    "unit_cost": [float(10 + 5 * i) for i in range(12)],
})
n = 400
sales = pd.DataFrame({
    "order_id": range(1, n + 1),
    "order_date": pd.to_datetime("2025-01-01") + pd.to_timedelta(rng.integers(0, 365, n), unit="D"),
    "customer_id": rng.integers(1, 41, n),
    "product_id": rng.integers(1, 13, n),
    "quantity": rng.integers(1, 6, n),
})
sales["unit_price"] = (sales["product_id"].map(products.set_index("product_id")["unit_cost"]) * 1.5).round(2)
calendar = pd.DataFrame({"date": pd.date_range("2025-01-01", "2025-12-31")})
calendar["year"] = calendar["date"].dt.year
calendar["quarter"] = calendar["date"].dt.quarter
calendar["month_number"] = calendar["date"].dt.month
calendar["month_name"] = calendar["date"].dt.strftime("%B")
sales["revenue"] = sales["quantity"] * sales["unit_price"]
fact = (sales.merge(customers, on="customer_id").merge(products, on="product_id")
        .merge(calendar, left_on="order_date", right_on="date"))
def rows_for_roles(roles):
    allowed = set()
    for countries in roles:
        allowed |= set(customers.loc[customers["country"].isin(countries), "customer_id"])
    return sales[sales["customer_id"].isin(allowed)]

uk = rows_for_roles([["UK"]])
de = rows_for_roles([["Germany"]])
both = rows_for_roles([["UK"], ["Germany"]])
print(len(uk), len(de), len(both))
print(round(float(both["revenue"].sum()), 2), round(float(uk["revenue"].sum() + de["revenue"].sum()), 2))
```

```output
83 113 196
33495.0 33495.0
```

The user in both roles sees 83 + 113 = 196 orders, the sum of the two views, worth 33,495.00. A person who needs less access must be removed from a role; adding a second role never narrows access.

### Example 4: Is the data fresh?

Check a refresh history against a rule: the last successful refresh must be less than 24 hours before the report is read.

```python run
from datetime import datetime

history = [
    {"time": "2025-12-01 06:00", "status": "success"},
    {"time": "2025-12-02 06:00", "status": "success"},
    {"time": "2025-12-03 06:00", "status": "failed"},
    {"time": "2025-12-04 06:00", "status": "failed"},
]

def parse(ts):
    d, t = ts.split()
    y, m, day = (int(x) for x in d.split("-"))
    hh, mm = (int(x) for x in t.split(":"))
    return datetime(y, m, day, hh, mm)

def freshness(history, now, max_hours=24):
    ok = [parse(h["time"]) for h in history if h["status"] == "success"]
    last = max(ok)
    age = (parse(now) - last).total_seconds() / 3600
    return last.strftime("%Y-%m-%d %H:%M"), age, "fresh" if age <= max_hours else "STALE"

last, age, verdict = freshness(history, "2025-12-04 09:00")
print(last, round(age, 1), verdict)
print(freshness(history[:2], "2025-12-02 09:00")[2])
```

```output
2025-12-02 06:00 51.0 STALE
fresh
```

The last successful refresh was 2025-12-02 06:00. Two failures later it is 51 hours old, so the verdict is STALE, although the report looks normal and the failed attempts are visible only in the history. The second call shows a fresh case, three hours after a success. A `Last Refresh` text on the report turns this check into something the reader can see.

### Example 5: A simplified permission table

Course rules for who can do what in a workspace (a simplification of the real roles).

```python run
permissions = {
    "Viewer": {"view"},
    "Contributor": {"view", "edit"},
    "Member": {"view", "edit", "share"},
    "Admin": {"view", "edit", "share", "manage"},
}

def can(role, action):
    return action in permissions[role]

for role in permissions:
    print(role, sorted(permissions[role]))
print(can("Viewer", "share"), can("Member", "share"))
```

```output
Viewer ['view']
Contributor ['edit', 'view']
Member ['edit', 'share', 'view']
Admin ['edit', 'manage', 'share', 'view']
False True
```

A Viewer can only look, a Contributor can also edit, a Member can share, an Admin manages the workspace. In the real Service the roles have more rules (for example, who may publish an app), so check the current documentation before relying on the table. The key design point stands: give the lowest role that does the job, and use RLS on top for row restrictions.

## Real-world applications

- **Regional sales reports.** One semantic model with a dynamic role gives every regional manager a report that shows only their market (Examples 1 and 2).
- **Operational trust.** A freshness check on refresh history, shown on the report, tells readers whether to rely on a figure (Example 4).
- **Cross-border compliance.** Customer data that may only be seen by teams in the same country is enforced with RLS, not with hidden pages (Examples 1 to 3).
- **Controlled distribution.** An app gives executives a read-only copy of the polished pages while the workspace stays with the builders (Example 5).

## Daily review

### Key takeaways

- Publishing sends a semantic model and a report to a workspace in the Service; later changes need a new publish.
- Import-mode data is as old as the last successful refresh; a gateway reaches private sources; a failed refresh keeps stale data.
- RLS roles are DAX filters on tables; static roles hard-code a value, dynamic roles use `USERPRINCIPALNAME()` and a user table.
- Several roles add up as a union; editors are not restricted by the role, so test as a viewer.
- Hidden slicers, pages and columns are not security.

### Common mistakes

- Believing that a hidden page or a visual-level filter protects data. Only RLS restricts the rows a viewer can reach.
- Adding a person to a second role to "tighten" access, which widens it.
- Putting an RLS filter on the fact table only and forgetting the dimension, or testing as an editor, who sees everything.
- Leaving a user out of the security table and not noticing that they get an empty report; decide whether blank is the desired behaviour.
- Ignoring failed refreshes because the report still opens, and so presenting stale numbers.

### Revision notes

- Publish: Desktop to workspace; semantic model plus report.
- Refresh: schedule, credentials, gateway for private sources, check history.
- RLS: Manage roles in Desktop, members in the Service, `USERPRINCIPALNAME()`, union of roles.
- Sharing: workspace roles, report links, apps.

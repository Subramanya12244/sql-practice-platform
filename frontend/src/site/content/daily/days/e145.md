## Objectives

- Draw a star schema and its snowflake variant, and say what each costs and gains in joins, redundancy and clarity.
- Explain why a warehouse assigns surrogate keys instead of using source business keys, and show a case where a business key breaks.
- Define a conformed dimension and use one to compare two fact tables without double counting (drill across).
- Add an unknown member row to a dimension so that a fact row never has to reference a missing key.
- Check a design against the grain: every dimension takes exactly one value per fact row.

## Understand

### The star

A **star schema** has one fact table in the centre and one table per dimension around it, each joined to the fact table by a single key. Drawn on paper it looks like a star. Each dimension is **denormalised**: all the descriptive attributes of that part of the business live in one wide table, even if that repeats a value. `dim_product` holds `product_name` and `category` together, so every product of the `Books` category repeats the word `Books`. A query that slices sales by category needs exactly one join (fact to product), and the same pattern works for every dimension.

```text
            dim_date
                |
dim_customer -- fact_sales -- dim_product
```

### The snowflake

A **snowflake schema** normalises the dimensions: the category moves into its own table, `dim_product` keeps a `category_key`, and a query that wants the category name needs two joins (fact to product to category). The snowflake removes the repetition of text, so it uses less storage, and a change to a category name is made in one row. In a warehouse these gains are small, because dimensions are small compared with the fact table, and the costs are real: more joins in every query, more tables for an analyst to understand, and more work for the optimiser. Most warehouses choose the star and accept the repeated text. The snowflake is sensible when a hierarchy is shared by several dimensions (a geography table used by both customer and store) or when a very large dimension would otherwise repeat long text millions of times. Both shapes give the same answers; the choice is between simplicity and storage.

### Surrogate keys

The source systems already have identifiers: `customer_id`, `product_id`. These are **business keys** (or natural keys), and they come with problems. They can change (two companies merge and renumber), be reused (a discontinued product code is assigned to a new product), come in different formats from different systems (`C001` here, `1001` there), and be composite or text, which makes the fact table wide and joins slow. A **surrogate key** is an integer that the warehouse generates for each dimension row and uses in the fact table. It has no meaning, never changes and never repeats, and it is small. The business key stays in the dimension as an ordinary column for lookups and traceability.

Surrogate keys have a second, essential job: they make **history** possible. If a customer moves from Portugal to Spain, the dimension can hold two rows for the same business key `C003`, each with its own surrogate key, so old facts keep pointing at the Portugal row and new facts at the Spain row. That is Day 146. With the business key as the join column, this would be impossible, because two rows would match each fact.

### Conformed dimensions

A **conformed dimension** is one dimension used, with the same keys and meaning, by several fact tables. The warehouse might have `fact_sales` and `fact_returns`, and both reference the same `dim_product` and `dim_date`. Conforming is what lets you compare them: returns per category next to sales per category, because "category" means the same thing in both. If each fact table had its own product table with slightly different category spellings, the two reports could not be put side by side. Conformed dimensions are the glue of a warehouse that grows beyond one process, and the date dimension is almost always conformed.

Comparing two facts needs a rule. Never join two fact tables to each other directly through a dimension key; for a product with 5 sales lines and 2 return lines you would get 10 rows, and every sum would be inflated. Instead **drill across**: aggregate each fact table separately to the shared dimension level (category and month), then join the two small results on those attributes.

### The unknown member

A fact row sometimes arrives before its dimension row exists, or with a missing value (a sale with no customer). A foreign key does not accept a missing parent, and a NULL key would drop the row out of every inner join. The usual practice is an **unknown member**: a reserved dimension row, for example `customer_key = 0` with the name `Unknown`, to which such facts are attached. Reports then show an `Unknown` group whose size is visible, and no facts are lost. Day 148 uses this for late-arriving data.

### Checking the design against the grain

Test a design with one question per dimension: for one row of the fact table (one order line), does the dimension take exactly one value? A line has one customer, one product and one date. If a dimension could have two values per line (for example a "promotion" that may have several at once), it cannot be a simple foreign key in this fact table; it needs a bridge table or a different design, and it must not be joined casually (Day 144's fan-out).

### Common misconception

Learners think a star schema is a normalised design with fewer tables. It is the opposite: it deliberately repeats descriptive text to make queries simple and consistent. The other common belief is that the business key is a good enough join column "because it is already unique". It is unique only in the source system, today.

### Why it matters

The shape and the keys are the hardest part of a warehouse to change later. A star with surrogate keys and conformed dimensions can grow by adding fact tables; a design built on business keys and private dimensions has to be rebuilt.

## Syntax and key functions

A snowflaked product dimension and the extra join it needs:

```sql-syntax
CREATE TABLE dim_category (category_key integer PRIMARY KEY, category text NOT NULL);
CREATE TABLE dim_product  (product_key integer PRIMARY KEY, product_id text NOT NULL,
                           product_name text NOT NULL, category_key integer REFERENCES dim_category);

SELECT c.category, sum(f.amount_cents)
FROM fact_sales f
JOIN dim_product p  ON p.product_key  = f.product_key
JOIN dim_category c ON c.category_key = p.category_key
GROUP BY c.category;
```

Drilling across two facts that share a conformed dimension:

```sql-syntax
WITH s AS (SELECT product_key, sum(amount_cents) AS sales FROM fact_sales GROUP BY product_key),
     r AS (SELECT product_key, sum(quantity) AS returned FROM fact_returns GROUP BY product_key)
SELECT p.category, sum(s.sales), sum(coalesce(r.returned, 0))
FROM dim_product p JOIN s USING (product_key) LEFT JOIN r USING (product_key)
GROUP BY p.category;
```

| Item | Meaning |
|---|---|
| Star | Fact plus one denormalised table per dimension; one join per dimension. |
| Snowflake | Normalised dimensions; more joins, less repetition. |
| Business key | Identifier from the source (`customer_id`); can change or repeat. |
| Surrogate key | Warehouse-assigned integer (`customer_key`); stable and meaningless. |
| Conformed dimension | One dimension shared by several facts with the same meaning. |
| Drill across | Aggregate each fact separately, then join the results. |
| Unknown member | Reserved row (key 0) for missing or late dimension values. |

## Learn by example

### Example 1: Star and snowflake give the same answer

`dim_category` is cut out of the product dimension to make a snowflake. The first query uses the star (one join), the second the snowflake (two joins) and returns the same totals. The row counts show what the snowflake saves: the category text exists in 4 rows instead of 8.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL,
    valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer,
    product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'),
    (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01', NULL, true FROM generate_series(1, 12) AS i;
INSERT INTO dim_product SELECT i, 'P' || lpad(i::text, 3, '0'), 'Product ' || i,
    (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
CREATE TABLE dim_category AS SELECT row_number() OVER (ORDER BY category)::int AS category_key, category FROM (SELECT DISTINCT category FROM dim_product) c;
CREATE TABLE dim_product_sf AS SELECT p.product_key, p.product_id, p.product_name, c.category_key FROM dim_product p JOIN dim_category c USING (category);
SELECT 'star' AS design, p.category, sum(f.amount_cents) AS cents
FROM fact_sales f JOIN dim_product p ON p.product_key = f.product_key GROUP BY p.category
UNION ALL
SELECT 'snowflake', c.category, sum(f.amount_cents)
FROM fact_sales f JOIN dim_product_sf p ON p.product_key = f.product_key JOIN dim_category c ON c.category_key = p.category_key GROUP BY c.category
ORDER BY 2, 1;
```

```output
design | category | cents
snowflake | Books | 19250
star | Books | 19250
snowflake | Stationery | 59000
star | Stationery | 59000
snowflake | Tools | 88000
star | Tools | 88000
snowflake | Toys | 80250
star | Toys | 80250
```

### Example 2: A business key that gets reused

The source reuses the product code `P003`: until February it meant product 3 and then it was assigned to a new product. A dimension keyed on the business key would have to overwrite the old row, changing the history of every old sale. With surrogate keys the two products are two rows, and the facts keep their keys. The query shows the revenue of each version of `P003`; joining the facts on `product_id` instead would mix them.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL,
    valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer,
    product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'),
    (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01', NULL, true FROM generate_series(1, 12) AS i;
INSERT INTO dim_product SELECT i, 'P' || lpad(i::text, 3, '0'), 'Product ' || i,
    (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
UPDATE dim_product SET product_id = 'P003', product_name = 'Product 3 (old)' WHERE product_key = 3;
INSERT INTO dim_product VALUES (9, 'P003', 'New gadget', 'Toys');
INSERT INTO fact_sales VALUES (61, 20260210, 1, 9, 2, 3000);
SELECT p.product_key, p.product_id, p.product_name, count(*) AS lines, sum(f.amount_cents) AS cents
FROM fact_sales f JOIN dim_product p ON p.product_key = f.product_key
WHERE p.product_id = 'P003' GROUP BY p.product_key, p.product_id, p.product_name ORDER BY p.product_key;
```

```output
product_key | product_id | product_name | lines | cents
3 | P003 | Product 3 (old) | 7 | 26250
9 | P003 | New gadget | 1 | 3000
```

### Example 3: Drill across two facts with conformed dimensions

`fact_returns` shares `dim_product` and `dim_date` with `fact_sales`. The first block is the right way: it aggregates each fact to the product first and then joins, giving sales and returned units per category side by side. The second block shows what a direct join of the two facts does.

```sql run

    product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'),
    (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01', NULL, true FROM generate_series(1, 12) AS i;
INSERT INTO dim_product SELECT i, 'P' || lpad(i::text, 3, '0'), 'Product ' || i,
    (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
CREATE TABLE fact_returns (return_id integer PRIMARY KEY, date_key integer REFERENCES dim_date, product_key integer REFERENCES dim_product, quantity integer);
INSERT INTO fact_returns VALUES (1, 20260120, 1, 1), (2, 20260125, 1, 2), (3, 20260203, 2, 1), (4, 20260211, 6, 1);
WITH s AS (SELECT product_key, sum(amount_cents) AS sales_cents FROM fact_sales GROUP BY product_key),
     r AS (SELECT product_key, sum(quantity) AS returned FROM fact_returns GROUP BY product_key)
SELECT p.category, sum(s.sales_cents) AS sales_cents, coalesce(sum(r.returned), 0) AS returned_units
FROM dim_product p JOIN s USING (product_key) LEFT JOIN r USING (product_key)
GROUP BY p.category ORDER BY p.category;
```

```output
Books | 19250 | 3
Stationery | 59000 | 0
Tools | 88000 | 2
Toys | 80250 | 0
```

### Example 4: The unknown member

A reserved row with key 0 lets a sale without a known customer be stored and counted. The sale is inserted with `customer_key = 0`, the foreign key accepts it, and a report by country shows an `Unknown` group instead of losing the row.

```sql run

CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL,

CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer,
    product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'),
    (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01', NULL, true FROM generate_series(1, 12) AS i;
INSERT INTO dim_product SELECT i, 'P' || lpad(i::text, 3, '0'), 'Product ' || i,
    (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
```

## Real-world applications

- **Choosing the shape.** A team that builds a sales warehouse picks the star for the BI tool's sake: one join per dimension and short queries.
- **Mergers and renumbering.** A surrogate key lets two customer systems with colliding ids sit in one dimension without rewriting any fact.
- **Cross-process reporting.** Sales and returns, shipments and inventory are compared through shared product and date dimensions.
- **Late data.** The unknown member keeps incomplete facts visible until the dimension row arrives.

## Daily review

### Key takeaways

- A star denormalises dimensions; a snowflake normalises them at the cost of joins.
- Surrogate keys are small, stable and enable history; business keys stay as attributes.
- Conformed dimensions let separate fact tables be compared; drill across, never join facts directly.
- An unknown member row (key 0) keeps facts whose dimension value is missing.
- Each dimension must take one value per fact row at the grain.

### Common mistakes

- **Joining two fact tables through a dimension.** Rows multiply and sums inflate. Aggregate each fact first.
- **Using the business key as the foreign key.** Reuse or renumbering rewrites history. Use surrogate keys.
- **Private product tables per fact table.** Categories do not match across reports. Conform the dimension.
- **NULL foreign keys for unknown values.** Rows vanish from inner joins. Use the unknown member.
- **Snowflaking by reflex.** More joins for little storage saved. Prefer the star unless a hierarchy is shared.

### Revision notes

- Star: one join per dimension. Snowflake: dimensions normalised.
- Surrogate key = integer assigned by the warehouse; business key kept as a column.
- Drill across: aggregate each fact, join on shared attributes.
- Unknown member: key 0, name Unknown.

## Understand

### Operators

On Day 157 a task was a unit of work. An **operator** is the template that defines what kind of work it is; a task is an operator used inside a DAG with a `task_id`. `BashOperator` runs a shell command (`bash_command`). `PythonOperator` calls a Python function (`python_callable`) and passes it keyword arguments (`op_kwargs`); Airflow also passes context values such as `ds` to a function that declares them. `EmptyOperator` does nothing and is used as a start, end or join marker so that the graph is readable. Other operators run SQL on a database, copy files to cloud storage or call a service; most of them come from separate **provider** packages that you install next to Airflow, for example `apache-airflow-providers-common-sql` for running SQL. Operators that wait for something, such as a file to appear, are called **sensors**. Choosing an operator means choosing where the work really happens: an operator that runs a transformation inside the Airflow worker uses the worker's memory, while an operator that submits SQL to the warehouse lets the warehouse do the work. A task should be small, repeatable and idempotent, the same property that made incremental loads safe to rerun in the ETL days: running it twice for the same interval must give the same result.

### Templating

Many arguments are **templated**: before the task runs, Airflow renders them with the Jinja template language and the run's context. `"echo {{ ds }}"` becomes `echo 2025-01-03` for the run whose logical date is 3 January 2025, because `ds` is that date as `YYYY-MM-DD`. Templating is how one DAG processes a different day's data on each run without any change to its code, and it is what makes reruns of old days possible.

### Schedules

The `schedule` argument says when runs are created. It can be a preset such as `"@hourly"`, `"@daily"`, `"@weekly"` (Sunday at midnight) and `"@monthly"` (the first of the month); a cron string such as `"30 2 * * *"` with the five fields from Day 153; a `timedelta` such as every six hours; or `None`, which means the DAG runs only when someone triggers it. In older Airflow 2 versions the argument was called `schedule_interval`; current versions use `schedule`.

### Data intervals: why the first run waits

Each scheduled run covers a **data interval**: a start and an end. For `@daily` the interval for 3 January is from 3 January 00:00 to 4 January 00:00. The run for an interval is created only after that interval has ended, because only then does the data of that day exist completely. The run's **logical date** is the start of the interval, so the run that starts shortly after midnight on 4 January carries the logical date 3 January. This is the most misunderstood fact in Airflow. A DAG with `start_date=datetime(2025, 1, 1)` and `@daily` does not run on 1 January; its first run covers 1 to 2 January and begins at the start of 2 January. A learner who unpauses the DAG at noon on 1 January and waits for a run sees nothing, and thinks the scheduler is broken. For cron schedules the first interval begins at the first schedule point on or after `start_date`.

### start_date and catchup

`start_date` is the earliest moment the DAG may have runs. Write it as a fixed date, never as `datetime.now()`: a moving start date means the first interval never completes. **Catchup** decides what happens to intervals that ended before the DAG was switched on. With `catchup=True` the scheduler creates one run for every missed interval from `start_date` up to the latest finished interval, which is how you **backfill** history automatically; the scheduler can start hundreds of runs at once if the start date is a year ago. With `catchup=False` it creates only the run for the most recent finished interval and carries on from there. Airflow 2 defaults to `True`, and the default can differ between versions and configuration, so always write `catchup` explicitly. A DAG that loads "yesterday's file" needs catchup only if the earlier days were never loaded.

### Why it matters

Wrong assumptions about intervals produce loads of the wrong day, double loads after a backfill, and DAGs that look dead. A model of the schedule that you can run turns these questions into arithmetic.

## Syntax and key functions

An Airflow 2.x DAG that uses three operators and a templated command (shown, not run):

```python
from datetime import datetime
from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.empty import EmptyOperator
from airflow.operators.python import PythonOperator


def load_orders(ds, **context):
    print(f"loading {ds}")


with DAG(
    dag_id="orders_daily",
    start_date=datetime(2025, 1, 1),
    schedule="@daily",
    catchup=True,
    max_active_runs=1,
) as dag:
    start = EmptyOperator(task_id="start")
    extract = BashOperator(task_id="extract", bash_command="echo extracting {{ ds }}")
    load = PythonOperator(task_id="load", python_callable=load_orders)
    start >> extract >> load
```

`start_date` and `schedule` define the intervals; `catchup=True` asks for runs of every missed interval; `max_active_runs=1` lets only one run be active at a time, so a backfill goes one day after another. `{{ ds }}` in the bash command is rendered per run. `load_orders(ds, **context)` receives the date because it declares a parameter named `ds`. In Airflow 3 the imports move (DAG from `airflow.sdk`, standard operators from the `airflow.providers.standard` package); check the documentation for your version.

| Item | Meaning |
|---|---|
| `schedule="@daily"` | One run per day, created after the day's interval ends. |
| `schedule="30 2 * * *"` | Cron string. |
| `schedule=timedelta(hours=6)` | Every six hours. |
| `schedule=None` | Only manual or API triggers. |
| `start_date` | Earliest moment for intervals; use a fixed date. |
| `catchup` | Create runs for missed intervals (`True`) or only the latest (`False`). |
| `{{ ds }}` | Logical date as `YYYY-MM-DD`. |

## Learn by example

### Example 1: Data intervals for a daily schedule

The model below computes the interval boundaries for the presets `@hourly`, `@daily`, `@weekly` and `@monthly` with plain `datetime` arithmetic (Airflow uses UTC by default; the model uses naive dates). The current time is 4 January 2025, 06:00. Each run is printed with the logical date (interval start) and the time its interval ended.

```python run
from datetime import datetime, timedelta


def next_boundary(moment, schedule):
    if schedule == "@hourly":
        return moment.replace(minute=0, second=0, microsecond=0) + timedelta(hours=1)
    midnight = moment.replace(hour=0, minute=0, second=0, microsecond=0)
    if schedule == "@daily":
        return midnight + timedelta(days=1)
    if schedule == "@weekly":
        return midnight + timedelta(days=7 - (midnight.weekday() + 1) % 7)
    if schedule == "@monthly":
        return (midnight.replace(day=1) + timedelta(days=32)).replace(day=1)
    raise ValueError(f"unsupported schedule {schedule!r}")


def intervals(start_date, schedule, now):
    begin = next_boundary(start_date - timedelta(microseconds=1), schedule)
    result = []
    while True:
        end = next_boundary(begin, schedule)
        if end > now:
            return result
        result.append((begin, end))
        begin = end


def planned_runs(start_date, schedule, now, catchup):
    found = intervals(start_date, schedule, now)
    return found if catchup else found[-1:]


def show(runs):
    for begin, end in runs:
        print(begin.strftime("%Y-%m-%d"), "ran after", end.strftime("%Y-%m-%d %H:%M"))


now = datetime(2025, 1, 4, 6, 0)
print("catchup=True")
show(planned_runs(datetime(2025, 1, 1), "@daily", now, True))
print("catchup=False")
show(planned_runs(datetime(2025, 1, 1), "@daily", now, False))
```

```output
catchup=True
2025-01-01 ran after 2025-01-02 00:00
2025-01-02 ran after 2025-01-03 00:00
2025-01-03 ran after 2025-01-04 00:00
catchup=False
2025-01-03 ran after 2025-01-04 00:00
```

With catchup on, three runs exist: the logical dates 1, 2 and 3 January. The interval of 4 January is still open at 06:00, so it has no run yet. With catchup off only the latest finished interval, 3 January, is run, and the first two days are skipped. This is the whole difference between backfilling and not.

### Example 2: No run until the first interval ends

The DAG is switched on at 23:00 on its own start date. The interval of that day ends at midnight, so there is nothing to run yet. The same `start_date` with `@hourly` has already produced 23 runs.


```output
0
23
1
```

The first number is 0: the first daily interval ends at 2 January 00:00. The hourly schedule has 23 finished one-hour intervals at 23:00. The last line moves the clock to exactly the end of the interval, and then one daily run exists. This is the arithmetic behind "my DAG did not run today".

### Example 3: Weekly and monthly schedules

A weekly schedule starts on Sundays and a monthly one on the first. A start date that is not on a boundary moves the first interval to the next boundary.

```python run
from datetime import datetime, timedelta


def next_boundary(moment, schedule):
    if schedule == "@hourly":
        return moment.replace(minute=0, second=0, microsecond=0) + timedelta(hours=1)
    midnight = moment.replace(hour=0, minute=0, second=0, microsecond=0)
    if schedule == "@daily":
        return midnight + timedelta(days=1)
    if schedule == "@weekly":
        return midnight + timedelta(days=7 - (midnight.weekday() + 1) % 7)
    if schedule == "@monthly":
        return (midnight.replace(day=1) + timedelta(days=32)).replace(day=1)
    raise ValueError(f"unsupported schedule {schedule!r}")


def intervals(start_date, schedule, now):
    begin = next_boundary(start_date - timedelta(microseconds=1), schedule)
    result = []
    while True:
        end = next_boundary(begin, schedule)
        if end > now:
            return result
        result.append((begin, end))
        begin = end


def planned_runs(start_date, schedule, now, catchup):
    found = intervals(start_date, schedule, now)
    return found if catchup else found[-1:]


def starts(start, schedule, now):
    return [begin.strftime("%Y-%m-%d") for begin, end in intervals(start, schedule, now)]


print(starts(datetime(2025, 1, 1), "@weekly", datetime(2025, 1, 20)))
print(starts(datetime(2025, 1, 15), "@monthly", datetime(2025, 5, 2)))
print(len(intervals(datetime(2025, 1, 1), "@weekly", datetime(2025, 3, 1))))
```

```output
['2025-01-05', '2025-01-12']
['2025-02-01', '2025-03-01', '2025-04-01']
7
```

1 January 2025 is a Wednesday, so the first weekly interval starts on Sunday 5 January and the second on the 12th (it ends on the 19th). The interval beginning on the 19th is still open on the 20th, so it has no run. A monthly DAG with a start date of 15 January begins on 1 February, and by 2 May three intervals (starting 1 February, 1 March and 1 April) have ended. Between 1 January and 1 March there are seven finished weekly intervals.

### Example 4: Operators and templating across runs

Small stand-ins for three operators show what each one does. `BashOperator` here returns its rendered command instead of running a shell, because the browser has no shell and Airflow is not installed. For every planned run the three tasks are executed in order with a context that holds `ds`.

```python run
from datetime import datetime, timedelta


def next_boundary(moment, schedule):
    if schedule == "@hourly":
        return moment.replace(minute=0, second=0, microsecond=0) + timedelta(hours=1)
    midnight = moment.replace(hour=0, minute=0, second=0, microsecond=0)
    if schedule == "@daily":
        return midnight + timedelta(days=1)
    if schedule == "@weekly":
        return midnight + timedelta(days=7 - (midnight.weekday() + 1) % 7)
    if schedule == "@monthly":
        return (midnight.replace(day=1) + timedelta(days=32)).replace(day=1)
    raise ValueError(f"unsupported schedule {schedule!r}")


def intervals(start_date, schedule, now):
    begin = next_boundary(start_date - timedelta(microseconds=1), schedule)
    result = []
    while True:
        end = next_boundary(begin, schedule)
        if end > now:
            return result
        result.append((begin, end))
        begin = end


def planned_runs(start_date, schedule, now, catchup):
    found = intervals(start_date, schedule, now)
    return found if catchup else found[-1:]

class Operator:
    def __init__(self, task_id):
        self.task_id = task_id

    def execute(self, context):
        raise NotImplementedError


class EmptyOperator(Operator):
    def execute(self, context):
        return None


class PythonOperator(Operator):
    def __init__(self, task_id, python_callable, op_kwargs=None):
        super().__init__(task_id)
        self.python_callable = python_callable
        self.op_kwargs = op_kwargs or {}

    def execute(self, context):
        return self.python_callable(**self.op_kwargs)


class BashOperator(Operator):
    def __init__(self, task_id, bash_command):
        super().__init__(task_id)
        self.bash_command = bash_command

    def execute(self, context):
        text = self.bash_command
        for key, value in context.items():
            text = text.replace("{{ " + key + " }}", value)
        return text


def load_orders(ds):
    return f"loading {ds}"


tasks = [
    EmptyOperator("start"),
    BashOperator("extract", "echo extracting {{ ds }}"),
    PythonOperator("load", load_orders, {"ds": "2025-01-01"}),
]
for begin, end in planned_runs(datetime(2025, 1, 1), "@daily", datetime(2025, 1, 3), True):
    context = {"ds": begin.strftime("%Y-%m-%d")}
    print(context["ds"], [task.execute(context) for task in tasks])
```

```output
2025-01-01 [None, 'echo extracting 2025-01-01', 'loading 2025-01-01']
2025-01-02 [None, 'echo extracting 2025-01-02', 'loading 2025-01-01']
```

The `EmptyOperator` returns nothing, the templated bash command changes with each run's date, and the `PythonOperator` returns the same text in both runs because its `op_kwargs` fixed `ds` to 2025-01-01. In Airflow the context value is passed in for you when the function declares `ds`, as in the DAG above; a hard-coded argument like this one makes every run reprocess the same day, a common bug.

## Real-world applications

- A nightly warehouse load uses `@daily`, `catchup=False` and `{{ ds }}` in its SQL so that each run loads exactly the day of its interval (Examples 1 and 4).
- A team backfilling six months of history sets `catchup=True` with `max_active_runs=1`, using the model first to count how many runs will be created (Examples 1 and 3).
- A support engineer answers "why has the new DAG not run today?" by checking the data interval: the first run starts only after the first interval has ended (Example 2).

## Daily review

### Key takeaways

- An operator is a task template: `BashOperator`, `PythonOperator`, `EmptyOperator`, SQL and sensor operators from providers.
- A daily run covers one interval and starts after that interval has ended; the logical date is the interval start.
- `start_date` is a fixed date; `catchup=True` creates every missed run, `catchup=False` only the latest.
- Template with `{{ ds }}` so the same code processes each run's own day.

### Common mistakes

- Expecting a run at the start date. Symptom: nothing runs on day one. Fix: wait for the first interval to end.
- Using `datetime.now()` as `start_date`. Symptom: the DAG never produces a run. Fix: use a fixed date.
- Leaving catchup on with an old start date. Symptom: hundreds of runs start at once. Fix: set `catchup=False` or limit `max_active_runs`.
- Hard-coding the date in a task. Symptom: every run loads the same day. Fix: use `{{ ds }}`.

### Revision notes

- `@daily` run for logical date D starts at D+1 00:00.
- `catchup=False` keeps only the latest interval.
- `{{ ds }}` is the logical date as `YYYY-MM-DD`.

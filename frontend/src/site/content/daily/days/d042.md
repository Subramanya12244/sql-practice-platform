## Objectives

- Join a table to itself with two aliases to relate rows of the same table, such as employees and their managers.
- Build pairs of rows from one table without pairing a row with itself or listing each pair twice.
- Use `CROSS JOIN` to produce every combination of two tables and predict its row count.
- Chain three or more tables with several `JOIN ... ON` clauses and trace which key links which table.
- Explain how the order of joins matters when outer and inner joins are mixed.

## Understand

### Self join: one table, two roles

Sometimes a table holds a relationship with itself. In `employees`, the column `reports_to` holds the `employee_id` of the person's manager, so each row points at another row of the same table. To show an employee next to the manager's name you need two copies of the table in one query: one playing the employee and one playing the manager. A **self join** is an ordinary join in which the same table appears twice under different aliases:

`FROM employees e JOIN employees m ON e.reports_to = m.employee_id`

Read it as two separate card files that happen to contain the same cards. `e` is the file you walk through; for each card you take its `reports_to` number and look up the card with that `employee_id` in file `m`. The aliases are mandatory, because without them the two copies cannot be told apart. Fuller, the vice president, has a NULL `reports_to`, so an inner self join drops him, as any inner join drops rows with no partner (day 40). Use `LEFT JOIN` when the top of the hierarchy must stay in the result (day 41).

### Self join for pairs

A self join also compares rows of one table with each other: customers in the same city, employees with the same title, products with the same supplier. The join condition says what the pair has in common: `a.city = b.city`. Written alone, this has two flaws. Every row pairs with itself (London customer AROUT matches AROUT), and every pair appears twice (AROUT with BSBEV and BSBEV with AROUT). Adding `a.customer_id < b.customer_id` removes both: a row never satisfies `<` against itself, and for any two rows only one order satisfies it. In this data `a.city = b.city` alone gives 179 rows (91 self pairs plus 88 ordered pairs), and with the `<` condition only the 44 distinct pairs remain.

### CROSS JOIN: every combination

A **cross join** has no join condition. It pairs every row of the first table with every row of the second, so its size is the product: 8 categories times 3 shippers give 24 rows. The result is called the **Cartesian product**. It is rarely what you want by accident (the classic bug is forgetting the `ON` clause of a join between two large tables and getting millions of rows), but it is the right tool on purpose to build a complete grid of combinations, such as every category with every shipper, which you can then compare with actual data. In PostgreSQL, `FROM a CROSS JOIN b` is the same as `FROM a, b` with no `WHERE`. Write `CROSS JOIN` so the intention is visible.

### Joining three or more tables

A join result is itself a table, so you can join another table to it, and again. Each `JOIN` adds one table and one `ON` condition that connects it to a table already present:

```sql-syntax
FROM orders o
JOIN customers c  ON c.customer_id = o.customer_id
JOIN employees e  ON e.employee_id = o.employee_id
JOIN shippers sh  ON sh.shipper_id = o.ship_via
```

To plan such a query, draw the path along foreign keys: `order_details` to `orders` to `customers`. For N tables you need N-1 join conditions. Add one table at a time and check the row count after each step. A missing condition silently turns that step into a cross join. Every join also changes the **grain**, meaning what one result row stands for. After joining `orders` to `order_details` the grain is one row per order line, so everything you learned about row multiplication on day 40 applies to the whole chain: add the tables you need and no more.

### Join order

For inner joins only, the order you write the joins in does not change the result. The database is free to start from whichever table is cheapest, and you will get the same rows. With outer joins order does matter, because each join works on the result of the previous one. Suppose you write `customers LEFT JOIN orders ... JOIN order_details ...`. Customers FISSA and PARIS have no orders, so after the left join their `order_id` is NULL; the following inner join needs `od.order_id = o.order_id`, which is unknown for NULL, and removes them. The query started as a left join and ended as an inner join. When a chain must keep unmatched rows, make every join after the first outer join a `LEFT JOIN` as well.

### Common misconception

Learners think more joins are always "more complete". Each join can add rows (one-to-many), remove rows (inner), or both, so a six-table query is only as trustworthy as each link in it. Another frequent belief is that a self join needs a special keyword. It does not: it is a normal join with aliases.

### Why it matters

Hierarchies (staff and managers, categories and parent categories), comparisons within one table (duplicates, pairs, before and after) and star-shaped reports (an order with customer, employee and shipper) are everyday problems, and they are all joins of the kinds you have now seen.

## Syntax and key functions

```sql-syntax
-- self join
SELECT e.last_name AS employee, m.last_name AS manager
FROM employees e
LEFT JOIN employees m ON e.reports_to = m.employee_id;

-- pairs without self-pairs or duplicates
FROM customers a
JOIN customers b ON a.city = b.city AND a.customer_id < b.customer_id

-- cross join and a chain of joins
FROM categories c CROSS JOIN shippers s
FROM t1 JOIN t2 ON t2.fk = t1.pk JOIN t3 ON t3.fk = t2.pk
```

| Idea | Rule |
|---|---|
| Self join | Two aliases of the same table; the condition links two columns of the same table |
| Pair join | Add `a.id < b.id` to avoid self pairs and mirrored duplicates |
| `CROSS JOIN` | No `ON`; rows = rows in A times rows in B |
| N tables | N-1 `ON` conditions, each linking a new table to one already joined |
| Inner joins | Written order does not change the result |
| Outer then inner | Later inner joins on the optional table remove the unmatched rows again |

## Learn by example

### Example 1: Employees and their managers

A self join with `LEFT JOIN` keeps Fuller, whose `reports_to` is NULL, so his manager column is NULL. The aliases `e` and `m` make one table play two roles. Notice that Fuller is the manager of most others, and Buchanan manages Suyama, King and Dodsworth.

```sql run
SELECT e.employee_id, e.last_name AS employee, m.last_name AS manager
FROM employees e
LEFT JOIN employees m ON e.reports_to = m.employee_id
ORDER BY e.employee_id;
```

```output
employee_id | employee | manager
1 | Davolio | Fuller
2 | Fuller | NULL
3 | Leverling | Fuller
4 | Peacock | Fuller
5 | Buchanan | Fuller
6 | Suyama | Buchanan
7 | King | Buchanan
8 | Callahan | Fuller
9 | Dodsworth | Buchanan
```

### Example 2: How many people report to each manager

Group the self join by manager. An inner join is right here, since we only count employees who have a manager. The result shows the span of control: five people report to Fuller and three to Buchanan.

```sql run
SELECT m.last_name AS manager, COUNT(*) AS direct_reports
FROM employees e
JOIN employees m ON e.reports_to = m.employee_id
GROUP BY m.employee_id, m.last_name
ORDER BY direct_reports DESC, manager;
```

```output
manager | direct_reports
Fuller | 5
Buchanan | 3
```

### Example 3: Pairs of customers in the same city

The condition `a.customer_id < b.customer_id` keeps one row per pair of different customers. Counting these pairs per city shows where customers are concentrated: London has 15 pairs (six customers give 6 x 5 / 2 = 15 pairs). The top four cities are shown.

```sql run
SELECT a.city, COUNT(*) AS pairs
FROM customers a
JOIN customers b ON a.city = b.city AND a.customer_id < b.customer_id
GROUP BY a.city
ORDER BY pairs DESC, a.city
LIMIT 4;
```

```output
city | pairs
London | 15
México D.F. | 10
São Paulo | 6
Buenos Aires | 3
```

### Example 4: Every category with every shipper

There is no `ON` clause, so every one of the 8 categories is paired with every one of the 3 shippers. The first six of the 24 rows are shown. A grid like this is the starting point for "which combinations had no sales", and combined with a left join it is how analysts fill gaps in a report.

```sql run
SELECT c.category_id, c.category_name, s.shipper_id, s.company_name AS shipper
FROM categories c
CROSS JOIN shippers s
ORDER BY c.category_id, s.shipper_id
LIMIT 6;
```

```output
category_id | category_name | shipper_id | shipper
1 | Beverages | 1 | Speedy Express
1 | Beverages | 2 | United Package
1 | Beverages | 3 | Federal Shipping
2 | Condiments | 1 | Speedy Express
2 | Condiments | 2 | United Package
2 | Condiments | 3 | Federal Shipping
```

### Example 5: An order with customer, employee and shipper

Four tables, three join conditions, and each one connects a new table to `orders`. Every join here is many-to-one (an order has one customer, one employee, one shipper), so the number of rows stays equal to the number of orders. Orders without an employee would drop out of this chain, because the joins are inner.

```sql run
SELECT o.order_id, c.company_name AS customer, e.last_name AS employee, sh.company_name AS shipper
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
JOIN employees e ON e.employee_id = o.employee_id
JOIN shippers sh ON sh.shipper_id = o.ship_via
ORDER BY o.order_id
LIMIT 3;
```

```output
order_id | customer | employee | shipper
10248 | Alfreds Futterkiste | Davolio | Speedy Express
10249 | Ana Trujillo Emparedados | Fuller | United Package
10250 | Antonio Moreno Taquería | Leverling | Federal Shipping
```

### Example 6: Keeping every customer through a chain

The chain goes from `customers` to `orders` to `order_details`, and both joins are left joins. The result keeps every customer, including FISSA and PARIS: 252 rows are the 250 order lines plus those two customers, and the distinct customer count is 91. If the last join were an inner join, the two customers would drop out again, leaving 250 rows and 89 customers.

```sql run
SELECT COUNT(*) AS result_rows,
       COUNT(DISTINCT c.customer_id) AS customers,
       COUNT(od.product_id) AS order_lines
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
LEFT JOIN order_details od ON od.order_id = o.order_id;
```

```output
result_rows | customers | order_lines
252 | 91 | 250
```

## Real-world applications

**Organisation charts.** Employee to manager (example 1) and direct report counts (example 2) are the basis of headcount, span-of-control and escalation reports. The same shape handles category trees and bills of materials.

**Duplicate and pair analysis.** Pairing rows of one table (example 3) finds customers who share an address, products with the same supplier, or events that happen close together. The `<` trick keeps the pair list free of mirror images.

**Complete grids.** A cross join (example 4) generates every month by every region, or every category by every shipper, so that empty cells can be shown as zero instead of being missing from a report.

**Star-shaped reports.** An order with its customer, employee and shipper (example 5), or a customer-to-lines chain like example 6, are typical dashboard queries. Knowing the grain after each join keeps the totals right.

## Daily review

### Key takeaways

- A self join uses the same table twice with two aliases; `reports_to = employee_id` links employees to managers.
- Pairs inside one table need `a.id < b.id` to avoid self pairs and duplicates.
- `CROSS JOIN` has no condition and returns rows(A) x rows(B).
- A chain of N tables needs N-1 join conditions; add tables one at a time and check row counts.
- Inner joins are order independent; after an outer join, a later inner join on the optional table removes unmatched rows.

### Common mistakes

- Using the same table twice without aliases: "table name "employees" specified more than once". Give each copy an alias.
- Forgetting a join condition between two tables in a chain and getting a huge row count (a cross join). Count rows after each added table.
- Listing every pair twice because the condition is `a.id <> b.id` instead of `a.id < b.id`.
- Using an inner self join for a hierarchy and losing the top person. Use `LEFT JOIN`.
- Mixing a `LEFT JOIN` followed by an inner `JOIN` and losing the unmatched rows.
- Summing an order-level column after joining to order lines in a longer chain (day 40's trap, now with more tables).

### Revision notes

- Self join: `FROM t a JOIN t b ON a.fk = b.pk`, always with two aliases.
- Pair: `ON a.x = b.x AND a.id < b.id`.
- `CROSS JOIN`: 8 categories x 3 shippers = 24.
- N tables, N-1 conditions; outer then inner undoes the outer join.

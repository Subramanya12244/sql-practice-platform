## Objectives

- Declare dependencies with `>>`, `<<` and lists, including fan-out and fan-in, and read the resulting graph.
- Pass small values between tasks with XComs (`xcom_push`, `xcom_pull`, return values, TaskFlow) and say what should not go in an XCom.
- Group tasks with a task group and explain how it changes task ids but not behaviour.
- Branch with a branching task, explain the `skipped` state, and choose a trigger rule for the join task.

## Understand

### Dependencies

Day 157 introduced `a >> b`: `b` runs after `a`. `a << b` is the same relation written the other way round. A list on one side fans out or fans in: `extract >> [clean, enrich] >> load` means two tasks that both start after `extract` and run in parallel, and `load` waits for both. A list may stand on only one side of an operator: `[a, b] >> [c, d]` is an error in Airflow, because it is ambiguous whether you want every pair; the helper `cross_downstream` exists for that case. Every `>>` adds edges to the graph, and the scheduler starts a task when its dependencies are satisfied; by default the condition is that all upstream tasks have `success`. Dependencies describe order only. They do not move data: a task cannot see the output of the previous task unless you pass it explicitly, which is the job of XComs.

### XComs

**XCom** (cross-communication) lets tasks exchange small messages. A task **pushes** a value under a key, and another task **pulls** it. The value is stored in the metadata database together with the task id, the run and the key, so it survives a worker restart and is visible in the web interface. The easiest way to push is to return a value from a task function: Airflow stores it under the key `return_value`. A downstream task pulls it with `ti.xcom_pull(task_ids="extract")`, where `ti` is the task instance. The **TaskFlow API** hides this: functions decorated with `@task` are tasks, and calling `load(transform(extract()))` both creates the dependencies and passes the values through XComs.

The rule that follows from the storage is: XComs carry small, serialisable values such as a row count, a file path, a date or a short list of ids. They do not carry data frames or files. Putting a million rows in an XCom loads the metadata database, which every component depends on, and can fail outright because databases limit the size of a stored value. The standard pattern is to write the data to a file, table or object store inside the task and pass its location through the XCom. A second, subtler fact: an XCom belongs to one DAG run, so a task never reads the value of another day's run by accident.

### Task groups

A **task group** collects related tasks under one name so that the graph view can collapse them. Tasks created inside `with TaskGroup(group_id="clean"):` get the id prefix `clean.`, for example `clean.strip` and `clean.dedupe`, which keeps ids unique when two groups both have a task called `validate`. A group changes how the graph is drawn and the task ids; it adds no behaviour of its own, and dependencies can be set on the group as a whole (`extract >> clean >> load`). A misconception is that a group is a sub-pipeline with its own schedule or retries; it is not.

### Branching

Sometimes only one of several paths should run: a full load on the first day of the month and an incremental load on other days. A **branching** task is a task whose function returns the `task_id` (or a list of ids) to follow; Airflow gives the other direct downstream tasks the state `skipped`. `skipped` is neither success nor failure: the task was deliberately not run. By default a task runs only if all its upstream tasks succeeded, and a skipped upstream task makes the downstream task skipped too. That breaks the join task after the branches, `report`, which would be skipped whichever way the branch went. The fix is a **trigger rule**, the condition under which a task starts. `all_success` is the default. `all_done` starts when all upstream tasks have finished in any state. `none_failed_min_one_success` starts when nothing failed and at least one upstream task succeeded, which is exactly what a join after a branch needs. The rule names exist in Airflow 2 and are stable, but check the documentation of your version for the full list.

### Why it matters

Real DAGs fan out over sources, pass counts and paths forward, keep large graphs readable with groups and choose paths with branches. Knowing what is stored and what is skipped prevents the three common failures: a metadata database full of XCom data, a join that never runs, and a `skipped` task misread as a failure.

## Syntax and key functions

An Airflow 2.x TaskFlow DAG (shown, not run):

```python
from datetime import datetime
from airflow.decorators import dag, task


@dag(dag_id="orders_flow", start_date=datetime(2025, 1, 1), schedule="@daily", catchup=False)
def orders_flow():
    @task
    def extract():
        return [{"order_id": 1, "amount_cents": 1200}, {"order_id": 2, "amount_cents": 800}]

    @task
    def transform(rows):
        return sum(r["amount_cents"] for r in rows)

    @task
    def load(total):
        print(f"total {total}")

    load(transform(extract()))


orders_flow()
```

`@dag` turns the function into a DAG; `@task` turns functions into tasks. `extract()` returns a list, which Airflow stores as an XCom. `transform(rows)` receives it, and the call `transform(extract())` creates the dependency `extract >> transform`. A branch with a group and a join (also shown, not run):

```python
from datetime import datetime
from airflow import DAG
from airflow.operators.empty import EmptyOperator
from airflow.operators.python import BranchPythonOperator
from airflow.utils.task_group import TaskGroup


def choose(ds, **context):
    return "full_load" if datetime.strptime(ds, "%Y-%m-%d").day == 1 else "incremental_load"


with DAG(dag_id="orders_branch", start_date=datetime(2025, 1, 1), schedule="@daily", catchup=False) as dag:
    extract = EmptyOperator(task_id="extract")
    with TaskGroup(group_id="clean") as clean:
        strip = EmptyOperator(task_id="strip")
        dedupe = EmptyOperator(task_id="dedupe")
        strip >> dedupe
    pick = BranchPythonOperator(task_id="pick", python_callable=choose)
    full_load = EmptyOperator(task_id="full_load")
    incremental_load = EmptyOperator(task_id="incremental_load")
    report = EmptyOperator(task_id="report", trigger_rule="none_failed_min_one_success")
    extract >> clean >> pick >> [full_load, incremental_load] >> report
```

The branch function returns the id of the path to take. The task ids inside the group are `clean.strip` and `clean.dedupe`. The `report` task declares the trigger rule that lets it run after a branch. In Airflow 3 some imports move (for example to `airflow.sdk`); check the documentation of your version.

| Item | Meaning |
|---|---|
| `a >> b`, `a << b` | `b` after `a`; `a` after `b`. |
| `a >> [b, c]`, `[b, c] >> d` | Fan-out; fan-in. |
| `ti.xcom_push(key, value)`, `ti.xcom_pull(task_ids=...)` | Store and read a small value. |
| return value | Pushed under key `return_value`. |
| `TaskGroup(group_id=...)` | Prefixes the ids of its tasks with `group_id.`. |
| branch return value | The task id(s) to follow; the others become `skipped`. |
| `trigger_rule` | When a task starts: `all_success` (default), `all_done`, `none_failed_min_one_success`, and others. |

## Learn by example

All examples use a pure-Python model of these ideas (a `Dag` with `link(ups, downs)`, tasks that receive a `ti` object with `xcom_push` and `xcom_pull`, branching and trigger rules). The model is verified here; it is not Airflow.

### Example 1: Dependencies and fan-in

`extract >> [clean, enrich] >> load` in the model is two calls of `link`. The levels show which tasks can run together.

```python run
class TI:
    def __init__(self, store, task_id):
        self.store = store
        self.task_id = task_id

    def xcom_push(self, key, value):
        self.store[(self.task_id, key)] = value

    def xcom_pull(self, task_ids, key="return_value"):
        return self.store.get((task_ids, key))


class Dag:
    def __init__(self, dag_id):
        self.dag_id = dag_id
        self.tasks = {}
        self.upstream = {}

    def add_task(self, task_id, func=None, rule="all_success", branch=False):
        if task_id in self.tasks:
            raise ValueError(f"duplicate task_id {task_id}")
        self.tasks[task_id] = {"func": func, "rule": rule, "branch": branch}
        self.upstream[task_id] = set()

    def link(self, ups, downs):
        ups = [ups] if isinstance(ups, str) else ups
        downs = [downs] if isinstance(downs, str) else downs
        for down in downs:
            self.upstream[down].update(ups)

    def levels(self):
        remaining = {t: set(u) for t, u in self.upstream.items()}
        result = []
        while remaining:
            ready = sorted(t for t, u in remaining.items() if not u)
            if not ready:
                raise ValueError("cycle detected")
            result.append(ready)
            for t in ready:
                del remaining[t]
            for u in remaining.values():
                u.difference_update(ready)
        return result


def decide(rule, up_states):
    bad = [s for s in up_states if s in ("failed", "upstream_failed")]
    if rule == "all_done":
        return "run"
    if bad:
        return "upstream_failed"
    if rule == "all_success":
        return "skipped" if "skipped" in up_states else "run"
    if rule == "none_failed_min_one_success":
        return "skipped" if up_states and all(s == "skipped" for s in up_states) else "run"
    raise ValueError(f"unknown rule {rule!r}")


def run_dag(dag):
    states, store, forced_skip = {}, {}, set()
    for level in dag.levels():
        for task_id in level:
            task = dag.tasks[task_id]
            up_states = [states[u] for u in dag.upstream[task_id]]
            verdict = "skipped" if task_id in forced_skip else decide(task["rule"], up_states)
            if verdict != "run":
                states[task_id] = verdict
                continue
            try:
                result = task["func"](TI(store, task_id)) if task["func"] else None
            except Exception:
                states[task_id] = "failed"
                continue
            states[task_id] = "success"
            if result is not None:
                store[(task_id, "return_value")] = result
            if task["branch"]:
                chosen = {result} if isinstance(result, str) else set(result)
                for t, ups in dag.upstream.items():
                    if task_id in ups and t not in chosen:
                        forced_skip.add(t)
    return states, store


dag = Dag("orders")
for task_id in ["extract", "clean", "enrich", "load"]:
    dag.add_task(task_id)
dag.link("extract", ["clean", "enrich"])
dag.link(["clean", "enrich"], "load")
print(dag.levels())
states, store = run_dag(dag)
print(states)
```

```output
[['extract'], ['clean', 'enrich'], ['load']]
{'extract': 'success', 'clean': 'success', 'enrich': 'success', 'load': 'success'}
```

`clean` and `enrich` are in the same level, so they may run at the same time, and `load` is alone in the last level because it needs both. All four tasks succeed. Dependencies fixed only the order.

### Example 2: Passing values through XComs

`extract` returns rows (stored as `return_value`). `transform` pulls them, pushes a second value with an explicit key and returns the total. `load` pulls both. The final store shows what the metadata database would hold for this run.

The `loaded 2 rows, total 2000` line is printed by `load` while the DAG runs. A value is addressed by task id and key. If a task pulls from a task that never pushed, it gets `None`, a common source of confusing downstream errors.

The join with `none_failed_min_one_success` ran because nothing failed and one branch succeeded. If `full_load` had failed instead, both reports would have been `upstream_failed`.

## Real-world applications

- A pipeline that ingests five sources fans out five extract tasks, fans in to one load task, and passes each extract's row count to a reconciliation task through XComs (Examples 1 and 2).
- A DAG with thirty tasks groups them into `ingest`, `clean` and `publish` so that the graph view stays readable (Example 3).
- A job runs a full refresh on the first of the month and an incremental load on other days with a branch, and uses a join rule so the final report always runs (Example 4).

## Daily review

### Key takeaways

- `>>` sets order; a list fans out or in, and a list cannot be on both sides.
- XComs carry small values (counts, paths, ids) by task id and key; return values use `return_value`; large data goes in files or tables.
- Task groups prefix task ids and organise the graph; they add no behaviour.
- A branch returns the id to follow, the rest are `skipped`; a join after a branch needs `none_failed_min_one_success`.

### Common mistakes

- Putting a data frame in an XCom. Symptom: a slow, bloated metadata database or a serialisation error. Fix: write the data to storage and pass the path.
- Writing `[a, b] >> [c, d]`. Symptom: an error when the DAG is parsed. Fix: use `cross_downstream` or an intermediate task.
- Leaving the default rule on the join after a branch. Symptom: the report is always skipped. Fix: use `none_failed_min_one_success`.
- Reading `skipped` as a failure. Symptom: time spent debugging a task that was never meant to run. Fix: look at the branch decision.

### Revision notes

- `ti.xcom_push(key, value)`, `ti.xcom_pull(task_ids, key="return_value")`.
- Group ids: `group_id.task_id`.
- States: `success`, `failed`, `upstream_failed`, `skipped`.

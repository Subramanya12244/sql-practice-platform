## Objectives

- Declare primary key, foreign key, `NOT NULL`, `UNIQUE` and `CHECK` constraints and explain what each rejects.
- Order a multi-table load so that every foreign key points at a row that already exists, and order deletes the other way round.
- Separate the rows a load can accept from the rows a constraint would reject, and keep the rejected rows with a reason.
- Catch constraint errors in Python, name the kind of violation, and explain how a PostgreSQL transaction behaves after an error.
- Prove a load by showing that accepted rows plus rejected rows equal the rows that were read.

## Understand

### Constraints are the database's promises

A **constraint** is a rule that the database enforces on every write. Because the database enforces it, the rule holds for every program that writes, not only for yours. Day 92 introduced them as design; today you load data into tables that have them, and the constraints become the first reviewer of your data.

- A **primary key** is a column or column group that is unique and never empty and identifies one row. A second row with the same key is rejected.
- A **foreign key** says that a column's value must exist as a key in another table. An order with `customer_key = 9` is rejected when no customer 9 exists.
- **`NOT NULL`** rejects an empty value in that column.
- **`UNIQUE`** rejects a repeated value where a primary key is not appropriate, such as an email address.
- **`CHECK`** rejects values that fail a condition, such as `amount_cents >= 0`.

Each violation has a name. In PostgreSQL the error carries a five-character code called an **SQLSTATE**: `23505` for a unique violation (including a primary key), `23503` for a foreign key violation, `23502` for `NOT NULL` and `23514` for `CHECK`. In Python, `psycopg` raises subclasses of `IntegrityError` for these (`UniqueViolation`, `ForeignKeyViolation`, and so on). In `sqlite3`, all of them raise `sqlite3.IntegrityError` and the message names the rule, for example `UNIQUE constraint failed: customer.email`.

### Load order

A foreign key creates a dependency. If `sales_order` points at `customer`, the customers must exist first. **Load parents before children**: customers and products, then orders, then order lines. When you delete or reload, the order reverses: children first, then parents, because deleting a customer who still has orders would orphan them (the database would refuse, or cascade the delete if a rule says so). In a schema with many tables you can compute the order from the dependencies; any ordering in which every table comes after the tables it references works. A circular dependency (a table referencing a table that references it) cannot be loaded in either order; it needs a deferred constraint or a two-step load, which is rare in a load you design yourself.

### Accepting and rejecting rows

There are two strategies. The first is **let the database reject**: insert and catch the error. It is simple and the constraint is always right, but a bulk statement stops at the first bad row, and in PostgreSQL the whole transaction is then **aborted**: every further command in it fails with "current transaction is aborted" until you `ROLLBACK`. The second is **pre-validate**: find the rows that would violate a rule (a join to the parent table shows orphans, a `GROUP BY` shows duplicates, a comparison shows a negative amount), set them aside in a **reject table** with a reason column, and insert the rest. Pre-validation produces a report a person can act on; the constraints remain as the safety net that guarantees nothing slipped through.

Row-by-row insertion with a `try` around each row is a third option for small loads: slow, but it records the exact error for each bad row. In PostgreSQL each attempt needs its own **savepoint** (a marker you can roll back to without abandoning the whole transaction), otherwise one failure aborts everything. `sqlite3` does not abort a transaction on a failed statement, which is one place where the stand-in behaves more gently than PostgreSQL.

### Duplicates and re-runs

Constraints interact with the idempotency work of Day 94. A primary key makes a plain rerun fail loudly on the first duplicate, which is better than silent double loading but still a failed run. `INSERT ... ON CONFLICT (key) DO NOTHING` skips rows whose key already exists and `DO UPDATE` replaces them. Both need the key declared as a primary key or unique constraint.

### Reconciliation at the end

After any load, the arithmetic must close: **rows read = rows loaded + rows rejected** (and rows skipped as duplicates, if you count those). If it does not, rows disappeared. Print the three numbers and make the job fail when they disagree; Day 100 builds this into a report.

### Common misconception

Learners think constraints slow the pipeline and switch them off for the load ("I will add the keys afterwards"). The result is a table that accepted duplicates and orphans, and creating the key later then fails on the bad data, or succeeds only after someone removes rows by hand. Load into constrained tables and let the rejects surface now, while the source file is at hand. A related belief is that `sqlite3` enforces foreign keys by default. It does not: you must run `PRAGMA foreign_keys = ON` on each connection. PostgreSQL always enforces them.

### Why it matters

Orphans and duplicates are the usual cause of wrong numbers downstream: a join drops orders, a sum counts a row twice. A load that rejects bad rows into a reject table, with a reason, turns invisible data problems into a short list that the data owner can fix at the source.

## Syntax and key functions

Table definition with all five constraint kinds (PostgreSQL syntax):

```sql-syntax
CREATE TABLE customer (
    customer_key integer PRIMARY KEY,
    email        text NOT NULL UNIQUE
);
CREATE TABLE sales_order (
    order_id     integer PRIMARY KEY,
    customer_key integer NOT NULL REFERENCES customer (customer_key),
    amount_cents integer NOT NULL CHECK (amount_cents >= 0)
);
```

Catching violations with `psycopg` on PostgreSQL (placeholders are `%s`; not run here because there is no server):

```python
import psycopg
from psycopg import errors

with psycopg.connect(dsn) as conn:
    try:
        with conn.transaction():                 # a savepoint when nested
            conn.execute("INSERT INTO sales_order VALUES (%s, %s, %s)", (12, 9, 300))
    except errors.ForeignKeyViolation as err:    # SQLSTATE 23503
        reject(12, str(err.diag.message_primary))
    except errors.UniqueViolation:               # SQLSTATE 23505
        reject(12, "duplicate key")
```

| Item | What it does or returns |
|---|---|
| `PRIMARY KEY`, `UNIQUE` | Reject a second row with the same value (`23505`). |
| `REFERENCES parent (key)` | Foreign key; rejects a value with no parent row (`23503`). |
| `NOT NULL`, `CHECK (cond)` | Reject empty values (`23502`) or failed conditions (`23514`). |
| `INSERT ... SELECT ... JOIN parent` | Inserts only rows whose parent exists. |
| `ON CONFLICT (key) DO NOTHING` | Skips rows whose key exists (SQLite 3.24+ and PostgreSQL). |
| `PRAGMA foreign_keys = ON` | Turns on foreign key enforcement in `sqlite3` only. |
| `sqlite3.IntegrityError` | Raised for every constraint violation in `sqlite3`. |
| `conn.transaction()` (`psycopg`) | Transaction block, a savepoint when nested. |

## Learn by example

### Example 1: The database rejects a child before its parent

`sqlite3` is the stand-in here. Foreign keys are off by default in SQLite, so the first insert succeeds and leaves an orphan; after `PRAGMA foreign_keys = ON` the same insert is rejected. Loading the parent first works. PostgreSQL behaves like the second case without any pragma.

```python run
import sqlite3

def make():
    conn = sqlite3.connect(":memory:")
    conn.executescript("""
    CREATE TABLE customer (customer_key INTEGER PRIMARY KEY, email TEXT NOT NULL UNIQUE);
    CREATE TABLE sales_order (order_id INTEGER PRIMARY KEY,
        customer_key INTEGER NOT NULL REFERENCES customer (customer_key),
        amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0));
    """)
    return conn

conn = make()
conn.execute("INSERT INTO sales_order VALUES (10, 9, 500)")
print("pragma off, orphan stored:", conn.execute("SELECT COUNT(*) FROM sales_order").fetchone()[0])

conn = make()
conn.execute("PRAGMA foreign_keys = ON")
try:
    conn.execute("INSERT INTO sales_order VALUES (10, 1, 500)")
except sqlite3.IntegrityError as err:
    print("child first:", err)
conn.execute("INSERT INTO customer VALUES (1, 'ana@x.com')")
conn.execute("INSERT INTO sales_order VALUES (10, 1, 500)")
for sql in ["INSERT INTO customer VALUES (2, 'ana@x.com')",
            "INSERT INTO sales_order VALUES (10, 1, 600)",
            "INSERT INTO sales_order VALUES (11, 1, -5)",
            "INSERT INTO customer VALUES (3, NULL)"]:
    try:
        conn.execute(sql)
    except sqlite3.IntegrityError as err:
        print(err)
```

```output
pragma off, orphan stored: 1
child first: FOREIGN KEY constraint failed
UNIQUE constraint failed: customer.email
UNIQUE constraint failed: sales_order.order_id
CHECK constraint failed: amount_cents >= 0
NOT NULL constraint failed: customer.email
```

Each message names the violated rule. The second block is what the load code catches and reports.

### Example 2: Compute a load order from the dependencies

Each table lists the tables it references. The function returns an order in which every table follows its parents; reversing it gives the delete order. A circular dependency is reported instead of looping forever.

```python run
def load_order(depends_on):
    order, placed = [], set()
    remaining = dict(depends_on)
    while remaining:
        ready = sorted(t for t, parents in remaining.items() if set(parents) <= placed)
        if not ready:
            raise ValueError("circular dependency among: " + ", ".join(sorted(remaining)))
        for t in ready:
            order.append(t)
            placed.add(t)
            del remaining[t]
    return order

schema = {
    "order_line": ["sales_order", "product"],
    "sales_order": ["customer"],
    "customer": [],
    "product": [],
}
order = load_order(schema)
print(order)
print(list(reversed(order)))
try:
    load_order({"a": ["b"], "b": ["a"]})
except ValueError as err:
    print(err)
```

```output
['customer', 'product', 'sales_order', 'order_line']
['order_line', 'sales_order', 'product', 'customer']
circular dependency among: a, b
```

### Example 3: Pre-validate, load the good rows, keep the rejects

Staged rows are classified before loading: an orphan customer, a negative amount and a duplicate order id each get a reason. The good rows load in one transaction and the rest go to a reject table with the reason. The last line is the reconciliation: read = loaded + rejected.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("PRAGMA foreign_keys = ON")
conn.executescript("""
CREATE TABLE customer (customer_key INTEGER PRIMARY KEY);
CREATE TABLE sales_order (order_id INTEGER PRIMARY KEY,
    customer_key INTEGER NOT NULL REFERENCES customer (customer_key),
    amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0));
CREATE TABLE reject (order_id INTEGER, reason TEXT);
""")
conn.executemany("INSERT INTO customer VALUES (?)", [(1,), (2,)])
staged = [(10, 1, 500), (11, 2, 700), (12, 9, 300), (13, 1, -50), (10, 1, 500), (14, 2, 100)]

known = {row[0] for row in conn.execute("SELECT customer_key FROM customer")}
good, seen = [], set()
rejects = []
for order_id, customer_key, amount in staged:
    if customer_key not in known:
        rejects.append((order_id, "unknown customer"))
    elif amount < 0:
        rejects.append((order_id, "negative amount"))
    elif order_id in seen:
        rejects.append((order_id, "duplicate order"))
    else:
        seen.add(order_id)
        good.append((order_id, customer_key, amount))

with conn:
    conn.executemany("INSERT INTO sales_order VALUES (?, ?, ?)", good)
    conn.executemany("INSERT INTO reject VALUES (?, ?)", rejects)
loaded = conn.execute("SELECT COUNT(*) FROM sales_order").fetchone()[0]
print(conn.execute("SELECT order_id, reason FROM reject ORDER BY order_id, reason").fetchall())
print("read", len(staged), "loaded", loaded, "rejected", len(rejects), loaded + len(rejects) == len(staged))
```

```output
[(10, 'duplicate order'), (12, 'unknown customer'), (13, 'negative amount')]
read 6 loaded 3 rejected 3 True
```

### Example 4: The same load on PostgreSQL syntax (PGlite)

This runs on PGlite, a PostgreSQL engine in the browser. The tables carry the same constraints. The `INSERT ... SELECT` joins to the parent and filters, `DISTINCT` removes the repeated staged row, and `ON CONFLICT DO NOTHING` makes a rerun harmless. The final query reports the counts: how many orders were loaded, and how many staged rows were orphans or negative.

```sql run
CREATE TABLE customer (customer_key integer PRIMARY KEY, email text NOT NULL UNIQUE);
CREATE TABLE sales_order (
    order_id integer PRIMARY KEY,
    customer_key integer NOT NULL REFERENCES customer (customer_key),
    amount_cents integer NOT NULL CHECK (amount_cents >= 0));
CREATE TABLE stg_order (order_id integer, customer_key integer, amount_cents integer);
INSERT INTO customer VALUES (1, 'ana@x.com'), (2, 'ben@x.com');
INSERT INTO stg_order VALUES (10, 1, 500), (11, 2, 700), (12, 9, 300), (13, 1, -50), (10, 1, 500), (14, 2, 100);
INSERT INTO sales_order
SELECT DISTINCT s.order_id, s.customer_key, s.amount_cents
FROM stg_order s
JOIN customer c ON c.customer_key = s.customer_key
WHERE s.amount_cents >= 0
ON CONFLICT (order_id) DO NOTHING;
SELECT 'loaded' AS what, count(*) AS n FROM sales_order
UNION ALL
SELECT 'orphans', count(*) FROM stg_order s WHERE NOT EXISTS (SELECT 1 FROM customer c WHERE c.customer_key = s.customer_key)
UNION ALL
SELECT 'negative', count(*) FROM stg_order WHERE amount_cents < 0
ORDER BY what;
```

```output
what | n
loaded | 3
negative | 1
orphans | 1
```

On a real PostgreSQL server the same statements work unchanged, and the `psycopg` code from the syntax section catches the violations that the filter would have prevented.

## Real-world applications

- **Nightly order loads.** Staging, then an `INSERT ... SELECT` joined to the customer table, then a reject table: finance sees "12 orders had an unknown customer" instead of a failed job.
- **Reference data.** Loading `product` before `order_line` is a computed order in a scheduler; the reversed order is the safe teardown for a test database.
- **Partner files with bad rows.** A `CHECK` on amount and a unique email catch the same defects a reviewer would, on every future file too.
- **Audit trail.** Rows read = loaded + rejected is the number an auditor asks for.

## Daily review

### Key takeaways

- Constraints are rules the database enforces for every writer; each violation has a name and a code.
- Load parents before children and delete in the reverse order.
- Pre-validate to build a reject list with reasons; keep the constraints as the safety net.
- A failed statement aborts a PostgreSQL transaction until rollback or savepoint; `sqlite3` is gentler.
- Reconcile: read = loaded + rejected.

### Common mistakes

- **Foreign keys off in `sqlite3`.** Orphans load silently. Run `PRAGMA foreign_keys = ON` on every connection.
- **Disabling constraints for speed.** The table accepts bad rows and adding the key later fails. Load with the constraints on.
- **Catching `Exception` and moving on.** Real bugs are swallowed. Catch the integrity error class and record the reason.
- **One bad row failing the whole batch.** Without pre-validation or savepoints the job restarts from nothing. Classify first.
- **Wrong delete order.** Deleting a parent first fails with a foreign key error. Reverse the load order.

### Revision notes

- PK, FK, NOT NULL, UNIQUE, CHECK and what each rejects.
- SQLSTATE 23505, 23503, 23502, 23514; `sqlite3.IntegrityError`.
- Order: parents first; delete: children first.

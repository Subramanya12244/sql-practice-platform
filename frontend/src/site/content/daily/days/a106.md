## Objectives

- Explain what exploratory data analysis (EDA) is for and write the questions an exploration must answer before opening any data.
- Profile a new table: its shape, column types, missing values, distinct counts and value ranges.
- Run data-quality checks for duplicates, impossible values, inconsistent labels and internal contradictions.
- Keep a written log of assumptions and decisions, so that every cleaning step can be justified later.
- Apply a repeatable EDA checklist that turns a first look at the data into a plan.

## Understand

### What EDA is, and what it is not

**Exploratory data analysis (EDA)** is the practice of examining a dataset to learn what it contains, how trustworthy it is and which questions it can answer, before building a final report, dashboard or model. The word "exploratory" matters. A report answers a known question with a finished number. EDA is the work done earlier: finding out what the columns mean, noticing that a quarter of the ratings are missing, discovering that two rows are the same order entered twice, and deciding which of the business questions the data can actually support.

It is not "run every chart and see what pops out". Looking at many variables without a question invites **false discoveries**: with enough charts and comparisons, something will look interesting by chance, a problem you met in A/B testing on Day 105 when many metrics were checked. Good EDA is a disciplined loop of asking a question, checking the data, recording what you found and refining the next question.

### Questions first

Start from the decision the analysis supports. "Why did revenue fall in May?" and "Which channel brings customers who return fewer orders?" are questions. "Explore the orders table" is not. A useful question is specific, names the metric and can be wrong. For each question, write down the columns you would need, the definition of the metric (for example, is revenue before or after discounts?) and what answer would change a decision. This first step often reveals that the data cannot answer the question, which is valuable to learn before spending a day on it.

Treat the first questions as a plan, not a promise. EDA produces surprises, and surprises generate better questions. Write the new ones down as they appear instead of chasing them immediately.

### Profiling: the first look

**Profiling** means producing a compact description of every column. For each column you record its data type, how many values are present or missing, how many distinct values it holds, and for numbers the minimum, maximum and typical value. You used the pieces on Day 70 (`head`, `info`, `describe`, `value_counts`) and Day 74 (missing values). Profiling puts them in one table so that you can scan the whole dataset at a glance.

Read a profile like a detective. A column with 100% distinct values is probably an identifier. A column with one distinct value carries no information. A numeric column stored as text (type `object`) usually contains a stray symbol. A date column stored as strings cannot be sorted or resampled. Missing values need two questions: how many, and are they missing at random, or for a reason? (Day 109 returns to that.)

### Data-quality checks

After profiling, test specific things that commonly go wrong.

- **Duplicates.** Fully repeated rows, or repeated values in a column that should be unique, such as an order id.
- **Impossible values.** A negative quantity, a rating of 7 on a five-point scale, a ship date before the order date.
- **Inconsistent labels.** The same category written as `paid`, `Paid ` and `PAID` counts as three groups until cleaned. Trailing spaces are invisible when printed, but `value_counts` exposes them.
- **Internal contradictions.** Columns that must agree, such as `order_total` against quantity x price x (1 - discount). A mismatch means one of the fields is wrong.
- **Range and coverage.** Does the date range match the period you were told? Does the data stop early, or have gaps?

Each check should produce a number, not an impression. "6 duplicate rows" can be acted on and defended; "a few duplicates" cannot.

### Documenting assumptions

Every decision in an exploration rests on an assumption: "a missing rating means the customer did not rate", "an order total is in dollars", "rows with a negative quantity are data-entry errors, not returns". Write each one down with the evidence that supports it and what you did about it. This **assumptions log** is the difference between an analysis someone can trust and one they must redo. It also protects you: when a stakeholder asks why 6 rows vanished, the log has the answer. Keep the raw data untouched, apply cleaning in code that can be rerun, and record how many rows each step changed.

### A repeatable checklist

Experienced analysts follow roughly the same sequence every time: state the questions and the metric definitions; load the data and confirm the shape matches what was promised; profile every column; check quality (duplicates, impossible values, labels, contradictions, range); decide and document how to treat each issue; only then move on to distributions and relationships, which the next days cover. A checklist is not bureaucracy. It stops you skipping the dull step that later turns out to explain the strange result.

### A running example

The next five days use one small online-store dataset of orders, created in code with a seeded random generator so that numbers are repeatable. Each row is one order with an id, date, customer, channel, device, category, quantity, unit price, discount, shipping days, order total, rating and a returned flag. In this lesson a messy version is used on purpose, with a few planted problems for you to find.

### Common misconception

"EDA is optional if the data comes from a database." A database enforces types and keys, but it does not know that a rating should be between 1 and 5 or that two orders with different ids are the same purchase. Another misconception is that the first cleaning pass is silent housekeeping. Every row you drop or value you fill changes the answer, so each is a decision that belongs in the log.

### Why it matters

Most wrong analyses fail on the data, not on the statistics. A mean calculated over duplicated rows, a growth rate across a partial month or a comparison of mislabelled groups can all be perfectly computed and still wrong. Profiling and quality checks are cheap insurance against that.

## Syntax and key functions

Profile a table:

```python
profile = pd.DataFrame({
    "dtype": df.dtypes.map(lambda t: {"i": "integer", "u": "integer", "f": "float", "b": "bool", "M": "datetime", "O": "text"}[t.kind]),
    "non_null": df.notna().sum(),
    "missing_pct": (df.isna().mean() * 100).round(1),
    "unique": df.nunique(),
})
```

Each line builds one column of the profile from a function that returns one value per column of `df`.

Quality checks:

```python
df.duplicated().sum()
df["col"].str.strip().str.lower().nunique()
(df["quantity"] <= 0).sum()
(df["a"] - df["b"]).abs().gt(0.01).sum()
```

| Function | Returns |
|---|---|
| `df.shape` | Tuple of row and column counts. |
| `df.dtypes` | Data type of each column. |
| `df.isna().mean()` | Share of missing values per column. |
| `df.nunique()` | Distinct non-missing values per column. |
| `df.duplicated()` | Boolean per row, `True` for repeats of an earlier row. |
| `df["c"].value_counts(dropna=False)` | Counts per value, including missing. |
| `df["c"].min()`, `.max()` | Range of a column. |
| `s.str.strip().str.lower()` | Labels with whitespace and case normalised. |

## Learn by example

### Example 1: Questions first

Before looking at a single row, the analyst writes the questions, the metric each one needs and the columns it depends on. A small check compares those needs with the columns the table was promised to have. This shows immediately which question cannot be answered yet.

```python run
questions = {
    "Which channel brings the most revenue?": ["channel", "order_total"],
    "Do late deliveries get lower ratings?": ["shipping_days", "rating"],
    "Which category is returned most often?": ["category", "returned"],
    "Does discount depth change basket size?": ["discount_pct", "quantity"],
    "What is the repeat-purchase rate by region?": ["region", "customer_id"],
}
available = ["order_id", "order_date", "customer_id", "channel", "device", "category",
             "quantity", "unit_price", "discount_pct", "shipping_days", "order_total",
             "rating", "returned"]

for question, needed in questions.items():
    missing = [c for c in needed if c not in available]
    status = "ready" if not missing else "blocked, needs " + ", ".join(missing)
    print(f"{status:<30} {question}")
```

### Example 2: The first look

The generator below builds the messy orders table that this lesson explores. The first look checks the shape, the column types and a few rows. A shape larger than expected, or a date column typed as `object`, would be the first thing to note.

```python run
import numpy as np
import pandas as pd

pd.set_option("display.width", 200)
pd.set_option("display.max_columns", 20)


def make_orders(messy=False):
    rng = np.random.default_rng(7)
    n = 600
    category = rng.choice(["home", "beauty", "sports", "electronics", "toys"], size=n, p=[0.30, 0.25, 0.20, 0.15, 0.10])
    base = pd.Series({"home": 40, "beauty": 25, "sports": 55, "electronics": 180, "toys": 20})
    discount = rng.choice([0, 5, 10, 20], size=n, p=[0.6, 0.15, 0.15, 0.1])
    ship = np.clip(rng.poisson(3.5, n) + 1, 1, 12).astype(float)
    df = pd.DataFrame({
        "order_id": np.arange(1001, 1001 + n),
        "order_date": pd.Timestamp("2025-01-01") + pd.to_timedelta(rng.integers(0, 180, n), unit="D"),
        "customer_id": rng.integers(1, 260, n),
        "channel": rng.choice(["organic", "paid", "email", "referral"], size=n, p=[0.4, 0.3, 0.2, 0.1]),
        "device": rng.choice(["mobile", "desktop", "tablet"], size=n, p=[0.55, 0.35, 0.10]),
        "category": category,
        "quantity": np.clip(rng.poisson(0.8 + discount / 20, n) + 1, 1, 6),
        "unit_price": (base[category].to_numpy() * rng.lognormal(0, 0.25, n)).round(2),
        "discount_pct": discount,
        "shipping_days": ship,
    })
    df.loc[rng.choice(n, 4, replace=False), "unit_price"] *= 8
    df["order_total"] = (df["quantity"] * df["unit_price"] * (1 - df["discount_pct"] / 100)).round(2)
    df["rating"] = np.clip(np.round(4.3 - 0.2 * ship + rng.normal(0, 0.8, n)), 1, 5)
    df["returned"] = rng.random(n) < 0.06 + 0.06 * (category == "electronics") + 0.03 * (ship > 6)
    df.loc[rng.random(n) < 0.05, "shipping_days"] = np.nan
    df.loc[rng.random(n) < 0.25, "rating"] = np.nan
    if messy:
        df.loc[rng.choice(n, 25, replace=False), "channel"] = "Paid "
        df.loc[rng.choice(n, 3, replace=False), "quantity"] = -1
        df = pd.concat([df, df.sample(6, random_state=1)], ignore_index=True)
    return df
orders = make_orders(messy=True)

print(orders.dtypes.map(lambda t: {"i": "integer", "u": "integer", "f": "float", "b": "bool", "M": "datetime", "O": "text"}[t.kind]).to_string())
print()
print(orders.head(3).to_string())

Putting it in a DataFrame makes it printable, filterable and easy to save with the analysis. The treatments are planned here, not yet applied; the raw table is left untouched.

## Real-world applications

- **Starting any new analysis.** Before a stakeholder meeting, an analyst runs a profile and a quality-check pass like Examples 3 and 4, so that the numbers presented later are not undermined by duplicates or mislabelled groups.
- **Inheriting a dataset.** When a table arrives from another team, the questions-first check in Example 1 shows which requests it can answer, and the assumptions log in Example 5 records what was assumed about its fields.
- **Data-quality monitoring.** The same checks, scheduled daily, catch a broken feed: a sudden rise in missing ratings or a new label spelling shows up as a changed number in the profile.
- **Handover and audit.** The log lets a colleague, or you in six months, see which rows were removed and why, and rerun the cleaning.

## Daily review

### Key takeaways

- EDA learns what the data holds and whether it is trustworthy; it starts from written questions, not from charts.
- A profile (type, missing share, distinct count, range) for every column is the fastest first look.
- Quality checks must return numbers: duplicates, impossible values, label variants, contradictions, date range.
- An assumptions log records each issue, the assumption and the treatment, and keeps the raw data untouched.
- A checklist makes the order repeatable: questions, load and shape, profile, quality, decisions, then analysis.

### Common mistakes

- Opening charts before writing any question, then reporting whatever looks interesting. Fix: write the questions and the metric definitions first.
- Trusting `describe()` alone. It ignores text columns and hides duplicates and label variants. Fix: add `value_counts`, `duplicated` and `nunique`.
- Missing trailing spaces, so `"paid"` and `"paid "` appear as separate groups. Fix: compare `nunique()` before and after `str.strip().str.lower()`.
- Dropping rows silently. The totals change and nobody knows why. Fix: count the rows affected and write the decision in the log.
- Overwriting the raw table with the cleaned one, so the original cannot be checked. Fix: clean into a new variable.
- Treating a missing value as zero. A missing rating is unknown, not a rating of 0.

### Revision notes

- EDA order: questions, shape and types, profile, quality checks, log, then distributions and relationships.
- Profile columns: dtype, non-null, missing %, unique, min, max.

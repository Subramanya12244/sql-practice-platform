## Understand

### Why servers say "slow down"

A **rate limit** is a cap on how many requests a client may send in a period, for example 100 per minute. Providers set limits to share capacity fairly and to protect themselves from a single noisy client. When you exceed the limit, a well-behaved server answers **`429 Too Many Requests`**, often with a **`Retry-After`** header: the number of seconds to wait before asking again (it can also be a date; a pipeline can fall back to its own backoff when it cannot read a number). Some providers add extra headers that report the remaining quota, but their names differ from provider to provider, so read the documentation instead of assuming. In the Orders API of this block, the server answers 429 with `Retry-After` on every third request in the practice examples, which is harsher than any real service and makes the behaviour easy to see.

The correct reaction to a 429 is to **wait and then repeat the same request**. The wrong reactions are to give up (the data is still wanted), to ignore the status and carry on (you skip a page without noticing), and to retry at once in a tight loop (you add to the overload and may be blocked for longer).

### Which failures are retryable

A **transient** failure is one that may succeed if you try again later: the service is busy (`429`, `503`), a gateway failed (`502`, `504`), the server had a temporary error (`500`), a read timed out, or the connection was reset. A **permanent** failure will give the same answer every time: `400` (malformed request), `401` and `403` (credentials), `404` (not found), `422` (invalid content). Retrying permanent failures wastes calls and delays the real fix. A retry policy is therefore a short table: this set of statuses and these exception types are retried; everything else is raised at once.

### Exponential backoff

If the server is struggling, the kind thing is to wait longer after each failure. **Exponential backoff** doubles the wait each time: with a base of 0.5 seconds, the waits are 0.5, 1, 2, 4, 8 seconds for attempts 1 to 5. A **cap** (for example 30 seconds) stops the waits from growing without limit. Together with a **maximum number of attempts** (for example 5) this bounds how long one failing call can hold up the job: the sum of the waits. After the last attempt, raise an error that names what failed; do not return a half result.

### Jitter

Imagine fifty workers all hit the limit at the same moment. With plain exponential backoff all fifty wait exactly 0.5 seconds, then retry together, hit the limit together, wait exactly 1 second, and so on: the retries arrive in synchronised waves, which is the **thundering herd** problem. **Jitter** adds randomness to the wait so that the retries spread out. The simplest form, called **full jitter**, waits a random time between 0 and the backoff value: `random.uniform(0, min(cap, base * 2 ** attempt))`. A `Retry-After` header takes precedence when present, because the server knows its own recovery time better than a formula does.

### Testing waiting code without waiting

Code that really sleeps makes tests slow, and random waits make output unpredictable. Both problems are solved by **injecting** the dependencies: the retry function receives a `sleep` function and a random generator as arguments. In production they are `time.sleep` and `random`; in tests, `sleep` is a function that only appends the requested wait to a list, and the generator is `random.Random(7)`, a generator seeded with a fixed number so that it produces the same sequence every time. The examples in this lesson do this, so they finish instantly and print the same numbers on every machine.

### Idempotent retries

Day 102 explained that `GET`, `PUT` and `DELETE` are idempotent and `POST` is not. A retry is safe when repeating the request cannot do harm. A timeout on a `POST /orders` is the dangerous case: the server may have created the order before the connection broke, and a retry creates a second one. Some APIs offer an **idempotency key**: the client generates a unique value for each logical operation and sends it in a header (providers commonly call it `Idempotency-Key`); the server remembers the key and, for a repeated request, returns the stored result instead of creating again. A pipeline that only reads, like this block's, has the easy case, but it must also make sure that a retried page is not appended twice to its own results: store a page only after it succeeds.

### Common misconception

Learners believe that retrying is always the safe default. It is safe only for transient failures of idempotent requests, with waits and a limit. Retrying a `401` ten times, or hammering a `429` without waiting, makes outages longer and can get a key blocked.

### Why it matters

Rate limits and temporary errors are normal at scale. A pipeline that handles them quietly finishes every night; one that does not fails at random, and an engineer reruns it by hand.

| Item | What it does or returns |
|---|---|
| `429 Too Many Requests` | The rate limit was exceeded; wait and retry. |
| `Retry-After` | Seconds to wait (or a date); preferred over your own backoff. |
| `base * 2 ** attempt` | Exponential backoff value for attempt 0, 1, 2, ... |
| `min(cap, value)` | Bounds the wait. |
| `rng.uniform(0, value)` | Full jitter. |
| `random.Random(7)` | Seeded generator: deterministic sequence. |
| `sleep` argument | Real `time.sleep` in production, a recorder in tests. |
| `Idempotency-Key` | Header (where supported) that makes a repeated `POST` safe. |

## Learn by example

### Example 1: Every third request is a 429 (browser-safe)

The stand-in API answers 429 with `Retry-After: 2` on every third request. The first loop ignores the status and quietly drops a page. The second waits for the time in the header (a fake sleep records it) and repeats the request, so all 120 orders arrive.

```python run
import json

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

class Response:
    """Looks like a `requests` response: status_code, headers, json(), raise_for_status()."""
    def __init__(self, status_code, body=None, headers=None):
        self.status_code = status_code
        self._body = body
        self.headers = headers or {}

    def json(self):
        return json.loads(json.dumps(self._body))

    def raise_for_status(self):
        if self.status_code >= 400:
            raise RuntimeError(f"HTTP {self.status_code}")

class RateLimitedAPI:
    def __init__(self, every=3):
        self.calls, self.every = 0, every

    def get_page(self, page, page_size=50):
        self.calls += 1
        if self.calls % self.every == 0:
            return Response(429, {"error": "slow down"}, {"Retry-After": "2"})
        pages = -(-len(ORDERS) // page_size)
        return Response(200, {"data": ORDERS[(page - 1) * page_size:page * page_size], "page": page, "total_pages": pages})

api = RateLimitedAPI()
naive = []
for page in (1, 2, 3):
    r = api.get_page(page)
    if r.status_code == 200:
        naive += r.json()["data"]
print("ignoring 429:", len(naive), "orders, requests:", api.calls)

api, waits, careful = RateLimitedAPI(), [], []
for page in (1, 2, 3):
    while True:
        r = api.get_page(page)
        if r.status_code != 429:
            break
        waits.append(int(r.headers["Retry-After"]))
    careful += r.json()["data"]
print("honouring 429:", len(careful), "orders, requests:", api.calls, "waits:", waits)
```

```output
ignoring 429: 100 orders, requests: 3
honouring 429: 120 orders, requests: 4 waits: [2]
```

The naive loop returned 100 orders of 120 and no error: the third page met the 429 and was skipped silently. The careful loop made one extra request and recorded one wait of 2 seconds.

### Example 2: Backoff schedules with and without jitter

The code prints the exponential waits for seven attempts with a base of 0.5 seconds and a cap of 8, then the full-jitter waits from a seeded generator. Each jittered wait is below its ceiling, and the same seed gives the same list on every run.

```python run
import random

def ceiling(attempt, base=0.5, cap=8.0):
    return min(cap, base * 2 ** attempt)

def jittered(attempt, rng, base=0.5, cap=8.0):
    return rng.uniform(0, ceiling(attempt, base, cap))

print([ceiling(a) for a in range(7)])
rng = random.Random(7)
waits = [round(jittered(a, rng), 2) for a in range(7)]
print(waits)
print(all(w <= ceiling(a) for a, w in enumerate(waits)))
again = random.Random(7)
print(waits == [round(jittered(a, again), 2) for a in range(7)])
print(round(sum(ceiling(a) for a in range(5)), 1))
```

```output
[0.5, 1.0, 2.0, 4.0, 8.0, 8.0, 8.0]
[0.16, 0.15, 1.3, 0.29, 4.29, 2.93, 0.46]
True
True
15.5
```

The last number is the worst case total wait for five attempts (0.5 + 1 + 2 + 4 + 8 = 15.5 seconds). That is how a retry policy bounds the time one failing call can take.

### Example 3: A retry function with a policy

`retry` calls a function, decides from the status (or a `TimeoutError`) whether to retry, waits using `Retry-After` when it is a whole number and jittered backoff otherwise, and gives up after `max_attempts`. Four callers show the cases: a call that succeeds on the third attempt, one that always fails with 503, one that returns 404 (not retried) and one that is rate limited with `Retry-After`.

```python run
import random

class Resp:
    def __init__(self, status_code, headers=None):
        self.status_code, self.headers = status_code, headers or {}

RETRY_STATUS = {429, 500, 502, 503, 504}

def retry(call, sleep, rng, max_attempts=5, base=0.5, cap=8.0):
    waits = []
    for attempt in range(1, max_attempts + 1):
        try:
            response = call()
        except TimeoutError:
            response = None
        if response is not None and response.status_code not in RETRY_STATUS:
            return response.status_code, waits
        if attempt == max_attempts:
            raise RuntimeError(f"gave up after {attempt} attempts, waited {round(sum(waits), 2)}s")
        header = response.headers.get("Retry-After", "") if response is not None else ""
        wait = float(header) if header.isdigit() else rng.uniform(0, min(cap, base * 2 ** attempt))
        waits.append(round(wait, 2))
        sleep(wait)

def scripted(*outcomes):
    queue = list(outcomes)
    def call():
        item = queue.pop(0)
        if item == "timeout":
            raise TimeoutError()
        return item
    return call

slept = []
rng = random.Random(7)
print(retry(scripted("timeout", Resp(503), Resp(200)), slept.append, rng))
print(retry(scripted(Resp(404)), slept.append, rng))
print(retry(scripted(Resp(429, {"Retry-After": "3"}), Resp(200)), slept.append, rng))
try:
    retry(scripted(*[Resp(503)] * 5), slept.append, rng)
except RuntimeError as err:
    print(err)
print(len(slept), "sleeps recorded, none of them real")
```

```output
(200, [0.32, 0.3])
(404, [])
(200, [3.0])
gave up after 5 attempts, waited 5.86s
7 sleeps recorded, none of them real
```

The 404 returned at once, because a permanent failure is not retried. The `Retry-After` value of 3 was used exactly, with no jitter. The sleeping function only recorded the waits, so the example runs instantly.

### Example 4: An idempotency key makes a `POST` retry safe

A timeout hides the fact that the server did create the order. The first client retries the `POST` without a key and ends up with two orders. The second sends the same key on both attempts, and the server returns the stored order instead of creating another.

```python run
class OrdersServer:
    def __init__(self):
        self.orders, self.keys = [], {}

    def post(self, body, key=None, lose_reply=False):
        if key is not None and key in self.keys:
            return self.keys[key]
        order = {"order_id": len(self.orders) + 1, **body}
        self.orders.append(order)
        if key is not None:
            self.keys[key] = order
        if lose_reply:
            raise TimeoutError("reply lost")
        return order

def create(server, body, key=None):
    for attempt in (1, 2):
        try:
            return server.post(body, key, lose_reply=(attempt == 1))
        except TimeoutError:
            continue

body = {"customer_id": 4, "amount_cents": 1500}
plain = OrdersServer()
create(plain, body)
print("without key:", len(plain.orders))
keyed = OrdersServer()
result = create(keyed, body, key="order-2026-03-05-0001")
print("with key:", len(keyed.orders), result["order_id"])
```

```output
without key: 2
with key: 1 1
```

Without a key the retry created order 2 as a duplicate of order 1. With the key, the second call returned order 1 and the count stayed at one.

### Example 5: Reading all pages through a real rate limit

The local server answers 429 with `Retry-After: 2` on every third request. The client reads the three pages, waits using an injected `sleep` that only records the waits (so the example runs instantly), and repeats the request after each 429. It ends with 120 orders after four requests.

```python local
import json
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import parse_qs, urlparse

import requests

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

API_KEY = "demo-key-123"

def start_server(orders, rate_limit_every=0):
    state = {"requests": 0, "orders": {o["order_id"]: dict(o) for o in orders}}

    def route(method, parts, query, body):
        table = state["orders"]
        if parts == ["orders"] and method == "GET":
            rows = [table[k] for k in sorted(table)]
            if "cursor" in query:
                start = int(query["cursor"] or 0)
                size = int(query.get("limit", 25))
                nxt = start + size
                return 200, {"data": rows[start:nxt], "next_cursor": str(nxt) if nxt < len(rows) else None}
            if "offset" in query:
                start, size = int(query["offset"]), int(query.get("limit", 25))
                return 200, {"data": rows[start:start + size], "offset": start, "total": len(rows)}
            page, size = int(query.get("page", 1)), int(query.get("page_size", 20))
            if page < 1 or not 1 <= size <= 100:
                return 400, {"error": "bad paging parameters"}
            pages = -(-len(rows) // size)
            return 200, {"data": rows[(page - 1) * size:page * size], "page": page, "total_pages": pages}
        if parts == ["orders"] and method == "POST":
            if not body or "customer_id" not in body:
                return 422, {"error": "customer_id is required"}
            new_id = max(table) + 1
            table[new_id] = {"order_id": new_id, **body}
            return 201, table[new_id]
        if len(parts) == 2 and parts[0] == "orders" and parts[1].isdigit():
            key = int(parts[1])
            if key not in table:
                return 404, {"error": "order not found"}
            if method == "GET":
                return 200, table[key]
            if method == "PUT":
                table[key] = {"order_id": key, **body}
                return 200, table[key]
            if method == "DELETE":
                del table[key]
                return 204, None
        return 404, {"error": "no such route"}

    class Handler(BaseHTTPRequestHandler):
        def log_message(self, *args):
            pass

        def handle_request(self, method):
            state["requests"] += 1
            length = int(self.headers.get("Content-Length") or 0)
            body = json.loads(self.rfile.read(length)) if length else None
            if self.headers.get("X-Api-Key") != API_KEY:
                status, payload, extra = 401, {"error": "invalid api key"}, {}
            elif rate_limit_every and state["requests"] % rate_limit_every == 0:
                status, payload, extra = 429, {"error": "slow down"}, {"Retry-After": "2"}
            else:
                url = urlparse(self.path)
                query = {k: v[0] for k, v in parse_qs(url.query, keep_blank_values=True).items()}
                status, payload = route(method, url.path.strip("/").split("/"), query, body)
                extra = {}
            data = b"" if payload is None else json.dumps(payload).encode()
            self.send_response(status)
            self.send_header("Content-Type", "application/json")
            self.send_header("Content-Length", str(len(data)))
            for name, value in extra.items():
                self.send_header(name, value)
            self.end_headers()
            self.wfile.write(data)

        do_GET = lambda self: self.handle_request("GET")
        do_POST = lambda self: self.handle_request("POST")
        do_PUT = lambda self: self.handle_request("PUT")
        do_DELETE = lambda self: self.handle_request("DELETE")

    server = HTTPServer(("127.0.0.1", 0), Handler)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    return server, f"http://127.0.0.1:{server.server_port}", state

server, base, state = start_server(ORDERS, rate_limit_every=3)
waits = []
headers = {"X-Api-Key": API_KEY}

def get_page(page, sleep=waits.append, max_attempts=5):
    for attempt in range(1, max_attempts + 1):
        r = requests.get(base + "/orders", params={"page": page, "page_size": 50}, headers=headers, timeout=5)
        if r.status_code != 429:
            r.raise_for_status()
            return r.json()
        sleep(int(r.headers["Retry-After"]))
    raise RuntimeError("rate limit did not clear")

try:
    orders = []
    for page in (1, 2, 3):
        orders += get_page(page)["data"]
    print(len(orders), state["requests"], waits)
finally:
    server.shutdown()
    server.server_close()
```

```output
120 4 [2]
```

## Real-world applications

- **Nightly extracts under quota.** A job that reads thousands of pages from a provider with a per-minute quota waits as told in `Retry-After` and still completes before the morning.
- **Fleet of workers.** Many workers sharing one key use jitter so that their retries do not align into waves.
- **Provider outages.** A 503 for two minutes is absorbed by five attempts with growing waits; a longer outage fails the run with a clear message and an alert.
- **Payments and writes.** Creating records downstream with a `POST` uses an idempotency key per record so that a timeout does not create a duplicate charge.

## Daily review

### Key takeaways

- A 429 means wait and retry; `Retry-After` says how long.
- Retry transient failures (429, 5xx, timeouts, connection errors); raise the other 4xx at once.
- Exponential backoff doubles the wait up to a cap; jitter randomises it to avoid synchronised waves.
- Bound the policy with a maximum number of attempts, and fail loudly after the last one.
- Inject `sleep` and a seeded generator for fast, deterministic tests; use idempotency keys for retried `POST`s.

### Common mistakes

- **Ignoring a 429 and moving on.** A page is skipped and nothing fails. Treat 429 as "repeat after waiting".
- **Retrying in a tight loop.** It adds load and can get the key blocked. Wait, with backoff.
- **Retrying every error.** A 401 or 404 returns the same answer. Retry only transient ones.
- **No upper bound.** An outage keeps the job alive for hours. Use `max_attempts` and a cap.
- **Retrying a POST blindly.** A lost reply creates a duplicate. Use an idempotency key or check for the record first.

### Revision notes

- `429` + `Retry-After`; retry set {429, 500, 502, 503, 504, timeout, connection error}.
- `min(cap, base * 2 ** attempt)`; full jitter `rng.uniform(0, ...)`.
- `random.Random(7)` and a recording `sleep` make tests exact.
- Idempotent: GET, PUT, DELETE; POST needs a key.

## Objectives

- Explain pushdown: letting the database filter, aggregate and join before data reaches Python.
- Measure the cost of a plan as rows and cells moved into Python, and compare two plans for the same answer.
- Read a large result in chunks with `read_sql(chunksize=...)` to keep memory bounded.
- Decide, for a task, whether SQL, pandas or a split between them is the right place for each step.

## Understand

### Two places to compute

A data task can run in two places. The **database** (PostgreSQL in production, `sqlite3` in today's runnable code) holds the data and can filter, group, join and sort it. **Python with pandas** runs on your machine or on the pipeline worker, after the rows have been fetched. The same answer can usually be produced either way: `SELECT status, SUM(amount_cents) ... GROUP BY status` returns three rows, while `SELECT * FROM events` followed by `df.groupby("status")["amount_cents"].sum()` returns the same three numbers but first brings every row across. The question for this day is where each step should happen.

### Pushdown

**Pushdown** means moving work down to the database, close to the data, so that less data travels. Filtering (`WHERE`), aggregating (`GROUP BY`), limiting columns (list the ones you need instead of `SELECT *`) and joining tables that already live together are all pushdown. The database is built for this: it can use indexes, work in compiled code on stored pages and send back only the result. The cost you avoid is real. Every row you fetch has to be read, serialised, sent over the network, turned into Python objects and held in memory. A table of 50 million rows cannot be read into a laptop DataFrame at all, but a `GROUP BY` over it returns a few hundred rows in seconds.

A useful measure is the **cells moved**: rows returned times columns returned. Comparing plans by cells moved is machine-independent, which is why today's examples count rows and columns and never print timings.

### Memory and chunking

A DataFrame lives entirely in RAM, and pandas often needs more than the raw size while it works (copies in `merge` or `sort`). When a result is large but the answer is small, there are three tools in order of preference: push the aggregation into SQL; select only the needed columns and filter rows; or read in **chunks**. `pd.read_sql(sql, conn, chunksize=5000)` returns an iterator of DataFrames of up to 5000 rows each, so you can update a running total per chunk and hold only one chunk at a time. Chunking bounds memory but still moves every row, so it is the fallback when SQL cannot express the logic.

### When pandas is the right place

Pushdown is not always correct. Pandas is better when the logic is awkward in SQL (regular expressions with custom rules, a Python function, joining with a small list that exists only in memory, such as exchange rates loaded from a config), when the data is already small and you will use it many times, or when you will iterate quickly on an exploration and want a local copy. SQL is better when the data is large, when a database index applies, when many people must get the same definition of a metric (a view or query is shared), and when the result must be consistent with other database consumers. A good default is **hybrid**: push down the filter and the heavy aggregation, bring the small result into pandas for the final reshaping and charting.

### Trade-offs to keep in mind

Before choosing, ask three questions. How many rows does the table have now and in a year? How many of those does the answer need? And does the logic already exist in SQL, or does it need something only Python has? If the first two numbers are far apart, push down. If the logic needs Python, push down as far as the SQL stays simple, then finish in pandas.

SQL logic is versioned with the database and fast but is harder to unit test line by line; pandas logic is easy to test in Python but may fetch too much. A pandas aggregate can differ from a SQL aggregate in details: how NULL is treated, how integer division and rounding work, and the sort order of ties. When you move logic from one place to the other, compare the results rather than assuming they match. Finally, remember that "fast on my sample" is not evidence; the cells moved grow linearly with the table, and a plan that fetches everything gets slower as the table grows, while a plan with pushdown usually stays flat.

A common misconception is that "SQL is always faster". A query without a usable index that scans a huge table repeatedly can be slower than one fetch and a pandas pass. The opposite misconception, "pandas is easier, so fetch everything", is the one that crashes pipelines at scale. Think in terms of what moves, not of which tool feels familiar.

## Syntax and key functions

```python
df = pd.read_sql("SELECT status, SUM(amount_cents) AS cents FROM events GROUP BY status", conn)   # pushdown
df = pd.read_sql("SELECT * FROM events", conn).groupby("status")["amount_cents"].sum()             # fetch all
for chunk in pd.read_sql("SELECT ... FROM events", conn, chunksize=5000):                         # chunked
    total += chunk["amount_cents"].sum()
```

| Item | What it does or returns |
|---|---|
| `pd.read_sql(sql, conn)` | Runs the query and returns a DataFrame. |
| `chunksize=n` | Returns an iterator of DataFrames with up to n rows each. |
| `df.shape` | `(rows, columns)`; rows times columns is the cells moved. |
| `df.groupby(col)[x].sum()` | The pandas version of `GROUP BY` with `SUM`. |
| `WHERE`, `GROUP BY`, column list | The SQL tools of pushdown: fewer rows, fewer columns, aggregated. |
| `df[col].map(dict)` | Looks values up in a Python dict, work that SQL cannot reach. |

## Learn by example

### Example 1: The same answer from two plans

`events` holds 12,000 rows. Plan A pushes the `GROUP BY` into SQL. Plan B fetches every row and groups in pandas. Both give the same totals; the shapes show what moved into Python.

```python run
import sqlite3
import pandas as pd

def build_events(n):
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE events (event_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, status TEXT, created_at TEXT)""")
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    conn.executemany("INSERT INTO events VALUES (?,?,?,?,?)",
        ((i, 1 + (i * 5) % 97, 500 + (i * 37) % 89 * 50, statuses[i % 6], f"2025-03-{1 + (i * 13) % 28:02d}") for i in range(1, n + 1)))
    return conn

conn = build_events(12000)
plan_a = pd.read_sql("SELECT status, SUM(amount_cents) AS cents FROM events GROUP BY status ORDER BY status", conn)
all_rows = pd.read_sql("SELECT * FROM events", conn)
plan_b = all_rows.groupby("status")["amount_cents"].sum().reset_index(name="cents").sort_values("status")
print(plan_a.to_string(index=False))
print("same answer:", plan_a["cents"].tolist() == plan_b["cents"].tolist())
print("plan A moved", plan_a.shape, "plan B moved", all_rows.shape)
```

```output
  status    cents
  failed  5405350
    paid 21620400
refunded  5379000
same answer: True
plan A moved (3, 2) plan B moved (12000, 5)
```
### Example 2: Cells moved

The cells moved by three plans for the question "paid revenue per day": fetch everything, fetch only the needed columns of paid rows, and push the whole aggregation. Fewer rows and fewer columns both reduce the cost.

```python run
import sqlite3
import pandas as pd

def build_events(n):
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE events (event_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, status TEXT, created_at TEXT)""")
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    conn.executemany("INSERT INTO events VALUES (?,?,?,?,?)",
        ((i, 1 + (i * 5) % 97, 500 + (i * 37) % 89 * 50, statuses[i % 6], f"2025-03-{1 + (i * 13) % 28:02d}") for i in range(1, n + 1)))
    return conn

conn = build_events(12000)
plans = {
    "fetch everything": "SELECT * FROM events",
    "needed columns, paid rows": "SELECT created_at, amount_cents FROM events WHERE status = 'paid'",
    "aggregate in SQL": "SELECT created_at, SUM(amount_cents) AS cents FROM events WHERE status = 'paid' GROUP BY created_at",
}
for name, sql in plans.items():
    df = pd.read_sql(sql, conn)
    print(f"{name}: {df.shape[0]} rows x {df.shape[1]} columns = {df.shape[0] * df.shape[1]} cells")
```

```output
fetch everything: 12000 rows x 5 columns = 60000 cells
needed columns, paid rows: 8000 rows x 2 columns = 16000 cells
aggregate in SQL: 28 rows x 2 columns = 56 cells
```
### Example 3: Chunked reading

When the logic is hard to express in SQL, read in chunks and keep a running result. The code never holds more than 5,000 rows at once; the total matches the single-query total.

```python run
import sqlite3
import pandas as pd

def build_events(n):
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE events (event_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, status TEXT, created_at TEXT)""")
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    conn.executemany("INSERT INTO events VALUES (?,?,?,?,?)",
        ((i, 1 + (i * 5) % 97, 500 + (i * 37) % 89 * 50, statuses[i % 6], f"2025-03-{1 + (i * 13) % 28:02d}") for i in range(1, n + 1)))
    return conn

conn = build_events(12000)
total, chunks, biggest = 0, 0, 0
for chunk in pd.read_sql("SELECT amount_cents FROM events WHERE status = 'paid'", conn, chunksize=5000):
    chunks += 1
    biggest = max(biggest, len(chunk))
    total += int(chunk["amount_cents"].sum())
direct = conn.execute("SELECT SUM(amount_cents) FROM events WHERE status = 'paid'").fetchone()[0]
print("chunks:", chunks, "largest chunk:", biggest)
print("chunked total == SQL total:", total == direct)
```

```output
chunks: 2 largest chunk: 5000
chunked total == SQL total: True
```
### Example 4: Hybrid, pushdown then pandas

The database does the heavy part: it reduces 12,000 rows to 28 daily totals. A small Python dict of weekday names, which the database does not have, is mapped in pandas, and the result is reshaped by weekday.

```python run
import sqlite3
import pandas as pd

def build_events(n):
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE events (event_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, status TEXT, created_at TEXT)""")
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    conn.executemany("INSERT INTO events VALUES (?,?,?,?,?)",
        ((i, 1 + (i * 5) % 97, 500 + (i * 37) % 89 * 50, statuses[i % 6], f"2025-03-{1 + (i * 13) % 28:02d}") for i in range(1, n + 1)))
    return conn

conn = build_events(12000)
daily = pd.read_sql("SELECT created_at AS day, SUM(amount_cents) AS cents FROM events WHERE status = 'paid' GROUP BY created_at", conn, parse_dates=["day"])
names = {0: "Mon", 1: "Tue", 2: "Wed", 3: "Thu", 4: "Fri", 5: "Sat", 6: "Sun"}
daily["weekday"] = daily["day"].dt.dayofweek.map(names)
by_weekday = daily.groupby("weekday")["cents"].sum().sort_values(ascending=False, kind="stable")
print(len(daily), "daily rows moved")
print(by_weekday.head(3).to_string())
```

```output
28 daily rows moved
weekday
Sat    3090850
Fri    3090500
Thu    3089450
```
### Example 5: Same logic, different NULL behaviour

When logic moves between SQL and pandas, check the details. The average of an amount column with a NULL ignores the NULL in SQL and, by default, in pandas too, but the sum of an all-NULL group differs: SQL returns NULL and pandas returns 0.

```python run
import sqlite3
import pandas as pd

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE t (grp TEXT, v INTEGER)")
conn.executemany("INSERT INTO t VALUES (?, ?)", [("a", 10), ("a", None), ("b", None)])
print(conn.execute("SELECT grp, AVG(v), SUM(v) FROM t GROUP BY grp ORDER BY grp").fetchall())
df = pd.read_sql("SELECT * FROM t", conn)
print(df.groupby("grp")["v"].agg(["mean", "sum"]).reset_index().values.tolist())
```

```output
[('a', 10.0, 10), ('b', None, None)]
[['a', 10.0, 10.0], ['b', nan, 0.0]]
```
## Real-world applications

- **Large fact tables.** A nightly job that needs revenue per day filters and groups in the warehouse and brings back a few hundred rows (Example 2), instead of copying the whole fact table to a worker.
- **Enrichment with outside data.** Exchange rates, holiday calendars and regex-based cleaning live in Python; the pipeline pushes down the heavy aggregation and maps the small result in pandas (Example 4).
- **Safe processing of huge extracts.** When an export must be processed row by row (for example a custom validation), chunked reading with a running state (Example 3) keeps memory flat for any table size.
- **Migrating logic.** When a pandas report is moved into a database view, comparing the two results (Example 5) catches NULL and rounding differences before users do.

## Daily review

### Key takeaways

- Pushdown means filter, aggregate and select columns in the database so that less data moves.
- Compare plans by cells moved (rows times columns), not by timings that vary by machine.
- `chunksize` bounds memory but still moves every row.
- A hybrid plan is common: heavy work in SQL, the small result finished in pandas.
- When logic changes place, compare the outputs, especially NULL handling.

### Common mistakes

- `SELECT *` into a DataFrame followed by `groupby`, which works on a sample and runs out of memory in production. Push the `GROUP BY` down.
- Fetching every column when two are needed, multiplying the cells moved.
- Pushing everything into SQL even when the logic needs a Python function or a small in-memory lookup, which produces unreadable SQL.
- Assuming SQL and pandas aggregates match: `SUM` of an all-NULL group is NULL in SQL and 0 in pandas. Check both.
- Using chunking and then collecting every chunk in a list, which rebuilds the whole table in memory. Keep a running result.

### Revision notes

- Filter early, aggregate in SQL, select only needed columns.
- Cells moved = rows x columns.
- `pd.read_sql(sql, conn, chunksize=n)` yields DataFrames of up to n rows.
- Hybrid: SQL for volume, pandas for shape and small lookups.

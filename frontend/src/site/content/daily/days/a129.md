## Understand

### The sample model

Every Power BI day in this phase uses the same small model. `Sales` is the fact table with `order_id`, `order_date`, `customer_id`, `product_id`, `quantity` and `unit_price`. `Customers` has `customer_id`, `customer_name`, `country` and `segment`. `Products` has `product_id`, `product_name`, `category` and `unit_cost`. A `Calendar` table has `date`, `year`, `quarter`, `month_number` and `month_name`. Each dimension table is on the one side of a one-to-many relationship with `Sales`, and `Calendar` is related on `order_date` (Days 126 to 128). The pandas code in this lesson builds the same data with a seeded generator: 400 orders in 2025, 40 customers and 12 products. Power BI Desktop is Windows-only and Power BI Service runs in a browser, so the formulas below are shown as text and every number they return is reproduced in pandas.

### DAX in one paragraph

**DAX** (Data Analysis Expressions) is the formula language of Power BI. It looks like an Excel formula, but it works on whole columns and tables of the model, not on cells. A DAX formula either defines a **calculated column**, a **measure**, or a **calculated table**. This lesson covers the first two. They look alike and behave very differently, and mixing them up is the most common first-week mistake.

### Calculated column: computed per row, stored in the table

A calculated column is evaluated once for every row of its table when the model is loaded or refreshed. The result is stored in the table like any imported column, so it takes memory and can be used on an axis, in a slicer or in a filter. While the formula runs it has a **row context**: it knows which row it is on, so `Sales[quantity]` means the quantity of that row.

```dax
Revenue = Sales[quantity] * Sales[unit_price]
```

In `Sales`, a column named `Revenue` is added and each row holds its own product of quantity and price. This matches the pandas line `sales["revenue"] = sales["quantity"] * sales["unit_price"]`. To use a value from another table on the one side of a relationship, the column formula calls `RELATED`, for example `Cost = Sales[quantity] * RELATED(Products[unit_cost])`. `RELATED` follows the relationship from the current `Sales` row to its product row, which is the same job as a pandas `merge` or `map`.

### Measure: computed on demand, not stored

A measure is a formula that is evaluated every time a visual needs it, for the cell it is drawing. Nothing is stored per row; only the formula is saved. The result depends on the **filter context** of the cell: the set of filters coming from the row and column of the visual, the slicers, and the page and report filters. A bar for the category `Hardware` sets a filter on `Products[category]`, and the measure aggregates only the sales rows that survive.

```dax
Total Revenue = SUM(Sales[Revenue])
```

The same measure gives a different answer in every cell of a matrix: one number per category, one per country, one for the grand total. The formula never changes; the context does. This is the central idea of DAX, and Day 130 develops it. In pandas, a measure is closer to a function that takes a filtered DataFrame and returns one number than to a column of that DataFrame.

### Choosing between them

Ask three questions. First, is the value a property of a single row that will be used to slice, group or filter, such as a price band or a full name? Then use a calculated column. Second, is it an aggregate that should react to whatever the user selects, such as revenue, a count or a ratio? Then use a measure. Third, can it be computed upstream, in the source query or Power Query? Then do it there, because a column computed in the source is compressed better and refreshes with the data. A calculated column should rarely be the first choice, and a measure should never be replaced by a column that is summed, because a stored ratio cannot be re-aggregated correctly.

### Implicit and explicit measures

When you drag a numeric column such as `unit_price` into a visual, Power BI summarises it automatically and shows "Sum of unit_price". This is an **implicit measure**. It is quick, but the summary is a guess: summing a price makes no sense, and the choice (Sum, Average, Count) sits in a visual setting that nobody sees in the model. An **explicit measure** is one you write and name, such as `Total Revenue`. It has one definition used by every visual, it can be reused in other measures, it can carry a format, and it shows up in the model for other report authors. Measures can refer to other measures in square brackets, `[Total Revenue]`, without a table name; columns always carry the table name, `Sales[Revenue]`.

### Aggregations and DIVIDE

The basic aggregators are `SUM`, `AVERAGE`, `MIN`, `MAX`, `COUNT` (numeric values), `COUNTROWS` (rows of a table) and `DISTINCTCOUNT` (distinct values of a column). A ratio is written with `DIVIDE(numerator, denominator)`, which returns blank when the denominator is zero or blank instead of an error, with an optional third argument for an alternative result. An average of a column and a ratio of two sums are different things: `AVERAGE(Sales[unit_price])` gives the unweighted mean of the row prices, while `DIVIDE([Total Revenue], [Units])` is the price actually paid per unit, weighted by quantity. Choosing the wrong one is a real reporting error.

### Formatting

A measure returns a number; how it looks is a separate property. In the Measure tools ribbon you pick a format such as whole number, currency or percentage and the decimal places. The value stored and used in other measures is unchanged. The `FORMAT` function returns text instead, which can no longer be summed or sorted as a number, so use the format property for numbers and keep `FORMAT` for labels.

### Why it matters

Almost every report is a set of measures. A clear measure library of explicit, named, formatted measures means that two reports built by two analysts agree. The usual misconception is that a calculated column "is faster" or "more flexible"; it is stored, static and blind to filters, so it is the wrong tool for any number that should respond to a slicer.

## Syntax and key functions

```dax
Column Name = <row expression>
Measure Name = <aggregation expression>
Ratio = DIVIDE(<numerator>, <denominator>, <alternate if zero>)
```

A calculated column is created from Table tools, New column; a measure from Home, New measure. Both are typed as `Name = expression`.

| Function | Returns |
|---|---|
| `SUM(Table[Col])` | The sum of a numeric column in the current filter context. |
| `AVERAGE(Table[Col])` | The unweighted mean of the column's values. |
| `COUNTROWS(Table)` | The number of rows of the table that survive the filters. |
| `DISTINCTCOUNT(Table[Col])` | The number of different values in the column. |
| `DIVIDE(a, b, alt)` | `a / b`, or blank (or `alt`) when `b` is zero or blank. |
| `RELATED(Table[Col])` | The value of a column on the one side of a relationship, for the current row. |
| `FORMAT(value, "0.0%")` | Text, not a number. |

The pandas counterparts of this lesson:

```python
fact.groupby("category")["revenue"].sum()
fact.groupby("category")["order_id"].nunique()
```

## Learn by example

### Example 1: A calculated column is a row-wise computation

The calculated columns `Revenue` and `Cost` are evaluated per row. `RELATED(Products[unit_cost])` is the lookup from each sale to its product.

```dax
Revenue = Sales[quantity] * Sales[unit_price]
Cost = Sales[quantity] * RELATED(Products[unit_cost])
```

```python run
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
countries = ["UK", "Germany", "France", "Spain"]
cats = ["Hardware", "Software", "Services"]
customers = pd.DataFrame({
    "customer_id": range(1, 41),
    "customer_name": [f"Customer {i:02d}" for i in range(1, 41)],
    "country": [countries[i % 4] for i in range(40)],
    "segment": [["Retail", "Corporate"][(i // 4) % 2] for i in range(40)],
})
products = pd.DataFrame({
    "product_id": range(1, 13),
    "product_name": [f"Product {i:02d}" for i in range(1, 13)],
    "category": [cats[i % 3] for i in range(12)],
    "unit_cost": [float(10 + 5 * i) for i in range(12)],
})
n = 400
sales = pd.DataFrame({
    "order_id": range(1, n + 1),
    "order_date": pd.to_datetime("2025-01-01") + pd.to_timedelta(rng.integers(0, 365, n), unit="D"),
    "customer_id": rng.integers(1, 41, n),
    "product_id": rng.integers(1, 13, n),
    "quantity": rng.integers(1, 6, n),
})
sales["unit_price"] = (sales["product_id"].map(products.set_index("product_id")["unit_cost"]) * 1.5).round(2)
calendar = pd.DataFrame({"date": pd.date_range("2025-01-01", "2025-12-31")})
calendar["year"] = calendar["date"].dt.year
calendar["quarter"] = calendar["date"].dt.quarter
calendar["month_number"] = calendar["date"].dt.month
calendar["month_name"] = calendar["date"].dt.strftime("%B")
sales["revenue"] = sales["quantity"] * sales["unit_price"]
fact = (sales.merge(customers, on="customer_id").merge(products, on="product_id")
        .merge(calendar, left_on="order_date", right_on="date"))
fact["cost"] = fact["quantity"] * fact["unit_cost"]
print(fact[["order_id", "quantity", "unit_price", "revenue", "unit_cost", "cost"]].head(3).to_string(index=False))
print(len(fact), round(float(fact["revenue"].sum()), 2), round(float(fact["cost"].sum()), 2))
```

```output
 order_id  quantity  unit_price  revenue  unit_cost  cost
        1         4        97.5    390.0       65.0 260.0
        2         5        37.5    187.5       25.0 125.0
        3         5        90.0    450.0       60.0 300.0
400 67132.5 44755.0
```

Order 1 sells 4 units at 97.50, so its stored revenue is 390.00, and the unit cost of its product is 65.00, so its cost is 260.00. These are row values; they exist whether or not anyone looks at a visual. The model has 400 rows, a total revenue of 67,132.50 and a total cost of 44,755.00.

### Example 3: Implicit sum versus explicit average

Dragging `unit_price` into the matrix gives "Sum of unit_price", which is a number without meaning. An explicit measure states what is intended.

### Example 4: Ratio of sums versus average of a column

Define units and a weighted price, and compare it with the plain average.

```dax
Units = SUM(Sales[quantity])
Price per Unit = DIVIDE([Total Revenue], [Units])
```

### Example 5: Distinct counts and a combined measure

Count orders with `DISTINCTCOUNT` and build an average order value from two measures.

## Real-world applications

- **A reusable measure library.** A finance team defines `Total Revenue`, `Total Cost` and `Gross Margin` once, in a shared model, and every report built on that model shows the same figures (Examples 2 and 5).
- **Slicer-aware KPIs.** An executive page shows `Average Order Value` as a card; it re-computes whenever a country or category is selected, because it is a measure and not a column (Example 5).
- **Safer ratios.** `DIVIDE` prevents error cards for filtered selections with no data, and ratios built from sums avoid the weighted-average error (Example 4).
- **Model audits.** Reviewing a report starts with finding implicit measures and columns that are summed when they should not be (Example 3).

## Daily review

### Key takeaways

- A calculated column is evaluated per row at refresh and stored; a measure is evaluated per visual cell at query time and stored only as a formula.
- A measure depends on filter context; the same formula returns different numbers in different cells.
- Write explicit, named measures; avoid dragging raw columns into visuals.
- Use `DIVIDE` for ratios and build ratios from sums, not by averaging a ratio column.
- Formatting changes the display only; `FORMAT` turns a number into text.

### Common mistakes

- Creating a calculated column for a total or a ratio. It shows a single fixed value per row and the visual then sums or averages it wrongly; write a measure instead.
- Summing a price or a percentage column, which gives a large meaningless number. Use `AVERAGE` or a weighted measure.
- Writing `A / B` instead of `DIVIDE(A, B)` and getting an infinity or error card when a filter leaves no rows.
- Referring to a measure as `Sales[Total Revenue]` or a column without its table name. Measures are written `[Total Revenue]`; columns are `Sales[Revenue]`.
- Using `FORMAT` inside a measure that other measures or a chart axis then use, so the value becomes text.

### Revision notes

- Column = row context, stored. Measure = filter context, on demand.
- `SUM`, `AVERAGE`, `COUNTROWS`, `DISTINCTCOUNT`, `DIVIDE`, `RELATED`.
- Explicit measures are named and reusable; implicit ones are visual settings.
- Ratio of sums, not average of ratios.
- Format property for numbers; `FORMAT()` for text labels.

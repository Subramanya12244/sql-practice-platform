## Objectives

- Find duplicate keys with `GROUP BY ... HAVING COUNT(*) > 1`.
- Keep exactly one row per key, the latest, with `ROW_NUMBER` and with PostgreSQL's `DISTINCT ON`.
- Find missing numbers in a sequence with `LEAD` (gaps).
- Group consecutive values into runs with the row-number-difference trick (islands) and report each run's start, end and length.

## Understand

### Duplicates: same real-world thing, several rows

A **duplicate** is a row that represents the same real-world entity as another row. Duplicates come from repeated imports, double clicks, systems that merge, or free-text typing (`ana@x.com` and `ANA@x.com`). They inflate counts and revenue, so cleaning them is routine. The first step is to define the **key**: the column or combination of columns that identifies an entity, such as a lower-cased email. Two kinds exist. Exact duplicates are identical in every column. Near duplicates share the key but differ elsewhere, for example in an update date, and then a rule decides which row to keep.

### Finding duplicates

Group by the key and keep groups with more than one row: `SELECT lower(email), COUNT(*) FROM contacts GROUP BY lower(email) HAVING COUNT(*) > 1`. `HAVING` (day 37) filters groups after counting. This tells you which keys are duplicated and how often, but not which rows. To see the rows themselves, rank them inside each key with `ROW_NUMBER() OVER (PARTITION BY key ORDER BY ...)` (day 50): row number 1 is the survivor and numbers above 1 are the duplicates.

### Keeping the latest row

Rule: keep the row with the newest update date, and break ties by the highest id, so the choice is deterministic. In window form, `ROW_NUMBER() OVER (PARTITION BY lower(email) ORDER BY updated_on DESC, contact_id DESC) = 1`. As with any window result, the filter on the row number has to be in an outer query. PostgreSQL also offers a shorthand, `SELECT DISTINCT ON (key) ... ORDER BY key, updated_on DESC`, which returns the first row of each key in the stated order. It is shorter but PostgreSQL-specific; the window version is portable.

To remove duplicates from a real table you use a `DELETE` of the rows whose number is above 1, after checking the result with a `SELECT`; this lesson only selects, because the runner here rolls statements back. Always preview the rows that would be removed.

### Gaps: what is missing in a sequence

A **gap** is a missing value in what should be a continuous sequence: invoice numbers, daily timestamps, order ids. A gap is detected by comparing each value with the next one using `LEAD` (day 51): if `next_value - value > 1`, the values between them are missing. The missing range is `value + 1` to `next_value - 1`, and the count of missing values is `next_value - value - 1`. Note that this method finds gaps between existing values. A gap before the first value or after the last needs a known expected start and end.

### Islands: runs of consecutive values

An **island** is a maximal run of consecutive values with no gap inside it: login days in a row, consecutive order ids, an uninterrupted period of a status. Islands are the complement of gaps. The standard technique is the **row-number difference**. Number the rows in order with `ROW_NUMBER()`. Inside a run of consecutive values, both the value and the row number increase by 1 on each row, so `value - row_number` stays constant. When a gap appears the value jumps and the difference changes. The difference is therefore a label (a group key) for each island. Group by it and take `MIN`, `MAX` and `COUNT` for the start, end and length of each island. For dates, `login_date - ROW_NUMBER()::int` is a date that works as the label. If duplicates of a value exist, remove them first, otherwise the difference is no longer constant.

### Common misconception

Learners often use `SELECT DISTINCT` to deduplicate and expect the "latest" row. `DISTINCT` compares whole rows, so two rows that differ in only one column, such as `updated_on`, are both kept; and it cannot choose which row survives. Another misconception is that `MAX(updated_on)` with `GROUP BY` returns the whole latest row. It returns only the date; the other columns of that row are lost unless you join back or use a window.

### Why it matters

Duplicates silently double-count customers and revenue. Gaps indicate lost data or missing records (a failed load, a missing day), and islands measure streaks, uptime and activity periods. These patterns appear in data-quality checks and in analytics such as customer engagement.

## Syntax and key functions

```sql-syntax
-- find duplicated keys
SELECT key_expr, COUNT(*) FROM t GROUP BY key_expr HAVING COUNT(*) > 1;

-- keep one row per key
SELECT * FROM (
  SELECT t.*, ROW_NUMBER() OVER (PARTITION BY key_expr ORDER BY ranking_column DESC, id DESC) AS rn
  FROM t
) AS x WHERE rn = 1;

-- PostgreSQL shortcut
SELECT DISTINCT ON (key_expr) * FROM t ORDER BY key_expr, ranking_column DESC;
```

```sql-syntax
-- gaps
SELECT value, LEAD(value) OVER (ORDER BY value) AS next_value FROM t;   -- gap if next_value - value > 1

-- islands
SELECT MIN(value), MAX(value), COUNT(*)
FROM (SELECT value, value - ROW_NUMBER() OVER (ORDER BY value)::int AS grp FROM t) AS x
GROUP BY grp;
```

| Tool | Use |
|---|---|
| `GROUP BY ... HAVING COUNT(*) > 1` | Which keys are duplicated, and how many times |
| `ROW_NUMBER() OVER (PARTITION BY key ORDER BY ...)` | Number the rows of each key, 1 is the survivor |
| `DISTINCT ON (key)` | PostgreSQL: first row per key in the `ORDER BY` order |
| `LEAD(v) - v > 1` | Gap detection |
| `v - ROW_NUMBER() OVER (ORDER BY v)` | Island label |

## Learn by example

### Example 1: find duplicated keys

An inline table of six contacts is built with `VALUES`, so you can see the whole data set. The key is the lower-cased email. `ana@x.com` appears twice (different capitalisation) and `cy@x.com` twice.

```sql run
WITH contacts (contact_id, email, name, updated_on) AS (
  VALUES (1, 'ana@x.com', 'Ana', DATE '2024-01-05'),
         (2, 'ANA@x.com', 'Ana B', DATE '2024-03-10'),
         (3, 'bo@x.com', 'Bo', DATE '2024-02-01'),
         (4, 'cy@x.com', 'Cy', DATE '2024-01-20'),
         (5, 'cy@x.com', 'Cy L', DATE '2024-01-20'),
         (6, 'di@x.com', 'Di', DATE '2024-04-02')
)
SELECT lower(email) AS email_key, COUNT(*) AS copies
FROM contacts
GROUP BY lower(email)
HAVING COUNT(*) > 1
ORDER BY email_key;
```

```output
email_key | copies
ana@x.com | 2
cy@x.com | 2
```

### Example 2: see which rows are the duplicates

`ROW_NUMBER` inside each key, newest first with the id as tie-breaker, labels the survivor `1` and the rows to discard `2`. Looking at all rows before deleting anything is a good habit.

```sql run
WITH contacts (contact_id, email, name, updated_on) AS (
  VALUES (1, 'ana@x.com', 'Ana', DATE '2024-01-05'),
         (2, 'ANA@x.com', 'Ana B', DATE '2024-03-10'),
         (3, 'bo@x.com', 'Bo', DATE '2024-02-01'),
         (4, 'cy@x.com', 'Cy', DATE '2024-01-20'),
         (5, 'cy@x.com', 'Cy L', DATE '2024-01-20'),
         (6, 'di@x.com', 'Di', DATE '2024-04-02')
)
SELECT contact_id, email, updated_on,
       ROW_NUMBER() OVER (PARTITION BY lower(email) ORDER BY updated_on DESC, contact_id DESC) AS rn
FROM contacts
ORDER BY lower(email), rn;
```

```output
contact_id | email | updated_on | rn
2 | ANA@x.com | 2024-03-10 | 1
1 | ana@x.com | 2024-01-05 | 2
3 | bo@x.com | 2024-02-01 | 1
5 | cy@x.com | 2024-01-20 | 1
4 | cy@x.com | 2024-01-20 | 2
6 | di@x.com | 2024-04-02 | 1
```

### Example 3: keep the latest row, two ways

First the portable window version: filter on `rn = 1` in an outer query. The result has one row per email. The last column checks that the PostgreSQL `DISTINCT ON (lower(email))` version keeps exactly the same rows.

```sql run
WITH contacts (contact_id, email, name, updated_on) AS (
  VALUES (1, 'ana@x.com', 'Ana', DATE '2024-01-05'),
         (2, 'ANA@x.com', 'Ana B', DATE '2024-03-10'),
         (3, 'bo@x.com', 'Bo', DATE '2024-02-01'),
         (4, 'cy@x.com', 'Cy', DATE '2024-01-20'),
         (5, 'cy@x.com', 'Cy L', DATE '2024-01-20'),
         (6, 'di@x.com', 'Di', DATE '2024-04-02')
), ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY lower(email) ORDER BY updated_on DESC, contact_id DESC) AS rn
  FROM contacts
), kept_window AS (
  SELECT contact_id FROM ranked WHERE rn = 1
), kept_distinct_on AS (
  SELECT DISTINCT ON (lower(email)) contact_id
  FROM contacts
  ORDER BY lower(email), updated_on DESC, contact_id DESC
)
SELECT c.contact_id, c.name, c.updated_on,
       c.contact_id IN (SELECT contact_id FROM kept_distinct_on) AS same_in_distinct_on
FROM contacts AS c
WHERE c.contact_id IN (SELECT contact_id FROM kept_window)
ORDER BY c.contact_id;
```

```output
contact_id | name | updated_on | same_in_distinct_on
2 | Ana B | 2024-03-10 | true
3 | Bo | 2024-02-01 | true
5 | Cy L | 2024-01-20 | true
6 | Di | 2024-04-02 | true
```

### Example 4: gaps with LEAD

Northwind order ids are continuous, so to have gaps we look only at the orders of employees 1 to 4. `LEAD` gives the next id, and the difference minus one is the count of ids that belong to other employees (the missing ones in this subset). The first rows of the list are shown.

```sql run
SELECT order_id AS gap_after, next_id AS next_present, next_id - order_id - 1 AS missing_count
FROM (
  SELECT order_id, LEAD(order_id) OVER (ORDER BY order_id) AS next_id
  FROM orders
  WHERE employee_id IN (1, 2, 3, 4)
) AS t
WHERE next_id - order_id > 1
ORDER BY order_id
LIMIT 4;
```

```output
gap_after | next_present | missing_count
10251 | 10257 | 5
10260 | 10266 | 5
10269 | 10275 | 5
10278 | 10284 | 5
```

### Example 5: islands with the row-number difference

Same subset. `order_id - ROW_NUMBER()` is constant within each run of consecutive ids, so grouping by it gives the islands. The query shows the first four islands with start, end and size.

```sql run
SELECT MIN(order_id) AS first_id, MAX(order_id) AS last_id, COUNT(*) AS island_size
FROM (
  SELECT order_id,
         order_id - ROW_NUMBER() OVER (ORDER BY order_id) AS grp
  FROM orders
  WHERE employee_id IN (1, 2, 3, 4)
) AS t
GROUP BY grp
ORDER BY first_id
LIMIT 4;
```

```output
first_id | last_id | island_size
10248 | 10251 | 4
10257 | 10260 | 4
10266 | 10269 | 4
10275 | 10278 | 4
```

### Example 6: login streaks per user

A realistic case with dates. Each user's login days are numbered inside the user, and `login_date - rn` gives a date label for every streak. Grouping by user and label returns each streak. User `u1` has two streaks (days 1 to 3 and 5 to 6), then a single day, so we also see a one-day island. `rn` is cast to `int` so that date minus integer works.

```sql run
WITH logins (user_id, login_date) AS (
  VALUES ('u1', DATE '2024-01-01'), ('u1', DATE '2024-01-02'), ('u1', DATE '2024-01-03'),
         ('u1', DATE '2024-01-05'), ('u1', DATE '2024-01-06'), ('u1', DATE '2024-01-09'),
         ('u2', DATE '2024-01-10'), ('u2', DATE '2024-01-11'), ('u2', DATE '2024-01-12'),
         ('u2', DATE '2024-01-13')
), labelled AS (
  SELECT user_id, login_date,
         login_date - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date))::int AS grp
  FROM logins
)
SELECT user_id, MIN(login_date) AS streak_start, MAX(login_date) AS streak_end, COUNT(*) AS days
FROM labelled
GROUP BY user_id, grp
ORDER BY user_id, streak_start;
```

```output
user_id | streak_start | streak_end | days
u1 | 2024-01-01 | 2024-01-03 | 3
u1 | 2024-01-05 | 2024-01-06 | 2
u1 | 2024-01-09 | 2024-01-09 | 1
u2 | 2024-01-10 | 2024-01-13 | 4
```

## Real-world applications

**Cleaning master data.** Customer, product and contact tables collect duplicates from imports. Examples 1 to 3 find them, rank them and keep the freshest record, and the same pattern deduplicates event streams loaded twice by a pipeline.

**Checking for missing records.** Gap detection (Example 4) finds missing invoice numbers, missing days in a daily load and missing sensor readings. Auditors and data engineers run it as a completeness test.

**Measuring streaks and uptime.** Islands (Examples 5 and 6) give consecutive active days, uninterrupted subscription periods and the longest period without errors. Product teams use streak length as an engagement metric.

**Building sessions and periods.** Collapsing a row per day into start and end of continuous activity turns event data into periods, which are easier to join and to report on.

## Daily review

### Key takeaways

- Define the duplicate key first; `GROUP BY key HAVING COUNT(*) > 1` finds duplicated keys.
- `ROW_NUMBER() OVER (PARTITION BY key ORDER BY newest DESC, id DESC)` marks the survivor as 1; keep `rn = 1`. `DISTINCT ON` is the PostgreSQL shortcut.
- Preview duplicates before deleting; a deterministic tie-breaker avoids random survivors.
- A gap exists where `LEAD(v) - v > 1`; missing values are `v + 1` to `next - 1`.
- Islands: `value - ROW_NUMBER()` is constant inside a run; group by it and take `MIN`, `MAX`, `COUNT`.
- Remove duplicate values before the island technique.

### Common mistakes

- Using `SELECT DISTINCT` and expecting it to keep the latest row. It compares all columns and cannot choose.
- Using `GROUP BY` with `MAX(updated_on)` and losing the other columns of the latest row.
- Deduplicating on the raw email without `lower()` and missing `ANA@x.com`.
- Forgetting a tie-breaker, so tied rows are kept or dropped arbitrarily.
- Applying the island technique to data with repeated values, which gives wrong groups. Deduplicate first.
- Mixing types in the island label: `date - bigint` is an error (`operator does not exist: date - bigint`); cast the row number to `int`.
- Expecting `LEAD` to find a gap before the first value.

### Revision notes

- Duplicate finder: `GROUP BY key HAVING COUNT(*) > 1`.
- Survivor: `rn = 1` with newest first and an id tie-breaker.
- Gap: `next - current > 1`. Island label: `value - ROW_NUMBER()`.
- Dates: cast the row number to `int`.

## Understand

### How this lesson works

Apache Spark needs a Java runtime (Java 17 or later for current versions) and the `pyspark` package, and neither is available in the browser or in the automated checks. The PySpark code in this lesson is therefore shown in plain code blocks that are syntax-checked but not run. Every result that a job would print is reproduced by an equivalent that does run: pandas for reading and layout logic, and SQL on the browser's PostgreSQL-compatible database for aggregations. Where an example says "equivalent", the number you see comes from the equivalent, and it is the number the Spark job produces because the logic is the same. What cannot be reproduced without Spark (the physical files, task scheduling, speed) is stated as such and tested with written exercises.

### Reading data: the reader and its options

In PySpark you read data through a **DataFrameReader**, reached as `spark.read`. A read does not load the data immediately: Spark builds a plan and executes it only when an action such as `show()`, `count()` or `write` asks for a result (Day 163 covered lazy evaluation). The common forms are `spark.read.csv(path, header=True, schema=schema)`, `spark.read.json(path)` and `spark.read.parquet(path)`. The path can be a file, a directory or a pattern; Spark reads every matching file as one DataFrame. The reader has options that matter in practice:

- **CSV `header`**: whether the first line holds column names. Without `header=True` the columns are named `_c0`, `_c1`, and the header line is read as data.
- **`inferSchema`**: when true, Spark makes an extra pass over the data to guess each column's type. It is convenient and costs a full read, and the guess can be wrong (an identifier such as `007` becomes the number 7, a column that is mostly empty may be typed from a few values). Without it, every CSV column is a string.
- **`schema`**: a `StructType` that you define yourself. It avoids the extra pass, gives the types you intend, and makes the job fail or produce nulls in a predictable way when the data does not fit. For anything that runs regularly, an explicit schema is the better practice.
- **`mode`**: what to do with a row that does not match the schema. `PERMISSIVE` (the default) keeps the row and sets the unparseable fields to null, `DROPMALFORMED` drops the row, and `FAILFAST` stops the job with an error. A permissive read hides bad data unless you count the nulls afterwards, which is why a validation step belongs right after a read.
- **JSON**: `spark.read.json` expects one JSON object per line by default (JSON Lines). A file holding one big multi-line JSON document needs the option `multiLine=True`. Nested objects become struct columns that you reach with dot notation, such as `col("customer.id")`, and arrays can be flattened with `explode`.

### Parquet: why it is the usual target

**Parquet** is a columnar file format: the values of each column are stored together, with the schema inside the file and compression applied by default. Three consequences are important. The schema travels with the data, so no inference is needed on the next read. A query that needs three columns out of fifty reads only those three (**column pruning**), and Parquet keeps minimum and maximum statistics per block so Spark can skip blocks that cannot match a filter (**predicate pushdown**). And because similar values sit together, the files are much smaller than the same data as CSV. CSV and JSON are formats for exchange with other systems; Parquet is the format for data that Spark will read again.

### Writing, modes and files

You write through a **DataFrameWriter**, reached as `df.write`, for example `df.write.mode("overwrite").parquet(path)`. The path is a **directory**, not a file. Spark writes one file for each partition of the DataFrame that has data (named like `part-00000-...snappy.parquet`) plus a marker file, so a DataFrame with 8 partitions produces 8 files. The **save mode** decides what happens if the path already exists: `errorifexists` (the default) raises an error, `overwrite` replaces the existing data, `append` adds new files next to the old ones, and `ignore` does nothing when the path exists. `append` is not idempotent: running the same job twice duplicates the data (Day 124's idea applies here as well), so a re-runnable job usually overwrites a partition rather than appending to it.

### Partitioned writes and partition pruning

`df.write.partitionBy("order_date").parquet(path)` splits the output by the values of a column into subdirectories such as `order_date=2025-03-01/`, each with its own files. The partition column's value is stored in the directory name and is not repeated inside the files, though it comes back as a column when you read the parent path. A query that filters on the partition column, such as `where order_date = '2025-03-01'`, reads only the matching directory: this is **partition pruning**, and it can cut the data read by a large factor. Choose partition columns that queries filter on and that have a moderate number of distinct values: a date is the classic choice, while a column with millions of distinct values (such as a customer id) creates millions of tiny directories. With `overwrite`, Spark's default replaces the whole path unless you set `spark.sql.sources.partitionOverwriteMode` to `dynamic`, which replaces only the partitions present in the new data.

### The small-files problem

Each task that holds data for a partition directory writes its own file, so a DataFrame with 200 partitions written with `partitionBy` over 30 dates can create thousands of tiny files. Many small files are slow to list and to open, and they make later reads inefficient. You control the layout before the write: `df.repartition(n)` redistributes the data into `n` partitions with a shuffle (Day 166), `df.repartition("order_date")` groups all rows of a date into one partition so that each date directory gets one file, and `df.coalesce(n)` reduces the number of partitions without a full shuffle. Fewer, larger files (a common target is tens to hundreds of megabytes) are better for reads, but too few files lose parallelism.

### Common misconception

Learners often think that `inferSchema` is harmless and that a successful read means correct data. A permissive read always succeeds: bad values just become null. The defence is an explicit schema plus a check of how many nulls each column has after reading.

## Syntax and key functions

```python
from pyspark.sql import SparkSession
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, DateType

spark = SparkSession.builder.appName("orders").getOrCreate()

schema = StructType([
    StructField("order_id", StringType(), False),
    StructField("customer_id", StringType(), True),
    StructField("amount", DoubleType(), True),
    StructField("order_date", DateType(), True),
])

orders = spark.read.csv("data/orders.csv", header=True, schema=schema, mode="PERMISSIVE")
events = spark.read.json("data/events.jsonl")
clean = spark.read.parquet("warehouse/orders_clean")

(orders.repartition("order_date")
       .write.mode("overwrite")
       .partitionBy("order_date")
       .parquet("warehouse/orders_clean"))
```

| Call | What it does |
|---|---|
| `spark.read.csv(path, header=True, schema=s, mode=m)` | Reads CSV with column names, a schema and a bad-row mode. |
| `spark.read.json(path)` | Reads JSON Lines; add `multiLine=True` for one multi-line document. |
| `spark.read.parquet(path)` | Reads Parquet; the schema comes from the files. |
| `df.printSchema()` | Prints the column names, types and nullability. |
| `df.write.mode(m).parquet(path)` | Writes a directory of Parquet files with the given save mode. |
| `.partitionBy("col")` | Writes one subdirectory per value of `col`. |
| `df.repartition(n)` or `df.repartition("col")` | Reshuffles to `n` partitions or by a column. |
| `df.coalesce(n)` | Reduces the number of partitions without a full shuffle. |

## Learn by example

### Example 1: What a permissive read with a schema produces

The PySpark call is `spark.read.csv(path, header=True, schema=schema)` with the schema above. The equivalent below parses the same text with pandas: values that do not fit the type become missing (the same as `PERMISSIVE`), and a null count per column is the check that follows a read. Note that without a schema every column would be text.

```python run
import io
import pandas as pd

text = """order_id,customer_id,amount,order_date
1001,C1,19.99,2025-03-01
1002,C2,abc,2025-03-01
1003,C1,45.00,2025-03-02
1004,,12.50,2025-03-02
1005,C3,30.00,not-a-date
"""
raw = pd.read_csv(io.StringIO(text), dtype=str)
print("without a schema, every column is text:", sorted(set(raw.dtypes.astype(str))))
typed = raw.copy()
typed["amount"] = pd.to_numeric(typed["amount"], errors="coerce")
typed["order_date"] = pd.to_datetime(typed["order_date"], format="%Y-%m-%d", errors="coerce")
print(typed.isna().sum().to_string())
print("rows read:", len(typed), "| rows with any null:", int(typed.isna().any(axis=1).sum()))
```

```output
without a schema, every column is text: ['object']
order_id       0
customer_id    1
amount         1
order_date     1
rows read: 5 | rows with any null: 3
```

The permissive read keeps all five rows. Three of them carry a null: a non-numeric amount, a missing customer and an invalid date. A job that only counted rows would report success, so counting nulls is the validation step.

### Example 2: Reading JSON Lines with nested fields

The PySpark call is `spark.read.json(path)`, and the nested customer is reached with `col("customer.id")`. The equivalent parses each line with the `json` module and flattens it with `pd.json_normalize`, whose dotted column names match Spark's dot notation.

```python run
import json
import pandas as pd

lines = [
    '{"order_id": 1, "customer": {"id": "C1", "country": "DE"}, "amount": 19.99}',
    '{"order_id": 2, "customer": {"id": "C2", "country": "FR"}, "amount": 45.0}',
    '{"order_id": 3, "customer": {"id": "C1", "country": "DE"}, "amount": 12.5}',
]
df = pd.json_normalize([json.loads(x) for x in lines])
print(list(df.columns))
print(df.groupby("customer.country")["amount"].sum().round(2).to_string())
```

```output
['order_id', 'amount', 'customer.id', 'customer.country']
customer.country
DE    32.49
FR    45.00
```

Each line is one record, which is why the format is called JSON Lines. A file with the same records inside one big array needs `multiLine=True` in Spark.

### Example 3: The layout of a partitioned write

The PySpark call is `df.write.partitionBy("order_date").parquet(path)`. The equivalent below builds the directory names and the rows each directory would hold. The partition value lives in the directory name, and the data files keep only the other columns.

```python run
import pandas as pd

df = pd.DataFrame({
    "order_id": [1, 2, 3, 4, 5, 6, 7],
    "order_date": ["2025-03-01", "2025-03-01", "2025-03-02", "2025-03-02", "2025-03-02", "2025-03-03", "2025-03-01"],
    "amount": [10.0, 20.0, 5.0, 7.5, 12.5, 40.0, 3.0],
})
layout = {}
for value, part in df.groupby("order_date"):
    layout[f"order_date={value}/"] = part.drop(columns="order_date")
for directory, part in layout.items():
    print(directory, "rows:", len(part), "columns in file:", list(part.columns))
```

```output
order_date=2025-03-01/ rows: 3 columns in file: ['order_id', 'amount']
order_date=2025-03-02/ rows: 3 columns in file: ['order_id', 'amount']
order_date=2025-03-03/ rows: 1 columns in file: ['order_id', 'amount']
```

Three directories are written, and the column `order_date` is not stored inside them. When the parent path is read again, Spark rebuilds `order_date` from the directory names.

### Example 4: Partition pruning and the number of files

A filter on the partition column lets Spark skip the other directories. The code counts the rows that a job would scan with and without the partition layout. It also simulates the number of output files: rows are spread over 3 tasks in turn, and every task writes one file for each date it holds. Repartitioning by date first gives one file per date. This is an illustration of the rule (one file per task and partition value with data), not a measurement of Spark.

```python run
import pandas as pd

dates = ["2025-03-01", "2025-03-02", "2025-03-03", "2025-03-04"]
df = pd.DataFrame({"order_id": range(1, 41), "order_date": [dates[i % 4] for i in range(40)]})

wanted = "2025-03-02"
print("rows in the data:", len(df), "| rows returned by the filter:", int((df["order_date"] == wanted).sum()))
print("rows scanned without partitions:", len(df), "| with partition pruning:", int((df["order_date"] == wanted).sum()))

tasks = 3
df["task"] = [i % tasks for i in range(len(df))]
files_default = df.groupby(["order_date", "task"]).ngroups
files_by_date = df["order_date"].nunique()
print("files with 3 mixed tasks:", files_default, "| after repartition by date:", files_by_date)
```

```output
rows in the data: 40 | rows returned by the filter: 10
rows scanned without partitions: 40 | with partition pruning: 10
files with 3 mixed tasks: 12 | after repartition by date: 4
```

Without a layout the job reads all 40 rows to return 10. With partitions it reads one directory. The mixed tasks produce 12 small files, and grouping by date first produces 4 files, which is the small-files effect in miniature.

### Example 5: Save modes

The behaviour of the four modes is easy to confuse, so it is simulated on a dictionary standing for the output directory. The function returns what the directory holds after the second write of the same data, or an error when the path already exists.

```python run
def write(store, rows, mode):
    exists = bool(store)
    if mode == "errorifexists" and exists:
        raise FileExistsError("path already exists")
    if mode == "ignore" and exists:
        return store
    if mode == "overwrite":
        return list(rows)
    return store + list(rows)

for mode in ("overwrite", "append", "ignore", "errorifexists"):
    store = write([], ["a", "b"], mode)
    try:
        store = write(store, ["a", "b"], mode)
        print(f"{mode:14} second run leaves {len(store)} rows: {store}")
    except FileExistsError as e:
        print(f"{mode:14} second run fails: {e}")
```

```output
overwrite      second run leaves 2 rows: ['a', 'b']
append         second run leaves 4 rows: ['a', 'b', 'a', 'b']
ignore         second run leaves 2 rows: ['a', 'b']
errorifexists  second run fails: path already exists
```

Only `overwrite` and `ignore` leave the data as it was after a repeated run; `append` doubles it. This is why re-runnable jobs overwrite their partition.

### Example 6: The aggregation a job would print

Suppose a job reads the orders and prints `df.groupBy(year("order_date")).count()`. The PySpark form is shown in the Syntax section's style, and the result is verified with the same aggregation in SQL on the browser database, which holds the Northwind orders.

```sql run
SELECT EXTRACT(year FROM order_date)::int AS year, COUNT(*) AS count
FROM orders
GROUP BY 1
ORDER BY 1;
```

```output
year | count
1996 | 34
1997 | 33
1998 | 33
```

The equivalent PySpark job is `orders.groupBy(F.year("order_date").alias("year")).count().orderBy("year").show()`, with `from pyspark.sql import functions as F`. The table it prints has the same rows. In Spark the row order of a grouped result is not guaranteed without `orderBy`.

## Real-world applications

- **Landing zone to curated layer**: raw CSV and JSON files from partners are read with an explicit schema, validated, and written as date-partitioned Parquet that analysts and downstream jobs read.
- **Cost control**: partitioning by date means a report on one day reads one directory instead of the whole history, as in Example 4.
- **Re-runnable daily jobs**: a job that overwrites only the day's partition can be run again after a failure without duplicating data (Example 5).
- **Small-file cleanup**: a compaction job reads a partition with hundreds of small files and rewrites it with `coalesce` into a few large ones.

## Daily review

### Key takeaways

- Reads are lazy; use an explicit schema for regular jobs, and know what `mode` does with bad rows.
- Count nulls after a permissive read, because the read itself never fails on bad values.
- Parquet carries its schema, prunes columns, skips blocks and compresses well.
- A write produces a directory of files, one per non-empty partition; `partitionBy` adds subdirectories named `col=value`.
- `append` duplicates on re-runs; overwrite the partition for idempotency; control file counts with `repartition` and `coalesce`.

### Common mistakes

- Relying on `inferSchema` for a production job. It costs an extra pass and can pick the wrong type; define a `StructType`.
- Treating a successful permissive read as clean data. Rows with bad values arrive with nulls; count them.
- Partitioning by a column with very many distinct values. You get a huge number of tiny directories; choose a date or another low-cardinality column.
- Using `append` in a job that is retried. The retry duplicates the data; overwrite the partition instead.
- Forgetting `multiLine=True` for a single multi-line JSON document. Spark produces a corrupt-record column instead of your fields.

### Revision notes

- Reader options: `header`, `schema`, `inferSchema`, `mode`; JSON Lines by default.
- Writer: `mode(...)`, `partitionBy(...)`, `repartition`, `coalesce`.
- Files written = non-empty partitions (times partition values when `partitionBy` is used).
- Equivalents: pandas for layout logic, SQL for aggregations; Spark's own speed and files cannot be tested here.

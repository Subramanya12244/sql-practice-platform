## Objectives

- Explain why a pipeline needs automated tests and which parts of it are cheap to test.
- Write unit tests for small transform functions with plain `assert` statements and `pytest.raises`.
- Build small test data with fixtures and `parametrize` so that tests stay short.
- Write an integration test that runs a whole extract, transform and load against a temporary database and checks the result and a rerun.
- Run `pytest` from the command line and read its summary line.

## Understand

### Why test a pipeline

A pipeline that "worked last night" has only shown that one input produced one output. A test is a small program that runs your code on chosen input and checks the output against what you decided it should be. When you change `clean_amount` next month, the tests tell you within seconds whether you broke a case you had already solved. Without them, the only test is the dashboard that a stakeholder opens.

Data pipelines are well suited to testing because most of their logic can be written as **pure functions**: functions whose output depends only on their inputs and that touch no database, file or network. `clean_amount("$1,250.50")` always returns `125050`. You can call it a thousand times in a test in a few milliseconds. The design advice that follows is practical: keep transforms as pure functions, push reading and writing to the edges of the pipeline, and the parts that hold the business rules become easy to test.

### Unit tests, fixtures and integration tests

A **unit test** exercises one small piece of code, usually one function, with a handful of inputs. In `pytest`, a test is a function whose name starts with `test_` in a file named `test_*.py` (pytest also accepts `*_test.py`). It passes when it finishes without raising an exception, and fails when an `assert` is false. `pytest` rewrites `assert` so that a failure prints both sides of the comparison, so you write plain `assert clean_amount("5") == 500` and need no special methods.

A **fixture** is a function marked with `@pytest.fixture` that builds something tests need, such as a small list of orders or an empty in-memory database. A test asks for it by naming it as a parameter, and `pytest` calls the fixture and passes the result in. This keeps repeated set-up out of the tests and gives each test a fresh copy. The data in a fixture should be **small and chosen**: five rows that each stand for one case (a duplicate, a failed order, a bad amount) teach more than five thousand random rows.

`@pytest.mark.parametrize("raw, expected", [...])` runs one test function once per pair of values, and reports each pair separately. It replaces a copy-pasted block of asserts when you want to check twenty spellings of an amount. Use `with pytest.raises(ValueError):` to assert that bad input is rejected: the test passes only if that exception is raised inside the block.

An **integration test** runs several pieces together, for example the real extract, transform and load against a temporary database, and checks the end state: the number of rows in the table, the sum of the amounts, and that running the pipeline a second time changes nothing (Day 94's idempotency). pytest provides `tmp_path`, a fixture that supplies a fresh temporary folder for each test, so the test can write an input file and a database file without touching your real data. Integration tests are slower and when one fails it points at a larger area, so you write many unit tests and a few integration tests.

### What to test

- **Normal cases** that represent real data.
- **Edge cases** found in real incidents: empty strings, a thousands separator, a currency symbol, a negative amount, a date at midnight.
- **Failure behaviour.** Does bad input raise a clear error, or silently become zero? Pipelines that quietly coerce a bad value into 0 are worse than ones that stop.
- **The pipeline contract.** Counts, totals and idempotency, using the checks of Days 136 and 137 as assertions.

Test the behaviour you want, not how the code is written. A test that calls a private helper or checks the order of internal steps breaks when you refactor, even though the pipeline still gives the right answer.

### Running pytest

From the project folder, `python -m pytest -q` finds the test files, runs the tests and prints one character per test (`.` pass, `F` fail, `E` error in set-up) and a summary such as `5 passed`. `-q` makes the output quiet. A failure prints the line of the failed assert with the values on both sides. The exit status is 0 only when everything passes, which is what a CI system (Day 140) checks. Running `python -m pytest` rather than `pytest` also adds the current folder to the import path, so `import transforms` works.

### Common misconception

Learners often think tests need the real database and the real files. They do not; a test that depends on yesterday's production data fails whenever the data changes and tells you nothing about your code. Another misconception is that a high number of tests means good coverage: ten tests of the happy path leave bad input untested. A third is to treat a failing test as an obstacle and loosen the assert. The assert is the specification; if it is wrong, change it deliberately and explain why.

### Why it matters

The first time a transform fix silently breaks the cases you handled last month, the cost of the missing test is a wrong number in production. Tests are also documentation: a new engineer reads `test_clean_amount` and learns every input format the pipeline accepts.

## Syntax and key functions

A test file:

```python
import pytest
from transforms import clean_amount

def test_plain_amount():
    assert clean_amount("12.50") == 1250

def test_rejects_text():
    with pytest.raises(ValueError):
        clean_amount("twelve")

@pytest.mark.parametrize("raw, expected", [("1,000", 100000), ("$5", 500)])
def test_formats(raw, expected):
    assert clean_amount(raw) == expected

@pytest.fixture
def orders():
    return [{"order_id": 1, "updated_at": "2026-01-01"}]

def test_with_fixture(orders):
    assert len(orders) == 1
```

Command line:

```text
python -m pytest -q                 # run everything quietly
python -m pytest -q -k amount       # only tests whose name contains "amount"
python -m pytest -q test_file.py::test_plain_amount   # one test
```

| Item | What it does |
|---|---|
| `assert a == b` | Fails the test when false and shows both values. |
| `pytest.raises(Exc)` | Passes only if the block raises `Exc`. |
| `@pytest.fixture` | Declares a reusable set-up function; tests receive it by name. |
| `@pytest.mark.parametrize(names, cases)` | Runs one test once per case. |
| `tmp_path` | Built-in fixture: a fresh temporary folder (`pathlib.Path`). |
| `-q`, `-k expr`, `-x` | Quiet output, select by name, stop at the first failure. |
| Exit status | 0 when all tests pass, non-zero otherwise. |

## Learn by example

pytest needs a real Python process and files, so the `bash run` examples create a throwaway folder and show their output read-only. The browser examples teach the same ideas with a small assert harness that you can run in the page: `run_tests` calls every function whose name starts with `test_` and counts failures, and `raises` plays the role of `pytest.raises`.

### Example 1: Unit tests for transforms with pytest

The module `transforms.py` holds the three pure transforms of the order pipeline. The test file covers normal input, a thousands separator, a currency symbol, bad input and the latest-wins rule. The sed filter removes the run time from the summary line so that the output is stable.

```bash run
cat > transforms.py <<'EOF'
from datetime import datetime
from decimal import Decimal, InvalidOperation

def clean_amount(raw):
    text = str(raw).strip().replace("$", "").replace(",", "")
    try:
        value = Decimal(text)
    except InvalidOperation:
        raise ValueError(f"bad amount: {raw!r}")
    return int(value * 100)

def parse_ts(raw):
    return datetime.strptime(raw.strip(), "%Y-%m-%d %H:%M")

def dedupe_latest(rows):
    latest = {}
    for row in rows:
        key = row["order_id"]
        if key not in latest or row["updated_at"] > latest[key]["updated_at"]:
            latest[key] = row
    return [latest[k] for k in sorted(latest)]
EOF
cat > test_transforms.py <<'EOF'
import pytest
from transforms import clean_amount, parse_ts, dedupe_latest

def test_plain_amount():
    assert clean_amount("12.50") == 1250

def test_symbol_and_separator():
    assert clean_amount(" $1,250.50 ") == 125050

def test_bad_amount_raises():
    with pytest.raises(ValueError):
        clean_amount("twelve")

def test_parse_ts():
    ts = parse_ts("2026-01-05 10:30")
    assert (ts.year, ts.month, ts.hour, ts.minute) == (2026, 1, 10, 30)

def test_dedupe_keeps_latest():
    rows = [
        {"order_id": 2, "updated_at": "2026-01-02", "status": "paid"},
        {"order_id": 1, "updated_at": "2026-01-01", "status": "paid"},
        {"order_id": 2, "updated_at": "2026-01-03", "status": "refunded"},
    ]
    result = dedupe_latest(rows)
    assert [r["order_id"] for r in result] == [1, 2]
    assert result[1]["status"] == "refunded"
EOF
python -m pytest -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output
.....                                                                    [100%]
5 passed
```

Each dot is one passing test. The bad-amount test passes because `clean_amount` raises the `ValueError` the test expects; if the function returned 0 for bad input, that test would fail and reveal the silent coercion.

### Example 2: Fixtures and parametrize

The fixture builds a small list of orders once per test. `parametrize` checks six amount spellings with one function, and each case counts as its own test (the summary shows 6 plus 2). One of the tests deliberately checks the filter that drops failed orders, using only the fixture.

```bash run
cat > transforms.py <<'EOF'
from decimal import Decimal, InvalidOperation

def clean_amount(raw):
    text = str(raw).strip().replace("$", "").replace(",", "")
    try:
        value = Decimal(text)
    except InvalidOperation:
        raise ValueError(f"bad amount: {raw!r}")
    return int(value * 100)

def keep_valid(rows):
    return [r for r in rows if r["status"] != "failed"]
EOF
cat > test_param.py <<'EOF'
import pytest
from transforms import clean_amount, keep_valid

@pytest.fixture
def orders():
    return [
        {"order_id": 1, "status": "paid"},
        {"order_id": 2, "status": "failed"},
        {"order_id": 3, "status": "refunded"},
    ]

@pytest.mark.parametrize("raw, expected", [
    ("5", 500), ("5.5", 550), ("$5.05", 505), ("1,000", 100000), ("  7 ", 700), ("0", 0),
])
def test_amount_formats(raw, expected):
    assert clean_amount(raw) == expected

def test_failed_orders_dropped(orders):
    assert [r["order_id"] for r in keep_valid(orders)] == [1, 3]

def test_fixture_is_fresh(orders):
    orders.append({"order_id": 99, "status": "paid"})
    assert len(orders) == 4
EOF
python -m pytest -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output
........                                                                 [100%]
8 passed
```

The last test adds an order to the list; because each test receives a new copy from the fixture, the earlier test is unaffected, whatever the order the tests run in.

### Example 3: An integration test with a temporary database

The pipeline reads CSV text, cleans it and loads it into a SQLite table with `INSERT OR REPLACE` so a rerun is safe. The test uses `tmp_path` for the database file, runs the pipeline twice and checks the row count and the total, which is the contract from Days 94 and 136.

```bash run
cat > pipeline.py <<'EOF'
import csv, io, sqlite3

def run(csv_text, db_path):
    rows = list(csv.DictReader(io.StringIO(csv_text)))
    conn = sqlite3.connect(db_path)
    conn.execute("CREATE TABLE IF NOT EXISTS orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER, status TEXT)")
    with conn:
        for r in rows:
            if r["status"] == "failed":
                continue
            conn.execute("INSERT OR REPLACE INTO orders_clean VALUES (?, ?, ?)", (int(r["order_id"]), int(round(float(r["amount"]) * 100)), r["status"]))
    conn.close()
EOF
cat > test_pipeline.py <<'EOF'
import sqlite3
from pipeline import run

CSV = "order_id,amount,status\n1,12.50,paid\n2,3.00,failed\n3,7.25,refunded\n"

def totals(db):
    conn = sqlite3.connect(db)
    out = conn.execute("SELECT COUNT(*), SUM(amount_cents) FROM orders_clean").fetchone()
    conn.close()
    return out

def test_load_counts_and_sum(tmp_path):
    db = tmp_path / "t.db"
    run(CSV, db)
    assert totals(db) == (2, 1975)

def test_rerun_is_idempotent(tmp_path):
    db = tmp_path / "t.db"
    run(CSV, db)
    run(CSV, db)
    assert totals(db) == (2, 1975)
EOF
python -m pytest -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output
..                                                                       [100%]
2 passed
```

The test checks outcomes only: count, sum and repeatability. If someone changes `INSERT OR REPLACE` to a plain `INSERT`, the second test fails with a primary-key error, which is the point of having it.

### Example 4: The same tests in the browser harness

Without pytest, the harness reproduces the mechanics: tests are functions, an assertion error is a failure, and `raises` checks an exception. One test is wrong on purpose so that you can see how a failure is reported, with its message.

```python run
from decimal import Decimal, InvalidOperation

class raises:
    def __init__(self, exc):
        self.exc = exc
    def __enter__(self):
        return self
    def __exit__(self, t, v, tb):
        if t is None:
            raise AssertionError(f"did not raise {self.exc.__name__}")
        return issubclass(t, self.exc)

def run_tests(ns):
    passed = failed = 0
    for name in sorted(ns):
        if name.startswith("test_") and callable(ns[name]):
            try:
                ns[name]()
                passed += 1
                print("PASS", name)
            except AssertionError as e:
                failed += 1
                print("FAIL", name, e)
    print(f"{passed} passed, {failed} failed")

def clean_amount(raw):
    text = str(raw).strip().replace("$", "").replace(",", "")
    try:
        value = Decimal(text)
    except InvalidOperation:
        raise ValueError(f"bad amount: {raw!r}")
    return int(value * 100)

def test_plain():
    assert clean_amount("12.50") == 1250

def test_separator():
    assert clean_amount("1,000") == 100000

def test_bad_raises():
    with raises(ValueError):
        clean_amount("abc")

def test_wrong_on_purpose():
    assert clean_amount("2.5") == 25, f"got {clean_amount('2.5')}"

run_tests(globals())
```

```output
PASS test_bad_raises
PASS test_plain
PASS test_separator
FAIL test_wrong_on_purpose got 250
3 passed, 1 failed
```

The failing line shows the value the function returned, as pytest does. The test was wrong, not the function: 2.5 is 250 cents. The assert is the specification, so the fix is in the test.

### Example 5: A realistic fixture-style integration test in the browser

The pipeline function runs on an in-memory `sqlite3` database and the tests check the expected row count, the total, and a rerun, using a helper that builds a fresh database for each test (the role of a fixture).

```python run
import sqlite3

def load(conn, rows):
    conn.execute("CREATE TABLE IF NOT EXISTS orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER, status TEXT)")
    with conn:
        for oid, amount, status in rows:
            if status != "failed":
                conn.execute("INSERT OR REPLACE INTO orders_clean VALUES (?, ?, ?)", (oid, amount, status))

def fresh_db():
    return sqlite3.connect(":memory:")

RAW = [(1, 1250, "paid"), (2, 300, "failed"), (3, 725, "refunded")]

def test_counts():
    conn = fresh_db()
    load(conn, RAW)
    assert conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0] == 2

def test_sum():
    conn = fresh_db()
    load(conn, RAW)
    assert conn.execute("SELECT SUM(amount_cents) FROM orders_clean").fetchone()[0] == 1975

def test_rerun():
    conn = fresh_db()
    load(conn, RAW)
    load(conn, RAW)
    assert conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0] == 2

for name in sorted(n for n in globals() if n.startswith("test_")):
    globals()[name]()
    print("PASS", name)
```

```output
PASS test_counts
PASS test_rerun
PASS test_sum
```

Each test builds its own database, so one test cannot leave rows behind for another.

## Real-world applications

- **Transform libraries.** The functions `clean_amount`, `parse_ts` and `dedupe_latest` are tested with every format found in production incidents, so a later fix cannot reintroduce an old bug.
- **Schema and contract tests.** A test loads a sample file and asserts the columns and types the pipeline promises downstream.
- **Pipeline regression tests.** A small input file and its expected output table are stored with the code; every change runs the whole pipeline against it and fails on any difference, using the comparison techniques of Day 136.
- **Gate before deployment.** The test command runs automatically on each pull request (Day 140), so broken code cannot reach the scheduler.

## Daily review

### Key takeaways

- Keep transforms pure and test them with plain `assert`; test failure paths with `pytest.raises`.
- Fixtures give each test small, fresh data; `parametrize` runs one test over many cases.
- Integration tests run the whole pipeline against a temporary database and check counts, sums and a rerun.
- Run with `python -m pytest -q`; exit status 0 means success.
- Few integration tests, many unit tests.

### Common mistakes

- **Testing against production data.** Tests break when the data changes. Use small chosen data.
- **Sharing mutable state between tests.** A list changed by one test changes the next. Build data in a fixture.
- **Asserting only the happy path.** Bad input then passes silently. Add `pytest.raises` cases.
- **Naming a file `checks.py` or a function `check_amount`.** pytest finds nothing and reports `no tests ran`. Use a `test_*.py` file and `test_*` functions.
- **Running `pytest` from the wrong folder so imports fail** (`ModuleNotFoundError`). Run `python -m pytest` in the project folder.

### Revision notes

- Names: `test_*.py`, `def test_*`. Fixture: `@pytest.fixture`. Parametrize: `@pytest.mark.parametrize`.
- `with pytest.raises(ValueError):`; `tmp_path` for temporary files.
- Summary line: `N passed`; `.` passed, `F` failed, `E` set-up error.
- Contract assertions: count, sum, idempotent rerun.

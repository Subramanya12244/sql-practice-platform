## Objectives

- Write a test as a function with plain `assert` statements and explain what a failing assertion reports.
- Name files, functions and classes so that pytest discovers them, and run pytest from the command line.
- Structure a test with arrange, act and assert.
- Test that a function raises the right exception with `pytest.raises`.

## Understand

### Why write tests

Code that worked yesterday can break today after an edit somewhere else. A **test** is a small program that calls your code with known input and checks the result. An **automated test suite** runs hundreds of such checks in seconds, so you find out immediately that a change broke something, long before wrong numbers reach a report or a customer. Tests also document what the code is supposed to do. In data work they protect cleaning functions, parsers and calculations: if `apply_discount(200, 10)` must return 180, a test says so, and it keeps saying so for as long as the code lives.

### The assert statement

Python's `assert condition` checks that a condition is true. If it is true, nothing happens. If it is false, Python raises an `AssertionError` (an exception, day 21). `assert x == 5, "x was wrong"` adds a message. Assertions are the building block of tests: a test function is just code that ends in one or more asserts. A test **passes** when the function finishes without an exception and **fails** when an assertion (or any other exception) is raised. Note that assertions can be switched off with `python -O`, so use them for tests and sanity checks, never to validate user input in real code.

### pytest

**pytest** is the most widely used Python test tool. It is a third-party package (`pip install pytest`), not part of the standard library, which is why the examples of this lesson run on your own computer and are shown read-only in the browser. pytest finds your tests, runs them, and prints a short report. Its main strength is that a test is only a function with plain `assert`: when the assertion fails, pytest rewrites it to show the values involved, such as `assert 190.0 == 180`, so you rarely need special comparison methods.

### Test discovery

You do not list tests by hand. pytest **discovers** them by naming convention, starting from the current folder: it collects files named `test_*.py` or `*_test.py`, inside them functions whose names start with `test`, and classes whose names start with `Test` (without an `__init__` method), with methods starting with `test`. Anything else is ignored: a function called `check_total` or a file called `helpers.py` is not a test. A common mistake is a misnamed function that silently never runs, and `pytest --collect-only` shows what was found. Running `python -m pytest` runs everything found; `-q` makes output quiet, `-v` lists each test, `-k text` selects tests whose name contains the text, and `-x` stops at the first failure.

### Reading the result

pytest prints one character per test: a dot for a pass, `F` for a failure and `E` for an error outside the test body, and finishes with a summary such as `1 failed, 3 passed`. For each failure it shows the test, the source lines, the failing line marked with `>` and the line starting with `E` that explains the mismatch. The process exit status is 0 when all tests pass and non-zero otherwise, so scripts and continuous integration can react.

### Arrange, act, assert

A readable test has three parts. **Arrange**: prepare the input and objects. **Act**: call the one thing you test. **Assert**: check the outcome. Keep one behaviour per test and give the test a name that says what it checks, such as `test_discount_over_100_is_rejected`. When a test fails, the name should tell you what broke before you read any code. Tests must not depend on each other or on the order in which they run.

### Testing exceptions

Sometimes the correct behaviour is to fail: a negative price must raise `ValueError`. Use `with pytest.raises(ValueError):` around the call. The test passes only if that exception type is raised inside the block, and fails if nothing is raised or a different exception occurs. `match="text"` checks the message with a regular expression search, and `as excinfo` gives access to the exception object through `excinfo.value`.

### Common misconception

Many beginners think that a test is only useful if it fails once. Its value is mostly protective: it passes thousands of times and fails the one time that something breaks. Another belief is that passing tests prove the code is correct. They prove that the cases you wrote work. Choosing the cases, especially the edge cases, is the real work (day 62).

### Why it matters

Data pipelines change often: new columns, new rules, new sources. A suite of fast tests around the transformation functions lets you change them with confidence and is the first thing reviewers expect in a professional repository.

## Syntax and key functions

```python
def test_name():
    # arrange
    ...
    # act
    result = function_under_test(...)
    # assert
    assert result == expected
```

```python nocheck
with pytest.raises(ExceptionType, match="regex"):
    function_under_test(bad_input)
```

```text
python -m pytest              # run all discovered tests
python -m pytest -q           # quiet output
python -m pytest -v           # one line per test
python -m pytest -k discount  # only tests whose name contains "discount"
python -m pytest -x           # stop after the first failure
python -m pytest --collect-only -q   # list what would run
```

| Item | Meaning |
|---|---|
| `assert cond` | Raises `AssertionError` when `cond` is false |
| `test_*.py`, `test_*()`, `Test*` | Names that pytest discovers |
| `pytest.raises(E)` | Passes only if the block raises `E` |
| `match="text"` | Regular expression searched in the exception message |
| `.` / `F` / `E` | Pass, fail, error in the progress line |
| exit status 0 | All tests passed |

## Learn by example

### Example 1: assert in plain Python

Before pytest, see what `assert` does. A true condition is silent. A false one raises `AssertionError` with the optional message. This runs in the browser because it needs no extra package.

```python run
def apply_discount(price, percent):
    return round(price * (1 - percent / 100), 2)

assert apply_discount(200, 10) == 180
print("first check passed")

try:
    assert apply_discount(200, 10) == 190, "expected 190"
except AssertionError as error:
    print("assertion failed:", error)
```

```output
first check passed
assertion failed: expected 190
```

### Example 2: a module, its tests, and a passing run

The shell commands write a small module `pricing.py` and a test file `test_pricing.py` in a throwaway folder, then run pytest. Four dots mean four passing tests. The `sed` command removes the elapsed time from the last line, so the output is the same each run. This needs pytest on your computer, so it is shown read-only here.

```bash run
cat > pricing.py <<'PY'
def apply_discount(price, percent):
    if not 0 <= percent <= 100:
        raise ValueError("percent must be between 0 and 100")
    return round(price * (1 - percent / 100), 2)

def total(items):
    return sum(price * qty for price, qty in items)
PY
cat > test_pricing.py <<'PY'
import pytest
from pricing import apply_discount, total

def test_discount_ten_percent():
    assert apply_discount(200, 10) == 180

def test_total_of_two_items():
    assert total([(10, 2), (5, 1)]) == 25

def test_total_of_nothing_is_zero():
    assert total([]) == 0

def test_discount_over_100_is_rejected():
    with pytest.raises(ValueError, match="between 0 and 100"):
        apply_discount(100, 120)
PY
python -m pytest -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output
....                                                                     [100%]
4 passed
```

### Example 3: reading a failure

This test has a wrong expectation on purpose: 10 percent off 200 is 180, not 190. pytest shows the test name, the source with a `>` marker on the failing line, and an `E` line with the comparison of the two values. The last line counts the outcome. The `-p no:cacheprovider` flag stops pytest from writing a cache folder.

```bash run
cat > pricing.py <<'PY'
def apply_discount(price, percent):
    return round(price * (1 - percent / 100), 2)
PY
cat > test_pricing.py <<'PY'
from pricing import apply_discount

def test_discount_ten_percent():
    assert apply_discount(200, 10) == 190

def test_no_discount():
    assert apply_discount(50, 0) == 50
PY
python -m pytest -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

### Example 4: what pytest discovers

Three files exist: `test_math.py` has a test and a helper, `check_text.py` has a function named `test_upper` that pytest ignores because the file name does not match, and `helpers.py` is not a test file at all. `--collect-only -q` lists the tests found without running them. Only the test function with the right name in the right file is collected.

```bash run
cat > test_math.py <<'PY'
def test_add():
    assert 1 + 2 == 3

def check_subtract():
    assert 3 - 2 == 1
PY
cat > check_text.py <<'PY'
def test_upper():
    assert "a".upper() == "A"
PY
cat > helpers.py <<'PY'
def test_helper():
    assert True
PY
python -m pytest --collect-only -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output
test_math.py::test_add

1 test collected
```

### Example 5: arrange, act, assert in a class

A `Cart` class is tested with three tests in a class named `TestCart`. Each test builds its own cart (arrange), calls one method (act) and checks one thing (assert). Tests do not share state, so the order does not matter. `-v` prints each test by name, which is why the names should describe the behaviour; the `grep PASSED` keeps only the result lines, because the header lines of `-v` differ between pytest versions.

```bash run
cat > cart.py <<'PY'
class Cart:
    def __init__(self):
        self.items = []

    def add(self, name, price, qty=1):
        self.items.append((name, price, qty))

    def total(self):
        return sum(price * qty for _, price, qty in self.items)
PY
cat > test_cart.py <<'PY'
from cart import Cart

class TestCart:
    def test_new_cart_is_empty(self):
        cart = Cart()
        assert cart.total() == 0

    def test_total_multiplies_price_by_quantity(self):
        cart = Cart()
        cart.add("pen", 2.5, qty=4)
        assert cart.total() == 10

    def test_total_adds_all_lines(self):
        cart = Cart()
        cart.add("pen", 2.5)
        cart.add("book", 12)
        assert cart.total() == 14.5
PY
python -m pytest -v -p no:cacheprovider 2>&1 | grep PASSED
```

```output
test_cart.py::TestCart::test_new_cart_is_empty PASSED                    [ 33%]
test_cart.py::TestCart::test_total_multiplies_price_by_quantity PASSED   [ 66%]
test_cart.py::TestCart::test_total_adds_all_lines PASSED                 [100%]
```

### Example 6: testing that an exception is raised

`validate_age` must reject negative and non-integer ages. Each rejection is checked with `pytest.raises`, one with `match` for the message. The last test shows `as excinfo` to inspect the exception. If the function failed to raise, the test would fail with `DID NOT RAISE`.

```bash run
cat > validate.py <<'PY'
def validate_age(age):
    if not isinstance(age, int):
        raise TypeError("age must be an integer")
    if age < 0:
        raise ValueError("age must not be negative")
    return age
PY
cat > test_validate.py <<'PY'
import pytest
from validate import validate_age

def test_valid_age_is_returned():
    assert validate_age(30) == 30

def test_negative_age_is_rejected():
    with pytest.raises(ValueError, match="negative"):
        validate_age(-1)

def test_text_age_is_rejected():
    with pytest.raises(TypeError):
        validate_age("30")

def test_exception_message_is_available():
    with pytest.raises(ValueError) as excinfo:
        validate_age(-5)
    assert str(excinfo.value) == "age must not be negative"
PY
python -m pytest -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output
....                                                                     [100%]
4 passed
```

## Real-world applications

**Protecting data-cleaning functions.** A function that normalises phone numbers or parses dates gets a few tests with typical and awkward inputs (Examples 2 and 5). When someone adds a new format, the old cases keep proving that nothing else changed.

**Failing loudly on bad data.** Pipelines should reject invalid input instead of passing it on. Testing the rejection with `pytest.raises` (Example 6) documents the contract and prevents a quiet change that lets bad rows through.

**Continuous integration.** The exit status of pytest tells a build server whether a change may be merged. A failed test blocks the merge, which is how teams keep shared data code reliable.

**Refactoring safely.** Before rewriting a slow transformation you run its tests, rewrite, and run them again. Green tests after the change are evidence that behaviour was preserved.

## Daily review

### Key takeaways

- A test is a function that calls code and uses `assert`; it passes when no exception is raised.
- pytest discovers `test_*.py` files, `test*` functions and `Test*` classes; other names are ignored.
- Read a failure from the `>` line and the `E` lines; the last line summarises the run.
- Keep tests small: arrange, act, assert, one behaviour per test, no dependence on order.
- `pytest.raises(E, match="...")` tests expected failures.
- Passing tests prove only the cases you wrote.

### Common mistakes

- Naming a test `check_total` or putting it in `utils.py`, so pytest never runs it. Use `--collect-only` to see what was found.
- Comparing floats exactly, such as `assert 0.1 + 0.2 == 0.3`, which fails. Use `pytest.approx` (day 62 shows it) or round.
- Writing several unrelated asserts in one test, so the first failure hides the others.
- Using `assert` with a tuple, `assert (cond, "message")`, which is always true. Write `assert cond, "message"`.
- Testing by printing instead of asserting; a test that prints nothing wrong can still pass.
- Catching the exception yourself with `try/except` and forgetting to fail when nothing is raised. Use `pytest.raises`.

### Revision notes

- File `test_*.py`, function `test_*`, run `python -m pytest -q`.
- `assert actual == expected`; pytest shows the values.
- `with pytest.raises(ValueError, match="text"):` for expected exceptions.
- Exit status 0 means all passed.

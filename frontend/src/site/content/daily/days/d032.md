## Understand

### The SELECT list is a set of expressions

Yesterday you wrote `SELECT column_a, column_b FROM table`. The part between `SELECT` and `FROM` is called the **select list**. Each item in it is an **expression**: anything the database can evaluate to produce one value for each row. A bare column name is the simplest expression. `unit_price * units_in_stock` is another; so is the text `'USD'`. The database evaluates every expression in the list once per row and returns the results as columns of the output.

This is the first piece of SQL's way of thinking. The `FROM` clause decides which rows are read, and then the select list decides what to compute from each row. The output is a brand-new table whose columns are whatever you listed, in the order you listed them. The original table is never changed by a `SELECT`.

### Choosing columns instead of using the star

`SELECT *` is handy for a first look, but in real work you should list columns. It keeps results small, it makes the query self-documenting, and it stops your report from changing shape when somebody adds a column to the table later. You may list the same column twice, and you may list columns in a different order from the table.

### Aliases: naming the output

An expression such as `unit_price * units_in_stock` has no natural name; PostgreSQL labels it `?column?`, which is useless. An **alias** gives an output column a name with the keyword `AS`: `unit_price * units_in_stock AS stock_value`. Aliases only rename the column in the result. They do not change the table. By convention aliases are lowercase words joined by underscores (`stock_value`). If you want spaces or capital letters, wrap the alias in double quotes: `AS "Stock value"`. Without quotes PostgreSQL folds names to lowercase.

The keyword `AS` is optional in PostgreSQL, so `unit_price price` also works. It is also a trap, because forgetting a comma between two columns silently turns the second one into an alias of the first. Always write `AS`.

### Expressions with numbers, text and dates

For numbers, SQL has the usual operators `+ - * /`, plus `%` (remainder) and `^` (power). Multiplication and division bind tighter than addition and subtraction; use parentheses when in doubt.

For text, `||` joins two strings: `first_name || ' ' || last_name`. Functions such as `UPPER`, `LOWER`, `LENGTH` and `LEFT(text, n)` take a value and return a value. If either side of `||` is NULL, the whole result is NULL; day 35 shows how to handle that.

For dates, you can add and subtract whole numbers of days. `order_date + 30` is a date thirty days later. Subtracting two dates gives a plain integer, the number of days between them.

A **literal** is a value written directly in the query: `42`, `1.5`, `'USD'` (text in single quotes) or `DATE '1998-05-06'`. Selecting a literal repeats it on every row, which is useful to add a constant label. You can also select expressions with no `FROM` at all, for example `SELECT 2 * 3;`. That returns one row and is perfect for testing a calculation.

### Data types and casting

Every expression has a data type, and the type decides the behaviour. The most important surprise for beginners is that **dividing two integers gives an integer**: `7 / 2` is `3`, not `3.5`. The fraction is thrown away. If either side is `numeric` (for example `7 / 2.0`), the result is numeric and keeps the fraction.

To convert a value from one type to another you **cast** it. The standard form is `CAST(value AS type)`; PostgreSQL also accepts the shorthand `value::type`. Casting `'42'` to `integer` turns text into a number. Casting a `numeric` such as `15.50` to `integer` rounds to the nearest whole number (it gives `16`); it does not cut off the decimals.

There is one more type issue that appears constantly in sales data. In Northwind, `order_details.unit_price` is `numeric` (exact), while `order_details.discount` is `real`, a binary floating point type. A calculation that mixes them is carried out in floating point, so the result is not exact and `ROUND(value, 2)` fails with the error `function round(double precision, integer) does not exist`. PostgreSQL only has a two-argument `ROUND` for `numeric`. The fix is to cast the odd one out: `CAST(discount AS numeric)`.

### Common misconception

People assume that an alias can be used anywhere in the query, for example in the same select list. It cannot: `SELECT unit_price * 2 AS double_price, double_price + 1` fails, because all select-list expressions are evaluated side by side. You will see on day 34 that `ORDER BY` is allowed to use an alias, because it runs after the select list; `WHERE`, which runs earlier, cannot.

### Why it matters

Almost every analytical query is a select list in disguise: revenue is `quantity * unit_price`, a full name is two text columns joined, a delivery window is the difference of two dates. Correct types and clear aliases are what separate a query that merely runs from a result a colleague can trust.

## Syntax and key functions

The select list with aliases:

```sql-syntax
SELECT expression_1 AS alias_1,
       expression_2 AS "Alias with spaces",
       column_3
FROM table_name;
```

A select list without a table, for testing an expression:

```sql-syntax
SELECT expression AS alias;
```

Casting, in the standard form and the PostgreSQL shorthand:

```sql-syntax
CAST(expression AS data_type)
expression::data_type
```

| Operator or function | What it returns | Example and result |
|---|---|---|
| `+  -  *` | Sum, difference, product; type follows the operands | `unit_price * 2` gives `36.00` for price `18.00` |
| `/` | Quotient; integer division when both sides are integers | `7 / 2` gives `3`, `7 / 2.0` gives `3.5000000000000000` |
| `%` | Remainder of integer division | `10 % 3` gives `1` |
| `^` | Power | `2 ^ 10` gives `1024` |
| `a \|\| b` | Text concatenation; NULL if either side is NULL | `'Nancy' \|\| ' ' \|\| 'Davolio'` gives `Nancy Davolio` |
| `UPPER(t)`, `LOWER(t)` | Text in upper or lower case | `UPPER('Chai')` gives `CHAI` |
| `LENGTH(t)` | Number of characters | `LENGTH('Chai')` gives `4` |
| `LEFT(t, n)` | First `n` characters | `LEFT('Nancy', 1)` gives `N` |
| `ROUND(numeric, n)` | Value rounded to `n` decimals; `numeric` only | `ROUND(19.8049, 2)` gives `19.80` |
| `date + integer` | A date that many days later | `DATE '1996-01-01' + 30` gives `1996-01-31` |
| `date - date` | Integer number of days between | `DATE '1996-01-15' - DATE '1996-01-01'` gives `14` |
| `CAST(x AS type)` or `x::type` | The value converted to the type | `CAST('42' AS integer)` gives `42` |

## Learn by example

### Example 1: Choose and reorder columns

Compare this with `SELECT *`. We name three columns of `products`, and we list them in an order different from the table. The `ORDER BY` and `LIMIT` are only here to keep the five rows stable; day 34 explains them.

```sql run
SELECT units_in_stock, product_name, unit_price
FROM products
ORDER BY product_id
LIMIT 5;
```

```output
units_in_stock | product_name | unit_price
21 | Chai | 18.00
22 | Chang | 19.00
23 | Aniseed Syrup | 10.00
24 | Chef Anton's Cajun Seasoning | 22.00
25 | Chef Anton's Gumbo Mix | 21.35
```

### Example 2: A calculated column with aliases

The stock value of a product is its price times the units in stock. The expression has no natural name, so we give it one with `AS`. We also rename two existing columns and add the literal `'USD'`, which appears unchanged on every row. The quoted alias `"Product"` keeps its capital letter. Notice that `numeric` times `integer` stays exact: `18.00 * 21` is `378.00`.

```sql run
SELECT product_name AS "Product",
       unit_price * units_in_stock AS stock_value,
       'USD' AS currency
FROM products
ORDER BY product_id
LIMIT 5;
```

```output
Product | stock_value | currency
Chai | 378.00 | USD
Chang | 418.00 | USD
Aniseed Syrup | 230.00 | USD
Chef Anton's Cajun Seasoning | 528.00 | USD
Chef Anton's Gumbo Mix | 533.75 | USD
```

### Example 3: Arithmetic, integer division and casts without a table

A `SELECT` with no `FROM` evaluates one row, so it is a calculator. The first two columns show integer division discarding the fraction versus a numeric division keeping it. Then multiplication before addition, parentheses overriding it, and the remainder. The last three columns cast: a numeric `15.5` becomes `16` (rounded, not cut), the text `'42'` becomes a number we can add to, and a text becomes a date we can add a day to.

```sql run
SELECT 7 / 2 AS integer_division,
       7 / 2.0 AS numeric_division,
       2 * 3 + 4 AS multiply_first,
       2 * (3 + 4) AS parentheses_first,
       10 % 3 AS remainder,
       CAST(15.5 AS integer) AS rounded,
       CAST('42' AS integer) + 1 AS text_to_number,
       CAST('1998-05-06' AS date) + 1 AS next_day;
```

```output
integer_division | numeric_division | multiply_first | parentheses_first | remainder | rounded | text_to_number | next_day
3 | 3.5000000000000000 | 10 | 14 | 1 | 16 | 43 | 1998-05-07
```

### Example 4: Building text

Here the `||` operator joins first name, a space literal and last name. `LEFT(name, 1)` takes the first letter of each, and `UPPER` makes the initials capital. `LENGTH` counts characters of the full name. Each expression is evaluated for every employee, and each gets an alias so the output has readable headings.

```sql run
SELECT employee_id,
       first_name || ' ' || last_name AS full_name,
       UPPER(LEFT(first_name, 1) || LEFT(last_name, 1)) AS initials,
       LENGTH(first_name || ' ' || last_name) AS name_length
FROM employees
ORDER BY employee_id
LIMIT 5;
```

```output
employee_id | full_name | initials | name_length
1 | Nancy Davolio | ND | 13
2 | Andrew Fuller | AF | 13
3 | Janet Leverling | JL | 15
4 | Margaret Peacock | MP | 16
5 | Steven Buchanan | SB | 15
```

### Example 5: Date arithmetic and your first NULL

`order_date + 30` adds days to a date. `required_date - order_date` subtracts two dates and returns an integer number of days. The first order has not been shipped, so `shipped_date` is NULL, and any arithmetic with NULL gives NULL. That is why `days_to_ship` shows `NULL` on the first row. Day 35 explains NULL in full.

```sql run
SELECT order_id,
       order_date,
       order_date + 30 AS payment_due,
       required_date - order_date AS days_allowed,
       shipped_date - order_date AS days_to_ship
FROM orders
ORDER BY order_id
LIMIT 6;
```

```output
order_id | order_date | payment_due | days_allowed | days_to_ship
10248 | 1996-01-01 | 1996-01-31 | 14 | NULL
10249 | 1997-02-02 | 1997-03-04 | 28 | 3
10250 | 1998-03-03 | 1998-04-02 | 28 | 3
10251 | 1996-04-04 | 1996-05-04 | 28 | 3
10252 | 1997-05-05 | 1997-06-04 | 28 | 30
10253 | 1998-06-06 | 1998-07-06 | 28 | 3
```

### Example 6: Mixing numeric and real, and fixing it with a cast

The line amount of an order line is `quantity * unit_price * (1 - discount)`. Because `discount` is a `real`, the raw result is a floating-point number and is slightly off: the first line shows `323.9999994635582` instead of `324`. Calling `ROUND` directly would fail. Casting the discount to `numeric` first makes the whole calculation exact, and then `ROUND(..., 2)` works and gives a clean money value.

```sql run
SELECT order_id,
       product_id,
       quantity * unit_price * (1 - discount) AS raw_float,
       ROUND(quantity * unit_price * (1 - CAST(discount AS numeric)), 2) AS net_amount
FROM order_details
ORDER BY order_id, product_id
LIMIT 6;
```

```output
order_id | product_id | raw_float | net_amount
10248 | 8 | 323.9999994635582 | 324.00
10249 | 16 | 191.95 | 191.95
10249 | 29 | 824.4999942183495 | 824.50
10250 | 10 | 341 | 341.00
10250 | 24 | 55.5749999564141 | 55.58
10250 | 29 | 468 | 468.00
```

## Real-world applications

**Derived metrics in reports.** Revenue, margin and stock value are all select-list expressions. Example 2 computes the value of stock on hand per product, and example 6 computes net revenue per order line, the building block of every sales dashboard in the later days.

**Cleaning and formatting for export.** A mailing list needs `first_name || ' ' || last_name` and upper-case initials, as in example 4. Writing this in SQL means the export is generated on the server and no spreadsheet formulas are needed.

**Service-level and delay measures.** Logistics and support teams measure days between two dates. Example 5 gives the days a customer allowed (`required_date - order_date`) and the days it took to ship, and a due date by adding days to a start date.

**Guarding against silent type errors.** Integer division, as in example 3, is a classic cause of wrong percentages (for example `successes / attempts` returning 0). Data analysts and engineers check types and cast at the point of calculation so that conversion rates and averages are right.

## Daily review

### Key takeaways

- The select list is a list of expressions evaluated once per row; the output is a new table with the columns you list.
- `AS` names an output column; use double quotes for spaces or capitals; always write `AS` explicitly.
- Numbers, text and dates each have their own operators; `||` joins text, and date minus date is a number of days.
- Integer divided by integer is an integer; make one side `numeric` to keep the fraction.
- `CAST(x AS type)` and `x::type` convert types; casting numeric to integer rounds.
- `ROUND(x, n)` needs a `numeric`; cast a `real` or `double precision` value first.

### Common mistakes

- Forgetting a comma between two select items, which turns the second into an alias of the first.
- Using an alias in `WHERE` or in the same select list; it does not exist yet at that point.
- Dividing two integer columns and being surprised by 0 or a whole number.
- Using double quotes for text values; they are for names, and single quotes are for text.
- Calling `ROUND(x, 2)` on a floating-point expression without casting it to `numeric`.
- Concatenating with `||` when a column may be NULL, which makes the whole text NULL.

### Revision notes

- Order of thought: FROM picks the rows, SELECT computes columns from each row.
- `AS alias`, `AS "Alias With Spaces"`.
- `7/2` is `3`, `7/2.0` is `3.5`. `x::numeric` fixes a type.
- `a || ' ' || b`, `UPPER`, `LOWER`, `LENGTH`, `LEFT`.
- `date + n`, `date - date`.
- `SELECT 1 + 1;` works without FROM and is a good way to test.

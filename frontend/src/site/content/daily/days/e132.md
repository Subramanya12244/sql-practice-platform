## Objectives

- Define six data quality dimensions precisely: completeness, validity, uniqueness, timeliness, consistency and accuracy.
- Measure each dimension on an orders DataFrame with a rate (good rows over checked rows) and name the failing rows.
- Tell the dimensions apart on a bad record (a value can be present but invalid, valid but inconsistent, consistent but inaccurate).
- Choose an honest threshold for a dimension from its business impact, and build a one-table scorecard.

## Understand

### Why quality needs words

"The data is bad" is not a finding. A manager cannot act on it and an engineer cannot test it. **Data quality dimensions** are agreed words for the different ways data can be wrong, and each comes with a way to measure it. With them, the statement becomes "2 of 10 customer ids are missing (80 percent complete), one status is outside the allowed list (90 percent valid) and one order id appears twice". The first is an opinion, the second can be put in a report and tracked from day to day. The ETL phase kept counts correct (Day 131: read equals quarantined plus duplicates plus skipped plus loaded). Counts say nothing about whether the values are right. This phase is about the values.

The running example is an `orders` DataFrame of ten rows with `order_id`, `customer_id`, `amount`, `status`, `currency`, `country` and `updated_at`. Several rows have deliberate defects, and every dimension finds a different one.

### Completeness

**Completeness** asks: is the data that should be there actually there? It is measured as the share of non-missing values in a column that is required: `1 - missing / total`. Missing means NULL or NaN, and also the placeholders that stand for nothing: empty text, a single space, `"N/A"`, `-1`, `1900-01-01`. A column that is allowed to be empty (an optional note) is not held to the rule; the first work is to decide which columns are required. In the example, two of ten `customer_id` values are missing and one `amount` is missing. Completeness can also be about rows: a day with 2 orders where 1,000 are expected is incomplete at the table level, which monitoring (Day 130) detects as a volume drop.

### Validity

**Validity** asks: does the value conform to the rules of its type and domain? A rule is a format (an order id matches `A` followed by digits), a range (`amount >= 0`), a set of allowed values (`status` is `paid`, `refunded` or `failed`) or a type (the amount is a number). Validity is measured as the share of non-missing values that satisfy the rule. Missing values are counted by completeness, not here, which keeps the two dimensions independent. In the example `shipped` and `PAID` are outside the allowed statuses and `-5.0` is outside the allowed range. A valid value is not necessarily true: `paid` is valid for an order that was never paid.

### Uniqueness

**Uniqueness** asks: is each real-world thing recorded once? It is measured on a key: `distinct keys / rows`, or the number of keys that appear more than once. The key must be chosen with care: `order_id` should be unique by itself, while `(order_id, line_number)` is the key of a line table. Duplicates are often exact copies (a retried load) or the same key with different values (two versions of one order, which Day 126's upsert resolves). In the example `A3` appears twice. A duplicate is dangerous because it silently doubles totals.

### Timeliness

**Timeliness** asks: is the data recent enough for its use? It is the age of a record against an expected freshness: `now - updated_at`. A threshold depends on the use: a daily revenue report may tolerate 26 hours, a fraud screen only seconds. Timeliness is the dimension that monitoring (Day 130's freshness) measures for the table as a whole; here it is applied to rows or columns. The clock must be passed in, so the check is repeatable: today's examples use a fixed `now` of 2025-03-06 12:00.

### Consistency

**Consistency** asks: does the data agree with itself? The same fact must not be recorded two different ways, within a record, across tables or over time. Within a record, an order in `country = US` should have `currency = USD` here; across tables, an order's `customer_id` must exist in the customer table (Day 135); over time, the status must not jump from `refunded` back to `created`. A different spelling of the same value (`EUR` and `eur`) is also an inconsistency. In the example, order `A10` is a US order paid in `EUR`. Each value is valid on its own; only the combination is wrong, which is why consistency needs its own rules.

### Accuracy

**Accuracy** asks: does the value match the truth? It is the hardest to measure because it needs a trusted **reference**: the source system, a control total, a signed document, a manual check of a sample. It is measured as the share of checked values that equal the reference. In the example a source extract shows that `A2` was `52.0`, but the table holds `25.0`: valid, complete, unique, recent and consistent, and still wrong. Accuracy can only be checked where a reference exists, usually for a sample or a total, which is why Days 136 and 137 compare source and target.

### Honest thresholds

A **threshold** is the rate below which a dimension fails. Pick it from the cost of being wrong, not from a round number: a missing `customer_id` might block a join in every report (require 100 percent and quarantine the rows), while a missing optional field can tolerate 5 percent. A threshold of 100 percent on everything fails every night and is ignored; a threshold of 50 percent protects nothing. State thresholds per dimension and per column, base them on a month of history, and review them when they fire for harmless reasons.

### Why it matters in data work

The dimensions turn quality into a table that can be built by code, published with each run and watched for trends. They also keep a team from fixing the wrong thing: duplicates need a key rule, invalid values need a source fix or a quarantine, inaccurate values need a reference.

## Syntax and key functions

```python
completeness = orders["customer_id"].notna().mean()                      # share present
validity = orders["status"].isin({"paid", "refunded", "failed"}).mean()    # share allowed (non-missing)
duplicates = orders["order_id"].duplicated(keep=False).sum()                # rows sharing a key
age_hours = (now - pd.to_datetime(orders["updated_at"])).dt.total_seconds() / 3600
```

| Item | What it does or returns |
|---|---|
| `s.notna().mean()` | Share of non-missing values (completeness). |
| `s.isin(allowed)` | Boolean per row: value in the allowed set. |
| `s.str.fullmatch(pattern)` | Boolean per row: the whole text matches the pattern; `NaN` for missing. |
| `s.duplicated(keep=False)` | True for every row whose value appears more than once. |
| `s.nunique() / len(s)` | Share of distinct values (uniqueness rate). |
| `pd.to_datetime(s)` | Converts text to datetimes. |
| `(a == b).mean()` | Share of rows where two series agree (accuracy against a reference). |

## Learn by example

### Example 1: Completeness

The share of non-missing values per column shows where data is absent. The required columns are `order_id`, `customer_id`, `amount` and `status`. Two customers and one amount are missing.

```python run
import pandas as pd

orders = pd.DataFrame({
    "order_id": ["A1", "A2", "A3", "A3", "A5", "A6", "A7", "A8", "A9", "A10"],
    "customer_id": [10, 11, None, 12, 13, 14, None, 15, 16, 17],
    "amount": [19.9, 25.0, 12.5, 12.5, -5.0, 40.0, None, 7.5, 3.0, 8.0],
    "status": ["paid", "paid", "refunded", "refunded", "shipped", "paid", "failed", "paid", "PAID", "paid"],
    "currency": ["EUR", "EUR", "USD", "USD", "EUR", "EUR", "EUR", "USD", "EUR", "EUR"],
    "country": ["DE", "FR", "US", "US", "DE", "DE", "FR", "US", "DE", "US"],
    "updated_at": ["2025-03-06 08:00", "2025-03-06 07:30", "2025-03-05 22:00", "2025-03-05 22:00", "2025-03-04 09:00",
                   "2025-03-06 10:15", "2025-03-01 12:00", "2025-03-06 06:45", "2025-03-06 09:30", "2025-03-02 08:00"],
})

required = ["order_id", "customer_id", "amount", "status"]
rates = orders[required].notna().mean().round(2)
print(rates.to_string())
print("rows with a missing required value:", orders["order_id"][orders[required].isna().any(axis=1)].tolist())
```

```output

customer_id    0.8
amount         0.9

```
### Example 2: Validity

Each rule is checked only on non-missing values. A format rule for the order id, a set rule for the status and a range rule for the amount each give a rate and the failing ids. The missing amount of `A7` is not counted here; it was counted by completeness.

```python run
import pandas as pd

orders = pd.DataFrame({
    "order_id": ["A1", "A2", "A3", "A3", "A5", "A6", "A7", "A8", "A9", "A10"],
    "customer_id": [10, 11, None, 12, 13, 14, None, 15, 16, 17],
    "amount": [19.9, 25.0, 12.5, 12.5, -5.0, 40.0, None, 7.5, 3.0, 8.0],
    "status": ["paid", "paid", "refunded", "refunded", "shipped", "paid", "failed", "paid", "PAID", "paid"],
    "currency": ["EUR", "EUR", "USD", "USD", "EUR", "EUR", "EUR", "USD", "EUR", "EUR"],
    "country": ["DE", "FR", "US", "US", "DE", "DE", "FR", "US", "DE", "US"],
    "updated_at": ["2025-03-06 08:00", "2025-03-06 07:30", "2025-03-05 22:00", "2025-03-05 22:00", "2025-03-04 09:00",
                   "2025-03-06 10:15", "2025-03-01 12:00", "2025-03-06 06:45", "2025-03-06 09:30", "2025-03-02 08:00"],
})

checks = {
    "order_id format": (orders["order_id"].str.fullmatch(r"A\d+"), orders["order_id"].notna()),
    "status allowed": (orders["status"].isin({"paid", "refunded", "failed"}), orders["status"].notna()),
    "amount >= 0": (orders["amount"] >= 0, orders["amount"].notna()),
}
for name, (ok, present) in checks.items():
    rate = ok[present].mean()
    print(f"{name}: {rate:.0%} valid, failing {orders['order_id'][present & ~ok].tolist()}")
```

```output
order_id format: 100% valid, failing []
status allowed: 80% valid, failing ['A5', 'A9']
amount >= 0: 89% valid, failing ['A5']
```
### Example 3: Uniqueness

The key `order_id` should be unique. The check counts the rows that share a key, the keys that are repeated and the uniqueness rate. Total of `amount` with and without the duplicate shows what it does to a sum.

```python run
import pandas as pd

orders = pd.DataFrame({
    "order_id": ["A1", "A2", "A3", "A3", "A5", "A6", "A7", "A8", "A9", "A10"],
    "customer_id": [10, 11, None, 12, 13, 14, None, 15, 16, 17],
    "amount": [19.9, 25.0, 12.5, 12.5, -5.0, 40.0, None, 7.5, 3.0, 8.0],
    "status": ["paid", "paid", "refunded", "refunded", "shipped", "paid", "failed", "paid", "PAID", "paid"],
    "currency": ["EUR", "EUR", "USD", "USD", "EUR", "EUR", "EUR", "USD", "EUR", "EUR"],
    "country": ["DE", "FR", "US", "US", "DE", "DE", "FR", "US", "DE", "US"],
    "updated_at": ["2025-03-06 08:00", "2025-03-06 07:30", "2025-03-05 22:00", "2025-03-05 22:00", "2025-03-04 09:00",
                   "2025-03-06 10:15", "2025-03-01 12:00", "2025-03-06 06:45", "2025-03-06 09:30", "2025-03-02 08:00"],
})

dupe_rows = orders["order_id"].duplicated(keep=False)
print("rows sharing a key:", int(dupe_rows.sum()), "| repeated keys:", orders.loc[dupe_rows, "order_id"].unique().tolist())
print("uniqueness rate:", round(orders["order_id"].nunique() / len(orders), 2))
print("amount total with duplicates:", orders["amount"].sum(), "| without:", orders.drop_duplicates("order_id")["amount"].sum())
```

```output
rows sharing a key: 2 | repeated keys: ['A3']
uniqueness rate: 0.9
amount total with duplicates: 123.4 | without: 110.9
```
### Example 4: Timeliness

Each row's age is computed against a fixed `now`. The rows older than 48 hours are listed and the rate of recent rows is computed. A real pipeline passes the current time; the fixed value keeps the example reproducible.

```python run
import pandas as pd

orders = pd.DataFrame({
    "order_id": ["A1", "A2", "A3", "A3", "A5", "A6", "A7", "A8", "A9", "A10"],
    "customer_id": [10, 11, None, 12, 13, 14, None, 15, 16, 17],
    "amount": [19.9, 25.0, 12.5, 12.5, -5.0, 40.0, None, 7.5, 3.0, 8.0],
    "status": ["paid", "paid", "refunded", "refunded", "shipped", "paid", "failed", "paid", "PAID", "paid"],
    "currency": ["EUR", "EUR", "USD", "USD", "EUR", "EUR", "EUR", "USD", "EUR", "EUR"],
    "country": ["DE", "FR", "US", "US", "DE", "DE", "FR", "US", "DE", "US"],
    "updated_at": ["2025-03-06 08:00", "2025-03-06 07:30", "2025-03-05 22:00", "2025-03-05 22:00", "2025-03-04 09:00",
                   "2025-03-06 10:15", "2025-03-01 12:00", "2025-03-06 06:45", "2025-03-06 09:30", "2025-03-02 08:00"],
})

now = pd.Timestamp("2025-03-06 12:00")
age_hours = (now - pd.to_datetime(orders["updated_at"])).dt.total_seconds() / 3600
recent = age_hours <= 48
print("recent rate:", round(recent.mean(), 2))
print("older than 48 h:", orders["order_id"][~recent].tolist(), age_hours[~recent].round(0).tolist())
```

```output
recent rate: 0.7
older than 48 h: ['A5', 'A7', 'A10'] [51.0, 120.0, 100.0]
```
### Example 5: Consistency and accuracy

Consistency uses a rule between two columns: the currency expected for each country. Accuracy compares the table with a reference extract from the source and reports the rows that differ.

```python run
import pandas as pd

orders = pd.DataFrame({
    "order_id": ["A1", "A2", "A3", "A3", "A5", "A6", "A7", "A8", "A9", "A10"],
    "customer_id": [10, 11, None, 12, 13, 14, None, 15, 16, 17],
    "amount": [19.9, 25.0, 12.5, 12.5, -5.0, 40.0, None, 7.5, 3.0, 8.0],
    "status": ["paid", "paid", "refunded", "refunded", "shipped", "paid", "failed", "paid", "PAID", "paid"],
    "currency": ["EUR", "EUR", "USD", "USD", "EUR", "EUR", "EUR", "USD", "EUR", "EUR"],
    "country": ["DE", "FR", "US", "US", "DE", "DE", "FR", "US", "DE", "US"],
    "updated_at": ["2025-03-06 08:00", "2025-03-06 07:30", "2025-03-05 22:00", "2025-03-05 22:00", "2025-03-04 09:00",
                   "2025-03-06 10:15", "2025-03-01 12:00", "2025-03-06 06:45", "2025-03-06 09:30", "2025-03-02 08:00"],
})

expected_currency = {"DE": "EUR", "FR": "EUR", "US": "USD"}
consistent = orders["country"].map(expected_currency) == orders["currency"]
print("consistent rate:", round(consistent.mean(), 2), "| inconsistent:", orders["order_id"][~consistent].tolist())

reference = pd.Series({"A1": 19.9, "A2": 52.0, "A3": 12.5, "A5": -5.0, "A6": 40.0, "A8": 7.5, "A9": 3.0, "A10": 8.0})
table = orders.drop_duplicates("order_id").set_index("order_id")["amount"]
checked = table.reindex(reference.index)
accurate = checked == reference
print("accuracy against the source extract:", round(accurate.mean(), 3), "| wrong:", accurate.index[~accurate].tolist(), checked[~accurate].tolist(), "vs", reference[~accurate].tolist())
```

```output
consistent rate: 0.9 | inconsistent: ['A10']
accuracy against the source extract: 0.875 | wrong: ['A2'] [25.0] vs [52.0]
```
### Example 6: A scorecard

One table summarises the dimensions: the checked rows, the failing rows, the rate and the threshold with the result. Thresholds differ by dimension because their cost differs. The table is the thing a run publishes.

```python run
import pandas as pd

orders = pd.DataFrame({
    "order_id": ["A1", "A2", "A3", "A3", "A5", "A6", "A7", "A8", "A9", "A10"],
    "customer_id": [10, 11, None, 12, 13, 14, None, 15, 16, 17],
    "amount": [19.9, 25.0, 12.5, 12.5, -5.0, 40.0, None, 7.5, 3.0, 8.0],
    "status": ["paid", "paid", "refunded", "refunded", "shipped", "paid", "failed", "paid", "PAID", "paid"],
    "currency": ["EUR", "EUR", "USD", "USD", "EUR", "EUR", "EUR", "USD", "EUR", "EUR"],
    "country": ["DE", "FR", "US", "US", "DE", "DE", "FR", "US", "DE", "US"],
    "updated_at": ["2025-03-06 08:00", "2025-03-06 07:30", "2025-03-05 22:00", "2025-03-05 22:00", "2025-03-04 09:00",
                   "2025-03-06 10:15", "2025-03-01 12:00", "2025-03-06 06:45", "2025-03-06 09:30", "2025-03-02 08:00"],
})

now = pd.Timestamp("2025-03-06 12:00")
present = orders["amount"].notna()
rows = [
    ("completeness: customer_id", len(orders), int(orders["customer_id"].isna().sum()), 1.00),
    ("validity: status allowed", int(orders["status"].notna().sum()), int((~orders["status"].isin({"paid", "refunded", "failed"})).sum()), 0.95),
    ("validity: amount >= 0", int(present.sum()), int((orders["amount"][present] < 0).sum()), 0.95),
    ("uniqueness: order_id", len(orders), int(orders["order_id"].duplicated(keep=False).sum()), 1.00),
    ("timeliness: <= 48 h", len(orders), int(((now - pd.to_datetime(orders["updated_at"])).dt.total_seconds() / 3600 > 48).sum()), 0.70),
]
report = pd.DataFrame(rows, columns=["check", "checked", "failing", "threshold"])
report["rate"] = ((report["checked"] - report["failing"]) / report["checked"]).round(2)
report["result"] = report.apply(lambda r: "PASS" if r["rate"] >= r["threshold"] else "FAIL", axis=1)
print(report[["check", "checked", "failing", "rate", "threshold", "result"]].to_string(index=False))
```

```output
                    check  checked  failing  rate  threshold result
completeness: customer_id       10        2  0.80       1.00   FAIL
 validity: status allowed       10        2  0.80       0.95   FAIL
    validity: amount >= 0        9        1  0.89       0.95   FAIL
     uniqueness: order_id       10        2  0.80       1.00   FAIL
      timeliness: <= 48 h       10        3  0.70       0.70   PASS
```
## Real-world applications

- **Run-time quality scorecards.** A pipeline publishes a table like Example 6 after each load, and a failing row blocks the dashboard refresh or opens a ticket.
- **Choosing the fix.** A missing customer id (completeness) is a source fix, `shipped` (validity) a mapping or quarantine rule, `A3` twice (uniqueness) a dedupe step and the currency mismatch (consistency) a cross-field rule.
- **Agreements with data owners.** Thresholds per dimension are what a data producer and consumer agree on, with the measurement that proves it.
- **Prioritising work.** Rates and failing counts show which dimension costs the most reports, so the team fixes that first.

## Daily review

### Key takeaways

- Completeness is present, validity is conforming, uniqueness is once, timeliness is recent, consistency is agreeing with itself, accuracy is matching the truth.
- Each dimension has a rate (good over checked) and a list of failing rows.
- Count missing values only in completeness; check validity on non-missing values.
- Accuracy needs a trusted reference; a clean-looking value can still be wrong.
- Choose thresholds from the cost of failure, per dimension and column, and review them.

### Common mistakes

- Treating the placeholder `N/A` or `-1` as a value, so completeness looks perfect. Normalise placeholders to missing first.
- Counting missing values as invalid too, so one defect is reported twice. Keep the dimensions separate.
- Checking uniqueness on the wrong key (for example `customer_id` in an orders table). Define the key first.
- Using `datetime.now()` inside the check so results change between runs. Pass `now` in.
- Believing valid means correct; a valid `paid` status on an unpaid order is only caught by accuracy.
- Setting every threshold to 100 percent and ignoring the alerts that follow.

### Revision notes

- Completeness `notna().mean()`; validity `isin`, `str.fullmatch`, ranges on non-missing; uniqueness `duplicated(keep=False)`; timeliness age against `now`; consistency cross-field maps; accuracy against a reference.
- Rate = (checked - failing) / checked.
- Thresholds per dimension, from cost.

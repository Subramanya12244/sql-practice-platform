## Objectives

- Design a small sales star schema from a stated grain and write the DDL with primary and foreign keys.
- Load the dimensions and the fact table reproducibly, and reconcile row counts, orphan keys and control totals.
- Answer business questions with star-join queries and package one of them as a reporting view with a window function.
- Document the model: grain, keys, a data dictionary taken from the catalog, and the checks that passed.

## Understand

### What the project builds

Today you build one small, complete warehouse from nothing and prove that it is correct. The project has six steps: design, load, reconcile, query, package, document. It uses the sales star schema that the warehouse days introduced: the fact table `fact_sales(sale_id, date_key, customer_key, product_key, quantity, amount_cents)` and the dimensions `dim_customer(customer_key, customer_id, customer_name, country, valid_from, valid_to, is_current)`, `dim_product(product_key, product_id, product_name, category)` and `dim_date(date_key, full_date, year, month)`. The data is small and synthetic: 12 customers, 8 products, 90 calendar days and 60 sales. Because the data is generated by `generate_series` arithmetic, every learner gets the same rows and every number in this lesson can be reproduced.

### Step 1: design starts with the grain

The **grain** is the sentence that says what one fact row means. Here it is one row per order line. Everything else follows from it: `quantity` and `amount_cents` are measures of a single line, `sale_id` identifies the line, and every foreign key points at the dimension row that describes that line. Write the grain down before the DDL. If you cannot state it in one sentence, the table will mix levels, and totals will double count. The dimensions use **surrogate keys** (`customer_key`, `product_key`, `date_key`): integers owned by the warehouse that stay stable when the source changes a business id. The business id (`customer_id`, `product_id`) is kept as an ordinary column for lookup. `dim_customer` carries `valid_from`, `valid_to` and `is_current` so that a changed customer could later be stored as a new row (slowly changing dimension, type 2); in this small data every customer has one current row.

### Steps 2 and 3: load, then reconcile

Load dimensions before the fact table because the fact table's foreign keys refer to them. After the load you reconcile, which means comparing what arrived with what you expected. Three families of check cover most failures. Counts: the number of rows in each table, and whether each key is unique. Referential integrity: a fact row whose dimension key matches nothing is an orphan, found with a `LEFT JOIN` and `WHERE dim.key IS NULL`. Control totals: a sum that you can compare with the source, here the total of `amount_cents`. A common misconception is that a successful `INSERT` proves a correct load. It proves only that the database accepted the rows; a join that duplicates or drops rows is found only by the checks.

### Steps 4 to 6: query, package, document

A **star join** begins at the fact table and joins each needed dimension on its key; then `GROUP BY` uses dimension attributes. The symptom of a wrong join is a total that no longer matches the control total, so you re-run the reconciliation total through every new query. A **view** gives a query a name so that everyone uses the same definition. Documentation is part of the product: the README states the grain, the key rules, the checks that passed with their results, and known limits (for example, no customer history exists in this data). Work in order and do not skip the check after each step; a project that is only queried and never reconciled is a demo.

### Why it matters

Warehouse work is trusted only when someone can show that the numbers tie out. Source-to-target reconciliation, grain statements and data dictionaries are the daily habits of an engineer who owns a warehouse, and the capstone later in the programme asks for the same evidence.

## Syntax and key functions

The project uses these SQL forms:

```sql-syntax
CREATE TABLE fact_x (id integer PRIMARY KEY, dim_key integer NOT NULL REFERENCES dim_x);
INSERT INTO target SELECT ... FROM generate_series(1, 60) AS g(i);
SELECT ... FROM fact f JOIN dim d ON d.key = f.key GROUP BY d.attribute;
CREATE VIEW name AS SELECT ...;
```

`REFERENCES dim_x` declares a foreign key to the primary key of `dim_x`. `INSERT ... SELECT` loads rows from a query, and `generate_series` produces the numbers or dates the query uses.

| Function or clause | What it gives you |
|---|---|
| `generate_series(a, b)` | One row per integer from `a` to `b`, or per date step when given dates and an interval. |
| `LEFT JOIN ... WHERE key IS NULL` | The rows with no match: the orphan check. |
| `count(DISTINCT col)` | The number of distinct values; equal to `count(*)` when the column is unique. |
| `to_char(date, 'YYYYMMDD')::integer` | The integer date key. |
| `rank() OVER (PARTITION BY ... ORDER BY ...)` | The rank inside each partition, with ties sharing a rank. |
| `information_schema.columns` | Column names and types for the data dictionary. |

## Learn by example

### Example 1: Design and load, then check the grain

Step 1 and step 2 of the project. The block below creates the three dimensions and the fact table with primary keys and foreign keys, then loads them with `INSERT ... SELECT` over `generate_series` so that the data is reproducible and small: 90 days, 12 customers, 8 products, 60 sales. Each block in this lesson repeats the same set-up because every example runs on its own empty database. The final query is the first check of the grain: how many rows each table holds, and whether `sale_id` really identifies one row.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
INSERT INTO dim_date
SELECT to_char(d, 'YYYYMMDD')::integer, d::date, EXTRACT(year FROM d)::integer, EXTRACT(month FROM d)::integer
FROM generate_series(date '2025-01-01', date '2025-03-31', interval '1 day') AS g(d);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL, valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
INSERT INTO dim_customer
SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || i, (ARRAY['DE', 'FR', 'UK', 'US'])[1 + i % 4], date '2024-01-01', NULL, true
FROM generate_series(1, 12) AS g(i);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
INSERT INTO dim_product VALUES
(1, 'P01', 'Notebook', 'Paper'), (2, 'P02', 'Pen', 'Paper'), (3, 'P03', 'Stapler', 'Office'), (4, 'P04', 'Desk Lamp', 'Office'),
(5, 'P05', 'Mouse', 'Tech'), (6, 'P06', 'Keyboard', 'Tech'), (7, 'P07', 'Monitor', 'Tech'), (8, 'P08', 'Headset', 'Tech');
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer, product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO fact_sales
SELECT i, to_char(date '2025-01-01' + (i * 3) % 90, 'YYYYMMDD')::integer, 1 + (i * 5) % 12, 1 + (i * 7) % 8, 1 + i % 4, (1 + i % 4) * (500 + 250 * ((i * 7) % 8))
FROM generate_series(1, 60) AS g(i);

SELECT 'fact_sales' AS table_name, count(*) AS row_count, count(DISTINCT sale_id) AS distinct_keys FROM fact_sales
UNION ALL SELECT 'dim_customer', count(*), count(DISTINCT customer_key) FROM dim_customer
UNION ALL SELECT 'dim_product', count(*), count(DISTINCT product_key) FROM dim_product
UNION ALL SELECT 'dim_date', count(*), count(DISTINCT date_key) FROM dim_date
ORDER BY table_name;
```

```output
table_name | row_count | distinct_keys
dim_customer | 12 | 12
dim_date | 90 | 90
dim_product | 8 | 8
fact_sales | 60 | 60
```

Every table has as many distinct keys as rows, so each key is unique. The fact table holds 60 rows, one per order line, which is the grain. Only 30 of the 90 dates have sales, which is normal: a date dimension lists every day, and a fact table lists only the days when something happened.
### Example 2: Reconcile the load

Step 3: prove the load is complete and consistent before anyone queries it. Three checks run in one query: the foreign keys all find a parent (the `REFERENCES` clauses already enforce this, but the check also works on a warehouse without constraints), the stored amount equals the quantity multiplied by the unit price implied by the product, and the total matches the control total that the source system would report.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
INSERT INTO dim_date
SELECT to_char(d, 'YYYYMMDD')::integer, d::date, EXTRACT(year FROM d)::integer, EXTRACT(month FROM d)::integer
FROM generate_series(date '2025-01-01', date '2025-03-31', interval '1 day') AS g(d);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL, valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
INSERT INTO dim_customer
SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || i, (ARRAY['DE', 'FR', 'UK', 'US'])[1 + i % 4], date '2024-01-01', NULL, true
FROM generate_series(1, 12) AS g(i);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
INSERT INTO dim_product VALUES
(1, 'P01', 'Notebook', 'Paper'), (2, 'P02', 'Pen', 'Paper'), (3, 'P03', 'Stapler', 'Office'), (4, 'P04', 'Desk Lamp', 'Office'),
(5, 'P05', 'Mouse', 'Tech'), (6, 'P06', 'Keyboard', 'Tech'), (7, 'P07', 'Monitor', 'Tech'), (8, 'P08', 'Headset', 'Tech');
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer, product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO fact_sales
SELECT i, to_char(date '2025-01-01' + (i * 3) % 90, 'YYYYMMDD')::integer, 1 + (i * 5) % 12, 1 + (i * 7) % 8, 1 + i % 4, (1 + i % 4) * (500 + 250 * ((i * 7) % 8))
FROM generate_series(1, 60) AS g(i);

SELECT
  (SELECT count(*) FROM fact_sales f LEFT JOIN dim_customer c ON c.customer_key = f.customer_key WHERE c.customer_key IS NULL) AS orphan_customers,
  (SELECT count(*) FROM fact_sales f LEFT JOIN dim_product p ON p.product_key = f.product_key WHERE p.product_key IS NULL) AS orphan_products,
  (SELECT count(*) FROM fact_sales f LEFT JOIN dim_date d ON d.date_key = f.date_key WHERE d.date_key IS NULL) AS orphan_dates,
  (SELECT count(*) FROM fact_sales WHERE amount_cents <> quantity * (500 + 250 * (product_key - 1))) AS bad_amounts,
  (SELECT sum(amount_cents) FROM fact_sales) AS total_cents,
  (SELECT sum(quantity) FROM fact_sales) AS total_units;
```

```output
orphan_customers | orphan_products | orphan_dates | bad_amounts | total_cents | total_units
0 | 0 | 0 | 0 | 215000 | 150
```

Zero orphans and zero bad amounts mean the load is internally consistent. The totals 215000 cents (2,150.00 in currency units) and 150 units are the control figures that the final report must reproduce. If a later query shows a different total, the query joins wrongly or filters rows: the reconciliation gives a fixed point to compare with.
### Example 3: The star join: revenue by category and month

Step 4: query. A star join starts at the fact table and joins each dimension on its surrogate key, then groups by dimension attributes. Revenue is stored in cents, so the query divides by 100.0 for readable output. The three joins do not change the row count of the fact table because each key matches exactly one dimension row.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
INSERT INTO dim_date
SELECT to_char(d, 'YYYYMMDD')::integer, d::date, EXTRACT(year FROM d)::integer, EXTRACT(month FROM d)::integer
FROM generate_series(date '2025-01-01', date '2025-03-31', interval '1 day') AS g(d);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL, valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
INSERT INTO dim_customer
SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || i, (ARRAY['DE', 'FR', 'UK', 'US'])[1 + i % 4], date '2024-01-01', NULL, true
FROM generate_series(1, 12) AS g(i);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
INSERT INTO dim_product VALUES
(1, 'P01', 'Notebook', 'Paper'), (2, 'P02', 'Pen', 'Paper'), (3, 'P03', 'Stapler', 'Office'), (4, 'P04', 'Desk Lamp', 'Office'),
(5, 'P05', 'Mouse', 'Tech'), (6, 'P06', 'Keyboard', 'Tech'), (7, 'P07', 'Monitor', 'Tech'), (8, 'P08', 'Headset', 'Tech');
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer, product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO fact_sales
SELECT i, to_char(date '2025-01-01' + (i * 3) % 90, 'YYYYMMDD')::integer, 1 + (i * 5) % 12, 1 + (i * 7) % 8, 1 + i % 4, (1 + i % 4) * (500 + 250 * ((i * 7) % 8))
FROM generate_series(1, 60) AS g(i);

SELECT d.month, p.category, count(*) AS lines, sum(f.quantity) AS units, round(sum(f.amount_cents) / 100.0, 2) AS revenue
FROM fact_sales f
JOIN dim_date d ON d.date_key = f.date_key
JOIN dim_product p ON p.product_key = f.product_key
JOIN dim_customer c ON c.customer_key = f.customer_key
GROUP BY d.month, p.category
ORDER BY d.month, p.category
LIMIT 10;
```

```output
month | category | lines | units | revenue
1 | Office | 5 | 13 | 140.00
1 | Paper | 6 | 15 | 105.00
1 | Tech | 11 | 26 | 500.00
2 | Office | 4 | 10 | 110.00
2 | Paper | 4 | 10 | 70.00
2 | Tech | 10 | 26 | 495.00
3 | Office | 5 | 12 | 135.00
3 | Paper | 4 | 10 | 70.00
3 | Tech | 11 | 28 | 525.00
```

Three months and three categories give nine rows, so the `LIMIT 10` cuts nothing. The customer join is not needed by this particular query, but it must not change any count: adding it and seeing the same figures is a quick proof that the dimension has one row per key.
### Example 4: A reporting view with a window function

Step 5: package the question so that others can reuse it. A view stores the star join under a name; the final query ranks categories inside each month with `rank() OVER (PARTITION BY month ORDER BY revenue DESC)`, the window idea from the earlier warehouse days. Anyone who queries `v_monthly_category` gets the same definition of revenue.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
INSERT INTO dim_date
SELECT to_char(d, 'YYYYMMDD')::integer, d::date, EXTRACT(year FROM d)::integer, EXTRACT(month FROM d)::integer
FROM generate_series(date '2025-01-01', date '2025-03-31', interval '1 day') AS g(d);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL, valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
INSERT INTO dim_customer
SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || i, (ARRAY['DE', 'FR', 'UK', 'US'])[1 + i % 4], date '2024-01-01', NULL, true
FROM generate_series(1, 12) AS g(i);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
INSERT INTO dim_product VALUES
(1, 'P01', 'Notebook', 'Paper'), (2, 'P02', 'Pen', 'Paper'), (3, 'P03', 'Stapler', 'Office'), (4, 'P04', 'Desk Lamp', 'Office'),
(5, 'P05', 'Mouse', 'Tech'), (6, 'P06', 'Keyboard', 'Tech'), (7, 'P07', 'Monitor', 'Tech'), (8, 'P08', 'Headset', 'Tech');
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer, product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO fact_sales
SELECT i, to_char(date '2025-01-01' + (i * 3) % 90, 'YYYYMMDD')::integer, 1 + (i * 5) % 12, 1 + (i * 7) % 8, 1 + i % 4, (1 + i % 4) * (500 + 250 * ((i * 7) % 8))
FROM generate_series(1, 60) AS g(i);

CREATE VIEW v_monthly_category AS
SELECT d.month, p.category, sum(f.amount_cents) AS revenue_cents
FROM fact_sales f
JOIN dim_date d ON d.date_key = f.date_key
JOIN dim_product p ON p.product_key = f.product_key
GROUP BY d.month, p.category;

SELECT month, category, revenue_cents, rank() OVER (PARTITION BY month ORDER BY revenue_cents DESC) AS rank_in_month
FROM v_monthly_category
ORDER BY month, rank_in_month, category
LIMIT 8;
```

```output
month | category | revenue_cents | rank_in_month
1 | Tech | 50000 | 1
1 | Office | 14000 | 2
1 | Paper | 10500 | 3
2 | Tech | 49500 | 1
2 | Office | 11000 | 2
2 | Paper | 7000 | 3
3 | Tech | 52500 | 1
3 | Office | 13500 | 2
```

The `LIMIT 8` shows the first eight of nine rows, in month order. The view holds no data of its own: it runs the join each time. Ranking inside a partition restarts at 1 for every month.

## Real-world applications

- A retailer's data team loads daily order lines into a star schema and runs the same orphan and control-total checks after every load, the reconciliation in Example 2, before dashboards refresh.
- An analytics engineer exposes `v_monthly_category`-style views so that finance and marketing use one definition of revenue (Example 4) instead of copying a query.

## Daily review

### Key takeaways

- State the grain first; every column and key must agree with it.
- Load dimensions before facts, then reconcile counts, orphans and control totals.
- A star join starts at the fact table and joins dimensions on surrogate keys; the total must still match the control total.
- Views share one definition; the catalog supplies the data dictionary.

### Common mistakes

- Trusting the load because the `INSERT` succeeded. Symptom: totals that differ from the source. Fix: run the reconciliation after every load.
- Joining on the business id in one query and the surrogate key in another. Symptom: counts that multiply. Fix: join facts to dimensions on the surrogate key only.
- Writing the README before checking. Symptom: documented checks that were never run. Fix: paste the real results of the checks into the README.

### Revision notes

- Grain: one row per order line. Measures: `quantity`, `amount_cents`.
- Control figures from the project data: 60 sales, 215000 cents, 150 units.
- Orphan check: `LEFT JOIN` then `IS NULL`.

## Objectives

- Describe an expected schema as data (column, type, nullable) and check a DataFrame against it, reporting every problem.
- Write a data contract: schema, rules, owner and freshness, with a version number.
- Classify a contract change as compatible (minor) or breaking (major) and say why.
- Detect drift between a new delivery and the last accepted schema, and validate records with hand-written code and with pydantic.

## Understand

### Structure fails before values do

Day 133 checked the values in the columns. Before any of that can run, the columns must exist and have the right type. A source team renames `amount` to `total`, a CSV export starts to include the text `pending` in a numeric column, an API adds a field, and the pipeline either fails with an obscure `KeyError` ten steps later or, worse, loads the wrong thing without complaint. A **schema** is the declared structure of a dataset: its columns, their types and whether each may be empty. A **schema check** compares a delivery with that declaration at the very start of a run and fails fast with a message that names every difference.

### A schema as data

Just as rules were data on Day 133, a schema is best written as data: a dictionary with one entry per column holding the expected kind (`int`, `float`, `string`, `datetime`) and `nullable`. The check function then loops over the entries and reports problems: **missing columns**, columns of the **wrong type**, **nulls** in a non-nullable column and, optionally, **unexpected columns**. Checking the kind with `pd.api.types.is_integer_dtype` and its relatives, not with the text of the dtype name, keeps the check independent of how wide the integer is on a platform. One subtle point: pandas stores an integer column that contains a missing value as floats, so a nullable integer column arrives as `float64` unless it was read as the nullable `Int64`; the check above accepts a float column for an `int` kind when every non-missing value is a whole number, and says so in a comment in real code.

### Data contracts

A **data contract** is an agreement between the team that produces a dataset and the teams that consume it. It states more than the schema: the **columns and types**, the **rules** that values obey (allowed statuses, an amount that is never negative), the **freshness** the producer promises (updated daily by 06:00 UTC), the **owner** to contact and a **version**. A contract is written down in a file kept in version control, so a change to it is a visible, reviewable event, and a pipeline can load it and validate every delivery against it. The contract turns surprises into conversations: the producer cannot silently rename a column, because the consumer's check fails and the contract says whose job it is to fix.

### Versioning

Contracts change. **Semantic versioning** classifies the change by its effect on consumers with a number `major.minor`. A **compatible** change keeps every existing consumer working: adding an optional column, adding an allowed value to a set that consumers ignore if unknown, widening a range. It raises the **minor** version (`1.2` to `1.3`). A **breaking** change can break a consumer: removing or renaming a column, changing a type, making a nullable column required, removing an allowed value that consumers read. It raises the **major** version (`1.3` to `2.0`) and needs a migration period in which both versions are delivered. The rule of thumb: if a query written against the old version could fail or change its answer, the change is breaking. A function can classify a change automatically by comparing the two contracts' columns.

### Drift detection

**Drift** is a difference between what arrives and what was agreed or last seen. **Schema drift** is a changed structure: new, missing or retyped columns. **Value drift** is a changed content with the same structure: a new status value, an amount distribution that shifts tenfold. Drift detection compares each delivery with the last accepted **snapshot** (the previous schema, plus summaries like the set of seen statuses) and reports what changed. Some drift is harmless (a new optional column) and some is an incident; the contract decides which. A frequent real case is a numeric column that turns into text because a single bad value appeared: `read_csv` then returns a column of type `object`, which a type check catches immediately.

### Validating records with a model

For records that arrive as dictionaries (JSON from an API) you can validate each one against a typed **model**. By hand this is a function that checks each field and returns the errors. The third-party library **pydantic** lets you declare the model as a class (`order_id: int`, `amount_cents: int = Field(ge=0)`, `status: Literal["paid", "refunded", "failed"]`) and does the checking and conversion (in its default mode the text `"2"` is converted to the integer 2) and returns each error with the field's location and an error type such as `missing`, `int_parsing` or `literal_error`. It is not available in the browser Python used for the graded exercises, so the graded versions use the standard library; the pydantic example runs on your own computer.

### Why it matters in data work

Contracts and schema checks move failures to the edge of the pipeline, where the cause is obvious and the owner is known, instead of the end, where a dashboard silently shows wrong numbers.

```python
from pydantic import BaseModel, Field, ValidationError
from typing import Literal, Optional

class Order(BaseModel):

    customer_id: Optional[int] = None

```

| Item | What it does or returns |
|---|---|
| schema | Column name to expected kind and nullability. |
| `pd.api.types.is_integer_dtype(s)` | True when the Series holds integers (any width). |
| `df.columns` | The column names of the delivery. |
| contract | Schema, value rules, freshness, owner and version, stored in a file. |
| major / minor | Breaking change raises major; compatible change raises minor. |
| drift report | Added, removed and retyped columns against the last snapshot. |
| `Model.model_validate(dict)` | pydantic: converts and validates one record, or raises `ValidationError`. |
| `e.errors()` | List of dicts with `loc` (field) and `type` (error kind) per problem. |

## Learn by example

### Example 1: A schema check

The schema is a dictionary and `check_schema` returns all problems in one list: a missing column, a column of the wrong type, nulls in a non-nullable column and an unexpected column. A good delivery returns an empty list.

```python run
import pandas as pd

KINDS = {
    "int": lambda s: pd.api.types.is_integer_dtype(s) or (pd.api.types.is_float_dtype(s) and bool((s.dropna() % 1 == 0).all())),
    "float": lambda s: pd.api.types.is_float_dtype(s) or pd.api.types.is_integer_dtype(s),
    "string": lambda s: pd.api.types.is_object_dtype(s) or pd.api.types.is_string_dtype(s),
    "datetime": pd.api.types.is_datetime64_any_dtype,
}

SCHEMA = {
    "order_id": {"kind": "int", "nullable": False},
    "customer_id": {"kind": "int", "nullable": True},
    "amount": {"kind": "float", "nullable": False},
    "status": {"kind": "string", "nullable": False},
}

def check_schema(df, schema, allow_extra=False):
    problems = []
    for name, spec in schema.items():
        if name not in df.columns:
            problems.append(f"missing column {name}")
            continue
        series = df[name]
        if not KINDS[spec["kind"]](series):
            problems.append(f"{name}: expected {spec['kind']}")
        if not spec["nullable"] and series.isna().any():
            problems.append(f"{name}: {int(series.isna().sum())} null(s) in a non-nullable column")
    if not allow_extra:
        problems.extend(f"unexpected column {c}" for c in df.columns if c not in schema)
    return problems

good = pd.DataFrame({"order_id": [1, 2], "customer_id": [10.0, None], "amount": [19.9, 25.0], "status": ["paid", "failed"]})
bad = pd.DataFrame({"order_id": [1, 2], "amount": ["19.9", "n/a"], "status": ["paid", None], "coupon": ["x", "y"]})
print(check_schema(good, SCHEMA))
for problem in check_schema(bad, SCHEMA):
    print(problem)
```

```output
[]
missing column customer_id
amount: expected float
status: 1 null(s) in a non-nullable column
unexpected column coupon
```
### Example 2: Drift from a CSV delivery

A single text value in a numeric column turns the whole column into `object`. The delivery is read with `read_csv` and compared with the schema; the drift appears as a type problem before any value check runs.

```python run
import io
import pandas as pd

KINDS = {
    "int": lambda s: pd.api.types.is_integer_dtype(s) or (pd.api.types.is_float_dtype(s) and bool((s.dropna() % 1 == 0).all())),
    "float": lambda s: pd.api.types.is_float_dtype(s) or pd.api.types.is_integer_dtype(s),
    "string": lambda s: pd.api.types.is_object_dtype(s) or pd.api.types.is_string_dtype(s),
    "datetime": pd.api.types.is_datetime64_any_dtype,
}

SCHEMA = {
    "order_id": {"kind": "int", "nullable": False},
    "customer_id": {"kind": "int", "nullable": True},
    "amount": {"kind": "float", "nullable": False},
    "status": {"kind": "string", "nullable": False},
}

def check_schema(df, schema, allow_extra=False):
    problems = []
    for name, spec in schema.items():
        if name not in df.columns:
            problems.append(f"missing column {name}")
            continue
        series = df[name]
        if not KINDS[spec["kind"]](series):
            problems.append(f"{name}: expected {spec['kind']}")
        if not spec["nullable"] and series.isna().any():
            problems.append(f"{name}: {int(series.isna().sum())} null(s) in a non-nullable column")
    if not allow_extra:
        problems.extend(f"unexpected column {c}" for c in df.columns if c not in schema)
    return problems

monday = "order_id,customer_id,amount,status\n1,10,19.90,paid\n2,11,25.00,failed\n"
tuesday = "order_id,customer_id,amount,status\n3,12,pending,paid\n4,13,8.00,paid\n"
for day, text in [("monday", monday), ("tuesday", tuesday)]:
    df = pd.read_csv(io.StringIO(text))
    print(day, check_schema(df, SCHEMA) or "matches the schema")
```

### Example 4: Classify a contract change

`classify` compares two contracts' columns and returns the new version number: a removed or retyped column or a column that becomes required is breaking (major), an added nullable column is compatible (minor), and no difference leaves the version alone.

```python run
def classify(old, new):
    major, minor = (int(x) for x in old["version"].split("."))
    breaking, compatible = [], []
    for name, spec in old["columns"].items():
        if name not in new["columns"]:
            breaking.append(f"removed {name}")
        else:
            n = new["columns"][name]
            if n["kind"] != spec["kind"]:
                breaking.append(f"retyped {name}")
            if spec["nullable"] and not n["nullable"]:
                breaking.append(f"{name} now required")
    for name, spec in new["columns"].items():
        if name not in old["columns"]:
            (compatible if spec["nullable"] else breaking).append(f"added {name}")
    if breaking:
        return f"{major + 1}.0", breaking
    if compatible:
        return f"{major}.{minor + 1}", compatible
    return old["version"], []

old = {"version": "1.2", "columns": {"order_id": {"kind": "int", "nullable": False}, "note": {"kind": "string", "nullable": True}}}
add_optional = {"columns": {**old["columns"], "channel": {"kind": "string", "nullable": True}}}
rename = {"columns": {"order_id": {"kind": "int", "nullable": False}, "memo": {"kind": "string", "nullable": True}}}
print(classify(old, add_optional))
print(classify(old, rename))
print(classify(old, old))
```

```output
('1.3', ['added channel'])
('2.0', ['removed note'])
('1.2', [])
```
### Example 5: Hand-written record validation

A record from an API is a dictionary. The function checks each field and returns `(field, error type)` pairs, using the same error names as pydantic so that the two can be compared. It converts numeric text the way pydantic does in its default mode.

```python run
ALLOWED_STATUS = {"paid", "refunded", "failed"}
ALLOWED_CURRENCY = {"EUR", "USD"}

def validate_order(rec):
    errors = []
    def as_int(name, required=True):
        if name not in rec:
            if required:
                errors.append((name, "missing"))
            return None
        try:
            return int(rec[name])
        except (TypeError, ValueError):
            errors.append((name, "int_parsing"))
    as_int("order_id")
    cents = as_int("amount_cents")
    if cents is not None and cents < 0:
        errors.append(("amount_cents", "greater_than_equal"))
    if rec.get("currency") not in ALLOWED_CURRENCY:
        errors.append(("currency", "literal_error"))
    if rec.get("status") not in ALLOWED_STATUS:
        errors.append(("status", "literal_error"))
    return errors

records = [
    {"order_id": 1, "customer_id": 10, "amount_cents": 1990, "currency": "EUR", "status": "paid"},
    {"order_id": "2", "amount_cents": "250", "currency": "EUR", "status": "paid"},
    {"order_id": 3, "amount_cents": -5, "currency": "GBP", "status": "shipped"},
    {"order_id": "x", "amount_cents": 10, "currency": "USD", "status": "paid"},
    {"order_id": 5, "currency": "USD", "status": "paid"},
]
for rec in records:
    print(validate_order(rec) or "ok")
```

```output
ok
ok
[('amount_cents', 'greater_than_equal'), ('currency', 'literal_error'), ('status', 'literal_error')]
[('order_id', 'int_parsing')]
[('amount_cents', 'missing')]
```
### Example 6: The same checks with pydantic

This example uses the third-party library pydantic, so it is a `python local` example. The model declares the types and rules; the printed `(field, error type)` pairs are the same as the hand-written version printed. An `extra="forbid"` setting turns an unexpected field into an error, which is schema drift at record level.

```python local
from typing import Literal, Optional
from pydantic import BaseModel, Field, ValidationError

class Order(BaseModel):
    order_id: int
    customer_id: Optional[int] = None
    amount_cents: int = Field(ge=0)
    currency: Literal["EUR", "USD"]
    status: Literal["paid", "refunded", "failed"]

records = [
    {"order_id": 1, "customer_id": 10, "amount_cents": 1990, "currency": "EUR", "status": "paid"},
    {"order_id": "2", "amount_cents": "250", "currency": "EUR", "status": "paid"},
    {"order_id": 3, "amount_cents": -5, "currency": "GBP", "status": "shipped"},
    {"order_id": "x", "amount_cents": 10, "currency": "USD", "status": "paid"},
    {"order_id": 5, "currency": "USD", "status": "paid"},
]
for rec in records:
    try:
        Order.model_validate(rec)
        print("ok")
    except ValidationError as exc:
        print([(e["loc"][0], e["type"]) for e in exc.errors()])

class StrictOrder(Order):
    model_config = {"extra": "forbid"}

try:
    StrictOrder.model_validate({**records[0], "coupon": "X"})
except ValidationError as exc:
    print([(e["loc"][0], e["type"]) for e in exc.errors()])
```

```output
ok
ok
[('amount_cents', 'greater_than_equal'), ('currency', 'literal_error'), ('status', 'literal_error')]
[('order_id', 'int_parsing')]
[('amount_cents', 'missing')]
[('coupon', 'extra_forbidden')]
```
## Real-world applications

- **Fail at the edge.** A schema check at the start of the run (Examples 1 and 2) turns a renamed column into a one-line message that names the column and the delivery.
- **Producer and consumer agreements.** A versioned contract file (Examples 3 and 4) tells a source team which changes need notice, and lets a consumer pin the major version it supports.
- **API ingestion.** Validating each JSON record (Examples 5 and 6) separates records that match from records to quarantine, with the field and error kind for each rejection.
- **Change review.** Running `classify` in a pull request that edits a contract file shows whether the change is breaking before it merges.

## Daily review

### Key takeaways

- A schema declares columns, kinds and nullability; check it first and report every problem together.
- A contract adds value rules, freshness, owner and version, and lives in version control.
- Compatible changes raise the minor version; breaking changes (remove, rename, retype, make required) raise the major version.
- Drift is a difference from the last accepted snapshot: schema drift and value drift.
- Validate records with a function or a model; pydantic gives field locations and error types and coerces by default.

### Common mistakes

- Checking dtype names as text (`"int64"`), which breaks across platforms. Use `pd.api.types` predicates.
- Forgetting that an integer column with missing values arrives as floats, and either rejecting good data or accepting wrong data. Decide the accepted kinds and nullability explicitly.
- Treating a rename as compatible: to a consumer it is a removed column plus a new one, which is breaking.
- Keeping the contract only in a wiki, so the pipeline never checks it. Store it as a file the code loads.
- Assuming pydantic only checks: in its default mode it converts `"2"` to `2`; use strict settings when conversion is not wanted.
- Letting new unexpected columns flow into the target silently, so downstream code sees them later. Decide to reject, warn or drop.

### Revision notes

- Schema = `{column: {kind, nullable}}`; check = missing, wrong kind, nulls, extra.
- Contract = schema + rules + freshness + owner + version.
- Breaking: remove, rename, retype, required. Compatible: add optional column.
- `read_csv` turns a numeric column with text into `object`.

## Understand

### The problem Airflow solves

A real pipeline has several steps that depend on each other: extract the orders, transform them, load the warehouse, then build a report. Run from cron (Day 153), the steps are one script or several cron lines whose timing you guess. If extract takes longer than expected the load starts on half a file, and when a step fails nobody is told which later steps were skipped. **Apache Airflow** is a workflow orchestrator: you describe the steps and their dependencies in Python, and Airflow decides what can run, runs it, records the outcome of every step and shows it in a web interface. It does not move data itself; it starts the programs, SQL and scripts that do.

### DAG, task, task instance, DAG run

A **DAG** (directed acyclic graph) is the description of a workflow. The graph has **nodes**, which are tasks, and **directed edges**, which are dependencies with a direction ("extract before transform"). **Acyclic** means you can never follow the arrows and return to where you started. A cycle would mean A waits for B and B waits for A, so nothing could ever start; Airflow refuses to load a DAG with a cycle. A **task** is one unit of work in the DAG, for example "run this SQL file", identified by a `task_id` that is unique inside the DAG. A **DAG run** is one execution of the whole DAG for one point in time, and a **task instance** is one task inside one DAG run. This distinction explains most of the web interface: the DAG and its tasks are the plan, which does not change between runs, and the DAG runs and task instances are the history, each with a **state** such as `scheduled`, `queued`, `running`, `success`, `failed` or `upstream_failed`. The last means "I did not run because something before me failed", which is different from failing yourself.

### Order and parallelism

The dependencies fix a partial order. A **topological order** is any list of the tasks in which every task comes after all tasks it depends on. Many tasks have no dependency between them (in the example below, `load` and `validate` both need only `transform`), so they may run in parallel; the order among them is not part of the plan. Airflow therefore runs a task as soon as all its upstream tasks have succeeded, not at a fixed time. The model later in this lesson groups the tasks into levels: all tasks in a level are ready at the same moment.

### The components

The **scheduler** is the process that reads the DAG files, creates DAG runs when their time has come, decides which task instances are ready and hands them on. The **executor** is the part of the scheduler configuration that decides how tasks are run (in local processes, on a pool of workers, on a Kubernetes cluster); the **workers** are the processes that actually execute task code. The **web server** shows the DAGs, runs and logs. All components share one **metadata database**, a normal relational database in which Airflow stores DAG runs, task instances, states, connections and variables. Nothing is kept in the memory of a process: if the scheduler restarts it reads the states back from the database and continues. SQLite is acceptable only for learning on one machine, and production installations use PostgreSQL or MySQL. In Airflow 3 the web interface is served by an API server and DAG files are parsed by a separate DAG processor; the roles in this lesson stay the same, so check the documentation of the version you install.

### What runs when

The scheduler parses every DAG file again and again, again and again on a short interval. The code at the top level of the file therefore runs on every parse, not only when a task runs. The common misconception is that a call at the top of the DAG file, such as a database query or an API request, runs once; it runs on every parse, loads the database and slows the whole scheduler. Put the work inside the task functions, which run only when the task instance runs, and keep the top level to cheap definitions. Example 4 counts the executions with a model.

### Why it matters

Orchestration gives a pipeline a map, a history and a way to rerun only what failed. The ideas of this lesson (graph, order, state, where code runs) are also the ideas behind dbt, Spark job graphs and CI pipelines.

## Syntax and key functions

An Airflow 2.x DAG file looks like this (shown, not run: Airflow is not installed here; a Python model of the same graph is run in the examples):

```python
from datetime import datetime
from airflow import DAG
from airflow.operators.bash import BashOperator

with DAG(dag_id="orders_etl", start_date=datetime(2025, 1, 1), schedule="@daily", catchup=False) as dag:
    extract = BashOperator(task_id="extract", bash_command="echo extract")
    transform = BashOperator(task_id="transform", bash_command="echo transform")
    load = BashOperator(task_id="load", bash_command="echo load")
    extract >> transform >> load
```

`with DAG(...) as dag:` creates the DAG; the `dag_id` is its unique name. `start_date`, `schedule` and `catchup` control when runs are created and are the topic of the next day. Each `BashOperator` is a task: `task_id` names it and `bash_command` is the shell command it runs. `extract >> transform >> load` declares that `transform` runs after `extract` and `load` after `transform`. In Airflow 3 the DAG class and decorators are imported from `airflow.sdk`, and the standard operators from the `airflow.providers.standard` package; check the documentation of your version for the exact import paths.

| Term | Model in this lesson |
|---|---|
| DAG | `Dag(dag_id)` with `tasks` and `upstream` dictionaries |
| Dependency `a >> b` | `dag.link("a", "b")` |
| Topological order | `dag.order()`, tasks sorted by name inside a level |
| Cycle check | `ValueError("cycle detected")` |
| Task instance and state | A row in a `task_instance` table of a SQLite database, standing in for the metadata database |

## Learn by example

### Example 1: A DAG, its levels and a cycle

The model stores each task and the set of tasks it depends on. `levels()` repeatedly picks the tasks whose upstream tasks are all done; if none are ready while tasks remain, there is a cycle.

```python run
import sqlite3


class Dag:
    def __init__(self, dag_id):
        self.dag_id = dag_id
        self.tasks = {}
        self.upstream = {}

    def add_task(self, task_id, func=None):
        if task_id in self.tasks:
            raise ValueError(f"duplicate task_id {task_id}")
        self.tasks[task_id] = func or (lambda: None)
        self.upstream[task_id] = set()

    def link(self, upstream_id, downstream_id):
        self.upstream[downstream_id].add(upstream_id)

    def levels(self):
        remaining = {t: set(u) for t, u in self.upstream.items()}
        result = []
        while remaining:
            ready = sorted(t for t, u in remaining.items() if not u)
            if not ready:
                raise ValueError("cycle detected")
            result.append(ready)
            for t in ready:
                del remaining[t]
            for u in remaining.values():
                u.difference_update(ready)
        return result

    def order(self):
        return [t for level in self.levels() for t in level]


dag = Dag("orders_etl")
for task_id in ["load", "extract", "transform", "report", "validate"]:
    dag.add_task(task_id)
dag.link("extract", "transform")
dag.link("transform", "validate")
dag.link("transform", "load")
dag.link("validate", "report")
dag.link("load", "report")
print(dag.levels())
print(dag.order())

loop = Dag("loop")
loop.add_task("a")
loop.add_task("b")
loop.link("a", "b")
loop.link("b", "a")
try:
    loop.order()
except ValueError as error:
    print(error)
```

```output
[['extract'], ['transform'], ['load', 'validate'], ['report']]
['extract', 'transform', 'load', 'validate', 'report']
cycle detected
```

The tasks were added in a jumbled order, yet the levels follow the dependencies: `extract`, then `transform`, then `load` and `validate` together (they are independent), then `report`, which needs both. The two-task DAG with `a` before `b` and `b` before `a` has no ready task, so the model reports a cycle, as Airflow does when it loads such a file.

### Example 2: A DAG run and the metadata database

`run_dag` plays the part of the scheduler and a worker. It inserts one row per task instance into a SQLite table (our stand-in for the metadata database), runs the tasks level by level and updates each state. The tasks append their names to a list so the order is visible.

```python run
import sqlite3


class Dag:
    def __init__(self, dag_id):
        self.dag_id = dag_id
        self.tasks = {}
        self.upstream = {}

    def add_task(self, task_id, func=None):
        if task_id in self.tasks:
            raise ValueError(f"duplicate task_id {task_id}")
        self.tasks[task_id] = func or (lambda: None)
        self.upstream[task_id] = set()

    def link(self, upstream_id, downstream_id):
        self.upstream[downstream_id].add(upstream_id)

    def levels(self):
        remaining = {t: set(u) for t, u in self.upstream.items()}
        result = []
        while remaining:
            ready = sorted(t for t, u in remaining.items() if not u)
            if not ready:
                raise ValueError("cycle detected")
            result.append(ready)
            for t in ready:
                del remaining[t]
            for u in remaining.values():
                u.difference_update(ready)
        return result

    def order(self):
        return [t for level in self.levels() for t in level]


def run_dag(dag, run_date, db):
    db.execute("CREATE TABLE IF NOT EXISTS task_instance (dag_id TEXT, run_date TEXT, task_id TEXT, state TEXT, PRIMARY KEY (dag_id, run_date, task_id))")
    for task_id in dag.tasks:
        db.execute("INSERT INTO task_instance VALUES (?, ?, ?, 'scheduled')", (dag.dag_id, run_date, task_id))
    states = {}
    for level in dag.levels():
        for task_id in level:
            if any(states[u] != "success" for u in dag.upstream[task_id]):
                state = "upstream_failed"
            else:
                try:
                    dag.tasks[task_id]()
                    state = "success"
                except Exception:
                    state = "failed"
            states[task_id] = state
            db.execute("UPDATE task_instance SET state = ? WHERE dag_id = ? AND run_date = ? AND task_id = ?", (state, dag.dag_id, run_date, task_id))
    run_state = "success" if all(s == "success" for s in states.values()) else "failed"
    return run_state


log = []
dag = Dag("orders_etl")
for task_id in ["extract", "transform", "load", "validate", "report"]:
    dag.add_task(task_id, lambda t=task_id: log.append(t))
dag.link("extract", "transform")
dag.link("transform", "validate")
dag.link("transform", "load")
dag.link("validate", "report")
dag.link("load", "report")

db = sqlite3.connect(":memory:")
print(run_dag(dag, "2025-01-01", db))
print(log)
for row in db.execute("SELECT task_id, state FROM task_instance ORDER BY task_id"):
    print(row)
```

```output
success
['extract', 'transform', 'load', 'validate', 'report']
('extract', 'success')
('load', 'success')
('report', 'success')
('transform', 'success')
('validate', 'success')
```

All five tasks ran in the level order and every row ended in `success`, so the DAG run succeeded. The rows are what the web interface reads: it does not ask a worker, it queries the database.


One task `failed` (`transform`) and two are `upstream_failed` (`load` and `report`). The first line shows the DAG run itself is `failed`. The query for `failed` finds the one task to investigate, which is how an operator reads the interface: start at the red task, not at the orange ones after it.

### Example 4: Top-level code runs on every parse

The scheduler keeps parsing the DAG file. The function below stands for a DAG file whose top level does work (here, counting). Parsing it three times runs that work three times; a task function runs only when its task instance runs.

```python run
calls = {"parse": 0, "task": 0}


def dag_file():
    calls["parse"] += 1

    def extract():
        calls["task"] += 1

    return {"extract": extract}


for _ in range(3):
    tasks = dag_file()

print(calls)
tasks["extract"]()
print(calls)
```

```output
{'parse': 3, 'task': 0}
{'parse': 3, 'task': 1}
```

After three scheduler parses the work in `dag_file` has run three times and no task has run. Only running the task function increments `task`. A real query at the top of a DAG file would execute at the same rate as the parse counter.

## Real-world applications

- A retailer's nightly pipeline is one DAG with extract, transform, load, validate and report tasks; the web interface shows which tasks ran, how long each took and where a failure stopped the chain (Examples 2 and 3).
- An on-call engineer finds the single `failed` task and reads its log, knowing that the `upstream_failed` tasks after it will run when it is fixed and cleared (Example 3).
- A team reviewing DAG code rejects a pull request that queries a database at the top of the file, because the scheduler would run the query on every parse (Example 4).

## Daily review

### Key takeaways

- A DAG is tasks plus directed dependencies with no cycles; a DAG run is one execution, a task instance is one task in one run.
- A task starts when all upstream tasks have succeeded; independent tasks can run in parallel.
- The scheduler reads DAG files and decides what is ready, workers run the tasks and the metadata database holds every state.
- Top-level code in a DAG file runs on every parse; heavy work belongs inside tasks.

### Common mistakes

- Confusing the DAG with a run. Symptom: "I changed the DAG, why did yesterday's run not change?" Fix: a run is history; new code affects new runs.
- Creating a cycle. Symptom: the DAG does not load and the UI shows an import error. Fix: remove one of the edges.
- Reading `upstream_failed` as a failure to fix. Symptom: time spent on the wrong task. Fix: find the task in state `failed`.
- Doing real work at the top of a DAG file. Symptom: a slow scheduler and many repeated queries. Fix: move it into a task function.

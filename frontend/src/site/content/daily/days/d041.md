## Objectives

- Write `LEFT JOIN`, `RIGHT JOIN` and `FULL JOIN` and say which rows each one keeps.
- Read the NULL columns that unmatched rows carry, and count with `COUNT(column)` instead of `COUNT(*)` to get 0 for no matches.
- Find rows with no partner using an anti-join: `LEFT JOIN ... WHERE right_key IS NULL`.
- Explain why a filter on the right table in `WHERE` turns a left join back into an inner join, and when to put it in `ON` instead.
- Choose between inner and outer joins for a given business question.

## Understand

### What the inner join loses

On day 40 you saw that an inner join keeps only matched pairs. That is wrong for questions such as "list every customer and their number of orders, including customers with none". A customer without orders has no partner row, so an inner join drops it and the report is silently incomplete. An **outer join** keeps the unmatched rows of one or both tables and fills the columns of the missing side with NULL.

### LEFT JOIN

`FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id` returns every row of the **left** table (the one written before `JOIN`), paired with its matching rows from the right table. If a left row has no match, it still appears once, with NULL in every column that would have come from the right table. A customer with three orders appears three times, and a customer with none appears once with `o.order_id` NULL. The Northwind customers FISSA and PARIS have no orders, so they are the two rows with NULLs. Because the result starts from the full left table, the number of rows is at least the number of left rows: 91 customers give 102 rows, which is 100 orders matched plus 2 unmatched customers.

Think of the card files from day 40. For each customer card you look for order slips. An inner join throws away cards with no slips; a left join keeps the card and clips a blank slip to it.

### RIGHT JOIN and FULL JOIN

`RIGHT JOIN` is the mirror image: it keeps every row of the right table. `A LEFT JOIN B` and `B RIGHT JOIN A` return exactly the same rows. Most people always write `LEFT JOIN` and put the table they want to keep first, because reading one direction is easier. `FULL JOIN` (also written `FULL OUTER JOIN`) keeps every row of both tables: matched pairs, left rows without a match (right columns NULL) and right rows without a match (left columns NULL). It is the tool for reconciling two lists, for example to see which rows exist in one system and not the other. `OUTER` is optional in all three forms.

### Counting through a left join

After a left join, `COUNT(*)` counts rows, and an unmatched customer is still one row, so `COUNT(*)` reports 1 for a customer with no orders. `COUNT(o.order_id)` counts only non-NULL values (day 36) and correctly reports 0. When you count the right side after an outer join, always count a column from the right table, preferably its key.

### Anti-join: rows with no match

To find the left rows that have no partner, left join and then keep the rows where the right key is NULL: `WHERE o.order_id IS NULL`. This pattern is called an **anti-join**. It works because the only rows where the right table's primary key is NULL are rows that found no match. Test a column that can never be NULL in matched rows, such as the right table's primary key; testing a column that may legitimately be NULL gives false hits. Day 48 shows another way to write the same thing.

### Filtering an outer join: ON or WHERE

Where you put a condition on the right table decides what the query means. Take "each customer with their orders from 1998".

- With the date test in `ON`: `LEFT JOIN orders o ON o.customer_id = c.customer_id AND o.order_date >= '1998-01-01'`. The condition is part of the matching rule, so customers without a 1998 order are kept, with NULLs. All 91 customers stay in the result.
- With the date test in `WHERE`: after the join, a customer without a match has `o.order_date` NULL, the comparison is unknown, and the row is dropped. Every unmatched customer disappears, and the left join behaves like an inner join.

The rule: conditions on the preserved (left) table go in `WHERE`; conditions on the optional (right) table that should limit which partners count go in `ON`. A `WHERE` condition on the right table is only right if you really want to drop customers without matches.

### Common misconception

Learners think `LEFT JOIN` means "the left table is bigger" or "returns the same rows as an inner join plus a few". It means every left row is kept at least once. A left row with several matches still multiplies exactly as in an inner join, so the day 40 warning about repeated values still holds.

### Why it matters

Completeness is a business requirement: all customers (including inactive ones), all products (including unsold ones), all employees (including those with no sales this quarter). Reports built on inner joins quietly hide the zero rows, which are often the most interesting ones.

## Syntax and key functions

```sql-syntax
SELECT l.column, r.column
FROM left_table l
LEFT JOIN right_table r ON l.key = r.key;
```

Anti-join, and a filter that belongs in `ON`:

```sql-syntax
SELECT l.column
FROM left_table l
LEFT JOIN right_table r ON l.key = r.key
WHERE r.primary_key IS NULL;

LEFT JOIN right_table r ON l.key = r.key AND r.some_column >= value
```

| Join | Keeps | NULLs appear in |
|---|---|---|
| `INNER JOIN` | Matched pairs only | Nowhere |
| `LEFT JOIN` | All left rows, matched or not | Right columns of unmatched left rows |
| `RIGHT JOIN` | All right rows, matched or not | Left columns of unmatched right rows |
| `FULL JOIN` | All rows of both tables | Either side, for unmatched rows |

| Pattern | Use |
|---|---|
| `COUNT(r.key)` | Count right-side matches; 0 when none |
| `WHERE r.key IS NULL` after a left join | Left rows without a match (anti-join) |
| Right-table filter in `ON` | Keep unmatched left rows |
| Right-table filter in `WHERE` | Drops unmatched rows (acts like an inner join) |

## Learn by example

### Example 1: A left join shows the missing side as NULL

Three customers: ALFKI has two orders, FISSA and PARIS have none. ALFKI appears twice (once per order), and the customers with no orders appear once each with a NULL `order_id`. The `WHERE` here filters the preserved left table, which is safe.

```sql run
SELECT c.customer_id, c.company_name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE c.customer_id IN ('ALFKI', 'FISSA', 'PARIS')
ORDER BY c.customer_id, o.order_id;
```

```output
customer_id | company_name | order_id
ALFKI | Alfreds Futterkiste | 10248
ALFKI | Alfreds Futterkiste | 10339
FISSA | FISSA Fabrica Inter. Salchichas | NULL
PARIS | Paris spécialités | NULL
```

### Example 2: COUNT(*) against COUNT(right key)

Group by customer and count with both forms. For FISSA and PARIS `COUNT(*)` says 1, because the unmatched customer is one row, while `COUNT(o.order_id)` says 0, the real number of orders. Only the second is right for "number of orders". The query lists the four customers with the fewest orders.

```sql run
SELECT c.customer_id,
       COUNT(*) AS rows_after_join,
       COUNT(o.order_id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id
ORDER BY orders, c.customer_id
LIMIT 4;
```

```output
customer_id | rows_after_join | orders
FISSA | 1 | 0
PARIS | 1 | 0
BOTTM | 1 | 1
BSBEV | 1 | 1
```

### Example 3: Anti-join, customers who never ordered

Keep only the left rows whose right key is NULL. `order_id` is the primary key of `orders`, so it is NULL only when no order matched. The result lists exactly the two customers from the dataset notes.

```sql run
SELECT c.customer_id, c.company_name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id;
```

```output
customer_id | company_name
FISSA | FISSA Fabrica Inter. Salchichas
PARIS | Paris spécialités
```

### Example 4: RIGHT JOIN keeps the right table

Here `employees` is on the right, so every employee is kept. Buchanan (employee 5) has no orders and shows 0 through `COUNT(o.order_id)`, while an inner join would omit him. Swapping the table order and using `LEFT JOIN` would return the same rows. The order with no employee, 10347, is not in this result because it has no matching right row to keep.

```sql run
SELECT e.employee_id, e.last_name, COUNT(o.order_id) AS orders
FROM orders o
RIGHT JOIN employees e ON o.employee_id = e.employee_id
GROUP BY e.employee_id, e.last_name
ORDER BY e.employee_id;
```

```output
employee_id | last_name | orders
1 | Davolio | 11
2 | Fuller | 11
3 | Leverling | 11
4 | Peacock | 11
5 | Buchanan | 0
6 | Suyama | 22
7 | King | 11
8 | Callahan | 11
9 | Dodsworth | 11
```

### Example 5: FULL JOIN finds unmatched rows on both sides

Joining employees to orders with `FULL JOIN` keeps everything. The `WHERE` keeps only the unmatched rows from either side: order 10347 has no employee (left columns NULL) and Buchanan has no order (right column NULL). This is how you reconcile two lists.

```sql run
SELECT e.employee_id, e.last_name, o.order_id
FROM employees e
FULL JOIN orders o ON o.employee_id = e.employee_id
WHERE e.employee_id IS NULL OR o.order_id IS NULL
ORDER BY o.order_id NULLS LAST;
```

```output
employee_id | last_name | order_id
NULL | NULL | 10347
5 | Buchanan | NULL
```

### Example 6: A condition in ON keeps every customer

The date test is part of the join rule, so the customers without a 1998 order are kept. The row count is 92 for 91 customers, because one customer has two 1998 orders (matched pairs repeat the customer). 33 rows have a matching 1998 order, and 59 customers have none. Moving the date test into `WHERE` would remove these 59 customers and leave only 33 rows.

```sql run
SELECT COUNT(*) AS result_rows,
       COUNT(o.order_id) AS matched_1998_orders,
       COUNT(*) FILTER (WHERE o.order_id IS NULL) AS customers_without_1998_order
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
                  AND o.order_date >= '1998-01-01';
```

```output
result_rows | matched_1998_orders | customers_without_1998_order
92 | 33 | 59
```

## Real-world applications

**Zero-inclusive reports.** "Orders per customer" or "units per product" must show zeros. A left join with `COUNT(right.key)` (example 2) produces them; an inner join would hide inactive customers and unsold products.

**Finding gaps.** Customers who never ordered (example 3), products never sold, employees without sales: the anti-join answers every "who has no X" question, which marketing and inventory teams ask constantly.

**Reconciling two sources.** A full join (example 5) compares an extract from one system with another and shows what is missing from each side, the first step of data migration checks.

**Time-limited activity.** "Customers and their orders in the last year, keeping inactive customers" needs the date test in `ON` (example 6) so that inactive customers stay in the report.

## Daily review

### Key takeaways

- `LEFT JOIN` keeps every left row; unmatched rows get NULL in the right columns. `RIGHT JOIN` is the mirror; `FULL JOIN` keeps both sides.
- `COUNT(*)` counts the unmatched row as 1; `COUNT(right.key)` counts real matches and gives 0.
- Anti-join: `LEFT JOIN ... WHERE right.primary_key IS NULL`.
- A right-table condition in `WHERE` removes the unmatched rows; in `ON` it only limits which partners match.
- A left join still multiplies rows when a left row has several matches.

### Common mistakes

- Using `COUNT(*)` after a left join and reporting 1 order for customers with none. Count `o.order_id`.
- Testing for no match with `WHERE o.order_id = NULL`, which never returns rows. Use `IS NULL`.
- Filtering the right table in `WHERE` (`WHERE o.order_date >= '1998-01-01'`) and wondering where the customers with no orders went. Move the condition to `ON`.
- Testing a nullable right column for the anti-join (for example `o.shipped_date IS NULL`) and catching matched rows with a missing value too. Test the right primary key.
- Putting the optional table on the left and the table to keep on the right in a `LEFT JOIN`: the wrong table is preserved. Keep the "all rows" table first.
- Forgetting that `FULL JOIN` results contain NULLs on both sides and then grouping by a key from only one side.

### Revision notes

- Left table survives in a `LEFT JOIN`; NULLs fill the right side.
- Count the right key, test the right key for IS NULL.
- Left-table filter: `WHERE`. Optional-table filter that must not drop rows: `ON`.
- Customers 91, orders matched 100, rows after the left join 102.

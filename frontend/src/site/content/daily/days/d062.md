## Objectives

- Share setup between tests with `@pytest.fixture`, and add teardown with `yield`.
- Run one test function over many inputs with `@pytest.mark.parametrize`.
- Use the built-in `tmp_path` fixture for tests that write files.
- Replace a slow or external dependency with a mock or `monkeypatch`.
- Choose what to test: typical cases, boundaries, errors, and what to leave out.

## Understand

### Repetition in tests

After day 61 your tests work, but they repeat themselves in two ways. Many tests start with the same setup, building the same cart or the same sample data. And many tests have the same shape and differ only in the numbers: five tests for five weights. pytest has one feature for each kind of repetition: fixtures for shared setup and parametrisation for shared shape.

### Fixtures

A **fixture** is a function that prepares something a test needs. You mark it with `@pytest.fixture`, and any test that lists the fixture's name as a parameter receives the value the fixture returns. pytest finds the fixture by name and calls it for you, so the test does not repeat the setup code. This is the arrange step (day 61) written once. Fixtures are re-created for each test by default, so tests stay independent: a test that adds items to a cart fixture does not affect the next test.

A fixture can also clean up. If it uses `yield value` instead of `return value`, the code after the `yield` runs after the test finishes, even if the test failed. This is **teardown**: closing a connection, deleting a temporary table. The fixture's **scope** controls how often it is created: `function` (the default, once per test), `module` (once per file) or `session` (once per run). Use a wider scope only for things that are expensive to build and are not changed by tests. Fixtures placed in a file called `conftest.py` are available to every test in that folder without importing them.

### Parametrisation

`@pytest.mark.parametrize("a,b,expected", [(1, 2, 3), (2, 2, 4)])` runs the same test function once per tuple, and each run is reported as a separate test. When one case fails, you see exactly which input broke instead of the first failing assert hiding the rest. The `ids` argument gives readable names. Parametrise when the behaviour is the same and only the data changes; write separate tests when the behaviour differs. A table of cases is also the best place to record the edge cases you have discovered.

### The tmp_path fixture

Code that reads and writes files should not touch your real folders in tests. pytest's built-in `tmp_path` fixture gives each test a fresh, empty temporary directory as a `pathlib.Path`. The test writes its inputs there, calls the function, and reads the outputs. pytest removes old temporary directories later, so tests leave no clutter and cannot interfere with each other. Pair this with the file handling from earlier days.

### Mocking basics

A function that calls a web service, reads the clock or sends an email is hard to test: it is slow, it changes between runs, and it has side effects. A **mock** replaces such a dependency with a stand-in that returns what you decide. The standard library offers `unittest.mock.Mock`: `Mock(return_value=1.2)` is a callable that returns 1.2 and records how it was called, which you can check with `assert_called_once_with(...)`. pytest's `monkeypatch` fixture temporarily replaces an attribute, such as `module.get_rate`, and puts the original back after the test. Keep mocks to real boundaries (network, time, randomness, disk outside `tmp_path`). Mocking your own pure logic makes tests brittle: they then check how the code is written instead of what it does.

### What to test

A function has more behaviours than the one example in your head. Good tests cover: the typical case; the **boundaries**, where the behaviour changes (0, 1, the exact limit, one beyond it); empty or missing input; invalid input that must raise; and a case from every bug you have fixed, so it cannot return. Do not test the language or the library (that `sum` adds), private details that can change without changing behaviour, or the same behaviour a second time with different numbers. Test behaviour through the public function. For floating-point results compare with `pytest.approx(0.3)` so that rounding noise is not a failure.

### Common misconception

Learners often put as much as possible into fixtures, and tests become unreadable because the setup is hidden in another file. A fixture should hide only the setup that is not important to the reader. A second misconception is that high coverage (every line executed) means good tests; a test that runs a line without asserting anything proves nothing. Aim for tests that fail when the behaviour changes.

### Why it matters

A real data project has dozens of transformation functions, files and sources. Fixtures, parametrised tables and mocks keep its test suite short enough to maintain, fast enough to run on every change, and independent of network and machine, which is what lets teams trust a green build.

## Syntax and key functions

```python nocheck
import pytest

@pytest.fixture
def cart():
    return Cart()            # or: yield Cart(); then cleanup code

def test_uses_fixture(cart):  # the parameter name selects the fixture
    ...

@pytest.mark.parametrize("weight,expected", [(0.5, 5), (1, 5), (1.01, 8)])
def test_bands(weight, expected):
    assert shipping_cost(weight) == expected

def test_writes_file(tmp_path):
    target = tmp_path / "out.csv"

def test_with_patch(monkeypatch):
    monkeypatch.setattr(module, "get_rate", lambda: 1.25)
```

```text
python -m pytest --setup-show -q    # show fixture setup and teardown
python -m pytest -v                 # parametrised cases appear as test_name[case]
```

| Item | Meaning |
|---|---|
| `@pytest.fixture` | Marks a setup function; tests request it by parameter name |
| `yield` in a fixture | Code after it is teardown |
| `scope="module"` / `"session"` | How long a fixture value lives |
| `conftest.py` | Shared fixtures for a folder |
| `@pytest.mark.parametrize(names, cases)` | One test run per case |
| `tmp_path` | Fresh temporary directory (`pathlib.Path`) per test |
| `monkeypatch.setattr(obj, name, value)` | Temporary replacement, undone after the test |
| `unittest.mock.Mock(return_value=x)` | Callable stand-in that records its calls |
| `pytest.approx(x)` | Float comparison with tolerance |

## Learn by example

### Example 1: a fixture removes repeated setup

Two tests need a cart that already holds two items. The fixture `cart` builds it once in code, and both tests receive a fresh copy by naming `cart` as a parameter. Changing the starting data now means editing one place. The `grep PASSED` keeps only the result lines, which are the same on every pytest version.

```bash run
cat > cart.py <<'PY'
class Cart:
    def __init__(self):
        self.items = []

    def add(self, name, price, qty=1):
        self.items.append((name, price, qty))

    def total(self):
        return sum(price * qty for _, price, qty in self.items)
PY
cat > test_cart.py <<'PY'
import pytest
from cart import Cart

@pytest.fixture
def cart():
    cart = Cart()
    cart.add("pen", 2.5, qty=2)
    cart.add("book", 12)
    return cart

def test_total_of_prepared_cart(cart):
    assert cart.total() == 17

def test_adding_changes_total(cart):
    cart.add("bag", 20)
    assert cart.total() == 37

def test_each_test_gets_a_fresh_cart(cart):
    assert len(cart.items) == 2
PY
python -m pytest -v -p no:cacheprovider 2>&1 | grep PASSED
```

```output
test_cart.py::test_total_of_prepared_cart PASSED                         [ 33%]
test_cart.py::test_adding_changes_total PASSED                           [ 66%]
test_cart.py::test_each_test_gets_a_fresh_cart PASSED                    [100%]
```

### Example 2: setup, teardown and scope

The fixture uses `yield`: the code before it is setup, the code after it is teardown. `--setup-show` prints when each fixture is created (`SETUP`) and destroyed (`TEARDOWN`). With the default function scope the fixture is built and destroyed for each of the two tests. The `F` marks a function-scoped fixture.

```bash run
cat > test_scope.py <<'PY'
import pytest

@pytest.fixture
def connection():
    conn = {"open": True}
    yield conn
    conn["open"] = False

def test_connection_is_open(connection):
    assert connection["open"]

def test_connection_is_open_again(connection):
    assert connection == {"open": True}
PY
python -m pytest --setup-show -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output

        SETUP    F connection
        test_scope.py::test_connection_is_open (fixtures used: connection) .
        TEARDOWN F connection
        SETUP    F connection
        test_scope.py::test_connection_is_open_again (fixtures used: connection) .
        TEARDOWN F connection
2 passed
```

### Example 3: parametrize, one test and many cases

A table of weights and expected costs replaces five near-identical tests. Each tuple is reported separately with its values in brackets, so a failure names the exact case. The boundary values 1 and 5 are included on purpose.

```bash run
cat > shipping.py <<'PY'
def shipping_cost(weight_kg):
    if weight_kg <= 0:
        raise ValueError("weight must be positive")
    if weight_kg <= 1:
        return 5
    if weight_kg <= 5:
        return 8
    return 12
PY
cat > test_shipping.py <<'PY'
import pytest
from shipping import shipping_cost

@pytest.mark.parametrize("weight,expected", [
    (0.5, 5),
    (1, 5),
    (1.01, 8),
    (5, 8),

def test_price_bands(weight, expected):
    assert shipping_cost(weight) == expected

@pytest.mark.parametrize("bad_weight", [0, -1])
def test_non_positive_weight_is_rejected(bad_weight):
```

### Example 4: tmp_path for tests that write files

`save_report` writes a CSV file. The test asks for `tmp_path`, writes into that private folder, and reads the file back to check its exact content. No real folder is touched, and the next test gets another empty folder.

```bash run
cat > report.py <<'PY'
import csv

def save_report(path, rows):
    with open(path, "w", newline="") as handle:
        writer = csv.writer(handle)
        writer.writerow(["name", "total"])
        writer.writerows(rows)
PY
cat > test_report.py <<'PY'
from report import save_report

def test_report_has_header_and_rows(tmp_path):
    target = tmp_path / "out.csv"
    save_report(target, [("ana", 10), ("bo", 5)])
    assert target.read_text().splitlines() == ["name,total", "ana,10", "bo,5"]

def test_empty_report_has_only_header(tmp_path):
    target = tmp_path / "empty.csv"
    save_report(target, [])
    assert target.read_text().splitlines() == ["name,total"]
PY
python -m pytest -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s//'
```

```output

2 passed
```

### Example 5: a mock records how it was called

`Mock` comes from the standard library, so this runs in the browser. `fetch_rate` stands in for a web call and returns 1.25 immediately, with no network. The function under test uses it, and afterwards we can check that it was called once, with the right argument.

```python run
from unittest.mock import Mock

def price_in_eur(amount_usd, fetch_rate):
    rate = fetch_rate("USD")
    return round(amount_usd * rate, 2)

fake_rate = Mock(return_value=1.25)
print(price_in_eur(10, fake_rate))
fake_rate.assert_called_once_with("USD")
print("called once with USD:", fake_rate.call_count == 1)
print("calls:", fake_rate.call_args_list)
```

```output
12.5
called once with USD: True
calls: [call('USD')]
```

### Example 6: monkeypatch and a table of edge cases

`convert` calls `get_rate`, which would use the network in real life. `monkeypatch.setattr` swaps it for a function returning 2.0 for the test and restores it afterwards. The `autouse=True` fixture applies the patch to every test in the file without being requested. The parametrised test covers edge cases of the conversion itself: zero, a negative amount, and a float compared with `pytest.approx`. The last test shows that inside tests the patched function is the one in use.

```bash run
cat > fx.py <<'PY'
def get_rate(currency):
    raise RuntimeError("no network in tests")

def convert(amount, currency):
    return amount * get_rate(currency)
PY
cat > test_fx.py <<'PY'
import pytest
import fx

@pytest.fixture(autouse=True)
def fixed_rate(monkeypatch):
    monkeypatch.setattr(fx, "get_rate", lambda currency: 2.0)

@pytest.mark.parametrize("amount,expected", [
    (10, 20),
    (0, 0),
    (-5, -10),
    (0.1, pytest.approx(0.2)),
])
def test_convert_uses_the_rate(amount, expected):
    assert fx.convert(amount, "USD") == expected

def test_get_rate_is_replaced_during_tests():
    assert fx.get_rate("EUR") == 2.0
PY
python -m pytest -v -p no:cacheprovider 2>&1 | grep -E "PASSED|FAILED"
```

```output
test_fx.py::test_convert_uses_the_rate[10-20] PASSED                     [ 20%]
test_fx.py::test_convert_uses_the_rate[0-0] PASSED                       [ 40%]
test_fx.py::test_convert_uses_the_rate[-5--10] PASSED                    [ 60%]
test_fx.py::test_convert_uses_the_rate[0.1-expected3] PASSED             [ 80%]

```

## Real-world applications

**Test data for pipelines.** A fixture that builds a small sample DataFrame or a few rows (Example 1) gives every transformation test the same known input. When the sample changes, one function changes.

**Tables of edge cases.** Parametrised tests (Examples 3 and 6) are how teams keep the list of tricky inputs found in production: odd dates, empty strings, boundary amounts. Each new bug becomes one more row in the table.

**File and report outputs.** `tmp_path` (Example 4) lets you test CSV and JSON writers without leaving files behind, which suits export jobs and report generators.

**Isolating external services.** Mocks and `monkeypatch` (Examples 5 and 6) let tests for API clients and loaders run in milliseconds on a laptop or a build server with no network, no credentials and no flaky failures.

## Daily review

### Key takeaways

- A fixture is a setup function that tests request by parameter name; use `yield` for teardown and `scope` for sharing.
- `@pytest.mark.parametrize` runs one test over a table of cases, each reported separately.
- `tmp_path` gives each test a private temporary folder for file tests.
- Mock only real boundaries: network, time, randomness, external files. `Mock` records calls; `monkeypatch` swaps and restores.
- Test the typical case, the boundaries, empty or invalid input, and every fixed bug; do not test the library.
- Use `pytest.approx` for floats. Keep tests independent and readable.

### Common mistakes

- Hiding too much in fixtures so that a test cannot be understood without opening `conftest.py`.
- Sharing a mutable fixture with `scope="module"` and letting one test change the data for the next.
- Writing real files into the project folder instead of `tmp_path`.
- Mocking your own logic, so tests pass while the real code is broken. Mock the boundary only.
- Patching the wrong name: patch where the code looks the function up (`fx.get_rate`), not where it was defined, if they differ.
- Forgetting that a parametrised case with the wrong expected value fails alone, then fixing the code instead of the table. Check the expectation first.
- Comparing floats with `==` instead of `pytest.approx`.

### Revision notes

- Fixture: `@pytest.fixture`, request by name, `yield` for teardown.
- Table test: `@pytest.mark.parametrize("a,expected", [...])`.
- Files: `tmp_path / "name"`. Floats: `pytest.approx`.
- Mock: `Mock(return_value=...)`, `monkeypatch.setattr(obj, "name", value)`.

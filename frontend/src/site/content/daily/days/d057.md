## Objectives

- Explain what a B-tree index is and what it speeds up: lookups, ranges and sorted output.
- Create single-column and composite indexes, and say which queries a composite index can serve (the leftmost-prefix rule).
- Judge an index by its selectivity and decide when an index helps and when the planner correctly ignores it.
- Describe the write cost of indexes and why you do not index every column.

## Understand

### The problem an index solves

Without help, finding the orders of one customer means reading every row of `orders` and testing each one. This is a **sequential scan**. It is fine for 100 rows and painful for 100 million. An **index** is a separate, sorted structure that stores the values of one or more columns together with pointers to the table rows. It works like the index at the back of a book: instead of reading all pages for "inflation", you look the word up in the sorted list and jump to the pages.

### The B-tree

PostgreSQL's default index type is the **B-tree** (balanced tree). It keeps the values in sorted order inside pages arranged as a tree: a root page points to a few levels of pages, and the bottom level, the leaves, holds the sorted values and row pointers. A lookup walks from the root to one leaf, which takes a handful of page reads even for millions of rows, because every page holds hundreds of entries. Because the leaves are sorted and linked, a B-tree also serves **range** conditions (`order_date >= '1998-01-01'`), prefix matches (`LIKE 'Ger%'`) and `ORDER BY` without a separate sort. It supports `=`, `<`, `<=`, `>`, `>=` and `BETWEEN`. PostgreSQL has other index types (hash, GIN for text and JSON, and more), which are outside today's scope.

### Indexes you already have

A primary key or a `UNIQUE` constraint creates a unique index automatically. In Northwind, `orders` has `orders_pkey` and two indexes made in the schema, on `customer_id` and `employee_id`. Foreign key columns are not indexed automatically in PostgreSQL, which is why the schema creates indexes on them: joins and deletes on those columns then avoid a sequential scan.

### Composite indexes and the leftmost prefix

A **composite** (multicolumn) index covers several columns in a fixed order: `CREATE INDEX ON orders (customer_id, order_date)`. The entries are sorted by the first column, and by the second inside equal first values, like a phone book sorted by last name and then first name. This index serves a search on `customer_id` alone, or on `customer_id` and `order_date` together, and it can return one customer's rows already sorted by date. It cannot serve a search on `order_date` alone efficiently, because dates are scattered across all customers: the index is only useful from its **leftmost prefix**. So put the column you filter with equality first and the range or sort column after it.

### Selectivity

**Selectivity** is how few rows a condition returns, as a share of the table. A condition returning 1 row in 100 million is highly selective, and an index pays off. A condition returning a third of the rows is not selective: reading the index and then jumping to a third of the table row by row costs more than a straight scan. In this table, `ship_via` has 3 distinct values over 100 rows, so `ship_via = 2` returns about a third of the table (33 rows), and it is a poor index target. `order_id` has 100 distinct values in 100 rows and is perfectly selective. A column with few distinct values (a status flag, a boolean) is usually a poor choice for a plain B-tree index.

### When the planner ignores your index

The **query planner** estimates the cost of each way to run a query and picks the cheapest. On tiny tables such as Northwind, a sequential scan reads a page or two and is cheaper than any index, so the planner will often choose `Seq Scan` even when a suitable index exists. That is correct behaviour, not a bug. To show what an index would do, examples below use `SET LOCAL enable_seqscan = off`, which discourages sequential scans for the current transaction only. This setting is a demonstration tool: never use it to fix a production query, because it forces the planner away from what it believes is faster. Day 58 teaches how to read the plans.

### The write cost

An index is not free. Every `INSERT` must add an entry to every index on the table, every `DELETE` must mark entries dead, and an `UPDATE` of an indexed column changes entries too. Indexes also use disk space and memory and make maintenance such as vacuuming slower. A table with ten indexes writes eleven structures per insert. The rule of thumb: index the columns that queries filter, join and sort by, check that the index is used, and drop indexes that no query needs.

### Common misconception

Many learners think adding an index always makes queries faster and that more indexes are better. An index helps only the queries whose conditions match it, may be ignored on small or unselective cases, and always slows writes. Another belief is that an index is used whenever the column appears in `WHERE`. A function on the column (`lower(ship_country) = 'germany'`) usually prevents use of a plain index on that column; day 59 explains how to avoid that.

### Why it matters

Slow queries on growing tables are the most common performance problem in analytics and applications, and the first thing to check is whether the filter and join columns have a suitable index.

## Syntax and key functions

```sql-syntax
CREATE [UNIQUE] INDEX [IF NOT EXISTS] index_name
ON table_name (column_1 [, column_2 ...]);

DROP INDEX index_name;
```

`UNIQUE` also forbids duplicate values. A composite index lists columns in the order of its sort.

```sql-syntax
SET LOCAL enable_seqscan = off;     -- demonstration only, current transaction
EXPLAIN (COSTS OFF) SELECT ...;     -- show the chosen plan without cost numbers
```

| Item | Meaning |
|---|---|
| B-tree | Default sorted index; supports `=`, ranges, `ORDER BY`, prefix `LIKE` |
| Composite index | Several columns, usable from the leftmost column |
| Unique index | Index that also enforces uniqueness (created by `PRIMARY KEY` and `UNIQUE`) |
| `Seq Scan` | Plan node that reads the whole table |
| `Index Scan` | Plan node that walks an index and fetches the matching rows |
| `pg_indexes` | System view that lists indexes: `indexname`, `indexdef` |

## Learn by example

### Example 1: the indexes of a table

The system view `pg_indexes` lists every index. The `orders` table has three: its primary key and the two on foreign key columns created by the schema. `indexdef` shows the `CREATE INDEX` statement that would recreate each.

```sql run
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders'
ORDER BY indexname;
```

```output
indexname | indexdef
idx_orders_customer | CREATE INDEX idx_orders_customer ON public.orders USING btree (customer_id)
idx_orders_employee | CREATE INDEX idx_orders_employee ON public.orders USING btree (employee_id)
orders_pkey | CREATE UNIQUE INDEX orders_pkey ON public.orders USING btree (order_id)
```

### Example 2: measuring selectivity

Count distinct values per column and compare them with the row count. `order_id` is unique, `customer_id` is close to unique, `ship_country` repeats about five times per value and `ship_via` has only three values. The more distinct values compared with rows, the more selective a condition on the column is.

```sql run
SELECT COUNT(*) AS total_rows,
       COUNT(DISTINCT order_id) AS order_ids,
       COUNT(DISTINCT customer_id) AS customers,
       COUNT(DISTINCT ship_country) AS countries,
       COUNT(DISTINCT ship_via) AS shippers
FROM orders;
```

```output
total_rows | order_ids | customers | countries | shippers
100 | 100 | 89 | 21 | 3
```

### Example 3: a lookup by primary key can use its index

A primary key lookup returns at most one row. On a table this small the planner may still prefer a sequential scan, and its choice depends on the statistics it holds at that moment, so the demonstration disables sequential scans for the transaction (see Example 5 for the setting). `EXPLAIN (COSTS OFF)` prints the plan as text without cost numbers, which vary between versions. Plan text from the browser database can differ in small details from PostgreSQL 16, but `Index Scan` and `Seq Scan` are stable node names.

```sql run
SET LOCAL enable_seqscan = off;
EXPLAIN (COSTS OFF)
SELECT * FROM orders WHERE order_id = 10250;
```

```output
QUERY PLAN
Index Scan using orders_pkey on orders
  Index Cond: (order_id = 10250)
```

### Example 4: an index the planner does not use on a tiny table

We create an index on `ship_country` and ask for the German orders. The table has 100 rows in three pages, so the planner correctly prefers the sequential scan, despite the new index. The statements run in one transaction that is rolled back, so the index does not stay.

```sql run
CREATE INDEX idx_orders_ship_country ON orders (ship_country);
EXPLAIN (COSTS OFF)
SELECT order_id FROM orders WHERE ship_country = 'Germany';
```

```output
QUERY PLAN
Seq Scan on orders
  Filter: ((ship_country)::text = 'Germany'::text)
```

### Example 5: forcing the index to see what it would do

`SET LOCAL enable_seqscan = off` tells the planner to avoid sequential scans in this transaction, so the index becomes the preferred path. Use it only to learn how a plan would look, as here. In real tuning, fix the index or the query instead of switching planner features off.

```sql run
CREATE INDEX idx_orders_ship_country ON orders (ship_country);
SET LOCAL enable_seqscan = off;
EXPLAIN (COSTS OFF)
SELECT order_id FROM orders WHERE ship_country = 'Germany';
```

```output
QUERY PLAN
Index Scan using idx_orders_ship_country on orders
  Index Cond: ((ship_country)::text = 'Germany'::text)
```

### Example 6: a composite index serves filter and sort

The composite index `(customer_id, order_date)` finds one customer's rows and returns them already ordered by date, so the plan has no `Sort` node. The first column is compared with equality and the second gives the order. With the single-column index only, the plan would need a `Sort` step.

```sql run
CREATE INDEX idx_orders_customer_date ON orders (customer_id, order_date);
SET LOCAL enable_seqscan = off;
EXPLAIN (COSTS OFF)
SELECT order_id FROM orders WHERE customer_id = 'ALFKI' ORDER BY order_date;
```

```output
QUERY PLAN
Index Scan using idx_orders_customer_date on orders
  Index Cond: ((customer_id)::text = 'ALFKI'::text)
```

## Real-world applications

**Speeding up lookups and joins.** Example 3 shows the pattern behind every primary-key lookup and foreign-key join. On production tables with millions of rows the index turns a full scan into a few page reads.

**Reports that filter and sort.** Dashboards often ask for "the latest orders of one customer". A composite index in the order of Example 6 (equality column first, sort column second) answers that without sorting a large result.

**Protecting data quality.** A unique index rejects duplicate rows (day 55 showed how to find the duplicates that already exist). Business keys such as email or invoice number are normally protected this way.

**Deciding what not to index.** Example 2 shows why indexing `ship_via` would not help: three distinct values give an unselective filter. Reviewing selectivity avoids useless indexes that only slow down loads.

## Daily review

### Key takeaways

- An index is a sorted structure with row pointers; the default B-tree supports equality, ranges and sorted output.
- A composite index works from its leftmost column; put equality columns before range or sort columns.
- Selectivity decides the benefit: few matching rows means a good index; a third of the table does not.
- Small tables are scanned sequentially even when an index exists; that is correct.
- Every index slows `INSERT`, `UPDATE` and `DELETE` and uses space.
- `SET LOCAL enable_seqscan = off` is for demonstration, never for production tuning.

### Common mistakes

- Indexing every column "to be safe", which slows writes and wastes space.
- Creating a composite index in the wrong column order, so the leading column is not in the query's filter.
- Indexing a column with very few distinct values (a status or flag).
- Assuming the planner is wrong when it ignores an index on a tiny table. It is not.
- Leaving `enable_seqscan = off` set in a session and wondering why plans are strange.
- Wrapping the indexed column in a function in `WHERE` (`lower(col)`, `col + 0`), after which a plain index is not used.

### Revision notes

- Syntax: `CREATE INDEX name ON table (col1, col2)`.
- Leftmost prefix: index on (a, b) serves `a` and `a, b`, not `b` alone.
- Selectivity: distinct values divided by rows, high is good.
- Cost: read faster, write slower.

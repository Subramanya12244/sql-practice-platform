## Objectives

- Use `ROW_NUMBER`, running `SUM`, `LAG` and a moving window in queries that a pipeline runs.
- Choose a window query for "latest row per key" and "change from the previous row" instead of Python loops.
- Handle query results from Python as tuples, dictionaries, `fetchmany` batches and DataFrames.
- Check a window query against the equivalent pandas calculation.

## Understand

### Windows in a pipeline

A **window function** computes a value for each row from a related set of rows (its **window**) without collapsing the rows, as `GROUP BY` does. You met the syntax in the SQL phase: `function() OVER (PARTITION BY ... ORDER BY ...)`. Today the focus is on why a pipeline uses them and how Python handles what comes back. Three jobs appear in almost every pipeline. **Deduplicate to the latest row**: an API or a change feed can send the same `order_id` several times, and `ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC)` marks the newest copy as 1 so a filter on `rn = 1` keeps exactly one row per key. **Running totals and moving averages**: `SUM(cents) OVER (ORDER BY day)` gives the cumulative revenue, and a frame such as `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` gives a seven-day window. **Change from the previous row**: `LAG(cents) OVER (ORDER BY day)` returns the previous row's value, so `cents - LAG(cents) ...` is the day-over-day change.

### Why push these into SQL

The same results can be computed in Python with loops, but a window query runs in the database, next to the data, returns only the final rows, and expresses the intent in one line. The Python loop that tracks "the latest row seen per key" is longer, slower on big tables, and easy to get wrong on ties and ordering. Day 115's pushdown rule applies: if the answer needs per-key ranking or ordered running values over millions of rows, do it in SQL and bring back the result. Windows are also the way to find the newest record per key when a table is loaded by upserts or appended by a feed, which Days 124 to 128 will use.

### Frames and ties

A window's **frame** says which rows around the current row take part. With `ORDER BY` and no frame, the default frame runs from the first row to the current row and, importantly, treats rows with the same `ORDER BY` value as peers, so in PostgreSQL and SQLite tied rows share one running total. When you want a strict row-by-row running value, state the frame: `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. For `ROW_NUMBER`, ties in the ordering give an arbitrary but valid numbering, so add a tie-breaker (`ORDER BY updated_at DESC, order_id`) to make the result deterministic. The misconception to avoid is that `ROW_NUMBER` is stable by itself; without a complete ordering two runs may keep different rows.

### Choosing the ranking function

For deduplication use `ROW_NUMBER`, not `RANK` or `DENSE_RANK`. Those two give tied rows the same number, so a filter on 1 can keep two rows for one key, which is exactly the duplicate you wanted to remove. `ROW_NUMBER` always gives each row in the partition a different number. The cost of the choice shows up late: the load succeeds, a primary key rejects the duplicate or, worse, the table has none and the duplicate flows into every total.

### Handling results from Python

A query returns rows. With `sqlite3` or `psycopg` the default row is a **tuple**, accessed by position, which is fragile when the select list changes. Two better habits: set `conn.row_factory = sqlite3.Row` so rows can be read by column name (psycopg has `row_factory` options too), or build dictionaries from `cursor.description`, which lists the column names. For large results read with `cursor.fetchmany(n)` in a loop, or iterate the cursor, so you hold one batch in memory; `fetchall()` pulls everything. For analysis, `pd.read_sql` gives a DataFrame whose columns have names and types. Window queries often return `None` (SQL NULL) in the first row of a `LAG`, which Python receives as `None`; decide explicitly what that means (no previous day) instead of letting it reach arithmetic, where `None - 5` raises a `TypeError`.

### Checking against pandas

Each window function has a pandas twin: `ROW_NUMBER` with `rank(method="first")` or `cumcount()`, running `SUM` with `cumsum()`, `LAG` with `shift(1)`, a moving sum with `rolling(n, min_periods=1).sum()`, and the partition with `groupby`. Computing both on a small table and comparing is the way to trust a window query, and the way to catch an off-by-one frame (a window of 3 preceding instead of 2 preceding, for example).

### Why it matters in data work

Latest-record-per-key and day-over-day change are the first two transformations that most pipelines need after loading. Doing them in SQL keeps the heavy part in the database, keeps definitions in one place, and gives Python a small, typed result to chart or load further.

## Syntax and key functions

```sql-syntax
ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC, tie_breaker)
SUM(x) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
SUM(x) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)
LAG(x, 1) OVER (ORDER BY day)
```

```python
conn.row_factory = sqlite3.Row                       # rows readable by name
cols = [d[0] for d in cur.description]               # column names of the last query
rows = [dict(zip(cols, r)) for r in cur.fetchall()]  # list of dicts
while batch := cur.fetchmany(1000): ...              # bounded memory
```

| Item | What it does or returns |
|---|---|
| `ROW_NUMBER() OVER (...)` | 1, 2, 3 within each partition in the stated order; ties are broken only by extra ORDER BY columns. |
| `SUM(x) OVER (ORDER BY ...)` | Running total; state the frame for row-by-row behaviour. |
| `LAG(x, n)` | The value n rows earlier in the window; NULL when there is none. |
| `cur.description` | Sequence of column descriptors; first item of each is the name. |
| `cur.fetchmany(n)` | Next n rows, empty list at the end. |
| `sqlite3.Row` | Row type readable by index and by column name. |
| `cumsum()`, `shift(1)`, `rolling(n)` | The pandas twins of running sum, `LAG` and moving window. |

## Learn by example

### Example 1: Latest row per key (PostgreSQL, PGlite)

The change feed sent order 1 three times and order 2 twice. `ROW_NUMBER` numbers each order's versions newest first, with the version id as a tie-breaker, and the outer filter keeps number 1. This runs on PGlite, the PostgreSQL stand-in in the browser.

```sql run
CREATE TABLE feed (version_id int, order_id int, status text, updated_at date);
INSERT INTO feed VALUES (1, 1, 'created', '2025-03-01'), (2, 1, 'paid', '2025-03-02'), (3, 2, 'created', '2025-03-02'),
                        (4, 1, 'refunded', '2025-03-05'), (5, 2, 'paid', '2025-03-03'), (6, 3, 'created', '2025-03-04');
SELECT order_id, status, updated_at
FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC, version_id DESC) AS rn FROM feed) t
WHERE rn = 1
ORDER BY order_id;
```

```output
order_id | status | updated_at
1 | refunded | 2025-03-05
2 | paid | 2025-03-03
3 | created | 2025-03-04
```
### Example 2: Running total, change and moving sum (PostgreSQL, PGlite)

Seven days of revenue get a running total, the day-over-day change with `LAG`, and a three-day moving sum with an explicit frame. The first row has no previous day, so its change is NULL.

```sql run
CREATE TABLE daily_rev (day date, cents int);
INSERT INTO daily_rev VALUES ('2025-03-01', 1200), ('2025-03-02', 900), ('2025-03-03', 1500), ('2025-03-04', 1500),
                             ('2025-03-05', 700), ('2025-03-06', 2100), ('2025-03-07', 1000);
SELECT day, cents,
       SUM(cents) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running,
       cents - LAG(cents) OVER (ORDER BY day) AS change,
       SUM(cents) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS moving3
FROM daily_rev
ORDER BY day;
```

```output
day | cents | running | change | moving3
2025-03-01 | 1200 | 1200 | NULL | 1200
2025-03-02 | 900 | 2100 | -300 | 2100
2025-03-03 | 1500 | 3600 | 600 | 3600
2025-03-04 | 1500 | 5100 | 0 | 3900
2025-03-05 | 700 | 5800 | -800 | 3700
2025-03-06 | 2100 | 7900 | 1400 | 4300
2025-03-07 | 1000 | 8900 | -1100 | 3800
```
### Example 3: The same window from Python, with named results

On `sqlite3` the same window syntax works. Python reads the rows by name through `sqlite3.Row`, builds dictionaries from `cursor.description`, and turns the `None` of the first `LAG` into an explicit label before it reaches any arithmetic.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE daily_rev (day TEXT, cents INTEGER)")
conn.executemany("INSERT INTO daily_rev VALUES (?, ?)", [("2025-03-01", 1200), ("2025-03-02", 900), ("2025-03-03", 1500), ("2025-03-04", 1500)])
sql = "SELECT day, cents, cents - LAG(cents) OVER (ORDER BY day) AS change FROM daily_rev ORDER BY day"
cur = conn.execute(sql)
cols = [d[0] for d in cur.description]
rows = [dict(zip(cols, r)) for r in cur.fetchall()]
print(cols)
for r in rows:
    print(r["day"], r["cents"], "no previous day" if r["change"] is None else r["change"])
conn.row_factory = sqlite3.Row
first = conn.execute(sql).fetchone()
print(first["day"], first["cents"])
```

```output
['day', 'cents', 'change']
2025-03-01 1200 no previous day
2025-03-02 900 -300
2025-03-03 1500 600
2025-03-04 1500 0
2025-03-01 1200
```
### Example 4: Check the window against pandas

The SQL window and the pandas twin are computed on the same data and compared. A mismatch would point to an off-by-one frame or a wrong order.

```python run
import sqlite3
import pandas as pd

data = [("2025-03-01", 1200), ("2025-03-02", 900), ("2025-03-03", 1500), ("2025-03-04", 1500), ("2025-03-05", 700)]
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE daily_rev (day TEXT, cents INTEGER)")
conn.executemany("INSERT INTO daily_rev VALUES (?, ?)", data)
sql = pd.read_sql("""SELECT day, cents,
    SUM(cents) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running,
    SUM(cents) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS moving3
    FROM daily_rev ORDER BY day""", conn)
pdf = pd.DataFrame(data, columns=["day", "cents"]).sort_values("day")
pdf["running"] = pdf["cents"].cumsum()
pdf["moving3"] = pdf["cents"].rolling(3, min_periods=1).sum().astype(int)
print(sql["running"].tolist() == pdf["running"].tolist(), sql["moving3"].tolist() == pdf["moving3"].tolist())
print(sql["moving3"].tolist())
```

```output
True True
[1200, 2100, 3600, 3900, 3700]
```
### Example 5: Stream a window result in batches

A window query on a larger table is read in batches of 4,000 rows with `fetchmany`, so only one batch is in memory. The loop keeps a running count and the largest running total seen, which is a result handled in Python.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE events (event_id INTEGER, customer_id INTEGER, cents INTEGER)")
conn.executemany("INSERT INTO events VALUES (?,?,?)", ((i, 1 + i % 5, 100 + i % 7) for i in range(1, 10001)))
cur = conn.execute("""SELECT event_id, customer_id,
    SUM(cents) OVER (PARTITION BY customer_id ORDER BY event_id) AS running
    FROM events ORDER BY event_id""")
batches, rows, top = 0, 0, 0
while True:
    batch = cur.fetchmany(4000)
    if not batch:
        break
    batches += 1
    rows += len(batch)
    top = max(top, max(r[2] for r in batch))
print("batches:", batches, "rows:", rows, "largest running total:", top)
```

```output
batches: 3 rows: 10000 largest running total: 206004
```
## Real-world applications

- **Deduplicating a feed.** The `ROW_NUMBER` filter of Example 1 is how a staging table of repeated API or change-feed records becomes one current row per key before loading.
- **Trend monitoring.** Running totals, day-over-day change and moving sums (Example 2) feed the volume and revenue charts of a pipeline report and detect sudden drops.
- **Typed results for the next step.** Reading rows by name or as dictionaries (Example 3) protects loaders and charts from a changed select list.
- **Trusting a rewrite.** Comparing the window query with the pandas calculation (Example 4) is the check when a calculation moves between SQL and Python.

## Daily review

### Key takeaways

- A window function adds a value to every row from related rows; `GROUP BY` collapses rows.
- `ROW_NUMBER() ... = 1` keeps the latest row per key; add a tie-breaker so the result is deterministic.
- State the frame (`ROWS BETWEEN ...`) when a running or moving value must be strictly row by row.
- Read results by column name, handle the NULL of `LAG`, and stream big results with `fetchmany`.
- Compare a window query with its pandas twin on small data.

### Common mistakes

- Filtering on a window result in the same `SELECT` (`WHERE rn = 1`); it fails because windows run after `WHERE`. Wrap the query in a subquery or CTE.
- Ordering `ROW_NUMBER` only by timestamp with ties, so reruns may keep different rows. Add a tie-breaker.
- Using the default frame and getting equal running totals on tied rows. State `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.
- Doing arithmetic on the `None` returned for the first `LAG` and getting a `TypeError`. Handle it or use `COALESCE`.
- Calling `fetchall()` on millions of rows. Use `fetchmany` or a chunked `read_sql`.

### Revision notes

- Dedupe: `ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC, id DESC)`, keep `rn = 1`.
- Running: `SUM(x) OVER (ORDER BY d ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`; change: `x - LAG(x)`.
- Names: `sqlite3.Row` or `cursor.description`.
- Pandas twins: `cumsum`, `shift(1)`, `rolling(n, min_periods=1)`.

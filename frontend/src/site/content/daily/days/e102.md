## Objectives

- Choose the right HTTP method (`GET`, `POST`, `PUT`, `DELETE`) for reading, creating, replacing and removing a resource.
- Explain safe and idempotent methods, and say which methods are which and why that matters for retries.
- Read a status code by its class (2xx, 3xx, 4xx, 5xx) and name the codes a data pipeline meets most often.
- Decide from a status code whether to accept the response, fix the request, wait and retry, or stop.
- Read and set the headers that matter for ingestion: `Content-Type`, `Accept`, `X-Api-Key`, `Retry-After`, `Location`.

## Understand

### Methods say what you want to do

Day 101 used `GET`, the method that asks for a resource without changing anything. HTTP has a small set of **methods**, also called verbs, and a REST API gives each a meaning on a resource.

- **`GET /orders/17`** reads order 17. It never changes data on the server.
- **`POST /orders`** creates a new order from the JSON body you send. The server chooses the new `order_id` and answers with the created record.
- **`PUT /orders/17`** replaces order 17 with the body you send. Send the whole record; fields you leave out are not kept.
- **`DELETE /orders/17`** removes order 17.

(There is also `PATCH`, which changes only some fields, but the Orders API of this block does not use it.) A data engineer mostly sends `GET`, because ingestion reads. The other three matter when you write back to a service, when you read API documentation, and above all when you decide whether a failed call is safe to repeat.

### Safe and idempotent

A method is **safe** when it only reads. `GET` is safe: calling it ten times changes nothing. A method is **idempotent** (Day 94 used the word for loads) when calling it several times has the same effect on the server as calling it once. `GET`, `PUT` and `DELETE` are idempotent: replacing order 17 with the same body twice leaves one order 17; deleting it twice leaves it deleted (the second call may answer `404`, but the state is the same). `POST` is **not** idempotent: posting the same new order twice creates two orders with two different ids.

This distinction is the root of the retry rules on Day 107. When a request times out you do not know whether the server did the work. Repeating a `GET` or a `PUT` is harmless. Repeating a `POST` can create a duplicate unless the API offers a way to make it safe (an idempotency key, covered on Day 107).

### Status codes come in five classes

Every response starts with a three-digit **status code**. The first digit is the class, and the class tells you who is responsible and what to do.

| Class | Meaning | Examples |
|---|---|---|
| 1xx | Informational | `100 Continue` (rare in data work) |
| 2xx | Success | `200 OK`, `201 Created`, `204 No Content` |
| 3xx | Redirection | `301 Moved Permanently`, `302 Found`, `304 Not Modified` |
| 4xx | Client error: your request is wrong | `400`, `401`, `403`, `404`, `409`, `422`, `429` |
| 5xx | Server error: the server failed | `500`, `502`, `503`, `504` |

Within the classes, learn these. `200 OK`: the request worked and the body has the result. `201 Created`: a `POST` made a resource; a `Location` header gives its address. `204 No Content`: success with no body, typical for `DELETE`. `400 Bad Request`: the request is malformed. `401 Unauthorized`: the credentials are missing or invalid (despite the name, it is about authentication). `403 Forbidden`: the credentials are valid but not allowed to do this. `404 Not Found`: no such resource. `409 Conflict`: the request clashes with the current state, such as creating something that exists. `422 Unprocessable Content`: the body is well formed but its content is invalid (the Orders API uses it for a missing field). `429 Too Many Requests`: you are calling too fast. `500 Internal Server Error`: the server hit a bug. `502` and `503` and `504`: a gateway or the service is down, overloaded or too slow.

### What a pipeline does with each class

The class gives you the first decision. **2xx**: use the body. **3xx**: `requests` follows redirects for `GET` by default, but know that the address moved. **4xx**: the request is wrong, so repeating it unchanged will fail again; fix the key, the URL or the parameters. The exception is `429`, which means "slow down", and waiting then repeating is the correct reaction. **5xx**: the server is at fault and the problem is often temporary; repeating after a pause is reasonable, with limits. A pipeline that retries a `401` ten times only wastes calls, and a pipeline that gives up on the first `503` fails every time the service restarts. Day 107 turns this into code.

### Headers

**Headers** are `Name: value` lines on requests and responses; names are case-insensitive. You will use: `Content-Type` (the format of the body: `application/json`), `Accept` (the format you want back), the credential header (`X-Api-Key` in the Orders API), `Retry-After` (on `429` and `503`: how many seconds to wait), and `Location` (on `201`: the address of the new resource). When you send JSON with `requests`, passing `json=body` sets `Content-Type: application/json` and encodes the body for you.

### Common misconception

Many learners believe that a response with a body is a successful response. Error responses carry JSON bodies too (`{"error": "invalid api key"}`). The status code, not the body, tells you whether the call worked. A second belief is that `401` and `403` are the same. `401` means the server does not know who you are; `403` means it knows and refuses.

### Why it matters

A pipeline's behaviour on failure is decided by status classes. A wrong reading either loses data (giving up on a temporary `503`) or damages it (repeating a `POST`). The codes are also the first thing to look at in a failing job's log.

## Syntax and key functions

```python
import requests

created = requests.post(url + "/orders", json={"customer_id": 4, "amount_cents": 1500}, headers=h, timeout=10)
replaced = requests.put(url + "/orders/17", json=full_record, headers=h, timeout=10)

    new_id = created.json()["order_id"]

```

| Item | What it does or returns |
|---|---|
| `requests.get/post/put/delete(url, ...)` | Send that method; return a `Response`. |
| `json=body` | Encode `body` as JSON and set `Content-Type`. |
| `response.status_code` | The integer code. |
| `response.ok` | `True` for status below 400. |
| `response.raise_for_status()` | Raises `requests.HTTPError` for 4xx and 5xx. |
| `response.headers.get("Retry-After")` | Seconds to wait, as text, when present. |
| `status_code // 100` | The class digit (2, 4, 5). |

## Learn by example

### Example 1: The four methods against a stand-in

`FakeAPI` keeps the first five orders and answers like the Orders API: `POST` creates (`201` with a `Location` header), `PUT` replaces (`200`), `DELETE` removes (`204`), and a missing resource gives `404`. A `POST` without `customer_id` gets `422`. The code prints method, status and what changed.

```python run
import json

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

class Response:
    def __init__(self, status_code, body=None, headers=None):
        self.status_code, self._body, self.headers = status_code, body, headers or {}

    def json(self):
        return json.loads(json.dumps(self._body))

class FakeAPI:
    def __init__(self, orders):
        self.table = {o["order_id"]: dict(o) for o in orders}

    def request(self, method, path, body=None):
        parts = path.strip("/").split("/")
        if method == "POST" and parts == ["orders"]:
            if not body or "customer_id" not in body:
                return Response(422, {"error": "customer_id is required"})
            new_id = max(self.table) + 1
            self.table[new_id] = {"order_id": new_id, **body}
            return Response(201, self.table[new_id], {"Location": f"/orders/{new_id}"})
        key = int(parts[1])
        if key not in self.table:
            return Response(404, {"error": "order not found"})
        if method == "GET":
            return Response(200, self.table[key])
        if method == "PUT":
            self.table[key] = {"order_id": key, **body}
            return Response(200, self.table[key])
        if method == "DELETE":
            del self.table[key]
            return Response(204)

api = FakeAPI(ORDERS[:5])
r = api.request("POST", "/orders", {"customer_id": 4, "amount_cents": 1500, "status": "paid"})
print("POST", r.status_code, r.headers["Location"])
print("POST", api.request("POST", "/orders", {"amount_cents": 1}).status_code)
r = api.request("PUT", "/orders/2", {"customer_id": 9, "amount_cents": 700, "status": "refunded"})
print("PUT", r.status_code, sorted(r.json()))
print("DELETE", api.request("DELETE", "/orders/3").status_code)
print("GET", api.request("GET", "/orders/3").status_code, api.request("GET", "/orders/2").status_code)
print(sorted(api.table))
```

```output
POST 201 /orders/6
POST 422
PUT 200 ['amount_cents', 'customer_id', 'order_id', 'status']
DELETE 204
GET 404 200
[1, 2, 4, 5, 6]
```

The `PUT` body had no `currency` or `created_at`, so the stored order lost them: `PUT` replaces the whole resource.

### Example 2: Decide from the status code

`action` maps a status code and headers to one of four decisions: `use` (2xx), `fix request` (4xx except 429), `wait and retry` (429, or 5xx with an optional `Retry-After`) and `follow redirect` (3xx). The function reads the class with integer division. It prints a decision for typical codes.

```python run
def action(status, headers=None):
    headers = headers or {}
    if status // 100 == 2:
        return "use"
    if status // 100 == 3:
        return "follow redirect"
    if status == 429 or status // 100 == 5:
        wait = headers.get("Retry-After")
        return f"wait {wait}s and retry" if wait else "wait and retry"
    if status // 100 == 4:
        return "fix request"
    return "unknown"

for status, headers in [(200, None), (201, None), (204, None), (301, None), (401, None), (404, None),
                        (422, None), (429, {"Retry-After": "2"}), (500, None), (503, {"Retry-After": "30"})]:
    print(status, action(status, headers))
```

```output
200 use
201 use
204 use
301 follow redirect
401 fix request
404 fix request
422 fix request
429 wait 2s and retry
500 wait and retry
503 wait 30s and retry
```

### Example 3: Idempotent and not

Posting the same order three times creates three orders. Putting the same record three times leaves one. Deleting twice leaves the same state, with a `404` the second time. The counts make the difference visible.

```python run
orders = {}
next_id = 1

def post(body):
    global next_id
    orders[next_id] = dict(body)
    next_id += 1

def put(order_id, body):
    orders[order_id] = dict(body)

def delete(order_id):
    return 204 if orders.pop(order_id, None) is not None else 404

body = {"customer_id": 4, "amount_cents": 1500}
for _ in range(3):
    post(body)
print("after 3 posts:", len(orders))

orders.clear()
for _ in range(3):
    put(1, body)
print("after 3 puts:", len(orders))
print("deletes:", delete(1), delete(1), len(orders))
```

```output
after 3 posts: 3
after 3 puts: 1
deletes: 204 404 0
```

This is why a timeout on a `POST` is dangerous and a timeout on a `PUT` is not: you cannot tell whether the first attempt succeeded.

### Example 4: The same methods over real HTTP

The local server from Day 101 handles all four methods. The client uses `requests.post`, `put` and `delete` with `json=`. It reads the status codes and `raise_for_status`, which raises on a `404` or a `422`.

```python local
import json
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import parse_qs, urlparse

import requests

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

API_KEY = "demo-key-123"

def start_server(orders, rate_limit_every=0):
    state = {"requests": 0, "orders": {o["order_id"]: dict(o) for o in orders}}

    def route(method, parts, query, body):
        table = state["orders"]
        if parts == ["orders"] and method == "GET":
            rows = [table[k] for k in sorted(table)]
            if "cursor" in query:
                start = int(query["cursor"] or 0)
                size = int(query.get("limit", 25))
                nxt = start + size
                return 200, {"data": rows[start:nxt], "next_cursor": str(nxt) if nxt < len(rows) else None}
            if "offset" in query:
                start, size = int(query["offset"]), int(query.get("limit", 25))
                return 200, {"data": rows[start:start + size], "offset": start, "total": len(rows)}
            page, size = int(query.get("page", 1)), int(query.get("page_size", 20))
            if page < 1 or not 1 <= size <= 100:
                return 400, {"error": "bad paging parameters"}
            pages = -(-len(rows) // size)
            return 200, {"data": rows[(page - 1) * size:page * size], "page": page, "total_pages": pages}
        if parts == ["orders"] and method == "POST":
            if not body or "customer_id" not in body:
                return 422, {"error": "customer_id is required"}
            new_id = max(table) + 1
            table[new_id] = {"order_id": new_id, **body}
            return 201, table[new_id]
        if len(parts) == 2 and parts[0] == "orders" and parts[1].isdigit():
            key = int(parts[1])
            if key not in table:
                return 404, {"error": "order not found"}
            if method == "GET":
                return 200, table[key]
            if method == "PUT":
                table[key] = {"order_id": key, **body}
                return 200, table[key]
            if method == "DELETE":
                del table[key]
                return 204, None
        return 404, {"error": "no such route"}

    class Handler(BaseHTTPRequestHandler):
        def log_message(self, *args):
            pass

        def handle_request(self, method):
            state["requests"] += 1
            length = int(self.headers.get("Content-Length") or 0)
            body = json.loads(self.rfile.read(length)) if length else None
            if self.headers.get("X-Api-Key") != API_KEY:
                status, payload, extra = 401, {"error": "invalid api key"}, {}
            elif rate_limit_every and state["requests"] % rate_limit_every == 0:
                status, payload, extra = 429, {"error": "slow down"}, {"Retry-After": "2"}
            else:
                url = urlparse(self.path)
                query = {k: v[0] for k, v in parse_qs(url.query, keep_blank_values=True).items()}
                status, payload = route(method, url.path.strip("/").split("/"), query, body)
                extra = {}
            data = b"" if payload is None else json.dumps(payload).encode()
            self.send_response(status)
            self.send_header("Content-Type", "application/json")
            self.send_header("Content-Length", str(len(data)))
            for name, value in extra.items():
                self.send_header(name, value)
            self.end_headers()
            self.wfile.write(data)

        do_GET = lambda self: self.handle_request("GET")
        do_POST = lambda self: self.handle_request("POST")
        do_PUT = lambda self: self.handle_request("PUT")
        do_DELETE = lambda self: self.handle_request("DELETE")

    server = HTTPServer(("127.0.0.1", 0), Handler)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    return server, f"http://127.0.0.1:{server.server_port}", state

server, base, state = start_server(ORDERS[:5])
try:
    h = {"X-Api-Key": API_KEY}
    created = requests.post(base + "/orders", json={"customer_id": 4, "amount_cents": 1500, "status": "paid"}, headers=h, timeout=5)
    print(created.status_code, created.headers["Content-Type"], created.json()["order_id"])
    print(requests.post(base + "/orders", json={"amount_cents": 1}, headers=h, timeout=5).status_code)
    print(requests.put(base + "/orders/2", json={"customer_id": 9}, headers=h, timeout=5).json())
    deleted = requests.delete(base + "/orders/3", headers=h, timeout=5)
    print(deleted.status_code, repr(deleted.text))
    missing = requests.get(base + "/orders/3", headers=h, timeout=5)
    print(missing.status_code, missing.ok)
    try:
        missing.raise_for_status()
    except requests.HTTPError as err:
        print("HTTPError:", err.response.status_code)
    print(sorted(state["orders"]))
finally:
    server.shutdown()
    server.server_close()
```

```output
201 application/json 6
422
{'order_id': 2, 'customer_id': 9}
204 ''
404 False
HTTPError: 404
[1, 2, 4, 5, 6]
```

## Real-world applications

- **Safe retries.** A job that reads (`GET`) can retry freely. A job that creates records in a downstream system with `POST` needs a deduplication plan.
- **Triage of failed runs.** In the log, `401` points to the key, `404` to the URL, `429` to the rate and `503` to the provider, so each failure has a different first action.
- **Write-back tasks.** Some pipelines send results back, for example marking orders as exported with `PUT`; idempotency means a rerun does not duplicate them.
- **Monitoring.** Counting responses per status class per run (`2xx: 118, 4xx: 0, 5xx: 2`) is a basic health signal for an ingestion job.

## Daily review

### Key takeaways

- `GET` reads, `POST` creates, `PUT` replaces, `DELETE` removes.
- `GET`, `PUT`, `DELETE` are idempotent; `POST` is not.
- The status class decides the first reaction: 2xx use, 4xx fix (429 is the exception), 5xx wait and retry.
- The status code, not the body, says whether the call worked.
- Key headers: `Content-Type`, `X-Api-Key`, `Retry-After`, `Location`.

### Common mistakes

- **Checking `if response.json()` instead of the status.** An error body is truthy. Check `status_code` or call `raise_for_status()`.
- **Retrying a `4xx`.** `401` or `404` repeated unchanged returns the same answer. Fix the cause. The exception is `429`.
- **Sending a partial record with `PUT`.** The missing fields vanish. Send the full record or use `PATCH` where available.
- **Retrying a `POST` blindly.** A timeout leaves it unknown whether the record was created. Use an idempotency key or check first.
- **Confusing `401` and `403`.** Unknown caller versus forbidden caller.

### Revision notes

- Methods: GET read, POST create (201 + Location), PUT replace, DELETE remove (204).
- Classes: 2xx ok, 3xx moved, 4xx your fault, 5xx their fault; 429 = slow down.
- Idempotent: GET, PUT, DELETE. Not: POST.
- `response.ok`, `raise_for_status()`, `Retry-After`.

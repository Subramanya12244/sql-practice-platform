## Objectives

- Frame a segmentation question around a decision (who to contact, with what, at what cost) before choosing any rules.
- Build rule-based customer segments from RFM measures in SQL and describe each segment by size, revenue share and behaviour.
- Profile segments beyond the rule variables, and check that segment sizes are large enough and stable over time.
- Turn segment profiles into recommendations with an expected return, stating the assumptions.
- Write a segmentation recommendation that a marketing manager can act on.

## Understand

### Start from the decision

Segmentation is a means, not a result. The scenario of this lesson: the marketing team can contact 30 customers a week with a personal offer and asks "who should we contact?". That sentence fixes three things that the analysis must respect. The unit is the **customer** (one row per customer, as in Day 145). The output must be **actionable**: a list or a few groups that the team can reach with a message. And the segments must be **few enough to act on** and **large enough to matter**: ten segments of four customers each cannot support ten campaigns. An analyst who starts by asking for the decision avoids the common failure, a beautiful segmentation that nobody uses.

### From RFM measures to segments

Day 145 computed recency, frequency and monetary value for each customer and scored them. For a scenario it is often better to use **explicit rules on the raw measures**, because the rules can be explained in a sentence to a non-technical reader. For example, with an as-of date of 1999-01-01:

- **active repeat**: two or more orders and the last order within 365 days;
- **lapsed repeat**: two or more orders and the last order more than 365 days ago;
- **recent single**: one order, within the last 365 days;
- **lapsed single**: one order, more than 365 days ago.

These four groups are mutually exclusive and cover every customer, which is a requirement: a customer must land in exactly one group. The rule thresholds (365 days, 2 orders) are choices; test whether the conclusions change when you move them a little, because conclusions that depend on a threshold chosen by luck are fragile.

### Profiling

**Profiling** describes each segment with measures that were not used to define it, so that you learn something new. The rule variables are already known, so a profile adds others: average order value, number of countries, favourite categories, the share of revenue, the shipping delay the customers experienced. Profiling answers "who are these people?" and often exposes that a segment is just one country or one account. Compare each segment with the overall figure, as lift (Day 111): a segment with an average order value of 1.5 times the overall average is a high-value group. Always show the number of customers beside any average, because an average of five customers is anecdote.

### Checking the segments

Three checks keep segmentation honest:

1. **Size**: each segment has enough customers for an average to mean something and for a campaign to be worth running.
2. **Coverage and exclusivity**: segment counts add up to the total number of customers, and no customer is in two segments.
3. **Stability**: segments are measured at a point in time. A customer moves between segments as time passes, a **transition**. Compute the segments at two dates and cross-tabulate them. If most customers change segment between the two dates, the segmentation describes a moment rather than a type of customer, and a campaign built on it will be out of date by the time it runs.

### Recommendations with an expected return

A recommendation for each segment has a **target action**, an **expected outcome** and an **expected cost**, and the expected return is `customers contacted x response rate x order value x margin - cost of contact`. The response rate and the margin are assumptions, because you do not know them for a campaign that has not run (Day 148 explains how to measure the real value with a holdout group). State the assumptions as variables, show how the ranking changes if they move, and recommend a **test** before a full roll-out when the assumptions are uncertain. A recommendation such as "contact the lapsed repeat customers first, with a personal offer, as a test with a 20 percent holdout" is concrete and checkable, whereas "engage lapsed customers" is not.

### Why it matters, and the misconception

Segmentation determines where limited marketing effort goes. The misconception is that more segments mean a better analysis. Beyond a handful of segments the groups get small, differences turn into noise, and the marketing team cannot run separate messages. A second misconception is that high past spend means high future value: a customer who made one large order a long time ago (a "lapsed single" with high monetary value) may never return.

## Syntax and key functions

```sql-syntax
WITH rfm AS (
  SELECT customer_id,
         DATE '1999-01-01' - MAX(order_date)  AS recency_days,
         COUNT(DISTINCT order_id)             AS frequency,
         SUM(line_revenue)                    AS monetary
  FROM ... GROUP BY customer_id)
SELECT CASE WHEN frequency >= 2 AND recency_days <= 365 THEN 'active repeat' ... END AS segment,
       COUNT(*) AS customers, SUM(monetary) AS revenue
FROM rfm GROUP BY 1;
```


| Function or formula | Returns |
|---|---|
| `CASE WHEN ... THEN ... END` | A label chosen by ordered rules (the first match wins). |
| `COUNT(*) / SUM(COUNT(*)) OVER ()` | Segment share of customers. |
| `pd.crosstab(a, b)` | Table of counts for each pair of values. |
| `normalize="index"` | Each row sums to 1: where customers from a segment went. |
| `n x response x value x margin` | Expected gross profit of a campaign. |
| `AVG(x) / overall AVG` | Lift of a segment on a measure. |

## Learn by example

### Example 1: Rule-based segments in SQL

The four RFM rules are applied as a `CASE`, with the as-of date written in the query. The result is checked: the customer counts must add up to the 89 customers with orders and the revenue shares to 100 percent.

```sql run
WITH rfm AS (
  SELECT o.customer_id,
         DATE '1999-01-01' - MAX(o.order_date) AS recency_days,
         COUNT(DISTINCT o.order_id) AS frequency,
         SUM(od.unit_price * od.quantity * (1 - od.discount)) AS monetary
  FROM orders o JOIN order_details od ON od.order_id = o.order_id
  GROUP BY o.customer_id
), seg AS (
  SELECT *,
         CASE WHEN frequency >= 2 AND recency_days <= 365 THEN 'active repeat'
              WHEN frequency >= 2 THEN 'lapsed repeat'
              WHEN recency_days <= 365 THEN 'recent single'
              ELSE 'lapsed single' END AS segment
  FROM rfm
)
SELECT segment,
       COUNT(*) AS customers,
       ROUND(SUM(monetary)::numeric, 0) AS revenue,
       ROUND((100 * SUM(monetary) / SUM(SUM(monetary)) OVER ())::numeric, 1) AS revenue_share_pct
FROM seg
GROUP BY segment
ORDER BY segment;
```

```output
segment | customers | revenue | revenue_share_pct
active repeat | 7 | 31925 | 23.1
lapsed repeat | 3 | 10595 | 7.7
lapsed single | 54 | 68700 | 49.7
recent single | 25 | 27100 | 19.6
```

The counts add up to 89 and the shares to 100 percent. Seven active repeat customers hold 23 percent of revenue, while 79 of the 89 customers ordered only once (54 of them more than a year ago) and hold about 70 percent of the revenue between them. The actions must differ by group.

### Example 2: Profile the segments

Measures that were not used to define the segments describe them: the average order value, the average number of order lines per order, the countries represented and the lift of the average order value against the overall average. The number of customers sits beside each average.

```sql run
WITH cust AS (
  SELECT o.customer_id, c.country,
         DATE '1999-01-01' - MAX(o.order_date) AS recency_days,
         COUNT(DISTINCT o.order_id) AS frequency,
         COUNT(*) AS lines,
         SUM(od.unit_price * od.quantity * (1 - od.discount)) AS monetary
  FROM orders o
  JOIN order_details od ON od.order_id = o.order_id
  JOIN customers c ON c.customer_id = o.customer_id
  GROUP BY o.customer_id, c.country
), seg AS (
  SELECT *,
         CASE WHEN frequency >= 2 AND recency_days <= 365 THEN 'active repeat'
              WHEN frequency >= 2 THEN 'lapsed repeat'
              WHEN recency_days <= 365 THEN 'recent single'
              ELSE 'lapsed single' END AS segment
  FROM cust
)
SELECT segment,
       COUNT(*) AS customers,
       COUNT(DISTINCT country) AS countries,
       ROUND((SUM(monetary) / SUM(frequency))::numeric, 0) AS aov,
       ROUND((SUM(lines)::numeric / SUM(frequency)), 1) AS lines_per_order,
       ROUND(((SUM(monetary) / SUM(frequency)) / (SELECT SUM(monetary) / SUM(frequency) FROM cust))::numeric, 2) AS aov_lift
FROM seg
GROUP BY segment
ORDER BY segment;
```

```output
segment | customers | countries | aov | lines_per_order | aov_lift
active repeat | 7 | 5 | 2128 | 2.3 | 1.54
lapsed repeat | 3 | 3 | 1766 | 2.8 | 1.28
lapsed single | 54 | 19 | 1272 | 2.5 | 0.92
recent single | 25 | 12 | 1084 | 2.6 | 0.78
```

The two large single-order segments spread over 19 and 12 countries, so a country-based campaign would cut across them. The repeat customers have the highest order values (lift 1.54 and 1.28), and the recent single customers the lowest (0.78). The lapsed repeat group has only three customers, so its averages are anecdotes, which is why the customer count sits beside every figure.

### Example 3: Are the segments stable?

A seeded order table covering one year is created, and the same four rules are applied at two as-of dates, 2025-07-01 and 2026-01-01, with "recent" shortened to 90 days. A cross-tabulation, normalised by row, shows where customers of each early segment ended up.

```python run
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
n = 900
tx = pd.DataFrame({
    "order_id": np.arange(5001, 5001 + n),
    "customer_id": (rng.random(n) ** 2 * 200).astype(int) + 1,
    "order_date": pd.Timestamp("2025-01-01") + pd.to_timedelta(rng.integers(0, 360, n), unit="D"),
    "amount": rng.lognormal(3.6, 0.5, n).round(2),
})
def segments(as_of):
    d = tx[tx["order_date"] < as_of]
    c = d.groupby("customer_id").agg(last=("order_date", "max"), freq=("order_id", "size"))
    rec = (as_of - c["last"]).dt.days
    seg = np.where((c["freq"] >= 2) & (rec <= 90), "active repeat",
          np.where(c["freq"] >= 2, "lapsed repeat",
          np.where(rec <= 90, "recent single", "lapsed single")))
    return pd.Series(seg, index=c.index)

early = segments(pd.Timestamp("2025-07-01"))
late = segments(pd.Timestamp("2026-01-01"))
both = pd.concat([early.rename("early"), late.rename("late")], axis=1).dropna()
print("customers in both:", len(both))
print(pd.crosstab(both["early"], both["late"], normalize="index").round(2).to_string())
print("share staying in the same segment:", round(float((both["early"] == both["late"]).mean()), 2))
```

```output
customers in both: 165
late           active repeat  lapsed repeat  lapsed single
early                                                     
active repeat           0.72           0.28           0.00
lapsed repeat           0.60           0.40           0.00
lapsed single           0.56           0.31           0.12
recent single           0.37           0.31           0.31
share staying in the same segment: 0.43
```

Fewer than half of the customers (43 percent) stay in the same segment, and no customer of the early "recent single" group is still a recent single six months later. Recency decays with time, so the segmentation is a snapshot that has to be refreshed when the campaign is planned, and the threshold for "recent" matters.

### Example 4: Expected return per segment

Each segment gets a contact cost, an assumed response rate and an assumed order value and margin. The expected profit of contacting all customers of the segment is computed and ranked, and then the ranking is rechecked after halving the response rates, to see how sensitive it is.

```python run
import pandas as pd

seg = pd.DataFrame({
    "segment": ["active repeat", "lapsed repeat", "recent single", "lapsed single"],
    "customers": [120, 300, 450, 900],
    "response": [0.12, 0.08, 0.05, 0.02],
    "order_value": [160.0, 140.0, 90.0, 70.0],
}).set_index("segment")
margin, cost_per_contact = 0.35, 1.5

def expected(resp_factor):
    n = seg["customers"]
    return n * seg["response"] * resp_factor * seg["order_value"] * margin - n * cost_per_contact

seg["profit"] = expected(1.0)
seg["profit_half_response"] = expected(0.5)
print(seg[["profit", "profit_half_response"]].round(0).to_string())
print("rank:", list(seg["profit"].sort_values(ascending=False).index))
print("rank at half response:", list(seg["profit_half_response"].sort_values(ascending=False).index))
```

```output
               profit  profit_half_response
segment                                    
active repeat   626.0                 223.0
lapsed repeat   726.0                 138.0
recent single    34.0                -321.0
lapsed single  -909.0               -1130.0
rank: ['lapsed repeat', 'active repeat', 'recent single', 'lapsed single']
rank at half response: ['active repeat', 'lapsed repeat', 'recent single', 'lapsed single']
```

The two repeat segments swap places when the response rate halves (lapsed repeat first at the assumed rate, active repeat first at half), and the recent single segment turns from a small profit into a loss. The lapsed single segment loses money under both assumptions. A recommendation that depends on such assumptions should be a small test, which also measures the real response rate.

## Real-world applications

- **Campaign targeting**: Example 1's segments tell the marketing team which list receives which message, and the expected return of Example 4 sets the order of the roll-out.
- **Customer service**: the active repeat group is flagged in the service system for faster handling and for a named account contact.
- **Business reporting**: segment counts and revenue shares are tracked monthly to show whether the share of lapsed customers is growing.
- **Product and pricing**: a profile showing that a segment buys few lines per order suggests cross-selling bundles for that group.

## Daily review

### Key takeaways

- Start from the decision, then define the unit and segments that can support it.
- Use explicit, mutually exclusive rules that cover all customers, and check that counts and shares add up.
- Profile with measures that were not used to define the segments, and show sizes.
- Test stability with a transition table at two dates.
- Recommendations carry an expected return with stated assumptions and, if uncertain, a test.

### Common mistakes

- Overlapping rules where a customer qualifies for two segments or none. Use a single `CASE` with a final `ELSE`, and check the totals.
- Using too many segments, which gives groups of a few customers. Keep to a handful.
- Averaging for a profile without the customer count. A small group's average misleads.
- Assuming segments are permanent. Customers move; measure transitions and refresh.
- Recommending an action without an expected return or a test, so nobody can tell afterwards whether it worked.

### Revision notes

- Segment by one `CASE`; the first matching branch wins; the last branch is `ELSE`.
- Checks: size, coverage (counts add up), stability (transition table).
- Profile = measures not used in the rules, plus lift against the overall figure.
- Expected return = `n x response x value x margin - n x cost`.

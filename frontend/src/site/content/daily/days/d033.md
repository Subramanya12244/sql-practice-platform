## Objectives

- Filter rows with `WHERE` using the comparison operators `=`, `<>`, `<`, `<=`, `>` and `>=`.
- Combine conditions with `AND`, `OR` and `NOT`, and use parentheses to control which conditions group together.
- Match one of several values with `IN` and an inclusive range with `BETWEEN`, including date ranges.
- Search text with `LIKE` and `ILIKE` using the wildcards `%` and `_`.
- Explain why a row is dropped when its condition is false or unknown, and why `= NULL` never works.

## Understand

### WHERE decides which rows survive

A table can hold millions of rows, and an analyst rarely wants all of them. `WHERE` is the **filter**: after `FROM` has chosen a table, `WHERE` looks at each row on its own and asks one question: is this condition true for this row? Rows for which it is true are kept, and all the others are discarded before anything is selected. The condition is called a **predicate**.

This gives the first step of SQL's logical order of work. Conceptually the database does `FROM` (find the rows), then `WHERE` (keep only matching rows), then `SELECT` (compute the output columns). You write `SELECT` first, but it is evaluated after `WHERE`. This explains why a `WHERE` clause cannot use a column alias created in the select list: the alias does not exist yet when filtering happens.

### Comparison operators

A predicate usually compares a column with a value. PostgreSQL uses `=` for equals (a single equals sign, unlike most programming languages), `<>` for not equals (`!=` also works), and `<`, `<=`, `>`, `>=` for ordering. They work on numbers, text and dates. Text and date literals go in single quotes: `country = 'Germany'`, `order_date >= '1998-01-01'`. Text comparison is **case sensitive** in PostgreSQL, so `'germany'` does not equal `'Germany'`. A `boolean` column such as `discontinued` can be used directly as a predicate: `WHERE discontinued` keeps the true rows and `WHERE NOT discontinued` keeps the false ones.

### AND, OR, NOT, and the precedence trap

Several predicates are joined with logical operators. `A AND B` is true only if both are true. `A OR B` is true if at least one is true. `NOT A` flips the result. The trap is **precedence**: `AND` is evaluated before `OR`, in the same way that multiplication comes before addition. So `country = 'UK' OR country = 'USA' AND hire_date > '1993-12-31'` means "UK, or (USA and hired late)", which is almost never what a beginner intended. Parentheses fix the grouping: `(country = 'UK' OR country = 'USA') AND hire_date > '1993-12-31'`. Whenever a condition mixes `AND` and `OR`, always write parentheses, even if the default would happen to be right. Examples 2 and 3 below run both versions on the same data so you can see the difference.

### IN and BETWEEN: shorthand for common patterns

`country IN ('Germany', 'France', 'Spain')` is the shorthand for three equality tests joined by `OR`. It is easier to read and to extend. `NOT IN` keeps rows whose value is not in the list.

`unit_price BETWEEN 10 AND 12` means `unit_price >= 10 AND unit_price <= 12`. Both ends are **included**. This matters for dates: `order_date BETWEEN '1997-01-01' AND '1997-03-31'` includes both of those days. Put the smaller value first; `BETWEEN 12 AND 10` returns nothing.

### Matching text patterns

`LIKE` compares text against a pattern with two wildcards. `%` stands for any number of characters, including none, and `_` stands for exactly one character. `'A%'` means starts with A, `'%market%'` means contains the word market anywhere, and `'B____'` means B followed by exactly four characters. `LIKE` is case sensitive. `ILIKE` is the PostgreSQL version that ignores case. Standard SQL has no `ILIKE`; in other databases you would compare `LOWER(column) LIKE ...` instead. `NOT LIKE` is the opposite.

Be careful with patterns that start with `%`, for example `'%market%'`. They are fine on small tables, but on large tables the database usually cannot use an index for them, so they are slow.

### A first look at NULL

Some values are NULL, meaning "no value". Comparing anything with NULL gives neither true nor false but **unknown**, and `WHERE` keeps only rows where the condition is true. So rows with NULL are silently dropped, no matter which comparison you use. In this copy of Northwind every customer's `region` is NULL; so `region = 'WA'` returns no rows and so does `region <> 'WA'`. You cannot test for NULL with `= NULL` either, because that comparison is also unknown. The correct test is `IS NULL`, which day 35 covers fully. For now, remember the rule that a row stays only when the condition is true.

### Common misconception

Many learners believe `NOT IN` or `<>` returns "everything else". It returns everything else that is not NULL in that column. A row with an unknown value is neither in the list nor outside of it, so it is excluded from both the `IN` query and the `NOT IN` query. If your row counts for a condition and its opposite do not add up to the total number of rows, look for NULLs.

### Why it matters

Every report is a question about a subset: customers in one country, orders in a quarter, products under a price. Filtering correctly, and knowing exactly which rows were excluded, is the difference between a trustworthy number and a misleading one.

## Syntax and key functions

The basic filter. The condition is evaluated for every row of the table:

```sql-syntax
SELECT column_list
FROM table_name
WHERE condition;
```

Conditions joined with logical operators, with parentheses to set the grouping:

```sql-syntax
WHERE (condition_a OR condition_b)
  AND NOT condition_c
```

Membership, range and pattern forms:

```sql-syntax
WHERE column IN (value_1, value_2, value_3)
WHERE column NOT IN (value_1, value_2)
WHERE column BETWEEN low AND high
WHERE column LIKE 'pattern'
WHERE column ILIKE 'pattern'
```

| Predicate | Meaning | Example |
|---|---|---|
| `=`, `<>` | Equal, not equal | `country = 'Spain'` |
| `<`, `<=`, `>`, `>=` | Ordering comparisons | `unit_price >= 50` |
| `a AND b` | Both true | `freight > 100 AND ship_via = 1` |
| `a OR b` | At least one true | `country = 'UK' OR country = 'USA'` |
| `NOT a` | Opposite of `a` | `NOT discontinued` |
| `x IN (...)` | Equal to any listed value | `country IN ('Germany', 'France')` |
| `x BETWEEN a AND b` | `a <= x <= b`, both ends included | `order_date BETWEEN '1997-01-01' AND '1997-03-31'` |
| `x LIKE 'A%'` | Case-sensitive pattern, `%` any text, `_` one character | `company_name LIKE 'A%'` |
| `x ILIKE '%market%'` | Case-insensitive pattern (PostgreSQL) | `company_name ILIKE '%market%'` |

Operator precedence from strongest to weakest: comparison operators, `NOT`, `AND`, `OR`.

## Learn by example

### Example 1: A single comparison

Keep only the products priced above 50. `WHERE` runs before `SELECT`, so the other 70 products are discarded first and we only see the expensive ones. The `ORDER BY` only keeps the row order stable (day 34 explains it).

```sql run
SELECT product_id, product_name, unit_price
FROM products
WHERE unit_price > 50
ORDER BY product_id;
```

```output
product_id | product_name | unit_price
9 | Mishi Kobe Niku | 97.00
18 | Carnarvon Tigers | 62.50
20 | Sir Rodney's Marmalade | 81.00
29 | Thüringer Rostbratwurst | 123.79
38 | Côte de Blaye | 263.50
51 | Manjimup Dried Apples | 53.00
59 | Raclette Courdavault | 55.00
```

### Example 2: AND and OR without parentheses

The intention was "employees in the UK or the USA who were hired after 1993". Because `AND` binds tighter than `OR`, the database reads this as "everyone in the UK, plus the employees in the USA hired after 1993". Buchanan and Suyama (both UK) were hired in 1993, yet they appear in the result.

```sql run
SELECT employee_id, last_name, country, hire_date
FROM employees
WHERE country = 'UK' OR country = 'USA' AND hire_date > '1993-12-31'
ORDER BY employee_id;
```

```output
employee_id | last_name | country | hire_date
5 | Buchanan | UK | 1993-10-17
6 | Suyama | UK | 1993-10-17
7 | King | UK | 1994-01-02
8 | Callahan | USA | 1994-03-05
9 | Dodsworth | UK | 1994-11-15
```

### Example 3: The same condition with parentheses

Parentheses make the grouping explicit: first decide the country, then apply the hire-date rule to every row. Buchanan and Suyama (hired in 1993) are now correctly removed. Compare this with example 2: the same words in the question, but a different result.

```sql run
SELECT employee_id, last_name, country, hire_date
FROM employees
WHERE (country = 'UK' OR country = 'USA') AND hire_date > '1993-12-31'
ORDER BY employee_id;
```

```output
employee_id | last_name | country | hire_date
7 | King | UK | 1994-01-02
8 | Callahan | USA | 1994-03-05
9 | Dodsworth | UK | 1994-11-15
```

### Example 4: Matching a list with IN

`IN` is shorthand for several `OR` equality tests on the same column. There are 27 customers in Germany, France or Spain, and `LIMIT 10` shows the first ten by `customer_id`. One of them, FISSA, will never have orders, a fact you will use on day 41.

```sql run
SELECT customer_id, company_name, country
FROM customers
WHERE country IN ('Germany', 'France', 'Spain')
ORDER BY customer_id
LIMIT 10;
```

### Example 5: A date range with BETWEEN

`BETWEEN` includes both ends, so every order dated from 1 January to 31 March 1997 qualifies. Date literals are written as text in the standard year-month-day order. Because both ends are included, the second end must be the last day you want, not the first day after the range.

```sql run
SELECT order_id, customer_id, order_date, freight
FROM orders
WHERE order_date BETWEEN '1997-01-01' AND '1997-03-31'
ORDER BY order_date, order_id;
```


### Example 6: Text patterns with LIKE and ILIKE

The first pattern `'A%'` keeps names that start with a capital A. It is case sensitive, so a name starting with a lowercase a would not match. The second pattern `'%market%'` would match nothing with `LIKE`, because the names contain `Markets` and `Market` with a capital M. `ILIKE` ignores case and finds all four. The `OR` joins the two predicates, and because there is only one logical operator no parentheses are needed.

```sql run
SELECT customer_id, company_name
FROM customers
WHERE company_name LIKE 'A%' OR company_name ILIKE '%market%'
ORDER BY customer_id;
```

```output
customer_id | company_name
ALFKI | Alfreds Futterkiste
ANATR | Ana Trujillo Emparedados
ANTON | Antonio Moreno Taquería
AROUT | Around the Horn
BOTTM | Bottom-Dollar Markets
GREAL | Great Lakes Food Market
SAVEA | Save-a-lot Markets
WHITC | White Clover Markets
```

## Real-world applications

**Scoping a report to a period.** Monthly and quarterly reports start with a date filter. Example 5 selects the first quarter of 1997 with `BETWEEN`. The same pattern limits an export to last week, a fiscal year, or the rows loaded since the previous run of a pipeline.

**Segmenting customers by market.** Sales teams own territories. `country IN (...)`, as in example 4, selects the customers in a territory in one readable line, and adding a country to the territory later only means adding one value to the list.

**Searching and cleaning names.** Finding company names that contain a word (example 6) is how analysts locate duplicates and variants such as `Market`, `Markets` and `MARKET` during data cleaning. `ILIKE` makes the search forgiving about case.

**Business rules with several conditions.** "Large orders from the Germany or France territory that did not use shipper 2" is a stack of `AND`, `OR` and `NOT`. Wrong precedence, as in example 2, silently returns the wrong people; checking the logic with parentheses prevents reports that look right and are wrong.

## Daily review

### Key takeaways

- `WHERE` keeps a row only when its condition is true; false and unknown rows are discarded before `SELECT` runs.
- `=` tests equality, `<>` tests inequality; text and date literals use single quotes; text comparison is case sensitive.
- `AND` binds tighter than `OR`. Use parentheses whenever both appear.
- `IN (...)` replaces chains of `OR`; `BETWEEN a AND b` includes both ends.
- `LIKE` uses `%` (any text) and `_` (one character) and is case sensitive; `ILIKE` ignores case and is PostgreSQL specific.
- Comparing with NULL never gives true, so use `IS NULL` (day 35), not `= NULL`.

### Common mistakes

- Writing `==` or a single `=` in the wrong place; SQL uses one `=` for comparison.
- Mixing `AND` and `OR` without parentheses.
- Writing `country = 'Germany' OR 'France'`; each side of `OR` must be a complete condition.
- Using `BETWEEN` on a date range and forgetting that the upper end is included, or putting the bigger value first.
- Searching with `LIKE '%market%'` and missing `Market` because `LIKE` is case sensitive.
- Using double quotes around text, which PostgreSQL reads as a column name.
- Expecting `NOT IN` and `IN` to cover every row when the column contains NULLs.

### Revision notes

- Order of work: FROM, then WHERE, then SELECT.
- Precedence: comparisons, NOT, AND, OR.
- `x BETWEEN a AND b` is `x >= a AND x <= b`.
- `%` is any text, `_` is one character, `ILIKE` ignores case.
- NULL is never equal or unequal to anything; the row is dropped.

## Understand

### Waiting is part of a pipeline

Day 160 made tasks survive failures. Many pipelines have a different problem: the work cannot start until something outside the DAG is ready. A partner drops a file at some time after 02:00, an upstream DAG finishes its load, a table is updated. If the DAG starts at 02:00 and the file is not there, the task fails, and a retry a few minutes later is a clumsy way of waiting. A **sensor** is a task whose only job is to wait for a condition and succeed when it holds. Downstream tasks depend on the sensor, so they start only when the condition is true.

A sensor repeatedly **pokes**: it checks the condition, and if it is false, it waits for `poke_interval` seconds and checks again. If `timeout` seconds pass without success, the sensor fails (or is skipped, with `soft_fail=True`). Airflow ships sensors for files (`FileSensor`), for the state of a task in another DAG (`ExternalTaskSensor`), for time (`TimeDeltaSensor`) and, through provider packages, for cloud storage objects, database rows and API conditions. Which package a sensor comes from depends on the Airflow version, so check the import path in the documentation of the version you run.

### Poke and reschedule mode

A sensor has a `mode`. In **poke** mode (the default) the sensor keeps its worker slot for its whole life, sleeping between pokes. That is simple and fast to react, but a sensor that waits six hours occupies a slot for six hours, and a few such sensors can use up all the slots so that no other task can run. In **reschedule** mode the sensor releases its slot between pokes and is scheduled again after `poke_interval`, so it occupies a slot only while it checks. Use reschedule for long waits and poke for waits of seconds or a few minutes. Many sensors can also be made **deferrable**: they hand the waiting to a lightweight trigger process and free the worker entirely; support depends on the sensor and the version.

A sensor that never succeeds is a design question: what should happen if the file never comes? `timeout` makes it fail, which triggers alerts and retries. `soft_fail=True` makes it skipped instead, which is right when the data is optional and the downstream tasks should be skipped quietly. Set the timeout deliberately: a default that is much longer than the business deadline means that the first alert arrives long after the deadline passed.

```python
from datetime import datetime, timedelta
from airflow.decorators import dag
from airflow.sensors.filesystem import FileSensor  # in Airflow 3 the standard provider holds it

@dag(schedule="@daily", start_date=datetime(2025, 1, 1), catchup=False)
def wait_then_load():
    wait = FileSensor(
        task_id="wait_for_orders",
        filepath="/data/in/orders_{{ ds }}.csv",
        poke_interval=60,
        timeout=3 * 60 * 60,
        mode="reschedule",
        soft_fail=False,
    )

wait_then_load()
```

### Callbacks

A **callback** is a function that Airflow calls when something happens to a task or a DAG run. The common ones are `on_failure_callback`, `on_success_callback` and `on_retry_callback`, set on a task or in `default_args`, and DAG-level callbacks for the state of the whole run. Each receives one argument, the **context**: a dictionary with the task instance, the logical date (`ds`), the DAG and, on failure, the `exception`. A callback is where an alert is built and sent: a message to a chat channel, an email, a call to a paging service. It runs in the worker, so it should be short and must not itself fail; wrap the sending in a try block. Airflow also has built-in email notification (`email_on_failure`, `email`) that needs mail settings in the Airflow configuration.

```python
def notify_failure(context):
    ti = context["task_instance"]
    message = f"{ti.dag_id}.{ti.task_id} failed on try {ti.try_number} for {context['ds']}: {context['exception']}"
    send_to_channel(message)

default_args = {"on_failure_callback": notify_failure, "retries": 2}
```

### Logs

Every attempt of every task writes a **log**, kept per attempt, so the log of the second try is separate from the first. Anything the task writes with the standard `logging` module or prints goes in. The UI shows it in the Logs tab of a task instance, and in production the logs are usually shipped to remote storage because workers are temporary. Log the facts that you will need at 03:00: the logical date, the number of rows read and written, the file or query used, and the reason for a decision. Log at the right level: `INFO` for progress, `WARNING` for something odd, `ERROR` for a failure. Never log secrets. When a task fails, read the log of the last attempt first, from the bottom, and look for the first `ERROR`.

### Monitoring and alerting

**Monitoring** is looking at the health of the pipeline: which runs succeeded, how long tasks take and whether data is fresh. The UI shows run history, durations and the schedule; Airflow can also emit metrics, for example to StatsD, for dashboards. **Alerting** is telling a person when they must act. Good alerts follow a few rules. Alert on outcomes that need action: a task failed after its last retry, a deadline was missed, data is older than its allowed age. Do not alert on every retry, which trains people to ignore the channel. Include context in the message: the DAG, the task, the logical date, the attempt and a link to the log. Send each problem once, and send a recovery message when it clears. Check for **freshness**: a pipeline that silently stops is invisible to failure alerts, so compare the age of the newest data with a limit.

### Why it matters

Pipelines fail at night and are fixed by people who were not watching. Sensors decide what happens when inputs are late, callbacks and logs decide how quickly a failure is understood, and alert design decides whether anybody still reads the alerts after a month. The misconception is that more alerts mean more safety. An alert that fires every night is ignored on the night it matters.

## Syntax and key functions

```python
FileSensor(task_id="wait", filepath="...", poke_interval=60, timeout=3600, mode="reschedule", soft_fail=False)
task = PythonOperator(task_id="load", python_callable=load, on_failure_callback=notify_failure)
```

| Setting or object | Meaning |
|---|---|
| `poke_interval` | Seconds between checks. |
| `timeout` | Seconds after which the sensor gives up and fails. |
| `mode` | `poke` keeps the worker slot; `reschedule` frees it between checks. |
| `soft_fail` | On timeout, mark the sensor skipped instead of failed. |
| `on_failure_callback`, `on_success_callback`, `on_retry_callback` | Functions called with the context dictionary. |
| `context["task_instance"]`, `context["ds"]`, `context["exception"]` | Task, logical date and error available in a callback. |
| `email_on_failure`, `email` | Built-in email notification (needs mail configuration). |

## Learn by example

### Example 1: A sensor with a fake clock

The file appears at a given second. The sensor checks every `poke_interval` seconds until `timeout`.

```python run
def sensor(appears_at, poke_interval, timeout):
    t, pokes = 0, 0
    while True:
        pokes += 1
        if t >= appears_at:
            return {"state": "success", "pokes": pokes, "at": t}
        if t + poke_interval > timeout:
            return {"state": "failed", "pokes": pokes, "at": t}
        t += poke_interval

print(sensor(appears_at=250, poke_interval=60, timeout=3600))
print(sensor(appears_at=0, poke_interval=60, timeout=3600))
print(sensor(appears_at=5000, poke_interval=60, timeout=600))
```

```output
{'state': 'success', 'pokes': 6, 'at': 300}
{'state': 'success', 'pokes': 1, 'at': 0}
{'state': 'failed', 'pokes': 11, 'at': 600}
```

The file appears at second 250; the checks at 0, 60, 120, 180 and 240 find nothing, so the sixth check at 300 succeeds, after six pokes. A file that is already there succeeds on the first poke. A file that appears at second 5000 with a timeout of 600 is never found: the sensor makes 11 pokes (the last at second 600) and fails.

### Example 2: Poke or reschedule, and the cost in worker slots

Compare how long each mode occupies a worker slot while waiting for a file that appears after two hours. Each poke takes 2 seconds of real work.

```python run
def slot_seconds(appears_at, poke_interval, mode, poke_cost=2):
    t, pokes = 0, 0
    while t < appears_at:
        pokes += 1
        t += poke_interval
    pokes += 1
    return t if mode == "poke" else pokes * poke_cost

for mode in ["poke", "reschedule"]:
    print(mode, slot_seconds(7200, 60, mode))
print(slot_seconds(30, 60, "poke"), slot_seconds(30, 60, "reschedule"))
```

```output
poke 7200
reschedule 242
60 4
```

Waiting two hours (7,200 seconds) with a poke every minute costs 7,200 slot-seconds in poke mode but only 121 pokes of 2 seconds, 242 slot-seconds, in reschedule mode. For a wait of only 30 seconds the modes differ little (60 against 4), which is why poke is fine for short waits. The model ignores scheduler overhead; the point is the order of magnitude.

### Example 3: A timeout, `soft_fail` and what happens downstream

Combine the sensor result with `soft_fail` to see the state of the sensor and of the next task.

```python run
def sensor_state(found, soft_fail):
    if found:
        return "success"
    return "skipped" if soft_fail else "failed"

def downstream_state(sensor):
    return "success" if sensor == "success" else ("skipped" if sensor == "skipped" else "upstream_failed")

for found, soft in [(True, False), (False, False), (False, True)]:
    s = sensor_state(found, soft)
    print(found, soft, s, downstream_state(s))
```

```output
True False success success
False False failed upstream_failed
False True skipped skipped
```

When the file is missing and `soft_fail` is off, the sensor fails and the load is `upstream_failed`, which raises an alert. With `soft_fail=True` the sensor is skipped and so is the load: nothing is loaded and nobody is alerted, which is correct for optional data and dangerous for mandatory data.

### Example 4: A failure callback builds the message

Run a task with a failing function, call the callback with a context dictionary and print the alert.

```python run
class TaskInstance:
    def __init__(self, dag_id, task_id, try_number):
        self.dag_id, self.task_id, self.try_number = dag_id, task_id, try_number

def notify_failure(context):
    ti = context["task_instance"]
    return f"ALERT {ti.dag_id}.{ti.task_id} failed on try {ti.try_number} for {context['ds']}: {context['exception']}"

def run_task(dag_id, task_id, fn, ds, on_failure_callback, retries=2):
    for attempt in range(1, retries + 2):
        try:
            return {"state": "success", "value": fn(attempt)}
        except Exception as exc:
            if attempt == retries + 1:
                ctx = {"task_instance": TaskInstance(dag_id, task_id, attempt), "ds": ds, "exception": exc}
                return {"state": "failed", "alert": on_failure_callback(ctx)}

def always_fails(attempt):
    raise ValueError("column amount missing")

print(run_task("orders_daily", "transform", always_fails, "2025-03-04", notify_failure))
print(run_task("orders_daily", "transform", lambda a: a, "2025-03-04", notify_failure))
```

```output
{'state': 'failed', 'alert': 'ALERT orders_daily.transform failed on try 3 for 2025-03-04: column amount missing'}
{'state': 'success', 'value': 1}
```

The callback runs once, after the last failed attempt (the third try), and builds a message with the DAG, the task, the attempt, the logical date and the exception: everything a person needs to start. A successful run calls no callback.

### Example 5: Logs per attempt

Capture the log of each attempt separately and find the first error line.

```python run
import io
import logging

def run_attempt(attempt, rows):
    buf = io.StringIO()
    log = logging.getLogger(f"attempt{attempt}")
    log.handlers.clear()
    log.propagate = False
    handler = logging.StreamHandler(buf)
    handler.setFormatter(logging.Formatter("%(levelname)s %(message)s"))
    log.addHandler(handler)
    log.setLevel(logging.INFO)
    log.info("reading %d rows for 2025-03-04", rows)
    if attempt < 3:
        log.warning("source slow")
        log.error("timeout after 30s")
    else:
        log.info("loaded %d rows", rows)
    return buf.getvalue().splitlines()

logs = {a: run_attempt(a, 120) for a in (1, 2, 3)}
for a, lines in logs.items():
    errors = [l for l in lines if l.startswith("ERROR")]
    print(a, len(lines), errors[0] if errors else "no errors")
print(logs[3][-1])
```

```output
1 3 ERROR timeout after 30s
2 3 ERROR timeout after 30s
3 2 no errors
INFO loaded 120 rows
```

Attempts 1 and 2 each wrote three lines and ended with `ERROR timeout after 30s`; attempt 3 wrote two lines and no error, and its last line, `INFO loaded 120 rows`, confirms the load. Because each attempt has its own log, the successful third attempt does not hide what happened in the first two.

### Example 6: Alert rules and alert fatigue

Apply two policies to the same stream of events: alert on every failed attempt, or only on a final failure, once per task per day.

```python run
events = [
    ("2025-03-04", "extract", "retry"), ("2025-03-04", "extract", "retry"), ("2025-03-04", "extract", "success"),
    ("2025-03-04", "load", "retry"), ("2025-03-04", "load", "failed"),
    ("2025-03-05", "extract", "retry"), ("2025-03-05", "extract", "success"),
    ("2025-03-05", "load", "failed"), ("2025-03-05", "load", "failed"),
]

noisy = [e for e in events if e[2] in ("retry", "failed")]
seen, quiet = set(), []
for day, task, state in events:
    if state == "failed" and (day, task) not in seen:
        seen.add((day, task))
        quiet.append((day, task))
print(len(noisy), len(quiet))
print(quiet)
```

```output
7 2
[('2025-03-04', 'load'), ('2025-03-05', 'load')]
```

Alerting on every retry and failure produces 7 messages for two ordinary days of data; alerting only on a final failure once per task per day produces 2, both of which need action (`load` failed on 4 and on 5 March). The retries of `extract` that succeeded needed no human. Fewer, better alerts are the ones that still get read.

## Real-world applications

- **Waiting for a partner file.** A reschedule-mode sensor with a three-hour timeout waits for the nightly drop and alerts if it does not arrive (Examples 1 to 3).
- **Cross-DAG dependencies.** An `ExternalTaskSensor` makes a reporting DAG wait for the load DAG's run of the same logical date, so that reports never run on partial data.
- **On-call alerting.** A failure callback posts the DAG, task, date and exception to the team channel, so the engineer starts with context (Example 4).
- **Post-incident analysis.** Per-attempt logs show whether a failure was transient or persistent and what the first error was (Example 5).

## Daily review

### Key takeaways

- A sensor waits for a condition; `poke_interval` and `timeout` set how often and how long; `soft_fail` skips instead of failing.
- Use reschedule mode (or a deferrable sensor) for long waits to free worker slots.
- Callbacks receive a context dictionary; build a message with DAG, task, attempt, date and error.
- Logs are kept per attempt; log facts you will need and never secrets.
- Alert on outcomes that need action, once, with context; also check freshness.

### Common mistakes

- Using a poke-mode sensor for a multi-hour wait and exhausting the worker slots.
- Leaving a very long default timeout so the alert arrives after the deadline.
- Using `soft_fail` on mandatory data, so a missing file silently skips the load.
- Alerting on every retry, so people mute the channel.
- A callback that raises an error itself, which hides the original failure.

### Revision notes

- Sensor: condition, poke_interval, timeout, mode, soft_fail.
- Callbacks: on_failure, on_success, on_retry with context.
- Logs per attempt; first ERROR from the last attempt.
- Alerts: actionable, once, with context; freshness checks.

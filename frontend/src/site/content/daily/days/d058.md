## Objectives

- Read the output of `EXPLAIN` as a tree of plan nodes and say what each node does.
- Distinguish `EXPLAIN` (the plan the planner expects) from `EXPLAIN ANALYZE` (the plan after actually running the query), and recognise `ANALYZE` as the separate statistics command.
- Name the common scan nodes (`Seq Scan`, `Index Scan`) and join algorithms (`Nested Loop`, `Hash Join`, `Merge Join`) and when each is chosen.
- Read `cost` and `rows` estimates, and compare estimated rows with actual rows to spot bad estimates.

## Understand

### SQL says what, the planner decides how

An SQL query describes the result you want and not the steps to get it. Between your text and the answer sits the **query planner** (also called the optimiser). It considers several ways to execute the query, estimates the cost of each from statistics about the tables, and chooses the cheapest. The chosen strategy is the **execution plan**. `EXPLAIN` shows it without running the query. Reading plans is how you find out why a query is slow and whether the index you created from day 57 is being used.

### A plan is a tree of nodes

A plan is a tree. Each **node** is one operation that takes rows from its children, does something to them and passes rows up. In the printed text the children are indented below the parent, and `->` marks a child. Execution starts at the leaves (usually table scans) and flows upward to the top node, which returns the final rows. Reading from the most indented line outwards tells you the order of work.

```text
Sort
  Sort Key: freight DESC
  ->  Seq Scan on orders
```

This plan reads `orders` with a sequential scan, then the `Sort` node orders the rows by freight and returns them.

### Scan nodes: how rows are read from a table

`Seq Scan` reads every row of the table in storage order and applies the `Filter` line, if there is one. `Index Scan` walks an index to the matching entries and then fetches those rows from the table; the `Index Cond` line shows the condition answered by the index. `Index Only Scan` can answer from the index alone when it contains every needed column. `Bitmap Heap Scan` with a `Bitmap Index Scan` collects the matching row locations first and then reads them in storage order, a middle path when many rows match. As day 57 said, tiny tables are often scanned sequentially because it is cheaper.

### Join algorithms

For a join, the planner chooses an algorithm. A **Nested Loop** takes each row of the outer input and looks up matches in the inner input, ideally through an index; it is excellent when the outer side has few rows. A **Hash Join** builds an in-memory hash table from one input (the `Hash` node) and probes it with the other; it handles large inputs without an index and is common for joining whole tables. A **Merge Join** needs both inputs sorted on the join key and walks them together, good for large sorted inputs. You cannot write the algorithm in SQL; it follows from the data sizes, the filters and the indexes. Examples 3 and 4 show the same join changing from Hash Join to Nested Loop when a filter leaves few rows.

### Other common nodes

`Sort` orders rows (with a `Sort Key` line). `HashAggregate` computes `GROUP BY` results with a hash table. `Limit` stops early. `Hash` builds the table for a Hash Join. Names like `Aggregate`, `GroupAggregate` and `Materialize` also occur. A big `Sort` or an unexpected `Seq Scan` on a large table is usually where to look first.

### Cost and rows

Plain `EXPLAIN` adds estimates in parentheses: `(cost=0.00..11.00 rows=1 width=926)`. `cost` has two numbers in arbitrary planner units: the cost before the first row can be returned and the total cost. They are only meaningful for comparing plans for the same query on the same server. `rows` is the planner's estimate of how many rows the node returns, and `width` is the estimated average row size in bytes. The numbers depend on version and statistics, so they will differ between PostgreSQL versions and between your machine and this browser, and you should not memorise them.

### EXPLAIN ANALYZE: estimates against reality

`EXPLAIN ANALYZE` actually executes the query and adds measured values: the real number of rows (`actual rows`), the number of repeats (`loops`) and, normally, the time for each node. Because the query really runs, never use it carelessly on `INSERT`, `UPDATE` or `DELETE`: they would really change data unless you wrap them in a transaction that you roll back. Times differ from run to run, so this lesson switches them off with `TIMING OFF` and `SUMMARY OFF` to keep outputs stable. The browser database may print `actual rows` with decimals (`13.00`) or an extra `Buffers` line that PostgreSQL 16 does not print; read past those details.

The most useful comparison is estimated `rows` against `actual rows`. A large gap, such as an estimate of 1 and an actual 13, or an estimate of 10 and an actual 10 million, means the planner chose with wrong information, and it may pick a bad plan.

### Statistics, and the other ANALYZE

The planner estimates from **statistics** stored about each table: row counts, distinct values and the most common values. `ANALYZE table_name;` (a statement, not an option of `EXPLAIN`) refreshes them. PostgreSQL runs it automatically in the background on real servers, but a new or freshly loaded table may have none, which gives poor estimates. Do not confuse `ANALYZE orders;` (collect statistics) with `EXPLAIN ANALYZE SELECT ...` (run and measure).

### Common misconception

Learners often believe a `Seq Scan` is always bad, or that high cost means slow. A sequential scan is the best plan for small tables or when most rows are needed. Cost is an estimate in planner units, not seconds. The proof of a slow query is measured time and the gap between estimates and actual rows, not a single scary node name.

### Why it matters

When a report slows down, a plan shows whether the database scans a huge table, sorts too much, or joins in a poor way. Reading it costs a minute and points straight to the fix: an index, a rewritten condition (day 59) or updated statistics.

## Syntax and key functions

```sql-syntax
EXPLAIN query;                                       -- plan with cost estimates
EXPLAIN (COSTS OFF) query;                           -- plan without numbers (stable text)
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF) query;    -- run it, show actual rows, no times
ANALYZE table_name;                                  -- refresh the planner statistics
```

| Output element | Meaning |
|---|---|
| `Seq Scan on t` | Read all rows of `t` |
| `Index Scan using i on t` | Use index `i` to find rows of `t` |
| `Hash Join` / `Nested Loop` / `Merge Join` | Join algorithm |
| `Sort`, `HashAggregate`, `Limit` | Sort, group, early stop |
| `cost=a..b` | Start-up cost and total cost, planner units |
| `rows=n` | Estimated rows from the node |
| `actual rows=n loops=k` | Measured rows per loop and number of loops (ANALYZE only) |
| `Filter`, `Index Cond`, `Hash Cond` | The condition applied at that node |
| `Rows Removed by Filter` | Rows read and discarded by the filter (ANALYZE only) |

## Learn by example

### Example 1: the plan with cost estimates

Plain `EXPLAIN` shows the plan without running the query. The single node is a sequential scan of `orders` with a filter. The estimate says `rows=1`, but Germany has 13 orders: no statistics had been collected for this table, so the planner guessed. The text is the output of one run in the browser database; it is shown but not run by the course tests, because estimates and costs change as soon as statistics change (for example after an index is created), and costs and widths vary by version.

```sql
EXPLAIN
SELECT * FROM orders WHERE ship_country = 'Germany';
```

```text
QUERY PLAN
Seq Scan on orders  (cost=0.00..11.00 rows=1 width=926)
  Filter: ((ship_country)::text = 'Germany'::text)
```

### Example 2: estimate against actual with EXPLAIN ANALYZE

The query now really runs. `actual rows=13.00` is the true number of German orders (this database prints a decimal; PostgreSQL 16 prints `13`) and `Rows Removed by Filter: 87` shows the rows that were read and thrown away. Compare with the estimate of 1 in Example 1. The options turn off times so the text is stable.

```sql run
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF)
SELECT * FROM orders WHERE ship_country = 'Germany';
```

```output
QUERY PLAN
Seq Scan on orders (actual rows=13.00 loops=1)
  Filter: ((ship_country)::text = 'Germany'::text)
  Rows Removed by Filter: 87
```

### Example 3: a join of two whole tables

With no filter, all 100 orders are joined to customers. The planner picks a Hash Join: it scans `customers` into a hash table (the `Hash` node) and scans `orders`, probing the table for each row. The `Hash Cond` line is the join condition.

```sql run
EXPLAIN (COSTS OFF)
SELECT o.order_id, c.company_name
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id;
```

```output
QUERY PLAN
Hash Join
  Hash Cond: ((o.customer_id)::text = (c.customer_id)::text)
  ->  Seq Scan on orders o
  ->  Hash
        ->  Seq Scan on customers c
```

### Example 4: the same join with a selective filter

Restricting to the 13 German orders changes the best plan: a Nested Loop that reads the filtered orders and looks up each customer by primary key. The join algorithm was never written in the query; the planner changed it because the filter left few rows.

```sql run
EXPLAIN (COSTS OFF)
SELECT o.order_id, c.company_name
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id
WHERE o.ship_country = 'Germany';
```

```output
QUERY PLAN
Nested Loop
  ->  Seq Scan on orders o
        Filter: ((ship_country)::text = 'Germany'::text)
  ->  Index Scan using customers_pkey on customers c
        Index Cond: ((customer_id)::text = (o.customer_id)::text)
```

### Example 5: grouping and sorting nodes

`GROUP BY` appears as a `HashAggregate` over a `Seq Scan`, and the `ORDER BY count(*) DESC` adds a `Sort` node on top. Read it bottom-up: scan, aggregate, then sort.

```sql run
EXPLAIN (COSTS OFF)
SELECT ship_country, COUNT(*) AS orders
FROM orders
GROUP BY ship_country
ORDER BY COUNT(*) DESC;
```

```output
QUERY PLAN
Sort
  Sort Key: (count(*)) DESC
  ->  HashAggregate
        Group Key: ship_country
        ->  Seq Scan on orders
```

### Example 6: statistics change the estimate

`ANALYZE orders` collects statistics, and the same query then estimates `rows=13`, matching the actual number from Example 2. This example is shown but not run by the course tests: `ANALYZE` writes the new statistics outside the transaction that the runner rolls back, so running it would change the plans printed by the other examples of this lesson. The text below is the output of one run in the browser database, and costs and widths vary by version. On a real server `ANALYZE` stays in effect, and autovacuum repeats it for you.

```sql
ANALYZE orders;
EXPLAIN
SELECT * FROM orders WHERE ship_country = 'Germany';
```

```text
QUERY PLAN
Seq Scan on orders  (cost=0.00..4.25 rows=13 width=773)
  Filter: ((ship_country)::text = 'Germany'::text)
```

## Real-world applications

**Diagnosing a slow report.** An analyst who sees a `Seq Scan` on a very large table with a `Filter` that removes almost every row (`Rows Removed by Filter`) knows to look for an index on the filtered column, as built on day 57.

**Checking that an index is used.** After creating an index, `EXPLAIN` should show it as `Index Scan`, `Index Only Scan` or `Bitmap Index Scan` for the query it was meant for; if not, the condition may not match the index (day 59).

**Finding bad estimates.** A gap between estimated and actual rows (Examples 1 and 2) points to missing statistics. Running `ANALYZE` (Example 6) is a one-line fix that often turns a bad join algorithm into a good one.

**Comparing two versions of a query.** When you rewrite a query, comparing the plans and the measured row counts shows whether the new version does less work, even before you time it (day 59).

## Daily review

### Key takeaways

- The planner chooses how to run a query; `EXPLAIN` shows the plan as a tree of nodes, read from the deepest node upward.
- Scan nodes: `Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Heap Scan`. Join nodes: `Nested Loop`, `Hash Join`, `Merge Join`.
- `cost` and `rows` are estimates in planner units; they vary by version and by statistics.
- `EXPLAIN ANALYZE` runs the query and adds `actual rows`; compare estimates with actual counts.
- `ANALYZE table` refreshes statistics and is a different thing from `EXPLAIN ANALYZE`.
- A `Seq Scan` is not always bad, and a high cost is not a time.

### Common mistakes

- Running `EXPLAIN ANALYZE` on an `UPDATE` or `DELETE` and changing real data. It executes the statement.
- Reading the plan from the top and thinking the first line runs first. The deepest node runs first.
- Treating cost numbers as milliseconds.
- Assuming a `Seq Scan` on a small table needs an index.
- Memorising cost or row numbers from a tutorial and expecting identical output on another server.
- Confusing `ANALYZE orders;` with the `ANALYZE` option of `EXPLAIN`.

### Revision notes

- Command: `EXPLAIN (COSTS OFF)` for stable text; `EXPLAIN (ANALYZE ...)` for actual rows.
- Read bottom-up: leaves are scans, parents are joins, sorts and aggregates.
- Estimated `rows` against `actual rows` shows whether the planner was misled.
- `ANALYZE t;` updates statistics.

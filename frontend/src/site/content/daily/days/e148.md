## Objectives

- Load a staging table into dimensions and into the fact table in the correct order, using surrogate key lookups by business key.
- Replace the business keys of staged rows with surrogate keys through joins, and count the rows whose lookup fails.
- Handle a missing dimension row with an inferred member and an unknown member, and repair the inferred row when the real data arrives.
- Load a late-arriving fact against the dimension version that was valid on the event date.
- Make the fact load idempotent with a primary key and `ON CONFLICT`, and reconcile staged, loaded and rejected rows.

## Understand

### The load as a pipeline

A warehouse load takes cleaned data from a **staging table** (Day 110) and writes it into the star. The order follows the foreign keys: first the **dimensions**, so that every key a fact needs exists, then the **fact table**. The staging row for a sale carries **business keys** (`customer_id`, `product_id`) and a date, because that is what the source knows. The fact table stores **surrogate keys**, so the load has to translate. This translation is the **key lookup**: for each staged sale, find the dimension row whose business key matches and take its surrogate key.

### Loading dimensions

A dimension load is an upsert shaped by the SCD type of each column (Day 146). New business keys are inserted. For type 1 columns, existing rows are updated in place (`INSERT ... ON CONFLICT DO UPDATE`). For type 2 columns, the current row is closed and a new version inserted. The load should be idempotent, with no new version when nothing changed, and it should run before the fact load in the same run, so that a sale for a brand-new customer finds the customer.

### Loading facts with key lookups

The fact load is one `INSERT ... SELECT` that joins the staging table to each dimension:

- the **date** is looked up by calendar date (`dim_date.full_date`),
- the **customer** by business key, taking the current row or the row valid on the sale date (see below),
- the **product** by business key.

An inner join drops any staged row for which one lookup fails, without error. That is a silent loss, so a load must **count** such rows: staged rows minus rows inserted must equal rows that failed a lookup, and the failures must be listed with the reason (unknown customer, unknown product, date outside the calendar). Left joins make the failures visible: a NULL key marks the missing dimension.

### Missing dimension rows

A sale may refer to a customer that the dimension does not know yet, because the customer feed lags behind the sales feed. Three treatments exist. **Reject** the fact to a reject table and reload it when the dimension catches up; this is simple and delays the fact. **Unknown member**: attach the fact to the reserved row with key 0 (Day 145), which keeps the fact in totals but loses the link to the real customer unless the business key is also stored in the fact. **Inferred member**: insert a placeholder dimension row for the unknown business key (`customer_id = 'C099'`, name `Unknown (inferred)`) so that the fact gets a real surrogate key, and when the real customer data arrives, update the placeholder in place. No fact row needs to be touched, because it already points at the correct row. The inferred member is the standard answer for late-arriving **dimensions**. Decide which dimension values count as "unknown": a missing business key in the source (null) goes to key 0, a business key that is not yet in the dimension gets an inferred row.

### Late-arriving facts

A **late-arriving fact** is an event that reaches the warehouse after the dimension has changed. A sale made on 20 January for customer `C003` arrives on 10 February; on 1 February the customer moved from Germany to Spain (type 2, Day 146). The fact belongs to the version valid on 20 January, so the lookup must use the event date: `valid_from <= sale_date AND (valid_to IS NULL OR sale_date < valid_to)`. A lookup that takes the current row (`is_current`) would attribute the January sale to Spain. For facts that arrive on time, both lookups give the same key, which is why the bug stays hidden until the first late fact. The date-effective lookup is correct for both cases, so many loads simply use it.

### Idempotent fact loads

The fact table has a primary key (`sale_id`, the identifier of the order line in the source). A plain `INSERT ... SELECT` run twice would fail on the second run, or, with no key, double every sale. `INSERT ... ON CONFLICT (sale_id) DO NOTHING` skips rows already loaded, so a re-run, or an overlapping extract, changes nothing. If sales can be **corrected** at the source (a quantity amended), use `DO UPDATE` with a change condition (Day 110) instead.

### Reconciling the load

After the load: staged rows = inserted rows + rows skipped as already loaded + rows rejected for a failed lookup. Print the three numbers and fail the run when the equation does not hold. Day 152's project will assemble these checks into a report.

### Common misconception

Learners write the fact load with inner joins and consider it correct when it does not fail. An inner join is a filter. Every row that fails a lookup disappears from the fact table and from every report. The count equation is how you notice.

### Why it matters

Fact tables are the numbers the business reads. A lost row changes revenue; a row attached to the wrong dimension version changes the region report; a doubled row inflates everything. Each of these is a lookup or key rule from today.

## Syntax and key functions

```sql-syntax
INSERT INTO fact_sales (sale_id, date_key, customer_key, product_key, quantity, amount_cents)
SELECT s.sale_id, d.date_key, c.customer_key, p.product_key, s.quantity, s.amount_cents
FROM stg_sales s
JOIN dim_date d     ON d.full_date = s.sale_date
JOIN dim_customer c ON c.customer_id = s.customer_id
                   AND c.valid_from <= s.sale_date AND (c.valid_to IS NULL OR s.sale_date < c.valid_to)
JOIN dim_product p  ON p.product_id = s.product_id
ON CONFLICT (sale_id) DO NOTHING;
```

| Item | Meaning |
|---|---|
| Key lookup | Join a business key to the dimension to get the surrogate key. |
| Date-effective lookup | `valid_from <= event_date AND (valid_to IS NULL OR event_date < valid_to)`. |
| Left join + `IS NULL` | Lists staged rows whose lookup failed. |
| Inferred member | Placeholder dimension row for a business key not yet known. |
| Unknown member | Reserved key 0 for a missing business key. |
| `ON CONFLICT (sale_id) DO NOTHING` | Skips facts already loaded. |
| staged = inserted + skipped + rejected | The reconciliation equation. |

## Learn by example

### Example 1: A fact load with lookups, and the rows that failed

Six sales are staged. Three have a problem: customer `C099` is not in the dimension, product `P999` is unknown, and the sale of 5 March is outside the date dimension (which ends on 28 February). The inner-join load inserts the three good rows. A left-join query then classifies the staged rows that were not loaded, and the final line reconciles.

```sql run
CREATE TABLE dim_date (
    date_key  integer PRIMARY KEY,
    full_date date    NOT NULL UNIQUE,
    year      integer NOT NULL,
    month     integer NOT NULL CHECK (month BETWEEN 1 AND 12)
);
CREATE TABLE dim_customer (
    customer_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id   text    NOT NULL,
    customer_name text    NOT NULL,
    country       text    NOT NULL,
    valid_from    date    NOT NULL,
    valid_to      date,
    is_current    boolean NOT NULL DEFAULT true,
    CHECK (valid_to IS NULL OR valid_to > valid_from)
);
CREATE UNIQUE INDEX uq_customer_current ON dim_customer (customer_id) WHERE is_current;
CREATE TABLE dim_product (
    product_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id   text NOT NULL UNIQUE,
    product_name text NOT NULL,
    category     text NOT NULL
);
CREATE TABLE fact_sales (
    sale_id      integer PRIMARY KEY,
    date_key     integer NOT NULL REFERENCES dim_date (date_key),
    customer_key integer NOT NULL REFERENCES dim_customer (customer_key),
    product_key  integer NOT NULL REFERENCES dim_product (product_key),
    quantity     integer NOT NULL CHECK (quantity > 0),
    amount_cents integer NOT NULL CHECK (amount_cents >= 0)
);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer (customer_id, customer_name, country, valid_from)
SELECT 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'), (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01'
FROM generate_series(1, 12) AS i;
INSERT INTO dim_product (product_id, product_name, category)
SELECT 'P' || lpad(i::text, 3, '0'), 'Product ' || i, (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
CREATE TABLE stg_sales (sale_id integer, sale_date date, customer_id text, product_id text, quantity integer, amount_cents integer);
INSERT INTO stg_sales VALUES
    (101, '2026-01-10', 'C001', 'P001', 2, 2000),
    (102, '2026-01-20', 'C003', 'P002', 1, 1000),
    (103, '2026-02-10', 'C003', 'P002', 1, 1000),
    (104, '2026-02-11', 'C099', 'P003', 1, 1000),
    (105, '2026-02-12', 'C002', 'P999', 1, 500),
    (106, '2026-03-05', 'C002', 'P001', 1, 750);
INSERT INTO fact_sales (sale_id, date_key, customer_key, product_key, quantity, amount_cents)
SELECT s.sale_id, d.date_key, c.customer_key, p.product_key, s.quantity, s.amount_cents
FROM stg_sales s
JOIN dim_date d ON d.full_date = s.sale_date
JOIN dim_customer c ON c.customer_id = s.customer_id AND c.is_current
JOIN dim_product p ON p.product_id = s.product_id;
SELECT s.sale_id, CASE WHEN c.customer_key IS NULL THEN 'unknown customer'
                       WHEN p.product_key IS NULL THEN 'unknown product'
                       WHEN d.date_key IS NULL THEN 'date outside calendar' END AS reason
FROM stg_sales s
LEFT JOIN dim_customer c ON c.customer_id = s.customer_id AND c.is_current
LEFT JOIN dim_product p ON p.product_id = s.product_id
LEFT JOIN dim_date d ON d.full_date = s.sale_date
WHERE c.customer_key IS NULL OR p.product_key IS NULL OR d.date_key IS NULL
ORDER BY s.sale_id;
```

```output
sale_id | reason
104 | unknown customer
105 | unknown product
106 | date outside calendar
```

The three failures are listed with their reasons. Staged 6 = loaded 3 + rejected 3.

### Example 2: Inferred members repair themselves

Instead of rejecting, the load first creates inferred dimension rows for business keys it has not seen, and extends the date dimension to March. All six sales then load. When the real data for customer `C099` arrives, one `UPDATE` fills the placeholder and the fact row needs no change.

### Example 5: The same lookups in pandas

For a Python pipeline, the key lookup is a `merge` with the dimension. The code merges staged sales with a product dimension and a customer dimension using `how="left"`, so that failures become visible as missing keys, fills them with the unknown key 0, and reconciles. The browser can run it because it uses only pandas.

```python run
import pandas as pd

stg = pd.DataFrame({
    "sale_id": [101, 102, 103, 104],
    "customer_id": ["C001", "C003", "C099", "C002"],
    "product_id": ["P001", "P002", "P003", "P999"],
    "amount_cents": [2000, 1000, 1000, 500],
})
dim_customer = pd.DataFrame({"customer_key": [1, 3, 2], "customer_id": ["C001", "C003", "C002"]})
dim_product = pd.DataFrame({"product_key": [1, 2, 3], "product_id": ["P001", "P002", "P003"]})

fact = (stg.merge(dim_customer, on="customer_id", how="left", validate="m:1")
           .merge(dim_product, on="product_id", how="left", validate="m:1"))
failed = fact[fact["customer_key"].isna() | fact["product_key"].isna()]
print(failed[["sale_id", "customer_id", "product_id"]].to_string(index=False))
fact[["customer_key", "product_key"]] = fact[["customer_key", "product_key"]].fillna(0).astype("int64")
print(fact[["sale_id", "customer_key", "product_key"]].to_string(index=False))
print(len(stg), len(fact), len(failed), int(fact["amount_cents"].sum()) == int(stg["amount_cents"].sum()))
```

```output

     103        C099       P003
     104        C002       P999
 sale_id  customer_key  product_key
     101             1            1
     102             3            2
     103             0            3
     104             2            0
4 4 2 True
```

## Real-world applications

- **Daily sales load.** Staged sales are translated to surrogate keys, bad rows are listed in a reject table, and the equation staged = loaded + rejected is checked.
- **Feeds that arrive out of order.** Orders can arrive before the customer master; inferred members keep the facts and are completed later.
- **Reprocessing.** A late event for last month is loaded against the dimension version of that month, so regional reports of that month stay correct.
- **Re-runs after a failure.** `ON CONFLICT DO NOTHING` lets the scheduler repeat the load without duplicates.

## Daily review

### Key takeaways

- Load dimensions first, then facts; translate business keys with lookups.
- Inner joins filter silently: list and count the rows whose lookup failed.
- Inferred members keep facts for late dimensions; key 0 is for missing business keys.
- Late facts use the dimension version valid on the event date.
- Idempotent fact load: primary key plus `ON CONFLICT`; reconcile staged = inserted + skipped + rejected.

### Common mistakes

- **Inner-join load with no count.** Rows vanish silently. Count and list the failures.
- **Current-row lookup for late facts.** Old sales get the new attributes. Use the date-effective lookup.
- **Key 0 for every unknown.** The link to the real customer is lost. Use inferred members for business keys that will arrive.
- **Loading facts before dimensions.** Foreign keys reject them. Order the load.
- **A non-idempotent insert.** A retry duplicates sales. Use the primary key and `ON CONFLICT`.

### Revision notes

- Order: dimensions, then facts.
- Lookup by business key (and date for SCD2).
- Left joins reveal failures; inferred member; key 0.
- `ON CONFLICT (sale_id) DO NOTHING`; staged = inserted + skipped + rejected.

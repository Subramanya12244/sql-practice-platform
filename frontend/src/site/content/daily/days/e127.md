- Compare query-based CDC (timestamps, snapshot comparison) with log-based CDC (reading the database's change log).

- Apply an ordered change feed to a target idempotently, with a sequence checkpoint, including deletes.

## Understand

### What CDC is

**Change data capture (CDC)** means detecting the changes made in a source and delivering them as a stream of **change events**: this row was inserted, that row was updated (with the new values), another row was deleted. The target applies the events to stay in step with the source. Day 125's watermark load is a simple form of CDC: it notices new and changed rows by their `updated_at`. It has two blind spots. It cannot see **deletes**: a row that no longer exists has no `updated_at` to compare. And it sees only the **latest state** at the time of the poll: if an order changed from `created` to `paid` to `refunded` between two polls, the pipeline sees only `refunded`. For many uses that is enough. For audit trails, for propagating deletes and for keeping a replica exactly in step, it is not.

### Query-based CDC

**Query-based CDC** asks the source database questions with ordinary queries. There are three common forms. A timestamp or version column read above a watermark (Day 125). A **snapshot comparison**: read the full table now, compare it with the previous snapshot by key and derive events. Keys present now but not before are inserts, keys present before but not now are deletes, keys in both whose values differ are updates. This catches deletes, at the price of reading everything every time. And a **soft delete flag**: the source marks rows as deleted (`deleted_at` set) instead of removing them, so a timestamp-based read sees the delete as an update. Query-based CDC needs no special access, only a SELECT permission, which is why it is common. Its costs are load on the source database on every poll, intermediate changes lost between polls, and for timestamps the risk that the application sets them wrongly.

### Log-based CDC

**Log-based CDC** reads the source database's own **transaction log**, the record the database keeps of every committed change so that it can recover from a crash. In PostgreSQL this is the write-ahead log (WAL), which can be decoded into change events through logical decoding; tools such as Debezium read it and publish the events. The log contains every insert, update and delete, in commit order, including each intermediate change, with almost no extra load on the source tables, because the database writes the log anyway. The costs are operational: it needs database configuration and permissions, a tool to run and monitor, and care about what happens when the consumer falls behind (the database must keep the log until it is read). There is no PostgreSQL server in this learning environment, so today's examples build the same idea in miniature: a change log filled by triggers in `sqlite3`, which captures every change in order. A trigger-based log is a real technique too, but it adds work to every write in the source.

### What a change event contains

A usable event has a **sequence number** (a strictly increasing order of commit), an **operation** (`I`, `U` or `D`), the **key**, and for inserts and updates the new column values (some systems also include the old values). The order matters: delete then insert of the same key leaves the row present, insert then delete leaves it absent, and the sequence number decides which happened last.

### Applying changes to the target

The target applies the events in sequence order. `I` and `U` become a guarded upsert (Day 126), which also makes an insert event safe when the row already exists and an update event safe when it does not. `D` becomes a `DELETE` by key, which is naturally safe to repeat. After applying a batch, the pipeline stores the highest applied sequence number in `etl_state`, in the same transaction, exactly as it stored the watermark. On the next run it asks for events with `seq` above that number. If the batch is delivered twice, the second application changes nothing. When only the final state matters, a batch can be reduced to the **latest event per key** first, which is the same ranking as Day 117's `ROW_NUMBER` and avoids upserting a key twice; when history matters (an audit table), keep all events.

### Choosing

Use a watermark when the source has a trustworthy `updated_at`, deletes are rare or soft, and the latest state is enough. Use snapshot comparison for small tables without timestamps. Use log-based CDC when deletes and every intermediate change matter, when the source is under load, or when the target must follow the source closely. A misconception is that CDC means real time: it can feed a streaming system, but applying the events in a nightly batch is still CDC.

## Syntax and key functions

```python
def diff_snapshots(old, new):          # old, new: dict key -> row
    inserts = [k for k in new if k not in old]
    deletes = [k for k in old if k not in new]
    updates = [k for k in new if k in old and new[k] != old[k]]
```

```sql-syntax
CREATE TRIGGER orders_after_update AFTER UPDATE ON orders
BEGIN
  INSERT INTO change_log (op, order_id, status) VALUES ('U', NEW.order_id, NEW.status);
END;
```

| Item | What it does or returns |
|---|---|
| change event | `(seq, op, key, values)`; `op` is `I`, `U` or `D`. |
| `seq` | Strictly increasing sequence number; the order in which changes were committed. |
| snapshot comparison | Derives events by comparing two full reads by key. |
| soft delete | A flag or `deleted_at` column instead of removing the row. |
| log-based CDC | Reads the database's transaction log (PostgreSQL WAL via logical decoding). |
| `NEW` / `OLD` in a trigger | The row after / before the change (SQLite and PostgreSQL triggers). |
| applied-seq checkpoint | Highest `seq` applied, stored with the data in `etl_state`. |

## Learn by example

### Example 1: Events from two snapshots

The old and new snapshots are dictionaries keyed by order id. The comparison returns the inserted, updated and deleted keys. The second line shows what a poll cannot see: if order 2 moved through `paid` on the way to `refunded` between the snapshots, the comparison reports one update to the final state.

```python run
def diff_snapshots(old, new):
    inserts = sorted(k for k in new if k not in old)
    deletes = sorted(k for k in old if k not in new)
    updates = sorted(k for k in new if k in old and new[k] != old[k])
    return inserts, updates, deletes

monday = {1: "paid", 2: "created", 3: "paid"}
tuesday = {1: "paid", 2: "refunded", 4: "paid"}
print(diff_snapshots(monday, tuesday))
print("order 2 changed twice in between (paid, refunded); the diff reports one update to", tuesday[2])
```

```output
([4], [2], [3])
order 2 changed twice in between (paid, refunded); the diff reports one update to refunded
```
### Example 2: A watermark cannot see deletes

The same data is read two ways. A timestamp read above the watermark finds the update and the new row but not the deleted order 3. With a soft-delete column, the deletion becomes a timestamped update that the watermark read does see.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE src (order_id INTEGER PRIMARY KEY, status TEXT, updated_at TEXT, deleted INTEGER DEFAULT 0)")
conn.executemany("INSERT INTO src (order_id, status, updated_at) VALUES (?, ?, ?)", [(1, "paid", "2025-03-01"), (2, "created", "2025-03-01"), (3, "paid", "2025-03-01")])
watermark = "2025-03-01"
conn.execute("UPDATE src SET status = 'refunded', updated_at = '2025-03-02' WHERE order_id = 2")
conn.execute("INSERT INTO src (order_id, status, updated_at) VALUES (4, 'paid', '2025-03-02')")
conn.execute("DELETE FROM src WHERE order_id = 3")
print("hard delete  :", conn.execute("SELECT order_id FROM src WHERE updated_at > ? ORDER BY order_id", (watermark,)).fetchall())

conn.execute("INSERT INTO src (order_id, status, updated_at) VALUES (5, 'paid', '2025-03-01')")
conn.execute("UPDATE src SET deleted = 1, updated_at = '2025-03-03' WHERE order_id = 5")
print("soft delete  :", conn.execute("SELECT order_id, deleted FROM src WHERE updated_at > ? AND order_id = 5", (watermark,)).fetchall())
```

```output
hard delete  : [(2,), (4,)]
soft delete  : [(5, 1)]
```
### Example 3: A change log filled by triggers

Triggers write every insert, update and delete into `change_log` with a sequence number from `AUTOINCREMENT`. This imitates log-based capture: every change is recorded in commit order, including the intermediate states of order 2.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE orders (order_id INTEGER PRIMARY KEY, status TEXT);
CREATE TABLE change_log (seq INTEGER PRIMARY KEY AUTOINCREMENT, op TEXT, order_id INTEGER, status TEXT);
CREATE TRIGGER t_ins AFTER INSERT ON orders BEGIN INSERT INTO change_log (op, order_id, status) VALUES ('I', NEW.order_id, NEW.status); END;
CREATE TRIGGER t_upd AFTER UPDATE ON orders BEGIN INSERT INTO change_log (op, order_id, status) VALUES ('U', NEW.order_id, NEW.status); END;
CREATE TRIGGER t_del AFTER DELETE ON orders BEGIN INSERT INTO change_log (op, order_id, status) VALUES ('D', OLD.order_id, NULL); END;
""")
conn.execute("INSERT INTO orders VALUES (1, 'paid')")
conn.execute("INSERT INTO orders VALUES (2, 'created')")
conn.execute("UPDATE orders SET status = 'paid' WHERE order_id = 2")
conn.execute("UPDATE orders SET status = 'refunded' WHERE order_id = 2")
conn.execute("DELETE FROM orders WHERE order_id = 1")
for row in conn.execute("SELECT * FROM change_log ORDER BY seq"):
    print(row)
```

```output
(1, 'I', 1, 'paid')
(2, 'I', 2, 'created')
(3, 'U', 2, 'paid')
(4, 'U', 2, 'refunded')
(5, 'D', 1, None)
```
### Example 4: Apply the events with a checkpoint

The `apply` function reads events above the stored sequence number, applies them in order (inserts and updates as upserts, deletes as deletes) and stores the new checkpoint in the same transaction. Applying the same events a second time does nothing, and a later event is applied from where the first stopped.

```python run
import sqlite3

events = [(1, "I", 1, "paid"), (2, "I", 2, "created"), (3, "U", 2, "paid"), (4, "U", 2, "refunded"), (5, "D", 1, None)]
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, status TEXT)")
conn.execute("CREATE TABLE etl_state (id INTEGER PRIMARY KEY CHECK (id = 1), last_seq INTEGER NOT NULL)")
conn.execute("INSERT INTO etl_state VALUES (1, 0)")
conn.commit()

def apply(conn, events):
    last = conn.execute("SELECT last_seq FROM etl_state").fetchone()[0]
    new = sorted(e for e in events if e[0] > last)
    with conn:
        for seq, op, key, status in new:
            if op == "D":
                conn.execute("DELETE FROM orders_clean WHERE order_id = ?", (key,))
            else:
                conn.execute("INSERT INTO orders_clean VALUES (?, ?) ON CONFLICT (order_id) DO UPDATE SET status = excluded.status", (key, status))
        if new:
            conn.execute("UPDATE etl_state SET last_seq = ?", (new[-1][0],))
    return len(new)

print("applied", apply(conn, events[:3]))
print("applied", apply(conn, events))
print("applied", apply(conn, events))
print(conn.execute("SELECT * FROM orders_clean ORDER BY order_id").fetchall(), conn.execute("SELECT last_seq FROM etl_state").fetchone()[0])
```

```output
applied 3
applied 2
applied 0
[(2, 'refunded')] 5
```
### Example 5: Apply a change feed in PostgreSQL syntax (PGlite)

The staging table holds a feed with several events per key. The latest event per order is chosen with `ROW_NUMBER`; orders whose latest event is a delete are removed, and the others are upserted. This reproduces the final state without replaying every step.

```sql run
CREATE TABLE cdc_events (seq int, op text, order_id int, status text);
CREATE TABLE orders_clean (order_id int PRIMARY KEY, status text);
INSERT INTO orders_clean VALUES (1, 'paid'), (3, 'paid');
INSERT INTO cdc_events VALUES (1, 'U', 1, 'refunded'), (2, 'I', 2, 'created'), (3, 'U', 2, 'paid'), (4, 'D', 3, NULL), (5, 'I', 4, 'paid'), (6, 'D', 4, NULL);
CREATE TABLE latest AS
SELECT order_id, op, status FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY seq DESC) AS rn FROM cdc_events) t WHERE rn = 1;
DELETE FROM orders_clean WHERE order_id IN (SELECT order_id FROM latest WHERE op = 'D');
INSERT INTO orders_clean SELECT order_id, status FROM latest WHERE op <> 'D'
ON CONFLICT (order_id) DO UPDATE SET status = EXCLUDED.status;
SELECT order_id, status FROM orders_clean ORDER BY order_id;
```

```output
order_id | status
1 | refunded
2 | paid
```
## Real-world applications

- **Keeping a replica or warehouse table in step.** Applying inserts, updates and deletes from a feed (Examples 4 and 5) keeps a reporting table equal to the production table, including deleted rows.
- **Audit and history.** A table of every change event (Example 3) answers which states order 2 passed through and in what order, which a latest-state load cannot.
- **Finding a lost delete.** When a report counts rows that the application deleted weeks ago, the cause is usually a watermark load with no delete handling (Example 2).
- **Reducing load on the source.** Reading a change log instead of polling large tables moves the work off the source database.

## Daily review

### Key takeaways

- CDC delivers changes as events (`I`, `U`, `D` with a key, a sequence and values), not as repeated full reads.
- Query-based CDC (timestamps, snapshot comparison) needs only SELECT, but misses deletes (timestamps) or intermediate changes, and loads the source.
- Log-based CDC reads the transaction log and sees every change in order, at the cost of setup and operation.
- Apply events in sequence order, upsert for `I` and `U`, delete by key for `D`, and store the highest applied sequence in the same transaction.
- Reducing a batch to the latest event per key gives the final state, not the history.

### Common mistakes

- Using a watermark on `updated_at` and never seeing deletes, so deleted rows stay in the target forever. Add soft deletes, snapshot comparison or a change feed.
- Applying events out of order (a delete before the insert that preceded it) and resurrecting a deleted row. Sort by sequence number.
- Treating an update event for an unknown key as an error. Upsert it.
- Saving the checkpoint outside the transaction that applies the events, so a crash replays or skips events. Commit both together.
- Reducing to the latest event per key and then expecting an audit trail. Keep every event when history matters.

### Revision notes

- Events: `(seq, op, key, values)`; `op` in `I`, `U`, `D`.
- Query-based: timestamp, snapshot diff, soft delete. Log-based: WAL via logical decoding (PostgreSQL).
- Apply: sort by seq; upsert `I`/`U`; delete `D`; checkpoint with the batch.
- Latest-per-key reduces to final state; keep all events for history.

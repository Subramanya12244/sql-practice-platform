## Objectives

- Write a shell script with a shebang, quoted variables, arguments, functions and a clean exit code.
- Use pipes and redirection (`|`, `>`, `>>`, `2>&1`) to build small pipelines and write a log file.
- Make a script fail loudly with `set -euo pipefail` and clean up with `trap`.
- Read and write the five-field cron syntax, and check an expression with a Python function that expands and validates it.

## Understand

### What a shell script is

A **shell** is the program that reads the commands you type in a terminal; Bash is the most common one. A **shell script** is a text file of such commands that the shell runs from top to bottom. Data engineers use scripts as the glue around the real work: they fetch a file, run a Python job, check that the output exists and write one line to a log. The first line of a script is the **shebang**, for example `#!/usr/bin/env bash`, which tells the system which program should run the file. To run a script directly you give it execute permission with `chmod +x etl.sh` and call `./etl.sh`; the permissions themselves are the topic of the next day. Without execute permission you can still run it as `bash etl.sh`.

### Variables, quoting and arguments

A variable is set with `name=value` with no spaces around `=` and read with `$name`. Always put the reference in double quotes, `"$name"`, because the shell splits an unquoted value at spaces: a file named `my data.csv` becomes two arguments and the command fails with a confusing "No such file" message. Arguments arrive as `$1`, `$2` and so on; `"${1:?usage: etl.sh FILE}"` stops the script with a message when the first argument is missing. Command output is captured with `$(command)`. Single quotes keep the text exactly as written, while double quotes still expand variables.

### Exit codes decide success

Every command ends with an **exit code**, a number from 0 to 255. Zero means success and anything else means failure; `$?` holds the code of the last command. `if`, `&&` and `||` all test the exit code: `a && b` runs `b` only if `a` succeeded and `a || b` runs `b` only if `a` failed. A script exits with the code of its last command unless you write `exit 3`. Schedulers and orchestrators (cron wrappers, Airflow, CI) read this one number, so a script that prints "failed" but exits 0 is reported as a success. That is the most expensive scripting mistake in data work.

### Failing loudly: set -euo pipefail

By default Bash carries on after a failed command. Three options change that. `set -e` exits when a command fails. `set -u` treats an unset variable as an error, which turns a typo such as `$ouput_dir` into a stop instead of an empty string (and an `rm -rf "$dir/"` that deletes the wrong place). `set -o pipefail` makes a pipeline fail when any stage fails; without it the exit code of `a | b` is the code of `b` alone, so `failing_extract | sort` looks successful. A common misconception is that `set -e` catches everything: it does not apply inside conditions such as `if cmd` or `cmd || other`, so test critical steps explicitly. `trap 'command' EXIT` registers cleanup that runs however the script ends, including after a failure.

### Pipes, redirection and logs

A **pipe** `a | b` feeds the standard output of `a` into the standard input of `b`, so small tools combine: `cut` selects columns, `sort` orders lines, `uniq -c` counts runs of equal lines, `awk` computes. Every process has stdout (stream 1) and stderr (stream 2). `>` writes stdout to a file and replaces it, `>>` appends, `2>&1` sends stderr to the same place as stdout. A job's log is normally `job.sh >> job.log 2>&1`; forgetting `2>&1` leaves the error messages in the terminal, or lost when no terminal exists. Use `>>` for logs: a single `>` erases yesterday's history.

### cron schedules

**cron** is the scheduler that runs commands at set times; the table of jobs is the **crontab**. A line has five time fields and then the command: minute (0 to 59), hour (0 to 23), day of month (1 to 31), month (1 to 12), day of week (0 to 7, where 0 and 7 are Sunday). In a field `*` means every value, `a,b` a list, `a-b` a range and `*/n` every n-th value. So `30 2 * * 1-5` is 02:30 on Monday to Friday. When both day of month and day of week are restricted, the standard cron rule is OR: `0 0 13 * 5` runs on the 13th and on every Friday, not only on Friday the 13th. cron starts jobs with a minimal environment and a different working directory, so use absolute paths, set what you need inside the script, and redirect output to a log. Cron schedules use the server's time zone unless the system is configured otherwise, so state the zone in the job's documentation.

### Why it matters

Scripts and cron are the oldest scheduler stack and still run many nightly loads. Understanding exit codes and the cron fields is also the base for Airflow later in this phase: a task fails when its command exits non-zero, and Airflow's own schedule strings use the same five-field syntax.

## Syntax and key functions

```text
#!/usr/bin/env bash
set -euo pipefail
name="value"              # assignment, no spaces
result=$(command)         # capture stdout
command1 | command2       # pipe
command >> file 2>&1      # append stdout and stderr
if [ "$x" -lt 2 ]; then ...; fi
trap 'cleanup' EXIT
```

```text
# minute hour day-of-month month day-of-week  command
30 2 * * 1-5 /opt/jobs/etl.sh >> /var/log/etl.log 2>&1
```

| Tool | What it does |
|---|---|
| `chmod +x file` | Adds execute permission. |
| `$?` | Exit code of the last command. |
| `set -euo pipefail` | Stop on error, on unset variables and on failing pipeline stages. |
| `trap 'cmd' EXIT` | Runs `cmd` when the script ends, however it ends. |
| `cut -d, -f1` | Selects the first comma-separated column. |
| `sort`, `uniq -c` | Orders lines; counts groups of equal adjacent lines. |
| `awk -F, '...'` | Per-line computation with a delimiter. |
| `tail -n +2` | Skips the header line. |
| `>`, `>>`, `2>&1` | Replace, append, merge stderr into stdout. |

## Learn by example

### Example 1: A script with arguments and an exit code

The script checks that the file has at least two lines (a header and one row). It exits with 3 and a message on stderr when it does not. The `|| echo` form is used below so that the shell running the whole example is not stopped by the failure.

```bash run
mkdir work && cd work
cat > etl.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
input="${1:?usage: etl.sh FILE}"
rows=$(wc -l < "$input" | tr -d ' ')
echo "rows=$rows"
if [ "$rows" -lt 2 ]; then
  echo "too few rows" >&2
  exit 3
fi
echo "ok"
EOF
chmod +x etl.sh
printf 'id,amount\n1,10\n2,20\n' > good.csv
printf 'id,amount\n' > empty.csv
./etl.sh good.csv
echo "exit=$?"
./etl.sh empty.csv 2>/dev/null || echo "exit=$?"
./etl.sh 2>/dev/null || echo "exit=$?"
```

```output
rows=3
ok
exit=0
rows=1
exit=3
exit=1
```

Three runs, three outcomes. The good file gives exit 0. The empty file prints its row count, then exits 3 through the explicit `exit 3`. Calling the script without an argument fails inside the `${1:?...}` expansion with exit 1 (the message went to stderr, which the example discards). The caller sees only the code, which is why the code must be right.

### Example 2: Pipes and a log file

The first pipeline counts rows per region by `cut`, `sort` and `uniq -c`, and `awk` reorders the columns because the spacing of `uniq -c` differs between systems. The second sums amounts with `awk`. The last part writes to a log with `>>` and shows that stderr joins it through `2>&1`.

```bash run
mkdir work && cd work
cat > sales.csv <<'EOF'
region,amount
north,10
south,5
north,7
east,3
south,9
EOF
tail -n +2 sales.csv | cut -d, -f1 | sort | uniq -c | awk '{print $2, $1}'
echo "---"
tail -n +2 sales.csv | awk -F, '{t[$1] += $2} END {for (r in t) print r, t[r]}' | sort
echo "---"
run() { echo "start"; echo "warning: skipped 1 row" >&2; echo "end"; }
run >> run.log 2>&1
run >> run.log 2>&1
wc -l < run.log | tr -d ' '
head -n 3 run.log
```

```output
east 1
north 2
south 2
---
east 3
north 17
south 14
---
6
start
warning: skipped 1 row
end
```

The counts are east 1, north 2, south 2, and the sums are east 3, north 17, south 14. The function was run twice and appended both times, so the log has six lines; the warning is in the log because stderr was merged. Replacing `>>` with `>` would leave only three lines.

### Example 3: Why pipefail matters

Both pipelines have a failing first stage and a succeeding last stage.

```bash run
false | true
echo "without pipefail: $?"
set -o pipefail
rc=0
false | true || rc=$?
echo "with pipefail: $rc"
( set -u; echo "value: $undefined_name" ) 2>/dev/null || echo "unset variable stopped the subshell with $?"
```

```output
without pipefail: 0
with pipefail: 1
unset variable stopped the subshell with 1
```

Without `pipefail` the pipeline reports 0 because only the last stage counts, so a broken extract would be hidden. With it, the pipeline reports the failure code 1. The third line shows `set -u` stopping at an undefined variable.

### Example 4: Cleanup with trap

The script creates a temporary directory, registers cleanup on `EXIT`, works, then fails. The cleanup message still appears and the exit code is that of the failing command.

```bash run
mkdir work && cd work
cat > job.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"; echo "cleaned up"' EXIT
echo "working in a temporary directory"
printf 'a\nb\n' > "$tmp/x"
wc -l < "$tmp/x" | tr -d ' '
false
echo "never printed"
EOF
bash job.sh || echo "job exit=$?"
```

```output
working in a temporary directory
2
cleaned up
job exit=1
```

The line after `false` never runs because of `set -e`, yet the trap fires, so the temporary directory is removed. The `job exit=1` line is what a scheduler would record.

### Example 5: Expand and validate a cron expression in Python

cron cannot run in the browser, so this function does the same job as cron's parser: it expands each field into the list of allowed values and rejects invalid ones. It also implements the OR rule for day of month and day of week, and treats weekday 7 as Sunday. The function is deterministic, so the output is the same on every machine.

```python run
from datetime import datetime

FIELDS = [("minute", 0, 59), ("hour", 0, 23), ("day", 1, 31), ("month", 1, 12), ("weekday", 0, 7)]


def expand_field(text, lo, hi):
    values = set()
    for part in text.split(","):
        step = 1
        if "/" in part:
            part, step_text = part.split("/", 1)
            if not step_text.isdigit() or int(step_text) < 1:
                raise ValueError(f"bad step {step_text!r}")
            step = int(step_text)
            if part != "*" and "-" not in part:
                raise ValueError(f"a step needs * or a range, got {part!r}")
        if part == "*":
            first, last = lo, hi
        elif "-" in part:
            low_text, high_text = part.split("-", 1)
            if not (low_text.isdigit() and high_text.isdigit()):
                raise ValueError(f"bad range {part!r}")
            first, last = int(low_text), int(high_text)
        elif part.isdigit():
            first = last = int(part)
        else:
            raise ValueError(f"bad value {part!r}")
        if first < lo or last > hi or first > last:
            raise ValueError(f"{part!r} is outside {lo}-{hi}")
        values.update(range(first, last + 1, step))
    return sorted(values)


def parse_cron(expression):
    parts = expression.split()
    if len(parts) != 5:
        raise ValueError(f"expected 5 fields, got {len(parts)}")
    parsed = {}
    for text, (name, lo, hi) in zip(parts, FIELDS):
        values = expand_field(text, lo, hi)
        if name == "weekday":
            values = sorted({v % 7 for v in values})
        parsed[name] = values
    parsed["day_any"] = parts[2] == "*"
    parsed["weekday_any"] = parts[4] == "*"
    return parsed


def matches(expression, when):
    c = parse_cron(expression)
    weekday = (when.weekday() + 1) % 7
    day_ok = when.day in c["day"]
    weekday_ok = weekday in c["weekday"]
    if c["day_any"] or c["weekday_any"]:
        date_ok = day_ok and weekday_ok
    else:
        date_ok = day_ok or weekday_ok
    return when.minute in c["minute"] and when.hour in c["hour"] and when.month in c["month"] and date_ok


print(expand_field("*/15", 0, 59))
print(parse_cron("30 2 * * 1-5")["weekday"])
print(matches("30 2 * * 1-5", datetime(2025, 3, 3, 2, 30)))
print(matches("30 2 * * 1-5", datetime(2025, 3, 2, 2, 30)))
print(matches("0 0 13 * 5", datetime(2025, 6, 13, 0, 0)), matches("0 0 13 * 5", datetime(2025, 6, 20, 0, 0)), matches("0 0 13 * 5", datetime(2025, 6, 14, 0, 0)))
for bad in ["61 * * * *", "* * * *", "*/0 * * * *", "a-b * * * *"]:
    try:
        parse_cron(bad)
    except ValueError as error:
        print(bad, "->", error)
```

```output
[0, 15, 30, 45]
[1, 2, 3, 4, 5]
True
False
True True False
61 * * * * -> '61' is outside 0-59
* * * * -> expected 5 fields, got 4
*/0 * * * * -> bad step '0'
a-b * * * * -> bad range 'a-b'
```

The first line lists the four minutes of `*/15`. `30 2 * * 1-5` matches Monday 3 March 2025 but not Sunday 2 March. The expression `0 0 13 * 5` matches both the 13th (a Friday in June 2025) and 20 June (another Friday), and not Saturday the 14th, which proves the OR rule. The four bad expressions are rejected with a reason, which is what a crontab linter does.

## Real-world applications

- A nightly load runs `etl.sh` from cron with `>> etl.log 2>&1`; the script ends with the exit code of the load so the monitoring wrapper can alert on a non-zero code (Examples 1 and 4).
- A data check pipeline counts rows per group with `cut | sort | uniq -c` on a fresh extract before the database load starts (Example 2).
- A crontab linter in a CI job parses every schedule with a function like Example 5, so an invalid line is rejected before it reaches the server.

## Daily review

### Key takeaways

- A script's value to a scheduler is its exit code: 0 success, non-zero failure.
- Start scripts with `set -euo pipefail`, quote every variable, and clean up with `trap`.
- `>>` appends, `2>&1` merges errors into the log, and a pipe passes stdout along.
- A cron line has five time fields then the command; day of month and day of week combine with OR when both are restricted.

### Common mistakes

- Leaving a variable unquoted. Symptom: a path with a space splits into two arguments. Fix: use `"$var"`.
- Forgetting `pipefail`. Symptom: a pipeline reports success although the first stage failed. Fix: set it at the top.
- Using `>` for a log. Symptom: only the last run is in the file. Fix: use `>>`.
- Relying on cron's environment. Symptom: the job works in the terminal and fails from cron with "command not found". Fix: use absolute paths and set variables inside the script.

### Revision notes

- `$?` is the last exit code; `&&` runs on success, `||` on failure.
- `set -euo pipefail`; `trap 'cmd' EXIT`.
- cron fields: minute hour day month weekday; `*/n`, `a-b`, `a,b`; weekday 0 and 7 are Sunday.

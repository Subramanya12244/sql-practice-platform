## Objectives

- Compute a running total with `SUM(...) OVER (ORDER BY ...)` and restart it per group with `PARTITION BY`.
- Explain the default window frame and how it changes the result when the sort column has ties.
- Write explicit frames with `ROWS BETWEEN ... AND ...` to build moving averages and centred averages.
- Choose between `ROWS` and `RANGE` for a given task.

## Understand

### Adding ORDER BY changes what an aggregate sees

On day 49 `SUM(x) OVER ()` and `SUM(x) OVER (PARTITION BY g)` gave every row in the window the same total. Add an `ORDER BY` inside `OVER` and the aggregate changes behaviour: each row now sees only the rows from the start of the partition up to itself. `SUM(revenue) OVER (ORDER BY month)` is therefore a **running total** (also called a cumulative sum): row 1 shows the first month, row 2 the first two months added up, row 3 the first three and so on.

The part of the partition that a row can see is called its **window frame**. The `ORDER BY` decides which rows are "earlier", and the frame decides how many of them are included. With an `ORDER BY` and no frame clause, PostgreSQL uses the default frame `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`: from the first row of the partition up to the current row, including the rows that tie with the current row.

### Running totals per group

A running total usually restarts for each entity: a customer's cumulative spend, a year's cumulative revenue. Add `PARTITION BY`. The window is then split into groups first, sorted inside each group, and the running total restarts at the first row of every group. Example 2 restarts a revenue running total each year.

### Frame clauses

You can state the frame yourself:

`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`

This frame contains the current row and the two rows before it, so at most three rows. The bounds are `UNBOUNDED PRECEDING` (the first row of the partition), `n PRECEDING`, `CURRENT ROW`, `n FOLLOWING` and `UNBOUNDED FOLLOWING` (the last row). A frame is always written from the earlier bound to the later one. Frames let the same aggregate function answer different questions: `SUM` over an unbounded frame is a running total, `AVG` over three rows is a moving average, `AVG` over one row before and one after is a centred average.

A **moving average** (or rolling average) smooths a series by averaging the last few values. Near the start of the partition the frame has fewer rows than requested. With `2 PRECEDING` the first row averages one value and the second averages two. Decide whether such incomplete windows should be shown, or hidden by comparing the frame's `COUNT(*)` with the expected size.

### ROWS versus RANGE

`ROWS` counts physical rows: "the two rows before this one". `RANGE` works with values of the sort column: it includes all rows whose sort value is equal (peers) to the current row's value, and for the bound `CURRENT ROW` it means "all peers of the current row". That is why the default frame is `RANGE`: two orders on the same date both see the full total of that date, so they show the same running total. With `ROWS` each row has its own total, and the order among tied rows decides who comes first.

Example 3 shows the difference on real data. For a running total of money, many analysts prefer `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` with a unique `ORDER BY` (a tie-breaker column), because every row gets a distinct, repeatable total. `RANGE` is the right tool when ties should be treated as one moment in time, for example "total up to and including this date". Numeric offsets in `RANGE`, such as `RANGE BETWEEN 7 PRECEDING AND CURRENT ROW`, need a single numeric or date-like sort column and are not needed today.

### Without ORDER BY, no running behaviour

If `OVER` has no `ORDER BY`, the frame is the whole partition and the result is the same on every row. A frame clause with no `ORDER BY` is not meaningful, because "preceding" has no definition.

### Common misconception

Learners often believe `SUM() OVER (ORDER BY x)` is "just the sum, sorted". It is a different calculation from `SUM() OVER ()`, because the `ORDER BY` activates the default frame. A second misconception is that a moving average over three rows is an average over three days. It is three rows. If a date is missing, the three rows span more than three days (as in day 51, months without data produce no row).

### Why it matters

Cumulative revenue against a target, year-to-date figures, rolling seven-day averages that smooth noise and a customer's balance after each transaction all rely on frames. They replace self-joins and correlated subqueries that are slower and harder to read.

## Syntax and key functions

```sql-syntax
aggregate(expression) OVER (
  [PARTITION BY group_column]
  ORDER BY sort_column
  [ROWS | RANGE BETWEEN frame_start AND frame_end]
)
```

```sql-syntax
frame_start / frame_end:
  UNBOUNDED PRECEDING | n PRECEDING | CURRENT ROW | n FOLLOWING | UNBOUNDED FOLLOWING
```

| Expression | Meaning |
|---|---|
| `SUM(x) OVER (ORDER BY t)` | Running total with the default frame (ties share a total) |
| `SUM(x) OVER (ORDER BY t, id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` | Running total, one distinct value per row |
| `AVG(x) OVER (ORDER BY t ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` | Moving average of the last three rows |
| `AVG(x) OVER (ORDER BY t ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING)` | Centred average of three rows |
| `COUNT(*) OVER (... ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` | Number of rows actually in the frame |

## Learn by example

### Example 1: a running total of monthly revenue

First a CTE aggregates revenue by month. Then `SUM(revenue) OVER (ORDER BY month)` adds the months one by one. The last column is the share of the final total reached so far, using an unordered window `OVER ()` for the grand total. Only six months are shown.

```sql run
WITH monthly AS (
  SELECT date_trunc('month', o.order_date)::date AS month,
         ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 2) AS revenue
  FROM orders AS o
  JOIN order_details AS od ON od.order_id = o.order_id
  GROUP BY 1
)
SELECT month, revenue,
       SUM(revenue) OVER (ORDER BY month) AS running_revenue,
       ROUND(100.0 * SUM(revenue) OVER (ORDER BY month) / SUM(revenue) OVER (), 1) AS pct_of_total
FROM monthly
ORDER BY month
LIMIT 6;
```

```output
month | revenue | running_revenue | pct_of_total
1996-01-01 | 5217.41 | 5217.41 | 3.8
1996-04-01 | 18574.06 | 23791.47 | 17.2
1996-07-01 | 19336.35 | 43127.82 | 31.2
1996-10-01 | 9197.44 | 52325.26 | 37.8
1997-02-01 | 7450.80 | 59776.06 | 43.2
1997-05-01 | 3460.08 | 63236.14 | 45.7
```

### Example 2: restart the total each year

`PARTITION BY` on the year restarts the cumulative sum when the year changes. The `EXTRACT` function returns the year as a number. In the output the running total of 1997 begins again at the first 1997 month.

```sql run
WITH monthly AS (
  SELECT date_trunc('month', o.order_date)::date AS month,
         ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 2) AS revenue
  FROM orders AS o
  JOIN order_details AS od ON od.order_id = o.order_id
  GROUP BY 1
)
SELECT month, revenue,
       SUM(revenue) OVER (PARTITION BY EXTRACT(YEAR FROM month) ORDER BY month) AS year_to_date
FROM monthly
ORDER BY month
LIMIT 8;
```

```output
month | revenue | year_to_date
1996-01-01 | 5217.41 | 5217.41
1996-04-01 | 18574.06 | 23791.47
1996-07-01 | 19336.35 | 43127.82
1996-10-01 | 9197.44 | 52325.26
1997-02-01 | 7450.80 | 7450.80
1997-05-01 | 3460.08 | 10910.88
1997-08-01 | 17801.84 | 28712.72
1997-11-01 | 11346.05 | 40058.77
```

### Example 3: RANGE (default) versus ROWS on ties

Orders 10248 and 10332 are both dated 1996-01-01. With the default `RANGE` frame both rows show the total of the whole date (212.57). With `ROWS` and a tie-breaker each row has its own total, 129.69 for the first and 212.57 for the second. The same happens on 1996-01-13.

```sql run
SELECT order_id, order_date, freight,
       SUM(freight) OVER (ORDER BY order_date) AS range_total,
       SUM(freight) OVER (ORDER BY order_date, order_id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS rows_total
FROM orders
ORDER BY order_date, order_id
LIMIT 6;
```

```output
order_id | order_date | freight | range_total | rows_total
10248 | 1996-01-01 | 129.69 | 212.57 | 129.69
10332 | 1996-01-01 | 82.88 | 212.57 | 212.57
10308 | 1996-01-05 | 197.96 | 410.53 | 410.53
10284 | 1996-01-09 | 166.73 | 577.26 | 577.26
10260 | 1996-01-13 | 10.17 | 786.67 | 587.43
10344 | 1996-01-13 | 199.24 | 786.67 | 786.67
```

### Example 4: a moving average and the frame size

`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` averages the current month and the two rows before it. The `frame_rows` column counts the rows really in the frame: the first two months have fewer than three, so their averages are based on less data. The `WINDOW w AS (...)` clause names the window once so that both functions can say `OVER w`. It is optional and only saves typing.

```sql run
WITH monthly AS (
  SELECT date_trunc('month', o.order_date)::date AS month,
         ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 2) AS revenue
  FROM orders AS o
  JOIN order_details AS od ON od.order_id = o.order_id
  GROUP BY 1
)
SELECT month, revenue,
       ROUND(AVG(revenue) OVER w, 2) AS moving_avg_3,
       COUNT(*) OVER w AS frame_rows
FROM monthly
WINDOW w AS (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)
ORDER BY month
LIMIT 5;
```

```output
month | revenue | moving_avg_3 | frame_rows
1996-01-01 | 5217.41 | 5217.41 | 1
1996-04-01 | 18574.06 | 11895.74 | 2
1996-07-01 | 19336.35 | 14375.94 | 3
1996-10-01 | 9197.44 | 15702.62 | 3
1997-02-01 | 7450.80 | 11994.86 | 3
```

### Example 5: a centred average and a whole-partition frame

`1 PRECEDING AND 1 FOLLOWING` takes the neighbours on both sides, so it needs rows after the current one. The last column uses the frame `UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`, the whole partition, to show the largest monthly revenue next to every row.

```sql run
WITH monthly AS (
  SELECT date_trunc('month', o.order_date)::date AS month,
         ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 2) AS revenue
  FROM orders AS o
  JOIN order_details AS od ON od.order_id = o.order_id
  GROUP BY 1
)
SELECT month, revenue,
       ROUND(AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING), 2) AS centred_avg,
       MAX(revenue) OVER (ORDER BY month ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS best_month_revenue
FROM monthly
ORDER BY month
LIMIT 4;
```

```output
month | revenue | centred_avg | best_month_revenue
1996-01-01 | 5217.41 | 11895.74 | 19336.35
1996-04-01 | 18574.06 | 14375.94 | 19336.35
1996-07-01 | 19336.35 | 15702.62 | 19336.35
1996-10-01 | 9197.44 | 11994.86 | 19336.35
```

### Example 6: running spend per customer

A realistic combination: per-customer cumulative order value. The CTE totals each order, the window sums the totals in date order for each customer, and `ROWS` with `order_id` as tie-breaker gives each order a distinct figure.

```sql run
WITH order_totals AS (
  SELECT o.customer_id, o.order_id, o.order_date,
         ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 2) AS order_value
  FROM orders AS o
  JOIN order_details AS od ON od.order_id = o.order_id
  GROUP BY o.customer_id, o.order_id, o.order_date
)
SELECT customer_id, order_id, order_date, order_value,
       SUM(order_value) OVER (PARTITION BY customer_id ORDER BY order_date, order_id
                              ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cumulative_spend
FROM order_totals
WHERE customer_id IN ('ALFKI', 'BONAP', 'BERGS')
ORDER BY customer_id, order_date, order_id;
```

```output

ALFKI | 10248 | 1996-01-01 | 324.00 | 324.00
ALFKI | 10339 | 1997-08-08 | 4379.69 | 4703.69
BERGS | 10252 | 1997-05-05 | 469.30 | 469.30
BERGS | 10343 | 1998-12-12 | 1462.59 | 1931.89
```

## Real-world applications

**Year-to-date and cumulative reporting.** Examples 1 and 2 are the form of year-to-date revenue, cumulative signups and progress against a target. Dividing by the final total (Example 1) gives the percent of target reached.

**Smoothing noisy series.** Example 4 is a rolling average. Operations teams use a seven-day average of tickets or orders so that weekday effects do not hide the trend.

**Balances and inventory.** A running sum of signed amounts (deposits positive, withdrawals negative) gives the balance after each transaction, and Example 6 has the same shape for customer spend.

**Pareto and share-of-total analysis.** A running total of sorted values divided by the grand total shows how few customers or products produce 80 percent of revenue.

## Daily review

### Key takeaways

- With `ORDER BY` in `OVER`, an aggregate becomes cumulative: each row sees the partition from its start up to itself.
- `PARTITION BY` restarts the cumulative result for each group.
- The default frame with an `ORDER BY` is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`; ties are peers and share a value.
- `ROWS` counts physical rows; add a unique tie-breaker to the `ORDER BY` for a repeatable running total.
- A moving average needs an explicit frame such as `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`, and the first rows have smaller frames.

### Common mistakes

- Forgetting the frame and not noticing that tied rows share the same running total. Use `ROWS` and a unique `ORDER BY` when each row needs its own total.
- Leaving out `ORDER BY`: `SUM(x) OVER ()` returns the grand total on every row instead of a running total.
- Treating "three rows" as "three days" when dates are missing.
- Writing the frame bounds the wrong way round, for example `BETWEEN CURRENT ROW AND 2 PRECEDING`. PostgreSQL reports `frame starting from current row cannot have preceding rows`.
- Presenting the first incomplete moving averages as if they were full-size averages.
- Forgetting `PARTITION BY`, so the running total of one customer continues into the next.

### Revision notes

- Running total: `SUM(x) OVER (ORDER BY t, id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`.
- Moving average of three: `AVG(x) OVER (ORDER BY t ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)`.
- `RANGE` groups ties together; `ROWS` does not.
- No `ORDER BY` in `OVER` means the whole-partition frame.

## Objectives

- Load a cleaned DataFrame into a database table with `to_sql`, and explain what `if_exists="append"` and `if_exists="replace"` do to the table's constraints.
- Create the target table yourself with a primary key and `CHECK` constraints, and show a constraint rejecting a bad batch.
- Wrap a load in a transaction so that a failing batch leaves the table unchanged.
- Make a load idempotent, so that running it twice gives the same table, with an upsert (`ON CONFLICT`) or a delete-and-insert of one batch.

## Understand

### From a clean DataFrame to a trusted table

Day 160 ended with a clean DataFrame and a designed target table. Loading looks like the easy part: one call and the rows are in. It is where most data-loading incidents happen, because loading is the step that changes a shared, permanent thing. A load that is run twice by accident duplicates a month of revenue. A load that fails halfway leaves half a file in the table. A convenience function that recreates the table silently removes the rules you designed. This day is about doing the load so that none of these can happen, and about proving afterwards that it worked.

### `to_sql` and what it does for you

`DataFrame.to_sql(name, con, if_exists=..., index=False)` writes the rows of a DataFrame into a table. The argument `if_exists` decides what happens when the table already exists: `"fail"` (the default) raises an error, `"append"` adds the rows to the existing table, and `"replace"` **drops the table and creates it again** from the DataFrame. The recreated table gets generic column types guessed from the data and **no primary key and no constraints**. That is the main trap: after a `replace` load the table has the right rows and none of the rules from Day 160, and every later bad row is accepted. The professional pattern is to create the table yourself with the SQL you designed and then load with `if_exists="append"`. Set `index=False` so that the DataFrame's row labels do not become an extra column. In this lesson `to_sql` writes through a `sqlite3` connection, which pandas supports directly; with PostgreSQL you give `to_sql` a SQLAlchemy engine instead (for example `create_engine("postgresql+psycopg://...")`), and the logic is the same. For large volumes PostgreSQL has a faster path, `COPY`, which streams rows to the server.

### Constraints are the safety net

A **constraint** is a rule the database enforces on every write: `PRIMARY KEY` (unique and not empty), `NOT NULL`, `CHECK (amount_eur >= 0)`, `UNIQUE`, `FOREIGN KEY`. When a row breaks a rule, the database refuses it and raises an error (in Python `sqlite3.IntegrityError`, in `psycopg` a subclass of `psycopg.errors.IntegrityError` such as `UniqueViolation`). An error on a load is good news: it means a bad row did not get in. The cleaning checks of Day 160 find problems early and give readable reports, and the constraints are the last line of defence behind them. You want both.

### Transactions: all or nothing

A **transaction** groups several statements so that they either all take effect or none do. A load inside a transaction that fails on row 900 leaves the table exactly as it was. Without one, the first 899 rows may already be saved and the table is in an unknown state. In `sqlite3`, `with conn:` commits when the block ends normally and rolls back when an exception leaves it; the connection stays open and still has to be closed. With `psycopg 3`, `with psycopg.connect(...) as conn:` commits at the end of the block, rolls back on an exception, and also closes the connection.

### Idempotent loads

A load is **idempotent** when running it twice (or ten times) leaves the table in the same state as running it once. Scheduled jobs are retried, people click twice, and a failed run is simply started again, so every load must be idempotent. There are two common ways to get there.

**Upsert** ("update or insert"): `INSERT ... ON CONFLICT (key) DO UPDATE SET ...` inserts a new row and updates the existing row when the key already exists. PostgreSQL has had this syntax since version 9.5, and SQLite supports the same form from version 3.24. Inside `DO UPDATE`, the name `excluded` (written `EXCLUDED` in PostgreSQL) refers to the row that was proposed for insertion. The variant `ON CONFLICT DO NOTHING` skips rows whose key exists. An upsert needs a unique key on the conflict columns, which is another reason to create the table yourself.

**Replace one batch**: inside one transaction, delete the rows that belong to the batch (for example one month) and insert the batch again. This is the right choice when rows can disappear from the source, since an upsert never deletes: if order 1002 was cancelled and no longer appears in the new file, the upsert leaves the old 1002 in the table, while delete-and-insert removes it.

### Checks after the load

Finish every load with checks that compare what you meant to load with what is in the table: the number of rows, the total of the key measure, and the set of keys. If the counts agree but the totals differ, a value was changed; if the totals agree but the counts differ, rows were dropped and made up for by others. Checks such as these are the beginning of the source-to-target reconciliation of Day 162.

### Why it matters, and the misconception

A reporting table is only as trustworthy as its last load. The misconception is that "no error" means "correct". `to_sql(if_exists="replace")` never errors, and it silently throws away your constraints. A load that runs twice without errors can silently double the revenue. Silence is not evidence; checks are.

## Syntax and key functions

```python
df.to_sql("sales_orders", conn, if_exists="append", index=False)   # table must exist, constraints stay
```

```sql-syntax
INSERT INTO <table> (<columns>) VALUES (<placeholders>)
ON CONFLICT (<key columns>) DO UPDATE SET <column> = excluded.<column>, ...;

INSERT INTO <table> (<columns>) VALUES (<placeholders>)
ON CONFLICT (<key columns>) DO NOTHING;
```

The same load with `psycopg` and PostgreSQL (needs a server, not run here). `executemany` sends the upsert once per row; `COPY` streams the rows and is much faster for large files:

```python
import os
import psycopg

UPSERT = (
    "INSERT INTO sales_orders (order_id, customer_name, order_date, amount_eur, status) "
    "VALUES (%s, %s, %s, %s, %s) "
    "ON CONFLICT (order_id) DO UPDATE SET customer_name = EXCLUDED.customer_name, "
    "order_date = EXCLUDED.order_date, amount_eur = EXCLUDED.amount_eur, status = EXCLUDED.status"
)

with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
    with conn.cursor() as cur:
        cur.executemany(UPSERT, rows)          # rows: a list of tuples

with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
    with conn.cursor() as cur:
        with cur.copy("COPY sales_orders (order_id, customer_name, order_date, amount_eur, status) FROM STDIN") as copy:
            for row in rows:
                copy.write_row(row)
```

| Function or clause | Returns or does |
|---|---|
| `df.to_sql(name, con, if_exists, index, dtype, chunksize)` | Writes the rows; `fail`, `append` or `replace` (drops and recreates the table). |
| `with conn:` (`sqlite3`) | Commits on success, rolls back on an exception. |
| `conn.executemany(sql, rows)` | Runs one statement for each row. |
| `df.itertuples(index=False, name=None)` | Plain tuples, ready for `executemany`. |
| `ON CONFLICT (key) DO UPDATE SET c = excluded.c` | Upsert: update when the key exists. |
| `ON CONFLICT DO NOTHING` | Skip rows whose key exists. |
| `sqlite3.IntegrityError` | Raised when a constraint rejects a write. |

## Learn by example

The Python examples use `sqlite3` in memory as a stand-in for PostgreSQL. It differs from PostgreSQL in these ways that matter here: placeholders are `?` (PostgreSQL drivers use `%s`), dates are stored as text, types are loose (a text value is accepted in a numeric column), and `to_sql` can use the raw connection (with PostgreSQL it takes a SQLAlchemy engine). The upsert syntax is the same in both. Dates are converted to text such as `2025-01-05` in the DataFrame so that SQLite stores them the way PostgreSQL's `date` would print them.

### Example 1: Append keeps the rules, replace removes them

The table is created by hand with a primary key and `CHECK` constraints. Appending the same three rows twice is refused, and the table keeps three rows. Then `if_exists="replace"` is shown: afterwards the primary key is gone and a negative amount is accepted.

```python run
import sqlite3
import pandas as pd

DDL = """CREATE TABLE sales_orders (
    order_id INTEGER PRIMARY KEY, customer_name TEXT NOT NULL, order_date TEXT,
    amount_eur REAL CHECK (amount_eur >= 0),
    status TEXT NOT NULL CHECK (status IN ('paid', 'refunded', 'failed')))"""
df = pd.DataFrame({
    "order_id": [1001, 1002, 1003],
    "customer_name": ["Ana Silva", "Ben Okafor", "Cy Tran"],
    "order_date": ["2025-01-05", "2025-01-07", "2025-01-09"],
    "amount_eur": [1200.5, 310.0, 89.9],
    "status": ["paid", "paid", "failed"],
})
count = lambda c: c.execute("SELECT COUNT(*) FROM sales_orders").fetchone()[0]

conn = sqlite3.connect(":memory:")
conn.execute(DDL)
df.to_sql("sales_orders", conn, if_exists="append", index=False)
print("after first append:", count(conn))
try:
    df.to_sql("sales_orders", conn, if_exists="append", index=False)
except Exception as e:
    print("second append refused:", "UNIQUE constraint failed" in str(e))
print("rows still:", count(conn))

df.to_sql("sales_orders", conn, if_exists="replace", index=False)
pk = [r[1] for r in conn.execute("PRAGMA table_info(sales_orders)") if r[5]]
print("primary key columns after replace:", pk)
conn.execute("INSERT INTO sales_orders VALUES (1001, 'Dup', '2025-02-01', -5.0, 'bogus')")
print("rows after bad insert:", count(conn))
conn.close()
```

```output
after first append: 3
second append refused: True
rows still: 3
primary key columns after replace: []
rows after bad insert: 4
```

After `replace` the table accepted a duplicate key, a negative amount and a status outside the list. Nothing raised an error, which is exactly why you create the table yourself and append.

### Example 2: A failed batch leaves nothing behind

The batch has a duplicate key as its second row. Inside `with conn:` the first row is inserted, the second raises `IntegrityError`, and the block rolls back, so the first row disappears too.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE sales_orders (order_id INTEGER PRIMARY KEY, customer_name TEXT NOT NULL, amount_eur REAL CHECK (amount_eur >= 0))")
conn.executemany("INSERT INTO sales_orders VALUES (?, ?, ?)", [(1001, "Ana Silva", 1200.5), (1002, "Ben Okafor", 310.0)])
conn.commit()

batch = [(1004, "Dee Park", 50.0), (1002, "Duplicate", 1.0), (1005, "Eli Roth", 75.0)]
try:
    with conn:
        conn.executemany("INSERT INTO sales_orders VALUES (?, ?, ?)", batch)
except sqlite3.IntegrityError as e:
    print("batch rejected:", e)
print("rows:", conn.execute("SELECT COUNT(*) FROM sales_orders").fetchone()[0])
print("1004 present:", conn.execute("SELECT COUNT(*) FROM sales_orders WHERE order_id = 1004").fetchone()[0] == 1)
conn.close()
```

```output
batch rejected: UNIQUE constraint failed: sales_orders.order_id
rows: 2
1004 present: False
```

Row 1004 was valid and was inserted before the error, but the rollback removed it: the table is exactly as before the batch.

### Example 3: An idempotent load with an upsert

The `load` function upserts every row in one transaction. Running it twice gives three rows. A corrected file (order 1002 now 320.0, plus a new order 1004) updates one row and adds one, with no duplicates.

```python run
import sqlite3
import pandas as pd

UPSERT = """INSERT INTO sales_orders (order_id, customer_name, amount_eur, status)
VALUES (?, ?, ?, ?)
ON CONFLICT (order_id) DO UPDATE SET
    customer_name = excluded.customer_name, amount_eur = excluded.amount_eur, status = excluded.status"""

def load(conn, frame):
    with conn:
        conn.executemany(UPSERT, frame.itertuples(index=False, name=None))

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE sales_orders (order_id INTEGER PRIMARY KEY, customer_name TEXT NOT NULL, amount_eur REAL, status TEXT NOT NULL)")
first = pd.DataFrame({"order_id": [1001, 1002, 1003], "customer_name": ["Ana Silva", "Ben Okafor", "Cy Tran"],
                      "amount_eur": [1200.5, 310.0, 89.9], "status": ["paid", "paid", "failed"]})
load(conn, first)
load(conn, first)
print("after running twice:", conn.execute("SELECT COUNT(*) FROM sales_orders").fetchone()[0])

corrected = pd.DataFrame({"order_id": [1002, 1004], "customer_name": ["Ben Okafor", "Dee Park"],
                          "amount_eur": [320.0, 50.0], "status": ["refunded", "paid"]})
load(conn, corrected)
for row in conn.execute("SELECT order_id, amount_eur, status FROM sales_orders ORDER BY order_id"):
    print(row)
conn.close()
```

```output
after running twice: 3
(1001, 1200.5, 'paid')
(1002, 320.0, 'refunded')
(1003, 89.9, 'failed')
(1004, 50.0, 'paid')
```

Order 1002 was updated to its new amount and status, order 1004 was added, and orders 1001 and 1003 were untouched. The second run of the same file changed nothing: that is idempotence.

### Example 4: When rows can disappear, replace the batch

The new January file no longer contains order 1002 (it was cancelled at the source). An upsert keeps the stale row; deleting the month's rows and inserting the file again, inside one transaction, removes it.

```python run
import sqlite3

def fresh():
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE sales_orders (order_id INTEGER PRIMARY KEY, order_date TEXT NOT NULL, amount_eur REAL)")
    conn.executemany("INSERT INTO sales_orders VALUES (?, ?, ?)", [(1001, "2025-01-05", 100.0), (1002, "2025-01-07", 50.0), (1010, "2025-02-03", 70.0)])
    conn.commit()
    return conn

january = [(1001, "2025-01-05", 100.0), (1003, "2025-01-20", 25.0)]

conn = fresh()
with conn:
    conn.executemany("INSERT INTO sales_orders VALUES (?, ?, ?) ON CONFLICT (order_id) DO UPDATE SET order_date = excluded.order_date, amount_eur = excluded.amount_eur", january)
print("upsert:", [r[0] for r in conn.execute("SELECT order_id FROM sales_orders ORDER BY order_id")])
conn.close()

conn = fresh()
with conn:
    conn.execute("DELETE FROM sales_orders WHERE order_date >= ? AND order_date < ?", ("2025-01-01", "2025-02-01"))
    conn.executemany("INSERT INTO sales_orders VALUES (?, ?, ?)", january)
print("replace batch:", [r[0] for r in conn.execute("SELECT order_id FROM sales_orders ORDER BY order_id")])
conn.close()
```

```output
upsert: [1001, 1002, 1003, 1010]
replace batch: [1001, 1003, 1010]
```

The upsert left the cancelled order 1002 in January. The batch replacement removed it and did not touch February's order 1010. Choose by asking whether rows can vanish from the source.

### Example 5: Upsert in PostgreSQL

The same upsert in PostgreSQL syntax on the PostgreSQL-compatible browser database. The `WHERE` after `DO UPDATE` skips rows whose values did not change, so an unchanged row is not rewritten. `IS DISTINCT FROM` is a comparison that treats `NULL` as a value, and `numeric(12,2)` keeps the money exact.

```sql run
DROP TABLE IF EXISTS ld_orders;
CREATE TABLE ld_orders (
    order_id      integer PRIMARY KEY,
    customer_name text NOT NULL,
    amount_eur    numeric(12,2) CHECK (amount_eur >= 0),
    status        text NOT NULL
);
INSERT INTO ld_orders VALUES (1001, 'Ana Silva', 1200.50, 'paid'), (1002, 'Ben Okafor', 310, 'paid');
INSERT INTO ld_orders (order_id, customer_name, amount_eur, status)
VALUES (1002, 'Ben Okafor', 320, 'refunded'), (1003, 'Cy Tran', 89.90, 'failed')
ON CONFLICT (order_id) DO UPDATE
SET amount_eur = EXCLUDED.amount_eur, status = EXCLUDED.status
WHERE ld_orders.amount_eur IS DISTINCT FROM EXCLUDED.amount_eur
   OR ld_orders.status IS DISTINCT FROM EXCLUDED.status;
SELECT order_id, customer_name, amount_eur, status FROM ld_orders ORDER BY order_id;
```

```output
order_id | customer_name | amount_eur | status
1001 | Ana Silva | 1200.50 | paid
1002 | Ben Okafor | 320.00 | refunded
1003 | Cy Tran | 89.90 | failed
```

The conflicting row 1002 was updated, 1003 was inserted and 1001 was not touched. With `psycopg`, the same statement is sent with `%s` placeholders and a list of rows.

### Example 6: Verify the load

After the load, a function compares the DataFrame with the table on row count, total and key set and prints a report. The second call shows what the report looks like when a row was lost.

```python run
import sqlite3
import pandas as pd

df = pd.DataFrame({"order_id": [1001, 1002, 1003], "amount_eur": [1200.5, 310.0, 89.9]})

def verify(conn, frame):
    n = conn.execute("SELECT COUNT(*) FROM sales_orders").fetchone()[0]
    total = conn.execute("SELECT COALESCE(SUM(amount_eur), 0) FROM sales_orders").fetchone()[0]
    keys = {r[0] for r in conn.execute("SELECT order_id FROM sales_orders")}
    missing = sorted(set(frame["order_id"]) - keys)
    checks = {
        "row count": n == len(frame),
        "total": round(total, 2) == round(float(frame["amount_eur"].sum()), 2),
        "no missing keys": not missing,
    }
    for name, ok in checks.items():
        print(f"{name}: {'OK' if ok else 'FAIL'}")
    if missing:
        print("missing keys:", missing)
    return all(checks.values())

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE sales_orders (order_id INTEGER PRIMARY KEY, amount_eur REAL)")
df.to_sql("sales_orders", conn, if_exists="append", index=False)
print("all good:", verify(conn, df))
conn.execute("DELETE FROM sales_orders WHERE order_id = 1003")
conn.commit()
print("all good:", verify(conn, df))
conn.close()
```

```output
row count: OK
total: OK
no missing keys: OK
all good: True
row count: FAIL
total: FAIL
no missing keys: FAIL
missing keys: [1003]
all good: False
```

The second report shows three failures at once, and the missing key names the lost row. These three comparisons are the core of Day 162.

## Real-world applications

- **Monthly file loads**: the finance workbook is cleaned (Day 160), loaded with an upsert and verified, so the job can be retried after a failure without duplicating a month (Examples 3 and 6).
- **Restating a period**: when the source corrects last month's file, the loader deletes and reinserts that month in one transaction, and cancelled rows disappear (Example 4).
- **Protecting a shared reporting table**: primary key and `CHECK` constraints reject bad rows from any script, including future ones written by other people (Examples 1 and 5).
- **Large loads**: for millions of rows a team switches from `executemany` to `COPY`, keeping the same table, transaction and checks (Syntax section).

## Daily review

### Key takeaways

- Create the target table yourself and load with `if_exists="append"`; `replace` drops the table and its constraints.
- Constraints turn bad rows into errors; a transaction makes a batch all-or-nothing.
- A load is idempotent when a second run changes nothing: use an upsert on a unique key, or replace one batch in a transaction.
- An upsert never deletes rows that vanished from the source.
- Verify after loading: row count, total, keys.

### Common mistakes

- Using `to_sql(if_exists="replace")` on a table with rules. The data loads without error and the primary key and checks are gone; create the table first and append.
- Loading without a transaction. A failure at row 900 leaves 899 rows saved; wrap the load in `with conn:`.
- Running an append twice. The first run succeeds, the second hits `UNIQUE constraint failed` (or, without a key, silently duplicates); use an upsert.
- Forgetting `index=False`. The DataFrame index appears as an extra `index` column and the insert fails or the table gets an unexpected column.
- Forgetting a unique key and then writing `ON CONFLICT (order_id)`. PostgreSQL raises "there is no unique or exclusion constraint matching the ON CONFLICT specification".

### Revision notes

- `df.to_sql(name, con, if_exists="append", index=False)`.
- `with conn:` commits or rolls back; close the connection yourself in `sqlite3`.
- `INSERT ... ON CONFLICT (key) DO UPDATE SET c = excluded.c`; PostgreSQL writes `EXCLUDED`, `%s` placeholders.
- Replace a batch: `DELETE` the batch and `INSERT` it again in one transaction.
- Post-load checks: count, sum, keys.

## Objectives

- Choose, for a given step of an analysis, whether to do it in SQL (inside the database) or in pandas (in Python memory), and justify the choice.
- Show that the same aggregation gives the same answer in both, and measure how much data each approach moves.
- Push filters, column selection and aggregation into the query so that only the needed data reaches Python.
- Process a result in chunks when it is too large to hold at once.
- Name the trade-offs that data volume, reuse, readability and team skills add to the decision.

## Understand

### The question behind the choice

Most analysis tasks can be done both ways. You can group and sum in a SQL query or load the rows and use `groupby` in pandas. The result is often identical, so the decision is about everything around the result: how much data has to move, where the computation runs, who must be able to read and maintain the work, and whether it can be repeated. This lesson gives a framework for deciding, and measures what is measurable (rows and cells moved) instead of quoting rules without evidence. It builds on Day 157, which showed how to run queries from Python.

### Where the work runs, and what moves

A database is built to scan, filter, join and aggregate large tables near where the data is stored, often with **indexes** that skip most rows. When you send a query, the heavy work happens there and only the **result** travels to your program. When you instead run `SELECT *` and aggregate in pandas, all the rows travel over the connection, are converted to Python objects and are held in the memory of your machine. If the table has fifty million rows and you need five totals, you moved fifty million rows to get five numbers. The first idea is therefore simple: **move the computation to the data when the result is much smaller than the input**. Filters and aggregations shrink data, so they usually belong in SQL. A join between two large tables also belongs in SQL, since the database can use indexes, whereas the pandas version needs both tables in memory.

### When pandas is the better place

Pandas does things that are awkward or impossible in SQL: arbitrary Python logic on each row (parsing messy text, calling a library), statistical modelling, plotting, reshaping that you will explore interactively, and exploring a small result many times without asking the database again. Once the data has been reduced to something that fits comfortably in memory, an interactive exploration in pandas is quicker to write and change than a series of queries. Pandas also lets you work on data that is not in a database at all (a CSV file or the response of an API). A good workflow therefore splits the job: SQL for **select, filter, join and aggregate**, pandas for **shape, model, check and present**.

### Data volume and memory

Pandas needs the whole DataFrame in memory, and the memory used is often a multiple of the size of the raw data, because of Python objects and intermediate copies. There is no universal row count at which pandas "stops working": it depends on the number and types of columns, the operations and the machine. Measure instead of guessing, for example with the number of rows times columns that your query returns, and with a test on a sample. When the data does not fit, there are three routes: reduce it in the database (aggregate, filter, select columns, sample); process it in **chunks**, reading a fixed number of rows at a time and combining partial results; or move to a tool built for larger data (Day 158 does not teach these tools, and later days discuss when a distributed engine is needed).

### Trade-offs beyond speed

Speed is only one of the factors, and an unmeasured claim that one is faster is a poor reason. Other factors:

- **Single source of truth.** A metric defined in a view or a query in the database is shared by every tool; the same logic copied into several notebooks drifts apart.
- **Reproducibility.** A query with fixed filters and a pinned dataset is easy to rerun; a notebook that edits a DataFrame step by step with hidden state is not, unless it is written as a clean script.
- **Readability and skills.** Choose the language your team can maintain. A long chain of CTEs may be harder for some readers than a few lines of pandas, and the reverse is also true.
- **Load on a shared database.** A heavy query on a production system affects other users; analysts often work on a replica or at quiet times.
- **Dialect and portability.** SQL differs between databases, while pandas code does not care where the data came from.
- **Cost of error.** In pandas it is easy to lose rows silently in a merge or convert types without noticing, and in SQL it is easy to multiply rows in a join. Check row counts after either.

### Why it matters, and the misconception

Wrong placement of the work makes reports slow, pipelines fragile and databases overloaded, and it makes analysis hard to repeat. The misconception is that SQL is for "simple" work and pandas for "real" analysis, or the other way round. Both are complete for aggregation and the choice should follow the questions above. A second misconception is that fetching everything first is safer because you can always filter later. It is expensive in transfer and memory, and it can leak data that the analysis never needed.

## Syntax and key functions

```python
# push work down: select columns, filter, aggregate in the query
df = pd.read_sql_query(
    "SELECT region, SUM(amount) AS total FROM sales WHERE amount > ? GROUP BY region ORDER BY region",
    conn, params=(40,))

# process in chunks and combine partial results
total = 0.0
for chunk in pd.read_sql_query("SELECT amount FROM sales", conn, chunksize=5000):
    total += chunk["amount"].sum()
```

| Function | Returns or does |
|---|---|
| `pd.read_sql_query(sql, conn, params=...)` | A DataFrame from a query. |
| `pd.read_sql_query(..., chunksize=n)` | An iterator of DataFrames of up to `n` rows. |
| `df.to_sql(name, conn, index=False)` | Writes a DataFrame to a table. |
| `df.groupby(key)[col].agg(...)` | The pandas version of `GROUP BY`. |
| `df.shape` | (rows, columns): a measure of the data moved. |
| `SUM(x) OVER (PARTITION BY g)` | A group total attached to every row, like `transform("sum")`. |

## Learn by example

### Example 1: The same aggregation, two places

A table of 20,000 sales rows is created in an in-memory `sqlite3` database. The totals per region are computed in SQL and in pandas after loading everything. The results are compared, and so are the amounts of data that reached Python.

```python run
import sqlite3
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
n = 20000
regions = np.array(["central", "east", "north", "south", "west"])
df = pd.DataFrame({
    "region": regions[rng.integers(0, 5, n)],
    "product": rng.integers(1, 41, n),
    "amount": rng.normal(50, 15, n).round(2),
})
conn = sqlite3.connect(":memory:")
df.to_sql("sales", conn, index=False)
in_sql = pd.read_sql_query("SELECT region, ROUND(SUM(amount), 2) AS total FROM sales GROUP BY region ORDER BY region", conn)
everything = pd.read_sql_query("SELECT * FROM sales", conn)
in_pandas = everything.groupby("region", as_index=False)["amount"].sum().rename(columns={"amount": "total"})
in_pandas["total"] = in_pandas["total"].round(2)
print("same result:", bool(np.allclose(in_sql["total"], in_pandas["total"])))
print("rows moved: SQL", in_sql.shape[0], "| pandas", everything.shape[0])
print("cells moved: SQL", in_sql.shape[0] * in_sql.shape[1], "| pandas", everything.shape[0] * everything.shape[1])
print(in_sql.to_string(index=False))
conn.close()
```

```output
same result: True
rows moved: SQL 5 | pandas 20000
cells moved: SQL 10 | pandas 60000
 region     total
central 201568.44
   east 202756.18
  north 193589.97
  south 198262.97
   west 200944.35
```

The answers are identical, but the SQL route moved five rows instead of twenty thousand. For a table with a hundred times more rows the SQL result would still have five rows.

### Example 2: Push the filter and the columns down

Only paid amounts above 60 in two regions are needed. Loading everything and filtering in pandas moves all rows and columns. A query with `WHERE` and a column list moves only what is used.

```python run
import sqlite3
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
n = 20000
regions = np.array(["central", "east", "north", "south", "west"])
df = pd.DataFrame({
    "region": regions[rng.integers(0, 5, n)],
    "product": rng.integers(1, 41, n),
    "amount": rng.normal(50, 15, n).round(2),
})
conn = sqlite3.connect(":memory:")
df.to_sql("sales", conn, index=False)
wide = pd.read_sql_query("SELECT * FROM sales", conn)
kept = wide[(wide["amount"] > 60) & (wide["region"].isin(["north", "south"]))]["amount"]
narrow = pd.read_sql_query("SELECT amount FROM sales WHERE amount > ? AND region IN (?, ?)", conn, params=(60, "north", "south"))
print("same count and sum:", len(kept) == len(narrow), round(float(kept.sum()), 2) == round(float(narrow["amount"].sum()), 2))
print("cells moved: load all", wide.shape[0] * wide.shape[1], "| pushed down", narrow.shape[0] * narrow.shape[1])
conn.close()
```

```output
same count and sum: True True
cells moved: load all 60000 | pushed down 1978
```

Selecting only the column and rows that are needed reduces the cells moved by about 97 percent. It also keeps unneeded columns (which may contain sensitive data) out of the notebook.

### Example 3: Both tools can do it: percent of total within a group

Each sale's share of its region's total is computed with a SQL window function and with pandas `transform`. The first rows are shown and all rows are compared. Windows in SQL keep the full row count; so does `transform`, so the result is as large as the input and the question of where to run it is open.

```python run
import sqlite3
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
n = 20000
regions = np.array(["central", "east", "north", "south", "west"])
df = pd.DataFrame({
    "region": regions[rng.integers(0, 5, n)],
    "product": rng.integers(1, 41, n),
    "amount": rng.normal(50, 15, n).round(2),
})
conn = sqlite3.connect(":memory:")
df.to_sql("sales", conn, index=False)
q = pd.read_sql_query(
    "SELECT rowid AS id, region, amount, amount * 100.0 / SUM(amount) OVER (PARTITION BY region) AS pct FROM sales ORDER BY rowid", conn)
d = pd.read_sql_query("SELECT rowid AS id, region, amount FROM sales ORDER BY rowid", conn)
d["pct"] = d["amount"] * 100 / d.groupby("region")["amount"].transform("sum")
print(q.head(5).round(4).to_string(index=False))
print("agree on all rows:", bool(np.allclose(q["pct"], d["pct"])))
print("result rows: SQL window", len(q), "| pandas", len(d))
conn.close()
```

```output
 id region  amount    pct
  1   west   34.05 0.0169
  2  south   57.30 0.0289
  3  south   46.95 0.0237
  4   west   41.94 0.0209
  5  north   59.94 0.0310
agree on all rows: True
result rows: SQL window 20000 | pandas 20000
```

The values agree. Because the output has one row per input row, there is no reduction of data volume, and the choice rests on the other factors: where the next step runs and what the team can read.

### Example 4: Chunks when the result is large

A result that is too big to hold is read in chunks of 5,000 rows, and the partial sums are combined. The answer must equal the sum of the whole column. Only one chunk is in memory at a time.

```python run
import sqlite3
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
n = 20000
regions = np.array(["central", "east", "north", "south", "west"])
df = pd.DataFrame({
    "region": regions[rng.integers(0, 5, n)],
    "product": rng.integers(1, 41, n),
    "amount": rng.normal(50, 15, n).round(2),
})
conn = sqlite3.connect(":memory:")
df.to_sql("sales", conn, index=False)
total, rows, chunks = 0.0, 0, 0
for chunk in pd.read_sql_query("SELECT amount FROM sales ORDER BY rowid", conn, chunksize=5000):
    chunks += 1
    rows += len(chunk)
    total += float(chunk["amount"].sum())
print("chunks:", chunks, "| rows:", rows)
print("sum in chunks:", round(total, 2), "| sum in the database:", round(conn.execute("SELECT SUM(amount) FROM sales").fetchone()[0], 2))
conn.close()
```

```output
chunks: 4 | rows: 20000
sum in chunks: 997121.91 | sum in the database: 997121.91
```

Chunking works for operations that can be combined, such as sums, counts, minimums and maximums. A median cannot be computed by combining chunk medians, and an operation like that has to be pushed into the database or approximated.

### Example 5: Pushing the aggregation in PostgreSQL

On the Northwind database, the table `order_details` has a line per product per order. The query returns revenue by category: eight rows computed from the whole table. The second column shows how many order lines lie behind each category (250 in total).

```sql run
SELECT c.category_name,
       COUNT(*) AS lines,
       ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 0) AS revenue
FROM order_details od
JOIN products p ON p.product_id = od.product_id
JOIN categories c ON c.category_id = p.category_id
GROUP BY c.category_name
ORDER BY revenue DESC, c.category_name;
```

```output
category_name | lines | revenue
Beverages | 31 | 29336
Confections | 49 | 20512
Meat/Poultry | 18 | 18705
Dairy Products | 36 | 18330
Seafood | 39 | 16579
Condiments | 36 | 15177
Produce | 16 | 11841
Grains/Cereals | 25 | 7840
```

The database read all 250 order lines and joined them to two other tables, and the Python program would receive only eight rows. This is the pattern: let the database reduce the data, then continue in pandas with the small table.

## Real-world applications

- **Reporting pipelines**: a nightly script runs aggregation queries in the warehouse and loads small result tables into pandas for formatting, instead of downloading raw events.
- **Data exploration**: an analyst pulls a one-percent sample with a `WHERE` or `LIMIT` to explore in pandas, then runs the final logic on the full data in SQL.
- **Large exports**: a job reads a big table in chunks and writes each piece to a file, keeping memory flat.
- **Code review**: reviewers look for `SELECT *` followed by a filter in pandas, and push the filter into the query.

## Daily review

### Key takeaways

- Move the computation to the data when the result is much smaller than the input: filters, joins and aggregations belong in SQL.
- Use pandas for row-wise Python logic, modelling, plotting and interactive work on a reduced result.
- Measure data moved with rows and cells; there is no universal size limit for pandas.
- Chunking handles results that do not fit in memory, for operations that combine across chunks.
- Weigh reuse, reproducibility, readability, load on the database and skills, not speed alone.

### Common mistakes

- `SELECT *` followed by a filter in pandas. Everything travels first; add the `WHERE` and the column list to the query.
- Taking a median of chunk medians. It is not the overall median; combine only sums, counts, minimums and maximums, or push the work into SQL.
- Joining in SQL without checking the row count and silently multiplying rows. Compare counts before and after.
- Claiming one approach is faster without measuring on your data. Test with a sample, and report the numbers.
- Copying the same business logic into many notebooks. Put shared definitions into one view or query.

### Revision notes

- Reduce in SQL (filter, join, aggregate); explore in pandas.
- `read_sql_query(..., params=...)` and `chunksize=`.
- Check the same answer both ways, and compare rows and cells moved.
- No fixed size limit: measure.

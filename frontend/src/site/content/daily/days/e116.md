## Objectives

- Split a SQL-plus-pandas job into three functions: query, transform and summarise.
- Write a query function that takes the connection and parameters and returns a typed DataFrame.
- Write transforms as pure functions that return a new frame and leave the input unchanged.
- Chain the steps with `DataFrame.pipe` and test each step on a tiny in-memory database.

## Understand

### Query, transform, summarise

Most reporting code does the same three things in the same order. It **queries** the database for the rows it needs. It **transforms** them: converts units, derives columns, drops or flags bad rows. It **summarises** them into the small table that a person or a chart reads. Day 115 decided where the heavy work belongs (filter and aggregate in SQL, finish in pandas). Today gives that decision a shape: three small functions, each with one job, an explicit input and an explicit output. A script that does all three in one long block works once; three functions can be tested, reused for another month or another status, and read by a colleague in a minute.

### The query step

The **query function** is the only place that touches the database. Its signature takes the connection and the parameters of the question, for example `query_orders(conn, status, start, end)`, and returns a DataFrame. Inside it uses a parameterised `read_sql` (Day 114), asks only for the columns the next steps need, and converts types once with `parse_dates` so that nobody downstream has to guess. Because the connection is an argument, not a global, the same function runs against the production database in a pipeline and against an in-memory `sqlite3` database in a test. The query step never formats or summarises: if the SQL starts to contain presentation logic, the step is doing too much.

### The transform step

A **transform function** takes a DataFrame and returns a DataFrame. It should be a **pure function**: the output depends only on the input and the function changes nothing outside itself. In pandas the usual trap is mutating the argument (`df["amount"] = ...` on the frame the caller passed). The caller's frame then changes behind its back, and running the transform twice gives different results. Avoid it with `df.assign(amount=df["amount_cents"] / 100)`, which returns a new frame, or by working on `df.copy()`. Keep each transform small and named for what it does (`add_amounts`, `drop_failed`), so that several can be chained and each can be tested with three rows.

### The summarise step

The **summarise function** reduces the transformed frame to the answer: `groupby` with named aggregations, sorted so the output is stable. It should not query and should not change rows; it only counts, sums and reshapes. Its output is small enough to print, chart or write to a table. Keeping the summary free of side effects is what lets a chart function (Day 118) take its result as input.

### Composing with pipe

`df.pipe(func, *args)` calls `func(df, *args)` and returns the result, which lets you read a chain from left to right: `query_orders(conn, "paid", start, end).pipe(add_amounts).pipe(summarise)`. It is only a way of writing function calls in order, nothing magical, but it makes the shape of the workflow visible: data enters, passes through named steps, and leaves as a result. A reader can comment out one step to see its effect.

### Testing the steps

Each function becomes testable because its inputs are explicit. Build a tiny in-memory `sqlite3` database with five rows whose answers you can compute by hand, call the query function and assert on the rows; hand a small DataFrame to the transform and assert on its columns; hand a transformed frame to the summary and assert on the totals. Three small tests on known inputs find most mistakes before real data does. A common misconception is that testing needs the real database; it needs rows whose expected result you know, and a database whose schema matches. Another is that a pipeline is "just a script" and cannot be organised: the cost of three functions is a few lines, and the first time someone changes the date range or the status they will be repaid.

### The contract between steps

The columns that one step returns are a contract with the next step. `add_amounts` expects `amount_cents` and promises `amount`; `summarise` expects `currency`, `order_id` and `amount`. If the query stops returning `currency`, the failure appears two steps later as a `KeyError` that names a column and not the real cause. Write the expected columns in a docstring or check them at the start of a step (`missing = {"currency"} - set(df.columns)`), and fail with a message that names the step. The symptom of an unchecked contract is an error far from its cause; the fix is a small assertion at the boundary.

### Why it matters in data work

A report or pipeline is rewritten many times: new filters, a new currency, a different period. Small reusable functions turn those changes into a changed argument or one changed function instead of a rewrite. They also give you obvious places to log counts between steps, which Day 129 will use.

## Syntax and key functions

```python
def query_orders(conn, status, start, end):
    return pd.read_sql("SELECT ... WHERE status = ? AND created_at >= ? AND created_at < ?",
                       conn, params=(status, start, end), parse_dates=["created_at"])

def add_amounts(df):
    return df.assign(amount=df["amount_cents"] / 100)

def summarise(df):
    return df.groupby("currency", as_index=False).agg(orders=("order_id", "count"), revenue=("amount", "sum"))

result = query_orders(conn, "paid", "2025-03-01", "2025-04-01").pipe(add_amounts).pipe(summarise)
```

| Item | What it does or returns |
|---|---|
| `df.assign(col=expr)` | Returns a new DataFrame with the column added; the original is untouched. |
| `df.copy()` | An independent copy that is safe to modify. |
| `df.pipe(f, *args)` | Returns `f(df, *args)`; chains steps left to right. |
| `groupby(...).agg(name=(col, func))` | Named aggregations; returns one row per group. |
| `as_index=False` | Keeps the group keys as ordinary columns. |
| `sort_values(by, kind="stable")` | A deterministic order for ties. |

## Learn by example

### Example 1: The query function

The function takes the connection and the question's parameters. The `created_at` text column is compared as ISO text, which sorts like dates, and converted to datetimes once. Only five rows are printed.

```python run
import sqlite3
import pandas as pd
import math

def make_orders():
    statuses = ["paid", "paid", "paid", "refunded", "paid", "failed"]
    rows = []
    for i in range(1, 121):
        rows.append({
            "order_id": i,
            "customer_id": 1 + (i * 5) % 17,
            "amount_cents": 500 + (i * 37) % 89 * 50,
            "currency": "EUR" if i % 5 else "USD",
            "status": statuses[i % 6],
            "created_at": f"2025-03-{1 + (i * 13) % 28:02d}T{(i * 3) % 24:02d}:{(i * 11) % 60:02d}:00Z",
        })
    return rows

ORDERS = make_orders()

def get_orders(page, page_size, api_key):
    """Stand-in for GET /orders?page=N&page_size=P, header X-Api-Key."""
    if api_key != "demo-key":
        return {"error": "unauthorized"}
    total_pages = math.ceil(len(ORDERS) / page_size)
    start = (page - 1) * page_size
    return {"data": ORDERS[start:start + page_size], "page": page, "total_pages": total_pages}


def make_conn():
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT)""")
    conn.executemany("INSERT INTO orders VALUES (:order_id,:customer_id,:amount_cents,:currency,:status,:created_at)", ORDERS)
    return conn

def query_orders(conn, status, start, end):
    sql = ("SELECT order_id, customer_id, amount_cents, currency, status, created_at FROM orders "
           "WHERE status = ? AND created_at >= ? AND created_at < ? ORDER BY order_id")
    return pd.read_sql(sql, conn, params=(status, start, end), parse_dates=["created_at"])

conn = make_conn()
df = query_orders(conn, "paid", "2025-03-01", "2025-03-08")
print(df.shape)
print(df.head(5).to_string(index=False))
```

### Example 3: The summary

The summary groups the transformed rows by currency with named aggregations and a stable sort. It takes a frame and returns a frame, so it can be tested without a database.

```python run
import pandas as pd

def summarise(df):
    return (df.groupby("currency", as_index=False)
              .agg(orders=("order_id", "count"), revenue=("amount", "sum"))
              .sort_values("currency", kind="stable")
              .reset_index(drop=True))

frame = pd.DataFrame({"order_id": [1, 2, 3, 4], "currency": ["EUR", "USD", "EUR", "EUR"], "amount": [10.0, 5.5, 20.0, 4.5]})
print(summarise(frame).to_string(index=False))
```

```output
currency  orders  revenue
     EUR       3     34.5
     USD       1      5.5
```

### Example 5: Testing the steps on a tiny database

Five rows with answers computable by hand make the tests. The asserts run silently when the functions are right; the last line prints only after they all pass.

```python run
import sqlite3
import pandas as pd

def query_orders(conn, status):
    return pd.read_sql("SELECT order_id, amount_cents, currency FROM orders WHERE status = ? ORDER BY order_id", conn, params=(status,))

def add_amounts(df):
    return df.assign(amount=df["amount_cents"] / 100)

def summarise(df):
    return df.groupby("currency", as_index=False).agg(orders=("order_id", "count"), revenue=("amount", "sum"))

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders (order_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT)")
conn.executemany("INSERT INTO orders VALUES (?,?,?,?)",
                 [(1, 1000, "EUR", "paid"), (2, 250, "EUR", "paid"), (3, 400, "USD", "paid"), (4, 999, "EUR", "failed"), (5, 100, "USD", "refunded")])

raw = query_orders(conn, "paid")
assert len(raw) == 3
before = list(raw.columns)
added = add_amounts(raw)
assert list(raw.columns) == before and "amount" in added.columns
out = summarise(added).set_index("currency")
assert out.loc["EUR", "revenue"] == 12.5 and out.loc["USD", "orders"] == 1
print("all steps pass")
```

```output
all steps pass
```
## Real-world applications

- **Monthly and per-segment reports.** The same three functions run for a different month, status or currency by changing the arguments, which replaces the copy-and-edit scripts that grow in many teams.
- **Testing before a deploy.** Example 5's tiny database lets CI check the SQL and the transform on known rows without touching production data.
- **Logging between steps.** Because each step returns a frame, the pipeline can log `len(df)` after each one (Day 129 builds on this) and find the step where rows disappear.
- **Handing a result to charts.** The summary frame is the input of a chart function (Day 118), so the report code never mixes database access with drawing.

## Daily review

### Key takeaways

- Query, transform and summarise are three functions with explicit inputs and outputs.
- The query function takes the connection and parameters, returns a typed frame, and is the only code that touches the database.
- Transforms are pure: they return a new frame and do not change their argument.
- `pipe` writes the workflow in reading order; a small database of known rows tests each step.

### Common mistakes

- Mutating the caller's frame inside a transform (`df["x"] = ...`), which changes data behind the caller's back and makes a second run different. Use `assign` or `copy()`.
- Opening a database connection inside the function with a hard-coded path, so tests cannot substitute a test database. Pass `conn` in.
- Mixing steps: a summary that also queries, so it cannot be tested without a database.
- Forgetting `as_index=False` and then wondering why `currency` is the index and not a column.
- Unsorted results in the summary, so printed output changes order between runs. Sort explicitly.

### Revision notes

- `query(conn, params) -> df`, `transform(df) -> df`, `summarise(df) -> df`.
- `df.assign(...)` does not mutate; `df.pipe(f)` equals `f(df)`.
- Test with a five-row `sqlite3` table whose answers you can compute.
- Sort the final output.

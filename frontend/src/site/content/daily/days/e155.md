## Understand

### Why containers

A data engineer needs the same database on a laptop, in a test job and on a server, without installing and configuring PostgreSQL each time. A **container** is a running process that is isolated from the rest of the machine: it has its own file system, its own network address and its own process list, but it shares the host's operating-system kernel, so it starts in seconds. An **image** is the read-only template a container is created from: the program, its libraries and default settings. One image can start many containers, in the same way one class creates many objects. Images are stored in a **registry** such as Docker Hub and are named `name:tag`, for example `postgres:16`. The tag selects a version. Docker is not installed in this course environment, so every Docker command below is shown, explained and never run here; the examples that run are Python models of the same ideas.

### The docker run command

This command starts a PostgreSQL 16 container:

```text
docker run --name pg -e POSTGRES_PASSWORD=change-me -p 5432:5432 -v pgdata:/var/lib/postgresql/data -d postgres:16
```

`docker run` creates and starts a container from an image. `--name pg` gives it a name that later commands use. `-e POSTGRES_PASSWORD=change-me` sets an **environment variable** inside the container; the official PostgreSQL image refuses to initialise a database without a password (or an explicit trust setting), so the container stops at start if it is missing. Optional variables `POSTGRES_USER` and `POSTGRES_DB` name the first user and database; the user defaults to `postgres` and the database to the user's name. `-p 5432:5432` publishes a **port**: the number before the colon is on your machine (the host) and the number after it is inside the container, so `-p 5433:5432` lets you reach the container's 5432 at host port 5433. `-v pgdata:/var/lib/postgresql/data` mounts a **named volume** `pgdata` at the directory where this image stores its data (for version 16 images). `-d` runs the container detached, in the background. `postgres:16` is the image and tag. Everyday commands are `docker ps` (running containers), `docker logs pg`, `docker exec -it pg psql -U postgres` (open a SQL shell inside it), `docker stop pg` and `docker rm pg`.

### Volumes and persistence

A container's own writable layer is **ephemeral**: `docker rm pg` deletes it and the database files with it. A **volume** is storage that Docker manages outside any one container. When a volume is mounted at the data directory, `docker rm pg` removes the container but `pgdata` stays, and a new container started with the same `-v pgdata:...` finds the database again. The misconception is that stopping a container loses data; stopping keeps the container's files. Removing it is what loses them, unless a volume holds the data. A related note: the image runs the `.sql` files placed in `/docker-entrypoint-initdb.d` only when it initialises an empty data directory, so changing those files has no effect on an existing volume.

### Docker Compose

Long `docker run` commands are hard to read and repeat. **Docker Compose** describes one or more services in a YAML file and starts them with one command:

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: change-me
      POSTGRES_DB: warehouse
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5
volumes:
  pgdata:
```

`services:` lists the containers; `db` is the service name, which other services in the same file use as a host name. `image` is the same image and tag as before. `environment` is the `-e` options as a mapping. `ports` is the `-p` options; the mapping is quoted so YAML does not read `5432:5432` as a number. `volumes` under the service is the `-v` option, and the top-level `volumes:` block declares the named volume `pgdata`; a service that mounts an undeclared name makes Compose stop with an error. `healthcheck` runs `pg_isready`, a tool shipped with PostgreSQL, every five seconds, so that other services can wait until the database accepts connections. `docker compose up -d` starts everything and `docker compose down` removes the containers and network but keeps named volumes (adding `-v` deletes them too).

### Habits that prevent trouble

Pin the tag. `postgres` with no tag means `postgres:latest`, which can change under you and break the data directory format between major versions. Keep secrets out of files you commit: use an `.env` file that is ignored by version control, or a secrets manager. Publish only the ports you need, because a published port is reachable from outside the container. Two services cannot publish the same host port, so a second PostgreSQL on 5432 fails to start; map it to another host port.

### Why it matters

Reproducible local databases make pipeline tests meaningful, and a compose file is documentation of how the stack is wired. Airflow's official quick-start also runs from a compose file, which the next days build on. The Python model below captures the same rules as checks you can run in a pull request before anything starts.

## Syntax and key functions

```text
docker run [options] IMAGE[:TAG] [command]
docker compose up -d      # start the services in docker-compose.yml
docker compose down       # stop and remove; named volumes stay
```

| Option or key | Meaning |
|---|---|
| `--name` | Name of the container. |
| `-e KEY=value`, `environment:` | Environment variable inside the container. |
| `-p HOST:CONTAINER`, `ports:` | Publish a container port on a host port. |
| `-v NAME:PATH`, `volumes:` | Mount a volume at a path in the container. |
| `-d` | Run in the background. |
| `image:` | Image and tag. |
| `healthcheck:` | A command that reports whether the service is ready. |

## Learn by example

### Example 1: Splitting an image reference and a port mapping

Image names carry a tag, and a missing tag means `latest`. A port mapping is `host:container`. These helpers are used by the rest of the day.

```python run
import re


def split_image(reference):
    name, _, tag = reference.partition(":")
    return name, tag or "latest"


def split_port(mapping):
    match = re.fullmatch(r"(\d+):(\d+)", mapping)
    if not match:
        raise ValueError(f"bad port mapping {mapping!r}")
    return int(match.group(1)), int(match.group(2))


print(split_image("postgres:16"))
print(split_image("postgres"))
print(split_port("5433:5432"))
try:
    split_port("5432")
except ValueError as error:
    print(error)
```

```output
('postgres', '16')
('postgres', 'latest')
(5433, 5432)
bad port mapping '5432'
```

`postgres:16` splits into the name and tag `16`; `postgres` gets the tag `latest`, which is the unpinned case the validator will flag. The mapping `5433:5432` publishes container port 5432 on host port 5433, and a single number is rejected.

### Example 2: Validate a compose-style configuration

PyYAML is not available in the browser, so the compose file is written as the equivalent Python dictionary. `validate_compose` returns a sorted list of problems; an empty list means the configuration passes these rules. The rules are a teaching subset, not Compose's full validation.

```python run
import re


def split_image(reference):
    name, _, tag = reference.partition(":")
    return name, tag or "latest"


def validate_compose(cfg):
    problems = []
    services = cfg.get("services") or {}
    if not services:
        return ["no services defined"]
    declared = set(cfg.get("volumes") or {})
    host_ports = {}
    for name in sorted(services):
        svc = services[name]
        if "image" not in svc:
            problems.append(f"{name}: image missing")
        else:
            image, tag = split_image(svc["image"])
            if tag == "latest":
                problems.append(f"{name}: pin the image tag")
            if image == "postgres" and "POSTGRES_PASSWORD" not in (svc.get("environment") or {}):
                problems.append(f"{name}: POSTGRES_PASSWORD missing")
        for mapping in svc.get("ports", []):
            match = re.fullmatch(r"(\d+):(\d+)", mapping)
            if not match or not all(1 <= int(g) <= 65535 for g in match.groups()):
                problems.append(f"{name}: bad port mapping {mapping!r}")
                continue
            host = int(match.group(1))
            if host in host_ports:
                problems.append(f"host port {host} used by {host_ports[host]} and {name}")
            else:
                host_ports[host] = name
        for volume in svc.get("volumes", []):
            source = volume.split(":")[0]
            named = "/" not in source and not source.startswith(".")
            if named and source not in declared:
                problems.append(f"{name}: volume {source} not declared")
    return problems


good = {
    "services": {"db": {"image": "postgres:16", "environment": {"POSTGRES_PASSWORD": "x"}, "ports": ["5432:5432"], "volumes": ["pgdata:/var/lib/postgresql/data"]}},
    "volumes": {"pgdata": {}},
}
bad = {
    "services": {
        "db": {"image": "postgres", "ports": ["5432:5432"], "volumes": ["pgdata:/var/lib/postgresql/data"]},
        "adminer": {"image": "adminer:4", "ports": ["5432:8080", "80"]},
    }
}
print(validate_compose(good))
for problem in validate_compose(bad):
    print(problem)
print(validate_compose({}))
```

```output
[]
adminer: bad port mapping '80'
db: pin the image tag
db: POSTGRES_PASSWORD missing
host port 5432 used by adminer and db
db: volume pgdata not declared
['no services defined']
```

The good configuration returns no problems. The bad one has five: a port mapping without a host side, an unpinned image, a missing `POSTGRES_PASSWORD`, two services wanting host port 5432, and a volume that was never declared. Each one corresponds to a real failure when you run the file with Compose.

### Example 3: A volume keeps data, a container does not

This is a model, not Docker. A container has its own files; a mounted volume has separate storage. Removing the container deletes only its own files.

```python run
volumes = {}
containers = {}


def run(name, volume=None):
    containers[name] = {"files": {}, "volume": volume}
    if volume and volume not in volumes:
        volumes[volume] = {}


def write(name, key, value):
    c = containers[name]
    target = volumes[c["volume"]] if c["volume"] else c["files"]
    target[key] = value


def read(name, key):
    c = containers[name]
    target = volumes[c["volume"]] if c["volume"] else c["files"]
    return target.get(key)


def remove(name):
    del containers[name]


run("pg_plain")
write("pg_plain", "table", "orders")
remove("pg_plain")
run("pg_plain")
print("without volume:", read("pg_plain", "table"))

run("pg_vol", volume="pgdata")
write("pg_vol", "table", "orders")
remove("pg_vol")
run("pg_vol", volume="pgdata")
print("with volume:", read("pg_vol", "table"))
```

```output
without volume: None
with volume: orders
```

The container without a volume starts empty after being recreated, so the table is gone. The one that mounted `pgdata` finds `orders` again because the volume outlived the container, which is exactly why the data directory must be on a volume.

### Example 4: Build a connection string from the service

Clients connect with a URL: `postgresql://user:password@host:port/database`. The function reads the user, database and published host port from the service definition, applying the image's defaults, and masks the password for logging.

```python run
def dsn(service, host="localhost", mask=True):
    env = service.get("environment", {})
    user = env.get("POSTGRES_USER", "postgres")
    database = env.get("POSTGRES_DB", user)
    password = "***" if mask else env["POSTGRES_PASSWORD"]
    host_port = int(service["ports"][0].split(":")[0])
    return f"postgresql://{user}:{password}@{host}:{host_port}/{database}"


db = {"image": "postgres:16", "environment": {"POSTGRES_PASSWORD": "change-me", "POSTGRES_DB": "warehouse"}, "ports": ["5433:5432"]}
print(dsn(db))
print(dsn({"image": "postgres:16", "environment": {"POSTGRES_PASSWORD": "x"}, "ports": ["5432:5432"]}))
```

```output
postgresql://postgres:***@localhost:5433/warehouse
postgresql://postgres:***@localhost:5432/postgres
```

The first URL uses the published host port 5433, not the container's 5432, and the database `warehouse`. The second shows the defaults: user `postgres`, and a database named like the user. With `docker run`, the client always connects to the host side of the mapping.

- A pull-request check runs `validate_compose`-style rules over the repository's compose file to catch unpinned images and port clashes before a teammate hits them (Example 2).

## Daily review

### Key takeaways

- An image is the template; a container is a running instance; a volume holds data outside the container.
- `-p HOST:CONTAINER` publishes a port; clients use the host side.
- Put the PostgreSQL data directory on a named volume and declare the volume in compose.
- Pin tags and keep passwords out of committed files.

### Common mistakes

- Starting `postgres` without `POSTGRES_PASSWORD`. Symptom: the container exits right after start and the logs name the missing variable. Fix: set the variable.
- Connecting to the container port instead of the host port. Symptom: connection refused on 5432 when the mapping is `5433:5432`. Fix: use 5433 from the host.
- Mounting a volume name that is not declared under the top-level `volumes:`. Symptom: Compose reports an undefined volume. Fix: declare it.
- Using `docker compose down -v` casually. Symptom: the database is empty on the next start. Fix: omit `-v` unless you want to delete the data.

### Revision notes

- `docker run --name pg -e POSTGRES_PASSWORD=... -p 5432:5432 -v pgdata:/var/lib/postgresql/data -d postgres:16`.
- Compose keys: `services`, `image`, `environment`, `ports`, `volumes`, `healthcheck`, top-level `volumes`.
- `docker rm` deletes container files; a volume survives.

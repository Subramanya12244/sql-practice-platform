## Objectives

- Work through a SQL interview question in a fixed routine: clarify, state the grain, plan, write, test on edge cases, explain.
- Write the interview staples correctly: anti-join, top-N per group, second-highest value, month-over-month change and conditional aggregation.
- Name and avoid the usual traps: `NOT IN` with NULLs, joins that multiply rows, window ties, `WHERE` versus `HAVING`, integer division.
- Pace a time-boxed question and explain an answer aloud in under two minutes.

## Understand

### What a SQL interview tests

An analyst SQL interview usually has two to four questions in 30 to 45 minutes, on a small schema you see for the first time. The questions come from a short list that you have already met in the SQL phase: joins and anti-joins, aggregation with `GROUP BY` and `HAVING`, top-N per group with window functions, running totals and period-over-period change, deduplication, and conditional counting. The interviewer is not only checking that your query runs. They watch how you reduce an ambiguous request to a precise one, whether you notice traps in the data, whether you test your answer, and whether you can explain it. A correct query written in silence and abandoned at the first error scores lower than a nearly correct one that is explained, tested and repaired.

### A routine for every question

Use the same six steps each time. **Clarify**: restate the question and ask what is unclear (what counts as a customer, are ties possible, which date column, do refunds count). **Grain**: decide what one output row is (one per customer, per category, per month), because the grain tells you the `GROUP BY` and the join shape. **Plan**: say the tables you need and the join keys, and sketch the query in words before writing it. **Write**: build in small pieces, starting with the simplest join and checking it before adding filters or windows. **Test**: run on the data, look at a few rows, and test an edge case (a customer with no orders, a tie, a NULL). **Explain**: say in two sentences what the query does and what you would check at scale. Practise out loud, and with a clock: a typical budget for a medium question is two minutes to clarify and plan, eight to write and test, and a minute to explain; stop and say what you would do next if time runs out, rather than going quiet.

### The staple patterns

An **anti-join** finds rows with no match: customers with no orders. Write it with `LEFT JOIN ... WHERE right.key IS NULL` or `NOT EXISTS`. A **top-N per group** question (the best product in each category) uses `ROW_NUMBER() OVER (PARTITION BY group ORDER BY metric DESC, tiebreaker)` in a subquery or CTE and then filters `rn = 1`, because a window function cannot be filtered in the same `SELECT`'s `WHERE`. Choose `RANK` or `DENSE_RANK` instead when ties should all be kept, and say which you chose. **Second-highest** is the same idea with `DENSE_RANK() = 2`, or `MAX(x) WHERE x < (SELECT MAX(x) ...)`. **Period-over-period change** aggregates to the period first and then uses `LAG(value) OVER (ORDER BY period)`. **Conditional aggregation** counts or sums part of a group with `COUNT(*) FILTER (WHERE condition)` or `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`, which gives rates such as the share of late orders per employee in one pass.

### Traps interviewers plant

The classic is **`NOT IN` with NULLs**: if the subquery returns even one NULL, `x NOT IN (...)` is never true and returns no rows, because comparing with NULL gives unknown. Prefer `NOT EXISTS` or the `LEFT JOIN` form. Next is **join fan-out**: joining orders to order lines and then summing an order-level column (freight) counts it once per line; aggregate to the right grain first. **Ties** in rankings: `ROW_NUMBER` picks one row arbitrarily unless you add a tiebreaker, and `RANK` leaves gaps. **`WHERE` versus `HAVING`**: `WHERE` filters rows before grouping, `HAVING` filters groups after. **Integer division**: in PostgreSQL `1 / 2` is `0`; cast to `numeric` or multiply by `100.0`. **`COUNT(col)` versus `COUNT(*)`**: the first ignores NULLs. **Date boundaries**: use `>= start AND < next_day` rather than `BETWEEN` on timestamps. Naming a trap aloud before the interviewer does is one of the strongest signals you can give.

### Why it matters, and the misconception

The misconception is that interviews reward the cleverest query. They reward the clearest correct one, with its assumptions stated. A long chain of simple CTEs, each checked, beats a one-line nested expression you cannot explain. In real analyst work the same routine prevents wrong numbers: the questions you ask in an interview are the ones to ask a stakeholder. Practice therefore pays twice: speed on the staple patterns frees your attention for the clarifying questions, and a habit of reconciling your result with a second method (an anti-join written two ways, a total compared with the overall sum) is also the habit that stops wrong numbers reaching a report.

## Syntax and key functions

```sql-syntax
-- anti-join
SELECT c.id FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.id IS NULL;
SELECT c.id FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- top 1 per group
SELECT * FROM (
  SELECT g, item, metric, ROW_NUMBER() OVER (PARTITION BY g ORDER BY metric DESC, item) AS rn FROM t
) x WHERE rn = 1;

-- change versus previous period
SELECT period, value, value - LAG(value) OVER (ORDER BY period) AS change FROM monthly;

-- rate with a filtered count
SELECT g, COUNT(*) FILTER (WHERE late) * 100.0 / COUNT(*) AS late_pct FROM t GROUP BY g;
```

| Tool | Use | Watch for |
|---|---|---|
| `LEFT JOIN ... IS NULL` / `NOT EXISTS` | Rows with no match | `NOT IN` and NULLs |
| `ROW_NUMBER`, `RANK`, `DENSE_RANK` | Top-N per group, nth value | Ties, gaps |
| `LAG`, `LEAD` | Previous or next row's value | First row is NULL |
| `COUNT(*) FILTER (WHERE ...)` | Conditional counts | Denominator choice |
| `HAVING` | Filter groups | Not for row filters |
| `::numeric`, `* 100.0` | Avoid integer division | Rounding last |

## Learn by example

### Example 1: The NOT IN trap

Both queries ask for the numbers from a small list that are not in a second list. The second list contains a NULL. `NOT IN` returns nothing at all, while `NOT EXISTS` gives the expected answer. This single result is worth knowing by heart before an interview.

```sql run
WITH a(n) AS (VALUES (1), (2), (3)),
     b(n) AS (VALUES (1), (NULL))
SELECT 'not in' AS method, COUNT(*) AS rows_returned FROM a WHERE n NOT IN (SELECT n FROM b)
UNION ALL
SELECT 'not exists', COUNT(*) FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.n = a.n)
ORDER BY method
```

```output
method | rows_returned
not exists | 2
not in | 0
```

### Example 2: Anti-join on Northwind

Question: which customers have never placed an order? The grain is one row per customer. The `LEFT JOIN` keeps every customer, and the rows where the order side is NULL are the ones with no match. The routine's test step: confirm with `NOT EXISTS` that the count agrees.

```sql run
SELECT c.customer_id, c.company_name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id
LIMIT 10
```

```output
customer_id | company_name
FISSA | FISSA Fabrica Inter. Salchichas
PARIS | Paris spécialités
```

### Example 3: Top product per category

Question: the highest-revenue product in each category. Revenue is the sum of price times quantity less discount per product, so first aggregate to product, rank within category and keep rank 1. The product name is added to the `ORDER BY` of the window as a tiebreaker so the result is deterministic.

```sql run
SELECT category_name, product_name, revenue
FROM (
    SELECT c.category_name, p.product_name,
           ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 0) AS revenue,
           ROW_NUMBER() OVER (PARTITION BY c.category_name
                              ORDER BY SUM(od.unit_price * od.quantity * (1 - od.discount)) DESC, p.product_name) AS rn
    FROM order_details od
    JOIN products p ON p.product_id = od.product_id
    JOIN categories c ON c.category_id = p.category_id
    GROUP BY c.category_name, p.product_name
) ranked
WHERE rn = 1
ORDER BY category_name
LIMIT 10
```

```output
category_name | product_name | revenue
Beverages | Côte de Blaye | 17510
Condiments | Northwoods Cranberry Sauce | 3148
Confections | Sir Rodney's Marmalade | 5577
Dairy Products | Mascarpone Fabioli | 4186
Grains/Cereals | Gnocchi di nonna Alice | 2559
Meat/Poultry | Thüringer Rostbratwurst | 17438
Produce | Rössle Sauerkraut | 5497
Seafood | Gravad lax | 3125
```

### Example 4: Month-over-month change with LAG

Question: how did revenue change from one month to the next in 1997? Aggregate to months first in a CTE, then use `LAG` on the result. The first month has no previous value, so its change is NULL, which is correct and worth saying aloud.

```sql run
WITH monthly AS (
    SELECT to_char(o.order_date, 'YYYY-MM') AS month,
           ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount))::numeric, 0) AS revenue
    FROM orders o JOIN order_details od ON od.order_id = o.order_id
    WHERE o.order_date >= DATE '1997-01-01' AND o.order_date < DATE '1998-01-01'
    GROUP BY 1
)
SELECT month, revenue,
       LAG(revenue) OVER (ORDER BY month) AS previous,
       revenue - LAG(revenue) OVER (ORDER BY month) AS change
FROM monthly
ORDER BY month
LIMIT 10
```

```output
month | revenue | previous | change
1997-02 | 7451 | NULL | NULL
1997-05 | 3460 | 7451 | -3991
1997-08 | 17802 | 3460 | 14342
1997-11 | 11346 | 17802 | -6456
```

### Example 5: Conditional aggregation for a rate

Question: what share of each employee's orders shipped after the required date? One pass with a filtered count gives both numbers. The multiplication by `100.0` avoids integer division, and the denominator is every order of the employee (state that choice).

```sql run
SELECT e.last_name,
       COUNT(*) AS orders,
       COUNT(*) FILTER (WHERE o.shipped_date > o.required_date) AS late,
       ROUND(COUNT(*) FILTER (WHERE o.shipped_date > o.required_date) * 100.0 / COUNT(*), 1) AS late_pct
FROM employees e
JOIN orders o ON o.employee_id = e.employee_id
GROUP BY e.employee_id, e.last_name
ORDER BY late_pct DESC, e.last_name
LIMIT 10
```

```output
last_name | orders | late | late_pct
Davolio | 11 | 1 | 9.1
Dodsworth | 11 | 1 | 9.1
Fuller | 11 | 1 | 9.1
King | 11 | 1 | 9.1
Leverling | 11 | 1 | 9.1
Peacock | 11 | 1 | 9.1
Suyama | 22 | 2 | 9.1
Callahan | 11 | 0 | 0.0
```

### Example 6: Second-highest value, two ways

Question: what is the second-highest freight charge? `DENSE_RANK` handles ties by giving tied rows the same rank; the `MAX` of values below the maximum is the alternative with no window function. Both must agree, and a good answer says what happens when the top value is tied.

```sql run
SELECT 'dense_rank' AS method, MAX(freight) AS second_highest
FROM (SELECT freight, DENSE_RANK() OVER (ORDER BY freight DESC) AS r FROM orders) t
WHERE r = 2
UNION ALL
SELECT 'max below max', MAX(freight) FROM orders WHERE freight < (SELECT MAX(freight) FROM orders)
ORDER BY method
```

```output
method | second_highest
dense_rank | 199.24
max below max | 199.24
```

## Real-world applications

- **Stakeholder questions.** The clarify and grain steps are exactly what you ask when a manager says "top customers": top by what, over which period, and one row per what.
- **Data quality checks.** Anti-joins (Example 2) find orders without customers or customers without orders, a daily check in many data teams.
- **Performance reviews and SLAs.** Conditional aggregation (Example 5) gives rates such as late deliveries per team in one query.
- **Trend reporting.** Period-over-period change (Example 4) is the base of every monthly business review.

## Daily review

### Key takeaways

- Use the same routine: clarify, grain, plan, write in pieces, test an edge case, explain.
- Know the staples: anti-join, top-N per group, nth value, `LAG`, filtered counts.
- Prefer `NOT EXISTS` to `NOT IN` unless you know the subquery has no NULLs.
- Aggregate to the right grain before joining or windowing, and add a tiebreaker to rankings.
- Say your assumptions aloud; they are part of the answer.

### Common mistakes

- `NOT IN` against a nullable column. Symptom: zero rows. Fix: `NOT EXISTS` or filter the NULLs out.
- Filtering a window function in `WHERE`. Symptom: an error that window functions are not allowed there. Fix: wrap in a subquery or CTE and filter outside.
- Summing an order-level column after joining to order lines. Symptom: totals too high. Fix: aggregate lines first or sum in a subquery.
- Integer division in a rate. Symptom: 0 for every group. Fix: `* 100.0` or a cast.

### Revision notes

- Routine: clarify, grain, plan, write, test, explain.
- `ROW_NUMBER() OVER (PARTITION BY g ORDER BY m DESC, tie)` then `rn = 1`.
- `LAG(x) OVER (ORDER BY period)`; first row NULL.
- `COUNT(*) FILTER (WHERE ...) * 100.0 / COUNT(*)`.

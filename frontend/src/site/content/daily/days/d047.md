## Objectives

- Combine the rows of two queries with `UNION` and `UNION ALL`, and explain when duplicates are removed.
- Find the rows two queries have in common with `INTERSECT` and the rows only the first has with `EXCEPT`.
- Meet the column rules of set operators: same number of columns, compatible types, names from the first query.
- Place `ORDER BY` correctly and use parentheses to control the order of several set operators.
- Choose between a set operator, a join and a subquery for a given problem.

## Understand

### Stacking results instead of matching columns

A join (days 40 to 42) puts the columns of two tables side by side, matching rows by a key. A **set operator** does something different: it stacks the rows of two whole queries into one result, the way you could stack two lists of names on one sheet. Set operators use the vocabulary of sets: the **union** of two lists contains everything that is in either, the **intersection** contains what is in both, and the **difference** contains what is in the first but not in the second. The two queries are written in full, and the operator goes between them.

### UNION and UNION ALL

`query_1 UNION query_2` returns every row of either query and **removes duplicates**: a row that appears in both, or twice in one, is shown once. `UNION ALL` keeps every row from both queries, duplicates included, and is faster because it skips the duplicate search. In Northwind, `customers` has 91 rows and `suppliers` has 29. `UNION ALL` of their countries gives all 120 rows. `UNION` gives only the 25 different countries. Choose `UNION ALL` when you want to stack rows (and you know there are no unwanted duplicates, or you want them), and `UNION` when you want a distinct list. Using `UNION` out of habit hides duplicates you may need and costs time on big data.

### INTERSECT and EXCEPT

`query_1 INTERSECT query_2` returns the distinct rows that appear in both results. For countries, `customers INTERSECT suppliers` lists the 12 countries that have both customers and suppliers. `query_1 EXCEPT query_2` returns the distinct rows of the first result that do not appear in the second. Order matters here, unlike the other two operators: customers' countries except suppliers' countries gives the 9 countries with customers but no supplier, while suppliers except customers gives the 4 with suppliers but no customers. `EXCEPT` is the set-operator way of asking "which values are missing from the other list", and it is a quick substitute for the anti-join of day 41: `SELECT customer_id FROM customers EXCEPT SELECT customer_id FROM orders` returns the customers with no orders. PostgreSQL also has `INTERSECT ALL` and `EXCEPT ALL`, which keep duplicates by counting them; you will rarely need them.

### How rows are compared

Set operators compare whole rows, value by value. Unlike `=` in a `WHERE` clause, they treat two NULLs as **equal** for this purpose, so `SELECT region FROM customers UNION SELECT region FROM suppliers` returns a single NULL row even though the regions are all NULL. This is what makes `EXCEPT` and `INTERSECT` convenient for comparing lists that contain missing values.

### The column rules

The two queries must have the **same number of columns**, and the columns in the same position must have **compatible types**. Otherwise PostgreSQL stops with `each UNION query must have the same number of columns` or `UNION types character varying and integer cannot be matched`. Matching is by **position**, not by name: the first column of the first query lines up with the first column of the second, whatever they are called. The names in the result come from the **first** query, so give your aliases there. A common technique is to add a constant column that labels where each row came from: `SELECT 'customer' AS kind, company_name, country FROM customers UNION ALL SELECT 'supplier', company_name, country FROM suppliers`.

### ORDER BY, LIMIT and precedence

`ORDER BY` and `LIMIT` apply to the final combined result and are written once, at the very end, after the last query. You can sort only by names or positions of the result's columns (the names from the first query). To sort or limit one part first, wrap that query in parentheses. With more than two queries, `INTERSECT` binds tighter than `UNION` and `EXCEPT`, in the same way as `AND` before `OR` (day 33), and the others group left to right. Use parentheses to say what you mean: `(a UNION b) INTERSECT c`.

### Set operators or joins?

Use a join to add columns from another table. Use a set operator to stack rows with the same shape, for example data from several tables or sources, or to compare two lists. `INTERSECT` and `EXCEPT` can often be written with `IN`/`NOT IN` or an anti-join, but they compare whole rows, so they are shorter when several columns together define a match.

### Common misconception

Learners think `UNION` just glues the result sets together. It also sorts or hashes the combined rows to remove duplicates, so it can silently reduce the row count, and it is slower than `UNION ALL`. A second belief is that columns are matched by name, which leads to values in the wrong columns when the order differs.

### Why it matters

Real data lives in several places: one table per year, one per country, one per source system. Stacking them with `UNION ALL`, comparing them with `EXCEPT`, and finding overlaps with `INTERSECT` is the daily work of reconciliation, deduplication and master-data building.

## Syntax and key functions

```sql-syntax
SELECT column_a, column_b FROM table_1
UNION [ALL]
SELECT column_x, column_y FROM table_2
ORDER BY 1
LIMIT 10;

SELECT column_a FROM table_1 INTERSECT SELECT column_x FROM table_2;
SELECT column_a FROM table_1 EXCEPT SELECT column_x FROM table_2;

(SELECT a FROM t1 UNION SELECT a FROM t2) INTERSECT SELECT a FROM t3;
```

| Operator | Returns | Duplicates | Order of queries matters |
|---|---|---|---|
| `UNION` | Rows in either query | Removed | No |
| `UNION ALL` | All rows of both queries | Kept | No (except for row order) |
| `INTERSECT` | Rows in both queries | Removed | No |
| `EXCEPT` | Rows in the first but not the second | Removed | Yes |

| Rule | Detail |
|---|---|
| Number of columns | Must be equal in both queries |
| Types | Must be compatible position by position |
| Column names | Taken from the first query |
| `ORDER BY` / `LIMIT` | Once, at the end, on the combined result |
| Precedence | `INTERSECT` before `UNION` and `EXCEPT`; use parentheses |
| NULL | Two NULLs count as equal |

## Learn by example

### Example 1: UNION against UNION ALL

The two scalar subqueries run both operators on the same two lists of countries. `UNION ALL` keeps all 91 + 29 = 120 rows, whereas `UNION` removes the duplicates and leaves the 25 different countries. The difference between the two numbers is the number of duplicates removed.

```sql run
SELECT (SELECT COUNT(*) FROM (SELECT country FROM customers
                              UNION
                              SELECT country FROM suppliers) u) AS union_rows,
       (SELECT COUNT(*) FROM (SELECT country FROM customers
                              UNION ALL
                              SELECT country FROM suppliers) a) AS union_all_rows;
```

```output
union_rows | union_all_rows
25 | 120
```

### Example 2: A labelled directory

`UNION ALL` stacks the Spanish customers and suppliers. The constant column `kind` records where each row came from, and the column names come from the first query. `ORDER BY` at the end sorts the whole result. There are five customers and one supplier in Spain.

```sql run
SELECT 'customer' AS kind, company_name AS name, country
FROM customers
WHERE country = 'Spain'
UNION ALL
SELECT 'supplier', company_name, country
FROM suppliers
WHERE country = 'Spain'
ORDER BY kind, name;
```

```output
kind | name | country
customer | Bólido Comidas preparadas | Spain
customer | FISSA Fabrica Inter. Salchichas | Spain
customer | Galería del gastrónomo | Spain
customer | Godos Cocina Típica | Spain
customer | Romero y tomillo | Spain
supplier | Cooperativa de Quesos | Spain
```

### Example 3: INTERSECT, what both lists share

Cities that appear both among customers and among suppliers. The result is distinct and sorted by the final `ORDER BY`. Without a set operator you would need a join between the two tables on `city` and a `DISTINCT`.

```sql run
SELECT city FROM customers
INTERSECT
SELECT city FROM suppliers
ORDER BY city;
```

```output
city
Berlin
London
Montréal
Paris
São Paulo
```

### Example 4: EXCEPT, what only the first list has

Countries where we have suppliers but no customers. Swapping the two queries would answer the opposite question (nine countries with customers but no supplier), which shows that `EXCEPT`, unlike `UNION` and `INTERSECT`, depends on the order.

```sql run
SELECT country FROM suppliers
EXCEPT
SELECT country FROM customers
ORDER BY country;
```

```output
country
Australia
Japan
Netherlands
Singapore
```

### Example 5: NULLs count as equal

Every `region` in both tables is NULL. A normal comparison would never match two NULLs, but a set operator treats them as the same value, so `UNION` returns exactly one row, a NULL. This behaviour is why `EXCEPT` and `INTERSECT` work on columns that contain missing values.

```sql run
SELECT region FROM customers
UNION
SELECT region FROM suppliers;
```

```output
region
NULL
```

### Example 6: A summary stacked from several tables

Each query returns one row with the same two columns, a label and a count. `UNION ALL` stacks them into a small report; the column names come from the first query, and the last `ORDER BY` can use the alias `records`. This is a common pattern for record-count checks across tables.

```sql run
SELECT 'customers' AS entity, COUNT(*) AS records FROM customers
UNION ALL
SELECT 'suppliers', COUNT(*) FROM suppliers
UNION ALL
SELECT 'employees', COUNT(*) FROM employees
ORDER BY records DESC;
```

```output
entity | records
customers | 91
suppliers | 29
employees | 9
```

## Real-world applications

**Combining partitioned data.** Tables split by year, region or source are stacked with `UNION ALL` into one analysis set (examples 2 and 6), and the added label column keeps track of the source.

**Reconciliation.** `EXCEPT` in both directions shows what exists in one system and not in the other (example 4), the first step of every data migration check, and a customer list compared with an order list finds inactive customers.

**Overlap analysis.** `INTERSECT` finds the cities, products or customers common to two groups (example 3): who buys from both of two campaigns, which countries are served by two business units.

**Master lists.** A distinct combined list of all countries or all partners, built with `UNION` from several tables (example 1), feeds dropdowns and dimension tables.

## Daily review

### Key takeaways

- Set operators stack the rows of two queries; joins add columns.
- `UNION` removes duplicates, `UNION ALL` keeps them and is faster; `INTERSECT` is the common rows; `EXCEPT` is first minus second and depends on order.
- Same number of columns, compatible types, matched by position, names from the first query.
- Two NULLs count as equal in set operations.
- `ORDER BY` and `LIMIT` go once at the end; use parentheses for several operators because `INTERSECT` binds first.

### Common mistakes

- Using `UNION` when `UNION ALL` is meant, and losing rows or paying for the sort. Use `UNION ALL` unless you want distinct rows.
- Selecting columns in a different order in the two queries and getting values under the wrong names, or a type error.
- Different numbers of columns: "each UNION query must have the same number of columns".
- Mixing text and numbers in the same position: "UNION types character varying and integer cannot be matched". Cast with `::text`.
- Putting `ORDER BY` after the first query. It must follow the last query and refer to the result's column names or positions.
- Expecting `EXCEPT` to be symmetric. `A EXCEPT B` and `B EXCEPT A` are different.
- Mixing `UNION` and `INTERSECT` without parentheses and getting an unexpected grouping.

### Revision notes

- UNION distinct, UNION ALL all rows, INTERSECT common, EXCEPT first minus second.
- Positions, not names; names from the first query.
- ORDER BY at the end only.
- 91 + 29 = 120 rows; 25 distinct countries; 12 common countries.

## Objectives

- Explain what a window function is and how `OVER` differs from `GROUP BY`.
- Write an aggregate such as `SUM`, `AVG` or `COUNT` as a windowed aggregate with `OVER ()` and `OVER (PARTITION BY ...)`.
- Compare each row with a group total or average without losing any rows.
- Compute a row's share of its group total, and explain why a window function cannot appear in `WHERE`.

## Understand

### The problem GROUP BY cannot solve

On day 37 you used `GROUP BY` to collapse rows. `SELECT category_id, AVG(unit_price) FROM products GROUP BY category_id` returns one row per category, and the individual products disappear. That is exactly what you want for a summary, but many questions need both levels at once: "show every product and next to it the average price of its category", or "show every order line and what percentage of its order it represents". With `GROUP BY` alone you would have to compute the summary in a subquery and join it back to the detail rows.

A **window function** solves this directly. It calculates a value from a set of related rows, called a **window**, and attaches the result to each row. No rows are collapsed. A query over the 77 product rows returns 77 rows, each with one or more extra columns.

### What OVER means

A window function is recognised by the keyword `OVER`. In `AVG(unit_price) OVER ()` the part before `OVER` is the function and the part in parentheses is the **window definition**: the rule that says which rows each row can see. An empty definition `OVER ()` means that the window is the whole result set, so every row gets the same value. Adding `PARTITION BY category_id` splits the rows into groups, called **partitions**, and the function is evaluated inside the partition that the current row belongs to. Rows from different partitions never mix.

Think of a class photo. `GROUP BY` takes one representative per class and sends the rest home. `PARTITION BY` keeps every child in the photo but writes the class average under each child's picture.

### Windowed aggregates

Every aggregate function you know can become a window function by adding `OVER`: `SUM`, `AVG`, `COUNT`, `MIN` and `MAX`. They do the same calculation as before; only the result placement changes. `COUNT(*) OVER (PARTITION BY category_id)` is the number of products in the row's category, repeated on each row of that category. A windowed aggregate can sit next to ordinary columns and next to other windowed aggregates with different `OVER` definitions in the same `SELECT`.

### When windows are computed

Window functions run late in the logical order of a query. The database does `FROM`, `WHERE`, `GROUP BY`, `HAVING`, then calculates the window functions, then `SELECT` output, `ORDER BY` and `LIMIT`. Two consequences follow.

First, `WHERE` filters rows before the windows are built. If you keep only categories 1 and 2 in `WHERE`, then `SUM(...) OVER ()` is the total of those two categories only, not of the whole table. This is useful when intended and a silent bug when not.

Second, you cannot write a window function in `WHERE`, `GROUP BY` or `HAVING`, because those steps happen before the window exists. PostgreSQL reports `window functions are not allowed in WHERE`. To filter on a window result, compute it in a subquery (day 43) or CTE (day 46) and filter in the outer query. Example 5 shows this.

### Windows and GROUP BY together

If a query has `GROUP BY`, window functions run on the grouped rows, and can only refer to grouped columns or aggregates. For example `SUM(SUM(quantity)) OVER ()` is the total of the group totals. This form is common in reports that show each group's share of the grand total, and Example 4 uses a simple version of it.

### Common misconception

Learners often think `OVER (PARTITION BY x)` is just another way to write `GROUP BY x`. The two differ in what they return: `GROUP BY` returns one row per group, while a window function returns the original rows. Also, `PARTITION BY` does not sort anything. If you need an ordered output, you still need `ORDER BY` at the end of the query. Next, `ORDER BY` inside `OVER` has a different meaning, which days 50 to 52 introduce, so on this day every `OVER` has only `PARTITION BY` or nothing.

### Why it matters

Shares of total, comparison with a group average, group size next to each row and "difference from the best in its group" are everyday analyst questions. Windows answer them in one pass over the data, without a self-join, and keep the query readable.

## Syntax and key functions

The general form of a windowed aggregate:

```sql-syntax
aggregate_function(expression) OVER ()
aggregate_function(expression) OVER (PARTITION BY column_1 [, column_2 ...])
```

`aggregate_function(expression)` is the calculation. `OVER` marks it as a window function. `PARTITION BY` lists the columns that define the groups. Rows with the same values in those columns belong to the same partition. Leave it out to treat all rows as one partition.

A windowed aggregate is an ordinary select-list expression, so you can compute with it:

```sql-syntax
SELECT column,
       value,
       value - AVG(value) OVER (PARTITION BY column) AS diff_from_group_avg,
       100.0 * value / SUM(value) OVER (PARTITION BY column) AS pct_of_group
FROM table_name;
```

| Expression | Returns |
|---|---|
| `SUM(x) OVER ()` | Total of `x` over all rows, on every row |
| `AVG(x) OVER (PARTITION BY g)` | Average of `x` within the row's group |
| `COUNT(*) OVER (PARTITION BY g)` | Number of rows in the row's group |
| `MIN(x) OVER (PARTITION BY g)` | Smallest `x` in the row's group |
| `MAX(x) OVER (PARTITION BY g)` | Largest `x` in the row's group |

## Learn by example

### Example 1: OVER () attaches one overall value to every row

Products in category 1 (beverages) with the average price of those products on every row. The window covers the rows left after `WHERE`, so the average is for category 1 only. The count column shows the window size. Every row keeps its own identity.

```sql run
SELECT product_id, product_name, unit_price,
       ROUND(AVG(unit_price) OVER (), 2) AS avg_price,
       COUNT(*) OVER () AS products_in_list
FROM products
WHERE category_id = 1
ORDER BY product_id
LIMIT 5;
```

```output
product_id | product_name | unit_price | avg_price | products_in_list
1 | Chai | 18.00 | 37.98 | 12
2 | Chang | 19.00 | 37.98 | 12
24 | Guaraná Fantástica | 4.50 | 37.98 | 12
34 | Sasquatch Ale | 14.00 | 37.98 | 12
35 | Steeleye Stout | 18.00 | 37.98 | 12
```

### Example 2: PARTITION BY compares a row with its own group

Now all categories are in play. Each product is compared with the average of its category. The `PARTITION BY category_id` window gives a different average for each category, and `unit_price - AVG(...)` shows how far the product is from it.

```sql run
SELECT category_id, product_id, unit_price,
       ROUND(AVG(unit_price) OVER (PARTITION BY category_id), 2) AS category_avg,
       ROUND(unit_price - AVG(unit_price) OVER (PARTITION BY category_id), 2) AS diff_from_avg
FROM products
WHERE category_id IN (1, 2)
ORDER BY category_id, product_id
LIMIT 6;
```

```output
category_id | product_id | unit_price | category_avg | diff_from_avg
1 | 1 | 18.00 | 37.98 | -19.98
1 | 2 | 19.00 | 37.98 | -18.98
1 | 24 | 4.50 | 37.98 | -33.48
1 | 34 | 14.00 | 37.98 | -23.98
1 | 35 | 18.00 | 37.98 | -19.98
1 | 38 | 263.50 | 37.98 | 225.52
```

### Example 3: the same question with GROUP BY

For contrast, `GROUP BY` answers "what is the average price per category" with one row per category. The product rows are gone. Use `GROUP BY` when you want the summary only, and a window when you also need the detail.

```sql run
SELECT category_id, COUNT(*) AS products, ROUND(AVG(unit_price), 2) AS avg_price
FROM products
GROUP BY category_id
ORDER BY category_id
LIMIT 4;
```

```output
category_id | products | avg_price
1 | 12 | 37.98
2 | 12 | 23.06
3 | 13 | 25.16
4 | 10 | 28.73
```

### Example 4: share of an order's total

An order has several lines in `order_details`. A line's value is `unit_price * quantity` (ignoring `discount` here to keep the idea clear). Dividing it by the sum of the order's lines gives the line's share. Order 10248 has a single line, which is 100 percent of its order, and order 10249 has two lines whose shares add up to 100.

```sql run
SELECT order_id, product_id,
       unit_price * quantity AS line_value,
       SUM(unit_price * quantity) OVER (PARTITION BY order_id) AS order_value,
       ROUND(100.0 * unit_price * quantity / SUM(unit_price * quantity) OVER (PARTITION BY order_id), 1) AS pct_of_order
FROM order_details
WHERE order_id IN (10248, 10249)
ORDER BY order_id, product_id;
```

```output
order_id | product_id | line_value | order_value | pct_of_order
10248 | 8 | 360.00 | 360.00 | 100.0
10249 | 16 | 191.95 | 1161.95 | 16.5
10249 | 29 | 970.00 | 1161.95 | 83.5
```

### Example 5: filtering on a window result needs a subquery

Which products are priced above the average of their category? `WHERE unit_price > AVG(unit_price) OVER (...)` is an error, because `WHERE` runs before windows exist. Calculate the average in an inner query, then filter in the outer query. The inner query is a derived table, as you used on day 43.

```sql run
SELECT category_id, product_id, product_name, unit_price, category_avg
FROM (
  SELECT category_id, product_id, product_name, unit_price,
         ROUND(AVG(unit_price) OVER (PARTITION BY category_id), 2) AS category_avg
  FROM products
) AS p
WHERE unit_price > category_avg
  AND category_id = 8
ORDER BY unit_price DESC, product_id;
```

```output
category_id | product_id | product_name | unit_price | category_avg
8 | 18 | Carnarvon Tigers | 62.50 | 20.68
8 | 10 | Ikura | 31.00 | 20.68
8 | 37 | Gravad lax | 26.00 | 20.68
8 | 30 | Nord-Ost Matjeshering | 25.89 | 20.68
```

### Example 6: windows after GROUP BY, share of total freight by country

First `GROUP BY` produces one row per ship country with its freight total. The window `SUM(SUM(freight)) OVER ()` then adds those totals together so each country's share of all freight can be computed. A window over grouped rows may use aggregates and grouped columns only.

```sql run
SELECT ship_country,
       SUM(freight) AS freight_total,
       ROUND(100.0 * SUM(freight) / SUM(SUM(freight)) OVER (), 1) AS pct_of_all_freight
FROM orders
GROUP BY ship_country
ORDER BY freight_total DESC, ship_country
LIMIT 5;
```

```output
ship_country | freight_total | pct_of_all_freight
Germany | 1455.01 | 14.8
France | 1436.84 | 14.6
Brazil | 1247.26 | 12.7
USA | 1225.61 | 12.4
UK | 759.19 | 7.7
```

## Real-world applications

**Benchmarking against a peer group.** Example 2 compares each product with its category average. The same shape flags employees paid above their department average, stores selling below their region's average or deliveries slower than the carrier's average.

**Contribution analysis.** Examples 4 and 6 show a row's share of its parent total. Finance and marketing reports use it for share of revenue by region, share of an invoice by line, or share of sessions by channel.

**Adding context to detail rows.** `COUNT(*) OVER (PARTITION BY ...)` puts the group size on every row, so a data-quality check can list rows that belong to unexpectedly large groups without a separate query.

**Outlier screening.** Comparing a value to its partition's `AVG`, `MIN` or `MAX` is the first step in finding unusual rows, such as an order whose freight is far above the average for its country.

## Daily review

### Key takeaways

- A window function calculates a value over a window of related rows and returns one result per input row; nothing is collapsed.
- `OVER ()` uses all rows as one window; `OVER (PARTITION BY g)` makes one window per distinct value of `g`.
- Aggregates (`SUM`, `AVG`, `COUNT`, `MIN`, `MAX`) become window functions by adding `OVER`.
- `WHERE` runs before windows, so it changes the window's contents; a window result cannot be filtered in the same query's `WHERE`.
- `GROUP BY` for a summary only; windows when detail rows and group figures are needed together.

### Common mistakes

- Writing `AVG(price) OVER` without parentheses: a syntax error. `OVER` always needs `(...)`, even if empty.
- Mixing a plain column and an aggregate without `OVER` or `GROUP BY`: the error is `column "..." must appear in the GROUP BY clause or be used in an aggregate function`. Add `OVER (...)` to the aggregate if you want to keep the rows.
- Putting a window function in `WHERE`: the error is `window functions are not allowed in WHERE`. Move the calculation into a subquery or CTE and filter outside it.
- Filtering with `WHERE` and then wondering why the "total" is smaller than the table total. The window sees only the rows that survived `WHERE`.
- Integer division: `100 * x / SUM(x) OVER ()` with whole numbers truncates. Multiply by `100.0` first.
- Expecting `PARTITION BY` to sort the result. Add `ORDER BY` at the end of the query.

### Revision notes

- `fn(x) OVER ()` is whole-table; `fn(x) OVER (PARTITION BY g)` is per group.
- Windows keep every row; `GROUP BY` returns one row per group.
- Logical order: FROM, WHERE, GROUP BY, HAVING, window functions, SELECT, ORDER BY, LIMIT.
- Share of total is `100.0 * x / SUM(x) OVER (...)`.

## Objectives

- Explain an incremental load and the high-water mark (watermark) that makes it possible.
- Store the watermark in a one-row `etl_state` table and advance it in the same transaction as the load.
- Choose between `>` and `>=` and decide what the watermark column should be.
- Handle late-arriving data with a lookback window and an idempotent load.

## Understand

### Reading only what is new

Day 124 reloaded everything on every run. That is right for small tables and wrong for a table of 60 million orders where 20,000 change per day. An **incremental load** reads only the rows that are new or changed since the last successful run. To do that the pipeline must remember where the last run ended. That memory is the **high-water mark**, usually called the **watermark**: the largest value of an ordering column (here the `updated_at` timestamp) among the rows already loaded. The next run asks the source for `WHERE updated_at > :watermark`, loads those rows, and moves the watermark up to the largest `updated_at` it just loaded. Think of the mark a river leaves on a wall: it records the highest level reached so far, and each new run looks only above it.

### Where the watermark lives: checkpoint storage

The watermark must survive between runs, so it cannot be a Python variable. It is stored as a **checkpoint** in durable storage. The simplest place is a small table in the target database. The pipeline's state table is `etl_state`, a table with exactly one row: `CHECK (id = 1)` on the primary key makes a second row impossible, and the single column `watermark` holds the text of the last loaded `updated_at`. The first run starts from a value older than any data, such as `1970-01-01T00:00:00Z`, which makes it a full load, so the same code covers the first run and all later ones. Storing the checkpoint in the same database as the data has an important advantage: both can be changed in one transaction.

### Advance the watermark with the load, atomically

The order of operations decides whether the pipeline loses data or loads it twice. If you update the watermark first and then the load fails, the next run starts above the rows that were never loaded: they are skipped forever, a **silent gap**. If you load first and the process dies before the watermark is saved, the next run reads the same rows again: harmless only if the load is idempotent. The safe design does both inside one transaction (`with conn:`): load the rows, update the watermark, commit. Either both happen or neither does. Today's load replaces rows by key (delete the keys, insert the rows), so a row that was changed appears once and a reread does no harm; Day 126 will replace this with a proper upsert.

### Choosing the watermark column

The column must increase when a row is created *or changed*, and must be set by the source reliably. An **updated timestamp** fits, since it catches both new and modified rows. An **auto-increment id** catches only new rows, since an update does not change the id, so an update to order 17 would never be seen. A timestamp written by the application can be wrong, or can be set before a transaction commits so that it commits later than a row with a bigger timestamp. Know your source: where the value comes from decides whether the watermark can be trusted.

### Strict or inclusive

`updated_at > watermark` skips any row that has exactly the watermark timestamp but arrives after the run: with second-level timestamps, two orders can easily share a second, and one might be committed just after the extract. `updated_at >= watermark` rereads the boundary rows every time, which is safe because the load is idempotent, and costs a few duplicate reads. Most robust pipelines use inclusive comparisons or a lookback (below) together with an idempotent load.

### Late-arriving data

A **late-arriving** row has an `updated_at` older than the current watermark when it reaches the source: a mobile app that was offline, a message queue that delayed, a replica that lagged. The watermark has already moved past it, so a strict incremental read never sees it. The usual defence is a **lookback window**: each run reads from `watermark - N hours` instead of from the watermark, and the idempotent load replaces the rows that were already loaded. The window costs rereading N hours of data, and it catches anything that arrives within N hours. Data later than the window needs a **backfill** (Day 128) or a periodic full reload as a safety net. A misconception is that a watermark guarantees completeness. It guarantees only "nothing above the mark was missed"; it says nothing about rows that arrive below it.

### Why it matters in data work

Incremental loading is what makes a pipeline scale: a nightly run that reads 20,000 rows instead of 60 million finishes in seconds and stays within API rate limits. The watermark is also the single piece of state whose corruption causes silent data loss, so it deserves care and a check.

## Syntax and key functions

```sql-syntax
CREATE TABLE etl_state (id integer PRIMARY KEY CHECK (id = 1), watermark text NOT NULL);
SELECT * FROM source WHERE updated_at > :watermark ORDER BY updated_at;
UPDATE etl_state SET watermark = :new_watermark;
```

```python
with conn:                                     # one transaction
    load(conn, new_rows)
    conn.execute("UPDATE etl_state SET watermark = ?", (newest,))
```

| Item | What it does or returns |
|---|---|
| watermark | The largest `updated_at` already loaded, stored between runs. |
| `etl_state` | A one-row table; `CHECK (id = 1)` forbids a second row. |
| `> watermark` | Strict: skips ties at the boundary. |
| `>= watermark` | Inclusive: rereads boundary rows, safe with an idempotent load. |
| lookback window | Reads from `watermark - N hours` to catch late data. |
| `max(updated_at)` of loaded rows | The new watermark; never move it down. |

## Learn by example

### Example 1: The state table and three runs

The first run starts at the 1970 watermark, so it loads everything. The second finds nothing new. The third loads only the two rows that arrived later. The helper functions are the ones the later examples reuse.

```python run
import sqlite3
from datetime import datetime, timedelta

FMT = "%Y-%m-%dT%H:%M:%SZ"

def open_db():
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER NOT NULL,
        status TEXT, updated_at TEXT)""")
    conn.execute("CREATE TABLE etl_state (id INTEGER PRIMARY KEY CHECK (id = 1), watermark TEXT NOT NULL)")
    conn.execute("INSERT INTO etl_state VALUES (1, '1970-01-01T00:00:00Z')")
    conn.commit()
    return conn

def get_watermark(conn):
    return conn.execute("SELECT watermark FROM etl_state").fetchone()[0]

def shifted(ts, hours):
    return (datetime.strptime(ts, FMT) - timedelta(hours=hours)).strftime(FMT)

def incremental_run(conn, source, lookback_hours=0):
    """source rows: (order_id, amount_cents, status, updated_at)"""
    watermark = get_watermark(conn)
    since = shifted(watermark, lookback_hours)
    new = [r for r in source if r[3] > since]
    if not new:
        return {"read": 0, "watermark": watermark}
    with conn:
        conn.executemany("DELETE FROM orders_clean WHERE order_id = ?", [(r[0],) for r in new])
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?, ?, ?)", new)
        newest = max(max(r[3] for r in new), watermark)
        conn.execute("UPDATE etl_state SET watermark = ?", (newest,))
    return {"read": len(new), "watermark": newest}

source = [(1, 1990, "paid", "2025-03-01T10:00:00Z"), (2, 4500, "paid", "2025-03-01T11:00:00Z"), (3, 750, "paid", "2025-03-02T09:00:00Z")]
conn = open_db()
print(incremental_run(conn, source))
print(incremental_run(conn, source))
source += [(4, 1200, "paid", "2025-03-03T08:00:00Z"), (5, 300, "failed", "2025-03-03T09:30:00Z")]
print(incremental_run(conn, source))
print(conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0], "rows; state rows:", conn.execute("SELECT COUNT(*) FROM etl_state").fetchone()[0])
```

```output
{'read': 3, 'watermark': '2025-03-02T09:00:00Z'}
{'read': 0, 'watermark': '2025-03-02T09:00:00Z'}
{'read': 2, 'watermark': '2025-03-03T09:30:00Z'}
5 rows; state rows: 1
```
### Example 2: A changed row is replaced, not duplicated

Order 2 is refunded after it was loaded, so the source holds a new version with a later `updated_at`. The run reads it because the timestamp moved, deletes the old version by key and inserts the new one. The row count stays the same and the status changes.

### Example 3: The watermark moves with the load or not at all

The second batch contains a row with a missing amount, which the `NOT NULL` column rejects. The transaction rolls back, so neither the good row in that batch nor the watermark changes. The next run, after the source is fixed, starts from the same mark and misses nothing.

```python run
import sqlite3
from datetime import datetime, timedelta

FMT = "%Y-%m-%dT%H:%M:%SZ"

def open_db():
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER NOT NULL,
        status TEXT, updated_at TEXT)""")
    conn.execute("CREATE TABLE etl_state (id INTEGER PRIMARY KEY CHECK (id = 1), watermark TEXT NOT NULL)")
    conn.execute("INSERT INTO etl_state VALUES (1, '1970-01-01T00:00:00Z')")
    conn.commit()
    return conn

    return conn.execute("SELECT watermark FROM etl_state").fetchone()[0]

def shifted(ts, hours):
    return (datetime.strptime(ts, FMT) - timedelta(hours=hours)).strftime(FMT)

def incremental_run(conn, source, lookback_hours=0):
    """source rows: (order_id, amount_cents, status, updated_at)"""
    watermark = get_watermark(conn)
    since = shifted(watermark, lookback_hours)
    new = [r for r in source if r[3] > since]
    if not new:

    with conn:
        conn.executemany("DELETE FROM orders_clean WHERE order_id = ?", [(r[0],) for r in new])

        conn.execute("UPDATE etl_state SET watermark = ?", (newest,))
    return {"read": len(new), "watermark": newest}

conn = open_db()
incremental_run(conn, [(1, 1990, "paid", "2025-03-01T10:00:00Z")])
bad_batch = [(2, 4500, "paid", "2025-03-02T10:00:00Z"), (3, None, "paid", "2025-03-02T11:00:00Z")]
try:
    incremental_run(conn, bad_batch)
except sqlite3.IntegrityError as exc:
    print("run failed:", type(exc).__name__)
print("watermark still:", get_watermark(conn))
print("rows:", conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0])
fixed = [(2, 4500, "paid", "2025-03-02T10:00:00Z"), (3, 800, "paid", "2025-03-02T11:00:00Z")]
print(incremental_run(conn, fixed))
```

```output
rows: 1
{'read': 2, 'watermark': '2025-03-02T11:00:00Z'}
```
### Example 4: Late data and the lookback window

Order 6 is stamped 10:00 but reaches the source after the run that already moved the watermark to 12:00. A strict incremental run never sees it. A run with a three-hour lookback rereads from 09:00, loads the late row and, because the load replaces by key, does not duplicate the rows it rereads.

```python run
import sqlite3
from datetime import datetime, timedelta

FMT = "%Y-%m-%dT%H:%M:%SZ"

def open_db():
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER NOT NULL,
        status TEXT, updated_at TEXT)""")
    conn.execute("CREATE TABLE etl_state (id INTEGER PRIMARY KEY CHECK (id = 1), watermark TEXT NOT NULL)")
    conn.execute("INSERT INTO etl_state VALUES (1, '1970-01-01T00:00:00Z')")
    conn.commit()
    return conn

def get_watermark(conn):
    return conn.execute("SELECT watermark FROM etl_state").fetchone()[0]

def shifted(ts, hours):
    return (datetime.strptime(ts, FMT) - timedelta(hours=hours)).strftime(FMT)

def incremental_run(conn, source, lookback_hours=0):
    """source rows: (order_id, amount_cents, status, updated_at)"""
    watermark = get_watermark(conn)
    since = shifted(watermark, lookback_hours)
    new = [r for r in source if r[3] > since]
    if not new:
        return {"read": 0, "watermark": watermark}
    with conn:
        conn.executemany("DELETE FROM orders_clean WHERE order_id = ?", [(r[0],) for r in new])
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?, ?, ?)", new)
        newest = max(max(r[3] for r in new), watermark)
        conn.execute("UPDATE etl_state SET watermark = ?", (newest,))
    return {"read": len(new), "watermark": newest}

def run_all(lookback):
    conn = open_db()
    incremental_run(conn, [(5, 500, "paid", "2025-03-04T12:00:00Z")], lookback)
    incremental_run(conn, [(5, 500, "paid", "2025-03-04T12:00:00Z"), (6, 600, "paid", "2025-03-04T10:00:00Z")], lookback)
    return [r[0] for r in conn.execute("SELECT order_id FROM orders_clean ORDER BY order_id")]

print("no lookback  :", run_all(0))
print("3h lookback  :", run_all(3))
```

```output
no lookback  : [5]
3h lookback  : [5, 6]
```
### Example 5: A watermark on PostgreSQL syntax (PGlite)

The state table stores a real `timestamp`. One statement loads the rows above the mark, a second moves the mark to the newest loaded value, and a second round shows that nothing is reloaded. The query at the end shows the count and the watermark.

```sql run
CREATE TABLE src (order_id int, amount_cents int, updated_at timestamp);
CREATE TABLE orders_clean (order_id int PRIMARY KEY, amount_cents int, updated_at timestamp);
CREATE TABLE etl_state (id int PRIMARY KEY CHECK (id = 1), watermark timestamp NOT NULL);
INSERT INTO etl_state VALUES (1, '1970-01-01');
INSERT INTO src VALUES (1, 1990, '2025-03-01 10:00'), (2, 4500, '2025-03-01 11:00'), (3, 750, '2025-03-02 09:00');
INSERT INTO orders_clean SELECT * FROM src WHERE updated_at > (SELECT watermark FROM etl_state);
UPDATE etl_state SET watermark = (SELECT COALESCE(MAX(updated_at), etl_state.watermark) FROM orders_clean);
INSERT INTO orders_clean SELECT * FROM src WHERE updated_at > (SELECT watermark FROM etl_state);
SELECT (SELECT COUNT(*) FROM orders_clean) AS loaded, (SELECT watermark::text FROM etl_state) AS watermark;
```

```output
loaded | watermark
3 | 2025-03-02 09:00:00
```
## Real-world applications

- **Large tables and API limits.** A nightly job reads 20,000 changed orders instead of 60 million, which fits within the API's rate limit and finishes in seconds (Examples 1 and 2).
- **Safe restarts.** Because the load and the watermark commit together (Example 3), a crashed run needs no cleanup: the next run starts at the same mark.
- **Mobile and event data.** Sources with offline clients or queues deliver late rows; a lookback window (Example 4) catches most of them without a full reload.
- **Auditing the state.** Comparing `etl_state.watermark` with `MAX(updated_at)` in the target is a one-line check that the pipeline is current.

## Daily review

### Key takeaways

- An incremental load reads rows above a stored watermark and moves the mark up after loading.
- Store the watermark in durable state (`etl_state`) and commit it with the load.
- Use an update timestamp as the watermark column; an id misses updates.
- Inclusive comparisons or a lookback window plus an idempotent load protect against boundary and late rows.
- A watermark says nothing about rows that arrive below it.

### Common mistakes

- Updating the watermark before the load finishes, so a failed load skips rows forever. Commit both together.
- Using an auto-increment id as the watermark for data that is updated; changes are never seen. Use an update timestamp.
- Moving the watermark to the current time instead of the maximum loaded `updated_at`, which skips rows still in flight. Use the data's own maximum.
- Strict `>` with second-resolution timestamps, losing rows stamped in the same second as the mark. Use `>=` or a lookback.
- Forgetting the first run: starting with no state raises an error. Initialise with an old timestamp.

### Revision notes

- `WHERE updated_at > :watermark`, then `watermark = max(updated_at of loaded rows)`.
- `etl_state(id CHECK (id = 1), watermark)`; `with conn:` load plus update.
- Lookback: read from `watermark - N hours`; load must be idempotent.
- Check: `etl_state.watermark` equals `MAX(updated_at)` in the target.

## Understand

### Why memory matters

A pandas table lives entirely in your computer's memory (RAM). A file of 2 GB on disk can need more than 2 GB once loaded, and when memory runs out the program slows down or stops with a `MemoryError`. Most beginners never meet this limit with small files, but the habits of choosing sensible column types and reading data in pieces make pipelines cheaper and are required once files grow. Day 75 introduced `astype` and the categorical dtype as a way to fix types; today the aim is memory and size.

An analogy is luggage. Every column is a suitcase. A suitcase of 64-bit integers is large even if every number is small, and a suitcase of text holds a separate wrapped item for every row, even when the same word repeats a million times. Choosing a smaller suitcase that still fits the contents saves space without losing anything.

### Dtypes and what they cost

Each column has a **dtype**, the type of its values. Integers come in sizes: `int8` stores numbers from -128 to 127 in one byte, `int16` from -32,768 to 32,767 in two bytes, `int32` in four and `int64` in eight. Floats come as `float32` and `float64`. Pandas chooses `int64` and `float64` by default when it builds a table from Python lists, which is safe but often more than needed. A column of ages fits in `int8`, and a column of ratings from 1 to 5 certainly does. Choose a size too small and values overflow: 200 stored in `int8` wraps around to a negative number, so shrink only after checking `min()` and `max()`. The helper `pd.to_numeric(s, downcast="integer")` does this check for you and picks the smallest integer type that holds all the values.

Text is stored differently. A column of strings has dtype `object`: it holds a pointer to a separate Python string for each row. The ordinary `memory_usage()` counts only the pointers, so it hides most of the cost. Use `df.memory_usage(deep=True)`, which follows the pointers and counts the text itself, and add `.sum()` for the total. The exact number of bytes differs between platforms and library versions, so compare two tables or compute a ratio instead of memorising a figure.

### Categoricals

A **categorical** column stores each distinct value once, in a list of categories, and keeps a small integer **code** for every row that points into the list. A million rows of 10 distinct country names become 10 strings plus a million one-byte codes. `s.astype("category")` converts a column, `s.cat.categories` lists the distinct values, and `s.cat.codes` shows the codes. The saving is large when a column has few distinct values compared with the number of rows, such as country, status, or product group. It brings nothing, and can cost more, when nearly every value is different, as with names or ids.

A categorical also keeps a fixed set of allowed values. Assigning a value that is not in the categories gives an error or `NaN`, which can be useful to protect a column. A categorical can have an order (`ordered=True`), for example `low < medium < high`, so sorting and comparisons follow that order rather than alphabetical order. When you group by a categorical column, pass `observed=True`; otherwise recent pandas versions warn and can produce rows for categories that have no data.

### Reading a file in chunks

When a file is too large to load at once, `pd.read_csv(path, chunksize=n)` returns an iterator that yields tables of at most `n` rows. You loop over it, process each chunk, keep only a small running result, and move on, so memory stays bounded by the chunk size. A running result must be something you can combine: totals and counts can be added across chunks, and a mean is the total divided by the count. A median cannot be combined from chunk medians, so some questions need a different approach. The file can be an open file or, as in the examples here, an `io.StringIO` object that behaves like a file.

Two more arguments save memory before the data is even built. `usecols=["a", "b"]` loads only the columns you need, and `dtype={"qty": "int16", "country": "category"}` creates the columns in the small types straight away, instead of loading large ones and converting afterwards.

### Efficient pipelines

An efficient pipeline combines these steps: read only the needed columns in small types, filter early so later steps see fewer rows, aggregate per chunk, and combine the partial results. Before optimising, look at where memory goes with `memory_usage(deep=True)` and decide whether the effort is needed. Data that fits comfortably in memory does not need chunking, and clarity is worth more than a saving nobody notices.

### Common misconception

Learners often believe that `df.memory_usage()` reports the true size. For text columns it reports only pointer sizes, so a table of long strings looks tiny. Always pass `deep=True` for text. Another belief is that `category` always saves memory; for a column of unique ids it does not.

### Why it matters

Memory limits are the usual reason a script fails on production data that ran fine on a sample. Knowing what costs memory, and how to read in pieces, lets one laptop handle files far larger than a toy sample, and lets you explain to a colleague why the same data takes much less space after conversion.

## Syntax and key functions

```python nocheck
df.memory_usage(deep=True).sum()
pd.to_numeric(s, downcast="integer")
s.astype("category")           # s.cat.categories, s.cat.codes
df.groupby("c", observed=True)["v"].sum()
for chunk in pd.read_csv(src, chunksize=1000, usecols=["a", "b"], dtype={"a": "int16"}):
    ...
```

| Call | Returns |
|---|---|
| `df.memory_usage(deep=True)` | bytes per column, including text contents |
| `pd.to_numeric(s, downcast="integer")` | the smallest integer dtype that fits |
| `s.astype("category")` | categorical column |
| `s.cat.categories`, `s.cat.codes` | the distinct values; the integer code per row |
| `pd.read_csv(..., chunksize=n)` | iterator of tables with at most `n` rows |
| `usecols`, `dtype` in `read_csv` | load fewer columns, in smaller types |

## Learn by example

### Example 1: Smaller integers

The values of `qty` lie between 1 and 9, so `int8` is enough. The comparison avoids printing byte counts, which differ between platforms.

```python run
import pandas as pd
df = pd.DataFrame({"qty": [3, 1, 9, 4, 2, 7, 5, 8] * 1000})
small = df["qty"].astype("int8")
auto = pd.to_numeric(df["qty"], downcast="integer")
print(df["qty"].dtype, small.dtype, auto.dtype)
print(df["qty"].min(), df["qty"].max())
print(small.memory_usage(index=False) < df["qty"].memory_usage(index=False))
print(small.equals(df["qty"].astype("int8")), (small == df["qty"]).all())
```

```output
int64 int8 int8
1 9
True
True True
```

The smaller type holds the same numbers in a fraction of the space.

### Example 2: Text versus category

A status column repeats three values. The categorical holds the same information in less space, and `observed=True` avoids a warning in the grouping.

```python run
import pandas as pd
status = pd.Series(["shipped", "pending", "returned", "shipped"] * 5000)
cat = status.astype("category")
as_text = status.memory_usage(deep=True)
as_cat = cat.memory_usage(deep=True)
print(as_cat < as_text)
print(round(as_text / as_cat) >= 5)
print(sorted(cat.cat.categories.tolist()))
print(cat.cat.codes.dtype)
df = pd.DataFrame({"status": cat, "amount": range(len(cat))})
print(df.groupby("status", observed=True)["amount"].count().to_string())
```

```output
True
True
['pending', 'returned', 'shipped']
int8
status
pending      5000
returned     5000
shipped     10000
```

The ratio check says at least five times smaller without printing a platform-dependent number. The codes use `int8` because there are fewer than 128 categories.

### Example 3: An ordered categorical

Sizes sort in their natural order, and a value outside the allowed list becomes missing.

```python run
import pandas as pd
sizes = pd.Categorical(["M", "S", "L", "S", "XL"], categories=["S", "M", "L"], ordered=True)
s = pd.Series(sizes)
print(s.tolist())
print(s.sort_values().tolist())
print((s >= "M").tolist())
```

```output
['M', 'S', 'L', 'S', nan]
['S', 'S', 'M', 'L', nan]
[True, False, True, False, False]
```

`XL` was not in the categories, so it became `NaN`. Comparisons follow the declared order, S before M before L.

### Example 4: Reading a file in chunks

A small CSV stands in for a file too big to load at once. Each chunk adds to a running total and count, and only two numbers are kept.

```python run
import io
import pandas as pd
text = "order_id,country,amount\n" + "\n".join(f"{i},{'UK' if i % 3 else 'US'},{i * 10}" for i in range(1, 11))
total = 0
count = 0
chunks = 0
for chunk in pd.read_csv(io.StringIO(text), chunksize=4, usecols=["country", "amount"]):
    chunks += 1
    total += chunk["amount"].sum()
    count += len(chunk)
print(chunks, count, total, total / count)
print(pd.read_csv(io.StringIO(text))["amount"].sum() == total)
```

```output
3 10 550 55.0
True
```

Ten rows in chunks of four give three chunks (4, 4 and 2 rows). The total matches a full read.

### Example 5: A chunked pipeline with filtering

Each chunk is filtered, grouped and reduced to small partial results, which are then combined with a second groupby.

```python run
import io
import pandas as pd
text = "country,amount\n" + "\n".join(f"{['UK', 'US', 'DE'][i % 3]},{i + 1}" for i in range(12))
parts = []
for chunk in pd.read_csv(io.StringIO(text), chunksize=5, dtype={"country": "category"}):
    big = chunk[chunk["amount"] >= 3]
    parts.append(big.groupby("country", observed=True)["amount"].agg(["sum", "count"]))
result = pd.concat(parts).groupby(level=0).sum()
result["mean"] = (result["sum"] / result["count"]).round(2)
print(result.to_string())
full = pd.read_csv(io.StringIO(text))
print(full[full["amount"] >= 3].groupby("country")["amount"].sum().to_dict() == result["sum"].to_dict())
```

```output
         sum  count  mean
country                  
DE        30      4   7.5
UK        21      3   7.0
US        24      3   8.0
True
```

The per-chunk results are small. Summing sums and counts and then dividing gives the same mean as the full table.

## Real-world applications

- **Fitting a big export into memory.** An analyst loads only the columns needed and stores `country` and `status` as categories, so a file that did not fit loads comfortably.
- **Streaming aggregation.** A data engineer totals a multi-gigabyte log by reading it in chunks and keeping only running sums per key.
- **Reducing cloud cost.** Smaller dtypes make a stored table smaller, so it loads faster and uses a smaller machine.
- **Protecting a column.** A categorical with a fixed list of valid statuses turns unexpected values into `NaN`, which a check can then catch.

## Daily review

### Key takeaways

- Use `memory_usage(deep=True)`; without `deep` the text cost is hidden.
- Downcast numbers after checking their range; use `category` for repeated text.
- `chunksize` gives pieces; keep results that can be combined (sums and counts).
- `usecols` and `dtype` reduce memory at load time.

### Common mistakes

- Reading `memory_usage()` without `deep=True` and concluding a text column is tiny.
- Downcasting to `int8` a column with values over 127: they wrap to wrong numbers. Check `min` and `max` first, or use `to_numeric(downcast=...)`.
- Converting a column of unique ids to `category`: no saving, since every value is a category. Convert only low-cardinality columns.
- Averaging per-chunk means: this is wrong when chunks have different sizes. Keep sums and counts and divide at the end.

### Revision notes

- `int8` holds -128 to 127; `int16` to 32,767.
- Category: few distinct values, many rows.
- `observed=True` when grouping by a category.
- A chunk result must be combinable.

## Objectives

- Separate transient errors (worth retrying) from permanent errors (never retry) and handle each correctly.
- Write a retry policy with exponential backoff and a cap, tested with a fake clock so no test ever waits.
- Emit structured logs to standard output with a configured handler, one event per line with named fields.
- Quarantine bad records with their reason instead of failing the run or silently dropping them, and keep the counts reconciled.

## Understand

### Things go wrong

Every pipeline meets failures: the API times out, the database refuses a connection for a second, one CSV row has a letter where a number belongs. What the pipeline does next separates a reliable system from one that needs a person at night. There are three decisions. Is the failure worth **retrying**? If the operation cannot succeed, how does the failure become visible, in a **log** someone can search? And if only some records are bad, does the whole run stop, or are the bad ones set aside, **quarantined**, so the good ones continue?

### Transient and permanent errors

A **transient error** is one that may disappear if you wait: a network timeout, an API answering 429 (too many requests) or 503 (unavailable), a database restarting. A **permanent error** will fail the same way every time: a wrong password, a malformed request (400), a missing table, a row that violates a rule. Retrying a permanent error wastes time and, for an API with a quota, can make things worse. Retrying everything is the commonest mistake; the second is retrying nothing. The first step of a policy is therefore a **classification**: catch the library's exceptions and convert them into your own two types (`TransientError`, `PermanentError`), and let the retry logic look only at those. Unknown exceptions are treated as permanent: failing loudly is safer than looping on a bug.

### Retry policy

A **retry policy** states how many attempts are made, how long to wait between them and when to give up. **Exponential backoff** doubles the wait after each failure (1 s, 2 s, 4 s, 8 s), which gives a struggling service room to recover instead of hammering it at a fixed rhythm. A **cap** (a maximum delay, for example 8 s) stops the waits from growing without limit. A **maximum number of attempts** ends the loop and raises the last error, so the failure reaches the scheduler and the on-call person. Real policies also add **jitter** (a small random amount) so that many clients do not retry at the same instant, and respect a server's `Retry-After` header when one is sent, as you did on the API days. A retry is only safe when the operation is idempotent (Day 124): retrying an insert that actually succeeded before the timeout would create a duplicate unless the load replaces rows by key.

### Testing with a fake clock

A policy that waits 1, 2, 4 and 8 real seconds makes a test slow, and tests that sleep are tests that get skipped. The fix is to **inject the clock**, as Day 121 injected the source and the sink: `with_retries(fn, max_attempts, sleep)` takes `sleep` as an argument. Production passes `time.sleep`; a test passes `delays.append`, a function that records the requested wait and returns at once. The test then asserts the exact sequence of delays, `[1.0, 2.0, 4.0]`, in microseconds. A fake function that fails a chosen number of times and then succeeds completes the picture.

### Structured logging

A log line such as `Loaded 120 rows` is readable by a person and awkward for a machine. A **structured log** writes one event per line with named fields, commonly as JSON: `{"level": "INFO", "event": "load_finished", "rows": 120, "run_id": "r42"}`. A log system can then count events, filter by `run_id` and chart rows over time, with no text parsing. Python's `logging` module does the plumbing: a **logger** (named, here `etl`), a **handler** that decides where the lines go and a **formatter** that decides how they look. A pipeline logs to **standard output**, not to a file it manages, so the platform that runs it (scheduler, container) can collect the stream. Configure the handler explicitly with `logging.StreamHandler(sys.stdout)`: without a handler, Python's last-resort handler prints warnings to standard error, which mixes streams. Never log secrets (Day 122) and log events with counts, not every row.

### Quarantining bad records

When a few of a million rows are bad, stopping the run punishes the good ones, and silently dropping the bad ones hides data loss. The usual answer is a **quarantine**: a table (or file) of rejected records with the raw content, the reason and the run identifier, kept for a human to inspect and, once the cause is fixed, to reprocess. The run then loads the good rows and reports `read = loaded + quarantined`, which is Day 95's reconciliation. A **threshold** guards against a disaster hidden in the quarantine: if more than, say, 5 percent of rows are quarantined, the run fails, because that means the source or the rule is broken, not a handful of records.

### Why it matters in data work

Pipelines run unattended. The combination of correct retries, searchable logs and a quarantine means that a transient glitch heals itself, a permanent problem is noticed and explained, and bad data is neither lost nor allowed to stop everything.

| Item | What it does or returns |
|---|---|
| `backoff_delay(n)` | `min(base * 2 ** (n - 1), cap)` seconds before retry number n. |
| `with_retries(fn, max_attempts, sleep)` | Calls `fn`, retries `TransientError` with backoff, re-raises after the last attempt. |
| `sleep` argument | `time.sleep` in production, a recording function in tests. |
| `logging.getLogger(name)` | The named logger. |

| `Formatter.format(record)` | Turns a log record into the text of one line. |
| `extra={"fields": {...}}` | Attaches named fields to a log record. |
| quarantine row | Raw record, reason and run id of a rejected record. |

## Learn by example

### Example 1: Backoff with a cap

The delay doubles with each attempt and stops growing at the cap. The list shows the waits a client would make over seven failures. The values are computed, not measured, so they are the same on every machine.

```python run
def backoff_delay(attempt, base=1.0, cap=8.0):
    return min(base * 2 ** (attempt - 1), cap)

print([backoff_delay(n) for n in range(1, 8)])
print("total wait over 7 retries:", sum(backoff_delay(n) for n in range(1, 8)), "seconds")
print("slower start:", [backoff_delay(n, base=0.5, cap=3.0) for n in range(1, 6)])
```

```output
[1.0, 2.0, 4.0, 8.0, 8.0, 8.0, 8.0]
total wait over 7 retries: 39.0 seconds
slower start: [0.5, 1.0, 2.0, 3.0, 3.0]
```
### Example 2: Retries with a fake clock

The flaky function fails twice with a transient error and then succeeds. The fake `sleep` records the requested delays instead of waiting. A permanent error is raised at once with no waiting, and a function that never succeeds raises after the last attempt.

```python run
class TransientError(Exception):
    """Might work if tried again: timeout, 429, 503."""

class PermanentError(Exception):
    """Will never work: bad credentials, bad request."""

def backoff_delay(attempt, base=1.0, cap=8.0):
    """Delay in seconds before retry number `attempt` (1, 2, 3, ...)."""
    return min(base * 2 ** (attempt - 1), cap)

def with_retries(fn, max_attempts, sleep):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except TransientError:
            if attempt == max_attempts:
                raise
            sleep(backoff_delay(attempt))

def flaky(failures):
    state = {"calls": 0}
    def fn():
        state["calls"] += 1
        if state["calls"] <= failures:
            raise TransientError("timeout")
        return "ok"
    return fn, state

waits = []
fn, state = flaky(2)
print(with_retries(fn, 5, waits.append), "after", state["calls"], "calls; waits", waits)

waits = []
def bad_password():
    raise PermanentError("401")
try:
    with_retries(bad_password, 5, waits.append)
except PermanentError as exc:
    print("permanent error raised at once:", exc, "waits", waits)

waits = []
fn, state = flaky(10)
try:
    with_retries(fn, 3, waits.append)
except TransientError as exc:
    print("gave up after", state["calls"], "calls; waits", waits)
```

```output
ok after 3 calls; waits [1.0, 2.0]
permanent error raised at once: 401 waits []
gave up after 3 calls; waits [1.0, 2.0]
```
### Example 3: Structured logs to standard output

A formatter turns each record into one JSON line with sorted keys and no timestamp, so the output is stable. The handler writes to `sys.stdout`. The run logs the events of a small load, with a `run_id` on every line.

```python run
import json
import logging
import sys

class JsonFormatter(logging.Formatter):
    def format(self, record):
        data = {"level": record.levelname, "event": record.getMessage()}
        data.update(getattr(record, "fields", {}))
        return json.dumps(data, sort_keys=True)

logger = logging.getLogger("etl")
logger.setLevel(logging.INFO)
logger.propagate = False
handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(JsonFormatter())
logger.addHandler(handler)

run = {"run_id": "r42"}
logger.info("run_started", extra={"fields": {**run, "window": "2025-03-04"}})
logger.warning("row_quarantined", extra={"fields": {**run, "order_id": 4, "reason": "bad amount"}})
logger.info("run_finished", extra={"fields": {**run, "read": 7, "loaded": 5, "quarantined": 1}})
logger.debug("not shown at INFO level")
```

```output
{"event": "run_started", "level": "INFO", "run_id": "r42", "window": "2025-03-04"}
{"event": "row_quarantined", "level": "WARNING", "order_id": 4, "reason": "bad amount", "run_id": "r42"}
{"event": "run_finished", "level": "INFO", "loaded": 5, "quarantined": 1, "read": 7, "run_id": "r42"}
```
### Example 4: Quarantine instead of failing

Each row is processed on its own. A row that raises a `ValueError` goes to the quarantine list with its raw text and a reason, and the run continues. The counts reconcile, and a threshold decides whether the run as a whole is acceptable.

```python run
rows = [("1", "19.90"), ("2", "abc"), ("3", "40.00"), ("4", ""), ("5", "12.00"), ("6", "7.50"), ("7", "3.25"), ("8", "1.00"), ("9", "2.00"), ("10", "8.00")]
good, quarantine = [], []
for order_id, amount in rows:
    try:
        good.append((int(order_id), round(float(amount) * 100)))
    except ValueError:
        quarantine.append({"order_id": order_id, "raw": amount, "reason": "not a number"})

print("read", len(rows), "loaded", len(good), "quarantined", len(quarantine))
print("reconciles:", len(rows) == len(good) + len(quarantine))
for q in quarantine:
    print(q["order_id"], repr(q["raw"]), "->", q["reason"])
rate = len(quarantine) / len(rows)
print(f"quarantine rate {rate:.0%}:", "run fails" if rate > 0.05 else "run accepted")
```

```output
read 10 loaded 8 quarantined 2
reconciles: True
2 'abc' -> not a number
4 '' -> not a number
quarantine rate 20%: run fails
```
### Example 5: A run with retries, logging and quarantine together

The extract function is flaky and succeeds on its third call; the transform quarantines one row; the load goes into `sqlite3`. The log lines record each retry and each outcome, and the run returns a result. This is the shape of a pipeline run you can trust.

```python run
import json
import logging
import sqlite3
import sys
class TransientError(Exception):
    """Might work if tried again: timeout, 429, 503."""

class PermanentError(Exception):
    """Will never work: bad credentials, bad request."""

def backoff_delay(attempt, base=1.0, cap=8.0):
    """Delay in seconds before retry number `attempt` (1, 2, 3, ...)."""
    return min(base * 2 ** (attempt - 1), cap)

def with_retries(fn, max_attempts, sleep):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except TransientError:
            if attempt == max_attempts:
                raise
            sleep(backoff_delay(attempt))

class JsonFormatter(logging.Formatter):
    def format(self, record):
        data = {"level": record.levelname, "event": record.getMessage()}
        data.update(getattr(record, "fields", {}))
        return json.dumps(data, sort_keys=True)

log = logging.getLogger("etl2")
log.setLevel(logging.INFO)
log.propagate = False
handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(JsonFormatter())
log.addHandler(handler)

calls = {"n": 0}
def extract():
    calls["n"] += 1
    if calls["n"] < 3:
        raise TransientError("timeout")
    return [("1", "19.90"), ("2", "abc"), ("3", "40.00")]

def sleep_and_log(seconds):
    log.warning("retry", extra={"fields": {"wait": seconds}})

rows = with_retries(extract, 5, sleep_and_log)
good, bad = [], []
for oid, amount in rows:
    try:
        good.append((int(oid), round(float(amount) * 100)))
    except ValueError:
        bad.append(oid)
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER)")
with conn:
    conn.executemany("INSERT INTO orders_clean VALUES (?, ?)", good)
log.info("run_finished", extra={"fields": {"read": len(rows), "loaded": len(good), "quarantined": len(bad), "attempts": calls["n"]}})
```

```output
{"event": "retry", "level": "WARNING", "wait": 1.0}
{"event": "retry", "level": "WARNING", "wait": 2.0}
{"attempts": 3, "event": "run_finished", "level": "INFO", "loaded": 2, "quarantined": 1, "read": 3}
```
## Real-world applications

- **Flaky APIs.** A retry with backoff and a cap (Examples 1 and 2) turns a brief 503 or a rate-limit response into a short pause, and a permanent 401 into an immediate, clear failure.
- **Searchable run history.** Structured lines with a `run_id` (Example 3) let a team find every event of one night's run and chart `quarantined` over weeks.
- **Dirty source files.** A quarantine table (Example 4) holds the bad rows for the data owner to fix while the rest of the file loads.
- **Fast tests.** Injecting the clock means the retry policy is tested in milliseconds, so it really is tested.

## Daily review

### Key takeaways

- Classify errors as transient or permanent; retry only transient ones; treat unknown errors as permanent.
- Exponential backoff with a cap and a maximum number of attempts, plus jitter and `Retry-After` in real systems.
- Inject the sleep function so tests use a fake clock and finish instantly.
- Log one JSON event per line to standard output with a configured handler; never log secrets.
- Quarantine bad records with raw value, reason and run id, keep `read = loaded + quarantined`, and fail the run above a threshold.

### Common mistakes

- Retrying every exception, so a wrong password is tried five times and a bug loops. Retry only the transient type.
- Retrying a non-idempotent write, which can duplicate rows when the first attempt actually succeeded. Make the load a replace or upsert first.
- Retrying without any delay or limit, hammering a failing service. Use backoff, a cap and a maximum.
- Printing log lines as free text, which cannot be filtered. Emit named fields.
- Dropping bad rows silently, so counts no longer add up and nobody knows. Quarantine them and reconcile.
- Calling `logging.warning` with no handler configured; the output goes to standard error. Configure a stdout handler.

### Revision notes

- `delay = min(base * 2 ** (attempt - 1), cap)`; stop at `max_attempts`; re-raise.
- `with_retries(fn, max_attempts, sleep)`; tests pass `delays.append`.
- Logger, handler (`StreamHandler(sys.stdout)`), formatter (JSON, sorted keys).
- Quarantine: raw, reason, run id; threshold on the rate.

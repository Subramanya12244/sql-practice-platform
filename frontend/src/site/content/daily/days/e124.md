## Objectives

- Define a full load (full refresh) and list when it is the right choice and when it is not.
- Implement three safe full-refresh patterns: delete and insert in one transaction, truncate and insert, and build-and-swap.
- Make every step of the orders pipeline safe to run twice, not only the final insert.
- Test idempotency by running a step twice and comparing the table snapshots.

## Understand

### What a full load is

A **full load** (also called a **full refresh**) replaces the whole content of the target with a fresh copy of the whole source on every run. The pipeline does not ask what changed: it reads everything and writes everything. For the orders pipeline that means extracting the complete orders file, cleaning it (Day 120's `clean_amount`, `parse_ts`, `dedupe_latest`) and making `orders_clean` equal to the result. The opposite is an **incremental load**, which reads only what changed since the last run and which Day 125 covers.

### Why choose a full load

A full load is the simplest correct design, and simple has value. There is no state to store (no watermark), no assumption that the source marks changes reliably, and deletes in the source are handled for free: a row that disappears from the source disappears from the target at the next run. Mistakes heal themselves, because the next run rewrites everything, whatever state the table was in. It fits small and medium tables (thousands to a few million rows, depending on how long the run may take), reference data such as product lists or country codes, and sources that offer no change information at all. It stops fitting when the table is so large that reading everything is slow or expensive, when the source cannot be asked for everything repeatedly (API rate limits), or when the target must keep history that the source no longer holds.

### Idempotency, again, with a purpose

An operation is **idempotent** when running it twice leaves the same state as running it once. Day 94 introduced the idea for loading. Today applies it to the whole pipeline and to full loads in particular. A full load is naturally idempotent if the replacement is done correctly: run it once or five times and the target equals the current source. But it is easy to make it only *almost* idempotent: an `INSERT` without clearing the table first appends the same rows again, doubling the table at every rerun. The exact danger is that nothing fails; the numbers are just wrong, and the symptom (totals exactly two times, then three times too big) appears in reports, not in the pipeline's log.

### Safe patterns for replacing a table

**Delete and insert in one transaction.** Run `DELETE FROM orders_clean` and the `INSERT`s inside a single transaction. A transaction is a group of statements that either all take effect or none do (Day 94). If the insert fails halfway, the delete is rolled back and readers still see the old data. Without the transaction, a failure leaves an empty or half-filled table.

**Truncate and insert.** `TRUNCATE TABLE orders_clean` empties a table faster than `DELETE` on large tables and in PostgreSQL it can be rolled back inside a transaction. It holds a stronger lock, which blocks readers while it runs, and it cannot be used with a `WHERE`, so it is for complete refreshes only.

**Build and swap.** Create `orders_clean_new`, load and validate it completely (row count, key uniqueness), then in one transaction rename `orders_clean` to `orders_clean_old` and `orders_clean_new` to `orders_clean`, and drop the old one. Readers never see a half-built table. This is the pattern for tables that people query while the load runs. It needs permission to create tables, and views or grants that point at the old name must be handled.

### Idempotent steps, not only idempotent loads

The final write is only one step. Creating the table should be `CREATE TABLE IF NOT EXISTS`. A raw file download should write to a deterministic name for the window (`orders_2025-03-04.csv`), not to a name with a timestamp, so a rerun overwrites the file instead of adding a second. Anything that sends something outside the database (an email, a message) needs its own guard, because a rerun would send it again. The test is simple: if the whole pipeline ran twice in a row, would anything be different the second time, other than the run log?

### Testing a rerun

An idempotency test **snapshots** the target after run one (all rows sorted by key), runs the pipeline again on the same input, snapshots again and compares. It is cheap and catches the doubled table before production does. A misconception is that a primary key makes any load idempotent: with a primary key a second plain insert fails with a constraint error, which is safer than silently duplicating, but a failed run is still not a safe rerun. Another is that full loads are "inefficient"; they are the most robust design, and efficiency is a question to ask only when the size or the source demands it.

### Why it matters in data work

Runs are repeated in real life: schedulers retry, engineers rerun after a fix, a backfill covers dates that were already loaded. A pipeline that cannot be rerun safely makes every one of those events an incident.

## Syntax and key functions

```python
with conn:                                   # one transaction: commit on success, rollback on error
    conn.execute("DELETE FROM orders_clean")
    conn.executemany("INSERT INTO orders_clean VALUES (?,?,?,?,?,?)", rows)
```

```sql-syntax
BEGIN;
ALTER TABLE orders_clean RENAME TO orders_clean_old;
ALTER TABLE orders_clean_new RENAME TO orders_clean;
COMMIT;
DROP TABLE orders_clean_old;
```

| Item | What it does or returns |
|---|---|
| `with conn:` | Commits if the block succeeds, rolls back if it raises. |
| `DELETE FROM t` | Removes all rows; can be rolled back; slower on huge tables. |
| `TRUNCATE TABLE t` | PostgreSQL: empties the table quickly; allowed inside a transaction; no `WHERE`. |
| `CREATE TABLE IF NOT EXISTS` | Creates the table only when missing; safe to rerun. |
| `ALTER TABLE a RENAME TO b` | Renames a table; the heart of build-and-swap. |
| `INSERT INTO t SELECT ...` | Fills a table from a query inside the database. |
| snapshot | `sorted(conn.execute("SELECT ..."))` taken before and after a rerun. |

## Learn by example

### Example 1: The append bug and the full refresh

The first loader only inserts, so each run adds the same rows again. The second deletes and inserts inside one transaction, so every run leaves the table equal to the source. The counts after three runs show the difference.

```python run
import sqlite3

source = [(1, 1990), (2, 125000), (3, 4500), (4, 750), (5, 1200)]

def fresh():
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE orders_clean (order_id INTEGER, amount_cents INTEGER)")
    return conn

def append_load(conn):
    with conn:
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?)", source)

def refresh_load(conn):
    with conn:
        conn.execute("DELETE FROM orders_clean")
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?)", source)

count = lambda c: c.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0]
a, b = fresh(), fresh()
for run in (1, 2, 3):
    append_load(a)
    refresh_load(b)
    print(f"after run {run}: append={count(a)} refresh={count(b)}")
```

```output
after run 1: append=5 refresh=5
after run 2: append=10 refresh=5
after run 3: append=15 refresh=5
```
### Example 2: A failure halfway leaves the old data

The source has a bad row that makes the third insert fail. Because delete and insert share one transaction, the failure rolls everything back, and readers still see the old three rows. Without the transaction the table would be empty or partly loaded.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER NOT NULL)")
conn.executemany("INSERT INTO orders_clean VALUES (?, ?)", [(1, 100), (2, 200), (3, 300)])
conn.commit()

new_source = [(10, 1000), (11, 1100), (12, None), (13, 1300)]
try:
    with conn:
        conn.execute("DELETE FROM orders_clean")
        for row in new_source:
            conn.execute("INSERT INTO orders_clean VALUES (?, ?)", row)
except sqlite3.IntegrityError as exc:
    print("load failed:", type(exc).__name__)
print("table still has:", conn.execute("SELECT order_id FROM orders_clean ORDER BY order_id").fetchall())
```

```output
load failed: IntegrityError
table still has: [(1,), (2,), (3,)]
```
### Example 3: Build and swap

The new table is built and checked first, then renamed into place inside one explicit transaction (`isolation_level=None` gives manual control of `BEGIN` and `COMMIT`). If the check fails, the live table is untouched. The same statements work in PostgreSQL.

```python run
import sqlite3

conn = sqlite3.connect(":memory:", isolation_level=None)
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER)")
conn.executemany("INSERT INTO orders_clean VALUES (?, ?)", [(1, 100), (2, 200)])

def swap_in(rows):
    conn.execute("DROP TABLE IF EXISTS orders_clean_new")
    conn.execute("CREATE TABLE orders_clean_new (order_id INTEGER PRIMARY KEY, amount_cents INTEGER)")
    conn.executemany("INSERT INTO orders_clean_new VALUES (?, ?)", rows)
    n = conn.execute("SELECT COUNT(*) FROM orders_clean_new").fetchone()[0]
    if n == 0:
        conn.execute("DROP TABLE orders_clean_new")
        return "rejected: new table is empty"
    conn.execute("BEGIN")
    conn.execute("ALTER TABLE orders_clean RENAME TO orders_clean_old")
    conn.execute("ALTER TABLE orders_clean_new RENAME TO orders_clean")
    conn.execute("COMMIT")
    conn.execute("DROP TABLE orders_clean_old")
    return f"swapped in {n} rows"

print(swap_in([]))
print(swap_in([(1, 150), (2, 250), (3, 350)]))
print(swap_in([(1, 150), (2, 250), (3, 350)]))
print(conn.execute("SELECT * FROM orders_clean ORDER BY order_id").fetchall())
```

```output
rejected: new table is empty
swapped in 3 rows
swapped in 3 rows
[(1, 150), (2, 250), (3, 350)]
```
### Example 4: Truncate and insert on PostgreSQL syntax (PGlite)

The refresh is `TRUNCATE` followed by `INSERT ... SELECT` from a staging table, and the block runs it twice. The final count and sum show that the second refresh left the same table as the first.

```sql run
CREATE TABLE stg_orders (order_id int, amount_cents int);
CREATE TABLE orders_clean (order_id int PRIMARY KEY, amount_cents int);
INSERT INTO stg_orders VALUES (1, 1990), (2, 125000), (3, 4500), (4, 750), (5, 1200);
TRUNCATE orders_clean;
INSERT INTO orders_clean SELECT order_id, amount_cents FROM stg_orders;
TRUNCATE orders_clean;
INSERT INTO orders_clean SELECT order_id, amount_cents FROM stg_orders;
SELECT COUNT(*) AS rows, SUM(amount_cents) AS total_cents FROM orders_clean;
```

```output
rows | total_cents
5 | 133440
```
### Example 5: A rerun test

`assert_idempotent` runs a loader twice and compares the sorted snapshots. It reports the append loader as failing and the refresh loader as passing. Test results like these belong in the pipeline's test suite.

```python run
import sqlite3

source = [(1, 1990), (2, 125000), (3, 4500)]

def snapshot(conn):
    return sorted(conn.execute("SELECT order_id, amount_cents FROM orders_clean"))

def assert_idempotent(loader):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE IF NOT EXISTS orders_clean (order_id INTEGER, amount_cents INTEGER)")
    loader(conn)
    first = snapshot(conn)
    loader(conn)
    return "PASS" if snapshot(conn) == first else f"FAIL ({len(first)} rows became {len(snapshot(conn))})"

def append_loader(conn):
    with conn:
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?)", source)

def refresh_loader(conn):
    with conn:
        conn.execute("DELETE FROM orders_clean")
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?)", source)

print("append :", assert_idempotent(append_loader))
print("refresh:", assert_idempotent(refresh_loader))
```

```output
append : FAIL (3 rows became 6)
refresh: PASS
```
## Real-world applications

- **Reference tables.** Product catalogues, country codes and price lists are small and change rarely; a full refresh (Examples 1 and 4) keeps them equal to the source with no state.
- **Reports that people read during the load.** Build-and-swap (Example 3) gives analysts a table that is always complete, never half loaded.
- **Retries and reruns.** A scheduler that retries a failed task, or an engineer who reruns after a fix, is safe when the load passes the rerun test of Example 5.
- **Healing after a bad run.** If a rule was wrong yesterday, the next full refresh with the corrected rule rewrites the table, with no cleanup script.

## Daily review

### Key takeaways

- A full load replaces the target with the whole source; it is simple, handles deletes and heals mistakes.
- It is idempotent only if the replacement is real: clear and insert in one transaction, truncate and insert, or build and swap.
- A plain `INSERT` into a non-empty table is the classic way to double data silently.
- Make every step safe to rerun: `IF NOT EXISTS`, deterministic file names, guards on outside effects.
- Test by running twice and comparing sorted snapshots.

### Common mistakes

- Appending without clearing, so every rerun doubles the totals. Clear in the same transaction as the insert.
- Deleting in one transaction and inserting in another; a crash between them leaves an empty table. Use one transaction.
- Truncating a table that readers use during business hours, which blocks them. Use build-and-swap for such tables.
- Naming the downloaded file with the current timestamp, so each rerun stores another copy. Use the window or date.
- Assuming a primary key makes a rerun safe; the second run fails with a constraint error. Make the load replace, not collide.

### Revision notes

- Full load: read everything, replace everything.
- Patterns: `with conn:` delete plus insert; `TRUNCATE` plus `INSERT ... SELECT`; build `_new`, rename in a transaction.
- Idempotent steps: `IF NOT EXISTS`, deterministic names.
- Test: run twice, compare sorted snapshots.

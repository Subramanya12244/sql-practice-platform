## Understand

### From a loaded table to answers

Days 101 to 111 produced a validated `orders` table: one row per order with `order_id`, `customer_id`, `amount_cents`, `currency`, `status` and `created_at`. This final lesson of the block asks questions of it. The analysis is done in SQL, inside the database, for the reasons of Day 115 (which compares SQL and pandas): the data is already there, the database aggregates many rows quickly, and a query is shareable and repeatable. The browser database already contains Northwind's `orders` table, so the examples use a table called `shop_orders` that is built inside each block with `generate_series` from the same formulas as the stand-in API, so the numbers are the same in every example. The same SQL runs on a PostgreSQL server unchanged.

### Aggregation with groups and filters

An **aggregate function** (`count`, `sum`, `avg`, `min`, `max`) collapses many rows into one value; `GROUP BY` collapses them per group. The questions an orders table answers are typically: how many orders and how much money per status, per currency, per day, per customer. Two details deserve care. **Money**: `amount_cents` is an integer count of cents; sum it as an integer and divide by 100 at the end. A `sum` of `bigint` values returns `numeric` or `bigint` depending on the input type, and `avg` returns `numeric`; a `real` or `double precision` value must be cast to `numeric` before `round(x, 1)` because PostgreSQL's two-argument `round` exists only for `numeric`. **Conditional counts**: `count(*) FILTER (WHERE status = 'refunded')` counts a subset inside one pass, so a single query can return orders, refunded orders and the refund rate side by side. Revenue questions need a business rule: here "revenue" means `paid` orders only, refunded and failed ones excluded; state the rule in the query name and in the review.

### Time series

A **time series** is a measure over time, here revenue per day. Group by the day of `created_at`. Because `created_at` is a `timestamptz` (a moment with a time zone), convert it first: `(created_at AT TIME ZONE 'UTC')::date` gives the UTC calendar day, and the choice of zone is part of the definition of "day". A subtle trap appears when some days have no orders: `GROUP BY` returns only days that exist, so the series has holes, and charts or moving averages computed on it are wrong. The fix is a **calendar**: `generate_series(date '2026-03-01', date '2026-03-07', interval '1 day')` produces every day, and a `LEFT JOIN` from the calendar to the aggregated data with `coalesce(x, 0)` fills the holes with zero.

### Window functions

A **window function** computes a value for each row using a set of related rows (its window) without collapsing them, unlike `GROUP BY`. The syntax is `function(...) OVER (PARTITION BY ... ORDER BY ... frame)`. `PARTITION BY` splits the rows into independent groups; `ORDER BY` orders rows within a group; the **frame** (`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`) says which neighbours are included. The functions used today:

- `sum(x) OVER (ORDER BY day)`: a **running total** (the default frame runs from the first row to the current one).
- `avg(x) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)`: a **moving average** over the last three days. Its first two values use fewer than three days; decide whether that is acceptable or whether to hide them.
- `lag(x) OVER (ORDER BY day)`: the previous row's value, so `x - lag(x)` is a **day-over-day change** (NULL on the first row).
- `rank() OVER (ORDER BY x DESC)`: the position in an ordering, with ties sharing a rank and gaps after them; `dense_rank()` leaves no gaps.
- `sum(x) OVER ()`: the total over all rows, so `100.0 * x / sum(x) OVER ()` is each row's **share of the total**.

Window functions run after `GROUP BY`, so a window may use an aggregate: `sum(sum(amount_cents)) OVER ()` is a total of the per-group sums. Because a query that uses window functions may still order its output arbitrarily, always finish with `ORDER BY` and `LIMIT`.

### Views

A **view** is a saved query with a name: `CREATE VIEW daily_revenue AS SELECT ...`. Selecting from it runs the query. Views give analysts one agreed definition of "paid revenue per day" so that every dashboard computes it the same way, and they hide the cleaning rules. A view stores no data. A **materialised view** (`CREATE MATERIALIZED VIEW`) in PostgreSQL stores the result and needs `REFRESH MATERIALIZED VIEW` to update it; it trades freshness for speed on large tables.

### Common misconception

Learners write a moving average or a running total on a grouped result without a calendar and trust the chart. A missing day shifts every following value into the wrong window. Check that the series has one row per day before applying windows. A second trap is summing `numeric` percentages, or rounding before summing; round only at the end.

### Why it matters

The business sees the analysis, not the pipeline. The quality of the answer depends on a clear revenue definition, a series without holes and windows with the right frame, which are all small choices in the SQL.

## Syntax and key functions

```sql-syntax
-- running total, 3-day moving average, day-over-day change
SELECT day, paid_cents,
       sum(paid_cents) OVER (ORDER BY day) AS running_cents,
       avg(paid_cents) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS moving_avg,
       paid_cents - lag(paid_cents) OVER (ORDER BY day) AS change
FROM daily;

-- calendar with gaps filled
SELECT d::date AS day, coalesce(x.cents, 0) AS cents
FROM generate_series(date '2026-03-01', date '2026-03-07', interval '1 day') AS d
LEFT JOIN daily_cents x ON x.day = d::date;

CREATE VIEW daily_revenue AS SELECT ...;
CREATE MATERIALIZED VIEW daily_revenue_mv AS SELECT ...;
REFRESH MATERIALIZED VIEW daily_revenue_mv;
```

| Item | What it does or returns |
|---|---|
| `count(*) FILTER (WHERE cond)` | Count of the rows meeting a condition. |
| `(created_at AT TIME ZONE 'UTC')::date` | The UTC calendar day of a `timestamptz`. |
| `generate_series(start, stop, step)` | One row per step; the base of a calendar. |
| `sum / avg / lag / rank OVER (...)` | Window versions: running total, moving average, previous row, rank. |
| `ROWS BETWEEN n PRECEDING AND CURRENT ROW` | Frame of the last `n + 1` rows. |
| `100.0 * x / sum(x) OVER ()` | Share of the total. |
| `CREATE VIEW name AS query` | A named, stored query (no data stored). |
| `round(x::numeric, n)` | Rounding; cast first when `x` is not `numeric`. |

### Example 1: Aggregates and conditional counts

The table is built from the same formulas as the stand-in API. The query groups by status and currency, counts the orders, sums the cents and averages them (cast to `numeric` before `round`). `FILTER` is shown in the second query, which returns the order count, the refunded count and the refund rate for each currency in one pass.

```sql run
CREATE TABLE shop_orders AS
SELECT i AS order_id, i * 7 % 25 + 1 AS customer_id, 1000 + i * 137 % 9000 AS amount_cents,
       CASE WHEN i % 4 = 0 THEN 'USD' ELSE 'EUR' END AS currency,
       (ARRAY['paid', 'paid', 'refunded', 'failed'])[i % 4 + 1] AS status,
       ('2026-03-01T00:00:00Z'::timestamptz + ((i - 1) / 4) * interval '1 day'
        + (i * 7 % 24) * interval '1 hour' + (i * 13 % 60) * interval '1 minute') AS created_at
FROM generate_series(1, 120) AS i;
SELECT status, currency, count(*) AS orders, sum(amount_cents) AS cents,
       round(avg(amount_cents)::numeric, 1) AS avg_cents
FROM shop_orders
GROUP BY status, currency
ORDER BY status, currency;
```

### Example 2: A time series without holes

Customer 9 orders on only a few days. Grouping by day returns only those days. The calendar from `generate_series`, left-joined to the grouped result with `coalesce`, returns one row for each of the first ten days of March, with zeros where the customer had no orders.

```sql run
CREATE TABLE shop_orders AS
SELECT i AS order_id, i * 7 % 25 + 1 AS customer_id, 1000 + i * 137 % 9000 AS amount_cents,
       CASE WHEN i % 4 = 0 THEN 'USD' ELSE 'EUR' END AS currency,
       (ARRAY['paid', 'paid', 'refunded', 'failed'])[i % 4 + 1] AS status,
       ('2026-03-01T00:00:00Z'::timestamptz + ((i - 1) / 4) * interval '1 day'
        + (i * 7 % 24) * interval '1 hour' + (i * 13 % 60) * interval '1 minute') AS created_at
FROM generate_series(1, 120) AS i;
WITH per_day AS (
    SELECT (created_at AT TIME ZONE 'UTC')::date AS day, count(*) AS orders, sum(amount_cents) AS cents
    FROM shop_orders
    WHERE customer_id = 9
    GROUP BY 1
)
SELECT d::date AS day, coalesce(p.orders, 0) AS orders, coalesce(p.cents, 0) AS cents
FROM generate_series(date '2026-03-01', date '2026-03-10', interval '1 day') AS d
LEFT JOIN per_day p ON p.day = d::date
ORDER BY day;
```

### Example 3: Running total, moving average and change

`daily` holds paid revenue per day (revenue means paid orders only). The window functions add the running total, the 3-day moving average and the day-over-day change with `lag`. The first row has no previous day, so its change is NULL, and the first two moving averages use fewer than three days.

```sql run
CREATE TABLE shop_orders AS
SELECT i AS order_id, i * 7 % 25 + 1 AS customer_id, 1000 + i * 137 % 9000 AS amount_cents,
       CASE WHEN i % 4 = 0 THEN 'USD' ELSE 'EUR' END AS currency,
       (ARRAY['paid', 'paid', 'refunded', 'failed'])[i % 4 + 1] AS status,
       ('2026-03-01T00:00:00Z'::timestamptz + ((i - 1) / 4) * interval '1 day'
        + (i * 7 % 24) * interval '1 hour' + (i * 13 % 60) * interval '1 minute') AS created_at
FROM generate_series(1, 120) AS i;
WITH daily AS (
    SELECT (created_at AT TIME ZONE 'UTC')::date AS day, sum(amount_cents) AS paid_cents
    FROM shop_orders
    WHERE status = 'paid'
    GROUP BY 1
)
SELECT day, paid_cents,
       sum(paid_cents) OVER (ORDER BY day) AS running_cents,
       round(avg(paid_cents) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 1) AS moving_avg_3d,
       paid_cents - lag(paid_cents) OVER (ORDER BY day) AS change
FROM daily
ORDER BY day
LIMIT 7;
```

### Example 4: A view, ranks and shares

The view `customer_revenue` is the agreed definition of paid revenue per customer. The query on top of it ranks the customers by revenue with `rank()` and shows each one's share of all paid revenue with a window over the whole result. Ties share a rank, and ranks skip after a tie.

```sql run
CREATE TABLE shop_orders AS
SELECT i AS order_id, i * 7 % 25 + 1 AS customer_id, 1000 + i * 137 % 9000 AS amount_cents,
       CASE WHEN i % 4 = 0 THEN 'USD' ELSE 'EUR' END AS currency,
       (ARRAY['paid', 'paid', 'refunded', 'failed'])[i % 4 + 1] AS status,
       ('2026-03-01T00:00:00Z'::timestamptz + ((i - 1) / 4) * interval '1 day'
        + (i * 7 % 24) * interval '1 hour' + (i * 13 % 60) * interval '1 minute') AS created_at
FROM generate_series(1, 120) AS i;
CREATE VIEW customer_revenue AS
SELECT customer_id, count(*) AS paid_orders, sum(amount_cents) AS paid_cents
FROM shop_orders
WHERE status = 'paid'
GROUP BY customer_id;

SELECT customer_id, paid_orders, paid_cents,
       rank() OVER (ORDER BY paid_cents DESC) AS revenue_rank,
       round(100.0 * paid_cents / sum(paid_cents) OVER (), 1) AS share_pct
FROM customer_revenue
ORDER BY revenue_rank, customer_id
LIMIT 5;
```

```output

13 | 3 | 17701 | 2 | 5.6
6 | 2 | 16385 | 3 | 5.2
10 | 3 | 16057 | 4 | 5.1
20 | 3 | 15962 | 5 | 5.1
```

### Example 5: The same series in pandas, as a cross-check

The same 120 orders are built in pandas. The code computes paid revenue per day, the running total, the 3-day moving average (`rolling(3, min_periods=1)`) and the change with `diff`, and prints the first seven days. The numbers agree with Example 3, which is the cross-check: two tools, one answer.

```python run
import pandas as pd

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

df = pd.DataFrame(ORDERS)
df["day"] = pd.to_datetime(df["created_at"], utc=True).dt.strftime("%Y-%m-%d")
daily = df[df["status"] == "paid"].groupby("day", as_index=False)["amount_cents"].sum().rename(columns={"amount_cents": "paid_cents"})
daily["running_cents"] = daily["paid_cents"].cumsum()
daily["moving_avg_3d"] = daily["paid_cents"].rolling(3, min_periods=1).mean().round(1)
daily["change"] = daily["paid_cents"].diff()
print(daily.head(7).to_string(index=False))
print(len(daily), int(daily["paid_cents"].sum()))
```

## Real-world applications

- **Daily revenue dashboard.** The view `daily_revenue` is the single definition behind the chart; the running total and the moving average smooth the daily noise.
- **Refund monitoring.** The `FILTER` query tracks the refund rate per currency and flags a jump.
- **Customer concentration.** Rank and share of revenue show whether a few customers carry the business.
- **Reliable charts.** A calendar join guarantees one point per day, so a quiet day shows as zero and does not distort a moving average.

## Daily review

### Key takeaways

- Aggregate with `GROUP BY` and `FILTER`; define revenue explicitly (paid only).
- Convert `timestamptz` to a UTC date before grouping by day; fill gaps with a calendar and `LEFT JOIN`.
- Window functions keep every row: running total, moving average with a frame, `lag` for change, `rank`, share with `sum() OVER ()`.
- A view names an agreed query; a materialised view stores the result and needs a refresh.
- Cross-check key numbers with a second tool.

### Common mistakes

- **Windows on a series with holes.** Missing days shift the frame. Join a calendar first.
- **`round` on a non-`numeric` value.** PostgreSQL has no two-argument `round` for `double precision`. Cast with `::numeric`.
- **Grouping by `created_at::date` without a time zone decision.** The day boundary moves. Use `AT TIME ZONE 'UTC'`.
- **Counting refunded and failed orders as revenue.** Filter to `paid`, and state it in the name of the view.
- **No `ORDER BY` in the final query.** Row order is undefined. Sort and limit.

### Revision notes

- `count(*) FILTER (WHERE ...)`, `(created_at AT TIME ZONE 'UTC')::date`.
- `generate_series` + `LEFT JOIN` + `coalesce`.
- `sum() OVER (ORDER BY ...)`, `avg() OVER (... ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)`, `lag()`, `rank()`, `sum() OVER ()`.
- `CREATE VIEW`; `REFRESH MATERIALIZED VIEW`.

## Objectives

- Create the star schema `fact_sales`, `dim_customer`, `dim_product` and `dim_date` with surrogate keys and constraints.
- Load dimensions with upserts so that loading the same data twice changes nothing, and keep customer history with valid dates.
- Load the fact table incrementally with a watermark, looking up surrogate keys, and prove that a re-run adds no rows.
- Check the load: row counts, no orphan keys, and the fact total equal to the paid total of the clean data.
- Write the PostgreSQL form of the schema and the upsert, and say where `sqlite3` differs.

## Understand

### What the warehouse stage builds

Day 175 produced a clean set of 114 orders. This stage loads it into a **star schema**: a central fact table of events surrounded by dimension tables that describe them. The shared sample used on the engineer path is `fact_sales(sale_id, date_key, customer_key, product_key, quantity, amount_cents)` with `dim_customer(customer_key, customer_id, customer_name, country, valid_from, valid_to, is_current)`, `dim_product(product_key, product_id, product_name, category)` and `dim_date(date_key, full_date, year, month)`. The grain, fixed on Day 173, is one paid order per fact row, so refunded and failed orders are cleaned but not loaded as sales.

### Surrogate keys and the lookup

A **surrogate key** is a meaningless integer the warehouse assigns to a dimension row. The **business key** (`customer_id` such as `C013`) comes from the source. Facts store the surrogate key, so the fact table stays small and a dimension row can change without rewriting facts. Loading a fact row therefore includes a **lookup**: find the dimension row for the order's business key, and store its surrogate key. A lookup that finds nothing is an **orphan**, and the load must not create one; on Day 175 the unknown-customer rule already quarantined such orders.

### History with valid dates

Customers move. If `C005` changes country on 15 February, an order from January belongs to the old country and an order from March to the new one. A **slowly changing dimension of type 2** keeps both versions: the old row is closed by setting `valid_to` and `is_current = 0`, and a new row with a new surrogate key starts at the change date. The fact lookup then picks the row whose validity range contains the order date: `valid_from <= order_date < valid_to`, where the open row ends on `9999-12-31`. Overwriting the country instead (type 1) would silently move January's sales to the new country in every report.

### Upserts make loads repeatable

An **upsert** inserts a row, or updates it when the key already exists. In PostgreSQL and `sqlite3` it is `INSERT ... ON CONFLICT (key) DO UPDATE SET col = excluded.col`, where `excluded` is the row you tried to insert. Dimensions are upserted on the business key and the fact table on `sale_id`. Because the result depends only on the input, not on how often the load ran, a retry after a crash is safe and a re-delivered record updates its row instead of duplicating it.

### Incremental loading with a watermark

A **full load** rewrites everything every night. An **incremental load** processes only what is new. The pipeline stores a **watermark**, the largest `created_at` it has loaded, in a one-row table `etl_state`. The next run selects records with `created_at` greater than the watermark, loads them in a transaction and moves the watermark in the same transaction, so the two never disagree. The weakness is late-arriving data: an order created before the watermark but delivered after it would be skipped. The usual remedies are to reload an overlap window (safe because of the upsert) or to filter by load time instead of event time. This capstone uses event time and relies on the daily reconciliation of Day 178 to notice gaps.

### Common misconception

Learners believe an incremental load is idempotent because it only loads new rows. It is idempotent only if the second run finds nothing new and a repeated row cannot create a duplicate; the primary key plus the upsert guarantee the second part, the watermark the first.

### Why it matters

Every report in the analytics layer of Day 177 reads these tables. A duplicated fact row inflates revenue, an orphan key drops sales from a join, and an overwritten dimension rewrites history.

## Syntax and key functions

The upsert in `sqlite3` and PostgreSQL:

```sql-syntax
INSERT INTO fact_sales (sale_id, date_key, customer_key, product_key, quantity, amount_cents)
VALUES (?, ?, ?, ?, ?, ?)
ON CONFLICT (sale_id) DO UPDATE SET amount_cents = excluded.amount_cents;
```

The type 2 lookup:

```sql-syntax
SELECT customer_key FROM dim_customer
WHERE customer_id = ? AND valid_from <= ? AND ? < valid_to;
```

| Item | What it does or returns |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | SQLite surrogate key; PostgreSQL uses `GENERATED ALWAYS AS IDENTITY`. |
| `ON CONFLICT (key) DO UPDATE` | Upsert; `excluded.col` is the value that was rejected. |
| `INSERT OR IGNORE` | SQLite shorthand that skips existing keys; PostgreSQL uses `ON CONFLICT DO NOTHING`. |
| `valid_from <= d AND d < valid_to` | Picks the dimension row valid on date `d`. |
| `etl_state(name, watermark)` | One row per loaded table holding the last loaded `created_at`. |
| `with conn:` | One transaction: commit on success, roll back on an exception. |

## Learn by example

### Example 1: Create the schema and load the simple dimensions

`init_warehouse` creates the five tables in an in-memory `sqlite3` database. `dim_date` is generated for the first quarter of 2026 (90 days, with an integer key `YYYYMMDD`), and `dim_product` is upserted from the product list. Loading products a second time, after a category was changed in the source, updates the row instead of adding one.

```python run
import random
from datetime import date, timedelta

COUNTRIES = ["DE", "FR", "IN", "US", "BR"]
CATEGORIES = ["tools", "books", "games"]

def generate(seed=7):
    """Seeded stand-in data: customers, products and 120 raw order records with planted defects."""
    rng = random.Random(seed)
    customers = [(f"C{n:03d}", f"Customer {n:02d}", COUNTRIES[n % 5]) for n in range(1, 21)]
    products = [(f"P{n:02d}", f"Product {n:02d}", CATEGORIES[n % 3]) for n in range(1, 9)]
    price = {pid: 500 * (i + 1) for i, (pid, _, _) in enumerate(products)}
    orders = []
    for n in range(1, 121):
        pid = products[rng.randrange(8)][0]
        qty = rng.randint(1, 4)
        day = date(2026, 1, 1) + timedelta(days=(n - 1) * 89 // 119)
        orders.append({
            "order_id": f"O{n:04d}", "customer_id": customers[rng.randrange(20)][0], "product_id": pid,
            "quantity": qty, "amount_cents": price[pid] * qty, "currency": "EUR",
            "status": rng.choices(["paid", "refunded", "failed"], weights=[8, 1, 1])[0],
            "created_at": f"{day}T{(n * 7) % 24:02d}:{(n * 13) % 60:02d}:00Z",
        })
    orders[29]["amount_cents"] = -1000
    orders[44]["customer_id"] = "C999"
    orders[59]["created_at"] = ""
    orders[74]["currency"] = "???"
    orders[104]["status"] = "pending"
    orders[119] = dict(orders[9])
    return customers, products, orders

import sqlite3
from datetime import date, timedelta

DDL = """
CREATE TABLE dim_date (date_key INTEGER PRIMARY KEY, full_date TEXT, year INTEGER, month INTEGER);
CREATE TABLE dim_product (product_key INTEGER PRIMARY KEY AUTOINCREMENT, product_id TEXT UNIQUE, product_name TEXT, category TEXT);
CREATE TABLE dim_customer (customer_key INTEGER PRIMARY KEY AUTOINCREMENT, customer_id TEXT, customer_name TEXT, country TEXT,
                           valid_from TEXT, valid_to TEXT, is_current INTEGER);
CREATE TABLE fact_sales (sale_id INTEGER PRIMARY KEY, date_key INTEGER, customer_key INTEGER, product_key INTEGER,
                         quantity INTEGER, amount_cents INTEGER);
CREATE TABLE etl_state (name TEXT PRIMARY KEY, watermark TEXT);
"""

def init_warehouse():
    conn = sqlite3.connect(":memory:")
    conn.executescript(DDL)
    return conn

def load_dim_date(conn, start, end):
    days = (end - start).days + 1
    rows = [(int(d.strftime("%Y%m%d")), d.isoformat(), d.year, d.month) for d in (start + timedelta(days=i) for i in range(days))]
    with conn:
        conn.executemany("INSERT OR IGNORE INTO dim_date VALUES (?, ?, ?, ?)", rows)

def load_dim_product(conn, products):
    with conn:
        conn.executemany("""INSERT INTO dim_product (product_id, product_name, category) VALUES (?, ?, ?)
                            ON CONFLICT(product_id) DO UPDATE SET product_name = excluded.product_name, category = excluded.category""", products)

def load_dim_customer(conn, customers, as_of, first_from="2026-01-01"):
    """Type 2 history: a changed customer gets a new row; the old row is closed on `as_of`."""
    with conn:
        for cid, name, country in customers:
            cur = conn.execute("SELECT customer_key, customer_name, country FROM dim_customer WHERE customer_id = ? AND is_current = 1", (cid,)).fetchone()
            if cur is None:
                conn.execute("INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current) VALUES (?, ?, ?, ?, '9999-12-31', 1)",
                             (cid, name, country, first_from))
            elif (cur[1], cur[2]) != (name, country):
                conn.execute("UPDATE dim_customer SET valid_to = ?, is_current = 0 WHERE customer_key = ?", (as_of, cur[0]))
                conn.execute("INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current) VALUES (?, ?, ?, ?, '9999-12-31', 1)",
                             (cid, name, country, as_of))

def load_fact(conn, good):
    """Incremental: only paid orders newer than the watermark; upsert on sale_id; the watermark moves after the load."""
    row = conn.execute("SELECT watermark FROM etl_state WHERE name = 'fact_sales'").fetchone()
    mark = row[0] if row else ""
    new = [g for g in good if g["created_at"] > mark]
    facts = []
    for g in new:
        if g["status"] != "paid":
            continue
        day = g["created_at"][:10]
        ck = conn.execute("SELECT customer_key FROM dim_customer WHERE customer_id = ? AND valid_from <= ? AND ? < valid_to", (g["customer_id"], day, day)).fetchone()[0]
        pk = conn.execute("SELECT product_key FROM dim_product WHERE product_id = ?", (g["product_id"],)).fetchone()[0]
        facts.append((g["sale_id"], g["date_key"], ck, pk, g["quantity"], g["amount_cents"]))
    with conn:
        conn.executemany("""INSERT INTO fact_sales VALUES (?, ?, ?, ?, ?, ?)
                            ON CONFLICT(sale_id) DO UPDATE SET date_key = excluded.date_key, customer_key = excluded.customer_key,
                            product_key = excluded.product_key, quantity = excluded.quantity, amount_cents = excluded.amount_cents""", facts)
        if new:
            conn.execute("INSERT INTO etl_state VALUES ('fact_sales', ?) ON CONFLICT(name) DO UPDATE SET watermark = excluded.watermark",
                         (max(g["created_at"] for g in new),))
    return len(facts)

customers, products, orders = generate()
conn = init_warehouse()
load_dim_date(conn, date(2026, 1, 1), date(2026, 3, 31))
load_dim_product(conn, products)
load_dim_product(conn, products)
print("dim_date rows:", conn.execute("SELECT COUNT(*) FROM dim_date").fetchone()[0])
print("per month:", conn.execute("SELECT month, COUNT(*) FROM dim_date GROUP BY month ORDER BY month").fetchall())
print("dim_product rows after two loads:", conn.execute("SELECT COUNT(*) FROM dim_product").fetchone()[0])
changed = [(pid, name, "books" if pid == "P01" else cat) for pid, name, cat in products]
load_dim_product(conn, changed)
print("rows:", conn.execute("SELECT COUNT(*) FROM dim_product").fetchone()[0], conn.execute("SELECT product_key, product_id, category FROM dim_product WHERE product_id = 'P01'").fetchone())
```

```output
dim_date rows: 90
per month: [(1, 31), (2, 28), (3, 31)]
dim_product rows after two loads: 8
rows: 8 (1, 'P01', 'books')
```

### Example 3: Incremental fact load and a re-run

The stage first cleans the orders (Day 175), then loads in three runs. Run 1 gets only the orders before 15 February, run 2 gets the whole clean set, and run 3 gets it again. The watermark moves after run 1; run 2 loads only the newer orders although it was handed all of them; run 3 finds nothing new. The totals at the end equal the paid total of the clean data.

from datetime import datetime

def first_problem(rec, seen, known):
    """The first rule a raw order breaks, or None. `seen` holds the order ids already processed."""
    if rec["order_id"] in seen:
        return "duplicate order_id"
    if not rec["created_at"]:
        return "missing created_at"
    try:
        datetime.strptime(rec["created_at"], "%Y-%m-%dT%H:%M:%SZ")
    except ValueError:
        return "bad created_at"
    if not isinstance(rec["amount_cents"], int) or rec["amount_cents"] <= 0:
        return "bad amount"
    if rec["customer_id"].strip().upper() not in known:
        return "unknown customer"
    if rec["currency"].strip().upper() != "EUR":
        return "bad currency"
    if rec["status"].strip().lower() not in ("paid", "refunded", "failed"):
        return "bad status"
    return None

def transform(rec):
    """Typed, normalised copy of a valid raw order."""
    return {"sale_id": int(rec["order_id"][1:]), "order_id": rec["order_id"],
            "customer_id": rec["customer_id"].strip().upper(), "product_id": rec["product_id"],
            "quantity": int(rec["quantity"]), "amount_cents": rec["amount_cents"],
            "status": rec["status"].strip().lower(), "created_at": rec["created_at"],
            "date_key": int(rec["created_at"][:10].replace("-", ""))}

def clean_orders(raw, known):
    good, quarantine, seen = [], [], set()
    for rec in raw:
        reason = first_problem(rec, seen, known)
        seen.add(rec["order_id"])
        if reason:
            quarantine.append({"order_id": rec["order_id"], "reason": reason, "payload": rec})
        else:
            good.append(transform(rec))
    return good, quarantine

    return len(facts)

known = {c[0] for c in customers}

### Example 4: Verify keys and history

Three queries check the load. The orphan checks are anti-joins from the fact table to each dimension and must return zero. The history check counts the orders of `C005` per dimension row, after a second customer file moved `C005` on 15 February: January orders keep the old row and later orders use the new one. A final revenue per country query shows the star schema at work.

```python run
import random
from datetime import date, timedelta

COUNTRIES = ["DE", "FR", "IN", "US", "BR"]
CATEGORIES = ["tools", "books", "games"]

def generate(seed=7):
    """Seeded stand-in data: customers, products and 120 raw order records with planted defects."""
    rng = random.Random(seed)
    customers = [(f"C{n:03d}", f"Customer {n:02d}", COUNTRIES[n % 5]) for n in range(1, 21)]
    products = [(f"P{n:02d}", f"Product {n:02d}", CATEGORIES[n % 3]) for n in range(1, 9)]
    price = {pid: 500 * (i + 1) for i, (pid, _, _) in enumerate(products)}
    orders = []
    for n in range(1, 121):
        pid = products[rng.randrange(8)][0]
        qty = rng.randint(1, 4)
        day = date(2026, 1, 1) + timedelta(days=(n - 1) * 89 // 119)
        orders.append({
            "order_id": f"O{n:04d}", "customer_id": customers[rng.randrange(20)][0], "product_id": pid,
            "quantity": qty, "amount_cents": price[pid] * qty, "currency": "EUR",
            "status": rng.choices(["paid", "refunded", "failed"], weights=[8, 1, 1])[0],
            "created_at": f"{day}T{(n * 7) % 24:02d}:{(n * 13) % 60:02d}:00Z",
        })
    orders[29]["amount_cents"] = -1000
    orders[44]["customer_id"] = "C999"
    orders[59]["created_at"] = ""
    orders[74]["currency"] = "???"
    orders[104]["status"] = "pending"
    orders[119] = dict(orders[9])
    return customers, products, orders

from datetime import datetime

def first_problem(rec, seen, known):
    """The first rule a raw order breaks, or None. `seen` holds the order ids already processed."""
    if rec["order_id"] in seen:
        return "duplicate order_id"
    if not rec["created_at"]:
        return "missing created_at"
    try:
        datetime.strptime(rec["created_at"], "%Y-%m-%dT%H:%M:%SZ")
    except ValueError:
        return "bad created_at"
    if not isinstance(rec["amount_cents"], int) or rec["amount_cents"] <= 0:
        return "bad amount"
    if rec["customer_id"].strip().upper() not in known:
        return "unknown customer"
    if rec["currency"].strip().upper() != "EUR":
        return "bad currency"
    if rec["status"].strip().lower() not in ("paid", "refunded", "failed"):
        return "bad status"
    return None

def transform(rec):
    """Typed, normalised copy of a valid raw order."""
    return {"sale_id": int(rec["order_id"][1:]), "order_id": rec["order_id"],
            "customer_id": rec["customer_id"].strip().upper(), "product_id": rec["product_id"],
            "quantity": int(rec["quantity"]), "amount_cents": rec["amount_cents"],
            "status": rec["status"].strip().lower(), "created_at": rec["created_at"],
            "date_key": int(rec["created_at"][:10].replace("-", ""))}

def clean_orders(raw, known):
    good, quarantine, seen = [], [], set()
    for rec in raw:
        reason = first_problem(rec, seen, known)
        seen.add(rec["order_id"])
        if reason:
            quarantine.append({"order_id": rec["order_id"], "reason": reason, "payload": rec})
        else:
            good.append(transform(rec))
    return good, quarantine

import sqlite3
from datetime import date, timedelta

DDL = """
CREATE TABLE dim_date (date_key INTEGER PRIMARY KEY, full_date TEXT, year INTEGER, month INTEGER);
CREATE TABLE dim_product (product_key INTEGER PRIMARY KEY AUTOINCREMENT, product_id TEXT UNIQUE, product_name TEXT, category TEXT);
CREATE TABLE dim_customer (customer_key INTEGER PRIMARY KEY AUTOINCREMENT, customer_id TEXT, customer_name TEXT, country TEXT,
                           valid_from TEXT, valid_to TEXT, is_current INTEGER);
CREATE TABLE fact_sales (sale_id INTEGER PRIMARY KEY, date_key INTEGER, customer_key INTEGER, product_key INTEGER,
                         quantity INTEGER, amount_cents INTEGER);
CREATE TABLE etl_state (name TEXT PRIMARY KEY, watermark TEXT);
"""

def init_warehouse():
    conn = sqlite3.connect(":memory:")
    conn.executescript(DDL)
    return conn

def load_dim_date(conn, start, end):
    days = (end - start).days + 1
    rows = [(int(d.strftime("%Y%m%d")), d.isoformat(), d.year, d.month) for d in (start + timedelta(days=i) for i in range(days))]
    with conn:
        conn.executemany("INSERT OR IGNORE INTO dim_date VALUES (?, ?, ?, ?)", rows)

def load_dim_product(conn, products):
    with conn:
        conn.executemany("""INSERT INTO dim_product (product_id, product_name, category) VALUES (?, ?, ?)
                            ON CONFLICT(product_id) DO UPDATE SET product_name = excluded.product_name, category = excluded.category""", products)

def load_dim_customer(conn, customers, as_of, first_from="2026-01-01"):
    """Type 2 history: a changed customer gets a new row; the old row is closed on `as_of`."""
    with conn:
        for cid, name, country in customers:
            cur = conn.execute("SELECT customer_key, customer_name, country FROM dim_customer WHERE customer_id = ? AND is_current = 1", (cid,)).fetchone()
            if cur is None:
                conn.execute("INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current) VALUES (?, ?, ?, ?, '9999-12-31', 1)",
                             (cid, name, country, first_from))
            elif (cur[1], cur[2]) != (name, country):
                conn.execute("UPDATE dim_customer SET valid_to = ?, is_current = 0 WHERE customer_key = ?", (as_of, cur[0]))
                conn.execute("INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current) VALUES (?, ?, ?, ?, '9999-12-31', 1)",
                             (cid, name, country, as_of))

def load_fact(conn, good):
    """Incremental: only paid orders newer than the watermark; upsert on sale_id; the watermark moves after the load."""
    row = conn.execute("SELECT watermark FROM etl_state WHERE name = 'fact_sales'").fetchone()
    mark = row[0] if row else ""
    new = [g for g in good if g["created_at"] > mark]
    facts = []
    for g in new:
        if g["status"] != "paid":
            continue
        day = g["created_at"][:10]
        ck = conn.execute("SELECT customer_key FROM dim_customer WHERE customer_id = ? AND valid_from <= ? AND ? < valid_to", (g["customer_id"], day, day)).fetchone()[0]
        pk = conn.execute("SELECT product_key FROM dim_product WHERE product_id = ?", (g["product_id"],)).fetchone()[0]
        facts.append((g["sale_id"], g["date_key"], ck, pk, g["quantity"], g["amount_cents"]))
    with conn:
        conn.executemany("""INSERT INTO fact_sales VALUES (?, ?, ?, ?, ?, ?)
                            ON CONFLICT(sale_id) DO UPDATE SET date_key = excluded.date_key, customer_key = excluded.customer_key,
                            product_key = excluded.product_key, quantity = excluded.quantity, amount_cents = excluded.amount_cents""", facts)
        if new:
            conn.execute("INSERT INTO etl_state VALUES ('fact_sales', ?) ON CONFLICT(name) DO UPDATE SET watermark = excluded.watermark",
                         (max(g["created_at"] for g in new),))
    return len(facts)

customers, products, orders = generate()
good, quarantine = clean_orders(orders, {c[0] for c in customers})
conn = init_warehouse()
load_dim_date(conn, date(2026, 1, 1), date(2026, 3, 31))
load_dim_product(conn, products)
load_dim_customer(conn, customers, "2026-01-01")
load_dim_customer(conn, [(c, n, "US" if c == "C005" else k) for c, n, k in customers], "2026-02-15")
print("facts:", load_fact(conn, good))
for name, sql in [
    ("orphan customers", "SELECT COUNT(*) FROM fact_sales f LEFT JOIN dim_customer c ON c.customer_key = f.customer_key WHERE c.customer_key IS NULL"),
    ("orphan products", "SELECT COUNT(*) FROM fact_sales f LEFT JOIN dim_product p ON p.product_key = f.product_key WHERE p.product_key IS NULL"),
    ("orphan dates", "SELECT COUNT(*) FROM fact_sales f LEFT JOIN dim_date d ON d.date_key = f.date_key WHERE d.date_key IS NULL"),
]:
    print(name, conn.execute(sql).fetchone()[0])
print(conn.execute("""SELECT c.country, c.valid_from, COUNT(*) FROM fact_sales f JOIN dim_customer c ON c.customer_key = f.customer_key
                      WHERE c.customer_id = 'C005' GROUP BY c.customer_key ORDER BY c.customer_key""").fetchall())
print(conn.execute("""SELECT c.country, SUM(f.amount_cents) FROM fact_sales f JOIN dim_customer c ON c.customer_key = f.customer_key
                      GROUP BY c.country ORDER BY c.country""").fetchall())
```

### Example 5: The PostgreSQL form

This is the same design in PostgreSQL syntax, run on PGlite with a few rows. The surrogate key is `GENERATED ALWAYS AS IDENTITY`, amounts are `integer` cents and dates are real `date` values. The fact table is loaded twice with `ON CONFLICT (sale_id) DO UPDATE`: the second statement carries a corrected amount for sale 2 and a new sale 3, so the result has three rows and the corrected amount. The differences from the Python stand-in are the identity syntax, `date` and `integer` column types instead of SQLite's flexible types, and the `%s` placeholders that `psycopg` uses where `sqlite3` uses `?`.

```sql run
CREATE TABLE dim_product (product_key integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY, product_id text UNIQUE NOT NULL, product_name text, category text);
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL, product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL CHECK (quantity > 0), amount_cents integer NOT NULL CHECK (amount_cents > 0));
INSERT INTO dim_product (product_id, product_name, category) VALUES ('P01', 'Product 01', 'books'), ('P02', 'Product 02', 'games');
INSERT INTO fact_sales VALUES (1, 20260105, 1, 2, 1000), (2, 20260106, 2, 1, 1500)
  ON CONFLICT (sale_id) DO UPDATE SET amount_cents = excluded.amount_cents;
INSERT INTO fact_sales VALUES (2, 20260106, 2, 1, 1600), (3, 20260107, 1, 1, 500)
  ON CONFLICT (sale_id) DO UPDATE SET amount_cents = excluded.amount_cents;
SELECT f.sale_id, p.product_id, f.amount_cents FROM fact_sales f JOIN dim_product p USING (product_key) ORDER BY f.sale_id;
```

## Real-world applications

- **Nightly warehouse loads.** The watermark and upsert of Example 3 are the standard pattern for loading orders, events or payments every night without reprocessing history.
- **Customer history in reporting.** The type 2 rows of Example 2 let finance report revenue by the country a customer lived in at the time of the sale.
- **Load verification.** The anti-joins of Example 4 are the post-load checks that run before dashboards refresh.
- **Moving to PostgreSQL.** Example 5 shows what changes when the stand-in becomes a real server: identity columns, real types, constraints and placeholders.

## Daily review

### Key takeaways

- The fact table holds one paid order per row and stores surrogate keys; dimensions describe it.
- Upsert on the business key (dimensions) and on `sale_id` (facts) makes loads repeatable.
- Type 2 history closes the old row and starts a new one; the fact lookup uses the order date against the validity range.
- An incremental load reads the watermark, loads newer rows and moves the watermark in the same transaction.
- Verify with counts, anti-joins and a total that matches the clean data.

### Common mistakes

- Overwriting a changed customer (type 1) when history is needed, which moves old sales to the new country.
- Looking up the current dimension row instead of the row valid on the order date.
- Moving the watermark before the load commits, so a crash skips rows. Do both in one transaction.
- Using plain `INSERT` for facts, so a retry fails on the primary key or, without one, duplicates rows.
- Loading refunded or failed orders as sales, which inflates revenue.
- Forgetting that late-arriving rows older than the watermark are skipped.

### Revision notes

- Upsert: `INSERT ... ON CONFLICT (key) DO UPDATE SET c = excluded.c`.
- Lookup: `valid_from <= d AND d < valid_to`; open rows end on `9999-12-31`.
- Expected on the data: 90 date rows, 8 products, 20 customers (21 rows after one move), a fact row per paid clean order, and 0 new rows on a repeated run.
- Watermark in `etl_state`, moved with the load.

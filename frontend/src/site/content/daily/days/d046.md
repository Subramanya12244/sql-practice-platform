## Understand

### The problem: queries that read inside out

On day 43 you wrote `FROM (SELECT ... ) t` to aggregate twice. It works, but nested queries read from the inside out: you must find the innermost parenthesis first and work outwards, and every extra level makes the query harder to read. With a few levels, nobody can follow it, including the person who wrote it two weeks ago.

A **common table expression**, usually shortened to **CTE**, solves this by letting you name each step and write the steps in the order you think of them: first this table, then that one built from it, finally the answer. It is defined with a `WITH` clause in front of the main query:

`WITH order_counts AS (SELECT customer_id, COUNT(*) AS n FROM orders GROUP BY customer_id) SELECT ... FROM order_counts`

`order_counts` is the CTE's name. Inside the main query it behaves like a table with the columns the inner query returns (`customer_id` and `n`). It is a temporary, named result that exists only for the duration of this one statement. Nothing is stored; when the statement ends, the name disappears. Think of writing the intermediate result on a sticky note, giving it a title, and referring to it by title in the rest of your work.

### Syntax

The `WITH` keyword comes first, then `name AS ( query )`, and the main `SELECT` follows. Column names inside the CTE come from the inner query, so give aliases to expressions (`COUNT(*) AS n`). You can also list column names after the CTE name: `WITH order_counts (customer_id, n) AS (...)`. A CTE can be used in `FROM`, in joins, and in subqueries of the main query, exactly like a table.

### Several CTEs

Separate CTEs with commas, writing `WITH` only once: `WITH first AS (...), second AS (...) SELECT ...`. A later CTE may use any CTE defined before it, but not one defined after it. This makes a pipeline: raw rows, then a per-customer summary built from them, then an average built from the summary, and the final query combines them. Each step is small enough to check on its own: you can run the main `SELECT` against the first CTE only while you debug, then add the next step.

### Using one CTE twice

A CTE can be referenced several times, which is a real advantage over a subquery. Suppose you need each customer's revenue, and also the average of all customers' revenue to compare against. With subqueries you would write the revenue calculation twice, once for the list and once for the average, and any change must be made in both places. With a CTE you define `customer_revenue` once, and use it in both places. The result is shorter, and the two uses cannot drift apart. In PostgreSQL 12 and later, a CTE that is used once and has no side effects is folded into the main query like a subquery, so the planner optimises it as one query; a CTE used several times may be calculated once and reused. You can force either behaviour with `AS MATERIALIZED` and `AS NOT MATERIALIZED`, but you rarely need to.

### CTE or subquery?

A CTE and a subquery in `FROM` usually return the same result, and the difference is mostly **readability and reuse**. Prefer a CTE when the query has more than one step, when a step is used more than once, or when you want to name a step so the query explains itself. A short scalar subquery such as `WHERE x > (SELECT AVG(x) FROM t)` is often clearer as it is. A correlated subquery (day 43) cannot be turned into a plain CTE, because a CTE cannot refer to a column of the main query; it is evaluated by itself.

### What a CTE is not

A CTE is not a table or a view: it is not stored, indexed or visible to other statements. It cannot be referenced in a second statement after the semicolon. It is not automatically faster; in modern PostgreSQL it is mostly a way of writing, not an optimisation. And two CTEs may not use the same name in one `WITH` clause. Later in the course you will meet recursive CTEs, which are a different feature; today covers only non-recursive ones.

### Common misconception

Learners think that a CTE runs "first, once, and is cached" in every case, so that placing a filter in a CTE is always efficient. Which parts run when depends on how the planner treats the CTE (see above). Write CTEs for clarity, and check performance separately with the tools of the performance days.

### Why it matters

Real analytical queries often have four or five steps: clean, aggregate, compare, rank, format. CTEs are how they are made readable and reviewable, and they are the standard shape of queries in data teams and in analytics tools such as dbt.

## Syntax and key functions

```sql-syntax
WITH step_one AS (
  SELECT key, COUNT(*) AS n
  FROM table_name
  GROUP BY key
),
step_two AS (
  SELECT AVG(n) AS avg_n FROM step_one
)
SELECT s.key, s.n
FROM step_one s
CROSS JOIN step_two t
WHERE s.n > t.avg_n;
```

| Part | Meaning |
|---|---|
| `WITH name AS ( query )` | Defines a named temporary result for this statement |
| `, name2 AS ( query )` | Another CTE; may use CTEs defined before it |
| `name (col1, col2)` | Optional list that renames the output columns |
| `AS MATERIALIZED` / `AS NOT MATERIALIZED` | Forces calculating once, or folding into the main query (PostgreSQL 12+) |
| Main query | Uses CTEs like tables in `FROM`, joins and subqueries |

| Use a CTE when | Use a plain subquery when |
|---|---|
| A step has a meaningful name | The step is short and used once |
| The same result is needed twice | A correlated condition refers to the outer row |
| The query has three or more steps | A single `IN` or scalar value is enough |

## Learn by example

### Example 1: Name the first step

This is the distribution query of day 43, rewritten with a CTE. The inner query is now a named step, `order_counts`, defined at the top, and the final query reads like a sentence: group the order counts and count customers for each. The result is the same as with the derived table.

```sql run
WITH order_counts AS (
  SELECT customer_id, COUNT(*) AS n
  FROM orders
  GROUP BY customer_id
)
SELECT n AS orders_per_customer, COUNT(*) AS customers
FROM order_counts
GROUP BY n
ORDER BY n;
```

```output
orders_per_customer | customers
1 | 79
2 | 9
3 | 1
```

### Example 2: Two chained CTEs

`customer_revenue` computes each customer's revenue from their order lines. `avg_rev` builds on it with one row, the average revenue. The final query keeps the customers above that average. The CTEs are written in the order of thought, and `avg_rev` has one row, so a `CROSS JOIN` attaches it to every customer row without changing the row count (day 42).

```sql run
WITH customer_revenue AS (
  SELECT o.customer_id,
         ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount::numeric)), 2) AS revenue
  FROM orders o
  JOIN order_details od ON od.order_id = o.order_id
  GROUP BY o.customer_id
),
avg_rev AS (
  SELECT AVG(revenue) AS avg_revenue FROM customer_revenue
)
SELECT cr.customer_id, cr.revenue, ROUND(a.avg_revenue, 2) AS average
FROM customer_revenue cr
CROSS JOIN avg_rev a
WHERE cr.revenue > a.avg_revenue
ORDER BY cr.revenue DESC
LIMIT 5;
```

```output
customer_id | revenue | average
FOLKO | 12905.32 | 1554.16
GOURL | 9578.85 | 1554.16
BOLID | 8095.04 | 1554.16
ALFKI | 4703.69 | 1554.16
BONAP | 4509.46 | 1554.16
```

### Example 3: One CTE used twice

`customer_revenue` is defined once and used in two places: in `FROM`, and inside the scalar subquery for the average. The query counts the customers whose revenue exceeds the average, and averages those customers' revenue. With plain subqueries the revenue calculation would appear twice.

```sql run
WITH customer_revenue AS (
  SELECT o.customer_id,
         ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount::numeric)), 2) AS revenue
  FROM orders o
  JOIN order_details od ON od.order_id = o.order_id
  GROUP BY o.customer_id
)
SELECT COUNT(*) AS above_average_customers,
       ROUND(AVG(revenue), 2) AS their_average_revenue
FROM customer_revenue
WHERE revenue > (SELECT AVG(revenue) FROM customer_revenue);
```

```output
above_average_customers | their_average_revenue
30 | 3192.32
```

### Example 4: A pipeline of three CTEs

Raw order lines become order values, order values become a yearly summary, and a one-row `overall` CTE holds the grand average. The final query compares each year with the overall average. Every step has a name that says what it holds, and you can run any of them on its own to check it.

```sql run
WITH per_order AS (
  SELECT o.order_id, o.order_date, SUM(od.unit_price * od.quantity) AS value
  FROM orders o
  JOIN order_details od ON od.order_id = o.order_id
  GROUP BY o.order_id, o.order_date
),
yearly AS (
  SELECT EXTRACT(year FROM order_date)::int AS yr,
         COUNT(*) AS orders,
         AVG(value) AS avg_value
  FROM per_order
  GROUP BY 1
),
overall AS (
  SELECT AVG(value) AS avg_value FROM per_order
)
SELECT y.yr, y.orders,
       ROUND(y.avg_value, 2) AS avg_order_value,
       ROUND(y.avg_value - o.avg_value, 2) AS diff_from_overall
FROM yearly y
CROSS JOIN overall o
ORDER BY y.yr;
```

```output
yr | orders | avg_order_value | diff_from_overall
1996 | 34 | 1659.35 | 181.04
1997 | 33 | 1289.24 | -189.06
1998 | 33 | 1480.84 | 2.53
```

### Example 5: A CTE that filters before joining

The CTE `heavy` keeps only the orders with freight above 150, and the main query joins just those rows to `customers`. The CTE name documents the intent. A plain `WHERE` on the join would give the same rows; the CTE is chosen for readability when the filter step is conceptually separate.

```sql run
WITH heavy AS (
  SELECT customer_id, freight
  FROM orders
  WHERE freight > 150
)
SELECT c.country,
       COUNT(*) AS heavy_orders,
       ROUND(AVG(h.freight), 2) AS avg_freight
FROM heavy h
JOIN customers c ON c.customer_id = h.customer_id
GROUP BY c.country
ORDER BY heavy_orders DESC, c.country
LIMIT 5;
```

```output
country | heavy_orders | avg_freight
Brazil | 4 | 179.31
France | 3 | 177.30
Germany | 3 | 187.98
Spain | 2 | 182.31
UK | 2 | 175.86
```

### Example 6: Share of total revenue by category

The CTE `cat_rev` holds the revenue of each category. The main query uses it twice: for each category's revenue and, in a scalar subquery, for the total across categories. Dividing gives each category's share, rounded to one decimal. The top three categories are shown.

```sql run
WITH cat_rev AS (
  SELECT p.category_id,
         SUM(od.unit_price * od.quantity * (1 - od.discount::numeric)) AS revenue
  FROM order_details od
  JOIN products p ON p.product_id = od.product_id
  GROUP BY p.category_id
)
SELECT c.category_name,
       ROUND(cr.revenue, 2) AS revenue,
       ROUND(100 * cr.revenue / (SELECT SUM(revenue) FROM cat_rev), 1) AS share_pct
FROM cat_rev cr
JOIN categories c ON c.category_id = cr.category_id
ORDER BY cr.revenue DESC
LIMIT 3;
```

```output
category_name | revenue | share_pct
Beverages | 29335.53 | 21.2
Confections | 20511.84 | 14.8
Meat/Poultry | 18705.28 | 13.5
```

## Real-world applications

**Readable analytical pipelines.** Data teams write reports as a chain of CTEs, one per step (example 4). Reviewers can check each step separately, and a new colleague can follow the logic from top to bottom.

**Benchmarks computed once.** Comparing every customer, product or year with an overall average (examples 2 to 4) needs both the detail and the benchmark. A CTE defines the detail once and feeds both.

**Shares and ratios.** "What percentage of revenue comes from each category" (example 6) divides a group value by a total that comes from the same CTE, a very common reporting shape.

**Refactoring legacy SQL.** Deeply nested queries are rewritten as CTEs during code review so that each step has a name, and bugs become easier to find.

## Daily review

### Key takeaways

- `WITH name AS (query)` defines a named temporary result for one statement; the main query uses it like a table.
- Several CTEs are separated by commas under one `WITH`; later ones can use earlier ones.
- A CTE can be referenced more than once, which avoids repeating a subquery.
- CTEs are mainly about readability; in PostgreSQL 12+ a CTE used once is optimised like a subquery.
- A CTE exists for one statement only and cannot be correlated with the main query.

### Common mistakes

- Writing `WITH` before each CTE instead of once. Use `WITH a AS (...), b AS (...)`.
- Referencing a CTE that is defined later: "relation does not exist". Order the CTEs so dependencies come first.
- Forgetting to alias an expression inside the CTE, then not being able to refer to the column. Write `COUNT(*) AS n`.
- Using a CTE name in a second statement after the semicolon. It exists for one statement.
- Assuming a CTE is stored or indexed like a table, or that it is always faster.
- Putting a semicolon inside the parentheses of a CTE: syntax error.
- Expecting a CTE to see columns of the main query (correlation). Use a correlated subquery instead.

### Revision notes

- `WITH a AS (...), b AS (...) SELECT ...` : one WITH, commas between steps.
- Name the steps; alias every expression.
- One CTE can feed the main query several times.
- CTE = readable subquery, not a table.

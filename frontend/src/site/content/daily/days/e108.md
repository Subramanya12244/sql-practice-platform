## Objectives

- Classify API failures (timeout, connection, bad status, malformed body, invalid record) and choose a reaction for each.
- Handle partial failure: keep the pages and records that succeeded, record what failed, and decide when the run as a whole must fail.
- Write useful log lines with Python's `logging` module: levels, key=value fields, no secrets, one summary at the end.
- Store records that cannot be processed in a dead-letter table with the raw payload, the error and the number of attempts, and re-process them later.
- Reconcile a run so that fetched = loaded + dead-lettered, with failed pages listed.

## Understand

### Failures come in layers

An API call passes through several layers, and each fails in its own way. The **network** layer: the host cannot be reached (`ConnectionError`) or does not answer in time (`Timeout`). The **HTTP** layer: the server answers with an error status (4xx, 5xx). The **body** layer: the status says success but the body is not what you expect: not JSON (a proxy returned an HTML page), truncated JSON, or valid JSON with a different shape (Day 104). The **record** layer: the JSON is fine but one record breaks your rules (a negative amount, a missing key). Day 107 handled the first two for transient cases. Today covers what remains after the retries are exhausted, and the body and record layers.

Naming the layer matters because the reaction differs. A timeout after retries is a page you could not get: record it and move on, or stop. A malformed body is a provider fault: log the beginning of the body (never the headers) and treat the page like a failure. An invalid record is a data problem: it should not stop the other 49 records on the page.

### Fail fast or continue

When something fails, a pipeline has two honest options. **Fail fast**: stop the run at the first unrecoverable error, which is right when later steps need every record (a total that is wrong by a page is worse than no total) or when the cause will affect every call (a revoked key). **Continue and report**: finish what can be finished and list what could not, which is right for independent records or pages and when a partial result is useful. The dangerous option is a third, accidental one: continue **without reporting**, for example a bare `except: pass` around the fetch. The result looks complete and is not.

A practical rule: continue past the failure of one page or one record, but fail the run when the share of failures passes a threshold (for example more than 5 percent of pages) or when the failure is of a kind that affects everything (`401`). Either way, finish with a summary that states what happened.

### Partial failure

**Partial failure** means that some of the work succeeded and some did not. For a paged API that means pages 1 to 40 loaded, page 17 failed after five attempts. Handling it well needs three things. **Keep the successes**: the 39 good pages are not thrown away. **Remember the failures**: a list of failed page numbers with the error for each. **Make the failure repairable**: a later run can fetch only the failed pages, because the job knows which they are. This leads to the idea of a **checkpoint**, a small record of progress (the last page done, the failed pages) that a rerun reads, which Day 110 and Day 111 build on when loading.

### Logging that helps at 03:00

The standard library's `logging` module writes messages with a **level**: `DEBUG` (details for development), `INFO` (normal progress), `WARNING` (something unusual but handled), `ERROR` (an operation failed), `CRITICAL` (the program cannot continue). Choose the level by what a person should do about it. A good line states the event and the identifying facts as `key=value` pairs, for example `page_failed page=17 status=503 attempts=5`, so that it can be searched. Log the **URL without secrets**, the status, the attempt number and the duration; never headers, tokens or full bodies that may hold personal data. Log one **run summary** at the end (`pages_ok=39 pages_failed=1 records=1950 dead_letters=3`); an on-call engineer reads that line first.

### Dead-letter records

A **dead letter** is a message or record that the system could not process and set aside instead of losing or looping on. A **dead-letter table** holds the raw payload exactly as received (as JSON text), the error message, where it came from (page, run id), the number of attempts and a timestamp. It has three uses. It stops one bad record from blocking the batch. It keeps the evidence for the provider conversation (the raw payload shows what they sent). And it supports **redrive**: after you fix the rule or the provider fixes the data, you process the dead letters again, and the ones that now pass are loaded and marked resolved. Treat the table as a work queue with an owner, not as a bin: a dead-letter table that nobody reads is silent data loss.

### Common misconception

Many learners think that catching exceptions is the same as handling errors. `except Exception: continue` catches everything and tells nobody. Handling means choosing a reaction for each kind of failure, recording it and making the final status of the run truthful.

### Why it matters

Pipelines run unattended. The difference between a run that fails with "page 17: 503 after 5 attempts" and one that succeeds with 1,950 of 2,000 records and no message is a week of wrong dashboards.

```python
import logging

logger = logging.getLogger("orders_etl")
logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")

logger.info("page_ok page=%d records=%d", page, len(data))
logger.warning("record_rejected order_id=%s reason=%s", order_id, reason)

```

```sql-syntax
CREATE TABLE dead_letter (
    id          integer PRIMARY KEY,
    source      text NOT NULL,          -- e.g. 'orders page 17'
    payload     text NOT NULL,          -- raw record as JSON text
    error       text NOT NULL,
    attempts    integer NOT NULL,
    created_at  text NOT NULL,
    resolved_at text
);
```

| Item | What it does or returns |
|---|---|
| `logging.getLogger(name)` | A named logger. |
| `logger.info / warning / error(msg, *args)` | Log at that level; `%s` placeholders are filled lazily. |
| `logging.basicConfig(level=, format=)` | Default handler and format. |
| `json.dumps(record)` | Raw payload text for the dead-letter row. |
| `response.json()` raising `ValueError` | Body is not JSON. |
| `failed_pages` list | Pages to refetch on redrive. |
| `resolved_at` | NULL while the dead letter is open. |

## Learn by example

### Example 1: Useful log lines (browser-safe)

A logger writes to an in-memory stream so that the example can print what was logged. The formatter shows level and message only, in a stable format. The lines use `key=value` fields. The last lines show the masking helper from Day 105 applied to a URL before logging, and a summary line.

```python run
import io
import logging
import re

stream = io.StringIO()
logger = logging.getLogger("orders_etl")
logger.handlers.clear()   # drop handlers left by an earlier run
logger.setLevel(logging.INFO)
logger.propagate = False
handler = logging.StreamHandler(stream)
handler.setFormatter(logging.Formatter("%(levelname)s %(message)s"))
logger.addHandler(handler)

def safe_url(url):
    return re.sub(r"((?:api_key|token)=)[^&]+", r"\1***", url)

logger.debug("this debug line is below the level and is not written")
logger.info("page_ok page=%d records=%d", 1, 50)
logger.warning("record_rejected order_id=%s reason=%s", 77, "negative amount")
logger.error("page_failed page=%d status=%s attempts=%d url=%s", 2, 503, 5,
             safe_url("https://api.shop.example/orders?page=2&api_key=demo-key-123"))
logger.info("run_summary pages_ok=%d pages_failed=%d dead_letters=%d", 2, 1, 1)
print(stream.getvalue().rstrip())
```

```output
INFO page_ok page=1 records=50
WARNING record_rejected order_id=77 reason=negative amount
ERROR page_failed page=2 status=503 attempts=5 url=https://api.shop.example/orders?page=2&api_key=***
INFO run_summary pages_ok=2 pages_failed=1 dead_letters=1
```

Each line can be searched for `page_failed` or `order_id=77`, and none contains the key.

### Example 2: Partial failure: keep the pages that worked

`fetch` raises for pages 2 and 4 (after retries, in a real job). The loop keeps the good pages, records each failure with its error, and then decides the status of the run from the share of failed pages. With a threshold of 30 percent, two failures out of five pages fail the run, and the summary still lists the failed pages so that a rerun can fetch them.

```python run
def fetch(page):
    if page in (2, 4):
        raise RuntimeError(f"HTTP 503 on page {page}")
    return [{"order_id": page * 10 + i} for i in range(3)]

def run(pages, max_failed_share):
    records, failed = [], {}
    for page in pages:
        try:
            records += fetch(page)
        except RuntimeError as err:
            failed[page] = str(err)
    share = len(failed) / len(pages)
    status = "FAILED" if share > max_failed_share else "OK with warnings" if failed else "OK"
    return records, failed, status

records, failed, status = run([1, 2, 3, 4, 5], max_failed_share=0.3)
print(len(records), sorted(failed), status)
print(failed[2])
records, failed, status = run([1, 2, 3, 4, 5], max_failed_share=0.5)
print(len(records), sorted(failed), status)
print(run([1, 3, 5], 0.3)[2])
```

```output
9 [2, 4] FAILED
HTTP 503 on page 2
9 [2, 4] OK with warnings
OK
```

The records of the good pages survive in every case. Only the verdict changes with the threshold.

### Example 3: A dead-letter table and a redrive

Each fetched record is validated. Invalid records are stored in `dead_letter` with the raw JSON, the error and one attempt; valid ones go to `orders`. The data owner then fixes the rule (accepting the currency `GBP`), and the redrive step re-checks the open dead letters, loads the ones that now pass and marks them resolved. The counts reconcile at the end.

```python run
import json
import sqlite3

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE orders (order_id INTEGER PRIMARY KEY, amount_cents INTEGER, currency TEXT);
CREATE TABLE dead_letter (id INTEGER PRIMARY KEY, payload TEXT NOT NULL, error TEXT NOT NULL,
                          attempts INTEGER NOT NULL, resolved_at TEXT);
""")

def validate(record, currencies):
    if not isinstance(record.get("amount_cents"), int) or record["amount_cents"] < 0:
        return "invalid amount_cents"
    if record.get("currency") not in currencies:
        return f"unknown currency {record.get('currency')}"
    return None

def process(records, currencies):
    for record in records:
        error = validate(record, currencies)
        if error is None:
            conn.execute("INSERT INTO orders VALUES (?, ?, ?)", (record["order_id"], record["amount_cents"], record["currency"]))
        else:
            conn.execute("INSERT INTO dead_letter (payload, error, attempts) VALUES (?, ?, 1)", (json.dumps(record, sort_keys=True), error))
    conn.commit()

fetched = [
    {"order_id": 1, "amount_cents": 500, "currency": "EUR"},
    {"order_id": 2, "amount_cents": -5, "currency": "EUR"},
    {"order_id": 3, "amount_cents": 900, "currency": "GBP"},
    {"order_id": 4, "amount_cents": 700, "currency": "USD"},
]
process(fetched, {"EUR", "USD"})
print(conn.execute("SELECT COUNT(*) FROM orders").fetchone()[0], conn.execute("SELECT COUNT(*) FROM dead_letter").fetchone()[0])
print(conn.execute("SELECT error FROM dead_letter ORDER BY id").fetchall())

def redrive(currencies):
    open_rows = conn.execute("SELECT id, payload FROM dead_letter WHERE resolved_at IS NULL ORDER BY id").fetchall()
    for row_id, payload in open_rows:
        record = json.loads(payload)
        if validate(record, currencies) is None:
            conn.execute("INSERT INTO orders VALUES (?, ?, ?)", (record["order_id"], record["amount_cents"], record["currency"]))
            conn.execute("UPDATE dead_letter SET resolved_at = 'fixed' WHERE id = ?", (row_id,))
        else:
            conn.execute("UPDATE dead_letter SET attempts = attempts + 1 WHERE id = ?", (row_id,))
    conn.commit()

redrive({"EUR", "USD", "GBP"})
print(conn.execute("SELECT COUNT(*) FROM orders").fetchone()[0])
print(conn.execute("SELECT id, attempts, resolved_at FROM dead_letter ORDER BY id").fetchall())
total = conn.execute("SELECT COUNT(*) FROM orders").fetchone()[0] + conn.execute("SELECT COUNT(*) FROM dead_letter WHERE resolved_at IS NULL").fetchone()[0]
print(total == len(fetched))
```

```output
2 2
[('invalid amount_cents',), ('unknown currency GBP',)]
3
[(1, 2, None), (2, 1, 'fixed')]
True
```

Order 3 was set aside, then loaded after the rule changed; order 2 stays open with two attempts. At every point, loaded plus open dead letters equals what was fetched.

### Example 4: Four failure layers over real HTTP

A local server has four endpoints: `/ok` (JSON), `/html` (status 200 with an HTML body), `/boom` (status 500) and `/slow` (answers after one second). The client has a timeout of 0.2 seconds and maps each outcome to a label: `ok`, `bad body`, `http 500`, `timeout`. A raw socket error is also shown. The classification function is the part to reuse.

```python local
import json
import threading
import time
from http.server import BaseHTTPRequestHandler, HTTPServer

import requests

class Handler(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def do_GET(self):
        if self.path == "/slow":
            time.sleep(1.0)
        status, body, kind = {
            "/ok": (200, json.dumps({"data": [1, 2]}), "application/json"),
            "/html": (200, "<html>maintenance</html>", "text/html"),
            "/boom": (500, json.dumps({"error": "boom"}), "application/json"),
            "/slow": (200, json.dumps({"data": []}), "application/json"),
        }[self.path]
        data = body.encode()
        self.send_response(status)
        self.send_header("Content-Type", kind)
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        try:
            self.wfile.write(data)
        except OSError:
            pass

server = HTTPServer(("127.0.0.1", 0), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()
base = f"http://127.0.0.1:{server.server_port}"

def classify(path):
    try:
        r = requests.get(base + path, timeout=0.2)
    except requests.exceptions.Timeout:
        return "timeout"
    except requests.exceptions.ConnectionError:
        return "connection"
    if r.status_code >= 400:
        return f"http {r.status_code}"
    try:
        r.json()
    except ValueError:
        return f"bad body ({r.headers['Content-Type']})"
    return "ok"

try:
    for path in ("/ok", "/html", "/boom", "/slow"):
        print(path, classify(path))
finally:
    server.shutdown()
    server.server_close()
print("/ok", classify("/ok"))
```

```output
/ok ok
/html bad body (text/html)
/boom http 500
/slow timeout
/ok connection
```

The last line is the same call after the server was shut down: the label is `connection`.

## Real-world applications

- **Unattended nightly loads.** The run summary line and a non-zero exit status let the scheduler alert the team while the good pages stay loaded.
- **Provider disputes.** The raw payload in the dead-letter table is the evidence that the provider sent a negative amount, with a timestamp and page.
- **Targeted reruns.** A job that stores its failed page numbers reruns only those pages instead of the whole extract.
- **Operational dashboards.** Counting `page_failed` and `record_rejected` lines per run shows a provider's quality over weeks.

## Daily review

### Key takeaways

- Failures happen at four layers: network, HTTP status, body, record. Each needs its own reaction.
- Continue past one page or record, but fail the run past a threshold or on a failure that affects everything.
- Keep successes, remember failures, make them repairable; a checkpoint is the record of progress.
- Log events as `key=value` with a level, without secrets, and end with a summary line.
- A dead-letter table holds raw payload, error, attempts; it needs an owner and a redrive path.

### Common mistakes

- **`except Exception: pass`.** The run looks complete and is not. Record every failure and make the status truthful.
- **Logging secrets or whole responses.** Keys and personal data end up in log storage. Log URL without secrets, status and ids.
- **A dead-letter table nobody reads.** It becomes silent data loss. Assign an owner and report its size.
- **Failing the whole run for one bad record.** Set the record aside and continue; fail only past a threshold.
- **No raw payload in the dead letter.** You cannot redrive or prove what was sent. Store the JSON as received.

### Revision notes

- Layers: network, status, body, record.
- Fail fast vs continue; threshold on the failed share.
- `logging`: level, `key=value`, summary line, no secrets.
- Dead letter: payload, error, attempts, `resolved_at`; redrive.
- fetched = loaded + open dead letters.

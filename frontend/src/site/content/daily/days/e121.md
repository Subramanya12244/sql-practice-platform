## Objectives

- Split a pipeline into extract, transform and load functions with one responsibility each.
- Write transform functions as pure functions that take and return plain data.
- Pass sources and sinks into a `run` function so a test can substitute fakes.
- Write table-driven tests that check each step on known inputs and return a structured run result.

## Understand

### The problem with one long script

The pipeline you met on Day 120 can be written in one block: read the CSV, loop over the rows, clean each field inline, `INSERT` as you go and `print` a message here and there. It works on the day you write it. Then someone asks to change how amounts are cleaned, and you must run the whole thing, with a real file and a real database, to see whether the change broke anything. A bug in the date parsing is hidden among database calls. A test needs the database. The cure is not clever code, it is **separation of concerns**: each function does one kind of work, and the kinds are kept apart.

### Three kinds of work

Pipeline code does three kinds of work. **Input/output (I/O)** is anything that touches the world outside the process: reading a file, calling an API, writing to a table. It is slow, can fail for reasons outside your control, and is hard to test. **Pure logic** is calculation on values you already hold: cleaning an amount, parsing a timestamp, choosing the latest row. It is fast, deterministic and easy to test. **Orchestration** decides the order and handles the results: call extract, then transform, then load, and report. A good design puts each kind in its own function and keeps the pure logic free of I/O. In the orders pipeline that gives `extract(source)` (I/O in, raw rows out), `clean_amount`, `parse_ts`, `dedupe_latest` and `transform(rows)` (pure), `load(conn, rows)` (I/O out) and `run(...)` (orchestration).

### Pure functions

A **pure function** returns the same output for the same input and has no side effects: it does not print, read files, change its arguments or use global state. `clean_amount("$1,250.00")` always gives `125000`. Purity is what makes testing trivial: you call the function with an input and compare with the expected output, with no setup. The common ways to lose purity are mutating the argument list (sorting it in place), reading the current time inside the function (pass the time in), and logging or printing inside the logic (return what happened and let the caller report it). A function that has to return both good rows and problems returns both, for example `(good, rejected)`, as the pipeline's `transform` does.

### Small functions with clear contracts

Each function states what it takes and returns, and does one thing. `parse_ts` takes text and returns text; `transform` takes a list of dictionaries and returns two lists. A function that needs a long comment to say what it does is usually two functions. Names state the job (`dedupe_latest`, not `process`). The functions should not know about each other's internals: `load` accepts the clean rows, and should not know that they came from a CSV.

### Passing dependencies in

The orchestrator should not decide where data comes from or goes to. Instead of calling `open("orders.csv")` inside `run`, it takes a `source` (a function that returns the raw text) and a `sink` (a function that accepts the clean rows). In production the source reads the real file or API and the sink writes to PostgreSQL. In a test they are two tiny fakes: a function that returns a string and a list that records what it received. This technique is called **dependency injection**, and it needs nothing more than function arguments. It lets you test the whole run, including its counting and error handling, without a database or a file.

### Structured results

`run` should return a result object (a dictionary or a `dataclass`) with `read`, `loaded` and `rejected`, instead of printing. Printing is for the command-line wrapper at the edge of the program; returning lets the next step log, alert or assert. A misconception is that splitting code into many functions is overengineering for a small job. The split costs a few lines and gives you tests, reuse and readable failures: when a test says `clean_amount("abc")` returned `0`, the bug has one possible home.

### Testing the steps

A **table-driven test** is a list of input and expected-output pairs and one loop that checks them all. It is the cheapest way to cover the edge cases of a pure function: empty text, a currency symbol, thousands separators, negative numbers, text that is not a number. When a bug is found in production, add its input to the table first, then fix the code.

## Syntax and key functions

```python
def extract(source):            # I/O in:  source() returns text
    return parse_csv(source())

def transform(rows):            # pure:    list of dicts in, (good, rejected) out
    ...

def load(sink, rows):           # I/O out: sink(rows) writes them
    sink(rows)

def run(source, sink):          # orchestration: returns a result, prints nothing
    raw = extract(source)
    good, rejected = transform(raw)
    load(sink, good)
    return {"read": len(raw), "loaded": len(good), "rejected": len(rejected)}
```

```text
etl_orders/
    extract.py      # extract(source)
    transform.py    # clean_amount, parse_ts, dedupe_latest, transform
    load.py         # load(conn, rows)
    pipeline.py     # run(source, sink)
    tests/test_transform.py
```

| Item | What it does or returns |
|---|---|
| pure function | Same input gives same output; no I/O, no mutation of arguments, no globals. |
| source / sink | Functions passed to `run`: where raw text comes from, where clean rows go. |
| `@dataclass` | A class with fields generated from annotations; a readable result object. |
| `assert actual == expected, message` | Fails with a message when a test case is wrong. |
| `if __name__ == "__main__":` | Code that runs only when the file is started as a program, not when imported. |

## Learn by example

### Example 1: Tangled versus modular

The tangled function reads, cleans, loads and prints in one place. The modular version has the same result but each part can be called alone. The check at the end shows that both load the same rows.

```python run
import csv
import io
import sqlite3
from datetime import datetime, timezone

def extract(text):
    return list(csv.DictReader(io.StringIO(text)))

def clean_amount(text):
    """'$1,250.00' -> 125000 (cents); None when the text is not a number."""
    cleaned = text.replace("$", "").replace(",", "").strip()
    try:
        return round(float(cleaned) * 100)
    except ValueError:
        return None

def parse_ts(text):
    """ISO 8601 with Z -> normalised UTC text 'YYYY-MM-DDTHH:MM:SSZ'."""
    parsed = datetime.fromisoformat(text.replace("Z", "+00:00")).astimezone(timezone.utc)
    return parsed.strftime("%Y-%m-%dT%H:%M:%SZ")

def dedupe_latest(rows):
    latest = {}
    for row in rows:
        key = row["order_id"]
        if key not in latest or row["updated_at"] >= latest[key]["updated_at"]:
            latest[key] = row
    return [latest[key] for key in sorted(latest)]

def transform(raw_rows):
    good, rejected = [], []
    for r in raw_rows:
        cents = clean_amount(r["amount"])
        if cents is None:
            rejected.append((r["order_id"], "bad amount"))
            continue
        good.append({"order_id": int(r["order_id"]), "customer_id": int(r["customer_id"]), "amount_cents": cents,
                     "currency": r["currency"].upper(), "status": r["status"].strip().lower(),
                     "updated_at": parse_ts(r["updated_at"])})
    return dedupe_latest(good), rejected

def open_db():
    conn = sqlite3.connect(":memory:")
    conn.execute("""CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, customer_id INTEGER,
        amount_cents INTEGER, currency TEXT, status TEXT, updated_at TEXT)""")
    return conn

def load(conn, rows):
    conn.executemany("INSERT INTO orders_clean VALUES (:order_id,:customer_id,:amount_cents,:currency,:status,:updated_at)", rows)

RAW = """order_id,customer_id,amount,currency,status,updated_at
1,10,19.90,EUR,paid,2025-03-01T10:00:00Z
2,11,"1,250.00",EUR,PAID,2025-03-01T11:30:00Z
3,10,40.00,EUR,paid,2025-03-02T09:00:00Z
3,10,45.00,EUR,refunded,2025-03-03T08:00:00Z
4,12,abc,USD,paid,2025-03-02T12:00:00Z
5,13,$7.50,USD,failed,2025-03-03T15:45:00Z
6,11,12.00,EUR,paid,2025-03-04T07:15:00Z
"""

def tangled(text, conn):
    n = 0
    for r in csv.DictReader(io.StringIO(text)):
        try:
            cents = round(float(r["amount"].replace("$", "").replace(",", "")) * 100)
        except ValueError:
            print("skip", r["order_id"])
            continue
        conn.execute("INSERT OR REPLACE INTO orders_clean VALUES (?,?,?,?,?,?)",
                     (int(r["order_id"]), int(r["customer_id"]), cents, r["currency"].upper(), r["status"].strip().lower(), r["updated_at"]))
        n += 1
    return n

a = open_db()
print("tangled loaded", tangled(RAW, a))

b = open_db()
good, rejected = transform(extract(RAW))
load(b, good)
sql = "SELECT * FROM orders_clean ORDER BY order_id"
print("modular loaded", len(good), "rejected", len(rejected))
print("same rows:", a.execute(sql).fetchall() == b.execute(sql).fetchall())
```

```output
skip 4
tangled loaded 6
modular loaded 5 rejected 1
same rows: True
```
### Example 2: Table-driven tests for a pure function

Each case is an input and the expected output. A single loop checks every case and collects the failures, so one run shows all of them. The last case is the kind you would add after a production bug.

```python run
def clean_amount(text):
    cleaned = text.replace("$", "").replace(",", "").strip()
    try:
        return round(float(cleaned) * 100)
    except ValueError:
        return None

CASES = [
    ("19.90", 1990),
    ("$1,250.00", 125000),
    ("  7.5 ", 750),
    ("0", 0),
    ("-5.00", -500),
    ("abc", None),
    ("", None),
]
failures = [(text, expected, clean_amount(text)) for text, expected in CASES if clean_amount(text) != expected]
print("cases:", len(CASES), "failures:", failures)
```

```output
cases: 7 failures: []
```

### Example 4: A result object and the real sink

The result is a `dataclass`, and the sink for production is a function that writes into the `sqlite3` table (the PostgreSQL stand-in). The same `run` function serves the test and the real database. The reconciliation `read == loaded + rejected + duplicates` is a property of the result.

```python run
from dataclasses import dataclass
import csv
import io
import sqlite3
from datetime import datetime, timezone

def extract(text):
    return list(csv.DictReader(io.StringIO(text)))

def clean_amount(text):
    """'$1,250.00' -> 125000 (cents); None when the text is not a number."""

    return parsed.strftime("%Y-%m-%dT%H:%M:%SZ")

def dedupe_latest(rows):

    conn.executemany("INSERT INTO orders_clean VALUES (:order_id,:customer_id,:amount_cents,:currency,:status,:updated_at)", rows)

RAW = """order_id,customer_id,amount,currency,status,updated_at
1,10,19.90,EUR,paid,2025-03-01T10:00:00Z
2,11,"1,250.00",EUR,PAID,2025-03-01T11:30:00Z
3,10,40.00,EUR,paid,2025-03-02T09:00:00Z
3,10,45.00,EUR,refunded,2025-03-03T08:00:00Z
4,12,abc,USD,paid,2025-03-02T12:00:00Z
5,13,$7.50,USD,failed,2025-03-03T15:45:00Z
6,11,12.00,EUR,paid,2025-03-04T07:15:00Z
"""

@dataclass
class RunResult:
    read: int
    loaded: int
    rejected: int

    @property
    def duplicates(self):
        return self.read - self.loaded - self.rejected

def run(source, sink):
    raw = extract(source())
    good, rejected = transform(raw)
    sink(good)
    return RunResult(len(raw), len(good), len(rejected))

conn = open_db()
result = run(lambda: RAW, lambda rows: load(conn, rows))
print(result)
print("duplicates removed:", result.duplicates)
print("in table:", conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0])
```

```output
RunResult(read=7, loaded=5, rejected=1)
duplicates removed: 1
in table: 5
```
### Example 5: Tests for the whole run with a failing source

A test also covers failure paths. The fake source raises an error; `run` should let it propagate before anything is written, so the sink is never called. The asserts pass silently, and the final line proves they ran.

def broken_source():

try:

## Real-world applications

- **Safer changes.** When a rule changes (for example, accept `€` in amounts), the table-driven test of Example 2 gets new cases and a run takes milliseconds, without a database.
- **CI for pipelines.** The fakes of Examples 3 and 5 let a build server run the whole `run` function on every commit without access to production systems.
- **Reuse.** The same `transform` serves the batch job and a later backfill job, because it does not know where its rows come from.
- **Clear incident reports.** A result object with `read`, `loaded` and `rejected` is what a monitoring step reports, instead of text scraped from print output.

## Daily review

### Key takeaways

- Keep I/O, pure logic and orchestration in separate functions.
- Pure functions are tested with input and expected output only.
- Pass the source and the sink into `run`; use fakes in tests.
- Return a result from `run`; printing belongs at the edge.
- Table-driven tests cover edge cases cheaply; add every production bug as a new case.

### Common mistakes

- Opening files or connecting to the database inside a transform, so it cannot be tested without them. Pass data in and return data out.
- Mutating the input list (`rows.sort()`) inside a transform, so the caller's data changes. Use `sorted(rows)`.
- Printing inside the logic, which cannot be asserted. Return a result and let the caller print.
- One giant `main` with no functions, where any change needs a full real run to check. Extract the steps.
- Testing only the happy path. Add the empty input, the bad value and the failing source.

### Revision notes

- extract (I/O in), transform (pure), load (I/O out), run (orchestration).
- `run(source, sink)` returns a result; fakes make it testable.
- Table-driven test: list of `(input, expected)`, one loop, collect failures.
- Layout: one module per concern, tests beside them.

## Objectives

- Apply a method to Python interview questions: restate with examples, choose a data structure, state the complexity, write, then test with edge cases.
- Pick the right built-in structure (dict, set, `Counter`, `deque`, list) and say why in terms of lookup cost.
- Write generators that process data lazily and in batches, and explain what they save.
- Process CSV and line-based files safely: parse, quarantine bad rows, aggregate, and never load more than needed.
- Write small pipeline functions (latest record per key, retry with a limit) that are deterministic and easy to test.

## Understand

### What a Python interview for data engineers asks

Expect three kinds of questions. **Data-structure problems** (count, group, find a pair, remove duplicates) check that you know the standard library and the cost of each operation. **Streaming and file problems** (process a file too big for memory, read a CSV with bad rows) check that you think about memory and failure. **Pipeline code problems** (deduplicate events, retry a call, validate records) check that you write small, deterministic, testable functions. The evaluator watches how you work as much as the answer: whether you ask what the input looks like, name the complexity, and test with a small example before saying you are done.

### A method for coding questions

1. **Restate with an example.** "Given a list of orders, return the customers with more than two orders. For `[a, b, a, a]` the answer is `[a]`." Ask about edge cases: empty input, duplicates, order of the output, input size.
2. **Choose the structure and say the cost.** "I will count with a dictionary, which is linear in the number of orders."
3. **Write the simple version** with clear names, then improve it if the interviewer asks.
4. **Test aloud** with the example, an empty input and an extreme case.
5. **State complexity** in time and memory (`O(n)`, `O(n log n)`), and mention what changes if the input does not fit in memory.

### Data structures and their costs

A **list** keeps order and lets you index by position; looking for a value in a list costs `O(n)`. A **dict** maps keys to values and a **set** keeps unique values; both find a key in about constant time on average, which makes them the first tool for "have I seen this?", counting, grouping and joining two collections. `collections.Counter` counts hashable items; `defaultdict(list)` groups items by a key; `deque` is a double-ended queue with fast appends and pops at both ends (a plain list is slow when you remove from the front); `heapq` keeps the smallest or largest items (top-k) in `O(n log k)`. Sorting costs `O(n log n)`, and `sorted` is stable: items with equal keys keep their original order, which you can use for tie-breaking. Two classic problems show the value of a dict: **two-sum** (find two numbers adding to a target) in one pass by remembering what you have seen, instead of a nested loop of `O(n^2)`; and **grouping anagrams** by using the sorted letters as the key.

### Generators and lazy processing

A **generator** is a function that uses `yield` to produce values one at a time and remembers where it stopped. It computes the next value only when asked, so a pipeline of generators handles a million lines while holding one line (or one batch) in memory. A list comprehension builds the whole list first; a generator expression, written with parentheses, does not. Generators are consumed once: after you iterate, they are exhausted. Batching is a common pattern: a generator collects `n` items into a list and yields it, which suits loading to a database in groups. A frequent interview follow-up is "what if the file is larger than memory?", and the answer is to iterate the file object line by line (it is already lazy) and keep only counters or a bounded structure.

### File and CSV processing

Open files with `with open(path, newline="", encoding="utf-8") as f:` so that they are closed even on error. The `csv` module parses quoting correctly: `csv.DictReader` gives a dict for each row keyed by the header. Real files contain bad rows (a missing field, text in a number column), so decide the policy before you code: skip with a count, quarantine the row with the reason, or fail fast. Never let one bad row crash a nightly job without a trace, and never drop rows silently (Day 168). Convert types at the boundary, in one place, and keep the parsing function separate from the aggregation so that each can be tested with a few lines of text. For tests and examples, `io.StringIO` stands in for a file.

### Pipeline code that is easy to test

Prefer **pure functions**: the output depends only on the input and nothing is printed or written inside. Pass dependencies in as arguments, for example a `sleep` function for a retry helper, so that a test does not wait. Make steps **idempotent**: processing the same input twice gives the same result (the latest-record rule, an upsert). Use `logging` rather than `print` in real jobs, and raise specific exceptions. A **retry** wraps a call, catches only the errors worth retrying, waits longer each time (exponential backoff) and gives up after a limit by re-raising the last error.

### Common pitfalls interviewers look for

A **mutable default argument** (`def f(x, seen=[])`) shares one list across calls. **Modifying a list while iterating** over it skips items. **Float equality**: `0.1 + 0.2 == 0.3` is false, so compare with a tolerance or use `Decimal` for money. `is` tests identity and `==` tests equality. **Copying**: `b = a` for a list makes a second name for the same list. **Integer division** in Python 3 is `//`, and `/` always gives a float.

### Why it matters, and the misconception

These skills are the daily tools of pipeline code. The misconception is that the interview is about clever tricks. A simple dict-based solution with a stated complexity and two tests beats a clever one-liner that you cannot explain.

## Syntax and key functions

```python
from collections import Counter, defaultdict, deque
import csv, heapq, io

counts = Counter(items)                    # item -> count
groups = defaultdict(list)                 # key -> list
seen = {}                                  # value -> index (two-sum)

def batches(iterable, n):                  # generator
    batch = []
    for x in iterable:
        batch.append(x)
        if len(batch) == n:
            yield batch
            batch = []
    if batch:
        yield batch
```

| Tool | Use and cost |
|---|---|
| `dict`, `set` | Membership and lookup in about `O(1)` on average. |
| `Counter(items).most_common(k)` | Count and rank items. |
| `defaultdict(list)` | Group items by key. |
| `deque` | Fast append and pop at both ends. |
| `heapq.nlargest(k, items)` | Top-k without a full sort. |
| `sorted(items, key=...)` | Stable sort, `O(n log n)`. |
| `csv.DictReader(f)` | Rows as dicts keyed by header. |
| `yield` | Produces values lazily, one at a time. |

## Learn by example

### Example 1: Data structures: counting, two-sum, anagram groups

Three classic questions, each with a dictionary. The two-sum solution makes one pass and remembers the index of every value seen. Grouping anagrams uses the sorted letters as the key.

```python run
from collections import Counter, defaultdict

orders = ["ana", "ben", "ana", "cy", "ana", "ben"]
print([c for c, n in sorted(Counter(orders).items()) if n > 1])

def two_sum(nums, target):
    seen = {}
    for i, x in enumerate(nums):
        if target - x in seen:
            return seen[target - x], i
        seen[x] = i
    return None

print(two_sum([2, 7, 11, 15], 9), two_sum([1, 2, 3], 10))

groups = defaultdict(list)
for w in ["listen", "silent", "enlist", "google", "gogole", "cat"]:
    groups["".join(sorted(w))].append(w)
print(sorted(sorted(g) for g in groups.values()))
```

```output
['ana', 'ben']
(0, 1) None
[['cat'], ['enlist', 'listen', 'silent'], ['gogole', 'google']]
```

Each solution is linear in the input size apart from the sorting of letters inside each word. State that, and name the structure you chose: a dict from value to index, and a dict from sorted letters to words.

### Example 2: Generators are lazy

The generator pipeline parses and filters ten items, but the print inside the source shows when each item is actually produced. With a list, all ten would be produced first. With generators, the first batch is produced after only the items it needs.

```python run
def source():
    for i in range(1, 11):
        print("produce", i)
        yield i

def evens(it):
    return (x for x in it if x % 2 == 0)

def batches(it, n):
    batch = []
    for x in it:
        batch.append(x)
        if len(batch) == n:
            yield batch
            batch = []
    if batch:
        yield batch

gen = batches(evens(source()), 2)
print("first batch:", next(gen))
print("then:", list(gen))
```

```output
produce 1
produce 2
produce 3
produce 4
first batch: [2, 4]
produce 5
produce 6
produce 7
produce 8
produce 9
produce 10
then: [[6, 8], [10]]
```

Only the items needed for the first batch were produced before it was printed (1 to 4), and the rest were produced when `list(gen)` asked for them. This is how a pipeline processes a file larger than memory.

### Example 3: CSV with bad rows

The parser converts types in one function and returns either a record or a reason. Bad rows are quarantined with the line number and reason, and the totals are computed on the good rows. The check at the end is the reconciliation of Day 168: every line is either good or quarantined.

```python run
import csv
import io

text = """order_id,customer,amount
1,ana,19.99
2,ben,abc
3,,12.50
4,cy,30.00
5,ana,
"""

def parse(row):
    if not row["customer"]:
        return None, "missing customer"
    try:
        return {"order_id": int(row["order_id"]), "customer": row["customer"], "amount": float(row["amount"])}, None
    except ValueError:
        return None, "bad number"

good, quarantine = [], []
for line_no, row in enumerate(csv.DictReader(io.StringIO(text)), start=2):
    rec, reason = parse(row)
    if rec:
        good.append(rec)
    else:
        quarantine.append((line_no, reason))
totals = {}
for r in good:
    totals[r["customer"]] = round(totals.get(r["customer"], 0) + r["amount"], 2)
print("good:", len(good), "| quarantined:", quarantine)
print("totals:", totals)
print("accounted for:", len(good) + len(quarantine) == 5)
```

```output
good: 2 | quarantined: [(3, 'bad number'), (4, 'missing customer'), (6, 'bad number')]
totals: {'ana': 19.99, 'cy': 30.0}
accounted for: True
```

Three of five rows are quarantined with their line numbers, which makes the failure reviewable. The empty amount in the last row fails `float("")` and is treated as a bad number.

### Example 4: Latest record per key

A pipeline function that keeps the latest event for each order, written as a pure function. Applying it to its own output gives the same result (idempotent), and the order of the input does not change the answer when timestamps differ.

```python run
def latest_per_key(events):
    best = {}
    for key, ts, value in events:
        if key not in best or ts > best[key][0]:
            best[key] = (ts, value)
    return {k: v[1] for k, v in sorted(best.items())}

events = [(1, 10, "paid"), (2, 10, "paid"), (1, 20, "refunded"), (3, 5, "paid")]
once = latest_per_key(events)
print(once)
as_events = [(k, 99, v) for k, v in once.items()]
print("idempotent:", latest_per_key(as_events) == once)
print("order independent:", latest_per_key(list(reversed(events))) == once)
```

```output
{1: 'refunded', 2: 'paid', 3: 'paid'}
idempotent: True
order independent: True
```

State the complexity: one pass, `O(n)` time and `O(k)` memory for `k` distinct keys. A follow-up is what to do on equal timestamps: decide a tie-break rule (for example the later position wins) and say it aloud.

### Example 5: A retry helper that tests quickly

The helper retries a flaky call up to a limit and re-raises the last error. The `sleep` function is passed in, so the test records the delays instead of waiting, and the delays show the exponential backoff.

```python run
def retry(fn, attempts, sleep, base=1.0):
    last = None
    for i in range(attempts):
        try:
            return fn()
        except ConnectionError as e:
            last = e
            if i < attempts - 1:
                sleep(base * 2 ** i)
    raise last

calls = {"n": 0}
def flaky():
    calls["n"] += 1
    if calls["n"] < 3:
        raise ConnectionError("temporary")
    return "ok"

delays = []
print(retry(flaky, 5, delays.append), "after", calls["n"], "calls; delays:", delays)

def always_fails():
    raise ConnectionError("down")
delays2 = []
try:
    retry(always_fails, 3, delays2.append)
except ConnectionError as e:
    print("gave up:", e, "| delays:", delays2)
```

```output
ok after 3 calls; delays: [1.0, 2.0]
gave up: down | delays: [1.0, 2.0]
```

Only `ConnectionError` is retried, so a programming error such as a `KeyError` would surface immediately. That choice, and the limit, are what an interviewer wants to hear.

## Real-world applications

- **Ingestion jobs**: the CSV parser with quarantine (Example 3) is the first stage of most file-based pipelines.
- **Large files**: generator batches (Example 2) feed a database loader without holding the file in memory.
- **Deduplication**: the latest-record function (Example 4) is the Python form of the SQL window rule used in the earlier days.
- **Resilient API calls**: the retry helper (Example 5) wraps calls to rate-limited services.

## Daily review

### Key takeaways

- Restate with an example, choose a structure, say the cost, write, test, state the complexity.
- dict and set give constant-time membership on average; `Counter` and `defaultdict` cover counting and grouping.
- Generators produce values on demand and can be consumed only once.
- Parse at the boundary, quarantine bad rows with a reason, and reconcile the counts.
- Prefer pure, idempotent functions with injected dependencies.

### Common mistakes

- Checking `x in some_list` inside a loop. It is `O(n)` each time and the whole is `O(n^2)`; use a set or dict.
- Reading a whole file with `f.read()` or `readlines()` when a line loop would do. Memory grows with the file.
- Reusing an exhausted generator. The second loop sees nothing; recreate it or store the data.
- A mutable default argument. State leaks across calls; use `None` and create the object inside.
- Catching `Exception` in a retry. Programming errors are retried and hidden; catch the specific error.

### Revision notes

- Costs: dict/set `O(1)`, list search `O(n)`, sort `O(n log n)`.
- `yield` for lazy sequences; batches with a list and a size check.
- `csv.DictReader` plus a parse function returning a record or a reason.
- Retry: limit, backoff, specific exception, injected sleep.

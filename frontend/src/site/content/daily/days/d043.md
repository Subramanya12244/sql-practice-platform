## Objectives

- Write a scalar subquery that returns one value and use it in `WHERE` or in the select list.
- Use `IN (subquery)` to filter by a list that another query computes.
- Write a correlated subquery that refers to the outer row, and explain why it runs once per outer row logically.
- Put a subquery in `FROM` as a derived table and aggregate over an aggregate.
- Choose between a subquery and a join for a given question.

## Understand

### A query inside a query

A **subquery** is a `SELECT` written in parentheses inside another query (the **outer query**). It lets one query use the result of another, so a question that needs two steps can be written as one statement. Suppose you want the products priced above the average price. Step one: find the average, 28.87. Step two: filter on it. You could run both steps and type 28.87 into the second, but the number would go stale as soon as prices change. A subquery computes it every time: `WHERE unit_price > (SELECT AVG(unit_price) FROM products)`. This is also the answer to day 36's "aggregates are not allowed in WHERE": the aggregate lives in its own query, which has already finished when `WHERE` runs.

Where a subquery may sit decides what shape of result it must have. There are four common places, and the four sections below take them in turn.

### Scalar subqueries: one value

A **scalar subquery** returns exactly one row and one column, a single value, so it can be used anywhere a value fits: in a comparison, in arithmetic, or as a column in the select list. `(SELECT MAX(order_date) FROM orders)` returns one date, so `WHERE order_date = (SELECT MAX(order_date) FROM orders)` finds the latest order. If a scalar subquery returns more than one row, PostgreSQL stops with "more than one row returned by a subquery used as an expression". If it returns no row, its value is NULL and a comparison with it is unknown, so nothing matches. Aggregates without `GROUP BY` always return exactly one row, which is why they are the most common scalar subqueries.

### IN subqueries: a list of values

`IN (subquery)` works like `IN` with a typed list (day 33), except the list is computed. The subquery must return a single column and may return many rows. `WHERE customer_id IN (SELECT customer_id FROM orders WHERE freight > 150)` keeps the customers who have at least one order with freight above 150. Each customer appears at most once, however many such orders they have, which is a difference from a join: a join would repeat the customer once per matching order (day 40). `NOT IN` keeps the customers not in the list, but it has a trap with NULLs: if the subquery's list contains a NULL, `NOT IN` returns no rows at all. Day 48 explains this and the safer alternative; for now use `NOT IN` only on a column that cannot be NULL.

### Correlated subqueries: one run per outer row

So far each subquery was independent: it could run alone, once, and the outer query used the result. A **correlated subquery** refers to a column of the outer query, so its result changes for every outer row. For "products priced above the average of their own category" the average depends on which product you are looking at:

`WHERE p.unit_price > (SELECT AVG(p2.unit_price) FROM products p2 WHERE p2.category_id = p.category_id)`

Think of the database working through the outer rows one by one. For each product `p` it plugs that product's `category_id` into the inner query, calculates the category average, and compares. The inner table needs its own alias (`p2`) so that `p2.category_id = p.category_id` states clearly which side is which. PostgreSQL's planner may rewrite this into a join internally, but you should reason about it as one inner run per outer row; on large tables that can be slow, so correlated subqueries are best on moderate data or with an index on the correlating column.

A correlated subquery can also sit in the select list, as a per-row calculation: for each order, `(SELECT COUNT(*) FROM order_details od WHERE od.order_id = o.order_id)` counts its lines. This avoids the row multiplication of a join, because the outer query still has one row per order.

### Subqueries in FROM: derived tables

A subquery in `FROM` produces a temporary table that the outer query uses like any table. It must have an alias. This is the way to aggregate twice. To find how many customers placed 1 order, 2 orders, 3 orders, first count orders per customer (an aggregate) and then count customers per order count (a second aggregate over the first result). An aggregate cannot be applied to another aggregate in one `SELECT`, so the inner query goes in `FROM`:

`SELECT n, COUNT(*) FROM (SELECT customer_id, COUNT(*) AS n FROM orders GROUP BY customer_id) t GROUP BY n`

Columns of a derived table are referred to by their aliases, so name them. Day 46 introduces common table expressions, which write the same thing more readably.

### Subquery or join?

Many questions can be written both ways. Use a join when you need columns from both tables in the output. Use a subquery when you only need the other table to decide which rows to keep (`IN`), or to compute a single value. Use a derived table to aggregate before joining or to aggregate twice.

### Common misconception

Learners think a subquery in parentheses is always evaluated once. Only uncorrelated subqueries behave that way. A correlated one depends on the outer row, which is why it can be correct but slow. Another belief is that `= (subquery)` and `IN (subquery)` are interchangeable: `=` demands a single value, `IN` accepts a list.

### Why it matters

Questions such as "above average", "the latest", "customers who ever did X" and "distribution of counts" all need a value computed from the data itself. Subqueries keep those values live and correct, and they are among the most common interview topics.

## Syntax and key functions

```sql-syntax
-- scalar subquery in WHERE or SELECT
WHERE column > (SELECT AVG(column) FROM table_name)
SELECT (SELECT COUNT(*) FROM child c WHERE c.fk = p.pk) AS child_count

-- list subquery
WHERE column IN (SELECT column FROM table_name WHERE condition)

-- correlated subquery
WHERE p.value > (SELECT AVG(p2.value) FROM table_name p2 WHERE p2.group_id = p.group_id)

-- derived table
FROM (SELECT key, COUNT(*) AS n FROM table_name GROUP BY key) t
```

| Kind | Must return | Placed in | Runs |
|---|---|---|---|
| Scalar | One row, one column | `WHERE`, `HAVING`, `SELECT` | Once |
| List (`IN`) | One column, any number of rows | `WHERE` | Once |
| Correlated | One value per outer row (usually scalar) | `WHERE`, `SELECT` | Logically once per outer row |
| Derived table | A whole table, with an alias | `FROM` | Once |

## Learn by example

### Example 1: Products above the average price

The inner query returns one number, 28.87 before rounding, and the outer query compares each price with it. The average is recalculated every time the query runs, so the result stays correct when prices change. Twenty-five of the 77 products are above average; the five dearest are shown.

```sql run
SELECT product_id, product_name, unit_price
FROM products
WHERE unit_price > (SELECT AVG(unit_price) FROM products)
ORDER BY unit_price DESC, product_id
LIMIT 5;
```

```output
product_id | product_name | unit_price
38 | Côte de Blaye | 263.50
29 | Thüringer Rostbratwurst | 123.79
9 | Mishi Kobe Niku | 97.00
20 | Sir Rodney's Marmalade | 81.00
18 | Carnarvon Tigers | 62.50
```

### Example 2: The latest order

A scalar subquery with `MAX` finds the most recent order date, and the outer query returns the orders on that date. Using `=` is safe because the subquery returns exactly one row. If two orders shared the latest date, both would be returned, which is the behaviour you usually want.

```sql run
SELECT order_id, customer_id, order_date
FROM orders
WHERE order_date = (SELECT MAX(order_date) FROM orders);
```

```output
order_id | customer_id | order_date
10331 | VICTE | 1998-12-28
```

### Example 3: Customers with a heavy order, using IN

The inner query returns the `customer_id` of every order with freight above 150, with repeats. `IN` only asks whether the customer is in that list, so each customer appears once in the result however many heavy orders they placed. Twenty-two customers qualify; the first six are shown.

```sql run
SELECT customer_id, company_name
FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders WHERE freight > 150)
ORDER BY customer_id
LIMIT 6;
```

```output
customer_id | company_name
ANATR | Ana Trujillo Emparedados
BLAUS | Blauer See Delikatessen
BLONP | Blondesddsl père et fils
BOLID | Bólido Comidas preparadas
BONAP | Bon app'
EASTC | Eastern Connection
```

### Example 4: Above the average of the product's own category

The subquery refers to `p.category_id` of the outer row, so it calculates a different average for each product. Product 38 (Côte de Blaye) is far above the average of category 1, whereas a price of 25.00 is above the lower average of category 2. The first six of the 27 matching products are shown.

```sql run
SELECT p.product_id, p.product_name, p.unit_price, p.category_id
FROM products p
WHERE p.unit_price > (SELECT AVG(p2.unit_price)
                      FROM products p2
                      WHERE p2.category_id = p.category_id)
ORDER BY p.category_id, p.product_id
LIMIT 6;
```

```output
product_id | product_name | unit_price | category_id
38 | Côte de Blaye | 263.50 | 1
43 | Ipoh Coffee | 46.00 | 1
6 | Grandma's Boysenberry Spread | 25.00 | 2
8 | Northwoods Cranberry Sauce | 40.00 | 2
61 | Sirop d'érable | 28.50 | 2
63 | Vegie-spread | 43.90 | 2
```

### Example 5: A correlated subquery as a column

For each order the subquery counts its lines. The outer query keeps one row per order, so there is no row multiplication, unlike joining to `order_details`. Order 10334 has the highest freight and three lines.

```sql run
SELECT o.order_id, o.freight,
       (SELECT COUNT(*) FROM order_details od WHERE od.order_id = o.order_id) AS lines
FROM orders o
ORDER BY o.freight DESC, o.order_id
LIMIT 3;
```

```output
order_id | freight | lines
10334 | 199.52 | 3
10344 | 199.24 | 1
10308 | 197.96 | 1
```

### Example 6: A subquery in FROM, aggregating twice

The inner query counts orders for each customer. The outer query then groups those counts: how many customers have 1 order, how many have 2, and so on. The inner result is a derived table named `t`, and its column `n` is used by the outer query. Customers without orders are not in the inner table, because it counts rows of `orders` only.

```sql run
SELECT t.n AS orders_per_customer, COUNT(*) AS customers
FROM (SELECT customer_id, COUNT(*) AS n
      FROM orders
      GROUP BY customer_id) t
GROUP BY t.n
ORDER BY t.n;
```

```output
orders_per_customer | customers
1 | 79
2 | 9
3 | 1
```

## Real-world applications

**Above and below the benchmark.** "Customers whose revenue is above average", "products priced above the category average" (example 4) and "orders larger than the typical order" are all comparisons with a computed benchmark.

**Latest and earliest records.** Finding the most recent order, the highest price or the newest hire uses a scalar subquery on `MAX` or `MIN` (example 2), a pattern that works in every SQL database.

**Membership filters.** "Customers who bought product X", "employees who handled an order above Y" use `IN` (example 3), which also guarantees one row per customer without `DISTINCT`.

**Distributions and nested statistics.** Counting how many customers have each number of orders (example 6) or computing the average of per-customer totals needs an aggregate over an aggregate, which is a derived table.

## Daily review

### Key takeaways

- A subquery is a `SELECT` in parentheses. Scalar returns one value, `IN` returns a column, a derived table returns a table.
- A scalar subquery with an aggregate lets `WHERE` compare with an average, maximum or count.
- A correlated subquery refers to the outer row and is logically evaluated per row; give both tables aliases.
- A derived table in `FROM` needs an alias and lets you aggregate an aggregate.
- Use `IN` when you only need to test membership; a join repeats rows, `IN` does not.

### Common mistakes

- Using `=` with a subquery that returns several rows: "more than one row returned by a subquery used as an expression". Use `IN`, or make the subquery return one row with an aggregate or `LIMIT 1`.
- Forgetting the alias on a derived table: "subquery in FROM must have an alias".
- Returning two columns from an `IN` subquery: "subquery has too many columns". Select only the key.
- Writing the correlation condition against the inner table only, for example `WHERE p2.category_id = p2.category_id`, which makes the subquery uncorrelated and compares every product with the overall average.
- Using `NOT IN` against a column that may contain NULL, and getting an empty result (day 48).
- Reaching for a correlated subquery on a huge table where a join and `GROUP BY` would be faster.

### Revision notes

- `WHERE x > (SELECT AVG(x) ...)`: scalar, once.
- `WHERE k IN (SELECT k ...)`: one column, many rows.
- Correlated: inner refers to outer alias, evaluated per outer row.
- `FROM (SELECT ...) t`: alias required, for aggregating twice.

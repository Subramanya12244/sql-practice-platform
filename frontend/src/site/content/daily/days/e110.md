## Objectives

- Load cleaned API records into a constrained `orders` table through a staging table, and explain why staging comes first.
- Write an upsert with `INSERT ... ON CONFLICT (order_id) DO UPDATE`, and avoid rewriting unchanged rows with a change condition.
- Count what a run did (inserted, updated, unchanged) and record it in a `load_log` table.
- Wrap a load in a transaction so that a failure leaves `orders` exactly as it was, while the failure itself is still logged.
- Show that running the same load twice changes nothing the second time, on `sqlite3`, SQLAlchemy and PostgreSQL syntax.

## Understand

### From a DataFrame to a table that already has rows

Day 109 produced a clean DataFrame whose columns and types match the target table. Day 94 loaded a CSV into an empty table. The API case is harder in one way: tomorrow's extract overlaps today's table. An order that was `paid` yesterday may be `refunded` today, and the same order id arrives again with a new status. A plain `INSERT` would fail on the primary key or, without a key, duplicate the order. The load therefore has to **insert the new orders and update the changed ones**, and leave the rest alone.

### Staging

A **staging table** is a plain copy of the extract, with no constraints and the same columns, that exists only to receive the batch. The flow has two steps. First, empty the staging table and bulk-insert the cleaned rows into it (`executemany`, `COPY`, or `DataFrame.to_sql` as on Day 94). Second, one SQL statement moves the rows from staging into `orders`. This design has four benefits. The slow, error-prone step (talking to the API, cleaning) is finished before the production table is touched. The real work happens inside the database as one set-based statement. You can query the staging table to **compare** it with `orders` before changing anything, which is how you count inserts and updates. And a failure leaves `orders` untouched because the second step runs in one transaction. Clearing the staging table at the start of each run, rather than the end, leaves the last batch available for inspection after a failure.

### The upsert

An **upsert** (update or insert) is `INSERT ... ON CONFLICT (order_id) DO UPDATE SET ...`. If no row with that key exists, the row is inserted. If one exists, the conflict clause updates it from `EXCLUDED`, the name for the row proposed for insertion. `DO NOTHING` skips rows whose key exists instead. Both forms need a primary key or unique constraint on the conflict column, and both work in PostgreSQL and in SQLite 3.24 and later. A `WHERE` after `DO UPDATE SET` limits the update to rows that really differ. Without it every existing row is rewritten on every run, which writes new row versions for nothing and, in PostgreSQL, bloats the table. In PostgreSQL the test is `WHERE orders.status IS DISTINCT FROM EXCLUDED.status OR ...`, where `IS DISTINCT FROM` is a comparison that treats two NULLs as equal. SQLite spells the same null-safe test `IS NOT`, which the Python examples use.

Two rules matter for correctness. First, the staging data must have **one row per key**: PostgreSQL raises "ON CONFLICT DO UPDATE command cannot affect row a second time" when one statement proposes the same key twice, which is why Day 109 removed duplicates first. Second, the update list must name only the columns that may change; the key itself is never updated.

### Transactions and the load log

Day 94 explained that a transaction makes a group of statements all-or-nothing. The staging fill and the upsert belong in one transaction: if a `CHECK` constraint rejects one row, everything rolls back and `orders` is exactly as before. The **load log** is separate. It is a small table with one row per run: when it started, how many rows were staged, how many were inserted, updated and unchanged, the final status (`running`, `ok`, `failed`) and the error text. It is written **outside** the main transaction, so that a failed run still leaves a `failed` row; if the log row were inside the transaction, the rollback would erase the evidence. Counting happens before the upsert by comparing staging with `orders`: rows with no match are inserts, matching rows that differ are updates, and the rest are unchanged. `staged = inserted + updated + unchanged` is the load's own reconciliation.

### Stand-ins and real PostgreSQL

No PostgreSQL server runs in these lessons. The Python examples use the standard library's `sqlite3` in memory, which has the same `ON CONFLICT` syntax and `excluded` row. A full PostgreSQL version of the upsert runs on PGlite in the SQL example. Differences from PostgreSQL to remember: placeholders are `?` in `sqlite3` and `%s` in `psycopg`; PostgreSQL has real types (`timestamptz` for `created_at`, `integer`, `text`) while SQLite stores what it is given; an `INSERT ... SELECT ... ON CONFLICT` in SQLite needs a `WHERE true` after the `SELECT` to avoid a parsing ambiguity, and PostgreSQL does not. Credentials come from environment variables (Day 105), never from the code.

### Common misconception

Learners believe that `to_sql(if_exists="replace")` is the simplest way to load an API extract. It drops the table, with its primary key, its constraints, its types and every other table's foreign key to it, and replaces it with whatever the DataFrame holds. Use it for staging at most, never for the target table.

### Why it matters

An API pipeline runs every night on overlapping data. An upsert makes the second night as safe as the first, the transaction makes failures clean, and the load log answers "what happened in last night's run" in one query.

## Syntax and key functions

```sql-syntax
INSERT INTO orders (order_id, customer_id, amount_cents, currency, status, created_at)
SELECT order_id, customer_id, amount_cents, currency, status, created_at FROM stg_orders
ON CONFLICT (order_id) DO UPDATE SET
    customer_id = EXCLUDED.customer_id, amount_cents = EXCLUDED.amount_cents,
    currency = EXCLUDED.currency, status = EXCLUDED.status, created_at = EXCLUDED.created_at
WHERE orders.status IS DISTINCT FROM EXCLUDED.status
   OR orders.amount_cents IS DISTINCT FROM EXCLUDED.amount_cents;
```

| Item | What it does or returns |
|---|---|
| `INSERT ... ON CONFLICT (key) DO UPDATE SET ...` | Insert new rows, update existing ones. |
| `EXCLUDED.col` / `excluded.col` | The proposed row's value. |
| `... WHERE target.col IS DISTINCT FROM EXCLUDED.col` | Update only rows that changed (PostgreSQL; `IS NOT` in SQLite). |
| `ON CONFLICT ... DO NOTHING` | Skip existing keys. |
| `conn.executemany(sql, rows)` | Batch insert into staging. |
| `with conn:` (sqlite3) / `with psycopg.connect(...)` | Commit on success, roll back on error. |
| `load_log` | One row per run: counts, status, error. |
| `engine.begin()` (SQLAlchemy) | A connection inside a transaction. |

## Learn by example

### Example 1: Stage, count and upsert, with a load log

`load_run` (shown in full) creates the tables, logs a `running` row, fills staging, counts new, changed and unchanged rows by comparing with `orders`, upserts only the changed rows and updates the log. The first run loads orders 1 to 6. The second run brings orders 4 to 9, with order 5 refunded and the amount of order 6 corrected.

```python run
import sqlite3

STATUSES = ["paid", "paid", "refunded", "failed"]
ORDERS = [
    {"order_id": i, "customer_id": i * 7 % 25 + 1, "amount_cents": 1000 + i * 137 % 9000,
     "currency": "EUR" if i % 4 else "USD", "status": STATUSES[i % 4],
     "created_at": f"2026-03-{(i - 1) // 4 + 1:02d}T{i * 7 % 24:02d}:{i * 13 % 60:02d}:00Z"}
    for i in range(1, 121)
]

SCHEMA = """
CREATE TABLE IF NOT EXISTS orders (
    order_id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL,
    amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0),
    currency TEXT NOT NULL, status TEXT NOT NULL, created_at TEXT NOT NULL);
CREATE TABLE IF NOT EXISTS stg_orders (
    order_id INTEGER, customer_id INTEGER, amount_cents INTEGER, currency TEXT, status TEXT, created_at TEXT);
CREATE TABLE IF NOT EXISTS load_log (
    run_id INTEGER PRIMARY KEY AUTOINCREMENT, rows_staged INTEGER, inserted INTEGER, updated INTEGER,
    unchanged INTEGER, status TEXT, error TEXT);
"""
COLUMNS = ("order_id", "customer_id", "amount_cents", "currency", "status", "created_at")
DIFFERENT = " OR ".join(f"s.{c} IS NOT o.{c}" for c in COLUMNS[1:])
CHANGED_ONLY = " OR ".join(f"orders.{c} IS NOT excluded.{c}" for c in COLUMNS[1:])
SET_CLAUSE = ", ".join(f"{c} = excluded.{c}" for c in COLUMNS[1:])

def load_run(conn, rows):
    conn.executescript(SCHEMA)
    run_id = conn.execute("INSERT INTO load_log (status) VALUES ('running')").lastrowid
    conn.commit()
    try:
        with conn:
            conn.execute("DELETE FROM stg_orders")
            conn.executemany("INSERT INTO stg_orders VALUES (?, ?, ?, ?, ?, ?)", [tuple(r[c] for c in COLUMNS) for r in rows])
            staged = conn.execute("SELECT COUNT(*) FROM stg_orders").fetchone()[0]
            new = conn.execute("SELECT COUNT(*) FROM stg_orders s WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.order_id = s.order_id)").fetchone()[0]
            changed = conn.execute(f"SELECT COUNT(*) FROM stg_orders s JOIN orders o ON o.order_id = s.order_id WHERE {DIFFERENT}").fetchone()[0]
            conn.execute(f"INSERT INTO orders SELECT {', '.join(COLUMNS)} FROM stg_orders WHERE true "
                         f"ON CONFLICT (order_id) DO UPDATE SET {SET_CLAUSE} WHERE {CHANGED_ONLY}")
        conn.execute("UPDATE load_log SET rows_staged = ?, inserted = ?, updated = ?, unchanged = ?, status = 'ok' WHERE run_id = ?",
                     (staged, new, changed, staged - new - changed, run_id))
    except sqlite3.IntegrityError as err:
        conn.execute("UPDATE load_log SET status = 'failed', error = ? WHERE run_id = ?", (str(err), run_id))
    conn.commit()
    return run_id

conn = sqlite3.connect(":memory:")
first = [dict(o) for o in ORDERS[0:6]]
load_run(conn, first)
second = [dict(o) for o in ORDERS[3:9]]
second[1]["status"] = "refunded"
second[2]["amount_cents"] = 4242
load_run(conn, second)
print(conn.execute("SELECT run_id, rows_staged, inserted, updated, unchanged, status FROM load_log ORDER BY run_id").fetchall())
print(conn.execute("SELECT COUNT(*) FROM orders").fetchone()[0])
print(conn.execute("SELECT order_id, status, amount_cents FROM orders WHERE order_id IN (5, 6) ORDER BY order_id").fetchall())
```

```output
[(1, 6, 6, 0, 0, 'ok'), (2, 6, 3, 2, 1, 'ok')]
9
[(5, 'refunded', 1685), (6, 'refunded', 4242)]
```

The second run staged 6 rows: 3 new (orders 7 to 9), 2 changed (orders 5 and 6) and 1 unchanged (order 4). The table now has 9 orders.

### Example 2: The same upsert on PostgreSQL syntax (PGlite)

This runs on PGlite. The browser database already contains a Northwind table called `orders`, so the table here is named `api_orders`; it has a primary key and a check. Two rows exist; the staging table holds one changed row, one unchanged row and one new row. The upsert uses `IS DISTINCT FROM` so that only the changed row is written, and `RETURNING` inside a data-modifying CTE lists what the statement wrote. The unchanged row does not appear because its update was skipped.

```sql run
CREATE TABLE api_orders (
    order_id integer PRIMARY KEY, customer_id integer NOT NULL,
    amount_cents integer NOT NULL CHECK (amount_cents >= 0),
    currency text NOT NULL, status text NOT NULL, created_at timestamptz NOT NULL);
CREATE TABLE stg_api_orders (LIKE api_orders);
INSERT INTO api_orders VALUES
    (1, 8, 1137, 'EUR', 'paid', '2026-03-01T07:13:00Z'),
    (2, 9, 1274, 'EUR', 'paid', '2026-03-01T14:26:00Z');
INSERT INTO stg_api_orders VALUES
    (1, 8, 1137, 'EUR', 'paid', '2026-03-01T07:13:00Z'),
    (2, 9, 1274, 'EUR', 'refunded', '2026-03-01T14:26:00Z'),
    (3, 10, 1411, 'USD', 'failed', '2026-03-01T21:39:00Z');
WITH written AS (
    INSERT INTO api_orders
    SELECT * FROM stg_api_orders
    ON CONFLICT (order_id) DO UPDATE SET
        customer_id = EXCLUDED.customer_id, amount_cents = EXCLUDED.amount_cents,
        currency = EXCLUDED.currency, status = EXCLUDED.status, created_at = EXCLUDED.created_at
    WHERE api_orders.status IS DISTINCT FROM EXCLUDED.status
       OR api_orders.amount_cents IS DISTINCT FROM EXCLUDED.amount_cents
    RETURNING order_id, status
)
SELECT order_id, status FROM written ORDER BY order_id;
```

```output
order_id | status
2 | refunded
3 | failed
```

The query shows only the rows that the statement wrote. Order 1 was identical, so its update was skipped and it is not listed; order 2 was updated and order 3 was inserted.

### Example 3: One bad row rolls everything back, and the log keeps the evidence

The extract contains a negative amount. The `CHECK` constraint rejects it during the upsert, the transaction rolls back (so `orders` stays as it was after run 1, with the staging fill undone as well), and the load log records a `failed` run with the error text. A corrected run then succeeds. The pieces are the same `load_run` as before.

### Example 4: Run the same load twice

The same extract loaded twice leaves the table unchanged and the log shows 0 inserts and 0 updates the second time. The final query computes a checksum over the table (sum of amounts and number of rows) to show that it is identical after both runs.

### Example 5: The same flow with SQLAlchemy

SQLAlchemy offers the same transaction idea through `engine.begin()`, which commits when the block ends and rolls back on an exception, and `text()` queries with named parameters (`:name`). The example uses `sqlite://` (in memory) as the stand-in engine; with PostgreSQL only the connection string changes. It needs SQLAlchemy, so it is a local example.

```python local
from sqlalchemy import create_engine, text

engine = create_engine("sqlite://")
rows = [{"order_id": i, "status": "paid"} for i in range(1, 6)]
with engine.begin() as conn:
    conn.execute(text("CREATE TABLE orders (order_id INTEGER PRIMARY KEY, status TEXT NOT NULL)"))
    conn.execute(text("INSERT INTO orders VALUES (:order_id, :status)"), rows)
upsert = text("INSERT INTO orders VALUES (:order_id, :status) "
              "ON CONFLICT (order_id) DO UPDATE SET status = excluded.status WHERE orders.status IS NOT excluded.status")
with engine.begin() as conn:
    conn.execute(upsert, [{"order_id": 5, "status": "refunded"}, {"order_id": 6, "status": "paid"}])
try:
    with engine.begin() as conn:
        conn.execute(upsert, [{"order_id": 7, "status": "paid"}])
        conn.execute(text("INSERT INTO orders VALUES (1, NULL)"))
except Exception as err:
    print("rolled back:", type(err).__name__)
with engine.connect() as conn:
    print(conn.execute(text("SELECT order_id, status FROM orders ORDER BY order_id")).fetchall())
```

```output
rolled back: IntegrityError
[(1, 'paid'), (2, 'paid'), (3, 'paid'), (4, 'paid'), (5, 'refunded'), (6, 'paid')]
```

Order 7 was inserted inside the failed block and does not exist afterwards: the whole block rolled back.

## Real-world applications

- **Nightly order sync.** Yesterday's and today's extracts overlap; the upsert keeps one row per order with its latest status.
- **Operations dashboard of loads.** `SELECT * FROM load_log ORDER BY run_id DESC LIMIT 7` shows the last week: rows staged, changed and any failures.
- **Safe reruns.** After a failure, the engineer reruns the same extract; the unchanged rows are skipped and the table ends in the right state.
- **Audit.** The log counts reconcile with the API's own total for the run.

## Daily review

### Key takeaways

- Load through staging: fill staging, compare, then one set-based statement into the target.
- `ON CONFLICT (key) DO UPDATE ... WHERE` inserts new rows, updates changed ones, and skips the unchanged.
- Staging must have one row per key (PostgreSQL rejects the same key twice in one statement).
- One transaction for fill plus upsert; the load log is written outside it so a failure is recorded.
- `staged = inserted + updated + unchanged`; a second identical run changes nothing.

### Common mistakes

- **`to_sql(if_exists="replace")` on the target.** It drops keys and constraints. Use staging and an upsert.
- **No change condition.** Every row is rewritten on every run. Add `WHERE ... IS DISTINCT FROM ...`.
- **Duplicate keys in staging.** PostgreSQL raises an error. Deduplicate before staging (Day 109).
- **Logging inside the transaction.** The rollback erases the failure record. Log outside it.
- **Forgetting `WHERE true` in SQLite.** `INSERT ... SELECT ... ON CONFLICT` can fail to parse. Add it in SQLite; PostgreSQL does not need it.

### Revision notes

- Staging table, compare, upsert, log.
- `ON CONFLICT (order_id) DO UPDATE SET col = EXCLUDED.col WHERE target.col IS DISTINCT FROM EXCLUDED.col`.
- `sqlite3`: `?` and `IS NOT`; `psycopg`: `%s` and `IS DISTINCT FROM`.
- Transaction around fill plus upsert; `load_log` row per run.

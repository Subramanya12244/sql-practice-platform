## Understand

### From a design to tables

Days 144 to 146 produced a design on paper: a `fact_sales` table at order-line grain, three dimensions, surrogate keys, history on the customer. Today it becomes SQL. The schema is **DDL** (data definition language): `CREATE TABLE` statements that state each column's type and every rule the database must enforce. In a warehouse the temptation is to leave constraints out because loads are fast without them and the data "comes from a trusted pipeline". Resist it. Constraints cost little at this scale, they document the model for the next engineer, and they are the last line of defence against a bad load (Day 99): a primary key that rejects a duplicate sale is cheaper than a report that doubles a total.

### Column types

Choose the narrowest type that fits and never store a number as text. Surrogate keys are `integer` (four bytes, up to about 2.1 billion) for dimensions, and `bigint` for the key of a fact table that may grow past that. `date` holds a calendar day. `text` is the normal string type in PostgreSQL (there is no speed benefit to `varchar(n)`; use a length limit only if the business has one). Money is stored as integer cents (`amount_cents integer`), which keeps sums exact (Day 101). Flags are `boolean`. The date dimension's key is the integer `20260115`: readable, sortable and cheap, a convention you will meet in many warehouses; the real date sits beside it in `full_date`.

### Keys

Every table has a **primary key**: dimensions on the surrogate key, the fact table on `sale_id`, the identifier of an order line. In a warehouse a fact table often has no natural primary key, because several rows may share the same dimension keys; if so a surrogate `sale_id` (or no key and a documented grain) is used. Surrogate keys can be generated by the database with `GENERATED BY DEFAULT AS IDENTITY`, which assigns the next integer when no value is given and allows explicit values when a loader needs them (the SQL standard form, preferred to the older `serial`). Note that explicit values do not advance the sequence, so a loader that mixes both must reset it. The **business key** is kept as an ordinary column with a `UNIQUE` constraint when it is unique, as `product_id` is here.

For the customer dimension, `customer_id` is not unique, because history creates several rows per customer. What must be unique is `customer_id` among the **current** rows. A **partial unique index** states exactly that: `CREATE UNIQUE INDEX uq_customer_current ON dim_customer (customer_id) WHERE is_current`. The index only covers rows with `is_current = true`, so any number of closed versions may exist, and a second current row for the same customer is rejected. This turns the rule "one current row per business key" from a convention into a guarantee.

### Foreign keys and the order of loading

`REFERENCES dim_date (date_key)` in the fact table says that every `date_key` must exist in `dim_date`. The database checks it on every insert, which fixes the **order of loading**: dimensions first, then facts. If a fact arrives whose dimension row does not exist, the insert fails; that is the behaviour you want, and Day 148 shows how to prepare for it with an unknown member. PostgreSQL does **not** create an index on the referencing column automatically (it does for the primary key it references), so a fact table usually gets an index on each foreign key column, to make joins and deletes on the dimension side fast (Day 149 discusses which indexes pay off).

### Checks

`CHECK (quantity > 0)` and `CHECK (amount_cents >= 0)` keep impossible values out. `CHECK (valid_to IS NULL OR valid_to > valid_from)` guards the SCD validity period. A `CHECK` with a column that may be NULL passes when the expression is NULL (unknown counts as not violated), so combine it with `NOT NULL` when absence is not allowed.

### Seeded sample data

A warehouse for learning needs repeatable data. The sample in this block is generated with `generate_series` and arithmetic on the series value, so every run produces the same 12 customers, 8 products, 59 dates and 60 sales. Seeded data makes the checks in tests exact. Load the dimensions first, then the fact table, and finish with queries that prove the load: row counts per table and a count of orphans (fact rows whose key has no dimension row), which the foreign key should make zero.

### Inspecting what you built

The catalogs describe the schema. `information_schema.columns` lists columns with their types and nullability. `pg_constraint` lists constraints by type (`p` primary key, `f` foreign key, `u` unique, `c` check). `pg_indexes` lists indexes with their definitions. Querying them is how you review a schema, compare environments and write a test that the schema is what you intended.

### Common misconception

Learners think warehouses do not need constraints because the data is loaded in bulk by trusted code. Trusted code has bugs, sources change, and the constraint is the only check that runs on every row. The other belief is that `GENERATED ... AS IDENTITY` and a `PRIMARY KEY` are the same thing; the first generates values, the second enforces uniqueness, and you usually want both.

### Why it matters

A schema with real constraints and honest types is the contract between the pipeline and every analyst. Everything later (loads, partitions, materialised views, reports) assumes it.

## Syntax and key functions

The complete DDL for the sales star (the examples run it on PGlite):

```sql-syntax
CREATE TABLE dim_date (
    date_key  integer PRIMARY KEY,
    full_date date NOT NULL UNIQUE,
    year      integer NOT NULL,
    month     integer NOT NULL CHECK (month BETWEEN 1 AND 12)
);
CREATE TABLE dim_customer (
    customer_key integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL,
    valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL DEFAULT true,
    CHECK (valid_to IS NULL OR valid_to > valid_from)
);
CREATE UNIQUE INDEX uq_customer_current ON dim_customer (customer_id) WHERE is_current;
-- dim_product likewise; fact_sales with REFERENCES and CHECKs
```

Creating and running it from Python with `psycopg` (credentials from the environment; not run here because there is no server):

```python
import os
import psycopg

with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
    conn.execute(open("star_schema.sql").read())     # the DDL above; one transaction
```

| Item | Meaning |
|---|---|
| `GENERATED BY DEFAULT AS IDENTITY` | Database-assigned integer; explicit values allowed. |
| `PRIMARY KEY`, `UNIQUE` | Uniqueness (`23505` on violation). |
| `REFERENCES t (col)` | Foreign key (`23503` on violation). |
| `CHECK (condition)` | Row rule (`23514` on violation). |
| `CREATE UNIQUE INDEX ... WHERE cond` | Partial unique index. |
| `information_schema.columns` | Column names, types, nullability. |
| `pg_constraint` (`contype` p, f, u, c) | Constraints by type. |
| `pg_indexes` | Indexes and their definitions. |

## Learn by example

### Example 1: Create the schema and read it back

The DDL runs on PGlite, then `information_schema.columns` is queried to list, for each table, the number of columns and how many are `NOT NULL`. The result is the schema as the database sees it.

```sql run
CREATE TABLE dim_date (
    date_key  integer PRIMARY KEY,
    full_date date    NOT NULL UNIQUE,
    year      integer NOT NULL,
    month     integer NOT NULL CHECK (month BETWEEN 1 AND 12)
);
CREATE TABLE dim_customer (
    customer_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id   text    NOT NULL,
    customer_name text    NOT NULL,
    country       text    NOT NULL,
    valid_from    date    NOT NULL,
    valid_to      date,
    is_current    boolean NOT NULL DEFAULT true,
    CHECK (valid_to IS NULL OR valid_to > valid_from)
);
CREATE UNIQUE INDEX uq_customer_current ON dim_customer (customer_id) WHERE is_current;
CREATE TABLE dim_product (
    product_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id   text NOT NULL UNIQUE,
    product_name text NOT NULL,
    category     text NOT NULL
);
CREATE TABLE fact_sales (
    sale_id      integer PRIMARY KEY,
    date_key     integer NOT NULL REFERENCES dim_date (date_key),
    customer_key integer NOT NULL REFERENCES dim_customer (customer_key),
    product_key  integer NOT NULL REFERENCES dim_product (product_key),
    quantity     integer NOT NULL CHECK (quantity > 0),
    amount_cents integer NOT NULL CHECK (amount_cents >= 0)
);
SELECT table_name, count(*) AS columns, count(*) FILTER (WHERE is_nullable = 'NO') AS not_null
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name IN ('dim_date', 'dim_customer', 'dim_product', 'fact_sales')
GROUP BY table_name ORDER BY table_name;
```

```output
table_name | columns | not_null
dim_customer | 7 | 6
dim_date | 4 | 4
dim_product | 4 | 4
fact_sales | 6 | 6
```

### Example 2: The constraints, by table and type

`pg_constraint` records the constraints. The query counts them by table and kind (`p` primary key, `f` foreign key, `u` unique, `c` check). `fact_sales` has one primary key, three foreign keys and two checks. The partial unique index is an index, not a constraint, so it appears in the third query.

```sql run
CREATE TABLE dim_date (
    date_key  integer PRIMARY KEY,
    full_date date    NOT NULL UNIQUE,
    year      integer NOT NULL,
    month     integer NOT NULL CHECK (month BETWEEN 1 AND 12)
);
CREATE TABLE dim_customer (
    customer_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id   text    NOT NULL,
    customer_name text    NOT NULL,
    country       text    NOT NULL,
    valid_from    date    NOT NULL,
    valid_to      date,
    is_current    boolean NOT NULL DEFAULT true,
    CHECK (valid_to IS NULL OR valid_to > valid_from)
);
CREATE UNIQUE INDEX uq_customer_current ON dim_customer (customer_id) WHERE is_current;
CREATE TABLE dim_product (
    product_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id   text NOT NULL UNIQUE,
    product_name text NOT NULL,
    category     text NOT NULL
);
CREATE TABLE fact_sales (
    sale_id      integer PRIMARY KEY,
    date_key     integer NOT NULL REFERENCES dim_date (date_key),
    customer_key integer NOT NULL REFERENCES dim_customer (customer_key),
    product_key  integer NOT NULL REFERENCES dim_product (product_key),
    quantity     integer NOT NULL CHECK (quantity > 0),
    amount_cents integer NOT NULL CHECK (amount_cents >= 0)
);
SELECT conrelid::regclass::text AS tbl, contype, count(*) AS n
FROM pg_constraint
WHERE conrelid IN ('dim_date'::regclass, 'dim_customer'::regclass, 'dim_product'::regclass, 'fact_sales'::regclass)
  AND contype IN ('p', 'f', 'u', 'c')
GROUP BY 1, 2 ORDER BY 1, 2;
```

```output
tbl | contype | n
dim_customer | c | 1
dim_customer | p | 1
dim_date | c | 1
dim_date | p | 1
dim_date | u | 1
dim_product | p | 1
dim_product | u | 1
fact_sales | c | 2
fact_sales | f | 3
fact_sales | p | 1
```

### Example 3: Load in order and verify

Dimensions are loaded before the fact table. The identity columns assign `customer_key` and `product_key` (1, 2, 3, ...). The final query returns the row counts and the orphan checks: fact rows whose key has no dimension row, which the foreign keys make impossible. The surrogate keys are the same as in the sample used on earlier days.

```sql run
CREATE TABLE dim_date (
    date_key  integer PRIMARY KEY,
    full_date date    NOT NULL UNIQUE,
    year      integer NOT NULL,
    month     integer NOT NULL CHECK (month BETWEEN 1 AND 12)
);
CREATE TABLE dim_customer (
    customer_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id   text    NOT NULL,
    customer_name text    NOT NULL,
    country       text    NOT NULL,
    valid_from    date    NOT NULL,
    valid_to      date,
    is_current    boolean NOT NULL DEFAULT true,
    CHECK (valid_to IS NULL OR valid_to > valid_from)
);
CREATE UNIQUE INDEX uq_customer_current ON dim_customer (customer_id) WHERE is_current;
CREATE TABLE dim_product (
    product_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id   text NOT NULL UNIQUE,
    product_name text NOT NULL,
    category     text NOT NULL
);
CREATE TABLE fact_sales (
    sale_id      integer PRIMARY KEY,
    date_key     integer NOT NULL REFERENCES dim_date (date_key),
    customer_key integer NOT NULL REFERENCES dim_customer (customer_key),
    product_key  integer NOT NULL REFERENCES dim_product (product_key),
    quantity     integer NOT NULL CHECK (quantity > 0),
    amount_cents integer NOT NULL CHECK (amount_cents >= 0)
);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer (customer_id, customer_name, country, valid_from)
SELECT 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'), (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01'
FROM generate_series(1, 12) AS i;
INSERT INTO dim_product (product_id, product_name, category)
SELECT 'P' || lpad(i::text, 3, '0'), 'Product ' || i, (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
SELECT 'dim_date' AS tbl, count(*) AS rows FROM dim_date
UNION ALL SELECT 'dim_customer', count(*) FROM dim_customer
UNION ALL SELECT 'dim_product', count(*) FROM dim_product
UNION ALL SELECT 'fact_sales', count(*) FROM fact_sales
UNION ALL SELECT 'orphan customers', count(*) FROM fact_sales f LEFT JOIN dim_customer c USING (customer_key) WHERE c.customer_key IS NULL
UNION ALL SELECT 'orphan dates', count(*) FROM fact_sales f LEFT JOIN dim_date d USING (date_key) WHERE d.date_key IS NULL
ORDER BY 1;
```

```output
tbl | rows
dim_customer | 12
dim_date | 59
dim_product | 8
fact_sales | 60
orphan customers | 0
orphan dates | 0
```

### Example 4: The constraints reject bad rows

Errors would stop the block, so the rejection is shown with `ON CONFLICT DO NOTHING`. The insert of a second current row for `C003` conflicts with the partial unique index and inserts nothing; a closed row for the same customer is accepted.

```sql run
CREATE TABLE dim_date (
    date_key  integer PRIMARY KEY,
    full_date date    NOT NULL UNIQUE,
    year      integer NOT NULL,
    month     integer NOT NULL CHECK (month BETWEEN 1 AND 12)
);
CREATE TABLE dim_customer (
    customer_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id   text    NOT NULL,
    customer_name text    NOT NULL,
    country       text    NOT NULL,
    valid_from    date    NOT NULL,
    valid_to      date,
    is_current    boolean NOT NULL DEFAULT true,
    CHECK (valid_to IS NULL OR valid_to > valid_from)
);
CREATE UNIQUE INDEX uq_customer_current ON dim_customer (customer_id) WHERE is_current;
CREATE TABLE dim_product (
    product_key  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id   text NOT NULL UNIQUE,
    product_name text NOT NULL,
    category     text NOT NULL
);
CREATE TABLE fact_sales (
    sale_id      integer PRIMARY KEY,
    date_key     integer NOT NULL REFERENCES dim_date (date_key),
    customer_key integer NOT NULL REFERENCES dim_customer (customer_key),
    product_key  integer NOT NULL REFERENCES dim_product (product_key),
    quantity     integer NOT NULL CHECK (quantity > 0),
    amount_cents integer NOT NULL CHECK (amount_cents >= 0)
);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer (customer_id, customer_name, country, valid_from)
SELECT 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'), (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01'
FROM generate_series(1, 12) AS i;
INSERT INTO dim_product (product_id, product_name, category)
SELECT 'P' || lpad(i::text, 3, '0'), 'Product ' || i, (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
INSERT INTO dim_customer (customer_id, customer_name, country, valid_from)
VALUES ('C003', 'Customer 03', 'ES', date '2026-02-01') ON CONFLICT (customer_id) WHERE is_current DO NOTHING;
INSERT INTO dim_customer (customer_id, customer_name, country, valid_from, valid_to, is_current)
VALUES ('C003', 'Customer 03 (old)', 'PT', date '2025-01-01', date '2025-12-31', false);
SELECT customer_id, is_current, count(*) AS versions
FROM dim_customer WHERE customer_id = 'C003' GROUP BY customer_id, is_current ORDER BY is_current;
```

```output
customer_id | is_current | versions
C003 | false | 1
C003 | true | 1
```

## Real-world applications

- **Schema as code.** The DDL lives in the repository and is applied by migrations; a review of constraints is a review of the data contract.
- **Safe backfills.** With keys and foreign keys in place, a re-run of a load fails loudly on duplicates instead of doubling the totals.
- **Environment checks.** A test queries `pg_constraint` and `pg_indexes` to prove that production has the same constraints as the repository.
- **Onboarding.** A new analyst reads `information_schema.columns` and the ER sketch, and knows what each column means and may contain.

## Daily review

### Key takeaways

- Use constraints in a warehouse: primary keys, foreign keys, `NOT NULL`, `CHECK`.
- Surrogate keys via `GENERATED BY DEFAULT AS IDENTITY`; business keys with `UNIQUE` where unique.
- A partial unique index enforces one current row per business key.
- Load dimensions before facts; index foreign key columns yourself.
- Verify with counts and orphan queries, and read the schema from the catalogs.

### Common mistakes

- **No constraints for speed.** Duplicates and orphans load silently. Keep them.
- **Unique constraint on a versioned business key.** It blocks history. Use a partial unique index on current rows.
- **Loading facts first.** Foreign keys reject them. Load dimensions first.
- **Mixed explicit and identity keys.** The sequence lags and later inserts collide. Reset the sequence after explicit loads.
- **Money as float or text.** Sums drift or fail. Use integer cents.

### Revision notes

- DDL: types, PK, FK, `NOT NULL`, `CHECK`, identity.
- Partial unique index `... WHERE is_current`.
- Order: dimensions, then facts.
- Catalogs: `information_schema.columns`, `pg_constraint`, `pg_indexes`.

- Guard an upsert with a `WHERE` clause so an older version never overwrites a newer one.

- Replace Day 125's delete-then-insert with a single upsert statement and check that reruns change nothing.

## Understand

### The insert-or-update problem

Incremental loads (Day 125) bring rows that are either **new** (the key is not in the target) or **changed** (the key exists and the values differ). Day 125 handled both by deleting the keys and inserting the rows. It works, but it is two statements per key and it depends on both staying in one transaction; run them in separate transactions and a reader sees the row missing in between. The other obvious approach is worse: for each row, `SELECT` to see whether it exists and then `INSERT` or `UPDATE`. Another process can insert the same key between your `SELECT` and your `INSERT`, and one of you fails with a duplicate-key error. The database has a single-statement answer that is atomic: the **upsert** (update or insert).

### INSERT ... ON CONFLICT

In PostgreSQL (and SQLite 3.24 or later) you add a conflict clause to an insert:

`INSERT INTO orders_clean (order_id, amount_cents, status, updated_at) VALUES (...) ON CONFLICT (order_id) DO UPDATE SET amount_cents = EXCLUDED.amount_cents, status = EXCLUDED.status, updated_at = EXCLUDED.updated_at`

The **conflict target** `(order_id)` names the unique column (a primary key or unique index) whose violation is expected. If the row's key is new, the insert happens. If the key exists, the **`DO UPDATE`** action runs on the existing row instead of raising an error. Inside the action, **`EXCLUDED`** is a name for the row you tried to insert, so `EXCLUDED.status` is the incoming value and `orders_clean.status` is the stored one. The alternative **`DO NOTHING`** silently skips a conflicting row, which suits append-only data such as an event log where the first copy wins. The conflict target must match a unique constraint: without one PostgreSQL reports that there is no unique or exclusion constraint matching the `ON CONFLICT` specification.

### Merge semantics: which columns, which version wins

An upsert is a small **merge** and you must decide its rules. Which columns are overwritten? Usually all the business columns, but never the key and perhaps not a `created_at` that should keep its first value. What if the incoming value is NULL? Overwriting a good value with NULL is often wrong; `SET status = COALESCE(EXCLUDED.status, orders_clean.status)` keeps the stored value when the new one is missing. Which version wins? The simple rule "last write wins" is dangerous when data arrives out of order: an old version of order 3 arriving after the new one would overwrite it. A **guard** fixes that: add `WHERE EXCLUDED.updated_at > orders_clean.updated_at` to the action, and the update only happens when the incoming row is newer. When the guard is false the existing row is left unchanged. PostgreSQL 15 added a separate `MERGE` statement with `WHEN MATCHED` and `WHEN NOT MATCHED` branches that expresses the same idea in standard SQL, and the browser database used in these lessons accepts it; `ON CONFLICT` is shorter and has been the common choice in PostgreSQL pipelines.

### Deduplicate the batch first

If one batch contains the same key twice, PostgreSQL stops with the error "ON CONFLICT DO UPDATE command cannot affect row a second time": the statement would have to update the row it just inserted, and the database refuses to guess which version you meant. SQLite instead applies the rows in order, so the last one wins, which hides the problem until the order changes. The fix is to **deduplicate before the upsert**: keep one row per key, the one with the latest `updated_at`, with `dedupe_latest` in Python (Day 120) or `DISTINCT ON (order_id) ... ORDER BY order_id, updated_at DESC` in PostgreSQL. This is the same ranking idea as the `ROW_NUMBER` window of Day 117.

### Idempotent by construction

An upsert with a guard is idempotent: run it twice with the same rows and the second run changes nothing, because the incoming rows are no longer newer than the stored ones. That makes it the standard load step of an incremental pipeline: the lookback window of Day 125 can reread rows freely, because rereading cannot damage the table. A common misconception is that `DO NOTHING` and `DO UPDATE` differ only in speed: they differ in meaning. `DO NOTHING` keeps the old row, which means changed data is never applied.

### Why it matters in data work

A loader that cannot upsert has to choose between duplicates, errors and gaps. The upsert is one atomic statement that handles new rows, changed rows and reruns together, and the guard makes it safe against late data.

## Syntax and key functions

```sql-syntax
INSERT INTO target (key, col1, col2, updated_at)
VALUES (?, ?, ?, ?)
ON CONFLICT (key) DO UPDATE
SET col1 = EXCLUDED.col1, col2 = EXCLUDED.col2, updated_at = EXCLUDED.updated_at
WHERE EXCLUDED.updated_at > target.updated_at;

INSERT INTO log (event_id, payload) VALUES (?, ?)
ON CONFLICT (event_id) DO NOTHING;
```

| Item | What it does or returns |
|---|---|
| `ON CONFLICT (col)` | The unique column whose violation is handled; must match a unique constraint. |
| `DO UPDATE SET ...` | Updates the existing row instead of failing. |
| `DO NOTHING` | Skips the conflicting row. |
| `EXCLUDED.col` | The value of `col` in the row that was proposed for insertion. |
| `WHERE` after `DO UPDATE SET` | The guard: the update happens only if it is true. |
| `RETURNING cols` | Returns the rows that were inserted or updated (not the skipped ones). |
| `DISTINCT ON (key) ... ORDER BY key, ts DESC` | PostgreSQL: one row per key, the latest. |
| `COALESCE(EXCLUDED.x, t.x)` | Keeps the stored value when the incoming one is NULL. |

## Learn by example

### Example 1: Insert or update in one statement

The table has a primary key. The first upsert inserts three rows. The second contains one changed row and one new row, and the printed counts show one row updated and one inserted. Running the same statement again changes nothing.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER, status TEXT)")
UPSERT = """INSERT INTO orders_clean (order_id, amount_cents, status) VALUES (?, ?, ?)
            ON CONFLICT (order_id) DO UPDATE SET amount_cents = excluded.amount_cents, status = excluded.status"""
count = lambda: conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0]

conn.executemany(UPSERT, [(1, 1990, "paid"), (2, 4500, "paid"), (3, 750, "failed")])
print("after first upsert:", count(), "rows")
before = count()
batch = [(2, 4500, "refunded"), (4, 1200, "paid")]
conn.executemany(UPSERT, batch)
print("inserted:", count() - before, "updated:", len(batch) - (count() - before))
conn.executemany(UPSERT, batch)
print(conn.execute("SELECT * FROM orders_clean ORDER BY order_id").fetchall())
```

```output
after first upsert: 3 rows
inserted: 1 updated: 1
[(1, 1990, 'paid'), (2, 4500, 'refunded'), (3, 750, 'failed'), (4, 1200, 'paid')]
```
### Example 2: The guard against old versions

Order 2 is stored with a newer `updated_at`. An older version arrives later. Without the guard it overwrites the new row, and with the guard it is ignored. Both tables start in the same state.

```python run
import sqlite3

def make():
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, status TEXT, updated_at TEXT)")
    conn.execute("INSERT INTO orders_clean VALUES (2, 'refunded', '2025-03-04T08:00:00Z')")
    return conn

PLAIN = "INSERT INTO orders_clean VALUES (?, ?, ?) ON CONFLICT (order_id) DO UPDATE SET status = excluded.status, updated_at = excluded.updated_at"
GUARDED = PLAIN + " WHERE excluded.updated_at > orders_clean.updated_at"
late = (2, "paid", "2025-03-01T11:00:00Z")
for name, sql in [("plain", PLAIN), ("guarded", GUARDED)]:
    conn = make()
    conn.execute(sql, late)
    print(name, conn.execute("SELECT status, updated_at FROM orders_clean").fetchone())
```

```output
plain ('paid', '2025-03-01T11:00:00Z')
guarded ('refunded', '2025-03-04T08:00:00Z')
```
### Example 3: Deduplicate the batch first

The incoming batch has two versions of order 5, the older one last. Applied in order without a guard, the older version would win. Reducing the batch to the newest version per key first makes the result independent of the order of rows, and it avoids PostgreSQL's error about affecting a row twice.

```python run
import sqlite3

def dedupe_latest(rows):
    latest = {}
    for row in rows:
        key = row[0]
        if key not in latest or row[2] >= latest[key][2]:
            latest[key] = row
    return [latest[key] for key in sorted(latest)]

batch = [(5, "paid", "2025-03-02T09:00:00Z"), (6, "paid", "2025-03-02T10:00:00Z"), (5, "refunded", "2025-03-03T09:00:00Z"), (5, "created", "2025-03-01T09:00:00Z")]
UPSERT = "INSERT INTO t VALUES (?, ?, ?) ON CONFLICT (order_id) DO UPDATE SET status = excluded.status, updated_at = excluded.updated_at"
for name, rows in [("raw order", batch), ("deduplicated", dedupe_latest(batch))]:
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE t (order_id INTEGER PRIMARY KEY, status TEXT, updated_at TEXT)")
    conn.executemany(UPSERT, rows)
    print(f"{name}: {len(rows)} rows applied ->", conn.execute("SELECT order_id, status FROM t ORDER BY order_id").fetchall())
```

```output
raw order: 4 rows applied -> [(5, 'created'), (6, 'paid')]
deduplicated: 2 rows applied -> [(5, 'refunded'), (6, 'paid')]
```
### Example 4: Upsert with a guard and RETURNING (PostgreSQL, PGlite)

The target holds orders 1 and 2. The statement upserts three rows: an older version of 1 (the guard skips it), a newer version of 2 (updated) and a new order 3 (inserted). `RETURNING` lists the rows that changed; the skipped row is absent. The final `SELECT` is not needed: the returned rows are the result.

```sql run
CREATE TABLE orders_clean (order_id int PRIMARY KEY, status text, updated_at timestamp);
INSERT INTO orders_clean VALUES (1, 'paid', '2025-03-05 10:00'), (2, 'paid', '2025-03-01 10:00');
INSERT INTO orders_clean (order_id, status, updated_at)
VALUES (1, 'created', '2025-03-01 09:00'), (2, 'refunded', '2025-03-04 08:00'), (3, 'paid', '2025-03-04 09:00')
ON CONFLICT (order_id) DO UPDATE
SET status = EXCLUDED.status, updated_at = EXCLUDED.updated_at
WHERE EXCLUDED.updated_at > orders_clean.updated_at
RETURNING order_id, status;
```

```output
order_id | status
2 | refunded
3 | paid
```
### Example 5: Deduplicate and upsert in one statement (PostgreSQL, PGlite)

The staging table holds two versions of order 7. `DISTINCT ON (order_id)` with `ORDER BY order_id, updated_at DESC` keeps the newest, so the upsert never sees the same key twice. The statement is run twice; the second run changes nothing because of the guard.

```sql run
CREATE TABLE stg_orders (order_id int, status text, updated_at timestamp);
CREATE TABLE orders_clean (order_id int PRIMARY KEY, status text, updated_at timestamp);
INSERT INTO stg_orders VALUES (7, 'created', '2025-03-01 09:00'), (7, 'paid', '2025-03-02 09:00'), (8, 'failed', '2025-03-02 10:00');
INSERT INTO orders_clean
SELECT DISTINCT ON (order_id) order_id, status, updated_at FROM stg_orders ORDER BY order_id, updated_at DESC
ON CONFLICT (order_id) DO UPDATE SET status = EXCLUDED.status, updated_at = EXCLUDED.updated_at
WHERE EXCLUDED.updated_at > orders_clean.updated_at;
INSERT INTO orders_clean
SELECT DISTINCT ON (order_id) order_id, status, updated_at FROM stg_orders ORDER BY order_id, updated_at DESC
ON CONFLICT (order_id) DO UPDATE SET status = EXCLUDED.status, updated_at = EXCLUDED.updated_at
WHERE EXCLUDED.updated_at > orders_clean.updated_at;
SELECT order_id, status FROM orders_clean ORDER BY order_id;
```

```output
order_id | status
7 | paid
8 | failed
```
## Real-world applications

- **The load step of incremental pipelines.** A guarded upsert is how the changed rows read above the watermark enter `orders_clean` (Examples 1 and 2), in one atomic statement.
- **Late and out-of-order data.** With the guard, an old version arriving late cannot overwrite a newer row (Example 2), which makes lookback windows safe.
- **Staging to target merges.** Warehouse jobs deduplicate a staging table with `DISTINCT ON` and upsert it into the target (Example 5), then clear the staging table.
- **Append-only logs.** `DO NOTHING` (shown in the syntax section) loads an event feed where a replayed message must not create a second row.

## Daily review

### Key takeaways

- `INSERT ... ON CONFLICT (key) DO UPDATE` handles new and changed rows in one atomic statement; `EXCLUDED` is the incoming row.
- `DO NOTHING` keeps the old row; it ignores changes.
- A `WHERE` guard on `updated_at` stops old versions from overwriting new ones.
- Deduplicate the batch first; PostgreSQL rejects a statement that affects one key twice.
- A guarded upsert is idempotent and makes reruns and lookback windows safe.

### Common mistakes

- Choosing `DO NOTHING` when changes must be applied, so updates never arrive and nobody notices. Use `DO UPDATE`.
- Omitting the guard and letting a late old row overwrite a newer one. Add `WHERE EXCLUDED.updated_at > table.updated_at`.
- Sending two rows with the same key in one PostgreSQL statement and getting "cannot affect row a second time". Deduplicate first.
- Using a conflict target that is not unique and getting an error about a missing unique constraint. Add a primary key or unique index.
- Overwriting good values with NULL from a partial record. Use `COALESCE(EXCLUDED.x, table.x)` where NULL means missing.

### Revision notes

- `ON CONFLICT (key) DO UPDATE SET c = EXCLUDED.c [WHERE guard]`; `DO NOTHING`.
- `EXCLUDED` is the incoming row; the table name is the stored row.
- Batch: `dedupe_latest` or `DISTINCT ON (key) ... ORDER BY key, ts DESC`.
- Idempotent: run twice, snapshot unchanged.

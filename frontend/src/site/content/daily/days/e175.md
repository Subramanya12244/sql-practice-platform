## Objectives

- Write small pure functions that turn a raw order into a typed, normalised record.
- Apply validation rules in a fixed order so that each bad record gets exactly one reason.
- Route failing records to a quarantine table with the reason and the original payload, instead of dropping them or stopping the run.
- Prove the stage with counts: raw equals clean plus quarantined, and the quarantine holds the six planted defects.
- Express the same rules in SQL with a `CASE` expression and count the violations per rule.

## Understand

### What the cleaning stage promises

Day 174 landed 120 raw order records and 20 customers. The cleaning stage reads the raw layer and produces two outputs: a **clean set** of typed, normalised records that the warehouse can load, and a **quarantine** that holds every record that failed a rule, with the reason. The promise is a count identity: raw records equal clean records plus quarantined records. Nothing is dropped silently, and nothing that is wrong reaches the warehouse. The raw layer is not touched, so a changed rule can be replayed.

### Transformations are small pure functions

A **transformation** changes the form of a value without changing its meaning: text to integer, `" c013 "` to `"C013"`, `"O0042"` to the number 42, `2026-02-03T10:15:00Z` to the date key `20260203`. Write each as a function of one record that returns a new record and touches nothing else. Pure functions are easy to test: you call them with a literal and compare the result. The stage in this capstone derives `sale_id` from the digits of the order id and `date_key` as an integer `YYYYMMDD`, because the warehouse of Day 176 joins on those.

### Validation: rules, order and reasons

A **validation rule** is a yes-or-no question about one record. The rules here are: the order id was not seen earlier, `created_at` is present and parses as a UTC timestamp, the amount is a positive integer of cents, the customer exists in the customers list, the currency is EUR, and the status is one of `paid`, `refunded` or `failed`. A record can break several rules; the stage reports the **first** failing rule in a fixed order so that every quarantined record has exactly one reason and the counts per reason add up to the quarantine size. The order of the rules is a design decision, and changing it changes which reason a record gets but not whether it is quarantined.

### Quarantine, not drop and not stop

There are three things a pipeline can do with a bad record. **Dropping** it hides the loss. **Stopping** the whole run makes one bad row block thousands of good ones. **Quarantining** it keeps the good flow going and keeps the bad record, its reason and its original payload where a person can look at it. The quarantine is a table, so it can be queried, counted in a metric, and replayed after the cause is fixed. A growing quarantine count is an early warning that a source changed.

### Repair or quarantine

Some defects can be repaired safely, such as stray spaces or lower-case letters in an id. Others cannot be repaired without guessing: a negative amount might be a refund or a typo. The rule of thumb is to repair only what is lossless and quarantine the rest. In this capstone the transformation trims and upper-cases customer ids and lower-cases statuses, and everything else is quarantined.

### Validation in SQL

The same rules can run in the database over a staging table: a `CASE` expression returns the first failing reason for each row, and `GROUP BY` the reason counts them. Python is better for rules that need parsing, SQL for rules over whole tables such as duplicates and foreign keys. Example 4 shows the SQL form on PGlite.

### Common misconception

Learners write the filter `WHERE status = 'paid'` and call it cleaning. A filter removes records without saying why; a pipeline needs to know that 114 of 120 were valid, which six were not, and what was wrong with each.

### Why it matters

The quarantine count and its reasons are the first thing on-call engineers check. They also decide whether a revenue figure can be trusted.

## Syntax and key functions

A rule function returning the first failing reason, and the split into two outputs:

```python
reason = first_problem(rec, seen, known)      # None when the record is valid
if reason is None:
    good.append(transform(rec))
else:
    quarantine.append({"order_id": rec["order_id"], "reason": reason, "payload": rec})
```

The SQL form of the same idea:

```sql-syntax
SELECT CASE WHEN <rule 1 fails> THEN 'reason 1'
            WHEN <rule 2 fails> THEN 'reason 2'
            ELSE 'ok' END AS reason, count(*) AS n
FROM staging GROUP BY 1 ORDER BY 1;
```

| Item | What it does or returns |
|---|---|
| `first_problem(rec, seen, known)` | The first broken rule's name, or `None`. |
| `transform(rec)` | A typed, normalised copy of a valid record. |
| `datetime.strptime(text, fmt)` | Parses text; raises `ValueError` when it does not match. |
| `clean_orders(raw, known)` | Returns `(good, quarantine)`. |
| `CASE WHEN ... THEN ... END` | Picks the first matching branch per row. |
| `raw == len(good) + len(quarantine)` | The reconciliation identity of the stage. |

## Learn by example

### Example 1: One record before and after

`transform` works on a single record. The input has stray spaces and a lower-case customer id, as a messy source might produce; the output has the typed keys the warehouse needs. The function is pure: the input dictionary is unchanged afterwards.

```python run
from datetime import datetime

def first_problem(rec, seen, known):
    """The first rule a raw order breaks, or None. `seen` holds the order ids already processed."""
    if rec["order_id"] in seen:
        return "duplicate order_id"
    if not rec["created_at"]:
        return "missing created_at"
    try:
        datetime.strptime(rec["created_at"], "%Y-%m-%dT%H:%M:%SZ")
    except ValueError:
        return "bad created_at"
    if not isinstance(rec["amount_cents"], int) or rec["amount_cents"] <= 0:
        return "bad amount"
    if rec["customer_id"].strip().upper() not in known:
        return "unknown customer"
    if rec["currency"].strip().upper() != "EUR":
        return "bad currency"
    if rec["status"].strip().lower() not in ("paid", "refunded", "failed"):
        return "bad status"
    return None

def transform(rec):
    """Typed, normalised copy of a valid raw order."""
    return {"sale_id": int(rec["order_id"][1:]), "order_id": rec["order_id"],
            "customer_id": rec["customer_id"].strip().upper(), "product_id": rec["product_id"],
            "quantity": int(rec["quantity"]), "amount_cents": rec["amount_cents"],
            "status": rec["status"].strip().lower(), "created_at": rec["created_at"],
            "date_key": int(rec["created_at"][:10].replace("-", ""))}

def clean_orders(raw, known):
    good, quarantine, seen = [], [], set()
    for rec in raw:
        reason = first_problem(rec, seen, known)
        seen.add(rec["order_id"])
        if reason:
            quarantine.append({"order_id": rec["order_id"], "reason": reason, "payload": rec})
        else:
            good.append(transform(rec))
    return good, quarantine

raw = {"order_id": "O0042", "customer_id": " c013 ", "product_id": "P06", "quantity": 2, "amount_cents": 6000,
       "currency": "EUR", "status": "Paid", "created_at": "2026-02-03T10:15:00Z"}
out = transform(raw)
for key in ("sale_id", "customer_id", "status", "date_key", "amount_cents"):
    print(key, repr(out[key]))
print("input unchanged:", raw["customer_id"] == " c013 ")
```

```output
sale_id 42
customer_id 'C013'
status 'paid'
date_key 20260203
amount_cents 6000
input unchanged: True
```

### Example 3: Clean the generated data and quarantine the rest

`clean_orders` splits the 120 raw records. The quarantine is written to a `sqlite3` table with the reason and the original JSON payload, replacing its previous content so that a re-run gives the same table. The last line is the reconciliation of the stage.

### Example 4: The same rules in SQL

On PGlite a small staging table holds ten rows. The `CASE` expression assigns the first failing reason, in the same order as the Python function, and `GROUP BY` counts each reason. The row with id 4 appears twice, so the duplicate check uses `row_number()` over the id: every row after the first for an id is a duplicate.

```sql run
CREATE TABLE staging (order_id text, customer_id text, amount_cents int, currency text, status text);
INSERT INTO staging VALUES
  ('O1','C001',500,'EUR','paid'), ('O2','C002',700,'EUR','refunded'), ('O3','C999',300,'EUR','paid'),
  ('O4','C001',900,'EUR','paid'), ('O4','C001',900,'EUR','paid'), ('O5','C002',-50,'EUR','paid'),
  ('O6','C001',400,'USD','paid'), ('O7','C002',250,'EUR','pending'), ('O8','C001',800,'EUR','failed'), ('O9','C002',600,'EUR','paid');
CREATE TABLE customer (customer_id text);
INSERT INTO customer VALUES ('C001'), ('C002');
WITH numbered AS (
  SELECT s.*, row_number() OVER (PARTITION BY order_id ORDER BY order_id) AS rn FROM staging s
)
SELECT CASE WHEN n.rn > 1 THEN 'duplicate order_id'
            WHEN n.amount_cents <= 0 THEN 'bad amount'
            WHEN c.customer_id IS NULL THEN 'unknown customer'
            WHEN n.currency <> 'EUR' THEN 'bad currency'
            WHEN n.status NOT IN ('paid','refunded','failed') THEN 'bad status'
            ELSE 'ok' END AS reason,
       count(*) AS n
FROM numbered n LEFT JOIN customer c ON c.customer_id = n.customer_id
GROUP BY 1 ORDER BY 1;
```

```output
reason | n
bad amount | 1
bad currency | 1
bad status | 1
duplicate order_id | 1
ok | 5
unknown customer | 1
```

### Example 5: The stage as a function with checks, and a planted defect

`run_stage` returns the report that the next days rely on: counts, counts per reason and a list of checks. The example then adds one new bad record (a negative amount on a new order id) to the raw data and shows that the quarantine grows by exactly one, which proves the checks can fail.

## Real-world applications

- **Data quality gates.** The `checks` dictionary of Example 5 is what a scheduler task evaluates before it lets the warehouse load start.
- **Support and finance follow-up.** The quarantine table of Example 3 gives the support team the order ids and reasons to chase with the source system.
- **Monitoring a source.** A jump from six to six hundred quarantined rows on one reason says the vendor changed a field, long before a report looks wrong.
- **Replays.** Because the raw layer is untouched, a corrected rule is applied by running the stage again; the quarantine is replaced and the result is repeatable.

## Daily review

### Key takeaways

- The stage splits raw into clean and quarantine, and `raw = clean + quarantined` always holds.
- Transformations are pure functions; repair only what is lossless.
- Rules run in a fixed order, so each bad record has exactly one reason.
- Quarantine keeps the reason and the original payload; dropping hides loss, stopping blocks good data.
- The same rules can be written as `CASE` in SQL; use `row_number()` for duplicates.

### Common mistakes

- Filtering with `WHERE status = 'paid'` and calling it validation, which hides what was removed.
- Letting a record count in two reasons, so the reason counts exceed the quarantine size. Return the first reason only.
- Mutating the input record in a transform, which changes the raw data other code still reads. Build a new dictionary.
- Checking `if not rec["amount_cents"]` and treating 0 as missing, or never checking the type. State the rule: positive integer.
- Appending to the quarantine on every run, so counts grow with re-runs. Replace the quarantine for the batch.
- Repairing guessed values, such as flipping a negative amount to positive.

### Revision notes

- Clean outputs: `good` (typed) and `quarantine` (reason + payload).
- Rule order: duplicate, missing timestamp, unparsable timestamp, amount, customer, currency, status.
- Expected on the generated data: 120 raw, 114 clean, 6 quarantined, one for each of six reasons.
- SQL: `CASE WHEN ... END` plus `GROUP BY 1`; duplicates via `row_number() ... > 1`.

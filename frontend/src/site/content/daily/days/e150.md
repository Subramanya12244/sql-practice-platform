## Objectives

- Explain why recomputing a heavy aggregate on every query is wasteful and name the two stored alternatives: a materialised view and an aggregate table.
- Create a materialised view in PostgreSQL, query it, and show that it is stale until it is refreshed.
- Use `REFRESH MATERIALIZED VIEW` (and `CONCURRENTLY` with a unique index) and say when each is appropriate.
- Maintain an aggregate table by recomputing the days a load touched, in one transaction, and avoid the double-counting trap of incremental addition.
- Design aggregates from additive parts (sums and counts) so that they can be rolled up and averages stay correct.

## Understand

### The repeated question

A dashboard shows revenue by month and category. Every time someone opens it, the database scans the whole fact table, joins two dimensions and groups millions of rows, and returns the same few dozen numbers it returned an hour ago. If the fact table only changes during the nightly load, nearly all of that work is wasted. The remedy is to **compute the answer once and store it**. Two tools do this: the **materialised view** (the database stores the result of a query and refreshes it on command) and the **aggregate table** (a normal table that your pipeline fills with summary rows).

### Views and materialised views

A regular **view** (Day 112) is a saved query: selecting from it runs the query again, so it saves typing and not time. A **materialised view** stores the **result rows** on disk, like a table that remembers the query that produced it. Selecting from it is as fast as reading a small table, and indexes can be created on it. The price is **staleness**: the stored rows reflect the base tables at the moment of the last refresh. New fact rows do not appear until `REFRESH MATERIALIZED VIEW name` runs, which re-executes the whole query and replaces the contents. During a plain refresh the view is locked for reading; `REFRESH MATERIALIZED VIEW CONCURRENTLY name` lets readers continue by building the new contents beside the old and swapping the differences, at the cost of more work, and it **requires a unique index** on the materialised view so that rows can be matched. A view can also be created `WITH NO DATA` and populated by the first refresh, and PostgreSQL does not refresh it automatically: the pipeline decides when, usually at the end of the load. Materialised views exist in PostgreSQL and in many warehouses; some database systems do not have them or maintain them differently, so know your platform.

### Aggregate tables

An **aggregate table** is the manual version: a table such as `agg_sales_daily(date_key, lines, units, cents)` that your load code keeps up to date. It gives you control that a materialised view does not: you can update only the part that changed instead of recomputing everything, you choose the types and constraints, and it works on platforms without materialised views. It also gives you responsibility for correctness.

The correct maintenance pattern is **recompute what the run touched**. If the load added sales for 10 and 11 February, delete the aggregate rows for those two days and insert the recomputed rows from the fact table, in one transaction (the "replace what the run owns" pattern of Day 94). A rerun repeats the same replacement and gives the same result: it is **idempotent**. The tempting alternative is to add the new rows' sums to the existing aggregate (`cents = cents + new_cents`). It is faster, and it double counts when the load is retried, when a fact row is corrected, or when late-arriving facts land in an old day. Reserve additive updates for data that is truly append-only and exactly-once.

### Design aggregates from additive parts

An aggregate that is going to be rolled up (days into months, months into years) must store **additive** measures. Store `lines`, `units` and `cents` (sums and counts), never an average price: the monthly average is `sum(cents) / sum(units)` computed from the stored parts, and an average of daily averages is wrong whenever the days have different volumes (Day 144). Distinct counts (unique customers) are not additive: the number of customers over a month is not the sum of the daily numbers, because a customer buying on two days is counted twice. Precompute them at the level you need or store a sketch, and do not roll them up by summing.

### What to precompute

Do not aggregate everything. Choose grains that match real dashboard questions: daily by product category, monthly by country. Each aggregate is another thing to keep correct and to refresh. A useful test: if a query runs often, scans a large table, and returns a small result, an aggregate is worth considering. If a query is rare or its filter changes every time, an index or partition pruning (Day 149) serves better.

### Common misconception

Learners treat a materialised view as a faster view that is always current. It is a snapshot. A dashboard that reads it after a failed refresh shows yesterday's numbers with no warning. Record the refresh time and compare it with the load log (Day 110), and fail loudly when the refresh fails.

### Why it matters

Precomputation turns an expensive question into a cheap lookup, and the cost shifts to the pipeline, which runs once instead of every time someone looks. The risk of a stale or double-counted aggregate is the cost of that choice.

## Syntax and key functions

```sql-syntax
CREATE MATERIALIZED VIEW mv_monthly_category AS
SELECT d.year, d.month, p.category, count(*) AS lines, sum(f.quantity) AS units, sum(f.amount_cents) AS cents
FROM fact_sales f JOIN dim_date d ON d.date_key = f.date_key JOIN dim_product p ON p.product_key = f.product_key
GROUP BY d.year, d.month, p.category;

CREATE UNIQUE INDEX ux_mv_monthly_category ON mv_monthly_category (year, month, category);

REFRESH MATERIALIZED VIEW mv_monthly_category;
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_monthly_category;   -- needs the unique index
```

An aggregate table refreshed for the days a load touched:

```sql-syntax
BEGIN;
DELETE FROM agg_sales_daily WHERE date_key IN (SELECT DISTINCT date_key FROM stg_sales_loaded);
INSERT INTO agg_sales_daily
SELECT date_key, count(*), sum(quantity), sum(amount_cents) FROM fact_sales
WHERE date_key IN (SELECT DISTINCT date_key FROM stg_sales_loaded) GROUP BY date_key;
COMMIT;
```

| Item | Meaning |
|---|---|
| Materialised view | Stored query result; refreshed on demand. |
| `REFRESH MATERIALIZED VIEW` | Recompute and replace the contents (readers blocked). |
| `... CONCURRENTLY` | Refresh without blocking readers; needs a unique index. |
| `WITH NO DATA` | Create empty; populate by the first refresh. |
| `pg_matviews` | Catalog view listing materialised views and `ispopulated`. |
| Aggregate table | Table maintained by the pipeline. |
| Recompute touched days | Idempotent maintenance; avoid `cents = cents + x`. |
| Additive measure | Sum or count that can be rolled up. |

## Learn by example

### Example 1: A materialised view and a query on it

The view stores revenue by year, month and category with additive parts (lines, units, cents). The query reads the stored rows for January, ordered by category. The stored result has 8 rows (2 months × 4 categories), however many fact rows there are.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL,
    valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer,
    product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'),
    (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01', NULL, true FROM generate_series(1, 12) AS i;
INSERT INTO dim_product SELECT i, 'P' || lpad(i::text, 3, '0'), 'Product ' || i,
    (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
CREATE MATERIALIZED VIEW mv_monthly_category AS
SELECT d.year, d.month, p.category, count(*) AS lines, sum(f.quantity) AS units, sum(f.amount_cents) AS cents
FROM fact_sales f JOIN dim_date d ON d.date_key = f.date_key JOIN dim_product p ON p.product_key = f.product_key
GROUP BY d.year, d.month, p.category;
CREATE UNIQUE INDEX ux_mv_monthly_category ON mv_monthly_category (year, month, category);
SELECT month, category, lines, units, cents FROM mv_monthly_category WHERE month = 1 ORDER BY category;
```

```output

1 | Books | 9 | 9 | 11750
1 | Stationery | 9 | 18 | 35000
1 | Tools | 7 | 28 | 40000
1 | Toys | 7 | 21 | 38250
```

### Example 4: An aggregate table maintained by recomputing touched days

`agg_sales_daily` is filled for all days. A late correction changes one fact row (sale 5, dated 16 January, amount raised by 1,000 cents). The maintenance step deletes the aggregate rows of the touched day and recomputes them from the fact table. The step is written twice in the block to show that repeating it gives the same numbers, and the last query checks the day against the fact table. (In a real load the delete and the insert would share one transaction.)

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL,
    valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer,
    product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'),
    (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01', NULL, true FROM generate_series(1, 12) AS i;
INSERT INTO dim_product SELECT i, 'P' || lpad(i::text, 3, '0'), 'Product ' || i,
    (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
CREATE TABLE agg_sales_daily (date_key integer PRIMARY KEY, lines integer NOT NULL, units integer NOT NULL, cents bigint NOT NULL);
INSERT INTO agg_sales_daily SELECT date_key, count(*), sum(quantity), sum(amount_cents) FROM fact_sales GROUP BY date_key;
UPDATE fact_sales SET amount_cents = amount_cents + 1000 WHERE sale_id = 5;
DELETE FROM agg_sales_daily WHERE date_key = 20260116;
INSERT INTO agg_sales_daily SELECT date_key, count(*), sum(quantity), sum(amount_cents) FROM fact_sales WHERE date_key = 20260116 GROUP BY date_key;
DELETE FROM agg_sales_daily WHERE date_key = 20260116;
INSERT INTO agg_sales_daily SELECT date_key, count(*), sum(quantity), sum(amount_cents) FROM fact_sales WHERE date_key = 20260116 GROUP BY date_key;
SELECT a.date_key, a.lines, a.units, a.cents,
       a.cents = (SELECT sum(amount_cents) FROM fact_sales WHERE date_key = a.date_key) AS matches_fact,
       (SELECT sum(cents) FROM agg_sales_daily) = (SELECT sum(amount_cents) FROM fact_sales) AS totals_agree
FROM agg_sales_daily a WHERE a.date_key = 20260116;
```

```output
date_key | lines | units | cents | matches_fact | totals_agree
20260116 | 1 | 2 | 6000 | true | true
```

### Example 5: Roll up from additive parts (pandas)

Daily aggregates hold `lines`, `units` and `cents`. The code rolls them up to months by summing, then computes the monthly average price as `cents / units`. The wrong figure, the mean of the daily average prices, is shown beside it. They differ because the days have different quantities.

```python run
import pandas as pd

daily = pd.DataFrame({
    "month": [1, 1, 1, 2, 2],
    "lines": [2, 1, 3, 1, 2],
    "units": [2, 10, 3, 1, 4],
    "cents": [2000, 5000, 3600, 900, 4400],
})
monthly = daily.groupby("month", as_index=False)[["lines", "units", "cents"]].sum()
monthly["avg_price_correct"] = (monthly["cents"] / monthly["units"]).round(1)
daily["avg_price"] = daily["cents"] / daily["units"]
monthly["avg_of_daily_avgs"] = daily.groupby("month")["avg_price"].mean().round(1).to_numpy()
print(monthly.to_string(index=False))
```

```output
 month  lines  units  cents  avg_price_correct  avg_of_daily_avgs
     1      6     15  10600              706.7              900.0
     2      3      5   5300             1060.0             1000.0
```

## Real-world applications

- **Executive dashboard.** An hourly refresh of a monthly-by-category materialised view serves every viewer from a few dozen rows instead of scanning the fact table.
- **Daily summary table.** The nightly load recomputes the days it touched, so late and corrected sales fix the summary without double counting.
- **Cost control.** On a pay-per-scan warehouse, a small aggregate table reduces the bytes scanned by a repeated query by orders of magnitude.
- **Freshness monitoring.** The refresh time is logged and compared with the load log, and the dashboard shows "data as of ..." from it.

## Daily review

### Key takeaways

- A materialised view stores a query's result; it is a snapshot that must be refreshed.
- `REFRESH MATERIALIZED VIEW CONCURRENTLY` needs a unique index and avoids blocking readers.
- An aggregate table gives control; maintain it by recomputing the touched grain, in one transaction.
- Store additive parts (sums, counts); derive ratios at read time; do not sum distinct counts.
- Check freshness: refresh time against the load time.

### Common mistakes

- **Reading a stale view as current.** After a failed refresh the numbers are old. Log and show the refresh time.
- **Adding deltas to an aggregate.** A retried or corrected load double counts. Recompute the touched days.
- **Storing averages.** They cannot be rolled up. Store sums and counts.
- **`CONCURRENTLY` without a unique index.** PostgreSQL raises an error. Create the index first.
- **Aggregating everything.** Each aggregate is more to maintain. Build the ones that real queries use.

### Revision notes

- `CREATE MATERIALIZED VIEW`, `REFRESH [CONCURRENTLY]`, unique index, `pg_matviews`.
- Aggregate table: delete and re-insert the touched days in one transaction.
- Additive measures; average = sum / count.

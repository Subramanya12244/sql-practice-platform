## Understand

### What Power BI is

Power BI is Microsoft's business intelligence product: a set of tools for loading data, modelling it, building interactive reports and sharing them. Two parts matter on day one. **Power BI Desktop** is the free authoring application. It runs only on Windows, so people on a Mac use a Windows machine, a virtual machine or the browser service for what they can. **Power BI Service** is the cloud site at app.powerbi.com that runs in any browser; you publish a finished report from Desktop to the Service to share it with colleagues, schedule data refreshes and build dashboards from report tiles. The Service can also create and edit reports in the browser, with fewer modelling features than Desktop. The usual flow is: get data, clean it, model it, write measures, build visuals in Desktop, publish to the Service.

This course uses one small sample model for the whole phase. It has a fact table `Sales(order_id, order_date, customer_id, product_id, quantity, unit_price)`, dimension tables `Customers(customer_id, customer_name, country, segment)` and `Products(product_id, product_name, category, unit_cost)`, and a `Calendar` date table. Revenue is `quantity * unit_price`. Because Power BI Desktop is not available in the browser lessons, every step is shown as text and every number is checked with pandas.

### The three views

Desktop has a left-hand rail with the main views. **Report view** is the canvas where you place visuals (charts, tables, cards) and slicers. **Table view** (called Data view in earlier versions) shows the rows of one table, as loaded, so you can inspect values and column formats. **Model view** shows each table as a box with its columns and the relationships between tables as lines. Working across the three is a loop: you notice a wrong total in Report view, find the cause in Table view (for instance a text column where numbers were expected), and fix the relationship or the data type in Model view or the query. Menu names change between releases, so look for the ideas (get data, transform, model, report) rather than memorising ribbon positions.

### Getting data: connectors

A **connector** is the component that knows how to read one kind of source. On the Home tab, `Get data` opens the list: `Text/CSV` for delimited files, `Excel workbook` for sheets and tables, `SQL Server` and other databases (which need a server name and credentials), `Web` for a URL, and `Folder` for many files at once. After you choose a file the **navigator** or preview window shows a sample of the rows. Two buttons matter: `Load` puts the data into the model as it is, and `Transform data` opens the Power Query Editor to clean it first (Day 125). If the preview shows anything wrong (a date read as text, a leading blank row), choose `Transform data`.

### Import and DirectQuery

Each table has a **storage mode**. In **Import** mode Power BI copies the data into its own compressed in-memory engine when you refresh, and every visual then reads from that copy, which is fast and supports the full set of modelling features. The report shows the data as of the last refresh. In **DirectQuery** mode the data stays in the source and each visual sends a query to the database when it is displayed, so the numbers are current, but each interaction waits for the database and some features are limited. For a small model like ours, and for most analyst work, Import is the default choice. DirectQuery is for data too large to import or that must be up to the minute.

### Column profiling and why it matters

The Power Query Editor can show **column quality** (the share of valid, error and empty values), **column distribution** (distinct and unique counts) and **column profile** (statistics and a value histogram for the selected column). Switch them on in the View tab. They are the Power BI version of the checks you ran in pandas with `isna`, `nunique` and `describe` in the EDA phase. Look at three things before you load: types (is `order_date` a Date?), empties (a key column with nulls will break relationships) and distinct counts (a dimension key must be unique, or the relationship will fail or give inflated totals; Day 127 shows why).

### Common misconception

People often treat the data loaded into the model as the same thing as the source. It is a copy, taken at the last refresh, with whatever type changes the query applied. If the report disagrees with the source, check the refresh time, then the query steps, then the relationships. The reverse mistake is to fix numbers in visuals by hand instead of in the data: the next refresh discards them.

### Why it matters

Most wrong Power BI numbers come from the first steps: a date loaded as text, a key with duplicates, rows lost in a filter. Checking row counts, keys and date coverage straight after loading takes minutes and prevents hours of debugging later. The checks in this lesson are exactly the ones to run on any new model.

## Syntax and key functions

Power BI Desktop steps are menu actions; the text below is the sequence for a CSV file:

```text
Home > Get data > Text/CSV > choose sales.csv
Preview: check delimiter, data types, header row
Transform data   (clean first)   or   Load   (as is)
Model view: confirm each table, then create relationships
Report view: add visuals
Home > Publish > choose a workspace   (to the Power BI Service)
```

The Power Query (M) text that Desktop writes for the CSV connector looks like this. The file path is only an example:

```
let
    Source = Csv.Document(File.Contents("C:\PowerBI\sales.csv"), [Delimiter=",", Columns=6, Encoding=65001, QuoteStyle=QuoteStyle.None]),
    #"Promoted Headers" = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
    #"Changed Type" = Table.TransformColumnTypes(#"Promoted Headers", {{"order_id", Int64.Type}, {"order_date", type date}, {"customer_id", Int64.Type}, {"product_id", Int64.Type}, {"quantity", Int64.Type}, {"unit_price", type number}})
in
    #"Changed Type"
```

Each line after `let` is a named step whose result is passed to the next; the last line after `in` is the query's result. The pandas equivalent used in the examples is:

```python
df = pd.read_csv(io.StringIO(text), parse_dates=["order_date"])
```

| Power BI item | Meaning | pandas check |
|---|---|---|
| Get data connector | Reads one kind of source | `read_csv`, `read_excel`, `read_sql` |
| Load / Transform data | Load as is / clean first | assign the DataFrame / apply cleaning steps |
| Import / DirectQuery | Copy data into the model / query the source live | in-memory DataFrame / live query |
| Column quality | Valid, error, empty share | `df.isna().mean()` |
| Column distribution | Distinct and unique counts | `df[col].nunique()` |
| Table view | Rows of one table | `df.head()` |
| Model view | Tables and relationships | key uniqueness and orphan checks |

## Learn by example

### Example 1: The four tables as CSV files

The sample model is generated with a seeded random generator: 40 customers, 12 products, 400 orders in 2025 and a 365-day calendar. Writing each table to CSV text stands in for the files you would connect to in Power BI. The line counts include one header line each.

```python run
import numpy as np
import pandas as pd


def make_model():
    rng = np.random.default_rng(7)
    customers = pd.DataFrame({
        "customer_id": np.arange(1, 41),
        "customer_name": [f"Customer {i:02d}" for i in range(1, 41)],
        "country": rng.choice(["UK", "Germany", "France", "Spain"], size=40),
        "segment": rng.choice(["Consumer", "Corporate", "Small Business"], size=40, p=[0.5, 0.3, 0.2]),
    })
    names = ["Desk", "Chair", "Bookcase", "Laptop", "Monitor", "Phone", "Notebook", "Pen Set", "Stapler", "Printer", "Lamp", "Cabinet"]
    categories = ["Furniture", "Furniture", "Furniture", "Technology", "Technology", "Technology",
                  "Office Supplies", "Office Supplies", "Office Supplies", "Technology", "Furniture", "Furniture"]
    products = pd.DataFrame({
        "product_id": np.arange(1, 13),
        "product_name": names,
        "category": categories,
        "unit_cost": rng.integers(5, 120, size=12),
    })
    sales = pd.DataFrame({
        "order_id": np.arange(1001, 1401),
        "order_date": pd.Timestamp("2025-01-01") + pd.to_timedelta(rng.integers(0, 365, 400), unit="D"),
        "customer_id": rng.integers(1, 41, 400),
        "product_id": rng.integers(1, 13, 400),
        "quantity": rng.integers(1, 8, 400),
    })
    cost = products.set_index("product_id")["unit_cost"]
    sales["unit_price"] = (cost[sales["product_id"]].to_numpy() * (1.3 + 0.5 * rng.random(400))).round(2)
    sales = sales.sort_values(["order_date", "order_id"]).reset_index(drop=True)
    dates = pd.date_range("2025-01-01", "2025-12-31", freq="D")
    calendar = pd.DataFrame({
        "date": dates,
        "year": dates.year,
        "quarter": dates.quarter,
        "month_number": dates.month,
        "month_name": dates.strftime("%B"),
    })
    return sales, customers, products, calendar

import io

tables = dict(zip(["Sales", "Customers", "Products", "Calendar"], make_model()))
csv_text = {name: df.to_csv(index=False) for name, df in tables.items()}
for name, text in csv_text.items():
    lines = text.strip().splitlines()
    print(f"{name:10} lines {len(lines):>4}  header: {lines[0]}")
```

```output
Sales      lines  401  header: order_id,order_date,customer_id,product_id,quantity,unit_price
Customers  lines   41  header: customer_id,customer_name,country,segment
Products   lines   13  header: product_id,product_name,category,unit_cost
Calendar   lines  366  header: date,year,quarter,month_number,month_name
```

### Example 2: What the preview infers

Reading CSV text back is what the Text/CSV connector does when it builds the preview: it splits the lines, uses the first row as headers and guesses a type for each column. The dates come back as text unless you tell pandas to parse them, just as Power BI's detection can be wrong for unusual formats, so you check the types. The example prints each column's type family, not machine-specific type names.

### Example 3: Column quality and distribution

Power Query shows the share of valid and empty values and the distinct count for each column. This is the same table built with pandas. A dimension key must have as many distinct values as rows (unique), and a fact key may repeat. The profile for Sales tells you at once that `order_id` is unique and `customer_id` repeats, which is what the one-to-many relationship will rely on.

### Example 4: Post-load checks on the whole model

After loading, three checks catch most problems: each dimension key is unique, every key in Sales exists in its dimension (no orphans, which Power BI would show as a blank group), and every order date falls inside the Calendar. The function returns a dictionary of results, so the same checks can run after every refresh.

```python run
import numpy as np
import pandas as pd


def make_model():
    rng = np.random.default_rng(7)
    customers = pd.DataFrame({
        "customer_id": np.arange(1, 41),
        "customer_name": [f"Customer {i:02d}" for i in range(1, 41)],
        "country": rng.choice(["UK", "Germany", "France", "Spain"], size=40),
        "segment": rng.choice(["Consumer", "Corporate", "Small Business"], size=40, p=[0.5, 0.3, 0.2]),
    })
    names = ["Desk", "Chair", "Bookcase", "Laptop", "Monitor", "Phone", "Notebook", "Pen Set", "Stapler", "Printer", "Lamp", "Cabinet"]
    categories = ["Furniture", "Furniture", "Furniture", "Technology", "Technology", "Technology",
                  "Office Supplies", "Office Supplies", "Office Supplies", "Technology", "Furniture", "Furniture"]
    products = pd.DataFrame({
        "product_id": np.arange(1, 13),
        "product_name": names,
        "category": categories,
        "unit_cost": rng.integers(5, 120, size=12),
    })
    sales = pd.DataFrame({
        "order_id": np.arange(1001, 1401),
        "order_date": pd.Timestamp("2025-01-01") + pd.to_timedelta(rng.integers(0, 365, 400), unit="D"),
        "customer_id": rng.integers(1, 41, 400),
        "product_id": rng.integers(1, 13, 400),
        "quantity": rng.integers(1, 8, 400),
    })
    cost = products.set_index("product_id")["unit_cost"]
    sales["unit_price"] = (cost[sales["product_id"]].to_numpy() * (1.3 + 0.5 * rng.random(400))).round(2)
    sales = sales.sort_values(["order_date", "order_id"]).reset_index(drop=True)
    dates = pd.date_range("2025-01-01", "2025-12-31", freq="D")
    calendar = pd.DataFrame({
        "date": dates,
        "year": dates.year,
        "quarter": dates.quarter,
        "month_number": dates.month,
        "month_name": dates.strftime("%B"),
    })
    return sales, customers, products, calendar

import io

tables = dict(zip(["Sales", "Customers", "Products", "Calendar"], make_model()))
csv_text = {name: df.to_csv(index=False) for name, df in tables.items()}
loaded = {name: pd.read_csv(io.StringIO(text), parse_dates=["order_date"] if name == "Sales" else ["date"] if name == "Calendar" else None)
          for name, text in csv_text.items()}


def model_checks(t):
    sales, customers, products, calendar = t["Sales"], t["Customers"], t["Products"], t["Calendar"]
    return {
        "rows": {k: len(v) for k, v in t.items()},
        "customer key unique": bool(customers["customer_id"].is_unique),
        "product key unique": bool(products["product_id"].is_unique),
        "orphan customers": int((~sales["customer_id"].isin(customers["customer_id"])).sum()),
        "orphan products": int((~sales["product_id"].isin(products["product_id"])).sum()),
        "dates outside calendar": int((~sales["order_date"].isin(calendar["date"])).sum()),
    }


for key, value in model_checks(loaded).items():
    print(f"{key}: {value}")
revenue = (loaded["Sales"]["quantity"] * loaded["Sales"]["unit_price"]).sum()
print("total revenue:", round(float(revenue), 2))
```

```output

customer key unique: True
product key unique: True
orphan customers: 0
orphan products: 0
dates outside calendar: 0
total revenue: 158823.32
```

## Real-world applications

- **Onboarding a new data source.** An analyst connects a finance extract, reads column quality in the preview, and decides whether to transform before loading (Examples 2 and 3), instead of discovering blank rows in a finished report.
- **Refresh monitoring.** Row counts and orphan checks (Example 4) are what a developer compares after each scheduled refresh in the Service to catch a source that changed shape.
- **Choosing Import or DirectQuery.** A team with a 10-million-row transaction table weighs freshness against interaction speed; a team with a monthly spreadsheet imports it.
- **Handover documentation.** The list of tables, rows, keys and relationships (Model view) is the first page of the documentation for a report.

## Daily review

### Key takeaways

- Desktop (Windows) is for authoring; the Service (browser) is for sharing and refresh.
- Views: Report for visuals, Table for rows, Model for tables and relationships.
- A connector reads one source type; the preview offers `Load` or `Transform data`.
- Import copies data into the model; DirectQuery queries the source live.
- After loading, check types, key uniqueness, orphans and date coverage.

### Common mistakes

- Loading a date column as text. Symptom: dates sort alphabetically and time-based features are missing. Fix: change the type to Date in Power Query before loading.
- A dimension key with duplicates. Symptom: the relationship cannot be one-to-many, or totals are inflated. Fix: find and remove duplicates or use the correct key.
- Fixing a number in a visual instead of the data. Symptom: the correction disappears at the next refresh. Fix: correct it in the query or the source.
- Assuming the report shows today's data. Symptom: a stakeholder quotes a figure that is a day old. Fix: show the last refresh time and understand the storage mode.

### Revision notes

- Desktop = authoring (Windows); Service = sharing (browser).
- Get data, then `Load` or `Transform data`.
- Column quality, distribution and profile = `isna`, `nunique`, `describe`.
- Checks: unique keys, no orphans, dates inside the calendar, row counts.

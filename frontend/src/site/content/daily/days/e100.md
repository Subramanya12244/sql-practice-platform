## Objectives

- Build the whole chain from a messy sheet to a constrained database table: extract, clean, load with a reject table, reconcile.
- Reconcile the load with three kinds of evidence: row counts, a sum compared with the sheet's own total, and key checks (duplicates, orphans, nulls).
- Explain a difference between the sheet total and the loaded total by adding the rejected amounts, so that the numbers close.
- Run the same reconciliation queries as PostgreSQL SQL on PGlite and as Python on `sqlite3`.
- Produce a short pass or fail report that names the failing check when the data is corrupted.

## Understand

### The project

This is a project day. You assemble the skills of Days 96 to 99 into one small pipeline and then prove it correct. The scenario: finance sends a workbook, `Regional sales 2026`, with a `Sales` sheet and a `Customers` sheet. The sales sheet has a title above the table, amounts stored as text (`$1,200.50`, `(50.00)`, `n/a`), dates stored as Excel serial numbers, a subtotal row, a footer line `Total` with the total the finance team believes is right, and a source note. Some rows are defective: one order id appears twice, one order belongs to a customer who is not in the customer sheet, and one order has no amount. The goal is a table `sales_order` in the database that holds every acceptable row, a table `reject` that holds every other row with a reason, and a report that proves that nothing went missing.

### The four steps

**Extract** reads each sheet as a raw grid with no header and finds the table by its landmarks (Day 97). **Clean** repairs types: serial dates to dates, amounts to integer cents (storing money as whole cents avoids floating-point rounding), identifiers to integers, and it drops subtotal, total and note rows after recording the reported total. **Load** writes parents before children into tables with primary keys, foreign keys and a check on the amount (Day 99). Rows that fail are classified before loading and written to `reject` with a reason, so that the load itself never fails on data it could have predicted. **Reconcile** compares what the source said with what the database holds.

### What reconciliation means

To **reconcile** two systems is to show that they agree, or to explain every difference. A reconciliation that only says "counts match" is weak because two different errors can cancel out. Use three kinds of evidence together.

1. **Row counts.** Rows read from the sheet equal rows loaded plus rows rejected (plus rows skipped as exact duplicates, if you separate them). If this fails, rows vanished between steps.
2. **A control total.** The sum of a numeric column in the database, compared with the figure the sheet reports for itself. Sums catch altered values that counts cannot. A sum on its own can be fooled when one value goes up and another down by the same amount; counts and key checks cover that case.
3. **Key and quality checks.** No duplicate keys, no orphan foreign keys, no nulls in required columns. Constraints should make these impossible in the loaded tables, and a query that confirms it costs almost nothing.

### Explaining the difference

The sheet total will often differ from the loaded total, and that is not a failure when the difference is explained. Here the footer says `$1,559.50`. The loaded orders sum to a smaller number, because one order was rejected for an unknown customer. The report must show the arithmetic: **sheet total = loaded total + rejected amount (where an amount exists)**. A rejected duplicate does not belong in that sum because the sheet's total did not count it twice. This distinction, which rejects were in the sheet total and which were not, comes from reading the sheet's own logic, and it is the part of reconciliation that needs a person's judgment. Write the rule in code with a comment, so the next engineer sees it.

### Why the report is part of the product

The business consumer does not read your queries; they read the one-page outcome. A good report states the counts, the control total with its explanation, the list of rejects with reasons and an overall pass or fail. It exits with a failure status when a check fails, so that a scheduler stops and a person looks. A report that is always green is as useless as no report.

### Common misconception

People believe that if the load did not raise an error, it is correct. A load can run without error and still drop a row (a filter that was too strict), double a row (a join that fanned out), or read a footer as data. Only a comparison against an independent figure from the source finds those.

### Scope

Everything here runs without a PostgreSQL server. The Python steps use `sqlite3` as a stand-in, and the reconciliation queries run again as PostgreSQL SQL on PGlite. The workbook itself is read with `openpyxl` only in the last, local example; the logic is tested on the raw grid that `read_excel(header=None)` returns.

## Syntax and key functions

The pipeline as functions, in the order it runs:

```python
raw = pd.read_excel("sales_2026.xlsx", sheet_name="Sales", header=None)   # extract
detail, reported_cents = clean_sales(raw)                                 # clean
loaded, rejects = load(conn, detail)                                      # load
report = reconcile(conn, source_rows=len(detail), reported_cents=reported_cents)
```

Reconciliation query shapes (PostgreSQL):

```sql-syntax
SELECT count(*) FROM sales_order;                                       -- loaded rows
SELECT sum(amount_cents) FROM sales_order;                              -- control total
SELECT order_id FROM sales_order GROUP BY order_id HAVING count(*) > 1; -- duplicates
SELECT o.order_id FROM sales_order o
LEFT JOIN customer c USING (customer_id) WHERE c.customer_id IS NULL;   -- orphans
```

| Item | What it does or returns |
|---|---|
| `clean_sales(raw)` | Detail rows with typed columns and the reported total in cents. |
| `load(conn, detail)` | Inserts acceptable rows, writes the rest to `reject`. |
| `reject(order_id, reason, amount_cents)` | One row per refused source row. |
| Control total | Sum of the amount column, compared with the sheet's total. |
| Count equation | read = loaded + rejected. |
| `GROUP BY ... HAVING count(*) > 1` | Finds repeated keys. |
| `LEFT JOIN ... WHERE parent IS NULL` | Finds orphans. |
| `round(x * 100)` | Converts money to integer cents (use `int(round(...))` in Python). |

## Learn by example

### Example 1: Extract and clean the Sales sheet

`raw` is the raw grid of the `Sales` sheet. The function finds the header by the landmark `Order`, removes the subtotal, total and source rows, converts serial dates, converts amount text to integer cents (`None` for `n/a`) and returns the reported total, which it reads from the `Total` row before dropping it.

```python run
import pandas as pd

nan = float("nan")
raw = pd.DataFrame([
    ["Regional sales 2026", nan, nan, nan],
    [nan, nan, nan, nan],
    ["Order", "Date", "Customer", "Amount"],
    [1001, 46023, 1, "$1,200.50"],
    [1002, 46023, 2, "300"],
    ["Subtotal day 1", nan, nan, "$1,500.50"],
    [1003, 46024, 1, "(50.00)"],
    [1004, 46060, 3, "$99"],
    [1005, 46061, 9, "$10"],
    [1002, 46023, 2, "300"],
    [1006, 46062, 2, "n/a"],
    ["Total", nan, nan, "$1,559.50"],
    ["Source: finance", nan, nan, nan],
])

def to_cents(text):
    text = str(text).strip()
    if text in ("n/a", "-", "", "nan"):
        return None
    negative = text.startswith("(") and text.endswith(")")
    value = float(text.strip("()").replace("$", "").replace(",", ""))
    return int(round((-value if negative else value) * 100))

def clean_sales(raw):
    header = raw.index[raw[0] == "Order"]
    if len(header) != 1:
        raise ValueError("landmark 'Order' must appear exactly once")
    body = raw.iloc[header[0] + 1:].copy()
    body.columns = ["order_id", "order_date", "customer_id", "amount"]
    label = body["order_id"].astype(str)
    reported = to_cents(body.loc[label == "Total", "amount"].iloc[0])
    detail = body[~label.str.startswith(("Subtotal", "Total", "Source"))].copy()
    detail["order_id"] = detail["order_id"].astype(int)
    detail["customer_id"] = detail["customer_id"].astype(int)
    detail["order_date"] = pd.to_datetime(detail["order_date"].astype(float), unit="D", origin="1899-12-30").dt.strftime("%Y-%m-%d")
    detail["amount_cents"] = pd.array([to_cents(a) for a in detail["amount"]], dtype="Int64")
    return detail[["order_id", "order_date", "customer_id", "amount_cents"]].reset_index(drop=True), reported

detail, reported = clean_sales(raw)
print(detail.to_string())
print("reported total cents:", reported)
```

```output
   order_id  order_date  customer_id  amount_cents
0      1001  2026-01-01            1        120050
1      1002  2026-01-01            2         30000
2      1003  2026-01-02            1         -5000
3      1004  2026-02-07            3          9900
4      1005  2026-02-08            9          1000
5      1002  2026-01-01            2         30000
6      1006  2026-02-09            2          <NA>
reported total cents: 155950
```

Seven source rows remain. Money is now whole cents in the nullable `Int64` type, so the missing amount shows as `<NA>` and the other values stay integers instead of turning into floats. That is the form the database will hold.

### Example 2: Load parents first and keep a reject table

The tables have the constraints from Day 99. Customers load first. Each detail row is classified (missing amount, unknown customer, duplicate order id) before insertion; good rows load in one transaction together with the reject rows. A rejected row keeps its amount, because the reconciliation needs it.

```python run
import sqlite3

detail = [
    (1001, "2026-01-01", 1, 120050), (1002, "2026-01-01", 2, 30000), (1003, "2026-01-02", 1, -5000),
    (1004, "2026-02-07", 3, 9900), (1005, "2026-02-08", 9, 1000), (1002, "2026-01-01", 2, 30000),
    (1006, "2026-02-09", 2, None),
]
customers = [(1, "Ana"), (2, "Ben"), (3, "Cy")]

conn = sqlite3.connect(":memory:")
conn.execute("PRAGMA foreign_keys = ON")
conn.executescript("""
CREATE TABLE customer (customer_id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE sales_order (order_id INTEGER PRIMARY KEY, order_date TEXT NOT NULL,
    customer_id INTEGER NOT NULL REFERENCES customer (customer_id), amount_cents INTEGER NOT NULL);
CREATE TABLE reject (order_id INTEGER, reason TEXT, amount_cents INTEGER);
""")

def load(conn, customers, detail):
    known = {c[0] for c in customers}
    good, rejects, seen = [], [], set()
    for row in detail:
        order_id, _, customer_id, cents = row
        if cents is None:
            rejects.append((order_id, "missing amount", None))
        elif customer_id not in known:
            rejects.append((order_id, "unknown customer", cents))
        elif order_id in seen:
            rejects.append((order_id, "duplicate order", cents))
        else:
            seen.add(order_id)
            good.append(row)
    with conn:
        conn.executemany("INSERT INTO customer VALUES (?, ?)", customers)
        conn.executemany("INSERT INTO sales_order VALUES (?, ?, ?, ?)", good)
        conn.executemany("INSERT INTO reject VALUES (?, ?, ?)", rejects)

load(conn, customers, detail)
print(conn.execute("SELECT COUNT(*), SUM(amount_cents) FROM sales_order").fetchone())
print(conn.execute("SELECT * FROM reject ORDER BY order_id, reason").fetchall())
```

```output
(4, 154950)
[(1002, 'duplicate order', 30000), (1005, 'unknown customer', 1000), (1006, 'missing amount', None)]
```

Four orders loaded and three rows rejected: 4 + 3 = 7 source rows.

### Example 3: Reconciliation queries on PostgreSQL syntax (PGlite)

The same four tables are rebuilt on PGlite from the loaded data and the rejects. One query returns the checks as rows: the loaded count, the rejected count, the control total of the loaded rows, the rejected amount that belongs to the sheet total (orphan rows) and the sum of the two, plus the duplicate-key and orphan checks on the loaded table, which must be zero.

```sql run
CREATE TABLE customer (customer_id integer PRIMARY KEY, name text NOT NULL);
CREATE TABLE sales_order (order_id integer PRIMARY KEY, order_date date NOT NULL,
    customer_id integer NOT NULL REFERENCES customer (customer_id), amount_cents integer NOT NULL);
CREATE TABLE reject (order_id integer, reason text, amount_cents integer);
INSERT INTO customer VALUES (1, 'Ana'), (2, 'Ben'), (3, 'Cy');
INSERT INTO sales_order VALUES (1001, '2026-01-01', 1, 120050), (1002, '2026-01-01', 2, 30000),
    (1003, '2026-01-02', 1, -5000), (1004, '2026-02-07', 3, 9900);
INSERT INTO reject VALUES (1005, 'unknown customer', 1000), (1002, 'duplicate order', 30000), (1006, 'missing amount', NULL);
SELECT check_name, value FROM (
    SELECT 1 AS k, 'loaded rows' AS check_name, count(*)::bigint AS value FROM sales_order
    UNION ALL SELECT 2, 'rejected rows', count(*) FROM reject
    UNION ALL SELECT 3, 'loaded cents', sum(amount_cents) FROM sales_order
    UNION ALL SELECT 4, 'rejected cents in sheet total', coalesce(sum(amount_cents), 0) FROM reject WHERE reason = 'unknown customer'
    UNION ALL SELECT 5, 'loaded + rejected cents', (SELECT sum(amount_cents) FROM sales_order) + (SELECT coalesce(sum(amount_cents), 0) FROM reject WHERE reason = 'unknown customer')
    UNION ALL SELECT 6, 'duplicate keys', count(*) FROM (SELECT order_id FROM sales_order GROUP BY order_id HAVING count(*) > 1) d
    UNION ALL SELECT 7, 'orphans', count(*) FROM sales_order o LEFT JOIN customer c USING (customer_id) WHERE c.customer_id IS NULL
) t ORDER BY k;
```

```output
check_name | value
loaded rows | 4
rejected rows | 3
loaded cents | 154950
rejected cents in sheet total | 1000
loaded + rejected cents | 155950
duplicate keys | 0
orphans | 0
```

The sheet reported `$1,559.50`, which is 155,950 cents. The loaded 154,950 plus the 1,000 rejected for an unknown customer is 155,950, so the control total closes.

### Example 4: A report that fails when the data is corrupted

`reconcile` runs the checks on a `sqlite3` connection and returns lines marked `PASS` or `FAIL`. It compares counts, the control total (loaded plus the explained rejects against the reported total) and the key checks. The second call deletes one loaded row to imitate a corrupted load: counts and the control total both fail, and the report names them.

```python run
import sqlite3

def build():
    conn = sqlite3.connect(":memory:")
    conn.executescript("""
    CREATE TABLE sales_order (order_id INTEGER PRIMARY KEY, customer_id INTEGER, amount_cents INTEGER NOT NULL);
    CREATE TABLE reject (order_id INTEGER, reason TEXT, amount_cents INTEGER);
    INSERT INTO sales_order VALUES (1001, 1, 120050), (1002, 2, 30000), (1003, 1, -5000), (1004, 3, 9900);
    INSERT INTO reject VALUES (1005, 'unknown customer', 1000), (1002, 'duplicate order', 30000), (1006, 'missing amount', NULL);
    """)
    return conn

def reconcile(conn, source_rows, reported_cents):
    loaded, loaded_cents = conn.execute("SELECT COUNT(*), COALESCE(SUM(amount_cents), 0) FROM sales_order").fetchone()
    rejected = conn.execute("SELECT COUNT(*) FROM reject").fetchone()[0]
    explained = conn.execute("SELECT COALESCE(SUM(amount_cents), 0) FROM reject WHERE reason = 'unknown customer'").fetchone()[0]
    dups = conn.execute("SELECT COUNT(*) FROM (SELECT order_id FROM sales_order GROUP BY order_id HAVING COUNT(*) > 1)").fetchone()[0]
    checks = [
        ("counts: read = loaded + rejected", source_rows == loaded + rejected),
        ("control total: reported = loaded + explained rejects", reported_cents == loaded_cents + explained),
        ("no duplicate keys", dups == 0),
    ]
    lines = [("PASS " if ok else "FAIL ") + name for name, ok in checks]
    return lines, all(ok for _, ok in checks)

conn = build()
lines, ok = reconcile(conn, 7, 155950)
print("\n".join(lines), "->", "OK" if ok else "STOP")
conn.execute("DELETE FROM sales_order WHERE order_id = 1004")
lines, ok = reconcile(conn, 7, 155950)
print("\n".join(lines), "->", "OK" if ok else "STOP")
```

```output
PASS counts: read = loaded + rejected
PASS control total: reported = loaded + explained rejects
PASS no duplicate keys -> OK
FAIL counts: read = loaded + rejected
FAIL control total: reported = loaded + explained rejects
PASS no duplicate keys -> STOP
```

## Real-world applications

- **Finance close.** A month-end workbook is loaded and reconciled to its control total before the ledger report is built; the report names the explained differences.
- **Partner onboarding.** A new data provider sends a workbook; the reject table and its reasons become the feedback email to the provider.
- **Migration sign-off.** Counts, a control total and key checks are the evidence that a spreadsheet's content moved into the database intact.
- **Scheduled monitoring.** The same `reconcile` function runs after each monthly delivery and stops the pipeline on a `FAIL`.

## Daily review

### Key takeaways

- A pipeline is extract, clean, load and reconcile; the reconciliation is what makes it trustworthy.
- Store money as integer cents; keep rejected rows with their reasons and amounts.
- Use counts, a control total and key checks together; each catches what the others miss.
- A difference is acceptable only when every part of it is explained.
- The report should fail loudly and name the failing check.

### Common mistakes

- **Reconciling counts only.** A changed amount passes. Add the control total.
- **Including duplicates in the explained difference.** The sheet's own total did not double count them. Write down which rejects belong to the total.
- **Rounding floats instead of using cents.** Sums drift by a cent. Convert to integer cents at cleaning time.
- **Dropping rejected rows without a record.** Nobody can say what was lost. Write them to `reject` with a reason.
- **A report that never fails.** If all checks return `True` by construction, they test nothing. Run it against a deliberately corrupted load once.

### Revision notes

- Steps: extract (landmarks), clean (types, cents, drop footers), load (parents first, rejects), reconcile.
- Equations: read = loaded + rejected; reported total = loaded + explained rejects.
- Checks: duplicates, orphans, nulls; confirm the report fails on a corrupted load.

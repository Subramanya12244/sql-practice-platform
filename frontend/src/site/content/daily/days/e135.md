## Objectives

- Declare `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `CHECK` and `FOREIGN KEY` constraints and explain what each one rejects.
- Write check queries that find duplicates, nulls, out-of-range or invalid values and orphan rows, and turn them into one violation report.
- Clean violating rows, then add a constraint, and read constraints back from `information_schema`.
- Choose between a constraint (prevent) and a check query (detect), and pick a foreign key action.

## Understand

### Two ways to defend data

Day 133 and 134 checked data in pandas, after it was extracted. The database itself can defend its tables in two ways. **Constraints** are rules declared on the table that the database enforces on every write: a row that breaks one is rejected, whoever wrote it. **Check queries** are ordinary `SELECT` statements that count or list rows that break an expectation; they find problems in data that is already there. Constraints **prevent**, check queries **detect**. A pipeline needs both: constraints are the last line of defence against a bug in a loader, and queries find what constraints cannot express (a total that differs from the source, a row that is too old) or what was loaded before the constraint existed.

All SQL in today's examples runs on PGlite, the PostgreSQL stand-in in the browser, with tables created in the block. The `sqlite3` version in Python is used where a rejection must be shown, since a rejected write is an error and a block that fails cannot print a result.

### The constraints

A **PRIMARY KEY** states that a column (or set of columns) identifies each row: the value must be unique and not NULL. A table has at most one. **NOT NULL** forbids missing values in a column: it is completeness, enforced. **UNIQUE** forbids two rows with the same value (or combination), but allows NULL (several NULLs do not count as duplicates in PostgreSQL); it is uniqueness, enforced, for keys that are not the primary key such as `email`. **CHECK** attaches a boolean expression to a row: `CHECK (amount >= 0)` or `CHECK (status IN ('paid', 'refunded', 'failed'))`; a row for which the expression is false is rejected, and a row for which it is NULL is accepted, which is the same missing-value trap as Day 133 (a NULL amount passes `amount >= 0`, so pair it with NOT NULL when presence is required). It is validity, enforced. A **FOREIGN KEY** states that a value in one table must exist in another: `customer_id REFERENCES qc_customers (customer_id)`; it is referential consistency, enforced. Naming constraints (`CONSTRAINT qc_orders_amount_ck`) makes error messages and reports readable.

### Referential integrity and its actions

**Referential integrity** means that every reference points to something that exists: no **orphan** rows (an order whose customer is not in the customer table). The foreign key rejects an insert of an order with an unknown customer, and also decides what happens when the parent is deleted. `ON DELETE RESTRICT` (or the default `NO ACTION`) refuses the delete while children exist; `ON DELETE CASCADE` deletes the children too (dangerous for data you may want to keep); `ON DELETE SET NULL` keeps the child and clears the reference. The choice is a business decision: orders should not vanish when a customer record is removed, so `RESTRICT` or `SET NULL` is the usual answer for them. Foreign keys cost a check on every write, and in warehouses they are often declared but not enforced, or left out for load speed, which moves the job to check queries that look for orphans after each load.

### Check queries

A check query counts violations: duplicates by `GROUP BY ... HAVING COUNT(*) > 1`, nulls with `WHERE col IS NULL`, invalid values with `WHERE status NOT IN (...)`, out-of-range values with `WHERE amount < 0` and orphans with a `LEFT JOIN ... WHERE parent.key IS NULL` or `NOT EXISTS`. Stacking them with `UNION ALL` gives one report of check name and violation count, the same shape as Day 95's validation report, where healthy means all zeros. Remember that SQL comparisons with NULL are not true: `WHERE amount < 0` does not return the row with a NULL amount, and `status NOT IN ('paid')` does not return a NULL status. Missing values need their own `IS NULL` check.

### Adding a constraint to existing data

`ALTER TABLE ... ADD CONSTRAINT` validates every existing row first and fails if any row violates it. So the safe order is: run the check query, fix or quarantine the violating rows, then add the constraint so that the problem cannot come back. PostgreSQL also offers `NOT VALID`, which adds the constraint for new writes without checking old rows, and a later `VALIDATE CONSTRAINT` once the cleanup is done; that is a tool for large tables where the check would lock them too long.

### Reading the catalogue

`information_schema` holds the database's own description of its tables. `information_schema.columns` lists each column with its `data_type` and `is_nullable`; `information_schema.table_constraints` lists constraints with a name and a type (`PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY`, `CHECK`). Pipelines read it to compare the live table with the contract of Day 134 (drift detection in SQL) and to see which defences exist. In recent PostgreSQL versions `NOT NULL` constraints may also appear as `CHECK` entries with generated names, so the examples select the constraints by their explicit names.

### Why it matters in data work

A constraint turns "we expect unique order ids" from a hope into a guarantee, and a check query shows how far reality is from the hope. Together they cut the time between a defect arriving and someone knowing about it from weeks to the next load.

## Syntax and key functions

```sql-syntax
CREATE TABLE t (
  id int CONSTRAINT t_pk PRIMARY KEY,
  email text NOT NULL CONSTRAINT t_email_uq UNIQUE,
  amount numeric(10,2) CONSTRAINT t_amount_ck CHECK (amount >= 0),
  parent_id int CONSTRAINT t_parent_fk REFERENCES parent (id) ON DELETE SET NULL
);
ALTER TABLE t ADD CONSTRAINT t_status_ck CHECK (status IN ('a', 'b'));
```

| Item | What it does or returns |
|---|---|
| `PRIMARY KEY` | Unique and not null; identifies the row. |
| `NOT NULL` | Rejects missing values. |
| `UNIQUE` | Rejects duplicates; NULLs are allowed and are not duplicates of each other. |
| `CHECK (expr)` | Rejects a row where the expression is false; NULL passes. |
| `REFERENCES p (k)` | Foreign key: the value must exist in `p.k`. |
| `ON DELETE RESTRICT / CASCADE / SET NULL` | What happens to child rows when the parent is deleted. |
| `ADD CONSTRAINT` | Adds a rule to an existing table after validating existing rows. |
| `information_schema.columns` | Column names, `data_type`, `is_nullable`. |
| `information_schema.table_constraints` | Constraint names and types per table. |

## Learn by example

### Example 1: Check queries find the defects

The two tables have no constraints and several defects: a customer listed twice, an order for an unknown customer (9), a negative amount, a missing customer, an invalid status, a missing amount and a duplicated order id. One report stacks the checks and counts the violations.

```sql run
CREATE TABLE qc_customers (customer_id int, email text);
CREATE TABLE qc_orders (order_id int, customer_id int, amount numeric(10,2), status text);
INSERT INTO qc_customers VALUES (1, 'a@x.com'), (2, 'b@x.com'), (3, 'c@x.com'), (3, 'c@x.com');
INSERT INTO qc_orders VALUES (10, 1, 19.90, 'paid'), (11, 2, 25.00, 'paid'), (12, 9, 12.50, 'refunded'),
  (13, 2, -5.00, 'paid'), (14, NULL, 40.00, 'shipped'), (15, 1, NULL, 'paid'), (15, 1, 8.00, 'paid');

SELECT check_name, violations FROM (
  SELECT 'duplicate customer_id' AS check_name, COUNT(*) AS violations FROM (SELECT customer_id FROM qc_customers GROUP BY customer_id HAVING COUNT(*) > 1) d
  UNION ALL SELECT 'duplicate order_id', COUNT(*) FROM (SELECT order_id FROM qc_orders GROUP BY order_id HAVING COUNT(*) > 1) d
  UNION ALL SELECT 'null customer_id', COUNT(*) FROM qc_orders WHERE customer_id IS NULL
  UNION ALL SELECT 'null amount', COUNT(*) FROM qc_orders WHERE amount IS NULL
  UNION ALL SELECT 'negative amount', COUNT(*) FROM qc_orders WHERE amount < 0
  UNION ALL SELECT 'invalid status', COUNT(*) FROM qc_orders WHERE status NOT IN ('paid', 'refunded', 'failed')
  UNION ALL SELECT 'orphan customer_id', COUNT(*) FROM qc_orders o WHERE o.customer_id IS NOT NULL AND NOT EXISTS (SELECT 1 FROM qc_customers c WHERE c.customer_id = o.customer_id)
) r ORDER BY check_name;
```

```output
check_name | violations
duplicate customer_id | 1
duplicate order_id | 1
invalid status | 1
negative amount | 1
null amount | 1
null customer_id | 1
orphan customer_id | 1
```
### Example 2: Find the orphan rows

The orphan check lists the rows, not only the count, so the data owner can see what to fix. The `LEFT JOIN` with `IS NULL` on the parent key is the anti-join pattern. The order with no customer at all is not an orphan: it has no reference to break, which is a completeness problem, not an integrity problem.

```sql run
CREATE TABLE qc_customers (customer_id int, email text);
CREATE TABLE qc_orders (order_id int, customer_id int, amount numeric(10,2), status text);
INSERT INTO qc_customers VALUES (1, 'a@x.com'), (2, 'b@x.com'), (3, 'c@x.com'), (3, 'c@x.com');
INSERT INTO qc_orders VALUES (10, 1, 19.90, 'paid'), (11, 2, 25.00, 'paid'), (12, 9, 12.50, 'refunded'),
  (13, 2, -5.00, 'paid'), (14, NULL, 40.00, 'shipped'), (15, 1, NULL, 'paid'), (15, 1, 8.00, 'paid');

SELECT o.order_id, o.customer_id
FROM qc_orders o
LEFT JOIN qc_customers c ON c.customer_id = o.customer_id
WHERE o.customer_id IS NOT NULL AND c.customer_id IS NULL
ORDER BY o.order_id;
```

```output
order_id | customer_id
12 | 9
```
### Example 3: Clean, then add constraints, then read them back

The cleanup removes the duplicate customer, quarantines nothing here but fixes the data to be valid, and then the constraints are added. If any row still violated one, `ADD CONSTRAINT` would fail. The final query lists the constraints by their explicit names, with the type and the table.

```sql run
CREATE TABLE qc_customers (customer_id int, email text);
CREATE TABLE qc_orders (order_id int, customer_id int, amount numeric(10,2), status text);
INSERT INTO qc_customers VALUES (1, 'a@x.com'), (2, 'b@x.com'), (3, 'c@x.com'), (3, 'c@x.com');
INSERT INTO qc_orders VALUES (10, 1, 19.90, 'paid'), (11, 2, 25.00, 'paid'), (12, 9, 12.50, 'refunded'),
  (13, 2, -5.00, 'paid'), (14, NULL, 40.00, 'shipped'), (15, 1, NULL, 'paid'), (15, 1, 8.00, 'paid');

DELETE FROM qc_customers WHERE ctid NOT IN (SELECT MIN(ctid) FROM qc_customers GROUP BY customer_id);
DELETE FROM qc_orders WHERE ctid NOT IN (SELECT MIN(ctid) FROM qc_orders GROUP BY order_id);
DELETE FROM qc_orders WHERE amount IS NULL OR amount < 0 OR customer_id IS NULL OR status NOT IN ('paid', 'refunded', 'failed')
   OR customer_id NOT IN (SELECT customer_id FROM qc_customers);
ALTER TABLE qc_customers ADD CONSTRAINT qc_customers_pk PRIMARY KEY (customer_id);
ALTER TABLE qc_orders ADD CONSTRAINT qc_orders_pk PRIMARY KEY (order_id);
ALTER TABLE qc_orders ADD CONSTRAINT qc_orders_amount_ck CHECK (amount >= 0);
ALTER TABLE qc_orders ADD CONSTRAINT qc_orders_status_ck CHECK (status IN ('paid', 'refunded', 'failed'));
ALTER TABLE qc_orders ADD CONSTRAINT qc_orders_cust_fk FOREIGN KEY (customer_id) REFERENCES qc_customers (customer_id);
SELECT table_name, constraint_name, constraint_type
FROM information_schema.table_constraints
WHERE constraint_name ~ '_(pk|ck|fk)$' AND table_name LIKE 'qc\_%'
ORDER BY table_name, constraint_name;
```

```output
table_name | constraint_name | constraint_type
qc_customers | qc_customers_pk | PRIMARY KEY
qc_orders | qc_orders_amount_ck | CHECK
qc_orders | qc_orders_cust_fk | FOREIGN KEY
qc_orders | qc_orders_pk | PRIMARY KEY
qc_orders | qc_orders_status_ck | CHECK
```
### Example 4: Constraints reject bad writes

The rejection is an error, so this example uses `sqlite3` in Python, which supports the same constraint types (foreign keys need `PRAGMA foreign_keys = ON`). Each insert is attempted and the result is printed as accepted or rejected with the kind of constraint that stopped it. SQLite's wording differs from PostgreSQL, so only the first words of the messages are printed.

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("PRAGMA foreign_keys = ON")
conn.executescript("""
CREATE TABLE customers (customer_id INTEGER PRIMARY KEY, email TEXT NOT NULL UNIQUE);
CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER REFERENCES customers (customer_id),
  amount REAL NOT NULL CHECK (amount >= 0), status TEXT NOT NULL CHECK (status IN ('paid', 'refunded', 'failed')));
INSERT INTO customers VALUES (1, 'a@x.com');
""")
attempts = [
    ("good row", "INSERT INTO orders VALUES (1, 1, 19.9, 'paid')"),
    ("duplicate key", "INSERT INTO orders VALUES (1, 1, 5.0, 'paid')"),
    ("negative amount", "INSERT INTO orders VALUES (2, 1, -5.0, 'paid')"),
    ("bad status", "INSERT INTO orders VALUES (3, 1, 5.0, 'shipped')"),
    ("missing amount", "INSERT INTO orders VALUES (4, 1, NULL, 'paid')"),
    ("unknown customer", "INSERT INTO orders VALUES (5, 9, 5.0, 'paid')"),
    ("duplicate email", "INSERT INTO customers VALUES (2, 'a@x.com')"),
]
for name, sql in attempts:
    try:
        conn.execute(sql)
        print(f"{name:18} accepted")
    except sqlite3.IntegrityError as exc:
        print(f"{name:18} rejected: {str(exc).split(':')[0]}")
print("orders stored:", conn.execute("SELECT COUNT(*) FROM orders").fetchone()[0])
```

```output
good row           accepted
duplicate key      rejected: UNIQUE constraint failed
negative amount    rejected: CHECK constraint failed
bad status         rejected: CHECK constraint failed
missing amount     rejected: NOT NULL constraint failed
unknown customer   rejected: FOREIGN KEY constraint failed
duplicate email    rejected: UNIQUE constraint failed
orders stored: 1
```
### Example 5: Foreign key actions

Two child tables reference the same parent but with different `ON DELETE` actions. Deleting customer 1 sets the reference to NULL on the order and deletes the loyalty row with it. The query shows what is left, which tells you the action in each case.

```sql run
CREATE TABLE qc_customers (customer_id int PRIMARY KEY);
CREATE TABLE qc_orders (order_id int PRIMARY KEY, customer_id int REFERENCES qc_customers (customer_id) ON DELETE SET NULL);
CREATE TABLE qc_loyalty (card_id int PRIMARY KEY, customer_id int REFERENCES qc_customers (customer_id) ON DELETE CASCADE);
INSERT INTO qc_customers VALUES (1), (2);
INSERT INTO qc_orders VALUES (10, 1), (11, 2);
INSERT INTO qc_loyalty VALUES (100, 1), (101, 2);
DELETE FROM qc_customers WHERE customer_id = 1;
SELECT 'order ' || order_id AS item, COALESCE(customer_id::text, 'NULL') AS customer FROM qc_orders
UNION ALL
SELECT 'card ' || card_id, customer_id::text FROM qc_loyalty
ORDER BY item;
```

```output
item | customer
card 101 | 2
order 10 | NULL
order 11 | 2
```
### Example 6: Compare the live table with the contract

The catalogue is queried for the columns and nullability of a table and compared with the expectation of the data contract of Day 134 in the same statement: expected columns are listed in a `VALUES` clause and a full join shows missing, extra and differing columns.

```sql run
CREATE TABLE qc_orders (order_id int NOT NULL, amount numeric(10,2) NOT NULL, status text, coupon text);
SELECT COALESCE(e.column_name, a.column_name) AS column_name, e.nullable AS expected_nullable, a.is_nullable AS actual_nullable,
       CASE WHEN a.column_name IS NULL THEN 'missing' WHEN e.column_name IS NULL THEN 'unexpected'
            WHEN e.nullable <> a.is_nullable THEN 'nullability differs' ELSE 'ok' END AS verdict
FROM (VALUES ('order_id', 'NO'), ('amount', 'NO'), ('status', 'NO'), ('customer_id', 'YES')) AS e(column_name, nullable)
FULL JOIN (SELECT column_name, is_nullable FROM information_schema.columns WHERE table_name = 'qc_orders') a ON a.column_name = e.column_name
ORDER BY 1;
```

```output
column_name | expected_nullable | actual_nullable | verdict
amount | NO | NO | ok
coupon | NULL | YES | unexpected
customer_id | YES | NULL | missing
order_id | NO | NO | ok
status | NO | YES | nullability differs
```
## Real-world applications

- **Last line of defence.** A `PRIMARY KEY` and a `CHECK` on the target table make a loader bug fail loudly instead of loading duplicates or negative amounts (Example 4).
- **Post-load reports.** The stacked check query of Example 1 runs after each load in a warehouse that does not enforce foreign keys, and a nonzero count blocks the dashboard refresh.
- **Safe cleanups.** The order in Example 3 (query, fix, then constrain) is how teams add integrity rules to old tables without breaking the load.
- **Contract drift in SQL.** The catalogue comparison of Example 6 spots a column that a source team dropped or loosened before the first consumer notices.

## Daily review

### Key takeaways

- Constraints prevent bad rows on write; check queries detect problems already stored. Use both.
- `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `CHECK`, `FOREIGN KEY` enforce completeness, uniqueness, validity and referential consistency.
- `CHECK` and comparisons treat NULL as unknown: NULL passes a `CHECK` and is not returned by `WHERE amount < 0`; check missing values separately.
- Orphan check: `LEFT JOIN ... WHERE parent.key IS NULL` (excluding NULL references) or `NOT EXISTS`.
- Add constraints after cleaning; `ADD CONSTRAINT` validates all existing rows; read the result from `information_schema`.
- Choose `ON DELETE RESTRICT`, `SET NULL` or `CASCADE` deliberately.

### Common mistakes

- Expecting `CHECK (amount >= 0)` to reject NULL; it accepts it. Add `NOT NULL` where presence is required.
- Counting orphans with a join that also returns rows with a NULL reference. Exclude `customer_id IS NULL` or report it as a completeness issue.
- Using `NOT IN (SELECT ...)` against a subquery that can return NULL, which returns no rows at all. Use `NOT EXISTS`.
- Adding a constraint before cleaning and getting a failure that names a violating row. Run the check query first.
- Using `ON DELETE CASCADE` on data that must be kept, so deleting a parent silently deletes history.
- Relying only on constraints for rules they cannot express, such as totals against a source. Use check queries and reconciliation.

### Revision notes

- Prevent: PK, NOT NULL, UNIQUE, CHECK, FK. Detect: `GROUP BY ... HAVING`, `IS NULL`, `NOT IN`, anti-join.
- NULL passes CHECK; `NOT IN` with NULL is dangerous; use `NOT EXISTS`.
- Clean, then `ALTER TABLE ... ADD CONSTRAINT`.
- `information_schema.columns` and `table_constraints` describe the live table.

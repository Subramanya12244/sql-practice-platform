## Objectives

- Explain how range partitioning splits a fact table, and write the PostgreSQL DDL for monthly partitions of `fact_sales`.
- Show partition pruning: a query that filters on the partition key reads only the matching partition.
- Choose indexes for analytical scans (foreign keys, composite, covering with `INCLUDE`, partial) and say when a full scan is the better plan.
- Use partitions for maintenance: detach or drop an old partition instead of deleting millions of rows.
- Compare, with a deterministic simulation in Python, the rows touched by a full scan, a pruned scan and an index lookup.

## Understand

### Why analytics tables need physical design

A fact table grows without bound: millions of rows a month, years of history. Most analytical queries ask about a slice of it: last month, one quarter, one customer. If the database must read every row to find the slice, query time grows with the whole table. Two techniques let it read less. **Partitioning** splits the table into physical pieces by a key, so that queries on that key skip most pieces. **Indexes** are separate sorted structures that locate rows without scanning. Both trade extra storage and maintenance for faster reads, and neither is free: the art is to apply them where the queries are.

### Range partitioning

A **partitioned table** is a logical table made of several **partitions**, each a real table that holds a range of the **partition key**. PostgreSQL's declarative syntax creates the parent with `PARTITION BY RANGE (date_key)` and each child with `PARTITION OF parent FOR VALUES FROM (a) TO (b)`; the range is **inclusive at the start and exclusive at the end**, so month partitions chain without gaps or overlaps. Rows inserted into the parent are routed to the right partition automatically; a row whose key matches no partition is rejected, which is why a load needs a partition for the new month before the month starts (or a `DEFAULT` partition for strays). For a date-ordered fact table the natural key is the date, and month is the usual size: small enough to drop and rebuild, large enough that there are not thousands of partitions.

A restriction to know: a primary key or unique constraint on a partitioned table must include the partition key, because uniqueness is enforced inside each partition. Our example uses `PRIMARY KEY (sale_id, date_key)`.

### Partition pruning

**Pruning** is the planner's decision to leave out partitions that cannot contain matching rows. A query `WHERE date_key >= 20260201 AND date_key < 20260301` can only match the February partition, so the plan scans one partition. A query that does not filter on the key (`WHERE customer_key = 3`) must scan all of them. `EXPLAIN (COSTS OFF)` prints the plan without cost estimates, and the list of partitions in it shows what is scanned; the exact wording of a plan can differ between PostgreSQL versions, so read it for the principle and do not copy it into code. Pruning only works when the filter is on the partition key in a form the planner can compare with the bounds: a filter on `to_char(...)` of the key or on a different column does not prune. This is why a date dimension key such as `20260201` that is itself the partition key is convenient: the filter `date_key BETWEEN ...` prunes.

### Indexes for scans

An **index** is a sorted structure (by default a B-tree) over one or more columns that points to table rows. Which indexes pay off in a warehouse differs from an application:

- **Foreign key columns** of the fact table (`customer_key`, `product_key`) are indexed when queries pick a few rows through a dimension attribute, such as the sales of one customer. PostgreSQL does not create these automatically.
- A **composite index** on `(customer_key, date_key)` serves a filter on customer and a range of dates, and the order of columns matters: the leading column is the one it can search by itself.
- A **covering index** adds payload columns with `INCLUDE (amount_cents)` so that a query can be answered from the index alone, without visiting the table.
- A **partial index** covers only the rows that a frequent query selects (`WHERE is_current`), keeping it small.
- For a very large table whose rows are naturally ordered by date, a **BRIN** index (block range index) is tiny and cheap to maintain and good at date range filters; it mentions only the minimum and maximum of each block of rows.

An index does not help when a query reads a large share of the table. Asking for 40 percent of the rows by index means jumping around the table 40 percent of the time, which is slower than reading it straight through; the planner then chooses a **sequential scan** correctly. Analytical queries that aggregate large slices usually scan, and benefit from partitioning and from reading fewer columns more than from indexes. Each index also slows inserts and takes space, so a warehouse keeps only the indexes that its real queries use.

### Maintenance

Partitions make life cycle work cheap. **Retention**: `ALTER TABLE parent DETACH PARTITION old` makes the old month an ordinary table, which can be archived or dropped instantly; deleting the same rows with `DELETE` would write millions of row versions and leave the table bloated. **Loading**: a new partition can be filled as a separate table and then attached with `ATTACH PARTITION`. Routine maintenance, written here for reference and not run in the examples, includes `ANALYZE` (refresh the planner's statistics after large loads, so that it knows the row counts), `VACUUM` (reclaim dead rows left by updates and deletes) and `REINDEX` (rebuild a bloated index). Run `ANALYZE` after every big load: the planner's choices depend on the statistics it holds.

### Common misconception

Learners add an index to every column "to make it fast". Indexes slow loads, take space and are ignored for large scans. Another belief is that partitioning speeds up every query. It speeds up queries that filter on the partition key and can slow down others slightly, because the planner handles several tables.

### Why it matters

At warehouse scale, the difference between reading one month and reading ten years is the difference between a dashboard that refreshes in seconds and one that does not. The decision is made when the table is created and is expensive to change.

## Syntax and key functions

```sql-syntax
CREATE TABLE fact_sales_p (
    sale_id integer NOT NULL, date_key integer NOT NULL, customer_key integer NOT NULL,
    product_key integer NOT NULL, quantity integer NOT NULL, amount_cents integer NOT NULL,
    PRIMARY KEY (sale_id, date_key)
) PARTITION BY RANGE (date_key);

CREATE TABLE fact_sales_2026_01 PARTITION OF fact_sales_p FOR VALUES FROM (20260101) TO (20260201);

CREATE INDEX ix_customer ON fact_sales_p (customer_key);
CREATE INDEX ix_cover    ON fact_sales_p (product_key) INCLUDE (amount_cents);

ALTER TABLE fact_sales_p DETACH PARTITION fact_sales_2026_01;
```

Maintenance commands (reference; not run in the examples):

```sql-syntax
ANALYZE fact_sales_p;          -- refresh statistics after a large load
VACUUM fact_sales_p;           -- reclaim space from dead rows
REINDEX TABLE fact_sales_p;    -- rebuild indexes
```

| Item | Meaning |
|---|---|
| `PARTITION BY RANGE (key)` | Split by value ranges of the key. |
| `FOR VALUES FROM (a) TO (b)` | Inclusive start, exclusive end. |
| Pruning | Planner skips partitions that cannot match the filter. |
| `EXPLAIN (COSTS OFF)` | Plan structure without cost numbers. |
| `INCLUDE (cols)` | Covering index payload. |
| Partial index (`WHERE cond`) | Index over selected rows only. |
| BRIN | Block-range index for naturally ordered data. |
| `DETACH PARTITION` | Turn a partition into a standalone table (retention). |
| `ANALYZE`, `VACUUM`, `REINDEX` | Statistics, space reclamation, index rebuild. |

## Learn by example

### Example 1: Monthly partitions and where the rows went

`fact_sales_p` is partitioned by `date_key`, with a partition for January and one for February 2026. The 60 sample sales are copied into the parent and routed automatically. `tableoid::regclass` shows the partition of each row; the query counts and sums per partition.

```sql run
CREATE TABLE dim_date (date_key integer PRIMARY KEY, full_date date NOT NULL, year integer NOT NULL, month integer NOT NULL);
CREATE TABLE dim_customer (customer_key integer PRIMARY KEY, customer_id text NOT NULL, customer_name text NOT NULL, country text NOT NULL,
    valid_from date NOT NULL, valid_to date, is_current boolean NOT NULL);
CREATE TABLE dim_product (product_key integer PRIMARY KEY, product_id text NOT NULL, product_name text NOT NULL, category text NOT NULL);
CREATE TABLE fact_sales (sale_id integer PRIMARY KEY, date_key integer NOT NULL REFERENCES dim_date, customer_key integer NOT NULL REFERENCES dim_customer,
    product_key integer NOT NULL REFERENCES dim_product, quantity integer NOT NULL, amount_cents integer NOT NULL);
INSERT INTO dim_date SELECT to_char(d, 'YYYYMMDD')::int, d::date, extract(year FROM d)::int, extract(month FROM d)::int
FROM generate_series(date '2026-01-01', date '2026-02-28', interval '1 day') AS d;
INSERT INTO dim_customer SELECT i, 'C' || lpad(i::text, 3, '0'), 'Customer ' || lpad(i::text, 2, '0'),
    (ARRAY['PT', 'ES', 'FR', 'DE'])[i % 4 + 1], date '2026-01-01', NULL, true FROM generate_series(1, 12) AS i;
INSERT INTO dim_product SELECT i, 'P' || lpad(i::text, 3, '0'), 'Product ' || i,
    (ARRAY['Stationery', 'Books', 'Tools', 'Toys'])[i % 4 + 1] FROM generate_series(1, 8) AS i;
INSERT INTO fact_sales SELECT i, to_char(date '2026-01-01' + i * 3 % 59, 'YYYYMMDD')::int, i * 5 % 12 + 1, i * 3 % 8 + 1, i % 4 + 1,
    (i % 4 + 1) * (500 + (i * 3 % 8 + 1) * 250) FROM generate_series(1, 60) AS i;
CREATE TABLE fact_sales_p (
    sale_id integer NOT NULL, date_key integer NOT NULL, customer_key integer NOT NULL, product_key integer NOT NULL,
    quantity integer NOT NULL, amount_cents integer NOT NULL,
    PRIMARY KEY (sale_id, date_key)
) PARTITION BY RANGE (date_key);
CREATE TABLE fact_sales_2026_01 PARTITION OF fact_sales_p FOR VALUES FROM (20260101) TO (20260201);
CREATE TABLE fact_sales_2026_02 PARTITION OF fact_sales_p FOR VALUES FROM (20260201) TO (20260301);
INSERT INTO fact_sales_p SELECT * FROM fact_sales;
SELECT tableoid::regclass::text AS part, count(*) AS rows, sum(amount_cents) AS cents
FROM fact_sales_p GROUP BY 1 ORDER BY 1;
```

```output
part | rows | cents
fact_sales_2026_01 | 32 | 125000
fact_sales_2026_02 | 28 | 121500
```

### Example 5: Rows touched by a scan, a pruned scan and an index (simulation)

A deterministic table of 120,000 rows covers 24 months with 5,000 rows each. The code counts the rows that three strategies must look at for the question "total of month 13": a full scan reads every row; a partitioned layout (rows grouped by month in a dictionary) reads only that month's partition; and a month-ordered index with `bisect` finds the first and last row positions and reads only the matching rows, plus a few comparisons. The counts, not timings, make the point.

```python run
from bisect import bisect_left, bisect_right

rows = [(m, i) for m in range(1, 25) for i in range(5000)]       # (month, value), ordered by month
target = 13

full_scan = sum(1 for _ in rows)
total_full = sum(v for m, v in rows if m == target)

partitions = {}
for m, v in rows:
    partitions.setdefault(m, []).append(v)
pruned_rows = len(partitions[target])
total_pruned = sum(partitions[target])

months = [m for m, _ in rows]
lo, hi = bisect_left(months, target), bisect_right(months, target)
index_rows = hi - lo
total_index = sum(v for _, v in rows[lo:hi])

print(full_scan, pruned_rows, index_rows)
print(total_full == total_pruned == total_index, total_full)
print(round(full_scan / pruned_rows))
```

```output
120000 5000 5000
True 12497500
24
```

All three strategies give the same answer. The full scan reads 24 times as many rows as the other two; for a query that needs one month of two years, pruning cuts the work to a twenty-fourth.

## Real-world applications

- **Monthly fact tables.** A sales fact partitioned by month makes "this month" and "last month" dashboards read one or two partitions out of dozens.
- **Retention policies.** Keeping 36 months of detail means detaching the 37th partition each month: instant and without table bloat.
- **Targeted indexes.** Customer-service lookups ("all sales of customer 4081") use an index on the customer key, while monthly revenue reports use pruning and scans.
- **After every large load.** `ANALYZE` refreshes the statistics so that the planner prunes and chooses scans correctly.

## Daily review

### Key takeaways

- Partition large facts by the key that queries filter on (usually date); ranges are inclusive at the start, exclusive at the end.
- Pruning works only for filters on the partition key; read `EXPLAIN (COSTS OFF)` for the partitions listed.
- Index foreign keys used in selective lookups; use composite, covering and partial indexes where queries need them; large scans do not use indexes.
- Detach or drop old partitions for retention; run `ANALYZE` after large loads.
- Every index costs space and load time.

### Common mistakes

- **A primary key without the partition key.** PostgreSQL rejects it. Include the key in the constraint.
- **No partition for new data.** Inserts fail when a new month starts. Create partitions ahead or add a `DEFAULT` partition.
- **Filtering on an expression of the key.** Pruning does not happen. Filter on the key itself.
- **Indexing every column.** Loads slow down and the planner ignores most indexes. Index what queries use.
- **Expecting an index to speed up a 40 percent scan.** A sequential scan is faster there.

### Revision notes

- `PARTITION BY RANGE`, `PARTITION OF ... FOR VALUES FROM (a) TO (b)`.
- Pruning on the key; `EXPLAIN (COSTS OFF)`.
- `INCLUDE`, partial index, BRIN; plain B-tree for FK lookups.
- `DETACH PARTITION`; `ANALYZE`, `VACUUM`, `REINDEX`.

## Understand

### What batch processing is

A **batch** is a bounded group of records processed together. **Batch processing** means that the pipeline collects data over a period (an hour, a day) and processes it in one run, in contrast to **streaming**, where each record is handled as it arrives. A nightly job that loads yesterday's orders is batch processing. It is simple, predictable and cheap: the job starts, does its work, reports and stops, and everything is measured by a run. Most data engineering pipelines are batch jobs, and the word is used at two levels: the **run** (all of yesterday's data) and the **batch inside the run** (the next 1,000 rows sent to the database). Today covers both: how to size the batches inside a run, how to cut a period into windows, and how runs are scheduled.

### Why process in batches inside a run

Loading a million rows one at a time sends a million statements to the database, and each statement costs a round trip: the request, the database's work and the reply. Sending all million at once avoids the round trips but must hold every row in memory, makes one giant transaction and gives you nothing to show for the first hour. A **batch size** between the two extremes keeps memory bounded (one batch at a time), cuts the number of round trips by the batch size (1,000,000 rows at 1,000 per batch is 1,000 round trips), and gives natural points to commit, log progress and resume. The helper that cuts an iterable into lists of at most `n` items is a small generator, and it works on a list, a file or a database cursor alike, because it only asks for the next item.

### Choosing a batch size

Three forces pull in different directions. **Round trips** favour large batches: the overhead per statement is paid once per batch. **Memory** favours small batches: a batch must fit comfortably in RAM, for the pipeline and for the database server's buffers. **Failure cost** favours small batches too: if a batch fails (a constraint violation, a timeout), the work of that batch is redone, and a bad row in a batch of 100,000 spoils a lot of good ones. Typical practice is a few hundred to a few thousand rows per batch, measured on your own system, not guessed: throughput usually rises quickly as batches grow, then flattens, and the right choice is where the curve flattens and memory is still safe. The batch size is a setting (Day 122), not a constant in code, so that it can be tuned without a deploy.

### Throughput

**Throughput** is how much work is done per unit of time, here rows per second. It depends on the batch size, the network, the database and the per-row work. Measuring it needs a clock, and clocks are noisy, so tests do not assert timings; they assert counts that explain the timing, such as the number of batches and round trips. In the examples today a simple cost model (a fixed overhead per round trip plus a cost per row) stands in for a clock and shows why throughput flattens.

### Windows

A **window** is the slice of data a run is responsible for, usually a time range such as one day or one hour. Windows must be **half-open**: include the start, exclude the end (`start <= t < end`). Then consecutive windows share a boundary without overlap and without a gap: a row stamped exactly midnight belongs to exactly one day. The common error is a closed interval (`BETWEEN start AND end`) on both sides, which counts the midnight row twice, once in each neighbouring window. Windows also make reruns clean: rerunning the window for 5 March reads the same rows and, with the idempotent load of Day 124, writes the same result.

### Scheduling

A **schedule** says when runs start. The classic format is the **cron expression** with five fields: minute, hour, day of month, month, day of week. `0 2 * * *` means minute 0 of hour 2 on every day, so 02:00 daily. A scheduler (cron on a server, or a workflow orchestrator) starts the job; the job itself should not contain the schedule. A schedule must leave room for the data to be complete: a job at 00:05 for "yesterday" can miss orders that arrive late, so jobs often run a few hours after the window closes and the pipeline stores the window it processed. Runs must also not overlap: a job that takes 90 minutes on an hourly schedule starts a second copy while the first is running, so the job needs a guard or the schedule a longer interval.

### Why it matters in data work

Batch size and windows decide whether a pipeline finishes in ten minutes or ten hours, whether it survives a bad row and whether it can be rerun for one day. They are cheap to get right at the start and expensive to retrofit.

## Syntax and key functions

```python
from itertools import islice

def batches(iterable, size):
    it = iter(iterable)
    while chunk := list(islice(it, size)):
        yield chunk

for batch in batches(rows, 1000):
    conn.executemany("INSERT INTO orders_clean VALUES (?,?,?,?,?,?)", batch)
    conn.commit()
```

```text
# minute  hour  day-of-month  month  day-of-week
  0       2     *             *      *            # 02:00 every day
  */15    *     *             *      *            # every 15 minutes
  30      6     *             *      1            # 06:30 on Mondays
```

| Item | What it does or returns |
|---|---|
| `islice(it, n)` | The next n items of an iterator (fewer at the end). |
| `while chunk := list(islice(...))` | Loops until a batch comes back empty. |
| `executemany(sql, batch)` | One statement for many rows. |
| `conn.commit()` | Makes the batch's changes permanent. |
| `start <= t < end` | A half-open window: no overlap, no gap. |
| cron `0 2 * * *` | Five fields: minute, hour, day of month, month, day of week. |

## Learn by example

### Example 1: A batching helper

The generator yields lists of at most four rows. Ten rows give three batches, the last one partial. Only one batch is held at a time, and the helper works on a list, a range and a generator alike.

```python run
from itertools import islice

def batches(iterable, size):
    it = iter(iterable)
    while chunk := list(islice(it, size)):
        yield chunk

sizes = [len(b) for b in batches(range(10), 4)]
print(sizes)
print(list(batches("abcde", 2)))
print(sum(1 for _ in batches((i for i in range(1000)), 250)), "batches of a generator")
```

```output
[4, 4, 2]
[['a', 'b'], ['c', 'd'], ['e']]
4 batches of a generator
```
### Example 2: Round trips by batch size

A counter records the calls to `executemany` while loading 5,000 rows into `sqlite3` with three batch sizes. Every call stands for one round trip to a server. The row count is always the same; the number of calls is what changes.

```python run
import sqlite3
from itertools import islice

def batches(iterable, size):
    it = iter(iterable)
    while chunk := list(islice(it, size)):
        yield chunk

def load(rows, size):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, amount_cents INTEGER)")
    calls = 0
    for batch in batches(rows, size):
        conn.executemany("INSERT INTO orders_clean VALUES (?, ?)", batch)
        conn.commit()
        calls += 1
    return calls, conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0]

rows = [(i, 500 + i % 89 * 50) for i in range(1, 5001)]
for size in (1, 100, 1000):
    calls, loaded = load(rows, size)
    print(f"batch size {size}: {calls} round trips, {loaded} rows loaded")
```

```output
batch size 1: 5000 round trips, 5000 rows loaded
batch size 100: 50 round trips, 5000 rows loaded
batch size 1000: 5 round trips, 5000 rows loaded
```
### Example 3: Why throughput flattens

A cost model replaces the clock: each round trip costs 5 ms of overhead plus 0.02 ms per row. Rows per second climb quickly and then flatten, and memory per batch keeps growing, which is why the choice is the knee of the curve, not the maximum.

```python run
OVERHEAD_MS = 5.0
PER_ROW_MS = 0.02
TOTAL = 100_000

for size in (10, 100, 1000, 10_000, 100_000):
    trips = -(-TOTAL // size)
    total_ms = trips * OVERHEAD_MS + TOTAL * PER_ROW_MS
    print(f"{size:>7} rows/batch  {trips:>6} trips  {TOTAL / (total_ms / 1000):>9,.0f} rows/s")
```

```output
     10 rows/batch   10000 trips      1,923 rows/s
    100 rows/batch    1000 trips     14,286 rows/s
   1000 rows/batch     100 trips     40,000 rows/s
  10000 rows/batch      10 trips     48,780 rows/s
 100000 rows/batch       1 trips     49,875 rows/s
```
### Example 4: Half-open windows

The period of three days is cut into daily windows with `start <= t < end`. Rows are assigned to windows by the same rule, and the counts of the windows add up to the total, with a row stamped exactly midnight counted once. A closed interval would count it twice.

```python run
from datetime import datetime, timedelta

def windows(start, end, step):
    current = start
    while current < end:
        yield current, min(current + step, end)
        current += step

start = datetime(2025, 3, 1)
end = datetime(2025, 3, 4)
stamps = [datetime(2025, 3, 1, 10), datetime(2025, 3, 2, 0), datetime(2025, 3, 2, 9), datetime(2025, 3, 3, 23, 59), datetime(2025, 3, 2, 0)]
counts = []
for lo, hi in windows(start, end, timedelta(days=1)):
    n = sum(1 for t in stamps if lo <= t < hi)
    counts.append(n)
    print(lo.date(), n)
print("sum of windows:", sum(counts), "total rows:", len(stamps))
closed = sum(1 for lo, hi in windows(start, end, timedelta(days=1)) for t in stamps if lo <= t <= hi)
print("closed intervals count:", closed)
```

```output
2025-03-01 1
2025-03-02 3
2025-03-03 1
sum of windows: 5 total rows: 5
closed intervals count: 7
```
### Example 5: A batch run with progress, windows and a result

The run processes one window of orders in batches of 4. After each batch it commits and records progress, and the final result reports the window, the batches and the loaded count. A failure in one batch would leave earlier batches committed and the window re-runnable.

```python run
import sqlite3
from datetime import datetime, timedelta
from itertools import islice

def batches(iterable, size):
    it = iter(iterable)
    while chunk := list(islice(it, size)):
        yield chunk

source = [(i, f"2025-03-0{1 + i % 3}T{i % 24:02d}:00:00Z", 100 * i) for i in range(1, 20)]
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_clean (order_id INTEGER PRIMARY KEY, created_at TEXT, amount_cents INTEGER)")

def run_window(lo, hi, batch_size):
    rows = [r for r in source if lo.strftime("%Y-%m-%dT%H:%M:%SZ") <= r[1] < hi.strftime("%Y-%m-%dT%H:%M:%SZ")]
    done = 0
    for n, batch in enumerate(batches(rows, batch_size), start=1):
        conn.executemany("INSERT OR REPLACE INTO orders_clean VALUES (?, ?, ?)", batch)
        conn.commit()
        done += len(batch)
    return {"window": lo.strftime("%Y-%m-%d"), "read": len(rows), "batches": n if rows else 0, "loaded": done}

lo = datetime(2025, 3, 2)
print(run_window(lo, lo + timedelta(days=1), 4))
print(run_window(lo, lo + timedelta(days=1), 4))
print("in table:", conn.execute("SELECT COUNT(*) FROM orders_clean").fetchone()[0])
```

```output
{'window': '2025-03-02', 'read': 7, 'batches': 2, 'loaded': 7}
{'window': '2025-03-02', 'read': 7, 'batches': 2, 'loaded': 7}
in table: 7
```
## Real-world applications

- **Large loads.** A nightly load of millions of rows uses batches of a few thousand with a commit after each, so memory stays flat and a failure costs one batch, not the whole run (Examples 2 and 5).
- **Tuning.** An engineer who needs a load to be faster picks batch size from measurements, as in the cost model of Example 3, and changes the setting without touching code.
- **Daily and hourly windows.** Half-open windows (Example 4) let reports and backfills agree on which rows belong to which day, even for a row stamped at midnight.
- **Scheduled jobs.** A cron line starts the job at 02:00 for the previous day's window, leaving time for late data, and the stored window makes a rerun safe.

## Daily review

### Key takeaways

- Batch processing handles bounded groups of records per run; inside a run, batches bound memory and round trips.
- Batch size trades round trips against memory and the cost of a failed batch; measure it and make it a setting.
- Throughput flattens as batches grow, so the best size is the knee of the curve.
- Use half-open windows `start <= t < end` to avoid gaps and double counting.
- A schedule starts runs; leave time for data to arrive and prevent overlapping runs.

### Common mistakes

- Loading row by row with a commit each time, which makes a large load take hours. Use `executemany` in batches.
- Reading everything into a list before batching, which defeats the memory limit. Batch from a generator or cursor.
- Using `BETWEEN start AND end` for windows, so a row at the boundary is counted in two windows. Use `>= start AND < end`.
- A batch size hard-coded at 100,000 that exhausts memory on a smaller worker. Make it a setting and test it.
- Scheduling an hourly job that sometimes takes longer than an hour, so two runs write at once. Add a guard or lengthen the interval.

### Revision notes

- `batches(iterable, n)` with `islice`; commit per batch; log progress.
- Round trips = rows / batch size; memory = one batch.
- Window: `start <= t < end`; consecutive windows tile the period.
- Cron: minute hour day-of-month month day-of-week.

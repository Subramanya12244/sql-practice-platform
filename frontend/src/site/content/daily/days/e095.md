## Objectives

- Build a small CSV-to-database pipeline from the earlier days: chunked read, validation, staging and a typed load.
- Prove a load is complete by reconciling counts: rows read equal rows loaded plus rows rejected.
- Compare aggregate checksums (a sum and a hash of the rows) between the file and the table, and explain why a hash catches errors a sum cannot.
- Write SQL validation queries that count duplicates, missing values, out-of-range values and orphan keys.
- Assemble the checks into one repeatable report that passes on a good load and names the failing check on a corrupted one.

## Understand

### A load that does not fail can still be wrong

Days 91 to 94 gave you the parts of a loader: connections, a designed target, chunked validation and repeatable writes. A load that runs without raising an error is not proof that the table holds the file. A chunk can be skipped by a bug, a cast can round a value, a join in a later step can drop rows, and a retry can double some of them. **Validating a load** means comparing what arrived in the target with what the source contained, using checks written independently of the loading code, so that a mistake in the loader cannot hide itself. This is the data engineer's version of a test: if you cannot show the check passing, you do not know that the data is right.

### Layer one: counts

The cheapest and most important check is the **reconciliation equation**: rows read from the file equal rows loaded plus rows rejected. The three numbers come from different places: rows read from your chunk loop, rows rejected from the reject list, and rows loaded from `SELECT COUNT(*)` on the target table, never from a counter in the loader. If the equation fails, rows were lost or invented, and nothing else is worth checking until it holds. Counts do not prove the values are right, only that no row went missing.

### Layer two: aggregates and checksums

A **checksum** is a small value computed from data so that two copies can be compared without reading every row. The simplest is a **control total**: the sum of a numeric column, computed from the good rows in the file and from the target table. Money should be summed exactly, with `decimal.Decimal` in Python and `numeric` in PostgreSQL, because floating-point sums differ in the last digits. A sum has a weakness: two amounts swapped between orders leave the sum unchanged. A **row hash** closes the gap. Write each row as text (`1001|19.90`), join the rows in key order and compute a digest such as MD5 over the whole text. Any changed, swapped, missing or added row changes the digest. A hash cannot say which row is wrong, so it is used as a pass or fail signal; on a mismatch you narrow down by comparing counts and sums per key range or per group. For the comparison to work both sides must format values identically, for example always two decimals.

### Layer three: validation queries in SQL

The third layer asks questions of the loaded data that should always have the answer zero. **Validation queries** each return the number of rows that break a rule: duplicate business keys (`GROUP BY key HAVING COUNT(*) > 1`), missing required values (`IS NULL`), values outside a legal range or date window (`NOT BETWEEN`), and **orphans**, child rows whose key has no parent row (a `LEFT JOIN` to the parent filtered with `IS NULL`, the anti-join of Day 41). Stacking them with `UNION ALL` gives one small report. When the table has constraints from Day 92 many of these can never fail; they are still worth running on tables that were loaded with `to_sql`, on tables you inherit, and as protection against someone loosening a constraint later.

### The shape of the project

The project has five steps, each of which you build and run. First, create the source: CSV text with known problems. Second, run the pipeline: read in chunks, validate, load the good rows and keep the rejects. Third, reconcile the counts. Fourth, compare the checksums. Fifth, run the SQL validation queries and assemble everything into one report with a pass or fail per check. To prove the report works, you corrupt the table on purpose and watch the right check fail. A final test of a good pipeline is to run the load twice (Day 94) and see the same report.

### Common misconception

Learners assume that a count match is enough. It is not: replacing one row's amount keeps the count, and swapping two amounts keeps the count and the sum. Each layer catches what the one before it cannot.

### Why it matters

Reports are built on loaded tables, and a silent loss of three percent of the rows changes a revenue figure that finance may act on. A pipeline that ends with a passing, written reconciliation can be trusted and handed over; one that ends with "no errors" cannot.

## Syntax and key functions

Reconciliation and control totals in Python:

```python
from decimal import Decimal

read == loaded + rejected
sum(Decimal(a) for a in good_amounts) == Decimal(str(table_total))
```

A row hash in Python and the equivalent in PostgreSQL:

```python
import hashlib

text = ",".join(f"{order_id}|{amount}" for order_id, amount in sorted(rows))
digest = hashlib.md5(text.encode()).hexdigest()
```

```sql-syntax
SELECT md5(string_agg(order_id::text || '|' || amount::text, ',' ORDER BY order_id))
FROM orders_loaded;
```

A validation report from stacked queries:

```sql-syntax
SELECT 'check name' AS check_name, count(*) AS violations FROM table WHERE <rule is broken>
UNION ALL
SELECT 'another check', count(*) FROM table WHERE <rule is broken>
ORDER BY check_name;
```

| Item | What it does or returns |
|---|---|
| `read == loaded + rejected` | The reconciliation equation; all three counts from independent sources. |
| `Decimal("19.90")` | Exact decimal; sum without floating-point noise. |
| `hashlib.md5(bytes).hexdigest()` | A 32-character digest of the bytes. |
| `md5(text)` (PostgreSQL) | The same digest of a text value, as hex text. |
| `string_agg(expr, sep ORDER BY key)` | Joins values into one text in a stated order. |
| `GROUP BY key HAVING count(*) > 1` | Lists duplicated keys. |
| `LEFT JOIN ... WHERE parent.key IS NULL` | Finds orphan rows. |
| `UNION ALL` of `count(*)` queries | One report row per validation rule. |

## Learn by example

### Example 1: Step 1 and 2, the pipeline

The CSV has 14 data rows with seven deliberate problems: a bad id, an unknown customer, an impossible date, a negative amount, a duplicate, a missing amount and a bad status. The pipeline reads in chunks of 5 as raw text, gives each row its first failing reason, and loads the good rows into a constrained table with `executemany` in one transaction. `sqlite3` has no exact decimal type, so the stand-in stores the amount as whole cents in an integer column; in PostgreSQL you would use `numeric(12,2)`. The function returns the statistics that later steps use.

```python run
import io
import sqlite3
from decimal import Decimal
import pandas as pd

CSV = """order_id,customer_id,order_date,amount,status
1001,1,2026-01-05,19.90,paid
1002,2,2026-01-06,25.00,paid
1003,1,2026-01-06,12.50,new
1004,3,2026-01-07,40.00,shipped
abc,2,2026-01-07,9.99,paid
1006,9,2026-01-08,15.00,paid
1007,2,2026-02-30,22.00,paid
1008,3,2026-01-09,-5.00,paid
1009,1,2026-01-09,31.25,cancelled
1010,2,2026-01-10,8.40,paid
1004,3,2026-01-07,40.00,shipped
1012,3,2026-01-11,,paid
1013,1,2026-01-12,17.80,paid
1014,2,2026-01-12,6.00,pending
"""

def run_pipeline(text, conn, chunksize=5):
    conn.execute("CREATE TABLE customer (customer_id INTEGER PRIMARY KEY)")
    conn.executemany("INSERT INTO customer VALUES (?)", [(1,), (2,), (3,)])
    conn.execute("""CREATE TABLE orders_loaded (
        order_id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL REFERENCES customer,
        order_date TEXT NOT NULL, amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0), status TEXT NOT NULL)""")
    known = {"1", "2", "3"}
    seen, read, rejects, good_rows = set(), 0, [], []
    for chunk in pd.read_csv(io.StringIO(text), chunksize=chunksize, dtype=str, keep_default_na=False):
        amount = pd.to_numeric(chunk["amount"], errors="coerce")
        day = pd.to_datetime(chunk["order_date"], format="%Y-%m-%d", errors="coerce")
        rules = [
            ("bad order_id", ~chunk["order_id"].str.fullmatch(r"[0-9]+")),
            ("unknown customer", ~chunk["customer_id"].isin(known)),
            ("bad date", day.isna()),
            ("bad amount", amount.isna() | (amount < 0)),
            ("bad status", ~chunk["status"].isin(["new", "paid", "shipped", "cancelled"])),
            ("duplicate order_id", chunk["order_id"].isin(seen) | chunk["order_id"].duplicated()),
        ]
        reason = pd.Series("", index=chunk.index)
        for label, failed in rules:
            reason = reason.mask((reason == "") & failed, label)
        ok = chunk[reason == ""]
        seen.update(ok["order_id"])
        read += len(chunk)
        rejects += [(int(i) + 2, why) for i, why in reason[reason != ""].items()]
        good_rows += [(int(r.order_id), int(r.customer_id), r.order_date, int(Decimal(r.amount) * 100), r.status) for r in ok.itertuples()]
    with conn:
        conn.executemany("INSERT INTO orders_loaded VALUES (?, ?, ?, ?, ?)", good_rows)
    return {"read": read, "rejected": len(rejects), "reasons": rejects,
            "file_total": sum(Decimal(r[3]) for r in good_rows) / 100}

conn = sqlite3.connect(":memory:")
stats = run_pipeline(CSV, conn)
print("read:", stats["read"], "rejected:", stats["rejected"])
print("loaded:", conn.execute("SELECT COUNT(*) FROM orders_loaded").fetchone()[0])
print("file total of good rows:", stats["file_total"])
for line, why in stats["reasons"]:
    print(f"  line {line}: {why}")
```

```output
read: 14 rejected: 7
loaded: 7
file total of good rows: 154.85
  line 6: bad order_id
  line 7: unknown customer
  line 8: bad date
  line 9: bad amount
  line 12: duplicate order_id
  line 13: bad amount
  line 15: bad status
```

### Example 2: Step 3, reconcile the counts

The three numbers come from different sources: the chunk loop, the reject list and a `COUNT(*)` on the table. The check prints `PASS` or `FAIL` with the numbers, so a failure explains itself. The second call simulates a load that lost a row between the file and the table.

```python run
def reconcile(read, loaded, rejected):
    status = "PASS" if read == loaded + rejected else "FAIL"
    return f"{status}: read {read} = loaded {loaded} + rejected {rejected} ({loaded + rejected})"

print(reconcile(14, 7, 7))
print(reconcile(14, 6, 7))
```

```output
PASS: read 14 = loaded 7 + rejected 7 (14)
FAIL: read 14 = loaded 6 + rejected 7 (13)
```

### Example 3: Step 4, sum and hash checksums

The file side is the seven good rows from Example 1 as exact text; the table side is read back from a `sqlite3` table in cents. The sum and the hash both match on the intact table. Then two amounts are swapped between two orders: the count and the sum are unchanged, so those checks still pass, but the hash changes and exposes the damage.

```python run
import hashlib
import sqlite3
from decimal import Decimal

file_rows = [(1001, "19.90"), (1002, "25.00"), (1003, "12.50"), (1004, "40.00"), (1009, "31.25"), (1010, "8.40"), (1013, "17.80")]

def digest(rows):
    text = ",".join(f"{i}|{a}" for i, a in sorted(rows))
    return hashlib.md5(text.encode()).hexdigest()

def table_rows(conn):
    return [(i, f"{Decimal(c) / 100:.2f}") for i, c in conn.execute("SELECT order_id, amount_cents FROM orders_loaded")]

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders_loaded (order_id INTEGER PRIMARY KEY, amount_cents INTEGER)")
conn.executemany("INSERT INTO orders_loaded VALUES (?, ?)", [(i, int(Decimal(a) * 100)) for i, a in file_rows])

def compare(label, conn):
    rows = table_rows(conn)
    count_ok = len(rows) == len(file_rows)
    sum_ok = sum(Decimal(a) for _, a in rows) == sum(Decimal(a) for _, a in file_rows)
    hash_ok = digest(rows) == digest(file_rows)
    print(label, "count", count_ok, "sum", sum_ok, "hash", hash_ok)

compare("intact:", conn)
with conn:
    conn.execute("UPDATE orders_loaded SET amount_cents = CASE order_id WHEN 1001 THEN 2500 WHEN 1002 THEN 1990 END WHERE order_id IN (1001, 1002)")
compare("swapped:", conn)
```

```output
intact: count True sum True hash True
swapped: count True sum True hash False
```

### Example 4: Step 4 continued, the same hash in PostgreSQL

The digest can be computed on the database side so that no rows have to leave the server. This Python block prints the hash of the three rows, and the SQL block that follows computes `md5` over the same text on PGlite; the two printed values are the same, because both sides write each row as `id|amount` with two decimals and join them in key order.

```python run
import hashlib

rows = [(1001, "19.90"), (1002, "25.00"), (1003, "12.50")]
print(hashlib.md5(",".join(f"{i}|{a}" for i, a in rows).encode()).hexdigest())
```

```output
29ce32b62ddbf37dd30dffca0d205750
```

```sql run
CREATE TABLE orders_loaded (order_id bigint PRIMARY KEY, amount numeric(12,2));
INSERT INTO orders_loaded VALUES (1003, 12.50), (1001, 19.90), (1002, 25);
SELECT md5(string_agg(order_id::text || '|' || amount::text, ',' ORDER BY order_id)) AS row_hash,
       count(*) AS row_count, sum(amount) AS total
FROM orders_loaded;
```

```output
row_hash | row_count | total
29ce32b62ddbf37dd30dffca0d205750 | 3 | 57.40
```

### Example 5: Step 5, SQL validation queries

The table here was loaded without constraints, as `to_sql` would leave it, and contains planted defects: a duplicated key, a missing amount, a negative amount, an unknown customer, a date outside January and a bad status. Each `SELECT` counts the rows that break one rule, and `UNION ALL` stacks them into one report that should read zero on a healthy table. The orphan check is the anti-join: `LEFT JOIN` to the parent and keep rows where the parent key is NULL.

```sql run
CREATE TABLE customer (customer_id int);
INSERT INTO customer VALUES (1), (2), (3);
CREATE TABLE orders_loaded (order_id int, customer_id int, order_date date, amount numeric(12,2), status text);
INSERT INTO orders_loaded VALUES
  (1001, 1, '2026-01-05', 19.90, 'paid'),
  (1002, 2, '2026-01-06', 25.00, 'paid'),
  (1002, 2, '2026-01-06', 25.00, 'paid'),
  (1003, 1, '2026-01-06', NULL, 'new'),
  (1004, 3, '2026-01-07', -40.00, 'shipped'),
  (1006, 9, '2026-01-08', 15.00, 'paid'),
  (1009, 1, '2026-03-09', 31.25, 'cancelled'),
  (1014, 2, '2026-01-12', 6.00, 'pending');
SELECT check_name, violations FROM (
  SELECT 'duplicate order_id' AS check_name, count(*) AS violations
    FROM (SELECT order_id FROM orders_loaded GROUP BY order_id HAVING count(*) > 1) d
  UNION ALL SELECT 'missing amount', count(*) FROM orders_loaded WHERE amount IS NULL
  UNION ALL SELECT 'negative amount', count(*) FROM orders_loaded WHERE amount < 0
  UNION ALL SELECT 'orphan customer', count(*) FROM orders_loaded o
    LEFT JOIN customer c ON c.customer_id = o.customer_id WHERE c.customer_id IS NULL
  UNION ALL SELECT 'date outside January', count(*) FROM orders_loaded
    WHERE order_date NOT BETWEEN '2026-01-01' AND '2026-01-31'
  UNION ALL SELECT 'bad status', count(*) FROM orders_loaded
    WHERE status NOT IN ('new', 'paid', 'shipped', 'cancelled')
) checks
ORDER BY check_name;
```

```output
check_name | violations
bad status | 1
date outside January | 1
duplicate order_id | 1
missing amount | 1
negative amount | 1
orphan customer | 1
```

### Example 6: The assembled report

All three layers are combined into one function that returns a list of `(check, status)` pairs, run against the table the pipeline of Example 1 produces and then against a copy with one row deleted and one amount edited. The report names the failing checks, which is what an on-call engineer needs to see.

```python run
import hashlib
import sqlite3
from decimal import Decimal

file_rows = [(1001, "19.90"), (1002, "25.00"), (1003, "12.50"), (1004, "40.00"), (1009, "31.25"), (1010, "8.40"), (1013, "17.80")]
expected = {"read": 14, "rejected": 7, "rows": file_rows}

def digest(rows):
    return hashlib.md5(",".join(f"{i}|{a}" for i, a in sorted(rows)).encode()).hexdigest()

def validate_load(conn, expected):
    rows = [(i, f"{Decimal(c) / 100:.2f}") for i, c in conn.execute("SELECT order_id, amount_cents FROM orders_loaded")]
    return [
        ("reconcile", "PASS" if expected["read"] == len(rows) + expected["rejected"] else "FAIL"),
        ("control total", "PASS" if sum(Decimal(a) for _, a in rows) == sum(Decimal(a) for _, a in expected["rows"]) else "FAIL"),
        ("row hash", "PASS" if digest(rows) == digest(expected["rows"]) else "FAIL"),
    ]

def build(rows):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE orders_loaded (order_id INTEGER PRIMARY KEY, amount_cents INTEGER)")
    conn.executemany("INSERT INTO orders_loaded VALUES (?, ?)", [(i, int(Decimal(a) * 100)) for i, a in rows])
    return conn

good = build(file_rows)
print(validate_load(good, expected))

bad = build(file_rows)
with bad:
    bad.execute("DELETE FROM orders_loaded WHERE order_id = 1013")
    bad.execute("UPDATE orders_loaded SET amount_cents = amount_cents + 100 WHERE order_id = 1010")
print(validate_load(bad, expected))
```

```output
[('reconcile', 'PASS'), ('control total', 'PASS'), ('row hash', 'PASS')]
[('reconcile', 'FAIL'), ('control total', 'FAIL'), ('row hash', 'FAIL')]
```

## Real-world applications

- **Sign-off on a migration.** When a table is moved from an old system, the reconciliation and a control total (Examples 2 and 3) are the evidence that nothing was lost, and they are attached to the change record.
- **Automatic post-load checks.** The SQL report of Example 5 runs after every nightly load, and the scheduler marks the run failed when any count is above zero, before a dashboard refreshes on bad data.
- **Finding silent corruption.** A rounding change or a swapped column keeps counts and sums plausible; the row hash of Examples 3 and 4 catches it, and per-group counts then locate it.
- **Handover to analysts.** A written `PASS` report (Example 6) tells analysts which tables can be trusted and how, which makes the pipeline something other people can rely on without reading its code.

## Daily review

### Key takeaways

- A load that raises no error is not proof of a correct load; validate against the source with independent checks.
- Reconcile counts first: read = loaded + rejected, with the loaded count taken from the table itself.
- Use exact decimals for control totals, and a row hash for what a sum cannot see (swapped or changed values); both sides must format values identically.
- Validation queries count rule breakers (duplicates, nulls, ranges, orphans); healthy means all zero.
- Test the checks by corrupting a copy of the data and confirming that the right check fails.

### Common mistakes

- Taking the loaded count from a counter in the loader instead of `SELECT COUNT(*)` on the table, so a bug cancels itself out.
- Comparing float sums with `==`, which fails on `0.30000000000000004` style differences. Use `Decimal` or `numeric`.
- Hashing rows in different orders or formats on the two sides (`19.9` against `19.90`), so a correct load reports a mismatch. Sort by key and format identically.
- Stopping at the count check, so swapped or changed values pass unnoticed.
- Writing a validation that cannot fail, for example one that checks a constraint the table already enforces and is never tested against bad data.
- Hiding the failing check in one overall `FAIL`; report each check with its numbers.

### Revision notes

- `read == loaded + rejected`; loaded from `SELECT COUNT(*)`.
- Control total with `Decimal`; hash with `hashlib.md5(text.encode()).hexdigest()` or `md5(string_agg(... ORDER BY key))`.
- Validation: duplicates `GROUP BY ... HAVING count(*) > 1`, nulls `IS NULL`, ranges `NOT BETWEEN`, orphans `LEFT JOIN ... IS NULL`.
- A sum cannot see a swap; a hash can; a hash cannot say where.

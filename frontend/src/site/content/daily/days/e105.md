## Objectives

- Explain the difference between authentication and authorization, and between a 401 and a 403 response.
- Send credentials three ways (API key header, bearer token, token obtained from an OAuth token endpoint) and explain the trade-offs.
- Describe the OAuth 2.0 client-credentials flow in steps and say what the access token, its expiry and its scope mean for a pipeline.
- Keep secrets out of code, logs and URLs by reading them from environment variables and masking them when printed.
- Write a token provider that caches a token, refreshes it before it expires and retries exactly once after a 401.

## Understand

### Two questions the server asks

Every protected API answers two questions about each request. **Authentication** asks who you are: the server checks the credential you sent and either recognises the caller or does not. **Authorization** asks what you are allowed to do: a recognised caller may still be refused, for example because a key that can read orders cannot delete them. The status codes follow the same split: `401` means the credential was missing, wrong or expired (authentication failed), and `403` means the server knows who you are and refuses (authorization failed). A pipeline reacts differently. A `401` often has a fix inside the pipeline (refresh the token), while a `403` needs a person to change permissions.

### API keys

An **API key** is a long random string that the provider issues to one account or application. The client sends it on every request, usually in a header; the Orders API uses `X-Api-Key: <key>`. It is the simplest scheme, and it fits server-to-server pipelines. Its weaknesses are practical: the key does not expire by itself, anyone who copies it can use it, and it often carries the full permissions of the account. Some APIs accept the key as a query parameter (`?api_key=...`). Avoid that if the choice exists: URLs are written to server logs, proxy logs, browser history and error messages, and so a key in the URL is a key in many places.

### Bearer tokens

A **bearer token** is a credential sent as `Authorization: Bearer <token>`. "Bearer" means that whoever holds (bears) the token is treated as the owner, so it must be protected like a password. Tokens differ from API keys in lifetime: they are usually **short-lived** (minutes or hours) and are obtained from the provider's token endpoint. A token is opaque to the client: you do not need to read it, only to send it, and to know when it expires. Some tokens are **JWTs** (JSON Web Tokens) that carry readable claims, but the client still treats them as an opaque string.

### OAuth 2.0 in one page

**OAuth 2.0** is the standard way to hand out tokens. It names four roles: the **resource owner** (the person or organisation whose data it is), the **client** (your application), the **authorization server** (issues tokens) and the **resource server** (the API holding the data). It defines several **grants**, which are procedures for getting a token. For a data pipeline running without a person, the relevant grant is **client credentials**. In it, the client has an id and a secret issued in advance; it sends them to the token endpoint (`POST /token` with `grant_type=client_credentials`, `client_id` and `client_secret`), and receives JSON such as `{"access_token": "...", "token_type": "Bearer", "expires_in": 3600}`. The client sends the access token as a bearer token until it expires, then asks again. The other common grant, **authorization code**, involves a person approving access in a browser and is used when an application acts for a user; it is mentioned here so that you recognise it in a provider's documentation, and not practised. A **scope** is a named permission such as `orders:read`. Ask for the narrowest scope that does the job.

### Keeping secrets safe

A secret in the source code is a secret in the repository, in every clone, and for ever in its history. The rules are short. **Read secrets from the environment** at start-up (`os.environ["ORDERS_API_KEY"]`), so the code holds names, not values; locally a `.env` file that is listed in `.gitignore` can fill the environment; in production a scheduler or a secret manager injects them. **Never log or print a secret**, and take care with indirect leaks: an exception message or a `repr` of a request can contain a header, and a URL with the key in the query contains it. **Mask** a value when you must show that it is present, for example the last two characters. **Use separate keys** for development and production, give each the least permissions it needs, and **rotate** them: when a key leaks, the response is to revoke it at the provider, not to hope. Failing early with a clear message (`missing environment variable ORDERS_API_KEY`) is part of the design: a pipeline that starts without its secret and fails on the first call produces an error far from the cause.

### Refreshing tokens

A token provider keeps the current token and its expiry time. Before each call it checks whether the token is still valid with a **safety margin** (refresh when less than a minute remains, so that a call in flight does not meet an expired token). When a call returns `401` anyway, because the server revoked the token or the clocks differ, the client refreshes the token and repeats the call **once**. A second `401` means the credentials themselves are wrong and the pipeline must stop with a clear error; repeating forever would hammer the token endpoint and could lock the account.

### Common misconception

Learners believe that a secret is safe because the repository is private, or because the code is only run on their machine. Repositories are cloned, forked and leaked, and a secret that has been committed must be treated as exposed. Another belief is that `401` and `403` are the same problem. They send you to different people: the key owner and the permission administrator.

### Why it matters

An expired token at 03:00 on a Sunday should refresh itself and not fail the nightly load, and a leaked key in a log file should never happen. Both are decided by small design choices made once, in the client.

## Syntax and key functions

```python
import os
import requests

api_key = os.environ["ORDERS_API_KEY"]                       # KeyError names the missing variable
headers = {"X-Api-Key": api_key}                             # API key
headers = {"Authorization": f"Bearer {token}"}               # bearer token

token_response = requests.post(
    "https://auth.shop.example/token",
    data={"grant_type": "client_credentials", "client_id": client_id, "client_secret": client_secret},
    timeout=10,
)
token = token_response.json()["access_token"]
```

| Item | What it does or returns |
|---|---|
| `os.environ["NAME"]` / `os.environ.get("NAME")` | Required secret (raises `KeyError`) / optional value (`None` if absent). |
| `X-Api-Key: <key>` | API key header (the name varies by provider). |
| `Authorization: Bearer <token>` | Bearer token header. |
| `POST /token` with `grant_type=client_credentials` | Token request; returns `access_token`, `token_type`, `expires_in`. |
| `expires_in` | Lifetime of the token in seconds. |
| `401` / `403` | Not authenticated / not authorized. |
| `requests.post(url, data={...})` | Form-encoded body, as token endpoints expect (not `json=`). |
| `.gitignore` entry for `.env` | Keeps a local secrets file out of the repository. |

## Learn by example

### Example 1: Secrets from the environment, and masking (browser-safe)

`get_secret` reads a required value from a mapping that stands in for `os.environ`, and fails with a message that names the variable and never contains a value. `mask` shows only the last two characters. `safe_url` removes a key that was put in the query string, which is what you would apply before logging a URL.

```python run
import re

def get_secret(env, name):
    try:
        return env[name]
    except KeyError:
        raise RuntimeError(f"missing environment variable {name}") from None

def mask(secret):
    return "*" * max(len(secret) - 2, 0) + secret[-2:]

def safe_url(url):
    return re.sub(r"(api_key=)[^&]+", r"\1***", url)

env = {"ORDERS_API_KEY": "demo-key-123"}
key = get_secret(env, "ORDERS_API_KEY")
print(mask(key), len(key))
try:
    get_secret(env, "ORDERS_CLIENT_SECRET")
except RuntimeError as err:
    print(err)
print(safe_url("https://api.shop.example/orders?page=2&api_key=demo-key-123&page_size=50"))
print({"X-Api-Key": mask(key)})
```

```output
**********23 12
missing environment variable ORDERS_CLIENT_SECRET
https://api.shop.example/orders?page=2&api_key=***&page_size=50
{'X-Api-Key': '**********23'}
```

A log line that contains `mask(key)` still proves that a key was loaded. The failing lookup shows the variable name only.

### Example 2: Three credentials against a stand-in, and 401 versus 403

The stand-in accepts an API key or a bearer token, and a read-only token is refused when it tries to delete. The code prints the status for each combination, so that the difference between "who are you" and "you may not" is visible.

```python run
KEYS = {"demo-key-123": {"read", "write"}}
TOKENS = {"tok-read": {"read"}, "tok-admin": {"read", "write"}}

def api(method, headers):
    credential = None
    if "X-Api-Key" in headers:
        credential = KEYS.get(headers["X-Api-Key"])
    elif headers.get("Authorization", "").startswith("Bearer "):
        credential = TOKENS.get(headers["Authorization"][7:])
    if credential is None:
        return 401
    needed = "read" if method == "GET" else "write"
    return 200 if needed in credential else 403

cases = [
    ("GET", {}),
    ("GET", {"X-Api-Key": "wrong"}),
    ("GET", {"X-Api-Key": "demo-key-123"}),
    ("GET", {"Authorization": "Bearer tok-read"}),
    ("DELETE", {"Authorization": "Bearer tok-read"}),
    ("DELETE", {"Authorization": "Bearer tok-admin"}),
]
for method, headers in cases:
    print(method, list(headers) or "no credential", api(method, headers))
```

```output
GET no credential 401
GET ['X-Api-Key'] 401
GET ['X-Api-Key'] 200
GET ['Authorization'] 200
DELETE ['Authorization'] 403
DELETE ['Authorization'] 200
```

The read-only token is recognised, so `GET` works, but `DELETE` is refused with `403`, not `401`.

### Example 3: A token provider with expiry, a margin and one retry

The provider asks a fake token endpoint for a token, remembers its expiry, refreshes when less than 60 seconds remain, and exposes `call(do_request)`, which repeats a request once after a `401`. A fake clock keeps the output fast and exact. The server revokes the first token early to force the `401` path.

```python run
class FakeAuthServer:
    def __init__(self):
        self.issued = 0
        self.revoked = set()
        self.reject_all = False

    def token(self):
        self.issued += 1
        return {"access_token": f"tok-{self.issued}", "expires_in": 3600}

class TokenProvider:
    def __init__(self, server, clock, margin=60):
        self.server, self.clock, self.margin = server, clock, margin
        self.token, self.expires_at = None, 0

    def get(self):
        if self.token is None or self.clock() >= self.expires_at - self.margin:
            reply = self.server.token()
            self.token, self.expires_at = reply["access_token"], self.clock() + reply["expires_in"]
        return self.token

    def call(self, do_request):
        status = do_request(self.get())
        if status == 401:
            self.token = None
            status = do_request(self.get())
        return status

now = [0]
server = FakeAuthServer()
provider = TokenProvider(server, clock=lambda: now[0])

def request(token):
    return 401 if server.reject_all or token in server.revoked else 200

print(provider.call(request), server.issued)
now[0] = 1000
print(provider.call(request), server.issued)
now[0] = 3550
print(provider.call(request), server.issued)
server.revoked.add(provider.token)
print(provider.call(request), server.issued)
server.reject_all = True
print(provider.call(request), server.issued)
```

```output
200 1
200 1
200 2
200 3
401 4
```

At time 3550 only 50 seconds of the first token remain, which is below the margin, so a new token is fetched before the call. The revoked token gives one `401`, one refresh and success (three tokens issued so far, and a fourth is requested in the last case). In the last case the server rejects every token: the fresh token is also refused, and the second `401` is returned to the caller instead of looping.

### Example 4: Client credentials against a real local server

This local example runs a small server with a token endpoint and a protected `/orders` route. Each token works for two calls, then the server answers `401`. The client reads the id and the secret from environment variables (set inside the script only for the demonstration), requests a token with form data, calls the API, and recovers from the expiry with the provider's one-retry rule. The log never shows the secret or the full token.

```python local
import json
import os
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import parse_qs

import requests

os.environ["ORDERS_CLIENT_ID"] = "etl-job"
os.environ["ORDERS_CLIENT_SECRET"] = "s3cret-value"

state = {"issued": 0, "left": {}}

class Handler(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def reply(self, status, body):
        data = json.dumps(body).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_POST(self):
        form = parse_qs(self.rfile.read(int(self.headers["Content-Length"])).decode())
        ok = (self.path == "/token" and form.get("grant_type") == ["client_credentials"]
              and form.get("client_id") == ["etl-job"] and form.get("client_secret") == ["s3cret-value"])
        if not ok:
            return self.reply(401, {"error": "invalid_client"})
        state["issued"] += 1
        token = f"tok-{state['issued']}"
        state["left"][token] = 2
        self.reply(200, {"access_token": token, "token_type": "Bearer", "expires_in": 3600})

    def do_GET(self):
        header = self.headers.get("Authorization", "")
        token = header[7:] if header.startswith("Bearer ") else ""
        if state["left"].get(token, 0) <= 0:
            return self.reply(401, {"error": "invalid or expired token"})
        state["left"][token] -= 1
        self.reply(200, {"data": [{"order_id": 1}], "page": 1, "total_pages": 1})

server = HTTPServer(("127.0.0.1", 0), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()
base = f"http://127.0.0.1:{server.server_port}"

def mask(secret):
    return "*" * (len(secret) - 2) + secret[-2:]

class Provider:
    def __init__(self):
        self.client_id = os.environ["ORDERS_CLIENT_ID"]
        self.client_secret = os.environ["ORDERS_CLIENT_SECRET"]
        self.token = None

    def get(self):
        if self.token is None:
            r = requests.post(base + "/token", data={"grant_type": "client_credentials", "client_id": self.client_id,
                                                     "client_secret": self.client_secret}, timeout=5)
            r.raise_for_status()
            self.token = r.json()["access_token"]
            print("new token", mask(self.token))
        return self.token

    def get_orders(self):
        for attempt in (1, 2):
            r = requests.get(base + "/orders", headers={"Authorization": f"Bearer {self.get()}"}, timeout=5)
            if r.status_code != 401:
                return r
            print("401, refreshing")
            self.token = None
        return r

try:
    provider = Provider()
    for i in range(1, 5):
        print(i, provider.get_orders().status_code)
    bad = requests.post(base + "/token", data={"grant_type": "client_credentials", "client_id": "x", "client_secret": "y"}, timeout=5)
    print(bad.status_code, bad.json())
finally:
    server.shutdown()
    server.server_close()
```

```output
new token ***-1
1 200
2 200
401, refreshing
new token ***-2
3 200
4 200
401 {'error': 'invalid_client'}
```

## Real-world applications

- **Nightly payment export.** The job reads the client id and secret from the scheduler's secret store, gets a token, and refreshes it when it expires part-way through a long run.
- **Leak response.** When a key appears in a log, the engineer revokes it at the provider and issues a new one; code that only reads from the environment needs no change.
- **Least privilege.** A read-only scope for the ingestion job means that a leaked credential cannot delete orders; a `403` in a test proves the limit works.
- **Safe logs.** Masked values and redacted URLs let support share logs with the provider without exposing secrets.

## Daily review

### Key takeaways

- Authentication is who you are (401); authorization is what you may do (403).
- API keys are static and simple; bearer tokens are short-lived and obtained from a token endpoint.
- OAuth client credentials: id and secret to the token endpoint, access token with `expires_in` back, sent as a bearer token.
- Secrets come from the environment, never from code, URLs or logs; mask and rotate.
- Refresh before expiry with a margin, retry once after a 401, then stop.

### Common mistakes

- **Hard-coding a key "just for now".** It enters the repository history. Read it from the environment from the first day.
- **Key in the query string.** It appears in logs. Send it in a header.
- **Retrying a 401 in a loop.** If the second attempt fails the credentials are wrong; stop with a clear error.
- **Printing the whole request for debugging.** Headers carry the secret. Print the method, URL without secrets and status.
- **Treating 403 as an expired token.** Refreshing does not help; the permission must change.

### Revision notes

- 401 = not authenticated, 403 = not authorized.
- Headers: `X-Api-Key`, `Authorization: Bearer`.
- Client credentials: `POST /token` form data, response `access_token`, `expires_in`.
- `os.environ["NAME"]`, `.env` in `.gitignore`, mask, rotate, least privilege.
- Refresh with a margin; one retry on 401.

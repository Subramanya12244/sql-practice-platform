## Introduction

`RIGHT JOIN` is the mirror image of `LEFT JOIN`: it keeps every row of the table written on the right.

## Definition

`A RIGHT [OUTER] JOIN B ON condition` returns all matched pairs plus every row of `B` with no match, with NULLs in `A`'s columns. It equals `B LEFT JOIN A ON condition` (column order aside).

## Why it matters

You will read it in existing code and interviewers ask you to convert between the two forms. Most style guides prefer `LEFT JOIN` because "keep everything from the first table" reads naturally.

## How it works

Same as a left join with the sides swapped: inner matches first, then unmatched right rows padded with NULLs.

## Syntax

```sql-syntax
SELECT a.col, b.col
FROM table_a a
RIGHT [OUTER] JOIN table_b b ON b.a_id = a.id;

-- equivalent
SELECT a.col, b.col
FROM table_b b
LEFT JOIN table_a a ON b.a_id = a.id;
```

## Simple examples

Every customer, with their orders if any (customers is the right table):

```sql
SELECT c.customer_id, o.order_id
FROM orders o
RIGHT JOIN customers c ON c.customer_id = o.customer_id
ORDER BY o.order_id NULLS FIRST, c.customer_id
LIMIT 5;
```

## Intermediate examples

Order count per employee, keeping employees with no orders:

```sql
SELECT e.employee_id, e.first_name || ' ' || e.last_name AS employee,
       COUNT(o.order_id) AS orders
FROM orders o
RIGHT JOIN employees e ON e.employee_id = o.employee_id
GROUP BY e.employee_id, employee
ORDER BY orders, e.employee_id;
```

Units sold per product, zero-filled:

```sql
SELECT p.product_id, COALESCE(SUM(od.quantity), 0) AS units_sold
FROM order_details od
RIGHT JOIN products p ON p.product_id = od.product_id
GROUP BY p.product_id
ORDER BY units_sold, p.product_id
LIMIT 5;
```

## Advanced examples

Chained right joins: each step preserves the newly added table. To keep all customers in a revenue report, the customers table must be the last right side:

```sql
SELECT c.customer_id,
       ROUND(COALESCE(SUM(od.unit_price * od.quantity * (1 - od.discount)), 0)::numeric, 2) AS revenue
FROM order_details od
RIGHT JOIN orders o    ON o.order_id = od.order_id
RIGHT JOIN customers c ON c.customer_id = o.customer_id
GROUP BY c.customer_id
ORDER BY revenue, c.customer_id
LIMIT 5;
```

## Real-world scenarios

- Appending a "keep all" lookup table at the end of a long existing join chain without reordering it.
- Code generated by BI tools.

## PostgreSQL specifics

- PostgreSQL usually plans a right join as a hash join with the inputs swapped; performance equals the left-join form.
- `RIGHT JOIN` and `RIGHT OUTER JOIN` are identical.

## Visual explanation

```text
orders o  RIGHT JOIN  customers c
   matched rows      +  customers with no order (o.* = NULL)

= customers c LEFT JOIN orders o
```

## Common mistakes

- Mixing `LEFT` and `RIGHT` joins in one query, which makes the preserved table hard to see.
- Filtering the left table in `WHERE`, which removes the NULL-padded rows (the mirror of the left-join trap).
- Assuming `RIGHT JOIN` returns something `LEFT JOIN` cannot.

## Performance

Identical to the equivalent `LEFT JOIN`. Index the join keys.

## Interview questions

### Can every RIGHT JOIN be rewritten as a LEFT JOIN?

Yes. Swap the table order and change `RIGHT` to `LEFT`.

### Why do teams avoid RIGHT JOIN?

Readability: queries read top to bottom from the main table. Mixing directions confuses which rows are preserved.

### In a RIGHT JOIN, which table's columns can be NULL?

The left table's columns, for rows of the right table without a match.

## Quick revision

- Keeps every row of the right table.
- `A RIGHT JOIN B` = `B LEFT JOIN A`.
- Prefer `LEFT JOIN` for readability.
- Filters on the non-preserved side belong in `ON`.
